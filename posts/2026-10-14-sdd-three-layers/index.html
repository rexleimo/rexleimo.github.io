「spec 驱动开发」火了，但 90% 的人停在了第一层

spec-driven development 最近火到 GitHub 上一个工具包就 130K 星、AWS 拿它三周做了个 drug discovery agent。但这个词的定义还没定下来，第三方实测下来，市面上能找到的都停在最浅的一层——spec 用完就删。我把它的三个层级、模板到底怎么约束 LLM、以及「审 markdown 真的比审代码轻吗」这个反直觉问题，一次讲透。

October 14, 2026 · 2 min · 295 words · 梦兽编程 -  | 

「spec-driven development」（SDD，规格驱动开发）这个词，最近热得有点虚。

热到什么程度：GitHub 上一个开源工具包 spec-kit，仓库自己挂出来的数字是 ~130K 星、270+ 贡献者、38 个 coding agent 集成（Copilot / Gemini / Codex / Claude / Kiro……）；AWS 的 Kiro 拿这套方法，官方发了一篇案例，说三周做了一个 drug discovery agent。

但我把市面上自诩「SDD」的工具翻完，加上第三方做的一次横评，最扎心的发现是：它们基本都停在了第一层，而第一层的 spec，往往用完就删了。

这篇讲三件事：这个词到底分几层、模板凭什么能约束住 LLM、以及那个反直觉的问题——审 markdown 真比审代码轻松吗。

先说清：SDD 不是一层，是三层#

「spec-driven」这四个字，到现在没有统一定义。第三方（martinfowler.com 上做工具横评的那位）把它按「spec 用完之后怎么办」切成了三层，这个切法目前最能自洽：

层级关键动作spec 的寿命
Spec-first先写 spec 驱动开发，任务完 spec 可能就删了短，一次性
Spec-anchoredspec 留着，后续演化/维护继续拿它当锚中，跟着 feature 走
Spec-as-sourcespec 是长期主文件，人只改 spec、不碰 code长，spec 就是真相

三层是递进的（as-source 建立在 anchored 上，anchored 建立在 first 上）。横评作者的实测结论很直接：他试过的工具，全都停在 spec-first；没有一个真的做到 spec-anchored，更别提 spec-as-source。 而「spec 之后怎么维护」这个问题，各家文档里普遍是含糊的。

所以「90% 的人停在了第一层」不是耸人听闻——是目前市面上能找到的，就没人往下走。

模板凭什么能约束住 LLM#

这一层最容易被忽略，但它是 SDD 真正有价值的部分。

Spec Kit 的做法：它的模板被作者原话叫「sophisticated prompts（精巧的提示词）」。规则很具体：

  • ✅ 让 LLM 聚焦 WHAT（用户要什么）和 WHY（为什么）
  • ❌ 禁写 HOW——不许出现 tech stack、API、code 结构

为什么这么卡？因为 spec 一旦漏进实现细节就废了。举它的例子：LLM 自然想写「用 React + Redux 实现」，模板把它摁回「用户需要实时看到数据更新」。前者把 spec 焊死在某个技术栈上，后者让 spec 保持稳定——换实现时 spec 一行不用改。

再叠一层：每个架构决策都要 trace 回某条 requirement，spec 里的每个 task 都挂到需求编号上。这是把「意图」和「代码」之间架了条可追溯的线，而不是拍脑袋。

这套约束，本质是给「AI 输出的文档」加了一道抽象层闸门：spec 只能停在「要什么」，不许滑到「怎么实现」。闸门在，spec 才稳；闸门一松，spec 就变成了 detailed prompt。

那个反直觉问题：审 markdown 真的比审 code 轻吗#

这是横评里最值钱、也最没被回答好的一个质疑。

SDD 的卖点常被讲成「你审 markdown，别审 code，轻松多了」。但第三方作者点出两件事：

  1. 「审 markdown over 审 code？」 他自己试用下来，Kiro 只给 3 个文件（requirements / design / tasks），心智模型「比 code 直观」——但他没说这是好事还是省事，只说更直观。
  2. Verschlimmbesserung（德语，意思是「为了修好反而弄糟」）：他的原话——「越是生成一堆文件的精致方案，我越担心它在放大 review 过载和幻觉，越修越糟。」

翻译成大白话：SDD 没让「审」这件事变轻，它可能让「审的东西」变多了。你从审一个 diff，变成审 requirements + design + tasks 三份文档，还要保证三份之间不自相矛盾——这不叫减负，这叫换了个地方堆活。

再加上一个词法层面的漂移：「spec-driven」已经开始 semantic diffusion（语义扩散）——已经有人把 spec 直接当「detailed prompt（详细提示词）」的同义词在用。当 spec 可以被理解成「一段更长的 prompt」，那 SDD 和「写个很长的 prompt」就只剩体面区别了。

三条边界，得写清楚#

  • brownfield 成本高：把这些工具引进一个已有代码库，第三方明确说「比 greenfield 费更多事」；他对「在真实代码库里用了一段之后值不值」，坦承「还有大量没答案的问题」。
  • 长期维护策略含糊：三层里只有第一层是「有」的，后两层「没看到谁真做到」。spec-as-source 现在停在概念。
  • 数字口径：spec-kit 的 130K 星 / 38 集成是仓库 self-report；Kiro 的「三周 drug discovery agent」是 AWS 官方案例自述——这两条我没独立核验，当「厂商/仓库口径」读，别当第三方实测。

那到底该不该用#

我的判断，落在第一层：

  • 对一个边界清晰的任务，先写 spec 再喂 AI，是省事的——它逼你在动手前把「要什么」想清楚，闸门也能挡住 LLM 滑进实现细节。spec-first 这层，真实有价值。
  • 但别往两层以上寄期望：spec-anchored / spec-as-source 现在没人真做到，你照着做大概率是「spec 写完就吃灰」。
  • 最大的坑是认知漂移：把 spec 当成「更长的 prompt」，那 SDD 就名存实亡了。spec 的价值在抽象层闸门，不在篇幅。

你是哪一层？评论区对一下：

  • A 派：只做 spec-first，spec 用完就删，不碰「长期维护」那个坑；
  • B 派：冲 spec-anchored，spec 跟着 feature 走，真信「spec 是资产」；
  • C 派：先别做，等语义扩散收敛、等有人真把 spec-as-source 落地再上。

你团队里 spec 现在写到哪一层？攒够一批我出续篇：把 spec-kit 的 specify 命令跑一遍，实测它的「抽象层闸门」到底卡不卡得住 LLM 写 HOW。

常见问题

spec-driven development 到底分几层？

第三方（martinfowler.com 的工具横评）把它拆成三层：spec-first（先写 spec 驱动开发，任务完 spec 可能删掉）、spec-anchored（spec 留着，后续演化继续用）、spec-as-source（spec 是长期主文件，人只改 spec 不碰 code）。作者实测：市面上找到的基本都停在第一层。

Spec Kit / Kiro 是什么？

Spec Kit 是 GitHub 开源的 SDD 工具包（仓库 self-report ~130K 星、38 个 agent 集成），核心流程 specify→plan→tasks→implement→converge。Kiro 是 AWS 的 AI IDE，产出 requirements/design/tasks 三个 Markdown，官方案例三周做了个 drug discovery agent。

模板怎么约束 LLM？

Spec Kit 的模板被当「sophisticated prompts」用：逼 LLM 只写 WHAT/WHY（用户要什么），禁写 HOW（不许出现 tech stack / API / code 结构），从而把 spec 锁定在抽象层——这样实现技术换了 spec 不用改。

审 markdown 真的比审 code 轻松吗？

这是没被回答好的问题。第三方作者说 Kiro 只有 3 个文件、心智模型更直观，但没下结论；他真正担心的是「越精致的方案生成一堆文件，可能放大 review 过载和幻觉（Verschlimmbesserung，越修越糟）」。审 markdown 未必比审 code 轻。

现在该不该用？

spec-first 这层在有清晰边界的任务上是有价值的；但别指望它到 spec-as-source。brownfield（已有代码库）成本高、spec 长期维护策略普遍含糊、甚至已经有人把 spec 当成 detailed prompt 的同义词——这是它最大的风险。
