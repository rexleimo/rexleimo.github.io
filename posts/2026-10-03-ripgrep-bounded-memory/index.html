Rust 写 CLI 工具为什么爽：ripgrep 10MB 内存查完 100GB，秘密不是「Rust 魔法」

ripgrep 能查 100GB 数据不爆内存？秘密不是 Rust 快，是「内存有界 + 流式固定缓冲」这个工程决策。我在 2 核机器上用 256MB/1GB/4GB 三档语料实测坐实：数据量涨 16 倍，RSS 纹丝不动（7MB 封顶），换一个「全部读进内存」的实现就跟着涨到 4GB。全代码开源可复现。

October 3, 2026 · 4 min · 745 words · 梦兽编程 -  |  English

100GB 这个数字，BurntSushi 官方其实没写过——他博客里最大的单文件基准是 13GB 字幕，多文件是 Linux 内核源码树。但我自己造了 256MB/1GB/4GB 三档语料在这台 2 核机器上跑了一遍：数据量涨 16 倍，ripgrep 的内存纹丝不动（7MB 封顶），换一个"全部读进内存"的实现就跟着涨到 4GB。秘密不是 Rust 快，是内存有界 + 流式固定缓冲——一个不写 Rust 的人也能抄走的工程决策。

先给结论：那 100GB，我自己查不到出处#

写这篇之前我翻了两遍 BurntSushi 的 ripgrep 博客和 README，想找"10MB 查 100GB"这句话——没找到。他 2016 年那篇详细对比里，最大的单文件基准是 13GB 的 OpenSubtitles 字幕，多文件基准是 Linux 内核源码树。100GB 是后来在传播中被放大的营销梗，连作者都没说过。

但"内存不随数据量增长"这个原理，他博客里写得清清楚楚（“Thou Shalt Not Search Line By Line”），而且能用最小实验复现。我选这条路：不背那个数字，把它拆成可验证的机制。

这篇讲几件事#

  1. 我自己造语料实测：ripgrep 的 RSS 真的不随数据量涨
  2. 对照组 B"读全部进内存"：证明这不是 Rust 红利，是有界缓冲的功劳
  3. 五个工程机制，每个能在源码/博客里查到出处
  4. 你写 CLI 该抄哪条

机器还是上一篇那台（2 核 / 7.8G Linux，Ubuntu，rg 14.1.0 用 apt 装的——GitHub 被墙，官方 release 走不通，apt 源够用）。

我做的 3 档语料：种子固定，小档是大档的前缀#

先造语料，不拿现成的：

$ rg --version
ripgrep 14.1.0

$ python3 make-corpus.py /tmp/rgbench/c256 256
generated /tmp/rgbench/c256: 3913 files, ~256MB (seed=20261003)

$ python3 make-corpus.py /tmp/rgbench/c1g 1024
generated /tmp/rgbench/c1g: 15651 files, ~1GB (seed=20261003)

$ python3 make-corpus.py /tmp/rgbench/c4g 4096
generated /tmp/rgbench/c4g: 62609 files, ~4GB (seed=20261003)

每档 1/3 文件末尾埋同一个字面量 needle_foo42。同 seed 意味着 256MB 那档是 1GB 那档的字节前缀——搜 256MB 的命中分布完全落在 1GB 分布里，没有"语料换了一版导致内存虚高"这种假变量。这是这套语料最重要的性质：数据量可加。

为什么埋字面量？因为 ripgrep 搜索字面量时走的根本不是完整正则引擎（下一节讲），这是它最快、最接近"生产 CLI 真实场景"的路径。

被测对象 + 两个对照组#

# 被测：warmup 一次（页缓存热），再测
$ rg needle_foo42 /tmp/rgbench/c256 > /dev/null   # warmup
$ /usr/bin/time -v rg needle_foo42 /tmp/rgbench/c256 2> /tmp/t.txt
$ grep -E 'Elapsed|Maximum resident' /tmp/t.txt
        0.07s    # 命中 1305 文件
       6.9MB

# 对照组 A：最朴素单线程 Python 搜索（流式，无优化）
$ /usr/bin/time -v python3 py-baseline.py /tmp/rgbench/c256 needle_foo42
        1.56s    # 命中 1305
       12.0MB

# 对照组 B：把全部文件一次读进内存再处理（反证关键）
$ /usr/bin/time -v python3 py-loadall.py /tmp/rgbench/c256
        0.22s
      274MB      # 注意：比 A 快 7 倍，但 RSS 是 A 的 23 倍

对照组 B 这段输出是关键——它把 A 在耗时上打翻 7 倍（一次性读完后查找是内存查表，比逐行 IO 快），但 RSS 也翻到 23 倍。这就是我要在 4GB 档放大的东西。

数据：rg 是条平线，对照组 B 是条 45° 斜线#

rg 的 RSS 不随数据量涨#

语料命中文件rg 默认(j2)rg 峰值 RSSrg -j1
256MB (3913 文件)13050.07s6.9 MB0.12s
1GB (15651 文件)52170.37s7.3 MB0.47s
4GB (62609 文件)2087026.3s7.8 MB64.2s

数据量 ×16（256MB→4GB），ripgrep 的峰值 RSS 6.9→7.3→7.8MB——一条平线。这是"内存有界"最直接的可复现证据，三个点全在本机重跑都能落回 7MB 附近。

耗时另一回事（4GB 那档 26s 主要是 I/O 读盘，下一节拆开）。

对照组 B「整读进内存」：跟着数据量线性涨#

语料整读 RSS整读耗时朴素流式 RSS朴素流式耗时
256MB274 MB0.22s12.0MB1.56s
1GB1.0 GB0.60s11.9MB3.69s
4GB4.0 GB1.20s12.3MB46.05s

同一组语料，两种 Python 写法：

  • 流式读（对照组 A）：RSS 稳定 12MB，耗时 1.6s→3.7s→46s（I/O 主导）。“有界但慢”。
  • 整读进内存（对照组 B）：RSS 跟着数据量走，274MB→1.0GB→4.0GB。“快但无界”。

ripgrep 占了两个好处：RSS 有界（7MB 平线）+ 不慢（4GB 26s，还比 A 快）。它凭什么？——就是下面五个机制。

一张图把"有界 vs 无界"钉死#

左图数据量 ×16，rg 的 RSS 在 7MB 附近晃；右图同一数据量，“整读进内存"的实现 RSS 跟着涨到 4GB。这就是"10MB 查 100GB"真正在说的东西：ripgrep 的内存占用和数据总量无关，所以外推到 100GB 也还是那几 MB。

把对照组 B 斜率外推到 100GB 语料：100GB 数据 → 整读需要 ~100GB 内存，而 rg 还是 7MB 上下。这是数学，不是宣传。

为什么快：五个机制，每个能在博客里查到出处#

ripgrep 的快不是"Rust 快”。这五个机制里只有一个跟语言强相关（编译期借用），剩下四个用任何语言都能抄：

① 流式固定缓冲（Mechanics 节）#

BurntSushi 博客：“Thou Shalt Not Search Line By Line… Instead, search over the contents of an in-memory byte buffer of a fixed size.”

ripgrep 不 mmap 整个文件、不读整文件进内存，用一个固定大小中间缓冲增量搜索。这就是第 3 节那条 7MB 平线的来源——缓冲有界，RSS 就有界。你写任何要吐大量数据的 CLI，第一步就是这条：永远不要把全部数据读进内存。

② mmap 反而慢（Counterintuitive 节）#

同篇 linux_literal 基准里 rg(mmap) 1.611s vs rg(ignore) 0.334s，mmap 慢 4.8 倍。反直觉对不对？——直觉里"映射不占物理内存"是优点，但多文件场景下虚拟内存页错误开销不划算，rg 直接禁用 mmap 走 IO 路径更快。数据量越大，越不能靠 mmap 救你。

③ SIMD 抽字面量（Literal optimizations 节）#

ripgrep 调 regex 库时，库自动从模式里抽字面量，用 memchr（编译成 SIMD，一次看 16 字节）先找候选，只在候选行才跑完整 regex 引擎。找 needle_foo42 这种固定串时，regex 引擎几乎完全不参与——所以字面量搜索比"通用正则"快一个数量级。这是 ripgrep 在生产场景（搜固定符号、ID、错误码）里最快的路径。

④ 有限状态机，线性时间（Regex engine 节）#

ripgrep 用 Rust regex（基于 RE2 的有限自动机），任意输入都是线性时间，没有 PCRE 那种 (a*)*c 回溯指数爆炸。博客举的例子：Silver Searcher（老的 Ruby grep）在某个嵌套量词模式上直接打崩，ripgrep 没这毛病。这是语言无关的正确性保证，跟 Rust 没直接关系，只是 Rust regex 库做得好。

⑤ lock-free work-stealing（Gathering files 节）#

ripgrep 把任务分发到 worker 池用的是 Chase-Lev 无锁队列（kinghajj/deque），其他工具（grep、老 ag）用互斥锁队列。我本机 2 核实测：-j1 强制单线程 4GB 要 64.2s，默认 2 线程 26.3s——~2.4× 收益，没有锁开销的税。这是"Rust 的红利"开始体现的地方：借用规则让你写不出 Vec::extend(整个语料) 这种"先把 100GB 读进来再处理"的灾难代码。Rust 的编译器在 ① 和 ⑤ 上的价值是编译期就拒绝你写出无界缓冲，不是"跑得比 C 快"。

一句话：快的每一分都有出处，没有一分来自"Rust 这个词"。

你写 CLI 该抄哪条#

  • 有界缓冲流式处理，永远不要先把全部数据读进内存——这是能扛 100GB 输入和只能扛 100MB 输入的分水岭，跟语言无关（①）
  • 字面量先筛，正则后验——如果你的搜索大多数是找固定串，抄 ripgrep 的 literal-skip 路径（③），收益最大
  • mmap 不是默认答案——数据大 ≠ 该映射，先看访问模式（②）
  • Rust 的价值在①⑤这类约束的编译期保证，不在"跑得快"三个字——上一篇 Rust vs Go 实测把"延迟快 3 倍"拆了，这篇把"快"的真正含义钉死在内存模型上

我踩的几个坑（诚实交代）#

Python 首跑超时，重跑快 13 倍。 4GB 那档我第一版脚本 warmup 没做，Python 单线程首跑超时 300s 还没跑完，我以为是 Python 太慢。重跑发现 46s 跑完——第一版是页缓存冷 + 没有 warmup 的复合效应。这是我在写"对照组"时最大的坑：你给被对照物跑的基线如果不公平（缓存状态不同），整个对照就无效。所以清单里我把每档 warmup 一次、页缓存热再测，且把 1GB 那档热/冷两个值都列出来了（3.69s vs 29.5s，同一语料）。

Python 整读 4GB 要 4.6GB 内存，本机差点 OOM。 7.8G 机器上我跑 4GB 语料"整读进内存"，RSS 到 4.0GB，加上 Python 解释器自身约 30-50MB，没崩但已经贴着机器内存上限。换 8GB 语料就 OOM 了。这是"整读"实现的真实代价——不只是"慢"，是"在 8GB 机器上直接没得跑"。

2 核机器看趋势不看绝对值。 rg 4GB 26s 主要 I/O 主导（4GB 读盘），不是 CPU 慢。我 2 核 -j1 64s vs 默认 26s，~2.4× 收益符合 2 核理论上限。多核机器（比如 8 核）的耗时绝对值完全不一样，但 RSS 那列（7MB 平线）不变——这才是本文要钉的东西。

诚实声明#

  • “10MB 查 100GB”未复现（本机没 100GB 语料），也查不到官方精确出处（BurntSushi 博客最大单文件基准是 13GB 字幕）；本文实测的是它的原理——内存有界（4GB 档 RSS 7.8MB 封顶），外推 100GB 是原理推论不是实测数字。
  • 2 核机器，绝对耗时不代表多核生产；4GB 档 rg 墙钟 26s 主要是 I/O 主导，不是 CPU 慢。
  • 语料是固定 seed 合成文本（随机英文词，非真实代码库）；命中分布 1/3 文件命中是刻意设计的——真实搜索命中率通常更低（对 rg 更有利），未测。
  • 复现材料全开源：bench/cli/（make-corpus.py、py-baseline.py、py-loadall.py、run-cli-bench.sh、results/numbers.md），一个命令可跑。

FAQ#

Q：为什么 rg 搜索字面量比通用正则快一个数量级？ A：ripgrep 调 regex 库时库自动抽字面量（Teddy128/Aho-Corasick），用 SIMD memchr 先找候选，只在候选行才跑完整正则引擎。找固定串时正则引擎几乎不参与，所以快一个量级。

Q：mmap 不是更快的吗？为什么 ripgrep 不默认开 mmap？ A：对搜索这种"全文件线性扫"的访问模式，mmap 的页错误开销不划算。同篇 linux_literal 基准 rg(mmap) 1.611s vs rg(ignore) 0.334s，mmap 慢 4.8 倍。

Q：2 核机器测的，多核机器结论变吗？ A：耗时会变（I/O + CPU 都变），但RSS 那列不变——7MB 平线跟核数无关。本文结论钉的是"RSS 是否随数据量涨"，不是"跑多快"。

Q：Python 流式搜索也是 12MB 平线啊，那"有界"不是语言无关吗？ A：对。“RSS 有界"这件事 Python 流式也做得到（12MB 平线）——它慢是因为没优化，不是因为有界。ripgrep 同时拿到有界 + 不慢（SIMD + 并行 + 字面量先筛），这是 ①③⑤ 三条叠出来的。

Q：100GB 到底是多少内存？我怎么自己验？ A：把本文的 make-corpus.py 跑 python3 make-corpus.py /tmp/rgbench/c100g 100*1024（生成 100GB 语料，需要 ~100G 磁盘），然后 rg needle_foo42 /tmp/rgbench/c100g，RSS 应该还是 7-8MB。本机我没法跑，但原理可验证。

常见问题

ripgrep 真能 10MB 内存查 100GB？

「10MB 查 100GB」这个精确数字我查不到官方出处（BurntSushi 博客最大单文件基准是 13GB 字幕），它是传播中的营销梗。但「内存有界」这个原理是真实的——我用 256MB/1GB/4GB 三档语料实测：rg 的 RSS 6.9→7.3→7.8MB 几乎不动，数据量 ×16 RSS 不变。外推 100GB 是原理推论，不是实测数字。

Rust 的价值在哪？不语言红利？

ripgrep 快 5 个机制里只有 1 个跟语言强相关（编译期借用规则逼你写不出「整读进内存」的灾难代码）。剩下 4 个——流式固定缓冲、mmap 反而慢、SIMD 字面量、lock-free 并行——任何语言都能抄。Rust 的价值在约束，不在「跑得快」三个字。

mmap 不是更快吗？

对搜索这种全文件线性扫模式，mmap 的页错误开销不划算。BurntSushi 同篇基准 rg(mmap) 1.611s vs rg(默认) 0.334s，mmap 慢 4.8 倍。数据量越大越不能靠 mmap 救你。

Python 流式搜索也是 12MB 平线啊？

对。「RSS 有界」Python 流式也做得到——它慢是因为没优化（4GB 46s vs rg 26s），不是因为无界。ripgrep 同时拿到有界 + 不慢（SIMD + 并行 + 字面量先筛），是 5 个机制叠出来的。

本机 2 核测的，多核结论变吗？

耗时会变（I/O + CPU 都变），但 RSS 那列（7MB 平线）不变——跟核数无关。本文结论钉的是「RSS 是否随数据量涨」，不是「跑多快」。
