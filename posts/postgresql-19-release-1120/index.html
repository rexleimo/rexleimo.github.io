PostgreSQL 19 发布：这次不是堆特性，而是把「不停机运维」做成了默认选项

PostgreSQL 19 于 2026 年 11 月 19 日正式发布。REPACK CONCURRENTLY 让大表在线瘦身不再锁库，pg_plan_advice 让慢计划可修且不用改业务代码，WAIT FOR LSN 把读写分离的读己之写做成数据库原生能力，逻辑复制不用重启、序列也能跟着复制。这是一篇面向 DBA 与后端开发的原创解读。

November 20, 2026 · 2 min · 293 words · 梦兽编程 -  |  English

2026 年 11 月 19 日，PostgreSQL 全球开发组正式发布 PostgreSQL 19。作为「世界上最先进的开源数据库」的最新大版本，PG 19 的主线很清楚：关键业务跑上规模之后，要管起来更省事、改起来不打断、查起来更可控。下面挑几处真正影响日常运维和开发的变化聊聊——是我自己的解读，不是照着发布通告抄一遍。

一、REPACK CONCURRENTLY：VACUUM FULL / CLUSTER 的时代可能要结束了#

任何一直在写入的数据库都躲不开「膨胀」（bloat）：一张频繁 UPDATE / DELETE 的表，没用的空间越堆越多，既占磁盘又拖慢查询。

过去靠 VACUUM FULL 或 CLUSTER 收拾，可这俩有个共同的毛病：独占锁表，清理期间业务读写全被挡在外面。对 7×24 的系统来说，这基本等于一次计划内停机。

PG 19 引入了 REPACK 命令：

  • 回收膨胀空间；
  • 可以按某个索引重新排列表数据（等价于 CLUSTER 的效果）；
  • 关键在于 REPACK (CONCURRENTLY)——全程不阻塞读写。

官方的说法是 REPACK 取代 VACUUM FULL 和 CLUSTER，后者为了兼容还留着。对 DBA 来说，这是这次最实用的一项：以后给大表「瘦身」，不用再挑凌晨的窗口了。

二、执行计划不再「漂移」：pg_plan_advice + pg_stash_advice#

优化器平时挺靠谱，可数据分布一变，原本好的计划说慢就慢——「昨天还好好的，今天慢查询告警」，多半就是这么来的。

PG 19 给出了一套官方的解法：

  • pg_plan_advice 扩展：提供一门「plan advice」小语言，可以固定某条查询的计划选择，也能拿来试验不同计划的效果；
  • pg_stash_advice 扩展：把 advice 存起来，并按 query identifier 自动套用到匹配的查询上。

后者更值得说：一行业务代码都不用改，就能把走歪的慢查询「掰」回正轨。执行计划的稳定性，从「靠统计信息祈祷」变成「能插手、能存下来」——这在生产环境里是块实打实的硬骨头。

三、备库「读己之写」：WAIT FOR LSN#

做了读写分离之后，这个坑几乎人人都踩过：应用在主机上写了一条，转头去备库读，主从延迟还没追上，读不到——用户以为数据丢了。

PG 19 新增 WAIT FOR LSN 命令：备库上的会话可以等到重放进度追到指定的 LSN（WAL 位置）再执行查询。也就是说，应用写完拿到 LSN，读之前先 WAIT FOR LSN，就能保证「刚写的能立刻读到」。

这是数据库层面原生给的读一致性保证，比在应用层 sleep 几百毫秒再重试靠谱得多。

四、逻辑复制的两个老麻烦，一起解决了#

1）开逻辑复制不用再重启实例。 以前开启逻辑复制往往得改 wal_level 再重启，生产环境里很麻烦。PG 19 里，你创建第一个逻辑复制槽时，自动把 effective WAL level 提升到 logical；新的 effective_wal_level 参数随时能看当前的实际级别。

2）序列（sequence）终于能跟着复制了。 用 CREATE PUBLICATION ... FOR ALL SEQUENCES 就能发布序列值，切换时再也不用手动对齐自增 ID。同时 CREATE PUBLICATION 加了 EXCEPT 子句（发 FOR ALL TABLES 时排除个别表），CREATE SUBSCRIPTION 可以用 SERVER clause 从 postgres_fdw 定义的外部服务器拿连接参数，新的 retain_dead_tuples 选项还能检测「更新与并发删除冲突」，并把冲突记进 pg_stat_subscription_stats。

五、开发者会喜欢的几个「小确幸」#

  • INSERT ... ON CONFLICT DO SELECT：RETURNING 现在能直接返回冲突的已有行，「get or create」这个高频模式省掉一次网络往返。
  • COPY 支持输出 JSON：甚至能输出成单个 JSON 数组，做数据导出、喂给下游更方便。
  • SQL/JSON path 增加字符串方法：lower()、upper()、replace()、split_part()、btrim()，处理 JSON 里的文本少写一堆嵌套函数。
  • 窗口函数支持 IGNORE NULLS：lead() / lag() / first_value() / last_value() / nth_value() 可以跳过 NULL，做「上一个非空值」这类填充逻辑简单多了。
  • random() 能生成范围内的随机日期/时间戳：造测试数据又少了一步。

六、autovacuum 与可观测性：运维的「仪表盘」更全了#

PG 19 给 autovacuum 加了并行能力：可以用 parallel worker 并行 vacuum 索引，由新参数 autovacuum_max_parallel_workers 控制；同时引入打分系统决定先处理哪些表，评分明细也能看到。

新增的监控视图包括：

  • pg_stat_lock：按锁类型的统计；
  • pg_stat_recovery：恢复状态；
  • pg_stat_autovacuum_scores：autovacuum 的表优先级打分。

EXPLAIN ANALYZE 新增 IO 选项（配套的 auto_explain 也能记录），报告异步 I/O 活动；pg_stat_wal、EXPLAIN (ANALYZE, WAL) 以及 vacuum/analyze 日志现在会统计「整页镜像」写了多少 WAL。排查 I/O 和 WAL 放大问题，终于有了一手数据。

七、性能与「默认行为」里的暗改#

有些变化不改一行 SQL 就能让程序变快：

  • 外键检查优化：测试中批量插入快了接近 2 倍；
  • 优化器增强：没有 NULL 时把 NOT IN 转成更高效的反连接（anti-join）；在 join 之前做 eager aggregation，减少参与连接的数据量；
  • 异步 I/O 自动伸缩：继 PG 18 引入异步 I/O 后，PG 19 在 io_method = worker（默认）下会自动在 io_min_workers / io_max_workers 之间调整 worker 数（这两个参数取代旧的 io_workers）；
  • LISTEN / NOTIFY 多频道场景的可扩展性也有提升。

还有几处默认值变化值得升级前重点确认：

  • JIT 默认关闭——官方说此前判断何时启用 JIT 的成本估算并不靠谱，跑大量分析型查询的同学可以手动打开；
  • 编译时带 LZ4 支持时，TOAST 默认压缩算法改为 lz4；
  • 新增 password_expiration_warning_threshold，密码快过期会提前告警；
  • 新增服务端 SNI 支持（通过 pg_hosts.conf 把不同主机名映射到不同证书）；
  • md5 认证成功后会发出弃用警告（PG 18 已弃用，未来移除，建议改 SCRAM），并移除了 RADIUS 认证。

写在最后#

如果把 PG 19 的更新浓缩成一句话：它把「在线、不中断、可干预」从少数高级玩法，变成了数据库自带的能力——给大表瘦身不用锁库（REPACK CONCURRENTLY）、慢计划能修且不用改代码（pg_plan_advice）、读写分离能读己之写（WAIT FOR LSN）、开逻辑复制不用重启。

升级前建议重点核对几处默认值变化：JIT 默认关、TOAST 压缩改 LZ4、RADIUS 认证移除、io_workers 被新参数取代。完整清单以官方 Release Notes 为准。

本文为基于官方发布公告的技术解读，具体参数和行为请以 PostgreSQL 19 官方文档（https://www.postgresql.org/docs/19/release-19.html）为准。

常见问题

PG 19 最值得 DBA 关注的变化是什么？

REPACK CONCURRENTLY：在线给大表回收膨胀空间、按索引重排数据，全程不阻塞读写，取代需要独占锁表的 VACUUM FULL 与 CLUSTER。

读写分离读到旧数据怎么解决？

新增 WAIT FOR LSN：备库会话等到重放进度追到指定 LSN 再执行查询，写完拿到 LSN、读之前先等一下，就能保证读己之写。

升级前要重点核对哪些默认值变化？

JIT 默认关闭、TOAST 默认压缩算法改为 lz4、RADIUS 认证被移除、io_workers 被 io_min_workers / io_max_workers 取代、md5 认证发出弃用警告。
