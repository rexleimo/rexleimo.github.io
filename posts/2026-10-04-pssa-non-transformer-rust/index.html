一个不用 PyTorch 的语言模型，纯 Rust 手写：生成比 transformer 快 12 倍？我差点被自己的 98 倍骗了

PSSA 是个 21MB 的仓库：选择性 SSM 循环 + 双曲记忆库 + 快速权重在线更新，无 PyTorch。作者说生成快 12 倍，正文表写 4.13 倍——我本机编译跑通，字符归一实测 9.3x，还抓到我差点踩进的 98x 假数字陷阱。梯度对账 3e-8 本机复现，全命令可复跑。

October 4, 2026 · 5 min · 1058 words · 梦兽编程 -  |  English

PSSA 是 HN 热榜上一个 21MB 的仓库：选择性 SSM 循环 + 双曲记忆库 + 快速权重在线更新，无 PyTorch 无 TensorFlow，62 个 Rust 文件。作者说它"生成文本快 12 倍"，正文表里却写 4.13 倍——两个数矛盾。我本机（AMD EPYC 9354P / rustc 1.99）把它编译跑通，实测字符归一口径 9.3x，还顺手抓到我自己差点踩进去的 98x 假数字陷阱：按名义 token 上限算吞吐，两边工作量根本不可比。梯度对账 3e-8 本机复现，全命令可复跑。

先给结论#

  1. PSSA 推理确实快，但"快 12 倍"取决于你怎么算口径。本机字符归一 9.3x；作者的 12x 是"生成 200 token"的短延迟口径，4.13x 是 19.9 万 token 批量评测口径——两个负载，两个数，不矛盾但混着看会误会。
  2. 我第一版实测算出 98.6x，是错的。PSSA 的旧 checkpoint 大量 prompt 提前撞 EOS（1024 上限只吐 107 字符），TF 退化循环吐满 1023 字符，按名义上限算 tok/s 就虚高到 98x。这坑比架构本身更有传播价值。
  3. 它最有价值的不是模型强，是工程纪律：每个 commit 的 batched kernel 都对 scalar 参考路径做梯度对账，本机 twin_check 跑通，max_grad_diff 2.98e-8——作者说的 3e-8 实锤。

架构三件套：一个 token 进 PSSA 后发生了什么#

README 把每层拆开讲得很干净（我引它原文 + 补读源码的理解），一个 token 进 PSSA 层要过四件事：

  1. 选择性 SSM 循环（selective diagonal SSM，“same family as S4 and Mamba, written out scalar-first so the backward pass can be checked term by term”）——这是主干，每 token 一次 O(d_m·d_s) 的循环状态更新，成本固定不随上下文涨。
  2. 双曲记忆库读（bounded read from an episodic memory bank in hyperbolic space）——每 token 最多读 4 个 slot（有界），这是它跟纯循环的关键差异：不是把信息硬塞进固定状态，而是维护一个能"查"的库。
  3. 学习门控（a learned gate that decides how much of that read reaches the residual stream）——读出来的记忆按门控权重注入残差流，防止记忆噪声污染主干。
  4. SiLU MLP——标准前馈。

默认配置：d_m = 256 通道、d_s = 16 状态/通道、rank-16 adapter。参数集中在循环和 adapter 上，跟同规模 transformer 比显存/内存占更小（本机 RSS 11.6MB vs 57.7MB 就是这个结构差）。

per-token 快权重：它最"激进"的一部分#

“rewrites part of its own weights while it runs”——运行中它不是固定权重往前推，而是每个 token 都在线微调自己的 fast weights（ridge 回归把本轮学到的东西巩固回基础转换矩阵）。这就是为什么它"必须"手写：

  • autograd 的 tape 是为"固定参数 + 一次 forward + 一次 backward"设计的；PSSA 每个 token 的 forward 里就改了权重，backward 得追一条变化的参数路径——“fighting the framework at every step”（作者原话）
  • 所以它把 forward/backward 直接写 Rust，保留一条 O(N) 的 scalar 参考路径做对账（twin_check 就守这条线）

代价很直白：失去 PyTorch 免费的混合精度、分布式、profiler。作者的选择是"架构定了实现语言"，不是"语言选了架构"。

这仓库是什么，为什么该看一眼#

PSSA（Plastic State-Space Architecture）= 选择性 SSM 循环（Mamba/HiPPO 那一族）+ 双曲空间 episodic memory bank（每 token 有界 4 slot 读）+ 运行中重写自身权重（ridge 回归巩固回基础矩阵）。默认 d_m=256 通道、每通道 16 个状态、rank-16 adapter。

HN 上吵得最凶的是标题：“non-transformer language model written from scratch in Rust”。评论区 21 条有料的，核心争议三派：

  • 「该用 PyTorch，不然没法判断是架构好还是实现 bug」
  • 「Rust 重写不会比 PyTorch 快多少，PyTorch 的 op 本来就是 Cython」
  • 「Rust 的意义是能直接部署，不用跟 pip 在 Windows 上死磕」

作者 README 里有一段直接回应（我引原文）：

“Not for speed points, and not because the language makes the architecture better. PSSA needed per-token weight updates, a memory bank written during the forward pass… Expressing that inside an autograd framework meant fighting the framework at every step.”

也就是说：per-token 权重更新 + forward 里写 memory bank，autograd 框架每一步都在打架，所以线性代数直接手写。这个理由我认可——但代价是自己承担了"框架免费给你的那套"（混合精度、分布式、profiler 生态）全没了。

我做了什么：编译 + 本地小训 + 双口径吞吐#

机器：AMD EPYC 9354P（Zen4，AVX-512 全开，本机 2 核切片）/ rustc 1.99.0 / 7.8G 内存。

$ git clone https://github.com/Sparticle62ops/pssa
$ cargo build --release
Finished `release` profile [optimized] target(s) in 4m 21s   # 62 个 rs 文件

仓库自带 2.2MB 旧 checkpoint（data/model.pssa，legacy V5 推理专用），但没有 transformer 对照的 checkpoint——我本地 train-transformer 50K token 训了一个（24.7MB，1.5M 参数，跟 PSSA 同参数量级）：

$ ./target/release/oxide_ai_pssa train-transformer data/downloaded.txt \
    -o data/model.trfm --max-tokens 50000 -e 1 --no-tui
✓ checkpoint written to data/model.trfm

注意：本地小训的 TF 权重质量差（50K token 没学开），但吞吐对比只比 kernel 结构不比模型质量——这正是干净的做法，我会在诚实声明里标清楚。

98x 陷阱：怎么把吞吐基准做废的#

我把第一版脚本跑出 98.6x 的时候，第一反应是"比作者 12x 还猛，稳了"。然后我打开了两边的实际输出：

  • PSSA “The quick brown fox”（上限 1024）→ 只吐了 107 字符（“information information to extract of information to extract patterns…"，撞 EOS 停了）
  • Transformer 同 prompt → 吐了 1023 字符（“the the the the…” 退化循环跑满上限）
  • 换 prompt “In a distant galaxy” → PSSA 直接 0 字符

两个模型在"干了多少活"上根本不可比：一个提前停了，一个吐到上限。按名义 1024 上限除时间，PSSA 分母虚大 10 倍。正确口径是按实际产出字符归一（chars/sec），我重算得到 9.3x。

这个坑我拆成三条可抄的纪律：

  1. 生成基准必须记录"实际产出 token/字符数”，不能只记墙钟——撞 EOS 的短输出会把 tok/s 算虚高
  2. 对照双方要锁死同一工作量（固定 N token 且两边都吐满 N，或按实际产出归一）
  3. 旧 checkpoint 的 EOS 行为是变量：PSSA 自带的是推理专用旧权重，不是作者 README 那张 12.7M token 曲线训出来的 ck64，EOS 早停是这个权重的问题

12x vs 4.13x：README 自相矛盾的裁决#

我把 README 全扫了一遍，发现两个数不是矛盾，是两个负载：

  • Line 11：generates text about twelve times quicker —— 营销句
  • Line 199-200（“And it is much faster to run"节）：4.13x = 批量评测吞吐（199,059 tokens @ 512/update：1716 vs 415 tok/s）
  • Line 213 表格：「Generating 200 tokens」226ms vs 2735ms = 12x = 短生成延迟

架构原因也成立：循环模型每 token 成本不随上下文长度增长（固定状态），transformer 每步重读整个上下文——所以生成越长，PSSA 优势越大；短生成（200 token 内）两边差距没那么夸张，批量评测（19.9 万 token）里杂了评测/词表开销，比率掉到 4x。标题写 12x、正文表写 4.13x 的观感，就是典型的"营销数字进标题、正文换口径”。我本机 9.3x（字符归一）落在两者之间，方向一致。

梯度对账：3e-8 本机复现#

作者说每个 commit 的 batched kernel 都对 scalar 参考路径做梯度对账，误差 ~3e-8。我直接跑它的 twin_check example：

$ cargo run --release --example twin_check
round 0 forward: loss=3.98721910 max_tape_diff=0.000e0
round 0 backward: max_grad_diff=2.980e-8
round 1 forward: loss=4.13920069 max_tape_diff=0.000e0
round 1 backward: max_grad_diff=5.960e-8
CPU TWIN CHECK PASSED: populated-memory/carry/adapter/MLP forward and backward

本机实锤：forward 位级一致（max_tape_diff=0.000e0），backward 最大梯度差 5.96e-8，作者"3e-8 量级"主张成立。这就是我说"它最有价值的是工程纪律"的依据——手写 ML 内核最大的坑就是 batched 路径和 reference 路径对不上还查不出来，这个仓库把对账做成了每个 commit 必跑的 CI 锚点。

生成质量：1.5M 参数，如实说#

两边都是"能出字但胡说"级别：

  • PSSA：“The quick brown fox” →「information information to extract of information to extract patterns. of information to extract patterns.」（循环但不崩）
  • TF（本地 50K 小训）→「the the the the the…」（纯退化循环）

README 自己也标注：这是 1.5M 参数在 12.7M token 上的 research toy model（“a settings check rather than a final number”）。别拿它跟任何生产模型比——它的卖点是架构主张（循环 + 记忆 + 快权重能学到什么程度），不是模型本身。

生成基准 5 条可抄的纪律（98x 坑拆细）#

98x 那个坑我拆成 5 条，你写任何 LLM 吞吐基准都能直接用：

  1. 必须记录"实际产出量"，不能只记墙钟。两边各吐多少 token/字符必须落到磁盘，否则分母是瞎的。我这版脚本把 chars_generated 和 chars 都写进 numbers.md 就是干这个。
  2. 撞 EOS ≠ 完成。生成模型有"提前想停"的自由，PSSA 旧权重大量 prompt 撞 EOS。把"撞 EOS 就停"算进吞吐，等于让被试少做题就交卷。
  3. 对照双方锁死同一工作量：要么都固定生成 N token 且都吐满 N，要么都按实际产出字符归一（chars/sec）。我这版取的是后者，且明确标"两边工作量不同"。
  4. 旧 checkpoint 的 EOS 行为是变量。作者的 ck64（12.7M token 训的）和我用的仓库自带 2.2MB 旧权重不是同一个，EOS 早停概率不同。换 checkpoint 必须重测，别沿用旧数字。
  5. 吞吐比 ≠ 质量比。循环架构"快"是结构性的，不代表"好"。我对照的 TF 是本地 50K 小训、质量差，吞吐对比只比 kernel 不比模型——这条要写进诚实声明，不然 9.3x 会被当成"质量也赢"。

循环 vs transformer：什么时候该信"快"#

成本模型说清楚了，“快多少"就有界了：

  • transformer：每步重读全上下文，注意力 O(L²)，每 token 成本随生成长度 L 增长。上下文越长，越慢。
  • PSSA 循环：每 token 一次固定大小的状态更新 + 有界记忆读，成本不随 L 涨（L 很大时是 O(1)/token）。

推论（可预测，不一定要本机全量验证）：生成越长的文本，PSSA 对 transformer 的优势越大。作者 200 token 短生成 12x（表），19.9 万 token 批量 4.13x（表）——短生成延迟差距被"生成快"放大、批量被评测/词表杂开销摊薄，方向跟成本模型一致。

适用场景（按"上下文多长、生成多长"筛）：

  • agent 长上下文 / 代码补全 / 流式长输出：循环架构优势最值钱，值得单独测
  • 短问答 / 固定长度任务：差距没那么夸张，别只信标题的 12x
  • 批量离线评测：4.13x 这一档，杂开销占比高

本机只做了 256 上限的短生成对照（9.3x 字符归一），长上下文 O(L²) vs O(1) 的全量曲线我没跑（2 核切片扛不动），标"未验，方向从成本模型推”。

为什么这个"玩具"值得你的团队看一眼（不是让你换模型）#

1.5M 参数的 PSSA 出字是胡说的，但没人该拿它当生产模型——它的价值在架构，不在权重。给你 3 个"该抄"的视角：

  1. 循环 + 有界记忆 vs 全注意力，是 2026 年长上下文的主战场。agent 场景上下文越来越长（代码库级），transformer 的 O(L²) 注意力成本会先于"质量"变成瓶颈。PSSA 的"每 token 成本不随 L 涨"是结构性的，不靠调参。你在选下一个 LLM 架构时，循环/SSM 族（Mamba、PSSA 这类）该在雷达里，哪怕你最后还用 transformer。
  2. 手写内核 + scalar 参考对账的工程纪律，能直接搬进你的项目。不管用不用 PSSA，“每个 commit 的 batched kernel 对 scalar 参考路径做梯度对账（阈值 1e-6 起步）“这套是任何手写/优化 ML 内核都该抄的——它把"并行路径和参考路径悄悄对不上"这个最难的 bug 类，变成了 CI 上必过的确定性检查。
  3. “架构定了实现语言"是个值得你拍板的判断点。你要做 per-token 在线权重 / forward 内写 memory 这类架构，autograd 框架每步打架，手写（Rust/裸 C）比"在 PyTorch 里硬塞"更顺。反过来，没有这种动态写参数的普通架构，老实 PyTorch，别被"纯 Rust 更优雅"带偏。

一句话：别抄它的模型，抄它的 kernel 纪律 和 成本模型判断。

你该抄哪条#

  1. 写生成基准先记实际产出量——98x 陷阱那条，9.9 成复现的人都得踩一遍
  2. 手写 ML 内核前，抄它的 twin_check 纪律：batched kernel 必须对 scalar 参考路径做逐 commit 梯度对账，阈值 1e-6 起步
  3. 用 PyTorch 还是手写，看你要不要 per-token 在线改权重：要 fast weights / forward 里写 memory，autograd 每步打架，手写更顺；不要就老实用 PyTorch
  4. 循环 vs transformer 的成本模型：生成超长文本（agent 长上下文、代码补全）时，循环架构"每 token 成本不随长度涨"是结构性优势，值得单独测一次

诚实声明#

  • “12x"与"4.13x"是我对 README 口径的裁决，9.3x 是本机实测（字符归一，AMD EPYC 9354P 2 核切片 / rustc 1.99.0）；不同机器/核数比率会漂，看量级和口径方法，别抄绝对值。
  • 训练曲线（12.7M token CE 3.98 vs 4.43）、held-out 泛化（PPL 54.4 vs 83.8、next-token acc 24.1% vs 18.0%）全部转述作者报告，未复现——本机 2 核跑不起 30000 updates。
  • 对照用的 TF 是我本地 50K token 小训（非作者 12.7M 的权重），吞吐对比只比 kernel 结构不比模型质量；PSSA 侧用的是仓库自带旧 checkpoint（非作者 ck64），EOS 早停行为受权重影响。
  • 复现：bench/gen-bench.py（吞吐双口径 + RSS）、cargo run --release --example twin_check（梯度对账），一条命令可跑。

FAQ#

Q：那"快 12 倍"到底能不能引用？ A：能，但要带口径。200 token 短生成延迟口径 ~12x（作者表），长批量吞吐口径 4.13x（作者表），我本机字符归一 9.3x。不带口径引用 12x，别人用批量口径复现就打脸了。

Q：为什么不用 PyTorch 是合理的？ A：PSSA 有 per-token 权重更新 + forward 内写 memory bank，autograd 的 tape 每步要追这些动态写，框架每步都在打架。代价：失去混合精度/分布式/profiler 生态。架构定了实现语言，不是语言选了架构。

Q：twin_check 是什么，我项目能抄吗？ A：它把 batched/parallel 路径和 scalar 参考路径在同一随机输入下各跑一遍，比较 forward 激活和 backward 梯度的最大差，阈值 ~3e-8，作为 CI 必过项。抄的点：手写任何 kernel（尤其并行/batched 版）都保留一条 O(N) 的 scalar 参考路径，两者对账。

Q：1.5M 参数小模型，学出来的东西能干嘛？ A：不能当生产模型。它的价值是验证"循环 + 记忆 + 快权重"这套架构在同等参数量/同等语料下训练 loss 和 held-out 都压过 transformer（作者报告 CE 3.98 vs 4.43）——这是架构主张，不是模型交付。

Q：本机跑 9.3x，作者的机器 12x，差在哪？ A：机器不同（我 EPYC 9354P 2 核切片 vs 作者 2vCPU）、PSSA 侧权重不同（我旧 checkpoint vs 作者 ck64，EOS 早停影响实际工作量）。差在变量，不在方法——照 gen-bench.py 的方法自己测。

常见问题

快 12 倍到底能不能引用？

能，但必须带口径。200 token 短生成延迟口径 ~12x（作者表），长批量吞吐口径 4.13x（作者表），我本机字符归一 9.3x。不带口径引用 12x，别人用批量口径复现就翻车了。

为什么不用 PyTorch 是合理的？

PSSA 有 per-token 权重更新 + forward 内写 memory bank，autograd 的 tape 每步要追这些动态写，框架每步打架。代价是失去混合精度/分布式/profiler 生态。架构定了实现语言，不是语言选了架构。

twin_check 是什么，我项目能抄吗？

它把 batched/parallel 路径和 scalar 参考路径在同一随机输入下各跑一遍，比较 forward 激活和 backward 梯度的最大差，阈值 ~3e-8，作为 CI 必过项。抄的点：手写任何 kernel 都保留一条 O(N) scalar 参考路径做对账。
