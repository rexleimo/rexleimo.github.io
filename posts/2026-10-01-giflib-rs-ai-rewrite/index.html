Google 让 AI 把 C 库翻译成 Rust：3000 万张 GIF 验证之后，它在一个 CVE 公布前就免疫了

Google 安全团队用 Gemini 把 3000 行的 C 图像库 giflib 重写成 Rust，业务逻辑 0 行 unsafe。验证不是跑一遍测试：3000 万张 GIF 全量回归、2 亿轮差分模糊、对抗性 AI 审查 + 专家逐块签核。最漂亮的注脚：原 C 版后来爆出越界堆写（CVE-2026-26740），已迁移的服务天然免疫——Google 原话：他们当时不知道这个 CVE 的存在，免疫是结构性的，不是定向修漏洞。

October 1, 2026 · 3 min · 537 words · 梦兽编程 -  |  English

先说结论#

8 月 24 日，Google Bug Hunters 发了一篇工程复盘：《Scaling Memory Safety: AI-Assisted Rewrites of C/C++ Dependencies to Rust》 外部链接 。作者 Bastian Kersting（软件工程师）和 Max Hils（安全工程师），讲的事很具体：用 Gemini 把 3000 行的 C 库 giflib 重写成 Rust，做成 ABI 兼容的 drop-in 替换，铺进 Google 自己的生产基础设施。

三个结论前置，数字都来自 Google 官方博客（8 月 24 日发布时点）：

  1. 能翻。~3000 行、无 SIMD/汇编、接口稳定的 C 库，one-shot 就能被 LLM 翻译完，之后是 FFI 层迭代 + 差分测试反馈回路，不是"提示词炼丹"。
  2. 要验。信任不来自"AI 写的"，来自 3000 万+ GIF 全量回归、2 亿+ 轮差分模糊（并跑 6 天以上）、对抗性 AI 审查，外加专家把每一块 unsafe 签核过。
  3. 赚到的是结构性免疫。原 C 版 giflib 后来爆出越界堆写漏洞（CVE-2026-26740），已经迁移到 Rust 版的服务天然免疫。Google 原话很硬：干活的时候他们不知道这个 CVE 的公开，免疫是"结构性的架构改动"顺手做到的，不是定向修的。

为什么是 giflib：试点不是随便挑的#

官方给的理由值得抄：

  • 内存安全漏洞占 C/C++ 漏洞总量的约 70%（Google 引用了自家 2023 年的研究数据）。第三方库尤其危险——它们解析的是不可信数据，而且经常跑在无沙箱环境里。
  • LLM 越强，漏洞从被挖出来到被武器化的间隔越短——所以"先修存量"比"等新版本"划算。
  • giflib（Eric S. Raymond 写的 GIF 处理库）刚好是理想靶子：约 3000 行、没有 SIMD/汇编优化、代码库稳定，复杂度轮廓干净，翻完能快速出验证结果。

选目标这件事本身是这篇文的第一课：AI 重写的第一站不该是最复杂的库，该是"3000 行、可差分、稳定"这种能一把验证掉的。

三步走：AI 重写的流水线#

官方把过程拆成三步：

第一步：one-shot 初翻#

因为库够小，Gemini 一次性把整个 C 代码库翻成 Rust。官方原话是"快速完成"——这一步不稀奇，稀奇在后面两步。

第二步：FFI 层迭代（反直觉的点在这）#

这是全篇最该细读的一段。把 C 库换成 Rust，不等于 unsafe 清零：为了对现有 C 调用方保持 ABI 兼容，Rust 这边必须把 C API 建模出来，指针的生命周期要在边界上手工管。官方原话：

We identified defects and an initially very unsound memory management pattern within the FFI boundary.

翻译过来：AI 第一版 FFI 层的内存管理模式本身就是不安全的（unsound）。后续靠迭代提示让模型修 C 兼容包装层，最终所有 unsafe 代码由专家逐块审查、判定正确才放行。

反直觉在哪？大家印象里"AI 写 Rust"的风险是"翻错逻辑"，这篇告诉你：最大的风险在语言交界处——unsafe 边界是 AI 最容易写出"看起来对"但实际漏的代码的地方。业务逻辑 0 unsafe，unsafe 全堆在 FFI 那一层，然后用 safer_cffi 加护栏。

第三步：验证反馈回路#

差分测试发现的行为/逻辑缺陷，直接喂回给模型生成定向修复。AI 不是写完就下班，它接住"测试→修"的循环。

凭什么信 AI 写的代码：四道验证闸#

这是"AI 重写进生产"能不能成的关键，官方的验证栈我按强度排了序：

闸做了什么结果
1. 全量回归内部数据管道跑 3000 万+ 张真实 GIF，逐张比对 C 版输出行为一致
2. 差分模糊C 和 Rust 实现并排 fuzz，连续 6 天以上、2 亿+ 轮无逻辑偏差
3. 对抗性 AI 审查专门 prompt 让模型找"两个代码库之间细微的行为差异"查出 LZW 解码器一个边界 case，还查出原 C 源码里一个 Google 内部 legacy patch 引入的越界写（Rust 版顺手修了）
4. 专家签核所有 unsafe 代码逐块人审判定正确

注意第 3 闸的副产品：验证管道不光保住了新代码，还顺手修掉了原 C 版里一个 Google 内部补丁自己引入的越界写漏洞——这就是"换语言"和"打补丁"的区别，补丁只修已知，语言把整类都关掉。

最漂亮的注脚：CVE-2026-26740#

官方标题这节叫 “Real-World Efficacy”。事情经过：

  • 迁移 rollout 刚开始不久，原 C 版 giflib 被报了一个内存破坏漏洞：越界堆写，编号 CVE-2026-26740 外部链接 。
  • 已经切到 Rust 版的生产服务天然免疫。
  • Google 原话：“we didn’t know about the disclosure or the CVE while working on this”——干活时根本不知道这个 CVE 存在。

把这句话拆开读：他们做的不是"发现 0day 然后修 0day"，是在不知道 0day 存在的时候，靠结构性改动把 0day 的存活空间关掉了。这就是"Secure by Design"和"打补丁"的差距：补丁追着漏洞跑，架构让漏洞无处跑。官方还加了一句更狠的：giflib 未来再出内存安全漏洞，他们已经免疫了。

性能和架构收益#

两个反常识的点：

  1. 性能持平。大家默认的"Rust 多了 bounds check 会拖性能"在这没发生——官方在全网图像处理服务上监控，确认 Rust 版 performance-neutral，而且他们在很多 Rust 替换场景里观察到持平甚至变快。
  2. 尾延迟下降。C 版跑在无沙箱环境里要靠资源开销很大的 sandboxing 兜底，换成 Rust 之后这层直接拆掉。安全架构简化换来的是性能收益——官方原话：secure-by-design 和业务目标（性能）居然对齐了。

仓库里能直接抄的东西#

google/giflib-rs 外部链接 已经开源（MIT，我拉下来核对过 README 和 Cargo.toml，数字都对得上）：

  • 版本 6.1.301：语义是"移植自 giflib 6.1.x，patch 位补两位给 giflib-rs 自己的补丁版本用"。edition 2024，依赖 libc 0.2.186 + safer_cffi 0.2（patch 指向 Google fork 的 safer_cffi），build 依赖 bindgen 0.72.1。
  • 业务逻辑 0 unsafe（README 原文），unsafe 只在"提供 C API + 接 C 传来的指针"两处。
  • README 明确推荐：如果不需要 ABI 兼容，直接用 crates.io 上的 gif 外部链接 crate——“它更快，API 更地道”。官方替你把"要不要为了 Rust 而 Rust"的边界画好了。
  • 仓库声明不是 Google 官方支持产品，也不在漏洞赏金计划里——第三方维护，引用时留意。

三个已知差分（下游注意）#

README 列了 3 处故意与 C 版行为不同的地方，全是修 C 的 bug：

  1. 错误字段置位：C 版 DGifSlurp 遇到非法尺寸（宽高 ≤0 或乘积溢出）返回 GIF_ERROR 但不置 GifFile->Error（留 0）；Rust 版置 D_GIF_ERR_DATA_TOO_BIG（108）。
  2. 写文件返回值：C 版忽略 write() 失败、照样返回 GIF_OK；Rust 版检查返回值、失败报错。
  3. OOM 行为：C 版分配失败返回错误码；Rust 版直接 panic。官方注了：Linux 默认 overcommit + OOM Killer，实际通常无感。

如果你的下游代码依赖旧行为（比如靠"返回错但不置 Error"来走 fallback），迁移时这三处会咬你。这是"重写"和"打补丁"的另一种区别：重写有权修 bug，但修 bug 对下游就是行为变更。

FAQ#

AI 写的 Rust 可以直接信吗？ 不能。这篇的启示是：AI 负责"翻译快"，信任靠四层验证挣——全量回归 + 差分模糊 + 对抗性审查 + 专家签核 unsafe。少任何一层都不进生产。

我的 C 依赖够小，能这么干吗？ 前提是两条：有可差分的行为基准（真实数据集/现有测试），下游能接受有意的行为修正。没基准的库，AI 翻完你验不出对错。

unsafe 是不是清零了？ 业务逻辑是（0 行）。FFI 边界清不掉——你要接 C 调用方的指针，那块靠 safer_cffi 加护栏 + 人审。“Rust 版"不等于"无 unsafe”，等于"unsafe 被关进了一个有围栏的房间"。

CVE-2026-26740 影响哪些人？ 还在用原 C giflib 解析不可信输入的。已经切 giflib-rs 的免疫。具体评级去 NVD 查（CVE 页 外部链接 ），本文没做独立评级。

性能会掉吗？ 官方监控口径：持平。拆掉 sandboxing 后尾延迟还降了。不同场景结论可能不同，进你项目前先跑自己的基准。

诚实声明#

  • 3000 万 GIF 回归、2 亿轮模糊、performance-neutral 等数字全部转引自 Google 官方博客（8 月 24 日发布时点），我本机没有跑全量复现（机器没有 Rust 工具链、也没有 3000 万张 GIF 的数据管道），以上验证结论以官方为准。
  • 仓库一手核对过的只有：README 的 0 unsafe / safer_cffi / 3 个已知差分、Cargo.toml 的 6.1.301 / edition 2024 / 依赖版本、MIT 许可、仓库 2026-07-06 创建、抓取时点 30 stars。没有逐行读 src/。
  • CVE-2026-26740 的漏洞类型（越界堆写）和"已迁移服务免疫"转引自官方博文，我未独立评级或复现该 CVE。

常见问题

AI 写的 Rust 能直接进生产吗？

不能裸奔。Google 这篇的验证栈是四层：3000 万+ GIF 全量回归（行为一致）、2 亿+ 轮差分模糊（C 和 Rust 并跑 6 天以上、无逻辑偏差）、对抗性 AI 审查（专门找两个版本的行为差异）、专家逐块签核所有 unsafe。AI 负责翻译和迭代，信任是靠验证数据 + 人签字挣来的。

重写之后真的一个漏洞都没有了吗？

不是绝对无漏洞，是整类漏洞出局。giflib-rs 业务逻辑 0 行 unsafe，unsafe 只集中在 FFI 边界（要接 C 调用方的指针），用 safer_cffi 加护栏。越界写、use-after-free 这类内存安全漏洞在架构上被堵掉了——原 C 版后来爆的 CVE-2026-26740 就是越界堆写，Rust 版天然免疫。

我项目里的 C 依赖能照抄吗？

可以，但要掂量两条前提：一是要有可差分的行为基准（真实数据集、现有测试），没基准就验不出 AI 改对没有；二是接受有意的行为修正——giflib-rs 的 README 列了 3 个已知差分，全是故意修 C 的 bug（错误字段不置位、写失败不报错、OOM 行为不同），下游如果依赖旧行为会踩到。另外仓库 README 明说：如果不需要 ABI 兼容，直接用 gif crate，它更快、更地道。
