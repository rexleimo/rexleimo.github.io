Pi 的 /compact 把 prompt cache 打碎了：这个扩展 99% 读缓存，667k 会话省 86%

Pi 内置 compaction 会换 system prompt、丢 tools、压平消息，provider 的 prefix cache 全 miss，全价计费。Nico Bailon 的 pi-cached-compaction 三样原样保留、只追加一条摘要指令，667k-token Opus 会话 99% 读缓存、$0.19 对 $1.40。我把 README 和 live-tests 的数字、源码的逐字节判据、它自己承认的反例全拆了一遍。

October 23, 2026 · 2 min · 405 words · 梦兽编程 -  | 

10 月 22 日 17:58 UTC，Nico Bailon 在 X 上发了一条带演示的帖子：Pi 的内置 compaction 会换 system prompt、丢 tools、把消息压平成文本，三者都对不上 provider 缓存里那一轮的字节，缓存全丢，整段摘要请求按全价计。他写了个扩展把这三样原样保留，只在末尾追加一条「summarize this」，同一轮对话续下去——667k-token 的 Opus 5.5 会话 99% 读缓存，$0.19 对 Pi 的约 $1.40，省 86%。帖子 16k 阅读、383 赞，仓库当天 push、MIT 协议。

卡片下方还有个容易被忽略的细节：footer 在倒数计时。⏱ 59m · claude-opus-5-5 · high——这是缓存寿命的倒计时，发条消息就重置，最后 30 秒变警告色，归零后显示 cache cold。它盯的是最贵的那次重写：667k 的缓存一旦过期，下一条消息要重写全部 666k token，按 1 小时档 $5.33。

缓存为什么会被 compaction 打碎#

provider 的 prompt cache 是前缀匹配：本轮请求和上一轮请求从第 0 个 token 起逐字节相同的部分，都按缓存读价 0.1× 输入价计，不同的部分从分岔点起全价。Pi 内置 compaction 的问题在于它构造的摘要请求和 agent 自己发的请求前缀就分岔了——summarizer 的 system prompt 不是 agent 的，工具声明没了，旧消息被 serializeConversation 压成带 2000 字符截断的文本块。

扩展的修法是把摘要请求当成同一轮对话的下一 turn：cached-request.ts 的 prefixMismatch 用 canonical() 做 JSON 序列化（第 76-78 行，cache_control 字段直接剥掉——Pi 每轮都把缓存断点挪到最新消息上，它不是被缓存的内容），逐字段比对捕获的上轮请求和重建的摘要请求，消息数组前 end 条必须逐条 was === now，尾部允许多出「新增的 turn」。对不上——编辑过消息、切了模型、thinking 等级变了、/tree 导航过——直接拒绝，回落到 Pi 自己的 compaction。

2000 字符截断丢掉的不是边角#

Pi 的摘要器只看每个工具结果的前 2000 字符（truncateForSummary）。长会话的重活在长输出里：整文件、测试运行、构建日志——失败通常排在尾部。官方在 11 个过了 700k token 的 Opus 5.5 subagent 会话里数了一遍：

摘要在哪停：引一条消息当界#

Pi 保留最近 keepRecentTokens（默认 20k）原文，摘要必须从保留区第一条消息开始前停笔。扩展的做法是把那条消息的开头文本引进指令：「Summarize what comes before the message starting with: …」。live-tests 里旧措辞（只引文本、不说数量）的泄漏率 6/6 和 2/3——摘要器把保留区的活也报成已完成；新措辞加上「保留了几条、从尾部数第几条、把对话当作在引用消息之前结束、句尾重复停点」，0/6。边界画出来长这样：

第一张保留消息没有可引的文本（只有图片或 thinking）时它不猜，直接交还给 Pi 的 compaction。

走开时赶在缓存过期前 20 秒压缩#

这是独立于 /compact 的第三档。Pi 默认缓存 5 分钟（Anthropic），大部分走开间隔超过它，回来第一条消息重写整个 session。扩展在交互会话里默认要 1 小时档（Anthropic 上写价 2× 输入价、读价不变；GPT-5.6+ 上 system prompt 和工具进 12 小时共享前缀），并盯着倒计时：idle 且无排队、上下文 ≥50k token、缓存路径可用时，在过期前 20 秒主动 compact 一次。下一条消息只重写摘要大小的上下文。阈值用 token 不用百分比——重写过期缓存的费用正比于大小，1M 窗口上百分比几乎不触发。

live-tests 的档位实测：5 分钟档 idle 8 分钟过期、重写 39,707 token；1 小时档同间隔仍热。12 小时前缀（GPT 共享 key）在 40 分钟 idle 后仍缓存，同写的 30 分钟档已过期。

各模型缓存命中（10-21 实测，小会话指令占 400-610 token 把占比压到 80s）：Opus 5.5 via bridge 96%/99%、Haiku 5.5 86-87%、gpt-6-luna 83-86%、grok-4.7 90%、kimi-k2.7-code 79-86%。tool_choice: "none" 在 GPT 上每次少读 72 token 缓存、在 Grok 上把命中从 90% 砍到 62-69%——所以扩展只对 openai provider 设它。

诚实边界#

本机没有 Pi 环境与 provider 凭据，未独立复跑：全部数字引自仓库 README 与 docs/live-tests.md（Pi 1.3.0 RPC 模式，2026-10-21），仓库 54 star、单作者、MIT，仓库创建 10-21、push 10-22。卡片里「vs Pi」那列是估算——Pi 的 compaction 从不实际运行，扩展用 Pi 自己的序列化器造同一条消息序列再按 provider 报的 token 数折算，官方自报误差 2~12%、恒偏高，卡片的节省额比真实的大几个点（50k 会话卡片说 62%，按真实费用算是 58%）。

常见问题

Pi 的内置 compaction 到底卡在哪？

它给摘要请求换一个自己的 summarizer prompt、丢掉工具声明、把旧消息压平成文本，三者都和 provider 已缓存的上一轮请求字节不一致，于是 prefix cache 全 miss，整段按全价输入计。

99% 读缓存怎么来的？

扩展重建摘要请求时，system prompt、tools、消息 1..N 与上一轮逐字节相同（源码用 canonical 化后逐字段比对，剥掉 cache_control 这类缓存断点字段），只在末尾追加一条 400~600 token 的 summarize 指令。前缀命中部分按缓存读价 0.1× 输入价计费，会话越大命中占比越高：2k 会话 83%、10k 95%、44k 99%、200k 自动 compaction 99.7%。

它比 Pi 省钱是有边界的吗？

有。README 自己写明：小会话、或会话大部分时间在读大文件时，Pi 反而更便宜（它截断每个工具结果到 2000 字符后要发的量本身就少）。895k 纯读文件会话里 Pi 只发 53k 全价 $0.25，扩展发 895k 但 99% 缓存 $0.22，仅省 12%。

本机复现了吗？

没有。本机没有 Pi 环境和 provider 凭据，全部数字引自仓库 README 与 docs/live-tests.md（2026-10-21 在 Pi 1.3.0 RPC 模式实测，7 个模型），未独立复跑。
