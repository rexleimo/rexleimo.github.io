13 天 5,283 star：Rust 写的 Kiri，冲着 Docker Desktop 的桌面生意来的

libracoder/kiri 11-02 建仓、13 天发 6 版，GitHub API 实测 5,283 star、247 fork。Rust 重写整套容器路径，兼容 docker CLI、Compose 和 buildx，官方自报起容器 2.55 ms。全文与讨论沉在 BBS。

November 16, 2026 · 2 min · 252 words · 梦兽编程 -  |  English

11 月 2 日 16:11（UTC），GitHub 上建了一个叫 libracoder/kiri 的仓；一分钟后，v0.1.14 发布。到 11 月 15 日，GitHub API 实测 5,283 star、247 个 fork，13 天里发了 6 个版本。语言一栏是 Rust，许可证 Apache-2.0，仓库描述一行字写明目标：macOS、Windows、Linux 上小巧快速的容器运行时，外加免费 Ngrok 替代。

图源：runkiri.com 官方 og 图（11-15 抓取），命令行一行 docker run in 22 ms。

它替代的不是 docker，是那个桌面应用#

不变的部分：docker 命令、Compose 文件、Dockerfile，一行都不用改；变的是 Engine API 背后那个引擎。容器跑在一个小 Linux 虚拟机里，Linux 宿主上直接贴着内核跑。kiri.local 本地域名配项目自签的证书机构，HTTPS 直接有；kiri k8s start 起单节点 k3s 集群约 20 秒就绪；kiri share 给任意容器一个公网 HTTPS 链接。v0.2.1 起窗口自带 38 种语言，简体中文在内。名字取自尼日利亚东南部伊博语里的 ntakịrị，意思是小。

官方自报的数字：2.55 毫秒对 213 毫秒#

README 对比表（同一台机器、同一套 CLI，alpine 起 true 再删掉，30 次取中位）：走 Docker Engine API，Kiri 2.55 ms，Docker Desktop 213 ms，OrbStack 380 ms；走 docker CLI，对应 14.2 ms 对 243 和 442 ms。官网首页是另一组：docker run –rm alpine true 用时 22 ms，对 Docker Desktop 178 ms、OrbStack 279 ms、Colima 152 ms，四个引擎各限 2 个 CPU 和 8 GB 内存，一台 M3 Max 测的。Windows 上 WSL2 后端单独一组：78 ms 对 491 ms。

这组数字全部要讲在前面：官方自报，未独立复现，官方自己还交代过一处测量瑕疵。测法倒是可以照抄：同一 CLI、同样限核、取中位，原始数据放在仓库的 bench/results.json，kiri bench 可重跑。

图源：runkiri.com/benchmarks 页面实拍（11-15），表头 MAC · 2 NOVEMBER 2026。

速度从哪来#

Docker Desktop 往虚拟机里摆全套 Docker 引擎：dockerd、containerd、每容器一个的 shim、真正创建容器的 runc。Kiri 不放 Docker 的引擎，换成自己写的两个：Mac 侧一个 daemon 服务 Docker Engine API，虚拟机内一个当 PID 1 的 agent；启动请求经 vsock 一帧到达，agent 用一次 clone3 系统调用把新进程直接放进新的命名空间和 cgroup。没有 runc，没有 shim，也没有 dockerd。官方连不利的数字都摊开了：起容器链路里最大单项开销是 veth 删除的 18.9 ms，比其余所有步骤加起来（6.26 ms）还大，这项在 bridge 网络上还没挪出关键路径，官方写明是待办。

诚实边界#

正文性能数字（2.55 ms、22 ms、88.9 次每秒、内存与唤醒时间、约 20 秒起集群）全部为官方自报、未独立复现。本机环境是 2 核 EPYC 的 Linux，无 GPU，桌面虚拟机形态在这里跑不起来。本机实测的两个数字：v0.2.1 产物字节数（官方下载 URL 的 HEAD 响应，11-15：lite deb 2,717,814 字节，完整 arm64 dmg 50,666,199 字节，差近 19 倍）与 star、fork、issue 计数（GitHub API，11-15；97 个未关闭 issue 含 PR）。Windows 容器、GPU、Extensions 和多机统一管理在官方不支持清单里，对比博客原话是这些场景请留 Docker Desktop。

常见问题

要改 Dockerfile 和 compose.yaml 吗？

不用。Kiri 服务同一套 Docker Engine API，docker、Compose、buildx 照原样用，官方还给了 kiri import 把既有镜像、卷、容器搬过来。

装完发现不合适，怎么回？

一条命令，docker context use desktop-linux。两个引擎本来就并存，互不接管对方的 socket。

能上生产吗？

不适合。它是开发机上的桌面侧工具，官方挂着 BETA，GPU、Windows 容器等边界自己列得清楚。
