在一台两核机器上，我把 Rust 编译从 20 秒砍到 0.05 秒

rustc 团队负责人 Nethercote 发文讲编译器提速，HN 第一。他测的是编译器内部；我测的是用户侧——在一台没装 Rust 的两核机器上，手动点亮工具链，跑出一组编译基准：冷启动 20 秒，增量 0.05 秒，差 330 倍。这篇讲我实际跑出了哪些数字、哪根杠杆没装成，以及 Nethercote 那个 4.57% 我为什么复现不了。

October 1, 2026 · 2 min · 337 words · 梦兽编程 -  |  English

HN 第一是 rustc 团队负责人 Nick Nethercote 的文章，讲编译器团队这两个月怎么把编译速度提上去的，核心数字是一个月内基准均值 wall-time 降了 4.57%。我读完了，写得是真好——但他量的是编译器内部：PGO、新 borrow checker、trait solver、dataflow 遍历。这些东西我作为用户碰不到，我那个 4.57% 也复现不了。

所以我干了另一件事：在我自己的机器上，把用户侧能拧的那几根杠杆真跑一遍，出一组我这台机器上的数字。

这台机器是两核、7.8GB 内存、没有 root、也没装 Rust。跟上一篇 TLA+ 那台是同一台。区别是这次工具链是 user 级的，一路顺，没卡。

机器上没有 rustc，我就 user 级装#

$ rustc --version
command not found: rustc

$ sh rustup-init.sh -y --profile minimal --default-toolchain stable
$ rustc --version
rustc 1.99.0 (stable)

不展开了，一行装完。跟 TLA 篇那个"apt-get 没权限、只能手动塞 JDK"的狼狈不一样，rustup 全程碰不到 root。这段放这篇里只占一行，是 A 声部里最不值钱也最诚实的一行：工具链点亮了，rustc 1.99.0。

我搭的被测对象：不是空 hello-world#

空 hello-world 编译两秒，测不出任何东西。我需要一个会真正放大编译时间的工程。搭法很简单，全是要在编译期干活的依赖：

  • serde + serde_derive：全量 derive 宏展开；
  • syn（full + proc-macro feature）+ quote + proc-macro2：真实语法树解析，这是编译时间里的大头；
  • clap（derive）：又是 derive；
  • regex + chrono：真实算法代码，release 下优化得动。

被测工程就一个 main.rs，把这几个库都 import 进依赖树。cargo tree 出来的依赖树是真实的，不是玩具。这是我亲手搭的被测对象，脚本和工程都在我这边，不是抄谁现成的。

四组数字，都是这台机器跑出来的#

计时方法：cargo clean 后全量 build 是冷启动，无改动再 build 是增量。dev 和 release 各一组：

场景实测（两次）含义
冷启动 dev21.7s / 18.1s全量重编
增量 dev0.05s / 0.06sfingerprint 全命中
冷启动 release41.5s / 39.1s比冷 dev 慢 ~90%
增量 release0.05s / 0.06s同上

脚本重跑两次，数字稳定在这个量级。复现脚本我存了（rustc-bench.py，贴文末）。

三句解读，每句都停在我实际看到的边界上：

  1. 增量 0.05 秒 vs 冷启动 18–21 秒，差 330 倍。 0.05 秒那一档没有任何 rustc 在跑——cargo 把上次 build 的每个 crate 的源码 hash、依赖版本、编译器版本存成 fingerprint，这次全命中，直接跳过。这就是为什么你改一行代码再 build 只需要几秒：只有你改的那个 crate 及其下游重编，上游全是 fingerprint 命中。
  2. 冷 release 比冷 dev 慢 ~90%（39–42s vs 18–21s）。 差在 -O 的全局优化和 codegen。我没做 opt-level 参数扫描（只测了默认两档），所以"LTO 还能再砍多少"我没答案，正文不装。
  3. 两核机器上这些数字就是这些数字。 Nethercote 那篇文章里 4.57% 的均值，是编译器团队在他们自己的大型基准套件上、用他们自己的硬件测的。我拿不到他的套件，也复现不了那个数——这条边界我写死。

第二根杠杆：sccache，我没装成#

用户侧真正能砍冷启动的杠杆只有一根：编译缓存，最常用的是 sccache。它把 rustc 的输出按输入 hash 缓存起来，第二次冷启动（比如 cargo clean 之后）命中缓存能砍掉大头。

我试了：从 GitHub 拉 sccache 的 musl 静态二进制，下载失败，没装成。

所以这里我只能给判断、不能给数字：sccache 命中时冷启动能砍掉大半——这是我的经验判断，没实测。宁缺毋滥，正文里就是"点出这根杠杆，标了没测成"，不装成测过。

我到底跑通了什么#

  • 跑通：工具链（无 root、user 级 rustup → rustc 1.99.0）；自搭 bench 工程（真实依赖树，不是玩具）；四组本机数字（上表，脚本可复现，重跑稳定）。
  • 没跑通：sccache（二进制没下成，冷启动缓存收益没测成）；Nethercote 的 4.57%（upstream 内部基准，我作为用户拿不到）；LTO/opt-level 扫描（没做）。
  • 每个数字的来源：上表是本机输出；4.57% 和各内部 PR 是 Nethercote 原文；“sccache 能砍冷启动大半"是我的判断、未实测。

正文到此。这是梦兽编程的规矩：我对我自己这台机器上发生的事负责，没复现就写没复现。

附：复现脚本#

#!/usr/bin/env python3
# rustc-bench.py — 本机 Rust 编译提速基准
import subprocess, time, json, os
CARGO = os.path.expanduser("~/.cargo/bin/cargo")
D = "research/rustc-bench"          # bench crate 目录

def run(args):
    t0 = time.time()
    r = subprocess.run([CARGO] + args, cwd=D, capture_output=True, text=True)
    dt = time.time() - t0
    if r.returncode != 0:
        print(f"FAIL {args}: {r.stderr[-300:]}")
        return None
    return dt

res = {}
run(["clean", "-q"]);   res["cold_dev"]     = run(["build", "-q"])
res["warm_dev"]         = run(["build", "-q"])
run(["clean", "-q"]);   res["cold_release"] = run(["build", "--release", "-q"])
res["warm_release"]     = run(["build", "--release", "-q"])
print(json.dumps({k: (f"{v:.2f}s" if v else "FAIL") for k, v in res.items()}, indent=2))
if res.get("cold_dev") and res.get("warm_dev"):
    print(f"增量收益: cold_dev {res['cold_dev']:.2f}s -> warm_dev {res['warm_dev']:.2f}s "
          f"({res['cold_dev']/max(res['warm_dev'],0.01):.0f}x 快)")

跑之前先按上面的依赖表建 bench crate（Cargo.toml 就六行）。本机环境：两核 / 7.8GB / rustc 1.99.0 stable / 无 root。

常见问题

增量 0.05 秒是怎么来的？

cargo 的 fingerprint：上一次 build 把每个 crate 的依赖、源码 hash、rustc 版本全记下来，无改动再 build 时全命中，一次 rustc 都不跑。我冷启动是 18–22 秒，无改动重 build 是 0.05 秒，两个都在这台两核机器上实测。

Nethercote 说的 4.57% 提速你复现了吗？

没有，也复现不了。那是编译器团队在他们自己的基准套件上测的，靠的是 PGO、新 borrow checker、trait solver 这些编译器内部改动。我作为用户拿到的是被动收益，我测的是用户侧杠杆。正文里我把这条边界写死了。
