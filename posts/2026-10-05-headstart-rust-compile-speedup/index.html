Headstart 让 Rust 编译快 2 倍？我在 2 核机器上把它量穿了

PowderworksCode/headstart 靠 9 个 patch 把 rustc 的 rmeta 早发提前，官方 16 核 check 最高 54%。我把 patch 打进 rustc/cargo 自建工具链，在 2 核 EPYC 切片上拿 topcoat（143 crate）跑开关对照：check 只剩 5.7%、build 3.2%——'up to 2x' 的核数衰减曲线，我用最低点坐实了。

October 5, 2026 · 3 min · 458 words · 梦兽编程 -  |  English

PowderworksCode/headstart：9 个 patch 把 rustc 一条内部优化「早发 rmeta」提前，官方 16 核机器上 cargo check 最高快 54%、build 42%，口径是 “up to twice as fast”。我把 9 个 patch 打进 rustc/cargo 源码自建了一套工具链，然后在我这台 2 核 EPYC 切片上，拿 topcoat 那个 143-crate 的 workspace 跑 clean check/build 开关对照。落到 2 核，check 只剩 5.7%、build 3.2%。 “up to” 这个词的水，我替读者量出来了。

这篇文章讲四件事：① Headstart 到底改了编译器什么；② 官方那串数字怎么来的、为什么「核越少越缩水」；③ 我在 2 核上把它量穿，以及为什么；④ 你今天就该抄的两条，以及为什么 2 核别急着自建 dev 工具链。机器：AMD EPYC 9354P 2 核切片，自建 rustc 1.101.0-dev + patched cargo 1.101.0，2026-10-05 实测，每条数字挂命令可复现。

它把编译卡的哪根筋切开了#

Rust 多 crate 编译有个老大难：下游 crate 要等上游 crate 把全量 metadata（接口 + 函数体 + 各种类型检查产物）全写出来，才能开始自己的工作。核心数多的机器上，下游核心就那么干等上游写完，闲置。Headstart 的思路是把 rustc 里「查接口」和「查函数体」这两条 query 劈开——接口查完就先写一份早发 metadata（.early-rmeta），下游凭它抢跑起来，函数体那些慢产物再慢慢补。活比喻：图纸还没画完，下游先拿毛坯开工，边盖边补图纸。这是它能在 16 核上抠出 54% 的全部来源——收益全部来自「本来闲置的核心」。

官方数字我逐条核过#

我在 2 核上把它量穿#

自建工具链后，对 topcoat 那个 143-crate（check）/ 364-crate（build）的 workspace，用同一套 patched 工具链跑开关对照：默认 cargo check/cargo build = upstream 基线，CARGO_UNSTABLE_HEADSTART=true = 开 headstart。每格 2 轮 clean（rm -rf target），dev profile。机器是 2 核 EPYC 9354P 切片，非独占，取 2 轮均值。

指标OFF（upstream）ON（-Zheadstart）gain官方 16 核对照
cargo check（clean，143 crate）484.4s456.8s5.7%54%（最高）
cargo build（clean，364 crate）578.0s559.5s3.2%42%（最高）
RUSTFLAGS=-Zthreads=2 check（无 headstart）479.0s—比 OFF 还慢 1%无对应

冒烟验证：开了 headstart 的 target 里出现 513 个 .early-rmeta，这是官方 README 里「早发 metadata」的标志性产物，确认开关真生效、不是空转。四格 8 轮 clean 全量编译都落进 CSV（bench-v3.csv），任何一轮崩了数据都不丢。

结论一句话：16 核 54% → 4 核 24% → 我 2 核 5.7%/3.2%，这条「核越少省得越少」的曲线，我用最低点给它坐实了。

为什么核心越少，省得越少#

headstart 的每一分收益都来自「让下游核心不空等」，前提是你确实有空等的核心。16 核机器下游有一大批核心在闲置，早发 metadata 让它们抢跑，能抠出 54%；到我这台 2 核，整个机子从头到尾就 2 条编译并行度，-Zthreads 顶满也就 2 个在跑，根本没什么「闲置核心」可供早发 metadata 去填——所以只剩 5.7%。更扎心的是：同一格 -Zthreads=2（并行化前端、稳定 nightly 就有、不用 headstart）实测 479.0s，比 OFF 的 484.4s 还慢 1%。这说明 headstart 的价值不在「并行化」——那是 -Zthreads 的事，我 2 核上已经做满了——全在「早发 metadata」这条机制上，而这条机制的核心受益者恰恰是「核心多、下游爱闲置」的场景。核少的人，省不出水来。

我自建工具链踩的坑（真发生的）#

三处，全是自建 dev 工具链特有的，贴出来给同样想自建的人：① bootstrap.toml 我加 jobs=2 防 OOM 时手滑，写成了两个 [build] 表，TOML 直接报错，重写合并成单表；② 9 个 patch 里有几个文件名带空格，patch 一行 glob 打不上，得逐个 patch -p1 < file；③ 编 patched cargo 时它 git2 依赖要找系统 OpenSSL，我机器上 pkg-config 是断链（指向不存在的路径），没 sudo 装不了系统包，改用 cargo build --features vendored-openssl 让 cargo 编自带 OpenSSL 绕开。这三坑加起来，是「为什么 2 核别急着自建」的体力成本注脚——你还没开始拿收益，光绕坑就够喝一壶。自建本身不算慢：rustc 全量 19 分 02 秒、patched cargo 7 分 54 秒（LLVM 走 CI 预编译，省掉了预估里的 2-4 小时大头）。

不用等它，现在就能白捡的折中#

RUSTFLAGS=-Zthreads=N 能并行化 rustc 前端，稳定 nightly 就有，不用等 patch 合入主线。但我 2 核实测它几乎不省（479.0s，比 OFF 还慢 1%）——因为 2 核你本就没得并行。核多的人（16 核、32 核）今天就能开上，这是 headstart 合入前性价比最高的一档。

# 任意项目，稳定 nightly
RUSTFLAGS="-Zthreads=$(nproc)" cargo check
# 2 核机器实测几乎无效，别开

它没解决的事，我主动列 3 条#

  1. 这是 dev 编译器，rustc 本体绝对时长不可比（官方口径也是只比开关增益、不比绝对值），拿 1.101.0-dev 的 484s 去比稳定版没有意义；
  2. patch 还没合入上游，-Zheadstart 目前只能在自建工具链里用，主线还得等 9 个 patch 过 review；
  3. 自建成本被低估：就算 LLVM 走 CI 预编译，19+8 分钟只是「这一次」，patch 更新、bootstrap.toml 调参、pkg-config 断链这些坑，2 核上反复绕就是真实体力。

你该抄的 2 条#

① 今天：核多的人 RUSTFLAGS=-Zthreads=$(nproc) 开上，稳定 nightly 就有，不依赖 headstart；2 核的人别开，我实测反慢 1%。② 盯着：把 PowderworksCode/headstart 的上游 PR 加进 watch，9 个 patch 合入主线后，cargo -Zheadstart 一行开关、零自建成本，那才是它的正主价值——对 8 核以上、依赖树深、下游 crate 多的项目（我 topcoat 那个 143-crate 在 16 核上就能复现个位数到两位数收益）。

FAQ#

  • 2 核值得自建吗？ 不值得。我 2 核省 5.7%/3.2%，扣掉绕坑体力成本是负收益。8 核以上、依赖树深才值得等它合主线。
  • 跟增量编译啥关系？ 增量是「没改的 crate 不重编」，headstart 是「干净全量编译时让下游抢跑」，正交，不冲突也不互相替代。
  • patch 合入主线没？ 还没，9 个 patch 在 review，现在只能自建工具链用。
  • Windows 能用吗？ 官方 results 是 Linux，我实测也是 Linux；Windows 得等主线合入。
  • 多小的项目才有感？ 依赖树越深、下游 crate 越多越有感；143-crate 的 topcoat 在 2 核上才 5.7%，小项目（<20 crate）2 核基本无感。

诚实声明#

  1. 我全篇用 dev 工具链，rustc 绝对时长（check 484s）不可与稳定版横比——我只比开关增益，沿官方口径；
  2. 2 核 EPYC 切片非独占、每格 2 轮 clean 取均值，抖动比 3 轮中位大一档，gain 数字有 ±2% 误差；
  3. -Zthreads=2 那格用的是稳定 nightly、没开 headstart，是独立折中对照，别和 ON 那格混读。

核多型（16 核以上、依赖树深）、核少型（2-4 核、就想白捡）、纯看型（就看官方 54% 那串数怎么来的）——评论区晒你几核 + 依赖深度，攒够一批我出续篇：核多的人 -Zheadstart 实跑 54% 到底能不能复现。转给那个 cargo build 要等 20 分钟、又不敢把核心跑满的同事。关注「梦兽编程」，上一篇 Topcoat 在我这儿跑了个 36 行最小版，这篇讲它姊妹机制 Headstart。

常见问题

2 核值得自建 headstart 工具链吗？

不值得。我 2 核省 5.7%/3.2%，扣掉绕坑体力成本是负收益。8 核以上、依赖树深才值得等它合主线。

跟增量编译什么关系？

正交。增量是'没改的 crate 不重编'，headstart 是'干净全量编译时让下游抢跑'，不互相替代。

patch 合入主线没？

没，9 个 patch 在 review，现在只能自建工具链用；主线合入后 cargo -Zheadstart 一行开关。
