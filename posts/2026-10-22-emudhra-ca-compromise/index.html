eMudhra 8 张中间 CA 被破，私钥值小到个位数，我把该升级谁捋了一遍

印度 CA eMudhra 8 张中间证书私钥被破，值小到 4。浏览器修了不等于全网修了，Go/VPN/代码签名才是真雷区

October 22, 2026 · 2 min · 298 words · 梦兽编程 -  | 

这条安全事件我追了两天，因为它是近十年 WebPKI 里少见的「根信任地基被动一下、全球浏览器 + 操作系统 + 编程语言全跟着动」的案子。我把事实和该升级谁写清楚，数字都就地标源。

8 张中间证书，私钥值最小是 4#

印度 CA eMudhra 的 8 张中间证书（Global TLS 业务下，挂在一个 ECC 根 G3 下）私钥被一个化名 Wayne 的研究者破出。时间线按官方 + Mozilla 通报写（我未独立复现密钥破解过程）：

10-17 20:06 UTC Mozilla 收到报告；当天用 OneCRL 在 Firefox 封了这 8 张，22:59 推全用户、不用重启。10-18 晚 eMudhra 被告知，Wayne 同时通知了 Apple/Google/Microsoft/Mozilla。10-19 eMudhra 吊销全部 8 张、Apple 封禁。10-20 Microsoft 封、Firefox 出 158.0.1 + ESR 兜自定义设置用户。Chrome 10-17 当天封了 6 张 TLS 中间（8 张里 6 张 TLS、2 张代码签名）。

密钥到底多弱：BleepingComputer 核法——这 8 张用的 P-384 ECC 私钥正常应有 384 bit 随机熵，但这些值都小于 256，有的就是个位数。研究者把 eMudhra 一张证书的私钥公开了，值就是 4，也就是说试 256 个数以内就能解出任意一张。BleepingComputer 独立核过，公开 key 确实匹配被吊销的那张证书。

Wayne 怎么证明手里有 key：拿每张被破的 key 对同一句短消息签名——“We have a problem here – Wayne”。签名验过 = 他控制 key = 同样这把 key 能给任何域名签一张被信任的证书。这就是全网当天 scramble 的原因。

根因：不是没用 HSM，是仪式里某一步出了第二套弱 key#

eMudhra 官方通报：key 是在 FIPS 140-2 Level 3 认证的 HSM 上生成的，「没用 HSM」这种说法是错的。真正的坑在 2025-04-30 那场 Key Generation Ceremony——wrap/unwrap 那一步产生了第二套弱 key，跟正常强 key 的标签长得像，结果弱 key 被选去签证书了。这个问题从 2025 年 4 月到 10-17 暴露之间躺了约 18 个月，中间过了两次独立审计周期都没查出。Wayne 据报用 AI 辅助工具反推出了这些弱 key。

影响面官方 + Mozilla 通报：8 张里 7 张从没进生产；进生产的那 1 张也没发过任何一张终端证书（crt.sh 的 CT 记录佐证）。所以「被破 key 签发过的下游证书」= 0 张。真正被波及的是那个 ECC 根 G3 被根计划整体 de-trust（预防性），而 de-trust 波及到挂在 G3 下、属于同一个美国客户生态的证书——官方说那个生态正在换证书。

我重点想说的：这不是只浏览器的事，Go 和不查吊销的客户端才是真雷区#

浏览器靠 OneCRL / CRLite / CRLSets 动态吊销能覆盖，但三类客户端救不到：

Go 标准库：Go 的 crypto/x509 自带一套内嵌根证书池，不查吊销。Go 团队直接把这 8 张 SPKI 的 SHA-256 哈希列进 Go 1.27.3 / 1.26.10 的硬编码黑名单，出 CVE-2026-111943。换句话说，你 docker/k8s/terraform/prometheus 里任何跑 Go 的组件，不重 build 就还信任着这 8 张（它们能签任意域名的伪造证书）。

VPN / 内网代理 / 嵌入式 / IoT：大量客户端带独立 trust store、不消费 CRL，得软件更新才修。Cisco Talos 直接点了 VPN 是重灾区。

代码签名那 2 张（挂 Sectigo/Comodo 交叉签）：恶意软件可能拿去签「可信」软件，这条比 TLS 劫持更难兜。

该升级谁#

  • 浏览器：Firefox 升 158.0.1 / ESR 115.43.1 / 153.5.1；Chrome/Edge/Safari 已自动，但自定义证书设置的用户要确认 OneCRL 真推到了
  • Go 应用：全部重 build 到 1.27.3+ / 1.26.10+（docker 基础镜像、k8s 组件、CI 里的 Go 工具链一并）
  • VPN / 反向代理 / 内网证书中间件：软件出补丁就升
  • 企业 TLS 客户：eMudhra 官方说会给每个企业 TLS 客户加一张备用公开信任 CA 的证书做冗余，避免单根出事业务断
  • 数字签名 / eSign / emSigner / CertiNext / emCA / Privatrust / SecurePass：官方明确不受影响（跑独立基础设施），不用动

你们生产里有没有用 Go 做网络侧的组件？这块最容易因为「浏览器都修了」而漏掉。代码签名那 2 张，你们签名流水线里用没用过 eMudhra 签发的 code-signing 证书？
