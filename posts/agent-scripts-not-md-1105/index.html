你的 CLAUDE.md 写了 80 行规则，agent 还是不听——官方文档早说破了

AGENTS.md / CLAUDE.md 是建议层，不是约束层。把偏好翻译成脚本、hook、CI check，才是把 agent 装进盒子的方法。arXiv 2509.14744 分析了 253 个 CLAUDE.md，大多数操作性指令其实可以脚本化。

November 6, 2026 · 4 min · 852 words · 梦兽编程 -  | 

你仓库里躺着一份 CLAUDE.md，80 行，写得挺清楚：用 2 空格缩进、提交前跑测试、别动 src/gen/ 目录、用 snake_case。agent 每次会话开头把它读进去，然后照样给你写出 4 空格的代码、漏跑测试、顺手改了生成文件。你把规则改得再狠一点——「必须」「绝对不要」「每次都」——它也还是听一半。

问题出在哪。Anthropic 官方 best practices 里有一张表，把 Claude Code 的指令分成两类：非确定性（CLAUDE.md、prompt、skill）和确定性（hooks、deny rules、CI）。前者的定义是「你写指令，模型读，模型决定听不听」。后者是「harness 强制执行，模型没有否决权」。官方原话：CLAUDE.md is advisory. 一句话把 80 行规则的定位说死了。

核心论点：把「建议」翻译成「约束」。哪些规则该留在 CLAUDE.md，哪些该写成脚本、hook、CI check，怎么判断，以及 arXiv 2509.14744 那篇实证研究给出的 253 个真实 CLAUDE.md 里，到底有多少内容其实可以脚本化。

官方文档那张表，先把话说明白#

Claude Code 的 best practices 页面里有一张对照表，左右两列分别是「非确定性（Claude decides）」和「确定性（Claude Code enforces）」，把「做什么」「能碰什么」「什么时候算完」「花多少钱」「谁说了算」五个维度各列一行。

「做什么」那行：非确定性是 prompt、CLAUDE.md、skill——模型自己消化；确定性是 hooks，以及哪些 skill 只有你能启动。官方给的判断标准就一句：「Almost every guideline has exceptions, and current models are good at reading the code in front of them and judging whether a guideline fits the situation.」翻译过来：agent 大部分时候会自己判断该不该遵守你的规则，你写再狠的词也拦不住它「这次情况特殊」。

「谁说了算」那行最狠。非确定性是「Claude 的总结」——它告诉你它做了什么，你怎么理解随意。确定性是「branch protection、一个审批 merge 的人」——不管模型怎么说，merge 闸口它过不了。这就是 dev.to 那篇说的「把 agent 装进盒子里」的官方版本。

CLAUDE.md 官方文档还有一条硬数字：target under 200 lines per CLAUDE.md file。超过 200 行，每行都在每个会话里消耗 token，模型还会因为信息过载开始挑着遵守。80 行的 CLAUDE.md 已经是官方上限的 40%。

253 个 CLAUDE.md 里，大多数内容可以脚本化#

arXiv 2509.14744 分析了 253 个 CLAUDE.md 文件，来自 242 个开源仓库，是 2025 年 9 月发的，挂在 cs.SE 下。核心发现：

文件结构很浅。绝大多数只有一个 H1 主标题加若干 H2/H3 子节，深层嵌套（H4 以上）基本没有。这说明写 CLAUDE.md 的人自己也没想清楚怎么组织——就是想到什么写什么。

内容分布：Build and Run（构建运行命令）占比最高，其次是 Implementation Details（实现细节）和 Architecture（架构说明）。Build and Run 这一类——「跑 make test」「npm run lint」「用 go 1.22」——全是操作性指令，每一条都可以直接写成 Makefile target、shell 脚本、pre-commit hook。写进 CLAUDE.md 的唯一理由是「agent 不知道去哪找命令」，但你把命令写成 make test 放进 Makefile，agent 跑 make test 比读一段自然语言描述更可靠。

50% 的文件包含 system overview（系统概述）。这部分是 CLAUDE.md 真正该留的内容——agent 光读代码推断不出来的项目背景、为什么选这个架构、哪个目录是遗留代码。但它是「上下文」不是「规则」，和脚本化不矛盾。

研究没做的一步：统计有多少行内容是「可执行指令」而非「背景说明」。253 个文件里，Build and Run 类占比最高意味着至少有一部分内容天然适合转成脚本。这个精确数字论文没给，但结构已经很清楚了。

四个场景，四种转法#

这是核心段落。拿四个真实场景，展示怎么把 CLAUDE.md 里的一行规则变成可执行的检查。

「用 2 空格缩进，Prettier 格式」

CLAUDE.md 写法：Use 2-space indentation. Run prettier after editing.

agent 听不听随缘。翻车场景：它改了 20 个文件，其中 3 个还是 4 空格，因为它「觉得这个文件本来就是这样」。

脚本化：pre-commit hook 加一条 prettier check，CI 加 required check。agent 写完代码，git commit 时 hook 自动跑 prettier –check，不通过 commit 直接被拦。它改不改？它得改，因为它自己得 commit。CLAUDE.md 那行删掉，省 token。

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/prettier/prettier
    rev: 3.4.2
    hooks:
      - id: prettier

# .github/workflows/ci.yml
- name: Lint & Format
  run: |
    npx prettier --check .

agent 跑 git commit，pre-commit hook 触发，prettier 报 3 个文件不合规，agent 看到错误，跑 npx prettier --write，再 commit。整个过程不需要它「记得」任何规则。

「提交前跑测试」

CLAUDE.md 写法：Always run tests before committing. Use npm test.

agent 偶尔会忘，尤其是它改了很多文件之后「觉得改完了」。

脚本化：pre-commit hook 加 npm test，或者更狠——把测试放进 CI required check，agent 开 PR 之后 CI 跑，红了它得修。本地 hook 它可以绕（--no-verify），CI required check 它绕不了，因为 merge 闸口在 GitHub 那边，它没有权限改 branch protection。

# .git/hooks/pre-commit（或用 pre-commit 框架）
npm test || exit 1

「别动 src/gen/ 目录」

CLAUDE.md 写法：Never edit files in src/generated/

agent 有时候会「顺手」帮你把生成文件里的东西也改了。

脚本化：Claude Code 的 PreToolUse hook。这是官方支持的确定性强制层，写进 .claude/settings.json：

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-gen.sh"
          }
        ]
      }
    ]
  }
}

#!/usr/bin/env bash
# .claude/hooks/protect-gen.sh
# 读 PreToolUse 的 JSON 输入，检查目标文件是否在 src/generated/ 下
# 是 → exit 2（拦截），否 → exit 0（放行）
input=$(cat)
file=$(echo "$input" | jq -r '.tool_input.file_path // empty')
case "$file" in
  */src/generated/*)
    echo "BLOCKED: $file is in generated code. Do not edit." >&2
    exit 2
    ;;
esac
exit 0

exit code 2 是 Claude Code 的拦截信号：PreToolUse 阶段 agent 的这次工具调用直接被跳过，agent 在对话里看到 stderr 的错误信息。它知道「不能动 src/generated/」不是因为读了 CLAUDE.md，而是因为 hook 拦了它。CLAUDE.md 那行可以删，也可以留着当「说明为什么」，但约束力来自 hook。

「把 20 个文件的 foo() 改成 bar()」

CLAUDE.md 写法：When refactoring, rename foo to bar across all files.

agent 要自己判断哪些文件包含 foo，哪些该改哪些不该改（比如字符串里的 foo 不是函数名）。它可能改漏，也可能改错。

脚本化：ast-grep。它基于 tree-sitter，做结构性匹配，不靠字符串搜索。写一条规则：

# .ast-grep/rg-foo-bar.yml
rule:
  pattern: foo($ARG)
  language: python
rewrite: bar($ARG)

sg run -r .ast-grep/rg-foo-bar.yml .

agent 跑这一条命令，ast-grep 自己找所有 foo(...) 调用点，全部改成 bar(...)，不改字符串、不改注释、不改 foo_bar 这种命名。改完 agent 跑测试验证，红了再修。它不需要「理解」重构规则，只需要跑脚本、读结果。

什么时候 CLAUDE.md 仍然不可替代#

不是所有规则都能脚本化。CLAUDE.md 真正该留的，分两种。

一种是 agent 光读代码推不出来的背景。「src/legacy/ 目录是 2019 年的老架构，新代码别往里加功能」「这个项目的部署走 AWS CodeDeploy，不是 k8s」「错误处理统一用 Result，不用 panic」——这些是「为什么」，不是「怎么做」。脚本只能检查「你做没做」，检查不了「你为什么这么做」。

另一种是审美判断和架构权衡。「这个函数太长了，拆一下」「这里用设计模式过度了，直接写」——没有确定性 pass/fail 标准，只能人（或 agent 在人的指导下）判断。

官方的说法是：CLAUDE.md 里每一行问自己「删掉这行 agent 会不会犯错」。如果会，但错的是「不知道这个项目的背景」，留 CLAUDE.md。如果错的是「没跑测试」「动了生成文件」「格式不对」，写成 hook 或 CI。

工具链全景，从本地到 merge 闸口#

完整的约束链，从 agent 动手到代码进 main，经过几道关：

本地：pre-commit hook（格式化、lint、secret 扫描）→ agent 自己 commit 时被拦。Claude Code PreToolUse hook → agent 在会话内改文件时直接被拦，不用等 commit。

PR：GitHub Actions required checks（全量测试、type check、build）→ agent 开 PR 后 CI 跑，红了 merge 按钮是灰的。Agent Evidence Gate（agent-evidence-gate 项目）→ 检查 PR 里的 evidence 文件是否真的跑了测试、有没有动 protected path、diff 是否超过 25 个文件上限。

merge：branch protection（至少 1 个 approval）→ 这是最后一道闸口，agent 没有 GitHub 权限改 branch protection，只有人能。

agent 能跳过的：本地 pre-commit（--no-verify）。能跳过的程度有限，因为 CI 还有一道。跳不过的：CI required check、branch protection、Claude Code hook（harness 强制执行）。

「agent 能跳本地 hook，所以要用 CI 兜底」——这个判断在 git hook 层面成立，但 Claude Code 的 PreToolUse hook 不一样：它不是 git hook，是 agent 框架层面的拦截，agent 没有 --no-verify 可以绕。

一个翻车案例：agent 绕了 md 没绕 hook#

某团队（agent-readiness 项目作者描述的场景）在 CLAUDE.md 里写了「提交前必须跑 npm test」。agent 前几次都跑了，后来有一次它「觉得这次改动很小」没跑，直接 commit 了。代码合进 main，CI 红了，线上出 bug。

他们把测试改成 pre-commit hook + CI required check。agent 再「觉得改动小」也没用——git commit 时 hook 自动跑测试，不通过 commit 失败；就算它 --no-verify 绕了本地，CI 还会拦一次，merge 按钮是灰的。agent 只能老老实实把测试跑绿。

agent-readiness 项目本身是另一个方向：不检查 agent 的行为，检查你的仓库是否「准备好了」让 agent 进。17 个 governance 信号，0-100 分，pip install agent-readiness-cli 跑一下。分数低于 70 的仓库，agent 进去大概率乱改。这和「把规则写成脚本」是同一个思路的两个方向：一个约束 agent 的行为，一个确保仓库本身结构清晰到 agent 不会迷路。

agent-readiness（chevy155）：17 个治理信号，0-100 分，pip 包，无 LLM 调用，无遥测。

FAQ#

Q：CLAUDE.md 和 AGENTS.md 是同一个东西吗？ A：功能类似，受众不同。CLAUDE.md 是 Claude Code 读的，AGENTS.md 是 Codex 等工具读的（Thoughtworks 2025 年 11 月把 AGENTS.md 放进了 Technology Radar，评「Trial」阶段）。核心逻辑一样：都是建议层，都不是约束层。

Q：hooks 里的 command type 和 agent type 有什么区别？ A：command hook 跑 shell 脚本，模型没有参与，完全确定性。agent hook 让另一个模型做判断（比如「这次改动是否涉及安全敏感代码」），有判断就有不确定性。enforce-hooks 项目专门强调：只有 command type 的 hook 能真正拦截工具调用，agent type 的 hook 在某些事件（如 SessionEnd）会被静默跳过。

Q：CI required check 能防住 agent 自己改 CI 配置吗？ A：CI 配置文件（.github/workflows/*.yml）本身是代码，agent 可以改它。防法：把 CI 配置放进 branch protection 的 protected path，agent 改了 CI 的 PR 本身过不了 required check（因为改了 protected path 需要人工审批）。agent-evidence-gate 读 PR base SHA 的 AGENTS.md 也是这个逻辑——策略文件从 base 分支取，不从 PR 分支取，agent 改 PR 里的 AGENTS.md 没用。

Q：prettier + pre-commit hook 会拖慢 agent 的迭代速度吗？ A：pre-commit 跑 prettier –check 大概 2-5 秒（取决于仓库大小），agent 每次 commit 等这几秒。对比：agent 不跑 prettier，CI 再跑一次，红了再改再 commit，来回两轮，每轮 10 秒起步。本地 hook 反而更快。

Q：agent 跑 ast-grep 重构之后，测试红了怎么办？ A：测试红了就是 ast-grep 规则写得太宽，或者重构涉及语义变化（不只是改名）。agent 读测试错误，判断是规则问题还是语义问题：规则问题改 .ast-grep 规则重跑；语义问题（比如 foo() 和 bar() 行为不完全等价）需要 agent 手动处理那几个特殊调用点，不能全交给 ast-grep。这是「判断力」该出场的地方，不是脚本能替代的。

诚实声明#

本文引用的 Claude Code hooks 文档、best practices 表、arXiv 2509.14744 数据均来自公开来源，未在本机独立复现 agent 绕 CLAUDE.md 的具体频率（「偶尔不听」是经验观察，不是统计数字）。agent-evidence-gate 和 agent-readiness 两个项目的功能描述基于其 README 和源码，未在本机跑过完整测试流。

常见问题

CLAUDE.md 和 AGENTS.md 是同一个东西吗？

功能类似，受众不同。CLAUDE.md 给 Claude Code 读，AGENTS.md 给 Codex 等工具读。核心逻辑一样：都是建议层，不是约束层。

CI required check 能防住 agent 自己改 CI 配置吗？

能。把 CI 配置放进 branch protection 的 protected path，agent 改了 CI 的 PR 本身过不了 required check。
