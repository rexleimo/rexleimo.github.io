OCR 引擎 RustO! 把 OpenCV 那套 C++ 全拆了：视觉层用 Rust 重建轮廓、裁剪、变形，推理层用 RTen 跑 PaddleOCR 的 PP-OCRv6 模型，不碰 g++，不链 .so，整个 CLI 5.5MB。我拉了仓库在本机 2 核 EPYC 上编译跑通：3 分 25 秒编完 0 警告，运行时依赖只有 5 行系统库，一张中英混排发票热态 1.2 秒。下面的数字全是本机跑出来的。

它要拆掉什么#

二十年下来，从 Tesseract 到 PaddleOCR，几乎每条 OCR 流水线都把 OpenCV 当成物理定律：模型只干检测和识别，把整条管线粘在一起的图像处理全在 OpenCV 里。代价是部署：动态链接的 .so 版本对不上，服务启动就崩；每张图在 cv::Mat 和推理张量之间来回拷；跨 macOS、Android、iOS 维护一整套 CMake 工具链。作者先试过 Rust FFI 包一层，几周 Android NDK 链接错误和竞态后得出结论：包 C++ 不解决 C++ 的问题。所以直接重写。

重写怎么做的：三个原语，一个推理层#

拆掉 OpenCV 后要自己实现的图像操作其实只有三件。DBNet 检测模型吐概率热图，传统做法调 findContours 变文字多边形；RustO! 用 Suzuki 边界跟踪法在纯 Rust 里扫二值化字节缓冲区，直接出外边界和内孔，不建中间矩阵。第二件是「反裁剪」：DBNet 训练时刻意把检测框缩小，好把相邻文字行分开，所以检测出的多边形偏小，要用 Vatti 多边形裁剪按 1.6 倍膨胀还原回真实文字框，官方说几何一致度 99.3%。第三件是并行：一张发票 30 到 60 个框，每个要裁剪、旋转、透视变形成标准横条再进识别，Rayon 一行 par_iter 铺满所有核。

推理引擎走过弯路：早期试阿里 MNN，快，但把 C++ 工具链问题重新请回来了（CMake、私有 .mnn 模型转换、可变 session 配置把多线程 web 服务搞崩）。0.3 起换 RTen，纯 Rust 的张量运行时：读 .rten 的 FlatBuffers 模型，权重走 mmap 直接从盘映到虚拟内存，多个进程共享同一份物理页，微虚拟机和容器场景内存开销砍一半。另外两个设计值得记：推理引擎抽象成 InferenceSession trait，想换 TensorRT 或 CoreML 就传自定义实现，管线不用改；初始化拆成 InitializeConfig（静态只读，一次加载进 Arc 全线程共享）和 OcrRunOptions（每请求无状态，按引用传），零锁，线程安全由借用检查器在编译期保证。

「零 C++」得带版本号#

0.3.1 的多边形裁剪依赖 geo-clipper，底层是 C++ Clipper，构建时要 C++ 编译器。10 月 25 日发的 0.3.2 换成了纯 Rust 移植的 clipper2-rust，当前依赖树里没有 clipper-sys。本机编 0.3.2 全程没装 g++：ldd 列出来 libgcc_s、libm、libc、ld 加 vdso 共 5 行，没有 libstdc++，没有 opencv，没有 MNN。二进制 du 量出来 5.5M，官方说 5.4MB，同一量级。

2 核上跑多少#

热态取法：模型加载后循环 5 遍取中位。Tiny INT8 在我这张 40 个文本块的中英发票上 1211 毫秒，仓库自带老发票 21 块 500 毫秒，Small INT8 同张 2624 毫秒，峰值内存 312MB。官方给的 70 到 87 毫秒没写硬件，RTen 推理线程数等于物理核数，这台机器只有 2 核，两边数字各挂各的机器，不互驳。识别精度：英文和数字全对，银行账号逐位正确；中文 30px 字号 4 组全对，34px 的「咨询服务」「年度维护」两组输出成占位方框，Tiny 和 Small 两档一样。

跨平台那几张表#

README 给了一组自报对照（未独立复现）：自包含 CLI 5.4MB 对 OpenCV+ONNX 的 50MB 以上；WASM 包 848KB 对 Emscripten 的 30MB 以上；Android 单 ABI 1.8MB 对 20MB 以上。两套依赖栈并排见图。浏览器端能纯客户端跑 OCR，文档不出设备，不付 API 费；PP-OCRv6 一个字典覆盖 50 多种语言，输出粒度还能选 2D 空间布局——读发票和财报时词间位置关系比字符本身重要，它把词聚成几何行、算出表格列和缩进，坐标数组和可读文本双路输出。

这个项目算什么#

70 颗星、crates.io 累计 1001 次下载、单人维护、MIT。它证明的是「Paddle 模型 + RTen 运行时 + 纯 Rust 视觉层」这条路线能走通，不是 PaddleOCR 的替代。没有 C++ 工具链约束的部署环境（WASM、serverless 小镜像、移动端）是它的主场；要生产级中文文档精度，得用 Medium 档 75.7MB 模型或官方 Paddle 栈，INT8 小模型的中文档差就挂在上面那张图里。

常见问题#

RustO 和 PaddleOCR 什么关系？ 模型都是 Paddle 的 PP-OCRv4/v5/v6，RustO 只是执行壳：同一套 .rten 模型，运行时从 C++ 换成 Rust。要全功能（GPU、更多后处理）还是官方栈。

零 C++ 现在指什么？ 0.3.2 构建时和运行时都成立：默认依赖树无 C++ 源码 crate，ldd 无 libstdc++。0.3.1 只成立运行时，构建时 clipper-sys 要 C++ 编译器。版本号不同，结论不同。

中文什么水平？ 本机 30px 中文全对、34px 两组输出占位框（Tiny/Small INT8 一致），英文数字不受影响。想要稳的中文精度换 Medium 档模型，那档我这次没测。

能上生产吗？ 规模和成熟度都还是实验阶段。部署环境选型可以拿它当架构参考，文档解析进生产前，先用自己的文档集测一遍精度。

怎么复现？ git clone 仓库，cargo build –release，从 GitHub releases 下 Tiny INT8 模型包，二进制加 det、rec、dict 三个参数跑图，全程不需要 C++ 工具链。

诚实声明：编译 3m25s、二进制 5.5M、ldd 5 行、热态 1211/500/2624 毫秒、峰值内存 312MB、识别 40 块中文 6 组对 4，全部为本机实测（2 核 EPYC 9354P，rustc 1.99.0，rusto-rs 0.3.2，Tiny/Small INT8 模型，2026-10-30）。70-87ms、85-120MB、跨平台体积对照、99.3% 几何一致度为项目 README 自报，未独立复现。
