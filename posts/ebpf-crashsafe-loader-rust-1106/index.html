eBPF 程序活得比你的进程长：Rust 写数据面，崩溃恢复才是真难点

挂在网卡上的 eBPF 程序，加载它的进程死了之后还活着。用 aya 写数据面不难，难的是启动时对账、崩溃恢复、清理——把 bpffs 的 pin 树当成唯一事实源，三个动作归约成同一次目录遍历。

November 6, 2026 · 3 min · 437 words · 梦兽编程 -  | 

控制面崩了，数据面还在跑#

做 eBPF 网络项目的人都会撞到同一个问题：挂在网卡上的 eBPF 程序，加载它的用户态进程死了之后还活着。内核 bpf(2) 手册的原话是，程序「会继续存活在内核里，即使加载它的进程已经退出」——具体存不存活，取决于它 attach 到了什么内核子系统。

这是 eBPF 数据面的卖点：控制面崩溃不丢流量。但反过来说，控制面永远不能假设自己拥有这份状态。你的进程每次启动，面对的都不是白纸。

「安装」一个 eBPF 程序其实是三步#

习惯上把「安装 eBPF 程序」当成一个动作，其实是三个，各自产出一个独立内核对象。

eBPF 官方站（ebpf.io）架构图：用户态应用经 Kernel Runtime 把程序送进内核，verifier 和 map 都在这一层（原文为 svg，已转 png）

Load：把解析好的指令流提交给内核，verifier 静态证明它安全——无越界内存访问、循环有界、内核指针不会泄漏——通过后拿到一个 program object。

Attach：把加载好的程序接到 hook 上（比如某个网卡），产出另一个对象：link，代表这一次具体的挂载关系。

Pin：给内核对象在 /sys/fs/bpf 这个特殊文件系统里起一个持久名。pin 不是什么玄学，就是一个命名了的、持久的引用。

三步分开写有意义，因为各自回答的问题不一样。Load 回答「这段代码能不能跑」，Attach 回答「在哪跑」，Pin 回答「创建它的进程死了它还在不在」。后面所有设计都绕着最后一个问题转。

启动时可能撞上的残留状态#

进程死掉的那一刻，内核侧留下什么，取决于死在哪一步。

已 attach 的程序：上次运行挂好的程序和 link 还在跑。孤儿 pinned 对象：map 和 link pin 在 bpffs 里，但进程死在「attach 完了、账还没记完」的中间态，这些对象成了没有主人的孤儿。半挂 endpoint：某个端点的一部分 hook 接好了，另一部分没接——崩溃就发生在中间。

这三类状态是后面架构决策的直接来源。

文件系统即状态#

这个设计最早期的一个决策，是把 bpffs 的 pin 树当成唯一可信的「实际在跑什么」的表示，用户态不维护任何影子状态。

为什么不用用户态数据结构（比如一个 endpoint 的 HashMap）。进程崩了，内存态全丢，盘上 pin 树还在，影子状态和内核实际状态就分叉了。而对账、重启恢复、清理这些动作，一旦归约成同一次目录遍历，就变成同一个问题而不是三个独立的一致性问题。

这个设计还顺带让 attach 和 detach 变成幂等的。已经 attach 的端点再 attach 一次，内核态不动；部分 attach 过的端点 detach，只删实际存在的 pin。正常运行和崩溃恢复走的是同一条路径：把 pin 树调整到期望状态。没有单独的恢复逻辑。

崩溃后对账时序（自画）：bpffs pin 树是唯一事实源，对账 / 重启恢复 / 清理归约为同一次目录遍历，attach/detach 幂等，正常运行与崩溃恢复走同一条代码路径

阻塞的内核调用，交给独立 actor#

控制面其余部分是常规 async Rust：tokio 运行时，netlink 异步操作，假设阻塞一个任务就是 bug。但加载 eBPF 对象、把程序 attach 到 hook、pin 内核对象，是同步操作，verifier 对大程序能吃掉可观的墙上时间。这些活儿放到 tokio worker 上，会把排在这个 worker 上的其他任务一起拖死。

解法是一个独立 OS 线程上跑的小 actor：它独占 loader，从 channel 收命令——加端点、删端点、对账、列出当前活跃端点。async 侧通过 channel handle 通信并 await 结果。阻塞只阻塞 actor 本身。

串行执行还顺手解决了并发控制：对同一端点的 add 和 remove 按定义顺序执行，没有锁，也没有 pin/unpin 竞态这一类问题。

没有内核也能测#

eBPF 代码和它的 loader 没法在普通单元测试环境里跑：内核执行态没有，用户态侧要 CAP_NET_ADMIN 和可写 bpffs。

做法是把 loader 边界做成 trait。生产实现走真 loader 加 syscall；测试实现是内存版 pin 树模型，可以在序列任意位置注入失败。于是崩溃类用例可以这么写：在加载后崩溃、在 attach 一半崩溃、在清理到一半崩溃，断言崩溃留下的 pin 树状态，从那个状态重启，验证对账结果和干净运行一致。全程不需要 root、不需要命名空间、不需要真内核。

真内核的集成测试只覆盖必须内核在场的部分：命名空间隔离、veth 搭建、真实 attach/detach。

数据绑定是永久的，多实例三选一#

加载好的 eBPF 程序，它用的 map 在加载时就解析成具体内核对象、写进指令流，之后 verifier 验证的就是这条指令流。没有事后重绑这回事。同一个程序对着不同 map 加载两次，是两个独立的 program object，不存在一个共享程序在运行时切配置。

多个逻辑实例（容器、端点、隧道）要共享程序逻辑、数据隔离，就三个选法：

per-instance 加载 + 改名 mapmap-of-maps单个 keyed 共享 map
verifier 跑几次每实例一次一次一次
实例频繁增删时成本线性涨平平
实例间隔离完全（独立对象）完全（独立内层 map）无（共享一张表）
每包查找成本一跳两跳一跳
容量与生命周期各自独立各自独立全部共享

per-instance 加载买的是完全隔离和简单清理，代价是每个端点生命周期内 verifier 跑一遍。map-of-maps 省掉加载成本，多一跳查找，还多一张用户态要维护对的间接表。共享 keyed map 最省，但容量和生命周期全绑死在一个 map 上，一个吵闹实例吃掉别人要的配额。

这个项目取 per-instance 加载加改名 map 这条路线：每个端点自己加载一遍程序、绑定端点专属的 map。当前规模下 verifier 成本可以接受；等端点频繁增删成了瓶颈，map-of-maps 是自然演化路径——程序逻辑不变，只换数据绑定模型。

别造多余的 ID#

per-instance 改名 map 之后马上冒出一个问题：改名叫什么。这个实现早期版本给某类端点造了一个合成数字 ID，基于一个假设的内核命名约束。后来那个约束被验证在别处也成立，这个多余 ID 就没有存在价值，删了。

网卡名本身就是对的 identity：内核提供、作用域内已唯一、边界由内核自己的限制框好。pin 路径由（端点种类，网卡名）派生，发现状态靠遍历这个结构，不需要另建索引。规则可以写成一句话：identity scheme 只包含问题本身要求的结构，每多一个标识符，就多一块要分配、要传播、要保持一致的状态。

内核侧的 pinning 有自己的脾气#

难啃的几个 bug 不是用户态设计出来的，是内核行为假设错了。

pin 是声明在对象上的，不由 loader 的调用推断。一个没开 pinning 的 map 或 link，就算 loader 传了 pin 路径，也不会出现在 bpffs 里。修法很直接：每个要活过重启的对象，显式声明 pinning。

stale pin 是另一类。pinned link 比它挂的网卡活得更久的情况真实存在：qdisc 被删、chain 被 flush，bpf_link 就断了，而 pin 还在。复用同一个 pin 路径之前，必须先探测并移除残留对象，否则新 attach 会因为路径被占直接失败。

所以内核状态迁移本身就是设计的一部分。真正重要的测试不是 happy path，是它周围的迁移：崩在第 N 步之后、设备删了 pin 还在、从半挂状态恢复。

可观测性被同一约束拖着走#

加载时绑定这条规则不只作用于数据 map，也作用于日志。eBPF 日志（aya-log）走 ring-buffer map，这个 map 在程序加载时就绑定了。既然按端点加载程序，每个端点自然有自己的日志流，这是同一个隔离模型的推论，不是独立的日志设计。

于是日志拉取的句柄必须随端点生命周期存活：没有读者，端点的日志流就成了没人清的缓冲。拉日志在端点加载时开始，在端点删除时停止。没有全局日志配置这回事，日志是端点状态机的一部分。

aya：这套东西的底座#

整个实现架在 aya 上。这个库的定位写得很清楚：纯 Rust 实现 eBPF，不依赖 libbpf 和 bcc，只靠 libc crate 走 syscall，BTF 加 musl 做到「编译一次到处运行」。GitHub API 拉数（2026-11-06）：4893 star、484 fork，51 个 release、127 个贡献者，语言构成 99% Rust。

难点到底在哪#

这个项目自己的转发逻辑（路由、ARP、策略）按作者说法还是 stub，真正 built out 的是底下这层加载器。原文明确把话说死了：数据面底下的生命周期管理是它自己的工程问题，有自己的失败模式——崩溃恢复、部分状态、陈旧内核对象、跨内核边界测试。

设计决策还会跨子系统传导：「按实例加载」这一个选择，同时决定了数据归属、清理方式、连可观测性的形态。把状态迁移做成显式且可恢复，转发逻辑才有地方可以往上盖。

FAQ#

Q：eBPF 程序为什么比加载进程活得久？ attach 到内核子系统（网卡、qdisc、tracepoint）之后，程序的生死由内核侧对象引用决定，不由用户态进程决定。bpf(2) 原话：「程序会继续存活在内核里，即使加载它的进程退出」。这是 eBPF 数据面能扛控制面崩溃的前提。

Q：crash 之后怎么知道内核里现在到底挂着什么？ 遍历 bpffs 的 pin 树。pin 是内核侧持久状态在用户态可见的唯一表示，把 pin 树当单一事实源，对账和恢复就变成目录遍历，不需要维护用户态影子状态。

Q：verifier 很慢，卡在 async 运行时上怎么办？ 把阻塞的内核调用隔离到独立 OS 线程（actor 模式），channel 通信。verifier 耗时再长也只阻塞 actor，不影响 tokio worker 上的其他任务。

Q：多个实例共享一份 eBPF 程序逻辑，数据怎么隔离？ 程序加载时 map 绑定是永久的，不能运行时重绑。三种选法：per-instance 加载加改名 map（全隔离，verifier 每实例跑一次）、map-of-maps（省加载、多一跳、共享间接表）、单个 keyed 共享 map（最省、容量生命周期全共享）。端点频繁增删时选 map-of-maps。

Q：不造合成 ID、直接用网卡名做 identity，什么情况下会翻车？ 网卡名在「同命名空间内唯一、作用域由内核限定」这个语义成立的前提下够用。跨命名空间、或者一个端点对应多张网卡（bonding）的场景，需要扩展 identity 结构——但扩展也要从内核已有的结构派生，不是另起一套编号。

资料出处#

机制与全部设计决策来自 Erwin Kok 的 Building a Crash-Safe eBPF Dataplane Loader in Rust（2026-08-06），实现代码在 github.com/erwin-kok/sarena：https://erwinkok.org/posts/ebpf-dataplane-loader/ 。

内核侧行为以官方文档为准：bpf(2) 的进程退出段落（man7.org）、内核 tree 里 bpftool 的 prog/map/link pin 文档（「FILE 必须位于 bpffs 挂载点」）、libbpf 对象 pinning 的 LWN 存档（2017，lwn.net/Articles/712690/）。

诚实声明#

「转发逻辑还是 stub」「verifier 成本可接受」等判断来自项目作者本人描述，未独立复现。多实例三方案的取舍基于原文对比表，本机没搭 eBPF 数据面跑过崩溃恢复演练，以上机制描述以原文与内核文档为准。

你是哪一派#

你做 eBPF 项目，恢复逻辑放在用户态影子状态里还是文件系统里？评论区说下你的 attach 方案碰过哪类 stale 状态，攒够一批出个「eBPF 数据面崩溃恢复模式对照」的续篇。

转给那个还在担心「控制面崩了内核里一堆孤儿对象没人管」的同事。
