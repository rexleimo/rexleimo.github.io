Rust 1.99：C 风格可变参数第一次能在 Rust 里写——我写了个 Rust 版求和函数让 C 代码来调

Rust 1.99.0（10-01 发布）把 extern "C" variadics 推进 stable：Rust 第一次能定义（不只是调用）C 风格 ... 函数，ABI 对齐 C 的 va_list。本机 stable 工具链实测：C 代码调 Rust 可变参函数，i32 求和 / C 字符串指针 / 混合 ABI 交错三组全对上，全程无 #![feature] 门。顺手验了 1.99 另外两个新稳定 API：Vec::into_parts、String::from_utf8_lossy_owned。

October 7, 2026 · 4 min · 762 words · 梦兽编程 -  |  English

Rust 跟 C 打交道有个 30 多年的老断档：C 的可变参数（printf 那种 ...），Rust 以前只能调用、不能定义。10 月 1 日发布的 1.99.0 把这个断档接上了——extern "C" variadics 进 stable，std::ffi::VaList 随包提供。我在本机 stable 工具链上把闭环走通：Rust 定义三个可变参函数，C 代码调用，C 端独立算期望值对答案，三组全过，全程一行 #![feature] 都不用写。 这篇把可复现代码、C 端驱动、以及 1.99 顺手新稳定的两个 API（Vec::into_parts、String::from_utf8_lossy_owned）全贴出来。

先说结论：三个事实#

  1. ... 语法在 1.99 stable 直接可用：pub unsafe extern "C" fn f(n: u32, ap: ...) -> i64，无需任何 feature 门（本机 rustc 1.99.0 编译通过）。
  2. 定义可变参函数必须是 unsafe fn：这是 rustc 明确强制的（报错原文见下），不是可选项——可变参读取没有类型系统兜底，unsafe 语义是入口。
  3. VaList 与 C va_list ABI 一致：next_arg 等价 va_arg、clone 等价 va_copy、drop 等价 va_end，且可跨 FFI 边界传递（官方文档原话）。

Rust 侧：三个可变参函数（stable 原样可编）#

// variadics.rs —— rustc --edition 2021 -O 直接编译，无 feature 门
use std::ffi::{c_char, VaList};
use std::os::raw::c_void;

/// i32 求和：count 个可变参
#[no_mangle]
pub unsafe extern "C" fn sum_i32s(count: u32, ap: ...) -> i64 {
    let mut va: VaList = ap;
    let mut sum: i64 = 0;
    for _ in 0..count {
        sum += unsafe { va.next_arg::<i32>() } as i64;
    }
    sum
}

/// 可变参里传 C 字符串指针，Rust 侧读回
#[no_mangle]
pub unsafe extern "C" fn first_cstr(ap: ...) -> *const c_char {
    let mut va: VaList = ap;
    unsafe { va.next_arg::<*const c_char>() }
}

/// 混合类型：定参 i32 + 可变参里 指针、i32 交错（验证 ABI 位置对齐）
#[no_mangle]
pub unsafe extern "C" fn mix3(a: i32, ap: ...) -> i64 {
    let mut va: VaList = ap;
    let p = unsafe { va.next_arg::<*mut c_void>() };
    let b = unsafe { va.next_arg::<i32>() };
    (a as i64) * 1000 + ((p as usize) >> 48) as i64 + b as i64
}

// 入口：Rust main 调 C 侧的测试驱动器（见 c_harness.c）
extern "C" { fn c_run(ok: *mut i32); }
fn main() {
    let mut ok: i32 = 1;
    unsafe { c_run(&mut ok) };
    if ok != 1 { std::process::exit(1); }
}

注意三个定义的写法都是 unsafe extern "C" fn ... ap: ...——编译第一版时我漏了 unsafe，rustc 的报错原文是：

error: functions with a C variable argument list must be unsafe
  --> variadics.rs:13:40
   |
13 | pub extern "C" fn sum_i32s(count: u32, ap: ...) -> i64 {
   |                                ^^^^^^^
help: add the `unsafe` keyword to this definition

定义即 unsafe，这条要写进你的肌肉记忆：可变参函数是 FFI 边界，没有类型系统给你兜底。

C 侧：调用 + 独立对答案#

// c_harness.c —— gcc -c c_harness.c -o c_harness.o
#include <stdio.h>
#include <stdint.h>

extern int64_t sum_i32s(uint32_t count, ...);   // Rust 侧 #[no_mangle] 导出
extern const char* first_cstr(...);
extern int64_t mix3(int32_t a, ...);

void c_run(int32_t* ok) {
    // 1) i32 求和：C 端自己先加一遍
    int32_t vals[5] = {42, -7, 20, 100, -1};
    int64_t expect = 0;
    for (int i = 0; i < 5; i++) expect += vals[i];
    int64_t got = sum_i32s(5, 42, -7, 20, 100, -1);
    printf("[sum]  期望(C自算)=%lld  Rust变参=%lld  %s\n",
           (long long)expect, (long long)got, got == expect ? "一致" : "!!不一致!!");
    if (got != expect) *ok = 0;

    // 2) 可变参里塞 C 字符串指针
    const char* s = first_cstr("hello-from-rust");
    printf("[cstr] Rust 读回指针 -> %s\n", s ? s : "(null)");
    if (!s || s[0] != 'h') *ok = 0;

    // 3) 混合 ABI：定参 7 + 可变参里 指针、i32 交错
    int32_t b = 3;
    void* p = (void*)0xABCDUL;          // 32 位地址，>>48 = 0
    int64_t expect3 = (int64_t)7 * 1000 + ((uintptr_t)p >> 48) + b;
    int64_t got3 = mix3(7, p, b);
    printf("[mix]  期望=%lld  Rust变参=%lld  %s\n",
           (long long)expect3, (long long)got3, got3 == expect3 ? "一致" : "!!不一致!!");
    if (got3 != expect3) *ok = 0;

    printf("\n== %s ==\n", *ok ? "ALL PASS (C 调 Rust 可变参)" : "FAILED");
}

本机实测结果（rustc 1.99.0 / gcc 13.3，x86-64）#

$ gcc -c c_harness.c -o c_harness.o
$ rustc --edition 2021 -O variadics.rs -o var-test -C link-args=c_harness.o
$ ./var-test
[sum]  期望(C自算)=154  Rust变参=154  一致
[cstr] Rust 读回指针 -> hello-from-rust
[mix]  期望=7003  Rust变参=7003  一致

== ALL PASS (C 调 Rust 可变参) ==

三组全过。第 1 组校验的是 next_arg::<i32> 跨 FFI 读整型；第 2 组是读指针型；第 3 组故意把定参和可变参交错，验证寄存器/内存位置对齐（x86-64 SysV ABI 下第 4 个参数起走栈，指针与 int 交错时最容易出错位）。

一个方法论点：校验口径是 C 端独立算期望值，不是"Rust 说什么都对"——加法在 C 里做一遍，Rust 只负责从 VaList 把值读出来，两边一致才说明 ABI 没错位。

1.99 顺手新稳定的两个 API（同批验过）#

Vec::into_parts / Vec::from_parts——把 Vec 拆成 (ptr, len, cap) 再拼回，from_parts 是 unsafe：

let v = vec![10, 20, 30, 40];
let (ptr, len, cap) = v.into_parts();
let v2 = unsafe { Vec::from_parts(ptr, len, cap) };
assert!(v2 == vec![10, 20, 30, 40] && v2.capacity() == 4);   // 本机过

String::from_utf8_lossy_owned——坏 UTF-8 做有损替换并保留 owned 语义，不再需要先 from_utf8 失败再手工 into_owned：

let bad: Vec<u8> = vec![0x41, 0xff, 0xfe, 0x42];   // A + 两个坏字节 + B
let s = String::from_utf8_lossy_owned(bad);
// s = "A\u{FFFD}\u{FFFD}B"，长度 8，恰好 2 个 U+FFFD

本机对照旧写法（from_utf8 失败 → from_utf8_lossy → into_owned），结果逐字节一致。

边界写清楚#

  • 本机 x86-64 Linux（SysV ABI）+ rustc 1.99.0 stable + gcc 13.3；其他 ABI（Windows x64、ARM64）的可变参寄存器规则不同，next_arg 行为由目标 ABI 决定，我没跨平台验。
  • next_arg 只能读实现 VaArgSafe 的类型（整型/指针族），读不出来就是读不出来——没有类型系统兜底，unsafe 的代价就是你自己保证"调用方传的类型和 T 兼容"。
  • 可变参函数体里 VaList 的构造是 ... 脱糖自动做的（等价 va_start），drop 等价 va_end——不要自己再手写 va_start/va_end 调 C 库，那是旧时代写法。

1.99 值得跟的就不止这一条#

可变参数是"终于能写进 Rust 模块"级别的补洞（之前 C API 替身得留在 C 里），另外两个 API 是日常 FFI/字符串处理里反复绕开的别扭写法。1.99 距离你现在的版本只差一个 rustup update，没有破坏性变更。

转给那个"Rust 写不了 C 的 printf 变长参数"就放弃 FFI 那层的同事：1.99 接上了，且定义处必须 unsafe fn 这条 rustc 会亲自教你。关注「梦兽编程」，下一篇（同批辅助篇）我把"零成本抽象"扔进汇编里验：Rust 单态化在 -O2 下连函数都不生成，而 dyn 动态分发和 C++ 虚函数是同一个 call * 形状——口号说"零税"，汇编说"看走哪条路"。

常见问题

1.99 里可变参数还要 nightly 吗？

不要。本机 1.99.0 stable 直接编译过，无任何 feature 门。代价是定义处必须是 unsafe fn（rustc 明确报错），且只能读实现了 VaArgSafe 的类型。

和 C 的 va_list 真等价吗？

ABI 等价：std::ffi::VaList 文档写明 layout 与平台 va_list 一致，next_arg 等价 va_arg，clone 等价 va_copy，drop 等价 va_end。本机三组 C↔Rust 调用对答案全通过。

实际用得上的场景？

给 C 库写 Rust 替身（printf 族日志函数）、Rust 里实现 C 头文件声明的 API、FFI 中间层。之前这类函数只能写在 C 里再调，现在可以写进 Rust 模块。

next_arg 读错类型会怎样？

没有类型系统兜底——读出来的值按 T 重新解释，错位就是错位的机器码含义，崩不崩看运气。这就是定义处强制 unsafe 的原因：编译器把 ABI 责任全推给定义方。

和 C 的 va_arg 宏比，Rust 这版多做了什么？

ABI 层面等价（layout/读取顺序都按平台 ABI），多的是：值走迭代器式 next_arg（无宏展开）、VaList 带 Drop（等价 va_end，不会泄漏）、可 clone（等价 va_copy）。语义是 Rust 式的，底下还是同一套 ABI 约定。
