rustc 静默喂错源码：两个路径哈希一撞，B 模块编译的其实是 A 文件

rustc 用路径哈希认源文件，而 Rust 的 Path 哈希忽略分隔符，两个目录名对得上就会撞车。撞车后编译器把第一个文件的内容静默喂给第二个，全程无警告。我在 rustc 1.99.0 上复现了两个版本，把机制和风险讲清楚。

October 22, 2026 · 2 min · 228 words · 梦兽编程 -  | 

Rust 卖点是「不会段错误、不会 use-after-free」，编译器类型系统当最后一道闸。这篇讲一个刚被报出来的口子：编译器最基础的「认文件」这一步就出了事——两个路径哈希撞车后，rustc 把 A 文件的内容静默喂给 B 模块，不报错、不警告，编译还成功。

issue 是 rust-lang/rust #164348，标题直白：miscompilation via engineered StableSourceFileId hash collisions。open 状态，issue 报在 1.99.0 和 nightly-2026-10-11。我把两个官方 repro 脚本拉到一台 2 核 EPYC、rustc 1.99.0 上跑通了，两个都错。

机制：rustc 靠路径哈希认源文件#

rustc 内部用 Path 的哈希码（Salsa 的 StableSourceFileId）来标识「这是哪个源文件」。问题出在 Rust 标准库的 std::path::Path 哈希实现：

它忽略分隔符。 也就是说，data/baselines/table.rs 和 database/line/stable.rs 这两个完全不同路径，只要它们「目录名 + 文件名」逐段的哈希拼起来恰好撞上，在 rustc 眼里就是同一个文件。

Rust 后来在 PR #127297 里试过补偿——把每个组件的长度也混进哈希。但 issue 说得很直接：「它依然很容易构造出撞车，而且撞出来的两边都长得像正常路径，不是乱码」。上面那对 table.rs / stable.rs 就是「两个都像真路径」的撞车。

撞车后发生什么#

两个文件哈希相同，rustc 就认为它们是同一份 StableSourceFileId，编译第二个时取到的是第一个文件的内容。编译照常通过，产物里第二个模块的行为由第一个文件定义。

我本机复现：两个版本都错#

PLAIN 版（有声音的那种）#

两个都是正经 mod，哈希撞车：

期望（正确的编译器）:  text of .../table.rs | text of .../stable.rs
我这边 1.99.0 实测:    text of .../table.rs | text of .../table.rs   ← 两半都是 table

B 模块（database::line::stable）打印出来的是 A 文件（data/baselines/table.rs）的字符串。cargo fmt 在这里也有问题：issue 说 plain 版会让 cargo fmt 把一个文件内容替换成另一个的。

QUIET 版（静默的那种，更狠）#

这个版本 data/baselines/table.rs 甚至不是一个 mod，只是被 include_str! 当测试 fixture 读进来。database::line::stable 这个模块由一个宏在 include_str! 之后展开，于是它的路径去源文件表里查，查到的是 fixture 的条目——fixture 的文本被当成模块源码编译了：

期望:  text of .../stable.rs
我这边实测:  text of .../table.rs, which is not a module of this crate   ← 编译进来的是非模块文件

QUIET 版的杀伤在于它静默：cargo clippy 和 cargo fmt --check 理论上查不出（issue 说它特意避开了）。我本机没装 rustfmt/clippy 组件，所以这一条我在本地没能独立核验，只能引 issue 的说法。

为什么这事值得单独写一篇#

表面上撞车顶多「报错很迷惑」，但 issue 点出了真正的风险——review 逃避 / 藏后门：

  • 两个撞车文件可以分两次 commit 加进去，降低被一眼看穿的概率；
  • 大多数审计工具不会去复现 rustc 的同一个路径哈希 bug，reviewer 也不会想到「去查有没有文件内容被替换」；
  • quiet 版还能绕开 clippy/fmt 这道静态检查。

换句话说，这是一条「攻击者能故意命名目录、编译期往别人的 crate 里塞内容」的路径。它不依赖权限，纯粹靠文件名撞哈希。

issue 提的修法#

把源文件 id 的 key 从「归一化后的 Path 哈希」换成整条路径的密码学哈希、不做任何归一化（引了 #127254 那条「哈希撞车要紧的场合就别用 Path 哈希」的讨论）。一句话：认文件这种「撞了就是事故」的地方，不能用会撞的哈希。

诚实边界#

  • 我本机复现在 stable 1.99.0（跟 issue 报的版本一致）；nightly-2026-10-11 我这边没跑。
  • QUIET 版「clippy/fmt 查不出」我没独立核验（本机缺 rustfmt/clippy 组件），引的是 issue 原文说法。
  • 撞车要两个路径「组件序列」哈希恰好相同，日常写代码撞上的概率极低；这条的价值在「攻击者可故意构造」，不是「你随机就中招」。

系列定位#

这是「Rust 安全模型被边界打穿」的第三棒：10-15 那篇讲 borrow checker 漏了一种 pattern 的 UB（rust#164250），这篇讲的是比类型检查更底层的路径识别层——编译器还没进到类型系统，就在「认哪个文件」这一步喂错了输入。

素材来源#

  • issue：rust-lang/rust#164348 外部链接 （含两个 repro 脚本 + 建议修法）
  • 关联：PR #127297（长度补偿）、#127254（Path 哈希撞车讨论）
  • 本机复现：2 核 EPYC，rustc/cargo 1.99.0，两个 repro 输出已留档 projects/1022-three-batch/src/hash-collide/

常见问题

这个 bug 现在还在吗？

issue 164348 处于 open。issue 报在 1.99.0 和 nightly-2026-10-11，我本机 1.99.0 两个 repro 都复现了。修复还没进 stable。

我正常写代码会撞车吗？

极低概率，得两个路径的「组件序列」哈希恰好相同。但要构造它不难——攻击者可以故意命名目录制造撞车。
