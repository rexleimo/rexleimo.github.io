LLM 把 TypeScript 编译器搬进 Rust：烧了 42 万美元 token，比官方 tsc 7 快 4.35 倍

一周之内，TypeScript 编译器被 LLM 移植了至少 3 份。最狠的一份把它整包搬进了 Rust——作者说烧了 42 万美元的 token、写了 130 万行 Rust，OpenAI 系模型卡在 84% 兼容爬不出来，最后换 Opus 5.5 从头重写、10 小时出了个能用的 v0。我把这份 tsc-rs 的速度基准、钱的去向、以及「为什么官方用 Go 你们又要用 Rust 再搬一份」这个争议，一次拆清楚。

October 14, 2026 · 3 min · 470 words · 梦兽编程 -  | 

一周之内，我数到了至少 3 份把 TypeScript 编译器交给 LLM 移植的活儿。最狠的一份，不是「让它帮忙改几行」，是把编译器、类型检查器、LSP 整包搬进了 Rust——作者还留了一句很重的话：他从没读过这里面生成的任何一行代码。

这份项目叫 tsc-rs。我把它能核实的数字、钱的去向、还有那个「凭什么官方用 Go、你们偏要用 Rust 再搬一份」的争议，一次拆清楚。

它搬了什么，又立了什么目标#

先把口径钉死。tsc-rs 是 t3dotgg（Triston，那个做 T3、Next 圈熟面孔）用 LLM 把 TypeScript 7 的 tsc 编译、检查、LSP 能力一起移植到 Rust 的实验项目，npm 包名 tsc-rs，仓库 pingdotgg/ts-rust。

README 开头就自曝了动机，我原样列出来：

  • 测试模型能力（Test model capabilities）
  • 做一个更快的 TypeScript 类型检查器
  • 做一个能在 WASM 里高性能跑的 TS checker
  • Memes（梗）

最后一条「Memes」别当玩笑——一个把「跑分」写进动机的编译器移植项目，本身就点破了这次移植的性质：它更像一次能力压力测试，副产物才是那个 4.35 倍快的 checker。

它把上游 pin 在 TypeScript 7.1.0-dev 的某个 commit（fed0bf24，2026-10-08），跟同一版本的 Go 实现对照。作者声明：在测过的每个真实项目里做到 100% 兼容，绝大多数应用可以当 drop-in 替换。

那 42 万美元是怎么烧没的#

这是全文最值钱的一张账。我把它拆成两段：先失败的那段，和翻盘的那段。

第一段，OpenAI 系栽在 84% 兼容上。 作者原话，他用了 OpenAI 系的大量模型去跑这个移植：

  • 累计 42 万美元以上的 API 计费 token，用的是 GPT-5.6 Sol 和 GPT 6 Astra；
  • 这些模型写了超过 130 万行 Rust，跑了数月的 /goal 循环；
  • 但始终没爬过 84% 兼容。

一句话总结第一段：烧了 42 万刀、130 万行代码，卡在 84%，出不来。

第二段，Opus 5.5 从头翻盘。 作者发现他 Claude Code 的限额烧得少得可怜，就顺手把 Opus 5.5 丢上去。结果两条关键反转：

  1. 他以为 Opus 会接着 OpenAI 那 130 万行继续写。错了。Opus 5.5 是从零重写的。
  2. 从零起步，它用了 1/10 的时间跑得比 Astra 更远，10 小时就给了一个能用的 v0。

翻盘那段的花费：全程约 2.4 万美元 API，摊到他 200 美元/周的 Claude 订阅上，占925%~983% 的周限额——一个模型的周配额被一个移植项目干到快 10 倍，这是把「Claude 用户」当燃料在烧的实证。

阶段模型投入结果
首段GPT-5.6 Sol + GPT 6 Astra42 万刀+ / 130 万+ 行 Rust / 数月卡在 84% 兼容
翻盘Claude Opus 5.5约 2.4 万刀 / 10 小时从头出 v0，快 Astra 约 10×

两段摆一起，它给出的信号比「哪个模型强」更狠：长程 agentic 移植里，模型不是拼 token 堆量，而是拼能不能推倒重来。前 130 万行是沉没成本，Opus 没有继承，反而更快——这条值得单独记下来。

快多少：一张数字表说清#

速度数据来自作者的基准：T3 Code（开 Effect 诊断）的全类型检查，时间是 5 个被检项目耗时中位数之和。越低越快。

Checker时间相对 tsc 7
tsc-rs --fast9.77s4.35×
tsc-rs14.30s2.98×
tsc 7（Go 官方）42.55s基准
bun check59.24s0.72×
tsc 6（JS 版）191.00s0.22×

两个反直觉点，先钉住：

  • --fast 档拉到 4.35×，默认档 2.98×——开不开那档优化，差出 1.4 倍，说明 Rust 版的收益很大一块来自编译期优化档位，不是「换语言自动快」。
  • bun check 比 tsc 7 还慢（0.72×）。同场基准里最快的 JS 系工具反而垫底，这是把「bun 一定快」这个流行印象，在一个具体场景里直接按倒的实证。

再叠一层：TS 官方 tsc 6（JS 版）191 秒，是 Rust 版默认档的 13.3 倍慢。语言从 JS 跳到 Rust，量级差就是这么来的。

为什么官方用 Go，它又偏要用 Rust#

这是评论区吵得最凶、也是这份项目真正的技术立场，我把对照钉死。

微软官方的 tsc Go 版（typescript-go，2024 起），当年选 Go 不为最快，是为人体工学和生态——写起来顺、团队好接手。所以官方那条路线的收益点是「可维护 + 比 JS 版快一档」，tsc 6 → tsc 7 从 191s 到 42s 已经兑现了。

ts-rust 选 Rust，目标完全不一样：README 白纸黑字写着要做一个能在 WASM 里高性能跑的 TS checker。WASM 高性能运行 + 内存安全 + 单文件静态链接，这几样 Rust 是给得出来、Go 在这个具体目标下不是最合适的组合。加上动机里那条「测试模型能力」，它其实是一鱼两吃：一边验证 LLM 能不能扛下编译器级移植，一边顺手出一个 WASM 友好的高性能 checker。

所以「一周 3 份移植」这件事本身，是同一个判断在圈内扩散：编译器这层，LLM 真的搬得动；差异只落在「搬到哪个语言、为什么搬」上。TS 团队员 DanRosenwasser（typescript-go 作者）在 HN 下的一句「一周内 3 份移植，太疯狂了」，就是这个判断官方也看见了。

哪些只能当「作者自述」信#

把没独立核验的划清楚，别把没跑的当成验过：

  1. 42 万刀 / 130 万行 / 84% / 10 小时 / 快 10× / 925%~983% 周限额——全部是作者 README 自述，我没法替他复跑，算他的口径。
  2. 「100% 兼容」是作者声明，不是第三方核验：他测过一批真实项目，但「测过的每个」的清单、方法他没在 README 里给全，我只拿到结论。
  3. 速度数字是作者在特定基准（T3 Code + Effect 诊断）的中位数：换个项目、关掉 Effect 插件，倍数会不一样——作者自己也在基准节强调了口径，我没重跑。
  4. 本机边界：我这边是 2 核 EPYC，tsc-rs 官方发版覆盖 Linux x64/arm64，理论上我能跑，但这篇我没动手复测，上面所有数字都是作者基准表原样照录。想自己压，装法就两行：npm i -D tsc-rs → npx tsc-rs -p tsconfig.json。
  5. 作者那句「我从没读过任何一行」是风险声明：一个 100% 兼容但没人逐行审过的编译器，压进关键流水线前，得自己掂量。

这件事的信号量#

把上面压缩成一句话：LLM 迁移的天花板，已经抬到「整个编译器 + 检查器 + LSP」这种工程体量，而且瓶颈不再是「写不写得出」，是「模型会不会推倒重来」。130 万行卡在 84%，换模型 10 小时从头出 v0——长程 agentic 工程里，敢放弃已有代码重开的能力，比堆 token 值钱。

对「AI 写代码」的判断，这也划了条线：能整包搬编译器，不等于能整包搬你的业务仓库。编译器是**有清晰边界、可对照（对着 TS 7 / Go 版逐条对）**的对象，业务代码没有那个「标准答案」垫底。搬编译器成功，是因为它有 benchmark 兜底；这是它敢上 42 万刀的前提，也是它和「让 LLM 重构你那个祖传 monorepo」的本质区别。

参考：pingdotgg/ts-rust README（速度基准、42 万刀/130 万行/84%/Opus 10h v0、tsc-rs 安装与 WASM 目标）；HN 讨论（item 50000676，TS 团队 DanRosenwasser「一周 3 份移植」）；microsoft typescript-go（Go 官方版语言选型对照）。

诚实声明：本文 42 万刀、1.3m 行、84% 兼容、10 小时 v0、4.35× 速度、925%~983% 周限额，均为作者 README 自述，我未独立复跑；「100% 兼容」是作者在其测试集上的结论，非第三方核验。本机 2 核 EPYC 具备跑 tsc-rs 的条件（Linux x64/arm64 均有发行版），本篇未复测，上述数字一律按作者基准原样照录并标注口径。

你是哪一派？我这边看到三种立场，评论区对一下：

  • A 派：编译器就该有 LLM 搬的，等 Rust 版 tsc 进 typescript-go 生态或单飞，性能党直接上；
  • B 派：「没读过一行代码」这句话就是红线，再快也不能压进关键流水线，当玩具；
  • C 派：这项目真正的价值不是那个 checker，是「10 小时推倒 130 万行」给长程 agent 划了条方法论——搬编译器只是载体。

你手里的 tsc 项目属于哪种？攒够一批我出续篇：tsc-rs 进 WASM 实测 + 跟 typescript-go 同场性能对账。

转给那个**「LLM 写编译器就是玩具」的同事**——它把 4.35 倍快的 checker 和『敢推倒 130 万行』这两件事，一次办了。微信搜索「梦兽编程」。

常见问题

tsc-rs 到底是什么？

t3dotgg（Triston）用 LLM 把 TypeScript 7 的编译器、类型检查器和 LSP 整包移植到 Rust 的项目，产物是 npm 包 tsc-rs。作者声明在测过的真实项目里做到 100% 兼容，可当大多数应用的 drop-in 替换。

它比官方快多少？

在 T3 Code（开 Effect 诊断）的全类型检查基准上，tsc-rs --fast 9.77 秒，是 tsc 7（42.55 秒）的 4.35 倍；普通 tsc-rs 14.30 秒、2.98 倍。同样这套测试里 bun check 反而比 tsc 7 慢（0.72 倍）。这些是作者自报的中位数，我本机没复跑。

42 万美元花在哪了？

作者用 GPT-5.6 Sol 和 GPT-6 Astra 跑了数个月 /goal 循环，写了 130 万多行 Rust，始终停在 84% 兼容；后来他把 Claude Opus 5.5 丢上去，Opus 没接着前面那坨代码，从零重写，10 小时给出可用 v0，比 Astra 用时快约 10 倍、跑得还远。全程 API 花费约 2.4 万美元，占到 200 美元/周 Claude 订阅限额的 925%~983%。

为什么官方用 Go，社区又用 Rust？

微软官方的 tsc Go 版（typescript-go）当年选 Go 是冲人体工学和生态，不为最快；这份 ts-rust 选 Rust 的目标是「一个能在 WASM 里高性能跑的类型检查器」，加上作者明写的动机之一是『测试模型能力』。同一份编译器两个语言各来一份，取舍点完全不同。

现在能上生产用吗？

作者自己写了两条警告：这是 early release；『我从没读过这里面的任何一行代码』。100% 兼容是他的声明，不是第三方核验结论。把它当实验性工具看，别当官方 tsc 的替身直接压到关键流水线。
