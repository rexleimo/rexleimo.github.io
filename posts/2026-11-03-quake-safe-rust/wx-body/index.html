1996 年的 Quake，今天在你浏览器里跑，不装任何东西。

我先把结论放这：这是把 id Software 的 WinQuake 从 C 源码移植到 Rust 的项目，零外部依赖、全篇没有一行 unsafe，浏览器版就是 WebAssembly 加一个 Web Worker，纯软件光栅，不用 GPU。作者管它叫 quake-srp，SRP 是 Slop Rust Port——slop 是他自己给这类 LLM 辅助移植起的外号，他没端着。

我把它拉到本机跑了一遍，数字都在这台机器上出的，先说环境：2 核 EPYC 9354P 切片、rustc 1.99.0、wasm 双目标构建 30 秒出头，浏览器里 demo1 放 10 秒，帧率 59.8，顶在刷新率上没掉下来。下文每个数字标了出处，作者自报的和本机实测的分开写。

一个周末能复现的东西，花了他四个月#

仓库 10 月 8 日建，10 月 9 日上了 HN，到今天 67 个 star、4 个 fork、0 个 open issue，GPL-2.0。作者是 terrapapagalli1516，README 里一句话交代了工作量：「这大概是四个月，是个爱好项目；我不知道这四个月里多少是干活、多少是在等下一个模型出来。」

代码本身是 Claude Code 写的，不是一个人对着终端敲的。README 原话：大部分工作跑在一个 agent 车队上，每个 agent 一条 git 分支、一份书面 brief，一个 chair agent 只在整套检查全过之后才合并分支。用户（也就是这位作者）定三条规矩，按顺序：零依赖、不写 unsafe、Classic 预设必须证明就是 id 的游戏。

我比较意外的是第三条。前两条是工程洁癖，第三条是把它当成一个「证明题」来做——移植完不算完，要拿出可对标的证据。证据是下面这个 oracle 体系。

像素级对表 id 的 C，一条命令全过#

仓库里有个 oracle/，把 id 自己的 WinQuake C 源码 headless 编出来当参照系（叫 oracle），然后跑 11 项检查：

四条对着「已知正确的树」录下来的值：三份参考渲染的哈希、浏览器客户端跑 id 官方 demo 和脚本走位的帧哈希、id 的 timedemo 帧数、九张地图全跑一遍的 census。七条是拿 id 的 C 并排跑：实体字段逐字段对、3D 视图逐像素对（四张图的首帧，有实体无实体两版）、几百帧的 exact 检查（九张图首帧各自转俯仰横滚、两种尺寸，再在怪物群中间走一圈，16 像素和 8 像素 span 各一遍，「一个像素都不许差」）、2D 层（状态栏菜单控制台）逐像素、demo 逐帧、混音器逐采样、粒子按网络消息字节对。

一条命令 uv run oracle/classic_check.py，全过打 ALL PASS。

这里有个细节值得说：oracle 编 C 用的是 SSE2 浮点，每个浮点操作按 C 声明的类型舍入——「这是源码说的，任何合规编译器都给这个结果」。作者把 gcc x87 的 80 位浮点、1996 年 id 自家二进制的 24 位 FPU 舍入都排除了，说那是另外两种算法，「哪一种是 1996 年玩家看到的」本身都无从考证，因为 id 从没开源过当年发货的那个引擎，那个数字永远拿不到。

浏览器版就是一个 WASI 程序#

架构上它不玩花活：quake.wasm 是个普通的 fn main() 程序，跑在 Web Worker 里，事件从 stdin 进，每帧出三样东西——一张 8 位像素图、这帧的 256 色调色板、一串声音调用。页面用 WebGL2 把调色板索引查回 RGBA（跟 VGA DAC 一个道理），PCM 直接灌进 AudioWorklet，用的还是 id 的混音器代码。

浏览器要用共享内存，所以页面得开 COOP/COEP 两个响应头（cross-origin isolated），仓库的 web/publish.sh 把这事连同 _headers 文件都做好了，丢 Cloudflare Pages 就能玩。数据方面仓库不带 pak，跑一条 ci/fetch_shareware.sh 把 id 官方镜像的 shareware 1.06 拉下来（9.1MB，sha256 校验过），id 的 licence 文件原样跟着发。

渲染是多线程的，但线程数不改变画面：BSP 遍历和边扫描跑在主线程，之后把视口切成行带，每条带按 id 的顺序走它的绘制 pass，画出来的每一帧跟开几个线程没关系。作者的性能笔记里还有一条：world 光栅化器每帧访问 3.8 到 5.2 倍于屏幕像素数的区域（扇形剖分加包围盒），所以动态光一进来就离开表面缓存走逐像素慢路径，枪口闪光、爆炸那些帧会明显变慢——这是渲染器的真实行为，不是 bug。

本机实测（2 核 EPYC，rustc 1.99）#

拉仓 20MB，四个数：

构建。wasm32-wasip1-threads release 30.4 秒，产物 quake.wasm 1.55MB；quaketool 原生 release 41.8 秒，产物 3.28MB。CI 钉的是 Rust 1.93.1、clippy 零警告，我本机 1.99 编出来 0 警告。

timedemo demo1，单线程。作者在 PERF_PLAN 里同一套测法下记过一组数： 2563 / 1113 / 617 fps（320×200 / 640×400 / 960×600），我这边 1551 / 838 / 460——他的桌面比这台 2 核切片快，两台机器的数别直接比，看量级就行。

quaketool 的 play demo1（浏览器同款客户端的原生版）960×540：660 帧按 1/72 秒步进，整个演示 1.7 秒跑完。

浏览器。本地起带 COOP/COEP 的静态服务，agent 窗口 780px 宽，wasm threads 版跑 demo1（e1m3），requestAnimationFrame 数 10 秒，59.8 fps。780px 的窗口内部渲染分辨率不高，这个帧率有水分，但「能跑、不卡、纯 CPU」这个结论在这台 2 核机器上是成立的。

它跟 id 原版到底差在哪#

差的地方作者自己列了一张清单（AUDIT.md 的 Open 段），我挑几条：转视角的角速度在端口里保持 f64，id 是 f32，正对某个触发器时判定可能差 9 帧；玩家移动的角度端口发给服务器时不取整，id 的客户端按 1.40625 度一档的字节发；爆炸粒子的初始位置端口用服务器精确值，id 的客户端是 1/8 单位取整的。这些在像素检查里是「已知差异，录了档」，不算失败项。

slop 预设和 Classic 的区别全在一张表里：Classic 就是 id 的 WinQuake——320×200 4:3、id 的状态栏、72 帧上限、11025Hz 混音；slop（默认）是「同一个软件渲染器给 2026 的机器用」：窗口什么形状就什么分辨率、帧率不封顶（跳跃和闪光还是按 72Hz 步进对齐）、怪物滑行、火把微微闪。两个预设一键互切，存档不受影响。

HN 上吵起来的几个点#

有人说「Quake 当年 486 都能跑，这有什么新鲜的」——底下回复是 Quake 当年臭名昭著地要吃奔腾级 FPU，486 上跑的是泥。有人去源码里 grep 0x5f3759df（快倒平方根那个魔数），没搜到，作者回：那是 Quake 3 的技巧，Quake 1 里就没有。还有人说「又一个一个月后被放弃的 slop 项目」，作者没回这条。

作者在热评里留了两句值得原话引：LLM 的舆论场「怪得让人难过」，它们烦人、天天犯错，「但跟它们一起干活是我做过最有回报的事之一」。另外那部 6 分钟解释片（怎么跑的、slop 改了什么）是 AI 制作、人辅助剪的。

边界，说清楚#

四个月爱好项目、单人维护、LLM 生成的代码，「会不会被放弃」这个问题只有作者自己知道。像素对表的覆盖面是「试过的所有视图」，不是全量遍历；SSE2 浮点目标本身就是一个选择，id 当年发货版本的浮点行为无解。没测 Safari/iPhone，多人联机没有（只移植了单人生态），注册版和任务包只能用自己的拷贝。作者自报的 fps 全出自他的桌面，我的全出自 2 核切片，两边机器不同，本文数字一律按「哪台机器跑的」读。
