Mold 3.0 把链接器重写成 Rust：我复现了官方那句"损坏输入会 segfault"，还找到了 C++ 源码里那行越界读

rui314 10 月 5 日放出 mold 3.0.0——mold 官方首个 Rust 版。HN 的通用心智是"Rust 重写 = 更快 + 更安全"。我本机两个判断都验了：速度没有更快（1501 .o 三轮中位 84ms vs 87ms，复现官方 "remains on par"），安全是真差异且复现了（畸形 .o：C++ 版 5/5 SIGSEGV，Rust 版干净 fatal），还定位到 C++ 源码那行越界读。

October 5, 2026 · 3 min · 609 words · 梦兽编程 -  |  English

mold 3.0.0 的 HN 热帖里有一个通用心智："Rust 重写，那肯定更快更安全。"我在本机 2 核 EPYC 上把这两句都验了。一句错，一句对——而且对的那句，我能指到 C++ 源码里那一行越界读。速度：打平。 1501 个 .o，3 轮中位，Rust 84ms vs C++ 87ms，复现了 release notes 原话 "Linking performance remains on par with 2.42.1"。安全：真差异，且我复现了那个 segfault。 构造一个 e_shnum=0 + e_shoff 越界 的畸形 .o 喂给 C++ 版，rc=139（SIGSEGV），5/5 稳定；喂给 Rust 版，干净一行 fatal。差异在 input-files.cc:95——C++ 把 sh_begin->sh_size 的解引用放在越界检查之前，Rust 版在 input_files.rs:456 用 slice::get 让那次越界解引用根本不存在。这就是 release notes 那句 "guarantee moved from test coverage to the type system" 的可复现版本，不是口号。

速度：第一个链接就证伪了#

"Rust 更快"是每个 Rust 重写 HN 帖的通用心智。对 mold 尤其如此——因为它的名气就是"比 GNU ld 快 9 倍"，读者会不自觉升级成"Rust 重写让它更快了"。没有。

1501 .o 负载（1500 个生成的 C 文件，gcc -O2，18MB 对象），3 轮中位：

# mold 3.0.0 (Rust)
$ /home/rex/hermes-workspace/projects/rust-mold-ripgrep/bench/mold3/mold-3.0.0-x86_64-linux/bin/mold data/objs/*.o -o out-m3 -e main
# 84ms 中位（三轮：冷 192 / 80 / 84）

# mold 2.42.1 (C++)
$ /home/rex/hermes-workspace/projects/rust-mold-ripgrep/bench/mold2421/mold-2.42.1-x86_64-linux/bin/mold data/objs/*.o -o out-m2 -e main
# 87ms 中位（三轮：83 / 87 / 87，极稳）

# 参照：GNU ld
$ /usr/bin/ld.bfd -static -o out-bfd data/objs/*.o -e main
# 热态 ~700ms（冷轮页缓存 miss 到 3.1s）

差 3.4%，C++ 版在冷轮之后还略领先。这就是 release notes 那句 "on par"，本机复现。"9.8 倍"是 mold 相对 GNU ld 的故事——2.42.1 就成立、3.0 还成立；Rust 重写在热路径上没加任何可测的东西。我查了 3.0 的构建变化（去 oneTBB、mimalloc 3.5.3 静态链、Rust 1.95+ 工具链）：单线程链接场景下，allocator 换掉 + 代码生成差异吃掉了语言重写可能带来的小幅优化，净效果是"不动声色地打平"。

安全：我把那个 segfault 复现了，还定位到行#

官方 release notes 原话：

The C++ version could read memory out of bounds on such input and crash with a segmentation fault. In mold 3.0, those reads are bounds-checked, so mold stops with a panic at the faulty access instead.

之前我试的两种畸形对象（尾部截断 512B；shstrndx 越界 3 节），两版都干净 fatal——因为 mold 在 e_shoff 阶段就提前拦住了，够不到那句描述。这次按源码把触发条件找对了：e_shnum == 0（节数不存 e_shnum 而存第 0 节的 sh_size）叠加 e_shoff 越界。

C++ 版 src/input-files.cc L89–L97（v2.42.1 tag 原文）：

ElfShdr<E> *sh_begin = (ElfShdr<E> *)(mf->data + ehdr.e_shoff);   // L89: 直接算指针，无越界检查
i64 num_sections = (ehdr.e_shnum == 0) ? sh_begin->sh_size : ehdr.e_shnum;  // L95: e_shnum==0 → 解引用 sh_begin->sh_size
if (mf->data + mf->size < (u8 *)(sh_begin + num_sections))        // L97: 越界检查在解引用之后
  Fatal(ctx) << mf->name << ": e_shoff or e_shnum corrupted: "

顺序就是整个 bug：先算 sh_begin（可能已越过文件尾）→ e_shnum == 0 时先解引用 sh_begin->sh_size → 然后才做越界检查。畸形 .o 让 e_shoff 指向文件外 + e_shnum = 0，L95 那次解引用就是越界读。x86-64 上读不读得出来取决于那个地址上映射了什么——小偏移能读到相邻页（虚拟内存连续）不炸，1GB 偏移打到映射边界就 SIGSEGV。"崩不崩"是布局问题；"检查在不在"不是：检查在解引用之后。

Rust 版 src/input_files.rs L449–L462（v3.0.0 tag 原文）：

let shoff = ehdr.e_shoff.get() as usize;                     // L449
let shdr_size = size_of::<ElfShdr<E>>();
let first = data.get(shoff..shoff + shdr_size).map(record_from_bytes::<ElfShdr<E>>);  // L456: get() 越界返回 None，不读
let num_sections = match (ehdr.e_shnum.get(), first) {
    (0, Some(first)) => first.sh_size.get() as usize,        // L458: first 为 None → 走 n 分支，不可能越界解引用
    (n, _) => n as usize,
};
let Some(shdr_bytes) = data.get(shoff..shoff + num_sections * shdr_size) else {  // L462: 兜底 fatal
    fatal!("{}: e_shoff or e_shnum corrupted: {} {num_sections}", ...)
};

一句话差异：C++ 把解引用放在检查之前，Rust 的 slice::get 让越界解引用在类型系统里不是一个能取到的值。 不是"Rust 作者记得写了个 if"，是越界读在类型系统里根本写不出来——保证从测试覆盖挪到了编译器，这正是 release notes 那句 "guarantee moved from test coverage to the type system" 的可复现版本。

复现命令（可原样跑）：

# 1) 造畸形 .o：取正常 main.o，e_shoff 置 0x40000000（1GB）、e_shnum 置 0
python3 - <<'EOF'
import struct
d = bytearray(open("data/objs/main.o","rb").read())
struct.pack_into("<Q", d, 0x28, 0x40000000)   # e_shoff
struct.pack_into("<H", d, 0x38, 0)            # e_shnum = 0 → 触发 L95 解引用分支
open("/tmp/corrupt-oob.o","wb").write(bytes(d))
EOF

# 2) C++ 版：SIGSEGV
$HOME/.../bench/mold2421/mold-2.42.1-x86_64-linux/bin/mold /tmp/corrupt-oob.o data/objs/main.o -o /dev/null -e main
# → 退出码 139 (SIGSEGV)，无 stderr，5/5 稳定

# 3) Rust 版：干净 fatal
$HOME/.../bench/mold3/mold-3.0.0-x86_64-linux/bin/mold /tmp/corrupt-oob.o data/objs/main.o -o /dev/null -e main
# → 退出码 1：\"mold: fatal: /tmp/corrupt-oob.o: e_shoff or e_shnum corrupted: 1288 13\"
版本退出码行为
mold 2.42.1 (C++)139 = SIGSEGV无 stderr，硬崩，5/5 稳定
mold 3.0.0 (Rust)1 = fatal一行诊断，受控停下

实际风险面：这是"你的构建喂了非编译器产物的 .o"的场景——损坏的 CI 缓存、截断的 tarball、第三方预编译对象。3.0 把这个场景从"链接步骤崩掉"变成"一行能 grep 的错误"。

3.0 真正卖的是什么#

速度从来不是卖点，release notes 自己也明说了。真正的一句战略：3.x 去补剩余的 GNU-ld 兼容缺口（linker script 为首），"pave the way for mold to be adopted as the default linker in Linux distributions"。mold 卡了几年"快是真快、但 linker script 兼容性差一截"，把目标钉死在"发行版默认链接器"上——进了默认，才谈得上每个 C 开发者默认享受它相对 GNU ld 的 9.8 倍（本机 ld.bfd 热态中位 ~700ms vs mold 84ms），而不是极客的 opt-in。

边界写清楚#

  • SIGSEGV 可复现但依赖越界幅度：1GB 偏移 5/5 稳炸；小偏移可能读到相邻映射页不炸——重点是 C++"检查在解引用之后" vs Rust"解引用不可能存在"，不是"C++ 必崩、Rust 必不崩"
  • 速度对照是静态链接口径（ld.bfd -static，动态链接 flag 与本机发行版不匹配没跑成）；两版 mold 输出字节级一致（10.14MB），可直接比
  • 2 核 EPYC 非独占切片：3 轮中位 + 冷轮（页缓存 miss）单列，热冷分开报

转给那个问"Rust 链接器是不是又快又安全"的同事：快的部分是 2.x 就有的（mold 相对 GNU ld 9.8 倍），安全的部分是 3.0 才补上的，补的还是最坏情况——我连 C++ 源码里那行越界解引用（input-files.cc:95）和 Rust 重写的回答（input_files.rs:456）都给你找出来了。关注「梦兽编程」，上一篇 Headstart 我在这台 2 核机器上把"up to 2x"量穿了，这篇把"重写 Rust"拆成速度（打平）和安全（segfault→fatal 可复现）两件事分别验——只有一件是真的。

常见问题

mold 3.0 比 2.42.1 快吗？

没有。1501 .o 链接、3 轮中位：Rust 84ms vs C++ 87ms，差 3.4% 在噪声内。官方 release notes 原话 "remains on par"，本机复现。

那重写成 Rust 到底买到了什么？

最坏情况行为：畸形 .o（e_shnum=0 + e_shoff 越界）喂给 C++ 版 5/5 SIGSEGV（rc=139），喂给 Rust 版干净 fatal。定位到 C++ input-files.cc L95——解引用发生在越界检查之前。

普通用户现在要切 3.0 吗？

命令行 drop-in 兼容。如果你的构建会喂第三方/损坏/截断的 .o（CI 缓存、tarball），崩溃变 fatal 这点值得；否则 2.42.1 够用。
