Postgres 19 的图查询，在发布前四天被撤了

SQL/PGQ 进了 PostgreSQL 19 Beta，又在那篇《把 Neo4j 负载跑了一遍》的文章发表四天后被 revert。我顺着 commit 和邮件线程把这件事捋了一遍，以及它还教会我们什么。

September 21, 2026 · 4 min · 764 words · 梦兽编程 -  |  English

Peter Eisentraut 在 9 月 3 日晚上回了一封邮件，正文三个词：

Ok, let’s do it.

他同意撤掉的，是 PostgreSQL 19 的头条特性——SQL Property Graph Queries。四天后，revert 提交落地：b1f106c80cbeb18d3a0219994d98a51a6eca8ede，2026-09-07 19:51（UTC+2），同一个作者，50 多个提交、124 个文件，一次清退。

而就在他敲下那三个字的同一天，Medium 上有一篇文章正在被转发，标题很解气：《Postgres 19 Adds Graph Queries. I Ran Our Neo4j Workload Against It》。作者把生产数据拉到备用机上，用四条 Cypher 查询对打，结论是：一跳两跳 Postgres 赢，三跳 Neo4j 赢，最后一条变长路径查询 Postgres 直接答不上来。

文章是真的，测试大概也是真的。但它测的那个东西，四天后没有了。

这篇不是来嘲笑谁的。我是想说：这件事里真正值钱的部分，跟"Postgres 有没有图查询"没关系。

一、先说清楚撤的是什么#

时间线钉死，全部可查：

时间事件
2026-03-16Eisentraut 提交 2f094e7a，SQL/PGQ 进主干，+14888 −72，122 个文件
2026-08-13PostgreSQL 19 Beta 3 发布，官方文档把 Property Graphs 单独列了一章
2026-08-22Andres Freund 对 catalog 表示提出疑问，线程开撕
2026-09-02 19:29Melanie Plageman 戴 RMT 帽子发难，建议 revert
2026-09-03 20:53Eisentraut：Ok, let’s do it
2026-09-07 19:51revert commit b1f106c8 落地

注意 Beta 3 和 revert 之间隔了半个月。也就是说：你从任何一篇"Postgres 19 图查询上手"教程里抄到的语法，在正式版里都不存在。 官方 release notes 里 Release date 那一栏至今还是 2026-??-??，而 Neon 的文档现在置顶挂着一句话：SQL/PGQ 已从 PostgreSQL 19 撤回，最早回归是 PostgreSQL 20。

那篇 Medium 文章的评论区里大概没人提醒作者这件事。它的发表日期和 revert 决定，是同一天。

二、SQL/PGQ 到底是个什么东西#

先把技术本身讲清楚，因为它撤归撤，设计思路是干净的。

PostgreSQL 19 的官方文档有一句定性的话，值得逐字读：

PostgreSQL implements SQL/PGQ … where a property graph is defined as a kind of read-only view over relational tables. So the actual data is still in tables or table-like objects, but is exposed as a graph for graph querying operations.

翻译成人话：没有图存储引擎，没有邻接表，不复制你一行数据。 你在既有表上盖一层元数据声明，声明它是个图，然后用接近 Cypher 的语法查它。

CREATE PROPERTY GRAPH social
  VERTEX TABLES (
    users KEY (id) LABEL person PROPERTIES (id, name)
  )
  EDGE TABLES (
    follows KEY (id)
      SOURCE KEY (src) REFERENCES users (id)
      DESTINATION KEY (dst) REFERENCES users (id)
      LABEL knows
  );

然后：

SELECT * FROM GRAPH_TABLE (social
  MATCH (a IS person WHERE a.id = 42)-[IS knows]->(b IS person)
  COLUMNS (b.id, b.name)
);

CREATE PROPERTY GRAPH 是纯元数据操作，DROP PROPERTY GRAPH 只删定义不动表。 Eisentraut 的提交信息里写得更直白：property graph 是一个新的 relkind RELKIND_PROPGRAPH，“It acts like a view in many ways. It is rewritten to a standard relational query in the rewriter.”

这句话是理解全部性能表现和全部坑的钥匙。

三、它为什么快，也为什么慢#

CYBERTEC 的 Julian Markwort 在今年 7 月做过一轮实盘验证，他的结论和那篇 Medium 文章的观察对得上：GRAPH_TABLE 是解析器级别的重写器，你写的箭头语法在进入规划器之前就被拍平成普通 join。

一跳 = 三表 join，两跳 = 五表，三跳 = 七。形状机械增长，代价模型还是原来那个。

EXPLAIN (COSTS OFF) 出来是这样：

QUERY PLAN
 Hash Join
   Hash Cond: (big_knows.b = big_person_1.id)
   -> Hash Join
        Hash Cond: (big_knows.a = big_person.id)
        -> Seq Scan on big_knows
        -> Hash
             -> Seq Scan on big_person
   -> Hash
        -> Seq Scan on big_person big_person_1

跟他手写的 join 树逐层一致：

SELECT a.name, b.name
FROM big_knows k
JOIN big_person a ON a.id = k.a
JOIN big_person b ON b.id = k.b;

同一套规划器、同一套统计信息、同一批索引、同一个 EXPLAIN。 没有图专属的执行节点藏着掖着。这是它对独立图数据库的结构性优势：备份、复制、行级安全、监控、权限，一个新增可动部件都没有。

代价也直接来自这里。Medium 那位作者写的"The Part Where I Looked Foolish"是全篇最有价值的一段，值得完整转述：

他第一次跑反向遍历（“谁关注了 42”）花了 340 毫秒，差点关掉终端宣布 Postgres 不合格。看执行计划，发现全表扫了 3800 万条边。原因很朴素：他们的边表只在源列上建了索引，目标列没有——因为 Neo4j 两个方向遍历免费，团队几年来从没想过这件事。补一条 CREATE INDEX ON follows (dst);，6 毫秒。

他的结论我很喜欢：

图数据库多年来一直在 quietly 给我们 schema 里的一个缺口擦屁股，而我管那叫魔法。

CYBERTEC 那边是同一件事的干净版本：6 万条边里找 6 条，Seq Scan 读 60000 行；在 (b) 上补索引，3.1ms → 0.16ms，buffer hit 287 → 29。

所以规则还是你早就听过的那条：要按它过滤，就给它建索引。 图遍历只是沿某一列取边。正向遍历吃主键，反向遍历吃第二条索引。没有新东西要学。

四、真正没做的部分#

19 Beta 的实现覆盖了标准里一个有用切片，但有三类东西明确缺席：

变长路径。 -[IS knows]->+（一跳以上）、-[IS knows]->{1,4}（一到四跳）都不支持。每一跳必须手写。想表达"深度是变量不是我敲死的数字"，GRAPH_TABLE 说不出这个话。

那篇 Medium 文章倒就倒在这：第四条查询 MATCH (a:Person {id: 42})-[:KNOWS*1..4]->(b:Person) RETURN DISTINCT b.name。退化方案是图数据库出现之前大家都会写的那招：

WITH RECURSIVE walk AS (
  SELECT dst AS id, 1 AS d FROM follows WHERE src = 42
  UNION
  SELECT f.dst, w.d + 1
  FROM walk w JOIN follows f ON f.src = w.id
  WHERE w.d < 4
)
SELECT DISTINCT id FROM walk;

能用。不优雅。

最短路径。 ANY SHORTEST / ALL SHORTEST 未实现，WITH RECURSIVE 加 ORDER BY depth LIMIT 1 是现实替代。

一个 MATCH 里的多个 pattern。 逗号分隔不支持，得拆成两次 GRAPH_TABLE 调用按顶点 id 拼。另外边同构默认不强制，不加 WHERE a.id <> b.id 同一条边会被匹配两次。

还有一层容易被忽略的：标准符合度。 有人逐条数过 PostgreSQL 19 的 Appendix D（SQL Conformance），SQL/PGQ 家族 100 个特性里实现了 26 个。19 比 18 多出的 27 个"已支持特性"中，26 个来自 SQL/PGQ——另一个是 LEAD/LAG 的 null 处理选项，孤零零一个。未实现的那 74 个里包括 TRAIL、SIMPLE、ACYCLIC 这些 path mode，缺了它们你无法要求"路径不重复顶点/边"。

换个说法：19 拿到的是图查询的"读入口"，不是"图查询能力"。

五、压死它的不是性能，是元数据#

到这里， revert 的原因才浮出来，而且跟跑分一点关系都没有。

RMT（PostgreSQL 发布管理团队）的 Melanie Plageman 在 2026-09-02 的邮件里列了三个设计问题。她的原话译过来是这样：

孤儿元数据。 外部的 DROP TABLE ... CASCADE 会留下孤儿的 label/property 元数据。它们以幽灵条目的形式出现在 information_schema 视图里，会让后续合法的 ALTER PROPERTY GRAPH 失败，还会让整个图变得无法 dump、无法 restore。9 月 1 日有个补丁想修，被认定为 stop-gap；真正的修复"out-of-scope for 19"。

作用域粒度。 当一个 property/label 从图里某个元素上被删掉、但图里别处还存在时，基于 GRAPH_TABLE 建的视图会静默变得不可查询。没有已发布的修复，且"正确行为本身"还在等标准解释——包括一个函数被两个 label 共享时该怎么办这种最基础的问号。

该不该有 pg_class 条目。 Andres Freund 最初的担忧没有被确认解决。而 Andrew Dunstan 报告的那个 bug——AlterPropGraph() 不校验目标到底是不是 property graph——让人怀疑还有更多代码在读 pg_class 时把图和表混为一谈。

外加一串没有修复方案的依赖顺序问题，比如物化视图查询 GRAPH_TABLE 时 pg_dump 的依赖环。

Plageman 的落点很克制，也很硬：

我们最担心的是，有几个已报告的问题涉及社区和补丁作者尚未解决的设计与行为问题。如果任何期望行为还未定，就没有足够时间在发布前修完它们。

Eisentraut 回了那三个词。他的理由在别处也说得明白：revert 掉，时间压力消失，才能在 20 里把这些问题修对，而不用背向后兼容和 backport 的包袱。

一个特性不是跑分输了被砍的。是它的元数据语义没人能说清楚，宁可不上车。

六、所以现在怎么办#

如果你正被"要不要为了图查询迁 PG 19"这个问题卡着，答案是：不用了，它不在了。但如果你的真实痛点是"我不想为四条查询维护一个 Neo4j"，路径还有：

  • 等 PG 20（按 Neon 的说法预计 2027 年 9 月）。这次 revert 反而让特性更可能以完整形态落地。
  • Apache AGE。Cypher 语法的 PG 扩展，变长路径支持早就有，代价是扩展存储和有限的 SQL 互操作。
  • 继续用 Neo4j / Memgraph，但把边表的目标列索引补上。Medium 那篇文章最实际的遗产就这一条，跟用什么数据库无关。
  • 固定深度的遍历（朋友的朋友、依赖两层、我朋友的雇主）本来就用 WITH RECURSIVE 手写，PG 19 回不回来都不影响你。

七、这件事真正该带走的判断力#

我对那篇 Medium 文章没有意见。它有真实数据、真实 EXPLAIN、真实到有点难堪的自我修正，比九成"新特性解读"强。

但它是 9 月 3 日写的，基于 Beta 2。它的读者如果今天照着抄，会在正式版里收到 syntax error at or near "PROPERTY"。

这不是作者的问题，这是读技术文章的方式问题。三个步骤，是我这篇写完沉淀下来的：

  1. 先看基线版本。 文章基于 Beta 1、Beta 2 还是 GA？没写的，默认按最旧的猜。带日期的版本号是时效性的起点。
  2. 去 git log 里搜那个特性名。 不是在 release notes 里搜"新增"，是搜"revert"“remove"“not shipped”。gitweb 一条 commit 一分钟，比读十篇二手解读都快。这次我搜 b1f106c8 就够定性了。
  3. 对不上就只信官方源。 官方文档的版本选择器能切到 19/devel/18——如果某篇教程的语法在你当前版本的文档里查不到，它写的就是一个不存在的东西。

“Postgres 19 有图查询了"这句话，在 2026 年 3 月是真的——代码进了主干。在 9 月 3 日还是真的——那天还有文章在推荐它，同日它的原作者同意了撤销。9 月 7 日之后，它是假的。

中间没有任何人宣布它假了。它只是被 revert 了。

三个问题，想听听你的答案#

一、站队。 如果你现在手上就有一个"四条查询撑一个 Neo4j"的处境，你选哪条路：等 PG 20、上 Apache AGE、还是继续留着 Neo4j 但把索引补全？我自己倾向于最后一个——它不用赌任何发布节奏。

二、数据征集。 你们的关系表是不是也只在源列建了索引？我猜一大批人是。评论里报一下你的边表索引情况（比如"只有 (src, dst) 主键”），我想知道这到底是个别疏忽还是普遍盲区。

三、一个画像。 如果你身边有那种"照着三年前的教程配了三年前的方案"的同事，把这篇文章转给他。不用评论，他看完自己会明白。

关于「梦兽编程」：本文每个 commit hash 和邮件线程都给了可点击来源，结论可自行复核，不用信我。想持续获得这类经过一手核验的数据库与 AI 工程解读，微信搜索公众号「梦兽编程」。
