Proa 号称比 React 快 35 倍：我复跑了 7 个渲染器，35 倍只在一格成立

Proa 是个 Rust SSR 框架，官方基准表写着比 React 渲染快 35 倍。我把官方 benchmark 仓拉到一台 2 核 EPYC 上跑通，7 个渲染器 × 3 个页面：35 倍只在最小的组件页那一格成立，1000 行大表它离 memcpy 地板还有 23 倍距离。Askama 反超 Proa 的那一格 …

October 18, 2026 · 4 min · 755 words · 梦兽编程 -  | 

前几天逛 GitHub 时看到 Proa，一个 Rust 写的 Web 框架。让我想动手的不是它的热度，是它团队发出来的一张 17 个渲染器的基准表：组件页 2µs，比 React 快 35.4 倍。表是自己测的、自己标的边界（Apple M4 Max，2026-09-05 capture），数字写得很明白。

我做的事只有一件：把官方 benchmark 仓拉到一台 2 核 EPYC 上跑通，7 个渲染器 × 3 个页面，看 35 倍这个数跨机型、跨页面站不站得住。

先说结论，三句话#

第一，35 倍是真的，但只在「组件页（25KB 小页）」那一格成立；1000 行大表（989KB）上，Proa 自己离 memcpy 地板还有 23.5 倍距离——大页面的天花板在输出字节量，不在框架。

第二，官方自己保留的反直觉格，本机复现了：Askama 组件页 1.84µs 反超 Proa 的 3.33µs，方向与 M4 官方表一致（0.71×）。

第三，冷启动官方 8.63ms，本机实测 13~16ms；压测后峰值 RSS 17.7MB。

下面按「官方表 → 本机复跑 → 踩坑」的顺序拆，每个数字挂来源。

官方 17 渲染器表：35 倍在哪一格#

Proa 团队维护一个独立的基准仓 Proa-Labs/proa-benchmarks，把 17 个渲染器（8 个组件框架 + 9 个模板引擎）喂同一份 fixture、渲染同样三个页面，过了同一道浏览器 DOM 一致性闸才计时。当前结果标在 2026-09-05、Apple M4 Max：

渲染器组件页（P50）1000行表（P50）商品网格（P50）
Proa2.00 µs · 1.00×0.25 ms · 1.00×0.026 ms · 1.00×
React70.9 µs · 35.4×3.34 ms · 13.2×0.39 ms · 15.0×

表里的 0.71× / 0.87× 意思是 Askama 比 Proa 还快——官方原文的措辞是 “Contrary cells stay”，专门把这些格保留下来不藏。

三个观察，都是表本身就写在里面的。

倍数随页面变大往下掉：组件页 35.4× → 大表 13.2× → 网格 15.0×。React 的优势建立在「组件树重建 + hydration 前成本」上，页面越大，两边输出字节都涨，差距被稀释。

纯编译期模板引擎（Askama/Sailfish）在小页面反超 Proa。原因是字节量：它们的模板保留作者写的缩进，输出 44,849 字节 vs Proa 的 25,108 字节，语义 DOM 一致但字节不同。在「不碰框架功能、只比裸渲染」的量纲下，零分配的模板引擎更快。

表尾写得很直白：“These ratios describe this capture, not every application.” 官方自己把 35× 圈死在那一台机器、那三个页面。

这张表是官方自报的数，我只引用，不下背书。本机能不能复现方向，往下看。

本机复跑：7 渲染器 × 3 页面（2 核 EPYC）#

工具链：rustc 1.95.0，proa 仓 7ab85e1（10-17 HEAD），benchmark 仓用官方自带的 representative_suite_bench 二进制，默认采样次数。每个渲染器单独跑、绑 taskset 核 1，核 0 留给系统噪声。

渲染 P50（本机实测，µs；括号内是相对 memcpy 地板的倍数——地板是本仓自带的对照项，把「渲染一次」的下限钉出来）：

memcpy 地板0.4621.725.38
Proa3.33（7.2×）510.93（23.5×）33.00（6.1×）
Askama1.841028.5631.51
Sailfish2.26853.2239.22

Dioxus299.165324.65635.04

本机方向与官方表一致，差异点在量级。

Askama 反超复现了。 本机 Askama 组件页 1.84µs < Proa 3.33µs（官方 M4 是 1.42 < 2.00，同方向）。Sailfish 也反超。两个纯模板引擎在小页面上赢 Proa，字节量原因同上。

Dioxus 拖底。 299µs 的组件页 P50，是 Proa 的 90 倍——比官方 M4 上 Dioxus 的 52.9× 更难看。x86 共享机上 Dioxus 的差距被放大，这格我不下结论，只记录。

Proa 离 memcpy 地板的距离随行变。 组件页 7.2×，大表 23.5×，网格 6.1×。大表那格最远，印证「输出字节量是大页面天花板」——989KB 的 HTML 再怎么零分配，拷贝本身就占掉了大头。

一个要写死的边界：本机 2 核共享机，绝对值（3.33µs 这种）只在同一次会话内可比，跨会话会漂；倍数看方向不看绝对值。官方 M4 上 Proa 组件页 2.00µs，本机 3.33µs——1.7 倍差距落在合理的跨机型噪声带里，方向没翻。

HTTP 线：单核吞吐与尾部延迟#

官方基准仓的 HTTP 对照是 Node 驱动的（React/Marko/Go 各起一个 server），本机没装 Node 压测栈，这条对照没复跑，下文官方数字只引用。但 Proa 自家的 HTTP server（Axum 适配器）我可以完整压：proa_page_server，PROA_WORKER_THREADS=1 绑核 1，压测器绑核 0，loopback。

路由c=1 RPS / P50c=50 RPS / P50 / P99c=200 RPS / P50 / P99
/cards（32卡·25KB）2457 / 0.31ms3943 / 11.4 / 21.4ms3724 / 33.9 / 224ms
/table（1000行·989KB）703 / 1.28ms1078 / 44.6 / 79.4ms999 / 193.9 / 371ms
/products（96卡·285KB）1990 / 0.44ms2629 / 17.6 / 47.3ms2542 / 66.4 / 181ms

两个数字值得记。

c=50 是饱和点。 /cards 在 c=50 拿到 3943 RPS，c=200 反而跌到 3724——排队把尾部拉爆（P99 从 21ms 飙到 224ms）。单核服务三页的容量上限就摆在这。

大表吞吐掉到 703 RPS（c=1）。989KB 的响应把单核带宽吃掉，和渲染线「大页面天花板是字节量」是同一件事的两个侧面。

内存：压测后 getrusage 峰值 RSS 17.7MB（压测前 5.6MB）。对比官方冷启动段写的 React 75.9MB / Go 12.5MB——Proa 17.7MB 落在中间偏下。

冷启动：官方 8.63ms，本机 13~16ms#

官方 README 里冷启动的衡量方式是「进程 spawn 到首个完整响应」：Proa 8.63ms / 4.5MiB，React 69.0ms / 75.9MiB，Go 15.2ms / 12.5MiB。

本机同样方式自测（spawn → /health 返回 ok，三轮）：13 / 15 / 15ms 与 15 / 13 / 16ms。x86 共享机、页缓存冷的条件下，比 M4 多 5~7ms，量级没变——冷启动快是 Proa 的真实特性（Rust 二进制不用 JS 引擎预热），不是营销话术。

踩坑：官方 benchmark 仓拉不起来，原因值得记#

这一节是本机复跑时实际撞上的，不是想象出来的。

benchmark 仓的 Cargo.toml 把 proa 五个 crate 全部 git = "https://github.com/Proa-Labs/proa", branch = "main" 依赖，Cargo.lock 钉死具体 revision。跑的时候直接废：

fatal: remote error: upload-pack: not our ref 7ffb8a19...
error: failed to load source for dependency of package proa_bench
Caused by: revision 7ffb8a19 not found

原因：上游 main 分支发生过一次 force-push，lockfile 钉的那个 revision 在远端已经不存在。官方仓自己的注释写着 “CI refreshes that revision before validating the suite”——意思是官方 CI 每次会先刷新 revision 再跑，本地直接 cargo build 没有刷新这一步，就撞上 dangling ref。

修法是把五个 git 依赖改成 path 依赖指向本地克隆的 proa 仓（7ab85e1，10-17 HEAD，比 lockfile 钉的还新），重新 resolve 后正常编译。首构建 6m33s（cargo 自报纯编译，2 核，含依赖拉取），产物 proa_page_server 6.0MB。

这个坑本身是个可复现性样本：一个「跟踪 main 分支的 benchmark 仓」，上游一次 force-push 就让本地全部失效，只有官方 CI 带着刷新逻辑才能复现。写进正文，因为这就是「我只发了跑出来的数字」的那部分代价。

它真正的卖点：同组件出 HTML 和 Markdown#

绕开渲染速度讲一句 Proa 的定位。核心 trait 分两套：WebRender（HTML）和 MdRender（Markdown），同一个数据源可以各自渲染出 HTML 页面给浏览器、Markdown 文档给 agent 直接读。官方原话把这件事叫做 “one typed, compiled interface layer that produces the right representation for whoever asks: complete HTML for people, targeted behavior for browsers, and dense machine-readable output for agents.”

HN 评论区里有一条点得很准（contingencies 原话翻译）：多目标 = {chat, web, markdown}，受众 = {human, bot}。也有人泼冷水：LLM 时代非统一的模型架构维护成本没那么高，这个角度的实际价值存疑。

这块我没在本机复跑（Markdown 渲染路径是同一套宏的另一侧 trait，纯渲染数字可以复用上面的表），只把官方定位和 HN 的两个方向都记下来。选它不选 Topcoat/loco，看的就是「页面本身就是 agent API」这件事对你重不重要。

诚实声明#

本机是 2 核 EPYC 8GB，rustc 1.95.0，proa 7ab85e1，2026-10-18 实测。render 倍数看方向不看绝对值，跨会话会漂。

官方 17 渲染器表（M4 Max 35.4×/13.2×/15.0×、冷启动 8.63ms）是官方自报的数，引用未复跑；本机复跑的是官方仓自带的 7 渲染器子集（memcpy/Proa/Leptos/Dioxus/Topcoat/Askama/Sailfish）。

React/Marko/Go 的 HTTP 对照未复跑（Node 压测栈没装）；RSJS 浏览器端 islands 未验（无 GUI 环境）。

Proa 有商用组件订阅（Pro 版，HN 评论区有 $2000/月 的争议），本文只涉及开源部分，订阅条款与免费层边界不展开。

参考：Proa 主仓 github.com/Proa-Labs/proa（README + AGENTS.md）；基准仓 github.com/Proa-Labs/proa-benchmarks（scoreboard.md 官方 M4 表、representative_suite_bench 二进制）；HN item 50105467（Show HN，106 分，作者评论区 10+ 轮回应）；proa.so（官网，多目标渲染说明）。

你的 Rust Web 项目现在用哪个框架？三档可以聊：A 档是在跑 Topcoat/Leptos/Dioxus 的，贴你的渲染场景（页面多大、有没有流式），我帮你判断 Proa 的多目标渲染值不值得迁。B 档是「SSR 够不够快」这件事，可以出一篇把 React/Marko 也拉进本机对照的补篇（把 Node 压测栈装上补完）。C 档是 Markdown 渲染给 agent 这条路线，等 Proa 生态里出现第二个非自用的生产案例再做盘点。

转给那个还在纠结 Rust Web 框架选哪个的同事——35 倍只在一个格子成立。微信搜索「梦兽编程」。

常见问题

Proa 到底是个什么项目？

Rust 写的 Web 框架，卖点是把服务端渲染做成序列化问题：模板在编译期固化成字节序列，运行时零分配往 buffer 里写 HTML，再叠路由、流式、RSJS islands（服务端组件 + 细粒度客户端交互）。仓库 7ab85e1，Apache-2.0。

35 倍这个数是怎么来的，为什么我说它窄？

官方 17 渲染器基准表（Apple M4 Max）：组件页 Proa 2.00µs vs React 70.9µs = 35.4×。但同表 1000 行大表只有 13.2×、商品网格 15.0×——页面越大，React 的「组件树重建」劣势被 Proa 自己的输出字节量追近，倍数往下掉。35× 是三个页面里最窄的那一格。

Askama 怎么反而比 Proa 快了？

官方表里 Askama 组件页 0.71×（比 Proa 快 41%）。原因是字节量不同：Askama 模板保留作者缩进，输出 44,849 字节 vs Proa 25,108 字节；小页面上纯编译期模板引擎没有框架税（路由/流式/islands 全不碰），裸渲染反而快。Proa 卖的是框架，不是裸渲染速度。本机 2 核也复现了同方向反超（1.84 vs 3.33µs）。

我选 Web 框架该看渲染速度吗？

看场景。Proa 的差异点在「同组件出 HTML 给人、出 Markdown 给 agent」的多目标渲染——agent 时代页面本身就是 API 的卖点。但渲染倍数只是其中一格；生态成熟度、部署工具链、团队熟悉度都算进去。HN 评论区里就有人直接说 decision paralysis：loco、topcoat、proa 全摆面前。
