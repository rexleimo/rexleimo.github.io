Linux 内核 Rust 块驱动 rnull：性能与 C 打平，真正的价值在长尾设备

三星的 Andreas Hindborg 把内核里最老的测试块驱动 null_blk 用 Rust 重写了一遍，83 个补丁对齐 C 版全部 24 项特性。官方基准：性能打平。rnull 的意义不在替代 C 驱动，在于给长尾小众设备一份能进 mainline 的 Rust 蓝图。

November 6, 2026 · 4 min · 698 words · 梦兽编程 -  | 

为什么一个空驱动值得盯#

内核里有个特殊的驱动叫 null_blk，它什么活都不干：接受所有 I/O 请求，立刻标记完成。它存在的意义就是给块层做性能基准测试。2026 年 6 月，三星的 Andreas Hindborg 把同样的东西用 Rust 重写了一遍，起名 rnull，patchset 一共 83 个补丁、改动 29 个文件，增 6603 行、删 342 行，目标是让 Rust 版和 C 版功能完全对齐。

为什么盯一个空驱动。C 版 null_blk 的 commit log 里，41% 的已合入修复是内存安全修复（Rust for Linux 项目页统计）。块层是内核里内存安全隐患最大的地方之一，rnull 的意义不在这个驱动本身，在于它证明了「用内核 Rust API 写一个功能完整的块驱动」这条路，现在走得通了。

极简版先合入，完整版在追功能对齐#

rnull 不是一步到位进 mainline 的。极简版在 2024 年 10 月的 6.11 合入窗进 v6.11-rc1，当时只有 blk-mq 接口、直接完成、4K 块大小这几个特性，项目页原话是 minimal stub。合入块层 Rust 支持时，LWN 的合入窗报道写得很直白：支持已经进来了，但当时唯一使用者就是 null_blk 这个示例驱动。

完整版是 2026 年两发。2026 年 2 月发 v1，79 个补丁，32 个文件，增 6278 删 309，基线 6.19-rc5；6 月发 v2，83 个补丁，目标树换到 rnull-v7.1-rc2。两发 patchset 的主体都在补 Rust 块层最后几块抽象：bio 模块、Request 私有数据、TagSet flags、configfs 宏、zoned storage（光 zoned.rs 一个文件就 696 行）、fault-injection、poll queue、FUA、内存 backing。

对齐全景是 24 个特性：blk-mq、direct / softirq / timer 三条完成路径、内存 backing、bio-based 提交、NUMA、discard、cache 仿真、带宽限速、IO 调度器配置、blocking 模式、shared tags、badblocks、zoned storage、poll queue（项目页特性清单）。C 版 null_blk 有的测试旋钮，Rust 版一个不缺。

把时间线拉出来看：2023 年 5 月 Hindborg 发公告和初代 RFC，432 个 fio 配置开始跑；2024 年 3 月发块层 API 的 RFC，把驱动名定成 rnull；2024 年 10 月极简版进 v6.11-rc1；2026 年 2 月和 6 月两发 feature parity patchset。三年多，从「块层 Rust 支持能不能立住」走到「Rust 块驱动能不能和 C 打平」。

v1 到 v2，改的都是实打实的坑#

v2 相对 v1 不是功能清单的简单追加，cover letter 里点名的修复有四个，都是 v1 跑起来才会暴露的问题：

transfer length 的移位计算方向写反了，这个 bug 从 2023 年 5 月的初代 RFC 就一直带着，到 v2 才修掉。

badblocks 现在限制 IO size 为一个，堵住一个越界窗口。

configfs 的 power 属性加了检查，修掉 create/delete 和 power 检查之间的 TOCTOU 窗口。

bio 模块在 v2 里被 Alice Ryhl 重写了一遍。

四条没有一条是「补功能」，全是「把 v1 的坑填平」。一个驱动在两发 patchset 之间修掉的是自己的历史账，不是新需求。

写出来的驱动长什么样#

rnull 的代码路径对想写块驱动的人价值最大。每个块设备用一个 NullBlkDevice 结构体表示，它实现内核 Rust API 的 Operations trait，#[vtable] 宏把 trait 的方法打包成一张 vtable，对内核其他部分来说和 C 实现看起来一模一样。

核心逻辑短得有点意外。关掉 fault-injection，处理一个请求就是：拿到请求锁，如果是 Flush 就刷一下内存 backing，然后标记完成；如果是 poll 就进 poll queue；否则直接完成。整个函数没有一次真正的磁盘操作，这正是 null 驱动该有的样子。

复杂的是脚手架。模块初始化包在 pin_init_scope 里，读模块参数、创建 nr_devices 个盘、把 configfs 接口和盘列表存进 pinned 数据：

pin_init::pin_init_scope(move || -> Result<_, Error> {
    let blocking = module_parameters::blocking.value();
    let shared_tag_set = NullBlkDevice::build_tag_set(...);
    let mut disks = KVec::new();
    for i in 0..module_parameters::nr_devices.value() {
        let disk = NullBlkDevice::new(...)?;
        disks.push(disk, GFP_KERNEL)?;
    }
    Ok(try_pin_init!(Self {
        configfs_subsystem <- configfs::subsystem(shared_tag_set),
        param_disks <- new_mutex!(disks),
    }))
})

代码摘录自 LWN 原文的 rnull v2 patchset。configfs 暴露和 C 版一样的配置项，但它用 const generics 为每个属性生成一张 vtable，比单个 #[vtable] 绕一圈。

用户态的操作方式和 C 版完全一致：挂载 configfs，建目录，往 power 写 1，内核就创建一个 GenDisk 块设备。

Null block device 6.6 性能测试（rnull 项目页配图，C 版 null_blk 时代的基准图）

2023 年的 432 配置 fio 矩阵就是为这类对比准备的：C 版和 Rust 版拉同样的活，看内存安全修不修、性能掉不掉。当年按 IO 计时的结论是略慢但打平，完整版的基准数字在下文。

性能：和 C 打平，不是碾压#

6.19-rc5 上的官方 benchmark 给的是定性结论，不是百分比。测试机是 AMD Ryzen 5 7600、单通道 DDR5 4800、三星 990 Pro、NixOS 24.11，每个配置 40 次采样，用 t 分布建模均值差、取 P95 置信区间。结果：单线程略差，高队列深度略差，部分请求尺寸反而更快，多数场景统计上分不出差异。

图里具体百分比读不出来，官方正文也没给数字，只给了这张差异图。密度版更能说明问题：C 分布的边界在左（蓝线），Rust 在右（橙线），两条分布高度重叠。

历史对照可以拉 2023 年初代 RFC 那批数字：432 个 fio 配置，读 IOPS Rust 相对 C 在 +6.8% 到 −11.8% 之间（均值 +0.2%），写 +16.8% 到 −4.5%（均值 +0.9%），fio randread 2 并发 16KiB 那个点 Rust 快 4.74%（Phoronix 转述 Hindborg 公告）。三年过去，结论稳定在同一句话上：Rust 绑定没有显著 overhead，但也没有 magic speedup。

7.1 又往快推了一档#

Linux 7.1 加了个 CONFIG_RUST_INLINE_HELPERS，把 C helper 以 LLVM IR 内联进 Rust 代码，需要 Clang 编译且 LLVM 大版本对齐。官方给的示例效果就是 Rust null block driver 快约 2%。这个配置要整套 Clang 工具链加 LLVM 版本对齐，能不能直接用取决于发行版内核怎么编（Phoronix 报道未覆盖发行版默认状态）。同版把最低 Rust 工具链从 1.78 提到 1.85，Bindgen 从 0.65.1 提到 0.71.1，和 Debian Trixie 对齐（Phoronix 报道）。

把两个数字放在一起读，意思就清楚了。Rust 块驱动经过 vtable 和 const generics 的抽象层，性能能跟手写 C 打平，说明这层抽象的开销落在测量噪声里；而 7.1 的内联 helper 又把它往上推了约 2%，说明块层 API 本身还在继续为 Rust 路径做优化。对驱动作者来说，这组数字意味着：现在写一个内核 Rust 驱动，不用为「Rust 会更慢」留性能余量。

它在整个 Rust 驱动版图里的位置#

截至 2026 年 8 月，内核里的 Rust 驱动分两类。一类是大项目：Android 的 Rust binder、Nova、Tyr，有团队愿意把所有需要的 Rust 抽象都实现掉。一类是长尾小驱动：两族网卡（AX88796B、QT2025）、TH1520 PWM 控制器、CPU 频率管理。

LWN 的判断很直接：大项目吸走注意力，但真正从 Rust 里受益更多的是长尾。内核里有一大堆「tiny, obscure, neglected」的小设备驱动，没有团队去维护，C 写起来又容易出内存安全问题。这些小驱动给「不敢写内核 C、但想给自己的小众设备加支持」的人一份蓝图，rnull 把同样的蓝图扩展到块设备。

落到具体场景：你手上有一个小众的存储控制器，没有商业团队愿意维护它的内核驱动，C 版没人接盘，写出来也怕 use-after-free。Rust 加上块层这套 API 意味着同一份代码可以直接发 patchset 进 mainline，review 门槛和 C 驱动一样，但类内存安全问题的修复量按 null_blk 的比例看能砍掉一大块（41% 的历史修复就是这一类）。

怎么开始写一个#

要试的话，rnull 的源码就在 mainline 的 drivers/block/rnull/ 下，配置项是 BLK_DEV_RUST_NULL，还是实验性标记。读代码路径比读教程有用：它把「Rust 块驱动的最小完整骨架」摊开了——module!() 声明模块、pin_init_scope 初始化、Operations trait + #[vtable]、configfs 脚手架。照着这个骨架把完成逻辑换成自己设备的逻辑，就是一个能提的内核 Rust 块驱动。

项目侧的两个仓库值得存：Rust for Linux 官方文档站（源码在 Rust-for-Linux/rust-for-linux.com，GitHub API 实测 78 star / 29 fork）和 Hindborg 的依赖树 git.kernel.org/pub/scm/linux/kernel/git/a.hindborg/linux.git（rnull-v6.19-rc5、rnull-v7.1-rc2 分支）。

另一个参照系是树外。fishinabarrel 的 linux-kernel-module-rust（GitHub API 实测 1337 star）是个树外 Rust 内核 LKM 框架，星标数远超树内项目，但定位不同：树外框架让你立刻写出能加载的 Rust 内核模块，树内 API 是让这类驱动最终能进 mainline 的落点。想进内核主干，rnull 读出来的习惯才是对的。

周期预期要摆正。rnull 从 2023 年 5 月初代 RFC 到 2026 年 6 月 v2，三年半走了两发 feature parity patchset、中间 2024 年 10 月合入过极简版。你的驱动不需要 83 个补丁，但「RFC 被拆开重做、补丁集在 review 轮次里膨胀、依赖树跟着上游 RC 换基线」是常态。按两到三个内核版本周期准备耐心，patchset 按模块切开、每发配齐基准数字，能显著压缩往返次数。

FAQ#

Q：rnull 能上生产吗？ 不能。null_blk 和 rnull 都是 benchmark 驱动，接受所有请求立刻完成，没有真实 I/O。它是块层 Rust API 的验证载体，不是给生产部署的。

Q：Rust 块驱动比 C 快吗？ 官方 6.19-rc5 基准：多数场景统计上无差异，单线程和高队列深度略差，部分请求尺寸略快。7.1 加内联 helper 后官方示例快约 2%。没有碾压级优势，主要收益是内存安全，不是性能。

Q：为什么选 null_blk 当 Rust 块驱动的起点？ 它功能面覆盖广（bad blocks、带宽限速、zoned、fault injection、poll queue），能把块层需要的 Rust 抽象全逼出来，又逻辑简单（没有真实 I/O），适合当 API 成熟度的试金石。

Q：我现在能提一个 Rust 块驱动到 mainline 吗？ API 还在补最后几块抽象（v2 patchset 的主体）。更现实的路径是先在 rnull 的依赖树（a.hindborg tree）上跑，等 feature parity 的 patchset 合进主线再提设备驱动。

Q：和 libbpf、bcc 有什么关系？ 没有直接关系。rnull 是内核态驱动，走内核 Rust API；libbpf/bcc 是用户态 eBPF 工具链。两者都属于「内核用 Rust 重写基础设施」的大方向，但技术栈不重叠。
