阿里开源 AgentScope 的 event-log 生产适用性：一张 KV 表、14 倍放大与 23 秒的代价

AgentScope Java 的 HarnessAgent 默认事件日志模式：journal 只追加、永不压缩，上游实测写放大 14~17 倍、读侧 O(n²) 退化。本地三后端复现 + 上游 issue 数字 + 生产适配 playbook。

November 7, 2026 · 6 min · 1193 words · 梦兽编程 -  |  English

一条没等来答案的提问#

前几天，有开发者在论坛里发了一条帖子：Java 生态做 webchat 平台级 agent，框架选了阿里开源的 AgentScope，跑起来后发现 HarnessAgent 默认的事件日志模式把所有原生日志都写进一张 KV 表，多用户并发之后这张表膨胀得很快，想找一个成熟的处理方案。帖子发了半天，没人回。

答案其实不藏在论坛里，而是拆散在框架源码、官方文档和上游 issue 列表里。把这几条线拼起来读完，你会得到一个相当具体的图景：这套事件日志是为审计设计的，不是为省空间设计的；它膨胀没有上限，读侧还会随会话深度二次方退化；官方给的后端可替换、导出、清理三件套是有的，但保留策略（retention）这一页，文档至今是空白的。本文把机制拆到源码行，用上游实测和本地复现的数字说清楚一件事：多用户 webchat 直接默认配置上生产，会发生什么，以及怎么改。

为什么这篇值得写：AgentScope Java 是 2026 年活跃度最高的一档 Java agent 框架之一——仓库 6,282 星、983 个 open issue、本文写作当日（11-07）还在推码，而它的事件日志子模块 10 月 19 日到 11 月 5 日之间集中开了 5 个读侧/体积 issue（#3816/#3647/#3987/#3812/#3995），紧随其后是修读侧和写侧挂起的 PR 管线（#3666/#3888）。这些 issue 全是同一类抱怨的不同切面：默认配置在单用户 demo 里无感，在多用户服务里会同时踩中存储、延迟、恢复三条线。

先把「事件日志」这个词读准#

AgentScope Java 2.0 里，HarnessAgent 的默认会话模式叫 EVENT_LOG。它的底层实现是 JournalSessionLog，一个不可变 commit 链：每个会话目录（agents/s_<agent>/sessions/s_<user>/s_<session>/）里有会话头 session.json、链尾指针 head.json、按批归档的 commits/<hash>.json 和大于 64KB 载荷单独存放的 blobs/<sha256> 对象[1]。commit 之间用 SHA-256 哈希链起来，每次提交走 head 的原子 CAS 加写者租约（fencing），防止两个写者同时接管同一个会话。

官方给它的定位是「审计级无损日志」：压缩（compaction）只缩小进模型上下文的窗口，journal 本身永不压缩、永不重写。这个定位决定了后面所有膨胀问题的性质——你不是遇到了 bug，而是遇到了设计。每个流式分片（model/chunk）、每次工具调用（tool/requested/tool/result）、每轮任务边界（turn/*）、每次模型调用前的完整请求（request/prepared）都会落成事件，事件目录里一共 40 多种类型[2]。

这条链不只是「记日志」。commit() 先校验事件 seq 连续，再写以 batchId 哈希命名的 commit 文件，然后在最多 32 次的重试环里做 head.json 的 CAS；如果当前 commit 的 ACK 丢了，它顺着 parent 指针回走链来补齐幂等语义（JournalSessionLog.java L193 起）。写者持租约：acquire(owner, lease) 与 renew(writer, lease) 把 owner 和过期时间写进 head，租约失效后旧写者的提交直接抛「Writer renewal contention」（acquire L106，renew L166）——这就是多副本场景下的 fencing，一个挂掉的旧进程不能把链写花。大载荷阈值是写死的 65,536 字节，单个事件超线就内容寻址进 blobs/<sha256>，commit 里只留引用。

写侧还有一个容易忽略的细节：SessionRecorder 用 1 秒周期的定时任务 flush，每秒只要缓冲区里有事件就提交一批[3]。也就是说 commit 数量跟着墙钟走，不跟内容走——上游实测 12 轮会话产生 506 次 commit，平均每轮 42 次[4]。

为什么多用户场景下一张表会失控#

膨胀是三个机制叠加的结果。第一层是「永不删」：commit 链只追加，blob 内容寻址只去重不回收，journal 的总字节数对事件总量单调递增。第二层是「重记」：每次模型调用都会把整份请求——消息历史、工具定义、选项——作为 request/prepared 再落一遍，会话越长这份记录越大，总量对轮数近似二次增长；上游已经提了 issue 要求提供 compact 模式，目前还开着[5]。第三层是「共享」：多用户 webchat 里，所有会话落在同一个存储里。

楼主说的「一张 KV 表」，最可能对应的就是 Windows/Java 文件系统后端的 journal.sqlite3：整库只有一张表 session_objects(path TEXT PRIMARY KEY, version, payload)，所有用户、所有会话的 commit、blob、head 全部挤在这张表的行里[6]。共享 KV 后端（Redis/JDBC 的 BaseStore）也一样，session 日志和 memory 共用一套命名空间段，key 形如 agentscope:store:item:agents\0<agentId>\0users\0<userId>\0sessions\0...[7]。官方文档在 KV 选型一节明确写了「不要把 OSS 当 KV 用」（高频小对象走 Redis/MySQL，大对象才走 OSS），但通篇没有保留策略——RedisAgentStateStore 是否该有 TTL，有人八月份就问过，至今 open[8]。

这张 SQLite 表为什么天生偏重，源码里三个细节。第一，SqliteSessionStorage 的类注释是「Windows local journal storage, using atomic SQL writes and synchronous rollback journals」：connect() 每次调用都 DriverManager.getConnection 开新连接并执行 PRAGMA synchronous=EXTRA（L42/L59/L63），EXTRA 是 SQLite 五档同步里最强的一档，而每次 CAS、每次 blob 去重检查都是独立事务，写放大直接乘上去。第二，读路径同样每次新建连接（L85 的 SELECT version, payload），上游 #3647 量到单读 0.69 ms，复用连接只要 0.053 ms[4]。第三，会话列表走 substr(path, 1, length(prefix)) 前缀扫（L125），没有轻量元数据索引——这就是「列 17 个会话要 6 秒」的根因[9]。

「共享」一层的成本在并发写。SQLite 数据库天然是单写者：任意时刻只有一个写事务在跑，而这个后端每次连接都设了回滚日志同步（synchronous=EXTRA），提交路径上的 fsync 更多——所有用户、所有会话的 commit 都在同一把写锁后面排队，多用户并发不产生并行收益，只产生等待。Redis 侧好一些，key 粒度天然可并发，但框架的 key 设计把整个日志树摊在同一个 store 的命名空间段里，RedisAgentStateStore 没有暴露 TTL 入口（#2781 问的就是这个，至今 open[8]），要给日志设保留周期只能自己在自定义 SessionLogStore 里包一层过期策略。

数字墙：上游先付过的学费#

上游社区已经把坑踩得很深了，这几个数字都出自 2026 年 10 月的 issue，场景都是「事件日志开在文件系统 journal 上」[4]：

一个只有 12 轮的测试会话，journal 14.35 MB、15,252 个事件、506 次 commit；而模型实际输出的正文、思考与工具参数合计只有 0.83 MB——放大 14 到 17 倍。读侧更糟：每轮运行前大约要全量重放 7 遍整条 commit 链，其中 SessionInteractions.pending() 是 O(n²) 的循环读（15,252 事件 ÷ 256 窗口 ≈ 60 次，每次都要走约 506 个 commit，合计约 6 万次存储读），单项耗时 12.7 秒；同一份数据做一次完整 scan 只要 0.786 秒。体验上的退化曲线：同一会话第 1 轮「提交 → 首个 token」间隔 0.06 秒，到第 10 轮变成 23 秒，而模型本身整轮只花 0.95 秒——用户感知到的 20 到 30 秒等待里，几乎没有一秒是模型在思考[4]。

Windows 后端的读侧还有额外税：每次存储读都新建一条 SQLite 连接并执行 PRAGMA synchronous=EXTRA，实测单读 0.69 ms，复用连接只要 0.053 ms，差 13 倍[4]。会话列表接口没有任何轻量元数据路径：列出 17 个会话要超过 6 秒，复杂度是会话数 × 全量重放[9]；JDBC 后端上 445 个 commit 段的会话，恢复要 ~35 秒才能出首 token[10]。

还有一条容易被漏掉的：#3812 指出每次模型调用前，完整请求体（消息历史 + 工具定义 + 选项）都会以 request/prepared 进 journal，且长会话里这份请求体随深度线性变大——事件总量对轮数近似二次增长，这是 14~17 倍放大的主要构成，也是它要求加 compact 模式的直接原因[5]。共享存储上的 #3995 更隐蔽：StoreSessionStorage 没覆写批量 readAll，于是每次重放在远端库里退化成逐事件 1 次 GET，事件越多网络往返越多，把 O(n²) 又乘了一个网络 RTT[14]。

本地复现：日志层的真实数字#

上游数字是 10 月底的，而读侧优化 #3666（批量段读，一次往返读完整条链）10 月 28 日才合入 main[11]。为看现状，我们在 main（v2.1.0-SNAPSHOT，2026-11-07 抓取）上直接驱动日志层：真实的 JournalSessionLog 加三种后端（POSIX 本地文件、内存 KV、SQLite 单表），事件分布按 #3816 的实测会话 profile 合成——85% 是小流式分片，7% 工具流量（其中 2% 跨 64KB 进 blob），6% 是整条 assistant 消息，2% 是随会话深度增长的 request/prepared（封顶 100KB，最大档的 O(n²) 主驱动），每 32 事件一批模拟 1 秒心跳，共 2,000 / 20,000 / 200,000 三档规模。机器是 2 个 vCPU（AMD EPYC 9354P 切片）、7.8 GB 内存，JDK 17.0.21[12]。方法论上一处例外要说明：本号惯例在 LiteBox 沙盒里跑测试代码，这次跑不了——HotSpot 在沙盒内被 seccomp 挡在 PaX exec-memory 探针（「failed to allocate memory for PaX check」），只能用宿主受限工作目录：所有产物落在项目目录与 /tmp，无全局副作用。压测工具 JournalBench 放在 io.agentscope.harness.agent.session 包私有作用域里，直接驱动日志层公开 API——acquire 拿写者租约，每 32 事件调一次 commit，读侧量 pending()、全量 scan(0, head)、以及 256 窗口循环 readAfter 三种读法，全程不碰任何 agent 推理路径，所以数字只反映日志层，不含模型 I/O。

四个观察。写放大的分母与上游不同：本地对比的是 journal 落盘字节对原始载荷字节（20K 档 26.6/22.3 ≈ 1.2 倍），而上游的 14~17 倍对比的是 journal 对「模型实际输出内容」——分母里那个 0.83 MB 不含 request/prepared 的重记项，所以两个数字都对，只是量的是不同的东西。第二，pending() 的 O(n²) 在合入批量读之后依然在：事件量 ×10，pending 从 ~0.2 秒跳到 ~10 秒；200K 档直接量到 802 秒——同一会话 20 万事件之后，单次 pending() 就是 13.4 分钟。这个调用点比直觉里多：AgentSession 的 submit/resume/respond 三条命令入口都会先调 SessionInteractions.pending(log) 做校验与请求归属解析（AgentSession.java L161/L206，命令 prepare 在 SessionExecution.java L69），进程重启的 SessionRecovery（L52）、会话状态变更检查 SessionStateAccess（L107）也要各调一次，而 AgentSession 的 dispatch 是 100ms 周期调度（AgentSession.java L124）——也就是说不是「某一次冷恢复」贵，是每次命令往返都在付这笔账。这就是 #3987 提议在链尾维护 anchors.json 把恢复降到 O(1) 的原因[10]。第三，SQLite 单表写代价在 20K 档是 POSIX 的 2.4 倍、内存 KV 的 11.5 倍（EXTRA 同步 + 每次 CAS 各自事务）；到 200K 档写时间差收窄（87.6 s vs POSIX 55.8 s，1.57 倍——单 commit 成本恒定，绝对差距由写次数主导），但同一张表上多用户并发写仍会被 fsync 串行化。第四，内存 KV 的 value 字节（35.6 MB）比 POSIX 落盘（26.6 MB）大 34%，因为 KV 后端把 commit 对象整体 JSON 化存储，去不掉 POSIX 文件里 8 字节版本前缀之外的任何东西——反过来说，Redis 里真实占用的内存要按 KV 侧数字估。表里 200K 档三个后端（189.6 / 254.2 / 195.5 MB）都是 blob 内容寻址去重之后的值：合成事件的大载荷按槽位确定性生成，跨轮同内容只存一份 blob，真实数据里工具输出各不相同，去重收益远小于这个数，容量预算要按 20K 档的 1.66 MB/模拟轮做保守估计。

表里有个对照值得单独说：全量 scan 三档都是线性（169 ms → 683 ms → 6.5 s，事件 ×100，耗时 ×38），这是 #3666 批量读的效果；而 pending() 三档 180 ms → 11.2 s → 802 s，事件 ×100 耗时 ×4,455——因为它不是批量读，是 256 窗口逐批 readAfter，每批都要从链头走一遍 commit，窗口数 × 链长就是 O(n²)。注意本地压测的 pendingInteractions 全程是 0：链上根本没有未交付的用户事件，但查询本身照样把全链放了一遍——也就是说这笔 O(n²) 不是「有待办才付」，是「每次查都付」。

按 20K 档 1.66 MB/模拟轮（1271 事件/轮，与上游实测会话同密度）外推：一个日活 1,000 人、每人每天 30 轮活动的 webchat，默认配置下事件日志每天新增约 50 GB 原始载荷（一周 350 GB），SQLite 单表和 Redis 在这基础上再乘 1.2~1.6，且没有任何组件会替你删。这就是「多用户下表快速膨胀」的完整算术。

数字的可复现性说明：每档压测结果落盘为 JSON 检查点（事件数、commit 数、写入/全量 scan/pending/循环 readAfter 四段耗时、落盘或 KV 字节、head 序号），机器是固定的 2 vCPU EPYC 切片——绝对值不可跨机搬运，但后端间的比值（SQLite 写是 POSIX 的 2.4 倍、pending 的 O(n²) 斜率）在同类硬件上可预期复现。压测合成事件是确定性 profile（同槽位同内容），200K 档的去重字节因此偏乐观，正文已按 20K 档做保守外推。

生产适配：能动手的地方#

先说清边界：本文没跑完整 agent 端到端（没有可用的模型密钥），所有本地数字来自日志层驱动，事件分布按上游实测 profile 合成；上游引文均出自 2026-10~11 的 issue 原文，版本 v2.1.0-SNAPSHOT。

框架给了四个杠杆。第一个是换后端：.sessionLogStore(...) 接受任意实现了 SessionLogStore 或 AtomicSessionStorage 的自定义存储，官方要求原子版本比较写、写租约、有序幂等提交，普通 KV 读写不够格[1]。这是做保留策略的正规入口——分片、TTL、冷热分层都在这一层解决。第二个是导出：SessionLogExporter 配应用自定义的 SessionExportSink 可以增量把已提交事件抽到数仓或审计系统，投递是 at-least-once，目标端按 eventId 去重[1]。热数据进 KV，冷数据进数仓，表就瘦下来了。第三个是清理：deleteSessionState(...) 提供会话级删除，LEGACY 侧的 maxPersistedContextMessages 可以给持久化快照限消息数——但注意默认值是无限，为了向后兼容[13]。第四个是换模式：.legacySessionHistory(true) 走 LEGACY 状态快照，体积有界（快照每次覆盖写），代价是丢掉事件级审计、重放和压缩事件。LEGACY 侧的状态走 AgentStateStore，官方核心加扩展模块一共给了 12 种实现（InMemory、JsonFile、Redis 三种客户端、JDBC/MySQL/PostgreSQL/Mongo、OSS/COS、JPA），快照只保存恢复会话需要的上下文，不保存事件时间线——HITL 的 pending 交互、工具调用的逐事件重放、session_search 这类基于 journal 的工具在 LEGACY 模式下都不可用；如果你的 webchat 依赖「会话列表 + 历史回溯」产品功能，换模式等于砍功能，不只是省空间。

多副本是另一个要提前设计的点：HarnessAgent 本身是无状态单例，官方多副本方案是所有副本指向同一个存储后端——RedisDistributedStore 注入 BaseStore，配 RemoteFilesystemSpec（IsolationScope.USER 做按用户隔离）加 WorkspaceIndex，或者 .sessionLogStore 单独指一个日志专用后端；checklist 要求副本间同库、同身份、同 namespace，否则哈希链会出现两条尾巴，CAS 全部失败[1]。切换 EVENT_LOG 与 LEGACY 模式是单向门：同一会话不能中途换，要删旧会话（deleteSessionState）起新会话迁移，在线切换会丢事件级时间线。

备份与恢复也要按后端分开做。POSIX 后端是目录树，直接对 agents/s_*/sessions/ 做一致性拷贝即可，恢复时原样拷回、hash 链自校验；Windows 的 journal.sqlite3 是单文件但带写锁，备份要先停写（或把整个实例引流量切走）再做一致性快照，直接拷运行中的库大概率拿到半提交状态；Redis 共享后端走 RDB/AOF，注意日志 key 与 memory key 在同一 store 里，恢复时两者的版本要匹配，否则 session.json 头与 commit 链对不上。

上游自己的修复管线值得跟进：#3666 批量段读已合入（10-28）[11]；#3888 的写侧中断修复也在路上（open PR）——它要解的是：flush 订阅被调用方取消（请求超时、订阅者消失）时，Reactor 的 boundedElastic 会中断正跑在 renew/commit 里的线程，写者租约状态被留在中间态，journal 写直接挂起[17]；#3987 的 anchors O(1) 恢复、#3812 的 compact 请求记录、#3995 的逐读修复还开着[10,5,14]；#2145 指出工具结果驱逐中间件在 Redis 状态里仍留全量输出，长会话的上下文封顶会被它绕过[15]。如果生产要跑长会话，建议盯 main 分支这几个编号的合入情况，别只看版本号。

给楼主的场景（Java 多用户 webchat）一个可执行的组合：共享 Redis 当 BaseStore（官方主推）+ 自定义 SessionLogStore 包一层 TTL 与冷热归档 + SessionLogExporter 定时 drain 进数仓 + 会话到期 deleteSessionState。四步都走官方接口，不 fork 框架。drain 频率按事件产出定：1 秒心跳 flush 的默认配置下，数仓侧至少 5 分钟粒度去拉游标（exportCursor 有原子推进，重放安全），KV 侧 TTL 给 7 天足够覆盖绝大多数审计窗口。

结论分级#

单用户或十人以内的小团队，本地默认配置没有问题，膨胀量以百 MB 计，一年也撑不满一块盘。百人到千人级 webchat、会话活跃度高、且不开保留策略的，会先撞上读侧：会话越深首 token 越慢（上游实测第 10 轮 23 秒），会话列表接口先于存储告警不可用——这是最容易误诊为「模型变慢」的一类事故。审计需求真实存在的团队，别为省空间关掉 EVENT_LOG，hash 链加内容寻址 blob 是有独立价值的；正确动作是把保留策略补上，让「无损」只对热数据成立。上生产前配两个监控：journal 目录字节数与 commit 计数（两者单调递增，增长率就是告警基准），以及 pending() 耗时的 P99——它持续抬头说明会话正在进入 O(n²) 区间，读侧雪崩比磁盘写满是更早的信号。落到自己场景可以先算一笔账：单会话日均轮数 × 1.66 MB/轮（20K 档实测，低去重保守值）× 活跃会话数，再乘你的 SQLite/Redis 系数 1.2~1.6，得到每周日志增量；这个数超过存储预算 20% 就该动保留策略了。一句话：这套日志适合当审计底座，不适合当默认的生产配置直接裸露。

FAQ#

能不能直接关掉事件日志？ 可以，.legacySessionHistory(true) 切 LEGACY 状态快照模式。代价是丢事件级时间线、session_search 类投影和无损重放，恢复只到快照粒度。混合部署注意：同一会话不能中途换模式，框架会抛 authority mismatch，要迁移到新会话[1]。

那张单 KV 表能撑多大规模？ 本地 20,000 事件 SQLite 写 9.9 秒、单库 27 MB；按 1.66 MB/活动轮次外推，千人日活平台一周就是几十 GB，SQLite 单文件还会被 fsync 串行写拖垮多用户并发——这也是为什么官方 going-to-production 把 Redis 当多副本默认，而 SQLite 后端只出现在 Windows 本地路径[7]。

Windows 和 Linux 差别在哪？ 逻辑对象完全相同（文档明确说同一套对象两种物理形态），差别在执行路径：POSIX 走临时文件加原子 rename 加目录 fsync；Windows 的 Java 文件系统打不开目录做同步，改用 journal.sqlite3 单表加 synchronous=EXTRA，且每次读新建连接（单读 0.69 ms vs 复用 0.053 ms）[6,4]。跨平台迁移历史要走日志迁移或共享后端。

多副本部署怎么共享日志？ 所有副本指到同一个共享后端：RedisDistributedStore 注入 BaseStore 加 RemoteFilesystemSpec（IsolationScope.USER 切租户），或用 .sessionLogStore(WorkspaceSessionLogStore(BaseStore)) 单独指日志后端。官方强调多副本必须同库同身份同 namespace，「每个副本各用同名本地目录」不等于共享[1,7]。

历史日志能不能删、怎么删？ 会话级 deleteSessionState(...)；批量冷热分层走 SessionLogExporter 抽到数仓后再清源；Windows 后端备份要整库一致性快照（先停写再拷，或 SQLite 一致性备份），单拷文件不等于完整备份[1,13]。
