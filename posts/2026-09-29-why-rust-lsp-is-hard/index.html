Rust 的 LSP 为什么难做：写 rust-analyzer 的人停更了，一个新作者把门重新推开

matklad 的 rust-analyzer 博客 2023 年停更，LSP 内部原理的中文资料几乎绝迹。9 月 16 日，Rust Glancer 作者 Igor Aleksanov（popzxc）发了篇长文《Why building a Rust LSP is hard》，从 VFS、查询并发、索引分层到「猜用户想干什么」，把 LSP 为什么难做讲了一遍。这篇拆它讲得最好的几层：懒求值的 salsa 和急求值的文件系统，为什么同一个问题有两个答案；以及 LSP 和编译器最根本的区别——编译器有「done」，LSP 永远只有「还不够」。

September 29, 2026 · 2 min · 392 words · 梦兽编程 -  |  English

先说结论#

rust-analyzer 博客 2023 年停了，matklad 不再写 LSP 内部原理。三年后，一个没人听过的名字（相对 matklad 而言）把门重新推开：Rust Glancer 的作者 Igor Aleksanov，9 月 16 日发了篇 30 分钟读量的长文，《Why building a Rust LSP is hard》 外部链接 。

开头那张梗图值得原样搬：r/rust 说"聊聊 LSP 吧"，“matklad 不写了”，“那你自己写”，“我？？？"。……确实，除了他也没别人了。

这篇值得读的核心理由不是"又一篇讲 LSP 的”，而是作者手里同时握着两把武器：rust-analyzer 的全量源码（他明说动笔前读了大量 rust-analyzer 代码）+ 自己从零写 LSP 的失败记录（Rust Glancer）。同一个人把两条路线的代价都付过一遍，所以文里每个"其实很难"的论断后面都跟着一个具体的坑，不是抽象抱怨。三个结论前置：

  1. LSP 和编译器最根本的区别：编译器有 done，LSP 没有。 编译器要么编过要么没编过，LSP 要在你边打字边犯错的状态下提供服务，它永远只是"猜用户想干什么"。
  2. 同一个问题（怎么索引代码）有两个正交的哲学答案：rust-analyzer 的 salsa 懒求值 + 缓存预热，Rust Glancer 的急求值全量分析 + 卸载到文件系统。没有对错，只有取舍。
  3. “难"不在任何单个技术点，而在所有边界条件同时成立：UTF-16 行号、换行符检测、协议外文件变化、百万级符号的 pathological case。原文一句话点破：Building LSP is ALL about pathological cases.

编译器有 done，LSP 没有#

先立靶子：LSP 协议的第一条 initialize 请求就暴露了它和编译器的本质差异。编译器定义"完成"很粗暴——二进制要么生成要么没生成。编 715/716 个 crate 然后停掉，你会骂人。

LSP 没有这个概念。它要在 第一毫秒 就给有用结果。你打开文件，还没读几行，光标下的类型、符号列表、补全列表就得有反应——哪怕此时你的代码是残缺的、语法都不完整。

这就是原文那句断言的含义：LSP 是一个猜谜游戏，每一步你看到的都是"可能错误的状态”，你的目标是猜出用户下一步想干什么。 编译器拒绝分析"错的"代码，LSP 不能——因为它的工作就是把"错的"修对。

一个具体例子：textDocument/hover。光标停在 fn foo(a: Bar) {} 的 Bar 上，你要回答"这个 Bar 是哪来的"。链路是：解析文件 → 构建 item tree → 解析模块建定义图 → 查光标下的符号 → 提取文档。每一步都依赖上一步，而文件此刻可能根本解析不出来。rust-analyzer 靠 salsa 把这条链路摊平了；Rust Glancer 靠提前把全量分析做掉摊平的。问题相同，答案两种，成本模型完全不同。

文件系统：LSP 协议里没有，但必须自己同步#

LSP 协议设计上不让你关心文件系统——只有"文档"和"编辑"。合理：文档可能没保存，你不知道它的内容。

不合理的是：LSP 假设它是唯一事实源，但你的代码在磁盘上，编辑器外的工具（git、格式化器、另一个终端的 cargo）随时在改。 客户端对这些外部编辑的通报"未必忠实"（原文原话：the client might not be very faithful in notifying you）。

解法是 virtual filesystem + source generation：每次请求带一个"源码状态版本号"，状态一变，所有在飞的查询作废重跑。听起来优雅，实际是个永无止境的竞态——这也是"写 LSP 是种自虐"的出处之一：你 90% 的代码在处理状态一致性，剩下 10% 才是语言分析。

两条索引哲学：懒 vs 急#

这是全篇最值钱的一张对比表，原文散在各处，我把它收成一张：

维度rust-analyzer（salsa 路线）Rust Glancer（急求值路线）
核心思想声明"输入→输出"，输出懒求值+记忆化，不主动索引启动时一次性全量分析，结果卸载到文件系统
内存模型状态常驻内存（salsa 数据库）低内存：语法树用完就丢，状态在盘上
首次响应慢（要靠 cache priming 预跑 workspace 语义层）快（盘上有现成分析，增量只重算变了的部分）
编辑器重启重新计算全部（代价大）几乎秒开（读盘就行）
重构实现基于 parser 基础设施（rowan），优雅专用算法各写各的，不依赖 rowan，“不优雅但好用”
代价内存高、重启慢首索引慢、实现量大

经验句：选 LSP 架构不是选"正确"，是选"你能接受哪种慢"。 rust-analyzer 的慢是每次改代码都感觉得到；Glancer 的慢是一次性的（首索引），之后编辑器可以随便杀。

matklad 自己的评价（Rust Glancer 那篇 外部链接 ）值得引一句：Glancer 比 rust-analyzer 少两个数量级 RAM，“incredibly cool”。他还顺手开了 rust-analyzer 一个口子：理想架构应该用 .rmeta 文件当依赖的 PSI 后端，“别对着 6666 个你还没看的依赖跑 salsa”——原文那句"rust-analyzer is a bit like that half-drawn horse meme, except it’s only the head half"，自嘲得很。

病态 case：一个 Option 毁掉你的查询计划#

原文最有味道的一段：find references。你在 VS Code 里对一个 Option 按"查找引用"（option+shift+F12），服务器要在全 workspace 的函数体里区分这个 Option 和所有别的 Option。

“想 Option 就完事了”——不对。文本匹配先筛出"可能"包含该标识符的文件，再逐个函数体精查。如果全仓库有 4000 个 Option，4000 个函数体都要过一遍。rust-analyzer 博客里叫 reference search plan，本质是个倒排索引 + 剪枝。

原文补刀：“如果你以为 Option 匹配多是个 pathological case……写 LSP 就全是这种 pathological case。” 这是全篇最该抄进贴墙的一句。

LSP 协议本身在跟你作对#

协议层还有两个没被说透的坑：

  1. UTF-16 行号。LSP 要求服务器用 UTF-16 code unit 计数（编辑器世界的事实标准），但你的源码是 UTF-8，行号还得按行/列算。解法是协议桥：内部全用 UTF-8 偏移，只在通信边界转换。但前提是得对每个文件建 line index——一个"解析"操作也得带状态了。
  2. 换行符。不能假设 Windows 是 \r\n、Unix 是 \n——同一个仓库可能混着用。猜错一次，编辑就对不上。所以除了行索引，还得检测并存储每个文件用的换行符种类。

经验句：协议层的每个"小"约定，落到实现里都是一份 per-file 元数据状态机。 LSP 架构里"状态"不是例外，是常态。

诚实声明#

  • 全文基于 popzxc 博客 + matklad 的 Rust Glancer 评论 + rust-analyzer 博客，未读 Rust Glancer 源码，架构对比以两篇博客的描述为准。
  • “比 rust-analyzer 少两个数量级 RAM"是 matklad 原话（two orders of magnitude less RAM），未在本地复现。
  • Glancer 自称"实验性”，生产可用性我没有结论，不替它背书。

常见问题#

Glancer 能直接替换 rust-analyzer 吗？ 原作者定位为实验项目，重点在低内存和秒开，不是功能完整度。想试可以 cargo 装，但别指望补全/重构体验和 rust-analyzer 对齐——那是两条路线，不是同一个产品的两个版本。

写 LSP 最值钱的先修知识是什么？ salsa。原文直接点名推荐"花两个晚上搞懂"，配 rust-analyzer 的 Durable Incrementality 外部链接 和 find usages 那篇 外部链接 。不懂 salsa，你读不懂 rust-analyzer 代码里为什么一半是宏生成的。

“编译器有 done，LSP 没有"这句话的实际后果是什么？ 后果是 LSP 永远不能拒绝服务。代码写错，编译器直接报错让你改；LSP 得在错的代码上继续给补全、hover、诊断——它的工作就是让你从"错"走到"对”。这决定了它所有的工程复杂度都在"不一致状态下的可用性"上，而不是"正确性"上。

常见问题

Rust Glancer 是什么？和 rust-analyzer 什么关系？

Rust Glancer 是 popzxc（Igor Aleksanov）写的实验性 Rust LSP，目标是低内存占用和编辑器秒重启，比 rust-analyzer 少两个数量级的 RAM（matklad 原话：two orders of magnitude less RAM）。它不是替代品，是同一问题的另一个解法，这篇的价值正在于把两种解法摆在一起对比。

LSP 难在哪？不是就是个补全接口吗？

难在三点：（1）编译器有「编译完/没编译完」的二元 done，LSP 没有——它要在代码写一半、必然是错的状态下提供服务；（2）不同查询代价差几个数量级，hover 很便宜，references 要扫全 workspace 的函数体，得并行读+状态一变就取消在飞查询；（3）LSP 协议不给你文件系统，只有「文档+编辑」，你得自己同步编辑器外部的文件变化，这是个永无止境的竞态。

salsa 是什么，为什么值得花时间学？

salsa 是 rust-analyzer 用的增量计算数据库：声明「输入→输出」的转换规则，输出懒求值+记忆化，输入变了只重算受影响的输出。原文说得很直接：salsa feels like magic，花两个晚上搞懂它，你会不一样。配 rust-analyzer 的 Durable Incrementality 博客一起读。

普通用户需要关心这些吗？

不写 LSP 就不需要关心实现。但这篇对「为什么你的 IDE 有时卡、有时秒」有解释力：卡顿通常不是某个查询慢，而是编辑器刚改了一行，一堆在飞的查询被取消重跑。理解「没有 done 只有还不够」，就能分清哪些是该等、哪些是工具在正常干活。
