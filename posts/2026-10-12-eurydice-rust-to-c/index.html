Eurydice：把 Rust 编译成「人类可读的 C」——反向移植到底图什么

大家往 Rust 里跑，Eurydice 反着来——把 Rust 代码编译成干净的 C 源码（不是机器码）。它出自 Inria + 微软的 Aeneas 形式化验证项目：高置信软件的合规工具只认 C，Rust 想进老工具链就得先转成 C。LWN 10-09 报道。一篇讲「Rust 向下兼容老体系」。

October 12, 2026 · 2 min · 387 words · 梦兽编程 -  | 

LWN 10 月 9 日发了一篇报道：Compiling Rust to readable C with Eurydice 外部链接 。方向反直觉：这两年所有 Rust 新闻都在讲「C 代码用 Rust 重写更快」，这个项目反着来——把 Rust 代码编译成 C。

先给三个结论，再展开：

  1. Eurydice 不是「另一个 rustc」，是「Rust→C 的转译器」：编译产出是 .c 源码，不是机器码，专门喂给只认 C 的老工具链。
  2. 它出自 Inria（法国国家 CS 研究机构）+ 微软的 Aeneas 项目，核心场景是形式化验证：合规工具要 C，Rust 想进就得先转 C。
  3. 它不是万金油：LWN 评论区里头号贡献者亲口承认——Rust 泛型进 C 还没解，得在 C 上搭个「最小 C++」（作者原话 yuck），这是当前最大缺口。

这篇讲四件事：它跟 mrustc/gccrs/Cranelift 的分野在哪、gcd/lcm 那段真实转译代码、谁在推、以及没解决的事。

先分清：它出的是「C 源码」，不是「机器码」#

Rust 这几年的编译器实现其实早就不止 rustc 一家了：

实现输出目的
rustc + LLVM机器码默认主力
mrustc / rust_codegen_gcc / GCC-rust（gccrs）机器码自举 / 多后端
Cranelift机器码快后端（Wasm/增量编译）
EurydiceC 源码转译给老 C 工具链

前五个都在拼「把 Rust 变成可执行的东西」，Eurydice 拼的是「把 Rust 变成 C 程序员和 C 合规工具能接着吃的东西」。一句话：别的出 .o，它出 .c。

真实转译：gcd/lcm 那段#

LWN 举的例子女码很有信息量。Rust 递归 gcd + lcm：

fn gcd(a: u64, b: u64) -> u64 {
    if b == 0 {
        a
    } else {
        gcd(b, a % b)
    }
}

fn lcm(a: u64, b: u64) -> u64 {
    (a * b) / gcd(a, b)
}

Eurydice 转成 C：

uint64_t example_gcd(uint64_t a, uint64_t b)
{
    uint64_t uu____0;
    if (b == 0ULL)
    {
        uu____0 = a;
    }
    else
    {
        uu____0 = example_gcd(b, a % b);
    }
    return uu____0;
}

uint64_t example_lcm(uint64_t a, uint64_t b)
{
    uint64_t uu____0 = a * b;
    return uu____0 / example_gcd(a, b);
}

三处值得看：

  • 结构保留：递归、控制流原样搬，不是揉成一坨汇编。
  • 求值顺序也保住：lcm 的 a*b 先存进 uu____0 再除——这是刻意保留 Rust 的求值顺序（C 里顺序是未定义的，它偏要显式化），对验证工具友好。
  • 代价是 uu____0 这种匿名临时变量：可读性「够看懂，不够整洁」。作者 Daroc Alden 的原话就是「是不是 readable 看个人口味」。

谁在推：形式化验证这条线#

Eurydice 不是孤立项目，它挂在 Aeneas 项目下（Inria + 微软），Aeneas 做「把形式化验证工具用到 Rust 代码上」的一整套。背景是：

  • 形式化验证（证明程序满足规约）这套工具链，几十年积累，几乎全吃 C 的中间表示（C 语义 / CIL）。
  • 你想对 Rust 写的高置信代码做形式化验证，工具不认识 Rust——先转成 C，塞进现有验证器。

已经落地的用例：一批后量子密码算法（PQC）从 Rust 转 C。这类代码安全敏感、要审计，正是「工具只认 C」的典型场景。

边界：泛型是最大缺口（作者原话 yuck）#

LWN 评论区里 Eurydice 最活跃贡献者 Jonathan Protzenko 回了一段，把缺口摆得很直白（原文）：

要给 Rust 泛型一个完整解，得让宏在每次泛型被用到处内联吐出具体类型名（大概用 ## 把类型名粘进标识符，像 C++ 的 name mangling）。说白了就是把预处理器当单态化引擎、在 C 上搭一个最小 C++。哪个……yuck，但我不觉得你做不到。

还有几条评论点到更细的：

  • _Generic（C 的泛型）顶不上 Rust 泛型：C 的 _Generic 选不了「换函数参数/返回类型」，只能挑单态化后的函数。
  • const generics 的机制还没定：C++ 的「非类型模板参数」是完全开放式的，Rust 不接受——能写出 Foo<NaN> 这种不健全的东西（NaN != NaN），所以 Rust 这边还在讨论。

这些缺口意味着：简单 C 风格 Rust（无泛型/无 const generics 的模块）今天就能转，但用到泛型就卡。

它值不值得你记一笔#

看你在哪条线上：

  • 做高置信/合规/形式化验证：这是你真正的桥——Rust 写完，Eurydice 出 C，喂给 C 验证器。今天能用的范围是「无泛型的核心模块」。
  • 想让老 C 代码库吃 Rust 抽象：它是「让 C 编译器环境用上 Rust 能力」的跳板（LWN 原话：「只有 C 编译器、没有可用 Rust 编译器」的环境里）。
  • 普通应用开发者：没你什么事。你是 C→Rust（重写求快），它是 Rust→C（转译求合规），方向相反。

一句话收口：Eurydice 不是一个「更好的 rustc」，是 Rust 往 C 世界（老工具链、合规、形式化验证）渗透的一把钥匙。钥匙能开的门是「今天能写、无泛型的那部分 Rust」，泛型那扇门还在焊着。

诚实声明：本篇所有转译代码与缺口描述，均来自 LWN 原文与评论区（作者 Daroc Alden 1/30 的报道），我没有跑 Eurydice、没有拿自己的 Rust 代码转 C 验证。Eurydice 可执行性需要 OCaml 工具链（LWN 评论区「bootstrapping OCaml」那条），本机未验证。

常见问题

Eurydice 是什么？跟 mrustc、gccrs 有什么区别？

都是 Rust 的编译器实现。区别在目标：mrustc/GCC-rust/Cranelift 编译出机器码（.o），Eurydice 编译出 C 源码（.c）——它把 Rust 程序转成一个 C 程序员能读、能喂给老 C 工具链的中间形态。所以它不是「另一个 rustc」，是「Rust 到 C 的转译器」。

为什么要这么反着来？

高置信软件（车载/医疗/航天/形式化验证环境）的合规与验证工具几十年积累，只认 C。Rust 想进这些场景，要么等工具追上来，要么先把代码转成 C。Eurydice 走的是后者：已把一批后量子密码算法从 Rust 转成 C 落地。

转出来的 C 代码质量如何？

LWN 给的例子里，Rust 的 gcd/lcm 转成 C 后结构保留、甚至保住了求值顺序，但会冒出 `uu____0` 这类临时变量——可读性是「能看懂」而非「整洁」。作者自己也说「是不是 readable 看个人口味」。

Rust 的泛型在 C 里怎么落地？

这是当前最大缺口。LWN 评论区里 Jonathan Protzenko（最活跃贡献者）直言：要让 Rust 泛型安全地进 C，需要把预处理器当「单态化引擎」、在 C 上搭一个最小 C++——「yuck，但我不觉得你做不到」。还没解决。
