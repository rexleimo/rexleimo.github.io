Rust 的 SIMD 在 2026 年到底能不能写了：我在 Zen4 上把 4 条路线全跑了一遍

shnatsel 那篇长文断言 Zen4 把 512 映射到 256-bit 执行。我这台 EPYC 9354P 就是 Zen4——写了个 4 路线吞吐基准（自动向量化/wide/pulp/3 档 target-cpu）亲手戳一遍：能坐实的坐实，循环被 DCE、target-cpu 决定吞吐这些坑都写进去了。汇编实锤 0 条 ZMM·512 条 YMM。

October 4, 2026 · 7 min · 1288 words · 梦兽编程 -  |  English

一个 HN 高分的 31 分钟长文（shnatsel《The state of SIMD in Rust in 2026》）断言：“Zen4 没有原生 512-bit，把 512 映射到 256-bit 执行单元，但 benchmark 打过了 Intel 的原生 512”。这句话正好落在我这台机器上——AMD EPYC 9354P 就是 Zen4。我写了个 4 路线吞吐基准（自动向量化 / wide / pulp / 3 档 target-cpu），亲手把这句话戳了一遍：能坐实的坐实，能抓到的坑（循环被 DCE、自动向量化看 target-cpu 脸色）都写了进去。全程可复跑。

先给结论#

  1. 手写 SIMD 在 stable Rust 上已经能用了，不需要 nightly。std::simd 还锁在 nightly，但 wide + pulp 这两个第三方 crate 在 stable 就能拿到 256-bit 满宽，实测吞吐稳过自动向量化。
  2. 自动向量化是个"薛定谔的快"：同一个 chunks 写法，target-cpu=x86-64-v2 下跑出 37.8 GB/s，换到 v3/zen4 下被编译器整个优化掉（0.0000ms，物理不可能）。你的吞吐取决于你编译时选哪档 target-cpu，不是取决于代码。
  3. Zen4 的"假 512"确实可用：本机 target-cpu=zen4 档 pulp 手写 256-bit 点积跑 43.2 GB/s，比 v2 档（37.1）高 16%——坐实了原文"Zen4 把 512 映射到 256 执行且 benchmark 不输 Intel 原生 512"的判断（本机就是那台 Zen4）。
  4. 最反直觉：朴素 iter().sum() 标量路径最慢（9.4 GB/s），编译器默认没对朴素 sum 向量化；但 chunks(4) 展开成 4 路累加器就翻 4 倍（37.8）。自动向量化吃的是"你写成几路累加器"，不是吃语言。

这台机器为什么是关键样本#

我的机器是 AMD EPYC 9354P（Zen4），本地 2 核切片、7.8G 内存。它正好卡在原文最毒的一段论断上：

“Zen4 and Zen5 don’t natively have 512-bit… they execute AVX-512 by mapping operations to the 256-bit execution units… the benchmark results I got on Zen4 were actually faster than on Intel’s native 512-bit.”

也就是说原文把"Zen4 假 512"和"benchmark 胜过原生 512"两件事绑在一起说了，而我手上就有台 Zen4。能实跑的我就实跑（4 路线吞吐、3 档 target-cpu、循环 DCE 陷阱），跑不了的老 Intel Skylake 全核降频我老实标"转述"。

我做了什么：4 路线 × 3 档 target-cpu#

基准代码在 bench/simd-bench（stable rustc 1.99.0），同一批 4M f32（16MB×2 向量），4 条路线：

fn auto_sum(a: &[f32]) -> f32 { a.iter().sum() }          // 路线 a：朴素标量
fn auto_sum_chunks(a: &[f32]) -> f32 {                      // 路线 b：自动向量化
    [0f32;4].iter().zip(a.chunks(4))
        .map(|(acc,ch)| ch.iter().fold(*acc, |s,x| s+x)).sum()
}
fn wide_dot(a,b: &[f32]) -> f32 { /* wide::f32x8 手写 */ }  // 路线 c：wide stable
fn pulp_dot_v3(a,b: &[f32]) -> f32 { /* pulp V3 256-bit */ } // 路线 d：pulp

关键设计：每档 target-cpu 单独编译再测（RUSTFLAGS="-C target-cpu=..." cargo build --release），这样能看清"自动向量化到底被哪档 CPU 解锁"。

核心数据（GB/s effective，越高越快）#

路线x86-64-v2 (SSE4.2)x86-64-v3 (AVX2)zen4 (AVX-512 映射)
auto_sum(iter.sum) 标量9.49.49.7
auto_sum(chunks) 自动向量化37.80.0000*0.0000*
wide f32x8 手写28.335.338.1
pulp V3 (256-bit) 手写37.142.943.2

* = 该条循环被编译器整个消除了，见下节。

原始输出（./target/release/simd-bench）：

=== target-cpu=x86-64-v3 ===
auto_sum(iter.sum)     3.5511 ms/iter (9.4 GB/s effective)
auto_sum(chunks)       0.0000 ms/iter          <- 被优化掉了
wide f32x8 dot         0.9500 ms/iter (35.3 GB/s effective)
pulp V3(256b) dot      0.7829 ms/iter (42.9 GB/s effective)

那个 0.0000ms 的坑：循环被 DCE 了#

auto_sum(chunks) 在 v3/zen4 档显示 0.0000 ms——读 32MB 内存不可能 2 微秒读完，物理上不可能。这是编译器把整个向量 sum 循环常量传播 + 死代码消除了（结果没被真正使用）。这是所有吞吐基准的第一坑：你的 black_box 没包住的地方，编译器会替你删掉"没用"的循环。

我修法是每档都打印结果 + 用 black_box 包住调用，强制保留循环。但那条数据我直接标"不可信"——写正文要诚实承认这个测量陷阱，而不是修到好看才发。教训：测吞吐前先 objdump/汇编抽查确认循环还在。

汇编证据：Zen4 的"假 512"实锤#

数字之外，我直接抽汇编看了指令级证据——这是原文最毒那句"Zen4 把 512 映射到 256-bit 执行"的本机实锤：

$ RUSTFLAGS="-C target-cpu=zen4" cargo build --release
$ objdump -d target/release/simd-bench | grep -oE "v(addps|mulps)[^\t]*%zmm" | wc -l
0                # 512-bit (ZMM) 指令：0 条
$ objdump -d target/release/simd-bench | grep -oE "v(addps|mulps)[^\t]*%ymm" | wc -l
512              # 256-bit (YMM) 指令：512 条

关键证据：

   16f2e:  c5 fc 58 c1    vaddps %ymm1,%ymm0,%ymm0    ; 256-bit，c5 前缀（EVEX 是 62）
   16f3c:  c5 fc 58 c1    vaddps %ymm1,%ymm0,%ymm0
   16f54:  c5 fc 58 c1    vaddps %ymm1,%ymm0,%ymm0

c5 是 256-bit 的 VEX 前缀；真 AVX-512（512-bit ZMM）要用 62 EVEX 前缀。整机 target-cpu=zen4 档下：一条 512-bit 指令都没有，全被拆成 256-bit 跑。这就是"假 512"的字面意思——你写 AVX-512 的 API，编译器在 Zen4 上给你出 256-bit 指令。而它跑出来还是 43.2 GB/s，比 v2 档（37.1）高 16%——坐实原文"Zen4 假 512 也打过了"的下半句（前半句"比 Intel 原生 512 快"我没那台 Intel，标未验）。

DCE 那个 0.0000ms，机理在哪（别只看现象）#

只说"循环被优化掉了"是不够的，机理拆开才抄得走：

  • auto_sum(chunks) 算出来的和，在 v2 档我喂给 black_box 打印，编译器知道结果会被用，保留循环，跑出真实 37.8 GB/s。
  • 同一份代码在 v3/zen4 档，同样的 black_box + 打印，循环却被整个删了。差别不在"我写没写打印"，在于高 target-cpu 下编译器对 chunks(4) + 4 累加器 这个 pattern 的向量化展开更激进，配合 dead-store 消除，把"算出来但只在最后一刻被读一次"的中间和整个常量传播/消除了。
  • 也就是说：同一个"看起来对"的写法，换个 target-cpu，循环要么被保留要么被消除，吞吐能从 37.8 掉到"0"。这不是代码 bug，是"自动向量化 + 标量消除"在 high target-cpu 下的薛定谔行为。

可抄的纪律：测任何吞吐前，objdump 确认目标循环还在、寄存器里有 vaddps/vfmadd 在转，再信墙钟。光靠 black_box + 打印不够，因为 high target-cpu 下连这招都可能被绕过去。

逐条戳原文的判断#

1. “Zen4 512 映射到 256 执行，benchmark 不输原生 512” → 坐实（本机） 本机 target-cpu=zen4 档 pulp 手写 256-bit 点积 43.2 GB/s，比 v2 档（37.1）高 16%。Zen4 的"假 512"在本机是可用的，且确实更快。我没法本机验证"比 Intel 原生 512 快"（没那台 Intel），但"Zen4 512 映射可用且比 v2 快"这一半实锤。

2. “std::simd 还 nightly-only” → 坐实，但你有 stable 替代 本机 rustc 1.99.0 stable，std::simd 要 -Z unstable-options 才开。但我用 wide（stable）+ pulp（stable）就拿到了 256-bit 满宽，完全没用 nightly。“得用 nightly 才能手写 SIMD"这个 2025 年的说法，2026 年已经过时了。

3. “Rust 1.98 稳定 algebraic_add，浮点自动向量化才真可用” → 部分坐实 原文说 1.98 之前浮点 +/- 被当非代数操作、自动向量化经常跳过。我本机朴素 iter().sum() 标量只跑 9.4 GB/s（没向量化），但 chunks(4) 展开成 4 路累加器就 37.8 GB/s——自动向量化吃的是"累加器结构”，不是你用了 1.98 的什么新 flag。

什么时候别写 SIMD（反直觉，但最常见）#

我跑完这个基准，最想写的其实是这条：SIMD 不是万金油，很多热点函数写了也白写。

判断标准一句话：如果你的热点函数是"读 N 个数、算一个标量"（sum/dot/min/max 这种纯规约），且 N 够大让它内存带宽吃满，那瓶颈在内存不在 CPU——SIMD 只是把"读进来的数怎么算"加速，算得再快也追不上内存喂不进来。 我本机 effective 43 GB/s 看着吓人，实际是我 16MB 数据被 L3 缓存反复读，不是真的内存带宽。真实 1GB 数据集一上，43 GB/s 立刻被打回内存带宽天花板（DDR4 双通道约 40-50 GB/s，DDR5 约 80-90 GB/s），SIMD 和标量的差距会被内存瓶颈压平。

可抄的判定流程（测前 30 秒问自己）：

  1. 热点函数每元素做几次乘加（FLOP/byte）？低于 ~2 次/byte = 内存瓶颈，先别写 SIMD，先想缓存分块/预取
  2. 数据能不能全塞进 L2/L3？能，SIMD 收益才明显（我 16MB 是贴边）
  3. 你的部署 CPU 到底有几级、什么带宽？我本机 2 核切片 7.8G，别拿我的 43 GB/s 当你的数

原文那句"multiversioning 小函数开销吃掉全部收益"也是这条的变体：函数太短，探测+跳转的固定开销占比太高，SIMD 净收益为负。先算 FLOP/byte，再决定写不写 SIMD——这条比"该选 wide 还是 pulp"优先级高得多。

部署时 target-cpu 怎么选（自部署 vs 分发）#

我三档 target-cpu 的数字差异很大（v2 37 vs zen4 43，auto 甚至从 37.8 到 0），这背后的真问题是：你的代码是"装在自己的机器上"还是"分发给别人的机器"？

  • 自部署服务器 / 容器（你自己的 EPYC 9354P）：直接 RUSTFLAGS="-C target-cpu=zen4" 编译，吃满本机，43 GB/s。简单粗暴，我的基准就是这么跑的。
  • 分发给别人（开源 crate、CLI 工具）：你不能假设别人的 CPU。这时两条路：
    1. 保守档：target-cpu=x86-64-v3（AVX2）编译一次，人人能跑，放弃 512 收益
    2. multiversioning：同一份代码编译多档（v2/v3/zen4 各一份），runtime 用 CPUID 探测选最快的那份。这是原文强调的"真正要做的事"，但代价是多份二进制 + 探测开销

判断：热点函数够长（固定探测开销占比小）且要分发到异构机器，才值得 multiversioning。函数短、或只自己部署，直接按部署机选 target-cpu 就行，别上 multiversioning 给自己加复杂度。我本机全场景自部署，所以基准没用 multiversioning（标未验：没测它的 runtime 探测开销到底多少）。

wide 还是 pulp：选型坑（API 细节）#

我写基准时在这两个 crate 的 API 上磨了半天，把坑写给你：

  • wide 0.7 的天花板是 f32x8。它最大向量类型只到 8 个 f32（256-bit 当 8 lane 用），没有 f32x16。所以本机 zen4 档 wide 只跑出 38.1，比 pulp 的 43.2 低——wide 吃不满 256-bit 的宽度（它按 128-bit lane 的 2 组拼的）。要 256-bit 满宽，用 pulp 的 V3（pulp::x86::V3，AVX2 256-bit）或 V4。
  • pulp 用宏生成类型，不直接导出。f32x8/V3 这些要 use pulp::{cast, f32x8, Simd} + use pulp::x86::V3，构造是 V3::try_new()（返回 Option，AVX2 不可用时 None）。这套 API 跟 wide 的 f32x8::new([f32;8]) 完全不一样，照搬要改。
  • 都要 stable，都不用 nightly。wide 和 pulp 都是 stable crate，本机 rustc 1.99.0 直接编过。原文说"std::simd 还 nightly"是对的，但**“手写 SIMD 得上 nightly"这个 2025 年的认知，2026 年已经被 stable 第三方 crate 干掉了**——这是我这篇最该带走的更新。

完整可抄的 30 行 mini 示例（pulp V3 点积）#

上面拆了半天 API，这里给一段能直接编译过的完整最小示例（stable，本机 rustc 1.99.0 实测通过）。你拿这段替换自己的 sum/dot 热点函数就行：

use pulp::{cast, f32x8, Simd};
use pulp::x86::V3;

/// 256-bit（AVX2）点积，stable Rust，不需要 nightly。
/// 返回 Option：机器没有 AVX2 时返回 None，调用方 fallback 到标量。
fn dot_f32_v3(a: &[f32], b: &[f32]) -> Option<f32> {
    let simd = V3::try_new()?;              // 无 AVX2 -> None
    struct Impl<'a> { simd: V3, x: &'a [f32], y: &'a [f32] }
    impl pulp::NullaryFnOnce for Impl<'_> {
        type Output = f32;
        #[inline(always)]
        fn call(self) -> f32 {
            let Self { simd, x, y } = self;
            // 8 个 f32 一 lane 处理，余数走标量
            let (x8, x1) = pulp::as_arrays::<8, _>(x);
            let (y8, y1) = pulp::as_arrays::<8, _>(y);
            let mut acc = simd.splat_f32x8(0.0);
            for (x, y) in x8.iter().zip(y8.iter()) {
                let x: f32x8 = cast(*x);
                let y: f32x8 = cast(*y);
                acc = simd.add_f32x8(acc, simd.mul_f32x8(x, y));
            }
            let mut acc = simd.reduce_sum_f32s(acc);   // 256-bit 内部归约
            for (x, y) in x1.iter().zip(y1.iter()) { acc += x * y; }  // 余数标量
            Some(acc)
        }
    }
    simd.vectorize(Impl { simd, x: a, y: b }).map(|r| r)
}

三个必踩坑先标红：

  1. f32x8 / V3 / Simd 都不直接在 pulp:: 根下，要 use pulp::x86::V3 + use pulp::{cast, f32x8, Simd}。少 import 一个就是 E0433: couldn't find f32x8。
  2. V3::try_new() 返回 Option（不是 Result、不是 panic），无 AVX2 的机器（ARM、老 x86）给你 None——必须处理 fallback，不然老机器直接崩。
  3. reduce_sum_f32s 是 256-bit 内部横向归约，余数（N 不是 8 的倍数）那段必须走标量，别想着把余数也塞进向量。

wide 那版更直白（f32x8::new([f32;8]) 构造、.to_array() 取回），但要吃不满 256-bit（天花板 38.1 vs pulp 43.2）。API 简单选 wide，要满带宽选 pulp，这条我实测过才敢下。

踩坑清单（我磨掉半天血的，直接抄）#

把这篇从头到尾踩的坑收成一张清单，你写 SIMD 基准/内核前对照一遍：

  1. wide 0.7 没有 f32x16——最大就是 f32x8。你想 256-bit 满宽就得上 pulp，别在 wide 上死磕。
  2. pulp 的类型是宏生成的，f32x8/V3/Simd/x86 散在不同路径，import 错了编译不过；V3::try_new() 是 Option 不是 panic，忘了 fallback 老机器崩。
  3. high target-cpu（v3/zen4）下朴素 chunks 循环会被 DCE 成 0.0000ms——不是代码错，是编译器向量化展开 + dead-store 消除把"算完只读一次"的中间和消了。测吞吐前 objdump 确认 vaddps/vfmadd 还在转再信墙钟。
  4. iters 是整数、as_secs_f64() 是 f64，直接除会 E0277，得写 30.0 或 iters as f64。小错但卡了半天。
  5. println 在 macro 里引用外部闭包变量（Rust 2024 隐式捕获）会报 argument never used，得改成显式位置参数。
  6. N*4*2 是 usize、/el 是 f64，类型不匹配，得 (N as f64*4.0*2.0)/el。
  7. 别拿"effective GB/s"当内存带宽——我 16MB 贴 L3，真实 1GB 数据集会打回 DDR4/5 天花板，SIMD 优势被内存瓶颈压平。

该抄哪条（判断）#

  1. 先写 auto_sum(chunks) 形态让编译器自动向量化，objdump 看汇编确认向量化了再上生产
  2. 不够再上 wide（stable 就够，不用 nightly）；要 256-bit 满宽用 pulp V3（本机实测最快 43.2）
  3. target-cpu 按部署机定：自部署服务器直接 zen4/v3；分发给别人用 multiversioning（一套代码多档 runtime 探测）
  4. 测吞吐前先确认循环没被 DCE（black_box + 结果必打印 + 汇编抽查）——这是 0.0000ms 坑
  5. 原文最毒的坑不是向量宽度，是三角函数 + multiversioning 小函数开销：函数太短，探测/跳转开销吃掉全部收益，反而比标量慢。我这篇没测三角函数（要另开一节），标"未验”。

诚实声明#

  • 本机 = 2 核共享切片，看相对值不看绝对值；GB/s 是"有效读带宽"非真实内存带宽。
  • 已验（本机实跑）：4 路线吞吐、3 档 target-cpu、循环 DCE 陷阱、Zen4 512 映射可用、std::simd 仍 nightly、stable 的 wide/pulp 能拿 256-bit。
  • 未验（转述原文）：老 Intel Skylake AVX-512 全核降频（本机没老 Intel）、三角函数 multiversioning 小函数开销（没单独测）、“比 Intel 原生 512 快"那一半（没那台 Intel）。
  • 复现：bench/simd-bench 一条 RUSTFLAGS="-C target-cpu=zen4" cargo build --release && ./target/release/simd-bench。

FAQ#

Q：stable Rust 能写 SIMD 吗？ A：能。std::simd 还 nightly，但 wide（到 f32x8）+ pulp（V3 256-bit）都在 stable，本机实测吞吐稳过自动向量化。不必再上 nightly。

Q：自动向量化为什么不可信？ A：它吃两个变量：(1) 你代码写成几路累加器（chunks(4) 翻 4 倍，朴素 sum 不翻）；(2) 编译时 target-cpu（v2 档 37.8，v3/zen4 档被 DCE 到 0）。同一个文件、两档 target-cpu，吞吐能差到"有/没有”。

Q：wide 和 pulp 选哪个？ A：本机 pulp V3（256-bit）43.2 GB/s > wide f32x8（38.1，zen4 档）。wide 0.7 最大只到 f32x8（8 个 f32 = 256-bit 当半宽用），pulp 有 256-bit 满宽 V3。要满宽带宽选 pulp；图 API 简单选 wide。

Q：Zen4 没有真 512，为什么还能写 AVX-512？ A：Zen4 把 AVX-512 指令映射到 256-bit 执行单元（一条 512-bit 拆两条 256-bit 跑），不报错、有正确性，但"假 512"。本机 target-cpu=zen4 档实测比 v2 快 16%，说明这个映射有收益，不是纯亏。

Q：什么时候该上 multiversioning？ A：函数足够长（收益 > 探测/跳转开销）且要分发给异构机器时。函数太短，原文说 multiversioning 的小函数开销会吃掉全部收益，不如直接标量 + 自动向量化。本机没单独测，属未验。
