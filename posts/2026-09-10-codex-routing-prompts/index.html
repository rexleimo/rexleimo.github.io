Codex 高效路由提示词：按风险选模型，按收益派子代理

Codex 系模型档位多、reasoning 档位多，上手第一感觉是乱：同一任务用什么模型、派不派子代理、reasoning 开多大，每次拍脑袋。这篇给出一套可直接复制的 AGENTS.md 路由配置，附完整源文件，按风险选模型，按收益派子代理。

September 10, 2026 · 2 min · 251 words · 梦兽编程 -

Codex 系模型档位多、reasoning_effort 档位多，上手的第一感觉不是强，而是乱：同一个任务，用什么模型、要不要派子代理、reasoning 开多大，每次都要现场拍脑袋。拍错了就是双输——轻模型给误判，重模型烧 token。

这篇给出一套可以直接落地的 AGENTS.md 路由配置。它的全部逻辑可以压缩成两句话：按风险选模型，按收益派子代理。

一句话版本#

允许并行，但别为了并行而并行；按风险选模型，reasoning 不能代替更强的模型；子代理是探子，只做探索不拍板。

完整配置（直接复制）#

以下就是完整配置，放在你仓库根的 AGENTS.md 即可生效。也可以直接下载源文件：AGENTS.md 。

# AI 模型使用规范

允许使用 subagent / 多 agent / 并行 agent。

## 一、subagent 使用原则

只有当任务可以明确拆分，且并行收益大于调度成本时，才使用 subagent。

简单、短小、单点任务由主线程直接处理。

subagent 只处理边界清晰、输入明确、输出可验证的子任务。

最终判断、方案整合、高风险决策由主线程负责。

## 二、智能调度原则

优先按任务风险和代码规模选择模型，再按难度选择 reasoning_effort。

reasoning_effort 不能替代更强模型；复杂代码评审、跨模块判断、高风险修复不得使用轻量模型。

如果任务复杂度不确定，先用更保守的模型配置，避免低配 subagent 给出误判。

## 三、模型与 reasoning_effort 规则

- 超轻量任务使用轻量模型（如 gpt-5.6 luna），reasoning_effort=low 或 medium。例如文件定位、简单搜索、命令输出摘要、单点事实核对、列表整理。
- 简单只读任务使用轻量模型，reasoning_effort=medium 或 high。例如多文件搜索、日志归纳、测试失败摘要、只读 MCP 查询汇总。不用于代码评审结论，只能提供事实和证据。
- 小规模代码只读 / 局部审查使用轻量模型，reasoning_effort=medium。例如 1-2 个文件、边界清晰、无跨模块影响的代码阅读、局部风险检查。
- 中等规模代码任务使用中等模型（如 gpt-6-astra 或 gpt-5.6 sol），reasoning_effort=medium 或 high。例如模块级阅读、局部实现、bug 定位、测试修复、普通代码审查。
- 如果涉及业务状态机、并发、权限、支付、数据库写入、数据一致性，直接使用强模型（如 gpt-5.6 sol）。
- 复杂任务使用强模型，reasoning_effort=high。例如复杂审查、跨模块影响分析、高风险修复、架构判断、关键业务流程验证。
- 架构级决策、最终整合、关键验收使用最强模型（如 gpt-6-astra），必要时 reasoning_effort=xhigh。
- 如果用户显式指定模型或 reasoning_effort，则优先按用户指定执行。

## 四、代码评审规则

- 真正的代码评审不得使用轻量模型。
- 小范围、低风险代码评审最低使用轻量模型 medium。
- 中高风险、跨文件、跨模块、业务关键路径评审使用 gpt-6-astra high。
- 安全、支付、退款、数据库写入、并发锁、权限、生产部署相关评审使用 gpt-6-astra high 或 xhigh。

## 五、工具 / MCP 调用规则

- 单次、阻塞、会立即决定下一步的工具调用由主线程执行。
- 多个独立、只读、可并行的搜索、日志摘要、MCP 查询，可以交给轻量模型 subagent。
- 涉及写入文件、写数据库、删除 / 移动、提权命令、关键业务判断的工具调用，由主线程执行或最终确认。

## 六、上下文与 token 控制

- 使用 subagent 时默认不要 fork 全量上下文，优先 fork_context=false。
- 只给 subagent 精简、独立、边界清楚的任务说明。
- 只有子任务确实依赖完整历史上下文时，才使用 fork_context=true。
- 避免多个 subagent 重复分析同一问题。

# 子代理使用

子代理是你的探子。把子代理当成手边最顺手的、用于「宽而重」读取的工具。

必须遵守：需要更激进和更频繁地调用子代理，在任何需要的情况下，而不仅仅在对话开头。更频繁的子代理调用可以避免上下文腐烂，主线程承担子代理编排者的角色。

## 何时直接处理

直接读取以及处理以下内容，不派子代理：

- 已知位置的小文件、少量代码或单一事实；
- 即将修改的具体代码；
- 派发、等待以及复核的成本不低于自己读取的任务。
- 奠基性文档，无论多长都自己读：架构文档、设计文档、交接备忘录——它们的价值全在细节与脉络，一经子代理转译即失真，长度不构成外包的理由。

## 何时适合派发

- 巨型大文件（奠基性文档除外）、跨文件或跨目录的检索；
- 相互独立、可以并行的探索或核验；
- 长任务当中需要重新确认模块现状的；
- 会产生大量日志、搜索结果或外围材料的阅读。

多个独立的任务应当并发派发。

## 委派与验证

- 给子代理的任务必须自包含，说明检索范围、具体问题以及期望的输出。精度重要的时候，要求返回 file:line、符号名以及必要的关键原文——这些出处就是复核的抓手。
- 子代理的结果只是线索，可能遗漏或出错。复核 = 顺着它给的 file:line 以及关键原文来，抽查真的需要主代理亲自阅读的少数部分，不要重新通读整份材料。
- 唯二需要亲自完整读原文的是：即将修改的确切代码、奠基性文档。子代理至多帮忙定位，读由主代理亲自来。
- 子代理默认只做探索、检索以及核验。代码修改、方案取舍以及最终验证由主代理负责。

## 派发机制

- 是否派、派几个由主代理自主决定，无需用户明确要求；较重的探索应当拆分成多个独立的轻任务并发派发。
- 最多并行分派 6 个子代理；子代理模型成本较低，只要任务需要就积极使用。
- 子代理使用默认配置，显式指定 agent_role = "default"。派生时必须显式 fork_turns = "none"，不复制主代理的历史，让每个探子保持干净、快、不背主代理正在腐烂的上下文。
- 需要多个子代理时在同一轮并发派发；派发之后主代理立即 wait_agent，停止其余的分析、检索、命令执行以及文件修改，直至全部返回。
- 收到子代理结果之后立即关闭；每个子代理只用一轮，不复用、不追派。
- 子代理累计运行 10 分钟仍未完成：视为异常，主代理必须介入、不得继续盲等；检查代理状态或运行记录，已有可用结果时采用其部分结果，然后停止这个子代理，并自行判断是否需要再派生或拆分更小任务重新分派。

逐节解读#

1. 为什么要按「风险」而不是按「难度」选模型#

难度决定 reasoning_effort 开多大，风险决定用哪档模型——这是两个维度。

文件定位这种活儿，轻模型 low 就够；但代码评审哪怕范围很小，只要结论会被人拿去改代码，就不能配最低档：评审结论错误的代价远高于评审本身的 token 成本。配置里把「只给事实和证据」「不下评审结论」写死，就是防止轻模型用自信的语气给出廉价判断。

2. reasoning_effort 不能替代更强模型#

给小模型开 xhigh，只是让它想得更久，不是让它想到更多。长上下文里的跨模块推理、业务语义理解，有硬上限。所以配置里的顺序是：先按风险锁定模型档位，再按难度调 reasoning。

3. 为什么写入类操作必须收归主线程#

并行写入没有单一决策点，冲突和不可复现几乎必然。配置只允许子代理做「只读、探索、核验」——写文件、写库、删除移动、提权、关键业务判断全部留在主线程，或者至少由主线程最终确认。

4. 子代理的「买压缩」模型#

委派的价值是「压缩」：让子代理替你啃完宽而重的材料，回一份带出处的摘要。所以复核不是重新通读，而是顺着它给的 file:line 抽查关键几处。把读过的再读一遍，等于把压缩当场退光。

配套的三条纪律：任务必须自包含（因为默认 fork_turns=none，子代理不背你的历史）；同一轮并发派发后主代理停止其他动作等待返回；单轮用完即关，10 分钟未完成视为异常介入。

怎么落地#

  1. 先抄「模型与 reasoning 路由」和「代码评审规则」两节，收益最大。
  2. 子代理部分重点抄「自包含任务 + 出处复核」，能省最多 token。
  3. 模型命名和参数名（fork_context、fork_turns、agent_role）跟你用的 Agent 框架对齐，别硬抄。
  4. 把 AGENTS.md 放仓库根，让每次会话都自动加载。

常见问题

核心结论是什么？

按风险选模型、按收益派子代理：超轻量与只读探索用轻模型，评审结论与写入收归主线程或强模型；子代理只做边界清晰、可验证的探索，主线程负责判断、整合与最终验收。

完整配置在哪里？

文章收录了完整的 AGENTS.md 全文，可直接复制；源文件也可从文章内链接下载。微信端直接复制正文即可。

轻模型能做代码评审吗？

不能做评审结论，只能给事实与证据。小范围低风险阅读可以做，跨文件、业务关键路径、安全支付并发权限相关评审必须用更强的模型与更高的 reasoning_effort。

子代理并行度怎么控制？

最大并行 7 个会话进程（1 主 + 6 子），同一轮并发派发后主代理 wait，子代理一律单轮用完即关，10 分钟未完成视作异常介入。
