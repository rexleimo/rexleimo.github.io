Google 官方 Rust 风格指南发布：63 条规则，5 条 Chrome 专属——glob import 和 Rc/Arc 都进黑名单了

Google style guide 站点（C++/Java/Go 那套）第一次把 Rust 排进官方序列：63 条规则、16 大类，Chrome 专属 5 条——禁 glob import、避开 Rc/Arc、Chrome 里不用 async。我把最有争议的 8 条拆了，并对照了微软自己的规范。

October 22, 2026 · 2 min · 382 words · 梦兽编程 -  | 

Google 的 style guide 站点——就是 C++、Java、Go 那一排官方规范——把 Rust 排进来了。位置在 google.github.io/styleguide/rustguide.html，跟 C++ 指南并列，页面上写明适用范围：google3、Android、ChromeOS、Fuchsia、Chrome。

全文 63 条规则，分 16 大类，其中 5 条带 [chrome] 标注（Chrome 专属），1 条带 [Fuchsia] 标注。 10 月 21 日在 HN 上了 front page，354 分 204 评。

先说这份文件的四条设计原则#

指南开头交代了它自己怎么定规则，这四条比具体条款更值得看，因为它解释了后面所有「反直觉」条款为什么存在：

  1. 可读性和可维护性优先于好不好写——代码预期要活很久，写的时候多花点成本换长期可读，值得。
  2. 规则要为自动化让路——Google 常见全代码库级的大规模重构（LSC, Large-Scale Changes），规则要帮工具跑通，一致性是前提。这条直接推出了「small crates」「flat file layout」那种条款。
  3. 和 Rust 大生态保持一致的地方就别另起炉灶——能跟随官方风格就不加戏。
  4. 每条规则必须「pull its weight」——所有 Rust 开发者和 reviewer 都要记着它，没有实际收益的条款不进文档。

第 4 条是筛子：63 条里没多少是「个人审美」型规则，大多数能指到一个具体痛点。

最有争议的 8 条，逐条拆#

1. 不用 glob import#

use foo::* 禁止，只留 4 个例外：内联模块里 use super::*、enum 方法体里 use enum::*、非叶模块 re-export pub use submodule::*、C++ interop 合并 namespace。

社区里 epage 直接开火：「Type 名必须 unqualified 使用」这条会把 io::Error 逼成 IoError 这种冗余命名。Google 的回应逻辑（文档 Rationale）是：unqualified 让 LSC 工具改起来最顺。

2. 一条 use 只引一个模块#

use std::fs::File; 可以，use std::{fs, io}; 不行。同一个 module 的多个项允许：use std::collections::{BTreeMap, BTreeSet};。

3. 避开 Rc 和 Arc#

原文：「优先 unique ownership 和借用。例外：当替代的所有权结构写得不可接受地复杂时可以用，这个判断在 code review 里讨论。」

这是整份指南争议最大的一条。HN 上 slaymaker1907 原话：「任何活在校栈之外的共享引用都应该用 Arc/Rc，为了骗编译器干奇怪 lifetimes 的事纯属糟蹋。」Google 的立场是 Rust 本来就能不靠共享指针表达对象图，共享指针有运行时开销，而且「从其他语言来的工程师太容易一上来就 Arc」。

注意措辞：是「prefer … over」不是「prohibit」——它留了 review 通道，和下面几条硬性禁止不一样。

4. Chrome 里不用 async / .await [chrome]#

原文就一句：「Don’t use async / .await in Chromium.」配 Chrome 的 task/sequence 调度模型，裸 future 语义和它打架。

5. Chrome 里不通过 std 起线程 [chrome]#

「In Chromium, prefer to use sequences instead of threads.」——同 4，都是 Chrome 调度模型决定的专属条款。

6. 不调 panic::catch_unwind#

First-party Rust 代码禁止。唯一例外：纯防御纵深（绝不能被依赖）的入口点包裹，且只适用于 panic=unwind 环境——而文档顺手指出 Chrome、Android、Fuchsia 全要求 panic=abort，所以那三个平台上这条等于没有例外。

7. expect 优先于 unwrap#

「如果必须 panic，用 expect("原因") 而不是 unwrap()，把不变量为什么成立写进字符串。」

8. hex 字面量强制小写#

rustfmt 配置里写死 hex_literal_case = Lower：0xab123cdef 不是 0xAB123CDEF。理由：数字和字母混排时小写更可读（moooss 在 HN 顶了这条，说大写的 B 和 8、D 和 0 容易看花）。

还有两条被低估的#

getter/setter 命名全家桶：foo() 按值取、foo_mut() 取 &mut、take_foo() 取走并置空、set_foo() 赋值、with_foo(closure) 闭包访问器、replace_foo() 赋值并返回旧值。incrediblers 在 HN 说这是全指南他最不同意的条款——「Label.text("hi") 之后 .get_text() 多一个 get_ 前缀」。

实现一组 API 要成套：写了 len() 就写 is_empty()（引 Clippy 的 len_without_is_empty 为据）。

对照：微软也有一份#

写这篇时顺手把微软的 Pragmatic Rust Guidelines 外部链接 翻了一遍——微软那份是「通用 + 代码库专属」两层结构，通用层强调实用主义、明确说「这些规则不是教条」。两份摆一起看：

Google（本文）微软
结构单文档 63 条，[chrome]/[Fuchsia] 标注专属通用 + 团队专属分层
Rc/Arc明确 discouraging，留 review 例外不点名
线程模型5 条 Chrome 专属（禁 async、禁 std 线程）无平台专属线程条款
态度「规则要为 LSC 自动化让路」「实用主义优先，别教条」

两家都把规则喂给 LLM 的路径铺好了（微软文档直接讲怎么塞给 copilot），Google 这份没明说，但 HN 评论区已经自发这么干了——younglunaman 的高赞回复：「ctrl+c ctrl+v 进我下个 Rust 项目的 AGENTS.md」。Thanemate 说得更直：「现在人看风格指南就一个目的：喂给模型。」

怎么用这份东西（以及不用）#

要用的：

  • 团队仓库：摘 ownership + concurrency + API 设计三组进 AGENTS.md / CLAUDE.md / 团队规范，10 条以内落地率最高
  • 用 LLM 写 Rust 的：整篇丢进项目上下文文件，63 条全是可执行措辞（有 Rationale、有例外），比「写干净的 Rust」这种空指令好使
  • Chrome 外围项目：那 5 条 [chrome] 条款单独抠出来，不用背全文

不用照搬的：

  • 它是 Google 内部规范外放，不等于 Rust 官方风格——官方页第一条就是「不冲突时先遵守公开 Rust 风格规则」，冲突处以它为准，但「冲突」的认定权在 Google
  • [chrome] 条款依赖 Chrome 的 task/sequence 调度模型，挪到别的框架上照抄就错了
  • 小 crate 那条（理想一文件一 crate）是 LSC 工具链的产物，个人项目里它和「组织合理」经常打架，HN 上 monocasa 说它「有 2010 年代的味道」不算刻薄

常见问题

这份指南管到哪些代码库？

google3、Android、ChromeOS、Fuchsia、Chrome。Android/Chromium 和其他代码库是「协商后打算开始用」的状态，各库对执行严格程度有自己的裁量权。

和 Rust 官方风格指南什么关系？

官方页第一句就是「不冲突时先遵守公开 Rust 风格规则」，冲突处以本文档为准。它是 Google 内部规范外放，不是 Rust 社区官方规范，rust-style 没有收编它。

我要全背吗？

不用。16 大类 63 条里大部分是 rustfmt 管的格式规则。真正影响写法的集中在 ownership、concurrency、API 设计三组。团队实际落地通常摘 10 条进 AGENTS.md/CLAUDE.md 就够。
