插件能不能「无痕卸载」？北大 × DeepSeek 的 92 页论文，把即插即拔变成了数学

arXiv 2608.25512：北大与 DeepSeek-AI 提出「时空可组合性」编程范式——可逆效应让插件卸载即无痕，响应式余效应让依赖断供自动下线，统一为 context paradigm 并实现为 Cordis。Koishi 生态 4000+ 插件生产验证，AI Agent 自进化 harness 是下一个目标。本文为付费文章，前半部分免费试读。

September 9, 2026 · 1 min · 156 words · 梦兽编程 -

如果你写过 VSCode 插件，或者折腾过 QQ 机器人、Discord Bot 的插件，大概率撞过同一堵墙：插件装上去容易，卸干净很难。

定时器还挂着、事件监听还注册着、数据库连接还开着——disable 掉的插件在内存里阴魂不散。VSCode 的官方解法简单粗暴：所有扩展跑在一个共享的 extension host 进程里，想卸载一个带代码的扩展？重启整个宿主，大家一起重来。

2026 年 8 月 26 日，北京大学和 DeepSeek-AI 的三位作者（Yifan Shi、Wei Zhang、Tianyi Cui）把这个问题写成了一篇 92 页的论文：A Programming Paradigm for Spatiotemporal Composability 外部链接 （arXiv:2608.25512）。我花了一个周末把它读完，这是我今年读过的「理论最重、但离工程最近」的一篇论文——它给「插件系统能不能做到即插即拔、卸载无痕」这件事补上了缺失的数学基础。

两个数字，两个维度#

论文用 VSCode 开了一刀，给了两个统计（2026 年 6 月 9 日从插件市场抓取）：

  • 安装量 top 100 的扩展里，87 个包含可执行代码——它们卸载时都需要重启宿主。VSCode 其实提供了 deactivate 钩子，但它只是宿主进程退出时的优雅关闭回调，没法做到「运行中单个摘除」；而且它把「副作用的创建」（activate）和「副作用的清理」（deactivate）拆在两处，写全清理逻辑全靠作者自觉。
  • top 100 里只有 7 个声明了对非内置扩展的依赖（extensionDependencies）。不是插件之间没有依赖，而是这套 API 只提供命令、视图这类固定的扩展点，扩展之间的交互拿到的还是个无类型的 any——没有结构化的契约，自然没人敢声明依赖。

这两个数字对应论文定义的两个正交维度：

  1. 时间可组合性（temporal composability）：卸载一个组件时，它对共享环境做过的所有修改——资源分配、事件注册、状态变更——必须被完整、安全地撤销；
  2. 空间可组合性（spatial composability）：组件能以结构化、可验证的方式声明彼此的依赖，系统响应式地解析、供给、收回这些依赖，并据此协调组件的上下线。

现在的业界方案：重启大法#

有人会说：这不早就解决了吗？进程崩了重启，依赖交给 Kubernetes。

论文把这叫粗粒度替代方案：操作系统以「进程」为单位提供时间可组合性，容器编排器以「服务」为单位提供空间可组合性。能跑，但代价不小：

  • 每次重启丢掉进程内的全部积累状态（缓存、连接池、算到一半的任务），重建要几秒到几分钟；为了保可用性还得养冗余副本；
  • 容器级编排表达不了同一地址空间里组件之间的依赖，本来一次本地函数调用的事，被拆成了网络调用。

粒度错配才是根因：现代软件在组件粒度上组合，而恢复和依赖管理却发生在进程/容器粒度。论文要做的，就是把这两件事拉回组件本身所在的层级。

核心思路：把编译期的理论搬到运行时#

程序语言理论里早就有一对概念：**效应系统（effect system）**描述「一段计算会对环境做什么修改」，**余效应系统（coeffect system）**描述「一段计算要求环境提供什么」。但它们一直是编译期静态分析的工具，作用域被词法框死——而插件是部署之后才加载的，没有任何词法作用域能框住它。

论文的做法是把这对概念实体化为运行时机制：

  • 可逆效应（revertible effects）：每一个副作用函数在修改上下文的同时，必须交出一个「逆操作」，由运行时统一保管。卸载组件时，运行时把这串逆操作按后进先出的顺序倒着执行——上下文就恢复原状了。插件作者从此不用写卸载逻辑，写加载时顺手 yield 出逆操作即可。
  • 响应式余效应（reactive coeffects）：组件声明自己需要什么（inject 清单），上下文的每一次变化都被对照这份清单分类为「激活、停用、无关」三选一——依赖齐了自动激活，依赖没了自动停机，无关变化视而不见。

两者统一在一个递归的「上下文」类型上，所有效应和余效应都经由它中转——论文称之为 context paradigm（上下文范式）。在这个范式下，不同组件的效应可以任意交错而不互相干扰，这是有定理保证的，不是口头承诺。

Cordis 与 Koishi：理论的生产级验证#

作者把这些想法实现成了 Cordis——一个「时空可组合性元框架」，提供 effect 跟踪、coeffect 解析、声明式组件加载器、配置调和和热模块替换（HMR）。

它最好的名片是 Koishi：一个构建在 Cordis 之上的开源聊天机器人框架，四年积累 4000+ 社区插件。在 Koishi 上，从控制台禁用一个插件，它的副作用会被原地回收；开发时改一行代码，HMR 引擎在保存时原地重放这个插件，其他插件的缓存和活动连接原封不动。互相独立的作者、只靠一个依赖键协调的插件，拼出一个还能保持一致的开放生态——这正是这套理论想证明的东西。

对 AI 从业者来说还有一层：论文的动机之一就是自进化的 agent harness——AI Agent 不停给自己生成和替换工具、组件、配置，每次修改都是一次动态组合，而每次修改都重启进程显然不现实。作者在结论里点名，把 Cordis 用到自进化 harness 上是最值得做的未来验证。

真正精彩的部分在后面#

不过，如果这篇论文只有「副作用配个逆操作、依赖声明个清单」，它顶多算个设计得比较好的 DI 框架。真正让我反复精读的，是它如何回答三个更难的问题：

  1. 「恢复原状」到底指什么？ malloc 出来的内存 free 掉了，但堆布局回不去了；一个生成的句柄名作废了，下次创建会拿到新的。物理状态根本无法字节级还原——那「无痕」的数学定义是什么？
  2. 卸载顺序被别人打乱怎么办？ 你的逆操作执行时，中间可能夹着别的组件的副作用——凭什么还能撤干净？什么样的两个组件才敢说「互相独立」？
  3. 谁先下线？ 依赖方还在读取提供方给出的服务时，提供方凭什么不能先撤？这套机制会不会死锁？

论文对这三问的回答——观测等价、交换性见证、guard 与进展性定理——才是整篇 92 页里最值得精读的部分，也是它区别于所有「又一个插件框架」的地方。付费部分我会把这三问的答案、九条规则的演算、Cordis 的关键算法（包括那套不需要手工标注 accept 边界的 HMR）和 Koishi 案例全部拆完，最后给一条 92 页论文的阅读路线。

常见问题

什么是时空可组合性（Spatiotemporal Composability）？

论文把「运行时动态装卸组件」拆成两个正交维度：时间可组合性指卸载组件时，它对共享环境做过的修改（注册、连接、状态变更）能被完整撤销；空间可组合性指组件能声明依赖、由系统响应式地解析和供给。论文分别用「可逆效应」和「响应式余效应」把这两个维度做成了运行时机制。

VSCode 插件卸载为什么 often 要重启？

VSCode 把所有扩展跑在一个共享的 extension host 进程里，扩展的 activate 函数执行后，没有机制单独卸载它的代码，禁用或卸载带代码的扩展就得重启整个宿主。论文统计（2026-06-09 抓取）：安装量 top 100 的扩展里 87 个含可执行代码，都逃不开这个问题。

Cordis 是什么？和 Koishi 什么关系？

Cordis 是论文作者实现的「时空可组合性元框架」，提供 effect 跟踪、coeffect 解析、声明式组件加载器、配置调和与热模块替换。Koishi 是构建在 Cordis 之上的开源聊天机器人框架，四年积累 4000+ 社区插件，是这套理论的生产级验证。

这篇论文和 AI Agent 有什么关系？

论文的动机之一就是自进化 agent harness：AI Agent 不停给自己生成和替换工具、组件、配置，每次修改都是一次动态组合。没有时间可组合性，每次自改都要重启进程丢掉全部运行时状态；没有空间可组合性，被替换模块的依赖方只能各自 ad hoc 适配。作者在结论里把「用 Cordis 验证自进化 agent harness」列为未来方向。
