WordCraft：clean-room 重做 Word 的纯 Rust 引擎，我本地实测 615 命令、97% 特性覆盖

WordCraft 用纯 Rust clean-room 重写 Microsoft Word，10-07 建仓，5 天 8,961 星。真正值钱的不是「又一个 Word」，而是它把整个 Word 拆成 615 个可命令化动作，同一套命令驱动 ribbon/CLI/MCP/agent。我本机 2 核 EPYC 编译跑通 4 条格式转换，实测数字与官方口径的差异都写清楚。

October 12, 2026 · 3 min · 511 words · 梦兽编程 -  | 

10 月 7 号建的一个仓，5 天攒到 8,961 星、2,384 fork，社区 10-12 冲到 98 分 97 评论的热度。项目叫 WordCraft（storytold/wordcraft），一句话是用纯 Rust 把 Microsoft Word 从头 clean-room 重写一遍：读 .docx（OOXML）、跑在 macOS/Windows/Linux/BSD 和 WASM 浏览器里，不碰 Electron 不碰 Tauri，原生 egui 上 GPU。

先说结论：它最值钱的不是「又一个 Word 替代品」，而是底层架构把整个 Word 拆成了 615 个可命令化动作，同一套命令同时驱动 ribbon、键盘快捷键、命令搜索、CLI、JSON 控制通道和 MCP server。文档应用顺手就能被 AI agent 当成一个可编程对象来驱动，这是它跟"照抄 Word 界面的开源项目"根本不一样的地方。

我 10-12 在本机 2 核 EPYC 上把它 compile 到 release、把 CLI 四条格式转换全跑通，实测数字、跟官方 README/ROADMAP 口径对不上的地方，下面都摊开写。

为什么 Rust 干这活最对#

先把 clean-room 这个前提讲清楚，因为它决定了这个项目能不能合法存在。

WordCraft 不是扒 Word 的壳。它的代码、图标、字体、模板全部原创或开放许可，文档格式只从公开规范来：OOXML 走 ECMA-376 / ISO 29500，RTF 走公开规范，ODF 走 OASIS 1.3，明确不碰 GPL/LGPL/AGPL 代码（LibreOffice、AbiWord、pandoc 那套都不抄）。官方还有一条铁律：仓库里任何一处都不许出现微软的资产，字体用系统已装的或 metric 兼容的开源替代，连图标都是 crates/ui-egui/src/icons.rs 里代码画出来的。

而 Rust 恰好是干这种"大体积文档应用 + 严格内存安全"最合适的语言。Word 这类应用最吃内存安全和布局稳定性——一个排版引擎崩了就是丢用户一整天的稿子。WordCraft 的 AGENTS.md 直接写死：生产代码 unsafe_code = "forbid"，零 unsafe；禁 unwrap/expect/panic!，所有错误走 Result<T,E>，连"用错参数绝不崩"都有回归测试兜着（hostile_params_never_panic 拿垃圾参数把每条命令跑一遍）。这种"把不变量交给编译器、运行时绝不崩"的工程纪律，跟 Rust 的所有权模型是天然咬合的。

底层拆成 17 个 crate，按 L0–L6 分层，层间依赖方向由 cargo xtask layers 强制：

层crate干什么
L0geom单位、矩形、测量解析
L1doc / fonts文档模型 + 编辑原语；字体库、shaping、Word 字体替代
L2layout / docx / formats断行、分页、表格、页眉页脚、命中测试；OOXML I/O；TXT/MD/HTML/RTF/ODT
L3render / pdf / proofvello_cpu 光栅化器；krilla 出 PDF；拼写校对
L4engineSession、undo、命令注册表、Word 特性目录、样例、I/O 分发
L5mcpMCP server（headless 或桥接运行中的 app）
L6ui-eguiWord 风格 egui 前端（可替换）

真正值钱：一切皆命令，agent 直接可驱动#

这是整篇我最想讲的点。WordCraft 的设计哲学是**“Everything is a command”**：每一个用户可见的行为，都是一条 CommandSpec（id、label、ribbon 位置、快捷键、参数文档、enabled、run），UI、快捷键、命令搜索、CLI、控制通道、MCP 全部按同一个 command id 分发。程序化调用永远不会弹对话框。

它甚至自己造了 4 类东西来证明这套基建是认真做给 agent 用的：

  • MCP server（crates/mcp）：wordcraft-cli mcp 可 headless 跑，也 --connect 127.0.0.1:7981 桥接运行中的 app；工具含 list_commands / execute / batch / type_text / inspect_document / render_page / save_document，agent 能靠 inspect_document 直接校验结果，不用截图。
  • JSON 控制通道：wordcraft --control 7981 起服务，发 JSON 行驱动，每个动作带 window key，防别的会话误操作。
  • CLI：wordcraft-cli convert in.docx out.pdf、wordcraft-cli run --template sample --cmd 'select.text={"text":"Studio"}' --cmd format.bold --save out.docx。
  • 特性目录 + parity 计量：catalog.rs 列出 Word 的 ribbon/menu 特性映射到 command id，cargo xtask parity 生成 checklist，一个测试强制覆盖率下限只升不降。

换句话说，你不用"看着它的 GUI"，可以直接把 WordCraft 当一个人格化的文档对象：告诉它"打开这个 docx，把第 3 节加粗，导出 PDF"，它按命令 id 一条条走。

我本地实测：数字全在这#

我在 2 核 EPYC（rustc 1.99.0）上 cargo build --release -p wordcraft-cli，首编 6 分 17 秒（整个 17-crate workspace + release 优化，正常）。然后跑 wordcraft-cli 子命令，逐条核验官方数字。

官方口径 vs 我复跑：

指标官方口径我本机复跑说明
命令数README 422 / ROADMAP 433615我跑的比官方多——5 天里 agent 还在往命令表加，这个数字是活的
catalog 特性覆盖487 / 502（97.0%）487 / 97.0%完全对上，wordcraft-cli parity 返回 live=487, percent=97.0
代码量~88,700 行 Rust全仓 .rs 190,094 行口径不同：官方"code"剔除测试/生成物，find 全量含测试
测试855 tests + 10 property1,659 个 test/proptest 标记我 grep 标记数，官方数测试函数，方法不同

四条格式转换，本机关机离线跑通（7,689 字符 / 40 节 + 40 表格基准文档）：

转换耗时产物
md → docx13.4 ms10.8 KB
docx → pdf221.8 ms147.6 KB（真实可选文本 PDF，非扫描件）
docx → odt21.9 ms7.4 KB
docx → html21.3 ms56.9 KB

四条 rc=0，全程离线、无 Electron、无浏览器、无网络。一条 docx 到带真文本层的 PDF 在 2 核上 220ms 出头，这个数字坐实了 README 说的"段落布局缓存、按需渲染"不是空话——重活（排版 + 光栅化）被 layout 缓存摊薄了。

诚实边界：什么我没跑、什么还没到#

按发文规矩把没验的部分说死，别让别人当成我背书过：

  • 188 页文档 1.4ms 重排我没复跑。那是 README/architecture 的声称（docs/architecture.md:45 “an edit relayouts only what changed (1.4 ms on a 188-page…)"），我只测了文件转换这条离线链路，没起 GUI 做 188 页交互排版。这条数字算官方口径，不算我实测。
  • 特性"覆盖 97%” ≠ “全功能齐了”。97% 是 catalog 条目有对应命令，但 ROADMAP 自己的 readiness 表写得很直白：feature 深度 68%、UI/UX 保真 65%、文件格式 60%、布局分页保真 55%、本地化 27%。而且官方明确"为什么还不是 beta：DOCX 从没在真实文件上测过，charts/SmartArt 还没到"。
  • 命令数 615 vs 433 的跳变，本身是"agent 在高速滚"的证据，但也说明项目还在早期，数字别当稳定值引用。
  • **Star 数（8,961）与建仓天数（10-07 建）**是我 10-12 拉的快照，热度和热度期强相关，别当长期指标。

为什么这个方向值得盯着#

它不是"再做个 Word 让你少交微软钱"。真正有意思的是：它把"文档应用"重构成了"agent 可编程对象"。615 个 command、MCP、JSON 控制通道、parity 自动计量，这一整套是照着"AI agent 也是使用者之一"设计的。文档处理恰好是个高频、结构化、可校验的领域，agent 驱动的空间大。

Rust 在这活里赢的点也清楚：内存安全扛住大文档排版、所有权模型配合"一切皆命令"的注册表、零 unsafe + never-crash 纪律保证不丢用户稿子、17-crate 严格分层让 layout/render/engine 各管一段还能并行。它把"用 Rust 写个大型 GUI 文档引擎"这件事的可行性，直接跑到了 8,961 星放在那儿。

下一步值得看的：feature 深度从 68% 往哪走、DOCX 真实文件测试什么时候补上、MCP 这套 agent 基建会不会单独抽出来给别的文档工具用。
