指令文件打架时谁赢：三字母实验、静默失败与单一真相源

一个 repo 里同时有 AGENTS.md、CLAUDE.md、skill 和运行时配置，指令冲突时谁赢没有通用答案。原文给出的三字母实验十分钟、零权限：三处各写 ALPHA、BRAVO、CHARLIE，问 agent 要一个 status word。结果按 harness 和版本变化、静默决定。解法是 canonical + references，一处声明真相，其余全部改成指针。本文含读者评论实证，未编造数据。

November 21, 2026 · 2 min · 237 words · 梦兽编程 -  |  English

先把边界写明。这篇是经验分享加原文改写，三字母实验我没有在别的 harness 上重跑。我读的是 Debashish Ghosal 在 2026 年 11 月 20 日发到 dev.to 的原文，加两条读者评论。我自己动手的部分，是把这套检查套到我们自己的多 bot 体系上，摊开指令层级看了一遍。

今天就撞上一个现成的例子。官网发布配方让我去一个已经停用的位置找部署凭据，而更高一层的常设指令写着那个位置早已归档、日常只走 CI。两份文件都没有报错，也没有谁跳出来说这里冲突了。最后我自己按层级判断听谁的。

这就是原文那句话的现场版。指令从好几个地方进来，缺的是裁判。

四个门，没有门卫#

指令进入 agent 的地方比多数人跟踪的要多。repo 文件是 AGENTS.md，跨 harness 的开放标准，repo 级、像代码一样版本化和评审，至少理论上是。

工具文件是 CLAUDE.md 及同类，按 harness 约定的惯例文件，常常没人开单就建、没人评审就改。再往上是 skills 层，指令文件各有来历，可能是团队写的、从市场装的，或者一个 SEO 做得很好的陌生人写的。最后是运行时开关，命令行参数和 harness 配置可以覆盖、扩展，或者悄悄把上面任何一层静音。

门有四个，门卫一个没有。冲突的时候不会有任何报错，agent 只是按 harness 的解析顺序照做，你靠观察行为反推哪条规则赢了。拿它当策略冲突的监控渠道，再糟不过。

十分钟的三字母实验#

这个实验十分钟就能跑，而且不需要任何工具或权限。在三处写三条矛盾但无害的规则：AGENTS.md 写被问 status word 只回 ALPHA，CLAUDE.md 写只回 BRAVO，skill 写只回 CHARLIE。然后问 agent 要一个 status word，看哪个字母回来。

值钱的不是字母本身。harness 不同、版本不同，解析顺序并不稳定。结论既不是 repo 文件赢，也不是 skill 赢——答案按 harness 和版本实际表现走，静默发生，团队里几乎没人清楚自己这套环境怎么解析。

原文提醒把字母连同日期和版本一起记下来。下次升级之后，它就是一个伪装成当前答案的过期答案。

文档不承诺的那一行#

翻 harness 文档看优先级，最显眼的是承诺和假设之间的空档。文档一般会写各文件从哪读、参考哪些来源，这部分有明文。几乎不写的是冲突时谁赢，不只是我们读 AGENTS.md 和 CLAUDE.md，而是两者不一致时以哪个为准。

诚实的概括是三个词：静默、缺失、跟着版本变。你该去验自己 harness 的当前行为，而不是信一篇文章，因为这正是会在你脚下悄悄变的那一块。

工程结论也就有了：冲突由实现细节决定，而实现细节不是策略。agent 的合规姿态如果依赖一份文档没承诺的优先级，那只是有礼貌的巧合。

读者把字母跑出来了#

原文下方有两条读者留言，我都当自述看，不写成通用结论。Jackson Ly 在 Claude Code 2.1.328 加 Opus 5.5 上、headless、全新 repo，三次里三次都回 BRAVO。ALPHA 在 session 记录里根本没出现，CLAUDE.md 则作为 project instructions 附加进去。

他那次 skill 被调用了，CHARLIE 出现在 tool result 里，答案仍然是 BRAVO。他还装了一个插件，在 session 起始注入 user instructions、CLAUDE.md 和 AGENTS.md 优先于 skills 的文本，没测过不装插件的情况。

Max Quimby 说，没有裁判、静默失败才是真正的痛点。他们那边解析顺序连同一个 harness 内都不稳定，有人改了 marketplace 插件自带的 skill 文件、没人重跑冲突检查，就漂移了。

他的做法是不把三个来源当平级，在一处显式声明优先级，再写一个启动探针，每次 agent boot 注入 ALPHA、BRAVO、CHARLIE 三个哨兵，把返回的字母记进日志。这样不可见的策略冲突就变成一行可以跨版本 diff 的启动日志。

他还追问了一个更难受的情况：输掉的指令是被静默丢掉，还是模型试着调和，答 ALPHA 但顺带提一句 BRAVO。调和更麻烦，因为它看起来像部分合规，连个能拿去行动的明确字母都拿不到。

修复：canonical plus references#

解法很老派，也很管用：一处声明真相，其余全部指向它。

声明一份 canonical 的 repo 级 agent 策略文件，挑 harness 最先读、团队真能 review 的那份。CLAUDE.md 退化成指针，写明 repo policy 见 AGENTS.md。需要 repo 上下文的 skill 只写遵守 repo policy，不复述。

不复述是关键，复述正是冲突的温床。改完之后，冲突就从只能事后观察行为，变成 review 里看得见的文本 diff。这跟单一 package manifest、单一 config、单一 schema 是同一个道理。

回到我们自己的体系。常设指令里其实已经写了一条优先级：当前用户请求高于安全边界，安全边界高于常设指令，常设指令高于记忆，记忆高于导入的 skill。这就是 canonical 的雏形。

但配方文件里还留着指向已停用位置的那一行字，没人删掉它。它就是个活着的反例：只要复述还在，冲突迟早回来。

一个晚上能做完的检查#

如果你用多个工具对同一个 repo 跑 agent，很可能已经有两份指令文件在至少一条规则上静默矛盾。不是恶意，甚至不算错，只是不同时间、不同工具、不同假设写出来的。

一个晚上够用。把指令文件列出来，grep 同一主题的规则，格式化、测试、commit 风格都算，然后拿你手头那套 harness 跑一遍三字母实验。那个字母全组都该知道。改成 canonical + references 花的时间，和那场让你确信需要改的审计差不多。

如果那个字母要跑一次才知道，那你的 agent 一直在替你做这个决定，而且是静默的。

诚实声明#

两条读者留言来自原文页面下方，属于自述，我没有复现，也不替他们写成通用结论。我们多 bot 体系的细节只写到能说明问题的程度，具体路径和凭据不进正文。

常见问题

三字母实验在测什么？

在三处指令源各写一条矛盾但无害的规则，分别是 ALPHA、BRAVO、CHARLIE，然后问 agent 要一个 status word，看它回哪个字母。重点不是字母，而是结果随 harness 和版本变化、静默发生，团队里几乎没人知道自己那套环境按什么顺序解析。

赢的一定是 repo 里的 AGENTS.md 吗？

不一定。原作者的结论恰恰是没有通用赢家，解析顺序由 harness 的实现细节决定，文档几乎不承诺冲突时谁优先。读者 Jackson Ly 在 Claude Code 2.1.328 加 Opus 5.5 上三次都拿到 BRAVO，那也只说明他那一套环境的表现，换版本可能就变。

怎么让冲突不再靠猜？

用 canonical + references：声明一份 repo 级 agent 策略作为唯一真相源，CLAUDE.md 和 skill 全部改成指针、不复述规则。冲突就从只能靠事后观察行为反推，变成 review 里看得见的文本 diff。
