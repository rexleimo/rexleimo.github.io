Rust 没有 GC，并发却照样能炸：100 个线程抢一个计数器，实测丢 51%~81% 的更新

「没有 GC 所以并发安全」是个误解。Rust 把数据竞争推到编译期，死锁和逻辑错留在运行时。本文 100 线程×10 万次抢一个计数器，实测 5 轮丢 51%~81%；-O 优化后 0 丢失——UB 之下结果对不对是运气。配双锁死锁、Rc/Arc 三姿态全部可复现示例。

October 10, 2026 · 3 min · 562 words · 梦兽编程 -  |  English

「没有 GC」常被当成并发安全的替罪羊，真正的敌人是数据竞争#

GC 管的是对象什么时候释放，并发程序最先坏掉的是多线程同时读写同一块内存时读到什么——数据竞争。Rust 的答法很明确：不靠 GC，把数据竞争推到编译期（Send/Sync 检查，不通过就编不过），把死锁和逻辑错留给运行时。

这篇文章的全部示例都在同一台机器上跑过：AMD EPYC 9354P（2 vCPU）、7GB 内存、rustc 1.99.0。每个示例给可复现命令，正文数字全部来自真实输出。三层防线，三个示例：

  • 编译期挡住的：Rc 跨线程（示例 3a，E0277 报错原文进文）
  • 运行时才炸的：双锁死锁（示例 1，2 秒超时判死锁）、RefCell 二次可变借用 panic（示例 3b-A）
  • UB 之下挡不住的：UnsafeCell + 裸指针造一个未同步共享计数器（示例 2，主菜）

示例 1：双锁顺序死锁——2 秒超时判实锤#

经典形态：线程 A 先拿锁 a 再拿锁 b，线程 B（这里用主线程）先拿锁 b 再拿锁 a。两边各持一把等另一把，永久阻塞。

判定手段：worker 完成后往 mpsc 发信号，主线程 recv_timeout(2s)——收不到即死锁成立。

let a = Arc::new(Mutex::new(1_u64));
let b = Arc::new(Mutex::new(2_u64));
let (tx, rx) = mpsc::channel();

let (a2, b2) = (a.clone(), b.clone());
let worker = thread::spawn(move || {
    let _x = a2.lock().unwrap();            // 先拿 a
    thread::sleep(Duration::from_millis(50));
    let _y = b2.lock().unwrap();            // 再拿 b —— 永远等不到
    let _ = tx.send("worker finished");
});

let _y = b.lock().unwrap();                 // 主线程：先拿 b
thread::sleep(Duration::from_millis(50));

match rx.recv_timeout(Duration::from_secs(2)) {
    Ok(msg)  => println!("没死锁：{msg}"),
    Err(RecvTimeoutError::Timeout) => println!("死锁实锤"),
    _        => {}
}

本机输出（rustc --edition 2021 -O deadlock.rs -o deadlock && ./deadlock）：

main: 已持有 b，worker 已持有 a，互为等待条件成立
死锁实锤：2 秒内 worker 没完成，它正阻塞在 b.lock() 上（main 持有 b，worker 持有 a）

死锁在 Rust 里编译期查不出来——Mutex 本身是安全的，锁序错了只是逻辑错。修法的两条路：所有线程约定同一把锁序（全局 a→b），或把两个资源锁进一把锁。

示例 2：100 线程抢一个计数器——先要签两份 unsafe，再谈丢失多少#

这是主菜，也是全文最重要的一节。目标：复现 Java/C++ 里「没加锁直接改共享计数器」的经典错法。在 Rust 里做出这件事本身就不容易，绕不过的编译期关卡有两道：

第一道：UnsafeCell 不是 Sync。 跨线程共享可变格子，Rust 的合法通道只有 Mutex 和原子类型。把 UnsafeCell 包进 Arc 直接编译拒绝，原始报错：

error[E0277]: `UnsafeCell<i64>` cannot be shared between threads safely
  --> src/race.rs:22:44
   |
22 |                   handles.push(thread::spawn(move || {
   |                              |
   = help: the trait `Sync` is not implemented for `UnsafeCell<i64>`

第二道：裸指针不是 Send。 走 unsafe 路线时，闭包要带 *mut i64 跨线程，必须手写 unsafe impl Send 的 newtype 包一层（还要实现 Copy，循环里反复捕获）。签完这两份「免责文件」才能开跑：

#[repr(transparent)]
struct Shared(*mut i64);
unsafe impl Send for Shared {}
impl Copy for Shared {}
impl Clone for Shared {
    fn clone(&self) -> Self { *self }
}

跑法：栈上一个 UnsafeCell<i64>，100 个线程各 10 万次 load-modify-store，全程零同步。期望 10,000,000。对照组：同负载的 Arc<AtomicI64>。

本机输出（rustc --edition 2021 race.rs -o race && time ./race，-O0 默认优化档）：

== 未同步共享 i64（5 轮采样）：期望 10000000 ==
  第1轮: 2831309   丢失 7168691（71.69%）
  第2轮: 1865145   丢失 8134855（81.35%）
  第3轮: 4870351   丢失 5129649（51.30%）
  第4轮: 2734908   丢失 7265092（72.65%）
  第5轮: 2455018   丢失 7544982（75.45%）
== AtomicI64 对照组: 10000000（恒等于 10000000，0 丢失）==

丢失量随调度交错程度浮动，51%~81% 这个区间就是 100 线程在这台机器上「未同步 load-modify-store」的典型分布。同一份代码换 -O 再跑：

== 未同步共享 i64（5 轮采样）：期望 10000000 ==
  第1~5轮: 10000000   丢失 0（0.00%）

-O 下 0 丢失。这段代码是未定义行为，编译器想丢就丢、想不丢就不丢——5 轮全对不是修复，是运气。这正是不加同步的共享读写不能进生产的原因：错误形态取决于优化档、微架构和调度，复现不了等于没发生。

对照数据（同机同负载）：

方案 100 线程 × 10 万次结果 丢失
UnsafeCell + 裸指针，-O0 5 轮：2.83M / 1.87M / 4.87M / 2.73M / 2.46M 51.3%~81.4%
UnsafeCell + 裸指针，-O 5 轮：10.00M × 5 0%（UB 运气）
Arc<AtomicI64>（Relaxed） 10,000,000 0%
Arc<Mutex<u64>>（示例 3b） 10,000,000 0%

示例 3：Rc→Arc，以及共享可变性的三种姿态#

3a：Rc 跨线程，编译期拒绝。 把 Rc<Vec<_>> 塞进 thread::spawn，原始报错：

error[E0277]: `Rc<Vec<i32>>` cannot be sent between threads safely
  --> src/rc-thread.rs:9:28
   |
 9 |       let _t = thread::spawn(move || {
   |                |
   = help: within this closure, the trait `Send` is not implemented for `Rc<Vec<i32>>`

Rc 的引用计数是普通整数——单线程假设。多线程下计数本身就成了数据竞争，所以它不是 Send。把 Rc::new 换成 Arc::new（原子计数），同一行代码编译通过。

3b：跨线程之后，「往里写」的三种姿态。 光 Arc<T> 只给共享只读；要写，内层还得自带可变通道：

姿态 机制 本机实测
A. RefCell 单线程内部可变性，运行时 borrow 检查 持有 RefMut 期间再取一次：panicked: RefCell already borrowed（already mutably borrowed）。且 RefCell 不是 Send，Arc<RefCell<T>> 无法跨线程
B. Mutex<T> 跨线程写竞争串行化 100 线程 × 10 万次 = 10,000,000，精确
C. AtomicU64 单值无锁 100 线程 × 10 万次 = 10,000,000，精确

RefCell 那条 panic 是运行时才暴露的——它属于示例 1 死锁同类的「逻辑错」：语法全对，运行时炸。

三层防线：哪类错误在哪层被挡住#

错误类型 挡在哪层 本文对应示例
数据竞争（无同步共享读写） 编译期：Send/Sync 检查不过就编不了 Rc 跨线程（3a）、UnsafeCell 不 Sync
死锁 运行时：锁序错了编译全过 双锁（示例 1）
内部可变性冲突 运行时：RefCell 二次 RefMut panic 3b-A
未定义行为 哪层都挡不住：UB 之下结果即运气 示例 2 的 -O「0 丢失」

无 GC 只回答「对象活多久」，不回答「两个线程同时写会怎样」。Rust 的答法是前两类尽量前移：竞争进类型系统，死锁留给运行时和锁序纪律；剩下的 unsafe 部分，写的人自负。

常见问题

Rust 没有 GC，是不是并发就安全了？

不是。Rust 把『数据竞争』（多线程无同步读写同一内存）推到编译期：Send/Sync 检查不通过就编不过。但死锁、逻辑错、以及你手写 unsafe 之后的未定义行为，全留在运行时。本文三个示例对应三层：编译期挡住的（Rc 跨线程）、运行时才炸的（双锁死锁、RefCell）、以及根本挡不住的（UnsafeCell + 裸指针）。

100 线程 × 10 万次，为什么丢 51%~81%？

每个线程做的是 load-modify-store 三步拆开：读共享格、本地加一、写回去。100 个线程并发做这件事，写回会互相覆盖（lost update）。本机 2 核实测 5 轮：丢失 51.30% / 71.69% / 72.65% / 75.45% / 81.35%。换成 Arc<AtomicI64> 或 Mutex 恒精确。

-O 优化后 0 丢失，是不是就安全了？

不是。-O0 下丢失 51%~81%，-O 下 5 轮全 0——编译器对未定义行为想怎么做就怎么做：丢掉更新是 UB，不丢也是 UB。『优化后结果恰好对』不能当安全证明，只能当运气。

Rc 和 Arc 差在哪？

引用计数策略不同：Rc 是普通整数（单线程假设，非 Send），跨线程直接编译拒绝；Arc 原子化计数（一次原子加/减的代价），能跨线程。单线程内 Arc 换 Rc 通常更快（原子操作在部分平台上更贵），多进程/跨线程必须 Arc。

什么时候用 RefCell，什么时候用 Mutex？

单线程内部可变性用 RefCell（运行时 borrow 检查，两次 RefMut 撞一起 panic）；跨线程可变共享用 Mutex 或 Atomic。RefCell 不是 Send，Arc<RefCell<T>> 无法跨线程——跨线程要写共享状态，Mutex<T> 或原子类型是合法通道。
