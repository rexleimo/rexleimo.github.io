微软开源了个 Rust 系统调用沙箱，我把 8 个 UnixBench 关进去跑了一遍

LiteBox 纯 Rust 系统调用级沙箱，本机拉仓编译 8 项 UnixBench 关进去跑：纯计算损耗 0.6%~1.0%，I/O 那几格是环境差别当更快，fork 类 N/A。

October 25, 2026 · 3 min · 470 words · 梦兽编程 -  | 

下午我把微软新开源的 LiteBox 拉下来编译了一遍，用它自带的那套 UnixBench 对比脚本，把一个普通 Linux 二进制原样跑、再关进它的沙箱里跑，各 3 轮取均值。结果里有一条我盯着看了很久：纯计算路径，套沙箱前后几乎没差，dhry2reg 原生 519.6M lps，沙箱里 522.7M lps，比的是同一台 2 核 EPYC。

先说它是什么。LiteBox 是微软丢出来的一个 Library OS，把整个 Linux 用户态当成一个「库」跑，系统调用在进内核之前被拦下来重写。它纯 Rust，github.com/microsoft/litebox 三个多 star，还在更新。我关心的是一个很具体的问题：把一个你信不过的程序关进这种沙箱，要多付多少性能。

本机编译：三个组件 + 一个踩出来的坑#

仓库是个 cargo workspace，跑起来要三个二进制。我把它们全编译了出来：

cargo build --release -p litebox_runner_linux_userland
cargo build --release -p litebox_syscall_rewriter
cargo build --release -p litebox_packager

1m06s，BUILD_EXIT=0。前两个顺，第三个卡了十分钟。packager 默认依赖 oci-client 的 native-tls 特性，那个特性拖 openssl-sys，要系统头文件 libssl-dev。这台机器只装了运行时的 libssl.so.3，没有头文件，sudo 又要密码，装不上。

我翻了 packager 的源码，本地打包路径根本用不到 OCI 拉镜像那套，openssl 纯粹是被依赖图捎进来的。把 Cargo.toml 里 oci-client 的 TLS 后端从 native-tls 换成 rustls-tls，纯 Rust，本机有 gcc 直接编，12.5MB 的 packager 二进制就出来了。这条改动我原样留着，没动别的东西。

它怎么把程序关进去#

不是虚拟机，也不是容器，是三件工具串起来：

litebox_packager 拿你的二进制做入口，跑 ldd 把直接依赖的共享库全列出来，一个接一个递归往下挖。每个找到的文件都过一遍 litebox_syscall_rewriter——它在 ELF 的机器码里把系统调用指令的位置找出来，换成跳进一个 trampoline 的调用。原始字节不动，只是改了指令指向。最后把改过的二进制加上它依赖的 .so，打进一个 tar。

litebox_runner_linux_userland 拿到这个 tar，解进一块内存文件系统，跑里面那条被你「改过」的主程序。跑的时候它往里塞了两样东西：LD_LIBRARY_PATH=/lib64:/lib32:/lib 让动态链接器找得到那套 .so；HOME=/。程序以为自己在正常 Linux 上跑，其实每个系统调用都先被 trampoline 截一下，交给 LiteBox 的 shim 层处理。shim 决定放行、改写还是拒掉。

我手动跑了一遍 dhry2reg 的打包过程，确认中间产物对得上：

$ ./litebox_packager .../pgms/dhry2reg -o /tmp/lb-smoke/dhry.tar
Found 3 unique files across 1 input file(s)
Rewriting 3 unique ELF files...
Created /tmp/lb-smoke/dhry.tar (3 entries, 2.3 MB)

3 个文件 = dhry2reg 本体加上它那两个 .so。2.3MB 的 tar，解进内存就能跑。

8 项 UnixBench 关了进去跑#

仓库里 dev_bench/unixbench/run_unixbench.py 就是官方给的对比脚本：同一条 UnixBench，先原样跑一遍当 baseline，再打包跑一遍，出对照表。我把 8 项非 fork 基准全跑了，3 轮取均值。机器是这台 2 核 EPYC 的 VPS，两边跑的是同一块盘、同一套 vCPU。

表我原样贴在这儿，逐项 3 轮均值：

基准类型原生沙箱比值
dhry2reg纯计算519.6M lps522.7M lps1.006
whetstone-double纯计算8890 MWIPS8798 MWIPS0.990
execl进程创建43.8K lpsN/Afork 未支持
fstime磁盘 I/O679K KBps2427K KBps3.57×
fsbuffer磁盘 I/O170K KBps666K KBps3.91×

三个我能下、三个我不能下的结论#

能下的就一条，也是最值钱的那条：纯计算路径，沙箱损耗在噪声里。dhry2reg 原生 519.6M、沙箱 522.7M，差 0.6%；whetstone 0.990，损耗 1.04%。两个数都落在 3 轮之间的抖动区间。也就是说把程序关进 LiteBox，只要你这段代码主要在 CPU 上转、不怎么碰系统调用，你几乎感知不到。这是整件事的卖点——拿一个可忽略的 CPU 开销，换一道系统调用级的隔离边界。

第二，execl 那一格是 N/A，不是我漏跑了。官方脚本里这一项标了 requires_fork=True，LiteBox 现在的 shim 不接 fork，所以进程创建基准只能跑原生侧。我在正文里原样写出来，不替它圆。

第三，I/O 那四格——fstime、fsbuffer、fsdisk、pipe、syscall——沙箱数值比原生高 2 到 3.9 倍。这个数字我不能用来论证「LiteBox 更快」，因为它是假的。我专门回去查了为什么：UnixBench 这些基准靠 wake_me(duration, report)，也就是 SIGALRM 到点就停、数窗口里累计了多少次。我单独量了 pipe 和 syscall 两边的真实墙钟——原生 10.01s，沙箱 10.01s，SIGALRM 都正常在 10s 停。时间一样，次数却差出几倍，只可能是执行环境不同：沙箱在内存 rootfs 里跑，原生在共享 VPS 的盘上跑，两者的 I/O 后端根本不是同一套。所以这张表里 I/O 那四格的「比值」我只当环境差异摆出来，不往「沙箱快多少倍」上靠。

它适合什么，不适合什么#

适合的场景是把「信不过的 / 第三方的 / 多租户的」代码关起来跑：云函数、插件加载、跑用户上传的东西。你付的代价，按我这组数，纯计算部分接近零，真正要担心的是 I/O 和系统调用密集的部分——但那是「沙箱会不会比原生慢」的问题，不是「沙箱能不能隔离」的问题，方向不一样。

不适合的，是 fork 密集的负载。execl 直接 N/A，shell1、shell8、spawn、context1 这几项官方脚本里都标了要 fork，现阶段同样跑不了。LiteBox 现在能关进去的是「单线程、主要靠系统调用交互、不太 fork」的程序。

可复现命令#

# 拉仓 + 编译三个组件
git clone --depth 1 https://github.com/microsoft/litebox
cd litebox
cargo build --release -p litebox_runner_linux_userland -p litebox_syscall_rewriter -p litebox_packager

# packager 的 TLS 后端改 rustls（本机没装 libssl-dev 时的绕法）
#   litebox_packager/Cargo.toml: oci-client features 由 native-tls 换 rustls-tls

# 下载 + 编译 UnixBench（路径写死在 dev_bench/unixbench/ 下）
# 跑对比（8 项非 fork 基准，3 轮，JSON 落盘）
python3 dev_bench/unixbench/run_unixbench.py \
  --benchmarks dhry2reg whetstone-double execl fstime fsbuffer fsdisk pipe syscall \
  --iterations 3 --mode both --release \
  --runner-path target/release/litebox_runner_linux_userland \
  --packager-path target/release/litebox_packager \
  --output /tmp/litebox-ubench.json

FAQ#

问：这套是虚拟机吗？ 不是。没有 hypervisor，不加载内核。它是把 Linux 用户态的二进制和 .so 一起打包、在宿主上通过系统调用拦截来跑，属于 Library OS / 沙箱这一类，隔离边界在系统调用层。

问：纯计算损耗 0.6% 意味着沙箱完全免费？ 不是。我那 0.6% 是 dhry2reg 这一个单线程纯寄存器运算的均值，落在 3 轮抖动里。多核、带锁、带 I/O 的负载我没在这台机上压，数字不外推。

问：execl 为什么 N/A？ LiteBox 现在的 shim 不实现 fork（官方脚本里 execl/spawn/shell1/shell8/context1 全标 requires_fork），进程创建这一类只能跑原生侧，跑不了沙箱内。

问：I/O 那四格沙箱比原生快 2~4 倍，是不是 LiteBox 特别快？ 不是，那是我的测试环境差异。沙箱在内存 rootfs 里，原生在这台共享 VPS 的盘上，两边 I/O 后端不一样，比值不能拿来比性能。我把真实墙钟（两边都是 10.01s）单独量过，时间相同、次数不同。

问：我能不能就这么用它跑不可信程序？ 机制上能，但 LiteBox 是 0.1.0、还在快速迭代，官方定位是研究原型。拿来扛生产要等它把 fork、信号这些补齐，我这边只验了单线程 + 系统调用拦截那条主路径。

我踩的坑#

packager 那条 OpenSSL 依赖是本机唯一的拦路虎。它默认 native-tls 拖 openssl-sys，要系统头文件；这台机器只有 libssl.so.3 运行时库、没有 -dev 包、sudo 又要密码。解法就是把 oci-client 的 TLS 后端换成 rustls-tls，纯 Rust 编译，本机 gcc 直接过。改动只在 Cargo.toml 一行，本地打包路径用不到 OCI，没有副作用。

延伸阅读#

LiteBox 官方仓库在 github.com/microsoft/litebox，dev_bench/unixbench/README.md 里把这套对比脚本的跑法写全了。

Library OS 这一类的早期工作可以看 Microsoft 的 Exos 论文，LiteBox 是它在用户态沙箱方向的延续。
