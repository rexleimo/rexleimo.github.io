Safe SIMD 续集：kernel! 宏是怎么把 unsafe 收到 1 处的——feature token 拆解

9 月底 fearless_simd 1.0 那篇我报过「50 块 unsafe vs 官方 0」。这篇补它没展开的机制：kernel! 宏靠「CPU feature token」+ 泛型 f32x8<L>，把 unsafe 收进 1 处可审计点，让你写 a+b 不用管底下是 AVX2 还是 …

October 12, 2026 · 3 min · 541 words · 梦兽编程 -  | 

9 月底那篇 Fearless SIMD v1.0 我报过结果：50 块 unsafe（对照组 wide 1.7.1 是 441 块），官方博文说「这个 crate 里找不到 ad-hoc unsafe」。但读者后台问得最多的是同一句：「kernel! 宏到底怎么把 unsafe 收掉的？」 那篇我没展开机制。这篇补上——拆作者 Shnatsel（rustc 核心成员、SIMD 标准库设计者）10 月 10 日亲自写的机制文。

先给三个结论：

  1. kernel! 宏不是「魔法删 unsafe」，是把 unsafe 搬进 1 处可审计点——宏展开后内部仍有 1 个 unsafe，但整个 crate 只需要审这 1 处，不是 441 处。
  2. feature token 是关键：一个类型 Avx2，代表「当前 CPU 支持 AVX2」。你拿到 token 才能调 AVX2 函数，拿不到就编译不过。它把「运行时 CPU 检测」搬进了类型系统。
  3. 还有 inline 税没解：调用泛型 SIMD 函数 a+b，得写在 #[inline(always)] 或带 #[target_feature] 的函数里，否则性能掉。作者明说「还没看到解法」。

这篇讲四件事：痛点在哪、feature token 是什么、泛型怎么把 token 藏起来、落到业务代码体感到什么。

痛点：「我要写 a + b，凭什么要写这一坨」#

原始 SIMD intrinsics 长这样（原文）：

unsafe {
    #[cfg(all(any(target_arch = "x86", target_arch = "x86_64"), target_feature = "avx2"))]
    _mm256_add_ps(a, b)
    #[cfg(all(any(target_arch = "x86", target_arch = "x86_64"), target_feature = "sse", not(target_feature = "avx2")))]
    _mm_add_ps(a, b)
    #[cfg(all(target_arch = "aarch64", target_feature = "neon"))]
    vaddq_f32(a, b)
}

作者原话：「Look at it. It’s hideous. And the whole thing is wrapped in unsafe!」 这还是简化版——没算 AVX-512、32-bit ARM、Wasm、RISC-V，没算把 &[f32] 加载成各 intrinsic 吃的形式，没算「按当前 CPU 选最优实现」。

Rust 的 SIMD 抽象（std::simd 系、wide、fearless_simd）就是来解决这个的——让你直接写 a + b。但 1.87 之前有个死结：

每个 intrinsic 调用都得裹一层 unsafe。 原因：调 AVX2 指令而 CPU 不支持，是未定义行为。所以你得先检测「这 CPU 支不支持 AVX2」，再决定调不调——检测逻辑本身就要 unsafe。

1.87 的小进步 + 残留的 unsafe#

Rust 1.87 开始，编译器自己追踪每个 intrinsic 需要哪些指令集了。于是你可以写：

#[target_feature(enable = "avx2")]
fn add_avx2(a: __m256, b: __m256) -> __m256 {
    _mm256_add_ps(a, b)  // avx2 intrinsic，无需 unsafe
}

注意：函数体内没有 unsafe 了——编译器知道「这个函数标了 avx2，里面的 avx2 intrinsic 就是安全的」。

但两个问题还在：

  • 你调用 add_avx2(a, b) 时还是得 unsafe { add_avx2(a, b) }——unsafe 只是上移了一层。
  • 更根本的：你没法在 impl Add for 某类型 上挂 #[target_feature]，因为 + 必须永远可调用。所以这条路给不了 a + b。

关键拼图：feature token#

作者的解法：给「当前 CPU 支持 AVX2」这件事造一个类型 Avx2：

#[target_feature(enable = "avx2")]
fn add_avx2(token: Avx2, a: __m256, b: __m256) -> __m256 {
    _mm256_add_ps(a, b)
}

token: Avx2 这个参数是关键——你只有拿到 Avx2 token 才能调这个函数。而 Avx2 token 只能在「当前 CPU 确实支持 AVX2」时才构造得出来。于是：

  • CPU 不支持 AVX2？你拿不到 Avx2，调用 add_avx2 直接编译不过——类型系统替你挡了。
  • CPU 支持？你拿到 token，调用安全。

但「怎么证明拿到的 token 是对的」这一步仍需 unsafe（跟编译器做约定）。作者的做法：把这个 unsafe 锁进一个宏 with_avx2!，宏展开后内部只有那 1 处 unsafe：

with_avx2! {
    fn add_avx2(token: Avx2, a: __m256, b: __m256) -> __m256 {
        _mm256_add_ps(a, b)
    }
}

这就是 kernel! 宏的本质：把「假设 CPU 支持 X」这个 unsafe 约定，收敛到 1 个宏里。整个 crate 只需审计这 1 个宏（它的正确性只有两个失败模式：token 映射到错误的 feature、允许 unsafe fn 在 safe 上下文调——两者都极易检查），其余 440 处业务逻辑不需要再碰 unsafe。

泛型把 token 藏起来：f32x8#

光有 token 还不够——你调 add_avx2 还得手动传 token，那 a + b 的糖还是吃不到。作者的绝活：用泛型把 token 塞进类型参数：

pub struct f32x8<L: Level> {
    data: [f32; 8],
    token: L,  // token 藏在类型参数里
}

impl std::ops::Add for f32x8<Avx2> {
    type Output = Self;
    fn add(self, rhs: Self) -> Self::Output {
        // 用 self.token 调安全包装，不用 unsafe
        let result = add_avx2(self.token, self, rhs);
        Self { data: store_m256(result), token: self.token }
    }
}

f32x8<Avx2>、f32x8<NoSimd>、f32x8<Sse2>……每个 CPU 能力档位一个泛型实例。你写 a + b 时，编译器按当前 CPU 自动选对实例。token 彻底不可见，a + b 直接工作，底层自动选 AVX2/NEON/标量。

这就是 fearless_simd 对外 API 的全部机制：泛型 Level 参数 = 运行时 CPU 检测的类型化版本。

inline 税：作者自己点出的未解项#

最后一节作者没藏：即使有上面这套，调用泛型 SIMD 函数 a+b，得写在 #[inline(always)] 里、或写在带 #[target_feature] 的函数里，否则能编译但性能掉。

作者引了 Struct Target Features RFC（rust-lang/rfcs#3525）说「它解了 add_avx2(token, a, b) 和 add::<S: Simd>(token, a, b) 这两层，但到 a + b 这层，我没看到路」。这是当前 fearless_simd 的诚实边界——v1.0 稳定了，但这层还没完全免 inline 标注。

落到你的业务代码#

如果你在用 fearless_simd（或未来 std::simd 稳定后的官方路径）：

  • 写 a + b 不用管 token：库内部用 f32x8<L> 泛型把 token 藏了，你只接触泛型参数，不接触 Avx2 类型。
  • 性能敏感路径：记得在 #[inline(always)] 或带 #[target_feature] 的函数里调用泛型 SIMD 函数，否则吃 inline 税（作者明说的）。
  • 要指令级控制：可以安全地混用——fearless_simd 把宏也暴露了，你想直接调 intrinsics 也能，unsafe 仍锁在那 1 处可审计点。

诚实声明：本篇机制全部转述自 Shnatsel 原文（10-10 发布，10 min read），我本机没有编译/跑 fearless_simd 的 simd 代码（本机无 Rust SIMD 目标工具链验证）。feature token、泛型 f32x8、inline 税三个点的代码块均从原文原样摘，未本地复现。

常见问题

跟 9/25 那篇 fearless_simd 1.0 什么关系？

续集。9/25 那篇报的是「结果」：50 块 unsafe、35 个直接依赖、3 年安全承诺。这篇拆的是「机制」：kernel! 宏到底怎么做到把 unsafe 收进 1 处可审计点，让你写 a+b 不用管底下是 AVX2 还是 NEON。两篇互补。

feature token 是什么？

一个类型层面的标记（Avx2()），代表「当前 CPU 确实支持 AVX2」。你只有拿到这个 token 才能调 AVX2 专用函数——拿不到就编译不过。token 只能在 CPU 支持该 feature 时才构造得出来，所以它把「运行时 CPU 检测」这件事搬到了类型系统里。

我写业务代码要拿到 token 吗？

不用。fearless_simd 把 token 藏在泛型参数里（f32x8<L>），你调用时它自动按当前 CPU 选对实现。你只管 a + b，token 是库内部的事。

inline 税是什么？

作者点出的未解项：调用 SIMD 泛型函数 a+b，要么写在 #[inline(always)] 里、要么写在带 #[target_feature] 的函数里，否则能编译但性能掉。Struct Target Features RFC 正在解这个，但「到 a+b 那一步」还没看到路。
