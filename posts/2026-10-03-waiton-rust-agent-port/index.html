把 1200 万周下载的 npm 包交给 AI 维护一周，我学到的 5 条护栏

一个 11 年的 npm 老牌包 wait-on（周下载 1200 万），新 maintainer 上任第一周就交给 coding agent 夜里并行干活：27 个 PR、6 个 release，还顺手启动了 Rust 双引擎移植。我逐条把这套东西在我本机验了一遍——能带走的是 5 条护栏，而不是 AI 多能干。

October 3, 2026 · 3 min · 576 words · 梦兽编程 -  |  English

我把一个 11 年的 npm 老牌包 wait-on 在新 maintainer 手上、交给 coding agent 维护第一周的全过程，在我本机逐条过了一遍：它是什么、活怎么跑的、哪几条规则真的能抄进你自己的仓库、哪几条看着酷但你学错就翻车。

先说为什么挑它：wait-on 周下载 1200 万级，装在几乎所有 e2e 测试管道里，Grafana、WordPress、Storybook、Node.js undici、Cloudflare、Shopify、Angular、Spotify、IBM 的 package.json 都挂着它。这个位置意味着一件事——它错一个字母，砸的是别人的 CI，不是自己的。 所以这个案例最值得拿来当「agent 维护基础设施」的标尺：在错的代价最大的地方，护栏到底能不能立住。

wait-on 是干嘛的：等 dev server 起来，再放行测试#

wait-on 干的事一句话：阻塞，直到某个文件、端口、socket 或 URL 就绪。典型用法就是「等 dev server 起来，再跑 e2e」。它 2015 年 7 月首 commit，到今天 11 年。

为什么它这么重。我本机拉了几个下游看它在生态里的位置：

  • npm stats 官方口径，周下载 12,921,231（我 2026-10-03 拉的 last-week 窗口）
  • npm view start-server-and-test dependencies → 精确钉死 "wait-on": "9.1.0"——一个字母的版本钉死
  • jest-dev-server → 靠字符串匹配错误文案 "Timed out waiting for" 判超时。你改它一个错误文案，下游的超时检测直接瞎

这两个不是抽象的「很多人依赖」。一个是精确钉版，一个是靠错误文案做协议——你的一个错误改动，下游要么挂死、要么假绿（测试全过、环境没起）。 这就是这个包上任何改动要过的门槛，也是后文所有护栏存在的理由。

活是怎么跑的：agent 夜里并行，人只定方向#

新 maintainer（Dorvie 工程总监 Kevin Old）上任第一周的实际产出：27 个 PR 合入（其中 24 个是原作者 review 后合的）、17 个 issue 关掉（最老一个开到 2017）、6 个 release（上一个正式 release 还停在 7 月）、Rust 双引擎移植 243 个 commit 落在 fork 的实验分支。

跑法不神秘，一套现成工具链（Every 的 Compound Engineering 插件）：先写计划再写代码、test-first 实现、把「这次踩到的非显然的东西」写进 docs/solutions/ 给下一个 agent 会话读。Rust 移植多压一层结构——一个大任务拆成若干条 lane，每条 lane = 一个 issue + 一份计划 + 一个 PR + 固定文件清单，越界不合并。几个 agent 夜里并行，就是这么不打架的。

一个我特意核的细节：这一周大部分活是「重做」不是「新写」。躺了多年的社区 PR（parseArgs、TS 类型定义、command resource）被 agent 逐个重构成小的、带测试的 PR，release notes 还保留了原社区作者的名字。agent 没有凭空造功能，它是在一个有存量、有测试、有 review 的仓库里安全地清账。 这是它能跑的前提，后面会说为什么没有这层前提你就别让它跑。

五条护栏（这才是这篇的重心）#

先把命题立住：活跑得越快，项目越需要机器能检查的规则。 人也好 agent 也好，都不会每次都做对。这 5 条不是谁拍脑袋定的，是出过事之后逼出来的。最硬的一次：axios 换成 fetch 的那个 PR，处理 env 代理的分支悄悄丢掉了 strictSSL、ca、cert——没有任何测试把「HTTPS 目标 + env 代理 + TLS 选项」组合在一起，最后是 reviewer 抓出来的。事故之后，test-first 变成强制项。

#护栏一句话我的判定
1test-first 强制每个 bug 先有一个失败复现；计划点名的每个风险变成一个失败测试；两个输入有交互就列组合、每组合一个测试整套体系的地基。没有它，后面 4 条都是纸面纪律
2一个 PR 一个关切拆到一个人能独立审的粒度agent 并行输出的正确解法——大 diff 拆回「人能审」的粒度
3人合并agent 开 PR，maintainer 决定合不合全文最贵的一条。它把「信不信 agent」变成伪问题：合并权本来就在人手里
4agent 不碰 CIRust lane 不许碰 .github/workflows/，只能改 npm script 里调 cargo xtask 的调用发版通道是供应链攻击面，agent 摸得到 CI 就全完了
5发版不存 tokensemantic-release 从 CI 走 npm OIDC trusted publishing「没有 token 可以被偷」——把一整类事故从「靠人不犯错」升级成「结构上不可能」

我的判断，讲明：第 3 + 第 5 条最值钱。 第 3 条消解了「AI 靠不靠谱」这个焦虑——你不用决定信不信，因为合不合的决策权不出门。第 5 条是把密钥泄露这类事故从「小心点」变成「结构上做不到」。这两条今天就能上，任何仓库、有 agent 没 agent 都受益。

哪些别抄（跟上面同等重要）#

上一条说 5 条护栏能抄。这条说案例里看着更酷、但抄错就翻车的三样：

  • 8 平台二进制塞一个 36MB tarball：那是 wait-on 供应链位置逼出来的特例——它要「零安装脚本 + ignore-scripts=true 可装」。你普通 npm 包用 per-platform optionalDependencies（各平台只下自己那份）就行，36MB 的账不用你付。作者自己都在压它（目标 packed 8MB，现在 15MB，CI 挂了 size budget）。
  • cargo-deny + cargo-vet 双闸：只在「原生二进制进供应链、要审 crate 清单」时才需要。你的 JS 项目没有 8 个原生二进制要审计，双闸是负资产。
  • 多 worker 并行（14 条 lane）：前提是存量测试套件够严（496 个测试 + Rust 核心 100% 行覆盖）。你的仓库测试覆盖不到的地方，agent 跑 1 个 worker 都多——没有地基，并行就是 bug 并行。

判断标准就一句：agent 越快，测试和护栏的存量要求越高，不是越低。速度是把地基照出来的探照灯，不是替代地基的东西。

为什么顺手上了 Rust：为供应链，不为快#

双引擎移植的真实动机排序是：砍供应链攻击面 > 没有 Node 也能用 > 启动速度 > 正确性。Rust 核心把 HTTP 栈和轮询循环整体换掉，JS 侧理论上只剩 joi。

有一句值得单独拎出来，它解释了为什么「二进制上了还不够」：npm provenance 只能证明这个二进制是谁构建的，证明不了里面的 crate 是安全的。 所以二进制之外还得有 cargo-deny/vet 双闸去审 crate 清单。

另外别抱性能期待：addon 方案还要 boot Node，启动速度它一分不赚——Rust 在这里纯粹是为「能整体审计掉的一块」服务的。

我本机实际跑了什么（结论垫底）#

「只发跑出来的数字」是这站的规矩，我把关键几条在本机跑了（2026-10-03）：

  1. Rust 引擎现在装不到。 npm view wait-on@10.0.0-rc.1 dist.unpackedSize → 57314（57KB）；npm pack 开包，里面只有 JS 入口，0 个 Rust 二进制。那个「36MB」是 fork 上构建的 prerelease，没发到 npm——Rust 引擎在实验分支等 soak。读这类东西，「我现在能不能装到」比「作者能不能跑通」更实在。
  2. 下游钉子户确实在钉。 npm view start-server-and-test dependencies → "wait-on": "9.1.0"；jest-dev-server → "^8.0.1"。所以 9→10 的切换得让 JS 引擎再陪跑一个 major，这是被下游 pin 逼出来的，不是我替它保守。
  3. 没验的写明没验。 27 PR、496 测试、243 commit 这些是 Kevin 复盘里给的数，我没进 GitHub 逐条数；「4 个大厂仓库挂 wait-on」我是看了链接清单、没逐仓点开。这些在下面「诚实声明」里全部标出来。

收尾判断#

作者那段话我认，它比任何「AI 多能干」的标题都准：

我的工作是把测试写到足够严，严到可以信任一份我不逐行读的代码。

落到你自己身上是三句话：信不信 agent 是伪问题（合并权留在人手里）；agent 越快测试存量越值钱（探照灯不是地基）；抄规则别抄姿势——5 条护栏今天能上，36MB 的 tarball 和 14 条 lane 是别人供应链位置的仗。

FAQ#

两个引擎跑的是同一套测试吗？ 是。JS 引擎 npm test，Rust 引擎 WAIT_ON_ENGINE=rust-strict，同一套 mocha、无 pending、Rust 核心 100% 行/region 覆盖。我没本地跑（npm 上的 rc 包还没有 Rust 引擎），转引。

ignore-scripts=true 装包，Rust 引擎能用吗？ 那正是「8 个二进制塞一个 tarball、零安装脚本」的目的——容器测试就是 ignore-scripts=true + 只读 + 无网络跑的。这条我没验，转引。

Node 版本要求？ 10.0 要求 Node 22.19+。自验：npm view wait-on@10.0.0-rc.1 engines。

普通小项目该抄哪几条？ 抄「5 条护栏」全 5 条（test-first / 一 PR 一关切 / 人合并 / agent 不碰 CI / 发版不存 token）。别抄「哪些别抄」那 3 样（特例打包 / 双闸 / 多 worker 架构）。

常见问题

5 条护栏我自己没有 AI 代理也能用吗？

能。test-first、一个 PR 一个关切、人合并、agent 不碰 CI、发版不存 token——没有一条依赖 Rust 或 agent。人写 PR 的仓库照抄同样受益，agent 只是让规则检查速度变成瓶颈。

AI 维护一个 1200 万周下载的包靠谱吗？

看地基。它成立的前提是这个 11 年包存量测试套件够严（496 个测试、Rust 核心 100% 行覆盖）——没有这层地基，agent 跑得越快摔得越狠。我自己把关键数字在本机验了一遍，没验过的都写明了。

Rust 双引擎那个 36MB 的包我现在能装上吗？

不能。npm 上 10.0.0-rc.1 我 `npm pack` 开过，unpacked 57KB、0 个 Rust 二进制——Rust 引擎停在 fork 的实验分支等 soak，未来 major 才进 npm。现在能装的都是纯 JS。

那些看着酷的（8 平台 36MB 打包、cargo-deny/vet 双闸、多 worker 并行），我普通项目要学吗？

别学。那是 wait-on 供应链位置逼出来的特例。判断标准一句话：agent 越快，测试存量越值钱——速度是探照灯，不是地基。
