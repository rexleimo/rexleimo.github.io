从 30% 到 0：一行 Skill description，我在本机实测省了 57% token

把重复提示词拆成 Claude Code Skill 之后，它开始自己乱跳流程。我没有照搬别人帖子里的数字，而是自己搭了个受控实验：宽 description 误触发 30%，收紧一行后 0；prompt 加一句角色锁定，token 实测降 57%。全部可在你机器上复现。

September 27, 2026 · 2 min · 307 words · 梦兽编程 -  |  English

先说结论#

我把 5 个高频重复提示词拆成 Claude Code Skill，结果它开始乱跳流程。我没去翻别人的帖子抄结论，而是自己搭了个受控实验，在自家机器上把两个数字跑了出来：

  • 写宽的 description：误触发 30%；收紧成一行触发条件后：0
  • 给 Skill prompt 加一句角色锁定：单次任务 token 实测降 57%

Skill 的触发权在 frontmatter 的 description 那几行字上，正文懒加载，根本不参与判断。 这条没搞懂，Skill 写得越多，误触发越凶。下面每一个数字都是我能交代复现方法的。

踩坑现场#

哥们，你写 Claude Code Skill 的时候是不是也这样——拆完提示词，以为一次到位从此躺平，结果它开始自己乱跳流程？

我忍了几天，决定别再凭感觉判断"是不是又误触发了"，专门搭了个最小区别化实验。方法很简单，就是把触发判断单独剥出来测：

实验一：description 写宽了到底误触发多少#

我构造了 20 条请求：10 条真的该触发代码审查（“帮我 review 这段"“这段代码有个 bug 帮我审查”），10 条不该（“帮我修个空指针"“写个快排"“格式化这段代码”）。然后把 description 换成两种写法，让模型只回答 YES/NO 该不该触发：

description该触发命中（/10）不该触发却触发（/10）误触发率
帮助用户进行代码审查和代码优化10330%
当用户明确要求 “code review” 或指出某段代码有 bug 需要审查时使用900

宽的那版连"帮我写个单元测试"都抢着触发——“代码"“优化"两个词宽到什么程度，你自己品。窄版丢了一个召回（“帮我审查下这个函数"没命中），代价可接受。注意它的结构：触发动词 + 具体词面 + 场景边界。从那以后我写 Skill 有个习惯：先写「什么时候该触发」这一行，写不出来，说明这个 Skill 本来就不该拆出来。

机制层：判断只看清单，不看正文#

为什么改一行字就有效果？把官方 docs 的链条理一遍：

  1. Skill 的正文（body）是懒加载的——被触发的那一刻才进上下文；
  2. 但模型启动时要预载一张清单：每个 Skill 的 name + description；
  3. 触发判断 = 你的请求跟清单做匹配，跟正文一字无关。

第 3 条是整篇文章的地基：description 不是写给人看的「功能介绍」，是给路由判断用的触发条件说明书。

实验二：角色锁定，token 降 57%#

触发修好之后我又顺手加了一刀——在 Skill prompt 开头放角色锁定：

你是一个严格的代码审查专家，只做以下三件事：
1. 找 bug
2. 给修改建议
3. 指出潜在风险
不要闲聊，不要解释背景。

同样是 8 段真实代码的审查任务，对比两种 system prompt（严格的 4096 上限，无一撞顶）：

对照组平均 completion tokens
宽松（“有帮助的助手，可以详细解释”）1421
角色锁定（上面那句）616
降幅57%（中位 61%）

模型不再跑偏去解释"为什么我不这么做”，输出直接短一截。触发对了是省 token 的第一步，行为收窄是第二步，两步都是改那几行字，一行代码不动。

我把 1% 预算当回事，因为我自己就超了#

docs 排障章节给了个多数人会扫一眼就划走的参数：预载清单的字符预算约为上下文窗口的 1%，超了就把 description 截断——截掉的正是路由判断要用的关键词。

我没当它是理论，把自己机器上的技能库数了一遍：70 个 Skill，description 共 3684 字符，均值 52，最长 105。按 200k 窗口算，1% ≈ 2000 字符——超了 1.8 倍。也就是说我技能库后半截的 description 现在就是残缺状态，路由一直在拿不完整的信息做判断。

所以我的纪律是量化到数字的：每个 Skill 的 description 压在一行以内，只留触发条件，写完全库字符数 ÷ 窗口 1% 预算 ≤ 1。团队里 5 个人各写 10 个三行 description，预算直接爆——别等截断开始造成误触发才想起来数这个账。

怎么在你机器上复现#

脚本就 30 行，核心逻辑：

# 触发实验：把路由判断剥出来
# ROUTER: "你是技能调度器。技能 [code-review] description: {desc}。
#         请求：「{req}」。该触发？只答 YES/NO。"
# 20 条固定请求（10 相关/10 无关），换 desc 跑两遍，统计无关组 YES 数
# token 实验：同 8 段代码，system prompt 一锁一放，各取 completion_tokens 均值

跑之前注意两点：① 固定 20 条请求和 8 段代码（存盘），换 desc 是唯一变量；② token 对比上限设 4096，撞顶的数字作废。模型换谁结论方向不变，幅度会变——我用的是 Agnes 端点 flash 档。

几点要说明白的事#

  • 30% / 0 误触发、57% token 降幅、70 个 Skill / 3684 字符 / 超 1.8 倍：全部是我本机实测，方法上文给全了，你可以原样复现；我的机器 ≠ 你的机器，幅度有出入属正常，方向不该变。
  • 1% 清单预算是官方 docs 原文（Claude Code Skills 文档 外部链接 ）；3684/70 那组数是我拉本机技能库逐条数出来的。
  • linux.sb 上有位楼主报告过"误触发接近 40%"（文末相关阅读），方向与我一致，数值我未采用。

你是哪一派#

  • A 派：description 写宽点好，宁可误触发也别漏 → 你算过误触发的账吗？它烧的是你每轮 token 和耐心，宽不是安全感，是慢性失血；
  • B 派：我 Skill 没几个，1% 预算够的，不用管 → 够用就没错；但团队里 5 个人各写 10 个，预算立刻爆，这条提前写进团队规范不亏；
  • C 派：我连 CLAUDE.md 都嫌长 → 那你更该学，一行 description 就是最小的可维护面。

你的 Skill 库现在多少个、description 都是什么风格？评论区晒出来，攒够一批我出个「Skill 触发率自查清单」续篇。

转给那个还在往 CLAUDE.md 里堆东西的同事——你堆的不是规范，是每轮都交的 token 税。

常见问题

Skill 和直接塞 CLAUDE.md 有啥区别？

CLAUDE.md 全程在线，写多了纯烧 token；Skill 的正文只在触发时加载，启动成本只有那行 description。高频刚需放 CLAUDE.md，低频专项流程放 Skill。

description 里的关键词怎么定？

抄你自己真实会说的话。你会说「帮我 review 这段」，description 里就得有 review 这个词面。用抽象名词（「代码优化」）不如用具体词（「code review」「bug」）——我 20 条受控请求测出来，宽词误触发 30%，窄词 0。

触发得太窄（该出没出）了怎么办？

把漏掉的触发词补进 description，一次加一两个、观察一周，别一次堆五个——堆多了又回到误触发老路。

为什么官方 docs 说 Skill 多了 description 会被砍？

启动时预载的 Skill 清单（name + description）有字符预算，约为上下文窗口的 1%。超预算的 description 会被截断。我自己技能库 70 个 Skill、3684 字符，已经超 1.8 倍了。
