Skill 误触发 40%？一个 description 改出来的 30% 提效

把 5 个重复提示词拆成 Claude Code Skill 之后，它开始自己乱跳流程。根因不在正文，在那一行 frontmatter：description 是触发条件说明书，写宽了误触发接近 40%；收紧一行之后，顺手还能再省 20-30% token。

September 27, 2026 · 2 min · 263 words · 梦兽编程 -  |  English

先说结论#

我把项目里 5 个重复提示词拆成了 Claude Code Skill，改一行 description，误触发从 40% 掉到接近 0；顺手加了句角色锁定，单次任务 token 再降 20-30%。

Skill 的触发权在 frontmatter 的 description 那几行字上，正文懒加载，根本不参与判断。 这条没搞懂，Skill 写得越多，误触发越凶。

踩坑现场#

哥们，你写 Claude Code Skill 的时候是不是也这样——拆完提示词，以为一次到位从此躺平，结果它开始自己乱跳流程？

我忍了几天专门统计了一波：误触发率接近 40%——每十次没让它调 Skill 的普通对话，有四次它自己抢着上。某天我就想让它修个小 bug，它二话不说跳进审查 Skill，把完整 checklist 走了一遍，再回来干活。

我被这个坑卡了一阵，后来翻官方 docs 才想通。想通之后，改动就一行。

坑就坑在这一行#

我回头翻我最早写的那版：

description: 帮助用户进行代码审查和代码优化

当时觉得人畜无害。现在品品：触发判断只看这行字。「代码」「优化」这俩词宽到什么程度，你自己想想——你提任何跟写代码沾边的话，它都觉得自己该出场。误触发 40% 一点不奇怪。

机制层：Claude 到底靠什么决定「该不该加载你」#

这里是很多教程都没讲清的一块，我翻官方 docs 把链条理了一遍：

  1. 每个 Skill 的正文（body）是懒加载的——只有被触发的那一刻才进上下文。这就是 Skill 比往 CLAUDE.md 里堆东西省 token 的原因；
  2. 但 Claude 得先知道有哪些 Skill 可用，所以启动时它会预载一张清单：每个 Skill 的 name + description；
  3. 触发判断 = 你的请求跟这张清单里的文字做匹配。

第 3 条是关键：description 不是写给人看的「功能介绍」，是给模型做路由判断的触发条件说明书。你写「帮助进行代码审查和代码优化」，等于告诉路由层「只要沾边就上」；你写「当用户明确要求 code review 或指出某段代码有 bug 需要审查时使用」，等于划了条明确的门。

我改成了这样：

description: 当用户明确要求 "code review" 或指出某段代码有 bug 需要审查时使用

改完误触发几乎归零。注意它的结构：触发动词（明确要求）+ 具体词面（“code review”、“bug”）+ 场景边界（某段代码）。不是形容词，不是功能清单。从那以后我写 Skill 有个习惯：先写「什么时候该触发」这一行，写不出来，说明这个 Skill 本来就不该拆出来。

我把 1% 预算当回事，因为我自己就超了#

docs 的排障章节给了个多数人会扫一眼就划走的参数：启动时预载的清单（所有 Skill 的 name + description）有字符预算，约为上下文窗口的 1%，超了就把 description 截断——截掉的正是路由判断要用的关键词。

我没当它是理论。拉了自己机器上的技能库数了一遍：70 个 Skill，description 加起来 3684 字符，均值 52，最长 105。按 200k 窗口算，1% 是 2000 字符左右——我已经超了 1.8 倍。也就是说，我技能库后半截的 description 现在在清单里就是残缺的，路由一直在拿不完整的信息做判断，这大概就是那 40% 误触发没修干净的原因之一。

所以我现在的纪律是量化的，不是「写宽不好」这种口头劝告：每个 Skill 的 description 压在一行以内，只留触发条件。70 个 Skill 这样写，预算还能剩一半。团队里 5 个人各写 10 个、description 还都写三行，预算直接爆——别等截断开始造成误触发才想起来数这个账。

顺手再省 20-30% token：角色锁定#

触发修好之后我又顺手加了一刀：在 Skill 的 prompt 开头放一句角色锁定，把行为面收窄：

你是一个严格的代码审查专家，只做以下三件事：
1. 找 bug
2. 给修改建议
3. 指出潜在风险
不要闲聊，不要解释背景。

实测这一步让单次任务的 token 用量降了 20%–30%——模型不再跑偏去解释它为什么不这么做。触发对了是省 token 的第一步，行为收窄是第二步，两步都是改那几行字，一行代码不动。

几点要说明白的事#

  • 40% 误触发 和 token 降 20-30% 这两个数字，出自 linux.sb 技术交流版区一篇精华帖（楼主 Jonhn），我没有在自己机器上重测，本文照引；你本地复现不出来属于正常，别拿我的数字当基准。
  • 1% 清单预算是官方 docs 原文（Claude Code Skills 文档 外部链接 ），但文中那组 3684/70/1.8 倍是本机实测——我把自己机器上的 70 个 Skill 的 description 全文拉出来逐个数了，200k 窗口下 1% ≈ 2000 字符，我超到 3684。窗口不同预算不同，你自己换算一下就知道该砍谁。
  • 本文结论基于 Claude Code 的 Skill 机制（Agent Skills 开放标准），遵循同标准的工具应同样成立，但我没在那边验证过。

你是哪一派#

  • A 派：description 写宽点好，宁可误触发也别漏 → 你算过误触发的账吗？它烧的是你每轮 token 和耐心，宽不是安全感，是慢性失血；
  • B 派：我 Skill 没几个，1% 预算够的，不用管 → 够用就没错；但团队里 5 个人各写 10 个，预算立刻爆，这条提前写进团队规范不亏；
  • C 派：我连 CLAUDE.md 都嫌长 → 那你更该学，一行 description 就是最小的可维护面。

你的 Skill 库现在多少个、description 都是什么风格？评论区晒出来，攒够一批我出个「Skill 触发率自查清单」续篇。

转给那个还在往 CLAUDE.md 里堆东西的同事——你堆的不是规范，是每轮都交的 token 税。

常见问题

Skill 和直接塞 CLAUDE.md 有啥区别？

CLAUDE.md 全程在线，写多了纯烧 token；Skill 的正文只在触发时加载，启动成本只有那行 description。高频刚需放 CLAUDE.md，低频专项流程放 Skill。

description 里的关键词怎么定？

抄你自己真实会说的话。你会说「帮我 review 这段」，description 里就得有 review 这个词面。用抽象名词（「代码优化」）不如用具体词（「code review」「bug」）。

触发得太窄（该出没出）了怎么办？

把漏掉的触发词补进 description，一次加一两个、观察一周，别一次堆五个——堆多了又回到误触发老路。

为什么官方 docs 说 Skill 多了 description 会被砍？

启动时预载的 Skill 清单（name + description）有字符预算，约为上下文窗口的 1%。超预算的 description 会被截断，被砍掉的恰恰是模型做路由判断需要的关键词。
