0.8B 模型、4GB 显存调成决策引擎：Unsloth 新能力里的两套数，我帮你对账了

Unsloth 给微调栈加了 Decision model 能力：把 Qwen3.5 0.8B 之类的小 LLM 调成'只出选项概率'的决策引擎，4GB 显存训得动。官方 X 帖前后写了两套数（20.7%→74.3% 与 30–37%→78%），我逐条对官方文档：这是聚合均值与单基准两种口径，拆开就能对齐。含全模型显存/时长表、复现设置陷阱（起手 r=16，复现要 r=64）。

October 10, 2026 · 3 min · 490 words · 梦兽编程 -  |  English

刷到这条的时候我先愣了几秒——官方自己的 X 帖，前后两套数。

@UnslothAI 2026-10-07 那条发布帖（“You can now train your own Decision model like Jev locally!"）：第一句写 “increased Qwen3.5 0.8B’s aggregate accuracy from 20.7% to 74.3% across 3 decision benchmarks - on just 4GB VRAM"；紧接下一段又写 “increasing downstream accuracy from 30–37% to 78%"。同一条帖、同一个模型、两个基线（20.7 vs 30–37）、两个上限（74.3 vs 78）——看着像算错账了。

我把官方文档整页拉下来逐条对：没算错，是两种口径，这套"流传数字对账"就是这篇的主线。

机制：Clef 头不写文本，只给选项打分#

官方文档的机制描述（引原文关键词）：LLM 把输入读一遍，一个**小头（same design as Cloudflare’s Clef）**看着 LLM 在"每个问题 × 每个选项"上的内部表示，直接给每个选项打分，一次前向把多个问题判完。

两个工程后果：

  • 不花输出 token：不用自回归解码，没有输出侧延迟，也就没有"JSON 写坏、解析失败"那类故障，结构化输出不再靠 parser 兜底；
  • 代价在输入侧：多挂的问题和选项会拉长序列，推理成本随问题数线性涨，决策模型不是零成本。

它本质是把"LLM 出答案"换成"LLM 出特征 + 小分类头出答案”。特征复用 LLM 的语义理解，判决交给便宜的确定性头，输出环节从"生成"降级成"打分”。

对账：官方两套数，拆口径就对齐#

把两个来源的数并排放：

来源 A：官方文档逐基准表（Qwen3.5-0.8B 行）：

基准 前 后
typed-decisions 36% 73%
BANKING77 7% 74%
CLINC150 19% 76%
混合留出（3000 行） — 78%

来源 B：官方 X 帖：“20.7% → 74.3%（3 基准聚合）” 与 “30–37% → 78%（downstream）"。

对账结果（我算的）：

  • 20.7% = (36 + 7 + 19) / 3 = 20.67 ≈ 20.7（三基准"前"的简单平均）
  • 74.3% = (73 + 74 + 76) / 3 = 74.33 ≈ 74.3（三基准"后"的简单平均）
  • 30–37%：文档原话"from 30–37% (which is roughly chance level)"——指的是各基准的"前"值区间（typed 36%、2B 是 33%，0.8B 那组落在这个带里），不是第三套数据
  • 78%：3000 行混合留出集（typed-decisions 2000 + BANKING77 500 + CLINC150 500）的准确率，和逐基准表的 Holdout 列对得上

结论是：同一条帖里的两组数，是"三基准简单平均"和"区间描述 + 混合留出"两种口径，没有谁算错。发布帖把两种口径挨着写、又没标口径，所以第一眼会读起来像自相矛盾。这就是这类流传数字最容易翻车的地方：数没错，错在没写口径。

全模型表：4GB 到 14GB 的显存梯度#

官方文档"所有模型"表（测试准确率 / 显存 / 训练时长，官方文档表格数据）：

模型 测试准确率 显存 训练时长
Qwen3.5-0.8B 78% 4GB 42 min
Qwen3.5-2B 81% 8GB 40 min
Llama 3.2 3B 79% 4.1GB 30 min
Gemma 4 E4B 77% 14.4GB 49 min
Laya（再微调） 77% 2.5GB 10 min

三行可以看细一点：

  • Llama 3.2 3B 只要 4.1GB 且 30 分钟——精度比 0.8B 低 1pp，显存省 1/4；
  • 2B 比 0.8B 高 3pp（81 vs 78），显存 2 倍；
  • Laya 再微调 2.5GB/10min：已有决策模型继续精调，比从头训便宜一个量级。

显存数字可以再交叉一层：Unsloth 的 Qwen3.5 微调页列 BF16 LoRA 显存 0.8B 为 3GB（同表 2B=5GB、4B=10GB），AMD 官方技术文章（2026-07）实测 Qwen3.5 在 3GB 显存的 AMD 卡上可训。决策表的 4GB（4bit 配方）与这两处 3GB（BF16 配方）口径不同但量级一致——4GB 显存能训 0.8B 决策模型，是三个独立来源交叉过的结论，不是单一口径。

训练数据配方（官方）：typed-decisions + 12 个来源（ag_news、arc、banking77、boolq、clinc150、commonsense_qa、mmlu、mnli、prompt_injections、snli、sst5、wanli）；测试 3000 行。测试集对训练数据做了去污染（decontaminated），这是 78% 可信的前提。

复现设置陷阱：起手 r=16，复现要 r=64#

复现设置还有一个坑，比口径问题更隐蔽：

  • 文档"Recommended settings”：4bit 底座、LoRA rank 16、lr 2e-4、2 epochs——这是给人上手用的 starter；
  • 但文档正文又说表格数字是 “fine-tuned with a Clef head using LoRA (r=64) for one epoch” 跑出来的；
  • 第三方报道也专门点了一句：复现表格数字要用 rank-64 配置，别拿 starter 默认值去对账。

文档示例代码块写的就是 r = 16, lora_alpha = 16（FastDecisionModel.get_peft_model 那段）。示例代码和表格数字不是同一套超参：照示例跑完，准确率到不了 78%。快速验证路线文档也给了：max_steps = 60，“Qwen3.5-4B reached 76% in 10 minutes on an L4”（L4 单卡，官方口径）。

训练数据集的结构#

LocalLLaMA/typed-decisions 是这套教程的数据底座，Hugging Face 上下载量 30,708 次。它分 5 个 config：all、agent_trace_observability、customer_service、invoice_processing、security_incidents。多数"决策任务"能直接落到某个现成子集上，不用拿全量混着训——比如做客服工单路由，customer_service 子集比 all 干净。

官方还注明：测试集对训练数据做了去污染（decontaminated）。

什么任务适合、什么不适合#

适合（答案落在有限集合里）：

  • 工单路由、意图分类（BANKING77/CLINC150 就是这类）；
  • 注入/风险筛查（训练源里有 prompt_injections）；
  • 一条输入判多个字段（docs 例子：同一张工单同时判"归哪个组 + 要不要退款”，一次前向出完）；
  • 文档打标、流程分支。

不适合：开放生成、需要解释链路的推理——这类还走 LLM 文本路径，决策头只是"出答案"的快捷方式。

第三方还提了一条：传统 encoder 分类器可能更省内存、更快，做选型时把这个 baseline 一并留着对照。决策模型的卖点是复用 LLM 的语义底座加结构化输出，精度上并不绝对领先。

生态位：Jev / Laya / Clef / Kev#

这个方向最近扎堆：

  • Jev / Laya / Clef：官方帖直接点名"train your own Decision model like Jev"——Jev 系（TypeSafe）走 API，Laya/Clef 是本地化分支，Clef 是 Cloudflare 的公开设计，Unsloth 这个头就是 Clef 同款；
  • Kev（GitHub jaredpalmer）：基于 Qwen3.5/3.8 的 0.8B–27B 决策模型家族，0.8B 能在笔记本跑，API 兼容 Jev 协议——和 Unsloth 教程是"预训练权重 vs 自己微调"两条路；
  • Unsloth 的差异化是：不给你权重，给你训练器（FastDecisionModel + DecisionTrainer 进开源包），训完接自家 Decision API。

数据来源与口径#

本文数字来自多个来源交叉：官方文档表格、官方 X 发布帖、第三方报道（alphasignal.ai，同表转引并标注 vendor-reported）。4GB / 42min / 78% 等训练结果属官方表格口径；显存另有两处交叉——Unsloth Qwen3.5 微调页的 BF16 LoRA 显存表（0.8B=3GB）与 AMD 官方技术文章（2026-07，实测 Qwen3.5 3GB 显存可训），三者量级一致。均值对账（(36+7+19)/3=20.7、(73+74+76)/3=74.3）是纯算术。

测试集按官方说明已对训练数据去污染（decontaminated）；“30–37% ≈ 随机水平” 是官方口径，各基准类别数不同，随机基线并不严格等于 1/类别数。

Unsloth 教程与表格迭代较快，本文以 2026-10-07 抓取版为准。

常见问题

Decision model 和普通 LLM 微调差在哪？

普通 LLM 输出是文本 token 流（要解码、可能写坏 JSON）；Decision model 加了一个小分类头（Clef 同款设计），LLM 把输入读一遍，头直接对每个选项打分出概率——不生成文本，没有输出 token 延迟，也没有解析失败。适合答案在有限选项里的问题（路由、意图、注入筛查）。

官方帖 20.7%→74.3% 和 30–37%→78% 到底哪个对？

都对，口径不同。20.7/74.3 是三个基准（typed-decisions 36→73、BANKING77 7→74、CLINC150 19→76）的平均值：(36+7+19)/3=20.7、(73+74+76)/3=74.3。30–37→78 是文档原话‘30–37%（约随机水平）拉到最高 78%’，78% 是 3000 行混合留出集的准确率。正文有逐条对账。

4GB 显存真的够？

官方决策模型表里 0.8B 微调峰值 4GB（42 分钟）、Llama 3.2 3B 4.1GB——4bit 底座 + LoRA 的路子。显存不是单一来源：Unsloth 的 Qwen3.5 微调页列 BF16 LoRA 显存 0.8B 为 3GB，AMD 官方技术文章（2026-07）也实测 Qwen3.5 能在 3GB 显存上训练。三个来源一致，4GB 够是交叉过的结论。

复现要按文档推荐的设置吗？

别。文档起手推荐 4bit + r=16 + lr 2e-4；但官方表格数字是 r=64、单 epoch 跑出来的，文档自己也注了：要复现表里数字用 rank-64，别拿 starter 默认值对账。

什么任务适合？

答案在有限集合里的：工单路由、意图分类、注入筛查、文档打标、多问合判。开放生成、要解释的推理不适合——这类任务还走 LLM 文本生成路径。传统 encoder 分类器可能更省更快，做选型时保留这个 baseline。
