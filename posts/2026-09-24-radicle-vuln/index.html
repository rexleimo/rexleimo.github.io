Radicle 全线沦陷：Noise 握完手就裸奔，私有仓库默认视为已泄露

9 月 23 日 Radicle 官方披露：全部已发布版本的节点网络流量不加密、握手身份可伪造。Noise XK 握手 32/32/48 字节之后，数据直接写进裸 socket。官方建议：私有仓库立即停播，已走过的链路视为公开。

September 24, 2026 · 3 min · 450 words · 梦兽编程 -  |  English

9 月 23 日，Radicle 官方在 radicle.dev 发了一篇罕见的公告，标题直白到刺眼：Disclosure of Vulnerability in the Network Protocol 外部链接 。HN 上 125 分、49 条评论，评论区几乎一边倒：“去中心化 Git 的 P2P 层连个 TLS 都没有？"——答案是比这更糟：不是没有 TLS，是握完手之后根本没人管。

先给结论，三个：

  1. 全部已发布版本（截至 1.10.3）的 Radicle 节点，握手之后的所有流量走的是裸 socket 明文；
  2. 连接握手还能伪造对方的 Node ID，私有仓库的白名单防不住直接冒充；
  3. 官方建议只有一句硬话：把已经通过网络传过的私有仓库，全部视为已泄露，密钥该轮换就轮换。

这篇把三件事讲清楚：漏洞到底在哪一行代码、你现在能做什么（官方给的纪律清单，逐条列）、以及为什么修复必须是 breaking 大版本。

两个漏洞，一个攻击链#

官方披露列了两个独立漏洞，分开看都不算新鲜，叠起来才是要命的：

#漏洞报告人 / 日期后果
1握手后流量全明文，无传输加密Konstantinos Maninakis，2026-06-24路径上任何观察者（ISP、中转、relay）可读全部对象
2握手对端身份可伪造（impersonation）cryptocode，2026-08-12攻击者冒充白名单 Node ID 直接拉取私有仓库

第二个漏洞单独打其实打不动：白名单不公开，路径外的攻击者得先猜到某个合法的 Node ID 才能冒充，猜一个 20+ 位的 ID 不现实。但把两个放一起，攻击链就通了——路径上的观察者天然看得到连接两端的 Node ID，而这两个 ID 正常情况下都在对方的白名单里。先蹭路径读明文，顺手记下 ID，之后摘下来直接拿着 ID 连你的节点拉整个私有仓库。官方原文的原话：

The realistic threat is anyone on the path between your node and the node it syncs with, and no setting or allow-list protects against them.

（现实的威胁就是你和它同步的节点之间的路径上任何人，没有任何配置或白名单能挡住他们。）

完整性倒还是有的：Git 对象是内容寻址的，ref 上有签名，篡改会在存储层被检测到。所以这个披露只谈机密性，不谈完整性——这条边界官方写得很干净，也说明他们没想把话说满。

根因：is_complete() 这一行条件，语义刚好写反了#

细节全部来自报告人 Maninakis 的源文 外部链接 （他做的是把 Radicle 节点跑进浏览器标签页的 Grove 项目，逐字节重写了传输层）。Radicle 的连接开头是一个 Noise XK 握手——和 WireGuard 同一协议族，三跳完成：

  1. 发起方：一次性公钥 + 与对端长期公钥做 Diffie-Hellman，32 字节出；
  2. 响应方：自己的一次性公钥 + 第二次 DH，32 字节回；
  3. 发起方：自己的长期公钥，加密在共享密钥下，48 字节出（32 字节密钥 + 16 字节认证 tag）。

到第三跳落地，双方各自推导出对称密钥对——Noise 管这叫 split，握手全部的意义就在这里。问题是从这之后开始：radicle-node 的 session.rs 里，Protocol 这个泛型包装器对写操作只检查一个条件——

// crates/radicle-node/src/reactor/session.rs，Radicle 1.9.1（1.10.3 同款逻辑，字段改名）
impl<M: StateMachine, S: Session> Write for Protocol<M, S> {
    fn write(&mut self, buf: &[u8]) -> io::Result<usize> {
        if self.state.is_complete() || !self.session.is_established() {
            log::trace!(target: M::NAME, "Passing writing to inner session");
            return self.session.write(buf);   // ← 直接写裸 socket
        }
        // ... 握手阶段的消息 ...
    }
}

buf 就是节点接下来要说的一切：gossip、ref 通告、私有仓库的 Git pack。这个分支的两个触发条件是早了（底层 socket 还没建立，没得加密）和晚了（握手完成，正是该开始加密的时刻）——两个极端走的是同一个分支，结果都是明文。代码自带的日志名说得毫不客气：“Passing writing to inner session”，直译就是"把写透传给内层会话”。

怎么错的？同一套 Protocol 还包着 SOCKS5 会话：SOCKS5 语义下，代理握手结束就该让路、透传字节，这个分支对它来说是对的；对 Noise 来说，握手结束才是真正工作的开始——同一个 is_complete()，两种完全相反的含义，只有一套实现，实现的是 SOCKS5 那一半。另外 noise-framework 0.4.1 明明算出了两个方向的 cipher state 存在 NoiseState::Active 里（字段还是 public 的），但只暴露了 get_handshake_hash 和 get_remote_static_key 两个访问器——节点拿到的是"握手成功了"，拿不到密钥本身，加密循环压根没写。（Maninakis 的文章里还附了完整的修复补丁：分片、帧长前缀、encrypt_with_ad，都齐了。）

一个旁证：Maninakis 抓包生产 seed，握手之后第一个字节、偏移 32，是 ASCII 的 r——rad，节点通告的开头。他原话是"I didn’t believe it at first"。

你现在能做什么：官方纪律清单#

官方公告给的 workaround 是四条，我按执行顺序排成表（前两条是"止血"，后两条是"善后"）：

动作命令 / 操作说明
列库存rad ls --private --all列出存储里所有私有仓库
停 seeding逐仓库 rad block <RID>（不要用 rad unseed）默认 seeding 策略是 block，rad unseed 回落默认即可；你改过 allow 的话 unseed 后会继续服务。rad block 显式封锁，怎么配都生效
停节点rad node stop彻底不服务任何仓库
轮换密钥凡是在私有仓库里放过的明文凭据 / token / key，全部视为已公开已传过的数据没有任何操作能撤回；Tor / VPN 挡不住身份伪造，别指望它

三条官方写死的边界，逐字认账：

  • rad block 只停你的服务，不删本地副本（副本在 $(rad path)/storage/<RID 去掉 rad: 前缀>），也够不到白名单同伴已经拉走的副本——那些节点有一模一样的漏洞，得让他们也 block；
  • 已经同步过网络的数据，视为已披露，没有 undo；
  • node.proxy 指向 Tor 不等于机密性：它只是把你的明文流量送到 Tor 出口节点，出口运营者照样读得懂，onion 同伴还得单独配 node.onion。

顺带一提，同一家（cyphernet-labs）的 Grove 走的是同一套线上字节，公告里 Maninakis 也点了名。

修复为什么必须是 breaking 大版本#

方向已经定了：把自研传输层整个换成 iroh 外部链接 ——基于 QUIC/TLS、开放标准的 P2P 网络栈，顺带拿到 NAT 穿透。公告原话是漏洞"给了我们更足的理由推进迁移"。

为什么不能小版本热修？两个原因叠在一起：线上协议没有版本协商能力 + 修复本身线上不兼容。也就是说，修完之后的节点和没修的节点互相听不懂，网络会直接裂成两个孤岛。官方的处理方式是"把破坏性集中在网络端，存储布局保持兼容"——仓库数据不用迁，但 1.x 网络里的节点升级 2.0 之后，就和 1.x 同伴失联了。

这是 P2P 系统绕不开的原罪：中心化服务可以灰度、可以双跑、可以按连接协商，P2P 网络里每个节点都是自己的服务端，升级节奏没人管得了。Radicle 选择在修复前发这个披露，理由也写在公告里——“你今天就该行动，后面任何修复都撤销不了已经发生的暴露”。这个姿态在开源圈不常见，值得记一笔。

诚实声明#

按惯例交代误差来源：

  • 本文没有在本机跑 Radicle 节点复现明文传输（没有部署 1.x 节点环境），字节级细节（32/32/48、偏移 32 的 rad、session.rs 源码）全部转引自 Maninakis 源文与 Radicle 官方披露原文，行号按 1.9.1 裁剪版，1.10.3 是"字段改名但条件相同"；
  • 修复侧只有官方 roadmap（换 iroh、breaking major），没有时间表，本文不预测发布日期；
  • “私有仓库默认视为已泄露"是官方建议口径，不是数学结论——它取决于你的同步链路实际经过了多少方，本文不替任何一条具体链路做风险评估。

常见问题

公开仓库受影响吗？

影响小。公开仓库的数据本来就要给所有人，路径上的监听者读到的东西没有增量。真正出事的是私有仓库：明文传输 + 可伪造的白名单身份，两者叠加意味着私有代码默认已对路径上的任何人公开。

挂 Tor / VPN 能解决吗？

解决不了身份伪造。官方披露原文写得很清楚：Tor、I2P、VPN 只能让路径监听者读不到明文，但伪造白名单 Node ID 的攻击不需要你在路径上——攻击者直接拿着伪造的 ID 连你的节点拉取私有仓库即可。官方原话是这类手段'不是足够保护'。

rad unseed 和 rad block 有什么区别？

rad unseed 只是移除该仓库的 seeding 策略，节点回落到默认策略——如果你把默认改成了 allow，unseed 之后你的节点照样在服务这个仓库。rad block 是显式封锁，节点优先检查 block 列表，与默认策略无关。官方推荐一律用 rad block。

修复版本什么时候有？

官方说 work in progress，但没有日期。方案是整体换掉传输层（从自研 Noise 协议换成 iroh，基于 QUIC/TLS），因为线上不兼容，必须大版本 breaking release——1.x 和 2.x 节点升级后互相连不上，网络会分裂成两个孤岛。

本地没同步过的私有仓库安全吗？

存储层是安全的：Git 对象内容寻址 + signed refs，攻击者伪造不了仓库内容，只能读。风险全部在'传过'这一步。没在网络上同步过的私有仓库，本地副本本身不受影响。
