LLM 写 Rust 的 3 个翻车点，第 3 个是你的错觉

让 LLM 生成 Rust，看着都对，跑起来才发现三个高频翻车点。我把这三个点在本机 2 核 EPYC + rustc 1.99.0 + -O 上各打一组数字：热路径 format! 分配税 113ms、无脑 .clone() 在 80MB 量级上多 60ms、而「迭代器链一定比手写循环慢」这条玄学，本机实测在 -O 下打平。第 3 个是你的错觉。

October 14, 2026 · 2 min · 332 words · 梦兽编程 -  | 

我最近让 LLM 生成 Rust 的时候，有个很固定的坏习惯：它给的代码我基本直接跑，不复查性能。直到有一段热循环在我机器上卡住，我才回头把它生成的 Rust 拆开看了三遍——发现里面躺着三个高频翻车点，前两个是真的坑，第三个是你（和我）都有的错觉。

这篇把这三个点在我机器上各打一组数字。机器、版本、优化级别全写清，你能自己复现。

翻车点①：热路径里塞 format!，藏着 113ms 的分配税#

LLM 生成代码最上瘾的一句话，就是 let s = format!("val={}", x)——读着特舒服，像人话。但它是 每调用一次就构造一个临时 String、触发一次堆分配。

我把它塞进 200 万次的热循环里，跟一个纯算术对照（同样循环、不分配）放一起打：

// LLM 常生成的样子
for _ in 0..2_000_000u64 {
    let s = format!("val={}", acc);   // 每次 new 一个 String + 堆分配
    acc += s.len() as u64;
}
// 本机实测：约 113 ms
场景本机实测（-O，200 万次）
循环内 format!≈ 113 ms
纯算术对照（不分配）< 0.1 ms（被 -O 压到不可测）

「不可测」不是 0，是打印精度下限——对照那档被优化到几乎不占时间。两条摆一起，format! 的分配税是量级级的，不是几个百分点。

怎么改：热路径用 write! 到一个预分配的 buffer，或者别在循环里造临时 String：

use std::fmt::Write;
let mut buf = String::with_capacity(64);
for _ in 0..2_000_000u64 {
    buf.clear();                      // 复用容量，不再堆分配
    let _ = write!(buf, "val={}", acc);
    acc += buf.len() as u64;
}

翻车点②：一个无脑 .clone()，80MB 量级上多 60ms#

第二个坑是 LLM 把借用签名抄歪。函数本来的意图是 fn f(v: &Vec<u64>) 借用着看，它一不留神写成按值传再 .clone()，或者把参数直接 clone 了一份。

我在 10M 个 u64（= 80MB）这个量级上打了两档：

场景本机实测（80MB）
借用 iter().sum()≈ 3 ms
.clone() 80MB 再 sum≈ 64~66 ms

单点税 60~63ms，20 倍于借用。80MB 已经是中等量级了——换成几百 MB 的数据、或者 clone 落在每帧/每请求的热路径里，这个数字会被放大到肉疼。

这类坑 Clippy 有现成的：redundant_clone、clone_on_ref。问题是 LLM 生成代码时不自检，它只保证「编译得过」，不保证「没多拷一份」。

翻车点③：「迭代器链一定比手写循环慢」——这条是错觉#

前两个是真的坑。但第三条，是最常被转发的「经验」：

「.filter().map().sum() 这种迭代器链比手写 for 慢，性能敏感的地方要改成手写循环。」

我专门打了两档，同一逻辑、-O、各 20 轮取中位，跑了两遍：

场景本机实测（2000 万次）
迭代器链 filter().map().sum()≈ 5.2~5.3 ms
手写 for 循环同逻辑≈ 5.0~5.5 ms
相对差一遍 +3%、一遍 −4%（在噪声里）

结论：-O 下迭代器链和手写循环打平。 单步操作被循环合并、部分向量化抹平了，±4% 的抖动是这台 2 核机器的测量噪声，不是「链慢」。这条流传说法，被本机数字证伪了。

真正的差别不在性能，在可读性和零成本抽象——迭代器链是「零成本」的，-O 下它不付额外代价。你该用哪个，看的是哪段代码更好读，不是哪个「听起来更快」。

为什么 LLM 不自己躲开这些坑#

把三个坑的根因收拢一下：

  • format! 分配税、无脑 .clone() —— 这两个是 Clippy 能静态抓的。cargo clippy 一跑，redundant_clone 直接红。但 LLM 生成完不自己跑 Clippy，它交付的是「编译过」的代码。
  • 迭代器链慢 —— 这条根本没有坑。它本来就是对的，是「流传的经验」错了。这种你没法让工具抓，只能靠本机打数字证伪。

所以最省的组合就一句话：LLM 生成 + cargo clippy 兜底 + 热路径自己压一遍微基准。前两个坑让 Clippy 挡，第三个坑别信玄学。

哪些是我没测的#

把边界划清：

  1. 本机 2 核 EPYC + rustc 1.99.0 + -O：以上是这套环境的中位值。换机器、换 -O0，绝对数字变，结论方向不变（format! 分配税、clone 深拷贝税都随量级放大，迭代器链 vs 循环在 -O 下打平）。
  2. -O0 下迭代器链 vs 循环的差距没测：那档（关闭优化）两者差距会拉开，是另一个故事，这篇只钉 -O 稳态。
  3. 数字口径：各 20 轮取中位、black_box 防优化、Instant 计时，跨两遍跑量级一致（113ms / 64ms / 5.2ms），可复现。

脚本 rust-flipbench3.rs，三步：

rustc -O rust-flipbench3.rs -o /tmp/rfb3
/tmp/rfb3

你是哪一派？评论区对一下：

  • A 派：AI 生成的 Rust 一律先过 cargo clippy，抓出 format!/clone 才敢进热路径；
  • B 派：热路径根本不让 LLM 写，让它写外围胶水，核心循环手写；
  • C 派：迭代器链那档你们也信了半年？本篇数字一出，直接把手写循环那版删了。

你被哪个坑咬过？攒够一批我出续篇：把 -O0 和真热路径（tokio 任务里）的迭代器链差距补全，再测无优化档。

转给那个**「AI 写的 Rust 编译过就能上生产」的同事**——它编译得过，不代表没多拷 80MB。微信搜索「梦兽编程」。

常见问题

热路径里的 format! 到底慢在哪？

format! 每轮都会构造一个临时 String、触发堆分配。本机 200 万次循环内嵌 format! 单档实测约 113ms，去掉分配的纯算术对照被 -O 压到不可测（<0.1ms）。热路径要改用预分配 buffer 的 write!，或避免在循环里构造临时 String。

一个无脑 .clone() 能浪费多少？

LLM 常把借用签名 fn f(v: &Vec<u64>) 抄成按值 + .clone()。本机 10M 个 u64（80MB）量级实测：借用 sum 约 3ms，clone 再 sum 约 64~66ms，单点税 60~63ms。热循环里这是量级级差距。Clippy 的 redundant_clone / clone_on_ref 能抓，但 LLM 生成时不自检。

迭代器链真的比手写循环慢吗？

这是最常被传的一条，但本机 -O 下打平：filter().map().sum() 与等逻辑手写 for，各 20 轮取中位都在 5.0~5.5ms，两遍跑一轮快 3%、一轮慢 4%——差异在噪声里。-O 的单步操作被循环合并抹平，真正差别在可读性，不在「链慢」。这条被本机数字证伪。

这些数字能复现吗？

能。复现脚本 rust-flipbench3.rs（本机 2 核 EPYC、rustc 1.99.0、-O、black_box、各 20 轮取中位）：rustc -O rust-flipbench3.rs -o /tmp/rfb3 && /tmp/rfb3。数字随工作集量级放大，结论方向不变。

为什么 LLM 不自己躲开这些坑？

LLM 生成的是「看起来对」的代码，不跑 Clippy、不压热路径、不量分配。前两个坑（format!、clone）是 Clippy 能静态抓的，第三个坑（迭代器链）根本没有——它本来就是对的。让 LLM 生成 + 本地 cargo clippy 兜底，是目前最省的组合。
