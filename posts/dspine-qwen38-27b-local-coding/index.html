DSpine 本地编程提速 3.87 倍？27B、128K 和显存这道关要先看懂

腾讯 DSpine 用并行投机解码加速本地大模型。本文核对官方论文、Qwen3.8-27B 模型卡和 RX 7900 XTX 第三方实测，讲清 3.87 倍、186 tok/s、128K KV Cache 与高并发显存代价。

November 25, 2026 · 2 min · 299 words · 梦兽编程 -  | 

先别换显卡。你卡住的可能不是算力，而是推理方式。

2026 年 11 月 25 日，玩客笔记公开了一组单卡实测：在同一张 RX 7900 XTX 24GB 上跑 Qwen3.8-27B IQ4_XS，同一段 32K 上下文的长代码任务，普通推理用了 66.97 秒，MTP 用了 35.34 秒，腾讯开源的 DSpine 只用了 17.15 秒。持续解码速度从 41.71 tok/s 提到 161.18 tok/s，总耗时压到原来的约四分之一。

这组数字很诱人，但先把口径说清楚：它是第三方在特定硬件、特定 llama.cpp 适配分支和特定任务上的结果，不是腾讯对每台机器的统一承诺。官方模型卡在 SGLang、BF16、并发 8 的条件下，给出的 WorkBuddy Code 端到端吞吐是 2.71 倍到 3.18 倍。两组数字不冲突，只是测试对象和运行方式不同。

所以这篇不打算把“3.87 倍”再喊一遍。我们更关心三个问题：DSpine 到底改了什么，为什么写代码比写散文更吃香，以及你把上下文拉到 128K 以后，显存会不会先扛不住。

DSpine 不是把草稿模型拉长，而是让预测互相接上#

普通自回归推理像一个字一个字往外挤，每个 token 都要等前一个定下来。投机解码先让小模型猜一段，再让目标模型一次批量验证。猜得越准，一次能放行的 token 越多，等待轮次就越少。

问题也在这儿。并行草稿一次猜一整块时，各个位置并不知道前一个位置最后会选什么，单看都合理，连起来却可能前后矛盾。目标模型按前缀顺序验收，只要中间错一个，后面猜得再多也可能一起作废。

DSpine 的做法是把“前一个位置正在猜什么”从第一层就喂给后一个位置。每一层都做一次相邻因果注入，让依赖关系随着网络深度往下传；等前一个 token 真正定下来，再用 transition cache 把相邻候选的分数并行算好。换句话说，它不是先各自猜完再补救，而是边算边把前后接起来。

官方论文里，Qwen3-8B 在温度 0、七项数学代码聊天基准上的平均接收长度从 DFlash 的 3.77 提到 4.82。这个指标的意思是每轮验证平均能推进多少 token，越高越好。注意，这是 Qwen3-8B 的论文数据，不是上面那组 27B 单卡实测。

代码特别适合这套机制。括号、变量名、函数签名、JSON 字段和工具调用都有强结构，前一个位置猜对以后，后一个位置更容易跟上。自由中文创作就不同了，话题一转，草稿模型连续猜中的概率会掉。玩客笔记那组样本里，普通推理是 42.50 tok/s，MTP 是 54.69，DSpine 反而降到 39.33。这个样本不能代表所有写作任务，但足够说明一件事：DSpine 是任务型加速器，不是万能外挂。

还有一个常见误解要说清。投机解码的草稿候选必须经过目标模型验证，算法层不是为了速度改答案；但如果你为了省显存把 KV Cache 量化成 Q4，那是另一笔有损的账，不能混在一起说“完全无损”。

真正难的不是 27B，是 27B 加上 128K#

短代码跑得快，不代表读整个仓库也快。上下文拉到 128K 以后，KV Cache、草稿状态和计算工作区会一起挤进显存。加速模块本身也吃资源。

玩客笔记那组 120931 token 长文档测试很典型。主 KV 保持 Q8 时，首字延迟达到 1014.5 秒，总耗时 1018.55 秒，几乎十七分钟。把主模型 KV 改成 Q4、草稿 KV 保留 Q8 以后，首字延迟降到 224.66 秒，总耗时 225.05 秒，三项细节检索仍然全对。

但别急着把“Q4 KV”当成默认答案。它是有损量化，这次答对不等于所有任务都无差别。日常写代码更稳的做法是先把上下文和 KV 分档：常用的 64K 保持 Q8，真正需要吞十万字文档时再临时切 128K 加 Q4，并且用自己的问题验证准确率。

高并发服务还会遇到另一堵墙。vLLM 合并 DSpine 的讨论里，评审者指出在 K=15 的配置下，GDN 状态约为 2.7 GiB 每请求，而无投机解码约为 0.175 GiB，接近十六倍。这个观察来自 B200 FP8 的特定配置，不能直接套到每张卡上，但它提醒我们：单人本地用着舒服，不等于几十路并发还能线性扩展。

想试 DSpine，按这四步走更不容易翻车#

1、先选对引擎。官方 README 当前明确给出 SGLang、vLLM 和 Apple Silicon MLX 路径。视频里的 llama.cpp 方案来自 Ajay9o9 的社区适配分支，能用，但要把它当社区路径，别拿 SGLang 的参数直接拼到 llama.cpp 上。

2、先确认显存账。Qwen3.8-27B IQ4_XS 主模型本身约 14.25GB，再算上草稿、KV 和缓冲，第三方测试在 32K 的峰值约 18.9GB。16GB 显存别硬上 27B 加 DSpine，掉进系统内存以后，快反而会变成慢。

3、拿真实长代码测，不拿一百 token 的短跑骗自己。至少记录首字延迟、总耗时、持续 tok/s 和生成结果能不能跑。那组实测里，105 token 的短工具调用冲到 212.65 tok/s，但真正写项目要看数千 token 的持续输出。峰值是乐趣，总耗时才是体验。

4、按任务开关。写代码、生成 JSON、调工具，优先 DSpine；自由写作、开放 brainstorm，普通推理或 MTP 可能更合适。上下文、并发或采样参数变了，就重新测，别沿用上一张显卡的结论。

如果你已经有一张 24GB 显卡，又在本地跑 Qwen3.8-27B 写代码，DSpine 值得认真试一次。它未必让你少买一张卡，但很可能让你先把现有显卡用明白。反过来，如果你只有 16GB，或者要做高并发服务，先算显存和 KV 预算，比追 186 tok/s 更重要。

几个直接回答#

DSpine 会降低模型质量吗？在正确的无损验证实现里，草稿候选仍要由目标模型验收，加速本身不以改答案为代价。但 Q4 KV 量化是有损的，要把这两件事分开验证。

DSpine 官方支持 llama.cpp 吗？官方 README 当前主推 SGLang、vLLM 和 MLX。llama.cpp 的 DSpine 方案来自社区适配分支，部署前要确认分支版本和参数，不能默认官方主线已经原生支持。

186 tok/s 是常态吗？不是。那是第三方一次 6673 token 长代码的峰值。同一篇实测里，真实长代码任务的持续速度是 161.18 tok/s，短任务还能更高，评估体验要看总耗时。

16GB 显存能跑 Qwen3.8-27B 加 DSpine 吗？在引用的第三方配置里，32K 峰值已经约 18.9GB，16GB 会明显占用系统内存并掉速。更实际的选择是降低模型规模或量化档位。

128K 一定要用 Q4 KV 吗？不一定。64K 加 Q8 更适合日常编程；128K 加 Q4 是长文档应急方案，用之前要拿自己的检索或问答任务验证。

信源与延伸阅读#

本文的事实核对截至 2026-11-25。机制与生态来自腾讯 DSpine 官方仓库、arXiv 论文和 Hugging Face 模型卡；3.87 倍、186.10 tok/s、128K 和自由写作对照来自玩客笔记的第三方实测；高并发显存观察来自 vLLM PR #67094 的合并讨论。文中没有把第三方数据写成梦兽编程自测。
