Rust vs Go 写微服务，"延迟差 3 倍"是假的

技术圈流传"用 Rust 重写服务，性能快 3 倍"。我把同一个 CRUD 微服务用 Rust（axum）和 Go（标准库 net/http）各写一版，放在同一台 2 核机器上压 6 组：延迟没有任何一档差 3 倍，中并发时 Go 的 p99 反而更低，Rust 真正拉开 2-3 倍差距的是内存。数据、代码、压测脚本全部开源可复现。

October 3, 2026 · 2 min · 347 words · 梦兽编程 -  |  English

技术圈有个流传很广的说法：“用 Rust 重写服务，性能直接快 3 倍。” 我最近拿它反复横跳，越听越不对劲——快 3 倍？快在哪？延迟？吞吐？内存？

我不打算拍脑袋。直接把同一个 CRUD 微服务用 Rust（axum）和 Go（标准库 net/http）各写一版，放在同一台机器、同一份负载下压，把延迟、吞吐、内存全测出来。数据、代码、压测脚本全部开源，文末可复现。

先剧透结论，正文一条条拆：

  • 延迟（p99）差不到 3 倍，任何并发档都没有——最大一档相对差 <20%，而且互有胜负。
  • 中并发（100）时 Go 的 p99 反而比 Rust 更快（23.2ms vs 26.0ms）。
  • Rust 真正实打实的优势在内存：稳态 RSS 大约是 Go 的 1/2 ~ 1/3。
  • 两边在高并发下都崩了（p99 从 0.4ms 涨到 100ms+），瓶颈是锁和调度，不是语言本身。

方法：怎么保证两边公平#

一台 2 核 / 7.8G 的 Linux 机器，两个服务逻辑逐行对齐：

Rust 版Go 版
框架axum 0.8 + tokio + serde标准库 net/http
优化release：opt-level=3, lto=truego1.27.1，GOMAXPROCS=2 GOGC=100
端点GET /api/items/item-0（读内存 map）同左

负载是纯 GET 读路径：服务启动时往内存 map 塞 1000 条数据，压测打其中一条。选 GET 是为了隔离"语言/框架层"的差异，不掺数据库、不掺写竞争（POST 会让两边的读写锁竞争更明显，对 Go 更有利，但会把结论搅浑，正文我会单独说）。

压测有个插曲：这台机器 GitHub 被墙，装不了 hey 这类现成工具。我索性自己用 Go 标准库写了一个压测器（并发 worker + 分位数统计），压测器自己固定 GOMAXPROCS=1 只占 1 核，让两个被压服务一视同仁。工具、代码全开源。

每档并发（c = 10 / 100 / 500）先 warmup 2000 请求，再正式跑 n = c×100，取 p50/p90/p99、吞吐、错误率，并采样稳态 VmRSS。

为什么"3 倍"是假的#

把上面三张表放一起看，“Rust 快 3 倍"这个说法没有一个数字撑得住：

  1. 延迟差不到 3 倍。 同并发下 p99 的相对差距全程 <20%，而且胜负在反复横跳——c=10 Rust 快，c=100 Go 快，c=500 Rust 又略快。这不是"稳定领先 3 倍”，这是同一量级、噪声级别的差距。
  2. 中并发 Go 更快（23.2 vs 26.0ms）不是偶然。 Rust 版用的是 RwLock，读端多、写端一进来就全拦。纯读负载下它本应占优，但在 c=100 这个档，Rust 的吞吐（18833）比 c=10（23226）还掉了一截——读锁本身成了瓶颈。Go 的 RWMutex 在这个场景反而更平滑。语言快不快，要看你用了什么锁、怎么调度，不是"Rust 三个字"。
  3. 两边在 c=500 都崩了，这才是重点。 吞吐从 c=10 的 ~2 万 req/s 掉到 c=500 的 ~5 千 req/s（4 倍跌落），p99 从 0.4ms 飙到 100–180ms。Rust 和 Go 一起崩，说明这个瓶颈来自共享的那把读写锁 + 2 核机器的调度，跟"选哪门语言"没关系。

一句话：读路径上，axum 和 net/http 是同一个量级；把"快 3 倍"算到 Rust 头上，是偷换了这个量级里的噪声。

Rust 真正拉开差距的地方：内存#

延迟打不出 3 倍，但内存打出来了——低并发稳态下 Rust 4.4MB，Go 13.4MB，正好 3 倍；并发越高差距收窄（锁和临时对象占大头），但 Rust 全程是 Go 的 1/2 ~ 1/3。

这才是 Rust 在微服务里最该被记住的卖点：单位内存能塞下更多副本。同样预算下，Rust 服务可以跑得比 Go 更密，云边/IoT/高并发小内存场景尤其明显。而且那个 3 倍数字，是内存不是延迟——标题里的"3 倍"，其实该记在内存账上。

什么时候选 Rust，什么时候 Go 够用#

  • 选 Rust：内存敏感（高密度部署、云边、嵌入式服务）、需要确定性延迟的写密集服务、团队本来就在 Rust 栈上。内存 2–3 倍的优势是真金白银。
  • Go 够用：常规 CRUD / 网关 / 后台服务，团队熟悉度、生态、招聘成本摆在那儿，读路径上 Go 的性能不比你想象的差（本文 c=100 就是 Go 赢的）。为"玄学的 3 倍"硬上 Rust，性价比不划算。

选型看的是你的瓶颈在哪：瓶颈是内存 → Rust；瓶颈是团队速度 → Go 更稳。

常见问题

Rust 真的没有比 Go 快 3 倍吗？

在我这台 2 核机器上、纯 GET 读路径下，任何并发档的 p99 差距都小于 20%，而且胜负反复横跳——并发 100 时 Go 的 p99（23.2ms）反而比 Rust（26.0ms）更低。'快 3 倍'在延迟上没有一个数字撑得住。

那 Rust 的优势在哪？

内存。稳态 VmRSS 低并发时 Rust 4.4MB、Go 13.4MB，正好约 3 倍；全程 Rust 是 Go 的 1/2 到 1/3。同样预算下 Rust 服务能跑得比 Go 密，云边、高密度部署、内存敏感场景尤其明显。

为什么高并发两边都崩了？

并发 500 时两边 p99 都从 0.4ms 基线飙到 100-180ms、吞吐跌 4 倍，Rust 和 Go 一起崩。瓶颈是共享的读写锁加 2 核机器的调度，跟'选哪门语言'关系不大。

这些数字能复现吗？

能。两个服务源码（svc-rust、svc-go）、自研压测器（bench-cli，纯 Go 标准库，因 GitHub 被墙装不了 hey）、压测脚本（run-bench.sh）和全部原始日志都开源在仓库 bench/ 目录下。
