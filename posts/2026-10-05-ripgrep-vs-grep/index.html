「ripgrep 比 grep 快几倍」——我把 4GB 语料喂完，第一个发现是这台机器上测不出倍数

'rg 快 3 倍'这类说法在我这台共享 2 核 EPYC 上测不稳：同一格 grep 扫 3.4GB，三个会话我测出 0.01s / 2.85s / 4.05s，漂 40 倍。能钉死的只有两层：单文件热态 grep 0.003s vs rg 0.011s（rg 的固定启动成本），以及 rg 默认只搜 55/106 个文件（数文件不计时，零 I/O 噪声）。

October 5, 2026 · 2 min · 309 words · 梦兽编程 -  |  English

命令行圈最稳的流传说法之一：“ripgrep 比 grep 快”。我在这台 2 核 EPYC 上把 4GB 语料喂了个遍，第一个发现不是谁快多少，而是"谁快多少"在这台机器上根本测不出来：同一格 grep -rc 扫 3.4GB，我三个不同会话测出 0.01s / 2.85s / 4.05s——漂 40 倍，而且三次都做了命中数校验、都在跑前记了 load。共享 2 核切片 + 非独占 I/O 带宽，“rg 快 X 倍"这类绝对倍数只在独占机器 + 固定负载下才是一个量；其余时候它是一个分布。

所以这篇写的是能测稳的两层，每层给全命令：① 单文件热态固定成本——grep 0.003s vs rg 0.011s，rg 的启动税（regex 编译 + 目录 walker + 线程池）在小负载上就是 3.7 倍差距，5 轮中位、命中校验、同会话跑完；② “搜得少”——数文件不计时，零噪声：混合目录 rg 默认搜 55 个文件，全开 106，字节口径 1.17MB vs 12.8MB，11 倍。

先把"测不出"这件事钉死：同题三会话，40 倍漂移#

同一台机器、同一格语料（3.4GB / 100 个 34MB 文件）、同一命令，都做了命中数校验（3000 行一致）、跑前记 load：

会话loadgrep -rc 耗时状态
22:470.14（最安静）2.85s热缓存、安静
23:100.474.05s热缓存、稍忙
次日偏高0.01s当时当"异常"复核过三次

三次都在页缓存命中状态跑，命中数一致，唯一变量是这台共享切片上别人在用什么。那格 0.01s 意味着 340GB/s 读带宽——本机 I/O 物理上限够不到，大概率是 I/O 调度层面把读请求全走了缓存旁路/丢失的假像（我没逐字节核验那次，只核验了命中数）。结论只有一条，但足够：在这台机器上，I/O 带宽类计时的绝对值不可信，任何"快 X 倍"都会随负载翻转。

这不是免责——它直接推翻了我上午写的第一版"小文件 grep 快 2.8 倍、大文件 rg 快 3.3 倍”：那两组数字是热缓存 + 特定负载下测的，跨会话不成立。下午重测安静会话后，小文件那格反而是 rg 单核反超 grep 近 10 倍。倍数只在独占机器 + 固定负载下才是一个量，其余时候它是一个分布。 这句话比任何"rg 快 X 倍"都更该进你的肌肉记忆。

能钉死的第 1 层：单文件热态，rg 有 3.7 倍固定启动成本#

单文件 34MB、热缓存、5 轮、命中数校验（每文件 30 行命中）：

# 语料：data/corpus-big/big000.log（34MB，needle-7f3a9c 命中 30 行）
$ grep -c needle-7f3a9c data/corpus-big/big000.log   # 0.003s（5 轮：0.0034/0.0035/0.0035/0.0044/0.0039）
$ rg -c needle-7f3a9c data/corpus-big/big000.log      # 0.011s（5 轮：0.0054→0.013 区间，中位 0.011）
$ rg -j1 -c needle-7f3a9c data/corpus-big/big000.log  # 0.010s（强制单核，和默认档几乎一样）

rg 的耗时里有一块和文件内容无关的固定量：编译 regex、起目录 walker、初始化线程池、搭结果管道。34MB 的扫描本身两工具差距不大，rg 那 ~8ms 的启动税在单文件小负载上就是 3.7 倍差距。rg -j1 与默认档几乎相同说明：单文件场景 rg 的线程池根本没活可分，税照交。

这层是全文最稳的数字：单文件、热态、命中校验、5 轮同会话跑完——I/O 量小到调度器没有发挥空间，5 轮方差 <15%。

能钉死的第 2 层：搜得少——数文件，不计时#

rg 真正的设计卖点是默认行为：内容检测跳二进制（\0 判定）、跳 .gitignore、跳隐藏文件。这层的优势不在"搜得快"，在搜得少。而"搜得少"有个完全不受 I/O 噪声影响的测法：不计时，数文件。

# 造混合目录：50 个普通文件 + 5 个 10MB 二进制 + 20 个隐藏 + 30 个 .gitignore 命中
$ rg --files data/mixed | wc -l                               # 55（默认）
$ rg --no-ignore --hidden --binary --files data/mixed | wc -l  # 106（关掉全部过滤）
$ du -sb data/mixed/src data/mixed/assets \
        data/mixed/.hidden* data/mixed/node_modules
# src 1.17MB / assets 10MB / hidden 478KB / node_modules 1.17MB，目录总量 12.8MB

rg 默认扫的字节口径 1.17MB，全开 12.8MB——11 倍。grep -r 的行为等价"全开"（不跳二进制、不跳隐藏、不读 .gitignore），在这目录里扫 12.8MB 且把 10MB 二进制逐行匹配。这一层不用任何计时：--files 数文件 + du 算字节，零 I/O 调度噪声，独占/共享机器上结论一致——这是全文唯一不依赖机器状态的一层。

“rg 快"这句话到底该信哪层#

  • “单文件更快”：本机不成立，反而 grep 快 3.7 倍（启动税）。rg 赢的是大文件池的并行吞吐，那层需要独占多核机器才测得稳，本机 2 核切片诚实声明：没测出可信倍数，不给数字。
  • “内存更少”：本机实测 rg 扫 3.95GB 峰值 RSS 9.7MB、扫 3.4GB 6.7MB——RSS 不随语料量单调涨（流式逐文件处理），这是"10MB 内存查 100GB"的机制来源；100GB 外推本机没做，只验了机制。
  • “搜得少”：成立且可复现——11 倍是字节口径，数文件 + du 即可核验，不依赖机器负载。

方法层面，这篇最有用的句子：跑性能测试前先分清哪层结论是布局不变量（文件数、字节量、RSS 量级），哪层是负载敏感量（I/O 带宽下的绝对耗时）。前者可以在共享机器上出，后者只能在独占机器上出。我上午那版把负载敏感量当不变量写了，下午推翻了它——推翻的过程比结论更值得看。

转给那个张口就"rg 快 3 倍"的同事：先问一句"你测的时候机器上还有什么在跑”。关注「梦兽编程」，上一篇 Mold 3.0 我在这台机器上把"Rust 重写更快"拆成速度（打平）和安全（segfault→fatal 可复现）两件事；这篇把"rg 快"拆成启动税、并行吞吐、搜得少三层——三层里只有两层在本机测得稳，稳的那两层命令全给全了，不稳定的那层我写了为什么不给数字。

常见问题

ripgrep 到底比 grep 快多少？

在共享 2 核机器上测不出可信倍数——同一格 grep 扫 3.4GB 我三个会话测出 0.01s/2.85s/4.05s，漂 40 倍。能钉死的是两层：单文件热态 grep 0.003s 快于 rg 0.011s（rg 固定启动成本 3.7 倍）；rg 默认只搜 55 个文件（全开 106），字节口径 1.17MB vs 12.8MB。

那 rg 的优势在哪？

在'搜得少'：默认跳二进制（内容检测）、跳 .gitignore、跳隐藏文件。这层用 --files 数文件 + du 算字节即可核验，完全不受 I/O 负载影响。'并行更快'那层需要独占多核机器才测得稳，本机诚实声明没做。

我自己怎么复现？

别复现倍数（负载敏感），复现两层稳的：单文件热态计时（5 轮中位 + 命中数校验）和 rg --files | wc -l 数文件（不计时）。文中命令全给全。
