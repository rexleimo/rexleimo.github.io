284B 塞进 64GB 纯 CPU：一条硬件优化新闻该怎么读

「284B 跑 64GB 零 GPU」新闻读法：位宽 3.75 bit、prefill 与 decode 两件事、KV 预算，四个问号补满再下结论。

November 9, 2026 · 2 min · 401 words · 梦兽 -  |  English

「284B 的 DeepSeek 跑在 64GB 内存、零 GPU、256K 上下文」——这种标题，扫一眼很容易信，也容易骂。信，是因为数字看着唬人；骂，是因为一台纯 CPU 机器塞下 284B 还报出双位数 tok/s，违背直觉。它两可，恰恰说明这种新闻得拆开读，不是站队。

这篇不讲这个项目好不好，讲一套读法：一条硬件优化的 headline 数字，背后压着四个问题——位宽多少、质量掉多少、跑在多大上下文、生成速度真实多少。把四个问号补上，再判断它「真实可用」还是「营销数字」。用 open-source 的 llama-modchip 当标本，把这套读法走一遍。

先说为什么这类新闻这波会变多。大模型的边际成本里，推理占大头，而推理成本里，硬件（GPU 显存、推理卡）又是大头。一旦「纯 CPU 也能跑大模型」这条线被反复验证，等于把一大片买不起显存的场景——边缘设备、合规环境、预算受限的团队——从「跑不了」变成「跑得动」，哪怕速度慢些。

所以 llama-modchip 这类项目的新闻价值，不在它某个数字多快，而在它把「不用 GPU」这条边界往 284B 又顶了一格。理解了这层动机，才不至于被 44.4 tok/s 震住，而是去问它在哪个甜区、代价是什么。

一条 marketing 数字，压着四个问号#

headline 只给你 284B、64GB、44.4 tok/s 这几个数。它没说位宽。44.4 是 prefill（喂长上下文那一瞬的速度），不是生成速度。它没说 256K 上下文下质量还剩几成。它没说 455 个 star 里，有多少人是真在那种机器上把 284B 跑通了。

读法就一条：每个 headline 数字，都要问一句「这是在什么条件下测的」。缺的条件就是质量风险所在。284B 本身是 DeepSeek 的旗舰规模，单靠「能跑起来」三个字，撑不起「好用」的结论。

prefill 和 decode 是两件事，别混着读#

很多人被 44.4 tok/s 震住，是因为没分清 prefill 和 decode。prefill 是把整个长 prompt 一次性喂进去，模型按位置算全层，计算密集，吃的是 CPU 的核数和算力，所以能跑得快。decode 是一个 token 一个 token 往外吐，每一步都要把全部权重从内存读一遍，吃的是内存带宽，是 memory-bound。

CPU 机器上，这两段速度差一到两个数量级很正常。llama-modchip 的 44.4 是 prefill，生成 9.1 到 14.7 tok/s 是 decode。真正决定「日常用起来爽不爽」的是 decode，不是 prefill。读硬件新闻，先问哪个数字是 prefill、哪个是 decode，只拿 prefill 当卖点的，默认打折。

量化曲线是非线性的，3.75 bit 已经是赌博#

这个项目把权重量化到自研的 Fractal-64（3.75 bit/权重）和 Fractal-MXFP4（4.25 bit）。这是非常激进的位宽。量化对质量的损伤不是线性掉，是有个甜点的：业界经验上 4 bit 附近是「体积换质量」的拐点，再往下掉得很快，很多场景 8 bit 以下就明显劣化。3.75 bit 压在拐点另一侧，等于拿质量去换那点内存。

所以「284B 塞进 59GiB」这个数字，真正的含义是：它用了一个大概率伤质量的位宽，才把 284B 压进 64GB。位宽越低，能塞进的小内存越多，但输出能不能用，是另一回事。headline 报的是「塞进去了」，没报「塞进去之后答得对不对」。

位宽的账可以拉直看，而且这一拉就有意思。把 284B 当总参数量，权重本体在 3.75 bit 下约 133GB，在 4 bit 下约 150GB，在 8 bit 下要 300GB——全都比 64GB 大。所以「284B 跑在 59GiB」这个 headline 本身就是一个算术红旗：要么 284B 是 MoE 总参数、真正驻留的是远小于它的子集，要么实际有效位宽比宣传的 3.75 更低，要么这数字是 marketing。

读法上，读者应该自己乘一遍：总参数 × 位宽 ÷ 8 = 权重本体的最小内存需求。这个数超过机器内存，那 284B 在 64GB 上就不成立，得追问它到底驻留了多少参数。别拿「能跑 284B」当结论，先把这个乘法做完。

内存的账，是 KV cache 说了算#

284B 模型要正常跑，光权重加满不压的 KV cache，内存需求在 150GB 量级。要把它压进 59GiB，除了 3.75 bit 量化权重，KV 也必须狠狠压。KV 压得越狠，能撑的上下文和一致性就越差。所以「256K 上下文」这个 headline 数字，要追问：256K 是在什么 KV 预算下测的，跑满 256K 时质量还剩多少。

有个参照系能让数字落地。有人在自己的 128GB 统一内存机器上，把 coding agent 跑到了「足够快」的程度，prefill 能到 300 tok/s 上下。128GB 是甜区，64GB 是极限边缘。同样是「不靠 GPU 跑大模型」，128GB 的结论比 64GB 稳得多。读新闻时，把机器配置和 headline 放一起看，才清楚你站在哪个甜区。

它是怎么把 284B 压进 59GiB 的#

要理解为什么能压进 64GB，得看它动了哪几个地方。权重位宽这块，用 Fractal-64/MXFP4 把 284B 权重压到 3.75 到 4.25 bit，权重本体的内存占比砍到 8 bit 时代的不到一半。KV cache 这块，把整段压成 snapshot，恢复一个 40 工具长 prompt 的快照只报 13.1 到 32.6ms，回滚走 O(1) 投机，省掉重复的 prefill 计算。调度这块，把不同子网在核上重排避开 cache 冲突，再叠一个 Stockfish 搜索式的调度器去挑访存 pattern。

这几处改动叠起来，才能把 284B 塞进 59GiB 还报出那个 decode 速度。但每一件都是在拿质量或通用性换内存：位宽越狠质量越伤，KV 快照压得越狠上下文越受限，调度器是 CPU 特化的，换个硬件就要重调。所以「能塞进去」是工程上的真本事，「塞进去之后干得了正事」是另一道题。

它到底适合谁用#

把它放对位置，价值就清楚了。适合的场景：没有 GPU 的纯 CPU 服务器、数据必须全落本地的合规环境、预算买不起大显存的团队、以及就想在一台高端机上跑本地 agent 不想付 API 的个人。在这些场景里，「不用 GPU 也能跑个能用的 284B」是实打实的增量。

不适合的场景：追求极致质量的生产环境（3.75 bit 的量化损耗你得自己扛）、需要 256K 满上下文且质量不能降的场景、以及手边有 GPU 的——有卡就别用 CPU 硬顶，性价比反而差。一句话：它是「没得选时的强方案」，不是「有得选时的首选」。

tok/s 不等于质量#

一个模型每秒吐 14 个 token，吐出来要是错的，那 14 tok/s 毫无价值。速度只回答「多快」，不回答「对不对」。这也是为什么光看跑分的硬件新闻都要打问号。有个叫 MaxxBench 的评测就专门挑这种毛病：模型在 DeepSWE 上拿了不错的分，但分是真实的吗？测的是不是刷出来的？速度分、跑通分、真实质量分，是三件不同的事。读硬件优化新闻，要把「跑通」「跑快」「跑对」拆开看，缺哪层就说哪层没验。

README 的 AI 味，本身是红旗#

这个仓库的 README 被不少人吐槽：emoji 堆满、措辞像 AI 生成的、平台假设没写清。README 的包装和它测没测是两回事。一堆「13ms 恢复」「O(1) 回滚」「Stockfish-PVS L3」这种听着高级的词，如果没配可复现的命令和别人的实测，那就是自报，不是实锤。

读法上，README 里所有性能数字默认标「官方自报、未独立复现」。要下结论，得自己在那种机器上跑一遍 bench 命令，看真实吞吐和质量，或者找别人实测交叉。没跑之前，数字只配进「待验」那一栏。

怎么判一条硬件优化新闻#

把上面串起来，读这类新闻时逐条把这五个问号补上：位宽是多少（低于 4 bit 就是质量赌博）；生成速度真实多少（别拿 prefill 冒充）；跑在多大上下文、KV 预算多少；质量有没有人实测过；README 里的数字能不能复现。五个问号补得越满，结论越实。补不满的，就老实写「没复现」，不替它下「好用」。

这套读法不只对这一个大模型项目。任何「把 X 压进 Y」的硬件优化 claim，都是同一张表：headline 给的是能塞进去，你要问的是塞进去之后还能不能干正事。

手边那台机器够不够验#

要真去验，最低门槛是那台 64GB 纯 CPU 的机器本身——买不到就别信 64GB 的数字，换成 128GB 的机器（比如带统一内存的机型）再测，结论的甜区完全不同。能测就先跑 bench 命令看 decode 速度，再喂同一个固定 prompt 跑质量对比，最后把「我的配置 + 位宽 + decode tok/s + 质量主观分」记下来。这套数据记出来，才算把这条新闻从「营销」变成「我验过」。

诚实边界#

手边没有 64GB 纯 CPU 的机器，没法独立跑通 llama-modchip，所以它的所有性能数字都是仓库自报，质量结论是靠量化规律和社区实测反推，不是我测出来的。位宽对质量的损伤是统计规律，不是这个仓库实测的质量分。要判断它「能不能日常用」，得找一台 64GB 的机器实跑一遍，或等别人出评测。没跑之前，这篇给的是读法，不是 verdict。

FAQ#

284B 真的能在 64GB 纯 CPU 上跑吗？ 能跑起来（官方自报，59GiB 以内），但靠 3.75 bit 激进量化加压 KV，质量和上下文完整性是没独立验证的问号。

44.4 tok/s 算快吗？ 那是 prefill，不是生成。生成是 9.1 到 14.7 tok/s，读硬件新闻别把两段速度混着看。

3.75 bit 量化质量掉多少？ 量化损伤非线性，4 bit 是甜点，压到 3.75 大概率明显劣化，但具体掉多少没这个仓库的实测质量分，属于待验。

128GB 那个参照说明什么？ 说明「不靠 GPU 跑大模型」有甜区。128GB 统一内存跑到 coding agent 够用，64GB 是极限边缘，两个配置的结论不能互相替。

该信这条新闻吗？ 信它的读法，别直接信它的数字。五个问号（位宽/生成速度/上下文 KV 预算/别人实测的质量/可复现）补满再下结论，补不满就写「没复现」。
