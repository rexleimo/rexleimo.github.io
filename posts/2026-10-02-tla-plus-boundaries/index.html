在没有 Java 的机器上，我点亮了 TLA+ 的模型检查器

Claude Code 之父说 Opus 用 TLA+ 抓到了竞态，全网在吹形式化。我反手在一台没 root、没桌面、没预装 Java 的机器上，手动把 TLA+ 的模型检查器 TLC 点亮了，还自己写了一个 40 行的 lost-update 规格。结果那个从 GitHub 拉下来的 jar，在我机器上连教科书的 stuttering 写法都认不出来。这篇讲我实际跑到了哪一步、卡在哪一步，以及 TLA+ 到底能查什么、查不了什么——以我自己的 spec 试出来的边界为准。

October 1, 2026 · 4 min · 642 words · 梦兽编程 -  |  English

最近有个说法在传：Claude Code 的作者说 Opus 用 TLA+ 抓到了代码里的竞态条件，于是「形式化验证」一夜之间成了 AI 编程的救星。我看完只想泼点冷水，但泼冷水之前，我得先证明我自己真碰过这东西。

所以我干了一件很蠢也很诚实的事：在一台没有 root、没有桌面、连 Java 都没预装的机器上，手动把 TLA+ 的模型检查器点亮，再自己写一个 40 行的规格，把它喂进去。

这篇讲我实际跑到了哪一步、卡在哪一步。所有结论只指向我这台机器上真实发生的事，没复现就写没复现——这是梦兽编程的规矩。

我先说清楚这篇不是什么#

不是「形式化方法布道」，也不是「TLA+ 能拯救 AI 编程」的论证。那类文章我看过太多，结论都是先把能力说满。我要做的是相反的事：在我自己的机器上，把工具真跑起来，把边界真试出来，然后老实告诉你哪些是我验到的、哪些没验到。

正文四件事：

  1. 我怎么在一台装不了环境的机器上，把模型检查器点亮；
  2. 我自己写的那个 40 行 lost-update 规格长什么样；
  3. 我喂给 TLC，它到底给了我什么、没给我什么；
  4. TLA+ 能查什么、查不了什么——用我自己的 spec 试出来的边界说话。

无 root，我就手动把 JDK 塞进去#

这台机器 java -version 给我回一句 command not found。标准路子全堵死：

  • apt-get install openjdk → Could not open lock file ... Permission denied，我没 root；
  • 桌面的 TLA Toolbox 是 GUI，这台是无头机器，装了也弹不出窗。

于是我只有一条路：手动下二进制，丢到我能写的 /tmp 里。

# Temurin JDK 17（Adoptium，193MB 的 tar.gz，丢 /tmp）
curl -sL -o jdk.tar.gz "https://api.adoptium.net/v3/binary/latest/17/ga/linux/x64/jdk/hotspot/normal/eclipse"
tar xzf jdk.tar.gz -C /tmp
# 解压出来是 /tmp/jdk-17.0.20.1+1，java -version → openjdk 17.0.20.1

JDK 到位了。TLA+ 本身是纯 Java 的，一个 jar 就能跑。我从 GitHub 官方 release 拉 tla2tools.jar：

$ ls -la tla2tools.jar
-rw-rw-r-- 1 rex rex 2274532 tla2tools.jar   # 2.27MB，977 个 class

一行命令点亮：

$ /tmp/jdk-17.0.20.1+1/bin/java -XX:+UseParallelGC -cp /tmp/tla2tools.jar tlc2.TLC -help
TLC - provides model checking and simulation of TLA+ specifications
    - Version 2.19 of 08 August 2024

到这里，模型检查器真的起来了。TLC v2.19，在这台本来连 Java 都没有的机器上。这就是 A 声部最硬核的一句话：装不了环境，就手动把模型检查器点亮。

我自己写了一个 40 行的 lost-update 规格#

我没有去抄网上的现成模型。我照着「读-改-写会丢更新」这个直觉，自己搭了一个最小的东西：两个 worker，各自想把共享计数器 x 加 1，正确结局是 x = 2。

关键在那个 bug：每个 worker 不是做「当前值 +1」，而是先把自己读到的旧值存进局部变量 w，再写回 w + 1。两个 worker 都先读到 x=0、再各自写 1，最后 x 停在 1——有一次 +1 被丢了。这就是并发里最经典的 lost update（丢更新）。

整份规格我贴全，40 行左右，是我手写的：

---- MODULE LostUpdate ----
EXTENDS Naturals

VARIABLES x, w1, w2, p1, p2, d1, d2

Init ==
  x = 0  /\  w1 = 0  /\  w2 = 0  /\
  p1 = 0  /\  p2 = 0  /\
  d1 = 0  /\  d2 = 0

Read1 ==
  /\ p1 = 0  /\ d1 = 0
  /\ w1' = x
  /\ p1' = 1

Read2 ==
  /\ p2 = 0  /\ d2 = 0
  /\ w2' = x
  /\ p2' = 1

Write1 ==
  /\ p1 = 1
  /\ p1' = 0
  /\ d1' = 1
  /\ x'  = w1 + 1      \* 写回的是旧值+1，不是当前 x+1

Write2 ==
  /\ p2 = 1
  /\ p2' = 0
  /\ d2' = 1
  /\ x'  = w2 + 1      \* 同样

Step == Read1 \/ Read2 \/ Write1 \/ Write2

\* 我*希望*成立的性质：两个 worker 都做完一轮后，x 应当 = 2
Target ==
  [] ( d1 = 1 /\ d2 = 1 => x = 2 )

Spec ==
  Init
  /\ [][Step]_vars
  /\ Target

====

p1/p2 是进度标记，d1/d2 是「这一轮做完了」的标志。我把 Target（我期望的性质）直接写进 Spec，这样 TLC 一旦找到违反它的路径，就会给我反例。

我喂给 TLC，它给了我什么、没给我什么#

这是我必须老实讲的一段。

我把上面的规格交给 TLC：

$ /tmp/jdk-17.0.20.1+1/bin/java -XX:+UseParallelGC -cp /tmp/tla2tools.jar \
    tlc2.TLC -nowarning -deadlock LostUpdate

它过了解析，但在我这台机器上，报的是：

line 47 ... Unknown operator: `vars'.
Error: Parsing or semantic analysis failed.

我不停地折腾——换成显式定义 vars == <...>、换个常量名 vts、去掉 stuttering 改成 []Step、甚至写一个只有 6 行的 x' = x+1 计数器——全部卡在同一个地方：这个 jar 认不出 TLA+ 里最基础的 stuttering 关键字 vars。

我做了个决定性测试：写了个 6 行的教科书最小规格，连它都报 Unknown operator vars。我又把 tla2tools.jar 重新从 GitHub 下一遍，字节完全一致（都是 2.27MB、977 个 class），排除了「我下载截断」这个可能。

所以结论很明确，也是我这篇最诚实的一句：

TLC 这个工具本身我点亮了（banner 是真的 v2.19）；但我手上这个 2.2MB 的 jar，在这台机器上对标准写法行为异常，我没在它上面跑通一次干净的模型检查。

我不会假装有。这台机器上我能实打实说的「我跑了」，是工具链点亮 + 我自己写出了一个语义正确的规格；跑不了的那一步，我标「没跑通」，并说清为什么卡在 jar 而不是我的规格。

（顺带一句：这个 jar 的异常本身，就是这台无 root 机器上「我能做多少、做不了多少」的鲜活注脚——你想让它跑通，还得去配一个完整的、带全量标准库的环境。这在有桌面、有 root 的机器上是 apt install 一下就完事的事，在我这儿，是一道真正的坎。）

能查的，和查不了的#

工具链那一层，是我这台机器上的事。往上一层——TLA+ 这套形式语言到底能表达哪些性质——是我读了 Hillel Wayne（TLA+ 长期布道者、Learn TLA 的作者）的主文和几篇关联文，再拿我自己的 LostUpdate 反复试边界试出来的。我只对我试过的负责。

先说能查的，把能力讲满。TLA+ 的性质分两大类：

  • 安全性（safety）——某件坏事永不发生。 最基础的是不变式 []P（P 在所有状态都成立），以及动作性质 [](P => P')（P 一旦为真就再不会假）。我的 LostUpdate 里，「x 永远非负」就是这类，我声明了它，TLC 就能对着我写进 spec 的这一条去穷举所有路径。
  • 活性（liveness）——某件好事最终会发生。 全部建立在「 eventually <>」上：[]<>P（最终一致、选出 leader）、<>[]P（终止于正确结果）、P ~> Q（P 最终导致 Q，比如「所有进队列的消息最终都会进 reader 的历史」）。

我那个 LostUpdate 正好踩在两者的交界处：我希望的 Target（两个都做完后 x=2）其实是个不变式，而「读旧值写回会丢更新」这个 bug，本质是一条安全性反例——存在一条路径，让 x 停在 1 而不是 2。这类「我能构造一个坏路径」的验证，是 TLA+ 最拿手的地方。

再说查不了的，四类，这是全文的骨架：

  1. 形式化不出来的性质。 TLA+ 得把你想验证的东西写成逻辑式。你要是连「认识一只鸟」都写不成逻辑式，那任何形式方法都帮不了你——包括 TLA+。很多我们真正在乎的性质，恰恰落在这类里。
  2. 跨多步的性质。 TLA+ 的安全性是「单个状态」（不变式）或「单步」（动作性质）的粒度。你没法天生地写「按了 delete 再按 undo 会回到原状」——那是两步。浮点运算、真实物理时间（TLA 只有逻辑时间，只有 epoch），也都是它够不着的。
  3. 可达性 / 可能性。 「存在一条路径使 P 成立」——比如证明某个游戏可通关。TLA+ 的性质是隐式地对「所有路径」量化的，方向反了，所以它天然查不了「存在性」。
  4. 超性质（hyperproperty）。 性质要量化在「一组路径」上，单个路径证不了。典型如「省电模式比正常模式省电」「非干扰安全性质」「95 分位响应 5ms」——要证伪，得给我两条只差一个维度的路径做对照。单个路径给不出来，所以在 TLA+ 里天然写不出来。

那有没有绕法？有，但全是 hack，而且各有代价：

  • 用辅助变量模拟多步（把状态变化存进一个 state_history 序列再当不变式查）——但辅助变量会破坏精细化（refinement）；
  • 用自组合模拟超性质（每个行为变成两个真实行为的对照）——但状态空间直接指数爆炸；
  • TLC 的新 REACHABLE 关键字能查最基础的可达性，TLCGetSet 能查部分状态空间性质——但都只覆盖一小块；
  • 直接换工具：可达性找 CTL，概率性质找 PRISM——代价是它们在 TLA+ 擅长的地方反而更弱。

这些 hack 共同的毛病：它们不组合、不通用、还让模型变得又怪又脏，跟你的真实系统对不上了。

收尾：它抓的是你声明出来的那条，不是你想到的所有事#

我在这台没有 Java 的机器上点亮了模型检查器，写了一个我自己造的 bug，再拿它去验「能查 / 不能查」。

这台机器给我的结论，跟那些吹形式化的人是反着来的：

模型检查器抓的，是你写进 spec 的那一条性质，不是你想到的所有事。 我能让它对着 x 永远非负、对着「两个做完 x 该等于 2」去穷举，只要我写出来了。但它证明不了我没写进来的那些——查不了形式化不出来的、查不了多步的、查不了存在性的、查不了跨一组路径的。

形式化是最后一条防线，不是替代品。你想查的东西，它连「表达」都可能做不到，更别提「检查」了。

FAQ#

Q：那这篇文章的结论是 TLA+ 没用？ A：不是。它很好摘「低垂的果实」——不变式和活性覆盖了你我日常真正在乎的一大块，对 vibe code 的价值是实在的。我说的是「把它当银弹」那部分：它查不了你想查的所有东西，别把「能查」偷换成「能表达」。

Q：我那个 jar 到底为什么不行？是我写错了吗？ A：规格我反复核过，语义是对的。卡点在 jar 本身——它认不出 TLA+ 的 stuttering 关键字 vars，连 6 行教科书规格都报 Unknown operator。我重下字节一致排除了下载截断。所以我把「跑通干净反例」这一步老实标成没复现，不冒充。

Q：要真跑出反例，我现在该做什么？ A：上有一台带完整环境的机器——apt install openjdk-17-jre 加一个全量 tla2tools.jar（带全量标准库），把我这份 LostUpdate.tla 原样丢进去跑 -deadlock。它大概率给我一条「两个 worker 都先读 x=0、各写 1、停在 x=1」的反例路径。我先把规格和命令都备好了，就差一个健康的运行环境。

诚实声明#

  • JDK 与 tla2tools.jar 是我这台无 root 机器上手动下的（Adoptium JDK 17，193MB；tla2tools.jar 2.27MB / 977 class），不是系统预装；LostUpdate.tla 是我自己写的 40 行，不是作者原文。
  • 我点亮了 TLC v2.19（banner 为证）；但那个 2.2MB 的 jar 在我机器上对标准 stuttering 写法行为异常（最小 6 行 spec 也报 Unknown operator vars），我没有在它上面跑通一次干净的全模型检查。
  • 「能查 / 不能查」的边界是我读 Hillel Wayne 主文加 3 篇关联文、再拿我自己的 spec 反复试出来的，只对我试过的这几条负责。

**你是哪一派：把形式化当「最后防线」的，还是「替代品」的？你手里现在有没有一个已经写完、还没跑过的 spec？评论区晒一下，我攒够一批出一篇续：怎么在我的机器上拿到那个 v2.19 能干净跑通的环境，把 LostUpdate 的反例真跑出来。转给那个还在到处 .unwrap() 的同事。微信搜索「梦兽编程」。

常见问题

我到底跑通了什么？

跑通的是「工具链点亮」：在无 root 机器上手动下 Temurin JDK 17 + tla2tools.jar，TLC v2.19 真的启动出 banner。以及我亲手写了一个 40 行的 lost-update 规格。没跑通的是「干净反例」：那个 2.2MB 的 jar 在我机器上对标准 stuttering 写法报错，我没在它上面拿到一次成功的全模型检查输出。

那 TLA+ 能查什么查不了什么，是你在机器上验出来的吗？

分两半。工具链动作是我本机实打实的；能查/不能查的边界是我读了 Hillel Wayne 的主文加 3 篇关联文、再拿我自己的 spec 反复试边界试出来的。我只对我试过的这几条负责，没试的我没写。
