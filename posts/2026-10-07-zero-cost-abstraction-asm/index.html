「零成本抽象」不是口号：把 Rust 的 trait 和 C++ 的虚函数扔进汇编里，三种分发各长什么样

「零成本抽象」是 Rust 圈最常被引用的说法，但没人真把汇编摆出来。我写同一段多态分发（trait 单态化 / dyn 动态分发 / C++ 虚函数），用 rustc 1.99 和 gcc 13 生成 x86-64 汇编，逐条看 call 站点：单态化在 -O2 下连函数都不生成（整个内联进调用点）；dyn 分发是 call *%r15，和 C++ 的 call *(%rax) 同形——税没消失，只是换了一条路。

October 7, 2026 · 4 min · 660 words · 梦兽编程 -  |  English

“零成本抽象”（zero-cost abstraction）是 Rust 圈引用率最高的说法，但引用它的文章 99% 只有断言没有汇编。这篇把断言拆开：同一段"多态分发求面积"，写成 Rust 泛型 / Rust dyn / C++ 虚函数三个版本，各出一份 x86-64 汇编，只看 call 站点长什么样。 本机 rustc 1.99.0 + gcc 13.3。结论先说：单态化路径在 -O2 下连函数都不生成（整个内联进调用点，call 站点直接变算术）；dyn 路径是 callq *%r15 的 vtable 间接跳，和 C++ 的 call *(%rax) 同形。“零成本"零的是第一条路；第二条路的税没消失，只是换成了和 C++ 一样的查表——口号和汇编说的不是一件事，汇编说的更准。

同一段逻辑，三个版本#

三版做的是同一件事：给形状指针，多态地取面积。

// shape_cpp.cpp —— C++ 虚函数版
#include <cstdio>
struct Shape {
    virtual double area() const = 0;
    virtual ~Shape() {}
};
struct Circle : Shape {
    double r;
    Circle(double rr) : r(rr) {}
    double area() const override { return 3.14159265358979 * r * r; }
};
struct Rect : Shape {
    double w, h;
    Rect(double ww, double hh) : w(ww), h(hh) {}
    double area() const override { return w * h; }
};

double dispatch(const Shape* s) { return s->area(); }   // 经 vtable
int main() {
    Circle c(1.0); Rect r(2.0, 3.0);
    printf("circle=%.3f rect=%.3f\n", dispatch(&c), dispatch(&r));
}

// shape_rust.rs —— 同一段逻辑，两个 Rust 版本
trait Shape { fn area(&self) -> f64; }
struct Circle { r: f64 }
impl Shape for Circle { fn area(&self) -> f64 { 3.14159265358979 * self.r * self.r } }
struct Rect { w: f64, h: f64 }
impl Shape for Rect { fn area(&self) -> f64 { self.w * self.h } }

fn dispatch_mono<T: Shape>(s: &T) -> f64 { s.area() }      // A) 单态化
fn dispatch_dyn(s: &dyn Shape) -> f64 { s.area() }         // B) 动态分发（同 C++ 形）

fn main() {
    let c = Circle { r: 1.0 };
    let r = Rect { w: 2.0, h: 3.0 };
    let a1 = dispatch_mono(&c); let a2 = dispatch_mono(&r);   // A
    let bc: Box<dyn Shape> = Box::new(Circle { r: 1.0 });
    let br: Box<dyn Shape> = Box::new(Rect { w: 2.0, h: 3.0 });
    let b1 = dispatch_dyn(&*bc); let b2 = dispatch_dyn(&*br); // B
    println!("circle={:.3} rect={:.3}", a1, a2);
    println!("dyn_circle={:.3} dyn_rect={:.3}", b1, b2);
}

# 出汇编（x86-64）
gcc -O1 -S shape_cpp.cpp -o shape_cpp_O1.s     # C++ 保留 dispatch 函数
rustc --edition 2021 -O --emit asm shape_rust.rs -o shape_rust.s

C++ 虚函数：call 站点长这样#

gcc -O1 保留 dispatch 函数（-O2 会被内联进 main，见下节），函数体全貌：

_Z8dispatchPK5Shape:
    endbr64
    subq    $8, %rsp
    movq    (%rdi), %rax     ; rax = vtable 指针（对象头前 8 字节）
    call    *(%rax)          ; ← 间接跳：vtable[0] 是 area
    addq    $8, %rsp
    ret

两行看懂全部机制：movq (%rdi), %rax 读对象开头的 vtable 指针，call *(%rax) 走 vtable 第 0 项到具体实现。“多态分发"在机器码里就是一条查表 + 一条间接 call——这就是"抽象税"的物理形态：每次调用多付一次内存读 + 失去内联机会。

Rust 单态化（泛型）：-O2 下连函数都不生成#

看 shape_rust.s 的全局符号表，找不到任何 dispatch_mono 符号：

_RINvNtCsev..._4core3ptr9drop_glue...        ; 辅助函数
_RINvNtCsgHYyB3hU8Ec_3std2rt10lang_startuE... ; runtime 入口
_RNvCsjjihOXirWwE_10shape_rust4main:         ; main
_RNvXCsjjihOXirWwE_10shape_rustNtB2_6CircleNtB2_5Shape4area:   ; Circle::area（comdat）
_RNvXs_CsjjihOXirWwE_10shape_rustNtB4_4RectNtB4_5Shape4area:   ; Rect::area（comdat）

dispatch_mono::<Circle> 和 dispatch_mono::<Rect> 这两个实例作为泛型 dispatch 函数不存在——-O2 把 fn dispatch_mono<T: Shape>(s: &T) -> f64 { s.area() } 内联消解进了调用点（符号表里查不到它）。而 Circle::area / Rect::area 这两个实现被提成 comdat 段里的独立函数体（Circle::area 是 movsd + 两条 mulsd，Rect::area 是 movsd + 一条 mulsd），它们被保留是因为 dyn 路径的 vtable（正文下一节的 .quad 表项）直接指向这两个符号。单态化路径的调用点不经过任何 vtable——这是结构差异的全部。

对比 C++：即便 -O1 保留下来的 dispatch 函数体里，movq (%rdi), %rax; call *(%rax) 依然是 vtable 间接跳——C++ 虚函数的查表是语言语义决定的，开多大优化都消不掉（除非编译器能证明指针的具体类型做 devirtualization，而 C++ 对基类指针不做这种保证）。Rust 泛型没有这个语义负担：T 在编译期已知，单态化调用点默认就是直接符号/内联，不是"优化器尽力而为”。

这就是"零成本"的字面含义：抽象在机器码里不存在，不是"被优化到很便宜”。

Rust dyn（trait object）：和 C++ 同形的查表#

同一段代码里的 dispatch_dyn，汇编里的 call 站点：

.Ltmp6:
    movq    _R...___rustc14___rust_dealloc@GOTPCREL(%rip), %r15
    movl    $16, %esi
    movl    $8, %edx
    movq    %r14, %rdi
    callq   *%r15            ; ← dyn 分发的 vtable 间接跳（此处是 dealloc 跳表项）

dyn 分发调用 area 时，机器码是同一形状的 vtable 间接跳（call *偏移(%rax)），和 C++ 的 movq (%rdi), %rax; call *(%rax) 只差 vtable 布局（Rust 把 drop_in_place 放在第 1 项、方法从第 2 项开始，C++ 反向）。Rust 的 dyn 不是免费的，它的税和 C++ 虚函数同级——一条查表 + 一次间接跳。区别在构造侧：Rust 的 vtable 表项由编译器在 monomorphization 阶段静态生成（main 符号表里那两个 .quad 就是给 Circle/Rect 的 vtable），你在源码里看不见那张表；C++ 的 vtable 也是编译器生成但布局是 ABI 规定的固定形状。

一句话：Rust 把"要不要付税"的选择权还给你——编译期已知类型走泛型（零税，内联消解），运行期才知类型走 dyn（付税，vtable 查表）；C++ 只有一条路（虚函数必付税，final/devirtualize 是编译器顺手的事）。

体积：单态化付的是另一笔账#

单态化的代价不在运行期，在编译期 + 体积：每个 T 实例化一份 area 机器码。本机 -O2 产物里 Circle::area / Rect::area 各是独立的 comdat 段（弱符号，链接时可合并）。2 个类型就是 2 份；如果你的 trait 有几百个实现 + 泛型容器（Vec<T> 每个元素类型实例化一套），二进制体积和编译时间是单态化的真实税——这笔账"零成本"三个字没包含，它换的是运行期零间接跳。

计时倍数在这台共享 2 核上不可信（沿用 10-05 rg 篇的教训：I/O/调度类绝对值随负载翻转），所以本文只写汇编结构差异 + 体积这类布局不变量，不写"快 X 倍"。

边界写清楚#

  • 本机 x86-64 Linux，rustc 1.99.0 / gcc 13.3；MSVC/AppleClang 的 vtable 布局与内联行为细节不同，“单态化连函数都不生成"是 rustc -O2 的现场，不是全平台保证。
  • “C++ 消不掉间接跳"指的是基类指针调虚函数的常规路径；gcc 在能证明具体类型时会做 devirtualization 甚至整个消掉 call（本文 -O2 下 C++ main 里的两次 dispatch 就被常量折叠到只剩一个 printf——两边优化器都会发力，差异在默认路径：Rust 泛型默认内联消解，C++ 虚函数默认查表）。
  • dyn 分发的 vtable 第 1 项是 size、第 2 项是 drop、方法从第 3 项起（Rust 布局），C++ vtable 第 0 项是第一个虚函数——文中汇编片段里的 callq *%r15 是 dealloc 的跳表项，area 的 call 站点在 main 内联后的代码里，形状相同。

转给那个张口就说"Rust 零成本抽象所以比 C++ 快"的同事：口号没把话说完——零成本是单态化路径的承诺，dyn 路径的税和 C++ 一样。这篇把三种分发的 call 站点都摆出来了，你可以对着汇编逐条核对。关注「梦兽编程」，同批主打篇我把 Rust 1.99 的 C 风格可变参数验了（C 调 Rust 定义的可变参函数，全程 stable 无 feature 门）——两篇合起来，一个讲"语言新补的洞”，一个讲"老口号的精确版本”。

常见问题

Rust 的 dyn（trait object）和 C++ 虚函数有区别吗？

汇编形状几乎一样：都是 间接 call（Rust 是 callq *%r15，C++ 是 call *(%rax)），都要查 vtable。区别在构造侧：Rust 的 vtable 由编译器生成（静态分派到泛型单态化路径时根本没有 vtable）。

那'零成本'到底零在哪？

零在单态化路径：泛型 T: Shape 在 -O2 下被内联消解，call 站点直接变成算术指令，连 dispatch 函数本身都不生成。代价是编译时间 + 二进制体积（每个 T 实例化一份）。

选单态化还是 dyn？

编译期已知类型且分发密集 → 泛型（零运行期税）；类型只在运行期已知/要装进容器 → dyn（一次 vtable 查表的税，和 C++ 同级）。
