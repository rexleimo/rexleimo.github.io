别让 AI 写代码：一位 Haskell 开发者的反烧玩手册

Haskell 论坛一篇纯手写万字长文在 HN 上 212 条评论炸开：一个职业 Haskell 开发者把 AI 辅助编程的边界切得很清楚——规划、研究、审阅交给 LLM，写代码这件事留给人。这篇拆他的核心主张。

September 27, 2026 · 1 min · 203 words · 梦兽编程 -  |  English

Haskell 论坛一篇纯手写的长文这两天在 Hacker News 上炸开了——163 分、216 条评论，评论区吵的不是技术细节，是程序员的情绪。

作者 turion 是职业 Haskell 开发者，开头就防了一手：“别误会我是挺 LLM 的 techbro，我这文 100% 人写的。” 他真正想解决的是三个很具体的焦虑：AI 烧玩（burnout）、被"没编程技能但有大 Claude 账号的人"抢饭碗、以及看着自己项目里的代码质量滑坡。

他的答案不激进，也不投降——让 AI 干除了写代码以外的所有事。

一句话版本#

规划交给它，研究交给它，代码审查交给它，琐碎重构交给它；写代码这件事，你自己来。原文原话：“让 agent 围绕你的工作方式转，而不是反过来。"（Make the agents group around your way to work, not the other way around.）

这个主张的价值不在"反 AI”，在于他把边界切得极清楚，每一条都能落地。

他切边界的那几刀#

1. “You are the coder” 是全文的转折点。 典型 coding harness 的套路是"先规划、再让 agent 写码"，他明确拒绝：规划可以一起做，但写完规划之后，代码你来敲。让 agent 去研究代码库、列 todo、标出所有要改的位置和潜在坑，然后你带着这份"被喂饱的 todo"去写。他的原话：这么干之后"活儿变好玩了，有时候比没有 LLM 之前还好玩"，像敏捷开发但去掉了所有烦人的流程。

2. 代码库的所有权。 全量生成 → 代码库变成"LLM wasteland"，只有你的 agent 能在里面活下来。而且技能是会退化的：交出去几周，你想自己捡回来都会觉得费劲。他认为 LLM 在"写好的人类可读代码"上被吹得过头了——它能自己继续写自己生成的那堆东西，但你要读、要 review，就是费劲。

3. 研究环节的反直觉用法。 让 agent 研究东西时，最诱人的操作是去喝咖啡看它"思考"。他说别：并行自己也用搜索引擎查一遍，“至少要大致知道 agent 会知道什么”。agent 研究的价值不是替你做出更好的决策，而是省掉"let me google that for you"。让它把研究结果落盘、附来源链接；下次它给你提了个怪方案，先问它"研究里哪条说的"——有一半概率它会发现自己错了。

4. review cycle（GAN 式）。 借生成对抗网络的思路：一个生成、一个判别，两个加一起比单个生成器强。落到 LLM 辅助编程就是——任何 LLM 产物（包括规划），你不经过自动化 review cycle 连读都别读。agent 写完一件事不算完，review agent 挑不出毛病才算完。他自己说给"自己的代码"也跑 review cycle，经常真能翻出 bug。

5. 别押 frontier。 他给了四条理由，最实际的一条：最花哨的模型 token 烧得最猛，你没法保证一次会话内任务能做完——“你用小模型能做的每件事，都是更安全的下注”。附带的好处：不依赖 frontier，未来就有机会换成开放权重模型，彻底不靠"technofeudal lord"。

两个金句，值得存一下#

把 token 耗尽当成"服务故障"，而不是"你买少了"。 你的工作流建立在别人的配额上，那个数字可以无缘无故变。你得有离线能干的活。

LLM 吐出的文字不像人话，它真不懂的时候更不像。把它当成可能伤害你心理健康的东西，别消费太多。 多跟人聊代码，别光读 LLM 的产物。

评论区最出圈的共鸣（top comment）来自 enobayram：“读一堆 LLM gibberish 对大脑的伤害，在生理层面是能直接感受到的，当天量大的时候特别疼。” 他管这叫"大脑的石棉"。

诚实声明#

这篇是转述 + 提炼，没有跑任何 benchmark——它本来就是观点文，不涉及可复现的性能数字。原文 1.9 万阅读、60 赞、HN 216 评（抓取时点 9 月 27 日）。我认同的是他"切边界"的工程纪律部分，至于"代码全自己写"这条，激进程度取决于你团队的容忍度，文末给你留了三个站队。

你是哪一派？

  • A 派（纯手写）：LLM 只做补全和查文档，代码一行不生成。评论区有 sourcehut/codeberg 在推"全面禁 LLM 的 FLOSS 项目"，这条线越来越清晰。
  • B 派（作者这种切边界）：规划研究 review 用 AI，写码用手。自报"快了大概一倍"，不是那种"快了十倍的 vibe coder"。
  • C 派（全量 agent）：spec 喂进去，agent 写完你只验收。评论区有人反问：我已经离不开 LLM 把脏活全干了，“没有 LLM 我怎么享受编程”。

评论区晒一下你属于哪派、实际提速多少，攒够一批出个续篇把三派的做法摆一起比。

常见问题

作者的核心主张一句话是什么？

让 AI 干除了写代码以外的所有事——规划、研究、代码审查、琐碎重构——但代码本身你自己写。'让 agent 围绕你的工作方式转，而不是反过来。'

为什么他反对全量 vibe coding？

他的理由不是效率，是所有权与可维护性：全量生成的代码库会变成'LLM 荒地'，只有 agent 自己能在里面活下来；而且几周不手写之后，你想捡回键盘都很费劲。他认为 LLM 在'写好的人类可读代码'这件事上被严重高估。

LLM 到底用在哪？

他把 LLM 当'可用自然语言记账的工具'：把领域专家的对话转成 todo、整理测试结果、让 agent 研究代码库并列出所有要改的位置和坑、跑自动化 review cycle。关键纪律：不让它做关键决策，要它来问你。

token 烧完了算谁的错？

他的重新定义很狠：别把 token 耗尽当成'买少了'，当成服务故障（service outage）。你的工作流建立在别人随时能改的配额上，得像在火车上工作那样预备离线可干的事。

那篇原文是 AI 写的吗？

作者开宗明义：100% 纯手写、零 AI 辅助，还专门解释了'因为以前常被误认成 LLM 生成的，所以声明一下'。全文 1.9 万阅读、60 赞。
