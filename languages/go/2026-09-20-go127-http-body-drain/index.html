resp.Body 要手动排空？Go 1.27 改了规矩

Go 1.27 改了 HTTP 客户端惯例：Close() 现在自动排空未读响应体（256 KiB 与 50 毫秒两个限额内）。我在同一台机器上装了 go1.26.4 与 go1.27.1 两套工具链实测 50 次请求，连接复用从 1/50 变成 50/50。本文讲清旧规则为什么成立、新规矩改了哪里、哪些场景仍要手写排空。附完整可复现代码与真实输出

September 20, 2026 · 7 min · 1326 words · 梦兽编程 -  | 

50 次请求打到同一个本地接口，代码一个字没改，只换编译用的工具链（A 行即正文实验，输出为真实运行记录）：

toolchain: go1.26.4
A. 只看状态码：不读 body 直接 Close                            复用  1/50  新建连接 49
toolchain: go1.27.1
A. 只看状态码：不读 body 直接 Close                            复用 50/50  新建连接  1

差别只在 resp.Body.Close() 之前有没有先执行 io.Copy(io.Discard, resp.Body)。「不排空 body 就丢连接」这条被无数 Go 教程当口诀背的规矩，本身没有错；错的是它隐含的后半句——所以你必须手动排空。2026 年 8 月发布的 Go 1.27 把后半句改了：Close() 现在会自动排掉未读的响应体。

这篇讲四件事：这条规矩当年为什么成立（小白先看懂协议层，再回头看代码）；Go 1.27 具体改了什么（release notes 和源码原文都在）；我在一台机器上装两套工具链实测出来的数字；以及新规矩覆盖不到、仍然要手写老惯例的三类场景。

为什么必须「读完再还」#

HTTP/1.1 的 keep-alive 让一条 TCP 连接按顺序串行处理多次请求/响应，不用每次都重做 TCP 握手（HTTPS 还要再加一次 TLS 握手）。复用热连接，是 Go 客户端默认性能的基础。

坑在 TCP 这一层。TCP 是字节流，它没有「消息」的概念——一条连接上，响应 1 的结尾和响应 2 的开头之间没有任何物理分界。想知道响应 1 到哪里结束，唯一的办法是正确解析 HTTP 的定界规则：按 Content-Length 读满指定的字节数，chunked 编码则一直读到 0\r\n\r\n 结束序列。

所以一条连接能不能安全放回连接池，取决于客户端是否确定当前响应的 body 已经全部消费。没读完就还回去，上一个响应剩下的字节还躺在 socket 缓冲区里，下一个请求会把这些残留当成新响应的开头来解析——解析器直接错位，拿到的是被污染的数据。这不是性能优化层面的洁癖，是协议正确性的要求。

打个比方：你从图书馆借一本连续刊载物的合订本，没翻到最后一页就还回去，也没告诉管理员读到哪。下一个人从书架上抽出同一本，以为接着自己的内容读，实际读进去的全是别人的页码。要么老实翻完再还，要么这本书就报废（断开连接）。

老版本（1.26 及更早）发生了什么#

net/http 的 Transport 给每条持久连接维护一个 persistConn，由一个专职的 readLoop goroutine 从连接上读响应。它交给你的 resp.Body 不是裸的连接读取器，而是一个叫 bodyEOFSignal 的包装类型，带两个回调：一个在 Read 返回 io.EOF 时触发（你真的读完了），一个在没等到 EOF 就 Close() 时触发（你中途放弃）。

readLoop 等这个信号，然后决定连接的生死。Go 1.26.4 发行包源码 src/net/http/transport.go（readLoop 第 2451 行起）的判定链：

		case bodyEOF := <-waitForBodyRead:
			alive = alive &&
				bodyEOF &&
				!pc.sawEOF &&
				pc.wroteRequest() &&
				tryPutIdleConn(rc.treq)

bodyEOF 为 false——也就是你没读完就 Close——alive 就是 false，连接不回池，底层 net.Conn 被真实关闭。下一个请求没有空闲连接可用，只能重新拨号。

两个值得较真的细节：

其一，resp.Body.Close() 不排任何东西。服务端是另一套行为：net/http.Server 在 handler 返回后会替客户端最多排掉 256 KiB 的未读请求体（maxPostHandlerReadBytes），专门保住连接复用。客户端这边，1.26 及以前什么都不做——你 Close 早了，连接就地死亡，没有商量。

其二，HTTP/2 根本没有这个问题：H2 的多路复用允许在同一条 TCP 连接上直接开新流，前一个流的 body 读没读完无所谓。go.dev issue #77370 开篇列出的三处不一致（H2 无影响、H1 服务端排 256 KiB、H1 客户端直接丢）正是改动的出发点。顺带一提，当年还有一批教程把这条 H1 规矩错误地推广到了 H2 场景，让读者在 H2 上也手动排空——issue 里点名了这种误用。

Go 1.27 改了什么#

先读官方口径。Go 1.27 release notes（go.dev/doc/go1.27）net/http 节的原句：

HTTP/1 Response.Body now automatically drains any unread content upon being closed, up to a conservative limit, to allow better connection reuse.

翻译：HTTP/1 的响应体在被关闭时，会自动排空未读内容，排空量有一个保守上限，目的是让连接复用得更充分。多数程序视角下这是无感改动，甚至是纯收益。

再看实现。改动由 CL 737720 引入、在 issue #77370 统一追踪（该 issue 于 2026-08-20 关闭，关闭备注写明 Go 1.27 已发布）。src/net/http/transport.go 第 2417 行起，新增的两个常量连同官方注释：

// maxPostCloseReadBytes is the max number of bytes that a client is willing to
// read when draining the response body of any unread bytes after it has been
// closed. This number is chosen for consistency with maxPostHandlerReadBytes.
const maxPostCloseReadBytes = 256 << 10

// maxPostCloseReadTime defines the maximum amount of time that a client is
// willing to spend on draining a response body of any unread bytes after it
// has been closed.
const maxPostCloseReadTime = 50 * time.Millisecond

判定链也长了新分支（Go 1.27.1 源码第 2604 行起）：

		case bodyEOF := <-waitForBodyRead:
			tryDrain := !bodyEOF && resp.ContentLength <= maxPostCloseReadBytes
			if tryDrain {
				eofc <- struct{}{}
				bodyEOF = maybeDrainBody(body.body)
			}
			alive = alive &&
				bodyEOF &&
				!pc.sawEOF &&
				pc.wroteRequest() &&
				tryPutIdleConn(rc.treq)

拆开读：你提前 Close（!bodyEOF）且 Content-Length 在 256 KiB 以内，readLoop 才会尝试排空。maybeDrainBody 起一个后台 goroutine 把剩余字节读进黑洞（io.CopyN 到 EOF），主流程最多等 50 毫秒——排干净，连接回池；超时或超限，照旧断开。等待发生在 readLoop 自己的 goroutine 里，不会阻塞你的业务代码，但 50 毫秒内没排完的连接仍然保不住。

这套改动的目标，issue #77370 里写得很直白：Go 团队希望今后推荐给所有人的惯例就是一句话——关掉 body 就行，别的什么都不用做（just close your HTTP body, no need to do anything else）。

实测：两套工具链跑同一个程序#

理论说完，跑数字。环境：Windows 11；go1.26.4（系统安装）；go1.27.1（官方 zip 解压即用，两个工具链互不干扰）。服务端用 httptest.Server 模拟一个 JSON API，并用 ConnState 回调统计服务端真实看到的新建连接数；客户端用 httptrace 的 GotConn.Reused 字段判断每次请求是否复用了连接。响应体做了三档：8 KB（限额内）、300 KB（超过 256 KiB）、200 KB 慢速流式（限额内但写完要 200 毫秒，超 50 毫秒限额）。

完整程序如下，存成 main.go 直接 go run 就能复现：

package main

import (
	"encoding/json"
	"flag"
	"fmt"
	"io"
	"net"
	"net/http"
	"net/http/httptest"
	"net/http/httptrace"
	"runtime"
	"sync/atomic"
	"time"
)

func newServer(conns *int64) *httptest.Server {
	mux := http.NewServeMux()
	// 8KB JSON：在 256KB 限额内
	mux.HandleFunc("/users/1", func(w http.ResponseWriter, r *http.Request) {
		pad := ""
		for len(pad) < 8192 {
			pad += "xxxxxxxx"
		}
		json.NewEncoder(w).Encode(map[string]string{"id": "1", "bio": pad})
	})
	// 300KB：超过 maxPostCloseReadBytes = 256<<10
	mux.HandleFunc("/big", func(w http.ResponseWriter, r *http.Request) {
		pad := ""
		for len(pad) < 300*1024 {
			pad += "yyyyyyyy"
		}
		fmt.Fprint(w, pad)
	})
	// 200KB 但慢慢吐（每 10ms 10KB，总耗时 ~200ms > 50ms 限额）
	mux.HandleFunc("/slow", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Length", "204800")
		flusher := w.(http.Flusher)
		chunk := make([]byte, 10240)
		for i := range chunk {
			chunk[i] = 'z'
		}
		for i := 0; i < 20; i++ {
			w.Write(chunk)
			flusher.Flush()
			time.Sleep(10 * time.Millisecond)
		}
	})
	srv := httptest.NewServer(mux)
	srv.Config.ConnState = func(c net.Conn, s http.ConnState) {
		if s == http.StateNew {
			atomic.AddInt64(conns, 1)
		}
	}
	return srv
}

// mode 0: Close 前不读 body
// mode 1: 手动 io.Copy(io.Discard) 再 Close
// mode 2: json.Decoder 解码后 Close（结尾 \n 没被吃掉）
func run(srv *httptest.Server, conns *int64, path, name string, mode, n int) {
	atomic.StoreInt64(conns, 0)
	client := &http.Client{Timeout: 5 * time.Second}
	reused := 0
	for i := 0; i < n; i++ {
		req, _ := http.NewRequest("GET", srv.URL+path, nil)
		var wasReused bool
		req = req.WithContext(httptrace.WithClientTrace(req.Context(),
			&httptrace.ClientTrace{
				GotConn: func(ci httptrace.GotConnInfo) { wasReused = ci.Reused },
			}))
		resp, err := client.Do(req)
		if err != nil {
			fmt.Println("ERR:", err)
			return
		}
		switch mode {
		case 1:
			io.Copy(io.Discard, resp.Body)
		case 2:
			var v map[string]string
			json.NewDecoder(resp.Body).Decode(&v)
		}
		resp.Body.Close()
		if wasReused {
			reused++
		}
	}
	fmt.Printf("%-52s 复用 %2d/%d  新建连接 %2d\n", name, reused, n, atomic.LoadInt64(conns))
}

func main() {
	slow := flag.Bool("slow", false, "只跑慢响应超时实验")
	flag.Parse()
	fmt.Println("toolchain:", runtime.Version())
	var conns int64
	srv := newServer(&conns)
	defer srv.Close()

	if *slow {
		run(srv, &conns, "/slow", "E. 200KB 但拖 200ms 才写完 / Close 不排空", 0, 5)
		return
	}
	run(srv, &conns, "/users/1", "(warmup /users/1 手动排空)", 1, 10)
	fmt.Println("---- 8KB 响应（256KB 限额内）----")
	run(srv, &conns, "/users/1", "A. 只看状态码：不读 body 直接 Close", 0, 50)
	run(srv, &conns, "/users/1", "B. 老手册姿势：io.Copy(io.Discard) 后 Close", 1, 50)
	run(srv, &conns, "/users/1", "C. json.Decoder 解码后 Close（剩一个 \\n）", 2, 50)
	fmt.Println("---- 300KB 响应（超过限额）----")
	run(srv, &conns, "/big", "D. 300KB 大 body：不读直接 Close", 0, 20)
	run(srv, &conns, "/big", "D2. 300KB 大 body：手动排空后 Close", 1, 20)
}

四行总结：

场景go1.26.4go1.27.1结论
A. 不读 body 直接 Close复用 1/50复用 50/50新规矩生效，老惯例被取代
B. 手动排空后 Close复用 49/50复用 50/50两版都正确，1.27 下已是多余动作
D. 300 KB 不读直接 Close复用 1/20复用 2/20超过 256 KiB，自动排空不尝试
E. 200 KB 慢流式不读 Close复用 0/5复用 0/5超过 50 毫秒，排空放弃、连接照旧丢

三点如实说明。1.27 的 A 行里「新建连接 1」与 50/50 复用并存，是关闭后排空协程与连接归还竞态产生的瞬时连接，对比对象是 1.26 的 49，不影响结论。C 场景对应 issue #20528（json.Decoder 只吃掉 JSON 值、结尾换行留在 body 里）——本机 loopback 加 8 KB 响应没有复现出丢连接，这个坑通常在真实网络、响应大到跨多次读取边界时才咬人，表格如实记录，不编造复现。所有数字为单次运行的计数指标，不是严格基准。

哪些场景还得手动排空#

对照限额和源码，老惯例没有全灭，以下四种情况你仍然要自己写 io.Copy(io.Discard, resp.Body)（或者干脆读完）：

  1. 响应体超过 256 KiB 且 Content-Length 已知。tryDrain 的判定条件是 resp.ContentLength <= maxPostCloseReadBytes，超限直接不尝试排空（D 行实测）。
  2. 慢流式响应。限额内但 50 毫秒读不完，排空放弃，连接丢失（E 行实测）。
  3. 生产工具链还在 1.26 及更早。规矩一个字没变，教程说的全对。
  4. 反向场景值得单独说：如果你故意提前 Close 来中止一个大下载，本意就是甩掉这条连接，1.27 会先替你白排最多 256 KiB / 50 毫秒。release notes 给的开关是 Transport.DisableKeepAlives = true，同时补了一句：需要这个开关的程序，通常说明 Transport 本身配置就有问题——比如把 MaxIdleConns 设成 0，或者每个请求新建一个 Client 绕开了池的上限。先修用法，再考虑关复用。

小白现在该抄哪份#

新标准姿势，抄这个：

resp, err := client.Do(req)
if err != nil {
	return err
}
defer resp.Body.Close()

if resp.StatusCode != http.StatusOK {
	return fmt.Errorf("api returned %s", resp.Status)
}

var user User
if err := json.NewDecoder(resp.Body).Decode(&user); err != nil {
	return err
}

四条规则按顺序记：

  1. defer resp.Body.Close() 永远保留。不 Close 的问题（连接资源滞留）在 1.27 之后依然存在，这一行没有任何版本可以省。
  2. Go 1.27+ 的小响应，不必手动排空，Close() 替你做了。
  3. 需要兼容 1.26 及以下、或者响应可能超 256 KiB / 是慢流式，Close 前加 io.Copy(io.Discard, resp.Body)——这条动作到今天依然不是错的，只是多数时候多余。
  4. 判断一篇教程还能不能用，成本最低的三步：看它基于的 Go 版本；打开 go.dev/doc 对应版本的 release notes 搜 net/http；对不上就只信官方文档。Medium 和各大社区的高赞文章，很多是按去年的语言行为写的——它们没错，只是过期了。

FAQ#

Go 1.27 会自动排空 body，手动排空没用了？

在限额内没用：256 KiB 以内、50 毫秒内能读完的响应，Close() 自己排。超过 256 KiB、写得慢的流式响应、以及还在 Go 1.26 及更早的环境，手动 io.Copy(io.Discard) 仍然是连接复用的前提。

为什么 body 不读完，连接就会被丢弃？

TCP 是字节流，没有消息边界。上一次响应的残留字节会被当成下一次响应的开头，HTTP 解析直接错位。客户端无法确认读完，就不敢把连接放回连接池，Go 1.26 及更早的 Transport 选择直接断开。

自动排空的限额是多少？

两个先到为准：256 KiB（源码常量 maxPostCloseReadBytes = 256 << 10）和 50 毫秒（maxPostCloseReadTime）。数值核验自 Go 1.27.1 源码 transport.go 与 go.dev/doc/go1.27。

升到 Go 1.27 程序会变慢吗？

官方口径是对多数程序 no-op 或性能提升。少数配置不当的程序（MaxIdleConns 设成 0、每个请求新建 Client）可能变慢，可设 DisableKeepAlives 关闭复用；release notes 指出这类劣化本身就说明 Transport 用法有问题。

你是哪一派#

这篇发出去之前，我把评论区会有的三种人先列出来：

  • A. 肌肉记忆派：io.Copy(io.Discard, resp.Body) 写了五年，代码能跑，不打算改——生产还在 1.26 及更早的话，你是对的
  • B. 新极简派：已经升 1.27，把手动排空当死代码删了——限额内的中小响应，你也是对的
  • C. 等等党：go.mod 里的版本还是 1.22，规矩怎么改跟你无关——直到某天升级后性能莫名变好，你会想起这篇

你的服务在生产环境观察过连接复用率吗？Transport trace、metrics、甚至 netstat 采样都行，贴一个真实数字——比任何一派的说法都有价值，攒够一批我出一篇「连接复用实战调查」的续篇。
