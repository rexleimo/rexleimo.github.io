Herdr 远程工作三条路径：SSH 里跑 herdr、--remote 薄客户端、手机 SSH，怎么选

官方原则是「在活儿所在的地方跑 Herdr，从你所在的地方 attach」。本文对比三条远程路径的真实差别：SSH 进去跑 herdr（tmux 式，最简单，但完全跑在远端、读不到本地剪贴板）、herdr --remote（远端 server 拥有 pane 并推流，本地 Herdr 用本地主题和键位画 UI，可桥接图片剪贴板粘贴）、手机 SSH（不需要 app 或 web dashboard，TUI 自适应窄屏）；外加 herdr agent attach / terminal attach 的直接终端接入，以及远程二进制从哪来、版本要不要一致、manage_ssh_config 与 ControlPersist、口令密钥为什么要先 ssh-add。

September 29, 2026 · 5 min · 954 words · 梦兽编程 -  |  English

验证版本： herdr 0.9.2（stable channel）· 本机实测 macOS / Apple silicon · 2026-09-29

官方 how-to-work 那页只有一句话，但它是整个远程模型的总纲：

Run Herdr where the work lives. Attach from wherever you are. 在活儿所在的地方跑 Herdr，从你所在的地方 attach。

支撑这句话的架构事实（核心概念 讲过）：

Herdr 是一个后台 session server，加一个或多个 terminal client。 pane 在 server 里持续运行。client 负责 attach、detach 和渲染会话。

所以「远程」这件事的真正问题不是「能不能连上」，而是： server 在哪、UI 在哪、剪贴板归谁、键位归谁。这四个问题决定了三条路径的全部差别。

先给结论：

默认选 herdr --remote <host>。 它是唯一一条**「远端跑活儿 + 本地画 UI」**的路， 因此也是唯一能桥接本地桌面能力（图片剪贴板粘贴）的路。 已经在 SSH shell 里生活、或者用手机 → 直接 ssh 进去跑 herdr，最省事。 要在一个窗口里同时看多台机器 → 别用这三条，用 herdr machine add（见上一篇 ）。

一、三条路径总览#

A · SSH 里跑 herdrB · herdr --remoteC · 手机 SSH
命令ssh you@server 然后 herdrherdr --remote workboxssh you@server 然后 herdr
server 在哪远端远端远端
client / UI 在哪远端本地远端（手机终端里）
本地桌面剪贴板❌ 读不到（只有普通终端文本粘贴）✅ 可桥接，含图片粘贴❌
键位来源远端 config本地 config（可切远端）远端 config
主题远端本地主题与呈现设置远端
适合谁已经生活在 SSH shell 里的人、想要最简单设置想让远程会话「感觉像本地」出门在外临时看一眼

官方对 A 的适用场景写得很具体：

当你已经生活在 SSH shell 里、当你在用手机上或平板上的 SSH client、 或者当你想要最简单的设置时，用这条路。

对 B：

当你想让远程会话感觉像本地时用这条路。

A 和 C 其实是同一条路（C 只是终端换成了手机），所以后面我把重点放在 B， 以及三条路共用的那些底层机制。

二、路径 A：SSH 进去跑 herdr#

ssh you@server
herdr

行为和一个终端多路复用器完全一样：

  • 你的 shell 是远程的
  • Herdr server 是远程的
  • agent 和 pane 跑在远程机器上
  • ctrl+b q detach、断开连接，然后 SSH 回去再跑一次 herdr

唯一的代价（官方明写）：

如果你先 SSH 进 server 再在那儿跑 herdr，Herdr 完全跑在那台 server 上， 除了普通终端文本粘贴之外无法访问你的本地桌面剪贴板。

对纯文本工作流这无所谓；对「截个图丢给 agent 看」这种流程就很致命——那要用路径 B。

三、路径 C：手机#

Herdr 在手机上工作，不需要移动 app，也不需要 web dashboard。 装任意 SSH client，连到跑 agent 的那台机器，在上面启动 Herdr。

ssh you@server
herdr

同一个持久 Herdr 会话就在你的手机终端里打开了。 官方特别提到：TUI 会适配窄屏，所以你可以在不离开 SSH 的情况下 查看 agent、切换 workspace、检查 pane。

iPhone 上官方点名 moshi 外部链接 效果不错。

这条路径的价值不在功能多少，而在它复用的是同一个 server： 你在笔记本上 detach 的会话，手机上 attach 上去看到的是同一批活着的 agent。

四、路径 B：herdr --remote（薄客户端）#

herdr --remote workbox
herdr --remote ssh://you@server:2222

分工：

远程 server 持有运行中的 pane，并通过 SSH 发送它们的终端内容和会话状态。 你本地的 Herdr 画 UI，包括它的侧边栏、菜单和主题。

为什么「client 在本地」这件事这么重要#

因为本地桌面能力可以被桥接过去。官方给的例子是图片剪贴板粘贴：

因为 client 在本地运行，Herdr 可以把本地桌面特性桥接进远程会话， 例如图片剪贴板粘贴——做法是把图片复制到一个远程临时文件，然后粘贴那个路径。

这是路径 A 结构上做不到的事：A 的 client 在远端，它根本不知道你本地剪贴板里有什么。

键位归谁（一个很容易忽略的细节）#

默认情况下，herdr --remote 为那次 attach 使用你本地 Herdr 的键位。 这样即使远程 server 的配置不同，本地的肌肉记忆也保持有效。 编辑完本地键位后，用 UI 的 reload config 动作就能应用，不需要 detach。 想要远程 server 的配置时，用 --remote-keybindings server。

⚠️ 一条安全设计：

本地的自定义命令键位不会被发送，因为那些命令会在远程主机上运行。

也就是说你在本地 [[keys.command]] 里配的 lazygit 弹窗， 在 --remote 会话里不会出现——它不会拿你本地的命令定义去远端执行。

用 SSH config 复用目标#

Host workbox
  HostName server.example.com
  User you
  Port 2222

herdr --remote workbox

远程命名会话#

herdr --remote workbox --session agents

--session 和 --remote 组合，attach 到远程主机上的一个命名会话。

五、三条路共用的底层机制#

这一节的内容对 A/B/C 都适用（差别只在「谁触发」）。

平台与版本#

支持矩阵（remote attach 和保存的 SSH 机器）：

本地 client远程 host
Linux / macOS / WindowsLinux 或 macOS，x86_64 或 aarch64
Linux / macOS / WindowsWindows，仅 x86_64

一旦双方都支持 stable endpoint generation，local 和 remote 版本就不需要匹配。

远端二进制从哪来（三种来源）#

在 Linux 和 macOS 宿主机上，Herdr 的查找顺序：

  1. 优先用远程 PATH 上一个已兼容的 herdr
  2. 然后检查常见的直接安装、Homebrew、mise 和 Nix profile 安装路径

在 Windows 宿主机上：检查 PATH 和活动的托管 release。

如果不存在兼容的二进制：

运行方式行为
交互式提示安装或更新一个
非交互式失败，而不是修改宿主机

安装位置：Linux 和 macOS 用 ~/.local/bin/herdr； Windows 用完整的 Windows 包和它的 app-local ConPTY 运行时。 如果 ~/.local/bin 不在远程 PATH 上，Herdr 会在安装后给出警告。

二进制的三种供给方式：

情况来源
Linux/macOS 宿主机且平台匹配复制当前的本地二进制
Homebrew / mise / Nix 安装、平台不同、或 Windows 宿主机从 https://herdr.dev/latest.json 下载与当前 client 版本匹配的 release asset
本地 build 或自定义包用 HERDR_REMOTE_BINARY 指定本地文件路径
HERDR_REMOTE_BINARY=target/release/herdr herdr --remote workbox

Linux 或 macOS 目标用裸的 Herdr 可执行文件；Windows 目标用完整的 herdr-windows-x86_64.zip 包。

SSH 连接的托管方式#

默认情况下，herdr --remote 通过一个临时 SSH config 来跑远程安装和 bridge： 它先包含你的 SSH config，然后追加 fallback keepalive 设置。 已有的用户 keepalive 设置优先（win）。

  • Linux 和 macOS client 还会用一个「每次 attach 私有的 control socket」做连接复用
  • Windows OpenSSH 不用（没有这个复用）
  • 想完全不用 Herdr 生成的 config 和 control socket：
[remote]
manage_ssh_config = false

之后就是裸 ssh。

认证#

  • remote attach 使用你正常的 OpenSSH 认证
  • 如果目标用的是带口令保护的密钥，而你处在非交互 shell、脚本、CI 任务或手机终端里 （也就是没法显示口令提示的地方），先把密钥加载进 ssh-agent：
ssh-add
herdr --remote workbox
  • 任何远程认证失败，先用 ssh workbox 验证普通 SSH 访问，然后再跑一次 herdr --remote workbox

版本不同会不会重启我的远端 server？#

版本差异本身不会替换或重启一个运行中的远程 server。 remote attach 只有在 server 缺乏必需的兼容性或 detached-daemon 支持时， 才会在停止它之前询问。默认答案是 No——停止 server 会结束它的 pane 进程。

确实需要那次一次性升级、又想保住 pane 进程时，显式加 --handoff：

herdr --remote workbox --handoff

（handoff 到底保住什么、不保住什么，见会话状态五条路径 。 再强调一次：它是实验特性，machine add 不使用它。）

六、第四条路：直接终端 attach（不开整个 workspace UI）#

这条严格说不是「远程路径」，但它解决的是同一个问题的另一面： 我只想要那一个 agent 的终端，不想要整个 UI。

完整的 Herdr attach 会打开整个 workspace UI。直接 attach 在你当前的终端里打开一个由 server 拥有的终端。

可用性：Linux 和 macOS，不是原生 Windows。

# 按 agent 目标
herdr agent attach reviewer

# 按 terminal ID
herdr terminal attach term_abc123

行为：

  • 先流式传输当前渲染的终端状态，然后是 live ANSI 帧
  • 输入直接送到那个终端
  • ctrl+b q detach
  • ctrl+b ctrl+b 发送一个字面的 ctrl+b（否则你永远打不出前缀键本身）
  • ⚠️ 只有一个可写的 direct attach client 拥有某个终端的输入和 resize —— 要抢过来用 --takeover：
herdr terminal attach term_abc123 --takeover

给第三方桥用的两种模式#

如果你只需要渲染后的终端字节，用只读的 terminal session observer：

herdr terminal session observe w1:p1 --cols 120 --rows 40
  • 打印换行分隔的 JSON terminal.frame 记录，ANSI 字节是 base64
  • server 关闭流时打印一条 terminal.closed 记录
  • 多个 observer 可以同时看同一个终端，不占用 input、resize、scroll 或 takeover 所有权

需要交互式桥时，用可写的 terminal session controller：

herdr terminal session control w1:p1 --takeover --cols 120 --rows 40
  • 打印同样的换行分隔帧记录，并从 stdin 读换行分隔的 JSON 命令
  • terminal.input 发送文本或 base64 字节
  • terminal.resize 改变 controller 视口
  • terminal.scroll 滚动已 attach 的视口
  • terminal.mouse 在某个 cell 上发送鼠标事件给已启用鼠标上报的应用
  • terminal.release 关闭 controller
  • 同一时刻只有一个 controller 拥有 input 和 resize

这两个命令是模块 4「编程化控制」的地基——想做一个网页版状态面板或者钉钉机器人， 从这里开始，而不是去解析 TUI。

七、怎么选：一张决策表#

你的情况选哪条
代码和凭据都在本地herdr，别折腾远程
已经常年 ssh 到那台机器上干活路径 A（ssh + herdr），最贴近你现有习惯
想让远程会话有本地的主题、键位、图片粘贴路径 B（herdr --remote）
手机 / 平板临时看一眼 agent 状态路径 C（SSH client + herdr）
一个窗口同时看本地 + 多台远程herdr machine add（上一篇 ）
只想要某一个 agent 的终端，嵌进别的工具里herdr agent attach <name>
做只读监控面板 / 录制herdr terminal session observe
做可交互的机器人或网页控制台herdr terminal session control --takeover
CI / 脚本里连远程路径 B 的非交互形式——注意它不会替你装远端二进制，缺就直接失败

八、避坑指南#

  1. 想贴图给远端 agent，就必须用 --remote。 SSH 进去跑 herdr 结构上读不到本地桌面剪贴板。
  2. --remote 默认用本地键位，不是远端的。 发现「远端配好的键位不生效」时， 加 --remote-keybindings server。反过来，本地自定义命令键位不会被发到远端。
  3. 改完本地键位不用 detach。 用 UI 的 reload config 动作。
  4. 非交互场景先 ssh-add。 带口令的密钥在脚本 / CI / 手机终端里没法弹提示，会直接认证失败。
  5. 认证失败先 ssh workbox。 把问题分成「SSH 本身不通」和「Herdr 的问题」两类，能省一半时间。
  6. 别在 CI 里指望 Herdr 自动装远端二进制。 非交互运行会失败而不是修改宿主机—— 这是正确的行为，但你需要在镜像里预装。
  7. ~/.local/bin 不在远程 PATH 上会收到警告。 别忽略它，否则下次 attach 又要重新发现。
  8. 不要为了版本对齐去停远端 server。 版本不必一致；只有缺兼容性/detached-daemon 支持时才会问你， 而默认答案是 No。
  9. --handoff 是实验特性，且 machine add 不用它。 只在明确需要「替换 server 但保住 pane 进程」时用。
  10. ctrl+b ctrl+b 才能发出一个字面的 ctrl+b。 直接 attach 时忘了这条会以为 pane 里的程序坏了。
  11. direct attach 的所有权是独占的。 第二个人 attach 不进去不是 bug，用 --takeover 明确接管。
  12. Windows 没有 direct terminal attach，也没有 control socket 复用。 规划跨平台自动化时先确认这条。

常见问题

ssh 进去跑 herdr 和 herdr --remote 有什么区别？

前者 Herdr 完全跑在服务器上，行为就像一个终端多路复用器，读不到你本地桌面剪贴板（超出普通终端文本粘贴之外）。后者远端 server 拥有运行中的 pane 并通过 SSH 发送终端内容和会话状态，你本地的 Herdr 负责画 UI（含侧边栏、菜单、主题），因为 client 在本地，所以能把本地桌面特性桥接过去，例如图片剪贴板粘贴会先复制到远程临时文件再粘贴那个路径。

手机上用 Herdr 需要装 app 吗？

不需要移动 app，也不需要 web dashboard。装任意 SSH client，连到跑 agent 的那台机器，在上面执行 herdr，同一个持久会话就在手机终端里打开了。TUI 会适配窄屏，可以查看 agent、切换 workspace、检查 pane。官方提到 iPhone 上 moshi 这类 app 效果不错。

herdr --remote 用的是本地键位还是远端键位？

默认用你本地 Herdr 的键位，这样即使远端 server 配置不同也能保持本地肌肉记忆。改完本地键位后用 UI 的 reload config 动作即可生效，不用 detach。想要远端 server 的配置就加 --remote-keybindings server。注意本地的自定义命令键位不会被发送，因为那些命令会在远程主机上运行。

本地和远端的 Herdr 版本必须一致吗？

不必。一旦双方都支持 stable endpoint generation，local 和 remote 版本就不需要匹配。远端二进制的来源分三种：Linux/macOS 宿主机且平台匹配时可以复制当前本地二进制；Homebrew/mise/Nix 安装、平台不同、或 Windows 宿主机则从 https://herdr.dev/latest.json 下载与当前 client 版本匹配的 release asset；本地 build 或自定义包用 HERDR_REMOTE_BINARY 指定路径。

远端没有 Herdr 会怎样？

在 Linux 和 macOS 宿主机上，Herdr 先找远程 PATH 里已兼容的 herdr，再检查常见的直接安装、Homebrew、mise 和 Nix profile 路径；Windows 宿主机检查 PATH 和活动的托管 release。如果找不到兼容二进制，交互式运行会提示安装或更新一个，非交互运行则直接失败而不是修改宿主机。Linux/macOS 装到 ~/.local/bin/herdr；若 ~/.local/bin 不在远程 PATH 上，安装后会给出警告。

只是版本不同，remote attach 会重启我的远端 server 吗？

不会。版本差异本身不会替换或重启一个运行中的远程 server。只有当 server 缺乏必需的兼容性或 detached-daemon 支持时，remote attach 才会在停止它之前询问，默认答案是 No（停止会结束它的 pane 进程）。确实需要那次一次性升级、又想保住 pane 进程时，才显式加 --handoff。
