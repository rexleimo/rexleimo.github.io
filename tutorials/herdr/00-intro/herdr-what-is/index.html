Herdr 是什么：为什么 tmux 不够用了

Herdr 是「你的编码智能体住在上面的运行时」：Rust 写的 Apache-2.0 项目，后台 server 持有真实终端，TUI / CLI / 纯 SSH 都只是 client。它比 tmux 多的那部分是语义化的 agent 状态（blocked / working / done / idle）、直接 attach 到单个 agent、以及给脚本和 agent 用的读-发-等 API。本文用本机 herdr 0.9.2 的真实输出说明差别，并讲清哪些人不需要它。

September 29, 2026 · 4 min · 839 words · 梦兽编程 -  |  English

验证版本： herdr 0.9.2（stable channel，2026-09-29 发布）· 本机实测平台 macOS / Apple silicon · 2026-09-29

这篇只回答一个问题：Herdr 到底是什么，凭什么它不是「又一个 tmux」。

先给结论，后面全是论证：

Herdr 是一个运行时（runtime），不是一个应用（app）。 后台 server 持有真实终端进程， 你的 agent 住在里面；TUI、CLI、甚至一个纯 SSH 会话，都只是接上去的 client。 tmux 也有这个 server/client 结构——Herdr 多出来的那部分是语义： 它知道哪个 pane 里是 agent、那个 agent 现在是 blocked 在等你还是 working， 以及怎么等它而不是轮询它。

一、先看一个你大概已经遇到的场景#

假设你今天同时开着这么几件事：

  • 一个 agent 在重构后端，跑了 20 分钟
  • 一个 agent 在写测试，中途要它自己确认一个删除操作
  • 一个 npm run dev 在跑前端
  • 一个日志窗口
  • 一个 SSH 到开发机的会话，上面还有两个 agent

现在问你：哪一个在等你？

用 tmux 的话，答案是「不知道，自己一个个切过去看」。tmux ls 会告诉你有 3 个 session， 但不会告诉你哪个 session 里有个 agent 正卡在「需要你批准这条命令」上。你只能 prefix + n 一个个翻，或者盯着屏幕等通知。

这不是 tmux 的 bug。tmux 诞生于 2007 年左右，它的设计目标是「让人类的终端会话活下来」—— 持久化 PTY、detach、SSH 回来接上。这个目标它完成得非常好，Herdr 也把这份继承完整保留了。 它没做的是「理解 pane 里跑的是什么」，因为在它诞生的年代，pane 里跑的只有 shell。

2026 年的情况变了：pane 里跑的是主动进程。它们自己干活、干到一半停下来等你批一个命令、 干完了等你看结果。于是「哪个在等我」成了每天都要回答几十次的问题。

Herdr 就是照着这个问题设计的。官方仓库的描述只有七个词：

the runtime your coding agents live on

二、把定义拆成三层#

官方文档给的定位是 Terminal workspace manager for AI coding agents。拆开看是三层能力， 每一层都对应一个你会真实用到的动作。

第 1 层：它是一个多路复用器（这层和 tmux 一样）#

后台一个 server 进程持有真实终端（PTY），client 接上去渲染。 你 detach、关终端窗口、断 SSH，pane 里的进程照跑。

herdr            # 启动或接上默认后台会话
# ctrl+b 然后 q  → detach，agent 继续跑
herdr            # 再跑一次，接回同一个会话
herdr server stop  # 真想全部停掉，只有这一条

这里有个新手最常犯的错：以为关掉窗口就等于停了。不是。想停就 herdr server stop。

第 2 层：它是鼠标优先的（这层和 tmux 相反）#

tmux 的门槛是键位。Herdr 明确把鼠标当第一入口，键盘是可选层：

  • 点击窗格 / 标签 / 工作区 / agent 来聚焦
  • 拖动分割边框改大小
  • 右键菜单里分割窗格、新建标签
  • 拖选文字即复制到剪贴板（不需要 ctrl+c）；双击选中一个 token，第二下按住拖动可按整词扩展
  • ctrl + 点击打开 pane 里的链接（支持 OSC 8 超链接和 http(s)://，包括被折行的链接）

官方文档原话：No keybindings are required to use Herdr.

如果你就是不喜欢终端程序抢鼠标，一行配置关掉：

[ui]
mouse_capture = false

第 3 层：它是 agent 感知的（这层是它存在的理由）#

Herdr 会识别 pane 里的 coding agent，给出五种状态之一，并在侧边栏按 workspace 汇总。 这是本机 herdr agent list 的真实输出（格式化过换行，内容未改）：

{"id":"cli:agent:list","result":{"agents":[
  {"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-videos",
   "focused":true,"pane_id":"w3:p1","tab_id":"w3:t1",
   "terminal_title":"π - rex-videos","workspace_id":"w3"},
  {"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-hugo",
   "pane_id":"w3:p2","terminal_title":"π - rex-hugo"},
  {"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-hugo",
   "pane_id":"w3:p4","terminal_title":"π - rex-hugo"}],"type":"agent_list"}}

注意几件事：

  • 它认出了 agent 的名字是 pi，不是「某个 node 进程」
  • 它知道每个 agent 的 cwd（哪个项目）、pane_id、tab_id、workspace_id
  • 它抓到了终端标题 π - rex-hugo
  • 状态是 working

而这台机器上一个 Herdr 集成都没装：

$ herdr integration status
pi: not installed (/Users/rex/.pi/agent/extensions/herdr-agent-state.ts)
omp: not installed (/Users/rex/.omp/agent/extensions/herdr-omp-agent-state.ts)
claude: not installed (/Users/rex/.claude/hooks/herdr-agent-state.sh)
codex: not installed (/Users/rex/.codex/herdr-agent-state.sh)
hermes: not installed (/Users/rex/.hermes/plugins/herdr-agent-state/__init__.py)
...（共 18 个）

这是理解 Herdr 的第一个关键点：检测和集成是两套东西。 检测靠「前台进程 + 屏幕清单（screen manifest）+ 可选集成」三条途径，零配置就有基本能力； 集成（往 agent 的 hook / extension 目录里装一个上报脚本）额外买到生命周期级状态和 agent 原生会话恢复——但它不一定替代屏幕检测。这块模块 3 会整篇拆开讲。

三、和 tmux / zellij 的差别，逐条对齐#

先说一样的部分，因为这部分最容易被夸大：

  • 都是 server + client，pane 在 server 里活着
  • 都支持 detach / reattach，都能 SSH 回来接上
  • 都有前缀键（Herdr 默认也是 ctrl+b，和 tmux 一样）
  • 都能分割窗格、开多标签、保留滚动历史

再说不一样的六条：

维度tmux / zellijHerdr
它眼里的 pane一个 PTY，里面跑着什么它不关心会尝试判定「这是哪个 agent」，并跟踪其状态
状态语义无。tmux ls 只给 session 名blocked / working / done / idle / unknown 五态，按 workspace 汇总到侧边栏
等一个 agent自己轮询（capture-pane + grep）一等公民：herdr agent wait，以及 socket API 的状态订阅
交互入口键盘优先，鼠标支持是后加的鼠标优先，键盘是可选层（可 mouse_capture = false 关掉）
多机器每台机器各跑一个 tmux，你自己切窗口Local 和保存的 SSH 机器在同一个窗口里，agent 列表合并，各连接独立重连
直连单个 agent无对应概念有：直接 attach 到某一个 agent 的终端

官方 compare 页 外部链接 还给了一个更大的矩阵，把 9 个工具分成五类。 注意这是厂商自己做的对比，天然有立场，我把它列出来是因为分类维度本身有参考价值：

类别代表「你关掉正在看的那个东西之后，活还在吗」
runtime + clientsHerdr在。server 持有终端，TUI 崩了 agent 也不知道
终端复用器tmux / zellij在。detach 就行，但没有 agent 语义
终端应用cmux / Warp靠 session restore。工作搬进了它的窗口、它的渲染器
进程面板Solo只在 App 开着的时候。它盯的是 dev 栈的 up/down
管理型 AppConductor / Emdash / Superset只在 App 开着的时候。退出 App，agent 跟着停

官方自己点出了那张表里最关键的一行：what happens to the agents when the thing you’re looking at goes away——当你正在看的那个东西消失时，agent 会怎样。

我认同这个判断标准，因为它对「跑长任务的 agent」是要命的：一个 App 形态的工具， 你为了省内存退出它，八个跑了半小时的 agent 就没了。而 runtime 形态下， client 是可丢弃的。

顺带说清楚一件事：这几类不是敌人。Herdr 官方也这么说——它可以和一个 worktree/diff 管理器配对用，也可以跑在你喜欢的任何终端里（ghostty / kitty / iTerm / alacritty 都不用换）。

两点值得注意：

  1. 版本号还是 0.9.x，不是 1.0。它迭代很快（13 天一个 stable，中间几乎每天一个 preview）， 这对使用者意味着：好处是修得快，代价是 preview channel 明确「可能回退（can regress）」。 生产环境老老实实待在 stable。
  2. Rust + Apache-2.0 这两条决定了它可以被审计、可以被自构建（官方给了 Nix flake）， 这对企业内网环境是硬指标。

五、避坑指南（这一篇就该记住的 5 条）#

  1. 不要在 Herdr pane 里再跑 herdr。 官方明确说 Herdr by design 阻止嵌套启动。 怎么判断自己是不是已经在里面：echo $HERDR_ENV，值为 1 就是。 （本专栏所有实测都在 Herdr pane 里做的，HERDR_ENV=1、TERM_PROGRAM=herdr。）
  2. 不要给 Herdr 喂 tmux 配置。 它不吃 .tmux.conf，配置文件是 ~/.config/herdr/config.toml（Windows 是 %APPDATA%\herdr\config.toml）， 而且没有配置文件也能正常跑。想看全部默认值：herdr --default-config（本机实测 377 行，全是注释掉的默认值）。
  3. 关窗口 ≠ 停。 pane 和 agent 都还在 server 里。真想停：herdr server stop。 反过来，如果你的 agent 莫名其妙「消失了」，先查是不是 server 被停了或者机器重启了—— 这两种情况的恢复路径不一样，见模块 1 第 3 篇。
  4. herdr update 只对直装（installer 装的）有效。 Homebrew / mise / Nix 装的必须用各自的包管理器升级， 否则会出现「client 是新版、server 还是旧版」的错配。查错配：herdr status 看 endpoint_compatible 和 update.server_binary_stale。
  5. 别指望装了集成就万事大吉。 官方文档反复强调：集成可能提供生命周期状态、原生会话恢复， 或者两者都给，但不一定替代屏幕检测。诊断顺序永远是先 herdr agent list（看它看到什么）、 再 herdr agent explain <target> --json（看它为什么这么判）、最后才是 herdr integration status。

六、哪些人不需要 Herdr#

说清楚反面，比一味夸有用：

  • 你只在本地跑一个 agent，跑完就看。 一个普通终端窗口 + agent 自己的通知就够了，多一个常驻 server 是净负担。
  • 你需要的是一个更好的终端。 Herdr 明确不替换你的终端，它跑在你已有的终端里。想要新渲染器、新补全体验，那是 ghostty / Warp / kitty 的活。
  • 你需要的是 worktree / diff / review 队列管理。 那是 Conductor / Emdash / Superset 这类管理型 App 的核心能力，Herdr 只是「与它配对」。
  • 你在 Windows ARM64 上要原生构建。 现在跑的是 x86_64 构建 + Windows 模拟，能用但不是原生。
  • 你完全不接受后台常驻进程。 Herdr 的整个价值都建立在「server 比 client 活得久」上，不接受这个模型就用不了它。

下一步#

先把安装与验证 走完——那一篇会给你一份能自证装对了的清单 （五种安装渠道、stable/preview 两个 channel、以及 herdr status 里每个字段该怎么读）。

装好之后，如果你觉得「概念还是有点绕」，直接读核心概念 ： session / workspace / tab / pane / agent / mode 六层，一次讲清各自该按什么粒度用。

常见问题

Herdr 是什么？

官方的两句话定义：terminal workspace manager for AI coding agents（面向 AI 编码智能体的终端工作区管理器），以及仓库描述 the runtime your coding agents live on（你的编码智能体住在上面的运行时）。技术上它是一个多路复用器：后台 server 持有真实终端进程，client 接上去渲染。

Herdr 和 tmux 的区别是什么？

持久化那部分两者一样（server 持有 PTY、detach 后进程照跑、可以 SSH 回来）。差别是 Herdr 知道哪个 pane 里是 agent、它现在是 blocked 还是 working、怎么等它而不是轮询它；另外 Herdr 鼠标优先，且 TUI / CLI / 纯 SSH 都是同一个 runtime 的 client。

Herdr 是开源的吗？用什么写的？

是。仓库 github.com/herdrdev/herdr，语言 Rust，许可证 Apache-2.0，2026-03-27 建仓，截至 2026-09-29 约 4.1 万 star。官方也提供 Nix flake 从源码构建。

Herdr 支持哪些平台？

stable channel 提供 Linux、macOS、Windows x86_64 二进制。Windows 已 GA 但有平台限制；Windows ARM64 跑的是 x86_64 构建 + Windows 模拟。

用 Herdr 必须背快捷键吗？

不必。Herdr 是鼠标优先的：点击窗格/标签/工作区、拖动分割线、右键菜单分割和新建、拖选即复制。键盘是可选层，前缀键默认 ctrl+b，prefix+? 可以随时列出当前生效的全部绑定。

不装任何集成，Herdr 也能认出我的 agent 吗？

能。检测来自前台进程、屏幕清单和可选集成三条途径。本机实测：18 个官方集成全部 not installed 的情况下，herdr agent list 仍然正确识别出 3 个 pi agent 且状态为 working。集成买到的是更可靠的生命周期状态和 agent 原生会话恢复。
