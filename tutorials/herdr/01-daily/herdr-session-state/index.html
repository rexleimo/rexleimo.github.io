Herdr 会话状态五条路径：detach、快照恢复、历史回放、agent 原生 resume 与 live handoff

「关掉窗口 / 断 SSH / 升级 Herdr / 机器重启之后，我的 agent 还在吗」这个问题有五个不同答案。本文逐条拆 Herdr 的五条状态路径：live persistence（detach 后进程照跑）、snapshot restore（布局回来但进程没了，含 session-backups 恢复副本与 48 份 session-snapshots 布局快照）、pane screen history replay（默认关闭的实验特性）、native agent session restore（默认开启，含 18 个 agent 的最低集成版本与 resume 命令表）、以及 live handoff（实验性、opt-in）；并给出四条路径的优先级与开启建议。

September 29, 2026 · 6 min · 1111 words · 梦兽编程 -  |  English

验证版本： herdr 0.9.2（stable channel）· 本机实测 macOS / Apple silicon · 2026-09-29

跑长任务的 agent 最怕一件事：它没了。而「没了」在 Herdr 里其实是五种完全不同的情况， 恢复手段也完全不同。搞混的代价是——你以为它还在跑，其实两小时前就被你停了； 或者你以为全丢了，其实一条命令就能接回原对话。

先给结论：

区分四个独立的问题，别问「还在不在」这种复合问题： ①进程还活着吗 ②布局回来了吗 ③屏幕内容回来了吗 ④agent 对话接上了吗。 detach 四个都是「是」；server 重启只有②是「是」，③④要分别开开关； live handoff 是「尽量四个都是」，但它是实验特性且要 opt-in。

官方给的那张矩阵（原文照录，这是全篇最重要的一张表）：

情况进程还在跑布局回来最近屏幕回来agent 对话接上
detach 后重新 attach✅ 是✅ 是✅ 是，来自活着的终端✅ 是，因为进程从没停
server 重启❌ 否✅ 是⚠️ 仅当开了 pane screen history⚠️ 仅当有 native agent session restore
升级，不带 --handoff⚠️ 兼容的 server 继续跑；需要重启的 server 可能要 stop/restart✅ 重启后是⚠️ 仅当开了 pane screen history⚠️ 仅当有 native agent session restore
升级，带 --handoff🔶 尽力而为（支持的运行中 server）✅ 是✅ 是，handoff 成功则来自活着的终端✅ 是，handoff 成功则进程一直在

上面那张图里那条虚线是官方明写的规则：如果 native agent session restore 适用于某个 pane， Herdr 就恢复 agent 会话，而不是为那个 pane 回放保存的屏幕历史。 两者不会叠加。

路径 1 · Live persistence：detach（最强的一条）#

ctrl + b q      # detach，pane 和 agent 继续跑
herdr           # 之后重新 attach

官方原话：This is the strongest persistence path because the original processes never stop. ——这是最强的持久化路径，因为原进程从没停止过。

server 在后台持有 pane。detach 的只是 client。所以：

  • shell、agent、开发服务器、测试、任何命令进程全都在跑
  • 重新 attach 后看到的是活着的终端，不是快照
  • agent 的对话当然也在，因为它压根没被打断

直接关掉终端窗口等效于 detach。

真想停：

herdr server stop

这一条是新手最大的认知坑，鼠标工作流那篇 也强调过： 关窗口 ≠ 停。

路径 2 · Snapshot restore：布局回来，进程没了#

server 停了又起来，原来的 pane 进程已经不存在。Herdr 恢复保存的会话形状：

workspaces、tabs、panes、cwd、layout、focus

明确不保留：运行中的 shell、服务器、测试、任意进程。 走不到更强恢复路径的 pane，会以**「保存在原目录下的新 shell」**回来。

一个很贴心的失败行为#

如果保存的目录不可用，或者 shell 起不来：

pane 会带着一个错误留在布局里，而不是消失、也不是被挪到你的 home 目录。 它保存的目录和 agent session 引用保持完整。

修复目录或 shell 配置后重启 server 重试，或者显式关掉这个 pane 把它移除。 （对比一下 tmux：目录没了窗口就没了。Herdr 选择「保留证据」。）

cwd 是怎么确定的#

保存时，在操作系统暴露 shell 目录的地方，Herdr 优先用活 shell 的目录； shell 退出后，保留最后一次确认过的目录。其他平台上退回用 shell 上报的目录。

这个区别在「cd 之后马上关窗口」这种场景下很重要——前者是内核层面的真相，后者依赖 shell 集成。

session.json 坏了怎么办#

如果 session.json 读不出来、解析失败、或者需要更新版本的 Herdr：

  1. Herdr 记录为什么加载失败
  2. 在保存或清除这个替代会话之前，把原始字节保存到 session.json 旁边的 session-backups/
  3. 把恢复路径记为日志字段 persist.backup
  4. 启动时缺失的文件，会在首次保存或清除之前再检查一次

规则细节：

  • 保留最近三份恢复副本；只有在新副本安全写入之后才裁剪旧的
  • 如果保存副本失败，autosave 和 shutdown 会保持原文件不动并记录失败，下次保存请求时重试
  • 副本永远不会被自动恢复。 要恢复就：停掉受影响的 server → 把恢复文件覆盖到它的 session.json → 重启
  • 恢复副本不包含 pane 屏幕历史
  • 这类「加载失败恢复副本」和正常的快照历史是两套东西

路径 2.5 · 关机保护与 48 份布局快照#

systemd-logind 关机延迟（仅 Linux）#

在有 systemd-logind 的 Linux 上，Herdr 监听宿主机的关机警告， 并请求一小段延迟用来保存和停止——这发生在 logind 继续关机流程之前。

限制（官方都写了）：延迟时长由操作系统限定，Herdr 不会无限期阻止关机； 没有 logind 就没有这个保护；不覆盖强制关机、断电、或在警告到达前就被杀的进程。

session-snapshots/：最多 48 份布局快照#

全平台都有，位置在 session.json 旁边。规则：

  • 第一份保存的布局立即复制
  • 之后的保存或清除，可以追加一份「上一次保存的布局」的快照，最多每 15 分钟一次
  • 未变化的快照不会重复
  • 这个间隔跨 server 重启保留——所以「一阵 pane 退出或重启」没法把旧布局全部轮转掉
  • ⚠️ 最近的改动可能不在恢复快照里

正常的 pane 关闭仍然会更新 session.json。没有恢复提示，也不会自动恢复旧快照。

手动恢复布局的四步（官方流程）#

# 1. 找到受影响的 session 目录
herdr session list --json

# 2. 停掉那个 server（默认会话用 server stop，命名会话用 session stop <name>）
herdr server stop
# 或：herdr session stop work

# 3. 备份当前 session.json，然后把 session-snapshots/ 里选中的那份覆盖上去
#    （文件的修改时间能告诉你快照是什么时候拍的）

# 4. 重新启动会话
herdr

快照里有什么、没什么：

有没有
布局（workspace/tab/pane/焦点）运行中的进程
agent session 引用pane 屏幕历史

官方还加了一句安全提醒：把它们当作私有会话数据对待。 另外，快照写入失败会被记录，但不会阻止主会话保存。

路径 3 · Pane screen history replay：找回屏幕内容#

server 完全重启后，在不恢复旧进程的前提下把最近的终端内容找回来。

默认关闭，理由官方写得很直白：

因为 pane 输出可能包含密钥、token、提示词和命令输出。

开启：

[experimental]
pane_history = true

开启后，历史存在 session.json 旁边的 session-history.json。 官方要求：把 Herdr 的 config/session 目录当终端历史一样对待（也就是：别随便同步、别随便提交）。

两条硬限制：

  1. 只有布局与保存时完全匹配才会回放。 不同布局来的历史会被忽略——包括手动快照恢复之后的情况
  2. 没有布局校验字段的旧历史文件也会被忽略；新保存的历史可以在下次重启时回放

所以这条路径的适用面比想象的窄：它救的是「server 意外挂了，但布局没动过」这种情况。

路径 4 · Native agent session restore：让 agent 接上原对话（默认开启）#

有些 agent 能恢复自己的对话会话。Herdr 可以用官方集成上报的 session 引用， 在 Herdr server 重启后重启受支持的 agent pane。

默认开启。 关掉：

[session]
resume_agents_on_restore = false

触发条件：pane 通过当前的官方 Herdr 集成上报了 native session 引用， 或者 pane 里的 agent 上报了自己的 resume 命令（后者见模块 3 的 给你自己的 agent 加 Herdr 支持 ）。

时机细节（容易被忽略）：

在 client attach 并提供了终端尺寸与主题上下文之后， Herdr 会跨 workspace 和 tab 恢复符合条件的 agent pane，不需要逐个 pane 被聚焦。

也就是说：恢复动作发生在你 attach 的那一刻，而且是批量的。

查你本机的集成版本：

herdr integration install <agent>              # 重装过旧的集成

herdr integration status   # → 18 条 "not installed"

注意这里的因果关系：集成没装 → 没有 session 引用上报 → server 重启后 agent 接不回原对话， 只能回退成新 shell。集成不只是「状态徽章」，它还是原生恢复的前提。

回退规则：不支持、缺失、无效、重复、或过期的 session 引用， 一律恢复成保存目录下的普通 shell——不会报错崩掉，也不会瞎猜。

路径 5 · Live handoff：替换 server 时保住进程#

前四条都是「进程已经没了，怎么重建状态」。handoff 是反过来的：

它试图让当前进程继续活着，而不是在旧 server 停掉之后重建状态。

用途：升级和远程 attach 这类需要替换一个正在运行的 Herdr server 的流程。 它请旧 server 把活的 pane 转交给新 server。

实验特性，opt-in：

herdr update --handoff
herdr --remote workbox --handoff

它保住什么、不保住什么#

✅ 保住（长期、server 拥有的会话状态）❌ 不保住（跨替换边界的临时协调）
pane 的 PTY 与进程in-flight 的 CLI 或 API 请求
agent 身份与持久元数据waits
替换后的 server 需要的 plugin / session 状态订阅流
client socket
pane 之间的消息

官方的建议：client 应该重连并重试这些东西。

64 pane 限制与分批#

更新后的 Unix server 可以通过分批转交在一次 handoff 里送超过 64 个 pane。 但有个前提：发送方 server 必须已经包含这个支持—— 一个更旧的、正在运行的 server 在第一次升级时仍然受它自己的 64 pane 限制。 那个限制可能需要一次正常的 server 重启（会结束 pane 进程）。 分批不改变升级的安装顺序，也不移除其他 handoff 兼容性要求。

什么时候其实不需要 handoff#

这两句官方说明能省掉很多焦虑：

  • herdr update（不带 handoff） 会安装新 client，并让 endpoint-generation-1 的 server 继续跑
  • herdr --remote workbox（不带 handoff） 也会在版本不同的情况下让兼容的远程 server 继续跑

只有一种情况必须停：从 pre-generation-1 的 server 做那次一次性升级。 当你明确想要替换一个受支持的运行中 server 而不丢它的 pane 进程时，才用 --handoff。

还有一个硬性限制：

herdr update --handoff 只适用于由 Herdr 自己的 updater 管理的安装。 Homebrew、mise、Nix 安装通过包管理器更新，所以那些环境里 herdr update 是被禁用的， 也无法执行 live handoff。

命名会话：状态隔离的单位#

想要互相独立的 Herdr server，用命名会话：

herdr session list
herdr session attach work
herdr session attach side-project
herdr session stop work
herdr session delete side-project

一个命名会话有自己的 pane、tab、workspace、socket 和运行时状态，但仍然共享同一份全局配置文件。

两个坑：

  1. 删除时名字必须和 herdr session list 显示的完全一致，包括大小写。 在大小写不敏感的文件系统上，herdr session delete foo 会拒绝删除名为 Foo 的会话
  2. 脚本里一律加 --json：herdr session list --json、herdr session stop work --json、 herdr session delete side-project --json

命名会话也可以走远程：herdr --remote workbox --session agents。

我该开哪些？一张决策表#

你的情况建议
只在本地跑，偶尔关窗口什么都不用配。detach 已经是最强路径
机器会重启 / server 会被停确认 agent 有官方集成且版本够新（路径 4 默认开着，但没集成就没引用）
agent 输出里有敏感信息别开 pane_history（它默认就是关的，这是正确的默认值）
经常需要回看重启前的输出，且输出不含敏感信息开 [experimental] pane_history = true，并把 config/session 目录当终端历史保护
经常升级 Herdr，且有长任务在跑用 herdr update --handoff（前提是 script 安装；包管理器安装用不了）
pane 数超过 64先做一次正常升级让发送方 server 具备分批能力，之后再指望 handoff 送超过 64 个
想彻底避免状态问题一个项目一个命名会话，隔离爆炸半径

避坑指南#

  1. herdr server stop 是不可逆的那一下。 它结束所有 pane 进程。手滑之前想清楚。
  2. 布局快照不会自动恢复，也没有提示。 你必须手动走那四步。所以发现布局不对时先别继续操作， 先去 session-snapshots/ 看修改时间。
  3. session.json 解析失败时，原始字节会被存进 session-backups/，但不会自动恢复。 日志里找 persist.backup 字段拿路径。
  4. pane screen history 只在布局完全匹配时回放。 你手动恢复过快照 → 布局变了 → 历史被忽略。 这两个恢复手段互相排斥，别指望叠加。
  5. native restore 优先于 history replay，且只对一个 pane 生效一次。 同一个 pane 不会「既恢复对话又回放屏幕」。
  6. 没有官方集成 = 没有 session 引用 = 重启后接不回对话。 herdr integration status 是你该定期看的一条命令。
  7. 集成版本太旧同样接不回。 对照上面那张表，herdr integration install <agent> 重装。
  8. 包管理器安装用不了 herdr update --handoff。 Homebrew / mise / Nix 走各自的包管理器， herdr update 在那里是禁用的。
  9. handoff 会打断 in-flight 请求和订阅流。 如果你的自动化正卡在 herdr pane wait 或某个流式订阅上， handoff 之后要重连重试。
  10. Linux 的关机保护不覆盖断电和强制关机。 别把它当成 UPS。
  11. session.json 和 session-history.json 是私有数据。 别提交进 git，别随手同步到网盘。

下一步#

本地这套弄明白了，接下来是把同一套模型延伸到另一台机器： Local 和 SSH 机器放在同一个窗口里、合并 agent 视图、每台机器独立重连—— 连接机器：Local 与保存的 SSH 机器同窗 。

而模块 2 里会反复用到的一个概念，本篇已经埋下了伏笔： 远程 server 拥有 pane，你的本地 Herdr 只负责画 UI——所以「升级远程 server」 和「handoff」这两件事在远程场景下更值得小心。

常见问题

detach 之后进程还在吗？

在。这是最强的一条持久化路径：ctrl+b q 让 client 断开，Herdr server 继续持有 pane、shell、agent、服务器、测试和命令进程。之后执行 herdr 就接回同一个会话，因为原进程从没停过。真正停掉只有 herdr server stop。

server 重启之后回来的是什么？

只有布局快照：workspace、tab、pane、cwd、布局、焦点。原来的进程已经没了，走不到更强恢复路径的 pane 会以「保存在原目录下的新 shell」形式回来。想找回屏幕内容需要开 experimental.pane_history；想让 agent 接上原对话需要 native agent session restore（默认开启）。

agent 的原生对话恢复默认开着吗？

开着。它用官方集成上报的 session 引用，在 Herdr server 重启后重启受支持的 agent pane。要关就设 session.resume_agents_on_restore = false。用 herdr integration status 查已装集成的版本，版本太旧就 herdr integration install <agent> 重装。

pane 历史回放为什么默认关闭？

因为 pane 输出里可能包含密钥、token、提示词和命令输出。开启方式是 experimental.pane_history = true，历史存在 session.json 旁边的 session-history.json。官方要求把 Herdr 的 config/session 目录当终端历史一样对待。

布局误删了能恢复吗？

能，靠 session-snapshots/ 里的布局快照（最多 48 份，全平台都有，第一份立即保存，之后最多每 15 分钟一份，间隔跨 server 重启保留）。恢复四步：herdr session list --json 找到目录 → 停掉该 server → 备份当前 session.json 后把选中的快照覆盖上去 → 重新启动。快照只含布局和 agent session 引用，不含运行进程和屏幕历史。

live handoff 是什么，我该开吗？

它是为「升级」和「远程 attach」这类需要替换运行中 server 的场景设计的实验特性：让旧 server 把活的 pane 转交给新 server，从而保住 pane 进程。opt-in，用 herdr update --handoff 或 herdr --remote workbox --handoff。它保留 PTY、进程、agent 身份与持久元数据，但不保留跨替换边界的临时协调（在-flight 请求、wait、订阅流、client socket、pane 间消息可能中断）。
