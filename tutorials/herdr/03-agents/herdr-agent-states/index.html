Herdr agent 状态模型：五种状态由谁判定、检测清单怎么工作，以及 VM 与 sandbox 为什么会挡住检测

Herdr 的 agent 状态有三个来源：读屏（detection manifest）、集成上报、agent 自报，本文讲清优先级与各自的失效条件。含本机 herdr 0.9.2 的真实 herdr agent explain 输出——pi 的 manifest 只有两条规则（whole_recent 匹配 Working... 字面量、bottom_non_empty_lines(12) 匹配盲文 spinner 边框正则），以及 fallback_reason: default_known_agent_idle_fallback 的实际含义；blocked 为什么故意严格、Codex 为什么回退到 unknown；HERDR_AGENT 与 HERDR_PROCESS_DETECTION=child-groups 两个 VM/sandbox 逃生阀；远程 manifest 自动更新与本地覆盖优先级；state rollup 与自定义标签。

September 29, 2026 · 7 min · 1361 words · 梦兽编程 -  |  English

验证版本： herdr 0.9.2（stable channel）· 本机实测 macOS / Apple silicon · 2026-09-29 本篇的解释器输出、manifest 文件内容、状态目录清单全部来自本机真实执行，不是文档摘抄。

Herdr 存在的理由，官方第一句就说了：

Herdr is built for running more than one coding agent at a time. Herdr 是为「同时跑多个 coding agent」而造的。

而「同时跑多个」能不能成立，取决于一件事：你能不能一眼看出哪个在等你。 这就是状态模型的全部意义——它不是花哨的徽章，它是这个工具的核心功能。

先给结论：

状态有三个来源，优先级是：集成/agent 自报 > 读屏。 读屏这条路又分两种清单：内置在二进制里的和从 herdr.dev 拉下来缓存的， 而本地覆盖文件永远赢。 另外记住一条反直觉的设计：blocked 故意判得很严， 宁可把「在问你问题」误报成 idle，也不乱报 blocked—— 因为误报 blocked 会让你以为有东西在等你，而实际上没有。

一、27 个 agent，三种支持方式#

官方 agents 页把「支持」分成两类，加上第三类「普通终端」，实际是三种情况：

agent 获得 Herdr 支持有两种方式：Herdr 支持它们，或者它们自己支持 Herdr。 两种方式下你都能看到每个 agent 的 idle、working、blocked 状态， 在它完成或需要你时收到通知，并且能从脚本里 wait 它。

其他 agent 仍然能在 Herdr pane 里正常运行，它们只是显示为普通终端。

二、状态到底是怎么判出来的#

官方 how status works 一节，三句话讲完：

对 Herdr 支持的 agent，Herdr 在每个 pane 里找到 agent 的进程，并读取那个 pane 活的底部 （the live bottom），而不是你滚动到的那部分。 检测清单里的规则决定那块屏幕意味着 idle、working 还是 blocked。 当集成也上报状态时，Herdr 用那些上报值代替读屏。

对支持 Herdr 的 agent，由 agent 自己的上报决定状态。

三个要点：

  1. 读的是「活的底部」——所以你把屏幕往上滚去看历史，不会影响状态判定
  2. 规则来自清单（manifest），而清单是可以远程更新的（见第五节）
  3. 上报优先于读屏——装了集成就以集成为准

本机实测：把解释器打开看#

这是本篇最有价值的部分。我在自己的 Herdr 里跑了 herdr agent explain：

从这里能读出的事实（每一条都有上面的输出作证）：

三、blocked 为什么判得这么严#

这一节的设计取舍值得单独讲，因为它解释了「为什么我的 agent 在问我问题却显示 idle」。

对读屏清单类的 agent，blocked 检测是故意严格的。 Herdr 只在活的底部缓冲快照匹配到已知的可见审批、提问或权限 UI 时才标 blocked。 如果一个已知 agent（Codex 除外）没有任何清单规则匹配， Herdr 回退到 idle，并在 explain 输出里把这个回退标为 default_known_agent_idle_fallback。 Codex 回退到 unknown，因为它的 title 和 composer 在一次活跃回合中和响应之后可能看起来一样。

以及官方的风险评估（这句很重要）：

对那些其他 agent，不寻常的新提示可能一开始显示为 idle 而不是 blocked， 直到 Herdr 学会那种屏幕形状。 这种误分类只影响可见状态和 wait。它不应该让 Herdr 发送输入或采取破坏性动作。

Codex 的特殊性（完整规则）#

屏幕上有什么能确立什么
可见的 spinner 或 live 活动计时器✅ working
可见的审批提示✅ blocked
普通的 title / composer，或缺少 spinner❌ 不能确立「回合已结束」

后果：Codex 可能在响应之后停留在 unknown，等 idle 或完成的 wait 可能超时。

还有一条容易误读的细节：

Managed startup 只用初始的 composer 来判断它什么时候可以接受一个 prompt； 那个观察不改变回合状态。

四、VM 与 sandbox 包装器：检测为什么会瞎#

这是实践中最常撞上的问题。

症状#

在 Linux 和 macOS 上，一个宿主机可见的包装器会把真正的 agent 进程从 Herdr 面前藏起来。 典型场景：fence、nono、各种 sandbox runner、容器 CLI。

解法 1：HERDR_AGENT#

在包装器命令上设置，告诉 Herdr 用哪个已有 agent 的屏幕清单：

# Linux
HERDR_AGENT=claude fence -- claude

# macOS
HERDR_AGENT=claude nono run --profile claude-code -- claude

三条限制（官方全写了）：

  1. 这个提示只对那个前台进程生效
  2. 如果你只在 VM 或容器内部设置它，Herdr 看不到
  3. 别全局 export 它，除非每一个继承它的前台进程都应该被当作那个 agent

解法 2：HERDR_PROCESS_DETECTION=child-groups#

有些受限的 Linux 运行时不暴露终端的前台进程组。 用 HERDR_PROCESS_DETECTION=child-groups 启动 Herdr server， 可以在原生检测不可用时选择加入「直接子进程组推断」。

规则：

  • 原生检测仍然是首选，默认的 native 模式永远不做这种推断
  • opt-in 模式是尽力而为：一个较新的后台 job 可能被误认为前台 job
  • 这个变量由 server 读取，需要重启
  • 要设在远程 server 的环境里，而不是设在 attach 的 client 上

解法 3（其实是陷阱）：别在 pane 里套 tmux#

Herdr 可以跑在 tmux 里面作为外层终端环境。 agent 检测不会检查在一个 Herdr pane 内部启动的 tmux 会话。 如果一个 shell 框架在 Herdr 里自动进入 tmux，Herdr 看到的是 tmux 这个 pane 进程， 而不是它背后的 agent。

修法：在你的 shell 启动规则里加 HERDR_ENV 检查，在它跑 tmux 之前：

if [[ -z ${TMUX:-} && ${HERDR_ENV:-} != 1 ]]; then
  tmux new-session -A -s my-session
fi

还有一条附带的物理现象：

从一个 Herdr pane 内部重新 attach 外层 tmux 会话，会递归地缩小终端并让它闪烁。

（本机实测：这个 session 就在 Herdr pane 里，echo $HERDR_ENV → 1， HERDR_PANE_ID → w3:p2。上面那段 zsh 判断就是给这种环境准备的。）

五、检测清单的三个来源与优先级#

来源位置优先级
本地覆盖~/.config/herdr/agent-detection/<agent>.toml永远赢
缓存的远程清单Herdr 的状态目录（本机：~/.local/state/herdr/agent-detection/remote/）与内置比较，取更新的兼容版本
内置清单在运行的 Herdr 二进制里兜底

官方原文：

本地覆盖永远赢。 没有本地覆盖时，Herdr 使用 缓存的远程清单和运行中二进制里的内置清单之间更新的那个兼容清单。

补充细节：

  • 在 debug build 上，同一个配置 helper 可能使用一个开发目录，例如 herdr-dev
  • 无效的覆盖文件会被忽略并给出警告，Herdr 对该 agent 回退到缓存的远程或内置清单
  • 远程清单只能给 Herdr 已经知道怎么识别的 agent 打检测规则的补丁。 加一个全新的 agent 仍然需要 Herdr 二进制更新（进程检测、标签、集成行为）
  • 关掉后台远程清单检查：
[update]
manifest_check = false

内存缓存与重载#

运行中的 server 在启动时把活跃清单加载进内存。 自动的远程清单更新会在新规则写入后重载那个内存缓存。

场景命令
立刻抓取远程清单更新并重载运行中的 serverherdr server update-agent-manifests
手动改了本地覆盖文件后应用到运行中的 serverherdr server reload-agent-manifests（或重启 Herdr）

注意这两个命令名不一样，用错了会发现「改了没生效」。

排障：herdr agent explain#

herdr agent explain <target>
herdr agent explain --file screen.txt --agent codex --json    # 离线复现

live explain 由运行中的 server 求值，所以它反映活跃的清单缓存。

explain 输出包含（官方列的完整清单）：agent、最终状态、屏幕检测是否被一个完整生命周期权威跳过、 清单来源与版本、缓存的远程版本、本地覆盖遮蔽情况、远程更新状态、命中的规则、 可见证据标志、被求值规则的 matcher 与 region 证据、 transcript viewer 的 skipped-update 原因、以及没有规则命中时的 idle 回退原因。

六、状态汇总（rollup）：这才是主工作流#

侧边栏把状态向上汇总。 一个 blocked 的 agent 会让它的 pane、tab 和 workspace 都看起来 blocked。 一个 working 的 agent 会让 workspace 看起来 active。 一个 done 的 agent 保持可见，直到你查看它。

这就是 Herdr 的主工作流：启动几个 agent，让它们并行工作， 然后用侧边栏看出哪个项目需要一个决定、哪个还在跑、哪个已经可以 review 了。

「done 保持可见直到你查看它」是一个刻意的设计：它把「已读」变成了你的动作， 而不是时间的函数。所以侧边栏本质上是一个未读收件箱。

本机实测正好抓到了这个状态：w3:p1 的 agent_status 是 done（completion_seq: 79）， 而 w3:p2 是 working——两个 pane 属于同一个 workspace w3， 所以 w3 在侧边栏里会同时体现「有个东西完成了」和「有个东西在跑」。

七、自定义标签：两种，别搞混#

改 agent 的显示名#

herdr agent rename w1:p1 reviewer
herdr agent rename reviewer --clear

target 接受：一个唯一的活 agent 名，或当前托管该 agent 的 pane ID。 不接受：terminal ID、裸的 agent-kind 标签。

改完之后就能 herdr agent attach reviewer 直接接进去（见下）。

改状态的显示文字（但不改语义状态）#

集成只把生命周期状态报告为语义状态。显示定制要单独用 pane metadata token 加。

herdr pane report-agent w1:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working

herdr pane report-metadata w1:p1 \
  --source custom:indexer-display \
  --token summary=indexing
东西控制什么
statewaits、通知、汇总
summary token只用于显示，可以在 Agent 侧边栏行里当 $summary 用

Agent 侧边栏行还可以选择性启用 terminal_title 或 terminal_title_stripped （两者都不在默认行里）：

  • terminal_title：最新的、经过安全规范化的 OSC 0/2 终端标题
  • terminal_title_stripped：去掉一个已识别的前导活动或 spinner 字形，以及随后的空白

三条注意：

  1. 这些值由 server 拥有
  2. 冷重启后它们是短暂的（ephemeral），且独立于 metadata 标题和语义 agent 状态
  3. spinner 动画因此可以更新原始标题而不产生 pane 更新——只要 stripped 文本保持不变 （这是个很聪明的去抖动设计）

八、直接 attach 到一个 agent#

herdr agent attach reviewer
  • ctrl+b q detach；ctrl+b ctrl+b 发送一个字面的 ctrl+b
  • 鼠标滚轮或普通 page up/down 滚动；普通输入会跳回底部
  • 另一个 direct attach client 已经拥有输入时，用 --takeover：
herdr agent attach reviewer --takeover

想对非 agent 终端做同样的事：herdr terminal attach <terminal_id>。

九、避坑指南#

  1. blocked 判得严是设计，不是 bug。 别指望「所有在等输入的 agent 都显示 blocked」。 要精确判断请用 herdr agent explain <target> 看 evaluated_rules。
  2. Codex 停在 unknown 是正常的。 它的 wait 可能超时——脚本里要给 Codex 单独的超时策略。
  3. 误分类不会让 Herdr 乱发输入。 官方明确说它只影响可见状态和 wait。
  4. 装了集成 ≠ 状态更准，而是「上报代替读屏」。 对 omp / mastracode 来说， 不装集成就完全没有状态。
  5. VM / sandbox 里跑 agent，先加 HERDR_AGENT。 而且要加在宿主机可见的包装器命令上， 加在容器里面没用。
  6. 别全局 export HERDR_AGENT。 它会让每个继承的前台进程都被当成那个 agent。
  7. HERDR_PROCESS_DETECTION=child-groups 要设在 server 环境并重启，设在 client 上没用。 而且它是尽力而为：新的后台 job 可能被误认成前台。
  8. 别在 Herdr pane 里自动进 tmux。 加 ${HERDR_ENV:-} != 1 判断，否则 Herdr 只看到 tmux。
  9. 改本地覆盖后要 reload-agent-manifests，抓远程更新要 update-agent-manifests。 两个命令别用混。
  10. 加全新 agent 不能靠改清单。 远程清单只能给已识别的 agent 打规则补丁， 新 agent 需要 Herdr 二进制更新。
  11. agent rename 不接受 terminal ID 和裸 agent-kind。 用唯一活 agent 名或 pane ID。
  12. 想改状态文字别去改 state。 state 驱动 wait/通知/汇总；显示用 summary metadata token。

常见问题

Herdr 怎么知道我的 agent 在 working 还是 blocked？

对 Herdr 支持的 agent，它在每个 pane 里找到 agent 进程，然后读那个 pane「活的底部」——不是你滚动到的位置。检测清单（detection manifest）里的规则决定那块屏幕意味着 idle、working 还是 blocked。当集成也上报状态时，Herdr 用上报值代替读屏。对自报状态的 agent，则由 agent 自己的报告决定。

为什么我的 agent 明明在问我问题，却显示 idle？

blocked 检测对读屏类 agent 是故意严格的：只有当活的底部缓冲快照匹配到已知的可见审批、提问或权限 UI 时才标 blocked。已知 agent 但没有规则匹配时（Codex 除外）回退成 idle，并在 explain 输出里标为 default_known_agent_idle_fallback。官方说明这种误分类只影响可见状态和 wait，不会让 Herdr 发送输入或执行破坏性动作。

Codex 为什么经常显示 unknown？

因为它的 title 和 composer 在一次活跃回合中和回合结束后看起来一样。所以 Codex 不匹配规则时回退到 unknown 而不是 idle。可见的 spinner 或活动计时器能确立 working，可见的审批提示能确立 blocked，但普通 title、composer 或缺少 spinner 都不能确立「回合已结束」。因此 Codex 可能在响应后停在 unknown，等 idle 或完成的 wait 可能超时。

在 VM、容器或 sandbox 包装器里跑 agent，Herdr 为什么看不到？

在 Linux 和 macOS 上，一个宿主机可见的包装器会把真正的 agent 进程藏起来。解决办法是在包装器命令上设 HERDR_AGENT=<agent>，告诉 Herdr 用哪个已有 agent 的屏幕清单，例如 HERDR_AGENT=claude fence -- claude。这个提示只对那个前台进程生效；如果你只在 VM 或容器内部设置，Herdr 看不到它。

检测规则更新了要重启 Herdr 吗？

远程清单更新不用重启：Herdr 会检查 herdr.dev 的远程清单更新，自动应用有效的按 agent 规则更新，并在新规则写入后重载内存缓存。想立刻抓取就 herdr server update-agent-manifests。但手动改了本地覆盖文件（~/.config/herdr/agent-detection/<agent>.toml）之后，需要重启或跑 herdr server reload-agent-manifests。

怎么排查一个 pane 显示的状态不对？

herdr agent explain <target>，或者离线复现用 herdr agent explain --file screen.txt --agent codex --json。live explain 由运行中的 server 求值，所以反映的是活跃的清单缓存。输出里有 agent、最终状态、屏幕检测是否被完整生命周期权威跳过、清单来源与版本、缓存的远程版本、本地覆盖是否在遮蔽、远程更新状态、命中的规则、可见证据标志、被求值规则的 matcher 与 region 证据，以及没有规则命中时的 idle 回退原因。
