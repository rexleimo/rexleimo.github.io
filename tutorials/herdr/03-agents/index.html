模块 3：Agent 集成（状态模型、18 个官方集成、给自己的 agent 加支持）

Herdr 的 agent 感知能力全解：五种状态由谁判定、检测清单与屏幕检测怎么工作、VM 与 sandbox 包装为什么会挡检测、blocked 的准确语义、状态汇总与自定义标签；18 个官方集成（Pi、Claude Code、Codex、Copilot、Devin、Droid、Kimi、OpenCode、Kilo、Hermes、Qoder、Qwen、Letta、Cursor、MastraCode、Antigravity、Grok、OMP）的安装与调试；以及如何给你自己的 agent 上报状态和恢复命令。基线 herdr 0.9.2 stable。
3 篇内容

模块 3：Agent 集成

这是本专栏的差异化重点，也是 Herdr 相对 tmux / zellij 唯一无法被「配置一下就行」追平的能力： 它知道 pane 里跑的是哪个 agent、那个 agent 现在是不是在等你。

这一模块把三件事讲透：状态是怎么判出来的、18 个官方集成装完到底多了什么、 你自己的 agent 怎么接入。第 2 篇含本机 Pi 与 Hermes Agent 实测。

基线：herdr 0.9.2 stable · 文档源 pinned v0.9.2 · 本机实测：18 个集成全部 not installed 状态下， Herdr 依然正确识别出 3 个 pi agent 且状态为 working

前置要求

  • 已完成模块 0 ，herdr status 能看到 server running
  • 至少在用一种 coding agent（Claude Code / Codex / Pi / OpenCode / Hermes 任一）
  • 第 3 篇需要能写一点脚本（shell / TypeScript / Python 任一），并会读 JSON

学习目标

完成本模块后，你能回答：

  • working / blocked / done / idle / unknown 五种状态各自的准确判据，以及为什么 done 和 idle 都表示「可以输入了」
  • 为什么 CLI / API 查到的状态和你屏幕上看到的 Done 角标可能不一致（每个 client 各自记录已展示过哪些完成）
  • 「屏幕检测」和「集成上报」分别提供什么：集成可能给生命周期状态、原生会话恢复，或者两者都给——但不一定替代屏幕检测
  • 怎么诊断「agent 没被认出来 / 状态不对」：herdr agent list 看它看到什么、herdr agent explain <target> --json 看它为什么这么判
  • agent 跑在 VM 或 sandbox 包装里时检测为什么会失效，怎么办
  • 18 个集成各自的安装落点（例如 Pi 是 ~/.pi/agent/extensions/herdr-agent-state.ts、Hermes 是 ~/.hermes/plugins/herdr-agent-state/__init__.py），以及 herdr integration status 怎么读
  • 怎么给一个官方没支持的 agent 加 Herdr 支持：上报状态、上报 resume 命令、退出时释放、直接走 socket 的取舍

一句话结论

检测和集成是两回事：不装任何集成，Herdr 也能靠前台进程 + 屏幕清单认出你的 agent 并给出状态； 装集成买到的是更可靠的生命周期状态和agent 原生会话恢复。 先 herdr agent list 看现状，再决定要不要装——而不是反过来。
