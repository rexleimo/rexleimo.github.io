Herdr 18 个官方集成逐个拆：装到哪个文件、改哪份配置、状态从哪来，以及 Pi 与 Hermes 的本机现状

herdr integration install/uninstall/status 三个子命令的完整语义，18 个集成各自写到哪个文件、改哪份配置、受哪个环境变量覆盖、卸载时留下什么；哪些集成只报会话身份（状态仍靠读屏）、哪 6 个额外上报生命周期状态、哪 2 个不装就完全没有状态；原生会话恢复的最低集成版本表（并标出 Hermes 在两份官方文档里 2 与 5 的冲突）；Claude v10 的 SessionStart 白名单、Codex 的 [features] hooks、OpenCode V1/V2 三文件与首启迁移、Antigravity 的 PreInvocation、Grok 的自包含 hooks/herdr.json、Letta 的实验性 CLI-only；以及本机 herdr 0.9.2 的 integration status 全量输出与 Pi / Hermes 目录现状。

September 30, 2026 · 10 min · 2125 words · 梦兽编程 -  |  English

验证版本： herdr 0.9.2（stable channel）· 本机实测 macOS / Apple silicon · 2026-09-30 本篇所有 integration status / --help 输出、目录现状均为本机真实执行结果。 我没有真的安装任何集成——安装会写入 Pi / Hermes 等工具的用户配置，属于需要单独批准的改动。 第八节说明「如果装了会发生什么」以及本机的当前状态。

上一篇 讲了状态是怎么判出来的。 这一篇讲怎么让状态更可靠、以及怎么让会话在 server 重启后接得回来——也就是集成。

先纠正一个几乎所有人都会有的误解：

集成不是「让 Herdr 认识你的 agent」。 官方第一句就是：Herdr detects the agents it supports automatically. 装一个 agent 的集成，是为了让 Herdr 在 server 重启后能 resume 同一个会话。 有些集成还额外直接上报 agent 的状态。

所以判断「我要不要装」的标准很简单：

你在意什么要不要装
只想知道 agent 现在是 working 还是 blocked大多数情况不用装（读屏就够）
server 重启 / 机器重启后要接回原对话必须装（没有集成就没有 session 引用）
用的是 OMP 或 MastraCode必须装（这两个的状态就需要集成）
想要权威状态而不是读屏推断装那 6 个会上报状态的

一、三个子命令，就三个#

$ herdr integration --help
Manage built-in agent integrations

Commands:
  install    Install an integration
  uninstall  Uninstall an integration
  status     Show integration status

没有 list。 敲 herdr integration list 会打印一段帮助文本（本机实测）， 内容是 18 条 herdr integration install <name> 的示例——它把「列表」当成帮助来给了。

install 的目标是一个封闭枚举（本机 --help 原文）：

possible values: pi, omp, claude, codex, copilot, devin, droid, kimi, opencode,
                 kilo, hermes, qodercli, qwen, cursor, mastracode,
                 antigravity-cli, grok, letta

18 个，注意 letta 排在最后（和文档正文里 Letta 那一节的位置不一致， 也和 herdr integration status 的输出顺序不同——别指望顺序稳定，用名字）。

两种安装入口#

在 Herdr 里打开 settings，用 integrations 标签页为「在你 PATH 上找到的 agent」安装推荐集成， 或者手动跑命令。

**「在你 PATH 上找到的」**这个限定很实用：它不会给你推荐一堆你没装的 agent。 （Letta 不在这个界面里，见下文。）

卸载#

18 条 herdr integration uninstall <name>，目标集合与 install 相同。

二、Herdr 到底怎么用这些集成#

每个集成都告诉 Herdr「这个 agent 在哪个 session 里」，这样 Herdr 才能在 server 重启后 resume 它。 用 [session] resume_agents_on_restore = false 关掉这件事。

Pi、OMP、Kimi Code CLI、OpenCode、Kilo Code CLI 和 MastraCode 的集成还上报 agent 的状态。 在它们上报期间，Herdr 用它们代替读屏。其余的把状态留给屏幕检测。

写入的原子性与 Windows 备份语义#

Herdr 在 Linux/macOS 上以及对新文件采用原子方式保存集成配置。 已存在的 Windows 文件通过「先备份、就地更新」保留它们的权限。

如果 Windows 报告了一个备份：

  1. 关掉 agent，在重试之前先检查配置
  2. 只有在验证过配置之后，才**丢弃（discard，不是 restore）**一个未完成的 .herdr-backup.pending
  3. 或者在需要时把已完成的 .herdr-backup 内容恢复进现有文件 （如果现有文件缺失，先建立它应有的权限）
  4. 然后验证配置并删除备份

四、Pi：本机相关，展开讲#

herdr integration install pi

Herdr 把捆绑的扩展写到：

~/.pi/agent/extensions/herdr-agent-state.ts

规则：

  • 如果设置了 PI_CODING_AGENT_DIR，Herdr 改写到 $PI_CODING_AGENT_DIR/extensions/herdr-agent-state.ts
  • 当 Pi 的 agent 目录已经存在时，Herdr 会创建 extensions 目录
  • 卸载只删除那一个扩展文件

本机现状（实测）：

$ ls -d ~/.pi ~/.pi/agent
/Users/rex/.pi
/Users/rex/.pi/agent          # ← agent 目录存在

$ ls ~/.pi/agent/extensions/
ls: /Users/rex/.pi/agent/extensions/: No such file or directory   # ← extensions 还没建

所以本机正好落在文档说的那个分支上：agent 目录存在、extensions 目录不存在 → install pi 会创建 extensions/ 并写入 herdr-agent-state.ts。

Pi 的特殊之处：它在 agents 页被标为 「also reports state」， 所以装了之后 working/idle/blocked 就从扩展上报来，而不再是读屏推断。 但注意——不装集成时 Pi 的状态依然可用（上一篇的 herdr agent explain 就是在 pi 集成 not installed 的情况下跑出 working 的，靠的是远程清单里那条盲文 spinner 正则）。

五、OMP：会和 Pi 抢目录，安装可能被拒绝#

herdr integration install omp

写到 ~/.omp/agent/extensions/herdr-omp-agent-state.ts。目录解析顺序：

  1. 设置了 PI_CODING_AGENT_DIR → 把它当作完整的 agent 目录
  2. 否则设置了 PI_CONFIG_DIR → 用 $HOME/$PI_CONFIG_DIR/agent
  3. 否则 → ~/.omp/agent

然后是这条极其重要的保护：

如果 Pi 和 OMP 解析到同一个 extensions 目录，Herdr 会拒绝 OMP 的安装， 这样 OMP 的扩展就不会被 Pi 加载。 在安装两个集成之前，先配置好分开的 agent 目录。

所以：想同时用 Pi 和 OMP，先设 PI_CODING_AGENT_DIR（或 PI_CONFIG_DIR）把它们分开，再装。 否则第二次安装会失败，而且失败原因是「保护你」而不是「装不上」。

OMP 集成的能力（比其他多数集成强）：

  • 通过 Herdr 的 socket API 上报 omp 作为 agent 标签、生命周期状态、原生会话身份
  • 它不需要对 omp 可执行文件的原生进程检测
  • server 重启后 Herdr 能用 omp --resume=<session> 恢复 OMP pane

六、几个有独特行为的集成#

Claude Code：v10 收紧了 SessionStart 白名单#

Claude 集成 v10 只匹配有文档记载的 SessionStart 来源： startup、resume、clear、compact 和 fork。 这防止 Grok 的 new 和 load 事件启动被导入的 Herdr Claude hook， 同时不禁用无关的 Claude 兼容 hook。 升级到 v10 之后要重装 Claude 集成，以迁移之前的通配 matcher。 新的 Claude source 值需要集成更新。

这是个真实的兼容性战争故事：Grok 的事件名会触发 Claude 风格的 hook， 所以 Herdr 从「通配」改成「白名单」。如果你之前装过，升级 Herdr 后记得重装一次。

其余：默认 ~/.claude，或 CLAUDE_CONFIG_DIR；配置目录必须已存在； 安装写 hooks/herdr-agent-state.sh 并更新 settings.json； 卸载移除匹配的 hook 条目并删除脚本。 Claude Code 的状态来自 Herdr 的屏幕清单检测——hook 只在 session start 时报会话身份。

Codex：安装会动 config.toml，卸载不会#

安装做四件事：

  1. 写 herdr-agent-state.sh
  2. 更新 hooks.json
  3. 确保 config.toml 里有 [features] hooks = true
  4. 移除已存在的、废弃的顶层 codex_hooks 标志

卸载：从 hooks.json 移除 Herdr 条目、删除 hook 脚本， 但保持 config.toml 不变。

⚠️ 所以如果你为了别的原因想彻底关掉 Codex hooks，卸载集成不会帮你改回 config.toml。

Codex 的状态来自屏幕清单——而且上一篇 讲过， Codex 是唯一一个不匹配规则时回退到 unknown 而不是 idle 的 agent。

Copilot CLI#

~/.copilot 或 COPILOT_HOME；写 hooks/herdr-agent-state.sh； settings.json 里加一个 SessionStart hook 条目。 在 Copilot 发出一个带 session 的事件之后，Herdr 可以用报上来的 session id 以 copilot --resume=<id> 恢复 pane。

Devin CLI：为什么状态还是读屏#

hook 从 Devin 的 session、prompt、tool-use、permission 和 stop 事件里上报原生会话身份。 Devin 的状态仍然来自 Herdr 的屏幕清单和 OSC 检测， 因为 Devin 的 hook 不会在每次权限取消或用户中断之后发出一个可靠的状态转换。

目录：设了 XDG_CONFIG_HOME 用 $XDG_CONFIG_HOME/devin； 否则 Linux/macOS 用 ~/.config/devin，Windows 用 %APPDATA%\devin。 文件：Unix herdr-agent-state.sh，Windows herdr-agent-state.ps1；更新 config.json。 hook 在 Devin 运行期间持续刷新 session 引用。 无论 hook 装没装，原生屏幕清单检测都仍然是状态的权威。

Kimi Code CLI：需要 0.14.0+#

  • 要求 Kimi Code CLI 0.14.0 或更新
  • 上报会话身份 + 生命周期状态，用于原生恢复和权威的 idle/working/blocked
  • 安装追加 Herdr 管理的 [[hooks]] 条目到 config.toml
  • 卸载移除那个 Herdr 管理的配置块并删除脚本

Droid：会顺手清理旧条目#

~/.factory（Factory 配置目录必须已存在）。安装：

  1. 写 hooks/herdr-agent-state.sh
  2. 更新 settings.json 加一个 Herdr SessionStart hook 条目
  3. 如果存在，移除 hooks.json 里更旧的 Herdr Droid hook 条目

卸载从两个配置文件里移除 Herdr 条目并删除脚本。 生命周期状态仍来自屏幕清单，因为 Droid 的 hook 不覆盖每一个生命周期转换。

OpenCode：最复杂的一个，值得单列#

支持版本：OpenCode V1 1.18.29 或更新，以及 OpenCode V2（用 beta 19242 测过）。

安装写三个文件（都在配置目录下）：

文件作用
~/.config/opencode/plugins/herdr-agent-state.jsserver 入口
herdr-tui-session.js共享的 TUI 插件
herdr-opencode/tui.jsV2 的 TUI 入口

注册：V1 TUI 插件注册进 tui.jsonc，V2 TUI 插件注册进 cli.json， 保留其他偏好和插件。

几个边界情况（官方逐条写了，我照录要点）：

  • tui.json 里已有的 V1 注册也算「已安装」并被复用，不会去创建 tui.jsonc
  • 如果 OpenCode 还有 V1 TUI 偏好待导入（tui.json 或 kv.json），Herdr 会推迟注册， 好让首启迁移能跑完 → 先启动一次 opencode2，之后再重装集成
  • 否则 Herdr 创建带插件注册的 cli.json
  • 安装之后要重启 OpenCode TUI
  • 卸载从两个 TUI 配置文件里移除 Herdr 注册，但保留文件和其他偏好； 同时移除托管的插件文件和它们的配置条目

V2 的生命周期上报跑在 pane-local 的 TUI 里，所以 即使多个 pane 共享一个 OpenCode server，它也能把事件关联到自己选中的 root session。

事件状态效果
完成、中断清除 working
待处理的权限请求、待处理的表单、失败的执行保持 pane blocked

⚠️ V2 Mini 和 headless client 不跑 TUI 插件，因此不提供这种生命周期上报。

V1 的 TUI 上报跟随 pane 选中的 session 及其后代：

  • 它们中任何一个忙或在重试 → pane 保持 working
  • 任何一个有待处理的权限或问题 → pane blocked
  • attach 会加载已有的活动
  • 被取消的工具请求在重连之后不会重新变成 blocker
  • 浏览一个 subagent 会保持原来的 session 家族； 而直接 attach 到一个子级会跟踪那个子级的子树，而不是它的兄弟

本地 V1 的 opencode run 和 opencode --mini 保留它们的 legacy server hooks； 这个改动不给 Mini/headless client 增加 pane-local 生命周期上报。

⚠️ 更新集成之后，除了 TUI 还要重启共享的 OpenCode server， 否则旧的 server reporter 可能覆盖 pane-local 的状态。

没装插件时，原生屏幕清单检测仍然可用。

Kilo Code CLI#

写 ~/.config/kilo/plugin/herdr-agent-state.js（Kilo 配置目录必须已存在）。 卸载只删那一个插件文件。 上报生命周期状态和会话身份； Kilo 发出带 session 的事件后可用 kilo --session <id> 恢复。

Hermes Agent：装完必须重启#

Herdr 在 Hermes home 目录下写 plugins/herdr-agent-state/， 并在它的 config.yaml 里启用 herdr-agent-state。 HERMES_HOME 在 Unix 上默认 ~/.hermes，在 Windows 上默认 %LOCALAPPDATA%\hermes。 Hermes 配置目录必须已存在。安装之后重启 Hermes，插件才会加载。 卸载移除插件目录，并从 plugins.enabled 里移除 herdr-agent-state。

它只上报可恢复的 session id；working/idle/blocked 用屏幕清单检测； server 重启后可用 hermes --resume <id> 恢复 pane。

Qoder CLI#

~/.qoder 或 QODER_CONFIG_DIR；写 hooks/herdr-agent-state.sh；更新 settings.json。 只报会话身份，因为 Qoder 的 hook 不覆盖每一个生命周期转换。 没装 hook 时屏幕清单检测仍可用。

Qwen Code#

SessionStart hook 只上报 Qwen Code 的会话身份用于原生恢复； 生命周期状态保持在 Herdr 的屏幕清单检测下。 写 hooks/herdr-agent-session.sh（Windows 是 .ps1），往 settings.json 加一个 Herdr 条目。 卸载只移除匹配的那个条目和托管脚本。

Letta Code：实验性、仅 CLI#

Letta Code 的集成安装是实验性的，且仅限 CLI。 它不会列在 Settings 的集成界面里，也不在 JSON 集成 API 里。 herdr integration status 把它报成 letta (experimental)。 agent 检测和 herdr agent start --kind letta 不受这个安装限制影响，独立可用。

quiet SessionStart hook 上报 conversation ID；状态仍来自屏幕清单。 ~/.letta（必须已存在）。 命名会话用 letta --conversation <id> 恢复；默认会话被记录为 default:<agent-id>， 用 letta --conversation default --agent <agent-id> 恢复。

Cursor Agent CLI：一条 PATH 要求#

~/.cursor 或 CURSOR_CONFIG_DIR；写 herdr-agent-state.sh（Windows .ps1）； 往 hooks.json 加一个 Herdr sessionStart 条目。

⚠️ 当 Herdr 恢复 pane 时，cursor-agent 命令必须在 PATH 上； Herdr 不会去启动那个通用的 agent 命令。

这是个很容易在「换了 shell / 用了不同 PATH 的 server」之后踩到的坑： 恢复会失败，而且原因不在 Herdr 这边。

MastraCode：没有兜底#

hook 上报 MastraCode 的生命周期状态和 thread 身份， 用于权威的 idle/working/blocked 状态和原生恢复。 MastraCode 没有屏幕清单兜底；状态来自 hook。

~/.mastracode；写 hooks/herdr-agent-state.sh（Windows .ps1）； 往 hooks.json 加 Herdr 命令条目，目录缺失时会创建它。 这是 18 个里唯一一个「不装集成就完全没有状态」而且「会替你建目录」的。

Antigravity CLI：session-only，而且要等第一个 prompt#

  • 目录：默认 ~/.gemini/config/，或 ANTIGRAVITY_CLI_CONFIG_DIR —— 这是 Antigravity CLI 读全局定制的目录，必须已存在
  • 写 hooks/herdr-agent-state.sh（Windows .ps1）， 往 hooks.json 加一个 Herdr 拥有的 herdr 块
  • Antigravity CLI 的 hooks.json 是按 hook 名 keyed 的， 所以安装只重写那一个块，不动其他命名 hook
  • 卸载移除 herdr 块并删除脚本

行为上的两个关键点：

这是一个 session-only 集成：它上报 pane 当前的 conversation，但不上报 agent 状态。 Herdr 继续从 Antigravity CLI 画在屏幕上的内容推导 working / idle / blocked。

hook 跑在 PreInvocation 上，所以 Herdr 是在第一个 prompt 发出之后才知道 conversation 的。 从那时起，Herdr 才能在 server 重启后用 agy --conversation <id> 恢复 pane。

含义：刚启动还没发过 prompt 的 Antigravity pane，重启后恢复不了。

Grok CLI：自包含，绝不碰别人的文件#

Grok 会合并那个目录里的每一个 hooks/*.json 文件， 所以安装写一个自包含的 hooks/herdr.json，里面是 Herdr 的 SessionStart 条目， 就放在 hooks/herdr-agent-state.sh（Windows .ps1）旁边， 并且从不编辑其他 hook 文件。 卸载精确删除那两个 Herdr 拥有的文件。

~/.grok 或 GROK_HOME（必须已存在）。 这是 18 个里侵入性最低的设计，值得当范本。

七、自定义状态标签（和集成共存的正确姿势）#

集成只把生命周期状态报告为语义状态。 例如，把一个 agent 报成 working， 而不往生命周期报告里加显示字段。

herdr pane report-agent w1:p1 \
  --source custom:docs \
  --agent docs-bot \
  --state working

然后是这一节最重要的一条纪律：

和 Herdr 托管的集成并排运行的用户 hook，应该用 metadata 而不是 report-agent。 metadata 改变呈现，而不接管那个集成的 idle/working/blocked 或会话恢复权威。

herdr pane report-metadata "$HERDR_PANE_ID" \
  --source user:claude-title \
  --agent claude \
  --title "Refactor auth middleware" \
  --display-agent "Claude: auth" \
  --token summary="refactor auth" \
  --state-label working="refactoring auth" \
  --ttl-ms 3600000

规则细节：

  • --agent 和 --applies-to-source 只保护呈现字段 （--title、--display-agent、--state-label）
  • token 补丁总是生效；它的 reporter 拥有清除或 TTL 刷新的责任
  • --display-agent 改变可见的名字
  • token 和 state label 是纯视觉的—— wait、通知和 workspace 汇总仍然使用语义状态

一句话：想改「看起来叫什么」用 metadata；想改「Herdr 认为它是什么状态」才用 report-agent。 而后者会和官方集成抢权威，所以只在没有官方集成时用。

八、本机现状：Pi 与 Hermes（以及为什么我没装）#

我没有执行任何 integration install，因为它会写入 Pi / Hermes 的用户配置目录 （~/.pi/agent/extensions/、~/.hermes/plugins/ + ~/.hermes/config.yaml）， 属于需要先批准的改动。这一节记录当前状态和装了会发生什么。

Pi#

项本机现状
~/.pi/agent存在
~/.pi/agent/extensions/不存在
herdr integration statuspi: not installed (~/.pi/agent/extensions/herdr-agent-state.ts)
装了会发生什么创建 extensions/ 目录（因为 agent 目录已存在），写入 herdr-agent-state.ts
装了之后状态来源从读屏（远程清单 pi.toml 的 spinner 正则）变成扩展上报
装了之后新增能力server 重启后用 pi --session <path-or-id> 接回原会话（需要集成版本 ≥ 2）
卸载只删那一个文件，extensions/ 目录留着

结论：对本机来说，装 pi 集成的唯一实质收益是「重启后接回会话」—— 状态本来就有（上一篇已实测证明）。

Hermes Agent#

项本机现状
~/.hermes/存在（config.yaml、plugins/、bin/ 等）
~/.hermes/plugins/存在，里面只有 rtk-rewrite
~/.hermes/config.yaml 的 plugins: 段enabled: 列表里只有 - rtk-rewrite
herdr integration statushermes: not installed (~/.hermes/plugins/herdr-agent-state/__init__.py)
装了会发生什么写 ~/.hermes/plugins/herdr-agent-state/ 目录，并把 herdr-agent-state 加进 config.yaml 的 plugins.enabled（rtk-rewrite 保留）
装完必须做重启 Hermes，插件才会加载
卸载删除插件目录 + 从 plugins.enabled 移除 herdr-agent-state

一个容易混淆的东西#

本机 ~/.hermes/hermes-agent/plugin-catalog/ 下有一个 herdr-auto-reconcile.yaml：

name: herdr-auto-reconcile
repo: https://github.com/chris-yyau/hermes-herdr-auto-reconcile
description: Wake Hermes when allowlisted Herdr panes need reconciliation,
  without routing or controlling pane work.
maintainer: chris-yyau
tier: community
category: automation

这不是 Herdr 的官方集成。 它是一个社区（tier: community）插件目录条目， 作用是「当白名单里的 Herdr pane 需要 reconcile 时唤醒 Hermes」—— 方向和官方集成正好相反：官方集成是 agent → Herdr（上报状态和会话）， 这个是 Herdr → agent（让 Hermes 去照看 pane）。

两者可以共存，但别把它们当成一回事。 看到 herdr- 前缀不代表是官方托管的文件； 官方的文件名是固定的 herdr-agent-state（或 qwen/letta 的 herdr-agent-session）。

九、调试集成状态#

官方给的三步：

# 1. 列出已知的 agent
herdr agent list

# 2. 需要确认「Herdr 到底看见了什么」时，读一个 pane
herdr pane read w1:p1 --source recent --lines 50

# 3. 如果集成状态看起来不对
#    先确认 agent 是在 Herdr 里面运行的，
#    并且相关的 hook 或插件是装给「同一个用户账号」的

第 3 条那个「同一个用户账号」是最常被忽略的： 用 sudo 装的 hook、或者在另一个用户下跑的 agent，都会让集成看起来「装了但不工作」。

再加上上一篇 的两个工具， 完整的排障顺序应该是：

herdr integration status --outdated-only   # 集成在不在、旧不旧
herdr agent explain <target>               # 状态是怎么判出来的（含 matched_rule 与 region 证据）
herdr pane read <pane> --source recent --lines 50   # Herdr 眼里那块屏幕长什么样

十、避坑指南#

  1. 没有 herdr integration list，也没有 status --json。 只有 install / uninstall / status， status 只有 --outdated-only 一个旗标。脚本里要解析就自己切字符串。
  2. 配置目录必须已存在（mastracode 除外）。先跑一次那个 agent，再装集成。
  3. Hermes 装完要重启 Hermes；OpenCode 装完要重启 TUI，更新集成后还要重启共享 server。 忘了这一步的表现是「装了但状态不变」。
  4. OpenCode 有 V1 偏好待迁移时，Herdr 会推迟注册。 先启动一次 opencode2，再重装集成。
  5. Pi 和 OMP 会抢 extensions 目录，Herdr 会拒绝 OMP 安装。 同时用两个的话， 先设 PI_CODING_AGENT_DIR 或 PI_CONFIG_DIR 分开。
  6. 升级到 Claude 集成 v10 之后要重装一次，以迁移旧的通配 matcher； 否则 Grok 的 new/load 事件可能触发它。
  7. Codex 卸载不会还原 config.toml。 它安装时确保了 [features] hooks = true，卸载留着。
  8. Cursor 恢复要求 cursor-agent 在 PATH 上，Herdr 不会退回通用的 agent 命令。
  9. Antigravity 在第一个 prompt 之前不知道 conversation（hook 跑在 PreInvocation）， 所以刚启动没发过话的 pane 重启后恢复不了。
  10. OMP 和 MastraCode 不装就没状态；MastraCode 连屏幕兜底都没有。
  11. Devin / Droid / Qoder 的 hook 不覆盖每个生命周期转换，所以状态仍以读屏为权威—— 别指望装了集成状态就 100% 准。
  12. 别用 report-agent 去和官方集成抢权威。 并排跑的用户 hook 用 report-metadata。
  13. herdr- 前缀不等于官方托管。 本机那个 herdr-auto-reconcile 是社区插件，方向相反。
  14. 两份官方文档对 Hermes 的最低集成版本说法不一致（5 vs 2）。 以 herdr integration status 为准，别背表。
  15. hook 要装给跑 agent 的同一个用户账号。 sudo 装、别的用户跑，等于没装。

如果你维护自己的 agent，不需要给 Herdr 提 PR，也不需要等它发版—— 从你自己的代码里上报状态和 resume 命令就能成为一等公民。 下一篇把这条路的三类上报、序号规则、resume 命令的四条硬约束讲完， 并给出不碰你正常会话的测试方法： 给你自己的 agent 加 Herdr 支持 。

常见问题

不装集成，Herdr 认不出我的 agent 吗？

认得出。官方原文是 Herdr detects the agents it supports automatically。装集成的目的是让 Herdr 在 server 重启后能 resume 同一个会话。部分集成还额外直接上报 agent 状态。例外是 OMP 和 MastraCode：这两个的状态需要集成，不装就没有状态（MastraCode 甚至没有屏幕清单兜底）。

哪几个集成会上报状态？

Pi、OMP、Kimi Code CLI、OpenCode、Kilo Code CLI、MastraCode 这 6 个。它们上报期间 Herdr 用上报值代替读屏。其余 12 个把状态留给屏幕检测，只报会话身份。

herdr integration status 支持 --json 吗？

不支持。本机 herdr 0.9.2 实测 herdr integration status --json 直接报 usage: herdr integration status [--outdated-only]。唯一支持的旗标是 --outdated-only。另外没有 herdr integration list 这个子命令——integration 只有 install / uninstall / status 三个，敲 list 会打印帮助。

集成装完要重启什么？

分三种。Hermes Agent 装完必须重启 Hermes 才能加载插件。OpenCode 装完要重启 OpenCode TUI，而且更新集成后还要重启共享的 OpenCode server，否则旧的 server reporter 会覆盖 pane-local 状态。其余 hook 类集成（Claude、Codex、Copilot、Devin、Droid、Kimi、Qoder、Qwen、Letta、Cursor、Grok、Antigravity）在 agent 下次触发对应 hook 事件时生效。

安装会不会破坏我已有的配置？

设计上不会。Grok 会合并该目录里所有 hooks/*.json，所以 Herdr 写一个自包含的 hooks/herdr.json，从不编辑其他 hook 文件；Antigravity 的 hooks.json 按 hook 名 keyed，安装只重写 herdr 块；OpenCode 注册插件时保留其他偏好和插件；卸载一律只移除 Herdr 自己的条目和托管文件。唯一的例外是 Codex 卸载不动 config.toml（它安装时确保了 [features] hooks = true，卸载留着）。

Letta 为什么在 Settings 里看不到？

Letta Code 的集成安装是实验性的且仅限 CLI。它不会出现在 Settings 的集成界面里，也不在 JSON 集成 API 里。herdr integration status 把它报成 letta (experimental)。但 agent 检测和 herdr agent start --kind letta 不受这个安装限制影响，照常可用。
