Herdr 插件与市场实战：manifest 的两条硬拒绝、注入的 14 个环境变量、config 与 state 不同根，以及注册表是全局的

用本机实测讲清 Herdr 插件模型：没有 SDK——整个 Herdr CLI 就是插件 API；manifest 四个必填顶层字段与两条硬拒绝错误码 invalid_plugin_min_herdr_version、plugin_requires_newer_herdr；link 与 install 在 build 命令上的分工；两条只警告不阻断的软校验（未知事件名、未声明 platforms）；实测抓到的 14 个注入环境变量与 HERDR_PLUGIN_CONTEXT_JSON 的完整字段；plugin config-dir 打印的是 config 目录而 HERDR_PLUGIN_STATE_DIR 在 ~/.local/state 的另一棵树；startup 钩子不在 link 时运行、只有 server 重启才跑；事件钩子的触发与 disable 后的静默；以及 plugins.json 是全局注册表、HERDR_CONFIG_PATH 搬不走它这个必须知道的副作用。附市场索引规则与信任边界。基线 herdr 0.9.2。

September 30, 2026 · 7 min · 1343 words · 梦兽编程 -  |  English

模块 4 前三篇解决了「从外部怎么指挥 Herdr」。这一篇解决另一件事：怎么把你总结出来的编排固化成 Herdr 里的一等公民——有菜单项、有键位、有事件钩子、有自己的 pane，别人一条 herdr plugin install 就能拿走。

Herdr 的插件模型有个很少见的决定：没有 SDK。听起来很自由，但它同时意味着没有类型检查、没有沙箱、没有编译期保护——所有约束都挪到了 manifest 校验和运行时。

这一篇把这套边界逐个实测出来：哪些字段缺了直接拒、哪些只警告不拦、命令到底被注入了什么、状态该往哪写、以及一个我在做实验时踩到的真实副作用。

基线：herdr 0.9.2 stable · macOS · 全部实验在隔离命名会话里做，实验结束后探针插件已从注册表清除（plugins.json 回到 []）。

结论前置#

Herdr 插件 = 一份 manifest + 若干 argv 命令，整个 CLI 就是它的 API。 manifest 只有四个必填顶层字段，缺了就硬拒；另外两类校验（未知事件名、未声明 platforms）只警告不阻断。 运行时 Herdr 注入 14 个 HERDR_* 变量，其中 config 目录和 state 目录不在同一棵树下。 startup 钩子不在 link 时运行，只有 server 重启才跑。 而插件注册表是全局的——HERDR_CONFIG_PATH 搬不走它。

一、职责边界：Herdr 管宿主，插件管实现#

文档给的分工很清楚：

Herdr 负责插件负责
安装、manifest 校验、键位、终端 pane、事件、调用上下文、socket 访问实现语言、依赖、文件、持久状态

没有独立的插件 SDK，也没有限制的命令集。 原文：「整个 Herdr CLI 就是插件 API」，插件可以运行你自己能以 herdr ... 运行的任何东西。

两条 v1 的明确边界值得先记住：

  • 运行时注册 action 不在 v1 范围内——action、event hook、pane、link handler 全部在 manifest 里静态声明
  • 原生非终端插件 UI 不在 v1 范围内——插件要 UI，就声明一个 pane 跑 TUI

第二条其实是个设计取向：Herdr 的扩展 UI 就是终端。这和它「终端工作区」的定位一致，也意味着插件 UI 自动获得分屏、滚动、SSH 复用这些能力。

二、manifest：四个必填、两类入口、一条命令规则#

id = "example.workspace-tools"
name = "Workspace Tools"
version = "0.1.0"
min_herdr_version = "0.9.0"
description = "Small workspace helpers"
platforms = ["linux", "macos", "windows"]

[[actions]]
id = "list-workspaces"
title = "List workspaces"
contexts = ["workspace"]
command = ["herdr", "workspace", "list"]

顶层 id、name、version、min_herdr_version 必填，description 可选。

id 的字符规则分两层，很容易记错：

id 类型允许字符允许点号
plugin idASCII 字母、数字、. : _ -✅
action / pane / link handler idASCII 字母、数字、: _ -❌ 不允许点号

原因是 Herdr 需要全局唯一时用 plugin.id.action 这种点号限定形式——局部 id 里有点号会让限定名歧义。

command 是 argv 数组，不经过 shell：没有 shell 展开，除非你自己的命令启动一个 shell。这条决定了两种写法各有用途：

command = ["herdr", "workspace", "list"]                        # 纯 argv，最可移植
command = ["sh", "-c", "env | sort >> \"$FOO\"; echo ok"]        # 需要管道/重定向时显式起 shell

（第二种我在实测探针插件里用了，因为要抓环境变量——见第四节。）

两条硬拒绝，实测错误码#

缺 min_herdr_version：

herdr --session lab plugin link /tmp/nomin

{"error":{"code":"invalid_plugin_min_herdr_version","message":"plugin min_herdr_version is required"},"id":"cli:plugin"}

声明的版本比当前二进制新：

herdr --session lab plugin link /tmp/newer     # 清单里 min_herdr_version = "0.99.0"

{"error":{"code":"plugin_requires_newer_herdr","message":"plugin requires Herdr 0.99.0 or newer; current Herdr is 0.9.2"},"id":"cli:plugin"}

min_herdr_version 的正确语义：填「支持你用到的插件 API、事件名、清单字段的最旧 Herdr 版本」。它是闸门也是承诺——你声明了，用户装的时候 Herdr 就能替他判断兼容性。

两条软校验：只警告，不阻断#

这是最容易漏的一类反馈——link 成功了，但返回体里有 warnings：

herdr --session lab plugin link /tmp/labplugin     # 故意漏掉 platforms，并把事件名拼错

{"result":{"plugin":{
  "plugin_id":"rex.hello-lab","enabled":true,"source":{"kind":"local"},
  "manifest_path":"/private/tmp/labplugin/herdr-plugin.toml",
  "min_herdr_version":"0.9.0","version":"0.1.0",
  "warnings":[
    "unknown event 'worktree.craeted'",
    "manifest does not declare platforms; platform support unknown"
  ]}}}

两条都在，而且 link 照样成功。plugin list 会把它们原样显示：

1 plugin installed:
- rex.hello-lab (Hello Lab) enabled [local:/private/tmp/labplugin; 2 warning(s)]
  warning: unknown event 'worktree.craeted'
  warning: manifest does not declare platforms; platform support unknown

事件名在 link 时就对已知事件表校验（文档明确），所以拼错事件名不会报错、只会静默不触发——必须去读 warnings。这也是第 2 篇那个坑的插件版：worktree.created 是合法事件名，worktree.craeted 不是，但两者在 TOML 里长得一样。

platforms 的分工也值得记：顶层声明表示「这个插件能在哪些 OS 跑」；build / startup / action / event / pane / link handler 各自也能声明 platforms 覆盖顶层；不覆盖就继承。调用一个有效 platforms 不含当前 OS 的 action 或 pane，返回 platform_unsupported。

三、link 与 install：build 命令只属于 install#

| | plugin link <dir|manifest> | plugin install owner/repo[/subdir] | |—|—|—| | 用途 | 本地开发、从 checkout 测试 | 从公开 GitHub 仓库安装 | | 跑 [[build]] | 不跑（作者自己构建工作树） | 确认后、注册前跑 | | build 失败 | 不适用 | 整个安装中止，插件不注册 | | 信任预览 | 无 | 交互式终端里展示源码与将运行的命令 | | 非交互 | — | --yes；--ref 钉版本 | | 存储位置 | 你的目录 | Herdr 管理的 checkout | | 重复安装 | — | 重装替换受管 checkout；覆盖本地 link 的插件会被拒绝 |

[[build]] 也是普通 argv 命令，但不接收运行时插件上下文，也不接收 Herdr socket 环境变量。它需要的 cargo / npm / bun / lua 得用户机器上有——Herdr 报告构建失败但不装工具链。构建失败信息包含 plugin id、build 序号、工作目录、命令、退出状态或 spawn 错误、以及截断后的 stdout/stderr，但不解释工具输出。

还有一条容易忽略：install 预览之后如果 build 改了 herdr-plugin.toml，安装中止。这是防「预览的是 A、装的是 B」的闸门。

四、运行时注入：实测 14 个变量#

我用一个把 env | grep '^HERDR_' 打到 stdout 的 action 抓了完整清单（本机实测，插件日志的 stdout 字段）：

HERDR_BIN_PATH=/Users/rex/.local/bin/herdr
HERDR_ENV=1
HERDR_PANE_ID=w1:p1
HERDR_PLUGIN_ACTION_ID=dump-env
HERDR_PLUGIN_CONFIG_DIR=/Users/rex/.config/herdr/plugins/config/rex.env-probe
HERDR_PLUGIN_CONTEXT_JSON={"workspace_id":"w1","workspace_label":"tmp","workspace_cwd":"/private/tmp","tab_id":"w1:t1","tab_label":"1","focused_pane_id":"w1:p1","focused_pane_cwd":"/private/tmp","focused_pane_agent":"agent-a","focused_pane_status":"working","invocation_source":"cli","correlation_id":"cli:plugin"}
HERDR_PLUGIN_ID=rex.env-probe
HERDR_PLUGIN_ROOT=/private/tmp/labplugin2
HERDR_PLUGIN_STATE_DIR=/Users/rex/.local/state/herdr/plugins/rex.env-probe
HERDR_SESSION=batch8-lab
HERDR_SOCKET_PATH=/Users/rex/.config/herdr/sessions/batch8-lab/herdr.sock
HERDR_TAB_ID=w1:t1
HERDR_WORKSPACE_ID=w1

逐个分组看：

组变量用途
回调 HerdrHERDR_BIN_PATH、HERDR_SOCKET_PATH前者可移植，后者 OS 特定
嵌套标记HERDR_ENV=1见下方警告
位置HERDR_SESSION、HERDR_WORKSPACE_ID、HERDR_TAB_ID、HERDR_PANE_ID调用发生在哪个会话的哪个位置
身份HERDR_PLUGIN_ID、HERDR_PLUGIN_ROOT、HERDR_PLUGIN_CONFIG_DIR、HERDR_PLUGIN_STATE_DIR我是谁、我在哪、我能写哪
入口HERDR_PLUGIN_ACTION_ID（action）/ HERDR_PLUGIN_EVENT（startup 与 event hook）/ HERDR_PLUGIN_ENTRYPOINT_ID（pane）哪个入口点触发我
上下文HERDR_PLUGIN_CONTEXT_JSON完整调用上下文

⚠️ HERDR_ENV=1 意味着插件里起不了嵌套 Herdr#

注入的环境里带 HERDR_ENV=1——所以插件命令里如果试图启动新的 Herdr client，会撞上第 1 篇那道嵌套保护闸门（nested herdr is disabled by default）。插件应该通过 CLI/socket 操作现有 server，而不是起新 client。

为什么官方建议用 HERDR_BIN_PATH 而不是裸 socket#

HERDR_SOCKET_PATH 背后的传输是 OS 特定的：Unix 连 socket 路径，Windows 连命名管道。走 HERDR_BIN_PATH 调 CLI 就绕开了这个差异。文档在插件和 socket API 两处都强调了这点。

config 目录和 state 目录不在同一棵树下#

这是实测里最容易踩空的一处：

HERDR_PLUGIN_CONFIG_DIR = ~/.config/herdr/plugins/config/<id>
HERDR_PLUGIN_STATE_DIR  = ~/.local/state/herdr/plugins/<id>

我最初把 state 写到 $HERDR_PLUGIN_STATE_DIR/env.log，然后去 ~/.config/herdr/plugins/ 下面找——找不到。文件其实写成功了，在 state 树里：

$ ls -l ~/.local/state/herdr/plugins/rex.env-probe/
-rw-r--r--@ 1 rex  staff  787 Sep 30 18:26 env.log

顺带一条 CLI 陷阱：

herdr plugin config-dir rex.env-probe
# /Users/rex/.config/herdr/plugins/config/rex.env-probe   ← 只有 config，没有 state

plugin config-dir 打印的是 config 目录，而且必须带 <plugin_id>（不带会 usage: herdr plugin config-dir <plugin_id>）。想知道 state 目录只能读 HERDR_PLUGIN_STATE_DIR。

三个目录的分工（文档明确）：

目录放什么Herdr 的行为
HERDR_PLUGIN_ROOT插件源码GitHub 安装下是受管 checkout；不要存凭据或持久状态
HERDR_PLUGIN_CONFIG_DIR用户可编辑配置（如 .env）会创建，并在存在时从旧的插件配置位置迁移播种；不校验、不同步、不删除内容
HERDR_PLUGIN_STATE_DIR本地运行状态会创建；文件格式与生命周期归插件

HERDR_PLUGIN_CONTEXT_JSON 里带着 agent 状态#

上面那份实测 JSON 里有两个字段值得单独指出：

"focused_pane_agent":"agent-a", "focused_pane_status":"working"

模块 3 讲的 agent 状态直接进了插件上下文。所以一个插件 action 可以只看上下文就知道「用户当前聚焦的 pane 里跑着哪个 agent、它在不在干活」，不需要额外调用。

还有 invocation_source: "cli" 和 correlation_id: "cli:plugin"——同一个 action 从 TUI 菜单点和从 CLI 调用，上下文里是可区分的。做「只在人工触发时才弹确认」这类逻辑用得上。

文档列出的上下文字段还包括 worktree、selected text、clicked URL、link handler——只在对应调用可用时出现（所以你的解析要按缺字段处理）。

五、三类入口的真实行为#

startup 钩子：不在 link 时跑#

文档说 startup 命令「在每个启用的插件恢复完会话、API socket 就绪后运行一次；live handoff 接管时再跑；client attach、config reload、插件 link 或 enable 时不跑」。

本机实测：link 之后 events.log 只有一行（事件钩子写的）；把命名会话 session stop 再重新起来之后：

event:workspace.created
startup-ran          ← 重启之后才出现

所以别在 link 之后假设 startup 钩子已经跑过。它的定位是 one-shot 初始化（恢复插件自己的状态、调用需要的 API、然后退出），不是常驻守护进程。启动失败不拖垮 server，只安静地记进插件命令日志。

一个正经的用法被文档点出来：把声明式的 Agent view 存到 HERDR_PLUGIN_STATE_DIR，然后在 startup 钩子里读回来重新应用——因为 server 重启后视图需要重建。

事件钩子：会触发，但 disable 后静默#

[[events]]
on = "workspace.created"
command = ["sh", "-c", "echo \"event:$HERDR_PLUGIN_EVENT\" >> \"$HERDR_PLUGIN_STATE_DIR/events.log\""]

本机实测四步：

创建 workspace            → events.log 追加 "event:workspace.created"    ✅ 触发
plugin disable 后创建     → events.log 行数不变（2 行）                  ✅ 不触发
disable 状态下 invoke     → rc=1  {"code":"plugin_disabled","message":"plugin rex.env-probe is disabled"}
plugin enable 后创建      → events.log 变 3 行                          ✅ 恢复触发

事件钩子额外收到 HERDR_PLUGIN_EVENT_JSON（完整事件负载）。

action：plugin action list 会显示继承来的 platforms#

{'plugin_id': 'rex.env-probe', 'action_id': 'dump-env', 'contexts': ['workspace'], 'title': 'Dump runtime env'}
keys: ['action_id', 'command', 'contexts', 'platforms', 'plugin_id', 'title']

注意 platforms 出现在 action 的 keys 里——即使我只在顶层声明了它。这就是第二节说的「继承」在服务端的体现。

CLI 调用形式（第 1 篇踩过的那个）：

herdr plugin action invoke <ACTION_ID> --plugin <PLUGIN_ID>

--plugin 是选项不是位置参数。返回体里带 context（含 correlation_id、focused pane 信息），和 plugin.action.invoke 的 socket 参数 context 对应。

六、注册表是全局的：一个我踩到的真实副作用#

文档说 plugins.json 写在 session.json 旁边。实测它是全局的，而且 HERDR_CONFIG_PATH 搬不走：

我设了 HERDR_CONFIG_PATH=/tmp/labcfg/config.toml 之后实际落点
config.toml/tmp/labcfg/config.toml ✅ 搬走了
release-notes.json/tmp/labcfg/release-notes.json ✅ 搬走了
sessions/<name>/~/.config/herdr/sessions/<name>/ ❌ 仍全局
plugins.json~/.config/herdr/plugins.json ❌ 仍全局
插件 config 目录~/.config/herdr/plugins/config/<id> ❌ 仍全局

后果不是理论上的：我在一个隔离会话里 link 了探针插件，然后 herdr plugin list 在默认会话（也就是我实际在用的那个）里同样列出了它。

所以：插件不是会话级资源。 会话隔离的是 socket、cwd、workspace 拓扑和注入的 HERDR_SESSION；插件安装状态跨所有会话共享。测插件时要么接受这个共享、要么测完立刻 plugin unlink（我做了后者，注册表已回到 []，默认会话 No plugins installed.）。

unlink 与 uninstall 的区别：unlink 只注销、保留文件；uninstall 注销并删除 Herdr 管理的 GitHub checkout 文件。对本地 link 的插件用 unlink。

七、市场：30 分钟刷新的自动索引#

市场的规则很简单，但每一条都有安全含义：

规则内容
收录条件公开 GitHub 仓库 + topic herdr-plugin + 默认分支上至少一个可解析必填元数据的 herdr-plugin.toml
卡片粒度一个仓库一张卡片，每个有效清单算一个可单独安装的插件
清单位置根目录或子目录都算
刷新每 30 分钟；仓库默认分支 head 变化时重扫
卡片显示仓库名、owner、描述、star 数、主语言、最后 push 时间；插件行显示 name 和 version 并链到确切源码目录
索引记录清单路径、id、name、version、platforms、min_herdr_version，加上默认分支的确切 commit
排除fork、归档仓库、无有效清单、元数据格式错误的清单
审核无

安装直接从 GitHub：

herdr plugin install ogulcancelik/herdr-plugin-examples/worktree-bootstrap

owner/repo[/subdir...] 简写形式，用 git，交互终端展示信任预览，跑支持的 build 命令，存进 Herdr 管理的目录。非交互用 --yes，钉版本用 --ref。

信任边界要自己承担#

文档说得非常直白，值得原文引用：

插件就是在你机器上运行的普通代码。它的 build 和 runtime 命令以你的用户身份运行、继承你的环境、并能调用完整的 Herdr CLI。 Herdr 校验 manifest、把每个插件的 config 和 state 放在各自目录里，但它不审查也不沙箱插件代码。

所以安装前该做的事：

  1. 读 herdr-plugin.toml，特别是 [[build]]、[[startup]] 和每个 command——startup 钩子是会自动运行的代码，install 预览会把它们全部列出来
  2. 读它要跑的那些脚本或二进制
  3. 用 --ref 钉一个你审过的 revision
  4. 记住 min_herdr_version 只保证 API 兼容，不保证恶意与否

八、避坑指南#

  1. link 成功不等于清单干净。warnings 里可能藏着拼错的事件名——它永远不会触发。每次 link 都读返回体。
  2. min_herdr_version 缺失是硬拒绝（invalid_plugin_min_herdr_version），不是警告。四个顶层必填字段一个都不能少。
  3. 别在 link 之后期待 startup 钩子已经跑过。只有 server 启动 / live handoff 才跑。
  4. state 和 config 不在同一棵树下。写文件用注入的 HERDR_PLUGIN_STATE_DIR，别去 ~/.config/herdr/plugins/ 找。
  5. plugin config-dir 只打印 config 目录，且必须带 <plugin_id>。
  6. 不要往 HERDR_PLUGIN_ROOT 写持久状态——GitHub 安装下它是受管 checkout，重装会被替换。
  7. 插件注册表是全局的，HERDR_CONFIG_PATH 搬不走。测插件之后记得 plugin unlink。
  8. plugin link 不跑 build 命令，所以「link 能用、install 挂掉」是正常现象——本地开发时自己构建。
  9. build 命令拿不到 socket 环境变量，别在 build 里调 Herdr。
  10. 插件命令里起新 Herdr client 会被嵌套保护拒绝（HERDR_ENV=1 被注入）。要操作 Herdr 就走 HERDR_BIN_PATH 的 CLI 或现有 socket。
  11. Windows 可移植性：优先 HERDR_BIN_PATH + CLI，不要自己拼命名管道名。
  12. action / pane / link handler 的局部 id 不能用点号——限定形式 plugin.id.action 需要点号做分隔。
  13. 运行时注册 action 不可能（v1 不含），需要动态行为就用 manifest 里静态声明的入口组合。
  14. 市场收录 ≠ 审查通过。它只意味着仓库自己打了 herdr-plugin 标签。

常见问题

写 Herdr 插件需要学一个 SDK 吗？

不需要，官方文档明确写着没有独立的插件 SDK，也没有受限命令集——整个 Herdr CLI 就是插件 API。插件清单里声明的 command 是一个 argv 数组，可以是 bash、node、python、rust 二进制、lua，或你机器上能跑的任何命令。需要多做事情时，命令再通过 HERDR_BIN_PATH 指回的 Herdr 二进制回调 CLI，或者自己走 socket。Herdr 负责宿主面：安装、清单校验、键位、终端 pane、事件、调用上下文、socket 访问；插件负责实现语言、依赖、文件和持久状态。

插件装不上，报 invalid_plugin_min_herdr_version 是什么意思？

min_herdr_version 是四个必填顶层字段之一（id、name、version、min_herdr_version），缺了就会被拒绝。本机实测两个错误码：缺字段时是 invalid_plugin_min_herdr_version，message 为 plugin min_herdr_version is required；声明的版本比当前二进制新时是 plugin_requires_newer_herdr，本机 message 原样是 plugin requires Herdr 0.99.0 or newer; current Herdr is 0.9.2。这个字段的语义是「支持本插件用到的插件 API、事件名和清单字段的最旧 Herdr 版本」，所以它既是安装闸门，也是你升版时该改的地方。

为什么我的 startup 钩子没有运行？

因为 startup 钩子只在 server 恢复完会话、API socket 就绪之后跑，link 和 enable 都不会触发它，client attach 和 config reload 也不会。本机实测：link 之后 events.log 里只有事件钩子写的一行；把那个命名会话 stop 再重新起来，startup-ran 才追加进去。另外它是 one-shot 初始化命令而不是被守护的常驻进程——该做的是恢复插件自己的状态、调用需要的 Herdr API、然后退出。启动失败不会拖垮 server，但只会安静地记在插件命令日志里。

插件的配置文件和运行状态该写在哪？

用注入的两个目录，别自己拼路径，而且要知道它们不在同一棵树下。本机实测 HERDR_PLUGIN_CONFIG_DIR 是 ~/.config/herdr/plugins/config/<plugin_id>，而 HERDR_PLUGIN_STATE_DIR 是 ~/.local/state/herdr/plugins/<plugin_id>——config 在 config 树、state 在 state 树。用户可编辑的东西（比如 .env）放 config，本地运行状态放 state。还有一个坑：herdr plugin config-dir <id> 打印的是 config 目录，不是 state 目录。至于 HERDR_PLUGIN_ROOT，那是安装或 link 的插件目录，GitHub 安装下它是被管理的源码 checkout，不要往那里写凭据或持久状态。

插件能装到某个会话单独一份吗？

不能。本机实测插件注册表 plugins.json 是全局的，位于 ~/.config/herdr/plugins.json，而且 HERDR_CONFIG_PATH 搬不走它——我把配置目录指到 /tmp 的独立会话里 link 了一个探针插件，结果默认会话的 herdr plugin list 也看到了它。真正按会话隔离的是 socket 和运行时环境（注入的 HERDR_SOCKET_PATH 和 HERDR_SESSION 会指向那个会话），插件本身是全局安装、按调用所在会话执行。

Herdr 插件市场会审核提交的插件吗？

不会。市场索引的是打了 GitHub topic herdr-plugin 的公开仓库，只要默认分支上有至少一个能解析出必填元数据的 herdr-plugin.toml 就会被收录，一个仓库一张卡片、每个有效清单算一个可单独安装的插件。索引每 30 分钟刷新一次，仓库默认分支头变化时会重新扫描。官方原文说得很直接：被收录意味着仓库自己打了标签，不代表 Herdr 审查过它。fork、归档仓库、没有有效插件清单的仓库、以及元数据格式错误的清单都会被排除。
