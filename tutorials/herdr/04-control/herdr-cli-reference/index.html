Herdr CLI 实战地图：18 个动词、三档退出码、四级会话路由，以及 agent 里调用它必撞的嵌套保护

把 herdr 命令行当成接口而不是菜单来读：本机 herdr 0.9.2 实测出 18 个顶层动词与 102 个 socket 方法的对应关系、单行 JSON 信封与 0/1/2 三档退出码的分界、--session 到 HERDR_SOCKET_PATH 到 HERDR_SESSION 到默认 socket 的四级路由、named session 独立 socket 的真实落点、HERDR_CONFIG_PATH 搬得走 config.toml 却搬不走 sessions 目录和 plugins.json、在 Herdr pane 里启动嵌套 Herdr 被默认拒绝以及零尺寸终端的真相、pane_id 与 agent target 的寻址边界，以及 pane run 把 -- 原样交给 shell、wait-output 的 --match/--regex 二选一、api schema 的参数名等六个参数陷阱。

September 30, 2026 · 10 min · 1937 words · 梦兽编程 -  |  English

你在 Herdr 的 pane 里跑着一个 agent，现在你想让这个 agent 反过来操作 Herdr：开一个 pane 跑测试、等另一个 pane 里的 agent 跑完、读一段屏幕输出。

第一反应是 herdr --help，然后你会看到 22 行用法、18 个动词、每个动词下面还有几个到二十几个子命令——而 help 里那些「Common commands」只挑了十来条给你看。

这篇不打算把命令抄一遍。这篇给你三样东西：命令面的真实结构（哪些是给人看的，哪些是给脚本用的）、输出与退出码的契约（脚本可靠性的全部依赖点）、路由与寻址规则（决定你的命令打到哪个会话、哪个 pane）。

基线：herdr 0.9.2 stable · macOS · 下文所有输出都是本机实测，标注了「本机实测」的地方你可以逐条复现。

结论前置#

herdr --help 是给人看的菜单，socket API 才是接口，而 CLI 是 API 的薄封装。 所以读 CLI 的正确姿势不是背命令，而是记住三件事：输出恒为单行 JSON 信封、退出码只有 0/1/2 三档且 1 的错误在 stderr、会话路由有四级优先级。 剩下的坑几乎全部来自两个边界：你正在 Herdr 里面（嵌套保护），和你以为的名字不是名字（target 寻址）。

一、命令面的真实结构：18 个动词，102 个方法#

先给一张实测的规模表。左列是 CLI 顶层动词，右列是它自己 help 里列出的子命令数量：

动词子命令数职责
pane25终端 pane 的全部操作：布局、读写、输入、生命周期上报
agent11agent 视角的操作：读、发键、prompt、wait、start、explain
plugin11插件安装、启停、action 调用、日志、pane
machine8保存的 SSH 机器：增删改、启停、状态、重连
workspace7工作区生命周期
tab6标签页生命周期
server5停止、重载配置、agent 检测清单三件套
session4命名会话 list / attach / stop / delete
integration3官方集成的 install / uninstall / status
terminal3attach / session / title
api2snapshot / schema
config2check / reset-keys
channel2show / set
notification1show
status / update / completion / worktree—工具型与专用族（worktree 实际有 4 个子命令）

本机实测：herdr --help 的 Usage 段列了 22 行，但那是「用法示例」而不是命令清单——plugin、terminal、status 都没出现在 Usage 里。想确认一个动词是否存在，直接 herdr <verb> --help，看它有没有回一句带描述的用法块。反过来，herdr doctor 回答：

unknown command: doctor
run 'herdr --help' for usage

退出码 2（本机实测）。也就是说 Herdr 没有 doctor 这种一键体检命令，排障要靠 config check、status、api snapshot 三件分开做。

CLI 覆盖的不是全部接口#

herdr api schema --json 在本机吐出 272 KB 的 JSON Schema，里面列了 102 个方法，分 19 个族：

pane 35 · agent 12 · plugin 11 · workspace 9 · tab 7 · server 6 · worktree 4
layout 3 · integration 3 · events 2 · client 2
+ 8 个单方法族：ping / command.invoke / session.snapshot / popup.close
  / notification.show / product_announcement.dismiss / release_notes.dismiss
  / client_shell.surface.set

对比第一张表就能看出结构：CLI 动词数（18）远小于方法数（102）。像 pane.scroll、pane.clear、pane.link.activate、layout.apply、agent.view.set、command.invoke 这些方法在 CLI 里没有对应命令，只能走 socket（第 2 篇）。

反过来也有一条规律值得记：CLI 的 id 字段就是它调了哪个方法。herdr pane current 返回 "id":"cli:pane:current"，herdr workspace list 返回 "id":"cli:workspace:list"。所以看任何一段 CLI 输出，都能立刻反推底层方法名，再去 schema 里查参数定义。

help 里藏着一份给 agent 的说明书#

每个 help 输出的末尾都有这么一段（本机实测）：

Are you an AI? Use these resources ONLY IF your task specifically asks you to:
  Help a human understand or set up Herdr for the first time:
    https://herdr.dev/agent-guide.md
  Debug or investigate a problem with Herdr:
    https://herdr.dev/llms.txt
  Control Herdr panes, agents, or workspaces:
    SKIP if a Herdr skill is already in your context. Otherwise run: herdr --skill

herdr --skill 在本机实测输出 14162 字节的技能文件，不需要联网、不需要装任何东西。这是给 agent 的操作手册，也是你写 agent 自动化脚本时最该先读的一份——比 --help 完整得多。

顺带一提，那段拒绝嵌套的报错里还带了一句《侏罗纪公园》的台词。这类细节说明 Herdr 的错误信息是写给人读的，而它的 JSON 错误是写给脚本读的——两套并存，别混着用（见下一节）。

二、输出契约：单行 JSON 信封 + 三档退出码#

成功时长什么样#

所有机器可读输出都是一行 JSON，固定信封：

herdr pane current

{"id":"cli:pane:current","result":{"pane":{"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-hugo","focused":true,"pane_id":"w3:p2","revision":1,"tab_id":"w3:t2","terminal_id":"term_65ca0990363e22","workspace_id":"w3"}}}

三个约定值得单独记：

  1. id 不是请求 id，是命令标识。CLI 自己生成，形如 cli:<verb>:<subcommand>。socket 直连时 id 才是你发什么回什么（第 2 篇）。
  2. result.type 是判别式。同一个 result 字段在不同命令下形状不同，靠 type 分支而不是靠猜 key。
  3. 成功可能没有任何输出。herdr pane report-agent 成功时什么都不打印（本机实测，rc=0、stdout 空）。别把「没输出」当失败——要判成功就判退出码。

失败时长什么样#

本机实测四组，退出码和流的分界非常干净：

场景命令rcstdoutstderr
目标不存在herdr agent get nosuch1空{"error":{"code":"agent_not_found","message":"agent target nosuch not found"},"id":"cli:agent:get"}
等待超时herdr pane wait-output w1:p1 --match NEVER --timeout 12001空JSON 错误
参数名错herdr pane list --bogus2空unknown option: --bogus
动词不存在herdr doctor2空unknown command: doctor

这正好对上文档里那句「A timeout or server error is emitted as JSON on stderr with exit status 1. CLI usage errors exit with status 2.」——实测一致。

所以脚本里正确的写法是：

# ① 用法错误和环境错误分开处理：2 是你写错了，1 是环境/目标有问题
if ! out=$(herdr agent wait "$PANE" --until idle --timeout 60000 2>/tmp/err); then
  rc=$?
  if [ "$rc" -eq 2 ]; then echo "命令行写错了，别重试"; exit 2; fi
  echo "运行期失败：$(cat /tmp/err)"   # 这里是 JSON，可以 jq .error.code
  exit "$rc"
fi

两个必须记住的分流规则：

  • 错误 JSON 在 stderr，不在 stdout。所以 herdr xxx | jq 在失败时 jq 收到空输入，你会误判成「没有结果」而不是「出错了」。要抓错误得单独重定向 stderr。
  • 退出码 2 不该重试（你的命令行是错的），退出码 1 才可能需要人看（目标没了、超时了、会话没起）。

--json 不是全局开关#

只有部分命令接受 --json：api schema、agent explain、plugin list、machine status 等。默认输出对列表类命令已经是 JSON，对人类可读类（plugin list、integration status、status）是文本，需要显式 --json。

herdr status 是个典型：默认输出三段文本（client: / server: / update:），而 herdr status client 和 herdr status server 各自只打一段——本机实测：

# herdr status client
version: 0.9.2
channel: stable
protocol: 22
endpoint_protocol_generation: 1
binary: /Users/rex/.local/bin/herdr

# herdr status server
status: running
version: 0.9.2
endpoint_compatible: yes
private_protocol: 22
private_protocol_compatible: yes
socket: /Users/rex/.config/herdr/herdr.sock

注意 protocol: 22 和 endpoint_protocol_generation: 1 这两个字段——它们是客户端和 server 的兼容性判据。脚本里在打 socket 之前先查 endpoint_compatible: yes，比事后收到协议错误便宜得多。

三、会话路由：四级优先，和两个「搬不走」的目录#

一条 CLI 命令要发到哪个 server，按这个顺序决定（文档定义，本机实测逐条验证）：

1. 显式 --session <name>
2. HERDR_SOCKET_PATH
3. HERDR_SESSION=<name>
4. 默认会话 socket

命名会话有各自独立的 socket：

~/.config/herdr/herdr.sock                          ← default
~/.config/herdr/sessions/<name>/herdr.sock          ← named

本机实测起了一个叫 batch8-lab 的会话，herdr session list 如实分开：

name                 status   directory                                        socket
default              running  /Users/rex/.config/herdr                         /Users/rex/.config/herdr/herdr.sock
batch8-lab           running  /Users/rex/.config/herdr/sessions/batch8-lab     /Users/rex/.config/herdr/sessions/batch8-lab/herdr.sock

而 herdr --session batch8-lab workspace list 返回的是那个会话自己的 w1，和我正在用的 w3 完全无关：

{"id":"cli:workspace:list","result":{"type":"workspace_list","workspaces":[{"active_tab_id":"w1:t1","agent_status":"unknown","focused":true,"label":"tmp","number":1,"pane_count":1,"tab_count":1,"workspace_id":"w1"}]}}

这就是安全边界：写操作只要带上 --session，物理上就走另一个 socket，不可能误伤你正在用的会话。做实验、测集成、跑破坏性脚本，都该这样隔离。

但 HERDR_CONFIG_PATH 不是隔离手段#

这是本篇最意外的实测。我想把整个 Herdr 状态搬到 /tmp，于是设了 HERDR_CONFIG_PATH=/tmp/labcfg/config.toml，然后起了个 labcfg 会话。结果：

项目实际落点搬走了吗
config.toml/tmp/labcfg/config.toml✅ 搬走了
release-notes.json/tmp/labcfg/release-notes.json✅ 搬走了
会话目录与 socket~/.config/herdr/sessions/labcfg/❌ 仍在全局
插件注册表~/.config/herdr/plugins.json❌ 仍在全局
插件配置目录~/.config/herdr/plugins/config/<id>❌ 仍在全局

最后一行不是纸上推演——我在 labcfg 会话里 link 了一个探针插件，然后 herdr plugin list 在默认会话里也能看到它。因为这个原因我立刻 plugin unlink 把注册表清回了 []。

结论要写死：HERDR_CONFIG_PATH 只搬配置文件，不搬运行时状态。真正的隔离单位是命名会话，插件注册表则是全局共享的——插件没有「只在这个会话里启用」这回事。

命名会话目录里还有一个符号链接值得注意#

本机实测 ~/.config/herdr/sessions/batch8-lab/ 的内容：

herdr.sock            ← 这个会话自己的 API socket
herdr-client.sock
herdr-server.log
herdr-client.log
session.json
session-snapshots/
herdr.sock.agent -> /Users/rex/.config/herdr/herdr.sock.agent   ← 指回默认会话！

最后一条是符号链接，指向默认会话的 agent socket。也就是说 agent 上报通道并不是每个命名会话一套。写多会话的 agent 集成时，这一点必须知道——否则你会以为给某个会话单独起了 agent 上报端点。

四、你在 Herdr 里面：两道门，一个绕法#

这是 agent 自动化最现实的问题：agent 跑在 Herdr 的 pane 里，它想开一个隔离会话做实验。

第一道门：嵌套保护#

本机实测，在 Herdr pane 里执行 herdr --session batch8-lab：

error: nested herdr is disabled by default.
see configuration if you want to enable it.

"you were so preoccupied with whether you could, you didn't stop to think if you should." — dr. malcolm

原因很直白：Herdr 给每个 pane 注入 HERDR_ENV=1，客户端看到这个变量就拒绝再套一层。这是防「agent 无限开新会话把机器吃光」的默认闸门。

第二道门：非交互环境没有终端尺寸#

清掉变量再试（env -u HERDR_ENV -u HERDR_PANE_ID），报错换了：

herdr: cannot attach without a usable terminal: terminal reported a zero-sized grid; run inside a terminal

两道门是不同性质的：第一道是策略（可以按配置放开），第二道是物理条件（客户端需要一个能报出行列数的终端才能渲染）。在 CI、脚本、script 命令这类假终端里，ioctl 问到的尺寸是 0×0，客户端直接放弃——它拒绝在一个不存在的屏幕上画东西。

顺带说，macOS 的 script -q /dev/null cmd 也不给你真实尺寸，所以别指望用 script 糊过去。

可用的绕法：分配一个带尺寸的 pty#

本机实测有效的做法是用 Python 的 pty.fork() 起子进程，然后显式设置窗口大小再让它 exec：

import os, pty, fcntl, termios, struct, select, time, signal

env = dict(os.environ)
for k in ("HERDR_ENV", "HERDR_PANE_ID", "HERDR_SOCKET_PATH", "HERDR_BIN_PATH"):
    env.pop(k, None)                      # 过第一道门

pid, fd = pty.fork()
if pid == 0:
    os.execvpe("herdr", ["herdr", "--session", "batch8-lab"], env)

# 过第二道门：给这个 pty 一个真实的行列数
fcntl.ioctl(fd, termios.TIOCSWINSZ, struct.pack("HHHH", 40, 140, 0, 0))

# 让 client 跑起来把 server 拉起来，然后我们只读输出不画屏
deadline = time.time() + 10
while time.time() < deadline:
    r, _, _ = select.select([fd], [], [], 0.3)
    if r:
        try:
            if not os.read(fd, 65536):
                break
        except OSError:
            break

os.kill(pid, signal.SIGTERM)              # client 死了，server 留着

跑完之后 herdr session list 里 batch8-lab 是 running，而那个 pty 里的 client 已经被我杀掉了。server 活得比 client 久——这一点在 ping 的能力协商里有明确声明（本机实测）：

{"id":"r1","result":{"type":"pong","version":"0.9.2","protocol":22,
  "capabilities":{"live_handoff":true,"detached_server_daemon":true,
    "endpoint_protocol_generation":1,"surface_interest":true,
    "health_check":true,"ssh_agent_registration":true}}}

detached_server_daemon: true 就是「client 不是 server 的父进程依赖」的承诺。所以起隔离会话的正确心智模型是：client 只是临时脚手架，用来把 server 拉起来；拉起之后你全程用 CLI 和 socket 操作，不需要任何 TUI。

收尾用 session stop，不要用 server stop#

测完了清理隔离会话：

herdr session stop batch8-lab     # 只停这一个命名会话

herdr server stop 停的是当前路由到的那个 server——如果你的 --session 写错或者忘了带，它停的就是你正在用的会话。在脚本里永远不要用 server stop，需要停测试会话就用 session stop <name>。这条我放在避坑清单第一条。

五、目标寻址：三种 id，两种能当 target#

Herdr 里有好几种 id，长得都像 w1:p1 / term_65ca0990363e22 / lab-bot，但能当 target 的只有两种。

文档规则：agent target 要么是唯一的 live agent 名字，要么是当前承载该 agent 的 pane id。terminal id 和裸的 agent kind 标签都不是 target。

这条规则我用了一次失败的实测才真正理解。

实测：显示名不是 live 名#

我给一个 pane 自报了一个 agent：

herdr --session batch8-lab pane report-agent w1:p1 \
  --source labtest --agent lab-bot --state working --seq <ms>

然后 agent list 里确实出现了它：

{"agents":[{"agent":"lab-bot","agent_status":"working","pane_id":"w1:p1","state_change_seq":5,...}],"type":"agent_list"}

但紧接着：

herdr --session batch8-lab agent get lab-bot
# {"error":{"code":"agent_not_found","message":"agent target lab-bot not found"},"id":"cli:agent:get"}   rc=1

herdr --session batch8-lab agent get w1:p1
# {"error":{"code":"agent_not_found","message":"agent target w1:p1 not found"},"id":"cli:agent:get"}

看起来自报的 agent 完全不可寻址。但这是我自己的测试时序有问题——我把 agent get 跑在了几秒之后，那时状态已经被清掉了（第 3 篇会讲这个 0.4 秒窗口）。重测、报告完立刻查：

+0.01s  agent get lab-bot               rc=1  agent_not_found
+0.01s  agent wait w1:p1 --until working rc=0  ✅ 成功返回，agent 字段就是 lab-bot
+0.02s  agent explain w1:p1             rc=1  agent_explain_unavailable
                                                  "does not have a detected agent label"

三条命令，三种语义，一次全部分开：

命令target 形式结果说明
agent waitpane id✅ rc=0走 pane 寻址，能命中自报状态
agent get自报名字❌ agent_not_found显示标签不是 live agent 名字
agent explainpane id❌ agent_explain_unavailableexplain 只解释检测结果，自报不算检测

所以正确的寻址方式是：自动化脚本一律用 pane id 当 target。 名字是给人看的，pane id 才是稳定的地址。agent start 起的 agent 才有可寻址的名字（文档原文：通过 agent start 启动的 agent 需要名字，手工启动的 agent 保持匿名，用它的 pane id 寻址）。

为什么这个区别重要#

因为「名字」在 Herdr 里有三个不同的来源，只有一个是可寻址的：

  1. agent start <name> --kind ... 的 <name> —— 可寻址，受 [a-z][a-z0-9_-]{0,31} 约束，live agent 之间唯一
  2. pane report-agent --agent <label> 的 <label> —— 显示标签，出现在 agent list 和侧边栏，但不是 target
  3. 检测清单识别出的 kind 标签（claude、pi、codex…）—— 由 Herdr 内部使用，agent explain --agent LABEL 的 --agent 接受它，但那是离线解释 fixture 的参数，不是 target

第 3 点和第 2 点的交互还藏着一个更深的坑（自报的 label 必须是 Herdr 认识的 kind 才留得住），那是第 3 篇的主题。

六、六个参数陷阱，全部实测#

① pane run 不吞 --#

herdr --session batch8-lab pane run w1:p1 -- echo hello-from-herdr-cli
# pane 里实际执行：-- echo hello-from-herdr-cli
# zsh: command not found: --

pane run <PANE_ID> <COMMAND>... 的 COMMAND 是变长位置参数，-- 被当成第一个参数原样送进 pane。正确写法：

herdr --session batch8-lab pane run w1:p1 echo hello-from-herdr-cli
# 2 秒后 pane read 回读：
# rex@… /tmp % echo hello-from-herdr-cli
# hello-from-herdr-cli

对比：pane report-agent 的 -- RESUME_COMMAND... 确实要 --（那是文档明确规定的分隔符）。同一个二进制里两种约定并存，判据是看 help 里 <COMMAND>... 前面有没有 --。

② pane wait-output 的 --match / --regex 是必填互斥组#

help 的 Usage 行写的是 [--match <TEXT>|--regex <PATTERN>]——clap 的 required group。两个都不给会是用法错误（rc=2）。两个都给是互斥错误。

本机实测的等待-匹配闭环：

( sleep 2; herdr --session batch8-lab pane run w1:p1 echo MARKER_7788 ) &
herdr --session batch8-lab pane wait-output w1:p1 --match MARKER_7788 --timeout 8000

{"id":"cli:pane:wait-output","result":{"matched_line":"rex@… /tmp % echo MARKER_7788","pane_id":"w1:p1","read":{"source":"recent_unwrapped","text":"…\nMARKER_7788\n…","truncated":false},"type":"output_matched"}}

注意返回里顺手带了整段快照（read 字段），所以你不需要匹配完再 read 一次。而 matched_line 匹配到的是命令行本身（echo MARKER_7788），不是输出行——因为回显也在屏幕里。这是个真实陷阱：如果你想等的是命令的输出，marker 要选一个不会出现在命令行里的串。

③ pane read 有 4 种 source，wait-output 只有 3 种#

pane read    --source  visible | recent | recent-unwrapped | detection
pane wait-output --source  visible | recent | recent-unwrapped

detection 只在 read 有——它给的是检测器看到的那份底部缓冲区，用来复现「为什么状态判错了」。想在 CLI 里复现 agent explain 的输入，就用它。

--format 还有 text 和 ansi 两档（read 支持，wait-output 不支持 --format，但有 --strip-ansi）。

④ api schema 的参数是 --output，不是 --out#

herdr api schema --out /tmp/s.json
# usage: herdr api schema [--json | --output PATH]

而且 --json 和 --output 是互斥的（用法行里是 [--json | --output PATH]）。默认输出是人类可读的摘要：

Herdr API schema
protocol: 22
schema_version: 1
schemas: error_response, event, request, subscription_event, success_response

要机器可读就 --json 重定向到文件（本机实测 272578 字节）。

⑤ plugin action invoke 的插件 id 是选项不是位置参数#

herdr plugin action invoke rex.hello-lab hello
# unknown option: hello      ← 第二个位置参数被当成选项解析失败

正确写法（help 明确：invoke [OPTIONS] <ACTION_ID>，插件是 --plugin <ID>）：

herdr plugin action invoke hello --plugin rex.hello-lab

⑥ plugin config-dir 必须带插件 id#

herdr plugin config-dir
# usage: herdr plugin config-dir <plugin_id>

七、避坑指南#

  1. server stop 会停掉你路由到的那个 server。忘了带 --session 就是停你正在用的会话。脚本里停测试会话只用 herdr session stop <name>。
  2. 别用 HERDR_CONFIG_PATH 做隔离。本机实测它只搬 config.toml 和 release-notes.json，sessions/ 和 plugins.json 仍在全局。真正的隔离单位是命名会话；插件注册表是全局的，没有 per-session 插件。
  3. 错误 JSON 在 stderr，不在 stdout。herdr xxx | jq 失败时 jq 收到空输入，你会把「出错」读成「没数据」。抓错误请 2> 单独重定向。
  4. 成功可能零输出。pane report-agent、pane run 成功时什么都不打印。判成功用退出码，不要用「有没有输出」。
  5. 退出码 2 不要重试（命令行写错了），1 才需要判断（目标丢失 / 超时）。把两者混在一个 if ! cmd 里，你会对着一个语法错误重试 30 次。
  6. 自报的 --agent 名字不能当 target。自动化一律用 pane id。agent get <自报名> 会得到 agent_not_found，这不是 bug。
  7. agent explain 对自报 agent 一定失败（agent_explain_unavailable）。explain 解释的是检测，不是上报。
  8. pane run 别加 --；pane report-agent 的 resume 命令必须加 --。两套约定并存。
  9. wait-output 的 --match 可能匹配到回显的命令行本身，不是命令输出。marker 选一个不出现在命令串里的值。
  10. pane.renamed 不是事件名。pane 侧是 pane.updated（这个坑在 socket 订阅里更致命，见第 2 篇：整个订阅会原子失败）。
  11. --help 的 Usage 段不是命令清单。plugin、terminal、status 都不在里面。别用 Usage 段推断功能面，用 herdr api schema 的 102 个方法。
  12. 嵌套保护是默认行为，不是环境坏了。在 Herdr 里起 Herdr 需要同时清 HERDR_ENV/HERDR_PANE_ID 并且给一个带真实尺寸的 pty，只做其中一件只会换一条错误信息。

九、速查：我建议你实际用的命令#

一份「日常真会用到」的最小子集，而不是全部 102 个方法：

# 环境与兼容性（先看这个，再谈别的）
herdr status                         # client / server / update 三段
herdr session list                   # 有哪些会话，socket 在哪

# 只读侦察
herdr api snapshot                   # 一次拿到全部 workspace/tab/pane/layout
herdr pane list --workspace w1       # 某个工作区的 pane
herdr pane current                   # 我在哪个 pane（agent 里最常用）
herdr pane read w1:p1 --source recent --lines 40

# 写操作（先确认 --session 指向隔离会话）
herdr --session lab pane run w1:p1 npm test
herdr --session lab pane wait-output w1:p1 --regex 'exit code [0-9]+' --timeout 60000
herdr --session lab agent wait w1:p1 --until idle --timeout 300000

# 诊断
herdr config check                   # 校验 config.toml 并打印诊断
herdr agent explain w1:p1 --json     # 状态为什么这么判（仅检测到的 agent）

api snapshot 是这里最被低估的一条：一次调用拿到 version、protocol、全部 workspaces / tabs / panes / layouts、focused_*_id 三件套。做自动化前先 snapshot 一次把 id 抄下来，比猜 id 再收 pane_not_found 快得多。

常见问题

herdr 的 CLI 命令有多少个？

分两层看。给人和脚本用的是 18 个顶层动词：agent、api、channel、completion、config、integration、machine、notification、pane、plugin、server、session、tab、terminal、update、worktree、workspace，加上 status 和 completion 两个工具型动词。其中 pane 一族最大，有 25 个子命令；agent 和 plugin 各 11 个；machine 8 个。真正的接口层是 socket API，herdr api schema --json 在本机吐出 102 个方法，分 19 个族，pane 占 35 个。CLI 只是这套 API 的薄封装，覆盖面比 API 小。

herdr 命令失败时怎么判断原因？

看退出码，只有三档。0 是成功。1 是运行期错误——错误 JSON 打在 stderr，stdout 是空的，比如查一个不存在的 agent 会得到 agent_not_found。2 是用法错误——参数名写错或者子命令不存在，比如 herdr pane list --bogus 回答 unknown option: --bogus，herdr doctor 回答 unknown command: doctor。所以脚本里判 1 和判 2 是两件不同的事：1 说明环境或目标有问题，2 说明你自己的命令行写错了。

为什么我在 Herdr 里开一个新 herdr 会话被拒绝了？

因为嵌套保护。Herdr 给你的每个 pane 注入 HERDR_ENV=1，在这个环境里再启动 herdr 客户端会被直接拒绝，报 nested herdr is disabled by default。这是有意的默认行为，不是 bug——否则 agent 会无限自我复制会话。绕法是在启动子进程时清掉 HERDR_ENV 和 HERDR_PANE_ID，但清掉之后你还会撞上第二道门：非交互环境没有可用的终端尺寸，报 terminal reported a zero-sized grid。要真正起一个隔离会话，得给它分配一个带真实窗口大小的 pty。

怎么让命令只作用于我的测试会话，不碰到正在用的那个？

用 --session <名字>，它排在会话路由四级优先的第一级。命名会话有自己独立的 socket，在 ~/.config/herdr/sessions/<名字>/herdr.sock，所以命令根本走不到你默认会话里去。注意 HERDR_CONFIG_PATH 不能当隔离手段用：本机实测它能把 config.toml 和 release-notes.json 搬到指定目录，但 sessions 目录仍然锚在 ~/.config/herdr/sessions/ 下面，插件注册表 plugins.json 也仍然写在全局位置。

herdr pane run 为什么要加 -- 反而失败了？

因为 pane run 不吞 --。本机实测 herdr pane run w1:p1 -- echo hi 会让 pane 里的 shell 收到字量的 -- echo hi，zsh 回答 command not found: --。正确写法是直接 herdr pane run w1:p1 echo hello，命令和它的参数依次跟在 pane id 后面。这个坑的来源是很多 CLI 习惯用 -- 分隔选项和位置参数，但这里的 COMMAND 是变长位置参数，不需要分隔符。

agent 命令的 target 到底能写什么？

两种：唯一的 live agent 名字，或者当前承载该 agent 的 pane id。terminal id 和裸的 agent kind 标签都不是 target。最容易踩的是自报名字——你用 herdr pane report-agent --agent my-bot 报上去的 my-bot 是给用户看的显示标签，不是 live agent 名字，所以 herdr agent get my-bot 会回答 agent_not_found。自己起的 agent 才有名字，手工启动的 agent 保持匿名，只能用它的 pane id 寻址。
