Herdr socket API 实战：一连接一请求的线格式、两套事件命名、schema 与运行时的四处不一致

CLI 只暴露 102 个 socket 方法里的一部分，这一篇直接写线协议：newline-delimited JSON 的真实帧格式、一连接一请求（实测第二个请求拿到 BrokenPipeError）、订阅连接为什么会话不断、id 必须是字符串的三种失败形态、非法 UTF-8 直接断连不给响应、未知参数被静默忽略、ping 的六个能力位、events.subscribe 的 27 个点号事件名与三个必填参数、events.wait 却要求下划线事件名且运行时只支持 pane_agent_status_changed、schema 声明与运行时行为的四处落差，以及用 herdr api schema --json 生成的 272KB JSON Schema 建客户端的正确姿势。基线 herdr 0.9.2。

September 30, 2026 · 6 min · 1251 words · 梦兽编程 -  |  English

第 1 篇末尾留了个问题：CLI 只覆盖 18 个动词，而底层有 102 个方法。差出来的那 80 多个方法，加上「事件订阅」这一整类能力，只能直接连 socket。

听起来是「换个传输层」的简单事。但我在本机把协议跑通的过程中撞到了 4 处 schema 声明和运行时行为不一致，其中两处足以让你的常驻客户端静默失效。这一篇把它们逐个摊开。

基线：herdr 0.9.2 stable · macOS · 所有帧内容都是本机实测原样输出。

结论前置#

Herdr 的 socket 协议是「一行一个请求、一次一条连接」的 NDJSON，不是多路复用的 RPC 通道。 除了订阅，你应当把每条连接当成一次函数调用：连上、发一行、读一行、关闭。 而事件系统有两套命名（订阅用点号、等待用下划线），events.wait 在 0.9.2 运行时只支持一种事件——尽管 schema 列了 19 种。 建客户端前先 herdr api schema --json，但不要只信 schema，用真实请求验证每一个你要用的方法。

一、传输层：三行说清，一帧验真#

Unix:      <config>/herdr.sock                    （命名会话：<config>/sessions/<name>/herdr.sock）
Windows:   named pipe
帧格式:     newline-delimited JSON，一行一个请求

本机实测最小一帧：

import socket, json
s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
s.connect("/Users/rex/.config/herdr/sessions/batch8-lab/herdr.sock")
s.sendall((json.dumps({"id": "r1", "method": "ping", "params": {}}) + "\n").encode())
buf = b""
while b"\n" not in buf:
    buf += s.recv(65536)
print(buf.split(b"\n")[0].decode())

{"id":"r1","result":{"type":"pong","version":"0.9.2","protocol":22,
  "capabilities":{"live_handoff":true,"detached_server_daemon":true,
    "endpoint_protocol_generation":1,"surface_interest":true,
    "health_check":true,"ssh_agent_registration":true}}}

六个能力位，每个都对应一类跨版本兼容判断：

能力位含义你该在什么时候查它
detached_server_daemonserver 不依赖 client 存活用临时 client 拉起 server 的脚本（第 1 篇）
live_handoff支持不丢会话的热交接升级 server 前
endpoint_protocol_generationUI 端点生成代（本机为 1）client/server 版本不同时
surface_interestSSH 联邦下只推选中机器的画面多机器场景
health_check静默断连能被判定远程/不稳定网络
ssh_agent_registrationSSH agent 注册远程机器接入

文档在协议稳定性一节明确写了：「Client and server builds do not need to match」，缺的方法只会禁用对应动作并给一个 client-local 提示，不会断连。但编号二进制协议（直接 terminal attach、live handoff）要求同装同版——用之前先查 ping 或 herdr status。

二、最重要的协议事实：一连接一请求#

这是本篇最值钱的一条，也是文档没有明说、只能实测出来的。

实测 A：管道化两个请求#

s.sendall(b'{"id":"q1","method":"ping","params":{}}\n{"id":"q2","method":"ping","params":{}}\n')

读到的是：

bytes=243 response-lines=1
   {"id":"q1","result":{"type":"pong",...

两个请求，一个响应，然后 recv() 返回空（server 关闭连接）。第二个请求根本没被处理。

实测 B：在同一连接上顺序发（等第一个响应回来再发第二个）#

request 1: {"id":"s1","result":{"type":"pong",...
request 2: BrokenPipeError: [Errno 32] Broken pipe

第一个响应之后连接的写端已经被关掉。不是「不推荐管道化」，是物理上不行。

正确的客户端模型#

def call(method, params, id_=None, sock=SOCK, timeout=5.0):
    """One request per connection — that is the protocol, not a limitation of this helper."""
    s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
    s.settimeout(timeout)
    s.connect(sock)
    try:
        s.sendall((json.dumps({"id": id_ or next_id(),
                               "method": method, "params": params}) + "\n").encode())
        buf = b""
        while b"\n" not in buf:
            chunk = s.recv(65536)
            if not chunk:
                raise ConnectionError("server closed without a response")
            buf += chunk
        return json.loads(buf.split(b"\n")[0].decode())
    finally:
        s.close()

唯一例外是订阅：文档写「Event subscriptions keep the connection open after the initial response」，实测确认——同一条订阅连接上我收到了 4 个事件帧（见第五节）。所以规则是：

请求类型连接行为
普通方法（102 个里的 100 个）一请求一连接，响应后 server 关闭
events.subscribe一帧 ack，然后持续推事件，连接保持

这也解释了为什么 CLI 每条命令都是独立进程：它没有别的选择。

三、id 与错误：五种失败形态，全部实测#

请求信封只有 id 是必填（{"required":["id"],"type":"object"}），method 和 params 在 schema 顶层没标必填——但缺了会以 invalid_request 报错。

本机实测五种畸形输入的响应：

输入响应
{"id":"a",broken{"id":"","error":{"code":"invalid_request","message":"invalid request: key must be a string at line 1 column 11"}}
{"id":123,...}{"id":"","error":{... "invalid type: integer \123`, expected a string at line 1 column 9"}}`
缺 id{"id":"","error":{... "missing field \id` at line 1 column 29"}}`
未知 method{"id":"r2","error":{"code":"invalid_request","message":"invalid request: unknown variant \no.such.method`, expected one of `ping`, `server.stop`, …"}}`
非法 UTF-8连接直接关闭，没有任何响应
空行 \n连接直接关闭，没有任何响应

三条实用结论：

  1. id 必须是字符串。给个整数你会收到 id:""，然后你的响应关联逻辑全崩。这是常驻客户端最容易写的 bug：你以为在等 id:123 的响应，实际收到 id:""，然后超时。
  2. 未知 method 的错误信息里列出了全部 102 个合法方法名。这是最快的接口清单来源——不用跑 schema，发一个假方法就能把名字全打出来。
  3. 非法 UTF-8 静默断连。文档写了「Transport errors, such as invalid UTF-8, can close the connection without a response」，实测确认。所以发送前自己校验编码，尤其是你把用户输入或屏幕抓取内容塞进 pane.send_text 的时候——Herdr 不会替你报错。

错误信封的形状#

{"id":"req_1","error":{"code":"not_found","message":"pane not found"}}

code 是稳定判别式，message 给人看。脚本里判 code，别判 message——message 里带行列号这种随实现变化的内容（上面几条错误里的 at line 1 column 115 就是 serde 的实现细节）。

未知参数被静默接受#

call("ping", {"nope": 1})   # → 正常返回 pong

多写的参数不会报错。这既是好事（向前兼容：新版本加了字段你旧客户端忽略即可，文档也明确要求「JSON API clients should ignore unknown fields」），也是坏事（你把 pane_id 拼成 paneid，不会有任何警告——它会被当成未知字段忽略，然后你收到「missing field」或者更糟：一个默认值下的成功响应）。

写客户端时建议自己加一层参数白名单校验，用 schema 里的 required 列表。

四、用 schema 建客户端，但别只信 schema#

herdr api schema                    # 摘要
herdr api schema --json             # 完整文档（本机 272578 字节）
herdr api schema --output herdr-api.schema.json   # 写文件

摘要长这样：

Herdr API schema
protocol: 22
schema_version: 1
schemas: error_response, event, request, subscription_event, success_response

五个子文档的规模（本机实测，字符数）：

schema大小内容
request55944102 个方法，oneOf + 每方法 const method 名
success_response49761各方法的 result 形状
event13480推送事件负载
subscription_event2827订阅帧信封
error_response389错误信封

request.oneOf 的每一项形如：

{"properties": {"method": {"const": "ping"}, "params": {"$ref": "#/schemas/request/$defs/PingParams"}},
 "required": ["method", "params"]}

顺着 $ref 到 $defs 就能拿到每个方法的必填/可选参数。本机实测几个常用的：

agent.wait            required=[target]                     optional=[timeout_ms, until]
pane.report_agent     required=[agent, pane_id, source, state]  optional=[agent_session_id, agent_session_path, message, resume_argv, seq]
pane.wait_for_output  required=[match, pane_id, source]     optional=[lines, strip_ansi, timeout_ms]
plugin.action.invoke  required=[action_id]                  optional=[context, plugin_id]
events.subscribe      required=[subscriptions]              optional=[]
events.wait           required=[match_event]                optional=[timeout_ms]

注意 pane.wait_for_output 的 source 是必填，而 CLI 里它有默认值 recent。这类差异在 CLI 上看不见，只有走 socket 才会撞上。

但 schema 和运行时之间有四道落差#

我把实测到的不一致列出来（这一节是全篇最容易省掉、也最容易害人的部分）：

#schema 说运行时实际
1EventMatch 列了 19 种事件可等待除 pane_agent_status_changed 外全部返回 unsupported_event_wait_match（见第五节实测）
2Subscription 用点号名 workspace.createdEventMatch 用下划线名 workspace_created——同一批事件两套命名
3Subscription 有 27 项里面没有 pane.renamed（pane 侧是 pane.updated），写错一个名字整个订阅原子失败
4pane_agent_status_changed 的 agent_status 是 required真的必填——不给它连 schema 校验都过不了，而 CLI 的 agent wait 把这块包得很顺

第 1 和第 2 条组合起来的实际后果：你以为能用 events.wait 等一个 pane 创建事件，结果拿到的是「不支持」而不是「超时」。而如果你按 subscribe 的点号名去写 wait，连 variant 解析都过不了。

五、事件系统：订阅流与单次等待是两套东西#

订阅：27 个点号名，三个要带参数#

Subscription 的 27 个变体（本机实测从 schema 提取）：

plain（只需 type）24 个：
  workspace.created / updated / metadata_updated / renamed / moved / reordered / closed / focused
  worktree.created / opened / removed
  tab.created / closed / focused / renamed / moved
  pane.created / closed / updated / focused / moved / exited / agent_detected
  layout.updated

带参数 3 个：
  pane.agent_status_changed   需要 pane_id
  pane.scroll_changed         需要 pane_id
  pane.output_matched         需要 pane_id + source + match

本机实测订阅并收流：

subs = [{"type": "workspace.created"},
        {"type": "tab.created"},
        {"type": "pane.agent_status_changed", "pane_id": "w1:p1"}]
s.sendall((json.dumps({"id":"sub3","method":"events.subscribe","params":{"subscriptions":subs}})+"\n").encode())
# ack: {"id":"sub3","result":{"type":"subscription_started"}}

然后从 CLI 触发活动（建 workspace、建 tab、上报一次 agent 状态变化），同一条连接上收到 4 帧：

{"data":{"type":"workspace_created","workspace":{"active_tab_id":"w4:t1","label":"tmp","number":4,"pane_count":1,"workspace_id":"w4"}},"event":"workspace_created"}
{"data":{"tab":{"label":"1","number":1,"tab_id":"w4:t1","workspace_id":"w4"},"type":"tab_created"},"event":"tab_created"}
{"data":{"tab":{"label":"4","number":4,"tab_id":"w1:t4","workspace_id":"w1"},"type":"tab_created"},"event":"tab_created"}
{"data":{"agent":"claude","agent_status":"blocked","pane_id":"w1:p1","workspace_id":"w1"},"event":"pane.agent_status_changed"}

三个观察：

  1. ack 之后连接不关，事件持续推——这是唯一的多帧场景。
  2. 事件帧里 event 和 data.type 是同一个下划线名。所以你写分发逻辑时，订阅请求用点号，事件负载用下划线，两套名字要在同一份代码里映射。
  3. 第二条和第三条都是 tab_created：herdr tab create 建在了当前聚焦的 workspace（w1:t4），而新建 workspace 自带一个 tab（w4:t1）。事件流里会看到不是你直接发起的那一帧——做状态同步时别把它当异常。

订阅是原子失败的#

本机实测：把第三个订阅写成 {"type":"pane.renamed"}（不存在）：

{"id":"sub1","error":{"code":"invalid_request","message":"invalid request: unknown variant `pane.renamed`, expected one of `workspace.created`, `workspace.updated`, ..."}}

然后触发活动，收到 0 个事件——前两个合法订阅一个都没生效。

所以：整个 subscriptions 数组要么全合法，要么一个都不生效。 加新事件名时先单独订阅它验证一次，别直接塞进已有的多订阅列表里——否则你会以为「事件没来」，实际是「订阅从没成功」。

单次等待：只支持一种事件#

events.wait 的 match_event 用 EventMatch（下划线名）。先按点号名试：

{"id":"e2","error":{"code":"invalid_request","message":"invalid request: unknown variant `workspace.created`, expected one of `workspace_created`, `workspace_updated`, ..."}}

换成下划线名：

{"id":"e3","error":{"code":"unsupported_event_wait_match","message":"events.wait currently supports pane agent status matches"}}

注意这不是超时，是「不支持」。schema 里列的 19 种事件，运行时只认 agent 状态。

再试 pane_agent_status_changed（必填 event + pane_id + agent_status）：

{"id":"e5","method":"events.wait","params":{
  "match_event":{"event":"pane_agent_status_changed","pane_id":"w1:p1","agent_status":"blocked"},
  "timeout_ms":12000}}

本机实测时序：先报 working，起 waiter，2 秒后 waiter 仍阻塞（正确），然后报 blocked：

+2.0s waiter still blocked? yes (no result yet)
  resolved at +2.1s -> {"id":"e5","result":{"type":"wait_matched","event":{"event":"pane_agent_status_changed","data":{"type":"pane_agent_status_changed","pane_id":"w1:p1","workspace_id":"w1","agent_status":"blocked","agent":"claude"}}}}

推模式在 0.9.2 只对 agent 状态可用。别的场景（等 pane 创建、等输出变化）只能：订阅流里自己过滤，或者轮询 pane.wait_for_output / session.snapshot。

六、session.snapshot：一次调用拿到整个运行时#

CLI 的 herdr api snapshot 就是包了这个方法。本机实测返回结构（顶层 keys）：

snapshot:
  version, protocol
  focused_workspace_id, focused_tab_id, focused_pane_id
  workspaces[]  → workspace_id, label, number, active_tab_id, pane_count, tab_count, agent_status, focused
  tabs[]        → tab_id, workspace_id, label, number, pane_count, agent_status, focused
  panes[]       → pane_id, workspace_id, tab_id, terminal_id, cwd, foreground_cwd,
                  agent_status, focused, revision, scroll{offset_from_bottom, max_offset_from_bottom, viewport_rows}
  layouts[]     → workspace_id, tab_id, area{x,y,width,height}, focused_pane_id,
                  panes[]{pane_id, rect}, splits[], zoomed

这是做只读可视化的唯一必要调用：一次拿全拓扑 + 每个 pane 的滚动位置 + 布局矩形。layouts[].splits 给的是分割树，rect 给的是绝对坐标，所以你不需要理解 Herdr 的内部布局就能重画。

两个字段值得单独说：

  • revision：pane 内容版本号。轮询时比对它能省掉重复抓取。
  • scroll.offset_from_bottom == 0 表示在底部。判断一个 agent pane 是不是在滚历史，用它比读屏幕便宜。

七、server.agent_manifests：检测清单的版本真相#

这个诊断方法在 CLI 里对应 herdr server agent-manifests，走 socket 能拿到结构化数据。本机实测：

type: agent_manifest_status | last_check_unix: 1790763094 | last_result: checked
manifests: 22
source_kind histogram: {'remote': 21, 'bundled': 1}
   {"agent":"pi",     "source":"remote:/Users/rex/.local/state/herdr/agent-detection/remote/pi.toml",     "source_kind":"remote", "active_version":"2026.09.14.1", "cached_remote_version":"2026.09.14.1", ...}
   {"agent":"claude", "source":"remote:/Users/rex/.local/state/herdr/agent-detection/remote/claude.toml", "source_kind":"remote", "active_version":"2026.09.11.1", ...}
   {"agent":"codex",  "source":"remote:/Users/rex/.local/state/herdr/agent-detection/remote/codex.toml",  "source_kind":"remote", "active_version":"2026.09.23.1", ...}

三个信息量很大的点：

  1. 22 个 agent 有清单，但只有 21 个来自 remote，1 个是 bundled。也就是说清单更新确实按 agent 粒度独立生效——某个 agent 的远端清单拉取失败时，它回落到二进制内置版本，其他 agent 不受影响。
  2. 每个清单版本是日期式版本号（2026.09.23.1），不同 agent 的版本日期各不相同（pi 是 09-14、claude 是 09-11、codex 是 09-23）。「Herdr 版本旧」不等于「检测规则旧」——远端清单不需要重启就生效。
  3. 远端清单缓存在 state 目录（~/.local/state/herdr/agent-detection/remote/），不是 config 目录。排查「检测行为变了但 Herdr 没升级」时，看这里。

诊断链条（模块 3 第 1 篇讲过检测，这里给 socket 版本）：

server.agent_manifests → 清单是哪来的、什么版本
agent.explain          → 这一屏为什么判成这个状态（需要 pane 里有被检测到的 agent）
pane.read --source detection → 检测器实际看到的那份缓冲区

八、避坑指南#

  1. 不要复用连接发第二个请求。实测 BrokenPipeError。除订阅外，一连接一请求。
  2. id 必须是字符串。给整数会得到 id:"" 的错误，你的响应关联逻辑会静默崩掉。
  3. 发送前自己校验 UTF-8。非法字节直接断连、零响应，Herdr 不会告诉你原因。
  4. 订阅名用点号，事件负载和 events.wait 用下划线。两套名字，别混。
  5. events.wait 在 0.9.2 只支持 pane_agent_status_changed。别的会立刻返回 unsupported_event_wait_match，不是超时。
  6. 订阅数组原子失败。一个非法名字让整批订阅全部不生效，症状是「事件一个都不来」。
  7. pane.agent_status_changed 订阅必须带 pane_id，pane.output_matched 必须带 pane_id + source + match。缺字段是 invalid_request，整批同样不生效。
  8. 未知参数被静默忽略。paneid 拼错不会报错，只会让服务端看到「少了 pane_id」或者拿到默认值。客户端侧自己按 schema 的 required 校验。
  9. pane.wait_for_output 的 source 在 socket 层是必填，CLI 有默认值 recent。从 CLI 迁到 socket 时这是隐形 breaking change。
  10. 升级 Herdr 后要重启或 live-handoff server 才能用 agent.explain（文档明确，因为它依赖运行中 server 的清单缓存）。
  11. 别用 herdr server stop 清理测试会话（第 1 篇讲过，socket 层同理：server.stop 停的是你连上的那个 socket 对应的 server）。
  12. Windows 上不要自己拼管道名。文档建议插件优先用 HERDR_BIN_PATH 加 CLI 包装来获得可移植行为；裸 socket 客户端要自己负责平台原生本地 socket 形式。

常见问题

什么时候需要绕过 CLI 直接连 socket？

三种情况。第一，CLI 没有对应命令：102 个方法里像 pane.scroll、pane.clear、pane.link.activate、layout.apply、agent.view.set、command.invoke、popup.close 都只能走 socket。第二，你需要事件流：CLI 没有 subscribe，只有 events.wait 单次等和 pane wait-output 轮询。第三，你要写常驻的协议客户端而不是每次起一个进程。反过来，如果只是脚本里调一两次，用 CLI——它帮你处理了 socket 路径解析、Windows 命名管道和协议协商，这些自己写很容易错。

能不能在一条 socket 连接上连续发多个请求？

不能，除订阅之外。本机实测：一次 sendall 里塞两个请求，只收到第一个响应，然后 recv 返回空（server 关闭连接）；等第一个响应回来再发第二个，直接 BrokenPipeError。所以正确模型是一连接一请求，把每条连接当成一次函数调用。唯一的例外是 events.subscribe——它先回一帧 subscription_started，然后在这条连接上持续推事件，实测在同一条连接上收到了 4 个事件帧。

为什么我的事件订阅一个事件都没收到？

最可能的原因是订阅数组里有非法名字，因为订阅是原子失败的：整个 subscriptions 数组要么全部合法生效，要么一个都不生效，而且你只会看到一条 invalid_request。本机实测把 pane.renamed（不存在，pane 侧是 pane.updated）塞进三个订阅里，结果三个订阅全部不生效、收到 0 个事件。加新事件名时先单独订阅它验证一次。另一个常见原因是必填参数缺失：pane.agent_status_changed 和 pane.scroll_changed 必须带 pane_id，pane.output_matched 必须带 pane_id、source、match。

订阅和等待的事件名为什么不一样？

因为它们是两套结构。events.subscribe 的 Subscription 用点号名（workspace.created、pane.agent_status_changed），而 events.wait 的 match_event 和推送帧里的 event 字段用下划线名（workspace_created、pane_agent_status_changed）。本机实测按点号名去调 events.wait 会直接收到 unknown variant 错误，错误信息里会把 19 个合法的下划线名全列出来。写客户端时你需要一张两套名字的映射表。

能用 events.wait 等一个 pane 被创建吗？

0.9.2 不能。schema 的 EventMatch 列了 19 种事件，但运行时只支持 agent 状态：实测用 workspace_created 会得到 unsupported_event_wait_match，message 是 events.wait currently supports pane agent status matches——注意这是立刻返回的错误，不是超时，所以你的重试逻辑不会等你期望的那个事件。等 pane 创建只能靠订阅流里自己过滤，或者轮询 session.snapshot。

JSON Schema 能直接当契约用吗？

能用它生成校验，但不能只信它。本机实测有四处 schema 与运行时不一致：events.wait 支持的事件范围、订阅与等待两套事件命名、Subscription 里其实没有 pane.renamed、以及 pane.wait_for_output 的 source 在 socket 层是必填而 CLI 给了默认值。另外未知参数会被静默忽略，所以把 pane_id 拼成 paneid 不会报错，只会得到 missing field 或者一个用了默认值的成功响应。建议用 schema 的 required 列表在客户端侧自己校验，并且对每个真要用的方法发一次真实请求确认。
