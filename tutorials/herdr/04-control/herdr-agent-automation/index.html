Herdr agent 自动化实战：三层原语、last-writer-wins 的状态权限，以及我被自己的测量骗过一次的过程

把 CLI 和 socket 拼成能跑的 agent 编排：layout/pane/agent 三层原语各自负责什么、为什么创建命令必须从 JSON 返回里抄 id 而不是猜、agent target 的实测四行矩阵（live 别名和 pane id 可用，kind 标签和 terminal id 不可用）、pane report-agent 的三条真实语义（多 source 后写覆盖、release-agent 不回滚到前一个 source、seq 落后被静默丢弃且 rc=0）、我在隔离会话里把「未知标签会被 0.4 秒清除」当成结论又被单 source 复测推翻的全过程、agent wait 与 prompt 的状态语义（默认匹配集、idle 与 done 的 seen 差别、blocked 直接拒绝 prompt、agent_prompt_stalled 的五秒窗口、无默认 timeout）、alternate-screen 历史读取的边界，以及三个可直接跑的编排配方。基线 herdr 0.9.2。

September 30, 2026 · 7 min · 1408 words · 梦兽编程 -  |  English

一个真实需求：你在 pane A 里跑着一个 coding agent，你想让它自己开一个 pane、在里面起第二个 agent、把活派下去、等它跑完、把结果读回来。

整条链路不需要 TUI、不需要第二个终端、不需要人。但把它跑通要跨三层抽象、两种寻址方式，还要正确处理一套失败时不报错的状态上报协议。

这一篇给你三层原语的分工、一份实测的寻址矩阵、三条状态上报的真实语义——以及一个我在这台机器上把结论测错、然后被自己的复测推翻的完整过程。那部分比任何结论都值钱，因为它就是你会遇到的坑的形状。

基线：herdr 0.9.2 stable · macOS · 全部实验在隔离命名会话 batch8-lab 里做（第 1 篇讲了怎么起），我实际用的会话 w3 全程没被碰。

结论前置#

Herdr 的 agent 自动化有三个不可省的动作：从创建命令的 JSON 里抄 id、用 pane id 寻址、上报之后读回确认。 因为状态是后写覆盖的、seq 落后是静默丢弃的、release 是不回滚的。 这三条合起来的含义是：你的脚本永远不能假设「我刚才报了 working，所以它现在是 working」。

一、三层原语：位置、终端、agent#

文档给的分工表很干净：

原语职责
Layout（workspace / tab / pane 拓扑）创建和组织终端位置
Pane控制一个原始终端：跑命令、发输入、读输出、等输出
Agent按名字和生命周期状态控制一个被识别的编码 agent

关键的一句话是：pane 是否存在与它里面有没有 agent 无关；agent 是「当前运行在某个 pane 里的那个被识别的进程」。所以 agent start 只激活一个已存在的 shell pane，它从不创建、分裂或移动布局。

另一个容易搞错的层级关系：创建 workspace 会连带创建它的第一个 tab 和根 pane；创建 tab 会连带创建根 pane。 所以正常流程是「创建 → 拿返回的根 pane id → 需要更多终端时才 split」。

实测：创建命令返回什么#

herdr --session batch8-lab workspace create --cwd /tmp --label api --no-focus

{"id":"cli:workspace:create","result":{"type":"workspace_created",
  "workspace":{"workspace_id":"w8","label":"api","number":8,"active_tab_id":"w8:t1","pane_count":1,"tab_count":1,"focused":false,"agent_status":"unknown"},
  "tab":{"tab_id":"w8:t1","workspace_id":"w8","label":"1","number":1,"pane_count":1,"focused":false,"agent_status":"unknown"},
  "root_pane":{"pane_id":"w8:p1","workspace_id":"w8","tab_id":"w8:t1","cwd":"/private/tmp","foreground_cwd":"/private/tmp","agent_status":"unknown","focused":false,"revision":0,"scroll":{...}}}}

三个字段都在：.result.workspace、.result.tab、.result.root_pane——和文档一致。

注意 --cwd /tmp 在返回里变成了 /private/tmp（macOS 的 /tmp 是符号链接，Herdr 报的是解析后的真实路径）。别拿返回的 cwd 去和你传入的字符串做相等比较。

再来一次 split：

herdr --session batch8-lab pane split w8:p1 --direction right --no-focus
# → .result.pane.pane_id = "w8:p2"

pane split 只返回 .result.pane（没有 move_result 那种包装）。

正确写法是从 JSON 里取，永远不要猜 id：

created=$(herdr workspace create --cwd ~/project --label api --no-focus)
pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

w8:p1 这种 id 看起来有规律（workspace 号 + pane 号），于是很容易写出 echo "w9:p1" 这种偷懒代码。它会偶尔正确、偶尔打到别人的 pane 上——这是自动化里最坏的一类 bug：不总错，所以测不出来。

二、寻址：一个实测四行矩阵#

文档规则：agent target 是唯一的 live agent 名字，或者当前承载该 agent 的 pane id。terminal id 和裸的 agent kind 标签都不是 target。

我在隔离会话里把四种形式各跑一遍（本机实测）：

target 写法它是什么rc结果
revieweragent rename 创建的 live 别名0✅ 返回 agent 对象
w1:p1pane id0✅ 返回 agent 对象
claudeagent kind 标签（出现在 agent 字段里）1❌ agent_not_found
term_65cb064b0fd241terminal id1❌ agent_not_found

第三行是最容易误解的：agent get 的返回里明明有 "agent":"claude"，但拿 claude 去查却查不到。因为 agent 字段是kind 标签，name 字段才是别名：

{"agent":{"agent":"claude","name":"reviewer","agent_status":"blocked","pane_id":"w1:p1","state_change_seq":54,...},"type":"agent_info"}

两个字段，只有 name 可寻址。

别名怎么来的，以及它的寿命#

agent rename 能给一个已被识别的 agent 起别名（实测 rc=0 并返回带 name 的对象）。但别名跟着 agent 身份活：

herdr --session batch8-lab agent rename w1:p1 myhelper   # rc=0，返回 name: myhelper
sleep 1.5
herdr --session batch8-lab agent get myhelper
# rc=1  agent_not_found

那次 rename 用的是一个未知标签的自报状态（--agent lab-bot），底层身份没被保住，别名就跟着没了。所以 agent rename 不是「让任意名字变可寻址」的手段，它只是给已经存在的 agent 身份贴个标签。

文档对别名寿命的定义：agent 退出、被 release、或被替换时别名清除；它不会永久重命名那个 pane。

实操建议#

编排脚本里一律用 pane id 当 target。 名字是给人看的便利，w1:p1 才是稳定地址。要给人看的界面，再额外维护一张 name → pane_id 的表。

三、状态上报的三条真实语义（以及我测错的那次）#

这是本篇的核心。pane report-agent 的返回只有成功和失败，而「成功」的含义比你想的少得多。

语义一：多 source 后写覆盖#

同一个 pane 上，两个 source 各报各的：

start:                              ('brand-x', 'working')
srcA 报 agent-a working  →  pane:   ('agent-a', 'working')
srcB 报 agent-b blocked  →  pane:   ('agent-b', 'blocked')   ← 第二个 source 接管了

pane 显示的是「最后被接受的那次报告」，不是「你认为有权报的那个集成」。 谁先报、报的标签 Herdr 认不认识，都不影响这条。

语义二：release 不回滚#

srcB release-agent  →  pane:  ('agent-b', 'blocked')   ← 仍然停在 srcB 的状态
srcA 再报 idle      →  pane:  ('agent-a', 'idle')

pane release-agent 结束的是那个 source 自己的生命周期权限，它不会把 pane 恢复到前一个 source 的状态。也就是说 release 之后 pane 上挂的还是被释放那个 source 报的最后状态。

语义三：seq 落后被静默丢弃，而且返回成功#

srcA 报 working               → pane: ('agent-a', 'working')
srcA 用 --seq 1000 报 blocked → rc=0, stdout 空
                              → pane 仍是 ('agent-a', 'working')   ← 什么都没发生

这条最危险：命令成功、零输出、状态没变。文档说的「Herdr 会忽略序号不高于它上次接受值的报告」是对的，但它没说失败信号是零。

所以：

  • 用毫秒时间戳当 seq（python3 -c 'import time;print(int(time.time()*1000))' 或 date +%s%3N），它天然跨会话跨重启单调递增
  • 关键上报之后 pane get 读回一次，别信 rc=0

我是怎么把这条测错的#

值得完整记下来，因为这就是「实测」这个词最容易被滥用的地方。

第一轮我在隔离会话里做了这么一批实验：反复用四个不同的 source（labtest、labprobe、rawprobe、custom:docs）对同一个 pane 上报，标签在 lab-bot（未知）和 claude/pi/grok（Herdr 认识的 kind）之间交替，每次 seq 从一个共享计数器 +1。

观察到的现象非常干净：

label=lab-bot  → +0.1s 有，+0.5s 有，+1.2s 没了
label=claude   → +0.1s 有 … +11.6s 还有
label=grok     → +11.6s 还有（而 grok 根本没装）
label=kitt-e   → 立刻没了

我据此下了结论：「Herdr 只保住它认识的 agent 标签，未知标签会在下一个检测 tick（约 0.4 秒）被清除」。这个结论还和文档里「添加全新 agent 需要 Herdr 二进制更新」那句话互相印证，看起来无懈可击。

然后我做了第二轮——单一 source、干净状态（先把所有碰过这个 pane 的 source 全部 release-agent）：

=== SINGLE source, shell foreground, UNKNOWN label:
   + 0.1s -> ('brand-x', 'working')
   + 0.5s -> ('brand-x', 'working')
   + 1.0s -> ('brand-x', 'working')
   + 2.0s -> ('brand-x', 'working')
   + 3.0s -> ('brand-x', 'working')
   + 5.0s -> ('brand-x', 'working')     ← 未知标签稳稳保持 5 秒以上

未知标签 brand-x 活得很好。我第一轮错了。

错在哪：第一轮里每个 source 的「上次接受的 seq」是各自记账的。当我在几个 source 之间交替上报、并且共享一个递增计数器时，某个 source 的新报告会被它自己更早的高位 seq 挡住，或者被另一个 source 后写的那一条盖掉。我看到的「0.4 秒后消失」其实是另一个 source 的状态重新成为 pane 的显示值——不是「未知标签被清除」。

更讽刺的是那个「grok 没装也能保持」的观察：它保持的原因根本不是标签，而是那轮里 grok 那条恰好是最后被接受的。

三条教训，我原样写进避坑清单：

  1. 多变量实验里，「A 有效 B 无效」的对照必须先排除共享状态。我的 seq 计数器和 source 列表都是共享的。
  2. 和文档互相印证的结论，仍然是待证结论。那句「需要二进制更新」是真的，但它解释的不是我测到的现象。
  3. 推翻自己的成本很低：清干净状态、只用一个 source、重跑一次。我花了大概 30 秒，省掉了一篇错文章。

那文档的示例到底对不对#

顺带把那个疑点收干净：socket-api.mdx 里 pane.report_agent 的例子用的是 "agent": "docs-bot"（一个 Herdr 不认识的标签）。实测这个标签能被接受并保持（单 source 下 brand-x 同理）。所以那个示例没问题，是我第一轮读错了。

一个仍然成立的相关事实#

未知标签虽然能保持状态，但不等于可寻址：agent get <自报标签> 依然 agent_not_found（第二节的矩阵）。保持和可寻址是两件事。

四、等待与提示：状态语义的准确边界#

agent wait#

herdr agent wait <target> [--until STATUS]... [--timeout MS]
  • 不带 --until 时匹配 idle、done、blocked 三种；unknown 必须显式写
  • 当前状态已匹配就立即返回，所以「先查再等」是多余的
  • 不带 --timeout 会无限等——在 CI 里这就是挂住
  • 超时是 timeout 错误，JSON 在 stderr，退出码 1
  • --until 可以重复给多个状态

idle 和 done 都意味着「可以输入了」，区别在谁看过它：done 是 idle 但还没被标记为 seen；显式的 pane focus / agent focus 会把目标标为 seen，读操作不会。每个 TUI client 各自记录自己看过哪些完成，所以屏幕上的 Done 角标和 CLI 查到的状态可以不一致（模块 3 第 1 篇讲过，这里是同一个机制的 CLI 侧表现）。

如果你的编排逻辑依赖「这个任务真的完成了一次」，用精确的 --until 状态，不要依赖 done/idle 的区分。文档还提到 agent 响应可能带 completion_seq，它标识当前这次 idle 转换是完成的工作、与谁看过无关，并且和该转换的 state_change_seq 对应；启动和会话切换不会设置它。旧 server 可能省略这个字段。

agent prompt#

herdr agent prompt <target> <text> [--wait] [--until STATUS]... [--timeout MS]

四条实测/文档一致的语义：

  1. 文本 + 延迟 Enter 作为一次有序提交，尊重终端当前的 bracketed-paste 模式；agent 正在 working 时也能提交
  2. 不带 --wait 的成功只代表写入被确认，不代表一轮开始
  3. agent 已经 blocked 时直接返回 agent_blocked，不写入任何输入——这是保护，别绕
  4. 带 --wait 且从非 working 状态发出时，提交后有 5 秒窗口必须观察到 working 或 blocked，否则返回 agent_prompt_stalled；如果调用方的 timeout 先到则返回普通 timeout

第 4 条的设计意图很明确：防止一个无关的 idle/done/会话变化把等待判成成功。

还有一句必须记住的：--until 在没有 --wait 时会被拒绝（文档：--until narrows the matching states and is rejected unless --wait is also present）。

agent start#

herdr agent start reviewer --kind codex --pane "$review_pane" -- -m gpt-5.4
  • 目标 pane 必须是可用的 shell pane：shell 自己持有前台，没有前台命令、编辑器或 agent 在跑
  • 成功返回意味着 Herdr 已在同一个 terminal 里检测到期望的 agent 并认为它可以接受交互输入，不是「进程起来了」
  • 启动期间检测报 blocked → 立即返回 agent_not_ready
  • 默认启动超时 30000 ms；--timeout 必须 > 3000 且 ≤ 300000
  • 名字必须匹配 [a-z][a-z0-9_-]{0,31} 且在 live agent 中唯一
  • 24 个 kind：pi、claude、codex、gemini、cursor、devin、agy、cline、omp、mastracode、opencode、copilot、kimi、kiro、droid、amp、grok、hermes、kilo、qodercli、qwen、letta、maki、muse

注意 agent start 不创建布局——先 split 拿到 pane，再 start。

一个我实测确认的用法细节：pane run 的参数形式#

herdr --session batch8-lab pane run w8:p2 "echo QUOTED_FORM_OK"   # ✅ 整串当一个参数也行
herdr --session batch8-lab pane run w8:p2 echo QUOTED_FORM_OK     # ✅ 多参数形式也行
herdr --session batch8-lab pane run w8:p2 -- echo X               # ❌ -- 被送进 shell

文档配方用的是带引号的单参数形式（herdr pane run w1:p3 "just test --watch"），实测可用——而且这是命令里含 -- 时的正确写法：引号里的 --watch 是命令自己的参数，不会被 Herdr 的解析器碰。

五、三个能直接跑的配方#

配方 1：起一个 helper，派活，等它落定#

#!/usr/bin/env bash
set -euo pipefail

# ① 在当前 pane 右边开一个 pane，从 JSON 里拿 id
split=$(herdr pane split --current --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

# ② 在那个 pane 里起 agent（pane 必须是可用 shell）
herdr agent start reviewer --kind codex --pane "$review_pane" -- -m gpt-5.4

# ③ 派活并等落定
herdr agent prompt reviewer "Review the current diff" --wait --timeout 120000

# ④ 收结果
herdr agent read reviewer --source recent-unwrapped --lines 120

每一处 jq 取 id 都是必需的，见第一节。

配方 2：等 agent 来问，看完再决定#

herdr agent wait reviewer --until blocked --timeout 120000
herdr agent read reviewer --source recent-unwrapped --lines 80
herdr agent send-keys reviewer esc

agent send-keys 发的是逻辑键名：enter、up、esc（escape 是别名）、ctrl+c。Herdr 会先校验所有键再写任何字节，所以不会发一半。

为什么这里必须用 send-keys 而不是 prompt：agent 处于 blocked 时 prompt 会直接拒绝。这是有意的——审批对话框需要的是一个明确的键，不是一段文本。

配方 3：普通进程不要当 agent 等#

herdr pane run w1:p3 "just test --watch"
herdr pane run w1:p3 "npm run build"
herdr pane wait-output w1:p3 --regex "passed|failed" --timeout 120000

文档明确：用 pane wait-output 等普通命令和服务，用 agent wait 等编码 agent。 pane wait-output 完全不解释 agent 生命周期。

一个实测细节：pane wait-output 立即检查一次当前快照，所以已经存在的输出也能匹配上。这意味着如果你不清屏就等一个 marker，可能匹配到上一轮的残留。我实测等 MARKER_7788 时，返回的 matched_line 是 rex@… /tmp % echo MARKER_7788——匹配到的是回显的命令行，不是输出行。marker 要选不出现在命令串里的值。

六、读长输出的边界：alternate screen#

Claude Code、OpenCode 这类全屏 agent 把 transcript 画在终端的 alternate screen 里，不是 Herdr 的宿主 scrollback。所以「读超过一屏的历史」需要特殊处理。

文档描述的机制（我没有全屏 agent 在跑，未在本机验证这条完整路径）：

  • 对一个 idle、已识别 的 agent，在 transcript 底部时，recent / recent-unwrapped 读取在 --lines 超过可见屏幕时会自动使用 agent 自己的鼠标滚轮接口翻页收集，读完后把视口送回底部
  • pane read 在 pane 里装着该 agent 时同样适用，不需要额外选项
  • 其他读取保持被动：visible、detection、ANSI 读取、输出等待和订阅、被人工滚动过的 agent、直接 attach、不上报鼠标滚轮的应用——Herdr 都不会移动应用视口
  • 显式 agent read --lines N 需要 alternate-screen 历史而 agent 正在 working / blocked / unknown 时，返回 agent_not_idle；等 idle 再试，或者改用 --source visible

如果完整响应还是拿不到，文档给的做法很实用：让 agent 把回答写成临时目录里的 Markdown 文件，只回一个路径，然后你直接读文件。这条在编排里比反复翻屏幕可靠得多。

顺带说，--lines 的默认值是 80 行（recent 类源），visible 和 detection 不给 --lines 时返回完整快照。

七、避坑指南#

  1. 不要猜 pane id。所有创建命令都打印 JSON，从 .result.root_pane.pane_id / .result.pane.pane_id 取。
  2. 一个 pane 只放一个生命周期权限持有者。多 source 是后写覆盖，你会看到不是你报的状态。
  3. release-agent 不回滚。释放之后 pane 仍挂着被释放那个 source 的最后状态。
  4. seq 落后被静默丢弃，rc=0、零输出。用毫秒时间戳当 seq，关键上报后 pane get 读回。
  5. agent wait 没有默认 timeout。CI 里必须给 --timeout，否则永久挂住。
  6. 区分退出码 1 和 2：1 是运行期（目标没了、超时），2 是用法错误（别重试）。
  7. --until 在 agent prompt 上必须配 --wait，否则被拒绝。
  8. agent prompt 对 blocked 直接返回 agent_blocked 且不写入。要回应审批用 agent send-keys。
  9. agent start 不创建布局，pane 必须是可用 shell 提示符；--timeout 必须落在 3000–300000。
  10. pane run 别加 --（第 1 篇实测）；命令里含 -- 时用引号包住整串。
  11. wait-output 的 marker 可能匹配到回显的命令行，不是命令输出。
  12. pane move 之后必须改用 .result.move_result.pane.pane_id（实测 w8:p2 → w1:p5），旧值在 previous_pane_id。已经进行中的 wait 会以 agent_not_running 结束。
  13. pane move 的 --workspace 不能单独用（实测 rc=2 用法错误），要配 --new-tab 或 --new-workspace，或者直接给 --tab。
  14. 别在多个变量共享状态的情况下做对照实验（第三节那次）。清状态、单 source、重跑，是 30 秒的事。

sequenceDiagram

        H-->>O: rc=0，返回 .result.agent

    H-->>O: agent=reviewer status=idle state_change_seq=N

    H-->>O: 文本（idle 时可翻 alternate screen 历史）

常见问题

能用 Herdr 让一个 agent 指挥另一个 agent 吗？

能，这就是 Herdr 相对 tmux 多出来的一层。你在一个 pane 里的 agent 可以调用 Herdr 的 CLI 或 socket：先 pane split 出一个新 pane 并拿到返回的 pane id，然后 agent start 一个受支持的 agent 并把那个 pane 交给它，再 agent prompt 派活并带 --wait 和 --timeout，最后 agent read 收集结果。整条链路不需要任何 TUI 交互，也不需要第二个终端。文档把这一层叫三个原语：layout 负责位置，pane 负责原始终端，agent 负责被识别的编码 agent 及其生命周期状态。

为什么我上报的 agent 状态过一会儿变了，但我没有再上报？

因为同一个 pane 上的多个 source 是后写覆盖。本机实测：srcA 报 agent-a working 之后 pane 显示 agent-a，srcB 再报 agent-b blocked 之后 pane 就显示 agent-b——谁最后被接受谁就是 pane 现在的样子。更要注意 release-agent 不会回滚：srcB release 之后 pane 仍然停在 agent-b/blocked，不会退回 srcA 的状态。所以一个 pane 只应该有一个生命周期权限持有者，并且任何依赖状态的脚本都要先读回来看 Herdr 当前相信什么。

我的 seq 用了自增计数器，为什么上报没生效也没报错？

因为落后的 seq 会被静默丢弃，而且返回成功。本机实测：先报 working，再用 seq=1000 报 blocked，命令 rc=0、stdout 空，但 pane 状态仍然是 working。Herdr 忽略序号不高于它上次接受值的报告，这样迟到或乱序的报告就无法覆盖更新的状态——这是设计，但它的失败信号是零。所以推荐用毫秒时间戳当 seq，并且在关键上报之后用 pane get 读回一次确认。

agent wait 会等多久？超时了怎么知道？

不带 --timeout 时它无限等。超时是运行期错误：JSON 错误打在 stderr，退出码 1。用法错误退出码 2，这种错误不该重试。默认匹配集是 idle、done、blocked 三种；要等 unknown 必须显式 --until unknown。另外 agent wait 在当前状态已经匹配时立即返回，所以「先查再等」和「直接等」在效果上是安全的。

agent prompt 和 pane send-text 有什么区别？

三件事。第一，prompt 会把文本和延迟 Enter 编成一次有序提交，并且尊重终端当前的 bracketed-paste 模式；send-text 只发字面文本不回车。第二，prompt 走 agent 寻址：它会解析当前 live agent，如果那个 agent 已经不再控制这个 pane，操作被拒绝；send-text 走 pane 寻址，不管 pane 里现在是什么。第三，prompt 对 blocked 的 agent 直接返回 agent_blocked 而不写入任何输入——这是保护，避免你把提示语打进一个审批对话框里。要回应审批 UI，用 agent send-keys 明确地按键。

为什么 agent get 用 agent 的名字查不到？

要看那个名字是哪来的。只有两种 target 合法：唯一的 live agent 名字，或者当前承载 agent 的 pane id。用 agent start 起的 agent 有 live 名字，用 agent rename 命名的也有；但你在 pane report-agent 的 --agent 参数里写的标签只是显示名，不等于 live 名字。本机实测四行矩阵：agent rename 出来的别名 rc=0，pane id rc=0，kind 标签 claude rc=1 agent_not_found，terminal id rc=1 agent_not_found。自动化脚本一律用 pane id 最稳。
