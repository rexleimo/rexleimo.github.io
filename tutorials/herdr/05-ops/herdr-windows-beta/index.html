Herdr 在 Windows 上的现状：ConPTY 换来的差异、六个明确不支持的功能，以及光标与 IME 的两难

按文档逐项核对 Herdr 0.9.2 的 Windows 支持边界：安装路径与 stable/preview 渠道规则（已有 preview 安装会留在 preview，迁移需要两步）、Windows Terminal 的 PowerShell 与 cmd 两种粘贴方式、ConPTY 下的光标两难（默认 auto 实际是单元格绘制，换 IME 锚点就换闪烁）、live cwd 在 PowerShell 下不可靠而 OSC7 可用、Kitty 图形在 Windows Terminal 上根本走不通、agent 进程树检测沿 Git Bash 的 exec 边界、12 个受支持的 Windows 集成、插件在 Windows 只是 preview，以及六项明确不支持的能力（直接 attach、live handoff、Unix fd handoff、前台进程组、剪贴板图片桥、签名/SmartScreen）——并说明每一条对你的实际工作流意味着什么。基线 herdr 0.9.2。

September 30, 2026 · 5 min · 973 words · 梦兽编程 -  |  English

Herdr 原本是围绕 Unix PTY 模型构建的，Windows 版换成了 ConPTY 和 Windows 进程/运行时模型。核心工作流基本都能用，但有一些能力不同、有一部分是平台相关的。

这一篇按文档逐项核对支持边界，并给每一条标上「对你的实际工作流意味着什么」——因为「partial」这种词本身不构成决策依据。

基线：herdr 0.9.2 stable · Windows 支持状态来自官方文档 pinned v0.9.2 · 本机为 macOS，本篇为文档核对，未在 Windows 实机验证。

结论前置#

Windows 上「大部分能用」的准确含义是：会话、pane、键鼠、通知、远程都在， 但直接 attach、live handoff、Unix fd handoff、前台进程组、剪贴板图片桥、签名规避这六项明确不支持。 而 partial 的几项里，最影响日常的是 live cwd（PowerShell 下不可靠）和光标（视觉稳定与 IME 锚点二选一）。 插件在 Windows 只是 preview。

一、安装与渠道：Windows 上有个迁移的坑#

安装#

powershell -ExecutionPolicy Bypass -c "irm https://herdr.dev/install.ps1 | iex"

如果端点安全拦了这条无文件 PowerShell 命令，改用 cmd：

curl.exe -fsSLo install.cmd https://herdr.dev/install.cmd && install.cmd && del install.cmd

安装器把 release 存在 %USERPROFILE%\.herdr\packages\standalone\releases，把当前版本目录放上 PATH，保留 %LOCALAPPDATA%\Programs\Herdr\bin 作为稳定兼容别名，并保留少量旧版本，避免正在跑的进程挡住更新。

渠道迁移要两步#

Windows 构建同时在 stable 和 preview 两个渠道发布。新安装默认 stable，官方推荐 stable。 但有个已知路径：

  • 已有的 preview 安装会一直留在 preview，直到你显式执行 herdr channel set stable
  • 如果你的 preview 版本太旧、不接受这个命令：先在 preview 上跑一次 herdr update，然后重试 herdr channel set stable

这是文档里给出的完整流程，两步都不能省。

关于自定义清单#

内部测试可以用 HERDR_MANIFEST_URL 指向自定义清单，HERDR_CHANNEL=preview 配自定义 preview 清单。正常用户不要设。

会话在 client 断开后继续运行#

本地持久化会话在 client 断开或终端窗口关闭后继续运行。通过 Windows OpenSSH 启动的 server 和 pane 进程也能在注销后存活，重新跑 herdr 就能重连。

这条比 Unix 版更强——你不需要担心关掉终端窗口会带走工作。

agent 检测的具体机制#

Windows 上的检测扫描 pane shell 的后代进程，识别直接的 agent 以及常见的命令包装，包括 npm/Node 和 Git Bash 的进程链，并且能跟随 Git Bash 启动的 agent 跨过模拟的 exec 边界。

但文档立刻补了一句关键限制：这和 Unix 的前台进程组检测不是一回事。 所以「Unix 上稳定、Windows 上飘」是有结构性原因的，不是 bug。

Windows 上支持的集成（12 个）#

Pi、OMP、Claude Code、Codex、GitHub Copilot CLI、Devin CLI、OpenCode、Kilo Code CLI、Droid、Kimi Code CLI、Qoder CLI、Antigravity CLI。

比 Unix 窄。 Herdr 会隐藏或拒绝那些安装格式在 Windows 上不支持的集成——所以在 Unix 上能看到某个集成而 Windows 上看不到，先看是不是这个原因。

三、部分支持：这几项最影响日常#

live cwd：PowerShell 下的真实边界#

方式状态
shell cd 之后的 live cwdpartial
通过 shell 集成 / OSC7 的 live cwdsupported

Herdr 能在正确的目录里启动 pane、也能按你启动它的目录建初始 workspace。但启动之后，它能检视到的进程信息在 PowerShell 下不能可靠跟踪后续的逻辑 cd。

处置：用 Herdr 集成，或者提示 shell 集成来上报 live cwd。模块 3 第 2 篇讲过 18 个集成的落点，这里不重复。

CJK IME 合成定位：partial#

见下一节，它是 partial 里体感最强的一个。

前缀输入源切换：只支持韩文 IME#

这是个 opt-in 实验：

[experimental]
switch_ascii_input_source_in_prefix = true

它在 prefix 命令激活时把韩文输入切到英文，退出 prefix 后恢复。其他语言的 IME 目前不支持（Windows 上）。macOS 和 Windows 以外是空操作。

Kitty 图形：Windows Terminal 根本走不通#

Kitty 图形默认启用，依赖外层终端。Herdr 在 Windows 上和别的平台一样发 Kitty 图形协议输出，但文档说明：Windows Terminal 并不暴露 Herdr 使用的那条 Kitty 图形路径。 如果外层终端处理不好图形输出，设：

[terminal]
kitty_graphics = false

剪贴板图片粘贴到 agent：terminal/agent 相关#

有些 Windows agent 能直接接收 ctrl+v 并读剪贴板图片。但 Herdr 自己的剪贴板图片读取器没有接到本地原生 Windows pane 上，所以 agent 原生的图片粘贴仍然依赖终端和 agent。agent 的图片粘贴快捷键（如 alt+v）也不会给 Herdr 管理的本地剪贴板加桥接。

远程剪贴板图片桥是另一回事，通过 herdr --remote 到 Linux/macOS/Windows 是支持的。

插件：preview#

插件支持 windows 作为 manifest 平台，但在 preview 阶段。GitHub install、local link、build 命令、actions、events 和插件 pane 都是尽力而为。

两个具体约束：

  1. 命令必须是 Windows 兼容的 argv 命令。npm、bun、node 这类 Node 包 shim 在 PATH 上就期待能用；但文档示例里 Unix 风格的 sh / Bash 写法需要 Windows 侧的替代。
  2. 平台过滤会跳过不支持的 build 命令，对不支持的 action 或 pane 返回 platform_unsupported。

这正好接上模块 4 第 4 篇实测的那两条警告——platforms 未声明时你会拿到 manifest does not declare platforms 的警告，而在 Windows 上它是有实际后果的。

四、光标：这一节单独讲，因为它是个两难#

为什么默认是「画出来的」光标#

Herdr 的原生 Windows pane 依赖 ConPTY。Windows 的终端光标路径在多路复用器重绘屏幕时会暴露中间位置——原生光标可能闪烁、跳动、或在输出活跃时短暂停在旧位置。

文档特别指出：这个行为在其他原生 Windows 终端多路复用器里也会复现，直接 VT 光标定位压力测试也能复现。所以 Herdr 无法在保留原生光标行为的同时消除它。

于是默认 host_cursor = "auto" 在原生 Windows 和 WSL 上把光标画成单元格内容。画出来的光标稳定、不闪，但代价是：

Windows 不用画出来的光标来定位 IME 组字和候选 UI，所以韩文、日文、中文输入法的组字窗可能出现在错误位置。

换回原生光标#

[ui]
host_cursor = "native"

原生模式恢复 IME 锚点，但可能重新引入输出活跃时的光标移动伪影。想回到视觉稳定就设 host_cursor = "drawn"，或者删掉这个设置回到 Windows 默认。

这是一个纯粹的取舍，没有第三条路：要么光标稳、要么输入法准。

键鼠的一个具体限制#

Windows 终端并不都以相同形状上报修饰键。Herdr 在 Windows 上保留了 Windows Terminal 和 Alacritty 的鼠标上报和 ctrl+j。原生 Windows 输入路径还保留了物理按键、重复、释放、独立 Escape、以及通过默认 ConPTY pane 的 shift+enter。

但修饰键仍然取决于外层终端是否上报一个独立按键事件：如果它把 shift+enter 上报成普通 Enter，Herdr 只能转发普通 Enter。

Windows 包里包含了微软当前的 app-local ConPTY 运行时，因为较老 Windows 10 上的系统 ConPTY 会丢掉 Kimi 和 Pi 这类 agent 使用的 Kitty 键盘协议序列。只有在诊断兼容性问题时才用 HERDR_WINDOWS_CONPTY=system 启动 Herdr。

五、复制粘贴#

场景做法
复制 pane 内文本在 pane 里拖选，复制经由 Herdr 完成
粘贴文本Windows Terminal 里用 ctrl+shift+v
多行粘贴有 bracket 处理，shell 和 agent prompt 会收到一次粘贴而不是逐行提交
用外层终端的粘贴按住 shift 右键点击，而不是把点击送进 Herdr

多行粘贴的 bracket 行为值得强调：agent prompt 收到的是一整次粘贴，不会每行触发一次提交。

六、明确不支持：六项#

能力状态
直接终端 attach（herdr terminal attach）unsupported

前两项和模块 4 的关系最直接：

  • 没有 live handoff，所以模块 4 第 1 篇那条「用 pty 起临时 client 拉起 server」的方案在 Windows 上不需要——因为 Windows 上本来就是 server 独立存活
  • 没有直接 terminal attach，模块 2 讲过的「直接接管一个裸终端流」在 Windows 上用不了，只能走 --remote

远程工作流（Windows 上）#

herdr --remote workbox

目标主机可以是 Linux、macOS 或 Windows。在 Windows 主机上，远程 attach 会复用 PATH 上的兼容包或当前受管 release；交互式直接 attach 和保存机器的 setup 会在需要时提示安装/更新完整包，但后台保存重连只能发现已安装的包，不能提示安装或更新。

一个具体的操作建议：Windows OpenSSH 不使用 Herdr 的 Unix 控制套接字复用，所以远程 setup 时建议走 Windows ssh-agent 的密钥认证，避免反复输入 passphrase。

七、报告 Windows 问题时要带什么#

文档列的清单本身就说明了什么最容易出问题：

  • Herdr 版本
  • Windows 版本
  • 终端应用
  • shell（PowerShell 或 cmd）
  • 是否用了命名 HERDR_SESSION
  • 相关 Herdr 日志
  • 精确的复现步骤

模块 4 第 1 篇和排障篇都讲过怎么取这些：版本 herdr -V，状态 herdr status，日志在 ~/.config/herdr/（Windows 上是 %APPDATA%\herdr\）。

八、避坑指南#

  1. preview 迁移要两步：herdr channel set stable，旧 preview 版本要先 herdr update 再重试。
  2. 光标和 IME 只能选一个。host_cursor = "native" 恢复输入法锚点，代价是可能的闪烁；drawn 稳定但输入法可能错位。
  3. ctrl+shift+v 是 Windows Terminal 的粘贴键，不是 ctrl+v。
  4. 多行粘贴是 bracket 的，agent prompt 收到一次粘贴，不会逐行提交。
  5. Kitty 图形在 Windows Terminal 上走不通，外层终端处理异常就设 terminal.kitty_graphics = false。
  6. PowerShell 下的 live cwd 不可靠，用集成或 shell 集成 / OSC7。
  7. Windows 上没有 direct attach、没有 live handoff，模块 2、4 里的相关方案要换成 --remote。
  8. Windows 集成只有 12 个，比 Unix 窄；看不到某个集成先查安装格式是否支持。
  9. 插件在 Windows 只是 preview，命令要 Windows 兼容；Unix 的 sh / Bash 示例要换掉。
  10. cjk_ime_agents 全是未知名字时 reveal 不生效，这在 Windows 上尤其容易发生（支持的 agent 列表更短）。
  11. 前缀输入源切换只支持韩文 IME，其他语言开了也没用。
  12. 改 ConPTY 运行时只在诊断时做：HERDR_WINDOWS_CONPTY=system 是排障开关，不是配置项。

常见问题

我的 Windows 预览版怎么切到稳定版？

先 herdr channel set stable。但有个坑：如果较旧的预览版版本不接受这个命令，先在 preview 渠道上跑一次 herdr update，然后重试。原因是 Windows 稳定版安装默认走 stable 渠道，而已存在的 preview 安装会一直留在 preview 除非你显式切换。

Windows 上光标闪烁或 IME 候选窗错位怎么办？

这两个是同一个开关的两面。默认 host_cursor = auto 在原生 Windows 和 WSL 上把光标画成单元格内容，视觉稳定但无法提供 IME 需要的原生光标锚点，所以 CJK 输入法的组字窗会跑到错误位置。改 host_cursor = native 可以恢复锚点，代价是输出活跃时可能重新出现光标闪烁、跳动或短暂停在旧位置。取舍在你。

在 Windows 上 agent 状态一直检测不到吗？

不是。Windows 上的 agent 进程树检测会扫描 pane shell 的后代进程，识别直接的 agent 以及常见的命令包装，包括 npm/Node 和 Git Bash 的进程链，它还能跟着 Git Bash 启动的 agent 跨过模拟 exec 边界。但它和 Unix 的前台进程组检测不是一回事，所以在 Unix 上正常而在 Windows 上不稳定时，这是原因之一。

哪些功能在 Windows 上完全不支持？

文档列了六项：直接终端 attach（herdr terminal attach）、live server handoff、Unix 文件描述符 handoff、Unix 前台进程组、Herdr 在本地原生 pane 里的剪贴板图片桥、以及签名二进制/SmartScreen 规避。前三项是跨平台工具链的代价，后三项是平台能力的边界。

我在 Windows 上怎么远程连到我的 Linux 机器？

herdr --remote workbox，和 Linux/macOS 上完全一样，目标主机可以是 Linux、macOS 或 Windows。注意一个限制：Windows OpenSSH 没有 Herdr 的 Unix 控制套接字复用，所以远程 setup 时建议用 Windows ssh-agent 做密钥认证，避免反复被要求输入 passphrase。另外后台重连只能发现已安装的包，不能提示你安装或更新。
