Herdr 排障清单：11 个真实故障模式，以及为什么「重启大法」在四种情况下会杀掉你的进程

把官方 11 条排障条目按「症状 → 根因 → 处置」重写成本机实测版：CJK 输入法候选窗错位与 host_cursor 的取舍、Enter/Tab/Backspace 双触发和三个终端的最低修复版本、Option+方向键冒出 ;3D 的 zsh bindkey 修法、升级后 session 还是旧的（哪些能热交接、哪些必须重启）、macOS Keychain 访问失败要先看 launchctl managername、注销后 SSH/DNS 失效的 No user exists for uid 症状、以及为什么 server stop 会杀掉所有 pane 进程、日志到底在哪。本机验证了日志路径、HERDR_LOG、config check 和 launchctl 的真实输出。基线 herdr 0.9.2。

September 30, 2026 · 5 min · 901 words · 梦兽编程 -  |  English

排障文章最容易写成「如果 X 就改 Y」的清单，读完还是不知道自己的问题是不是那个。这一篇反过来做：先给判断，再给处置，最后说清楚每种处置的代价。

因为 Herdr 的排障里最贵的一个动作是 herdr server stop——它会杀掉所有 pane 里的进程。文档在两条故障里都提到它，但那是「恢复手段」，不是「无所谓的重试」。搞清这一点，你才知道什么时候该用它、什么时候该用命名会话代替。

基线：herdr 0.9.2 stable · macOS · 诊断命令的输出都是本机实测。

结论前置#

Herdr 排障的第一原则是分清「谁持有问题」：外层终端、操作系统、还是 Herdr 本身。 上面两类问题 Herdr 改不了（终端双发按键、终端 IME 光标锚点），必须去外层终端修； 第三类才是 Herdr 的配置或 session 生命周期问题。 而所有涉及 session 的修复里，herdr server stop 都是有代价的——它结束 pane 进程。命名会话里请改用 herdr session stop <name>。

零、先收集事实，再动手#

官方排障文档的第一句就要求这几样，本机实测都能直接拿到：

herdr -V        # herdr 0.9.2
herdr status    # client / server / update 三段

除版本和会话状态外，还要记清楚：操作系统、外层终端的名字和版本、这个会话是本地还是远程、有没有和 tmux 套娃。

最后那一条经常被忽略但很关键——Herdr 套在 tmux 里时，「按键被上层吃掉」和「Herdr 画错了」是两种完全不同的故障，不确认套娃关系会往错的方向查。

一、输入法相关：CJK 候选窗错位#

症状#

中文/日文/韩文输入法的组字或候选窗出现在错误位置。

根因#

Herdr 在原生 Windows 和 WSL 上默认用「单元格绘制」的光标（host_cursor = "auto" 的实际取值），因为原生光标在 ConPTY 多路复用器重绘屏幕时会闪烁、跳动、停在旧位置。而单元格绘制的光标无法提供 IME 组字 UI 依赖的原生光标锚点。

处置#

[ui]
host_cursor = "native"

这是用闪烁换位置准确的取舍：原生模式恢复 IME 锚点，但输出活跃时可能重新出现光标跳动。想回到视觉稳定就设 host_cursor = "drawn"，或者删掉这个设置回到 Windows 默认。

macOS 上的对应开关#

macOS 没有这个 ConPTY 问题，但 TUI 会自己隐藏光标（Claude Code、pi、codex 都这样），这会让 macOS 原生输入法失去候选窗锚点。Herdr 为此提供了一个实验开关：

[experimental]
reveal_hidden_cursor_for_cjk_ime = true
cjk_ime_cursor_shape = "steady_block"
cjk_ime_agents = ["claude", "pi", "codex"]

它的取舍写在配置参考里，值得原文引用：开启后，对于那些「隐藏光标但不绘制替代物」的应用（vim 普通模式等），外层终端会多出一个可见的硬件光标。 cjk_ime_agents 让你把范围限制到具体 agent，空列表表示对任何聚焦 pane 生效。

二、按键重复：Enter / Tab / Backspace 触发两次#

症状#

按一次 Enter 执行两次，Tab 或 Backspace 同样。

根因#

外层终端的旧版本，在应用开启 Kitty 键盘事件上报后，把 Enter、Tab、Backspace 的松开事件发成了和按下相同的字节。Herdr 收到重复字节之后无法区分。

处置：升级外层终端#

终端含修复的最低版本
kitty0.33.0
foot1.20.0
Alacritty0.15.0

这个问题在 Linux 长期支持发行版的旧终端包上尤其常见（因为它们锁版本）。如果升到最新版终端仍然复现，请带上「终端精确版本」和「在 Herdr 之外是否也发生」一并报告——这两个信息能把问题从「可能是终端」推进到「可能是 Herdr」。

三、Option+方向键打出 ;3D#

症状#

按 Option+Left 之后屏幕上出现 ;3D，Option+Right 出现 ;3C。

根因#

终端普遍把 Alt+Left / Alt+Right 发成 ESC[1;3D 和 ESC[1;3C。macOS 上必须先让外层终端把 Option 当作 Alt。 如果 shell 没绑定这些序列，zsh 会把剩下那部分字符原样打出来。

处置#

# 加到你自己的 zsh 配置里
bindkey $'\e[1;3D' backward-word
bindkey $'\e[1;3C' forward-word

为什么 kitty 在 Herdr 之外看起来是好的#

这是一个特别容易误判的现象：kitty 的自动 zsh 集成只给它自己直接启动的 shell 装这些绑定，不给多路复用器创建的 shell 装。 所以同一个 kitty 里，手开的终端正常、Herdr 里的不正常。

修法是按 kitty 的手动 shell 集成说明配置，或者干脆在 kitty.conf 里映射，让按键在到达 shell 之前就转好：

map alt+left send_text all \x1bb
map alt+right send_text all \x1bf

Herdr 刻意不改写#

文档给了理由：终端应用可能直接使用 Alt+Left / Alt+Right，Herdr 改写会破坏它们。 所以这是「不动」而不是「修不好」。

四、升级后 session 还是旧的#

症状#

herdr update 成功，但界面和行为没变。

根因#

更新二进制不会替换已经在运行的兼容 server。

处置#

herdr server stop
herdr

先 herdr status 看清楚是 client 侧还是 server 侧的落后。文档给的这条命令有代价：停 server 会退出它所有 pane 的进程。

命名会话请改用：

herdr session stop <name>

Unix 上还有 live handoff 可以在不杀 pane 进程的前提下交接，但交接的前提是双方版本都支持——从旧版本过来的服务器需要先更新一次才会走 handoff 这条路。

五、macOS：Keychain 工具在 Herdr 里失败#

症状#

在 Herdr pane 里跑需要访问 Keychain 的工具（git 凭证、签名工具等）失败。

第一步：先看启动上下文，别急着重启#

launchctl managername

本机实测输出：Background。文档特别说明——自动启动的 macOS server 返回 Background 是正常的，它本身并不说明 Keychain 有问题。跳过这一步直接重启的人经常白重启一次。

处置#

只有在 Keychain 访问确实失败、并且 server 是通过 SSH 或后台作业启动的情况下，才需要：

herdr server stop   # 从正常的 GUI 终端里重启 Herdr
herdr

根因#

Herdr 的 pane 继承的是那个长生命周期 server 的 macOS launch 上下文。 一个通过 SSH 或后台作业启动的 server，可能拿不到交互式 Keychain 服务。

六、macOS：注销之后 SSH / DNS 失效#

症状#

macOS 注销重登后，Herdr pane 里的 SSH 或 DNS 全部失败，典型报错：

No user exists for uid 501
Could not get manager name.
curl: (6) Could not resolve host

一个必须知道的反直觉事实#

重新登录并不能修好那个旧 server。 你登录回去了，但那个 server 还带着注销前的上下文。

处置#

停掉受影响的会话，从新登录的 GUI 终端里启动 Herdr。这会结束 pane 里的实时进程，但会恢复保存下来的 session 布局。

为什么 handoff 救不了这个场景#

文档明确说了原因：live handoff 保留源 server 的 service 上下文，而这个故障的根因恰恰就是它继承的上下文坏了。所以老服务器需要完整的 session 重启才能采用这个修复，handoff 做不到。

还不行就看这一行日志#

如果新起的 server 仍然有问题，去 herdr-server.log 里找：

could not select persistent user service context

文档解释了什么时候会出现：Herdr 在所需的 macOS API 不可用时会保留继承来的上下文。

自动启动 vs 显式启动#

自动启动的 macOS server 使用每用户服务上下文，所以注销不会让它的 pane 失去到 macOS 服务的连接；显式的 herdr server 启动则保留调用者的上下文。这个差异决定了你是会遇到还是不会遇到这个故障。

七、其余几条快速排查#

症状检查处置
herdr: command not found外层终端的环境重启终端让它重载环境；确认安装目录在 PATH 上。包管理器安装的，用包管理器更新并让它暴露到 PATH
某个直连键位毫无反应是不是被 OS 或外层终端吃掉了在那一层释放这个组合键，或者换一个键位
远程 attach 无法认证常规 OpenSSH 通不通先确认 ssh <host> 正常。用口令保护的密钥在非交互 shell / CI / 移动端终端里，先把密钥加载进 ssh-agent 再启动远程 attach
CJK 光标闪烁见第一节见第一节

「键位无反应」的排查顺序#

这一条最容易卡住，因为它至少有三个可能的层。按这个顺序排除：

  1. OS 层：macOS 的「系统键盘快捷键」抢占了（比如某些输入法的切换键）。去系统设置里找。
  2. 外层终端层：kitty / Alacritty 自己的配置里绑定了同一个组合键，并且在到达 Herdr 之前就消费掉了。
  3. Herdr 层：以上都不是，才看 Herdr 自己的键位配置。模块 1 第 2 篇讲过怎么把某个键位从冲突清单里解开。

八、日志在哪、以及 server stop 的真实代价#

日志#

~/.config/herdr/herdr.log
~/.config/herdr/herdr-client.log
~/.config/herdr/herdr-server.log

本机实测：这三个文件确实在。herdr-server.log 持续记录结构化事件，例如：

2026-09-30T10:49:24.154095Z  INFO herdr::logging: pane child spawned event="pane.spawned" subsystem="pane" outcome="ok"
2026-09-30T10:49:24.154263Z  INFO herdr::logging: tab focused event="tab.focus" subsystem="tab" outcome="ok" workspace_id=...

这条日志格式本身就有用：出问题时 grep outcome="error" 或具体的 event=，比顺着时间轴读快得多。

更详细的内容：

HERDR_LOG=herdr=debug herdr status     # 本机实测可用

报告问题时把当前日志和它的轮转副本一起附上。

server stop 的代价（再说一次）#

命令作用范围pane 进程
herdr server stop当前路由到的那个 server会被结束
herdr session stop <name>指定的命名会话该会话内的 pane 会被结束
herdr agent rename / config reload / 各种 pane 命令—不影响任何其他进程

模块 4 第 1 篇讲过那个坑：忘了带 --session 时，server stop 停的就是你正在用的会话。 在脚本里需要「停掉一个测试会话」时，永远用 session stop <name>。

九、避坑指南#

  1. 不要看到异常就 server stop。它结束所有 pane 进程。先用 herdr status 判断是 client 侧还是 server 侧。
  2. 命名会话里一律用 session stop <name>，它范围明确。
  3. launchctl managername 返回 Background 不等于 Keychain 有问题（本机实测就是这个值）。它是自动启动 server 的正常状态。
  4. 重新登录修不好注销后 SSH/DNS 失效的那个 server，必须从新 GUI 终端完整重启。
  5. live handoff 保留源 server 的上下文，所以它修不了上下文本身坏了的故障。
  6. 双发按键要升级外层终端（kitty ≥0.33.0 / foot ≥1.20.0 / Alacritty ≥0.15.0），改 Herdr 配置没有用。
  7. host_cursor = "native" 是拿闪烁换 IME 锚点，不是单纯的「修复」。
  8. reveal_hidden_cursor_for_cjk_ime 会让隐藏光标的应用多出一个可见硬件光标（vim 普通模式典型）。用 cjk_ime_agents 限定范围。
  9. kitty 的自动 zsh 集成不给多路复用器的 shell 装绑定，这是「外面好好的、里面坏掉」的常见真因。
  10. 不要在 zsh 配置里用 shell 改写去"修" Alt+方向键的全局行为，用 bindkey 显式绑定。
  11. 排障第一步永远是记下「有没有套 tmux」。套了层时，上下层的表现会互相掩盖。
  12. grep 日志里的 outcome= 而不是顺着读，比肉眼看快。

常见问题

为什么我按文档执行 herdr server stop 之后我的终端都没了？

因为停 server 会连带结束它所有 pane 的进程——这不是 bug，是 server 和 pane 的父子关系。文档在两条不同故障里都写了这句话（升级后 session 是旧的、Keychain 访问失败），但它是「恢复手段」而不是「无代价操作」。如果你只是想关掉一个测试会话，用 herdr session stop <name>，它只停那一个命名会话，不影响你正在用的会话。要停默认会话前，先确认 pane 里没有正在跑的长任务。

Enter 键在 Herdr 里按一次触发两次，怎么修？

这是外层终端的旧版本在应用开启 Kitty 键盘事件上报后，把 Enter、Tab、Backspace 的「松开」事件发成了和「按下」相同的字节，Herdr 收到重复字节后无法区分。修法是升级外层终端到含上游修复的版本：kitty 0.33.0、foot 1.20.0、Alacritty 0.15.0。Linux 长期支持发行版的旧版终端包最常见这个问题。如果在最新版终端上仍然复现，请带上终端版本号、以及是否在 Herdr 之外也发生，一并报告。

按 Option+Left 却打出 ;3D 怎么办？

终端把 Alt+Left/Alt+Right 发成 ESC[1;3D 和 ESC[1;3C，macOS 上外层终端要先把 Option 当作 Alt 配置。如果 shell 没有绑定这些序列，zsh 会把剩下的字符显示出来，就是你看到的 ;3D 和 ;3C。加显式绑定即可：bindkey $'\e[1;3D' backward-word 和 bindkey $'\e[1;3C' forward-word。kitty 在 Herdr 之外看起来正常，是因为它的自动 zsh 集成只给它自己启动的 shell 装这些绑定，不给多路复用器创建的 shell 装。Herdr 本身刻意不改写带修饰的箭头键，因为终端应用可能直接使用 Alt+Left。

我升级了 Herdr，为什么界面还是旧的？

因为更新二进制不会替换已经运行的兼容 server。重新启动 Herdr 就会用上新的 client。如果你还需要 server 侧的改动，看 herdr status，然后停掉会话再重新启动。这里要分清两类更新：client 侧（界面、键位、主题）重开 Herdr 即可；server 侧（pane 进程、检测清单、插件注册表）需要重启对应会话。Unix 上还有 live handoff 可以不杀进程地交接，旧版本不支持的服务器需要先更新一次才会走 handoff。

日志在哪里？出问题时该给我什么？

默认在 ~/.config/herdr/ 下：herdr.log、herdr-client.log、herdr-server.log（本机实测这三个文件存在，server 日志会持续记录 pane.spawned、tab.focus 这类结构化事件）。需要更详细的内容时设 HERDR_LOG=herdr=debug。报告问题时把当前日志和它的轮转副本一起附上。另外官方排障文档开头就要求先给版本和会话状态：herdr -V 和 herdr status。
