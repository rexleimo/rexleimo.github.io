Herdr 实战完全指南

本专栏基线：herdr 0.9.2 stable channel（本机实测 macOS / Apple silicon）。

所有命令、config key、socket 方法都对齐官方 pinned revision v0.9.2 的文档源 （raw.githubusercontent.com/herdrdev/herdr/v0.9.2/docs/next/website/src/content/docs/*.mdx）， 标注「本机实测」的输出是真机跑出来的原样结果，不是凭记忆写的。

一句话说清 Herdr 是什么

Herdr 是一个面向 AI 编码智能体的终端工作区管理器。

它和 tmux 一样是多路复用器：后台 server 持有真实终端进程，client 只是接上去渲染， 你 detach、关窗口、断 SSH，pane 里的进程照跑。

它和 tmux 不一样的地方有三条，而这三条恰好都是「2026 年你在终端里干的活」变了之后才出现的需求：

维度tmux / zellijHerdr
交互入口键盘优先，必须背快捷键鼠标优先：窗格、标签、工作区、分割线、右键菜单全可点，键盘是可选层
它眼里跑的是什么一堆 shell 进程能认出 pane 里是哪个 coding agent，以及它现在是 working 还是 blocked 在等你
状态可见性你得一个个 pane 切过去看侧边栏按 workspace 汇总 agent 状态，哪个项目在等你一眼就看到
编程化控制tmux send-keys 那套字符串黑魔法一等公民的 CLI + 本地 socket API，给脚本和 agent 用来编排别的 agent
多机器每台机器各开一个 tmuxLocal 和保存的 SSH 机器在同一个窗口里，agent 列表合并，各连接独立重连
扩展.tmux.conf + 脚本带 manifest 的本地可执行插件（动作 + 事件钩子 + 自己的 pane），有市场

官方给自己的定位就是这句：Terminal workspace manager for AI coding agents。 不是「又一个 tmux」，而是多 agent 的调度台。

为什么现在值得单开一个专栏

因为「终端里的进程」这件事变了。以前你在 pane 里跑的是 shell、编辑器、日志、服务， 它们是被动的——你不看它，它就不动。现在你在 pane 里跑的是 Claude Code、Codex、Pi、 Hermes Agent 这类主动进程：它们自己干活、干到一半停下来等你批一个命令、干完了等你看结果。

于是「我有 8 个终端窗口」这件事的真正痛点不再是布局，而是：

  • 哪个 agent 在等我？（blocked）
  • 哪个已经干完了我还没看？（done）
  • 我 SSH 断了、笔记本合盖了、机器重启了，那些跑到一半的 agent 还在不在？
  • 我想让「A agent 跑完测试就自动叫 B agent 来修」，脚本怎么写？

Herdr 是照着这四个问题设计的。它的官方博客标题就很直白： Coding agents are becoming runtimes、Ten agents, three clients, 95% less CPU。

本机实测：它真的认得我的 agent

写这个专栏时，我这个人（和这个 pi 会话）就跑在 Herdr 里。下面是真机输出，一个字没改：

$ herdr --version
herdr 0.9.2

$ herdr status
client:
  version: 0.9.2
  channel: stable
  protocol: 22
  endpoint_protocol_generation: 1

server:
  status: running
  version: 0.9.2
  endpoint_compatible: yes
  private_protocol: 22
  private_protocol_compatible: yes
  socket: /Users/rex/.config/herdr/herdr.sock

update:
  restart_needed: no
  server_binary_stale: no

再看它认出了什么：

$ herdr agent list
{"id":"cli:agent:list","result":{"agents":[
  {"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-videos",
   "focused":true,"pane_id":"w3:p1","tab_id":"w3:t1",
   "terminal_title":"π - rex-videos","workspace_id":"w3", ...},
  {"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-hugo",
   "pane_id":"w3:p2","terminal_title":"π - rex-hugo", ...},
  {"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-hugo",
   "pane_id":"w3:p4","terminal_title":"π - rex-hugo", ...}],"type":"agent_list"}}

三个 pane，三个 pi agent，全部 working，连终端标题 π - rex-hugo 都抓到了。

而这台机器上一个 Herdr 集成都没装：

$ herdr integration status
pi: not installed (/Users/rex/.pi/agent/extensions/herdr-agent-state.ts)
claude: not installed (/Users/rex/.claude/hooks/herdr-agent-state.sh)
codex: not installed (/Users/rex/.codex/herdr-agent-state.sh)
hermes: not installed (/Users/rex/.hermes/plugins/herdr-agent-state/__init__.py)
...（共 18 个）

这就是本专栏最想讲清楚的一件事：Herdr 的 agent 检测和 agent 集成是两套东西。 检测靠前台进程 + 屏幕清单，零配置就能用；集成（hook / extension）额外给你 生命周期级状态和 agent 原生会话恢复。装不装、装哪个、装完差在哪，模块 3 会拆开讲。

这个专栏解决什么

官方文档有 21 页，写得很干净，但它是参考手册：按主题平铺，不告诉你上手顺序， 也不告诉你哪些坑是真会踩的。本专栏补的是这段：

  • 第一次用，鼠标够用吗？什么时候才真的需要学 ctrl+b？
  • session / workspace / tab / pane 四层，我到底该按什么粒度切？
  • 关窗口、断 SSH、herdr update、机器重启——这四种情况下我的 agent 分别还活着吗？ （答案不一样，而且有一条叫 live handoff 的路径最容易被忽略）
  • 远程有三条路：SSH 进去跑 herdr、herdr --remote <host>、把机器 herdr machine add 存起来。 差别在哪？为什么只有其中一条能把本地剪贴板的图片贴进远程 pane？
  • 侧边栏显示 blocked 到底是谁判的？done 和 idle 有什么区别？为什么 CLI 查到的状态 和我屏幕上看到的角标不一致？
  • 我想让脚本/另一个 agent 来编排这些 agent，用 CLI 还是直接连 socket？两者的边界在哪？

这些问题的答案分散在 6 个文档页里，需要交叉阅读才能拼出来。这个专栏替你拼好，并且每条都实测过。

适合谁读

  • 正在用 AI coding agent 的人（Claude Code / Codex / Pi / OpenCode / Hermes 任一）：这是你的主战场，从模块 0 顺序读。
  • tmux / zellij 老用户：概念你已经有了，直接读核心概念 对齐术语差异，然后跳模块 3 看 agent 部分。
  • 没用过任何复用器的人：可以读。Herdr 鼠标优先，上手不需要背键位，这也是它相对 tmux 最大的门槛优势。
  • 想做 agent 编排自动化的人：模块 3 之后接模块 4「编程化控制」（CLI / socket API / agent-automation / 插件，后续批次开放）。

不适合：只想找个 tmux 配置文件模板的人（Herdr 不吃 .tmux.conf，配置是 config.toml）； 需要 Windows ARM64 原生构建的人（当前跑的是 x86_64 构建 + Windows 模拟）； 以及完全不接受「后台常驻一个 server 进程」这个模型的人。
