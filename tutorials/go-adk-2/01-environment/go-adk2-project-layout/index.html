2.x 项目结构与 go.mod 规范：让 ADK Go 项目能被团队维护

ADK Go v2.4.0 时代的目录规范、go.mod 与工具链钉版、go.work 处理 v1/v2 共存期、独立模块（plugin/agentanalytics）、图与工具的分包策略、testdata goldenfile 与 CI 约定。

September 26, 2026 · 4 min · 768 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0 · Go 1.27.1

装好环境只保证「你这台机器能跑」。这一篇要的是另一个人 clone 下来 5 分钟能跑，CI 上 3 分钟能构建，半年后没人记得为什么这样写也能改。

2.x 对结构的影响比 1.x 更大：多了图引擎（workflow）、多了注册表与安全层（agentregistry/auth/authn/authz）、多了压缩（session/compaction）。这些不加约束的话，最后都会长进同一个 main.go。

推荐结构（中等规模应用）#

myagent/
├── cmd/
│   └── agent/
│       └── main.go              # 只负责：读配置 → 组装 → Execute(ctx, cfg, os.Args[1:])
├── internal/
│   ├── agents/                  # LlmAgent 定义，一个 Agent 一个文件
│   │   ├── coordinator.go       #   Mode: llmagent.ModeChat（默认，root）
│   │   ├── weather.go           #   Mode: llmagent.ModeSingleTurn
│   │   └── booking.go           #   Mode: llmagent.ModeTask + InputSchema/OutputSchema
│   ├── graph/                   # 图拓扑：节点 + 边，不写业务
│   │   ├── research.go          #   AddFanOut / NewJoinNode / AddFanIn
│   │   └── routing.go           #   StringRoute / IntRoute / MultiRoute
│   ├── tools/                   # functiontool / MCP toolset / skill 目录
│   ├── store/                   # session/artifact/memory 服务的构造与迁移
│   ├── platformx/               # 自定义 platform provider（确定性时间/UUID，仅测试与重放用）
│   └── config/                  # 配置结构体 + 校验（凭据、模型名、超时、compaction）
├── testdata/
│   ├── golden/                  # 事件序列快照（.events.json / .events.yaml）
│   └── skills/                  # SkillToolset 用的 SKILL.md 样例
├── deploy/
│   ├── Dockerfile
│   └── cloudrun.tf | agentengine.yaml
├── .env.example
├── go.work                      # 迁移期或 monorepo 才需要，见下节
├── go.mod
└── go.sum

三条硬规则：

  1. main.go 不写 Agent 逻辑。 它的职责到「把 launcher.Config 填完 + Execute」为止。原因很实际：一旦逻辑进了 main，你就没法在测试里换 SessionService 或注入 platform provider。
  2. 图拓扑与节点实现分开。 internal/graph/ 只描述「谁连谁、什么路由条件」；节点函数放 internal/agents/ 或 internal/tools/。2.x 的 workflow.EdgeBuilder 让拓扑变得很薄，混在一起时你会看不清改动的影响面。
  3. internal/ 而不是 pkg/。 除非你真打算让别人 import 你的 Agent 定义（那就是 agentregistry 那条路，见模块 10）。

go.mod 规范#

module github.com/yourorg/myagent

go 1.27.1

require (
	github.com/joho/godotenv v1.5.1
	google.golang.org/adk/v2 v2.4.0
	google.golang.org/genai v1.xx.x
)

要点：

约定理由
go 指令写完整版本（1.27.1 而非 1.27.0/1.26）ADK 要求下限 1.26.6；写低会在 go test 时撞 Go 1.27 新增的 stdversion vet 检查
ADK 依赖锁具体版本，禁 @latest上游 2.x 每 4~6 周一个次版本（v2.1→v2.4 只用了 7 周），行为会变
每两周跑一次 go list -m -u all 看有没有新 v2.x别等出问题才发现 v2.5.0 已经发布
升级走独立 PR，且 PR 描述里写版本号go version -m 能反查线上二进制，PR 记录能反查为什么升
生产构建后留痕：go version -m ./agent > build-info.txt事故排查时第一个要问的就是「线上到底是哪个版本」

上游有独立子模块要单独拿： plugin/agentanalytics 在 v2.4.0 树里带自己的 go.mod（plugin/agentanalytics/go.mod），所以它不在主模块包集合里：

go get google.golang.org/adk/v2/plugin/agentanalytics@v2.4.0

第一次跑 go build 会顺手把 google.golang.org/adk（1.x 路径）拉进 module cache —— 这是正常现象，不是你的问题：1.x 是主模块，/v2 的若干工具链/内部依赖仍从主模块解析。别为了「看起来干净」去加 exclude，那只会带来更难查的问题。

v1 与 v2 共存期：两种做法#

因为 google.golang.org/adk 与 google.golang.org/adk/v2 是两个模块，同一个 go.mod 里可以同时要求两者。这让按包灰度成为可能（详见迁移实操 ）。

做法 A：单模块内共存（推荐，改造期）

require (
	google.golang.org/adk   v1.7.0   // 还没迁的老包
	google.golang.org/adk/v2 v2.4.0  // 新写的包
)

纪律要求：一个包只用一条线，禁止同一文件里混用两套类型（agent.Context 在两条线上是不同类型，混用会立刻编译失败——这是好事，编译器帮你把关）。迁完删掉旧 require 并 go mod tidy。

做法 B：go.work（monorepo / 需要改上游本地 fork）

go 1.27.1

use (
	./apps/customer-agent     // 用 /v2
	./libs/legacy-router      // 还在 /v1
	../internal/adk-fork      // 本地源码调试时才加
)

go.work 要提交到仓库，但不要让 CI 依赖它（CI 用 GOWORK=off 跑，验证「单独 clone 也能构建」）。这条纪律能帮你提前抓出「只有我本机能编译」的问题。

多 Agent 与 loader 的选择#

v2.4.0 agent/loader.go 提供两种（注释里还留着 TODO：将来会搬到更合适的包，所以不要把 Loader 的实现细节当稳定 API）：

// 单根 Agent
loader := agent.NewSingleLoader(rootAgent)

// 一个根 + 若干其它 Agent（Dev UI 里可切换、按名字加载）
loader, err := agent.NewMultiLoader(rootAgent, subAgentA, subAgentB)

接口能力：ListAgents() []string、LoadAgent(name string) (Agent, error)、RootAgent() Agent。

选哪个的判断标准很简单：你要不要在同一个进程里服务多个可独立对话的 Agent。 需要的话就用 NewMultiLoader，把 Agent 名字当作路由键（配合 launcher.Config 的 web/api 端点）；只是「一个 root + 若干 SubAgents」的组合，用 NewSingleLoader 就够——注意 SubAgents 不是 loaders，两者别混。

launcher.Config 才是你的装配清单#

2.x 的 cmd/launcher/launcher.go 里，Config 字段就是运行期能力的全部开关：

config := &launcher.Config{
	AgentLoader:      agent.NewSingleLoader(root),
	SessionService:   ss,          // session.InMemoryService() | session/database | session/vertexai
	ArtifactService:  as,          // artifact | artifact/gcsartifact
	MemoryService:    ms,          // memory | memory/vertexai
	A2AOptions:       []a2asrv.RequestHandlerOption{ /* ... */ },
	PluginConfig:     pc,          // runner.PluginConfig
	TelemetryOptions: []telemetry.Option{ /* ... */ },
	Authenticator:    authn.NewNoop(),       // nil = Noop；非 nil 时对 restapi 端点做认证，未过 401
	Authorizer:       authz.NewStrict(),     // nil = authz.NewNoop()；Strict 提供 CanActAsUser(ctx, userID)
	Compaction:       nil,                   // 进程级！nil = 关闭
}

两个必须在结构上预留位置的字段：

  • Authenticator / Authorizer：安全层默认是「全放开」（authn.NewNoop() / authz.NewNoop()）。server/authn 自带三种 provider 实现：header.go（反向代理传头）、iap.go（Google IAP）、custom.go（自接）；server/authz 只有 NewNoop() 与 NewStrict()，后者暴露 CanActAsUser(ctx, userID)（调用者能否代表该用户行动）。这不是「以后再说」的字段，新项目第一周就该把 provider 装上，否则除 /health、/version 外的端点是裸的。
  • Compaction：官方注释写明它是进程级设置 —— 一个 launcher 通过 agent loader 服务多个应用时，它们共享同一份压缩配置、同一个 Summarizer 实例（也就是同一个模型）。如果两个业务的压缩策略不同，或者不能共享 summarizer，就必须拆进程。这条约束决定了你的部署单元粒度，属于架构决策，不是配置项。

配置与凭据#

type Config struct {
	ModelName   string        // "gemini-flash-latest"
	Location    string
	Timeout     time.Duration // 节点级默认
	GeminiKey   string        // 或走 Vertex ADC
	UseVertex   bool
}

func Load() (Config, error) { /* 读 env → 校验 → 返回 */ }

约定：凭据只从环境变量读，配置结构体在 main 里一次性装配完并校验，不要让 os.Getenv 散落在 Agent 定义内部。理由：GOOGLE_GENAI_USE_VERTEXAI 这类开关一旦散在各处，切环境时必漏。

测试目录怎么摆#

层位置做法
单元测试internal/*/\*_test.go上下文用 agent.StrictContextMock 内嵌 fake，断言 var _ agent.Context
确定性platformx/注入固定 platform.WithTimeProvider / WithUUIDProvider，让 session.NewEvent(ctx, …) 产出可比对的 ID/时间
事件回归testdata/golden/*.events.json一次 invocation 的事件序列（type/partial/stateDelta）落盘，逐字段比对
端到端cmd/agent/e2e_test.go真模型调用打 //go:build integration，CI 里按 tag 分跑
Skill 资源testdata/skills/参照上游 examples/skills/skills/weather/SKILL.md（带 references/、assets/）

goldenfile 这一条值得强调：图引擎重构（模块 5）几乎必然改变事件序列，没有基线快照，你无法区分「预期的结构变化」和「回归 bug」。

CI 约定#

# .github/workflows/ci.yml
image: golang:1.27.1
env:
  GOTOOLCHAIN: go1.27.1+auto    # 钉住，行为可预测
  GOWORK: off                    # 不许「只有我本机能编」
cache:
  paths: ['${{ env.GOMODCACHE }}']
steps:
  - run: go vet ./...
  - run: go test -race -count=1 ./...
  - run: go test -tags=integration -count=1 ./...   # 需要凭据，仅 main 分支
  - run: go build -trimpath -o agent ./cmd/agent
  - run: go version -m ./agent > build-info.txt

补一个 2.x 特有的检查：CI 里加一步 go doc 冒烟，防止有人误把 1.x 路径写回来：

常见问题

ADK Go 项目推荐什么目录结构？

cmd/ 放入口，internal/agents/ 放 LlmAgent 定义，internal/tools/ 放函数工具，internal/graph/ 放图拓扑，internal/store/ 封装 session/artifact/memory 服务，testdata/ 放事件 goldenfile 与 skill 资源。

v1 和 v2 能在同一个仓库共存吗？

能，模块路径不同（google.golang.org/adk 与 google.golang.org/adk/v2）。迁移期可以按包灰度；跨模块联调用 go.work。

agentanalytics 插件为什么要单独 go get？

因为 plugin/agentanalytics 在上游是独立 go.mod 的子模块，不属于主模块的包集合。

一个根 Agent 和多个 Agent 怎么切换？

launcher.Config.AgentLoader 用 agent.NewSingleLoader(a)（单根）或 agent.NewMultiLoader(root, others...)（多根/多 Agent，按名字加载）。

自己封装 ADK 发版时要注意什么？

若你的库以大版本 2 发布，模块路径同样要加 /v2；且 go.mod 的 go 指令不低于依赖要求（ADK v2.4.0 为 go 1.26.6）。
