函数工具与流式工具：functiontool.New、Config 全字段与工具内能拿到的上下文

ADK Go v2.4.0 工具层地基：functiontool.New 的泛型签名 Func[TArgs,TResults]、schema 自动推断（jsonschema 而非 genai.Schema）、NewStreaming 返回 iter.Seq2[string,error]、IsLongRunning 的真实语义、工具内部通过 agent.Context 能做什么，以及 Google Search 与函数工具不能混用时用 agenttool 拆子 Agent 的官方绕法。

September 26, 2026 · 4 min · 800 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 tool/tool.go、tool/functiontool/{function.go,streaming_function.go}、tool/agenttool/、tool/toolutils/，样例 examples/tools/multipletools/main.go。

工具是 Agent 唯一能改变外部世界的地方。2.x 在这一层做了一件很实在的事：工具函数第一个参数就是统一的 agent.Context——工具不再是个纯函数，它能看到会话、能改状态、能发事件、能要求人工确认。这一篇把函数工具与流式工具讲透，下一篇再讲 MCP。

最小函数工具：一个泛型签名搞定#

type Input struct {
	LineCount int `json:"lineCount"`
}

type Output struct {
	Poem string `json:"poem"`
}

poemTool, err := functiontool.New(functiontool.Config{
	Name:        "poem",
	Description: "Returns poem",
}, func(ctx agent.Context, in Input) (Output, error) {
	return Output{Poem: strings.Repeat("A line of a poem,", in.LineCount) + "\n"}, nil
})

源码里的类型定义（v2.4.0 原文）：

// Func represents a Go function that can be wrapped in a tool.
// It takes a agent.Context and a generic argument type, and returns a generic result type.
type Func[TArgs, TResults any] func(agent.Context, TArgs) (TResults, error)

func New[TArgs, TResults any](cfg Config, handler Func[TArgs, TResults]) (tool.Tool, error)

三个直接结论：

  1. 不用写 JSON Schema。 Config.InputSchema/OutputSchema 留 nil 时由泛型参数推断（// Input schema is automatically inferred from the input and output types.）。结构体 tag 用 json:"city" 控制字段名。
  2. 返回值是任意类型，不是 map[string]any。tool.Tool 接口层的 Run 返回 map[string]any，但 functiontool 帮你做了序列化——这是它比裸实现接口舒服的地方。
  3. 参数类型不合法会返回 functiontool.ErrInvalidArgument（比如传了个 map 或无法映射成 JSON Schema 的类型），所以 New 的 error 别忽略。

想给模型更多提示，用 jsonschema tag（官方 MCP 样例就这么写）：

type Input struct {
	City string `json:"city" jsonschema:"city name"`
}

functiontool.Config 全字段（7 个）#

字段类型说明
Namestring模型看到的工具名
Descriptionstring模型决定要不要调它的唯一依据
InputSchema*jsonschema.Schemanil = 从 TArgs 推断
OutputSchema*jsonschema.Schemanil = 从 TResults 推断
IsLongRunningbool标记为长任务
RequireConfirmationbooltrue = 框架自动发起 HITL 确认

两个 schema 字段的类型是 jsonschema.Schema，而 llmagent.Config.InputSchema/OutputSchema 用的是 genai.Schema——同一个概念两套类型，这是上游已知的不一致（llmagent 侧注释里有 TODO 说要换成 jsonschema）。别把它写进你自己的抽象层，包一层转换函数。

RequireConfirmationProvider 是 any，签名有讲究#

// Required signature for a provider function:
// func(toolInput ToolArgs) (bool)
// where ToolArgs is the input type of your go function

注意它收的是你这个工具的入参类型，不是 (name, input)——和 tool.ConfirmationProvider（func(toolName string, toolInput any) bool，用在 toolset 层）签名不同。因为 any 不做编译期检查，签名写错只会在运行时炸。第 3 篇里我给一个安全的写法。

IsLongRunning 的真实语义#

标记后框架不把它当同步调用等结果。典型用法是「先受理、后回填」：工具立刻返回一个 request_id，真正的结果由外部事件（第 8 篇的 pubsub/eventarc）另开一轮写回会话。别指望它自动帮你轮询。

流式工具：NewStreaming 返回 iter.Seq2[string, error]#

type StreamingFunc[TArgs any] func(agent.Context, TArgs) iter.Seq2[string, error]

func NewStreaming[TArgs any](cfg Config, handler StreamingFunc[TArgs]) (tool.Tool, error)

searchTool, err := functiontool.NewStreaming(functiontool.Config{
	Name:        "live_search",
	Description: "Search and stream results as they arrive",
}, func(ctx agent.Context, in Input) iter.Seq2[string, error] {
	return func(yield func(string, error) bool) {
		for _, chunk := range fetchChunks(ctx, in) {
			if !yield(chunk, nil) {
				return          // 调用方 break 了，必须立刻收手
			}
		}
	}
})

三个必须记住的点：

  • yield 返回 false 就必须马上返回。false 表示下游不再要了（客户端断开、break 取消）。不检查返回值是最常见的流式泄漏——正好对应 Go 工具链那篇 讲的 iter 协议与 goroutine 泄漏检测。
  • 没有 TResults 泛型参数：流式工具的输出就是一串 string 片段，类型参数只剩 TArgs。
  • 底层接口是 RunStream(ctx agent.Context, args any) iter.Seq2[string, error]，并且它实现了 toolinternal.StreamingFunctionTool——只有走流式模型请求时才会真的逐段推送，非流式配置下会被攒成一次结果。开关见模块 7。

工具内部能拿到什么（agent.Context 的工具段）#

这是 2.x 合并 ToolContext/CallbackContext 之后真正值钱的部分：

func myTool(ctx agent.Context, in Input) (Output, error) {
	// 读
	who := ctx.UserID()
	app := ctx.AppName()
	sid := ctx.SessionID()
	scope := ctx.IsolationScope()     // 隔离作用域，空=未隔离
	branch := ctx.Branch()            // "a1.a2.a3"，并行子 Agent 用来互相看不见
	callID := ctx.FunctionCallID()    // 本次工具调用的唯一 ID

	// 读写状态
	prev, _ := ctx.State().Get("approved_days")

	// 语义检索记忆
	mem, err := ctx.SearchMemory(ctx, "用户偏好")

	// 改状态 / 转移 Agent / 结束本轮
	ctx.Actions().StateDelta["last_tool"] = callID
	ctx.Actions().TransferToAgent = "summarizer"
	ctx.EndInvocation()

	// HITL（第 3 篇）
	if c := ctx.ToolConfirmation(); c == nil {
		return out, ctx.RequestConfirmation("要删除 3000 行，确认？", map[string]any{"lines": 3000})
	}
}

Actions() 返回的是 *session.EventActions，这就是工具影响 Agent 行为的唯一后门——StateDelta、TransferToAgent、EndInvocation、SkipSummarization 全在它上面。详细字段见模块 4 。

FunctionCallID() 为什么重要：HITL 与长任务都要「暂停—恢复」，恢复时框架会用同一个 call ID 重跑工具函数。所以你必须拿它当幂等键存进度，否则会重复扣款/重复建单。第 3 篇的官方样例正是这么做的。

官方绕法：Google Search 不能和函数工具混在一个 Agent#

examples/tools/multipletools 的包注释写得很直白：

demonstrates a workaround for using Google Search tool with other tools ... This is necessary due to limitations in the genai API.

结构是按工具类型拆子 Agent，root 用 agenttool 调它们：

searchAgent, _ := llmagent.New(llmagent.Config{
	Name: "search_agent", Model: model,
	Description: "Does google search.",
	Instruction: "You're a specialist in Google Search.",
	Tools:       []tool.Tool{geminitool.GoogleSearch{}},
})

poemAgent, _ := llmagent.New(llmagent.Config{
	Name: "poem_agent", Model: model,
	Description: "returns poem",
	Instruction: "You return poems.",
	Tools:       []tool.Tool{poemTool},
})

root, _ := llmagent.New(llmagent.Config{
	Name: "root_agent", Model: model,
	Description: "You can do a google search and generate poems.",
	Instruction: "Answer questions about weather based on google search unless asked for a poem," +
		" for a poem generate it with a tool.",
	Tools: []tool.Tool{
		agenttool.New(searchAgent, nil),
		agenttool.New(poemAgent, nil),
	},
})

两个细节决定成败：

  • Description 是路由依据。root 的模型只看这段文字决定委派给谁，写「does google search」这种具体动词，别写「a helpful agent」。
  • root 的 Instruction 要写明仲裁规则（官方那句「unless asked for a poem」就是仲裁）。

这条限制值得记住，因为它会让「一个 Agent 挂五种工具」的直觉设计失败——工具类型冲突时，ADK 的答案是多 Agent 而不是多工具。

过滤与裁剪工具集#

ts := tool.FilterToolset(mcpToolSet, tool.AllowedToolsPredicate([]string{"get_weather"}))
  • tool.Predicate = func(ctx agent.ReadonlyContext, tool Tool) bool——能拿到只读上下文，所以可以按用户/状态动态放行；
  • StringPredicate(names) / AllowedToolsPredicate(names) 是现成的白名单实现；
  • mcptoolset.Config.ToolFilter 已标 Deprecated: use tool.FilterToolset instead，新代码别再用那个字段。

为什么要主动裁剪：工具声明会进 prompt，几十个 MCP 工具的 schema 能吃掉几千 token，还会稀释模型选对工具的概率。裁剪是既省钱又提准的第一招。

自检#

// 工具数量与名字会直接决定成本，测试里就断言掉
func TestToolSurface(t *testing.T) {
	tools, err := ts.Tools(readonlyCtx)
	if err != nil {
		t.Fatal(err)
	}
	if len(tools) != 1 || tools[0].Name() != "get_weather" {
		t.Fatalf("unexpected toolset: %v", names(tools))
	}
}

函数工具本身是纯 Go 函数，直接调用它测逻辑（传 agent.StrictContextMock），不要每次都过模型。

常见问题

ADK Go 2.x 怎么定义一个函数工具？

functiontool.New(functiontool.Config{Name, Description}, handler)，handler 签名是泛型 functiontool.Func[TArgs,TResults] = func(agent.Context, TArgs) (TResults, error)，输入输出 schema 由类型自动推断。

流式工具怎么写？

functiontool.NewStreaming(cfg, handler)，handler 返回 iter.Seq2[string, error]——一段一段 yield 文本片段和错误，边生成边推给前端。

工具内部能拿到什么上下文？

统一后的 agent.Context：State()/ReadonlyState()、Session()、Artifacts()、Memory()、SearchMemory()、Actions()（可改 state、可转移 Agent）、FunctionCallID()、ToolConfirmation()/RequestConfirmation()，以及 IsolationScope()、Branch()。

为什么 Google Search 和我的函数工具放一起不工作？

genai 层限制：内置搜索工具与函数声明不能同时挂在同一个 LlmAgent 上。官方 examples/tools/multipletools 的绕法是把两类工具各自包进子 Agent，root agent 用 agenttool.New(subAgent, nil) 当工具调用。

IsLongRunning 有什么用？

把工具标记为长任务：框架不会当成一次普通同步调用等结果，配合前端可先返回「已受理」再回填。functiontool.Config 有这个字段，MCP 侧由服务端声明。

怎么临时禁用某个工具？

tool.FilterToolset(toolset, tool.StringPredicate(names)) 做白名单；也可自己写 tool.Predicate = func(agent.ReadonlyContext, tool.Tool) bool。mcptoolset.Config.ToolFilter 已标 Deprecated，改用 FilterToolset。
