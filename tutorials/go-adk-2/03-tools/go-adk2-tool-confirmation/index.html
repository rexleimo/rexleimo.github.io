工具人工确认（HITL）：一个 flag 就够，还是要自己接管协议？

ADK Go v2.4.0 的 tool confirmation 双档设计：声明式 RequireConfirmation / RequireConfirmationProvider / tool.WithConfirmation，与手动档 ctx.ToolConfirmation() + ctx.RequestConfirmation(hint, payload)；adk_request_confirmation 协议契约（FunctionResponse 必须同 id、name、带 confirmed）、toolconfirmation.OriginalCallFrom 解析、幂等重入与 FunctionCallID 的用法。

September 26, 2026 · 4 min · 766 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 tool/tool.go、tool/toolconfirmation/tool_confirmation.go、agent/context.go，样例 examples/toolconfirmation/main.go。

2.x 把 human-in-the-loop 做成了一等公民，而且给了两个档位：声明式一行配置，手动档完全接管。官方样例的包注释把选择标准写得很清楚：

It uses ctx.ToolConfirmation() and ctx.RequestConfirmation() to define the confirmation process. This is the example for most advanced scenario which gives the full control how to define confirmation flow. For simpler setup use RequireConfirmation or RequireConfirmationProvider in functiontool.Config.

先给结论：90% 的场景用声明式。需要「改参数再执行」「部分批准」「审批人要看到人类可读摘要」时才上手动档。

档位一：声明式（推荐起点）#

deleteTool, err := functiontool.New(functiontool.Config{
	Name:                "delete_records",
	Description:         "Deletes records by query",
	RequireConfirmation: true,             // ← 一行
}, func(ctx agent.Context, in DeleteArgs) (DeleteResult, error) {
	return doDelete(in), nil
})

动态判断（按入参决定要不要问）：

type TransferArgs struct {
	Amount   float64 `json:"amount"`
	Currency string  `json:"currency"`
}

cfg := functiontool.Config{
	Name:        "transfer_money",
	Description: "Transfer money between accounts",
	// 签名必须是 func(toolInput TransferArgs) bool —— 注意是你这个工具的入参类型
	RequireConfirmationProvider: func(in TransferArgs) bool {
		return in.Amount > 1000        // 小额直接过
	},
}

⚠️ RequireConfirmationProvider 字段类型是 any，写错签名编译期不报错。安全做法是自己定义一个具名类型再赋值，让编译器替你检查：

type confirmFn func(TransferArgs) bool

var p confirmFn = func(in TransferArgs) bool { return in.Amount > 1000 }
cfg.RequireConfirmationProvider = p

toolset 层（MCP 等成组工具）用另一个签名：

// tool.ConfirmationProvider
type ConfirmationProvider func(toolName string, toolInput any) bool

ts := tool.WithConfirmation(mcpToolSet,
	false,
	func(name string, input any) bool {
		return name == "create_issue" || name == "delete_branch"
	})

WithConfirmation(toolset, requireConfirmation bool, provider ConfirmationProvider) Toolset——provider 优先级高于 flag（源码注释：If set, this takes precedence）。

三个入口的字段对照：

协议层到底发生了什么#

框架发出的那个 FunctionCall 名字是常量：

// tool/toolconfirmation/tool_confirmation.go
const FunctionCallName = "adk_request_confirmation"

它的 args 里有两个键（源码注释原文归纳）：

  • "toolConfirmation"：一个 ToolConfirmation，带 Hint；
  • "originalFunctionCall"：模型本来想调的那个调用（name + args）。

源码对客户端提了 5 条硬性要求，我原样列出来——这就是你前端要实现的契约：

1. Listen for events containing a FunctionCall with this name.
2. Extract the details of 'originalFunctionCall' from the arguments.
3. Present a clear confirmation prompt to the human user, explaining the action and potential consequences.
4. Capture the user's decision (e.g., true for yes/approve, false for no/deny).
5. Send a FunctionResponse message back to the ADK. This FunctionResponse MUST:
     - Have the same 'id' as the received "adk_request_confirmation" FunctionCall.
     - Have the name set to "adk_request_confirmation".
     - Include a response payload, typically a map like {"confirmed": bool}.

id 和 name 必须一致——这两条错了，框架收不到答复，工具就永远卡在待确认。这是自己写前端最容易错的地方。

ToolConfirmation 结构（v2.4.0 原文）：

type ToolConfirmation struct {
	Hint      string `json:"hint"`       // 给用户看的理由
	Confirmed bool   `json:"confirmed"`  // 用户决定；未响应前通常是零值
	Payload   any    `json:"payload"`    // 应用自定义数据
}

Payload 是 any，双向可用：请求时塞「将要删除 3000 行」给审批人看，答复时塞「批准 5 天而不是 10 天」回来——下面官方样例就是这么做的。

档位二：手动接管（完整控制确认流）#

examples/toolconfirmation/main.go 的请假审批场景，逐段拆：

func requestVacationDays(ctx agent.Context, args RequestVacationArgs) (*RequestVacationResults, error) {
	// ① 用 FunctionCallID 作为跨暂停/恢复的关联键
	if confirmation := ctx.ToolConfirmation(); confirmation == nil {
		requestID := nextRequestID()
		requestsByReqID[requestID] = &VacationRequest{ID: requestID, UserID: args.UserID, Days: args.Days, Status: "PENDING"}
		requestsByCallID[ctx.FunctionCallID()] = req

		// ② 发起确认，payload 会原样回传给审批人
		if err := ctx.RequestConfirmation(
			"Please approve or reject the tool call ... by responding with a FunctionResponse with an expected ToolConfirmation payload.",
			ConfirmationPayload{DaysApproved: 0}); err != nil {
			return nil, err
		}
		// ③ 本轮先返回一个「待审批」结果，不要继续往下执行
		return &RequestVacationResults{Status: "Manager approval is required.", RequestID: requestID}, nil
	}

	// ④ 恢复后重入：同一个 FunctionCallID 找回上下文
	req, ok := requestsByCallID[ctx.FunctionCallID()]
	if !ok {
		return nil, fmt.Errorf("unable to get request using function call id %s", ctx.FunctionCallID())
	}
	if !confirmation.Confirmed {
		req.Status = "REJECTED"
		return &RequestVacationResults{Status: "The time off request is rejected.", DaysApproved: 0, RequestID: req.ID}, nil
	}

	// ⑤ 批准了，还能读审批人改过的 payload（部分批准）
	var payload ConfirmationPayload
	jsonRoundTrip(confirmation.Payload, &payload)          // any → 结构体要过一遍 JSON
	approvedDays := min(payload.DaysApproved, args.Days)   // 审批人可下调，不能上调
	req.Status = "APPROVED"
	return &RequestVacationResults{Status: "The time off request is accepted.", DaysApproved: approvedDays, RequestID: req.ID}, nil
}

这段样例里有 5 个必须抄下来的设计：

  1. ctx.ToolConfirmation() == nil 是「第一次进来」的判据。非 nil 表示这是确认后的重入。
  2. ctx.RequestConfirmation(hint, payload) 返回 nil 只代表「请求已发出」，不代表批准——源码注释专门强调这点（It does NOT mean the action is approved）。所以发出后必须立刻 return，不能继续执行敏感操作。
  3. FunctionCallID() 当幂等键。恢复时框架重跑同一个工具函数，你需要一个键把第一次生成的 requestID/状态找回来。用 map 只是样例简化，生产请落库。
  4. confirmation.Payload 是 any，从 JSON 反序列化回来的是 map[string]any——官方样例用 json.Marshal + json.Unmarshal 做一次转换才拿到结构体。别直接类型断言。
  5. 审批人可以改参数（DaysApproved 下调）。这是手动档存在的理由：声明式只能「同意/拒绝」，手动档能「同意但打折」。

拒绝之后发生什么#

框架侧两个哨兵错误：

var ErrConfirmationRequired = errors.New("requires confirmation, please approve or reject")
var ErrConfirmationRejected = errors.New("call is rejected")

被拒绝时不会执行原工具，模型会收到一个 error 型 function response。所以你的 Instruction 要提前告诉它「被拒绝就问用户要不要改条件」，否则模型会拿着一个错误硬编下去。

解析被包装的原始调用#

前端/中间层经常需要「这次到底是想调什么」：

original, err := toolconfirmation.OriginalCallFrom(functionCall)  // *genai.FunctionCall

OriginalCallFrom 兼容 originalFunctionCall 的两种格式（对象与 JSON 字符串），所以不同版本的 UI 回传都能解析——自己手写解析逻辑是重复劳动。

两套机制可以共存：图节点里调一个需要确认的工具，就会出现「节点暂停 + 工具确认」两层交互。先设计节点边界，再决定哪些工具要确认，否则恢复语义会打架。

测试怎么写#

确认流程要跨两轮，测试里别用 launcher，用 runner 手动驱动两次：

// 第一轮：应当产生 adk_request_confirmation 调用，且不执行真实删除
for ev, err := range r.Run(ctx, uid, sid, msg, agent.RunConfig{}) { … }

// 断言出现了待确认事件、且副作用没发生
if !hasConfirmationCall(events, toolconfirmation.FunctionCallName) { t.Fatal("no confirmation requested") }
if store.DeletedCount() != 0 { t.Fatal("tool executed before approval") }

// 第二轮：把 FunctionResponse（同 id、name、confirmed:true）作为 user content 喂回去

这类测试是 HITL 唯一可靠的担保——「没批准就不能有副作用」是必须断言的安全不变量。

常见问题

ADK Go 2.x 怎么让工具执行前先问用户？

最省事：functiontool.Config.RequireConfirmation=true（或 mcptoolset 同名字段、或 tool.WithConfirmation 包 toolset）。要动态判断就用 RequireConfirmationProvider / tool.ConfirmationProvider。

确认请求在协议层长什么样？

框架发出一个 FunctionCall，名字固定为 toolconfirmation.FunctionCallName = "adk_request_confirmation"，args 里带 toolConfirmation（含 hint）与 originalFunctionCall。

前端要怎么回答？

回一个 FunctionResponse：id 必须与收到的 FunctionCall 相同、name 必须是 adk_request_confirmation、payload 里带 {"confirmed": bool}（可带自定义 payload）。true 则执行原调用，false 则拦截并返回错误。

工具函数在恢复后会被重新执行吗？

会。确认后框架用同样的入参重跑工具，所以工具必须能区分「第一次进来」和「已确认后再进来」——判据就是 ctx.ToolConfirmation() 是否为 nil。

怎么拿到被包装的原始调用？

toolconfirmation.OriginalCallFrom(functionCall) 从 adk_request_confirmation 的 args 里还原 originalFunctionCall，兼容对象与 JSON 字符串两种格式。

图节点里的 HITL 和工具确认是一回事吗？

不是。工具确认走 adk_request_confirmation 这个 FunctionCall；图节点暂停走 workflow.NewRequestInputEvent + ErrNodeInterrupted。两套机制，模块 5 讲前者。
