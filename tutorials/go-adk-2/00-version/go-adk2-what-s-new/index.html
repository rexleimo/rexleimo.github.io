ADK Go 2.0 带来了什么：v0.2 → v1.7 → v2.4 变更地图

基于 google/adk-go v2.4.0 源码树核实的大版本变更地图：图工作流引擎、Collaboration 三模式、统一 agent.Context、内置 HITL、CLI 改名 adkgo、Go 门槛 1.26.6。

September 26, 2026 · 5 min · 1057 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0（2026-09-11）｜对照版本 v1.7.0（2026-09-14）、v0.2.0（2025-11-21） 依据： 三个 tag 的 GitHub 源码树 + release notes + 官方 README-v2.md 迁移指南，全部实测核对，非二手转述。

本站旧专栏 Go ADK 实战完全指南 写于 v0.2.0 时代。今天回头看，那批文章的问题不是「写得不好」，而是基线整体过期：CLI 名字、模块路径、Go 门槛、上下文类型、编排模型全变了。所以这篇变更地图要先解决一个问题——哪些变化是「换个 import」，哪些是「重写成不同架构」。

先给结论表，再逐条展开。

一、变更总览：一次跳了两个大版本#

维度v0.2.0（旧专栏基线）v1.7.0（1.x 现役）v2.4.0（本专栏）
模块路径google.golang.org/adk同左google.golang.org/adk/v2
go.mod go 指令1.24.41.25.01.26.6
CLI 包cmd/adkcmd/adkgocmd/adkgo
Launcher Execute无 ctx 形参Execute(ctx, cfg, args)同 v1
gemini.NewModel无 ctxNewModel(ctx, name, cfg)同 v1
session.NewEventNewEvent(invocationID)同左（+临时 NewEventWithContext）NewEvent(ctx, invocationID)
上下文类型ToolContext / CallbackContext 分裂同左统一 agent.Context
编排Sequential/Parallel/Loop 三件套三件套（agent/workflowagents/*）图引擎 workflow + workflowagent，三件套建于其上
人机协同工具级 toolconfirmation同左引擎级 HITL（RequestInput / resume）

顶层新包——workflow、agent/workflowagent、agentregistry、auth、server/authn、server/authz、session/compaction、model/openaimodel、plugin/agentanalytics、tool/toolutils

注意一个容易误判的点：platform 包不是 2.x 才有的，v1.7.0 里就有 platform/time.go、platform/uuid.go。变化在于 2.x 把它接到了事件生成上（见第三节）。这种细节只有翻过源码树才不会写错。

二、真正的架构变化：图工作流引擎#

v2.0.0 的 release notes 把这一项列为头号特性，也确实值这个位置。新增顶层包 workflow，源码树里的文件已经把能力面摊开了：

workflow/  （v2.4.0，24 个非测试文件）
  agent_node.go       dynamic_node.go     request_input.go
  base_node.go        dynamic_scheduler.go resume.go
  branch.go           edgebuilder.go      retry.go
  config.go           errors.go           run_node.go
  function_node.go    graph.go            scheduler.go
  join_node.go        node_span.go        state.go
  parallel_worker.go  persistence.go      tool_node.go
  validation.go       workflow.go         workflow_node.go

对应的用户侧 API，看官方 examples/workflow/basic/main.go（v2.4.0 原文，无删改）：

package main

import (
	"context"
	"log"
	"os"
	"strings"

	"google.golang.org/adk/v2/agent"
	"google.golang.org/adk/v2/agent/workflowagent"
	"google.golang.org/adk/v2/cmd/launcher"
	"google.golang.org/adk/v2/cmd/launcher/full"
	"google.golang.org/adk/v2/workflow"
)

func main() {
	ctx := context.Background()

	upperFn := func(ctx agent.Context, input string) (string, error) {
		if input == "" {
			return "No input received", nil
		}
		return strings.ToUpper(input), nil
	}
	suffixFn := func(ctx agent.Context, input string) (string, error) {
		return input + " IS AWESOME!", nil
	}

	nodeConfig := workflow.NodeConfig{
		RetryConfig: workflow.DefaultRetryConfig(),
	}
	nodeA := workflow.NewFunctionNode("upper", upperFn, nodeConfig)
	nodeB := workflow.NewFunctionNode("suffix", suffixFn, nodeConfig)

	edges := workflow.Chain(workflow.Start, nodeA, nodeB)

	myWorkflow, err := workflowagent.New(workflowagent.Config{
		Name:        "simple_sequence_workflow",
		Description: "Converts string to uppercase and appends a suffix",
		Edges:       edges,
	})
	if err != nil {
		log.Fatalf("failed to create workflow: %v", err)
	}

	config := &launcher.Config{
		AgentLoader: agent.NewSingleLoader(myWorkflow),
	}
	l := full.NewLauncher()
	if err = l.Execute(ctx, config, os.Args[1:]); err != nil {
		log.Fatalf("Run failed: %v\n\n%s", err, l.CommandLineSyntax())
	}
}

读这段代码要注意三个范式信号：

  1. 工作流本身就是一个 Agent（workflowagent），可以放进 SubAgents，可以和 llmagent 混着套。1.x 里「workflow」是 runner 的编排概念，2.x 里它是图节点的聚合体。
  2. 节点函数签名带 agent.Context，不是 context.Context。这个统一上下文同时是 ctx、是会话句柄、是事件发射器、是 state 读写入口。
  3. 重试是节点级配置（NodeConfig.RetryConfig），不再是你在外层手写 for 循环包一层。

官方样例集（examples/workflow/）把能力面钉得很清楚，我列成表——这张表也就是本专栏模块 5 的目录：

样例演示内容需要 LLM
basicFunctionNode + workflow.Chain 顺序链否
complexfan-out → JoinNode fan-in → LLM 汇总（AddFanOut/AddFanIn）是
routing/string按字符串值分支 StringRoute否
routing/int按数值分支 IntRoute / MultiRoute[int]否
routing/llmLLM 分类，引擎按 StringRoute 分发是
hitl_simple两节点最小 pause/resume（RequestInput）否
hitl_rerun单节点重入式 HITL（ResumeOrRequestInput）否
dynamic/basicNewDynamicNode + RunNode 命令式编排否
dynamic/hitl动态编排 + 暂停等人否
dynamic/llm动态编排里调 LlmAgent 节点是
dynamic/use_as_outputWithUseAsOutput 把子节点输出提升为自身输出是

核心概念只有四类：

  • 节点 — FunctionNode（Go 函数）、AgentNode（包 LlmAgent）、ToolNode（包 tool.Tool）、JoinNode（fan-in 屏障）、DynamicNode（命令式编排器）
  • 边 — workflow.Chain / workflow.Concat / EdgeBuilder（Add / AddFanOut / AddFanIn）
  • 路由 — 节点在 Event.Routes 上写标签，边用 StringRoute / IntRoute / MultiRoute 匹配
  • HITL — 节点发射 RequestInput 暂停，人类回复后继续

三、破坏性变更（README-v2.md 的三条 + 实测一条）#

1. 模块路径带 /v2#

Go 的 major version 规则，所有 import 全量重写：

-	"google.golang.org/adk/agent"
-	"google.golang.org/adk/agent/llmagent"
-	"google.golang.org/adk/model/gemini"
+	"google.golang.org/adk/v2/agent"
+	"google.golang.org/adk/v2/agent/llmagent"
+	"google.golang.org/adk/v2/model/gemini"

2. session.NewEvent 首参变成 context.Context#

// v1（含临时的 NewEventWithContext）
ev := session.NewEvent(ctx.InvocationID())
ev := session.NewEventWithContext(ctx, ctx.InvocationID())

// v2
ev := session.NewEvent(ctx, ctx.InvocationID())

为什么值得单列一条？ 因为事件 ID 和时间戳现在由 platform 包提供的 provider 决定（platform.WithTimeProvider / platform.WithUUIDProvider）。session.NewEvent 自己的注释说得很直接：这让 workflow engine 之类的调用方能产出**确定、可重放（deterministic, replay-safe）**的事件。也就是说，图引擎的可恢复执行能工作的前提，就是这里多出来的一个 ctx 参数——不是随手加的。

工程后果：任何你自己造事件的辅助函数都得开始往下透传 ctx。别在函数中间 context.Background()——官方迁移文档专门点名了这点。

3. 上下文统一：ToolContext + CallbackContext → agent.Context#

合并本身是好事（回调里终于能拿到和工具一样的东西），但测试 mock 会当场崩：老 mock 只实现了 CallbackContext 的方法集，接口一扩，var _ agent.Context = (*MyMock)(nil) 直接编译失败。

官方给的解法有两条。笨办法是手补齐方法：

func (m *MockCallbackContext) Actions() *session.EventActions                       { return nil }
func (m *MockCallbackContext) FunctionCallID() string                               { return "" }
func (m *MockCallbackContext) ToolConfirmation() *toolconfirmation.ToolConfirmation { return nil }
func (m *MockCallbackContext) RequestConfirmation(hint string, payload any) error {
	return fmt.Errorf("RequestConfirmation() is not supported for MockCallbackContext")
}
func (m *MockCallbackContext) SearchMemory(ctx context.Context, query string) (*memory.SearchResponse, error) {
	return nil, fmt.Errorf("SearchMemory() is not supported for MockCallbackContext")
}

聪明办法是内嵌 agent.StrictContextMock，只覆盖你要用的方法：

type fakeContext struct {
	agent.StrictContextMock
}

var _ agent.Context = (*fakeContext)(nil)

func TestSomething(t *testing.T) {
	cc := &fakeContext{agent.StrictContextMock{Ctx: context.Background()}}
	// 需要哪个方法就在 fakeContext 上覆盖哪个
}

差别不是省事，是前向兼容：接口以后再加方法，内嵌 StrictContextMock 的 fake 不会挂；而且没覆盖的方法直接 panic “not implemented”，脏调用会当场炸出来，而不是悄悄返回零值让你的断言以错误的方式通过。

v2 源码树里对应的实现文件：agent/context.go、agent/common_context.go、agent/common_context_mock.go、agent/context_mock.go，另外 agent/tool_context_wrapper.go / agent/callback_context_wrapper.go 还在（做兼容包装）。

4. CLI 改名 adkgo（实测补充项，官方迁移文档没写）#

v1.7.0 和 v2.4.0 的树里都只有 cmd/adkgo，没有 cmd/adk：

// cmd/adkgo/adkgo.go
// adkgo is a CLI tool to help deploy and test an ADK application.
package main

import (
	_ "google.golang.org/adk/v2/cmd/adkgo/internal/deploy/agentengine"
	_ "google.golang.org/adk/v2/cmd/adkgo/internal/deploy/cloudrun"
	"google.golang.org/adk/v2/cmd/adkgo/internal/root"
)

func main() { root.Execute() }

根命令 Use: "adkgo"。所以旧专栏里这些内容现在全是坏的：

go install google.golang.org/adk/cmd/adk@latest   # 404，包不存在
adk version                                       # command not found

正确写法（细节见模块 1 第 1 篇 ）：

go install google.golang.org/adk/v2/cmd/adkgo@latest
adkgo --help

还有两个坑要提前说：adkgo 没有 version 子命令（根命令只挂了 deploy，其下是 cloudrun 与 agentengine），所以查版本要用 go list -m google.golang.org/adk/v2；而且 adkgo 不是用来跑 Agent 的，它是部署 CLI——console / web / api / webui 这些运行期子命令来自你 main.go 里的 launcher，用 l.CommandLineSyntax() 打印。细节见模块 1 第 1 篇 。

顺带注意部署子命令：v2 内置 deploy/cloudrun 和 deploy/agentengine 两个 driver，是以 blank import 注册进去的——你自己加私有部署目标也是这个套路。

四、新增能力面（不只是改签名）#

除了图引擎，v2.4.0 相对 1.x 的结构性新增：

① Collaboration 三模式。 llmagent.Config 多了 Mode 字段。internal/llminternal 里定义（type Mode = llminternal.Mode，字符串类型）：

ModeChat       Mode = "chat"
ModeTask       Mode = "task"
ModeSingleTurn Mode = "single_turn"

语义差别（官方 collaboration 样例）：

子 Agent模式能否和用户对话何时交还控制权
travel_plannerchat（root）完整对话n/a
weather_checkersingle_turn不能自动，带结果返回
flight_bookertask可以问澄清问题自动，带结构化结果返回

配合 InputSchema / OutputSchema（*genai.Schema），task 子 Agent 的输入输出是被 schema 约束的，官方 testdata 里甚至有 TestDelegation_07_ChatToTaskValidationRetry 这种「schema 校验失败后重试」的用例——说明这不是装饰性字段。

② 注册表与服务端安全层。 agentregistry（client.go / factory.go / registry.go / requester.go / resolve.go，把 agent 当成可注册、可解析的资源）、auth + auth/gcp、server/authn + server/authz（launcher 侧的认证/授权）——旧专栏对「谁来调我的 Agent」这块几乎是空的，2.x 把它做成了正式包。

③ 工具与模型层。 把 v1.7.0 和 v2.4.0 的包目录做一次集合差，只有 2.x 才有的包是这些（这份清单是机器算出来的，不是印象）：

agent/workflowagent   auth                  model/openaimodel     server/authz
agentregistry         auth/gcp              plugin/agentanalytics session/compaction
server/authn          tool/toolutils        workflow

反过来「1.x 有、2.x 也有」的差集为空——2.x 没有删包，只加包。两个值得注意的点：

  • model/openaimodel 是 2.x 才有的。也就是说，想用 OpenAI 兼容端点跑 ADK Go，1.x 里没有官方适配器，这点对国内走中转/自建网关的同学很关键（详见模块 2）。
  • session/compaction（上下文压缩）也是 2.x 独有：v2.4.0 树里有 examples/compaction + examples/compactionrecall，以及 agent/llmagent/testdata/TestCompactionE2E.httprr。

而 tool/skilltoolset、tool/exitlooptool、tool/loadartifactstool、tool/preloadmemorytool、tool/functiontool 的流式变体、plugin/retryandreflect、tool/toolconfirmation —— 这些在 v1.7.0 里就已经存在，别被「2.0 新特性」的标题党带偏。

④ A2A。 server/adka2a/v2 与 agent/remoteagent/v2（A2A 协议第 2 版实现）在 v1.7.0 里就有，所以这不是 2.x 的卖点。2.x 线上的实际增量是修复与收口，例如 v2.4.0 把「抓取到的 agent card 的接口 URL 钉在其来源 origin 上」（防 SSRF 式漂移），以及 remoteagent/v2 在聚合 artifact 事件后正确跑 after-callback。这类细节在模块 9 讲。

五、1.x 还会更新，别信「2.x 是唯一选择」#

有个反直觉的事实值得写下来，防止读者被带节奏：

v1.7.0  2026-09-14   ← 比 v2.4.0 还新 3 天
v2.4.0  2026-09-11

上游为 1.x 单独配了 release-please-config-v1.json 和 manifest，CI 同时跑 main 和 v1 分支（v2.1.0 的 changelog 里有 docs(contributing): document v1/v2 branch split、ci: run Go workflow on main and v1 branches）。也就是说：

  • 1.x 是有维护的旧大版本，不是废弃分支；
  • 但 1.x 不会拿到图引擎、collaboration 模式、agent.Context 统一——这些是 2.x 独有；
  • 1.x 的 Go 门槛是 go 1.25.0，而 Go 官方只同时维护两个次版本（当前 1.27.x / 1.26.x），1.25 已经没有安全更新了。这才是真正该催你上 2.x 的理由，而不是新特性。

所以我的判断：新项目无条件 2.x；已有 1.x 项目按迁移成本排期，但工具链必须先跟上 Go 1.26.6+（原因见第 3 篇）。

六、跨语言对齐：为什么你会看到「ADK 2.10」#

顺手澄清一个常见的版本混淆。同一套 ADK 的多语言实现，版本号不同步：

实现2026-09-26 最新2.0.0 时间点
Python google-adk2.10.0早于 Go
Go google.golang.org/adk/v22.4.02026-06-30
Java / Kotlin / TypeScript / Web各自独立—

所以「ADK 2.0」在 Go 语境里指 v2.0.0（2026-06-30）这一版，Python 那边已经走到 2.10。看英文教程时如果版本对不上，先确认它讲的是哪个语言实现——这也是A2A 与跨语言 那两篇要处理的坑。

常见问题

ADK Go 有 2.0 吗？

有。google/adk-go 在 2026-06-30 发布 v2.0.0，模块路径同时迁移到 google.golang.org/adk/v2，截至 2026-09-26 最新为 v2.4.0（2026-09-11）。

ADK Go 1.x 还在维护吗？

在维护。1.x 线独立发版，最新 v1.7.0（2026-09-14），上游仓库有 v1 分支与独立的 release-please 配置；但图工作流引擎等新特性只进 2.x。

ADK Go 2.x 的模块路径是什么？

google.golang.org/adk/v2，安装命令 go get google.golang.org/adk/v2。所有 import 都要带 /v2 后缀。

ADK Go 2.x 需要哪个 Go 版本？

v2.4.0 的 go.mod 声明 go 1.26.6，即最低 1.26.6；Go 1.27.x 同样可用，也是本专栏的实操基线。1.x 线（v1.7.0）声明 go 1.25.0。

以前的 adk 命令行工具还能用吗？

不能。2.x 的 CLI 包是 cmd/adkgo，二进制叫 adkgo；2.x 树里已经没有 cmd/adk，所以 go install google.golang.org/adk/cmd/adk@latest 会失败。

1.x 的 Sequential/Parallel/Loop 在 2.x 还存在吗？

以 workflowagents 的形式存在（sequentialagent/parallelagent/loopagent），但它们现在建立在图引擎之上，行为与 1.x 的独立实现有差异，迁移时要重新验证编排语义。
