1.x → 2.x 迁移实操：模块路径、agent.Context、NewEvent(ctx)

ADK Go 从 1.x 迁到 2.x 的完整实操：go.mod 与工具链、import 重写、session.NewEvent 加 ctx、agent.Context 统一与 StrictContextMock、图引擎改写编排、逐包验证与回滚策略。

September 26, 2026 · 5 min · 956 words · 梦兽编程 -  |  English

验证版本： 起点 v1.7.0，终点 v2.4.0；官方迁移文档 google/adk-go/README-v2.md（2026-09-26 原文）。

上一篇讲的是「2.0 有什么」，这篇讲「怎么把手上的代码搬过去，而且不炸」。

先给一个大多数教程不会告诉你的好消息：v1 和 v2 是两个不同的 Go 模块（google.golang.org/adk 与 google.golang.org/adk/v2）。这意味着它们可以同时出现在一个 go.mod 里。所以正确姿势不是「大爆炸式改完」，而是按包灰度。

迁移总账：4 件必做 + 1 件选做#

#事项必做？自动化程度
1Go 工具链升到 1.26.6+✅手动（CI 镜像 + 本地）
2依赖切到 adk/v2✅go get
3import 全量加 /v2✅可脚本化
4session.NewEvent + 测试 mock✅编译器全量指路
5顺序/并行/循环 → 图引擎⭕ 选做必须人写

前 4 项是「让它编译」，第 5 项才是「让它变好」。别把顺序搞反：先跑起来，再改架构。

第 0 步：先建基线，别裸奔#

迁移前把这三样钉住，否则你分不清「是我改坏了」还是「本来就这样」：

git status --porcelain          # 干净
go build ./...                  # 必须绿
go test -race ./... 2>&1 | tee /tmp/v1-baseline.log

ADK 这种事件驱动的库，没有跑过的测试等于没有测试。如果 1.x 项目本身测试覆盖薄，先补一层「行为快照」：把 root agent 的一次完整 invocation 的事件序列（type/partial/stateDelta）落成 goldenfile，迁移后逐字节对。这是我做框架升级的标准做法，比事后 debug 快一个数量级。

第 1 步：工具链#

go version                       # 先看现状
# 需要 go1.26.6 及以上（当前 stable：go1.27.1）

为什么工具链要先升？因为只要 ADK 的 go.mod 写了 go 1.26.6，Go 1.24/1.25 上直接是：

go: google.golang.org/adk/v2@v2.4.0 requires go >= 1.26.6 (running go 1.25.6; GOTOOLCHAIN=local)

GOTOOLCHAIN=auto（默认）时 Go 会自己去下载 go1.26.6 工具链；但国内 CI 常把它设成 local（或干脆封了 proxy.golang.org 的下发通道），这时候就会卡在这句错误上。两种解法：

# 方案 A：允许自动下发（需要能访问模块代理）
go env -w GOTOOLCHAIN=auto

# 方案 B：显式钉住本地工具链（推荐用于 CI，行为可预测）
go env -w GOTOOLCHAIN=go1.27.1+auto

CI 镜像里更干净的做法是直接换基础镜像：

# .github/workflows/ci.yml
container:
  image: golang:1.27.1        # 不要再用 golang:1.24 / golang:1.25

自己项目的 go.mod 也要一起提，否则 go mod init 生成的低版本号会让「1.26 才有的 API」在 go test 时被新的 vet 检查拦下（Go 1.27 起 go test 默认跑 stdversion，专门报告「你用了比你 go 指令更新的库 API」）。

go get go@1.26.6    # 或 go@1.27.1

第 2 步：依赖切到 /v2（保留 1.x 共存）#

go get google.golang.org/adk/v2@v2.4.0
go list -m all | grep 'golang.org/adk'

期望看到两行并存（迁移期正常状态）：

google.golang.org/adk v1.7.0
google.golang.org/adk/v2 v2.4.0

为什么要故意留着 1.x：因为一个中等规模项目里 ADK 的 import 点通常散在 30~80 个文件，一次性全改完再编译，报错信息会糊成一片。留着 1.x，让你可以「改完一个包，编译一个包」。

第 3 步：import 重写#

先看清楚有多少要改：

grep -rln '"google.golang.org/adk' --include='*.go' . | wc -l

然后批量替换。三个要求：根包 "google.golang.org/adk"（无斜杠）不能漏；注释/文档里的仓库名 google.golang.org/adk-go 和 https://google.golang.org/adk/... 链接不能误伤；已经是 /v2 的要幂等跳过。

所以下面这个脚本只改整行形状像 import 语句的行（带别名、_、. 均已覆盖），我在示例文件上实跑验证过：

#!/usr/bin/env perl
# adkimp.pl —— 把 ADK Go 的 import 路径从 1.x 改到 /v2，只碰 import 行
use strict; use warnings;
my $total = 0;
while (my $l = <>) {
    if ($l =~ m{^(\s*(?:(?:[A-Za-z_][A-Za-z0-9_]*|_|\.)\s+)?)\"google\.golang\.org/adk((?:/[^\"]*)?)\"\s*$}) {
        my ($pre, $rest) = ($1, $2);
        my $path = $rest =~ m{^/v2(/|\z)} ? "google.golang.org/adk$rest"
                                         : "google.golang.org/adk/v2$rest";
        $total++ if $path ne "google.golang.org/adk$rest";
        $l = qq{$pre\"$path\"\n};
    }
    print $l;
}
print STDERR "rewritten import lines: $total\n";

git ls-files '*.go' | xargs perl -i adkimp.pl   # 先 git diff 看一遗

# 复核：还有没有漏网的 1.x import
grep -rn '"google\.golang\.org/adk"' --include='*.go' . | grep -v '/v2"'
grep -rn '"google\.golang\.org/adk/' --include='*.go' . | grep -v '/adk/v2/'

# 再确认误伤：注释里的仓库名与链接应该还在
grep -rn 'adk-go' --include='*.go' .

跑完 gofmt -l . 看看格式，剩下的交给编译器。

go fix 帮不上这个忙。Go 1.26 把 go fix 重写成了「modernizers」（配 //go:fix inline 可以把自己的 API 迁移写成规则），但它只懂语言和标准库。ADK 的改名还得靠 gopls + 编译器。

第 4 步：编译器会指向的两处真破坏#

4.1 session.NewEvent 多了 ctx#

// v1
ev := session.NewEvent(ctx.InvocationID())
ev := session.NewEventWithContext(ctx, ctx.InvocationID())  // 临时形态，v2 已删

// v2
ev := session.NewEvent(ctx, ctx.InvocationID())

改起来机械，但别把 ctx 传错。官方文档明确点了一句：事件 ID 和时间戳现在由挂在 ctx 上的 provider 决定（platform.WithTimeProvider / platform.WithUUIDProvider）。所以：

// ❌ 错：在链路中间造一个新 ctx，provider 注入全丢，确定性重放失效
ev := session.NewEvent(context.Background(), ctx.InvocationID())

// ✅ 对：透传当前 agent.Context / context.Context
ev := session.NewEvent(ctx, ctx.InvocationID())

agent.Context 本身 embed 了 context.Context，所以手里的 ctx agent.Context 直接当第一参传就行。规则跟标准库一致：context.Background() 只出现在 main、init 和顶层测试 setup。

如果你的辅助函数还没收 ctx，就给它加一个 ctx context.Context 形参，从调用方往下传。这是唯一正确的方向。

4.2 上下文统一：mock 会当场崩#

ToolContext 与 CallbackContext 合并成单个 agent.Context。生产代码通常受益（回调里终于能拿到工具级的东西），测试代码会先炸：老的 MockCallbackContext 只实现了旧方法集，接口一扩就编译失败。

别手写补齐（官方给了这条笨路，但它是反应式的）：

// 每加一个方法就要改一次 mock，永远在追接口
func (m *MockCallbackContext) Actions() *session.EventActions { return nil }
func (m *MockCallbackContext) FunctionCallID() string { return "" }
// ...

改成内嵌 agent.StrictContextMock：

type fakeContext struct {
	agent.StrictContextMock
}

var _ agent.Context = (*fakeContext)(nil) // 编译期断言，直接对统一接口断言

func TestSomething(t *testing.T) {
	cc := &fakeContext{agent.StrictContextMock{Ctx: t.Context()}}
	// 只覆盖这个用例真正会调的方法
}

两个理由让它更值：

  1. 前向兼容：接口以后再加方法，内嵌者不用改。
  2. 失败要响：未覆盖的方法 panic "not implemented"，脏调用当场炸；手写 mock 会悄悄返回零值，让你以错误的方式通过测试。

顺带把 Go 1.24+ 就有的 t.Context() 用起来（自动在测试结束时 cancel），比 context.Background() 干净。

第 5 步（选做）：把编排改写成图#

前 4 步跑通后你的 1.x 语义应该原样保留 —— agent/workflowagents/{sequential,parallel,loop}agent 在 2.x 里路径没变，但它们已经建在新的图引擎之上（1.x 里是独立实现）。所以即使你不主动改写，也必须重新验证编排行为：迭代上限、子 Agent 的 transfer 时机、Event.Routes 语义、并行分支的取消传播。

值得改写成 workflowagent + 图的，是这几类：

你 1.x 里的写法2.x 图引擎对应收益
Sequential + 手写条件跳转StringRoute / IntRoute / MultiRoute分支变成边，代码少一层
Parallel + 自己 errgroup 聚合AddFanOut + NewJoinNode + AddFanInfan-in 屏障由引擎管
外层 for 循环包重试NodeConfig{RetryConfig: workflow.DefaultRetryConfig()}重试降到节点粒度
全局超时 context.WithTimeout节点级 timeout单节点失败不拖全局
人工问答靠 prompt 反复问RequestInput + ErrNodeInterrupted状态可持久化，进程重启能续

改造示例（顺序链，官方 examples/workflow/basic/main.go）：

package main

import (
	"context"
	"log"
	"os"
	"strings"

	"google.golang.org/adk/v2/agent"
	"google.golang.org/adk/v2/agent/workflowagent"
	"google.golang.org/adk/v2/cmd/launcher"
	"google.golang.org/adk/v2/cmd/launcher/full"
	"google.golang.org/adk/v2/workflow"
)

func main() {
	ctx := context.Background()

	upperFn := func(ctx agent.Context, input string) (string, error) {
		if input == "" {
			return "No input received", nil
		}
		return strings.ToUpper(input), nil
	}
	suffixFn := func(ctx agent.Context, input string) (string, error) {
		return input + " IS AWESOME!", nil
	}

	nodeConfig := workflow.NodeConfig{RetryConfig: workflow.DefaultRetryConfig()}
	nodeA := workflow.NewFunctionNode("upper", upperFn, nodeConfig)
	nodeB := workflow.NewFunctionNode("suffix", suffixFn, nodeConfig)

	edges := workflow.Chain(workflow.Start, nodeA, nodeB)

	root, err := workflowagent.New(workflowagent.Config{
		Name:        "simple_sequence_workflow",
		Description: "Converts string to uppercase and appends a suffix",
		Edges:       edges,
	})
	if err != nil {
		log.Fatalf("failed to create workflow: %v", err)
	}

	l := full.NewLauncher()
	if err := l.Execute(ctx, &launcher.Config{
		AgentLoader: agent.NewSingleLoader(root),
	}, os.Args[1:]); err != nil {
		log.Fatalf("Run failed: %v\n\n%s", err, l.CommandLineSyntax())
	}
}

注意 workflowagent 本身就是一个 agent.Agent，可以塞进别人的 SubAgents。这是 2.x 编排最重要的心智变化：图不是「工作流引擎」，图是一种 Agent。细节见模块 5 。

第 6 步：验证与灰度#

go build ./...
go vet ./...
go test -race ./...
go test ./... -run 'Integration' -count=1     # 事件序列对 goldenfile

顺序建议（每步一个 commit，可独立回滚）：

  1. 工具链 + go.mod（代码一行不改，仍用 1.x 依赖）
  2. import 批量重写 + 修编译错（此步会同时暴露 4.1/4.2，因为编译器全指出来）
  3. 测试 mock 换 StrictContextMock
  4. 行为回归：goldenfile 全绿
  5. 挑一个低价值 workflow 改成图引擎，跑一周
  6. 再批量迁

第 5 步是关键——先迁一个不心疼的，把踩到的坑（JoinNode 部分失败、resume 后 state 丢失）在小范围内交完学费。

最后删掉 1.x 依赖：

go mod tidy
go list -m all | grep 'golang.org/adk'    # 只剩 /v2

高频坑清单（按出现概率排序）#

  1. CI 镜像没升 → requires go >= 1.26.6。见第 1 步。
  2. mock 编译失败 → 不是 bug，是接口统一了。用 StrictContextMock。
  3. NewEvent 里塞 context.Background() → 编译通过、时间戳乱掉、重放测试不稳定。
  4. GOFLAGS=-mod=mod + 内网代理没同步 /v2 → 拉不到包。先 GOPROXY 指到能出网的代理，或 vendor 进来。
  5. go mod tidy 后出现两个 genai 版本 → v2 依赖的 google.golang.org/genai 比 1.x 新；共存期正常，删掉 1.x 后消失。
  6. 期望 adkgo version 能查版本 → 不存在这个子命令，用 go list -m google.golang.org/adk/v2。
  7. 照抄旧专栏的 go install google.golang.org/adk/cmd/adk@latest → 包已不存在。
  8. 并行分支改成图后没设节点 timeout → 一个卡住的外部调用把整个 fan-in 拖死，这是迁移期最常见的线上事故（下一模块细讲）。

常见问题

ADK Go 1.x 和 2.x 能共存吗？

能。模块路径不同（google.golang.org/adk 与 google.golang.org/adk/v2），同一个 go.mod 可以同时依赖两者，因此可以按包灰度迁移，不必一次性改完。

迁移到 ADK Go 2.x 最小要做哪几件事？

四件：Go 工具链升到 1.26.6+；go.mod 依赖换成 google.golang.org/adk/v2；全部 import 加 /v2；修 session.NewEvent 的 ctx 形参与测试 mock 的 agent.Context 接口。

CLI 需要从 adk 换成 adkgo 吗？

1.x 后期就已经是 cmd/adkgo 了，只有更早的 v0.x 时代的 cmd/adk 需要改。注意 adkgo 没有 version 子命令，查版本用 go list -m。

迁移后 Sequential/Parallel/Loop 还能用吗？

包路径 agent/workflowagents/{sequential,parallel,loop}agent 保持不变，但 2.x 里它们构建在新的图引擎之上，编排语义要重新验证；新代码建议直接用 workflowagent + 图。

go fix 能自动完成 ADK 迁移吗？

不能。Go 1.26 重写后的 go fix 只处理语言与标准库 idioms，不知道 ADK 的类型改名。主循环仍然是 gopls + 编译器逐处报错。
