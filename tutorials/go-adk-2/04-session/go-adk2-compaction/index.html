上下文压缩：滑窗与尾保留怎么配，以及召回率实测告诉你的代价

ADK Go v2.4.0 的 session/compaction 深潜：两种策略的触发时机与「常数因子 vs 真正封顶」、60 轮实测的 prompt 长度对照表、召回全有或全无的成因、默认 prompt 的 Durable facts 逐字保留条款（实测 5/10 全丢 vs 9/10 不丢）、把不可丢的事实放进 state 的逃生舱、Config 五字段与 Validate 规则、ErrCompaction 与 decline/failure 之分、尾保留绕过插件管道（脱敏必读），以及 launcher 进程级约束。

September 26, 2026 · 6 min · 1170 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 session/compaction/{compaction.go,llm_summarizer.go}、session/session.go（EventCompaction）、cmd/launcher/launcher.go、样例 examples/compaction、examples/compactionrecall。

session/compaction 是 2.x 独有的包（1.x 没有）。它的包注释是我在 ADK 里见过的最诚实的性能文档——给了实测数字、给了失效条件、还写明了默认值是怎么量出来的。这一篇基本就是把那份注释翻译成人能直接执行的决策。

一句话原理：追加一条摘要事件，而不是删历史#

type EventCompaction struct {
	StartTimestamp   time.Time      // 覆盖范围起点
	EndTimestamp     time.Time      // 覆盖范围终点
	CompactedContent *genai.Content // 摘要正文
	ExcludedEvents   []EventRef     // 被顶替掉的具体事件（{InvocationID, Timestamp}）
}

包注释原文：

A compaction never modifies or deletes history. Summarizing a range of events appends one new session.Event carrying a session.EventCompaction that records the covered timestamp range and the summary content. When the next prompt is built, the raw events inside that range are dropped and the summary is materialized in their place.

三个推论，都直接影响运维：

  1. 数据库不会变小，变的是"组装 prompt 时读哪些"。想真的瘦身得自己归档。
  2. 审计链是完整的（ExcludedEvents 逐条点名），合规场景友好。
  3. 压缩事件必须能原样往返存储——它的 Content 是 nil、没有 delta，按内容判断"要不要存"的后端会静默丢掉它，然后每一轮把同一段重新摘要、重新付钱（这条我写在模块 4 第 1 篇 的存储契约里）。

两种策略：一个降常数，一个真封顶#

滑窗 Sliding window
  触发：一次调用完成后，累计满 CompactionInterval 个"用户发起的调用"
  动作：把这批调用换成一条摘要
  关键：摘要不会被再摘要
  结果：prompt 仍随对话长度增长，只是斜率变小（常数因子）

尾保留 Tail retention
  触发：一次调用内部、模型调用之前，prompt token 数达到 TokenThreshold
  动作：除最近 EventRetentionSize 个事件外全部摘要，且新摘要以旧摘要为种子
  结果：历史 = 一条滚动摘要 + 原始尾巴 → prompt 有上限

要真上限就开尾保留，注释原话：“An agent that needs a genuine ceiling on prompt size should enable it.”

滑窗还有个隐藏作用：它是逐窗排空。CompactionInterval 同时封顶单次覆盖范围，所以在一个已经很长的会话上开启压缩，是"一次一窗"地消化存量，而不是一把梭全摘要。

配错的典型：尾保留根本不触发#

注释点名的失效模式：

Tail retention fires only when more events have accumulated since the last sliding-window compaction than EventRetentionSize holds back. A short interval keeps that number small, and with a large retention size it never reaches it: tail retention never runs, and the prompt grows with the conversation as though it were not configured at all.

60 轮实测（摘要约 500 字符）：

CompactionIntervalEventRetentionSize最终 prompt形态
21013,935 字符仍在增长
3109,147 字符仍在增长
1010543 字符封顶
202495 字符封顶
关闭10543 字符封顶（只开尾保留）

规则一句话：EventRetentionSize 要小于一个压缩周期内产生的事件数。 最后一行更重要：只开尾保留是不用算数的配置，需要上限就先用它。

对照上游样例：examples/compaction/main.go 故意只开滑窗（CompactionInterval: 2, OverlapSize: 1），尾保留注释掉并写明原因——那个 interval 下它不会触发。compactionrecall 的示例命令则给了另一组：-threshold=32000 -retention=10。

代价：召回是「全有或全无」#

这是本篇最需要读三遍的部分。

The loss, when it happens, is not gradual. Each pass either copies a value forward or generalizes it to its label — “the deployment region” in place of “europe-west4” — and a value replaced by its label cannot come back, because the next pass sees only the previous summary and the retained tail. So recall tends to be all or nothing rather than fading.

为什么不是缓慢衰减：尾保留的每一轮只能看到「上一版摘要 + 保留的尾巴」。一个值一旦被写成标签，原文就不在任何输入里了。

所以别看平均值。compactionrecall 的注释专门讲了这个统计陷阱：

a config tends to score 8/8 or 0/8 rather than something in between, and two configs that both average 50% can mean “always half-remembers” and “works perfectly half the time”.

这就是为什么那个样例默认 -runs=3 并逐次打印分数。

默认 prompt 里的 Durable facts 条款#

默认模板（defaultPromptTemplate）有三段 CRITICAL INSTRUCTIONS，逐字摘：

1. Explicitly identify and state the primary language used by the user
   at the top of your summary (e.g., "Conversation Language: English").
2. If the agent called any tools, accurately list the exact tool names
   used to maintain tool grounding.
3. Maintain a section titled "Durable facts" listing every concrete
   detail the user has stated: identifiers, names, dates, numbers, chosen
   options and the reasons given for them. Copy each one verbatim. …
   Never drop or generalize a durable fact to save space; drop narrative instead.

上游是怎么验证这条值得存在的（8 个任意事实，埋在早期轮次，被摘要掉之后再逐条问）：

prompt结果
没有这条逐字保留指令10 次对话里 5 次全丢（8/8 → 0/8）
默认 prompt9 次里一次不丢

⚠️ 两个直接推论：

  • 自定义 PromptTemplate 时把这条抄上，否则你把实测验证过的保护拆掉了；
  • 只要"concise summary"这种措辞就足以重新引入丢失——注释原话：“asking only for a ‘concise’ summary is enough to do the loss”。

逐字保留不是免费的#

Carrying values forward costs summarizer calls, because larger summaries cross TokenThreshold sooner: about twice as many in the same measurement.

摘要变大 → 更早撞 TokenThreshold → 更频繁调摘要模型。同一批实测里，摘要调用次数大约翻倍。

于是有了本篇最有价值的一条设计建议——

逃生舱：不可丢的信息不要走摘要#

Where that matters, or where the detail absolutely cannot be lost, keep it out of the summary altogether. Compaction does not touch session state, and an Instruction referencing state with a {key} placeholder is re-templated on every request, so a value held there reaches the model however many passes have run.

这三句话把模块 4 前两篇串成了一条完整策略：

// 会话里必须长存的具体值：写进 state，用模板回inject
ctx.State().Set("user:deployment_region", "europe-west4")

a, _ := llmagent.New(llmagent.Config{
	Instruction: "部署区域固定为 {user:deployment_region}，所有资源操作以此为准。",
	// …
})
信息类型放哪为什么
必须逐字生效的常量/ID/区域/价格state + {key} 模板压缩不动 state，模板每轮重渲染，永久有效
对话过程、决策理由、未完成任务交给摘要摘要擅长，量也最大
大块文本/文件artifact（{artifact.x} 也是每轮现取）同 state 逻辑，且不占 prompt 常驻

把关键事实留在对话里指望摘要带下去，是把确定性机制交给概率机制。 这是这一篇真正想让你带走的东西。

Config 五字段与 Validate 规则#

type Config struct {
	CompactionInterval int   // 滑窗：几个调用一次；0 关闭；同时封顶单次窗口
	OverlapSize        int   // 滑窗：往回拉几个已压缩调用做衔接
	TokenThreshold     int   // 尾保留：prompt token 阈值；0 关闭
	EventRetentionSize int   // 尾保留：保留最近几个事件原始；与 TokenThreshold 同时必填
	Summarizer         Summarizer // nil → 用根 agent 的模型造 LLMSummarizer
}

三条容易误配的语义，注释都写了：

  1. OverlapSize 的重叠是「重复」不是「共享」：被拉回来的那个调用会被两条摘要各描述一次，模型看到它两遍，prompt 多带约 OverlapSize 个调用的文字。而且事后删不掉（重复已经在摘要散文里了）。默认留 0，除非明显看到窗口之间断了线。
  2. 两个策略都没开 → Validate() 报错（“会白占一个配置步骤且什么都不做”）。要关闭就把整个 Config 留 nil。
  3. TokenThreshold 配了但 EventRetentionSize 是 0 → 报错，错误信息很具体：“a compaction would summarize the whole conversation including the turn being answered”——窗口会一直延伸到最新事件，把模型正要回答的那句话也摘要掉。

Summarizer 为 nil 时 runner 用根 agent 的模型造默认实现，注释因此提醒：根 agent 必须是 LLM agent。纯 workflow 根 + nil Summarizer 是要显式给一个的。

失败与拒绝：两种"没摘要成"#

var ErrCompaction = errors.New("context compaction failed")

Summarizer 接口注释区分了两种返回：

// Returning a result with no content and no error is a decline: this range
// was not summarized, the caller leaves history alone and carries on.
// Returning an error is a failure, which is reported and traced. Reporting
// a failure as a decline makes a summarizer that never succeeds look
// identical to an idle one while the prompt keeps growing on every turn.
type SummarizeResult struct {
	Content *genai.Content                                // nil 表示拒绝
	Usage   *genai.GenerateContentResponseUsageMetadata   // 拒绝/失败时也有意义
}
  • decline 别拿来掩盖 error。自己写 Summarizer 时，把失败上报成拒绝，效果是"看起来闲着、prompt 每轮变大"。
  • Usage 在拒绝和失败时也要填：摘要模型可能花了钱却没产出可用结果，而"永不成功的压缩"是最贵的那种。
  • 调用侧按 ErrCompaction 分流：
for event, err := range r.Run(ctx, uid, sid, content, agent.RunConfig{}) {
	if errors.Is(err, compaction.ErrCompaction) {
		log.Printf("compaction failed: %v", err)   // 记账失败，本轮答案不受影响
		continue
	}
	if err != nil {
		return err
	}
	// 正常处理事件
}

注释的理由：“Compaction is bookkeeping: the events of the turn are already persisted before it runs, so a failure costs a smaller prompt later, not the user’s answer.” 但它仍然要冒出来——永不成功的压缩值得被知道。

⚠️ 尾保留绕过插件管道（脱敏必读）#

Summaries produced by this strategy do not pass through the plugin pipeline. … Tail retention runs inside an invocation and appends directly, so a plugin does not see it. An application relying on a plugin to redact content before it is stored should know these events bypass it, because nothing reports that they did.

拆开说：

滑窗尾保留
运行时机一次调用结束后调用内部、模型调用前
落库路径runner 常规 append直接 append
插件能看到摘要事件吗✅❌

上游还补了一句"这不是我们独有的选择"：adk-python 与 Kotlin 两条路径都不跑插件钩子，Kotlin 是这套设计的参照来源。所以别指望插件挡住压缩内容——脱敏要在进入会话之前做，或者只开滑窗。

LLMSummarizer 的六个旋钮#

type LLMSummarizerConfig struct {
	Model                 model.LLM       // 必填
	PromptTemplate        string          // 必须含 ConversationHistoryPlaceholder；空=内置
	MaxToolContentChars   int             // 默认 2000；负数=不截断
	MaxTranscriptChars    int             // 默认 200_000；负数=不设上限
	Timeout               time.Duration   // 默认 0 = 无超时
	GenerateContentConfig *genai.GenerateContentConfig // SystemInstruction 与 Tools 会被清空
}

四条来自注释的实用判断：

  • MaxToolContentChars 对普通文本一样生效（故意如此）：粘贴的文档和被重新吐成文本的工具结果也计入，否则同样的载荷会因为"落在哪种 part"而成本不同。它按字符数而非字节——中文会话不会被系统性低估。
  • 超 MaxTranscriptChars 时报错，而不是丢最老的轮：因为那些轮次仍在被记为"已覆盖"范围里，丢了就真丢了。代价是这轮 prompt 更大，解法是窗口更小。
  • Timeout 值得设：摘要调用在 run loop 里同步执行，卡住就等于卡住后面那一轮，而"压缩是个优化，放弃它很便宜"。
  • GenerateContentConfig 由 runner 传根 agent 的配置：你为应用设的安全开关和输出上限，也会管住"唯一能看到整份对话记录的那次调用"；不传则静默回落到 provider 默认值。同时 SystemInstruction 和 Tools 被强制清空——摘要器有自己的指令，不能被喂工具。

内置模板"不发布、不是契约"（注释：它是某个默认的措辞，导出后每次改进都变破坏性变更）——所以别在代码里断言 prompt 内容，需要稳定措辞就自带 PromptTemplate。

部署：这是进程级配置#

cmd/launcher 的注释：

This setting is process-wide. One launcher can serve many applications through its agent loader, and they all get this config or none of them do, including the same Summarizer instance and so the same model. If different applications need different compaction, or must not share a summarizer, run them separately.

三条部署结论：

  1. 别指望 per-app 配压缩——需要不同策略就分进程部署。
  2. 一个贵模型的应用会把它用于所有应用（共享实例），成本和合规都得按"整进程"评估。
  3. launcher.Config 有个 Validate()，启动时就把压缩配置验一遍。注释的理由很实在：runner 是按请求构造的，不当场检查就会出现"进程起得来、每个请求都失败、错误信息里没有任何运维能行动的东西"。

自己 runner.New 的应用不受第 2、3 条约束，但要自己调 cfg.Compaction.Validate()。

落地清单#

  • 明确目标：要"更省"还是"有上限"。要上限 → 尾保留（TokenThreshold + EventRetentionSize）
  • 两个都开时核对 EventRetentionSize < 一个周期的事件数，上线后抽查 prompt 长度是否真的平了
  • 不可丢的具体值全部迁到 state + {key} 模板，或 artifact
  • 自定义 PromptTemplate 必须带逐字保留条款，并在 compactionrecall 里跑一遍
  • 设 Timeout；GenerateContentConfig 传根 agent 的
  • 依赖插件做脱敏的话，只开滑窗，或把脱敏前移
  • 调用侧 errors.Is(err, compaction.ErrCompaction) 分流，别让它失败整轮
  • 会话服务后端要过 sessiontestsuite，确认 Compaction 能往返

到这里，模块 4 的三件套齐了：state 放确定事实、platform 给确定性、compaction 管增长。下一篇开始进 2.x 最大的新增面——模块 5：图工作流引擎 。

常见问题

ADK Go 2.x 怎么开上下文压缩？

runner.Config.Compaction = &compaction.Config{...}。整个 Config 留 nil 就是关闭；启用至少一种策略，否则 Config.Validate() 直接报错。

滑窗和尾保留该开哪个？

只要「prompt 有上限」就开尾保留（TokenThreshold + EventRetentionSize），它不需要算数。滑窗只按常数因子缩减、不封顶，单独用适合不想改变摘要结构的场景。

两个一起开要注意什么？

EventRetentionSize 必须小于一个压缩周期内产生的事件数，否则尾保留永远不触发，prompt 长得像没配一样。包注释给的直觉规则就是这一条。

压缩会不会丢早期说过的具体值？

会，而且是「全有或全无」式地丢——每次 pass 要么原样带下去，要么泛化成标签（用「部署区域」代替 europe-west4），一旦泛化就再也回不来。默认 prompt 用 Durable facts 条款压这个风险。

绝对不能丢的信息怎么处理？

别交给摘要。放进 session state，并用 {key} 写进 Instruction：压缩不动 state，模板每次请求重新渲染，所以多少轮之后这个值都还在。

压缩失败会让这轮回答失败吗？

不该。ErrCompaction 标记的是记账失败——本轮事件早已落库，代价只是下一轮 prompt 更大。用 errors.Is 区分后记日志继续。
