事件与 platform：NewEvent(ctx,…) 背后那三个可替换的接缝

ADK Go v2.4.0 的事件模型与 platform 包：Event 内嵌 model.LLMResponse 后的 12 个字段各自谁写谁读、Branch 与 IsolationScope 的两种历史可见性规则、EventActions 七个字段（含框架独占的 Compaction）、NewEvent(ctx,…) 为什么必须交 ctx，以及 platform.Now / NewUUID / RunTasks 三个接缝怎么做确定性重放与并发可控的测试。

September 26, 2026 · 4 min · 789 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 session/session.go（Event、EventActions、RequestInput、NodeInfo、EventCompaction 全部定义在这个文件，没有 session/event.go）、platform/{doc.go,time.go,uuid.go,exec.go}。

模块 0 说过 session.NewEvent 多了个 ctx 参数，很多人以为只是签名变动。它其实是整个 2.x 可测试性的地基：事件的身份证（ID）和心跳（时间戳）从"直接问系统"变成"问 ctx 上装的 provider"。

先看事件到底长什么样#

type Event struct {
	model.LLMResponse          // 内嵌：Content / Partial / UsageMetadata / FinishReason 等

	// Set by storage
	ID        string           `json:"id"`
	Timestamp time.Time        `json:"timestamp"`

	// Set by agent.Context implementation.
	InvocationID   string      `json:"invocationId"`
	Branch         string      `json:"branch,omitempty"`
	IsolationScope string      `json:"isolationScope,omitempty"`
	Author         string      `json:"author"`
	Actions        EventActions `json:"actions"`

	LongRunningToolIDs []string      `json:"longRunningToolIds,omitempty"`
	Routes             []string      `json:"routes,omitempty"`
	RequestedInput     *RequestInput `json:"requestedInput,omitempty"`
	Output             any           `json:"output,omitempty"`
	NodeInfo           *NodeInfo     `json:"nodeInfo,omitempty"`
}

内嵌 model.LLMResponse 这件事影响很大：ev.Content、ev.Partial、ev.UsageMetadata 都是提升字段。所以判断"这条事件是不是模型回复"永远要判空——LLMResponse 是值内嵌，字段全空的"动作事件"（工具响应、状态变更）在类型层看不出来。

按谁写谁读分类，这 12 个字段才好记：

写入方字段读者
存储层ID、Timestamp排序、断点恢复、GetRequest.After
agent.Context 实现InvocationID、Author、Actions、Branch、IsolationScope状态合并、prompt 组装
模型/工具流Content（内嵌）、Partial、LongRunningToolIDs客户端渲染、异步回调
图引擎Routes、RequestedInput、Output、NodeInfoscheduler、UI

Timestamp 由存储写（注释 Set by storage）——NewEvent 虽然会填一个初始值，但落库时以存储为准，别拿本地时钟当事实源。

历史可见性：两套正交机制#

这是 2.x 多 agent 场景最容易配错的地方。

Branch：点分路径，做"平级隔离"

agent_1.agent_2.agent_3     ← agent_1 是 agent_2 的父，以此类推

注释原话：“Branch is used when multiple sub-agent shouldn’t see their peer agents’ conversation history.” 子 agent 沿自己的 branch 读写，兄弟之间互不可见。

IsolationScope：精确匹配，做"作用域私有"

// an event is visible only when event.IsolationScope equals the
// agent's isolation scope (exact match; empty sees only empty)

⚠️ empty sees only empty——没有作用域的 agent 看不到任何带作用域的事件。这意味着动态子 agent（作用域形如 <父路径>/<子名>@<run_id>）产生的事件，父 agent 如果自己是空作用域，就看不见。想让父看见，要么两边同作用域，要么靠节点 Output 显式往外传，而不是指望历史自动汇合。

在工具里读当前值：ctx.Branch()、ctx.IsolationScope()（模块 2 的上下文方法表里已列）。

EventActions：七个字段，一个禁区#

type EventActions struct {
	StateDelta               map[string]any                        `json:"stateDelta"`
	ArtifactDelta            map[string]int64                      `json:"artifactDelta"`
	RequestedToolConfirmations map[string]toolconfirmation.ToolConfirmation `json:"requestedToolConfirmations,omitempty"`
	SkipSummarization        bool                                  `json:"skipSummarization,omitempty"`
	TransferToAgent          string                                `json:"transferToAgent,omitempty"`
	Escalate                 bool                                  `json:"escalate,omitempty"`
	Compaction               *EventCompaction                      `json:"compaction,omitempty"`
}
  • StateDelta / ArtifactDelta：NewEvent 会初始化成非 nil map，可以直接写；裸 Event{} 构造则是 nil map，写就 panic。
  • RequestedToolConfirmations：模块 3 的 HITL 就落在这里，key 是 function call ID。
  • SkipSummarization：只对 function response 事件有效（注释：Only valid for function call response event），置 true 后框架不再叫模型总结工具结果——省一次模型调用的开关。
  • TransferToAgent / Escalate：LLM 驱动的移交与上报，模块 6 展开。
  • Compaction 是框架独占，注释原文：
Setting it from a tool handler or a callback has no effect: it is
cleared wherever caller-supplied actions are copied onto an event.
A record is not a request but an instruction to drop the events it
names and show its own content in their place, which is not a
decision the code running inside a turn gets to make about the
conversation it is running in.

翻译成人话：“能不能删历史"不是本轮代码能决定的事。压缩摘要事件长这样：Compaction != nil、LLMResponse.Content == nil、没有 state/artifact delta——这也是上一篇文章里"存储实现必须让 Compaction 原样往返"的原因。

序列化细节：MarshalJSON 在 StateDelta/ArtifactDelta 为 nil 时省略这两个键。所以你手写的事件 JSON 缺这两个键是合法的，反序列化回来是 nil map（不能直接写）。

图引擎专属字段（模块 5 的伏笔）#

type RequestInput struct {
	InterruptID    string              `json:"interruptId"`      // 恢复时必须回传
	Message        string              `json:"message,omitempty"`
	ResponseSchema *jsonschema.Schema  `json:"responseSchema,omitempty"`
	Payload        any                 `json:"payload,omitempty"`
}

type NodeInfo struct {
	Path            string   // 静态顶层节点为空；动态子节点是 "<父路径>/<子名>@<run_id>"
	MessageAsOutput bool     // 置位且 Output 为 nil 时，读方用事件正文当节点输出
	OutputFor       []string // 这次输出算给哪些节点（委托链共用一份，不重复发）
}

RequestedInput 的注释里有一条硬约束：“At most one event per node activation may carry this field”——一个节点激活最多发一个人机请求事件。scheduler 在事件分发时观察这个字段把节点切到 NodeWaiting，UI 读同一字段渲染输入框。别手搓第二条，恢复语义会错乱。

NodeInfo.Path 用 @run_id 后缀区分同一动态节点的第 N 次运行——这是 dynamic node 重跑后历史不互相污染的关键。

NewEvent 与三个接缝#

func NewEvent(ctx context.Context, invocationID string) *Event {
	return &Event{
		ID:           platform.NewUUID(ctx),
		InvocationID: invocationID,
		Timestamp:    platform.Now(ctx),
		Actions:      EventActions{StateDelta: make(map[string]any), ArtifactDelta: make(map[string]int64)},
	}
}

platform 包的定位（doc.go）：“seams for overriding system operations”。默认用墙钟和随机 UUID。三个接缝形状完全一致——函数类型 + context 装载 + 读取：

type TimeProvider func() time.Time
func WithTimeProvider(ctx context.Context, p TimeProvider) context.Context
func Now(ctx context.Context) time.Time

type UUIDProvider func() string
func WithUUIDProvider(ctx context.Context, p UUIDProvider) context.Context
func NewUUID(ctx context.Context) string

type TaskRunner func(ctx context.Context, tasks []func(context.Context))
func WithTaskRunner(ctx context.Context, runner TaskRunner) context.Context
func RunTasks(ctx context.Context, tasks []func(context.Context))

三点设计意图：

  1. provider 挂在 ctx 上而不是包级变量。doc.go 明说：“Carrying the provider on the context (rather than in a package-level variable) also keeps the provider scoped to a single call tree, which is what makes concurrent runs with independent providers safe.” —— 并行子测试各装各的假时钟，互不串味。
  2. nil provider 会被忽略并回落到默认实现（uuid.go / time.go 的 ok && p != nil 判断），装 nil 不会炸。
  3. RunTasks 自己强制完成屏障：它把每个任务包一层 defer wg.Done() 再交给 runner，wg.Wait() 由 RunTasks 执行。所以注释才敢写：“Callers may therefore read per-task results as soon as RunTasks returns, even if a custom runner does not block until its tasks finish.” 传空/nil slice 直接返回，什么都不做。

recipe：确定性重放测试#

// 固定时钟 + 可预测 ID，事件序列完全确定
base := time.Date(2026, 9, 26, 10, 0, 0, 0, time.UTC)
tick := 0

ctx := platform.WithTimeProvider(context.Background(), func() time.Time {
	tick++
	return base.Add(time.Duration(tick) * time.Second)   // 每次调用前进 1 秒
})
ctx = platform.WithUUIDProvider(ctx, func() string {
	return fmt.Sprintf("evt-%04d", seq.Add(1))
})

ev := session.NewEvent(ctx, "inv-1")   // ID / Timestamp 全部可预期

为什么时间要"每次前进"而不是固定值：事件排序靠 Timestamp，全等的时间戳会让重放顺序不稳定（尤其数据库后端）。测试里给一个单调假时钟，才能同时断言内容与顺序。

把并发也钉死（复现"事件交错"类 bug 时特别有用）：

// 串行 runner：消除 goroutine 调度带来的顺序抖动
ctx = platform.WithTaskRunner(ctx, func(ctx context.Context, tasks []func(context.Context)) {
	for _, t := range tasks {
		t(ctx)          // 一个 goroutine 跑完，顺序与切片一致
	}
})

doc 里点名的三种动机都在：限并发、换成自己的 executor、单 goroutine 顺序执行。

注意：provider 装在根 ctx上，之后所有派生 ctx 都继承。因此"每轮测试装一个新 ctx"是必须的，别装到进程级共享 ctx 上。

遍历事件：三种方式#

sess, err := svc.Get(ctx, &session.GetRequest{AppName: "a", UserID: "u", SessionID: "s"})
if err != nil { … }

// ① range-over-func（推荐）
for ev := range sess.Session.Events().All() {
	if ev.Actions.Compaction != nil { … }   // 压缩摘要事件
}

// ② 索引访问（Events 接口保证保序）
n := sess.Session.Events().Len()
last := sess.Session.Events().At(n - 1)

Events 接口的 All() 注释明确 “preserving their order”，所以按索引取是安全的。判压缩摘要事件用 ev.Actions.Compaction != nil；不要拿 Content == nil 当判据——工具响应等事件的 Content 也可能为空，但它们的 Actions.Compaction 一定是 nil。

常见问题

session.NewEvent 为什么在 v2 要多传一个 ctx？

因为事件的 ID 和时间戳不再直接调 time.Now / 随机 UUID，而是走 platform.NewUUID(ctx) 与 platform.Now(ctx)。ctx 上可以装 provider，从而造出确定性的、可重放的事件。

platform 包有哪几个接缝？

三个：WithTimeProvider(ctx, TimeProvider) + Now(ctx)、WithUUIDProvider(ctx, UUIDProvider) + NewUUID(ctx)、WithTaskRunner(ctx, TaskRunner) + RunTasks(ctx, tasks)。

Branch 和 IsolationScope 有什么区别？

Branch 是点分路径（agent_1.agent_2.agent_3），用于平级子 agent 互相看不到对方历史；IsolationScope 是精确匹配——事件的作用域必须等于 agent 的作用域才进 prompt，空的只看到空的。

能在工具里自己设 Actions.Compaction 吗？

设了也没用。源码注释明确：该字段由框架写、prompt 组装读，调用方提供的 actions 被复制到事件时会被清掉。

自定义 TaskRunner 能异步跑任务吗？

可以。RunTasks 自己用 sync.WaitGroup 强制完成屏障，即使 runner 不阻塞，RunTasks 返回后读各任务结果也是安全的。

并发跑两个测试、各装不同 provider 会串味吗？

不会。provider 显式挂在 context.Context 上（不是包级变量），作用域限在一次调用链内，platform 包注释点明了这点。
