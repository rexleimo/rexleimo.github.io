Session 与 State：三个前缀、一次 delta 合并，和能被测的存储契约

ADK Go v2.4.0 会话层全景：session.Session/State/Events 三个接口的真实签名、app:/user:/temp: 三种状态作用域、StateDelta 如何经 AppendEvent 落库并剥离临时键、指令里的 {var}/{var?}/{artifact.file} 占位符规则、session/database(GORM) 与 vertexai 两套持久化、sessiontestsuite 一致性测试套件，以及 artifact/memory 两个兄弟服务的边界。

September 26, 2026 · 4 min · 752 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 session/{session.go,service.go}（Event、EventActions、RequestInput、NodeInfo、EventCompaction 全在 session.go）、session/database、session/vertexai、session/sessiontestsuite、internal/llminternal/instruction_processor.go、util/instructionutil。

模块 2 里 Runner 的构造参数你已经见过：SessionService、ArtifactService、MemoryService。这一篇把这三样一次讲清，重点在状态作用域和落库契约——2.x 把后者写成了可测试的规范，这是相对 1.x 最实质的进步。

三个接口，签名照抄#

type Session interface {
	ID() string
	AppName() string
	UserID() string
	State() State
	Events() Events
	LastUpdateTime() time.Time
}

type State interface {
	Get(string) (any, error)          // 键不存在 → session.ErrStateKeyNotExist
	Set(string, any) error
	All() iter.Seq2[string, any]      // 2.x：Go 1.23+ range-over-func
}

type Events interface {
	All() iter.Seq[*Event]            // 保序
	Len() int
	At(i int) *Event
}

只读的上下文里拿到的是 ReadonlyState（少一个 Set），所以工具在 agent.Context 上能写、在回调的只读视角里只能读——类型替你把关，不靠自觉。

Get 的失败是哨兵错误，不是 (value, ok)：

v, err := ctx.State().Get("topic")
if errors.Is(err, session.ErrStateKeyNotExist) {
	v = "默认主题"
} else if err != nil {
	return nil, err
}

作用域由键前缀决定#

const (
	KeyPrefixApp  string = "app:"   // 应用级，跨所有用户与会话
	KeyPrefixUser string = "user:"  // 用户级，同 app 内跨会话共享
	KeyPrefixTemp string = "temp:"  // 仅本次调用，结束即丢
)
前缀生命周期典型内容落库
裸键单个会话本轮任务状态、草稿✅
app:整个应用配置、词表、特性开关✅（存 app 维度）
user:单个用户跨会话偏好、语言、地址✅（存 user 维度）
temp:单次调用中间变量、检索结果、鉴权主体❌ 剥离

temp: 是 2.x 里被严重低估的工具。它把"这次调用内部传个值"和"写进持久历史"分开了：

ctx.State().Set("temp:retrieved_docs", docs)   // 下一个工具/回调能读，会话里没有
ctx.State().Set("user:preferred_lang", "zh")   // 下次会话还在

AppendEvent 的接口注释原文：“used to append an event to a session, and remove temporary state keys from the event"——剥离发生在存储层，所以任何实现都必须遵守。

database 后端确实按维度分表存：storageSession / storageEvent / storageAppState / storageUserState（AutoMigrate 迁移的就是这四个），并用 extractStateDeltas 把一个 StateDelta 拆成 app/user/session 三份，读回时 mergeStates 再合成一个视图。你的自定义实现也要有这个语义，否则 app: 键会变成"每个会话一份"的假象。

一次写入的真实路径#

// 工具里
ctx.State().Set("counter", n)     // 立刻可读
// ↓ 框架把这次改动记在事件上
event.Actions.StateDelta["counter"] = n
// ↓ Runner 调 SessionService.AppendEvent(ctx, sess, event)
// 合并进 session state、剥离 temp:、事件入库

三个容易踩的点：

  1. Set 之后当轮立即可见，但持久化发生在事件落库时。如果这轮中途 panic，改动可能没进存储。
  2. NewEvent 已经把两个 map 初始化成非 nil（源码：Actions: EventActions{StateDelta: make(...), ArtifactDelta: make(...)}），所以手写事件时别自己 Event{} 裸构造，否则 StateDelta 是 nil map，写进去就 panic。
  3. StateDelta 是"增量”，不是快照。同 key 后写覆盖前写，跨事件按时间顺序合并。

Instruction 里引用 state：四种写法#

模板解析在 internal/llminternal/instruction_processor.go，正则是 {+[^{}]*}+，规则：

{topic}                 取 state["topic"]，缺键 → 报错
{topic?}                可选：缺键渲染成空串
{user:preferred_lang}   带作用域前缀
{artifact.chart.png}    从 ArtifactService 加载，取 Part.Text

源码里三条值得单独拎出来：

  • 合法名字：isValidStateName 只接受「裸标识符」或「app:/user:/temp: + 标识符」（首字符字母或下划线，其余字母数字下划线）。{my-key}、{a.b}（除 artifact.）原样保留不替换——所以键名请写合法标识符，别用连字符。
  • artifact. 分支会调 ctx.Artifacts().Load(...)，没配 artifact 服务时直接报 artifact service is not initialized。配了 runner.NewInMemory(...) 就不会撞这条。
  • 缺键默认是错误，会让整轮失败。写模板时默认加 ?，除非这个键确实必须有。

自己预渲染也可以（InstructionProvider 之外的一条路）：

// util/instructionutil
text, err := instructionutil.InjectSessionState(ctx, "用户 {user:lang}，主题 {topic?}")

注意公开版的入参是 agent.ReadonlyContext——只读上下文就够，不需要完整 InvocationContext。

llmagent.Config 还有配套的四个入口：Instruction / InstructionProvider / GlobalInstruction / GlobalInstructionProvider。Provider 版收 agent.ReadonlyContext 返回 (string, error)，每轮重新求值，两者都设时 Provider 接管；Global* 由根 agent 提供、对所有子 agent 生效。

⚠️ 源码注释里有一条很容易踩：InstructionProvider 不做 {} 替换，把它当普通字符。也就是说，把模板从 Instruction 搬到 InstructionProvider 的瞬间，所有 {user:lang} 会原样出现在 prompt 里。需要模板就自己调上面的 InjectSessionState；反过来，如果你的指令里本来就有 JSON 例子这种花括号，用 Provider 才是正确选择（Instruction 会试着解析它们，非法名字虽然会原样保留，但合法名字会被意外替掉）。

三套会话服务，和一个一致性套件#

// 1) 内存：session 包里的函数，没有 session/inmemory 子包
svc := session.InMemoryService()

// 2) 关系库（GORM）
svc, err := database.NewSessionService(dialector, opts...)        // 自己开连接
svc, err := database.NewSessionServiceFromDB(existingGormDB)      // 复用连接（v2.4.0 新增）
err = database.AutoMigrate(svc)                                   // 迁移四张表

// 3) Vertex AI 会话库
svc, err := vertexai.NewSessionService(ctx, vertexai.VertexAIServiceConfig{
	ProjectID: "p", Location: "us-central1", ReasoningEngine: "re-id",
})

两个坑：

  • AutoMigrate 靠类型断言到私有实现 *databaseService，传别的 session.Service 会返回 invalid session service type。所以顺序必须「先 New，再 AutoMigrate」，也别把 AutoMigrate 当通用能力——它是数据库后端专用。
  • Vertex 版的事件 ID 由服务端分配，不写回调用方对象。接口注释点名了这个例外：“session/vertexai is one, and it does not assign in place”。依赖 AppendEvent 后立刻读 event.ID 的代码，换后端会拿到空串。

自己实现 session.Service？先跑套件：

// session/sessiontestsuite
func RunServiceTests(t *testing.T, opts SuiteOptions, setup func(t *testing.T) session.Service)
func Snapshot(s session.Session) ExpectedSession

func TestMySessionService(t *testing.T) {
	sessiontestsuite.RunServiceTests(t, sessiontestsuite.SuiteOptions{}, func(t *testing.T) session.Service {
		return newMyService(t)
	})
}

接口注释说得很直白：这两条义务由该套件检查，“so an implementation that misses either goes red there rather than failing quietly in production”。两条义务是：

  1. 没有 ID 的事件必须获得 ID（agent/工具用结构体字面量造的事件不过 NewEvent，没有 ID 就没法被按 ID 引用）；
  2. EventActions.Compaction 必须能原样往返——压缩摘要事件的 LLMResponse.Content 是 nil、也没有 state/artifact delta，按内容决定"要不要存"的后端会静默丢掉它，后果是"那段历史既没被摘要、又花了钱再摘要一遍，每一轮都重犯"。

第三条惯例：未找到时包装哨兵错误，注释给的写法是 fmt.Errorf("%w: …: %w", session.ErrNotFound, err)——用 errors.Is(err, session.ErrNotFound) 判断，别比对字符串。

Get 还有两个限流字段，长会话必用：

resp, err := svc.Get(ctx, &session.GetRequest{
	AppName: "my-app", UserID: "u1", SessionID: "s1",
	NumRecentEvents: 40,          // 只取最近 40 条
	After:           time.Now().Add(-24 * time.Hour),
})

Artifact 与 Memory：边界在哪#

Artifact（artifact.Service）：Save/Load/Delete/List/Versions/GetArtifactVersion，定位键是 AppName + UserID + SessionID + FileName，带 Version int64。

resp, err := artifactSvc.Save(ctx, &artifact.SaveRequest{
	AppName: "my-app", UserID: "u1", SessionID: "s1",
	FileName: "chart.png",
	// genai.Part 的二进制字段是 InlineData *genai.Blob，MIMEType 在 Blob 上
	Part: &genai.Part{InlineData: &genai.Blob{Data: pngBytes, MIMEType: "image/png"}},
})
// 读回来：LoadResponse.Part 是 *genai.Part；文本型 artifact 直接用 .Part.Text
  • 每个请求都带 Validate()，文件名走 validateFileName（挡路径穿越）——自己实现时别跳过；
  • 写入后事件上的 Actions.ArtifactDelta[fileName] = version 由框架维护，这是"哪个事件产出了哪一版"的审计线索；
  • 模型侧有 load_artifacts 工具（tool/loadartifactstool，名字 "load_artifacts"，描述 "Loads the artifacts and adds them to the session."）；
  • 后端：artifact.InMemoryService() 与 artifact/gcsartifact（GCS）。

Memory（memory.Service）只有两个方法：

type Service interface {
	AddSessionToMemory(ctx context.Context, s session.Session) error
	SearchMemory(ctx context.Context, req *memory.SearchRequest) (*memory.SearchResponse, error)
}
// SearchRequest{Query, UserID, AppName} → SearchResponse{Memories []Entry}

语义差别要记牢：session 是"这次对话的全部事实"，memory 是"跨会话的可检索摘要"，而且 memory 是 write-only-by-session（你只能把整个会话喂进去，不能直接塞条目）。两个现成工具：

工具行为适合
load_memory（tool/loadmemorytool）打包成工具让模型自己按 query 检索，并追加使用说明记忆量大、相关性稀疏
preload_memory（tool/preloadmemorytool）每轮请求前用当前用户输入搜一遍，把命中的历史直接注入指令记忆量小、几乎总是相关

两者都实现了 toolinternal.RequestProcessor（ProcessRequest），也都不是长运行工具（IsLongRunning() 返回 false），但机制完全不同：

  • load_memory 用 toolutils.PackTool 把工具本身挂到请求上，再追加一段使用说明——模型自己决定何时查、查什么；
  • preload_memory 不挂工具，直接拿 ctx.UserContent().Parts[0].Text 当作 query 去 ctx.SearchMemory，命中就把记忆文本追加进指令。源码里有三重提前返回：用户内容为空/无 Part/首段无文本 → 跳过；搜索无结果 → 跳过。

⚠️ 因此 preload_memory 只看本轮用户输入的第一个文本 Part：如果用户发的是图片或先一句无意义招呼，这一轮就不会有任何记忆注入。别同时挂两个，等于同一份记忆进两次 prompt。

测试时一行接全：

r, err := runner.NewInMemory("my-app", rootAgent)   // session/artifact/memory 全内存

小结与自检清单#

  • 键名是合法标识符（否则 {} 不替换）；带前缀时只用 app:/user:/temp:
  • 模板里的非必需键都加了 ?
  • 中间变量走 temp:，没有污染持久历史
  • 自定义 session.Service 跑过 sessiontestsuite.RunServiceTests
  • Get 用 NumRecentEvents/After 限流，长会话不全量拉
  • 换后端时确认事件 ID 是否在原地写回（vertexai 不在）

常见问题

ADK Go 2.x 的 state 有几种作用域？

前缀决定：裸键=session 级；app:=应用级（跨所有用户）；user:=用户级（同 app 内跨会话）；temp:=仅本次调用，调用结束即丢弃。常量是 session.KeyPrefixApp/KeyPrefixUser/KeyPrefixTemp。

工具里改了 state 什么时候真正落库？

写进事件的 Actions.StateDelta，由 SessionService.AppendEvent 合并进会话；temp: 前缀的键在 AppendEvent 里被剥离，不落库。

Instruction 里怎么引用 state？

{key}、带作用域的 {user:key}、可选的 {key?}、以及 {artifact.文件名}。非法名字原样保留；缺键默认报错，加 ? 才渲染成空串。

自己实现 session.Service 要注意什么？

两条被一致性套件检查的硬义务：无 ID 的事件必须获得 ID；EventActions.Compaction 必须能原样往返。另外未找到时要包装 session.ErrNotFound。

会话很长，Get 会不会全量拉？

会，除非你限流：GetRequest 有 NumRecentEvents 和 After time.Time 两个字段，按需只取最近 N 条或某时刻之后的事件。

state 和 artifact 怎么分？

小而结构化的判断值放 state；大块二进制/文本（图片、PDF、生成物）放 artifact（按 AppName/UserID/SessionID/FileName 定位，带版本号）。指令模板 {artifact.x} 会自动加载并取 Part.Text。
