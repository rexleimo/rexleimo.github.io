Chat UI 与线层协议：/run、/run_sse、/run_live 三条通路，和 ADK Go 尚未实现的那几块 Dev UI

ADK Go v2.4.0 的 server/adkrest 线层：三个 runtime 端点各自怎么走（POST /run、POST /run_sse 的 SSE 帧格式与 write deadline、GET /run_live 的 WebSocket 帧与硬编 LiveRunConfig）、RunAgentRequest 的严格解码与那个「收了但忽略」的 functionCallEventId、每请求新建 Runner 的含义、DevPrefix=/dev/apps/{app_name} 这个 v2 API 分层、以及 eval / agent builder / tests 三块用 501 明确表态的未实现功能（含为什么不能用 404）。

September 26, 2026 · 8 min · 1611 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 server/adkrest/{adkrest.go,internal/routers/*,internal/models/*,controllers/*}、cmd/launcher/web/{web.go,webui/webui.go}。

模块 2 讲过 launcher，模块 7 第 1 篇讲进程内流。这一篇是线层：前端到底要对接什么。

一、三条 runtime 通路#

server/adkrest/internal/routers/runtime.go 里就三条路由：

路由名方法路径形态
RunAgentPOST/run一次性 JSON，返回 []*session.Event
RunAgentSsePOST/run_ssetext/event-stream，逐事件下发
RunAgentLiveGET/run_liveWebSocket（gorilla/websocket）

请求体（models.RunAgentRequest）：

type RunAgentRequest struct {
	AppName    string        `json:"appName"`
	UserId     string        `json:"userId"`
	SessionId  string        `json:"sessionId"`
	NewMessage genai.Content `json:"newMessage"`
	Streaming  bool          `json:"streaming,omitempty"`
	StateDelta *map[string]any `json:"stateDelta,omitempty"`
	// FunctionCallEventID identifies the event whose function call this
	// request answers (e.g. a human-in-the-loop reply from the web UI).
	// Accepted for adk-python parity but currently ignored; declared so
	// strict decoding (DisallowUnknownFields) does not reject the request.
	FunctionCallEventID *string `json:"functionCallEventId,omitempty"`
}

四个必须知道的解码事实：

  1. appName / userId / sessionId / newMessage 四者非空校验（AssertRunAgentRequestRequired），缺一个直接 400。

  2. 解码用 DisallowUnknownFields() ——多传一个字段整个请求就 400。跨语言对齐时这条最容易翻车，也正是 functionCallEventId 必须声明出来的原因（注释说明它存在只为"严格解码不要把请求拒掉"）。

  3. ⚠️ functionCallEventId 目前被忽略。所以 HITL 回答不能靠这个字段，要把它变成 newMessage 里的 FunctionResponse part：

    newMessage: genai.Content{
    Role: genai.RoleUser,
    Parts: []*genai.Part{{FunctionResponse: &genai.FunctionResponse{
        ID:     "<之前事件里 FunctionCall.ID>",
        Name:   "adk_request_input",       // 或 adk_request_confirmation
        Response: map[string]any{"confirmed": true},
    }}},
}

    ID 对齐是唯一的路由依据（模块 3 的确认流、模块 5 的 adk_request_input 都是"按 ID 派发"这套机制）。

  4. streaming:true 才会开流：getRunner 里就是

    streamingMode := agent.StreamingModeNone
if req.Streaming { streamingMode = agent.StreamingModeSSE }

    顺带一条容易被忽略的：agent.RunConfig 在这里只设了 StreamingMode——SaveInputBlobsAsArtifacts 走 REST 时永远是 false。想把用户上传的图片自动存成 artifact，走 REST 这条路不行，得自己在前后端之间搬一次。

二、SSE 帧的真实形状#

RunSSEHandler 的完整行为（照源码顺序）：

rc := http.NewResponseController(rw)
deadline := time.Now().Add(c.sseTimeout)
rc.SetWriteDeadline(deadline)          // ① 每请求覆盖服务端全局超时
// … 解码、authz.CanActAsUser、validateSessionExists、getRunner 都在设 header 之前

rw.Header().Set("Content-Type", "text/event-stream")
rw.Header().Set("Cache-Control", "no-cache")
rw.Header().Set("Connection", "keep-alive")
rc.Flush()                             // ② 立刻 flush，防客户端掉连接

for event, err := range r.Run(...) {
	if err != nil {
		if errors.Is(err, compaction.ErrCompaction) { log.Printf(…); continue }  // ③
		flashErrorEvent(rc, rw, err)                  // ④
		continue
	}
	if event == nil { continue }
	marshalledData, _ := json.Marshal(models.FromSessionEvent(*event))
	flashEvent(rc, rw, string(marshalledData))        // ⑤ 每事件一次 flush
}
#行为对你的意义
①SSE 有独立写超时（字段 sseTimeout），注释写明是"per request 覆盖 server 全局 timeout"长任务要调的是它：web api 子启动器暴露为 -sse-write-timeout（默认 120s），反向代理那边的 proxy_read_timeout 也要一起放宽
②先校验再设 header，然后马上 flush校验失败还能返回正常 HTTP 状态码；一旦进入 SSE，之后只能靠 event: error 报错
③compaction.ErrCompaction 只记日志，不下发注释理由：“Streaming an error event here would tell a client its answer failed after it has already received it."（模块 4 的"压缩是记账不是对话"在线层的对应）
④错误帧是两行：event: error\n + data: {"error":"…"}\n\n客户端要单独处理 event: error，别把它当普通 data
⑤正常帧是 data: <event JSON>\n\n一次一事件，写完立刻 flush
—marshal 失败 → return（断连）；flashErrorEvent 自身失败 → return已经发给客户端的答案不会被事后改判

事件 JSON 的字段来自 models.FromSessionEvent，注意它把 LLMResponse 的字段拍平到顶层了：

type Event struct {
	ID           string           `json:"id"`
	InvocationID string           `json:"invocationId"`
	Branch       string           `json:"branch,omitempty"`
	Author       string           `json:"author"`
	Partial      bool             `json:"partial,omitempty"`
	LongRunningToolIDs []string   `json:"longRunningToolIds,omitempty"`
	Content      *genai.Content   `json:"content"`
	TurnComplete bool             `json:"turnComplete,omitempty"`
	Interrupted  bool             `json:"interrupted,omitempty"`
	ErrorCode    string           `json:"errorCode,omitempty"`
	ErrorMessage string           `json:"errorMessage,omitempty"`
	FinishReason genai.FinishReason `json:"finishReason,omitempty"`
	ModelVersion string           `json:"modelVersion,omitempty"`
	InputTranscription  *genai.Transcription `json:"inputTranscription,omitempty"`
	OutputTranscription *genai.Transcription `json:"outputTranscription,omitempty"`
	Actions      EventActions     `json:"actions"`
	Output       any              `json:"output,omitempty"`
	NodeInfo     *session.NodeInfo `json:"nodeInfo,omitempty"`
}

这就是前端解析契约。 三条要点：

  • partial / turnComplete（第 1 篇的两个字段）不在嵌套的 llmResponse 里，在顶层；
  • nodeInfo 的 wire key 是 nodeInfo（camelCase），前端写 TS 类型时别按 Go 字段名猜；
  • 图工作流的最终产出在顶层 output，actions.compaction 在 actions 里。

最小可用前端解析（TS）：

const res = await fetch('/run_sse', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ appName, userId, sessionId, streaming: true,
                         newMessage: { role: 'user', parts: [{ text: prompt }] } }),
});
const reader = res.body!.getReader();
const dec = new TextDecoder();
let buf = '';
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  buf += dec.decode(value, { stream: true });
  let i;
  while ((i = buf.indexOf('\n\n')) >= 0) {       // 帧以空行分隔
    const frame = buf.slice(0, i); buf = buf.slice(i + 2);
    let name = 'message', data = '';
    for (const line of frame.split('\n')) {
      if (line.startsWith('event: ')) name = line.slice(7);
      else if (line.startsWith('data: ')) data += line.slice(6);
    }
    if (name === 'error') { showError(JSON.parse(data).error); continue; }
    const ev = JSON.parse(data);
    if (ev.partial) appendToTypewriter(ev.content?.parts?.[0]?.text ?? '');
    else replaceMessage(ev.author, ev.content?.parts?.[0]?.text ?? '');  // 整体替换！
  }
}

⚠️ 别用 EventSource——它只支持 GET、不支持自定义 body。用 fetch + ReadableStream 手解（就是上面这段）。

三、/run_live：WebSocket 帧与一个硬编配置#

q := req.URL.Query()
appName := q.Get("appName"); if appName == "" { appName = q.Get("app_name") }
// userId / sessionId 同样双写兼容

参数走 query，且 camelCase 与 snake_case 都收。 三者缺一 → appName, userId, and sessionId are required（这个错误发生在 Upgrade 之前，所以是普通 HTTP 错误）。

客户端 → 服务端两种帧：

帧类型映射
Binaryagent.LiveRequest{RealtimeInput: &genai.Blob{MIMEType: "audio/pcm;rate=16000", Data: p}}
Text（JSON models.LiveRequest）{content, blob, activityStart, activityEnd, close}
type LiveRequest struct {
	Content       *genai.Content       `json:"content,omitempty"`
	Blob          *blob                `json:"blob,omitempty"`          // {mime_type, data}
	ActivityStart *genai.ActivityStart `json:"activityStart,omitempty"`
	ActivityEnd   *genai.ActivityEnd   `json:"activityEnd,omitempty"`
	Close         bool                 `json:"close,omitempty"`
}

Text 帧的优先级（源码 if-else 链，只认一个）：ActivityStart > ActivityEnd > Blob。close:true 直接 break 读循环。

⚠️ binary 帧的 MIME 是写死的：audio/pcm;rate=16000。想传别的采样率/编码，只能走 text 帧里的 blob.mimeType。

服务端 → 客户端：ws.WriteJSON(models.FromSessionEvent(*event))——和 SSE 同一套事件 schema，所以事件解析代码可以复用。

配置那一行是关键限制：

liveSession, eventIter, err := r.RunLive(req.Context(), userID, sessionID, agent.LiveRunConfig{
	MaxLLMCalls:              100, // Reasonable default
	ResponseModalities:       []genai.Modality{genai.ModalityAudio},
	InputAudioTranscription:  &genai.AudioTranscriptionConfig{},
	OutputAudioTranscription: &genai.AudioTranscriptionConfig{},
})

这四个值是服务端硬编的，客户端传不进来（/run_live 没有 config 参数）。要改音色、SpeechConfig、EnableAffectiveDialog、Proactivity、SaveLiveBlob，只有两条路：自己写 handler 直接调 Runner.RunLive，或者给 adkrest 加自定义 router。

关闭路径也值得抄：sendClose 会 SetReadDeadline(now+1s) 然后把剩余消息读干——WebSocket 的"发完 close 再收客户端 close"握手，自己实现时照这个做才不会 broken pipe。

四、路由分层：/dev/apps/{app_name} 这个前缀#

internal/routers/routers.go 里一个常量，讲了整个 v2 API 的分层史：

// DevPrefix is the path prefix ADK v2 clients use for developer-only
// endpoints: evaluation, tracing, the agent builder and the tests tab.
//
// ADK split its API in two at v2. Production endpoints keep their original
// paths, while everything a developer tool needs moved under
// /dev/apps/{app_name}/. The ADK web UI has addressed these endpoints this way
// since then, so a route reachable only at the pre-v2 path is unreachable from
// the UI.
const DevPrefix = "/dev/apps/{app_name}"

这条对迁移最要命：只注册了 v2 前旧路径（例如 /debug/trace/{event_id}）的后端，Dev UI 打不开链路视图——UI 请求的是 /dev/apps/{app}/debug/trace/session/{sid}。

对照实际路由表（两套都注册了，这是官方做法）：

能力生产路径Dev 路径
会话链路GET /debug/trace/session/{session_id}GET /dev/apps/{app}/debug/trace/session/{session_id}
事件图GET /apps/{a}/users/{u}/sessions/{s}/events/{e}/graphGET /dev/apps/{a}/users/{u}/sessions/{s}/events/{e}/graph
Agent 图GET /dev/apps/{a}/build_graph、/build_graph_image—
应用/会话GET /list-apps、/apps/{a}/users/{u}/sessions[/{s}]（CRUD 全套）—
ArtifactGET/DELETE /apps/{a}/users/{u}/sessions/{s}/artifacts[/{name}[/versions/{v}]]—
版本GET /version—

做 Chat UI 至少要用到：/list-apps 选应用 → POST /apps/{…}/sessions 建会话 → /run_sse 对话 → GET …/artifacts/{name} 拉图/PDF → GET /debug/trace/session/{sid} 排障。

⚠️ 但最后一项有条件：debug 路由只在 -include_debug_api 为 true 时才注册（flag 注释：“will be included in the API if and only if the flag is set to true”）。也就是说Dev UI 的链路视图默认不可用，本地调试要显式开关，生产环境则应该关掉（下一节讲为什么）。

五、明确不做的三块：为什么是 501 不是 404#

controllers/devfeatures.go 的开头注释，是我见过对"未实现"最讲究的处理：

// This file answers the developer-only endpoints that the ADK web UI calls but
// ADK Go does not implement: evaluation, the agent builder, and the tests tab.
//
// They are registered rather than left unrouted on purpose. An unrouted path
// returns a bare 404 that a client cannot distinguish from talking to the wrong
// server or the wrong path prefix, and it hides the fact that the UI expects
// the endpoint at all. Registering them makes the gap explicit, gives each
// response a body a developer can read, and makes the behavior testable.

三档处理方式各不相同，各自有理由：

端点族响应理由
eval 执行 / tests501 Not Implemented + {"error":"<feature> is not implemented in ADK Go","detail":…}“501 tells a client the endpoint is recognised and the feature is missing, which is the difference between ’this server is a different version’ and ’this server cannot do that’.”
GET /dev/apps/{a}/metrics-info200 + {"metricsInfo":[]}“An empty list is the accurate answer and keeps the client from logging a transport error for a question that has a valid empty result.”
GET /dev/apps/{a}/builder（读配置）200 + 空 body（text/plain）“ADK Go agents are defined in Go code, so there is no editable configuration to hand back, and the UI reads an empty body as ’nothing to edit here’ and disables the builder toggle.”

还有一段踩坑记录必须抄下来——它解释了 eval 的 detail 里为什么必须出现 "not installed" 这四个字：

// NotInstalledDetail is the marker the ADK web UI looks for to tell "this
// server cannot run evals" apart from "this eval run failed".
// … An earlier version of this file answered the eval endpoints with 404 instead,
// on the theory that the UI hides its Evals tab on a 404. It does not: the eval
// tab component emits that decision on a shouldShowTab output, and the side
// panel that hosts the component subscribes to four of its outputs but not that
// one. The signal goes nowhere, so 501 is used, consistently with every other
// unimplemented developer endpoint.
const NotInstalledDetail = "not installed"

三条结论：

  1. UI 靠 detail 里的子串 "not installed" 判断"这台服务器不能跑评测”，而不是靠状态码。自写后端如果要接 ADK Web UI，这个短语必须出现在 detail 里。
  2. “404 会隐藏标签"是错的——它解释过为什么改回 501。别照直觉"优化”。
  3. “能答空值的就别报错”（metrics-info、builder）——错误状态会给客户端制造无意义的 transport error 日志。

这套设计值得直接搬进你自己的项目。它比大多数团队"未实现就 404 或 501 二选一"的做法严谨一个量级。

六、webui 子启动器：UI 是嵌进二进制的#

cmd/launcher/web/webui/webui.go：

//go:embed distr/*
var content embed.FS

Web UI 静态资源被编译进你的二进制，作为 web launcher 的一个 SubLauncher 挂载（Keyword() = "webui"）。所以：

go run ./yourapp web api            # 只开 API
go run ./yourapp web api webui      # 同时挂 Dev UI

启动后打印：

printer(fmt.Sprintf("       webui:  you can access API using %s%s", webURL, w.config.pathPrefix))

pathPrefix 是可配的——挂在子路径下时，UI 的前端资源与 API 前缀都要跟着改，别只改 nginx。webui 专门做了这件事：

// rewriteBaseHref points the <base href> of index.html at pathPrefix.
replacement := []byte(`<base href="` + html.EscapeString(pathPrefix) + `"`)

api 子启动器的四个 flag（全部实测自源码 flag 定义）：

flag默认作用
-path_prefix/apiREST API 前缀（registerAPIRoutes 用它挂路由）
-sse-write-timeout120sSSE 写超时
-webui_addresslocalhost:8080CORS 允许的 UI origin（来自主机+端口会被读成 http://；* 表示任意源）
-include_debug_apifalse⚠️ 注释原文：“debug endpoints are not safe to be used in production environment, do not set them to true in production.”

前缀不一致时最容易忘的是 CORS：UI 换域名后如果 -webui_address 没跟着改，/api/run_sse 会被浏览器拦在预检（Access-Control-Allow-Methods 由 corsAllowMethods 从实际路由方法集拼出来）。

顺带对照 api 子启动器（cmd/launcher/web/api/api.go）：它挂的是 adkrest 那套路由。两者是平级子启动器，不是包含关系——想要"UI + API"必须同时写 api webui 两个关键字。

七、每请求一个 Runner，为什么没问题#

func (c *RuntimeAPIController) getRunner(req models.RunAgentRequest) (*runner.Runner, *agent.RunConfig, error) {
	curAgent, err := c.agentLoader.LoadAgent(req.AppName)
	r, err := runner.New(runner.Config{
		AppName: req.AppName, Agent: curAgent,
		SessionService: c.sessionService, MemoryService: c.memoryService,
		ArtifactService: c.artifactService, PluginConfig: c.pluginConfig,
		Compaction: c.eventsCompactionConfig, AutoCreateSession: c.autoCreateSession,
	})
	…
}

两条判断：

  1. 安全：Runner 不持会话状态，状态全在 session.Service 里（模块 4）。模块 5 也确认过 agent 实例可并发服务多会话。
  2. 有成本：每次请求都 LoadAgent + runner.New。agent.NewSingleLoader 无所谓，但如果你用 agent.NewMultiLoader 配了远程 loader、或 agent 构造里有重活（建 MCP 连接、读文件），这条热路径会放大它。高并发场景建议自己包一层缓存 loader。

Compaction 直接透传服务端配置——呼应模块 4 那条"launcher 级 compaction 是进程共享的"。

自检清单#

  • 前端用 fetch + 手解 SSE，不用 EventSource
  • 帧解析按 \n\n 切，处理 event: error 分支
  • partial 累加、非 partial 整体替换（防文字翻倍）
  • HITL 回答走 newMessage 的 FunctionResponse，不依赖 functionCallEventId
  • 请求体不要多传字段（DisallowUnknownFields）
  • sseTimeout 与反向代理读超时一起放宽（web api -sse-write-timeout，默认 120s）
  • UI 换域名后同步 -webui_address（否则 CORS 拦在预检）
  • 生产环境绝不开 -include_debug_api
  • 需要 blob 自动入 artifact 时别走 REST（自己调 Runner 才设得了）
  • dev 类端点两套路径都注册（/dev/apps/{app}/… + 原路径）
  • 自建后端若要接 Dev UI：未实现处给 501 + detail 含 "not installed"，可空答的给 200 空值
  • Live：非 16k PCM 音频走 text 帧的 blob.mimeType；要改 MaxLLMCalls/音色就自己写 handler

常见问题

前端怎么接 ADK Go 的流式回答？

POST /run_sse，请求体 streaming:true，按 SSE 帧解析（data: 一行 JSON，空行结束）。注意浏览器原生 EventSource 只能 GET，所以要用 fetch + ReadableStream 自己解析。

SSE 的错误怎么传给客户端？

多一行 event: error，然后 data: {"error":"…"}。但 compaction.ErrCompaction 例外——它只记日志不下发，因为「已经回答完了再报错误导客户端」。

HITL 怎么回答？

不要用 functionCallEventId——adkrest 明确注释它「为 adk-python 对齐而收，当前忽略」。正确做法是在 newMessage.parts 里放一个 FunctionResponse，ID 对齐之前事件里的 FunctionCall.ID。

Dev UI 的 Evals / Agent Builder / Tests 三个标签为什么报错？

ADK Go 不实现这三块，但故意注册了路由并返回 501 + {error, detail}。用 404 会让客户端分不清「路径不对」和「能力缺失」，UI 也不会隐藏标签。

语音实时怎么做？

GET /run_live?appName=&userId=&sessionId= 升级到 WebSocket。二进制帧自动当 16k PCM 音频；文本帧是 JSON（content/blob/activityStart/activityEnd/close）。配置是服务端硬编的（MaxLLMCalls 100、audio 输出、双向转写）。

为什么每个请求都 new 一个 Runner？

adkrest 的 getRunner 就是每请求 runner.New。Runner 本身无会话状态（状态在 session.Service 里），所以这样是安全的；但热路径上要注意它每次也会重新 LoadAgent。
