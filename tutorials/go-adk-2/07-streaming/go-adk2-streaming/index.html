流式三层：Partial/TurnComplete 的真实语义、聚合器、以及 break 掉的那半个契约

ADK Go v2.4.0 的流式：模型层 GenerateContent(ctx,req,stream bool)、事件层 iter.Seq2、线层 SSE/WebSocket 三者的关系；agent.StreamingMode 只有 none/sse（bidi 藏在内部）；LLMResponse.Partial 那句「Runner 只完整处理最后一个非 partial 事件」意味着什么；streamingResponseAggregator 怎么缓冲文本、拼 thought signature、用 PartialArgs 的 jsonPath 重建工具参数；Event.IsFinalResponse() 的完整判定（含为什么把 compaction 事件排除）；以及 break 提前退出时 compaction 靠 defer 兜底这个隐晦契约。

September 26, 2026 · 9 min · 1767 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 model/llm.go、agent/run_config.go、agent/live.go、internal/agent/runconfig/run_config.go、internal/llminternal/stream_aggregator.go、session/session.go、runner/runner.go。

一、先把三层分清#

很多"流式怎么不生效"的问题，都是把三层混成一层了。

层类型谁负责
模型层model.LLM.GenerateContent(ctx, req, stream bool) iter.Seq2[*model.LLMResponse, error]模型适配器（gemini、openaimodel、apigee、你自己的）
事件层Runner.Run(...) iter.Seq2[*session.Event, error]Runner + flow processors
线层SSE data: {json}\n\n / WebSocket JSON帧server/adkrest（第 2 篇 ）

stream 是 GenerateContent 的第三个参数，不是接口分离。同一个 model.LLM 实现同时承担流式与非流式：

type LLM interface {
	Name() string
	GenerateContent(ctx context.Context, req *LLMRequest, stream bool) iter.Seq2[*LLMResponse, error]
}

二、开关只有一个公开值#

type StreamingMode string

const (
	// StreamingModeSSE enables server-sent events streaming, one-way, where
	// LLM response parts are streamed immediately as they are generated.
	StreamingModeNone StreamingMode = "none"
	StreamingModeSSE  StreamingMode = "sse"
)

type RunConfig struct {
	StreamingMode StreamingMode
	// If true, ADK runner will save each part of the user input that is a blob
	// (e.g., images, files) as an artifact.
	SaveInputBlobsAsArtifacts bool
}

内部版本 internal/agent/runconfig 多一个值和一个字段：

type StreamingMode string
const (
	StreamingModeNone StreamingMode = "none"
	StreamingModeSSE  StreamingMode = "sse"
	StreamingModeBidi StreamingMode = "bidi"   // ← 公开包没有
)
type RunConfig struct {
	StreamingMode StreamingMode
	Live          *agent.LiveRunConfig
}

Runner.Run 唯一的动作是把它塞进 context：

ctx = runconfig.ToContext(ctx, &runconfig.RunConfig{
	StreamingMode: runconfig.StreamingMode(cfg.StreamingMode),
})

然后 LLM flow 读出来决定给 GenerateContent 传 stream=true 还是 false。

三条推论：

  1. StreamingMode 是每次调用的参数，不是 agent 配置。同一个 agent，这一轮流、下一轮不流，完全合法。
  2. bidi 拿不到（Run 的签名只收 agent.RunConfig）。双向流是 RunLive 专属，它内部硬写 StreamingMode: runconfig.StreamingModeBidi, // Live is always bidirectional streaming。
  3. 流式与否不由 launcher 决定：adkrest 是按请求体里的 streaming 字段现算 agent.StreamingModeNone/SSE（第 2 篇展开）。

三、Partial：Runner 只完整处理最后一个#

model.LLMResponse 里这两个字段的注释，是整篇最需要背下来的：

// Partial indicates whether the content is part of a unfinished content stream.
// Only used for streaming mode and when the content is plain text.
// The Runner fully processes only the final non-partial event, partial
// events are simply forwarded downstream (eg. to UI for display).
Partial bool `json:"partial,omitempty"`

// Indicates whether the response from the model is complete.
// Only used for streaming mode.
TurnComplete bool `json:"turnComplete,omitempty"`

拆成三条规则：

规则后果
Partial 只对纯文本有意义工具调用、函数响应不走 partial 语义
Runner 只完整处理最后一个非 partial 事件回调、state delta、工具执行、落库都挂在那个事件上
partial 事件只向下转发别指望在 AfterModelCallbacks 里看到逐字片段

所以正确分工是：

for ev, err := range r.Run(ctx, userID, sessID, msg, agent.RunConfig{StreamingMode: agent.StreamingModeSSE}) {
	if err != nil { return err }
	if ev == nil { continue }

	if ev.Partial {
		ui.AppendText(ev.Content.Parts[0].Text)   // 只喂打字机效果
		continue
	}
	// 非 partial：这是权威版本，落库/计费/解析结构都在这儿
	final = ev
}

⚠️ 同一个字不会既在 partial 里出现又在最终事件里"追加"出现——最终事件带的是完整聚合文本（见下一节）。如果你的 UI 一边累加 partial、一边又用最终事件重绘，必须整体替换而不是追加，否则文字翻倍。这是流式 UI 的头号 bug。

四、聚合器在做什么#

internal/llminternal/stream_aggregator.go 的类型注释：

streamingResponseAggregator aggregates partial streaming responses.
It aggregates content from partial responses, and generates LlmResponses for
individual (partial) model responses, as well as for aggregated content.

状态机字段（照抄，它们就是行为清单）：

usageMetadata     *genai.GenerateContentResponseUsageMetadata
groundingMetadata *genai.GroundingMetadata
citationMetadata  *genai.CitationMetadata
response          *model.LLMResponse

currentThoughtSignature []byte          // Gemini "思考" 签名跨 chunk 保持

sequence             []*genai.Part
currentTextBuffer    string
currentTextIsThought bool
finishReason         genai.FinishReason

currentFunctionName             string
currentFunctionID               string
currentFunctionArgs             map[string]any
currentFunctionThoughtSignature []byte

四条值得注意的行为：

  1. ProcessResponse 可能一次 yield 两个响应——注释：“yields that result, also yielding an aggregated response if the GenerateContentResponse has zero parts or is audio data”。音频/空 chunk 会触发即时聚合，因为音频不能"逐字"渲染。

  2. 文本 buffer + Close() 收尾：Close generates an aggregated response at the end, if needed。流末尾一定会有一份完整文本。

  3. 工具参数是逐段拼的：

    for _, arg := range part.FunctionCall.PartialArgs {
    jsonPath := arg.JsonPath
    value, ok := s.getValueFromPartialArg(arg, jsonPath)
    s.setValueByJSONPath(jsonPath, value)   // 按 "$.a.b[0]" 这类路径写回嵌套 map
}

    模型侧确实能拿到半成品参数（PartialArgs + JsonPath），但聚合器负责拼成完整 Args 再交给工具执行。想在 UI 上显示"正在生成的参数"，你得自己接模型层，别在事件层找。

  4. thoughtSignature 被单独维护（文本的和函数调用的各一份）。Gemini 的"思考"内容跨 chunk 有签名绑定，丢了签名后续请求会报错——自己写模型适配器时这是必修的一课，别只 copy Text。

五、终态判定：IsFinalResponse() 的完整逻辑#

这是消费端最该用、也最容易被自己写错的一个函数。源码全文：

func (e *Event) IsFinalResponse() bool {
	// A compaction event is bookkeeping rather than conversation: it carries a
	// record and no content of its own. It satisfies every clause below, so
	// without this a streaming client deciding what to show a user would surface
	// an empty final response every time compaction ran.
	if e.Actions.Compaction != nil {
		return false
	}
	if e.Actions.SkipSummarization || len(e.LongRunningToolIDs) > 0 {
		return true
	}
	return !hasFunctionCalls(&e.LLMResponse) &&
		!hasFunctionResponses(&e.LLMResponse) &&
		!e.LLMResponse.Partial &&
		!hasTrailingCodeExecutionResult(&e.LLMResponse)
}

四条判据，每条都有坑：

判据含义坑
Actions.Compaction != nil → false压缩事件是记账别把它当"空回答"渲染（注释里就是这个事故）
SkipSummarization 或 LongRunningToolIDs 非空 → true长运行工具/跳过总结也算终态长运行工具（异步/委派）会提前给出终态，此时真正的结果还没来
无 functionCall / functionResponse纯文本才算回答工具轮不算
!Partial只有非 partial 才是终态partial chunk 永不终态 ✓

字段注释还有一句常被忽略的：

Note: when multiple agents participate in one invocation, there could be
multiple events with IsFinalResponse() as True, for each participating agent.

一轮里可能有多个"最终回答"（每个参与的 agent 一个）。所以别写 if ev.IsFinalResponse() { break } 来"拿到答案"——多 agent 场景你会拿到第一个 agent 的回答就走。要结束整轮，用 InvocationID + 你自己的"root agent 终态"判据，或者依赖 yield 返回 false 的自然结束。

六、break 掉流，压缩还在跑吗？#

在跑。这是 runner.Run 里一段专门为流式消费者写的注释，值得整段读：

// Compaction has to happen however iteration ends. Breaking out of the
// range loop on the terminal event is the ordinary streaming idiom, and
// what the A2A executor does, so a hook placed only after the loop
// would never run for those callers and compaction would silently never
// happen. Deferring makes it unconditional.
//
// On an early exit the error cannot be yielded, because yield must not
// be called once it has returned false, so it is logged instead.

三条契约：

  1. 压缩放在 defer 里，就是为了兼容"看到终态就 break"。早退不会丢压缩。
  2. 早退时的错误拿不到——只能进服务端日志。所以 break 之后别假设"没有 error 就没出错"。
  3. yield 返回 false 之后绝对不能再调 yield（Go iter 的硬规则，注释复述了一遍）。自定义 producer 时最容易违反。

七、错误在流里怎么走#

iter.Seq2[*session.Event, error] 的错误和事件共用一个游标：

for ev, err := range stream {
	if err != nil { /* 终止或降级 */ }
	if ev == nil { continue }   // 有 error 时 ev 可能是 nil
}

源码里到处是 if !yield(event, err) { return } 和 yield(nil, err)——这就是"错误算一条流内事件"的实现，不是 panic、不是 channel close 语义。

对照消费：别只用 if ev != nil 判有效数据，先判 err。上一模块（模块 4）讲事件持久化时也提过这条：RangeEvents 的错误处理里就有 err != nil && ev != nil 才 break 的写法。

八、Live：双向流是另一套 API#

func (r *Runner) RunLive(ctx context.Context, userID, sessionID string,
	cfg agent.LiveRunConfig, opts ...RunOption,
) (agent.LiveSession, iter.Seq2[*session.Event, error], error)

type LiveSession interface {
	Send(req LiveRequest) error
	Close() error
}

type LiveRequest struct {
	// RealtimeInput can be *genai.Blob, *genai.ActivityStart, or *genai.ActivityEnd.
	RealtimeInput any
	// Content represents standard text or multimodal content from the user.
	// Can also represent a reply to a tool call if it contains a FunctionResponse part.
	Content *genai.Content
}

注意签名：RunLive 没有 msg 参数——源码注释：// msg is nil for Live run as it's streaming。输入全部走 LiveSession.Send。

LiveRunConfig 十个字段（全部直通 Gemini Live）：

type LiveRunConfig struct {
	ResponseModalities       []genai.Modality
	SpeechConfig             *genai.SpeechConfig
	InputAudioTranscription  *genai.AudioTranscriptionConfig
	OutputAudioTranscription *genai.AudioTranscriptionConfig
	RealtimeInputConfig      *genai.RealtimeInputConfig
	EnableAffectiveDialog    bool
	Proactivity              *genai.ProactivityConfig
	SessionResumption        *genai.SessionResumptionConfig
	SaveLiveBlob             bool
	MaxLLMCalls              int
}

三个值得单独点的：

  • MaxLLMCalls：Live 轮的模型调用上限（防语音死循环）。adkrest 的 /run_live 硬编 MaxLLMCalls: 100, // Reasonable default——用 REST 起 Live 时你改不了这个值，要改就自己组 Runner。
  • SaveLiveBlob：把实时音频 blob 存进 artifact。默认 false，不存就事后无从复盘。
  • SessionResumption + LLMResponse.SessionResumptionHandle：断线重连靠这个 handle 续上会话，而不是重建。

并发语义（模块 6 提过）：LiveSession 是单活动子会话模型。sequentialagent 的实现最能说明问题——它用一个 mutex 保护的 activeSess，任何时刻只有一个子 agent 的 live 会话是活的：

if s.closed { return fmt.Errorf("session is closed") }
if s.activeSess == nil { return fmt.Errorf("no active sub-agent live session") }

所以链式/顺序 live 编排里，切换 agent 时旧子会话已被替换，拿着旧 LiveSession 再 Send 就是这两个错误之一。

能跑 Live 的 agent 也有限制：Sequential/Parallel/Loop 里只有 SequentialAgent 实现了 RunLive（模块 6 第 1 篇），adkrest 会做 liveAgent, ok := ... 断言。

九、base_flow.go 里三条不写在文档里的终态规则#

上面都是"字段说什么"。这三条是"运行时会怎么做"，全部来自 internal/llminternal/base_flow.go，每一条都能解释一类线上奇象。

9.1 final 但没答案：thinking-only 轮会重调模型#

const maxConsecutiveThoughtOnlyTurns = 10

if lastEvent.IsFinalResponse() {
	// A thought-only ("thinking") turn reports as final but has no
	// answer; don't stop on it — call the model again. Give up once
	// the model has produced only thoughts too many times in a row,
	// leaving the last thinking event as the result.
	if !isThoughtOnlyTurn(lastEvent) { return }
	thoughtOnlyTurns++
	if thoughtOnlyTurns >= maxConsecutiveThoughtOnlyTurns { /* 放弃，返回最后一条 thinking */ }
}

含义：IsFinalResponse() == true 不保证有可读答案。 思考型模型（thinking parts 无正文）会先报 final，框架再重调，最多 10 次。所以：

  • 你数"这轮调了几次模型"时，thinking-only 轮是额外消耗，不是 bug；
  • 前端拿到 content 为空/只有 thought 的 final 事件是合法中间态（只有第 10 次放弃时才会真的交给你是终态）；
  • 日志里会看到 produced %d consecutive thought-only turns without an answer (limit %d) —— 看到这行就是模型在空转，该换模型或改提示了。

9.2 流断在 partial 上：这一轮不会进 session 历史#

if lastEvent.LLMResponse.Partial {
	// The last event is a partial streaming response. The realistic cause
	// is a producer that ends a stream without a terminal aggregate (e.g.,
	// an a2a peer whose stream ends on an appended artifact chunk with no
	// terminal status). The turn was truncated, not completed, which is
	// not expected, so we log a warning and return instead of looping again.
	log.Printf("adk: agent %q (invocation %q): step ended on a partial event from %q; the producer did not close its stream with an aggregated final event, so the turn will not appear in session history", …)
	return
}

三个结论：

  1. 框架不重试、不报错，只记 warning 就 return。 所以这种丢轮在 API 层面完全看不出来——只能看日志。
  2. 点名的高发原因：A2A 对端（流结束在一段 artifact chunk 上、没有 terminal status）。模块 9 会再遇到它。
  3. turn will not appear in session history —— 下一轮读历史时这段话根本不存在，用户看起来像"它忘了我刚说的话"。自己写流式 producer（含自定义 model.LLM、自定义 A2A executor）时，必须以一条非 partial 聚合事件收尾。

9.3 工具结果被复制成一份可见文本（但确认类不会）#

// SkipSummarization causes the parent agent loop to terminate on this
// event … without the LLM ever seeing the function response. Since most UIs
// don't render function response parts, attach the result as a visible text
// part so it isn't silently dropped from the terminal event.
//
// This only applies to tools that opt in via
// SkipSummarizationResultDisplayer (agenttool): SkipSummarization is
// also set by tools whose result is an internal detail never meant
// for display - e.g. a pending tool confirmation … or a UI/widget tool's
// acknowledgement - and those must not have their result leaked into
// a visible text part.
if actions := toolCtx.Actions(); actions.SkipSummarization {
	if displayer, ok := curTool.(toolinternal.SkipSummarizationResultDisplayer); ok && displayer.DisplayResultOnSkipSummarization() {
		if text, ok := displayableToolResultText(result); ok {
			parts = append(parts, &genai.Part{Text: text})   // 同一条事件里多一个 text part
		}
	}
}

四条：

事实影响
工具结果事件可能同时带 functionResponse 和 text 两个 part前端按 parts[0] 取内容的写法会偶发取到 functionResponse 而“看不见回答”——要遍历 parts
仅当工具显式 opt-in DisplayResultOnSkipSummarization()（agenttool 就是）普通工具不会多送一份，别本身依赖它
待确认（RequestedToolConfirmations）与 widget 类工具故意不送注释原话：“must not have their result leaked into a visible text part”——这是防泄露，不是漏实现
工具错误从 result["error"] 取（error 或 string 两种都接）工具里 return map[string]any{"error": err} 会被当成工具错误处理，而不是普通结果

另外两个从同一函数里读到的硬事实，顺便记住：

  • 工具结果事件的 Content.Role 是 "user"（不是 "model"）——按 role 过滤消息的 UI 会把工具回显归到用户那边。
  • result == nil 且工具 DefersResponse() 或 IsLongRunning() → 直接 return，不发 functionResponse 事件（模块 6 的 task 委派就靠这个）。
  • ev.Actions.Compaction = nil —— 再次印证模块 4：工具写的 Compaction 会被擦掉。

十、自定义模型怎么支持流式#

写一个 model.LLM 实现时，流式契约全部是你自己的责任：

  1. stream=true 时逐 chunk yield，每 chunk 一个 *LLMResponse；
  2. 中间 chunk 设 Partial: true，最后一个纯文本 chunk 必须 Partial: false 且带完整文本；
  3. 轮次结束设 TurnComplete: true；
  4. 用量/引用/grounding 往最后的响应上挂（聚合器负责累加 usageMetadata）；
  5. 出错就 yield(nil, err)，别 return error 后还继续 yield；
  6. 用 Gemini 的 thought signature 就得原样透传，否则下一轮请求 400。

对照第 1–4 条契约实现；额外注意 9.2 那条硬要求：流必须以非 partial 聚合事件收尾，否则整轮不入历史。

对照参考实现就是 model/gemini 与 model/openaimodel（后者还要处理"OpenAI 没有 thought signature"的差异）。

十一、消费端最小正确实现#

func streamAnswer(ctx context.Context, r *runner.Runner, userID, sessID string, msg *genai.Content) (string, error) {
	var final string
	var sb strings.Builder
	breakSeen := false

	for ev, err := range r.Run(ctx, userID, sessID, msg, agent.RunConfig{
		StreamingMode: agent.StreamingModeSSE,
	}) {
		if err != nil {
			// 流内错误：早退时错误可能已在服务端日志里，这里只能尽力而为
			return "", fmt.Errorf("stream: %w", err)
		}
		if ev == nil {
			continue
		}
		if ev.Partial {
			sb.WriteString(textOf(ev))    // 只累加 partial
			continue
		}
		breakSeen = true
		final = textOf(ev)                // 非 partial：整体替换，不追加
	}
	if final == "" && breakSeen {
		final = sb.String()               // 纯 partial 收尾的兜底
	}
	return final, nil
}

要点全部来自上面几节：partial 累加、非 partial 整体替换、err 先判、ev == nil 跳过、以及不在流里 break（要真停就 return 出这个 range，让 defer 的压缩跑完）。

自检清单#

  • 业务逻辑只挂在非 partial 事件上
  • UI 侧 partial 累加、最终事件整体替换（不追加）
  • 终态判定用 IsFinalResponse()，并接受"一轮多个终态"
  • 压缩事件不作为回答渲染（Actions.Compaction != nil 跳过）
  • 消费循环里 err 先于 ev != nil 判
  • 需要 blob 入 artifact 时设 RunConfig.SaveInputBlobsAsArtifacts
  • Live：SaveLiveBlob 决定是否留音频、MaxLLMCalls 有上限、切换 agent 后丢弃旧 LiveSession
  • 自定义模型满足 partial/turnComplete 六条契约

线层怎么变成前端能消费的 SSE/WebSocket、以及 ADK Web UI 与 Go 后端的真实差距，见 Chat UI 与实时通路 。

常见问题

流式模式下每个 chunk 都会被 Runner 处理吗？

不会。model.LLMResponse.Partial 的注释写明：Runner 只完整处理最后一个非 partial 事件，partial 事件只是向下转发（例如给 UI 显示）。所以业务逻辑要挂在非 partial 事件上，UI 渲染才看 partial。

怎么判断一轮回答结束了？

事件流上看 Event.IsFinalResponse()；线层 JSON 上另有 turnComplete 字段。注意多 agent 参与同一轮时会有多个 IsFinalResponse()==true 的事件（每个参与 agent 一个）。

为什么我的压缩事件在流里看不见？

两层保护：IsFinalResponse() 对 Actions.Compaction != nil 直接返回 false；adkrest 的 SSE 循环把 compaction.ErrCompaction 只记日志不下发。压缩是记账，不是对话内容。

agent.StreamingMode 为什么没有 bidi？

公开常量只有 StreamingModeNone / StreamingModeSSE。bidi 属于内部 runconfig，只有 Runner.RunLive 会强制设成 StreamingModeBidi——双向流是 Live 专属，不能用 Run 开。

工具调用的参数能边生成边看到吗？

模型层可以（PartialArgs + jsonPath 逐段下发），但聚合器会把它们拼成完整 args 再交出去。所以业务侧看到的是完整参数，只有 UI 侧才需要关心半成品。

提前 break 掉事件流安全吗？

安全，但有半个契约：compaction 是在 defer 里跑的，就是为了兼容「看到终态事件就 break」这个常见写法（A2A executor 就这么干）。你自己写消费循环时也别在 break 后继续依赖 yield。
