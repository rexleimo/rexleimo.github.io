`adkgo` CLI：一个只做部署的命令，和它替你生成的 Dockerfile

ADK Go v2.4.0 的 cmd/adkgo 全解：它只有 deploy 一条支路（cloudrun / agentengine 两个目标，靠 blank import 注册）、cloudrun 生成的 Dockerfile 是 distroless + CMD ["/app/exe","web","-port","8080"]（所以入口必须接受 web 子命令）、本地带认证代理 8081 与 a2a_agent_url 的关系、--a2a/--api/--webui/--debug_api/--pubsub/--eventarc 六个开关、agentengine 的源码包上传与 memory bank 三个 flag、以及为什么没有 adk run / adk web / adk eval。

September 26, 2026 · 4 min · 806 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 cmd/adkgo/{adkgo.go,internal/root/root.go,internal/deploy/*}。

一、它真的只有 deploy#

cmd/adkgo/adkgo.go 全文的有效部分：

package main

import (
	_ "google.golang.org/adk/v2/cmd/adkgo/internal/deploy/agentengine"
	_ "google.golang.org/adk/v2/cmd/adkgo/internal/deploy/cloudrun"
	"google.golang.org/adk/v2/cmd/adkgo/internal/root"
)

func main() { root.Execute() }

根命令：

var RootCmd = &cobra.Command{
	Use:   "adkgo",
	Short: "CLI tool for use with ADK-GO",
	Long:  `adkgo is a CLI tool which allows developer to quickly deploy and test an agentic application`,
}

deploy 命令本体：

var DeployCmd = &cobra.Command{
	Use:   "deploy",
	Short: "Makes deployment to various platforms easy",
	RunE: func(cmd *cobra.Command, args []string) error {
		if len(args) == 0 { return cmd.Help() }   // 不给目标就打印帮助
		return nil
	},
}
func init() { root.RootCmd.AddCommand(DeployCmd) }

所以命令树就三层：adkgo → deploy → {cloudrun, agentengine}。 两个目标的注册方式是各自的 init() 里 deploy.DeployCmd.AddCommand(...)，主文件用空导入触发——想加第三个部署目标，写个包 + 加一行 blank import 即可，这是刻意的插件式设计。

三条"没有"必须提前知道（从 1.x 或从 Python 版过来的人一定会问）：

期望现实
adkgo run / adkgo web（本地跑）没有。本地开发是你自己的 main.go + cmd/launcher：go run ./myagent console、... web api webui（模块 2 第 3 篇 ）
adkgo scaffold / new（生成骨架）没有。手工建 module + main.go 即可（模块 1 第 2 篇 ）
adkgo eval（评测）没有，而且 ADK Go 整体没实现评测——adkrest 把 eval 端点注册成 501 并在 detail 里写 "not installed"（模块 7 第 2 篇 ）

⚠️ 根命令的 Long 里写着 “deploy and test"，但没有任何测试/评测子命令——这句描述是过时的，别当契约。

二、安装#

go install google.golang.org/adk/v2/cmd/adkgo@v2.4.0
adkgo deploy --help

cmd/adkgo 是独立 main 包，用 go install <path>@<version> 最干净——不要 go get 进你的项目，它会为了拉 CLI 而把 Cloud Run / Agent Engine 的 SDK 依赖（cloud.google.com/go/clouddeploy、aiplatform 等）拖进你的 go.mod。

两个目标都要求本机有 gcloud 且已认证（--project_name / --region 是共同必填项，源码里默认值都是空串，不给会在部署阶段才失败）。

三、deploy cloudrun：本地编译 + distroless 镜像 + 带认证本地代理#

命令描述（原文）：

Deployment prepares a Dockerfile which is fed with locally compiled server
executable containing Web UI static files.
Service on Cloudrun is created using this information.
Local proxy adding authentication is started.

三件事：① 本地编译一个内含 Web UI 静态文件的 server 可执行文件；② 用它生成 Dockerfile 建服务；③ 起一个加认证的本地代理。

生成的 Dockerfile（源码里就是这几行拼接）#

FROM gcr.io/distroless/static-debian11
COPY <execFile>  /app/<execFile>
EXPOSE <server_port>
CMD ["/app/<execFile>", "web", "-port", "<server_port>"]

四条推论，每条都能省一次部署失败：

  1. distroless/static 里没有 shell、没有 curl、没有 apt。容器内排查只能靠日志，别想着 exec -it /bin/sh。
  2. CMD 带的是 web -port <port>——你的入口必须是能解析 web 子命令的 launcher（universal/web），不是一个自己 ListenAndServe 的裸 server。否则镜像起来就是 unknown command "web"。这是 cloudrun 部署最常见的失败原因。
  3. EXPOSE/server_port 要和 Cloud Run 的实际端口一致：
    adkgo deploy cloudrun --server_port 8080 ...
  4. Web UI 静态资源编译期嵌入（模块 7 讲过 //go:embed distr/*），所以镜像里没有 static/ 目录可挂、也没有可替换的前端文件。

全部 flag（照源码抄，含默认值）#

flag简写默认说明
--project_name-p空GCP 项目
--region-r空GCP 区域
--service_name-s空Cloud Run 服务名
--temp_dir-t空构建临时目录，默认 os.TempDir()（Dockerfile 写在这里）
--entry_point_path-e空入口 main 的路径
--server_port8080云端服务端口
--proxy_port8081本地代理端口
--a2atrue启用 A2A 子路由
--a2a_agent_url-ahttp://127.0.0.1:8081公开 agent card 里对外 advertised 的 URL
--apitrue启用 REST API
--webuitrue启用 Web UI
--debug_apifalse启用 Debug API（需要 --api）
--pubsubfalse挂 PubSub 触发器子路由
--eventarcfalse挂 Eventarc 触发器子路由
--pubsub_max_retries / _base_delay / _max_delay / _max_concurrent_runs3 / 1s / 10s / 100PubSub 触发器重试与并发
--eventarc_max_retries / _base_delay / _max_delay / _max_concurrent_runs同上Eventarc 触发器（两套参数彼此独立）

三个容易看错的点：

  • A2A 默认开（--a2a 默认 true），意味着 api/webui/a2a 三套子路由默认同时挂在同一个 web server 上。不想对外暴露 A2A 要显式 --a2a=false。
  • --a2a_agent_url 的默认值是本地代理地址（127.0.0.1:8081）。这个值会写进公开的 agent card——不改它，别的 agent 拿到的调用地址就是你本机，跨机调用必然失败。部署时它应当是 Cloud Run 的公网 URL。
  • --debug_api 与触发器是两条独立开关，但 debug 端点在 adkrest 侧的原话是 “not safe to be used in production environment”——云端别开。

四、deploy agentengine：源码包上传 + 可原地更新#

Deploys the application to Agent Engine. It creates a source archive, uploads it
to create a Reasoning Engine, and cleans up temporary files.

和 cloudrun 的机制差异是根本性的：cloudrun 是"本地编译产物 + 镜像”，agentengine 是"打包源码上传，由服务端构建 Reasoning Engine"。

flag简写默认说明
--project_name-p空同上
--region-r空同上
--name-s空Agent Engine 名称
--temp_dir-t空临时目录（打包用）
--server_port8080服务端口
--entry_point_path-e空入口 main
--source_dir-d空要归档的目录，默认当前工作目录
--agent_engine_id空给了就是原地更新这个实例，不给则新建
--mem_deployfalse同时部署 memory bank
--mem_modelpublishers/google/models/gemini-2.5-flash记忆生成模型
--mem_ttl8760h（365 天）记忆 TTL

四条实操要点：

  1. 默认打包"当前工作目录"。在 monorepo 根目录跑会把无关内容一起上传——显式给 --source_dir，并确认 .gitignore/构建产物不会撑大归档。
  2. --agent_engine_id 是"更新"的开关。CI 里第一次部署要记下返回的 ID（或先查后传），否则每次跑都新建一个实例。
  3. 构建用的 Go 版本常量是 defaultBuilderGoVersion = "latest"。“latest” 意味着不可复现：某天上游新 Go 版本改了行为，你的部署会跟着变。要稳定就在自己的流水线里显式控制构建环境（这个常量没有对应 flag）。
  4. memory bank 三个 flag 是可选的第二步。--mem_deploy 会连 memory bank 一起建，--mem_model 默认是 gemini-2.5-flash（注意：记忆生成模型和对话模型是两回事，别以为跟着 agent 走）。这也对应模块 4 里 memory.Service 的 Vertex 实现——开了 mem_deploy 才谈得上 load_memory/preload_memory 走托管记忆。

五、部署链路全景#

把这条链画出来，出问题时才知道看哪一段：

你的 main.go（launcher/universal 或 web）
  └─ go build（本地交叉编译，含 //go:embed 的前端静态资源）
       └─ Dockerfile：distroless/static + COPY + CMD ["web","-port","8080"]
            └─ gcloud → Cloud Run 服务
                 └─ 本地 proxy（:8081，加认证）→ 你的浏览器 / Dev UI / agent card

四个断点各查一处：

症状先查
起不来，日志 unknown command "web"入口不是 launcher（第三节推论 2）
服务起来但 UI 空白--webui/--api 是否被关，-port 与 --server_port 是否一致
别的 agent 调不到你的 A2A--a2a_agent_url 还是 127.0.0.1:8081（模块 9 展开 agent card）
触发器 429 后消息丢失--pubsub/--eventarc 没开，或 trigger_max_retries 太小（第 2 篇 ）

六、和 CI 的配合#

adkgo 依赖 gcloud 与本机 Go，因此在 CI 里要注意：

  1. Go 版本按模块 0 第 3 篇 钉死（adk/v2 要求 go 1.26.6+）。CI 用 setup-go 显式指定，别用镜像自带版本。
  2. gcloud auth 走 workload identity，不要把 key 文件写进仓库（模块 0 的隐私边界同样适用于部署）。
  3. cloudrun 会在 CI 机器上做一次真实 go build，所以 CI 的构建缓存（GOCACHE/module cache）会明显影响部署耗时——首次跑几分钟是正常的。
  4. --temp_dir 默认指向系统临时目录。CI 里如果临时目录空间受限（常见于小 runner），显式指到有大容量挂载的路径。

自检清单#

  • 入口是 launcher/universal，能接受 web -port N
  • --project_name / --region / --service_name 三者在脚本里固定，不靠交互
  • --a2a_agent_url 改成公网 URL（或显式 --a2a=false）
  • --debug_api 保持 false
  • agentengine：显式 --source_dir，并记录 --agent_engine_id 以便原地更新
  • 需要事件触发时 --pubsub/--eventarc 与四个重试参数一起配好
  • CI 里 Go 版本钉死、临时目录有空间、gcloud 用 workload identity

常见问题

adkgo 有 run / web / eval 吗？

没有。cmd/adkgo 只注册了 deploy 命令（v2.4.0 源码里 root 下只有 agentengine 与 cloudrun 两个 blank import）。开发/预览用你自己的 main + cmd/launcher 子命令，评测（eval）在 ADK Go 里根本没实现。

为什么要写 go install google.golang.org/adk/v2/cmd/adkgo@v2.4.0 而不是 go get？

它是 cmd/ 下的独立 main 包，用 go install 带版本号安装最干净，不会污染你项目的 go.mod。

cloudrun 部署会构建 Docker 镜像吗？

它先在本地编译出一个内含 Web UI 静态资源的可执行文件，生成一个 FROM gcr.io/distroless/static-debian11 的 Dockerfile，再交给 Cloud Run。镜像里没有 shell，也别指望有 CA 之外的工具。

部署完打不开 UI？

先看 --webui（默认 true）与 --api（默认 true）有没有被显式关掉，再看生成的 CMD 是 "web -port <server_port>"，所以你的入口必须是能解析 web 子命令的 launcher，而不是裸 http.Server。

--debug_api 能开到线上吗？

不建议。flag 描述里就写着需要 --api 才有意义，而 adkrest 侧对 debug 端点的原话是「not safe to be used in production environment」。

Agent Engine 部署和 Cloud Run 部署最大差别？

cloudrun 是「本地编译 + 镜像 + 本地带认证代理」；agentengine 是「打包源码上传，服务端建 Reasoning Engine」，多了 --source_dir / --agent_engine_id（原地更新）和三个 memory bank 开关。
