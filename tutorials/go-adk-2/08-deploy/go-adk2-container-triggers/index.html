容器、会话存储与触发器：一次投递一个会话，429 用尽后交给 Pub/Sub 重投

ADK Go v2.4.0 的事件触发部署面：/apps/{app_name}/trigger/pubsub 与 /trigger/eventarc 两个端点的消息契约（base64 data、attributes 合并、CloudEvents structured vs binary 两种模式）、userID 来自 subscription / event.Source、一次投递一个会话且重试复用同一会话、429 判定靠错误字符串包含、指数退避加一半抖动、用尽后回 500 让上游重投、ErrCompaction 只记日志不 NACK、并发信号量在 Pub/Sub 控制器里没接上这个实现事实，以及触发器表面上压缩为什么几乎无效。

September 26, 2026 · 8 min · 1502 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 server/adkrest/controllers/triggers/{triggers.go,pubsub.go,eventarc.go,config.go}、cmd/launcher/web/triggers/{pubsub,eventarc}、server/adkrest/internal/models/triggers.go。

上一篇 讲的是"怎么把服务推上去"。这一篇讲推上去之后怎么被触发，以及触发器这个表面独有的语义。

一、两个端点，六个开关#

启动方式（adkgo deploy cloudrun 的 flag，或本地 web 子启动器）：

go run ./myagent web api webui pubsub eventarc
# 部署时：adkgo deploy cloudrun --pubsub --eventarc ...

注册出来的路由（两个子启动器都走 SetupSubrouters）：

subrouter.HandleFunc("/apps/{app_name}/trigger/pubsub", controller.PubSubTriggerHandler).Methods(http.MethodPost)
subrouter.HandleFunc("/apps/{app_name}/trigger/eventarc", controller.EventarcTriggerHandler).Methods(http.MethodPost)

都在 {path_prefix} 下，默认 /api（两个子启动器各自的 -path_prefix 默认 /api，且会 TrimSuffix("/")）。所以完整路径是：

POST /api/apps/{app_name}/trigger/pubsub
POST /api/apps/{app_name}/trigger/eventarc

启动后子启动器会打印实际 URL：

printer(fmt.Sprintf("       pubsub:  PubSub trigger endpoint is available at %s%s/apps/{app_name}/trigger/pubsub", webURL, p.config.pathPrefix))

把它复制去填 Eventarc/Pub/Sub 订阅的 push endpoint，别手拼——app_name 是路径参数，靠 appName(r) 从 mux 变量里取；取不到返回 500（“no application name provided”），不是 400。

子启动器层的四个 flag（pubsub 与 eventarc 各有一套同名 flag，互不影响）：

flag默认校验（Parse 里直接返回 error）
-path_prefix/api去尾斜杠
-trigger_max_retries3必须 > 0
-trigger_base_delay1s必须 ≥ 0
-trigger_max_delay10s必须 > 0
-trigger_max_concurrent_runs100必须 > 0

注意 adkgo deploy cloudrun 侧对应的是带前缀的 flag 名（--pubsub_max_retries / --eventarc_base_delay / …，见上一篇），最终落到同一组 TriggerConfig。

二、消息 → agent 输入：不是原文转发#

Pub/Sub push#

type PubSubTriggerRequest struct {
	Message      PubSubMessage `json:"message"`
	Subscription string        `json:"subscription"`
}
type PubSubMessage struct {
	Data        []byte            `json:"data"`  // 注释：This will always be a base64-encoded string.
	MessageID   string            `json:"messageId"`
	PublishTime string            `json:"publishTime"`
	Attributes  map[string]string `json:"attributes,omitempty"`
	OrderingKey string            `json:"orderingKey,omitempty"`
}

Data []byte + JSON = Go 自动 base64 解码，所以 string(req.Message.Data) 拿到的就是原始字节。

内容组装规则（messageContentFromPubSub）：

messageContent := make(map[string]any)
if len(req.Message.Data) > 0       { messageContent["data"] = string(req.Message.Data) }
if len(req.Message.Attributes) > 0 { messageContent["attributes"] = req.Message.Attributes }
if len(messageContent) == 0 { return "", fmt.Errorf("empty message data and attributes") }
agentMessage, _ := json.Marshal(messageContent)

三条后果：

  1. agent 收到的是 JSON 字符串：{"data":"…","attributes":{"k":"v"}}，不是裸 payload。写指令时要预期这层包裹（否则模型会去"解读 JSON"）。
  2. 只有 attributes 没有 data 也合法——事件语义全在 attributes 里时正好用得上。
  3. 两者都空 → 400（“empty message data and attributes”）。Pub/Sub 会按退避策略重投空消息，注意别形成放大。

身份：

userID := req.Subscription
if userID == "" { userID = pubSubDefaultUserID }   // "pubsub-caller"

userID = 订阅名。含义：同一个订阅下的所有消息共用一个 user 维度作用域（user: 前缀的 state、artifact、memory 都归到它）。要按业务主体隔离，别指望这里，得自己在消息里带主体并让 agent 走 app: 之外显式的 key 设计，或者一个租户一个订阅。

Eventarc / CloudEvents#

if contentType == "application/cloudevents+json" {
	// structured mode：整个 body 是 CloudEvent，data 落在 event.Data
	json.NewDecoder(r.Body).Decode(&event)
} else {
	// binary mode：整个 body 就是 data，原样读字节
	bodyBytes, _ := io.ReadAll(r.Body)
	event.Data = bodyBytes
}

然后分岔：

// data 里如果是 Pub/Sub 包装，就拆一层，复用 PubSub 的内容组装逻辑
if err := json.Unmarshal(event.Data, &pubsub); err == nil && (pubsub 有内容) {
	agentMessage, err = messageContentFromPubSub(pubsub)
} else {
	// 否则把整个 CloudEvent 序列化成 JSON 交给 agent
	messageBytes, err := json.Marshal(event)
}

所以 Eventarc 有两种输入形态，且行为不同：

上游你收到的agent 实际看到
Eventarc ← Pub/Sub（最常见）data 是 Pub/Sub 信封拆包后 {"data":…,"attributes":…} —— 和 Pub/Sub 通道一致
Eventarc ← 其他源（Storage、Firestore 等）data 是业务事件体整个 CloudEvent 的 JSON（含 id/source/type/time/data）

models.EventarcTriggerRequest.Data 的类型注释正好点明了这个不确定性：

// In structured mode, ``data`` is always present.
// In binary mode, the entire body is the data (often a Pub/Sub wrapper).
// But sometimes it can be just a JSON object.

结论：给 agent 写指令时要按"输入是一段 JSON、字段结构不固定"来设计，最稳的做法是让 agent 先看 type 字段判断事件种类（整个 CloudEvent 形态下 type 在里面）。

身份：userID := event.Source。来源路径当用户——同一个 bucket/topic 的事件共享 user 作用域，语义和 Pub/Sub 那条一样是"按来源聚合"。

错误码风格与 Pub/Sub 通道略不同：binary 模式读 body 失败 → 500；data 拆 Pub/Sub 失败 → 500；内容取不到 → 400。

三、一次投递一个会话#

这是触发器面最重要的语义，源码注释写得比任何文档都清楚：

// RunAgent runs the agent for the given message and returns the resulting events.
func (r *RetriableRunner) RunAgent(ctx context.Context, appName, userID, messageContent string) ([]*session.Event, error) {
	// One session per delivery. Retries of that delivery reuse it, so a
	// throttled message accumulates invocations rather than starting over.
	sessResp, err := r.sessionService.Create(ctx, &session.CreateRequest{AppName: appName, UserID: userID})
	…
	userMessage := genai.Content{Role: "user", Parts: []*genai.Part{{Text: messageContent}}}
	curAgent, _ := r.agentLoader.LoadAgent(appName)
	runR, _ := runner.New(runner.Config{AppName: appName, Agent: curAgent, SessionService: r.sessionService,
		MemoryService: r.memoryService, ArtifactService: r.artifactService,
		PluginConfig: r.pluginConfig, Compaction: r.eventsCompactionConfig})
	return r.runAgentWithRetry(ctx, runR, sessResp.Session.UserID(), sessResp.Session.ID(), &userMessage)
}

四条推论：

  1. 消息之间没有对话历史。每条投递都是全新会话，{user:…} / {…} 占位符读不到"上一条消息"。想做跨消息记忆，只有两条路：memory.Service（load_memory / preload_memory），或者你自己按业务键复用会话 ID（触发器面不给你这个入口——CreateRequest 没带 State）。
  2. 同一投递的重试共享会话（“accumulates invocations rather than starting over”）。所以限流重试不是幂等的：第二次 attempt 会看到第一次已写入的部分事件历史。副作用要幂等这条要求在触发器上尤其硬。
  3. 消息内容走 Parts: []*genai.Part{{Text: messageContent}}——纯文本 part。Pub/Sub 的 data 里塞二进制不会变成 inlineData，会被当字节转字符串。要传附件：走 artifact，消息里给 URI（模块 4）。
  4. 每次投递都 LoadAgent + runner.New，和 adkrest 一样（模块 7 第 2 篇）。触发器吞吐高时这两步是真实开销，loader 要有缓存。

四、429 的两层重试契约#

// runAgentWithRetry uses exponential backoff with jitter to handle 429 rate-limit errors.
// After MaxRetries is exhausted, raises an error to signal the upstream service (Pub/Sub, Eventarc)
// to retry at a higher level.
for i := 0; i <= r.triggerConfig.MaxRetries; i++ {
	resp := runR.Run(ctx, userID, sessionID, userMessage, agent.RunConfig{StreamingMode: agent.StreamingModeNone})
	isThrottled := false
	for event, err := range resp {
		if err != nil {
			if errors.Is(err, compaction.ErrCompaction) { log.Printf("triggers: %v", err); continue }   // ①
			runErr = err
			if isResourceExhausted(err) { isThrottled = true }
			break
		}
		events = append(events, event)
	}
	if !isThrottled && runErr == nil { return events, nil }          // ②
	if i < r.triggerConfig.MaxRetries && isThrottled {
		time.Sleep(calculateBackoff(i, r.triggerConfig.BaseDelay, r.triggerConfig.MaxDelay))
		runErr = nil                                                 // ③
		continue
	}
	break                                                            // ④
}
return nil, runErr

五个要点：

① 压缩失败不 NACK。 注释理由很硬：

// A compaction failure is bookkeeping, not the delivery. The
// agent has already answered and its events are persisted, so
// failing here would NACK a message that was handled, and on
// Pub/Sub push that means redelivering work already done.

continue（而不是 break）——继续消费事件流，把这轮正常做完。这和模块 7 里 adkrest 的处理方式（只记日志不下发 error 帧）是同一个判断的两次落地。

② StreamingModeNone。 触发器永远不用流式——事件收集进切片，跑完再决定响应码。前端那套 partial 语义在这里不存在。

③ 只有 429/ResourceExhausted 才重试。 判定方式是字符串匹配：

func isResourceExhausted(err error) bool {
	return err != nil && (strings.Contains(err.Error(), "429") || strings.Contains(err.Error(), "ResourceExhausted"))
}

⚠️ 这是脆弱点：错误信息里不带 429/ResourceExhausted 字样的限流错误会被当永久错误（②之后的 break → 直接 500 一次，不做进程内重试）。自己实现 model.LLM 适配器时，限流错误请在这两个词之一上留痕，否则白白丢掉一层退避保护。

④ 非限流错误立即失败（break → return nil, runErr → HTTP 500 → 上游重投）。所以"要不要重试"这件事你只能在上游（订阅的 dead-letter / 重试策略）继续管。

⑤ 退避公式：

backoff := float64(base) * math.Pow(2, float64(attempt))
delay := min(time.Duration(backoff), maxDelay)
jitter := time.Duration(rand.Float64() * float64(delay) * 0.5)
return delay + jitter

默认参数下：1s→2s→4s，各自再加 0～50% 抖动，封顶 10s。注意 jitter 是加在封顶之后的延迟上，所以实际单次等待最坏可到 maxDelay * 1.5（默认 15s）。整条投递最坏阻塞 ≈ 3 + 6 + 12 = 21s 加模型耗时——这个时长必须小于你的订阅 push 超时与容器 --server_port 前面的网关超时，否则上游以为失败、这边还在跑。

响应体统一是：

type TriggerResponse struct {
	Status string `json:"status"`   // 'success' or error message
}

成功 → 200 {"status":"success"}；失败 → {"status":"<错误文本>"} + 对应状态码。别用 HTTP 200 + status 字段判成败，状态码才是权威。

五、并发限制：一条实现事实#

两个控制器都有同样的骨架：

if c.semaphore != nil {
	c.semaphore <- struct{}{}
	defer func() { <-c.semaphore }()
}

但构造时只有一边给了通道：

// eventarc.go
func NewEventarcControllerWithConfig(cfg ControllerConfig) (*EventarcController, error) {
	…
	return &EventarcController{
		runner:    retriable,
		semaphore: make(chan struct{}, cfg.TriggerConfig.MaxConcurrentRuns),   // ✅ 建了
	}, nil
}

// pubsub.go
func NewPubSubControllerWithConfig(cfg ControllerConfig) (*PubSubController, error) {
	retriable := newRetriableRunner(cfg)
	if err := retriable.validateCompaction(); err != nil { return nil, err }
	return &PubSubController{
		runner: retriable,          // ⚠️ semaphore 没赋值
	}, nil
}

我在 v2.4.0 源码里确认：PubSubController.semaphore 没有任何赋值点（只有声明和 nil 检查），所以 -trigger_max_concurrent_runs 对 Pub/Sub 通道实际不起作用；Eventarc 通道起作用。 这条不是设计意图（字段和 guard 都还在，是漏接），但当前行为就是这样，因此：

  • 别指望 --pubsub_max_concurrent_runs 50 真能限住并发；Pub/Sub push 的并发度要去订阅侧的 max_delivery_attempts / ordering / 自建限流上控制；
  • 需要真限流就在容器入口自己加 semaphore（或 golang.org/x/sync/semaphore）包一层 handler；
  • 顺带：MaxConcurrentRuns 若为 0，make(chan struct{}, 0) 是无缓冲通道——写 c.semaphore <- struct{}{} 会阻塞到有人读，等于自锁。子启动器 Parse 里那条 triggerMaxRuns <= 0 的校验正好挡住了这种情况，所以别绕过 launcher 自己构造 TriggerConfig 却忘了校验。

--pubsub_max_concurrent_runs 的 flag 描述 “Maximum concurrent PubSub trigger runs” 与实际行为不符，这是上游待修的缺陷，用之前自己确认一遍你版本的源码。

六、触发器面上压缩几乎无效#

ControllerConfig.Compaction 的注释是这方面最好的一段说明，值得整段读：

// Note what a trigger surface is. A delivery gets a session of its own, so
// history does not accumulate across messages and a sliding window counting
// completed invocations has little to count. Tail retention works normally,
// because it measures the prompt inside a single run.

newRetriableRunner 更进一步，对两种滑窗配置各打一条日志（不拒绝启动）：

你的配置日志内容含义
CompactionInterval == 1“fires on every delivery and writes a summary into a session that is discarded when the delivery ends. Use TokenThreshold and EventRetentionSize to compact within a single run.”白花一次摘要调用，产物没人读
CompactionInterval > 1“a delivery handled in one attempt runs a single invocation, so the window will not reach its interval.”基本不会触发（只有重试过的投递才有多个 invocation）

所以触发器上的正确姿势：

  1. 默认不开压缩（Compaction 留 nil）。一条消息一轮，本来没什么可压的。
  2. 单条消息可能引发很多轮内部调用（复杂 agent、多工具、重试）→ 要控 prompt 就上尾保留：TokenThreshold + EventRetentionSize。它是"量单次运行内的 prompt"，与"跨投递"无关，所以在触发器上工作正常。
  3. 构造时的校验别忘了接：NewXxxControllerWithConfig 会调 validateCompaction()（内部是 compactionvalidate.AgainstAgents，检查压缩配置与 agent 是否兼容）并返回 error；Launcher 侧把它转成启动失败。旧的 NewXxxController（无 WithConfig）把这个 error 丢掉了（c, _ :=）——所以它被 Deprecated 了，注释理由：“which surfaces a configuration error instead of discarding it”，并说明*“candidate for removal at the next major version”*。新代码一律用 WithConfig 版本。

七、会话存储怎么选（容器场景）#

触发器/Web 都要落 session，容器重启不能丢：

方案适用备注
session.InMemoryService()本地开发、单实例 demo重启即丢，多实例互不可见，容器里不要用
session/database（GORM）Cloud Run / 任意容器见模块 4 第 1 篇 ：database.NewSessionService(dialector) + database.AutoMigrate(svc)；AutoMigrate 只认 *databaseService
session/vertexaiVertex AI Reasoning Enginevertexai.NewSessionService(ctx, VertexAIServiceConfig{ProjectID, Location, ReasoningEngine})；事件 ID 由服务端分配，回填不进对象

和模块 8 第 1 篇对上：adkgo deploy cloudrun 走的是你自己 main 里的 launcher 配置——CLI 不会替你的 launcher.Config 指定 session/artifact/memory service。所以部署前确认你的入口不是 NewInMemory：go run ./myagent web api webui pubsub 能跑，但 Cloud Run 上多实例 + 缩容到零会把会话打得稀碎。

launcher.Config 就是服务注入口（字段：SessionService / ArtifactService / MemoryService / AgentLoader / PluginConfig / Compaction / Authenticator / Authorizer）：

import (
	"gorm.io/driver/postgres"
	"gorm.io/gorm"

	"google.golang.org/adk/v2/agent"
	"google.golang.org/adk/v2/cmd/launcher"
	"google.golang.org/adk/v2/cmd/launcher/universal"
	"google.golang.org/adk/v2/cmd/launcher/web"
	"google.golang.org/adk/v2/cmd/launcher/web/api"
	"google.golang.org/adk/v2/cmd/launcher/web/triggers/eventarc"
	"google.golang.org/adk/v2/cmd/launcher/web/triggers/pubsub"
	"google.golang.org/adk/v2/session/database"
)

db, err := gorm.Open(postgres.Open(dsn), &gorm.Config{})
if err != nil { log.Fatal(err) }
sessSvc, err := database.NewSessionServiceFromDB(db)
if err != nil { log.Fatal(err) }

l := universal.NewLauncher(
	web.NewLauncher(
		api.NewLauncher(),            // 必须有：agentLoader/services 靠它进 adkrest
		pubsub.NewLauncher(),         // POST {prefix}/apps/{app}/trigger/pubsub
		eventarc.NewLauncher(),       // POST {prefix}/apps/{app}/trigger/eventarc
	),
)
if err := l.Execute(ctx, &launcher.Config{
	SessionService: sessSvc,
	AgentLoader:    agent.NewSingleLoader(root),
}, os.Args[1:]); err != nil {
	log.Fatalf("run failed: %v\n\n%s", err, l.CommandLineSyntax())
}

三个容易写错的地方（均已在 v2.4.0 编译核实）：

  1. web.NewLauncher(sublaunchers...) 返的是 launcher.SubLauncher，还要套一层 universal.NewLauncher(...) 才是能 Execute 的 launcher.Launcher；直接给 full.NewLauncher() 就省了这件事（它已经包含 console + web，见模块 2 第 3 篇 ）。
  2. 触发器子启动器在 cmd/launcher/web/triggers/{pubsub,eventarc}，不是 cmd/launcher/web/ 直接下面。它们的 Keyword() 分别是 pubsub / eventarc，所以命令行是 ... web pubsub eventarc。
  3. 三个子启动器共用 launcher.Config 里的同一个 SessionService 与同一个 Compaction——上一节那条“触发器上压缩无效果”是全局设置带来的副作用：如果你为了 Web 长会话开了滑窗压缩，每条投递都会多挨一次摘要调用并打出那条日志。要么用尾保留，要么自己拆成两个进端口。

自检清单#

  • 触发端点 URL 从启动日志复制，app_name 已在路径里
  • agent 指令按"输入是 JSON、可能带 attributes/可能是整个 CloudEvent"来写
  • 需要跨消息记忆 → 用 memory.Service，不是靠会话
  • 副作用幂等（同一投递的重试共享会话，历史会累积）
  • 限流错误文本里含 429 或 ResourceExhausted，否则丢退避
  • 进程内退避总时长 < 上游 push 超时与网关超时
  • 不依赖 --pubsub_max_concurrent_runs，Pub/Sub 侧自己限流
  • 用 NewXxxControllerWithConfig，并处理它返回的校验 error
  • 触发器上不开滑窗压缩；需要压 prompt 用 TokenThreshold + EventRetentionSize
  • 容器里 session 用 database 或 vertexai，不是 InMemoryService

常见问题

触发器一条消息会开一个会话吗？

会。RetriableRunner.RunAgent 每次投递都 session.Create 一个新会话，同一投递的重试复用它，所以被限流的消息是累积调用而不是从零开始。跨消息不共享历史。

userID 是谁？

PubSub 用 req.Subscription（空则为 pubsub-caller）；Eventarc 用 event.Source。也就是说同一订阅的所有消息共享同一个 user 维度状态作用域。

消息内容怎么变成 agent 输入？

不是原文。控制器把 data 与 attributes 组成 {"data":"…","attributes":{…}} 再 JSON 序列化，所以模型看到的是一段 JSON 文本，不是裸字符串。

429 怎么处理？

两层：进程内指数退避重试（默认 3 次、基数 1s、上限 10s、再加最多 50% 抖动），用尽或非限流错误就回 500，让 Pub/Sub / Eventarc 自己重投。

触发器要开压缩吗？

基本不要。一次投递只有一个会话、多数投递一次就完成，滑窗没东西可压缩。源码会在 interval==1 和 interval>1 两种配置下各打一条日志提示，并建议改用 TokenThreshold + EventRetentionSize。

MaxConcurrentRuns 生效吗？

Eventarc 生效（构造时建了信号量通道）；但 Pub/Sub 控制器的 WithConfig 构造没有给 semaphore 赋值，handler 里 `if c.semaphore != nil` 永远为假，所以并发限制实际没生效。要限流得自己加。
