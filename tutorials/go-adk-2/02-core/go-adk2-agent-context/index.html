统一上下文 agent.Context：2.x 最重要的一个类型

ADK Go 2.x 把 ToolContext 与 CallbackContext 合并成 agent.Context。本文按 v2.4.0 源码逐方法拆解它的能力面：invocation/agent call/step 三层术语、State/Actions/SearchMemory/RequestConfirmation、Branch 与 IsolationScope 的并行隔离语义、StrictContextMock 测试写法与四个反模式。

September 26, 2026 · 3 min · 638 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 agent/context.go（2026-09-26 原文逐条核对）。

如果 2.x 只允许你记住一个类型，就是它。图引擎、HITL、记忆检索、state 读写、测试写法全部挂在 agent.Context 上。1.x 时代你要在 ToolContext 和 CallbackContext 之间做映射，2.x 之后这件事消失了。

先把术语钉死：invocation / agent call / step#

agent/context.go 开头有一段官方注释，我认为是整个 ADK Go 最值得背下来的模型图：

┌─────────────────────── invocation ──────────────────────────┐
┌──────────── llm_agent_call_1 ────────────┐ ┌─ agent_call_2 ─┐
┌──── step_1 ────────┐ ┌───── step_2 ──────┐
[call_llm] [call_tool] [call_llm] [transfer]

官方定义：

层级起点终点谁负责
invocation一条用户消息最终响应（可含多次 agent call）runner.Run()
agent call一次 agent.Run()该 Run() 返回具体 Agent
step调一次 LLMLLM + 工具都跑完，或有人调了 EndInvocation()LlmAgent 内部循环

两个容易忽略的细节：

  1. invocation 可以包含多个 agent call —— 只要 Agent 请求 transfer 到别的 Agent。也就是说「一次用户提问」和「一次模型调用」不是一回事。
  2. 「对 function response 做总结」算作另一个 step，因为它是一次额外的 LLM 调用。这条直接决定了你的 token 账单怎么解释。

为什么要背这个？因为计费、超时、取消、重试的边界全在这里。NodeConfig.Timeout 约束的是节点单次激活，invocation 的 deadline 来自你传给 Run() 的 ctx，step 是 LLM 调用次数——三层各管一段，搞混了就会出现「我明明设了 5 秒超时，为什么跑了 40 秒」。

Context 的构成：四段能力拼成一个接口#

type Context interface {
	ReadonlyContext      // 只读视图
	InvocationContext    // 本次调用的所有权与控制
	// —— 回调段 ——
	Artifacts() Artifacts
	State() session.State
	// —— 工具段 ——
	FunctionCallID() string
	Actions() *session.EventActions
	SearchMemory(ctx context.Context, query string) (*memory.SearchResponse, error)
	ToolConfirmation() *toolconfirmation.ToolConfirmation
	RequestConfirmation(hint string, payload any) error
	// —— 图节点段 ——
	ResumedInput(interruptID string) (any, bool)
	Path() string
	RunID() string
	SubScheduler() DynamicSubScheduler
	// —— 派生 ——
	WithAgentContext(ctx context.Context) Context
	WithAgentTimeout(timeout time.Duration) (Context, context.CancelFunc)
	WithAgentCancel(...) ...
}

我要用什么注意
读用户这次说了什么UserContent() *genai.Content是本轮起点内容，不是历史
拿会话 / stateSession()、State() session.State写 state 走 State().Set(...)

三个真正要小心的点#

① HITL 的顺序：先查状态，再发请求#

源码注释给的用法是这个形状：

// 工具内部：在做敏感操作之前
if confirmation := ctx.ToolConfirmation(); confirmation == nil {
	// 还没有确认记录 —— 发起确认，本轮不要执行敏感操作
	if err := ctx.RequestConfirmation(
		"转账 5000 元到工商银行尾号 1234，需要您确认",
		map[string]any{"amount": 5000, "to": "****1234"},
	); err != nil {
		return nil, err
	}
	return nil, nil          // 交还给引擎，等用户决定
}
// confirmation != nil 时，再读它的状态决定放行还是拒绝

两个语义陷阱：

  • RequestConfirmation 返回 nil 只表示「确认请求已成功排队」，不表示用户批准。 官方注释特意强调这点。工具的这次执行会挂起，等用户回应后才继续。
  • 确认请求会让框架发一个特殊事件（例如 adk_request_confirmation 这样的 FunctionCall）给客户端/UI。没有 UI 的 headless 场景必须自己接这个事件，否则表现为「Agent 卡住不动」。

② Branch() 与 IsolationScope()：并行子 Agent 的隔离靠它们#

源码注释：

  • Branch() —— 形如 agent_1.agent_2.agent_3 的层级路径，agent_1 是 agent_2 的父。用途是「多个并行子 Agent 不应该看到彼此的会话历史」，主要服务于 parallel agent（它们并发跑）。
  • IsolationScope() —— 一旦设置，Agent 的提示历史里只包含 IsolationScope 精确匹配的事件；空值表示不设作用域。

工程后果很直接：并行分支里如果没管好 Branch/IsolationScope，你会看到 A 分支把 B 分支的中间结论当事实继续推理。 这类 bug 表现为「答案偶尔串台」，极难复现。模块 5 讲 JoinNode 时会用一个真实拓扑演示。

③ WithContext 是临时的，别依赖它#

InvocationContext 上有这条注释（原文照抄）：

// WithContext returns a new instance of the context with overridden embedded context.
// NOTE: This is a temporary solution and will be removed later. The proper solution
// we plan is to stop embedding go context in adk context types and split it.
WithContext(ctx context.Context) InvocationContext

官方计划是不再把 context.Context 内嵌进 ADK 上下文类型，而是拆开。所以：

  • 需要「换底层 ctx」的场景（注入 provider、加超时）优先用 WithAgentTimeout / WithAgentCancel；
  • 不要在库函数之间到处传 WithContext(...)，它大概率在某个 v2.x 里被移除（这是 API 稳定性风险，不是现在就坏）；
  • 也别把 agent.Context 存进 struct 长期持有 —— 它是每次激活的句柄，跨 invocation 复用必然出错。

测试：StrictContextMock 是唯一正确姿势#

接口这么大，手写 fake 是自我折磨，而且会随接口扩张反复崩。正确做法：

type fakeContext struct {
	agent.StrictContextMock
	actions *session.EventActions
}

func (f *fakeContext) Actions() *session.EventActions { return f.actions }

var _ agent.Context = (*fakeContext)(nil)   // 编译期对统一接口断言

func TestTransferToolWritesState(t *testing.T) {
	sd := map[string]any{"confirmed": true}
	ctx := &fakeContext{
		StrictContextMock: agent.StrictContextMock{Ctx: t.Context()},
		actions:           &session.EventActions{StateDelta: sd},   // 注意字段名是 StateDelta
	}
	if err := myTool(ctx, payload); err != nil {
		t.Fatalf("tool failed: %v", err)
	}
}

为什么这样写，两个理由（都是官方迁移文档明说的）：

  1. 前向兼容：StrictContextMock 实现了完整的统一上下文方法集，以后接口再加方法，你的 fake 不用动。
  2. 失败要响：未覆盖的方法直接 panic "not implemented"。手写 mock 返回零值会让测试「以错误的方式通过」——这是框架快速演进期最阴的一种假绿。

agent.StrictContextMock{Ctx: ...} 里标准 context.Context 的四个方法（Deadline/Done/Err/Value）从 Ctx 读，不 panic。

反模式后果正确做法
在链路中间 context.Background()丢掉 platform provider（时间/UUID）与 trace，重放测试不稳定一路透传手里的 ctx
把 agent.Context 存进全局变量或 struct 字段跨 invocation 复用同一句柄，state/事件错乱只在函数生命周期内使用

常见问题

ADK Go 2.x 的 agent.Context 是什么？

它是传给回调和工具的唯一上下文类型，由 1.x 的 ToolContext 与 CallbackContext 合并而来，同时内嵌 context.Context，提供会话/state 读写、事件动作、记忆检索、HITL 确认和图节点运行时信息。

为什么 2.x 要合并 ToolContext 和 CallbackContext？

因为回调和工具经常需要同样的能力（读 state、改 event actions、请求用户确认）。分裂时同一个逻辑要在两套接口里写两遍，测试还要两套 mock。

测试里怎么处理 agent.Context？

内嵌 agent.StrictContextMock，只覆盖用例真正会调的方法，并断言 var _ agent.Context = (*fakeContext)(nil)。未覆盖的方法会 panic，脏调用当场暴露。

Branch 和 IsolationScope 有什么区别？

Branch 是形如 agent_1.agent_2.agent_3 的层级路径，用于并行子 Agent 之间互相看不到会话历史；IsolationScope 是精确匹配的事件作用域，只有 scope 完全相等的事件才会进入模型提示历史，空值表示不设作用域。

能在 agent.Context 上直接调用 context 的方法吗？

能，它内嵌了 context.Context，所以 Deadline/Done/Err/Value 都有；节点函数、工具函数收到的 ctx agent.Context 可以直接当 context.Context 往下传。
