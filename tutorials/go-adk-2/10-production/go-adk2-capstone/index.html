综合实战：把十个模块缝成一个可上线的图文情报 agent

ADK Go v2.4.0 端到端落地：一个"抓取→分析→人工核准"的流水线 agent，用 workflowagent + Chain 建图、FunctionNode 做确定性抓取、AgentNode 挂 llmagent、DynamicNode + ResumeOrRequestInput 做 HITL、RetryConfig 做退避、OutputKey 传简报、postgres session service 做持久化、loggingplugin + retryandreflect 做横切、telemetry.New 做可观测、universal.NewLauncher + authn.NewIdentityAwareProxy + authz.NewStrict 上 Web 表面、adkgo deploy cloudrun 发布。全部代码经 go build 与 go vet 验证。

September 26, 2026 · 7 min · 1330 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0 + Go 1.26.8。本篇所有 Go 代码都实际通过 go build ./... 与 go vet ./...（零错误零告警），这也是模块 0 立下的承诺。

这一篇不讲新 API，只做一件事：把前十个模块的决策落到一个程序里，并解释每个位置为什么长这样。目标形态：

抓取(确定性) → 分析(模型) → 人工核准(HITL)
     ↓ RetryConfig 退避      ↓ ResumeOrRequestInput
  postgres 会话持久化  ←  OutputKey 传简报
     ↓
 loggingplugin + retryandreflect 横切  +  telemetry 导出
     ↓
 universal.NewLauncher(api + webui) + IAP 认证 + Strict 授权
     ↓
 adkgo deploy cloudrun

一、go.mod 与依赖（模块 1）#

module intel

go 1.26.0

require (
	github.com/google/jsonschema-go v0.4.3
	google.golang.org/adk/v2 v2.4.0
	google.golang.org/genai v1.35.0
	gorm.io/driver/postgres v1.6.3
	gorm.io/gorm v1.31.2
)

/v2 是硬要求（模块 0）。jsonschema-go 出现在这里是因为下面的 HITL 响应 schema。

二、业务类型：图的边就是这些类型的流动（模块 5）#

type Raw struct {
	Sources []string `json:"sources"`
	Items   []string `json:"items"`
}

type gateIn struct {
	Summary string `json:"summary"`
}

type Approved struct {
	Approved bool   `json:"approved"`
	Note     string `json:"note,omitempty"`
}

为什么 gateIn 只有 Summary 一个字段：analyzer 用 OutputKey: "brief/summary" 把结果写进 state（模块 4），下游 human_gate 的输入由引擎按 schema 从 state 组装。声明小 schema 是给模型的约束面，也是给读者的契约（模块 6 第 2 篇）。

三、确定性节点：抓取不交给模型（模块 5 第一原则）#

func fetchFeeds(ctx agent.Context, in Raw) (Raw, error) {
	in.Items = append(in.Items, in.Sources...)
	return in, nil
}

fetchNode := workflow.NewFunctionNode[Raw, Raw]("fetch", fetchFeeds, workflow.NodeConfig{
	RetryConfig: &workflow.RetryConfig{MaxAttempts: 3, InitialDelay: time.Second},
})

三个决策：

决策理由
NewFunctionNode（不是 tool + llmagent）抓取必须发生，不需要模型判断"要不要抓"。模块 5：确定的步骤用节点
泛型参数 [Raw, Raw]输入输出类型直接写进函数签名，引擎据此推 schema
RetryConfig{MaxAttempts: 3, InitialDelay: 1s}字段名是 MaxAttempts（含首次执行），不是 MaxRetries——模块 5 第 4 篇的坑。默认还有 BackoffFactor/Jitter/MaxDelay/ShouldRetry 可调

顺带保留一个 functiontool，给将来"让模型自己决定抓哪个源"留口：

pullTool, err := functiontool.New(functiontool.Config{
	Name: "pull_feeds", Description: "按源拉取原始条目",
}, func(c agent.Context, in Raw) (Raw, error) { return fetchFeeds(c, in) })
if err != nil {
	return nil, fmt.Errorf("tool: %w", err)
}

functiontool.New 返回 error（模块 3），所以这里必须处理。

四、模型节点：只让模型做那一件不确定的事（模块 2 + 6）#

m, err := gemini.NewModel(ctx, "gemini-flash-latest", nil)
// …
analyzer, err := llmagent.New(llmagent.Config{
	Name: "analyzer", Model: m,
	Description: "从原始条目提炼结论与风险",
	OutputKey:   "brief/summary",
})
// …
analyzeNode, err := workflow.NewAgentNode(analyzer, workflow.NodeConfig{
	RetryConfig: &workflow.RetryConfig{MaxAttempts: 2},
})

四条：

  1. gemini.NewModel(ctx, name, cfg) 是 v2 的构造函数（模块 0：agents.NewLlm 没了），返回 (model.LLM, error)。
  2. Name 就是模型可见的工具名（模块 6 第 2 篇），所以 analyzer 这个名字要按"给模型读的标识符"来起。
  3. Description 是工具描述——写"从原始条目提炼结论与风险"而不是"分析"，因为它同时是给模型的调用时机提示。
  4. OutputKey: "brief/summary"：模块 4 讲的"agent 结果落 state 的标准做法"。状态键用 前缀/名 的层级写法，多 agent 协作时避免撞名。

⚠️ llmagent.Config 里我故意没写 Mode —— 模块 6 第 2 篇的 IncludeContents 那条不对称（作为单轮节点时 unset 与显式 IncludeContentsDefault 行为不同）在这里就是活教材：作为图节点的 agent，你要么明确写 Mode: llmagent.ModeSingleTurn，要么清楚 unset 时它只看到当前轮。这里依赖 InputSchema 驱动的结构化输入，unset 是可接受的，但要写下注释。

五、HITL 节点：一行式暂停（模块 5 第 5 篇）#

func approvalSchema() *jsonschema.Schema {
	s, err := jsonschema.For[Approved](nil)
	if err != nil {
		panic(err) // 静态类型，启动期即失败
	}
	return s
}

func humanGate(ctx agent.Context, in gateIn, emit func(*session.Event) error) (Approved, error) {
	var out Approved
	val, err := workflow.ResumeOrRequestInput(ctx, emit, session.RequestInput{
		Message:        "批准这份简报发布？",
		ResponseSchema: approvalSchema(),
		Payload:        map[string]any{"summary": in.Summary},
	})
	if err != nil {
		return out, err // ErrNodeInterrupted 或 emit 失败
	}
	raw, _ := json.Marshal(val)
	_ = json.Unmarshal(raw, &out)
	return out, nil
}

gateNode := workflow.NewDynamicNode[gateIn, Approved]("human_gate", humanGate, workflow.NodeConfig{})

逐条说明为什么这样写：

  1. InterruptID 留空。RequestInput.InterruptID 的注释：“leave it empty and the engine fills in a fresh UUID (the recommended default)"，并且明确警告：Dev UI 按 ID 记账，同一个会话里复用固定字面量会导致后面不再弹输入框。手抄一个 "approval" 常量就是这个 bug。

  2. ResponseSchema 用 jsonschema.For[Approved](nil) 从 Go 类型推导，与 Approved 结构体同源——手写 JSON Schema 早晚和代码漂移。

  3. Payload 把待批准的简报正文带过去，UI 才能"看着内容决定批不批”。

  4. ResumeOrRequestInput 展开后就是模块 5 第 5 篇那三段样板：

    func ResumeOrRequestInput(ctx agent.Context, emit func(*session.Event) error, req session.RequestInput) (any, error) {
	if reply, ok := ctx.ResumedInput(req.InterruptID); ok {
		return reply, nil
	}
	if err := emit(NewRequestInputEvent(ctx, req)); err != nil {
		return nil, err
	}
	return nil, ErrNodeInterrupted
}

    返回类型是 any（不是你的结构体），所以这里用 json.Marshal + Unmarshal 落到 Approved。为什么不用类型断言：resume payload 从 session 事件反序列化而来，运行期是 map[string]any——直接断言 *Approved 必然 panic。这段"二次编解码"看着笨，但它是跨事件边界的唯一稳当转换。

  5. err != nil 直接返回：ErrNodeInterrupted 必须原样冒泡，scheduler 靠它把节点转成 NodeWaiting（模块 5）。在这里把它包成别的 error 会让整轮 finalize，人就不会被问第二次。

panic 在 approvalSchema 里是可接受的：输入是静态类型，失败只可能是编程错误，让它启动即崩比运行期返回一个含糊 error 好。

六、建图：workflowagent 而不是手写 Workflow（模块 5 + 6）#

return workflowagent.New(workflowagent.Config{
	Name:        "intel",
	Description: "每日情报简报：抓取→分析→人工核准",
	SubAgents:   []agent.Agent{analyzer},
	Edges: workflow.Chain(
		workflow.Start,
		fetchNode,
		analyzeNode,
		gateNode,
	),
})

四个选择：

  1. 用 workflowagent.New 而不是 workflow.New(...) 自己跑：因为要自动 resume。模块 5 第 5 篇讲过，workflowagent 外层 wrapper 检查 ctx.UserContent() 里是否有与已发出 InterruptID 匹配的 FunctionResponse，据此分派 Run vs Resume。手写 wf.Resume 只在你直接驱动 *workflow.Workflow 时才需要。
  2. Config 只有六个字段（Name/Description/SubAgents/Before…/After…/Edges），没有 MaxConcurrency、没有 StateSchema——需要那些就下潜 workflow.New（模块 6 第 1 篇）。
  3. SubAgents: []agent.Agent{analyzer}：让 Dev UI 与 agent graph 端点能看见它（模块 6），也便于将来加 transfer_to_agent。注意 analyzer 同时是图节点和 sub-agent ——这是允许的，两条到达路径不同（图按边驱动 vs 模型按名字转交）。
  4. workflow.Chain 返回 []Edge，正好是 Edges 的类型——所以 Chain 是"线性默认"的语法糖，加路由只需往这个切片里再塞 workflow.NewConditionalEdge(...)（模块 5 第 3 篇）。

七、持久化与可观测（模块 4 + 8 + 10）#

providers, err := telemetry.New(ctx, telemetry.WithOtelToCloud(false))
providers.SetGlobalOtelProviders()

db, err := gorm.Open(postgres.Open(os.Getenv("DATABASE_URL")), &gorm.Config{})
sessSvc, err := database.NewSessionServiceFromDB(db)

logP := loggingplugin.MustNew("intel_audit")
retryP, err := retryandreflect.New(
	retryandreflect.WithMaxRetries(2),
	retryandreflect.WithTrackingScope(retryandreflect.Invocation),
)
plugins := []*plugin.Plugin{logP, retryP}
defer func() {
	for _, p := range plugins {
		if cerr := p.Close(); cerr != nil {
			log.Printf("close plugin %s: %v", p.Name(), cerr)
		}
	}
}()

四条决策：

决策理由出处
WithOtelToCloud(false)，只走自建 collector数据不出自己 VPC；GCP trace 需要显式开，且 GCP logs exporter v2.4.0 未实现模块 10 第 2 篇 §5
database.NewSessionServiceFromDB(db) 而非 session.NewInMemoryHITL 会话要跨进程恢复——图状态在 session 事件里（ReconstructRunState），内存存储重启即丢模块 4 + 模块 5 第 5 篇
loggingplugin.MustNew("intel_audit") 带唯一名同名注册会让 runner.New 直接失败模块 10 第 2 篇 §2
retryandreflect 用 Invocation scopeGlobal 的计数器跨用户共享，多租户下一个租户刷失败会耗尽所有人的重试额度模块 10 第 2 篇 §3

⚠️ plugins 自己 defer Close()：v2.4.0 的库没有任何非测试路径调用 PluginManager.Close()，runner.PluginConfig.CloseTimeout 也是"赋值但从未被读"。这是本篇最需要独立验证的一条事实。

八、两种运行形态（模块 8）#

if os.Getenv("INTEL_RUN_ONCE") == "1" {
	runOnce(ctx, root, sessSvc)
	return
}

l := universal.NewLauncher(
	web.NewLauncher(api.NewLauncher(), webui.NewLauncher()),
)
if err := l.Execute(ctx, &launcher.Config{
	SessionService: sessSvc,
	AgentLoader:    agent.NewSingleLoader(root),
	PluginConfig:   runner.PluginConfig{Plugins: plugins},
	Authenticator:  authn.NewIdentityAwareProxy(),
	Authorizer:     authz.NewStrict(),
}, os.Args[1:]); err != nil {
	log.Fatalf("launch: %v\n\n%s", err, l.CommandLineSyntax())
}

同一个二进制两种形态，靠 INTEL_RUN_ONCE 分流——这就是模块 8 讲的"adkgo 只部署、Web 入口回到你的 main"。

四点对应关系：

  1. universal.NewLauncher(web.NewLauncher(api.NewLauncher(), webui.NewLauncher()))：web.NewLauncher 返回 launcher.SubLauncher，必须再套 universal.NewLauncher 才有 Execute（模块 2 第 3 篇）。图省事就直接 full.NewLauncher()。
  2. launcher.Config 是唯一的注入口——SessionService 与 AgentLoader 都从这儿进（模块 8 第 2 篇的字段表）。
  3. authn.NewIdentityAwareProxy() + authz.NewStrict() 必须成对：模块 10 第 1 篇的四象限表，只配前者=任何登录者可冒充任何用户，只配后者=服务全挂。
  4. PluginConfig 也传进 launcher，所以 Web 表面的每次 runner.New 都带上插件——注意 getRunner 是每请求重建 Runner 的（模块 7），所以插件实例是共享的、跨会话的（第七点 retryandreflect 用 sync.Mutex 的原因）。

批量形态#

func runOnce(ctx context.Context, root agent.Agent, sessSvc session.Service) {
	const app, user = "intel", "cron"
	sess, err := sessSvc.Create(ctx, &session.CreateRequest{AppName: app, UserID: user})
	if err != nil {
		log.Fatalf("create session: %v", err)
	}
	r, err := runner.New(runner.Config{AppName: app, Agent: root, SessionService: sessSvc})
	if err != nil {
		log.Fatalf("runner: %v", err)
	}
	msg := &genai.Content{Role: "user", Parts: []*genai.Part{{Text: `{"sources":["rss://a"]}`}}}
	for ev, err := range r.Run(ctx, user, sess.Session.ID(), msg, agent.RunConfig{}) {
		if err != nil {
			log.Fatalf("run: %v", err)
		}
		if ev.Output != nil {
			log.Printf("output from %s: %v", ev.Author, ev.Output)
		}
	}
}

三条：

  1. 自己 Create session，而不是用 runner.Config{AutoCreateSession: true}。原因值得记住：adkrest.ServerConfig 里没有 AutoCreateSession 字段，handler.go 建 RuntimeAPIController 时也不设它——所以 REST 路径永远是 false，必须先建会话。批量与 Web 行为一致地写，别一边靠 AutoCreateSession 一边靠手工 Create。
  2. for ev, err := range r.Run(...) —— 迭代器协议，err 出现即 break（模块 4/5 同款）。
  3. ev.Output 而非 ev.Content：图节点的结构化产出在 Output（模块 5），Content 是给模型看的文本。

⚠️ 这里故意不做 HITL 的自动批准。批量路径遇到 human_gate 会发出 adk_request_input 然后暂停；要么你在这个函数里读 ev.RequestedInput 并追加一个 FunctionResponse 事件再 Resume（模块 5 第 5 篇），要么批量形态就不该有人工节点——这是产品决策，不是框架能替你决定的。

九、部署（模块 8 第 1 篇）#

FROM golang:1.27 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags=-s -ldflags=-w -o /exe ./cmd/intel

FROM gcr.io/distroless/static-debian11
COPY --from=build /exe /app/exe
ENTRYPOINT ["/app/exe"]

docker build -t REGION-docker.pkg.dev/PROJ/repo/intel:latest .
docker run -p 8080:8080 -e GEMINI_API_KEY=... -e DATABASE_URL=... \
  intel web api webui -global_port 8080

go install google.golang.org/adk/v2/cmd/adkgo@latest
adkgo deploy cloudrun --project_id "$PROJ" --region "$REGION" \
  --image REGION-docker.pkg.dev/PROJ/repo/intel:latest --a2a false --debug_api false

ENTRYPOINT ["/app/exe"] 而不是 /app/exe web —— 把子命令留给 adkgo 生成的 CMD ["/app/exe","web","-port","<port>"]，两边就不打架（模块 8 第 1 篇第 2 节）。

--a2a false：这个 agent 有人工核准环节，暂时不需要对外暴露 A2A。真要做多 agent 协作，参考模块 9——并记得先给 A2A 表面单独配认证（它不走 launcher.Config.Authenticator）。

小结：全系列的一条主线#

回头看，ADK Go v2 的十个模块其实在反复讲同一件事的四个侧面：

  • 类型是契约：agent.Context 一个接口（模块 2）、iter.Seq2 一套流协议（模块 4/5/7/9）、泛型节点与工具直接把 Go 类型变成模型侧 schema（模块 3/5）、any 出现的地方就是校验点（模块 5/6）。
  • 状态是唯一的真相：图状态存在 session 事件里（模块 4/5），所以会话存储决定一切恢复能力；OutputKey 与 prefix/名 的层级是跨 agent 通信的标准方式（模块 4/6）。
  • 暂停是一种状态而不是错误：ErrNodeInterrupted 必须原样冒泡、InterruptID 必须唯一、LongRunningToolIDs 让事件不算 final（模块 5/6/7）——HITL 与长运行工具走的是同一套机制。
  • 默认值都是开发值：NewInMemory、authn.Noop + authz.Noop、无 exporter 的 telemetry、CloseTimeout 与 Pub/Sub 的 MaxConcurrentRuns、-include_debug_api false（模块 8/10）。“字段存在"和"字段生效"是两件事——这条贯穿全系列，也是我把每个结论都回到 v2.4.0 源码或编译验证的原因。

三十篇文章到此。回去按你自己的场景挑模块读：做工具型 agent 从模块 3 + 6 入手，做流程自动化从模块 5 + 4 入手，做对外服务从模块 8 + 9 + 10 入手。

常见问题

这个例子的代码能直接跑吗？

每个 Go 片段都在 /tmp 的独立 module 里对 adk/v2 v2.4.0 + go1.26.8 跑过 go build 与 go vet（零错误）。你需要自备 GEMINI_API_KEY 与一个 PostgreSQL DSN，然后按文末的命令跑。

为什么抓取用 FunctionNode 而不是让模型调工具？

因为抓取是确定性的、必须发生的步骤。模块 5 的第一原则就是"确定的步骤用节点，不确定的判断才用模型"。这里 llmagent 只负责"提炼结论与风险"这一件不确定事。

人工核准那一步在 Web 界面上长什么样？

节点发一个 adk_request_input 的 FunctionCall 事件（workflow.NewRequestInputEvent），A2A/REST 侧表现为 task 进入 input-required（模块 9）。Dev UI 会弹输入框；用户提交后 workflowagent 自动识别 resume 并重跑图。

ResumeOrRequestInput 帮我省了什么？

三行样板。它等价于"ctx.ResumedInput(InterruptID) 命中就返回答案，否则 emit NewRequestInputEvent + 返回 ErrNodeInterrupted"。不写它就自己抄这段，抄错就是节点永不恢复。

一次投递一个会话，那我做定时批处理怎么写？

见 runOnce：Create 一个 session 再 runner.Run。注意模块 8 讲的触发器语义——重试复用同一会话（累积上下文），跨投递不复用。要跨天记忆就用 OutputKey + memory service，而不是靠同一个 sessionID。

为什么插件要自己 Close？

v2.4.0 的库代码里没有任何非测试路径调用 PluginManager.Close()，Runner 也没有 Close 方法，且 PluginConfig.CloseTimeout 被赋值但从未读取。所以插件持有的资源必须你在退出路径上自己收（模块 10 第 2 篇）。
