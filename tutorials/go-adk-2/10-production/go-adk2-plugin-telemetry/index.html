插件与 OpenTelemetry：14 个生命周期钩子、early-exit 语义，和三个没人读的字段

ADK Go v2.4.0 的横切层：plugin.Config 的 14 个钩子与四类签名、PluginManager 的 early-exit 与同名注册失败语义、CloseFunc 与 PluginConfig.CloseTimeout 在 v2.4.0 里没有任何调用方这个实现事实、三个内置插件（loggingplugin 十二钩子全开、retryandreflect 把失败注回模型、functioncallmodifier 改模型可见 schema）、telemetry.New 的九个 Option 与 exporter 的环境变量驱动、五种 span 命名、工具参数无条件上报与对话内容需环境变量显式开启的隐私不对称。

September 26, 2026 · 7 min · 1408 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 plugin/plugin.go、internal/plugininternal/plugin_manager.go、plugin/{loggingplugin,retryandreflect,functioncallmodifier}/、telemetry/{config.go,telemetry.go,setup_otel.go}、internal/telemetry/{telemetry.go,node_tracing.go,compaction.go,logger.go,genaimessages.go}。

一、plugin.Config：14 个钩子，四个阶段#

type Config struct {
	Name string

	OnUserMessageCallback OnUserMessageCallback
	OnEventCallback       OnEventCallback

	BeforeRunCallback BeforeRunCallback
	AfterRunCallback  AfterRunCallback

	BeforeAgentCallback agent.BeforeAgentCallback
	AfterAgentCallback  agent.AfterAgentCallback

	BeforeModelCallback  llmagent.BeforeModelCallback
	AfterModelCallback   llmagent.AfterModelCallback
	OnModelErrorCallback llmagent.OnModelErrorCallback

	BeforeToolCallback  llmagent.BeforeToolCallback
	AfterToolCallback   llmagent.AfterToolCallback
	OnToolErrorCallback llmagent.OnToolErrorCallback

	CloseFunc func() error
}

一次 New(cfg) 造一个插件，返回 (*Plugin, error)；New 里唯一的兜底是：

// Ensure closeFunc is never nil so p.Close() doesn't panic
if p.closeFunc == nil { p.closeFunc = func() error { return nil } }

（New 目前不做任何校验，name 为空也照样成功——但空名会让下面的同名检查变得危险。）

签名决定能力#

type OnUserMessageCallback func(agent.InvocationContext, *genai.Content) (*genai.Content, error)
type BeforeRunCallback     func(agent.InvocationContext) (*genai.Content, error)
type AfterRunCallback      func(agent.InvocationContext)
type OnEventCallback       func(agent.InvocationContext, *session.Event) (*session.Event, error)
钩子能改什么能阻断什么
OnUserMessageCallback替换用户输入内容返回非 nil content → 用它，后续插件不跑
BeforeRunCallback凭空造一条 content同上，注释语义是"跳过正常处理"
OnEventCallback替换将要落盘的事件返回非 nil event → 用它
AfterRunCallback什么都不能（无返回值）纯观测点

agent / model / tool 三层复用模块 2 与模块 3 讲过的回调类型 —— 插件就是"把 agent 级回调提升到整个 run 的所有 agent"，语义完全一致（比如 BeforeAgentCallback 返回非 nil content 就跳过那个 agent）。

OnEventCallback 是最强也最危险的位置#

它拿的是 *session.Event（模块 4），能改 Actions、LongRunningToolIDs、CustomMetadata——直接改写事件的持久化内容。而模块 5 讲过 Actions.StateDelta 由 scheduler 在写 session 前应用，OnEventCallback 在其上游还是下游取决于事件流转位置：用插件改 state 请优先用 RunOption WithStateDelta（模块 4），改事件只用于脱敏、打标、审计这类不改语义的场景。

⚠️ 另外，模块 4 讲过平台压缩事件被 IsPlatformEvent() 过滤，不会进 appendEvent —— 所以 OnEventCallback 看不到它。

二、PluginManager 的两条硬规则#

规则一：early exit —— 顺序即优先级#

internal/plugininternal/plugin_manager.go 里每个 Run* 方法都是同一个形状：

for _, plugin := range pm.plugins {
	callback := plugin.BeforeToolCallback()
	if callback != nil {
		newArgs, err := callback(ctx, tool, args)
		if err != nil {
			return nil, err
		}
		if newArgs != nil {
			return newArgs, nil // Early exit
		}
	}
}
return nil, nil

三条推论：

  1. err != nil 立即终止整个链，且不继续跑后面的插件。
  2. 返回值非 nil 也立即终止 —— 后面的插件根本看不到这次调用。
  3. 因此：
    • 观测型插件（打日志、记指标）必须永远返回 nil, nil，否则会把同批次的其他插件"吃掉"。
    • 插件注册顺序 = 优先级。想抢占就先注册；想让别的插件先看，就后注册。
    • 想做"多方都能改一遍"的链式加工？这个管理器不支持（BeforeRunCallback 拿不到前一个插件的产物，因为非 nil 就 return 了）。

AfterRunCallback 是唯一不短路的一类（无返回值，全跑）。

规则二：名字唯一#

// RegisterPlugin adds a new plugin to the manager.
func (pm *PluginManager) registerPlugin(plugin *plugin.Plugin) error {
	if plugin == nil {
		return fmt.Errorf("cannot register nil plugin")
	}
	for _, p := range pm.plugins {
		if p.Name() == plugin.Name() {
			return fmt.Errorf("plugin with name '%s' already registered", plugin.Name())
		}
	}
	pm.plugins = append(pm.plugins, plugin)
	return nil
}

内置插件的名字是写死的（例如 retryandreflect 用 "RetryAndReflectPlugin"）。所以：

  • 同一个插件包注册两次会直接失败（runner.New 返回 error）。
  • 起名的安全做法：mycompany_auth_plugin、metrics_v1 这类带前缀的唯一名。

规则三（是坑不是规则）：Close 路径在 v2.4.0 里没接上#

func (pm *PluginManager) Close() error {
	var errors []error
	for _, plugin := range pm.plugins {
		if err := plugin.Close(); err != nil {
			errors = append(errors, fmt.Errorf("error closing plugin '%s': %w", plugin.Name(), err))
		}
	}
	// …
}

我在 v2.4.0 全量 grep 的结果：

事实证据
PluginManager.Close() 没有任何非测试调用方全库搜索只出现在 plugin_manager_test.go
runner.Runner 没有 Close() 方法grep "func (r \*Runner) Close" 无结果
CloseTimeout 被赋值但从未读取全库只有 4 处：runner/runner.go:85（字段声明）、:129（传给 manager）、plugin_manager.go:34,40,46（声明与赋值），没有第 5 处读它

结论：plugin.Config.CloseFunc 与 runner.PluginConfig.CloseTimeout 在 v2.4.0 都是死配置。 如果你的插件持有连接池、file handle、后台 goroutine，必须自己管：

plugins := []*plugin.Plugin{logging, retry, mine}
r, err := runner.New(runner.Config{
	AppName: appName, Agent: root, SessionService: sessSvc,
	PluginConfig: runner.PluginConfig{Plugins: plugins},   // CloseTimeout 写了也没用
})
// …
// 进程退出路径上自己收
defer func() {
	for _, p := range plugins {
		if err := p.Close(); err != nil {
			log.Printf("close plugin %s: %v", p.Name(), err)
		}
	}
}()

（与模块 8 那条 -trigger_max_concurrent_runs 对 Pub/Sub 无效是同一类：配置字段存在 ≠ 生效。）

三、三个内置插件#

loggingplugin：十二钩子全开#

func New(name string) (*plugin.Plugin, error) {
	if name == "" { name = "logging_plugin" }
	p := &loggingPlugin{name: name}
	return plugin.New(plugin.Config{
		Name: name,
		OnUserMessageCallback: p.onUserMessage,
		BeforeRunCallback:     p.beforeRun,
		OnEventCallback:       p.onEvent,
		AfterRunCallback:      p.afterRun,
		BeforeAgentCallback:   p.beforeAgent,
		AfterAgentCallback:    p.afterAgent,
		BeforeModelCallback:   p.beforeModel,
		AfterModelCallback:    p.afterModel,
		OnModelErrorCallback:  p.onModelError,
		BeforeToolCallback:    p.beforeTool,
		AfterToolCallback:     p.afterTool,
		OnToolErrorCallback:   p.onToolError,
	})
}

十二个钩子，name 为空时回落到 "logging_plugin"（说明它允许注册多个实例做分流日志，只要给不同名字）。它是观测型插件的参考实现——所有钩子都不消费返回值，因此不会踩 early-exit。

生产排查第一步就是它：“图不推进"类问题（模块 5 调度器表）在 invoke_node 边界打日志比读代码快得多。

retryandreflect：把工具失败注回模型#

r := &retryAndReflect{
	maxRetries:           3,   // A sensible default
	errorIfRetryExceeded:  false,
	scope:                Invocation,
	scopedFailureCounters: make(map[string]map[string]int),
}
// …
if r.maxRetries < 0 { return nil, fmt.Errorf("maxRetries must be a non-negative integer") }
return plugin.New(plugin.Config{
	Name:                "RetryAndReflectPlugin",
	AfterToolCallback:   r.afterTool,
	OnToolErrorCallback: r.onToolError,
})

三个配置项：

func WithMaxRetries(maxRetries int) PluginOption
func WithErrorIfRetryExceeded(errorIfRetryExceeded bool) PluginOption
func WithTrackingScope(scope TrackingScope) PluginOption

const (
	Invocation TrackingScope = "invocation"   // 按调用统计
	Global     TrackingScope = "global"       // 跨轮次、跨用户全局统计
)

它只挂 AfterTool + OnToolError，机制是：把失败信息用模板渲染成文本喂回模型（reflection.md）：

The call to tool `{{.ToolName}}` failed.

**Error Details:**
{{.ErrorDetails}}

**Tool Arguments Used:**
{{.ArgsSummary}}

三条判断：

  1. Global scope 是跨用户的共享计数器。多租户服务上开 Global 意味着一个租户疯狂失败会把所有租户的该工具重试额度耗尽（返回类型常量 reflectAndRetryResponseType = "ERROR_HANDLED_BY_REFLECT_AND_RETRY_PLUGIN"）。默认 Invocation 才是安全的。
  2. 它用 sync.Mutex 保护计数器 —— 说明插件实例在多会话并发下共享状态（模块 6 第 1 篇讲过"一个实例服务多会话”），你自己写插件同理。
  3. maxRetries=0 合法（只允许 <0 报错），语义等价"关掉重试但保留错误改写"。想彻底禁用就别注册。

functioncallmodifier：改模型看到的工具契约#

type FunctionCallModifierConfig struct {
	Predicate           func(toolName string) bool
	Args                map[string]*genai.Schema
	OverrideDescription func(originalDescription string) string
}

按工具名命中，替换参数 schema 与描述。用途很具体：

  • 模型总在某个工具上传错枚举值 → 收紧 schema。
  • 某个工具名太长/太术语化 → 换描述让模型更容易选中。
  • ⚠️ 它与模块 6 第 2 篇的委派工具名直接相关：委派工具名就是子 agent 的 Name()，改这个插件可能改变模型可见的工具集，但不会改变代码里的路由。

它是"提示工程之外的第二个调模型行为的地方"，代价是声明与实际实现可能漂移（改了 schema 但工具本身没改），所以务必把 Predicate 写窄。

五、exporter 由环境变量决定 —— 默认什么都不导出#

configureExporters 的真实逻辑（结构照抄）：

otelEndpointEnv       := strings.TrimSpace(os.Getenv("OTEL_EXPORTER_OTLP_ENDPOINT"))
otelTracesEndpointEnv := strings.TrimSpace(os.Getenv("OTEL_EXPORTER_OTLP_TRACES_ENDPOINT"))
if otelEndpointEnv != "" || otelTracesEndpointEnv != "" {
	exporter, err := otlptracehttp.New(ctx)
	spanProcessors = append(spanProcessors, sdktrace.NewBatchSpanProcessor(exporter))
}
if cfg.oTelToCloud {
	spanExporter, err := newGcpSpanExporter(ctx, cfg)
	spanProcessors = append(spanProcessors, sdktrace.NewBatchSpanProcessor(spanExporter))
}
otelLogsEndpointEnv := strings.TrimSpace(os.Getenv("OTEL_EXPORTER_OTLP_LOGS_ENDPOINT"))
if otelEndpointEnv != "" || otelLogsEndpointEnv != "" {
	exporter, err := otlploghttp.New(ctx)
	logProcessors = append(logProcessors, sdklog.NewBatchProcessor(exporter))
}
// Golang OTel exporter to CloudLogging is not yet available.

四条：

目标触发条件
OTLP tracesOTEL_EXPORTER_OTLP_ENDPOINT 或 OTEL_EXPORTER_OTLP_TRACES_ENDPOINT 非空
GCP tracesoTelToCloud == true（WithOtelToCloud 或子启动器开关）
OTLP logsOTEL_EXPORTER_OTLP_ENDPOINT 或 OTEL_EXPORTER_OTLP_LOGS_ENDPOINT 非空
GCP logs❌ 没有实现（注释：“not yet available”）

两个连锁后果：

  1. initTracerProvider 在没有任何 span processor 时返回 nil（if len(cfg.spanProcessors) == 0 { return nil }）→ 不设环境变量就没有 TracerProvider，SetGlobalOtelProviders 也就是个空操作。
  2. ⚠️ OTEL_EXPORTER_OTLP_ENDPOINT 是"一刀切" —— 设了它就同时开 traces 和 logs 的 OTLP 导出。只想导 trace 就得用 ..._TRACES_ENDPOINT 那个更具体的变量。

六、span 命名与语义约定#

internal/telemetry 造的五类 span：

span 名属性来源
invoke_agent <name>gen_ai.agent.name、gen_ai.agent.description、gen_ai.conversation.id、gcp.vertex.agent.invocation_id
invoke_workflow <name>gen_ai.workflow.name、gen_ai.conversation.id
invoke_node <name>gen_ai.node.name、gen_ai.conversation.id
generate_content <model>gen_ai.request.model、gcp.vertex.agent.invocation_id
execute_tool <name>gen_ai.tool.name、gcp.vertex.agent.tool_call_args.args_name

再加一类压缩（模块 4）：

tracer.Start(ctx, fmt.Sprintf("%s %s", compactEventsName, params.Trigger), …)

invoke_workflow / invoke_node 是 v2 图引擎特有的——模块 5 那张"节点被 SKIP/RETRY 为什么"的排查表，在 trace 里就是 invoke_node 缺失/报错。这三层 span 树一目了然定位卡住的节点。

属性里还埋了一句迁移注释，值得注意：

gcpVertexAgentInvocationID.String(ictx.InvocationID()), // used by adk-web
// … 注释原文：Used by adk-web, can be removed once it reads the invocation id from invoke_agent span.

Chat UI 的"这条回复属于哪次调用"目前是靠这个私有属性接的（模块 7 第 9 节），所以别在自定义 exporter 里丢掉 gcp.vertex.agent.* 前缀的属性。

隐私不对称：工具参数无条件、对话内容按需#

// Request is the request about to be sent to the model. It is used only
// to record the opt-in gen_ai.input.messages and
// gen_ai.system_instructions attributes, and may be nil.

semconv.GenAIConversationID(sessionID(ictx)),   // 会话 id：无条件
gcpVertexAgentToolCallArgsName.String(safeSerialize(params.Args))  // 工具参数：无条件
const captureMessageContentEnvVar = "OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT"
数据是否默认上报
模型名、agent 名、工具名、node 名、invocation id、conversation id（= sessionID）✅ 无条件
工具调用参数（safeSerialize(args)）✅ 无条件
对话消息内容 gen_ai.input.messages、系统指令 gen_ai.system_instructions❌ 需 OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT

内容属性还有个时序讲究（注释原文）：

// After the sampling decision, not before: converting a whole conversation
// costs milliseconds, and on a span the sampler drops it buys nothing. …
// Still before the model call, so the prompt is on the span even when the call
// fails and no response is ever traced.

内容属性在采样决策之后、模型调用之前写入 —— 省掉被丢弃 span 的序列化开销，同时保证"调用失败也留有 prompt"。

⚠️ 但工具参数没有这层保护：把身份证号、地址、token 当参数传给工具（模块 3 的常见形态），它们会进 trace。这和本篇上面 ConsentRequiredError 那条禁令是同一件事：trace exporter 是数据出境通道（见第 1 篇 第七节）。

生产建议：给敏感工具加一层 BeforeToolCallback 插件做脱敏（返回替换后的 args —— 注意 early-exit 意味着你这个插件会独占改 args 的机会），或者在 exporter 侧按 gen_ai.tool.name 白名单丢弃参数属性。

七、最小生产接线#

import (
	"google.golang.org/adk/v2/agent"
	"google.golang.org/adk/v2/plugin"
	"google.golang.org/adk/v2/plugin/loggingplugin"
	"google.golang.org/adk/v2/plugin/retryandreflect"
	"google.golang.org/adk/v2/runner"
	"google.golang.org/adk/v2/telemetry"
)

// 1) telemetry 必须先于 runner 建立，并注册成全局 provider
providers, err := telemetry.New(ctx,
	telemetry.WithGcpQuotaProject(quotaProject),
	telemetry.WithOtelToCloud(false), // 先只走自建 OTLP collector
)
if err != nil { log.Fatal(err) }
providers.SetGlobalOtelProviders()

// 2) 插件：名字呌唯一；观测型先注册
logP := loggingplugin.MustNew("audit")                 // 空名字会回落到 logging_plugin
retryP, err := retryandreflect.New(
	retryandreflect.WithMaxRetries(2),
	retryandreflect.WithTrackingScope(retryandreflect.Invocation), // 别用 Global
)
if err != nil { log.Fatal(err) }
defer func() { // 框架不会调，自己收
	for _, p := range []*plugin.Plugin{logP, retryP} {
		if cerr := p.Close(); cerr != nil {
			log.Printf("close plugin %s: %v", p.Name(), cerr)
		}
	}
}()

r, err := runner.New(runner.Config{
	AppName: appName, Agent: root, SessionService: sessSvc,
	PluginConfig: runner.PluginConfig{Plugins: []*plugin.Plugin{logP, retryP}},
})
if err != nil { log.Fatal(err) }
defer func() { _ = r.Close() }()   // 只关 artifactService 等自有资源（模块 3/4）
_ = agent.Name

八、上线前的可观测性自查#

  • 每个插件返回唯一非空名字（同名会整个 runner.New 失败）
  • 观测型插件全部返回 nil, nil，避免吃掉后面插件
  • 明确知道插件顺序=优先级，抢占型插件放前面
  • 自己调 Plugin.Close()（框架不会调），CloseTimeout 别指望
  • retryandreflect 用 Invocation scope（Global 会跨租户串）
  • 知道 maxRetries=0 仍会改写错误
  • 设 OTEL_EXPORTER_OTLP_TRACES_ENDPOINT 而不是通用那个，除非你确实想同时开 logs
  • 需要 GCP trace 时显式开 WithOtelToCloud(true)；GCP logs 不可用，别配了以为在生效
  • 保留 gcp.vertex.agent.invocation_id（Chat UI 依赖）
  • 敏感工具参数已脱敏（无条件上报项）
  • 未开 ..._CAPTURE_MESSAGE_CONTENT，或开启前确认合规

常见问题

插件钩子会全部执行吗？

不会。PluginManager 每个 Run* 方法都是 early-exit 循环：某个插件返回非 nil 结果就直接返回，后面的插件不再执行。所以插件顺序就是优先级，写观测类插件时要保证自己永远返回 nil。

插件名能重复吗？

不能。registerPlugin 遇到同名直接返回 "plugin with name '%s' already registered" 错误，整个 runner.New 会失败。内置插件名是固定的（如 RetryAndReflectPlugin），你自己起名要注意撞车。

插件的 CloseFunc 会被调用吗？

v2.4.0 的库代码里没有任何非测试路径调用 PluginManager.Close()，Runner 也没有 Close 方法，所以 CloseFunc 不会自动执行；runner.PluginConfig.CloseTimeout 被赋值但从未被读取。要清理请自己持有插件切片并在进程退出时调 Close()。

OTel 数据默认导出到哪？

默认哪儿都不去。只有设了 OTEL_EXPORTER_OTLP_ENDPOINT 或对应的 *_TRACES_ENDPOINT / *_LOGS_ENDPOINT 才会建 OTLP exporter；GCP 侧要额外 oTelToCloud=true 才有 span exporter。日志的 GCP exporter 官方注释写着"尚未可用"。

trace 里会有对话内容吗？

分两种。generate_content span 的 gen_ai.input.messages 与 gen_ai.system_instructions 是 opt-in，需要 OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT；但 execute_tool span 的工具参数是无条件序列化上报的。

想让工具报错自动重试回模型有现成插件吗？

有，plugin/retryandreflect。默认 maxRetries=3、scope=Invocation、errorIfRetryExceeded=false。它把失败的工具名、错误详情、当时的参数用模板渲染成文本回灌给模型，让模型自己改参数重试。
