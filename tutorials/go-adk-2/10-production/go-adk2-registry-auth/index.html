Agent Registry 与入站鉴权：默认全开的 Noop，和一个 header 就当成身份的风险

ADK Go v2.4.0 的注册表与鉴权层：agentregistry 客户端（ADC + mTLS 端点选择、quota project 优先级、All* 的 iter.Seq2、RemoteAgent/MCPToolset 工厂与 cleanName 标识符规则）、入站 authn 四种实现（Noop/Header/IAP/Custom）与 401/500 分流、authz 的 CanActAsUser 语义与 Noop/Strict 两态、哪些路由是 Public、哪些控制器根本没有过 authorizer，以及出站 auth 包的 CredentialProvider 与 ConsentRequiredError 的禁止日志要求。

September 26, 2026 · 9 min · 1861 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 agentregistry/{registry,client,factory,resolve,types}.go、server/authn/{authn,noop,header,iap,custom}.go、server/authz/{authz,noop,strict}.go、server/adkrest/{handler.go,internal/routers/routers.go}、auth/{credential,providers,transport}.go。

本篇是"生产化"第一篇：把模块 8 的部署形态接上身份与受治理的能力目录。

一、先说结论：adkrest 默认是裸奔的#

adkrest.New 的开头两行：

authorizer := cfg.Authorizer
if authorizer == nil {
	authorizer = authz.NewNoop()
}
// …
authenticator := cfg.Authenticator
if authenticator == nil {
	authenticator = authn.NewNoop()
}

ServerConfig 的注释把后果写在脸上（逐句读）：

// When nil it defaults to [authn.Noop], which authenticates every request as
// an empty caller's identity — leaving every endpoint reachable without credentials.
// Setting an Authenticator without also setting an Authorizer authenticates
// callers but lets any authenticated caller act as any user; pair it with an
// Authorizer to restrict that.

// When nil it defaults to [authz.Noop], which permits any identity to act as
// any user. Use [authz.NewStrict] to require the authenticated UserID to match
// the path — but only alongside an Authenticator that sets a non-empty
// UserID, since [authn.Noop]'s empty caller's identity would then be denied for every
// user.

四象限速查表（这是本篇最该记住的东西）：

AuthenticatorAuthorizer实际效果
nil（Noop）nil（Noop）无凭证可达所有非 Public 端点，且任何调用方可读写任意 userID 的会话
真实 providernil（Noop）认证了身份，但身份与路径 userID 无关 → 已登录者可冒充任何人
nil（Noop）authz.NewStrict()全部请求被拒（空身份无法等于任何 userID）——看起来"更安全"，其实是把服务打挂
真实 providerauthz.NewStrict()✅ 唯一正确的组合（或换成你自己的 Authorizer）

二、哪些路由不需要认证#

SetupSubRouters 逐条路由决定是否挂 authn 中间件：

var authMiddleware func(http.Handler) http.Handler
if authenticator != nil {
	authMiddleware = authn.Middleware(authenticator)
}
for _, api := range subrouters {
	for _, route := range api.Routes() {
		var handler http.Handler = route.HandlerFunc
		if authMiddleware != nil && !route.Public {
			handler = authMiddleware(handler)
		}
		router.Methods(withHead(route.Methods)...).Path(route.Pattern).Name(route.Name).Handler(handler)
	}
}

三条：

  1. route.Public 为真的路由完全不过 authn。v2.4.0 里只有 /version 标了 Public: true（routers/version.go）。

  2. /health 更特殊——它是在 adkrest.New 里直接注册到根 router 的，根本不在 subrouters 循环里：

    router.HandleFunc("/health", healthHandler).Methods(http.MethodGet, http.MethodHead)

    所以健康检查天然无认证（对探针正确），但也意味着它不受你的 Authenticator 策略影响。

  3. withHead(route.Methods) —— 模块 7 第 9.4 节讲过的"GET 自动加 HEAD"就发生在这一行，也意味着 HEAD 请求同样经过 authn 中间件。

哪些控制器没有 authorizer#

CanActAsUser 的调用点分布（grep 全量）：

控制器是否过 authorizer依据的 userID 来源
sessions.go（4 处 + 1）✅sessionID.UserID（URL 路径）
artifacts.go✅sessionID.UserID
runtime.go（/run、/run_sse、live）✅runAgentRequest.UserId / userID
debug.go✅sessionID.UserID
apps（列应用/agent 列表）❌无 user 维度
agentgraph（agent 图）❌无 user 维度
version❌（Public）—

结论：/apps/{app_name} 与 agent graph 这两个面对任何"已认证"调用者都可见（Authorizer 只管"能不能 acting as 某个 userID"，而它们没有 userID）。里面装着你的 agent 名、层级结构、描述（模块 6 第 2 篇讲过 agent 名就是模型可见的工具契约）。

如果你的 agent 名/描述本身是敏感信息（内部产品代号、未发布功能），这两个端点要网关层再挡一次，或干脆不开 web/api 表面、只用 A2A / 触发器。

三、authn 四种实现与 401/500 分流#

type Caller struct {
	UserID string            // 稳定标识
	Claims map[string]any    // provider 自定义属性（email、roles、token scopes…），可为 nil
}
type Authenticator interface {
	Authenticate(r *http.Request) (*Caller, error)
}

四种 provider#

构造语义适用
authn.NewNoop()永远返回空 Caller只该出现在开发环境
authn.NewHeader(name)从单个请求 header 读 UserID。实现上会拒掉两种情况：header 缺失，以及同名 header 出现多个值（防 header 拆分/重复注入）。注释：“This is not HTTP Basic authentication; it trusts a header set by a trusted upstream (a proxy or gateway), so only use it when clients cannot set that header themselves.”网关/IAP 后置
authn.NewIdentityAwareProxy()读 GCP IAP 写入的 X-Goog-Authenticated-User-Email / -Id（UserEMailHeader、UserIDHeader）。注释点名场景：“for instance for Cloud Run-based deployment”Cloud Run + IAP
authn.NewCustom(AuthenticatorFunc)你自己写 func(r *http.Request) (*Caller, error)OIDC、自研 token、mTLS SAN…

错误分类：401 只给凭证问题，其余 500#

// ErrUnauthenticated reports that a request carried no valid credentials. An
// [Authenticator] returns it, or an error wrapping it, to make [Middleware]
// answer 401 Unauthorized. Any other error is treated as an internal provider
// failure and answered 500.
func writeAuthError(w http.ResponseWriter, err error) {
	if !errors.Is(err, ErrUnauthenticated) {
		// A provider-internal failure (for example an unreachable token
		// issuer), not a credential problem. Keep the detail out of the
		// response; a provider is expected to log its own errors.
		http.Error(w, "authentication failed", http.StatusInternalServerError)
		return
	}
	http.Error(w, "unauthorized", http.StatusUnauthorized)
}

三条实现要求：

  1. 要拿 401 就必须（直或 wrap）返回 ErrUnauthenticated —— errors.Is 判定，所以 fmt.Errorf("...: %w", authn.ErrUnauthenticated) 可以。

  2. 500 的响应体是固定文案 "authentication failed"，不含 err 内容。注释说明理由：“Keep the detail out of the response; a provider is expected to log its own errors.” → 你的 custom provider 必须自己打日志，否则线上只看到 500 且无任何线索。

  3. 还有个容易忽略的分支：

    if id == nil {
    // A provider that reports neither caller's identity nor error is
    // treated as a decline rather than silently letting the
    // request through unauthenticated.
    writeAuthError(w, ErrUnauthenticated)
    return
}

    (nil, nil) 被当作拒绝（401），不是放行。写 custom provider 时想短路必须返回真身份。

Middleware(nil) 是安全的 pass-through#

// A nil a yields pass-through middleware, so a caller can wire Middleware
// unconditionally.

所以你可以无条件写 authn.Middleware(myAuth)，不用 if 判空。

四、authz：只有"能不能 acting as 这个 userID"这一件事#

// Authorizer provides information whether the [Caller] can act as a userID
// It is used in ADK REST API (adkrest), which has the userID in paths.
type Authorizer interface {
	// CanActAsUser returns nil iff the [Caller] from the ctx can act as a userID. Otherwise returns an error
	// WARNING: avoid returning PII data in the error, it will be send back to the client.
	CanActAsUser(ctx context.Context, userID string) error
}

两行注释各值一票否决：

  1. 接口粒度只有 CanActAsUser —— 没有"能不能列会话"“能不能删 artifact"这种资源级授权。v2.4.0 的授权模型是用户作用域（{user_id} 路径段），资源级细粒度得你在自己的 Authorizer 里查 ctx 里的 path 或者在控制器外面做。

  2. ⚠️ 错误信息会原样发给客户端（WriteHTTPStatusForAuthError 把 err.Error() 拼进 403 body）：

    func WriteHTTPStatusForAuthError(rw http.ResponseWriter, err error) {
 errMsg := "forbidden"
 if err != nil {
 	errMsg = errMsg + ": " + err.Error()
 }
 http.Error(rw, errMsg, http.StatusForbidden)
}

    → 绝对不要把用户记录、员工姓名、内部 ID、数据库详情放进 authz 的 error。这和上一条 authn 500 的"不外泄细节"是同一条原则的两面。

状态码选择也有讲究：

// Forbidden, not Unauthorized (401): the
// caller is authenticated but not permitted to act as the requested user.

401 = 身份不明，403 = 身份已知但越权。前端据此决定"跳登录"还是"提示无权限”。

两态实现#

func NewNoop() Authorizer    // allows any [authn.Caller] to act as any userID
func NewStrict() Authorizer  // ensures exact match between the authenticated user and the user from the payload

NewStrict 就是"路径 userID 必须等于 Caller.UserID"。够用，但单租户/内部工具场景最常见；有角色模型就自己实现 Authorizer（比如 admin 可 acting as 任意用户）。

cleanName：注册表名字 → Go 标识符#

// cleanName converts an arbitrary display name into a valid identifier suitable
// for use as an agent or tool name. It mirrors adk-python's _clean_name:
// non-identifier characters become underscores, runs of underscores collapse,
// leading/trailing underscores are trimmed, and a leading digit is prefixed
// with an underscore.
func cleanName(name string) string {
	s := reNonIdentifier.ReplaceAllString(name, "_")   // [^a-zA-Z0-9_] → _
	s = reUnderscores.ReplaceAllString(s, "_")          // __+ → _
	s = strings.Trim(s, "_")
	if s != "" && s[0] >= '0' && s[0] <= '9' {
		s = "_" + s
	}
	return s
}

“为什么必须是合法标识符"这件事在 ADK 里有实际后果：agent 名就是模型可见的工具名（模块 6 第 2 篇：委派工具名直接取 Name()）。所以：

  • 中文名 翻译助手 → 全部非标识符字符 → 被清成空串。这类 name 在 registry 里能存在，但不能直接当 agent 名用（工厂会退化到别的字段或报错）。
  • 24x7-support → _24x7_support。
  • 两个不同显示名可能折叠成同一个标识符（a-b 与 a_b）→ 批量注册时名字冲突的隐蔽来源。

七、出站 auth 包：ConsentRequiredError 是禁止日志的#

工具/MCP 侧的凭据是另一个包（google.golang.org/adk/v2/auth），与入站 authn 无关：

type Credential interface {
	// Apply writes the credential's auth headers onto h.
	Apply(h http.Header) error
}
type CredentialProvider interface { … }   // + ProviderFunc 适配

现成 provider：

func StaticToken(token string) CredentialProvider
func APIKey(name, value string) CredentialProvider
func TokenSourceProvider(ts oauth2.TokenSource) CredentialProvider
func ADC(scopes ...string) CredentialProvider
func ServiceAccount(cfg ServiceAccountConfig) CredentialProvider
func WithHeaders(inner Credential, headers map[string]string) Credential

凭据类型：APIKeyCredential、BearerCredential、BasicCredential、OAuth2Credential；Transport 负责把 provider 挂进 http.Client。

最关键的一段是 ConsentRequiredError 的注释，逐句照抄：

// ConsentRequiredError signals that interactive, 3-legged OAuth consent is needed
// before a credential can be issued. Consumers detect it with errors.As.
type ConsentRequiredError struct {
	// AuthURI is the URL the end user must visit to grant consent.
	//
	// Hand it to that user and to nobody else. It is built by the credentials
	// service, and a 3-legged authorization URI normally carries the acting user
	// in a login_hint parameter, so it is not redacted the way service text in
	// other errors is — the identifier in it is what makes the URL work. Do not
	// log it, do not put it in a span, and do not serialize this error: every
	// field is exported, so a json.Marshal of it publishes the URI whatever
	// Error() says.
	AuthURI string
	// Nonce is an opaque value echoed back to correlate the consent response.
	// Sensitive on the same terms as AuthURI, which embeds it.
	Nonce string
	// Key is the credential-store key to resume the flow under.
	Key string
}

四条纪律（这是官方注释里最严厉的一段）：

  1. AuthURI 里嵌了 login_hint（即当前用户身份），所以它故意不做脱敏——那个标识符正是 URL 能用的原因。
  2. 不要 log 它、不要放进 span、不要 json.Marshal 这个 error 结构体（字段全导出，序列化必然泄漏）。
  3. 只能交给那个用户本人。
  4. 用 errors.As 检测，不是 errors.Is。

⚠️ 第 2 条和第 2 节 authz 的"别把 PII 放进 error”、第 3 节 authn 的"500 不外泄细节"构成同一条工程原则：ADK Go v2.4.0 在三条不同代码路径上反复强调同一件事——错误信息是公开面。做可观测性时（第 2 篇 ）尤其要注意：trace exporter 会把 error message 带出进程。

ConsentRequiredError 的正确处理是"把 AuthURI 单独回传给这个用户，让他去授权，然后按 Key 续跑流程”——它是一个交互协议，不是一个失败。

八、上线前的鉴权自查#

  • Authenticator 与 Authorizer 同时配置（四象限表最后一行）
  • 选 Header provider 前确认网关剥离客户端自带的同名 header（库里已经拦了“多值”，但单值透传拦不了）
  • Cloud Run 上优先 NewIdentityAwareProxy()（而不是自己写 header 解析）
  • custom Authenticator 自己记日志（500 响应体是固定文案，线上没线索）
  • custom Authenticator 不会返回 (nil, nil)（会被当 401 拒）
  • Authorizer 的 error 不含 PII（会随 403 发给客户端）
  • 意识到 /apps/{app} 与 agent graph 不过 authorizer，敏感 agent 名需要额外遮挡
  • A2A 表面的认证单独通过 launcher.Config.A2AOptions 配（不继承 adkapi 的配置）
  • 触发器表面的 userID 来自 subscription/source（模块 8 第 2 篇），不受 authn 影响
  • ConsentRequiredError.AuthURI / Nonce 不进日志、不进 span、不序列化
  • registry 名字过 cleanName 后检查冲突与空串

常见问题

adkrest 默认有鉴权吗？

没有。Authenticator 为 nil 时用 authn.NewNoop（把每个请求认证成空身份），Authorizer 为 nil 时用 authz.NewNoop（允许任何身份冒充任何用户）。两者都 nil = 除 /health 与 /version 外所有端点无凭证可达。源码注释把这一点写得很直白。

只配 Authenticator 行不行？

比不配好，但仍不完整。注释原话：只配 Authenticator 而不配 Authorizer 会"认证了调用者，却允许任何已认证调用者冒充任何用户"。因为 userID 在 URL 路径里，authorizer 才是那条边界。

用 NewHeader 有什么风险？

它信任上游（代理/网关）写入的 header，不是 HTTP Basic 认证。注释明确要求：只在客户端无法自己设置那个 header 时用。如果网关没剥离客户端自带的同名 header，任何人报个名字就是那个用户。

authz.NewStrict 什么时候不能用？

当 Authenticator 不提供非空 UserID 时（例如 authn.Noop）。Strict 要求认证身份与路径 userID 精确相等，空身份会导致所有请求被拒。

Agent Registry 怎么接？

agentregistry.New(ctx, agentregistry.Config{ProjectID, Location}) —— 两个字段都必填。默认用 ADC 认证并自动选 mTLS 端点；要预认证就自己传 HTTPClient（此时 mTLS 由你的 client 负责）。

注册表里的 agent 名字能直接当 Go agent 名用吗？

不能。要走 cleanName：非标识符字符换成下划线、连续下划线折叠、首尾下划线裁掉、数字开头补一个下划线前缀。这是与 adk-python 的 _clean_name 对齐的规则。
