三种固定编排 Agent：Sequential / Parallel / Loop 的实现语义与边界

ADK Go v2.4.0 的 agent/workflowagents 三包：Config 只包一层 agent.Config（LoopAgent 多一个 MaxIterations uint）、三者都拒绝自定义 Run、Sequential 的固定顺序与 RunLive 实时入口、Parallel 的 errgroup + 分支命名 <父>.<子> + 早停取消与 teardown 等待、Loop 的 count==0 无限循环与 Actions.Escalate 退出，以及它们与图工作流引擎的选型边界。

September 26, 2026 · 3 min · 590 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 agent/workflowagents/{sequentialagent,parallelagent,loopagent}/agent.go，样例 examples/workflowagents/*。

先说清一件事：这三个包不是 2.x 新增（v1.7.0 树里就有），2.x 对它们做的是"继续存在但不再是唯一选项"。上一模块那张图引擎把编排能力推到了另一端点，这一篇讲中间地带——编排形状固定时，你不必建图。

三个 Config 长一个样#

type Config struct {
	AgentConfig agent.Config    // 三个包都有这一个字段
}

// loopagent 多一个
type Config struct {
	AgentConfig   agent.Config
	MaxIterations uint
}

没有 SubAgents []agent.Agent 字段——子 agent 走 AgentConfig.SubAgents，运行时用 ctx.Agent().SubAgents() 读。所以构造形态是：

seq, err := sequentialagent.New(sequentialagent.Config{
	AgentConfig: agent.Config{
		Name:      "pipeline",
		SubAgents: []agent.Agent{extract, transform, load},
	},
})

三个 New 共有的一条硬规则：

if cfg.AgentConfig.Run != nil {
	return nil, fmt.Errorf("SequentialAgent doesn't allow custom Run implementations")
}

Run 不许设。 编排语义由包决定，不是给你覆写的钩子。（想自定义编排 → 那就是图引擎或者 agent.New + 自己的 Run。）

三家还会各自打上 state.AgentType = TypeSequentialAgent / TypeParallelAgent / TypeLoopAgent——遥测层靠它区分 span 类型（模块 10 展开）。

Sequential：固定顺序，且是唯一有 RunLive 的#

// SequentialAgent executes its sub-agents once, in the order they are listed.
// Use the SequentialAgent when you want the execution to occur in a fixed,
// strict order.

“once” 是关键词：每个子 agent 只跑一遍，不是循环。

seqAgent 结构体值得注意——它在 agent.Agent 之外多嵌了一个 *agentinternal.State，并实现了 RunLive：

func (s *seqAgent) RunLive(ctx agent.InvocationContext) (agent.LiveSession, iter.Seq2[*session.Event, error], error)

三个包里只有 Sequential 暴露了实时入口（另两个的 New 返回裸 agent.Agent）。所以语音/实时流水线要固定顺序时，Sequential 是直接可用的那一个；Parallel/Loop 要跑 live 得自己接（模块 7 讲 LiveSession）。

Parallel：errgroup、branch 命名、早停#

run() 的实现有三条工程细节值得逐条看。

① 每个子 agent 一条独立 branch：

branch := fmt.Sprintf("%s.%s", curAgent.Name(), sa.Name())
if ctx.Branch() != "" {
	branch = fmt.Sprintf("%s.%s", ctx.Branch(), branch)
}

也就是说 Parallel 自动做兄弟隔离——agentA 与 agentB 同时在跑时，彼此的中间事件互不可见（模块 4 第 2 篇的 Branch 语义在这里生效）。如果你希望它们看到同一个上下文，别用 Parallel，改用图里的显式共享节点或 state 传递。

② 每个子 ctx 是重建的，不是继承的：

subCtx := icontext.NewInvocationContext(errGroupCtx, icontext.InvocationContextParams{
	Artifacts: ctx.Artifacts(), Memory: ctx.Memory(), Session: ctx.Session(),
	Branch: branch, Agent: subAgent, UserContent: ctx.UserContent(),
	RunConfig: ctx.RunConfig(), InvocationID: ctx.InvocationID(),
})

注意这里没有 State 字段——session 是共享的（Session: ctx.Session()），所以状态读写走同一个会话。这也意味着并发子 agent 写同一个 state key 是竞态（模块 4：State.Set 最终经事件 delta 落库，但同一轮内并发写仍不安全）。并发分支要传值，用不同 key 或交给 JoinNode 式的下游汇总。

③ 早停与 teardown 的取舍（注释原文照抄）：

Cancelable so an early consumer stop aborts each sub-agent's in-flight Run
promptly. Teardown still runs to completion and the iterator waits for it
(see the deferred cleanup), so a sub-agent that blocks in teardown blocks run.

取消是即时的，但 deferred teardown 会被等完。所以：子 agent 的清理逻辑（回调、flush、关闭远端连接）里不要做无超时的阻塞，否则"停止"按钮按下去还是卡着。

错误传播用 errgroup.WithContext：任一子 agent 返回 error → 整体 error，并 cancel 其他分支。错误会被包一层 failed to run sub-agent %q: %w——errors.Is 仍然可用。

Loop：两个退出条件#

func (a *loopAgent) Run(ctx agent.InvocationContext) iter.Seq2[*session.Event, error] {
	count := a.maxIterations
	return func(yield func(*session.Event, error) bool) {
		for {
			shouldExit := false
			for _, subAgent := range ctx.Agent().SubAgents() {
				for event, err := range subAgent.Run(ctx) {
					if !yield(event, err) { return }
					if event != nil && event.Actions.Escalate { shouldExit = true }
				}
				if shouldExit { return }
			}
			if count > 0 {
				count--
				if count == 0 { return }
			}
		}
	}
}

四条从代码里直接读出来的语义：

  1. MaxIterations == 0 = 无限循环，注释确认：“LoopAgent runs indefinitely or until any sub-agent escalates”。给 0 之前请确保一定有 escalate 出口，否则就是死循环打模型。字段类型是 uint（不是 int），所以不用担心负数。
  2. 退出靠 event.Actions.Escalate——子 agent 在事件上置这个标志位就能终止整个循环。这就是模块 4 里 EventActions 那个字段的实际用途。
  3. escalate 的检查粒度是子 agent 的整轮迭代：先跑完当前子 agent 的全部事件，再看 shouldExit。不是逐事件中断——所以 escalate 后当前子 agent 剩下的事件仍会被 yield。
  4. yield 被拒绝（消费者 break）时直接 return，不等收尾。
  5. 每一轮都重读 ctx.Agent().SubAgents()——顺序固定、成员固定，运行期不能动态换子 agent。

⚠️ 常见事故：Loop 里没有 escalate，MaxIterations 又设很大，每一轮都打 N 个 LLM agent。生产上请同时设 MaxIterations 和 escalate 出口，并给节点配 Timeout（图里）或调用侧 deadline。

什么时候用哪个#

形状用什么理由
A→B→C 固定流水线sequentialagent三行搞定，且能 RunLive
多路并发查询、彼此不需要对方的结果parallelagent自动 branch 隔离 + errgroup
“草稿→评审→改"重复到通过loopagent + escalate内置计数与升级退出
需要条件分支 / fan-in 汇总 / 中途问人workflow 图引擎这三件事固定编排都不支持
运行期才知道要跑哪些步骤图 + DynamicNode子成员固定 vs 动态
LLM 自己决定交给谁collaboration 模式（下一篇 ）委派是模型行为，不是图结构

两者可以套：workflow.NewAgentNode(seq, cfg) 把一个 Sequential agent 当图节点，图负责分支与恢复、内部固定流水线交给轻量编排。不要为了用图而把三步直线流程拆成五个节点——可读性会倒退。

迁移提醒#

1.x 专栏里 Sequential/Parallel/Loop 是"唯一的编排手段”。2.x 请把它们看成图引擎的特例快捷方式：形状匹配时用最省字的那个，一旦需求超出"固定顺序 + 无恢复"，立刻上 workflow。

常见问题

SequentialAgent / ParallelAgent / LoopAgent 和图工作流怎么选？

顺序固定、无分支、无恢复需求 → 三个固定编排包最省事。需要条件路由、fan-in 屏障、跨请求暂停恢复、动态派发 → 用 workflow 图引擎（模块 5）。

它们的 Config 里能填什么？

只有 AgentConfig agent.Config 一层（LoopAgent 额外有 MaxIterations uint）。子 agent 通过 AgentConfig.SubAgents 传，编排逻辑不接受自定义 Run——设了会直接报错。

ParallelAgent 是真并发吗？

是，用 errgroup。每个子 agent 拿到独立 branch（<父名>.<子名>，有父 branch 时前缀拼接），所以兄弟默认互相看不到历史。

LoopAgent 什么时候停？

两个条件：MaxIterations 耗尽（0 表示不限），或任一子 agent 的事件里 Actions.Escalate 为 true。后者会在当前子 agent 迭代结束后立刻 return。

消费者提前 break 会泄漏 goroutine 吗？

Parallel 不会——它会 cancel 子 agent 并 drain 结果通道后才返回。但注释警告：子 agent 若在 teardown 里阻塞，整个 run 也会阻塞。

这些 agent 能被图引擎当节点用吗？

能。它们都是 agent.Agent，所以可以直接 workflow.NewAgentNode(a, cfg) 塞进图里当节点。
