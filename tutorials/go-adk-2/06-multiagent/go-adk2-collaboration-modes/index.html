Collaboration 三模式：chat / task / single_turn，以及框架替你的模型注入的那些工具

ADK Go v2.4.0 的 llmagent.Config.Mode 怎么落地：installTaskTools 按子 Agent 的模式自动在父级装上同名委派工具、ModeTask 自己拿到 finish_task、委派工具的 Name/Description/Parameters 全部来自 agent 配置（所以 Name 就是工具名）、task 工具描述里被硬编的「不要并行调用」那句、DefersResponse 与 synthesizeTaskFREvent 的绕道、IncludeContents 在 single_turn 节点上的不同默认，以及 9 个 TestDelegation_* 用例当规范用。

September 26, 2026 · 6 min · 1196 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 agent/llmagent/{llmagent.go,testdata/}、internal/workflowinternal/{single_turn_tool.go,task_agent_tool.go,finish_task_tool.go,task.go}、internal/llminternal/agent_transfer.go，样例 examples/multiagent/*。

模块 5 的图解决"谁先谁后由代码定"。这一篇解决另一半：谁干活由模型定。

一、Mode 四值与默认规则#

type Mode = llminternal.Mode

const (
	ModeUnset      = llminternal.ModeUnset // 没显式设置
	ModeChat       = llminternal.ModeChat        // 经 transfer_to_agent 可达
	ModeTask       = llminternal.ModeTask        // 会与人多轮澄清以完成任务
	ModeSingleTurn = llminternal.ModeSingleTurn  // 不与用户对话，干完交结果
)

Config.Mode 字段的注释把默认规则写成一句话：

Default value is ModeChat as a sub-agent, ModeSingleTurn as a node in a workflow.

同一个 agent，放的位置不同，行为就不同。 这是 ResolveMode(mode, fallback) 存在的理由——ModeUnset 不是"chat"，是"看场景再说"：

switch llminternal.ResolveMode(subState.Mode, llminternal.ModeChat) {
case llminternal.ModeSingleTurn: /* … */
case llminternal.ModeTask:       /* … */
}

注意 switch 里没有 chat 分支——见下一节。

二、installTaskTools：委派工具是长出来的，不是你写的#

llmagent.New 在返回前必走这一步：

if err := installTaskTools(a); err != nil { return nil, err }

它的逻辑分两半，方向和作用点完全不同：

if state.Mode == llminternal.ModeTask {
	finishTool, err := workflowinternal.NewFinishTaskTool(a)
	state.Tools = append(state.Tools, finishTool)     // ① 装给「自己」
}

for _, sub := range a.SubAgents() {
	switch llminternal.ResolveMode(subState.Mode, llminternal.ModeChat) {
	case llminternal.ModeSingleTurn:
		t, _ := workflowinternal.NewSingleTurnTool(sub)
		state.Tools = append(state.Tools, t)          // ② 装给「父级」
	case llminternal.ModeTask:
		t, _ := workflowinternal.NewTaskAgentTool(sub)
		state.Tools = append(state.Tools, t)          // ② 装给「父级」
	}
}
你是框架给你装装在谁身上名字
ModeTask agentfinish_task自己常量 FinishTaskToolName = "finish_task"
父级，子 agent 是 ModeTasktask 委派工具父级= 子 agent 的 Name()
父级，子 agent 是 ModeSingleTurnsingle_turn 委派工具父级= 子 agent 的 Name()
父级，子 agent 是 ModeChat（或 unset）什么都不装—走 transfer_to_agent

最后一行是三种模式真正的分水岭。README 一句话总结：

A single_turn or task sub-agent returns control to the coordinator automatically once it produces its result; no explicit transfer_to_agent call is required (this contrasts with default chat mode, which requires a manual handoff).

chat = 转交即失联（控制权交给对方，不会自动回来）；single_turn / task = 调用即返回（模型把它当函数调，拿到结果继续想）。

后果一：Name 和 Description 就是工具契约#

两个委派工具的 Name() 都只有一行：

func (t *TaskAgentTool) Name() string      { return t.agent.Name() }
func (t *SingleTurnTool) Name() string     { return t.agent.Name() }
func (t *TaskAgentTool) Description() string { return t.agent.Description() }

所以你的 agent 命名直接进入模型的 tool-selection 提示。 "a1" 这种名字等于让模型瞎猜；Description 要写清"什么时候该调我、需要什么输入、返回什么"。这条比 1.x 更重要，因为委派现在是工具调用而不是路由标签。

后果二：InputSchema 决定参数形状#

MakeFunctionDeclaration(curAgent)（single_turn）与 createTaskAgentFuncDeclaration（task）都是同一套：

decl := &genai.FunctionDeclaration{Name: curAgent.Name(), Description: …}
if agentInputSchema := getInputSchema(curAgent); agentInputSchema != nil {
	decl.Parameters = agentInputSchema
} else {
	decl.Parameters = &genai.Schema{Type: "OBJECT",
		Properties: map[string]*genai.Schema{"request": {Type: "STRING", /* task 版多一句描述 */}},
		Required:   []string{"request"}}
}

没写 InputSchema → 兜底 {request: string}（必填）。 task 版那句描述是 "Detailed instructions or context for the task sub-agent."。

后果三：task 工具的描述里被硬编了一句行为约束#

Description: strings.TrimSpace(fmt.Sprintf(
	"%s\nIMPORTANT: This tool delegates execution to a specialized agent. Do NOT call this tool in parallel with any other tools.",
	curAgent.Description())),

这句不是你写的，框架加的。 意思是：task 委派不能和别的工具并行调（因为委派会把控制权整段交给子 agent，并行的另一半没有执行时机）。single_turn 版没有这句——它可以并行，README 的示例输入 What's the weather like at home today? 就是多工具串起来的。

所以「能不能并行委派」是模式决定的，不是你自己 Parallel 一下就行。 想要并行 fan-out 多个 task 子 agent，官方 testdata 里也只有 TestDelegation_02_ChatToTwoTaskSequential（两个 task 但顺序），并行的那条是 TestDelegation_04_ChatToTwoSingleTurnParallel——名字本身就是答案。

后果四：非 Gemini 模型才需要额外的响应声明#

if !googlellm.IsGeminiAPIVariant(agentState.Model) {
	if outputSchema != nil { decl.ResponseJsonSchema = &genai.Schema{Type: "OBJECT"} }
	else { decl.ResponseJsonSchema = &genai.Schema{Type: "STRING"} }
}

换模型会改变送给模型的工具声明（Gemini 走原生结构化输出，所以跳过）。跨模型评测时记着这条差异。

三、finish_task：task agent 的"交卷"动作#

const (
	FinishTaskToolName      = "finish_task"
	FinishTaskSuccessResult = "Task completed."
)

注释说明两件事：

NewFinishTaskTool allows the model to signal that the agent has completed its task.
On success it sets `tool_context.actions.finish_task` with a serialized `TaskResult` dict.

taskAgent: ... The agent's `output_schema` is used for validation. If None, the
default schema (a single `result` string) is used.
谁来调task agent 自己（模型决定何时算完）
校验依据你的 OutputSchema；没给就退化成 {result: string}
结果落点actions 上的 finish_task（序列化后的 TaskResult）
失败面模型不调它 → 任务不会"交卷"；输出不符合 schema → 见下一节重试

数据结构三个（internal/workflowinternal/task.go，全部导出）：

type TaskRequest struct { AgentName string; Input map[string]any }
type TaskResult struct { Output any }
type DefaultTaskInput struct { Goal string; Background string }

DefaultTaskInput{Goal, Background} 是官方推荐的"不写 schema 时该给什么"——委派时把目标和背景分两个字段讲清楚，比塞一整段 request 文本可靠。

四、task 委派绕过了工具管线#

两处很反直觉的实现细节：

func (t *TaskAgentTool) Run(toolCtx agent.Context, args any) (map[string]any, error) {
	// Framework handles task delegation dispatch directly via the LlmAgent chat wrapper.
	return nil, nil
}

// DefersResponse implements toolinternal.ResponseDeferrer: the FunctionResponse for
// a task delegation is produced by the chat wrapper (synthesizeTaskFREvent), not by
// the standard tool-execution pipeline.
func (t *TaskAgentTool) DefersResponse() bool { return true }

含义：

  1. Run 是空的。 你在 BeforeToolCallbacks / AfterToolCallbacks 里对 task 委派名做拦截，看到的参数和"结果"不代表真实执行——真正跑子 agent 的是 chat wrapper。要观测 task 委派，看事件流里的子 agent 事件，不要看工具回调。
  2. FunctionResponse 是合成的。 所以 task 多轮澄清（子 agent 问人 → 人答 → 继续）能挂在这条委派调用上而不超时。官方 TestDelegation_06_ChatToTaskHITLResume 就是测这个：task 子 Agent 内部暂停问人，外层恢复。

顺带一句：模块 5 讲过图里 RunNode 派发 task 型 LlmAgent 要 WithIsolationScopeFromNodePath()（跨嵌套图/重名节点保证唯一）——同一个隔离需求在这里由 chat wrapper 内部处理，两条路径不同，别混。

五、IncludeContents：single_turn 的历史可见性#

type IncludeContents string

const (
	IncludeContentsNone   IncludeContents = "none"
	IncludeContentsDefault IncludeContents = "default"
)

Config.IncludeContents 的字段注释有个必须记住的不对称：

Left unset, an agent placed as a single_turn workflow node sees only the current turn.
Setting IncludeContentsDefault explicitly keeps the history even there.
设置普通对话 agent作为 single_turn 工作流节点
不填（零值）看历史只看当前轮
IncludeContentsDefault看历史看历史
IncludeContentsNone只看当前轮 + 之后自己的事件只看当前轮

“显式设置和留空不等价”，注释是这么写的（“Setting it explicitly is not the same as leaving the field unset”）。这是本模块最容易踩的静默差异：同一个 agent 直接跑正常，塞进图里当 single_turn 节点就"失忆"。要它记得，显式给 IncludeContentsDefault。

六、transfer_to_agent 的方向规则#

internal/llminternal/agent_transfer.go 顶部（对齐 Python 的 auto_flow.py）定义了两种 flow：

SingleFlow: no sub-agents are allowed, i.e.
    DisallowTransferToParent == true && DisallowTransferToPeers == true && len(SubAgents) == 0

AutoFlow — Agent transfers are allowed in the following directions:
  1. From parent to sub-agent.
  2. From sub-agent to parent.
  3. From sub-agent to its peer agent.
Peer-agent transfers are only enabled when all the following conditions are met:
  - The parent agent is also an LLMAgent.

三条实操结论：

  1. 想彻底关掉转交（做一个不能踢球的 agent）：三个条件全满足才降级到 SingleFlow——两个 Disallow* 都 true 且 SubAgents 为空。只设 DisallowTransferToParent 是不够的。
  2. 同辈互转要求父级也是 LLMAgent。父级是 sequentialagent / workflowagent 这种非 LLM 编排 agent 时，子 agent 之间转不了——它们没有共同的可推理父级。
  3. 跨同辈转交官方有用例背书：TestDelegation_09_ChatPeerTransferAcrossSiblings。

七、OutputSchema 与 set_model_response#

Config.OutputSchema 注释里藏着一个"框架不牺牲工具能力"的设计：

When OutputSchema is set, the framework transparently injects a
set_model_response tool so the model can still invoke other tools
(function tools, RAG, agent transfer, etc.) while producing structured output.
See internal/llminternal/outputschema_processor.go for details.

结构化输出不是靠"强制 JSON 模式"实现的，而是给模型一个"提交最终答案"的工具。所以设了 OutputSchema 之后模型仍然能调工具、仍能转交——如果你发现设了 schema 就没法调工具，那是别处配置问题，不是这条机制。

八、把 testdata 当规范用#

agent/llmagent/testdata/ 里的 TestDelegation_* 就是这套机制的行为合同，编号基本是难度递增：

用例验的事
01_ChatToTaskToToolchat → task → 工具 三层穿透
02_ChatToTwoTaskSequential两个 task 顺序委派
03_ChatToSingleTurn单次 single_turn 委派
04_ChatToTwoSingleTurnParallel两个 single_turn 并行（task 不行）
05_ChatChainedThroughChatToTaskchat → chat → task 链式转交
06_ChatToTaskHITLResumetask 子 agent 内部问人并恢复
07_ChatToTaskValidationRetryschema 校验失败后重试
08_ChatToTaskPlusFunctionTooltask 委派与普通工具混用
09_ChatPeerTransferAcrossSiblings同辈之间转交

改这块行为前先跑这些用例。 每个用例配 .events.yaml（期望事件流）+ .httprr（录制的模型请求/响应），是本地可重放的——不用 API key。

九、完整可编译示例#

examples/multiagent/collaboration/main.go 的三模式组合：

weatherChecker, err := llmagent.New(llmagent.Config{
	Name:  "weather_checker",            // 这就是模型看到的工具名
	Model: model,
	Mode:  llmagent.ModeSingleTurn,      // 不问人，自动交回
	Tools: []tool.Tool{getWeatherTool, userInfoTool, geocodeAddressTool},
})

flightBooker, err := llmagent.New(llmagent.Config{
	Name:         "flight_booker",
	Model:        model,
	Mode:         llmagent.ModeTask,      // 允许问澄清问题
	InputSchema:  flightInputSchema,      // 决定委派工具参数形状
	OutputSchema: flightResultSchema,     // 决定 finish_task 校验依据
	Tools:        []tool.Tool{searchFlightsTool, bookFlightTool},
})

travelPlanner, err := llmagent.New(llmagent.Config{
	Name:      "travel_planner",
	Model:     model,
	SubAgents: []agent.Agent{weatherChecker, flightBooker},
	// Mode 留空 = ModeUnset，作为 root 按 chat 处理
})

README 的收尾建议：“The coordinator delegates by mentioning the sub-agent’s name in its instruction.” 也就是在协调者的 Instruction 里点名 weather_checker / flight_booker 的适用场景——委派工具已经自动注入了，你要做的是让模型知道什么时候该用。

四个官方样例输入（覆盖三条路径）：

What's the weather like at home today?              → single_turn
Is it raining in Tokyo?                             → single_turn + 多工具
Please book me a flight from Zurich to London on 2026-07-12. I'm Alex Müller, window seat.
                                                    → task，信息齐，不追问
Book a flight Zurich → Barcelona on 2026-08-01.     → task，缺乘客名，会反问

跑法：

export GOOGLE_API_KEY=...
go run ./examples/multiagent/collaboration console
go run ./examples/multiagent/collaboration web api webui

隔离版样例：examples/multiagent/single_turn（只看 single_turn）、examples/multiagent/task_sub_agent（两个 task 子 agent）。

十、选型：模式 vs 图#

需求选
步骤固定、由你决定顺序图 / sequentialagent（模块 5、6-1）
该找谁由用户这句话决定collaboration 模式
子任务要能反问人、要多轮澄清ModeTask + Input/OutputSchema
纯查询、无交互、要并行ModeSingleTurn（可并行，见 04 用例）
需要跨请求恢复整轮状态图（RunState + Resume），模式本身不提供
只要"转交就走别回来"ModeChat + transfer_to_agent

两者可叠：图节点里放一个 chat 协调 agent，它照样能对自己的 SubAgents 装委派工具。反过来，finish_task 与图 HITL 是两套暂停机制（前者是模型主动交卷，后者 adk_request_input 是被迫等人），别指望它们互相触发。

自检清单#

  • 每个子 agent 的 Name 是模型能读懂的语义名，Description 说清"何时用我"
  • 需要结构化往返的 task agent 一定给 InputSchema + OutputSchema
  • 没有把 task 委派和别的工具放在同一批并行调用里
  • single_turn 节点需要历史时显式设 IncludeContentsDefault
  • 想要"不能踢球"的 agent：两个 Disallow* + SubAgents 空，三者齐全
  • 同辈转交场景下确认父级是 llmagent
  • 观测 task 委派看事件流，不依赖工具回调

常见问题

子 Agent 的模式会改变父 Agent 吗？

会，而且是自动的。llmagent.New 里的 installTaskTools 会遍历 SubAgents，按每个子 Agent 的 Mode 在父级 Tools 上追加一个委派工具；ModeTask 的子 Agent 自己还会拿到一个 finish_task 工具。

委派工具叫什么名字？

就叫子 Agent 的 Name()。TaskAgentTool/SingleTurnTool 的 Name() 都是 return t.agent.Name()，Description() 同理。所以 agent 的 name/description 就是模型看到的工具契约。

chat 模式和另外两个的最大区别？

chat 子 Agent 不装委派工具，靠 transfer_to_agent 手工转交，控制权不会自动回来；single_turn / task 干完自动把结果交回协调者，不需要显式 transfer。

不写 InputSchema 会怎样？

框架给一个兜底参数：{request: string} 且必填。task 工具那份还带描述「Detailed instructions or context for the task sub-agent.」。所以不写 schema 也能跑，但模型只能塞一句自然语言。

task 子 Agent 里能问人吗？

能。官方有专门用例 TestDelegation_06_ChatToTaskHITLResume。委派工具 DefersResponse() 为 true，所以它的 FunctionResponse 由 chat wrapper 合成，不会走标准工具执行管线。

single_turn 子 Agent 看得到历史吗？

默认看不到。Config.IncludeContents 的注释：未设置时，作为 single_turn 工作流节点的 agent 只见当前轮；显式设 IncludeContentsDefault 才会保留历史。
