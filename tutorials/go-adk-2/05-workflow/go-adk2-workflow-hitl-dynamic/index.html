动态图与 HITL：RunNode 七个选项、adk_request_input 线上格式，和跨请求恢复

ADK Go v2.6.0 图引擎最难的两块拼在一起：DynamicNode + RunNode 的运行期编排（七个 With* 选项、稳定 RunID 的单飞去重、失败分类、输出委托）、NewRequestInputEvent 合成的 adk_request_input FunctionCall 与 LongRunningToolIDs、InterruptID 的唯一性要求（Dev UI 按 ID 记账不再重复提问）、RerunOnResume 的重入/交棒两种模式与重复 Resume 的分叉语义、ResumeOrRequestInput 一行式写法、Workflow.Resume 与 ErrNothingToResume、ReconstructRunState 如何从事件历史重建状态（v2.6.0 起 RunState 不再当 blob 持久化），以及并行 HITL 不被支持这条硬限制。

September 26, 2026 · 7 min · 1336 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.6.0（10-13 发布），源码 workflow/{dynamic_node.go,run_node.go,request_input.go,resume.go,persistence.go,state.go,errors.go,dynamic_scheduler.go}，样例 examples/workflow/{hitl_simple,hitl_rerun,dynamic/*}；标注「v2.6.0 起」处为相对 v2.4.0 的行为变化。

前四篇的图都是建图时定型的。这一篇解决两件运行时的事：跑什么由代码临场决定（动态子节点）、跑到一半问人（HITL）。它们在实现上共用同一套暂停/恢复机制，所以放一篇讲。

一、暂停：NewRequestInputEvent 到底发了什么#

最简写法（examples/workflow/hitl_simple/main.go 的真实结构）：

ask := workflow.NewEmittingFunctionNode[any, any]("ask_name",
	func(ctx agent.Context, in any, emit func(*session.Event) error) (any, error) {
		// Unique InterruptID per request: a reused ID would let the
		// client treat a fresh prompt as already answered.
		if err := emit(workflow.NewRequestInputEvent(ctx, session.RequestInput{
			InterruptID: "ask_name-" + uuid.NewString(),
			Message:     "What is your name?",
		})); err != nil {
			return nil, err
		}
		return nil, workflow.ErrNodeInterrupted
	},
	workflow.NodeConfig{},
)

greet := workflow.NewFunctionNode[any, string]("greet", /* … */, workflow.NodeConfig{})

rootAgent, err := workflowagent.New(workflowagent.Config{
	Name:  "hitl_simple",
	Edges: workflow.Chain(workflow.Start, ask, greet),
})

⚠️ 这里有个很多人缺少的认知：你不需要自己调 wf.Resume。 workflowagent.New 包了一层 workflowAgent，它的注释写得很明确：

workflowAgent is the wrapper that dispatches between Workflow.Run (fresh turn)
and Workflow.Resume (resume turn). The dispatch decision is made by inspecting
ctx.UserContent for a FunctionResponse targeting a previously-emitted RequestInput.

也就是说：用户回一个指向 InterruptID 的 FunctionResponse，下一轮自动走恢复路径（detectResume 干这件事）。手写 Resume 只在你直接驱动 *workflow.Workflow（不经 workflowagent）时才需要——本篇最后一节给那种写法。

顺带三条从 New 源码里读到的硬事实：

  1. workflowagent.Config 只有 6 个字段（Name / Description / SubAgents / BeforeAgentCallbacks / AfterAgentCallbacks / Edges）——没有 MaxConcurrency、没有 StateSchema，因为它内部就是 workflow.New(cfg.Name, cfg.Edges)，option 一条没传。要限并发只能自己构 *workflow.Workflow 再包。
  2. 图名字 = agent 名字，所以 Name 非空时每个事件都带这个路径前缀（v2.6.0 起这只是 label，不是持久化开关，见第 2 篇）。
  3. 注释明确：一个 agent 实例可以服务多并发会话 —— v2.6.0 原话：“the per-invocation run state is rebuilt from session event history on a resume turn rather than held on the agent”。所以不要每请求新建 agent，也没必要加锁。

上游 README 对这两个样例的定位一句话可辨：

样例 演示
hitl_simple 两个节点的最小 pause/resume（ask 暂停、greet 交棒接住答复）
hitl_rerun 单个节点的重入式 HITL，用 ResumeOrRequestInput
NewRequestInputEvent(ctx, req) 内部做了六件事（源码逐条）： 
if req.InterruptID == "" { req.InterruptID = uuid.NewString() }   // ① 兜底 ID
ev := session.NewEvent(ctx, ctx.InvocationID())
ev.RequestedInput = &req                                          // ② 专用字段
args := map[string]any{"interruptId":…, "message":…, "payload":…} // ③ 镜像成 args
if req.ResponseSchema != nil { args["responseSchema"] = … }
ev.LLMResponse = model.LLMResponse{Content: &genai.Content{
	Role: genai.RoleModel,
	Parts: []*genai.Part{{FunctionCall: &genai.FunctionCall{
		ID: req.InterruptID, Name: WorkflowInputFunctionCallName, Args: args,
	}}}}}
ev.LongRunningToolIDs = []string{req.InterruptID}                // ④ 标长运行
ev.Author = ctx.Agent().Name()                                   // ⑤ 归因
ev.Branch = ctx.Branch()                                         // ⑥ 归属分支

关键在第 ③ 步：它同时写了两条通道。

  • Event.RequestedInput 是给 scheduler 看的（“这个节点要暂停，转 NodeWaiting"）；
  • 合成的 FunctionCall 是给通用客户端看的——注释原话：“so generic FunctionResponse-by-ID dispatch can route the human’s reply back to this agent on the follow-up turn”，而且"不解析专用字段也能只靠 args 把提示显示出来”。

线上名字是常量：

const WorkflowInputFunctionCallName = "adk_request_input"

注释对它的定性很硬：这是与其他 ADK runtime 共享的 wire-format 标识符，改动需要跨运行时协同——“一个运行时记录的 session 必须能在任何其他运行时的 resume dispatch 上往返”。所以别在你的前端里造第二个暂停协议，接这个就天然跨语言。

对照模块 3 的工具确认：toolconfirmation.FunctionCallName = "adk_request_confirmation"。两个前缀一致、语义不同的名字，分别对应"问参数批准"和"问业务输入"，UI 里要分两条渲染路径。

InterruptID 唯一性不是建议，是功能要求#

注释点名了客户端行为：

Avoid a fixed literal that recurs across separate runs in the same
session: clients such as the Dev UI track answered requests by this ID
and will not re-prompt for one already resolved earlier in the session.

写死 "ask_name" 的后果：同一会话里第二次到这里，UI 认为"这个 ID 已回答过"，不再弹框，流程静默卡住。正确姿势就是样例里的 "节点名-" + uuid（“readable-but-unique”）。

session.RequestInput 四个字段：

type RequestInput struct {
	InterruptID    string              `json:"interruptId"`
	Message        string              `json:"message,omitempty"`         // 给人看的问题
	ResponseSchema *jsonschema.Schema  `json:"responseSchema,omitempty"`  // 答复结构约束
	Payload        any                 `json:"payload,omitempty"`         // 给人看的上下文
}

⚠️ 一条硬约束（Event.RequestedInput 的字段注释）：“At most one event per node activation may carry this field.” 一次激活问一次。要并行问多个人 → 拆成多个节点。

二、两种恢复模式：重入 vs 交棒#

type NodeConfig struct {
	RerunOnResume *bool   // 三态
	WaitForOutput *bool
	// …
}
&true 重入（re-entry） &false 交棒（handoff） nil
谁接答复 asker 自己从头再跑一遍 asker 的后继把答复当输入 引擎当前按交棒
asker 会重新执行吗 ✅ 会（副作用要幂等） ❌ 不会 不会
答复怎么拿 ctx.ResumedInput(interruptID) 直接是节点 input —
NodeState.ResumedInputs 累加多次提问的答复 不存在（注释：absent for handoff-mode） —
典型样例 hitl_rerun hitl_simple

DynamicNode 帮你改了默认值——applyDynamicDefaults 里就四行：RerunOnResume == nil 时强制设成 &true。因为编排器被暂停后必须能接着跑完剩下的编排逻辑，交棒对它没意义。

重入模式的一行式写法（ResumeOrRequestInput，六个参数变两个）：

reply, err := workflow.ResumeOrRequestInput(ctx, emit, session.RequestInput{
	InterruptID: "approve-" + uuid.NewString(),
	Message:     "确认删除这 3000 行？",
})
if err != nil {
	return nil, err        // 首轮：内部已 emit 暂停事件，err == ErrNodeInterrupted
}
// 到这里 = 已拿到人类答复

实现就三步，值得记住（因为它就是"重入"的标准骨架）：

if reply, ok := ctx.ResumedInput(req.InterruptID); ok { return reply, nil }
if err := emit(NewRequestInputEvent(ctx, req)); err != nil { return nil, err }
return nil, ErrNodeInterrupted

⚠️ InterruptID 必须是稳定的那个（注释：“req.InterruptID is the shared key for the request and the resume lookup”）。如果你在这里也用 uuid.NewString()，重入时生成了新 ID，ctx.ResumedInput 永远查不到 → 无限暂停。样例里 ID 是从 state 或确定性来源取的。这是重入模式最容易犯的错，我在写这篇时差点也写错。

WaitForOutput 是第三种"暂停"，但它没有 interrupt ID：RunNode 派发的子节点跑完却没设 output 时，父节点 parked 重跑而不是用零值假完成。对应的错误很有意思——它是包装过的：

ErrNodeWaitingForOutput = fmt.Errorf("%w: waiting for output", ErrNodeInterrupted)

注释说明这是刻意的：“Wraps ErrNodeInterrupted so existing errors.Is(ErrNodeInterrupted) checks still treat it as a pause.” 想区分"问人"和"等 output"用 errors.Is(err, workflow.ErrNodeWaitingForOutput)。

三、恢复：Workflow.Resume 的语义（v2.6.0 按模式分叉）#

func (w *Workflow) Resume(
	ctx agent.Context,
	state *RunState,
	responses map[string]any,     // key = InterruptID，value = 人类答复
) iter.Seq2[*session.Event, error]

契约（v2.6.0 把重复提交的语义按重入/交棒分叉过，比 v2.4.0 明确得多）：

  1. 先校验再消费：payload 先按中断声明的 ResponseSchema 校验（不匹配 → ErrInvalidResumeResponse，节点留在 NodeWaiting、中断记录还在，可以拿修正后的 payload 重试）。重复提交不再是「天然幂等」——分叉看模式：

    • 重入节点（RerunOnResume=&true）：置 NodePending 重新调度，答复经 ctx.ResumedInput 递进去——重复的 Resume 会把它再跑第二遍。注释原话：“a duplicate Resume re-runs it a second time”。
    • 交棒节点：置 NodeCompleted，答复路由给后继，asker 不再执行；重复提交匹配不到等待节点，落到第 4 条。

    所以必须把双提交当成功处理的调用方，要容忍 ErrNothingToResume（注释：“It is never a no-op in the re-entry case”）——前端重试点「提交」时，交棒模式安全，重入模式会真的再跑一遍，副作用必须幂等。

  2. 没被回答的等待节点原地不动（responses 里没有它的 ID 就保持 NodeWaiting）。

  3. responses 非空但没有任何等待节点匹配 → ErrNothingToResume，注释解释动机：“so the caller can distinguish a successful resume from a stale or mistargeted submission”——典型是响应指向了过期/已消费的中断，或者图演化后那个等待节点已经不存在了（第 2 篇的发布风险在运行时的表现）。空 map 或 nil state 是干净 no-op，不报错。

还有一个实现细节直接影响图设计：Resume 走两趟（two passes）——一次调用满足多个 asker 时，先让 JoinNode 看到"所有前驱都 NodeCompleted“再评估屏障。否则 JoinNode 会在半齐状态下误判。

答复会被按 ResponseSchema 校验（validateResumeResponse），不匹配返回：

var ErrInvalidResumeResponse = errors.New("workflow: resume response does not match request schema")

所以 ResponseSchema 不只是给 UI 渲染表单用的，它同时是服务端校验契约。前端自己校验只是体验，服务端这份才是担保。

四、状态从哪来：ReconstructRunState#

跨请求恢复不靠"进程里还留着对象”，靠从事件历史重算：

state, err := wf.ReconstructRunState(sess, invocationID)   // 从 session 事件重建
if err != nil { … }
for ev, err := range wf.Resume(ctx, state, map[string]any{interruptID: reply}) { … }

persistence.go 里两个扫描器分工明确：

  • scanHistory(events, nodesByName, invocationID)：按节点收集 interrupts（插入序保稳定）、resolved（interrupt ID → 最后一次答复）、resolvedCount、以及从事件里重新抽取的 interruptSchemas，并维护 interruptOwner（谁问的）；
  • collectNodeOutputs(events, …)：算出每个节点的 output 和是否已完成。

resolvedCount == 1 就是上一节说的 answeredThisTurn（本轮首次被回答 vs 重复 replay）——幂等判据也是重算出来的，不持久化。

NodeState.Interrupts 的注释也印证了这套设计的来源：“Mirrors adk-python NodeState.interrupts.”

持久化边界（v2.6.0：事件历史重建，不存 blob）#

state.go 里 RunState 的注释（v2.6.0）把方向说死了：“It is not carried across turns as a stored value: a resume turn rebuilds it by scanning session event history (see ReconstructRunState)"。跨请求的状态实际活在 session 事件流里，RunState 只是恢复轮的重算产物。三条边界：

  • 隔离单位是 invocation ID：ReconstructRunState(sess, invocationID) 按它圈定单次运行（runner 在恢复轮复用暂停轮的 invocation ID，暂停与答复共享同一个）。invocationID 为空 = 扫全部历史——此时同会话两张节点重名的图必然混（第 2 篇的碰撞条件）。
  • 改节点名/图结构就发布 = 挂着的 HITL 停摆：重建时按节点名匹配历史，旧名字的等待记录找不到了，那个中断永远等不到答复，Resume 只报 ErrNothingToResume。v2.4.0 时代「换 name 开新命名空间」的补救失效——name 只是路径前缀，改它不影响事件归属。动节点名前先把未决会话清掉。
  • 节点 Input/Output 必须 JSON 可编码（NodeState 字段没变），二进制进 artifact、state 里存 URI。

五、动态图：DynamicNode + RunNode#

orchestrator := workflow.NewDynamicNode[Issue, Report]("orchestrate",
	func(ctx agent.Context, in Issue, emit func(*session.Event) error) (Report, error) {
		fix, err := workflow.RunNode[FixResult](ctx, fixerAgent, in)
		if err != nil {
			if errors.Is(err, workflow.ErrNodeInterrupted) {
				return zero, err          // 子节点问人了，让它冒泡
			}
			var nre *workflow.NodeRunError
			if errors.As(err, &nre) {
				log.Printf("child %s (%s) failed: %v", nre.ChildName, nre.ChildPath, nre.Cause)
			}
			return zero, err
		}
		return Report{Fix: fix}, nil
	},
	workflow.NodeConfig{},
)

签名 RunNode[OUT any](ctx agent.Context, child Node, input any, opts ...RunNodeOption) (OUT, error)——泛型出参直接给你类型，不用手工断言。

失败分类表#

RunNode 注释列了四类，照抄成表：

判定 含义
errors.Is(err, ErrNodeInterrupted) 子节点为 HITL 暂停（含包装的 ErrNodeWaitingForOutput）
errors.Is(err, ErrNodeFailed) + errors.As(&NodeRunError) 子节点重试耗尽后失败，结构体给 ChildName/ChildPath/RunID/Cause
ErrInvalidRunNodeContext ctx 不是当前执行中动态节点的 ctx（没有子调度器）
ErrInvalidRunID 自定义 run id 非法
ctx.Err() 父取消

ErrInvalidRunID 的规则很具体（纯数字被保留）：

id must be non-empty, contain at least one non-digit character
(purely numeric ids collide with the auto-counter), and exclude the
composite-path separators '/' and '@'.

七个选项#

选项 作用 注意
WithRunID(id) 用稳定 ID 替掉自动计数（可重排序列表按 order id 键控） ID 格式规则见上；v2.6.0 起同激活内单飞去重，见下方专节
WithUseSubBranch() 派生 <parentBranch>.<childName>@<runID> 并发/独立子节点必加，否则 LLM 子 agent 会看见兄弟事件
WithOverrideBranch(b) 整段替换继承的 branch 与 WithUseSubBranch 可叠加：override 定基、再追加子段
WithUseAsOutput() 把子节点 output 提升为编排器的终结 output（丢弃 Go 函数返回值） 一次激活最多一个，第二个 → ErrOutputAlreadyDelegated
WithIsolationScope(s) 给子节点及其事件打作用域 空 = 无作用域
WithIsolationScopeFromNodePath() 用完整节点路径当作用域（跨嵌套图/重名节点保证唯一） task 模式 LlmAgent 的用法；与上一个同设时 WithIsolationScope 优先
WithRaiseOnWait() 子节点带未决长运行工具结束时当作中断而非正常完成 聊天协调器派发 task 子 agent 时必须能区分"子暂停了"和"子干净结束了但没 output”

WithUseAsOutput 还有个连带效应，第 2 篇讲过：NodeInfo.OutputFor 会列出"这份 output 算给哪些节点路径"（发射者 + 所有委托祖先），一条事件顶替整条委托链，不是每层各发一份重复事件。

DynamicNode 内部两个辅助也值得知道：coerceInput（把上游 any 转成 IN）、composePath（拼 <父路径>/<节点名>@<runID>）——动态子节点的路径就是在这里定的，也是模块 4 里 NodeInfo.Path 那个 @run_id 后缀的来源。

单飞去重：稳定 RunID 的四条工程规则（v2.6.0 新加，#1043）#

WithRunID 的注释在 v2.6.0 扩成一段硬契约，核心一句话：稳定 ID = 一次动态节点激活内的去重键。

A stable id deduplicates calls within one activation of the enclosing
dynamic node: a repeat returns the first run's output without
re-running the child, and calls that overlap in time share one
execution and its outcome. A failed or interrupted run is not
retained, so a later call runs the child again. Do not rely on this
across a HITL pause: the resume turn re-executes the dynamic node's
body, and a child that completed before the pause can run again.

拆成四条：

  1. 同激活内重复调用 = 拿缓存：第二个 RunNode(id="order-42") 直接返回第一次的输出，不再跑子节点；时间上重叠的并发调用共享一次执行和结果（dynamic_scheduler.go 里的 inflightByPath 就是这套单飞表）。
  2. 失败/中断不进缓存：跑挂了或暂停了的不保留，下一次调用重新跑子节点——这是刻意的，别指望缓存帮你兜底。
  3. 跨 HITL 暂停失效：恢复轮会重跑动态节点函数体，暂停前已经完成的子节点可能再跑一遍（和第 3 节重入模式重复 Resume 再跑一遍是同一件事的两面）。
  4. 自等待死锁：「一个非动态子节点，不能在它自己的 run 里用自己的 name+id 调 RunNode」——内层调用会解析到那个正在跑的自己，等它结束，即等自己，直到 invocation 被取消。动态节点可以这么递归，因为它的函数体本来就是按自己的路径派子节点的。

同一版还有一条配套的小变化：makeEmit 现在回报消费者是否已走（consumerGone()）。调用方 break 掉 range 循环之后，节点体里的 emit 返回 context.Canceled，编排器每次 yield 前检查这个标记就停——「用户停止生成」时动态编排器不再对着已关闭的消费者硬跑。

自检清单#

  • InterruptID 每次运行唯一（前缀 + UUID），且重入模式下恢复时用的是同一个 ID
  • ResponseSchema 设了——它同时是服务端校验契约
  • 重入模式的节点体幂等（会被从头再跑）
  • 一次激活只问一个人；要并行问就拆节点（ErrParallelHITLUnsupported）
  • 并发子节点加了 WithUseSubBranch()
  • Resume 处理了 ErrNothingToResume（陈旧/错投的提交）
  • 图 name 非空；改节点名/图结构前先把未决 HITL 会话处理掉（重建匹配不上旧节点名，ErrNothingToResume）
  • 稳定 RunID 的去重只在同一次激活内有效；跨 HITL 暂停不假设（恢复轮会重跑动态体）
  • 非动态子节点不在自己 run 里用自己的 name+id 调 RunNode（自等待死锁）
  • 跨暂停传的数据 JSON 可编码，二进制走 artifact

模块 5 到此收束：这套图引擎在 Go 里就是一等 Agent，能暂停、能恢复、能被 LLM 驱动，而且线上格式跨语言对齐。下一篇进模块 6：多 Agent 新范式 ——workflowagents 与协作式 agent 的 chat/task/single_turn 三种模式。

常见问题

图节点里怎么问人并暂停？

yield 一个 workflow.NewRequestInputEvent(ctx, session.RequestInput{...})，然后返回 workflow.ErrNodeInterrupted。scheduler 观察 Event.RequestedInput 把节点转成 NodeWaiting，整轮不 finalize。

重入模式和交棒模式怎么选？

NodeConfig.RerunOnResume：&true 重入（节点从头再跑，靠 ctx.ResumedInput 拿答复）、&false 交棒（答复作为输入给后继，asker 不再执行）、nil 引擎当前按交棒。DynamicNode 默认帮你设成重入。

同一个节点能同时问两个人吗？

不能。一次激活最多一个待决 HITL，违反返回 ErrParallelHITLUnsupported。要并行问人就拆成多个节点。

InterruptID 有什么讲究？

必须每次运行唯一。Dev UI 之类客户端按这个 ID 记录"已回答"，用固定的字面量会导致它再也不重新提问。推荐可读前缀 + UUID，例如 "human_review-" + uuid.NewString()。

RunNode 只在 DynamicNode 里能用？

对。ctx 必须携带子调度器，否则返回 ErrInvalidRunNodeContext。判断依据就是 ctx.SubScheduler() 是否非 nil。

跨请求恢复是怎么做到的？

RunState 不再当 blob 持久化（v2.6.0），恢复轮用 wf.ReconstructRunState(sess, invocationID) 扫 session 事件历史重建，再 wf.Resume(ctx, state, map[interruptID]payload) 驱动。
