边与执行模型：EdgeBuilder、8 条建图校验，和那个单消费者 goroutine

ADK Go v2.4.0 图引擎的连接层：Edge{From,To,Route} 与 Start 哨兵、EdgeBuilder 六个方法与 Chain/Concat、workflow.New 的 8 条合法性校验（重复边/多默认路由/不可达/无条件环/子图重名…）、name 作为 RunState 持久化命名空间的后果与图演化风险、Run 的"每节点一个 goroutine + 单消费者"模型、事件按到达顺序 yield 的含义、userInput 的文本拼接规则。

September 26, 2026 · 4 min · 652 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 workflow/{workflow.go,edgebuilder.go,graph.go,validation.go}。

边就仨字段#

type Edge struct {
	From  Node
	To    Node
	Route Route   // 条件；nil 就是无条件边
}

var Start Node = &startNode{BaseNode: NewBaseNode("START", "Start node", NodeConfig{})}

Start 是哨兵：Run 里什么都不 yield（func(yield ...) {}），只作为"图的入口"存在。所以每个图必须有一条 From: workflow.Start 的边，否则 ErrNoStartNode。

裸写法完全够用：

wf, err := workflow.New("my-flow", []workflow.Edge{
	{From: workflow.Start, To: intake},
	{From: intake, To: classify},
	{From: classify, To: urgent, Route: workflow.StringRoute("urgent")},
	{From: classify, To: normal, Route: workflow.StringRoute("normal")},
	{From: urgent, To: join},
	{From: normal, To: join},
})

三种更省字的构造方式#

// ① 链
edges := workflow.Chain(a, b, c)     // len < 2 时返回 nil（不报错）

// ② 混合合并：Edge 和 []Edge 都能塞
edges := workflow.Concat(
	workflow.Chain(a, b),
	workflow.Edge{From: b, To: c, Route: workflow.BoolRoute(true)},
	[]workflow.Edge{{From: c, To: d}},
)

// ③ 链式 builder
edges := workflow.NewEdgeBuilder().
	Add(workflow.Start, a).
	AddRoute(a, b, workflow.IntRoute(2)).
	AddFanOut(b, c1, c2, c3).
	AddFanIn(join, c1, c2, c3).
	AddRoutes(a, map[string]workflow.Node{"x": b, "y": d}).   // 内部转成 StringRoute
	Build()

Concat(items ...any) 用 type switch 只认 Edge 和 []Edge 两种，塞错类型不会报错、会被静默忽略——这是它比 append 危险的地方，写完最好打一下 len(edges)。

AddRoutes 的入参是 map[string]Node，route key 会被转成 StringRoute。Go map 遍历序是随机的，所以它生成的边顺序不稳定——图语义上不依赖边顺序（路由是"哪些匹配"，不是"第一条匹配"），但如果你有测试断言 edges 切片内容，会 flaky。

workflow.New 的 8 条校验#

New(name, edges, opts...) 依次跑 validateNodes → validateSubWorkflowNames → newGraph → validateWorkflow。任何一条失败在建图时返回错误，不是运行时：

哨兵触发条件备注
ErrDuplicateNodeName两个不同实例共用一个 Name()生命周期 map 以名字为 key，撞名即串状态
ErrNoStartNode没有 START 出边
ErrNodePointsToStart有节点指回 START入口不能被当普通前驱
ErrDuplicateEdge(From, To) 相同不看 Route，注释直接给了替代方案：用 MultiRoute 表达"同一目标多条件"
ErrMultipleDefaultRoutes一个节点有多条默认路由见第 3 篇
ErrNodesNotReachable有节点从 START 不可达写了但永不执行的节点
ErrUnconditionalCycle环里没有任何条件边无条件环 = 死循环，直接拒
ErrSubWorkflowNameCollision子工作流与父同名命名空间冲突

最后一条注释里点出一个重要事实：NodeCompleted 状态可以被触发缓冲区里的新条目重新激活——“this is what enables loops as graph cycles”。也就是说合法的循环 = 环 + 条件边，靠路由把循环收敛掉。

name 不只是标签：它是持久化命名空间#

// New 的注释（摘录）
// The name forms part of the session.State key under which this
// workflow's RunState is persisted. It must be unique within any session
// that runs more than one workflow: two workflows sharing a name and a
// session will silently overwrite each other's RunState, leading to
// corrupted resume behaviour. ... An empty name disables persistence.

三个后果：

  1. 一个会话跑多张图 → 名字必须各不相同，否则恢复行为静默错乱（不报错！）。
  2. 想让图能跨轮恢复（HITL），name 不能为空。空名字的图正常跑，但 RunState 不存也不读。
  3. 上游留了两个 TODO，其中一个直接关系到发布安全：
// TODO(wolo): record a graph fingerprint (e.g. sorted node names hash)
// on the Workflow and verify it against any loaded RunState in Resume;
// today a name collision or a graph evolution between deploys silently
// corrupts the resume path.

目前没有图指纹校验。 所以：改了节点名或图结构就部署，而线上还挂着未完成的会话状态，恢复路径会静默吃坏数据。跨发布要改图结构时，先处理掉旧的 RunState（或给新图换 name——反正 name 是持久化 key 的一部分，改 name 等价于开新命名空间）。

执行模型：每节点一个 goroutine，单个消费者#

Run 的注释把模型讲得很干净：

The engine model: each scheduled node runs in its own goroutine pushing events into a buffered channel. A single consumer goroutine (this one) drains the channel, applies state-side effects, yields events to the caller, and schedules successors when nodes complete. The consumer is the only mutator of the per-node lifecycle map and of session state.

四条工程含义：

  • 节点体内不需要为"改 session state"加锁——那是消费者的活儿。你的节点只要保证自己的内部状态并发安全。
  • 事件按到达顺序 yield（注释：“in arrival order”）。并发分支之间没有确定序，别在下游假设"A 的事件一定先于 B"。要序就在图里建依赖，或者接 JoinNode。
  • 中途 break 是安全契约：“the caller may break from the range loop at any point and the engine will cancel all in-flight nodes before returning”。所以 UI 侧"停止生成"直接 break 就行，引擎会取消并 wg.Wait()（RunNode 末尾那句注释：All goroutines have returned; ensure no leak）。
  • WithMaxConcurrency(n) 超额的节点排队成 NodePending（n <= 0 关闭上限），但它对 RunNode 派发的动态子节点不生效——因为父节点在原地 await 子节点，卡住子节点会死锁。这条例外写在 WithMaxConcurrency 的注释里，很容易踩。

两种驱动方式#

// ① 作为 agent 跑（Runner 调它）：输入取自本轮用户内容
for ev, err := range wf.Run(ctx) { … }

// ② 显式给输入（WorkflowNode 内部就是这个）
for ev, err := range wf.RunNode(ctx, myInput) { … }

Run 会先做一件事：把 ctx “提升"成带路径的 context ——Path = "<wfName>@1"（有父路径时是 父路径/<wfName>@1）、RunID = "1"，然后 w.RunNode(c, userInput(c))。

⚠️ userInput 的行为要记住：它把 ctx.UserContent().Parts 里所有非空 Text 拼成一个字符串返回；UserContent() 为 nil 时返回 nil。多模态输入（图片 part）会被丢掉——图需要图片时，别指望 Run 自动传，走 RunNode 显式传输入，或者用 {artifact.x} 从 state/artifact 取。

isRootWrapper 这个 option 也顺带解释了一个现象：Runner 跑单个非图 agent 时，Go 会造一个合成的单节点 wrapper workflow 让所有执行都走同一套图引擎；此时不加父命名空间前缀，以保持和 adk-python 的事件路径严格对齐（Python 不包 wrapper）。你在遥测里看到 app/agent@1 这类路径差异，根源就在这。

排错速查#

症状先看
New 报 nodes not reachable from start node漏了 START 出边，或边写反
图卡在某个节点不动那个节点是 JoinNode 吗？有没有条件边指向它（不允许）
恢复后行为怪异两张图同名？改过节点名后旧 RunState 还在？name 是否为空
并发分支事件顺序不稳定正常，按到达序；要序就加依赖或 JoinNode
多模态输入进不了图Run 只拼文本 part，用 RunNode 显式传

常见问题

ADK Go 2.x 怎么声明工作流的边？

[]workflow.Edge{{From: workflow.Start, To: a}, {From: a, To: b}}，或 workflow.Chain(a, b, c) 生成链、NewEdgeBuilder() 链式构造、Concat(...) 合并混合片段。

两条边从 A 到 B 只是路由不同，可以吗？

不行。ErrDuplicateEdge：(From,To) 相同即视为重复，不看 Route。要表达"同一目标的多个条件"用 MultiRoute。

工作流的名字有什么用？

它是 RunState 在 session.State 里的命名空间（同一会话跑多个工作流时必须唯一）。空名字=关闭持久化，Resume 找不到可恢复的状态。

图里的节点会并发跑吗？

会——每个被调度的节点跑在自己的 goroutine 里，事件推进一个 buffered channel；只有单个消费者 goroutine 修改生命周期 map 和 session state。

事件顺序可依赖吗？

因果序可以，全局到达序不可以——并发分支的事件按到达顺序 yield。要确定顺序就在图里加依赖（或用 JoinNode）。

workflow.New 会检查哪些错误？

八个哨兵：重复节点名、没有 START、有节点指向 START、重复边、多个默认路由、节点不可达、无条件环、子工作流重名。
