调度器生命周期与重试：7 个节点状态、5 次退避，和一个不重试校验错误的默认值

ADK Go v2.4.0 图引擎的调度层：NodeStatus 七个状态的确切语义（含 NodeWaiting 的两种成因、NodeRunning 重启后必须重排、NodeCancelled 的两种来源）、NodeState/RunState 的可持久化边界与二进制载荷处理、重试策略 DefaultRetryConfig 的 5/1s/60s/2.0/full jitter、ShouldRetry 与 CalculateDelay 两个可导出的纯函数、默认不重试 ErrInputValidation 的原因、结构化字面量 vs DefaultRetryConfig 的坑，以及并发上限与取消传播（cancelAll/echoesCancellation/sibling 取消返回 nil）。

September 26, 2026 · 5 min · 870 words · 梦兽编程 -  |  English

验证版本： google.golang.org/adk/v2 v2.4.0，源码 workflow/{state.go,scheduler.go,retry.go,config.go,errors.go}。

前两篇讲的是"图长什么样、往哪走"，这一篇讲"每个节点此刻在哪、失败了怎么办"。2.x 的调度器状态机写得相当严谨，而且状态定义本身就是文档。

七个状态，逐个抄录语义#

type NodeStatus uint8

const (
	NodeInactive  NodeStatus = iota // 零值：还没被碰过
	NodePending                     // 就绪待跑（输入到了，或失败后等待重试）
	NodeRunning                     // 本进程内有任务在飞
	NodeCompleted                   // 完成并产出 output
	NodeWaiting                     // 暂停（两种成因，见下）
	NodeFailed                      // 返回错误且重试策略耗尽。终态
	NodeCancelled                   // 被取消。两种来源，终态
)

四条注释里的关键规则：

  1. NodePending 有两个来源：“输入到了"和"失败后重试排队”。所以当 WithMaxConcurrency 限流时，节点会停在 NodePending —— 观测卡住时先确认是"没输入"还是"被限流"。
  2. NodeCompleted 不是绝对终态：注释写明*“a node in NodeCompleted may still be re-triggered by a fresh entry in the trigger buffer (this is what enables loops as graph cycles)"*。循环就是靠这个实现的。
  3. NodeWaiting 一出现，整个工作流就不 finalize：“While any node is NodeWaiting the workflow does not finalize.” 两种成因共用一个状态：HITL 暂停 / fan-in 未齐（WaitForOutput=true，例如 JoinNode）。排查"图不结束"时，得先分清是哪一种——看 NodeState.Interrupts 非空就是 HITL，看是否有前驱没完成就是 fan-in。
  4. NodeRunning 是进程内的概念：注释直接要求
A NodeRunning entry that has no live task in the run state
(e.g. after a process restart) must be re-scheduled.

这意味着节点体必须能安全重跑——崩溃恢复后同一个节点会再来一次，副作用（写库、发消息）要幂等。这条和第 5 篇的 HITL 重入模式（RerunOnResume）叠加时尤其重要。

NodeCancelled 的注释也值得照抄：

NodeCancelled means the node was cancelled: either because a sibling
node failed and the engine cancelled all running tasks, or because the
invocation context was cancelled from outside the engine. Terminal in
both cases — the two are told apart by whether the run reports an error,
not by this status.

想知道"是我们错了还是被连坐”，看 error，别看 status。handleCompletion 的实现就是按这个来的：

if s.parentCtx.Err() != nil {
	if it.err != nil && !s.echoesCancellation(it.err) {
		ns.Status = NodeFailed
		return it.err                 // 保留原始错误，"says more than cancelled"
	}
	ns.Status = NodeCancelled
	return nil
}
if errors.Is(it.err, context.Canceled) {
	ns.Status = NodeCancelled
	return nil                        // 兄弟取消，不是原始错误
}

（注释里还点名了跨实现对齐：adk-python 在 finally 里 _cleanup_all_tasks 把回收到的任务一律标 CANCELLED。）

生命周期记录：什么能持久化，什么不能#

type NodeState struct {
	Status        NodeStatus   `json:"status"`
	Input         any          `json:"input,omitempty"`
	Output        any          `json:"output,omitempty"`
	TriggeredBy   string       `json:"triggeredBy,omitempty"`
	Branch        string       `json:"branch,omitempty"`
	Interrupts    []string     `json:"interrupts,omitempty"`
	Attempt       int          `json:"attempt,omitempty"`
	ResumedInputs map[string]any `json:"resumedInputs,omitempty"`
	// 私有且不持久化：interruptSchemas、answeredThisTurn
}

type RunState struct {
	Nodes map[string]*NodeState // 缺失条目 = inactive
}

RunState 注释：“It rides in session.State across pause and resume turns”。这带来一条硬性约束，NodeState 的注释直接给了处理方式：

JSON-marshallable: ... The Input, Output, and PendingRequest.Payload fields
are typed any and must therefore be JSON-encodable for the persisted state
to round-trip. Nodes that need to carry binary data across a pause should
store the bytes via agent.Artifacts and stash a URI string in place of the
bytes.

所以：跨暂停传二进制 = 存 artifact，state 里放 URI 字符串。别指望 any 里塞 []byte 之外的自定义类型能活着回来（json.Marshal 会当场失败，或静默丢掉不可导出字段）。

两个"看起来该持久化其实没有"的字段，理解它们能省很多困惑：

  • interruptSchemas：每个请求从事件历史里重建（注释：“the schema lives only in the events and is rebuilt each turn”），所以 Resume 能校验 payload 结构，但你不能从 RunState 里读到它。
  • answeredThisTurn：幂等判据——区分"本轮第一次被回答"和"重复提交的 resume replay"。终端 handoff asker（没有后继）靠它把首轮算作有效 resume、把重复算作 no-op。

Attempt 的措辞要注意：“the number of times this node has been failed” —— 计的是失败次数，不是执行次数。ShouldRetry(cfg, err, failedAttempts) 就是拿它和 MaxAttempts 比。

重试：默认值、两个可测的纯函数、一个反直觉的默认行为#

// 推荐姿势（config.go 注释原样）
rc := workflow.DefaultRetryConfig()   // 返回副本
rc.MaxAttempts = 10
cfg := workflow.NodeConfig{RetryConfig: rc}

默认策略（defaultRetryConfig）：

MaxAttempts: 5, InitialDelay: time.Second, MaxDelay: 60*time.Second,
BackoffFactor: 2.0, Jitter: 1.0, ShouldRetry: defaultShouldRetry,

注释把这套数字翻译成了人话：“5 attempts, 1s initial delay, 60s cap, 2x backoff, full jitter, retry every error”。

⚠️ “retry every error” 和实现有出入，这是本篇最需要提醒的一点。 字段注释写的是"If not specified, default to true"，但代码里的默认是：

func defaultShouldRetry(err error) bool {
	return !errors.Is(err, ErrInputValidation)
}

也就是说默认不重试输入校验失败，ShouldRetry 的理由写在注释里：“we do not retry input validation errors because the input is deterministic per activation. Retrying would just loop on the same failure.”

判断很对，但文档字段和实现不一致——如果你依赖"默认重试一切"，就会踩空。真需要重试校验错误时，注释也给了口子：显式给 ShouldRetry（“This allows users to override the default behavior and retry validation errors if desired”）。

RetryConfig 各字段的精确语义：

字段语义边界
MaxAttempts含首次的总尝试数0 或 1 = 不重试；不填默认 5
InitialDelay首次重试前延迟不填默认 1s
MaxDelay延迟上限不填默认 60s；<=0 时不封顶
BackoffFactor每次乘的倍率1.0 常数、2.0 指数、<1.0 会逐次缩短（允许）；<=0 被当 1.0（否则会塌成 0）
Jitter[0,1] 随机因子实际延迟从 delay * (1 ± Jitter) 采样；0 = 完全确定
ShouldRetry谓词，true 才重试nil 时走 defaultShouldRetry

RetryConfig 是"扁平纯值"结构，注释说明这是刻意的：“no dependency on cenkalti/backoff/v5”。所以延迟算法可以自己单测——两个导出函数就是为此存在的：

d := workflow.CalculateDelay(rc, 3)              // 第 3 次失败后的等待
ok := workflow.ShouldRetry(rc, err, failedCount) // 该不该再试

CalculateDelay 的实现值得看两行，因为它有两个容易忘的行为：抖动是在封顶之后才施加（所以接近 MaxDelay 时可能略微超出），且抖动后 delay < 0 会被夹回 0。写测试时用 Jitter: 0 拿确定值。

为什么别用结构体字面量：注释明确 “Constructing via struct literal is permitted but discouraged: any unset field defaults to its zero value, not to DefaultRetryConfig’s value. The zero RetryConfig is a valid ’no retry, no backoff, no jitter’ policy.” 也就是说 RetryConfig{MaxAttempts: 5} 会得到 InitialDelay: 0（立刻重试 5 次），而不是 1 秒起步。这个坑只有读注释能防住。

NodeConfig.RetryConfig 本身是 *RetryConfig，nil = 该节点不重试（默认不重试！重试是逐节点显式开的）。

并发、超时、取消#

图级上限：workflow.New(name, edges, workflow.WithMaxConcurrency(8))。n <= 0 关闭上限；超额节点停在 NodePending 排队。

⚠️ 注释里的例外必须记住：

Does NOT apply to dynamic sub-nodes invoked via workflow.RunNode from
inside a DynamicNode body — they are awaited inline by the parent and
gating them would deadlock.

节点级并发是另一个旋钮：ParallelWorker（NewParallelWorker(name, wrapped, maxConcurrency, cfg)）和 NodeConfig.ParallelWorker bool。图级管"多少个节点同时在跑"，节点级管"一个列表项并发多少"。两者独立。

超时：NodeConfig.Timeout，注释说清粒度——“bounds a single activation of the node via context.WithTimeout on the per-node context”，每次激活一个预算，0（默认）表示只受父调用 deadline 约束。所以配了重试时，Timeout × MaxAttempts 才是这个节点的最坏墙钟。

取消：cancelAll() 由消费者在 break/失败时调用。工程含义：节点体内一定要尊重 ctx 取消——yield 返回 false 就立刻退出，长循环里加 ctx.Err() 检查。引擎保证 wg.Wait() 后无泄漏，但前提是你的节点会结束。

失败怎么往外报#

type NodeRunError struct {
	ChildName string   // "fixer_agent"
	ChildPath string   // "code_workflow/fixer_agent@2"
	RunID     string   // 自动计数或 WithRunID
	Cause     error
}
// Error(): "workflow: dynamic child <path>: <cause>"

errors.As 拿字段，Unwrap 拿到 cause。外层判定用 errors.Is(err, workflow.ErrNodeFailed)（注释：“wraps a child node’s runtime failure after retries” —— 重试耗尽才算 NodeFailed）。

遥测侧有个细节：isNodeControlFlow(err) 会把 ErrNodeInterrupted 这类控制流错误和真失败分开，不污染 span 的 error 记录。所以你在 trace 里看到"节点红色"就是真失败，不会混进 HITL 暂停。

自检清单#

  • 所有节点对"重跑"安全（NodeRunning 重启后必须重排）
  • RetryConfig 一律从 DefaultRetryConfig() 拿副本再改
  • 需要重试校验错误时显式设 ShouldRetry（默认不重试）
  • 有副作用的节点设 Timeout；估算 Timeout × MaxAttempts 的上界
  • 跨 HITL 暂停传的数据全是 JSON 可编码；二进制走 artifact + URI
  • 动态节点多的图别指望 WithMaxConcurrency 卡住它们（会死锁）
  • “图不 finalize"时先看是不是有节点 NodeWaiting，再分 HITL / fan-in

常见问题

ADK Go 图节点的默认重试策略是什么？

5 次尝试（含首次）、初始延迟 1 秒、上限 60 秒、倍率 2.0、full jitter（Jitter=1.0），且默认不重试 ErrInputValidation。但默认策略只在你显式给 NodeConfig.RetryConfig 时生效——nil 表示不重试。

为什么 RetryConfig 不建议用结构体字面量？

注释明说：字面量未设的字段是零值，不是默认值。零值 RetryConfig 是一个合法的"不重试、不退避、无抖动"策略。要改就 DefaultRetryConfig() 拿副本再覆盖。

NodeWaiting 有几种情况？

两种共用一个状态：① HITL 暂停（yield 了 RequestInput，等 FunctionResponse）；② fan-in（WaitForOutput=true，跑过但前驱没齐）。任一节点处于 NodeWaiting，工作流就不 finalize。

进程重启后 NodeRunning 的节点怎么办？

状态注释明确要求：run state 里存在没有存活任务的 NodeRunning 条目（例如进程重启后）**必须被重新调度**。所以节点体要幂等。

节点被取消是失败吗？

不是。兄弟失败导致的取消返回 nil error（只有原始错误保留），外部取消才让整轮带错误。区分依据是"运行是否报告错误"，不是 NodeCancelled 这个状态本身。

并发上限怎么配？

workflow.New 的 WithMaxConcurrency(n)（n<=0 关闭），超额节点排队成 NodePending。注意它不管 RunNode 派发的动态子节点——那会死锁。
