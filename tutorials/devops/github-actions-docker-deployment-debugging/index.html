GitHub Actions 自动部署 Docker 服务：一场 SSH、端口与 Go 版本的连续排障

记录一次脱敏后的 Docker 服务自动部署排障：从网关端口冲突，到 SSH 密钥、GitHub Environment Secrets、容器内构建和 Go 版本不匹配。

August 29, 2026 · 7 min · 1304 words · 梦兽编程 -  |  English

有些教程里的自动部署，流程通常是这样的：

git push
  ↓
GitHub Actions
  ↓
docker compose up -d
  ↓
部署完成

看起来像一条笔直的高速公路。

真正做过一次的人都知道，现实更像开车去一个陌生城市：导航说还有 20 分钟，结果先遇到入口修路，再遇到收费站不收这张卡，最后发现目的地的门牌号还写错了。

这篇文章记录一次脱敏后的 Docker 服务自动部署过程。案例中的服务叫 example-api，部署到一台已经运行网站网关的 VPS 上。项目名、域名、IP、用户名、目录和所有密钥都使用虚构值。

文章不讨论某一个具体业务，而是记录一条可以迁移到其他项目的排障方法：每次只确认一层，绝不把“看起来应该可以”当成“已经可以”。

一、先把架构想清楚：谁负责什么#

案例中的服务器原本已经运行着一套网站服务：

  • 一个 WordPress 容器；
  • 一个 Caddy 网关容器；
  • 一个数据库容器。

其中，Caddy 已经占用宿主机的 80 和 443 端口，负责公网 HTTPS 和域名路由。

现在要新增一个 Go API 服务。如果把 API 项目自带的 Caddy 也照搬上去，就会出现两个网关争夺同一扇门：

已有网关：宿主机 80/443
新增网关：也想使用宿主机 80/443

Docker 最终会很诚实地报错：

port is already allocated

所以第一步不是写 CI/CD，而是拆分职责：

已有 Caddy
  ├── website.example.com → WordPress
  └── api.example.com     → example-api

example-api
  └── 容器内部监听 8080

API 项目不再启动自己的 Caddy，只启动 API 容器。

二、宿主机端口和容器端口不是一回事#

API 容器内部仍然监听 8080，但不能再占用宿主机的 80 或 443。可以映射到一个只监听本机的高位端口：

services:
  api:
    build:
      context: ..
      dockerfile: deploy/Dockerfile
    restart: unless-stopped
    ports:
      - "127.0.0.1:18080:8080"

这行配置的意思是：

宿主机 127.0.0.1:18080
        ↓
容器内部 8080

这里的三个数字和地址各有含义：

  • 127.0.0.1：只允许宿主机本地访问；
  • 18080：宿主机端口；
  • 8080：容器内部端口。

不要误以为“容器内部使用 8080，所以宿主机 8080 就一定冲突”。只有配置了宿主机端口映射，宿主机才会占用对应端口。

也不要轻易写成：

- "18080:8080"

这种写法会把 18080 监听在所有网卡上，API 可能绕过网关直接暴露到公网。当前方案让网关访问本机 18080，API 本身不直接接受公网流量。

三、GitHub Actions 应该部署谁，而不是重复构建谁#

这个服务的代码在独立仓库中。部署目标是：只要推送到 main，服务器自动拉取最新代码、构建镜像并重启 API。

最初很容易写出一份臃肿的工作流：

Checkout 仓库
  ↓
安装 Go
  ↓
在 GitHub Runner 上运行测试
  ↓
SSH 登录 VPS
  ↓
服务器再拉一次代码
  ↓
服务器再构建 Docker

如果这个工作流的真正目标只是“通知 VPS 部署”，那么 Runner 上的 Checkout、Go 安装和测试并不是必需步骤。它们会增加耗时和失败点，还让人误以为代码已经在 Runner 上构建完成。

更简单的职责划分是：

GitHub Actions
  ├── 验证部署密钥
  └── SSH 到服务器

VPS
  ├── 拉取自己的仓库
  ├── 生成运行时文章或资源
  ├── 构建 Docker 镜像
  └── 启动容器

一个精简后的工作流可以是：

name: Deploy example-api

on:
  push:
    branches:
      - main
  workflow_dispatch:

concurrency:
  group: example-api-production
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    timeout-minutes: 20

    steps:
      - name: Validate deployment key
        env:
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
        run: |
          set -eu
          umask 077
          printf '%s\n' "$DEPLOY_SSH_KEY" > "$RUNNER_TEMP/deploy_key"
          ssh-keygen -y -f "$RUNNER_TEMP/deploy_key" > "$RUNNER_TEMP/deploy_key.pub"
          ssh-keygen -lf "$RUNNER_TEMP/deploy_key.pub"
          rm -f "$RUNNER_TEMP/deploy_key" "$RUNNER_TEMP/deploy_key.pub"

      - name: Deploy to VPS
        uses: appleboy/ssh-action@v1.2.0
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          script_stop: true
          command_timeout: 15m
          script: |
            set -eu
            APP_DIR=/srv/example-api
            cd "$APP_DIR"
            git fetch origin main
            git pull --ff-only origin main
            cd deploy
            docker compose build api
            docker compose run --rm api \
              /app/publish-article \
              -src /app/articles-src \
              -out /app/articles
            docker compose up -d --remove-orphans
            docker compose ps
            curl --fail --silent --show-error \
              http://127.0.0.1:18080/ >/dev/null

真实项目中，production、/srv/example-api 和域名都应该替换成自己的值。本文刻意不使用真实部署信息。

四、环境变量到底配置在哪里：VPS 和 GitHub 是两套系统#

这部分最容易绕晕，因为“环境变量”其实分成两类，分别放在两个地方。

1. VPS 应用变量：放在服务器上的 .env#

这些变量是 API 容器运行时需要的配置，例如：

ADMIN_JWT_SECRET=一串生产环境随机密钥
WECHAT_APP_ID=可选
WECHAT_SECRET=可选
WECHAT_MCH_ID=可选

它们应该放在 VPS 的部署目录中：

/srv/example-api/deploy/.env

然后由 Docker Compose 自动读取：

environment:
  - ADMIN_JWT_SECRET=${ADMIN_JWT_SECRET:?ADMIN_JWT_SECRET is required}

这个 .env 是服务器的生产配置，不要提交到 GitHub。它解决的是：

容器启动时，应用需要哪些运行参数？

2. GitHub Actions 部署 Secret：放在 GitHub 网页#

打开对应的独立服务仓库，例如：

GitHub → example-api 仓库

然后按这个路径进入：

Settings
→ Secrets and variables
→ Actions

页面上有两个区域：

Environment secrets
Repository secrets

本案例使用 Environment secrets。具体操作是：

  1. 在 Settings → Secrets and variables → Actions 页面找到 Environments 区域；

  2. 点击 Manage environments；

  3. 创建一个环境，名称使用：

    production

  4. 进入 production 环境；

  5. 找到 Environment secrets；

  6. 点击 Add secret 或 New environment secret；

  7. 依次添加：

    DEPLOY_HOST
DEPLOY_USER
DEPLOY_SSH_KEY

这三个值的含义是：

Secret 名称填写内容
DEPLOY_HOSTVPS 公网 IP 或部署域名，不带 https:// 和端口
DEPLOY_USERVPS 上实际用于部署的 Linux 用户，例如 deploy
DEPLOY_SSH_KEYGitHub Actions 登录 VPS 的私钥全文

私钥必须包含完整边界：

-----BEGIN OPENSSH PRIVATE KEY-----
...
-----END OPENSSH PRIVATE KEY-----

不要填写：

私钥密码
VPS 登录密码
.pub 公钥文件

3. Environment 名称必须和 YAML 一致#

如果 Secret 配置在 production 环境，工作流的 Job 必须写：

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production

如果没有这一行，即使 GitHub 页面上能看到三个 Secret，工作流也可能读不到它们，最终出现：

Error: missing server host

Secret 的引用方式仍然是：

host: ${{ secrets.DEPLOY_HOST }}
username: ${{ secrets.DEPLOY_USER }}
key: ${{ secrets.DEPLOY_SSH_KEY }}

4. Repository secrets 和 Environment secrets 不要混淆#

如果你把 Secret 放在 Repository secrets，工作流不需要声明 Environment；如果你把 Secret 放在 Environment secrets，工作流必须绑定对应 Environment。

两种方式都可以，但一个项目最好只选一种。排障时先回答三个问题：

Secret 在 Repository 还是 Environment？
Environment 的准确名称是什么？
Job 的 environment 是否写了同一个名称？

5. 配置后的安全验证#

GitHub 不会显示 Secret 原文，这是正常的。可以在工作流中只输出私钥导出的指纹，不能输出私钥：

- name: Validate deployment key
  env:
    DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
  run: |
    set -eu
    umask 077
    printf '%s\n' "$DEPLOY_SSH_KEY" > "$RUNNER_TEMP/deploy_key"
    ssh-keygen -y -f "$RUNNER_TEMP/deploy_key" > "$RUNNER_TEMP/deploy_key.pub"
    ssh-keygen -lf "$RUNNER_TEMP/deploy_key.pub"

VPS 上检查：

ssh-keygen -lf /home/deploy/.ssh/authorized_keys

两个指纹必须一致。

这次排障得到的第一个教训是：

VPS .env 负责容器运行，GitHub Environment Secrets 负责 Actions 登录服务器；两者不能互相替代。

五、第一次失败：Environment Secret 明明存在，Actions 却说没有 Host#

第一次运行时，SSH Action 报错：

Error: missing server host

当时 GitHub 页面上确实能看到：

DEPLOY_HOST
DEPLOY_USER
DEPLOY_SSH_KEY

问题在于，它们被配置在了 GitHub Environment，而工作流没有绑定这个 Environment。

GitHub Secrets 有几个层级：

Repository secrets
Environment secrets
Organization secrets

工作流读取：

${{ secrets.DEPLOY_HOST }}

并不代表它会自动读取任意 Environment 下的同名 Secret。Job 必须声明对应环境：

jobs:
  deploy:
    environment: production

如果 Environment 的名字是 production，就必须写：

environment: production

如果三个 Secret 被放到了名为 DEPLOY_HOST 的 Environment，就必须写：

environment: DEPLOY_HOST

这个名字虽然不够优雅，但能工作。

这次排障得到的第二个教训是：

Secret 存在，不等于当前 Job 有权限读取它。先检查 Secret 所属层级，再检查 Job 是否绑定对应 Environment。

五、第二次失败：SSH 握手失败#

绑定 Environment 后，错误从：

missing server host

变成了：

ssh: handshake failed: ssh: unable to authenticate
attempted methods [none publickey]

这是一个重要变化。

它说明：

GitHub Actions 已拿到 Host
GitHub Actions 已经连接到 SSH 端口
但公钥认证没有通过

SSH 自动部署需要两边各有一半：

GitHub Secret DEPLOY_SSH_KEY
        = 私钥

VPS ~/.ssh/authorized_keys
        = 对应的公钥

私钥和公钥不是把同一段文本复制两遍，而是密码学上的一对钥匙。

VPS 上必须存在：

/home/deploy/.ssh/authorized_keys

文件名不能写成：

authorized_key
authorized-keys
authorized_keys.txt

权限也必须正确：

chmod 700 /home/deploy/.ssh
chmod 600 /home/deploy/.ssh/authorized_keys
chown -R deploy:deploy /home/deploy/.ssh

六、不要凭感觉判断钥匙是否相同，要看指纹#

“我已经配置了同一把私钥”这句话，人工很难验证。SSH 指纹可以把这个问题变成一个简单的字符串比较。

GitHub Runner 侧可以从 Secret 中导出公钥并打印指纹：

printf '%s\n' "$DEPLOY_SSH_KEY" > /tmp/deploy_key
ssh-keygen -y -f /tmp/deploy_key > /tmp/deploy_key.pub
ssh-keygen -lf /tmp/deploy_key.pub

VPS 侧查看授权公钥指纹：

ssh-keygen -lf /home/deploy/.ssh/authorized_keys

两边必须完全一致：

GitHub Secret 导出的指纹
        =
VPS authorized_keys 中的指纹

一次排障中，两边的指纹分别是：

GitHub：SHA256:AAAA...
VPS：   SHA256:BBBB...

虽然两边看起来都像“有效的 ED25519 密钥”，但 AAAA 和 BBBB 不一样，认证当然失败。

这往往是因为：

  • 把另一把私钥复制到了 GitHub；
  • 复制了 .pub 文件而不是无扩展名的私钥；
  • 修改了错误的 Environment；
  • VPS 上生成了新密钥，但 GitHub Secret 仍是旧密钥。

这次排障得到的第二个教训是：

不要比较文件名，也不要比较“我记得是那一把”；直接比较公钥指纹。

七、第三次失败：本地能连 SSH，GitHub Runner 却超时#

密钥修正后，某次运行又出现：

dial tcp <host>:22: i/o timeout

这和“unable to authenticate”完全不是同一类问题。

前者是：

网络连接阶段失败

后者是：

网络连接成功，身份认证失败

本地执行：

nc -vz example.com 22

显示成功，只能说明：

你的电脑 → VPS:22

是通的。

GitHub Actions 走的是另一条路径：

GitHub Runner → VPS:22

两者来源 IP 不同。可能的拦截位置包括：

  • VPS 内部 UFW；
  • 云厂商安全组；
  • fail2ban；
  • SSH 只监听了回环地址；
  • 错误的 DNS 或 IPv6 记录；
  • 机房对部分来源网络做了限制。

检查 VPS：

sudo ss -ltnp | grep ':22'
sudo ufw status verbose
sudo fail2ban-client status

如果需要观察 SSH 服务是否收到连接：

sudo journalctl -u ssh -f

但要注意：如果防火墙在 SSH 服务之前就丢弃数据包，sshd 日志里可能什么都没有。这时要看云安全组或用网络抓包确认。

另一个容易忽略的问题是 DEPLOY_HOST 的格式���它应该是：

203.0.113.25

而不是：

https://203.0.113.25
203.0.113.25:22
ssh://203.0.113.25

如果使用非标准 SSH 端口，则显式配置：

port: ${{ secrets.DEPLOY_PORT }}

并在 Environment 中添加：

DEPLOY_PORT=2222

这次排障得到的第三个教训是：

本地能连，不代表 GitHub Runner 能连。先按 TCP 网络层、SSH 握手层、远程命令层分别判断。

八、第四次失败：远程服务器没有 Go#

网络和密钥问题解决后，远程诊断终于开始输出：

=== remote identity ===
uid=1001(...)
srv-example
/home/...
=== runtime versions ===

然后在这里失败：

command -v go

原因很简单：VPS 上没有安装 Go。

但这里又出现了一个架构问题：既然服务本来就用 Docker，为什么还要求宿主机安装 Go？

答案是：部署脚本错误地在宿主机执行了：

go run ./cmd/publish-article

这其实把构建环境和运行环境混在了一起。

更合理的做法是让 Docker 自己完成 Go 编译。宿主机只负责：

Git
Docker
Docker Compose
SSH

九、把资源生成工具也编译进 Docker 镜像#

Dockerfile 使用多阶段构建：

FROM golang:1.25-alpine AS builder
WORKDIR /build

COPY go.mod go.sum ./
RUN go mod download
COPY . .

RUN CGO_ENABLED=0 go build -o /app/server ./cmd/server
RUN CGO_ENABLED=0 go build -o /app/publish-article ./cmd/publish-article

FROM alpine:3.19
RUN apk add --no-cache ca-certificates
WORKDIR /app

COPY --from=builder /app/server .
COPY --from=builder /app/publish-article .
COPY migrations ./migrations

EXPOSE 8080
CMD ["./server"]

Compose 需要把源文件目录挂载给临时容器：

volumes:
  - ./data:/app/data
  - ./articles:/app/articles
  - ../articles-src:/app/articles-src:ro

部署时先构建镜像，再用临时容器生成运行时文件：

docker compose build api

docker compose run --rm api \
  /app/publish-article \
  -src /app/articles-src \
  -out /app/articles

docker compose up -d --remove-orphans

这条链路中，Go 只出现在：

Docker builder 阶段

VPS 宿主机完全不需要 Go。

十、第五次失败：Go 版本不满足 go.mod#

改成容器内构建后，部署又前进了一步，但 Docker 构建报错：

go.mod requires go >= 1.25.0
running go 1.24.13

这次不是 VPS 没有 Go，而是 Dockerfile 中的 builder 镜像版本落后于项目要求：

FROM golang:1.24-alpine

而 go.mod 要求：

go >= 1.25.0

修复为：

FROM golang:1.25-alpine AS builder

这件事很容易被忽略，因为开发机上的 Go 版本可能已经够新，只有干净的 CI/CD 环境才会暴露问题。

部署前应该明确检查：

go version
grep '^go ' go.mod

并让以下版本保持一致：

开发机 Go 版本
CI Runner Go 版本（如果使用）
Docker builder Go 版本
项目 go.mod 要求

这次排障得到的第四个教训是：

Dockerfile 里的基础镜像也是项目依赖。不要只看代码版本，还要看构建环境版本。

十一、让诊断日志按层输出#

最后成功的关键，不是增加更多命令，而是把命令按层分组：

echo "=== remote identity ==="
whoami
id
hostname
pwd

echo "=== runtime versions ==="
command -v docker
docker --version
docker compose version

echo "=== deployment paths ==="
stat -c '%A %U:%G %n' \
  "$HOME" "$HOME/.ssh" "$HOME/.ssh/authorized_keys" \
  "$APP_DIR" "$APP_DIR/.git" 2>&1 || true

echo "=== authorized key fingerprints ==="
ssh-keygen -lf "$HOME/.ssh/authorized_keys" 2>&1 || true

echo "=== port and docker state ==="
ss -ltn 2>/dev/null | grep -E ':(22|18080)\\b' || true
docker ps

这样看日志时，可以迅速判断失败层级：

层级典型错误说明
Secretmissing server hostEnvironment 没绑定或 Secret 不可见
SSH 网络i/o timeoutTCP 连接没有建立
SSH 认证unable to authenticate私钥、公钥、用户或权限问题
远程环境command not foundVPS 缺少命令或 PATH 不对
Gitcould not readVPS 拉仓库权限问题
Composerequired variable missing服务器 .env 缺失或变量为空
Docker 构建go.mod requiresbuilder 基础镜像版本不匹配
健康检查curl --fail容器没启动、端口错误或 API 未就绪

最怕的不是失败，而是所有失败都只显示一句“部署失败”。那样排障就像闭着眼修钟表，拆到哪儿算哪儿。

十二、最终的自动部署闭环#

完整流程应该是：

向独立仓库 push
        ↓
GitHub Actions 触发
        ↓
读取 production Environment Secrets
        ↓
验证部署私钥指纹
        ↓
SSH 登录 VPS
        ↓
进入固定项目目录
        ↓
git fetch + git pull
        ↓
Docker 构建镜像
        ↓
容器内生成运行时文章/资源
        ↓
docker compose up -d
        ↓
检查容器状态
        ↓
检查 127.0.0.1:18080
        ↓
现有网关代理公网域名

最终的职责关系是：

主站仓库
  → 构建免费内容

这次排障表面上遇到了很多问题：

  • 网关端口冲突；
  • Environment Secret 不可见；
  • SSH 公钥认证失败；
  • GitHub Runner 连接超时；
  • VPS 没有 Go；
  • Docker builder 的 Go 版本过低。

它们其实都指向同一个根问题：系统边界没有一开始就说清楚。

谁占用 80/443？谁负责 HTTPS？谁负责拉代码？Go 在宿主机还是容器里？Secret 属于哪个 Environment？文章源稿在哪里？运行时文件由谁生成？

这些问题如果不提前回答，部署工具就会替你随机回答，而且通常回答得不太客气。

真正可靠的 CI/CD，不是把一堆命令塞进 YAML，而是让每个组件只做自己应该做的事：

GitHub Actions 负责触发和连接
VPS 负责拉取和运行
Docker 负责构建环境
Compose 负责容器编排
现有网关负责公网入口

当这些边界真正清楚之后，部署才会从“每次都要祈祷”变成“推送之后等日志”。

常见问题

为什么新增 API 容器时报错 port is already allocated？

因为已有 Caddy 网关已经占用了宿主机的 80 和 443 端口，新增 API 项目如果自带 Caddy 也要使用宿主机 80/443，就会产生端口冲突。解决办法是拆分职责：API 不再启动自己的网关，只启动 API 容器，并把容器端口映射到宿主机高位端口。

映射端口时 127.0.0.1:18080:8080 和 18080:8080 有什么区别？

127.0.0.1:18080:8080 只允许宿主机本地访问 18080，API 不会直接暴露到公网；18080:8080 会把 18080 监听在所有网卡上，API 可能绕过网关直接暴露到公网。建议使用前一种。

GitHub Actions 里需要先 Checkout 代码、安装 Go 并构建吗？

如果工作流的目标只是通知 VPS 部署，就不需要。更简单的职责划分是：GitHub Actions 只验证部署密钥并 SSH 到服务器；VPS 自己拉取仓库、构建 Docker 镜像并启动容器。这样能减少耗时和失败点。

API 运行时需要的环境变量应该放在哪里？

放在 VPS 部署目录中的 .env 文件里，例如 /srv/example-api/deploy/.env，然后由 Docker Compose 自动读取。该 .env 是服务器生产配置，不要提交到 GitHub。

Environment secrets 和 Repository secrets 有什么区别？使用 Environment secrets 时要注意什么？

如果把 Secret 放在 Repository secrets，工作流不需要声明 Environment；如果放在 Environment secrets，工作流必须绑定对应 Environment。两种方式都可以，但一个项目最好只选一种。排障时先确认 Secret 在哪个区域、Environment 的准确名称、Job 的 environment 是否写一致。
