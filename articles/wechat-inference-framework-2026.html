llama.cpp · vLLM · SGLang 推理框架深度对比

梦兽编程 · 2026年7月

框架性能不是常数，而是你流量的函数。

如果你在 2026 年问任何一个做过自托管推理的工程师「哪个框架最强」，你大概率会得到三种完全不同的答案——而且他们都没有撒谎。

同样跑 Llama 3.3 70B，vLLM 和 SGLang 的吞吐差距在纯净负载下只有 1-4%——落在运行间噪声范围内。但在 Agent 多轮负载下，SGLang 能把后续请求延迟从 1.8 秒压到 0.35 秒。差距不是「谁更快」，而是「你的流量长什么样，决定谁的快对你有效」。

💡 本文不列参数表。只追问一个问题：
当你面对这三个框架时，什么才是真正影响你决策的变量？

三强定位速览

🦙 llama.cpp

MIT · C/C++ · 11.8 万 Stars

核心：GGUF 量化 + ggml 可移植运行时
缓存：基础分页 · 无连续批处理
适用：个人验证 / 消费级硬件 / 隐私场景

⚡ vLLM

Apache 2.0 · Python/C++ · 7.8 万 Stars

核心：PagedAttention + 连续批处理
缓存：16-token 块级分页 · 显存浪费 <4%
适用：高并发 API / 生产推理 / 多硬件

🧠 SGLang

Apache 2.0 · Python+Rust · 2.7 万 Stars

核心：RadixAttention + 零开销调度
缓存：token 级基数树 · 任意重叠命中
适用：多 Agent / 前缀密集 / RL 后端

KV 缓存的三条哲学路线

KV 缓存管理是推理框架的灵魂——它决定了同样一张 GPU 能同时服务多少个请求。三个框架在这个问题上走出了三条截然不同的道路：

框架 KV 缓存策略 设计哲学 并发上限
🦙 llama.cpp 基础分页 "够用就行" ~16 槽位
⚡ vLLM PagedAttention 块级分页 "榨干每一字节显存" 百级并发
🧠 SGLang RadixAttention 基数树 "缓存是一等公民" 百级 + 前缀复用

一个你大概率没测过、但决定了一切的指标

🔍 为什么大多数团队没测这个？

他们测了吞吐、延迟、并发上限——但没测那个真正决定「SGLang 的 RadixAttention 值不值得额外运维复杂度」的指标。

结果：用 vLLM 跑 Agent 抱怨延迟高，用 SGLang 跑代码补全抱怨「怎么跟 vLLM 差不多还多了一套路由要维护」。

推荐成长路径

不是「三选一」，而是「三段式」

① llama.cpp 验证想法 → ② vLLM 承载生产流量 → ③ SGLang 优化 Agent 流量

三个阶段有三个评估标准：验证期看「能不能跑」，生产期看「稳不稳定」，优化期看「快了多少」

三个可带走的原则

1. 前缀重叠率是你最应该测、但大概率没测的指标

比任何第三方 benchmark 都更能预测框架在你流量上的表现。测法：抓几千条 prompt，统计请求间的 LCP 分布。

2. 「先 vLLM 后 SGLang」不是保守，是唯一不靠猜的路径

vLLM 的文档和生产履历能兜底所有「第一次部署」的坑；SGLang 的加速比需要在你的流量上复测才能确认。两者都是 OpenAI 兼容 API，迁移只需改 base URL。

3. 框架不是「选一次」的决策，是「持续评估」的过程

三框架均以周为单位迭代。成熟的团队不是在选框架，而是在建路由——按模型与负载类型在网关层共存。
