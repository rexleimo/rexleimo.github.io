三强争霸还是各取所需？llama.cpp、vLLM 与 SGLang 推理框架深度选型

梦兽编程 · 2026年7月

框架性能不是常数，而是你流量的函数。

同样跑 Llama 3.3 70B，vLLM 和 SGLang 的吞吐差距在纯净负载下只有 1-4%。但在 Agent 多轮负载下，SGLang 能把后续请求延迟从 1.8 秒压到 0.35 秒。差距不是「谁更快」，而是「你的流量长什么样，决定谁的快对你有效」。

本文不列参数表。只追问一个问题：当你面对这三个框架时，什么才是真正影响你决策的变量？

三强定位速览

🦙 llama.cpp

MIT · C/C++ · 11.8 万 Stars

核心：GGUF 量化 + ggml 可移植运行时
缓存：基础分页 · 无连续批处理
适用：个人验证 / 消费级硬件 / 隐私场景

⚡ vLLM

Apache 2.0 · Python/C++ · 7.8 万 Stars

核心：PagedAttention + 连续批处理
缓存：16-token 块级分页 · 显存浪费 <4%
适用：高并发 API / 生产推理 / 多硬件

🧠 SGLang

Apache 2.0 · Python+Rust · 2.7 万 Stars

核心：RadixAttention + 零开销调度
缓存：token 级基数树 · 任意重叠命中
适用：多 Agent / 前缀密集 / RL 后端

KV 缓存的三条哲学路线

KV 缓存管理是推理框架的灵魂——它决定了同样一张 GPU 能同时服务多少个请求。

框架 KV 缓存策略 设计哲学 并发上限
🦙 llama.cpp 基础分页 "够用就行" ~16 槽位
⚡ vLLM PagedAttention 块级分页 "榨干每一字节显存" 百级并发
🧠 SGLang RadixAttention 基数树 "缓存是一等公民" 百级 + 前缀复用

最关键的选型指标：前缀重叠率

前缀重叠率

= 流量中多少比例的请求共享了相同的开头 token

< 40%

vLLM 与 SGLang 性能等价 → 选 vLLM

40–60%

SGLang 收益开始显现 → 值得测试

> 60%

TTFT 降 37% · 成本降 30% → 选 SGLang

大多数团队没测这个——他们测了吞吐、延迟、并发上限，但没测那个真正决定「SGLang 值不值得」的指标。结果：用 vLLM 跑 Agent 抱怨延迟高，用 SGLang 跑代码补全抱怨没区别。

推荐成长路径

不是「三选一」，而是「三段式」

① llama.cpp
验证想法 → ② vLLM
承载生产 → ③ SGLang
优化 Agent

验证看「能不能跑」· 生产看「稳不稳定」· 优化看「快了多少」

三个可带走的原则

1. 前缀重叠率是你最应该测、但大概率没测的指标

比任何第三方 benchmark 都更能预测框架在你流量上的表现。抓几千条 prompt，统计请求间的 LCP 分布。

2. 「先 vLLM 后 SGLang」不是保守，是唯一不靠猜的路径

vLLM 兜底「第一次部署」的所有坑；SGLang 的加速比需在你的流量上复测。两者都兼容 OpenAI API，迁移只需改 base URL。

3. 框架不是「选一次」的决策，是「持续评估」的过程

三框架均以周为单位迭代。成熟团队不是在选框架，而是在建路由——按模型与负载类型在网关层共存。
