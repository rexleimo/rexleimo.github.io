Codex 总是忘记前面的代码？372K 上下文到底有没有用

梦兽编程 · Codex CLI 0.146.0 上下文窗口实验

Codex 做大型项目做到一半，开始忘记前面改过的文件；刚刚解释过的架构，它又重新问一遍；终端里还出现了上下文压缩。

很多人第一反应是：把上下文窗口调大不就行了？

这篇文章用 Codex CLI 0.146.0 做了一次实验：默认 272K，实验配置 372K，95% 有效窗口对应 353400。

先说结论：这不是模型升级，也不是让服务端凭空获得更大的上下文能力。它修改的是 Codex 客户端读取到的模型元数据和上下文预算。

一、当前 Codex CLI 的默认值

先确认本机版本：

codex --version

本文实测版本：

codex-cli 0.146.0

再查看当前模型目录：

codex debug models

GPT-5.6-Sol 的默认元数据类似：

{
  "slug": "gpt-5.6-sol",
  "context_window": 272000,
  "max_context_window": 272000,
  "effective_context_window_percent": 95,
  "multi_agent_version": "v2"
}

默认有效窗口大约是：

272000 × 95% = 258400

二、372000 和 353400 分别是什么？

实验配置将本地模型目录中的窗口改成：

{
  "context_window": 372000,
  "max_context_window": 372000,
  "effective_context_window_percent": 95
}

于是得到：

372000 × 95% = 353400

95% 是 Codex 为系统提示词、工具调用和模型输出预留空间后，认为可以用于输入的比例。

353400 是 Codex 客户端计算出来的有效窗口，不等于服务端模型一定支持 353400 tokens。

三、它到底能解决什么问题？

如果任务经常接近上下文上限，这项配置可能带来一些帮助：

  • 更晚触发上下文压缩；
  • 大型代码仓库分析时保留更多文件；
  • 长日志排查时减少前文丢失；
  • 长时间运行的 Agent 任务更从容。

但它不会改变：

  • GPT 模型本身的推理能力；
  • 服务端真实上下文上限；
  • 不同任务之间的永久记忆；
  • 模型理解超长内容时的注意力分配。

更准确的表述：它可能扩大 Codex 的“上下文预算”，但不会扩大模型的“理解能力”。

四、为什么要同时修改 max_context_window？

Codex 客户端通常会把运行时配置和模型元数据的最大值进行比较：

最终窗口 = min(配置值, max_context_window)

如果只在 config.toml 中设置 372000，但模型目录仍然是 272000，配置可能会被限制回 272000。

五、配置前先备份

Windows PowerShell 示例：

$codexHome = if ($env:CODEX_HOME) {
    $env:CODEX_HOME
} else {
    Join-Path $HOME ".codex"
}

$backupDir = Join-Path $codexHome ("backups\context-window-" + (Get-Date -Format "yyyyMMdd-HHmmss"))
New-Item -ItemType Directory -Path $backupDir -Force | Out-Null

foreach ($name in @("config.toml", "custom_models.json")) {
    $source = Join-Path $codexHome $name
    if (Test-Path -LiteralPath $source) {
        Copy-Item -LiteralPath $source -Destination (Join-Path $backupDir $name) -ErrorAction Stop
    }
}

如果当前没有 custom_models.json，不要直接创建一个不完整的 JSON 文件，应该从当前模型目录生成完整文件。

六、修改配置并验证

在 ~/.codex/config.toml 顶层设置：

model = "gpt-5.6-sol"
model_context_window = 372000
model_catalog_json = "~/.codex/custom_models.json"

然后重新执行：

codex debug models

如果 Sol 显示 372000，说明本地模型目录被读取。注意：这还不能证明服务端支持 353400。

七、必须做长任务对照测试

新建一个 Codex 任务，不要继续使用旧任务。用同一个项目、同一个模型和同一个提示词，比较默认配置与实验配置：

  • 第一次上下文压缩发生在哪一轮；
  • 最大 token 使用量；
  • 是否出现 context length exceeded；
  • 任务耗时和输出质量；
  • 是否出现服务端截断。

本地事件中的：

task_started.model_context_window
token_count.info.model_context_window

验证标准：客户端显示 353400，只能证明本地配置生效；真实长任务结果，才能证明配置有用。

八、如何回滚

关闭 Codex，恢复备份的 config.toml 和 custom_models.json，然后重新执行：

codex debug models

如果服务端报错，不要继续提高数值，直接回滚到默认配置。

最终结论

这项配置不是模型升级、无限上下文、永久记忆或服务端限制突破。

它更接近：修改 Codex CLI 本地模型元数据，尝试让客户端使用更大的上下文预算。

对于大型代码仓库、长时间运行的 Agent 任务、频繁触发上下文压缩的用户，这种调整可能有帮助；对于普通短任务，基本没有明显收益。

最终请记住：

本地元数据变大，不等于服务端真实上限变大。
