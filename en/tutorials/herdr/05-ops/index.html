Module 5: Troubleshooting and Tuning

The first four modules covered features: what it is, how to use it, and how code controls it. This module covers what to do when something breaks and how to tune it into the shape you want.

Both topics look unglamorous, yet they decide whether you can rely on a tool long-term. A feature can be excellent, but if the diagnosis order is unclear and you cannot tell why a configuration change did nothing, you will still uninstall it the second time you hit the same bug.

All three articles follow one principle: give the judgement first, then the remedy, and finally the cost. Because the most expensive action in troubleshooting is rarely a wrong command — it is not knowing whether that command will kill running processes.

Baseline: herdr 0.9.2 stable · docs pinned to v0.9.2 Measured: log paths and structure, config check, reload-config, launchctl managername, a 377-line default config, 208 configuration keys across 14 sections

Learning goals

After this module you can answer:

  • Where to investigate an anomaly: the outer terminal, the operating system, or Herdr itself — and why that order cannot be reversed
  • Why herdr server stop ends all pane processes, and what to use instead in a named session
  • Double key presses, a misplaced IME candidate window, and ;3D appearing from an Option+arrow key — whose problem is each
  • Why “SSH or DNS fails after logout” cannot be fixed by logging back in or by live handoff
  • After editing config.toml, how to tell whether the key name is wrong, the setting belongs to the other process, or it is startup-only
  • Which experimental switch is the nested-launch gate you met in module 4
  • On Windows: what is usable, what is partial, what is explicitly unsupported, and which two partials actually affect daily work

One-sentence conclusion

For troubleshooting, split “who owns the problem”; for tuning, split “who owns this setting”. The first decides whether you change the terminal, the OS, or Herdr; the second decides whether you reload or restart a session. And the cost awareness behind both is the same single fact: server stop ends pane processes, so confirm there is nothing running in there first.

Three counter-intuitive points in this module

  1. launchctl managername returning Background does not indicate a Keychain problem — measured on this machine it is exactly that value. It is the normal state of an auto-started server, and many people skip this step and restart for nothing.
  2. Logging back in does not repair the server with broken SSH/DNS after a macOS logout, and live handoff cannot repair it either, because handoff preserves the very context that is broken. This needs a full restart.
  3. Keys that work outside Herdr but not inside it is a real phenomenon: kitty’s automatic zsh integration installs its bindings only for shells it launches itself, not for shells created by a multiplexer.
