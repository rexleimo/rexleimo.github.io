Herdr Configuration in Depth: 208 Keys Across 14 Sections, and What "I Reloaded but Nothing Changed" Really Means

Reorganise Herdr's 208 configuration keys by which process owns them and when they take effect, rather than by name: where the config file lives and the Windows difference, how to use the 377-line herdr --default-config, the real output of herdr config check and server reload-config, what a reload applies to and what it cannot (pane defaults, worktrees, integrations, and custom commands belong to the server; themes, sidebar, and copy behaviour belong to the client), the real rules behind headless_cols and headless_rows, the trade-offs in the three terminal keys, the difference between keys.prefix and direct keys, and the observation that experimental.allow_nested is exactly the nested-launch gate from module 4. Includes a 14-section key-count table and a risk ranking of the experimental keys. Baseline herdr 0.9.2.

September 30, 2026 · 13 min · 2624 words · Mengshou Programming -  |  中文

Herdr has 208 configuration options. Memorising them by name is obviously wasteful — but grouping them by name is also wrong, because what actually determines whether a configuration change takes effect is which process owns that setting.

In one config.toml, a theme change takes effect on reload, a pane default shell applies only to newly created panes, and a graphics switch needs a server restart. That is not a bug; those settings belong to different processes with different responsibilities.

This article reorganises the 208 keys around “who owns it / when does it apply”, and ranks the experimental keys by risk so you know what each true is buying you.

Baseline: herdr 0.9.2 stable · macOS · key counts and defaults come from the config-reference.json cached on this machine (14 sections); the herdr -V / config check / reload-config outputs are measured.

Conclusion first#

Herdr’s configuration applies at three tiers: client hot reload, server reload, and startup-only restart. When a change has no effect, first ask which process owns the setting, then whether it is startup-only — those two questions resolve most “but I definitely changed it” cases. And separately, turning a problem off and turning it on each have costs (cursor anchoring, the IME cursor, nested launching); the trade-off sentences in the descriptions matter more than the defaults.

1. Where the 208 keys and the config file live#

Location#

Linux / macOS:  ~/.config/herdr/config.toml
Windows:         %APPDATA%\herdr\config.toml

herdr --help shows the resolved path for your machine. The socket: field of herdr status points into the same root directory (measured: /Users/rex/.config/herdr/herdr.sock).

Starting from the defaults#

herdr --default-config          # print the full default config, 377 lines measured
herdr --default-config > ~/.config/herdr/config.toml   # start from zero

You can also look up just one key’s correct name and values:

herdr --default-config | grep -n 'headless_cols\|allow_nested'

Measured, those keys are in commented-out state in the default config (# allow_nested = false and similar), which means a misspelled key name produces no error — the reload succeeds and the setting does nothing. When a setting fails to apply, confirm the spelling first.

Validating and applying#

herdr config check              # validate the config
herdr server reload-config      # make the running server re-read it

Both outputs measured on this machine:

$ herdr config check
config: ok

$ herdr server reload-config
{"id":"cli:server:reload-config","result":{"diagnostics":[],"status":"applied","type":"config_reload"}}

An empty diagnostics array means the reload produced no diagnostics. Per the docs, an invalid value makes Herdr fall back to a safe default with a startup warning — so “configured wrong and nobody told you” is possible on the hot path, and that one line of config check is worth running after every edit.

3. Three tiers of application: who owns this setting#

This is the core of the article. The docs draw the boundary plainly:

Themes, sidebar layouts, copy behaviour, and other presentation settings come from the client’s local config, including when you are viewing an SSH machine. Pane defaults, worktrees, integrations, and custom commands belong to the server where the panes run. The UI’s reload config action reloads both the client’s local settings and the selected server’s config.

Which yields three tiers:

TierRepresentative keysHow a change takes effect
Client, hottheme.*, ui.* (sidebar, copy, toast, sound), local keys.*reload config is enough
Server, on reloadterminal.*, worktrees.*, session.*, remote.*, advanced.*server reload-config
Startup-only, restart requiredexperimental.kitty_graphics (docs: restart the server or reattach the client), session.startup_per_agent_delay_ms (docs: restart the server to apply), ui.sidebar_start_collapsed (docs: takes effect on the next launch)restart the corresponding session

So “I changed the theme and nothing happened” and “I changed the default shell but new panes still use the old one” are two different phenomena: the first means the client never received the reload, the second is normal — existing panes keep their current shell until they are recreated.

One exception in keybindings#

Local keybindings do reload, but with --remote-keybindings server you are using the selected server’s keybindings instead. So which set you are editing depends on which keybinding mode you run.

4. The server section: headless size, and your CI#

[server]
headless_cols = 160
headless_rows = 50

These two apply only when no client is attached (both are commented out in the measured default config, i.e. 120×40). The complete rules:

Client stateBehaviour
0All layout and new panes use the configured virtual size
1All tabs follow it
SeveralEach viewed tab follows the client that most recently focused, selected, or interacted with it
2 → 1Everything immediately returns to the remaining client’s size
1 → 0Existing pane PTYs keep their last size; only new layout uses the configured fallback

That last row is the important one: once a client has connected, when all clients disconnect the PTY size stays wherever the last client left it — only brand-new panes use the headless fallback.

That matters when you run Herdr in CI: if you connected a TUI first and then disconnected before running a script that measures layout, the size you get differs from a purely headless run. Either never connect, or set the values before you connect.

5. The terminal section: three commonly misunderstood keys#

default_shell#

[terminal]
default_shell = "nu"

This is an executable name or path, not a shell command line — writing "nu --login" is invalid. When empty it falls back to $SHELL, then /bin/sh on Unix; on Windows it uses pwsh.exe when that resolves on PATH and otherwise the inbox powershell.exe. Existing panes keep their current shell until they are recreated.

shell_mode#

[terminal]
shell_mode = "auto"   # the default

Three values: auto, login, non_login.

auto is most useful on macOS: it starts login shells in new panes, so PATH setup that only runs in a login shell — /usr/libexec/path_helper, Homebrew shell initialisation — actually takes effect. Other platforms keep the existing non-login behaviour.

If you have ever hit “the command brew installed is not found in a new pane”, shell_mode = "login" is the cure.

new_cwd#

[terminal]
new_cwd = "follow"   # the default
ValueBehaviour
followInherits the source pane or workspace cwd (the default). With no source workspace, $HOME is used
homeAlways $HOME
currentHerdr’s process directory
A fixed pathFor example "~/Projects"

Whatever you choose, an explicit --cwd from the CLI or socket API still takes precedence (article 1 measured --cwd /tmp being normalised to /private/tmp).

kitty_graphics#

Defaults to true. The docs contain one sentence worth remembering: “the external socket pane-overlay API is no longer available” — so the “external socket pane overlay for images” approach found in older tutorials no longer works in 0.9.2. Disable it with false, and note the requirement to restart the server or reattach the client.

6. The keys section: prefix versus direct keys#

keys.prefix = "ctrl+b"

The default prefix is ctrl+b. Keybinding strings have two meanings, and this distinction is the most common source of configuration mistakes:

SpellingMeaning
prefix+nPress the configured prefix, then n
ctrl+alt+nA direct shortcut that does not enter prefix mode

Module 1 article 2 covers keybindings in depth. The configuration-specific point worth adding: the keys section has 63 keys, one of the two largest sections, and prefix itself accepts an array so you can have several prefix keys at once (for example "f12").

A direct keybinding that does nothing is usually not a problem here — follow the elimination order in the troubleshooting article section 7 (OS layer, terminal layer, Herdr layer).

7. update and manifest_check: detection rules have their own channel#

[update]
channel = "stable"
version_check = true
manifest_check = true

manifest_check controls background updates of the agent detection manifests (the rules from module 3). Turn it off and detection uses only the manifests bundled in the binary.

Article 2 measured the return of server.agent_manifests: 22 agents, 21 from remote, 1 bundled, each with a date-style version such as 2026.09.23.1. Therefore:

  • “An old Herdr binary” does not mean “old detection rules” — manifests update independently and need no restart
  • When investigating “detection behaviour changed”, look at the manifest version, not at herdr -V

channel has an extra meaning on Windows: a stable Windows install defaults to stable, while an existing preview install stays on preview until you explicitly run herdr channel set stable.

8. The experimental section: read the description before enabling#

Seven experimental keys, from lower to higher risk:

KeyDefaultTrade-off
switch_ascii_input_source_in_prefixfalseTemporarily switches to an ASCII-capable input source while prefix mode is active so prefix commands are read as ASCII even with an IME running. On Windows this supports the Korean IME only; for any other language the input source is left unchanged
reveal_hidden_cursor_for_cjk_imefalseExposes the focused pane’s cursor anchor to the outer terminal even when the pane requested ?25l (hiding the cursor). Cost: an extra visible hardware cursor for applications that hide the cursor without painting a replacement (vim normal mode)
cjk_ime_cursor_shapesteady_blockThe cursor shape rendered for the IME anchor
cjk_ime_agents[]Restricts the previous key to named agents (empty means any focused pane). Unknown names are ignored, and if the list contains no valid names the reveal does not apply
pane_historyfalsePersists pane screen history to session-history.json
allow_nestedfalseThe nested-launch gate from article 1 of module 4
kitty_graphicsunsetDeprecated compatibility key; the current one is terminal.kitty_graphics, which takes precedence when both are set

allow_nested, connected back to module 4#

Article 1 measured starting a nested Herdr inside a Herdr pane being refused:

error: nested herdr is disabled by default.
see configuration if you want to enable it.

The “see configuration” in that message points at this key. Measured, it is commented out in the default config (default false).

Before you actually need it, weigh what that implies: an agent inside a pane being able to start Herdr is an agent able to duplicate sessions. If all you want is to test some startup logic, the named-session approach from article 1 (--session <name> plus a separate socket) is enough, and you do not need to open this gate.

9. worktrees and remote: two single keys#

[worktrees]
directory = "~/.herdr/worktrees"   # default

[remote]
manage_ssh_config = true           # default

worktrees.directory is the root for checkouts, created as <directory>/<repo>/<branch-slug>. Point it at ~/Projects/herdr-worktrees for sibling-style checkouts.

With remote.manage_ssh_config enabled, herdr --remote writes a private temporary SSH config that includes your user and system SSH configs first and then adds fallback ServerAliveInterval and ServerAliveCountMax values — your own keepalive settings win. Linux and macOS clients also use a private per-attach OpenSSH control socket to reuse the first authenticated connection; Windows OpenSSH does not. Setting false runs remote attach through plain ssh with nothing generated by Herdr.

Module 2 covers SSH authentication recovery; the configuration angle is worth one sentence: because the reuse path exists, “no repeated passphrase prompt” is expected, so if remote setup keeps asking for a password, that reuse path is probably not taking effect.

10. The session section: the two agent-restore keys#

[session]
resume_agents_on_restore = true
startup_per_agent_delay_ms = 100

With resume_agents_on_restore enabled, restoring a Herdr session resumes supported agent panes into their native conversation sessions. Module 1 article 3 covers session state; this key is the switch for “the agent’s conversation comes back too”.

startup_per_agent_delay_ms is the spacing between automatic agent restores after a server restart — the first agent starts with no delay and 0 disables spacing entirely. The docs state that it does not delay manual launches or explicit terminal attaches, and requires a server restart to apply. Tune it when many agents restoring at once fight over CPU or affinity.

11. Trap list#

  1. When “I changed it and nothing happened” arrives, split client versus server first. Themes and the sidebar belong to the client; pane defaults, worktrees, and integrations belong to the server.
  2. Startup-only settings ignore reload, including terminal.kitty_graphics, session.startup_per_agent_delay_ms, and ui.sidebar_start_collapsed.
  3. Run herdr config check after every edit. On the hot path an invalid value falls back silently, and the reload’s diagnostics array is the only signal.
  4. Many keys are commented out in the default config, so a misspelled key name raises no error. Use herdr --default-config | grep to confirm.
  5. Headless sizing governs new layout only while zero clients are connected; after a client disconnects existing PTYs keep their last size.
  6. default_shell takes an executable name, not a command line. "nu --login" is invalid.
  7. A new pane cannot find your brew commands → shell_mode = "login". On macOS auto is already equivalent to login.
  8. --cwd always beats new_cwd, and on macOS it is normalised to a real path (/tmp → /private/tmp).
  9. terminal.kitty_graphics replaced the old external socket overlay API, so that recipe from older tutorials is dead.
  10. manifest_check = false falls detection back to the bundled rules, so confirm that switch before investigating a detection difference.
  11. If cjk_ime_agents contains only unknown names, the reveal does not apply — not a bug, but a direct consequence of “no valid target”.
  12. allow_nested defaults to false to stop agents duplicating sessions. Avoid opening it if a named session will do.

Frequently Asked Questions

How do I make a config.toml change take effect?

herdr server reload-config. Its measured return is status=applied with a diagnostics array, in this shape {"id":"cli:server:reload-config","result":{"diagnostics":[],"status":"applied","type":"config_reload"}}; an empty diagnostics array means no diagnostics. Remember that a reload applies most UI settings without restarting panes, while startup-only settings still need a restart.

Why did my reload have no effect?

Because configuration belongs to two different sides. The docs are explicit: themes, sidebar layouts, copy behaviour, and other presentation settings come from the client's local config, including when you are viewing an SSH machine, while pane defaults, worktrees, integrations, and custom commands belong to the server where the panes run. So editing the wrong side and seeing no hot reload is normal. On top of that, a batch of startup-only settings is unaffected by a reload and requires restarting the corresponding session.

How should I use herdr --default-config?

It prints the complete default configuration, 377 lines measured here. To start from scratch run herdr --default-config > ~/.config/herdr/config.toml. Its other use is looking up the correct name and values for a key — for example, if you copied a key name from a blog and neither the reload reported an error nor the setting took effect, the name is probably wrong and commented out in the default config.

Can I safely enable the experimental keys?

Read the key name and the trade-off text first. experimental.allow_nested is the switch behind the nested-launch gate from module 4, and it defaults to false. The description of experimental.reveal_hidden_cursor_for_cjk_ime states its trade-off explicitly: when enabled, an extra hardware cursor becomes visible for applications that hide the cursor without painting a replacement. Since these keys can change meaning between versions, read the description before enabling one.

What terminal size does Herdr use when no client is attached?

The server uses a 120×40 virtual terminal for layout and for newly created panes, which you can change with headless_cols and headless_rows under [server] (both are commented out in the measured default config). With one client attached all tabs follow its size; with several clients each viewed tab follows the client that most recently focused, selected, or interacted with it; when all but one client detach, all tabs immediately return to the remaining client's size; when none remain, existing pane PTYs keep their last size and only new headless layout uses the configured fallback.
