Herdr on Windows: the Differences ConPTY Brings, Six Explicitly Unsupported Capabilities, and the Cursor versus IME Dilemma

Go item by item through Herdr 0.9.2's Windows support boundary against the documentation: the install path and the stable/preview channel rules (an existing preview install stays on preview, and migrating takes two steps), the two paste methods in Windows Terminal, the cursor dilemma under ConPTY where host_cursor auto actually means drawn cells and switching to native trades flicker for an IME anchor, live cwd being unreliable under PowerShell while OSC7 works, Kitty graphics being unavailable in Windows Terminal, agent process-tree detection following Git Bash exec boundaries, the 12 supported Windows integrations, plugins being preview only on Windows, and the six explicitly unsupported capabilities — direct attach, live handoff, Unix fd handoff, foreground process groups, the clipboard image bridge, and signed binary/SmartScreen avoidance — with what each one means for your actual workflow. Baseline herdr 0.9.2.

September 30, 2026 · 12 min · 2470 words · Mengshou Programming -  |  中文

Herdr was originally built around the Unix PTY model, and the Windows edition replaces it with ConPTY plus Windows process and runtime behaviour. Core workflows work, but some capabilities differ and some remain platform-dependent.

This article goes through the support boundary item by item and attaches “what this means for your actual workflow” to each, because “partial” is not by itself a basis for a decision.

Baseline: herdr 0.9.2 stable · Windows support status taken from the official documentation pinned to v0.9.2 · this machine is macOS, so this article is a documentation cross-check and was not verified on Windows hardware.

Conclusion first#

“Mostly usable” on Windows means, precisely: sessions, panes, keyboard and mouse, notifications, and remote access all work, while six things are explicitly unsupported — direct attach, live handoff, Unix fd handoff, foreground process groups, the clipboard image bridge, and signed binary avoidance. Among the partials, the two that actually affect daily work are live cwd (unreliable under PowerShell) and the cursor (visual stability versus IME anchoring). Plugins on Windows are preview only.

1. Installation and channels: there is a migration catch on Windows#

Installing#

powershell -ExecutionPolicy Bypass -c "irm https://herdr.dev/install.ps1 | iex"

If endpoint security blocks that fileless PowerShell command, use Command Prompt instead:

curl.exe -fsSLo install.cmd https://herdr.dev/install.cmd && install.cmd && del install.cmd

The installer stores releases under %USERPROFILE%\.herdr\packages\standalone\releases, puts the active versioned release directory on PATH, keeps %LOCALAPPDATA%\Programs\Herdr\bin as a stable compatibility alias, and retains a small number of older releases so running processes do not block updates.

Channel migration takes two steps#

Windows builds ship through both the stable and preview update channels. New installs use stable by default and stable is recommended. But there is a known path:

  • An existing preview install stays on preview until you explicitly run herdr channel set stable
  • If your preview build is too old to accept that command: run herdr update once on preview first, then retry herdr channel set stable

That is the complete documented flow, and neither step can be skipped.

About custom manifests#

Internal testing can point HERDR_MANIFEST_URL at a custom manifest, with HERDR_CHANNEL=preview for a custom preview manifest. Ordinary users should not set this.

Sessions keep running after the client detaches#

Local persistent sessions continue running after the client detaches or its terminal window closes. Servers and pane processes launched through Windows OpenSSH also survive logout; run herdr again to reconnect.

That is stronger than the Unix behaviour — you do not have to worry that closing the terminal window takes your work with it.

How agent detection actually works on Windows#

Windows detection scans the descendants of the pane shell, recognising direct agents plus common command wrappers, including npm/Node and Git Bash process chains, and it follows Git Bash-launched agents across emulated exec boundaries.

The docs immediately add the important caveat: this is not the same as Unix foreground process-group detection. So “stable on Unix, flaky on Windows” has a structural cause rather than being a bug.

The 12 supported integrations on Windows#

Pi, OMP, Claude Code, Codex, GitHub Copilot CLI, Devin CLI, OpenCode, Kilo Code CLI, Droid, Kimi Code CLI, Qoder CLI, and Antigravity CLI.

Narrower than on Unix. Herdr hides or rejects integrations whose install format is unsupported on Windows — so if an integration is visible on Unix but missing on Windows, check that first.

3. Partial support: these are the two that actually bite#

live cwd: the real boundary under PowerShell#

MethodStatus
live cwd after a shell cdpartial
live cwd via shell integration / OSC7supported

Herdr can launch panes in the right directory and can create the initial workspace from the directory you started it in. But after startup, the process information Herdr can inspect does not reliably track later logical cd changes in PowerShell.

Remedy: use a Herdr integration, or prompt shell integration, for live cwd reporting. Module 3 article 2 covers where the 18 integrations install, so it is not repeated here.

CJK IME composition anchoring: partial#

See the next section — it is the partial you feel most.

Prefix input-source switching: Korean IME only#

This is an opt-in experiment:

[experimental]
switch_ascii_input_source_in_prefix = true

It switches Hangul input to English while prefix commands are active and restores the previous mode afterwards. Other Windows IMEs are not supported by this option yet (on Windows). macOS and Windows only, and a no-op elsewhere.

Kitty graphics: unavailable in Windows Terminal#

Kitty graphics is enabled by default and depends on the outer terminal. Herdr emits Kitty graphics protocol output on Windows as it does elsewhere, but the docs state that Windows Terminal does not expose the Kitty graphics path Herdr uses. If the outer terminal mishandles graphics output:

[terminal]
kitty_graphics = false

Clipboard image paste into agents: terminal and agent dependent#

Some Windows agents can receive ctrl+v and read clipboard images directly. But Herdr’s own clipboard image reader is not wired into local native Windows panes, so agent-native image paste stays dependent on the terminal and the agent. Agent image-paste shortcuts such as alt+v do not add a Herdr-managed local clipboard bridge either.

Remote clipboard image bridging is a separate matter and is supported through herdr --remote to Linux, macOS, and Windows hosts.

Plugins: preview#

Plugins support windows as a manifest platform, in preview. GitHub install, local link, build commands, actions, events, and plugin panes are all best-effort on Windows. Two concrete constraints:

  1. Commands must be Windows-compatible argv commands. Node package shims such as npm, bun, and node are expected to work when they are on PATH, but Unix-only examples using sh or Bash need Windows alternatives.
  2. Platform filters skip unsupported build commands and return platform_unsupported for unsupported actions or panes.

That connects directly to the two warnings article 4 of module 4 measured — an undeclared platforms gives you the warning manifest does not declare platforms, and on Windows that has real consequences.

4. The cursor: its own section, because it is a dilemma#

Why the default is a drawn cursor#

Herdr’s native Windows panes rely on ConPTY. The Windows terminal cursor path can expose intermediate positions while a multiplexer repaints the screen: a native cursor may flicker, jump, or briefly remain at an old position during active output.

The docs point out that this behaviour also reproduces in other native Windows terminal multiplexers and with direct VT cursor-position stress tests, so Herdr cannot eliminate it while preserving native cursor behaviour.

So the default host_cursor = "auto" draws Herdr’s cursor as terminal cell content on native Windows and WSL. Other Linux and macOS clients continue to use the native terminal cursor. The drawn Windows cursor is steady and non-blinking, but it does not provide the outer terminal’s native blink, shape, or cursor colour.

And the cost, stated exactly:

Windows does not use a drawn cursor to position IME composition and candidate UI. Korean, Japanese, or Chinese IME UI may therefore appear at the wrong location.

Opting back into the native cursor#

[ui]
host_cursor = "native"

Native mode restores the IME anchor, but it can reintroduce occasional cursor flicker, jumps, or stale cursor positions during active output. Return to visual stability with host_cursor = "drawn", or remove the setting to use the Windows default.

This is a pure trade-off with no third path: either the cursor is stable or the input method is accurate.

One concrete keyboard and mouse limitation#

Windows terminals do not all report modified keys in the same shape. Herdr preserves mouse reporting and ctrl+j in Windows Terminal and Alacritty on Windows. The native Windows input path also preserves physical key presses, repeats, releases, standalone Escape, and shift+enter through default ConPTY panes.

But modified keys still depend on the outer terminal reporting a distinct key event: if it reports shift+enter as a plain Enter, Herdr can only forward a plain Enter.

Windows packages include Microsoft’s current app-local ConPTY runtime, because the system ConPTY on older Windows 10 builds drops the Kitty keyboard protocol sequences used by agents such as Kimi and Pi. Set HERDR_WINDOWS_CONPTY=system before starting Herdr only when diagnosing a compatibility problem with the bundled runtime.

Use the outer terminal’s pasteHold shift and right-click, rather than sending the click through Herdr

The bracketing of multiline paste is worth emphasising: an agent prompt receives one paste, not a submission per line.

6. Explicitly unsupported: six items#

CapabilityStatus
Direct terminal attach (herdr terminal attach)unsupported
Live server handoffunsupported
Unix file-descriptor handoffunsupported
Unix foreground process groupsunsupported
Herdr’s clipboard image bridge in local native panesunsupported
Signed binary / SmartScreen avoidanceunsupported

The first two connect most directly to module 4:

  • No live handoff means the pty-based “start a throwaway client to bring up a server” recipe from article 1 is unnecessary on Windows — because on Windows the server already survives on its own
  • No direct terminal attach means the “attach straight to a bare terminal stream” workflow from module 2 is unavailable, and --remote is the only path

The remote workflow on Windows#

herdr --remote workbox

The target host can be Linux, macOS, or Windows. On a Windows host, remote attach reuses a compatible package from PATH or the active managed release. Interactive direct attach and saved-machine setup prompt before installing or updating the complete package when needed, but background saved reconnect only discovers installed packages and cannot prompt for installation or updates.

One practical note: Windows OpenSSH does not use Herdr’s Unix control-socket reuse, so key authentication through the Windows ssh-agent is recommended during remote setup to avoid repeated passphrase prompts.

7. What to include when reporting a Windows issue#

The docs’ own list tells you what tends to go wrong:

  • Herdr version
  • Windows version
  • Terminal application
  • Shell, such as PowerShell or cmd
  • Whether you used a named HERDR_SESSION
  • Relevant Herdr logs
  • Exact steps to reproduce

Articles 1 and the troubleshooting article cover how to obtain these: versions with herdr -V, status with herdr status, logs under %APPDATA%\herdr\ on Windows.

8. Trap list#

  1. Preview migration takes two steps: herdr channel set stable, and on older preview builds an herdr update first.
  2. Cursor and IME are a single switch with two faces. host_cursor = "native" restores the IME anchor at the cost of possible flicker; drawn is stable but may misplace the input method window.
  3. The paste key in Windows Terminal is ctrl+shift+v, not ctrl+v.
  4. Multiline paste is bracketed, so an agent prompt receives one paste rather than a submission per line.
  5. Kitty graphics does not work through Windows Terminal, and the outer terminal misbehaving is fixed with terminal.kitty_graphics = false.
  6. live cwd is unreliable under PowerShell, so use an integration or shell integration / OSC7.
  7. No direct attach and no live handoff on Windows, which means the module 2 and module 4 approaches must become --remote.
  8. There are only 12 integrations on Windows, narrower than on Unix, and unsupported ones are hidden or refused.
  9. Plugins are preview on Windows, commands must be Windows-compatible, and Unix sh / Bash examples need replacing.
  10. cjk_ime_agents with only unknown names applies no reveal, which is more likely on Windows because the supported agent list is shorter.
  11. Prefix input-source switching supports only the Korean IME, so enabling it for another language does nothing.
  12. Changing the ConPTY runtime is a diagnostic switch, not a configuration: HERDR_WINDOWS_CONPTY=system is for investigation only.

Frequently Asked Questions

How do I move my Windows preview build to stable?

Run herdr channel set stable. There is a catch: if an older preview build rejects that command, run herdr update once on preview and retry. Stable Windows installs default to the stable channel, while an existing preview install remains on preview until you switch explicitly.

The cursor flickers or the IME candidate window is misplaced on Windows. What now?

Those are two sides of the same switch. The default host_cursor = auto draws the cursor as cell content on native Windows and WSL, which is visually stable but cannot provide the native cursor anchor that IME composition needs, so CJK candidate windows appear in the wrong place. Changing host_cursor to native restores the anchor at the cost of possible cursor flicker, jumping, or brief stale positions during active output. The trade-off is yours to make.

Does agent detection just not work on Windows?

No. Windows agent process-tree detection scans descendants of the pane shell and recognises direct agents plus common command wrappers, including npm/Node and Git Bash process chains, and it follows Git Bash-launched agents across emulated exec boundaries. But it is not the same as Unix foreground process-group detection, so instability that only happens on Windows has a structural reason to exist.

Which capabilities are explicitly unsupported on Windows?

The docs list six: direct terminal attach (herdr terminal attach), live server handoff, Unix file-descriptor handoff, Unix foreground process groups, Herdr's clipboard image bridge in local native panes, and signed binary / SmartScreen avoidance. The first three are the price of the cross-platform toolchain, and the last three are limits of what the platform offers.

How do I connect from Windows to my Linux machine?

herdr --remote workbox, exactly as on Linux and macOS, and the target host can be Linux, macOS, or Windows. One limitation matters: Windows OpenSSH has no Herdr Unix control-socket reuse, so key authentication through the Windows ssh-agent is recommended during remote setup to avoid repeated passphrase prompts. Background reconnect can only discover already-installed packages and cannot prompt you to install or update.
