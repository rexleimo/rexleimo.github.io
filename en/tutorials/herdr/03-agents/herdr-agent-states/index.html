Herdr's Agent State Model: Who Decides the Five States, How the Detection Manifest Works, and Why VMs and Sandboxes Block Detection

Herdr's agent state has three sources: screen reading (the detection manifest), integration reports, and agent self-reporting. This article clarifies the precedence and each source's failure conditions, using real herdr agent explain output from herdr 0.9.2 on this machine — pi's manifest has exactly two rules (whole_recent matching the literal Working... and bottom_non_empty_lines(12) matching a braille-spinner border regex), plus what fallback_reason: default_known_agent_idle_fallback actually means; why blocked is deliberately strict, why Codex falls back to unknown; the HERDR_AGENT and HERDR_PROCESS_DETECTION=child-groups escape valves for VMs and sandboxes; remote manifest auto-update versus local override precedence; state rollup and custom labels.

September 29, 2026 · 16 min · 3280 words · Mengshou Programming -  |  中文

Verified version: herdr 0.9.2 (stable channel) · tested on this machine: macOS / Apple silicon · 2026-09-29 Every explainer output, manifest file body and state-directory listing in this article comes from a real run on this machine, not from copying docs.

The official first sentence states Herdr’s reason for existing:

Herdr is built for running more than one coding agent at a time.

Whether “more than one at a time” actually works hinges on one thing: can you see at a glance which one is waiting on you. That is the entire point of the state model — it is not a decorative badge, it is the core function of the tool.

Conclusion first:

State has three sources, and the precedence is: integration / agent self-report > screen reading. The screen-reading route has two kinds of manifest: built into the binary and fetched from herdr.dev and cached — and a local override always wins. Also memorise one counter-intuitive decision: blocked is deliberately judged strictly. Herdr would rather misreport “asking you a question” as idle than falsely claim blocked — because a false blocked makes you believe something is waiting on you when nothing is.

1. 27 agents, three ways of being supported#

The official agents page splits “support” into two kinds, and adding “plain terminal” makes three real cases:

An agent gets Herdr support in two ways: Herdr supports it, or it supports Herdr. Under both you see each agent’s idle, working, blocked state, get notified when it finishes or needs you, and can wait for it from a script.

Other agents still run normally inside Herdr panes; they simply appear as plain terminals.

Category 1: Herdr supports it and there is an installable integration (18)#

Herdr recognises these agents and reads state from what they draw on screen. To get the same session back after a Herdr server restart, install its integration: herdr integration install <name>.

2. How state is actually decided#

The official “how status works” section says it in three sentences:

For agents Herdr supports, Herdr finds the agent’s process in each pane and reads that pane’s live bottom, not the part you scrolled to. Rules in the detection manifest decide whether that screen means idle, working or blocked. When an integration also reports state, Herdr uses those reported values instead of screen reading.

For agents that support Herdr, the agent’s own reports decide the state.

Three takeaways:

  1. what is read is the “live bottom” — so scrolling up into history does not affect the state decision
  2. rules come from a manifest, and manifests can be updated remotely (section 5)
  3. reports outrank screen reading — install an integration and the integration is authoritative

Facts readable from this (each backed by the output above):

  1. pi’s detection is exactly two rules, and no integration is involved — this machine’s herdr integration status shows the pi integration as not installed. So this working came purely from screen reading.
  2. rules have a region concept: whole_recent (all of the recent buffer) and bottom_non_empty_lines(12) (the bottom 12 non-empty lines). The latter is the concrete implementation of “live bottom”.
  3. matching uses contains and line_regex — pi’s spinner border regex is ^── [⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏] Working ─+$, with each braille spinner glyph enumerated inside the character class.
  4. evaluated_rules tells you why each rule failed to match, including region_bytes and region_preview (the raw matched screen region). This is the troubleshooting gold mine.
  5. local_override_shadowing_remote: false — whether a local override is shadowing the remote manifest, visible at a glance.

What that manifest looks like#

The full body of ~/.local/state/herdr/agent-detection/remote/pi.toml (456 bytes):

id = "pi"
version = "2026.09.14.1"
min_engine_version = 1
updated_at = "2026-09-14T00:00:00Z"
aliases = ["herdr:pi"]

[[rules]]
id = "working_literal"
state = "working"
priority = 100
region = "whole_recent"
visible_working = true
contains = ["Working..."]

[[rules]]
id = "working_border"
state = "working"
priority = 100
region = "bottom_non_empty_lines(12)"
visible_working = true
line_regex = ['^── [⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏] Working ─+$']

This is the template for writing your own local override file. Note min_engine_version — it decides whether an older Herdr accepts the manifest at all.

3. Why blocked is judged so strictly#

This design trade-off deserves its own section, because it explains “my agent is asking me something yet shows idle”.

For screen-manifest agents, blocked detection is deliberately strict. Herdr marks blocked only when the live bottom buffer snapshot matches a known visible approval, question or permission UI. If no manifest rule matches for a known agent (except Codex), Herdr falls back to idle and labels the fallback default_known_agent_idle_fallback in the explain output. Codex falls back to unknown, because its title and composer can look the same during an active turn and after the response.

And the official risk assessment (this line matters):

For those other agents, an unusual new prompt may initially show as idle rather than blocked, until Herdr learns that screen shape. This misclassification only affects visible state and wait. It should not cause Herdr to send input or take a destructive action.

Codex’s special case (the complete rule)#

What is on screenWhat it establishes
a visible spinner or live activity timer✅ working
a visible approval prompt✅ blocked
an ordinary title / composer, or a missing spinner❌ cannot establish “the turn ended”

Consequence: Codex may stay at unknown after responding, and waits for idle or completion can time out.

One more detail that is easy to misread:

Managed startup uses only the initial composer to decide when it can accept a prompt; that observation does not change turn state.

4. VM and sandbox wrappers: why detection goes blind#

This is the most commonly hit problem in practice.

Symptom#

On Linux and macOS, a host-visible wrapper hides the real agent process from Herdr. Typical cases: fence, nono, various sandbox runners, container CLIs.

Fix 1: HERDR_AGENT#

Set it on the wrapper command, telling Herdr which existing agent’s screen manifest to use:

# Linux
HERDR_AGENT=claude fence -- claude

# macOS
HERDR_AGENT=claude nono run --profile claude-code -- claude

Three limits (all in the docs):

  1. the hint applies only to that foreground process
  2. if you set it only inside the VM or container, Herdr cannot see it
  3. do not export it globally unless every inheriting foreground process should be treated as that agent

Fix 2: HERDR_PROCESS_DETECTION=child-groups#

Some restricted Linux runtimes do not expose the terminal’s foreground process group. Starting the Herdr server with HERDR_PROCESS_DETECTION=child-groups opts into direct-child-group inference when native detection is unavailable.

Rules:

  • native detection still takes precedence, and the default native mode never performs this inference
  • the opt-in mode is best effort: a newer background job can be mistaken for the foreground job
  • the variable is read by the server and requires a restart
  • set it in the remote server’s environment, not on the attaching client

Fix 3 (really a trap): do not nest tmux inside a pane#

Herdr can run inside tmux as the outer terminal environment. Agent detection does not inspect a tmux session started inside a Herdr pane. If a shell framework auto-attaches tmux inside Herdr, Herdr sees the tmux pane process, not the agent behind it.

The fix is to add an HERDR_ENV check to your shell startup rule, before it runs tmux:

if [[ -z ${TMUX:-} && ${HERDR_ENV:-} != 1 ]]; then
  tmux new-session -A -s my-session
fi

One incidental physical effect too:

Re-attaching the outer tmux session from inside a Herdr pane recursively shrinks the terminal and makes it flicker.

(Measured on this machine: this session is inside a Herdr pane, echo $HERDR_ENV → 1, HERDR_PANE_ID → w3:p2. The zsh guard above was written for exactly this environment.)

5. The three manifest sources and their precedence#

SourceLocationPrecedence
local override~/.config/herdr/agent-detection/<agent>.tomlalways wins
cached remote manifestHerdr’s state directory (here: ~/.local/state/herdr/agent-detection/remote/)compared with built-in, the newer compatible version wins
built-in manifestinside the running Herdr binarythe floor

Official text:

A local override always wins. With no local override, Herdr uses the newer compatible manifest between the cached remote manifest and the built-in manifest in the running binary.

Additional details:

  • in debug builds, the same config helper may use a development directory such as herdr-dev
  • an invalid override file is ignored with a warning, and Herdr falls back to the cached remote or built-in manifest for that agent
  • remote manifests can only patch detection rules for agents Herdr already knows how to recognise. Adding a brand-new agent still requires a Herdr binary update (process detection, labels, integration behaviour)
  • to disable background remote manifest checks:
[update]
manifest_check = false

In-memory cache and reload#

A running server loads the active manifests into memory at startup. Automatic remote manifest updates reload that in-memory cache after new rules are written.

ScenarioCommand
fetch remote manifest updates now and reload the running serverherdr server update-agent-manifests
apply a manually edited local override to the running serverherdr server reload-agent-manifests (or restart Herdr)

Note the two command names differ; use the wrong one and you will conclude “my change did nothing”.

Troubleshooting: herdr agent explain#

herdr agent explain <target>
herdr agent explain --file screen.txt --agent codex --json    # reproduce offline

Live explain is evaluated by the running server, so it reflects the active manifest cache.

The explain output contains (the official complete list): the agent, the final state, whether screen detection was skipped by a full lifecycle authority, manifest source and version, cached remote version, local override shadowing, remote update status, the matched rule, visible evidence flags, the matcher and region evidence for evaluated rules, the transcript viewer’s skipped-update reason, and the idle fallback reason when no rule matched.

6. State rollup: this is the main workflow#

The sidebar rolls state upward. A blocked agent makes its pane, tab and workspace all look blocked. A working agent makes its workspace look active. A done agent stays visible until you look at it.

This is Herdr’s main workflow: start several agents, let them work in parallel, then read from the sidebar which project needs a decision, which is still running, and which is ready for review.

“A done agent stays visible until you look at it” is a deliberate decision: it makes “read” your action rather than a function of time. The sidebar is essentially an unread inbox.

A measurement on this machine caught exactly that state: w3:p1’s agent_status was done (completion_seq: 79) while w3:p2 was working — both panes belong to the same workspace w3, so w3 simultaneously expresses “something finished” and “something is running” in the sidebar.

7. Custom labels: two kinds, do not mix them up#

Changing the agent’s display name#

herdr agent rename w3:p1 reviewer
herdr agent rename reviewer --clear

The target accepts: a unique live agent name, or the pane ID currently hosting that agent. It does not accept: terminal IDs, bare agent-kind labels.

After renaming you can attach directly with herdr agent attach reviewer (see below).

Changing the displayed text (but not the semantic state)#

Integrations report lifecycle state only as semantic state. Display customisation is added separately with a pane metadata token.

herdr pane report-agent w3:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working

herdr pane report-metadata w3:p1 \
  --source custom:indexer-display \
  --token summary=indexing
ThingControls
statewaits, notifications, rollup
summary tokendisplay only, usable as $summary in the Agent sidebar row

The Agent sidebar row can also selectively enable terminal_title or terminal_title_stripped (neither is in the default row):

  • terminal_title: the latest, safely normalised OSC 0/2 terminal title
  • terminal_title_stripped: with one recognised leading activity or spinner glyph, and the following whitespace, removed

Three notes:

  1. these values are server-owned
  2. after a cold restart they are ephemeral, and independent of the metadata title and the semantic agent state
  3. so a spinner animation can update the raw title without producing a pane update — as long as the stripped text stays the same (a clever debouncing design)

8. Attaching directly to one agent#

herdr agent attach reviewer
  • ctrl+b q detaches; ctrl+b ctrl+b sends a literal ctrl+b
  • the mouse wheel or ordinary page up/down scroll; normal typing jumps back to the bottom
  • when another direct attach client already owns input, use --takeover:
herdr agent attach reviewer --takeover

For the same thing on a non-agent terminal: herdr terminal attach <terminal_id>.

9. Traps to avoid#

  1. Strict blocked judging is design, not a bug. Do not expect “every agent waiting for input shows blocked”. For precision use herdr agent explain <target> and read evaluated_rules.
  2. Codex sitting at unknown is normal. Its waits can time out — give Codex its own timeout policy in scripts.
  3. Misclassification never makes Herdr send input on its own. The docs state plainly that it affects visible state and wait only.
  4. Installing an integration does not mean “more accurate state”, it means “reports replace screen reading”. For omp / mastracode, no integration means no state at all.
  5. Running an agent in a VM / sandbox? Add HERDR_AGENT first — and add it to the host-visible wrapper command; setting it inside the container does nothing.
  6. Do not export HERDR_AGENT globally. It would make every inheriting foreground process be treated as that agent.
  7. HERDR_PROCESS_DETECTION=child-groups must be set in the server environment plus a restart; setting it on the client does nothing. And it is best effort: a new background job can be mistaken for the foreground one.
  8. Do not auto-attach tmux inside Herdr panes. Add the ${HERDR_ENV:-} != 1 guard, or Herdr only sees tmux.
  9. After editing a local override use reload-agent-manifests; to fetch remote updates use update-agent-manifests. Do not swap the two commands.
  10. You cannot add a brand-new agent by editing manifests. Remote manifests only patch rules for already-recognised agents; a new agent needs a Herdr binary update.
  11. agent rename does not accept terminal IDs or bare agent-kind labels. Use a unique live agent name or a pane ID.
  12. To change state wording, do not touch state. state drives waits/notifications/rollup; use the summary metadata token for display.

Frequently Asked Questions

How does Herdr know whether my agent is working or blocked?

For agents Herdr supports, it finds the agent process in each pane and reads that pane's live bottom — not wherever you scrolled. Rules in a detection manifest decide whether that screen means idle, working or blocked. When an integration also reports state, Herdr uses the reported values instead of screen reading. For agents that self-report, the agent's own reports decide.

Why does my agent show idle when it is clearly asking me a question?

Blocked detection is deliberately strict for screen-reading agents: a pane is marked blocked only when the live bottom buffer snapshot matches a known visible approval, question or permission UI. When no rule matches for a known agent (except Codex), Herdr falls back to idle and labels it default_known_agent_idle_fallback in the explain output. The docs state this misclassification only affects visible state and wait; it does not make Herdr send input or take destructive action.

Why does Codex often show unknown?

Because its title and composer can look identical during an active turn and after the response. So when no rule matches, Codex falls back to unknown rather than idle. A visible spinner or live activity timer can establish working, and a visible approval prompt can establish blocked, but an ordinary title, composer, or missing spinner cannot establish that the turn ended. Codex may therefore stay unknown after responding, and waits for idle or completion can time out.

Why can't Herdr see my agent when it runs inside a VM, container or sandbox wrapper?

On Linux and macOS a host-visible wrapper hides the real agent process. The fix is to set HERDR_AGENT=<agent> on the wrapper command, which tells Herdr which existing agent's screen manifest to use, for example HERDR_AGENT=claude fence -- claude. The hint applies only to that foreground process; setting it only inside the VM or container is invisible to Herdr.

Do manifest rule updates require restarting Herdr?

Remote manifest updates need no restart: Herdr checks herdr.dev for remote manifest updates, applies per-agent rule updates that are valid, and reloads the in-memory cache after new rules are written. Run herdr server update-agent-manifests to fetch immediately. But after editing a local override file (~/.config/herdr/agent-detection/<agent>.toml) you need a restart or herdr server reload-agent-manifests.

How do I debug a pane whose state looks wrong?

herdr agent explain <target>, or reproduce offline with herdr agent explain --file screen.txt --agent codex --json. Live explain is evaluated by the running server, so it reflects the active manifest cache. The output includes the agent, final state, whether screen detection was skipped by a full lifecycle authority, manifest source and version, cached remote version, whether a local override is shadowing, remote update status, the matched rule, visible evidence flags, and the matcher and region evidence for evaluated rules, plus the idle fallback reason when nothing matched.
