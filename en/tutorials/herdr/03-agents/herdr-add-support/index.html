Adding Herdr Support to Your Own Agent: Three Kinds of Report, --seq Monotonicity, the Four Hard Constraints on a Resume Command, and How to Test Without Touching Your Normal Session

If you are building a coding agent, you can make it a first-class citizen in Herdr from your own code — no pull request to Herdr, no waiting for a Herdr release. This article covers the three reports and nothing else: state (pane report-agent --state working/idle/blocked), resume command (pane report-agent with the command after --, or pane report-agent-session), and release on exit (pane release-agent). Plus the four environment variables, why --seq must increase across sessions and restarts or your reports are silently dropped, the four hard constraints on a resume command and the invalid_resume_argv / resume_not_accepted error codes, why the integration must never block your agent, CLI versus raw socket, the Prime Agent reference implementation, and testing restoration in a separate named session.

September 30, 2026 · 15 min · 3102 words · Mengshou Programming -  |  中文

Verified version: herdr 0.9.2 (stable channel) · tested on this machine: macOS / Apple silicon · 2026-09-30 ⚠️ The code samples in this article were not executed against an active pane on this machine: pane report-agent rewrites the target pane’s agent identity and state, and the pane on this machine is running a real task. Section 9 explains why that restraint is itself a discipline.

The previous two articles were about “using agents Herdr supports”. This one is the reverse direction:

If you are building a coding agent, you can report agent state and a resume command to Herdr from your own code, making it a first-class citizen in Herdr — without submitting a pull request to Herdr and without waiting for a Herdr release.

The docs also give a refreshingly practical reason:

Herdr maintains integrations for agents whose vendors do not provide one. If you maintain your own agent, owning the integration means you can fix it on your own release schedule.

In other words: waiting for Herdr to adapt means your fix window is its release cycle; reporting it yourself means the window is yours.

Conclusion first:

There are exactly three kinds of report: state, resume command, and release on exit. All of them go through the binary at $HERDR_BIN_PATH, and fire only when HERDR_ENV=1. The two things people get wrong most often: --seq not increasing monotonically across restarts (reports silently discarded), and forgetting that your source must already own the pane before sending a resume command (you get back resume_not_accepted).

1. What the user gets once you report#

The four benefits the docs list:

  • your agent’s name and its idle / working / blocked state in the sidebar and in herdr agent list
  • notifications when it completes or needs a decision
  • herdr agent wait and other agent-state-waiting automation
  • the same session coming back in the same pane after a Herdr server restart

The third and fourth are the most valuable: they make your agent orchestrable by scripts and able to survive a restart. (herdr agent wait belongs to module 4, programmatic control, in a later batch.)

2. The four environment variables#

Every process inside a Herdr pane inherits these environment variables:

VariableMeaning
HERDR_ENV1 inside Herdr
HERDR_PANE_IDthe pane your agent is running in
HERDR_BIN_PATHthe Herdr binary that owns this pane
HERDR_SOCKET_PATHHerdr’s API socket

And the discipline you must follow:

Report only when HERDR_ENV=1 and the other variables are set. Outside Herdr, your integration should do nothing.

Measured here (this session is running inside a Herdr pane):

$ echo "$HERDR_ENV  $HERDR_PANE_ID"
1  w3:p2

Why $HERDR_BIN_PATH rather than herdr: because the binary that owns this pane is the correct party to talk to — the user’s PATH may hold a different version, or nothing at all (for instance when Herdr is served through a remote bridge).

3. Report type 1: state#

"$HERDR_BIN_PATH" pane report-agent "$HERDR_PANE_ID" \
  --source my-agent \
  --agent my-agent \
  --state working \
  --seq 1

The rules for the four parameters#

--state: when to report what

StateWhen
workingat the start of a turn
idlewhen your agent is ready to accept input
blockedwhen it needs the user to decide something (and use --message to explain the block)

--agent: the name the user sees

Use your own agent’s name, not the name of an agent Herdr already supports.

--source: identifies your integration

Keep it stable and unique. Do not start it with herdr:, because Herdr’s own integrations use that prefix.

(Same convention as the custom:indexer and user:claude-title examples in the integrations article : use a namespace prefix, and stay off herdr:.)

--seq: optional but strongly recommended

It must increase with every report from your source, including across sessions and across restarts of your agent. A timestamp is a good choice. Herdr ignores a report whose sequence number is not higher than the last value it accepted for that pane and source, so a late or out-of-order report cannot overwrite a newer state.

This is the easiest thing to get wrong in the whole protocol. An “in-process auto-incrementing counter” implementation trips here: the agent restarts, the counter resets to zero → every reported seq is lower than the value Herdr remembers → all reports are silently ignored, with no error.

Recommended implementation (monotonic, survives restarts, no persistence needed):

# a millisecond timestamp as seq
seq_now() { python3 -c 'import time; print(int(time.time()*1000))'; }
# or: date +%s%3N (GNU date) / perl -MTime::HiRes -e 'printf("%d\n", Time::HiRes::time()*1000)'

4. Report type 2: the resume command#

Put the command that restores the current session after --, and include the options that session needs — model, permission mode, and so on — so the restored session behaves the same:

"$HERDR_BIN_PATH" pane report-agent "$HERDR_PANE_ID" \
  --source my-agent \
  --agent my-agent \
  --state idle \
  --seq 2 \
  --agent-session-id "$SESSION_ID" \
  -- my-agent --resume "$SESSION_ID" --model my-model

When to send it#

You can attach the command to any state report, or send it with pane report-agent-session when only the session changed. Re-report it whenever your agent switches session.

What Herdr does when it restores#

After a Herdr server restart, Herdr opens that pane in the same directory and runs the command there.

The four hard constraints#

#Constraint
1the first word is a bare command name on the user’s PATH, e.g. my-agent, not a path
2no parameter contains an apostrophe or a control character
3at most 64 parameters and 8 KiB in total
4your source must already own the pane — so send a state report with report-agent before or together with the command; otherwise Herdr answers resume_not_accepted

Number 4 is the one people hit: you cannot “just send the resume command”. A state report must first (or simultaneously) make the pane yours.

The two error codes#

ErrorTriggered byConsequence
invalid_resume_argvviolating the first three rulesHerdr rejects the command and does not apply the report
resume_not_acceptedviolating rule four (the source did not own the pane first)the command is not accepted

The user-side switch#

Users can disable resume with [session] resume_agents_on_restore = false.

(That is the path-4 switch from the session-state article — it governs official integrations and self-reporting agents alike.)

⚠️ The version gate#

The resume command needs Herdr 0.10.0 or newer. Older versions ignore resume commands, so state reports and release still work there.

This machine runs 0.9.2 (stable channel), so by that statement self-reported resume commands would be ignored on the current stable, while state and release work normally.

Distinguish this from official integrations: the “minimum integration version” table for the 18 official integrations in the integrations article is a different path (a session reference reported by an integration Herdr maintains itself), and the session-state page says it is enabled by default. The 0.10.0 gate in this section applies to the path where a third-party agent reports its own resume command after --. Before building the integration, measure an actual restore on your target version — do not rely on docs alone.

Gradual strategy: ship state reporting first (works on 0.9.x, and the benefit is already large), send the resume command anyway (newer versions pick it up automatically, older ones ignore it harmlessly), and verify the restore chain once 0.10.0 lands.

5. Report type 3: release on exit#

"$HERDR_BIN_PATH" pane release-agent "$HERDR_PANE_ID" \
  --source my-agent \
  --agent my-agent \
  --seq 3

Release immediately clears your agent’s name, state and resume command from the pane.

Two usage rules:

  1. release only when the user genuinely quit
  2. if your agent replaces a session with another session in the same process, report the new session — do not release

What happens if you forget to release: the safety net#

If your agent exits without releasing, Herdr notices when the pane returns to its idle shell prompt and clears the agent and its resume command. This usually takes a second or two. It is a safety net, not a replacement for release.

Why you cannot lean on it: during those seconds, the sidebar shows an agent that no longer exists, herdr agent wait may wait on a dead target, and a notification may fire wrongly. In orchestrated automation, a second or two is enough for a script to decide incorrectly.

6. Do not slow your agent down: three engineering rules#

  • Do not slow your agent down for Herdr. Send reports in the background or with a short timeout, and ignore failures.
  • Send only the newest state. If several changes queue while a report is in flight, drop the older ones.
  • The resume command needs Herdr 0.10.0 or newer. Older versions ignore them, so state reports and release keep working.

The first two translate into implementation requirements:

RequirementHow
never block the main loopput reporting on a background thread/subprocess, or add a short timeout (say 200–500 ms) and give up
failure must not affect the agentswallow the error, at most log one debug line. Never exit or stall the agent because a report failed
send only the newesta “dirty flag + current state” coalescing model, not an unbounded queue

These three rules are essentially saying: the Herdr integration must be disposable. An agent that crashes because the Herdr socket was unavailable is worse than an agent with no integration at all.

7. If you want the socket directly#

HERDR_BIN_PATH plus the CLI is the portable choice, including on Windows. If your agent needs direct IPC, send the equivalent pane.report_agent, pane.report_agent_session and pane.release_agent requests (see the agent-state-reporting section of the Socket API docs External link ). Put the resume command in the resume_argv array.

Choosing:

ApproachUse it when
CLI ($HERDR_BIN_PATH)pick this by default. Cross-platform (including Windows), no protocol coupling, process-level isolation
socket ($HERDR_SOCKET_PATH)high-frequency reporting, needing several things on one connection, or your agent is already event-driven

Note the socket path comes from $HERDR_SOCKET_PATH — do not hand-assemble ~/.config/herdr/herdr.sock; under a named session or a remote bridge that path is wrong.

8. Verifying your integration#

Basic self-check#

Start your agent in a Herdr pane, then check what Herdr saw:

herdr pane get "$HERDR_PANE_ID"
herdr agent list

Combined with the explainer from the state article , the full three-piece kit is:

herdr pane get "$HERDR_PANE_ID"     # this pane's current agent / state / metadata
herdr agent list                    # is it in the list, is the state right
herdr agent explain <target>        # how the state was decided (reports short-circuit screen reading)

Test restoration without touching your normal session#

To test restoration without disturbing your normal session, use a separate named session:

  1. start herdr --session my-agent-test, then run your agent in a pane there
  2. stop that session with herdr session stop my-agent-test
  3. start herdr --session my-agent-test again. The pane should run your resume command and your agent should report again

This three-step method comes straight from the docs and is worth copying verbatim into your CI or manual checklist. The key point: a named session has its own server, socket and runtime state (see the session-state article ), so session stop only kills the test session — it does not touch the one you are working in.

A real-world reference implementation#

Prime Agent’s built-in Herdr reporter External link is a real-world integration. It activates only inside Herdr, maps agent events to working, idle and blocked, keeps its report ordering across sessions, and releases the pane on exit.

Those four points correspond exactly to four sections of this article: activation condition, state mapping, --seq monotonicity, release. Checking your implementation against it is faster than reading docs.

If you only want to change the display, not the state#

To change how your agent is presented without changing its state — a title, or custom status text — see Custom status labels External link .

That means herdr pane report-metadata (--title / --display-agent / --token summary= / --state-label / --ttl-ms), and not report-agent, which would seize authority over semantic state.

9. A runnable minimal reporter (example, not executed against an active pane here)#

#!/usr/bin/env bash
# my-agent-herdr.sh — a minimal working Herdr reporter
# Usage: source it from your agent, or use it as a subprocess wrapper
set -uo pipefail

# 1 activation condition: completely silent when not inside Herdr
[[ "${HERDR_ENV:-}" == "1" ]] || return 0 2>/dev/null || exit 0
: "${HERDR_PANE_ID:?}" "${HERDR_BIN_PATH:?}"

SOURCE="my-agent"          # stable, unique, not prefixed with herdr:
AGENT="My Agent"           # the name users see; must not clash with a supported agent name

# 2 seq: a millisecond timestamp, naturally monotonic across sessions and restarts
_seq() { python3 -c 'import time; print(int(time.time()*1000))'; }

# 3 never blocks, never throws: short timeout + swallowed failure
_report() {  # _report <state> [message]
  local state="$1" msg="${2:-}"
  local args=(pane report-agent "$HERDR_PANE_ID"
              --source "$SOURCE" --agent "$AGENT"
              --state "$state" --seq "$(_seq)")
  [[ -n "$msg" ]] && args+=(--message "$msg")
  timeout 0.4 "$HERDR_BIN_PATH" "${args[@]}" >/dev/null 2>&1 || true
}

herdr_working() { _report working; }
herdr_idle()    { _report idle; }
herdr_blocked() { _report blocked "$1"; }

# 4 resume command: a state report must own the pane first (hence the _report call)
herdr_set_session() {  # herdr_set_session <session-id> [model]
  local sid="$1" model="${2:-default}"
  _report idle
  timeout 0.4 "$HERDR_BIN_PATH" pane report-agent "$HERDR_PANE_ID" \
    --source "$SOURCE" --agent "$AGENT" --state idle --seq "$(_seq)" \
    --agent-session-id "$sid" \
    -- my-agent --resume "$sid" --model "$model" >/dev/null 2>&1 || true
}

# 5 call only when the user really quit; on a session swap inside the same process use herdr_set_session
herdr_release() {
  timeout 0.4 "$HERDR_BIN_PATH" pane release-agent "$HERDR_PANE_ID" \
    --source "$SOURCE" --agent "$AGENT" --seq "$(_seq)" >/dev/null 2>&1 || true
}
trap herdr_release EXIT INT TERM

The script deliberately implements every rule from the earlier sections: ① activation condition ② timestamp seq ③ short timeout + swallowed errors ④ state report before the resume command ⑤ release on exit + trap.

Why I did not run it here: pane report-agent rewrites the target pane’s agent identity and state. This machine’s only active pane (w3:p2) is running a real task, and reporting --agent "My Agent" onto it would pollute the sidebar, notifications, and the semantics of herdr agent wait. To try it, use the separate named session from section 8 (herdr --session my-agent-test) — that is not merely a caution in this article, it is the officially recommended way to test.

10. Traps to avoid#

  1. Use a timestamp for --seq, not an in-process counter. Resetting to zero on restart = every report silently ignored, with no error.
  2. Do not prefix --source with herdr:. That prefix belongs to Herdr’s own integrations.
  3. Do not let --agent clash with a supported agent name. Users will see two “claude” entries in the sidebar.
  4. You cannot send only the resume command. Your source must own the pane first, otherwise resume_not_accepted.
  5. The first word of the resume command must not be a path. It has to be a bare command name on the PATH.
  6. Resume parameters must contain no apostrophes or control characters, capped at 64 parameters / 8 KiB. Violations give invalid_resume_argv, and the whole report is not applied.
  7. --agent-session-id and the command after -- must agree. Report id A but resume id B, and restoration yields a different session.
  8. Re-report the resume command whenever the session switches. Otherwise a server restart restores the old session.
  9. Swapping session inside the same process is not an exit. Report the new session, do not release.
  10. Do not rely on the “second or two” safety net. It exists, but during that window the sidebar shows an agent that no longer exists.
  11. Reporting must be non-blocking and allowed to fail. Short timeout + swallow the error. If Herdr dies, your agent keeps working.
  12. Send only the newest state; drop queued older changes. An unbounded queue makes state lag into “already stale”.
  13. The resume command has a version gate (0.10.0+). Measure an actual restore on your target version; do not trust docs alone.
  14. Test in a separate named session. herdr --session my-agent-test → session stop → start again — three steps to verify the restore chain without touching the session you are using.
  15. Do not hand-assemble the socket path. Use $HERDR_SOCKET_PATH; a fixed path is wrong under named sessions and remote bridges.
  16. To change display only, do not use report-agent. Use report-metadata (--title / --display-agent / --state-label / --token / --ttl-ms), which does not take over semantic-state authority.

Frequently Asked Questions

Do I need a pull request to Herdr to support my own agent?

No. You can report agent state and a resume command to Herdr from your own code, without submitting a pull request to Herdr or waiting for a Herdr release. The docs note that Herdr maintains integrations for agents whose vendors do not, and that if you maintain your own agent, owning the integration means you can fix it on your own release schedule.

Why are my state reports being ignored?

Most likely a seq problem. --seq must increase with every report from your source, across sessions and across agent restarts — a timestamp is a good choice. Herdr ignores reports whose sequence number is not higher than the last value it accepted for that pane and source, so a late or out-of-order report cannot overwrite a newer state. An in-process counter resets to zero on restart, which means every subsequent report is silently discarded with no error.

Why did my resume command get rejected?

Two error codes to read. invalid_resume_argv means the command violated one of the first three rules: a bare command name on the PATH rather than a path, no parameter containing an apostrophe or control character, at most 64 parameters and 8 KiB total; in that case Herdr rejects the command and does not apply the report. resume_not_accepted means your source did not already own the pane — so send a state report with report-agent before or with the command.

What happens if my agent exits without releasing?

A safety net: if your agent exits without releasing, Herdr notices when the pane returns to its idle shell prompt and clears the agent and resume command, typically within a second or two. It is a safety net, not a substitute for release. Use release only when the user genuinely quits; if your agent replaces a session with another session in the same process, report the new session rather than releasing.

How do I make the integration safe to leave installed?

Report only when HERDR_ENV is 1 and the other Herdr environment variables are set, so your integration does nothing outside Herdr. Send reports in the background or with a short timeout and ignore failures, and send only the newest state — if several changes queue while a report is in flight, drop the older ones.

How do I test session restoration without disturbing my work?

Use a separate named session: start herdr --session my-agent-test and run your agent in a pane there, stop it with herdr session stop my-agent-test, then start herdr --session my-agent-test again — the pane should run your resume command and your agent should report again. Named sessions have their own server, socket and runtime state, so stopping the test session does not touch the one you work in.
