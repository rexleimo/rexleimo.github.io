All 18 Official Herdr Integrations: Which File Each Installs, Which Config It Touches, Where State Comes From, and the Local Pi and Hermes Situation

Installing an integration is not how Herdr recognises your agent — detection is automatic. Integrations exist so Herdr can resume the same session after a server restart, and six of them additionally report agent state. This article walks all 18 targets: which file each writes, which config it edits, which environment variable overrides the directory, whether the directory must already exist, and whether state still comes from screen reading. Plus minimum integration versions for native session restore, Claude v10's SessionStart source whitelist, OMP competing with Pi over the extensions directory, OpenCode's three files and V1/V2 differences, why Devin/Droid/Qoder still rely on screen reading, MastraCode having no fallback, Grok's self-contained hooks.json, coexisting with report-metadata, and the measured state of Pi and Hermes on this machine.

September 30, 2026 · 22 min · 4506 words · Mengshou Programming -  |  中文

Verified version: herdr 0.9.2 (stable channel) · tested on this machine: macOS / Apple silicon · 2026-09-30 Every integration status / --help output and directory listing below is a real execution result on this machine. I did not actually install any integration — installation writes into the user configuration of tools such as Pi / Hermes, which counts as a change needing separate approval. Section 8 describes “what would happen if you did install” and this machine’s current state.

The previous article explained how state is decided. This one covers how to make state more reliable, and how to get a session back after a server restart — that is, integrations.

First, correcting a misconception almost everyone has:

An integration is not “what makes Herdr recognise your agent”. The official first sentence is: Herdr detects the agents it supports automatically. You install an agent’s integration so that Herdr can resume the same session after a server restart. Some integrations additionally report agent state directly.

So the test for “should I install one” is simple:

What you care aboutInstall or not
only knowing whether the agent is working or blockedusually no (screen reading suffices)
rejoining the original conversation after a server / machine restartrequired (no integration means no session reference)
using OMP or MastraCoderequired (those two need the integration for state itself)
wanting authoritative state instead of screen-reading inferenceinstall the six that report state

1. Three subcommands, exactly three#

$ herdr integration --help
Manage built-in agent integrations

Commands:
  install    Install an integration
  uninstall  Uninstall an integration
  status     Show integration status

There is no list. Typing herdr integration list prints a block of help text (measured here) containing 18 herdr integration install <name> examples — it serves the “list” as help.

install’s target is a closed enumeration (verbatim from this machine’s --help):

possible values: pi, omp, claude, codex, copilot, devin, droid, kimi, opencode,
                 kilo, hermes, qodercli, qwen, cursor, mastracode,
                 antigravity-cli, grok, letta

18 items, note letta last (which disagrees with where the Letta section sits in the docs, and with the order of herdr integration status output — do not rely on ordering, use names).

Two install entry points#

In Herdr, open settings and use the integrations tab to install recommended integrations for the agents found on your PATH, or run the commands by hand.

“found on your PATH” is a useful qualifier: it will not recommend a pile of agents you never installed. (Letta is not in this UI, see below.)

Information readable from this real output that the docs never spell out:

  1. status tells you directly “which file it will look at” — far quicker than reading docs, and the first troubleshooting step
  2. two integrations use the filename herdr-agent-session.sh instead of herdr-agent-state.sh: qwen and letta. The name itself is telling you: they report session identity only, not state

  4. letta carries the (experimental) suffix
  5. codex and cursor put the script directly at the root of the config directory, not in a hooks/ subdirectory

2. What Herdr actually does with these integrations#

Each integration tells Herdr which session the agent is in, so Herdr can resume it after a server restart. Turn this off with [session] resume_agents_on_restore = false.

The Pi, OMP, Kimi Code CLI, OpenCode, Kilo Code CLI and MastraCode integrations also report agent state. While they report, Herdr uses them instead of screen reading. The rest leave state to detection.

Write atomicity and Windows backup semantics#

Herdr saves integration configuration atomically on Linux/macOS and for new files. Existing Windows files are preserved with their permissions by backing up first, then updating in place.

If Windows reported a backup:

  1. close the agent and review the configuration before retrying
  2. only after verifying the configuration, discard (not restore) an incomplete .herdr-backup.pending
  3. or, when needed, restore the contents of a complete .herdr-backup into the existing file (if the existing file is missing, create it with its intended permissions first)
  4. then verify the configuration and delete the backup

4. Pi: relevant to this machine, expanded#

herdr integration install pi

Herdr writes the bundled extension to:

~/.pi/agent/extensions/herdr-agent-state.ts

Rules:

  • if PI_CODING_AGENT_DIR is set, Herdr writes instead to $PI_CODING_AGENT_DIR/extensions/herdr-agent-state.ts
  • Herdr creates the extensions directory when Pi’s agent directory already exists
  • uninstall removes that one extension file only

This machine’s state (measured):

$ ls -d ~/.pi ~/.pi/agent
/Users/rex/.pi
/Users/rex/.pi/agent          # ← the agent directory exists

$ ls ~/.pi/agent/extensions/
ls: /Users/rex/.pi/agent/extensions/: No such file or directory   # ← extensions not created yet

So this machine sits exactly on the branch the docs describe: agent directory exists, extensions directory missing → install pi would create extensions/ and write herdr-agent-state.ts.

What makes Pi special: the agents page marks it “also reports state”, so after installing, working/idle/blocked come from the extension’s reports rather than screen-reading inference. But note — Pi’s state works without the integration too (the herdr agent explain output in the previous article produced working while the pi integration was not installed, using the braille spinner regex from the remote manifest).

5. OMP: competes with Pi over the directory, the install may be refused#

herdr integration install omp

Writes ~/.omp/agent/extensions/herdr-omp-agent-state.ts. Directory resolution order:

  1. if PI_CODING_AGENT_DIR is set → treat it as the complete agent directory
  2. else if PI_CONFIG_DIR is set → use $HOME/$PI_CONFIG_DIR/agent
  3. else → ~/.omp/agent

Then this very important protection:

If Pi and OMP resolve to the same extensions directory, Herdr refuses the OMP install so that the OMP extension is not loaded by Pi. Configure separate agent directories before installing both integrations.

So: to use Pi and OMP together, set PI_CODING_AGENT_DIR (or PI_CONFIG_DIR) to separate them first, then install. Otherwise the second install fails, and the reason is “protecting you” rather than “cannot install”.

What the OMP integration can do (stronger than most):

  • reports omp as the agent label, lifecycle state, and native session identity via Herdr’s socket API
  • it does not need native process detection of the omp executable
  • after a server restart Herdr can restore OMP panes with omp --resume=<session>

6. Integrations with distinctive behaviour#

Claude Code: v10 tightened the SessionStart whitelist#

Claude integration v10 matches only the documented SessionStart sources: startup, resume, clear, compact and fork. This prevents Grok’s new and load events from firing an imported Herdr Claude hook, without disabling unrelated Claude-compatible hooks. Reinstall the Claude integration after upgrading to v10 to migrate the earlier wildcard matcher. New Claude source values require an integration update.

A genuine compatibility-war story: Grok’s event names triggered Claude-style hooks, so Herdr moved from “wildcard” to “whitelist”. If you installed before, reinstall once after upgrading Herdr.

Otherwise: default ~/.claude, or CLAUDE_CONFIG_DIR; the config directory must already exist; install writes hooks/herdr-agent-state.sh and updates settings.json; uninstall removes the matching hook entry and deletes the script. Claude Code’s state comes from Herdr’s screen manifest detection — the hook only reports session identity at session start.

Codex: install touches config.toml, uninstall does not#

Install does four things:

  1. writes herdr-agent-state.sh
  2. updates hooks.json
  3. ensures config.toml contains [features] hooks = true
  4. removes any existing deprecated top-level codex_hooks flag

Uninstall: removes the Herdr entries from hooks.json and deletes the hook script, but leaves config.toml alone.

⚠️ So if you want Codex hooks fully disabled for other reasons, uninstalling the integration will not revert config.toml for you.

Codex’s state comes from the screen manifest — and as the previous article explained, Codex is the only agent that falls back to unknown instead of idle when no rule matches.

Copilot CLI#

~/.copilot or COPILOT_HOME; writes hooks/herdr-agent-state.sh; adds one SessionStart hook entry to settings.json. After Copilot emits an event carrying a session, Herdr can restore the pane with copilot --resume=<id> using the reported session id.

Devin CLI: why state is still screen reading#

The hook reports native session identity from Devin’s session, prompt, tool-use, permission and stop events. Devin’s state still comes from Herdr’s screen manifest and OSC detection, because Devin’s hooks do not emit a reliable state transition after every permission cancellation or user interrupt.

Directory: with XDG_CONFIG_HOME set, $XDG_CONFIG_HOME/devin; otherwise ~/.config/devin on Linux/macOS and %APPDATA%\devin on Windows. Files: herdr-agent-state.sh on Unix, herdr-agent-state.ps1 on Windows; config.json is updated. The hook keeps refreshing the session reference while Devin runs. Native screen manifest detection remains authoritative for state, whether or not the hook is installed.

Kimi Code CLI: requires 0.14.0+#

  • requires Kimi Code CLI 0.14.0 or newer
  • reports session identity plus lifecycle state, used for native restore and authoritative idle/working/blocked
  • install appends Herdr-managed [[hooks]] entries to config.toml
  • uninstall removes that Herdr-managed configuration block and deletes the script

Droid: cleans up after itself#

~/.factory (the Factory config directory must already exist). Install:

  1. writes hooks/herdr-agent-state.sh
  2. updates settings.json with a Herdr SessionStart hook entry
  3. removes the older Herdr Droid hook entry from hooks.json if present

Uninstall removes the Herdr entries from both config files and deletes the script. Lifecycle state still comes from the screen manifest, because Droid’s hooks do not cover every lifecycle transition.

OpenCode: the most complex one, worth its own subsection#

Supported versions: OpenCode V1 1.18.29 or newer, and OpenCode V2 (tested with beta 19242).

Install writes three files (all under the config directory):

FileRole
~/.config/opencode/plugins/herdr-agent-state.jsserver entry
herdr-tui-session.jsshared TUI plugin
herdr-opencode/tui.jsV2’s TUI entry

Registration: the V1 TUI plugin registers into tui.jsonc, the V2 TUI plugin into cli.json, preserving other preferences and plugins.

Several edge cases (the docs list them item by item; here are the points):

  • an existing V1 registration in tui.json also counts as “installed” and is reused — Herdr does not create tui.jsonc
  • if OpenCode still has V1 TUI preferences pending import (tui.json or kv.json), Herdr defers registration so the first-launch migration can complete → start opencode2 once, then reinstall the integration
  • otherwise Herdr creates cli.json with the plugin registration
  • restart the OpenCode TUI after installing
  • uninstall removes the Herdr registrations from both TUI config files but keeps the files and other preferences; it also removes the managed plugin files and their config entries

V2’s lifecycle reporting runs in the pane-local TUI, so it correlates events to its own selected root session even when several panes share one OpenCode server.

EventState effect
completion, interruptclears working
pending permission request, pending form, failed executionkeeps the pane blocked

⚠️ V2 Mini and headless clients do not run the TUI plugin, so they provide no such lifecycle reporting.

V1’s TUI reporting follows the pane’s selected session and its descendants:

  • if any of them is busy or retrying → the pane stays working
  • if any of them has a pending permission or question → the pane is blocked
  • attaching loads existing activity
  • a cancelled tool request does not become a blocker again after a reconnect
  • browsing a subagent keeps the original session family; whereas attaching directly to a child tracks that child’s subtree, not its siblings

Local V1 opencode run and opencode --mini keep their legacy server hooks; this change does not add pane-local lifecycle reporting for Mini/headless clients.

⚠️ After updating the integration, restart the shared OpenCode server as well as the TUI, otherwise an old server reporter may override pane-local state.

With no plugin installed, native screen manifest detection remains available.

Kilo Code CLI#

Writes ~/.config/kilo/plugin/herdr-agent-state.js (the Kilo config directory must already exist). Uninstall deletes that one plugin file. Reports lifecycle state and session identity; restore uses kilo --session <id> once Kilo emits an event carrying the session.

Hermes Agent: a restart is mandatory afterwards#

Herdr writes plugins/herdr-agent-state/ under the Hermes home directory, and enables herdr-agent-state in its config.yaml. HERMES_HOME defaults to ~/.hermes on Unix and %LOCALAPPDATA%\hermes on Windows. The Hermes config directory must already exist. Restart Hermes after installing, or the plugin will not load. Uninstall removes the plugin directory and drops herdr-agent-state from plugins.enabled.

It reports only a restorable session id; working/idle/blocked use screen manifest detection; after a server restart the pane is restorable with hermes --resume <id>.

Qoder CLI#

~/.qoder or QODER_CONFIG_DIR; writes hooks/herdr-agent-state.sh; updates settings.json. Reports session identity only, because Qoder’s hooks do not cover every lifecycle transition. Screen manifest detection stays available without the hook.

Qwen Code#

The SessionStart hook reports Qwen Code’s session identity only for native restore; lifecycle state stays under Herdr’s screen manifest detection. Writes hooks/herdr-agent-session.sh (.ps1 on Windows) and adds one Herdr entry to settings.json. Uninstall removes only the matching entry and the managed script.

Letta Code: experimental, CLI-only#

The Letta Code integration install is experimental and CLI-only. It is not listed in the Settings integrations UI and not in the JSON integration API. herdr integration status reports it as letta (experimental). Agent detection and herdr agent start --kind letta are unaffected by this install limitation and work independently.

A quiet SessionStart hook reports the conversation ID; state still comes from the screen manifest. ~/.letta (must already exist). Named conversations restore with letta --conversation <id>; the default conversation is recorded as default:<agent-id> and restores with letta --conversation default --agent <agent-id>.

Cursor Agent CLI: one PATH requirement#

~/.cursor or CURSOR_CONFIG_DIR; writes herdr-agent-state.sh (.ps1 on Windows); adds one Herdr sessionStart entry to hooks.json.

⚠️ When Herdr restores the pane, the cursor-agent command must be on the PATH; Herdr does not launch the generic agent command.

An easy trap to hit after “switched shells / the server uses a different PATH”: restoration fails, and the reason is not on Herdr’s side.

MastraCode: no fallback#

The hook reports MastraCode’s lifecycle state and thread identity, used for authoritative idle/working/blocked state and native restore. MastraCode has no screen manifest fallback; state comes from the hook.

~/.mastracode; writes hooks/herdr-agent-state.sh (.ps1 on Windows); adds Herdr command entries to hooks.json, creating the directory when it is missing. This is the only one of the 18 with “no integration means no state at all” and “it creates the directory for you”.

Antigravity CLI: session-only, and it waits for the first prompt#

  • directory: default ~/.gemini/config/, or ANTIGRAVITY_CLI_CONFIG_DIR — the directory Antigravity CLI reads for global customisation, and it must already exist
  • writes hooks/herdr-agent-state.sh (.ps1 on Windows), and adds a Herdr-owned herdr block to hooks.json
  • Antigravity CLI’s hooks.json is keyed by hook name, so the install rewrites only that block and leaves other named hooks alone
  • uninstall removes the herdr block and deletes the script

Two behavioural key points:

This is a session-only integration: it reports the pane’s current conversation but not agent state. Herdr continues to derive working / idle / blocked from what Antigravity CLI draws on screen.

The hook runs on PreInvocation, so Herdr learns the conversation only after the first prompt is sent. From that point on, Herdr can restore the pane with agy --conversation <id> after a server restart.

Implication: an Antigravity pane that just started and has not been prompted yet cannot be restored after a restart.

Grok CLI: self-contained, never touches anyone else’s files#

Grok merges every hooks/*.json file in that directory, so the install writes a self-contained hooks/herdr.json containing Herdr’s SessionStart entries, alongside hooks/herdr-agent-state.sh (.ps1 on Windows), and never edits other hook files. Uninstall deletes precisely those two Herdr-owned files.

~/.grok or GROK_HOME (must already exist). The least invasive design of the 18 — worth using as a template.

7. Custom state labels (the correct way to coexist with an integration)#

Integrations report lifecycle state as semantic state only. For instance, report an agent as working without adding display fields to the lifecycle report.

herdr pane report-agent w1:p1 \
  --source custom:docs \
  --agent docs-bot \
  --state working

Then the single most important discipline in this section:

User hooks running alongside Herdr-managed integrations should use metadata rather than report-agent. Metadata changes presentation without taking over that integration’s idle/working/blocked or session-restore authority.

herdr pane report-metadata "$HERDR_PANE_ID" \
  --source user:claude-title \
  --agent claude \
  --title "Refactor auth middleware" \
  --display-agent "Claude: auth" \
  --token summary="refactor auth" \
  --state-label working="refactoring auth" \
  --ttl-ms 3600000

Rule details:

  • --agent and --applies-to-source protect presentation fields only (--title, --display-agent, --state-label)
  • token patches always apply; that reporter owns the responsibility to clear or refresh by TTL
  • --display-agent changes the visible name
  • tokens and state labels are purely visual — waits, notifications and workspace rollups still use semantic state

In one line: to change “what it appears to be called”, use metadata; only use report-agent to change “what state Herdr believes it is in” — and the latter competes with official integrations for authority, so use it only where there is no official integration.

One easily confused item#

This machine has a herdr-auto-reconcile.yaml under ~/.hermes/hermes-agent/plugin-catalog/:

name: herdr-auto-reconcile
repo: https://github.com/chris-yyau/hermes-herdr-auto-reconcile
description: Wake Hermes when allowlisted Herdr panes need reconciliation,
  without routing or controlling pane work.
maintainer: chris-yyau

This is not Herdr’s official integration. It is a community (tier: community) plugin catalogue entry whose job is “wake Hermes when allowlisted Herdr panes need reconciliation” — the direction is exactly opposite to the official integration: the official one is agent → Herdr (reporting state and session), this one is Herdr → agent (making Hermes look after panes).

The two can coexist, but do not treat them as the same thing. A herdr- prefix does not mean “Herdr-managed file”; the official filenames are fixed as herdr-agent-state (or herdr-agent-session for qwen/letta).

9. Debugging integration state#

The official three steps:

# 1. list known agents
herdr agent list

# 2. when you need to confirm "what Herdr actually sees", read a pane
herdr pane read w1:p1 --source recent --lines 50

# 3. if integration state looks wrong,
#    first confirm the agent is running inside Herdr,
#    and that the relevant hook or plugin is installed for the SAME user account

That “same user account” in step 3 is the most commonly overlooked part: a hook installed with sudo, or an agent running under a different user, both produce “installed but not working”.

Add the two tools from the previous article and the full troubleshooting order should be:

herdr integration status --outdated-only   # is the integration present, and is it stale
herdr agent explain <target>               # how state was decided (includes matched_rule and region evidence)
herdr pane read <pane> --source recent --lines 50   # what that screen looks like through Herdr's eyes

10. Traps to avoid#

  1. There is no herdr integration list, and no status --json. Only install / uninstall / status, and status has the single --outdated-only flag. To parse it in a script, split strings yourself.
  2. The config directory must already exist (mastracode excepted). Run that agent once first, then install.
  3. Hermes needs a Hermes restart after installing; OpenCode needs the TUI restarted, and after an integration update the shared server too. Forgetting this looks like “installed but state never changes”.
  4. OpenCode defers registration while V1 preferences await migration. Start opencode2 once, then reinstall the integration.
  5. Pi and OMP fight over the extensions directory and Herdr refuses the OMP install. Using both? Set PI_CODING_AGENT_DIR or PI_CONFIG_DIR to separate them first.
  6. Reinstall once after upgrading to Claude integration v10 to migrate the old wildcard matcher; otherwise Grok’s new/load events may trigger it.
  7. Codex uninstall does not restore config.toml. Install ensured [features] hooks = true; uninstall leaves it.
  8. Cursor restoration requires cursor-agent on the PATH; Herdr will not fall back to the generic agent command.
  9. Antigravity does not know the conversation before the first prompt (its hook runs on PreInvocation), so a freshly started, never-prompted pane cannot be restored after a restart.
  10. OMP and MastraCode have no state without the integration; MastraCode has no screen fallback either.
  11. Devin / Droid / Qoder hooks do not cover every lifecycle transition, so state still defers to screen reading — do not expect “installed means 100% accurate”.
  12. Do not use report-agent to fight official integrations for authority. User hooks running alongside should use report-metadata.
  13. A herdr- prefix does not mean Herdr-managed. That herdr-auto-reconcile on this machine is a community plugin pointing the other way.
  14. Two official documents disagree on Hermes’s minimum integration version (5 vs 2). Trust integration status --outdated-only, not the table.
  15. Install the hook for the same user account that runs the agent. Installed with sudo but run as another user is equivalent to not installed.

Frequently Asked Questions

Do I have to install an integration before Herdr recognises my agent?

No. Herdr detects supported agents automatically. Installing an agent's integration is so Herdr can resume the same session after a Herdr server restart, and some integrations additionally report agent state directly.

Which integrations report agent state rather than relying on screen reading?

Pi, OMP, Kimi Code CLI, OpenCode, Kilo Code CLI and MastraCode. During their reports Herdr uses them instead of screen reading, and the rest leave state to detection. For OMP and MastraCode the integration is required for state at all — MastraCode has no screen manifest fallback, so with no integration it has no state.

Why did installing an integration appear to do nothing?

Common causes: Hermes needs a restart afterwards for the plugin to load; OpenCode needs its TUI restarted, and after an integration update the shared OpenCode server too, or an old server reporter may overwrite pane-local state; the agent's config directory has to exist first, so run the agent once before installing; and Claude needs reinstalling after upgrading to integration v10 to migrate the previous wildcard matcher.

Can I use Pi and OMP together?

Yes, but configure separate agent directories before installing both integrations. OMP resolves its directory from PI_CODING_AGENT_DIR, then PI_CONFIG_DIR plus HOME plus agent, then ~/.omp/agent. If Pi and OMP resolve to the same extensions directory, Herdr refuses the OMP install so that the OMP extension is not loaded by Pi.

How do I add my own display fields alongside a managed integration?

Use pane metadata rather than report-agent. Integrations report lifecycle state as semantic state only, so make an agent appear as working without adding display fields to the lifecycle report. User hooks running alongside managed integrations should use report-metadata, which changes presentation without taking over the integration's idle, working, blocked or session restore authority. Tokens and state labels are purely visual; waits, notifications and workspace rollups still use semantic state.

How do I check integration status?

herdr integration status shows each target and the file it looks at, and --outdated-only lists stale ones. There is no list subcommand and status has no --json flag. To debug a wrong state, confirm the agent runs inside Herdr and that the hook or plugin is installed for the same user account, then use herdr agent list, herdr pane read, and herdr agent explain.
