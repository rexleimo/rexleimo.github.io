Herdr Socket API in Practice: One Request per Connection, Two Event-Naming Schemes, and Four Places Where the Schema and the Runtime Disagree

Write the wire protocol directly, because the CLI only covers part of it: the real framing of newline-delimited JSON, the one-request-per-connection rule (measured: a second request gets a BrokenPipeError), why a subscription connection stays open, the three failure shapes of a malformed id, connections that close silently on invalid UTF-8, unknown parameters that are quietly ignored, the six capability bits of ping, the 27 dotted event names of events.subscribe and the three that need parameters, the underscored names events.wait demands together with the single event it actually supports at runtime, four gaps between the schema and runtime behaviour, and the correct way to build a client from the 272 KB JSON Schema emitted by herdr api schema --json. Baseline herdr 0.9.2.

September 30, 2026 · 15 min · 3030 words · Mengshou Programming -  |  中文

Article 1 ended with a question: the CLI covers only 18 verbs while the underlying layer has 102 methods. The missing eighty-plus, plus the entire category of event subscriptions, are reachable only by connecting to the socket.

That sounds like a simple change of transport. But while getting the protocol working on this machine I hit four inconsistencies between the schema and runtime behaviour, two of which are enough to make a long-lived client fail silently.

This article takes them one at a time.

Baseline: herdr 0.9.2 stable · macOS · every frame below is measured output, verbatim.

Conclusion first#

Herdr’s socket protocol is newline-delimited JSON with one request per connection, not a multiplexed RPC channel. Except for subscriptions, you should treat every connection as a single function call: connect, write one line, read one line, close. The event system, meanwhile, has two naming schemes (dotted for subscribe, underscored for wait), and events.wait at runtime in 0.9.2 supports only one event despite the schema listing 19. Build the client from herdr api schema --json, but do not trust the schema alone — send one real request per method you intend to use.

1. The transport: three lines to explain, one frame to verify#

Unix:      <config>/herdr.sock                    (named sessions: <config>/sessions/<name>/herdr.sock)
Windows:   named pipe
Framing:   newline-delimited JSON, one request per line

Measured, the minimal frame:

import socket, json
s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
s.connect("/Users/rex/.config/herdr/sessions/batch8-lab/herdr.sock")
s.sendall((json.dumps({"id": "r1", "method": "ping", "params": {}}) + "\n").encode())
buf = b""
while b"\n" not in buf:
    buf += s.recv(65536)
print(buf.split(b"\n")[0].decode())

  "capabilities":{"live_handoff":true,"detached_server_daemon":true,

Six capability bits, each corresponding to a class of cross-version compatibility judgement:

The protocol-stability section states explicitly that client and server builds do not need to match. A missing method only disables the corresponding action and shows a client-local notice; it does not disconnect the UI. However, the numbered binary protocol (direct terminal attach, live handoff) requires the same install — check ping or herdr status before using those across builds.

2. The most important protocol fact: one request per connection#

This is the most valuable thing in the article, and the one you can only learn by measuring, because the docs never state it outright.

Measurement A: pipelining two requests#

s.sendall(b'{"id":"q1","method":"ping","params":{}}\n{"id":"q2","method":"ping","params":{}}\n')

What came back:

bytes=243 response-lines=1
   {"id":"q1","result":{"type":"pong",...

Two requests, one response, then recv() returned empty (the server closed the connection). The second request was never processed.

Measurement B: sending sequentially on the same connection (waiting for the first response before sending the second)#

request 1: {"id":"s1","result":{"type":"pong",...
request 2: BrokenPipeError: [Errno 32] Broken pipe

The write side was already closed after the first response. This is not “pipelining is discouraged” — it is physically impossible.

The correct client model#

def call(method, params, id_=None, sock=SOCK, timeout=5.0):
    """One request per connection — that is the protocol, not a limitation of this helper."""
    s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
    s.settimeout(timeout)
    s.connect(sock)
    try:
        s.sendall((json.dumps({"id": id_ or next_id(),
                               "method": method, "params": params}) + "\n").encode())
        buf = b""
        while b"\n" not in buf:
            chunk = s.recv(65536)
            if not chunk:
                raise ConnectionError("server closed without a response")
            buf += chunk
        return json.loads(buf.split(b"\n")[0].decode())
    finally:
        s.close()

The only exception is the subscription: the docs say event subscriptions keep the connection open after the initial response, and measurement confirms it — on one connection I received four event frames (section 5). So the rule is:

Request typeConnection behaviour
Ordinary methods (100 of the 102)One request per connection; the server closes after responding
events.subscribeOne acknowledgement frame, then continuous event pushes, connection stays open

This also explains why every CLI command is its own process: it has no other choice.

3. id and errors: five failure shapes, all measured#

Only id is required in the request envelope ({"required":["id"],"type":"object"}); method and params are not marked required at the schema’s top level — but omitting them produces an invalid_request error.

Measured, five malformed inputs and their responses:

InputResponse
{"id":"a",broken{"id":"","error":{"code":"invalid_request","message":"invalid request: key must be a string at line 1 column 11"}}
{"id":123,...}{"id":"","error":{... "invalid type: integer \123`, expected a string at line 1 column 9"}}`
missing id{"id":"","error":{... "missing field \id` at line 1 column 29"}}`
unknown method{"id":"r2","error":{"code":"invalid_request","message":"invalid request: unknown variant \no.such.method`, expected one of `ping`, `server.stop`, …"}}`
invalid UTF-8The connection closes with no response at all
empty line \nThe connection closes with no response at all

Three practical conclusions:

  1. id must be a string. Give it an integer and you get id:"" back, and your response-correlation logic falls apart. This is the easiest bug to write in a long-lived client: you think you are waiting for the response to id:123, you actually receive id:"", and then you time out.
  2. The unknown-method error lists all 102 legal method names. That is the fastest possible interface inventory — you do not need to run the schema, just send a bogus method and have the names printed at you.
  3. Invalid UTF-8 disconnects silently. The docs note that transport errors such as invalid UTF-8 can close the connection without a response, and measurement confirms it. So validate encoding yourself before sending, especially when you are stuffing user input or captured screen content into pane.send_text — Herdr will not report the reason to you.

The error envelope#

{"id":"req_1","error":{"code":"not_found","message":"pane not found"}}

code is the stable discriminant; message is for humans. Branch on code, never on message — messages carry implementation details such as line and column numbers (the at line 1 column 115 fragments above come from serde).

Unknown parameters are silently accepted#

call("ping", {"nope": 1})   # → pong, as normal

Extra parameters produce no error. That is good for forward compatibility — new fields are ignored by old clients, and the docs explicitly require that JSON API clients ignore unknown fields — but it is also bad, because writing paneid instead of pane_id produces no warning at all: it is treated as an unknown field, and you get either a missing-field error or, worse, a successful response built on defaults.

When writing a client, add your own allowlist validation of parameters using the schema’s required list.

4. Build the client from the schema, but do not trust it#

herdr api schema                    # summary
herdr api schema --json             # the full document (272578 bytes measured)
herdr api schema --output herdr-api.schema.json   # write it to a file

The summary looks like this:

Herdr API schema

schema_version: 1
schemas: error_response, event, request, subscription_event, success_response

The sizes of the five sub-documents (measured, in characters):

SchemaSizeContents

success_response49761The result shape of each method

Each entry in request.oneOf looks like:

{"properties": {"method": {"const": "ping"}, "params": {"$ref": "#/schemas/request/$defs/PingParams"}},

Following the $ref into $defs gives you each method’s required and optional parameters. Measured for the commonly used ones:

agent.wait            required=[target]                     optional=[timeout_ms, until]
pane.report_agent     required=[agent, pane_id, source, state]  optional=[agent_session_id, agent_session_path, message, resume_argv, seq]

events.wait           required=[match_event]                optional=[timeout_ms]

Note that source is required for pane.wait_for_output, while the CLI gives it a default of recent. Differences like this are invisible from the CLI and only appear once you go over the socket.

But there are four gaps between schema and runtime#

The inconsistencies I measured — the section easiest to skip and the most dangerous:

#The schema saysAt runtime
1EventMatch lists 19 waitable eventsEverything except pane_agent_status_changed returns unsupported_event_wait_match (measured, section 5)
2Subscription uses dotted names workspace.createdEventMatch uses underscored names workspace_created — two naming schemes for the same events
3Subscription has 27 entriesIt contains no pane.renamed (the pane-side name is pane.updated); one wrong name makes the whole subscription fail atomically
4agent_status is required for pane_agent_status_changedGenuinely required — you cannot even pass schema validation without it, while the CLI’s agent wait papers over that

The combination of 1 and 2 has a concrete consequence: you think you can use events.wait to wait for a pane creation event, and what you get back is “unsupported” rather than a timeout. And if you write the wait using the subscribe spelling, it does not even get past variant parsing.

5. The event system: subscription streams and single waits are different things#

Subscriptions: 27 dotted names, three of which need parameters#

The 27 variants of Subscription (extracted from the schema on this machine):

plain (type only), 24 of them:
  workspace.created / updated / metadata_updated / renamed / moved / reordered / closed / focused
  worktree.created / opened / removed
  tab.created / closed / focused / renamed / moved
  pane.created / closed / updated / focused / moved / exited / agent_detected
  layout.updated

with parameters, 3 of them:
  pane.agent_status_changed   requires pane_id
  pane.scroll_changed         requires pane_id
  pane.output_matched         requires pane_id + source + match

Measured, subscribing and receiving a stream:

subs = [{"type": "workspace.created"},
        {"type": "tab.created"},
        {"type": "pane.agent_status_changed", "pane_id": "w1:p1"}]
s.sendall((json.dumps({"id":"sub3","method":"events.subscribe","params":{"subscriptions":subs}})+"\n").encode())
# ack: {"id":"sub3","result":{"type":"subscription_started"}}

Then triggering activity from the CLI (creating a workspace, creating a tab, reporting one agent state change) produced four frames on the same connection:

{"data":{"type":"workspace_created","workspace":{"active_tab_id":"w4:t1","label":"tmp","number":4,"pane_count":1,"workspace_id":"w4"}},"event":"workspace_created"}
{"data":{"tab":{"label":"1","number":1,"tab_id":"w4:t1","workspace_id":"w4"},"type":"tab_created"},"event":"tab_created"}
{"data":{"tab":{"label":"4","number":4,"tab_id":"w1:t4","workspace_id":"w1"},"type":"tab_created"},"event":"tab_created"}
{"data":{"agent":"claude","agent_status":"blocked","pane_id":"w1:p1","workspace_id":"w1"},"event":"pane.agent_status_changed"}

Three observations:

  1. The connection does not close after the acknowledgement — events keep arriving. This is the only multi-frame scenario.
  2. In the event frame, event and data.type are the same underscored name. So in your dispatch logic, the subscription request uses dots and the event payload uses underscores, and one piece of code must map between the two.
  3. The second and third frames are both tab_created: herdr tab create created a tab in the currently focused workspace (w1:t4), while the newly created workspace brought its own tab (w4:t1). The event stream will show you frames you did not directly cause — do not treat that as an anomaly when synchronising state.

A subscription fails atomically#

Measured: writing the third subscription as {"type":"pane.renamed"} (which does not exist):

{"id":"sub1","error":{"code":"invalid_request","message":"invalid request: unknown variant `pane.renamed`, expected one of `workspace.created`, `workspace.updated`, ..."}}

Then triggering activity produced zero events — not one of the two valid subscriptions took effect.

So: the entire subscriptions array is either wholly valid or wholly ineffective. When adding a new event name, subscribe to it alone and verify once before putting it into an existing multi-subscription list — otherwise you will conclude “no events are arriving” when in fact the subscription never started.

Single waits: exactly one supported event#

events.wait’s match_event uses EventMatch (underscored names). First trying the dotted spelling:

{"id":"e2","error":{"code":"invalid_request","message":"invalid request: unknown variant `workspace.created`, expected one of `workspace_created`, `workspace_updated`, ..."}}

Switching to the underscored spelling:

{"id":"e3","error":{"code":"unsupported_event_wait_match","message":"events.wait currently supports pane agent status matches"}}

Note that this is not a timeout, it is “unsupported”. The schema lists 19 events; the runtime recognises only agent status.

Trying pane_agent_status_changed (requiring event + pane_id + agent_status):

{"id":"e5","method":"events.wait","params":{
  "match_event":{"event":"pane_agent_status_changed","pane_id":"w1:p1","agent_status":"blocked"},
  "timeout_ms":12000}}

Measured timing: report working first, start the waiter, confirm it is still blocked after two seconds (correct), then report blocked:

+2.0s waiter still blocked? yes (no result yet)
  resolved at +2.1s -> {"id":"e5","result":{"type":"wait_matched","event":{"event":"pane_agent_status_changed","data":{"type":"pane_agent_status_changed","pane_id":"w1:p1","workspace_id":"w1","agent_status":"blocked","agent":"claude"}}}}

Push-based waiting is available for agent state only in 0.9.2. For anything else — waiting for a pane creation, waiting for an output change — you must filter a subscription stream yourself, or poll pane.wait_for_output / session.snapshot.

6. session.snapshot: the whole runtime in one call#

The CLI’s herdr api snapshot wraps this method. Measured top-level structure:

snapshot:
  version, protocol
  focused_workspace_id, focused_tab_id, focused_pane_id
  workspaces[]  → workspace_id, label, number, active_tab_id, pane_count, tab_count, agent_status, focused
  tabs[]        → tab_id, workspace_id, label, number, pane_count, agent_status, focused
  panes[]       → pane_id, workspace_id, tab_id, terminal_id, cwd, foreground_cwd,
                  agent_status, focused, revision, scroll{offset_from_bottom, max_offset_from_bottom, viewport_rows}
  layouts[]     → workspace_id, tab_id, area{x,y,width,height}, focused_pane_id,
                  panes[]{pane_id, rect}, splits[], zoomed

This is the only call you need for read-only visualisation: one request gives you the entire topology, each pane’s scroll position, and the layout rectangles. layouts[].splits gives you the split tree and rect gives absolute coordinates, so you do not need to understand Herdr’s internal layout to redraw it.

Two fields deserve individual mention:

  • revision: the pane content version. Comparing it while polling saves you from re-scraping unchanged content.
  • scroll.offset_from_bottom == 0 means the pane is at the bottom. Determining whether an agent pane is scrolled back through history is cheaper with this than by reading the screen.

7. server.agent_manifests: the truth about detection manifest versions#

This diagnostic method corresponds to herdr server agent-manifests on the CLI; over the socket it returns structured data. Measured:

type: agent_manifest_status | last_check_unix: 1790763094 | last_result: checked
manifests: 22
source_kind histogram: {'remote': 21, 'bundled': 1}
   {"agent":"pi",     "source":"remote:/Users/rex/.local/state/herdr/agent-detection/remote/pi.toml",     "source_kind":"remote", "active_version":"2026.09.14.1", "cached_remote_version":"2026.09.14.1", ...}
   {"agent":"claude", "source":"remote:/Users/rex/.local/state/herdr/agent-detection/remote/claude.toml", "source_kind":"remote", "active_version":"2026.09.11.1", ...}
   {"agent":"codex",  "source":"remote:/Users/rex/.local/state/herdr/agent-detection/remote/codex.toml",  "source_kind":"remote", "active_version":"2026.09.23.1", ...}

Three highly informative points:

  1. 22 agents have manifests, but only 21 come from remote and 1 is bundled. In other words manifest updates really do take effect per agent independently — when the remote fetch fails for one agent it falls back to the version in the binary without affecting the others.
  2. Every manifest carries a date-style version (2026.09.23.1), and the dates differ per agent (pi is 09-14, claude is 09-11, codex is 09-23). “An old Herdr binary” does not mean “old detection rules” — remote manifests take effect without a restart.
  3. Remote manifests are cached in the state directory (~/.local/state/herdr/agent-detection/remote/), not the config directory. That is where to look when “detection behaviour changed but Herdr was not upgraded”.

The diagnostic chain (module 3 article 1 covers detection; this is the socket-level version):

server.agent_manifests → where a manifest came from, and at what version
agent.explain          → why this screen was judged that way (needs a detected agent in the pane)
pane.read --source detection → the buffer the detector actually saw

8. Trap list#

  1. Do not reuse a connection for a second request. Measured BrokenPipeError. Except for subscriptions, one request per connection.
  2. id must be a string. An integer yields an id:"" error and silently breaks your response correlation.
  3. Validate UTF-8 yourself before sending. Invalid bytes close the connection with zero response, and Herdr will not tell you why.
  4. Subscription names use dots; event payloads and events.wait use underscores. Two schemes; do not mix them.
  5. events.wait supports only pane_agent_status_changed in 0.9.2. Anything else returns unsupported_event_wait_match immediately, not a timeout.
  6. A subscription array fails atomically. One illegal name makes the whole batch ineffective, and the symptom is “not a single event arrives”.
  7. The pane.agent_status_changed subscription requires pane_id, and pane.output_matched requires pane_id + source + match. A missing field is an invalid_request and fails the whole batch identically.
  8. Unknown parameters are silently ignored. paneid misspelled raises no warning; you get a missing field, or a successful response built on defaults. Validate against the schema’s required client-side.
  9. source is required for pane.wait_for_output at the socket layer, while the CLI defaults it to recent. Migrating from CLI to socket makes this a hidden breaking change.
  10. After upgrading Herdr, restart or hand off the server before using agent.explain — the docs say so explicitly, because it depends on the running server’s manifest cache.
  11. Do not use herdr server stop to clean up a test session (article 1 covers this; the socket layer is the same: server.stop stops the server your socket points at).
  12. Do not assemble pipe names yourself on Windows. The docs recommend that plugins prefer HERDR_BIN_PATH plus CLI wrappers for portable behaviour; raw socket clients are responsible for the platform-native local socket form.

Frequently Asked Questions

When should I bypass the CLI and talk to the socket directly?

In three situations. First, when the CLI has no command: methods like pane.scroll, pane.clear, pane.link.activate, layout.apply, agent.view.set, command.invoke, and popup.close are reachable only over the socket. Second, when you need an event stream: the CLI has no subscribe, only the single-shot events.wait and polling through pane wait-output. Third, when you want a long-lived protocol client rather than a process per call. The reverse also holds: if you only call it once or twice from a script, use the CLI, because it handles socket path resolution, the Windows named pipe, and protocol negotiation for you — all of which are easy to get wrong by hand.

Can I send several requests over one socket connection?

No, subscriptions aside. Measured: sending two requests in one sendall returns only the first response and then recv returns empty because the server closes the connection; waiting for the first response and sending the second raises BrokenPipeError. So the right model is one request per connection, treating each connection as a single function call. The only exception is events.subscribe, which returns one subscription_started frame and then keeps pushing events on that connection — measured receiving four event frames on a single connection.

Why does my event subscription receive nothing at all?

Most likely an illegal name in the subscription array, because a subscription fails atomically: either the entire subscriptions array is valid and effective, or none of it is, and you will only see one invalid_request. Measured with pane.renamed (which does not exist; the pane-side name is pane.updated) placed into a three-item subscription list: all three failed and zero events arrived. When adding a new event name, subscribe to it alone and verify once. Another common cause is a missing required parameter: pane.agent_status_changed and pane.scroll_changed require pane_id, and pane.output_matched requires pane_id, source, and match.

Why are subscription and wait event names different?

Because they are two different structures. The Subscription used by events.subscribe uses dotted names (workspace.created, pane.agent_status_changed), while the match_event of events.wait and the event field of pushed frames use underscored names (workspace_created, pane_agent_status_changed). Measured: calling events.wait with a dotted name returns an unknown variant error immediately, and the error message lists all 19 legal underscored names. Writing a client means keeping a mapping table between the two schemes.

Can I use events.wait to wait for a pane being created?

Not in 0.9.2. The schema's EventMatch lists 19 events, but the runtime supports only agent state: measured with workspace_created you get unsupported_event_wait_match, whose message is events.wait currently supports pane agent status matches — note that this is returned immediately rather than as a timeout, so your retry logic will not wait for the event you expected. Waiting for a pane creation requires filtering a subscription stream yourself, or polling session.snapshot.

Can I treat the JSON Schema as a contract?

You can generate validation from it, but you should not trust it alone. Measured, there are four places where schema and runtime disagree: the set of events events.wait supports, the two naming schemes for subscriptions versus waits, the fact that Subscription contains no pane.renamed at all, and the fact that agent_status really is required for pane_agent_status_changed even though the CLI smooths that over. In addition, unknown parameters are silently ignored, so writing pane_id as paneid raises no warning — you get a missing field error, or worse, a successful response using a default. Validate against the schema's required list on the client side, and send one real request per method you intend to use.
