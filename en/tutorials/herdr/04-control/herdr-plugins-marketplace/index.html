Herdr Plugins and the Marketplace in Practice: Two Manifest Refusals, 14 Injected Environment Variables, Config and State Under Different Roots, and a Global Registry

Explain the Herdr plugin model from measurement: there is no SDK, the entire Herdr CLI is the plugin API; four required top-level manifest fields and two hard refusals with the error codes invalid_plugin_min_herdr_version and plugin_requires_newer_herdr; the division of labour between link and install around build commands; two validations that only warn and never block; the 14 injected environment variables captured live plus the full shape of HERDR_PLUGIN_CONTEXT_JSON; why plugin config-dir prints the config directory while HERDR_PLUGIN_STATE_DIR lives under a different tree; that the startup hook does not run at link time but only after a server restart; event hook firing and the silence after disable; and plugins.json being a global registry that no config override relocates. Plus the marketplace indexing rules and the trust boundary. Baseline herdr 0.9.2.

September 30, 2026 · 16 min · 3316 words · Mengshou Programming -  |  中文

The first three articles of module 4 solved “how to control Herdr from outside”. This one solves a different problem: how do you freeze the orchestration you worked out into a first-class citizen of Herdr — with menu entries, keybindings, event hooks, and its own pane, so anyone else can take it with one herdr plugin install.

Herdr’s plugin model makes an unusual decision: there is no SDK. That sounds liberating, but it also means no type checking, no sandbox, and no compile-time protection — every constraint moves to manifest validation and runtime behaviour.

This article measures that boundary item by item: which fields are refused outright, which only warn, what a command is actually injected with, where state should be written, and one real side effect I hit while experimenting.

Baseline: herdr 0.9.2 stable · macOS · all experiments ran in isolated named sessions, and afterwards the probe plugin was removed from the registry (plugins.json returned to []).

Conclusion first#

A Herdr plugin is a manifest plus a few argv commands, and the entire CLI is its API. The manifest has four required top-level fields, and omitting one is a hard refusal; two other classes of validation only warn and never block. At runtime Herdr injects 14 HERDR_* variables, and the config directory and the state directory are not under the same tree. The startup hook does not run at link time — only after a server restart. And the plugin registry is global — HERDR_CONFIG_PATH cannot move it.

1. The boundary: Herdr owns the host, the plugin owns the implementation#

The docs give a clean split:

Herdr ownsThe plugin owns
Installation, manifest validation, keybindings, terminal panes, events, invocation context, socket accessImplementation language, dependencies, files, durable state

There is no separate plugin SDK and no restricted command set. The original wording: “the entire Herdr CLI is the plugin API”, and a plugin can run anything you can run yourself as herdr ....

Two explicit v1 boundaries are worth knowing up front:

  • Runtime action registration is not part of v1 — actions, event hooks, panes, and link handlers are all declared statically in the manifest
  • Native non-terminal plugin UI is not part of v1 — if a plugin wants a UI, it declares a pane and runs a TUI in it

The second one is really a design stance: Herdr’s extension UI is the terminal. That is consistent with its terminal-workspace identity, and it means a plugin UI automatically inherits splits, scrollback, and SSH multiplexing.

2. The manifest: four required fields, two classes of entry point, one command rule#

id = "example.workspace-tools"
name = "Workspace Tools"
version = "0.1.0"
min_herdr_version = "0.9.0"
description = "Small workspace helpers"
platforms = ["linux", "macos", "windows"]

[[actions]]
id = "list-workspaces"
title = "List workspaces"
contexts = ["workspace"]
command = ["herdr", "workspace", "list"]

Top-level id, name, version, and min_herdr_version are required; description is optional.

The character rules for ids have two layers, which are easy to remember wrongly:

Id typeAllowed charactersDots allowed
Plugin idASCII letters, digits, . : _ -✅
Action / pane / link handler idASCII letters, digits, : _ -❌ dots are not allowed

The reason is that Herdr needs a globally unique qualified form of the shape plugin.id.action, and dots inside a local id would make the qualified name ambiguous.

command is an argv array that is not passed through a shell: there is no shell expansion unless your command starts a shell itself. That decides the two idioms:

command = ["herdr", "workspace", "list"]                        # pure argv, most portable
command = ["sh", "-c", "env | sort >> \"$FOO\"; echo ok"]        # start a shell explicitly when you need pipes or redirects

(I used the second form in the measurement probe below, because I needed to capture environment variables — see section 4.)

Two hard refusals, with measured error codes#

Missing min_herdr_version:

herdr --session lab plugin link /tmp/nomin

{"error":{"code":"invalid_plugin_min_herdr_version","message":"plugin min_herdr_version is required"},"id":"cli:plugin"}

A version newer than the running binary:

herdr --session lab plugin link /tmp/newer     # manifest says min_herdr_version = "0.99.0"

{"error":{"code":"plugin_requires_newer_herdr","message":"plugin requires Herdr 0.99.0 or newer; current Herdr is 0.9.2"},"id":"cli:plugin"}

The correct semantics of min_herdr_version: fill in the oldest Herdr version that supports the plugin APIs, event names, and manifest fields you use. It is a gate and a promise at once — by declaring it, you let Herdr decide compatibility on the user’s behalf at install time.

Two soft validations: warn, never block#

This is the easiest class of feedback to miss — the link succeeds, but the response body contains warnings:

herdr --session lab plugin link /tmp/labplugin     # deliberately omits platforms and misspells an event name

{"result":{"plugin":{
  "plugin_id":"rex.hello-lab","enabled":true,"source":{"kind":"local"},
  "manifest_path":"/private/tmp/labplugin/herdr-plugin.toml",
  "min_herdr_version":"0.9.0","version":"0.1.0",
  "warnings":[
    "unknown event 'worktree.craeted'",
    "manifest does not declare platforms; platform support unknown"
  ]}}}

Both are present, and the link still succeeded. plugin list displays them verbatim:

1 plugin installed:
- rex.hello-lab (Hello Lab) enabled [local:/private/tmp/labplugin; 2 warning(s)]
  warning: unknown event 'worktree.craeted'
  warning: manifest does not declare platforms; platform support unknown

Event names are validated against the known event table at link time (the docs state this), so a misspelled event name raises no error and simply never fires — you must read the warnings. This is the plugin-shaped version of the trap in article 2: worktree.created is a legal event name and worktree.craeted is not, but in TOML they look identical.

The division of labour around platforms is also worth remembering: the top level declares “which operating systems can run this plugin”; build / startup / action / event / pane / link handler entries can each declare platforms that override the top-level list, and inherit it when they do not. Invoking an action or opening a pane whose effective platforms exclude the current OS returns platform_unsupported.

3. link versus install: build commands belong to install only#

plugin link <dir|manifest>plugin install owner/repo[/subdir]
PurposeLocal development, testing from a checkoutInstalling from a public GitHub repository
Runs [[build]]No (the author builds their own working tree)After confirmation and before registration
Build failureNot applicableThe entire install aborts and the plugin is not registered
Trust previewNoneInteractive terminals show the source and the commands to be run
Non-interactive—--yes; --ref to pin a revision
Storage locationYour directoryA Herdr-managed checkout
Reinstalling—Reinstalling replaces the managed checkout; installing over a locally linked plugin is refused

[[build]] entries are ordinary argv commands too, but they receive no runtime plugin context and no Herdr socket environment. Whatever cargo / npm / bun / lua they need must already be on the user’s machine — Herdr reports build failures but does not install missing toolchains. Build failure output includes the plugin id, build index, working directory, command, exit status or spawn error, and capped stdout/stderr, without interpreting tool output.

One easily missed rule: if the build modifies herdr-plugin.toml after the install preview, the install aborts. That is the guard against “what was previewed is A, what gets installed is B”.

4. The injected runtime: 14 variables, measured#

I captured the full list with an action that pipes env | grep '^HERDR_' to stdout, read back from the plugin log (measured):

HERDR_BIN_PATH=/Users/rex/.local/bin/herdr
HERDR_ENV=1
HERDR_PANE_ID=w1:p1
HERDR_PLUGIN_ACTION_ID=dump-env
HERDR_PLUGIN_CONFIG_DIR=/Users/rex/.config/herdr/plugins/config/rex.env-probe
HERDR_PLUGIN_CONTEXT_JSON={"workspace_id":"w1","workspace_label":"tmp","workspace_cwd":"/private/tmp","tab_id":"w1:t1","tab_label":"1","focused_pane_id":"w1:p1","focused_pane_cwd":"/private/tmp","focused_pane_agent":"agent-a","focused_pane_status":"working","invocation_source":"cli","correlation_id":"cli:plugin"}
HERDR_PLUGIN_ID=rex.env-probe
HERDR_PLUGIN_ROOT=/private/tmp/labplugin2
HERDR_PLUGIN_STATE_DIR=/Users/rex/.local/state/herdr/plugins/rex.env-probe
HERDR_SESSION=batch8-lab
HERDR_SOCKET_PATH=/Users/rex/.config/herdr/sessions/batch8-lab/herdr.sock
HERDR_TAB_ID=w1:t1
HERDR_WORKSPACE_ID=w1

⚠️ HERDR_ENV=1 means a plugin cannot start a nested Herdr#

The injected environment carries HERDR_ENV=1 — so if a plugin command tries to launch a new Herdr client, it hits the nested-launch guard from article 1 (nested herdr is disabled by default). A plugin should operate the existing server through the CLI or socket, not start a new client.

Why the docs recommend HERDR_BIN_PATH over the raw socket#

The transport behind HERDR_SOCKET_PATH is OS-specific: a Unix client connects to a Unix socket path, a Windows client connects to a named pipe. Going through the CLI via HERDR_BIN_PATH avoids that difference. The docs stress this in both the plugin and socket API sections.

The config directory and the state directory are not under the same tree#

This is the easiest thing to look in the wrong place for:

HERDR_PLUGIN_CONFIG_DIR = ~/.config/herdr/plugins/config/<id>
HERDR_PLUGIN_STATE_DIR  = ~/.local/state/herdr/plugins/<id>

I first wrote to $HERDR_PLUGIN_STATE_DIR/env.log and then searched under ~/.config/herdr/plugins/ — and found nothing. The file had in fact written successfully, in the state tree:

$ ls -l ~/.local/state/herdr/plugins/rex.env-probe/
-rw-r--r--@ 1 rex  staff  787 Sep 30 18:26 env.log

And one CLI trap alongside it:

herdr plugin config-dir rex.env-probe
# /Users/rex/.config/herdr/plugins/config/rex.env-probe   ← config only, never state

plugin config-dir prints the config directory, and it requires a <plugin_id> (without one you get usage: herdr plugin config-dir <plugin_id>). The only way to learn the state directory is to read HERDR_PLUGIN_STATE_DIR.

The division of labour among the three directories (from the docs):

DirectoryWhat goes thereHerdr’s behaviour
HERDR_PLUGIN_ROOTPlugin sourceA managed checkout under GitHub install; do not store credentials or durable state
HERDR_PLUGIN_CONFIG_DIRUser-editable configuration (such as .env)Created, and seeded from legacy plugin config locations when present; it does not validate, sync, or delete contents
HERDR_PLUGIN_STATE_DIRLocal runtime stateCreated; the file format and lifecycle belong to the plugin

Agent state flows into the plugin context#

Two fields in the measured JSON above deserve their own mention:

"focused_pane_agent":"agent-a", "focused_pane_status":"working"

The agent state from module 3 lands directly in the plugin context. So a plugin action can learn which agent is running in the user’s focused pane and whether it is busy, without an extra call.

There are also invocation_source: "cli" and correlation_id: "cli:plugin" — the same action invoked from a TUI menu and from the CLI are distinguishable in the context. That is useful for logic like “only ask for confirmation when a human triggered this”.

The docs list worktree, selected text, clicked URL, and link handler among the available context fields — present only when available for that invocation, so parse defensively.

5. The three kinds of entry point, measured#

The startup hook does not run at link time#

The docs state that startup commands “run once for each enabled plugin after Herdr restores the session and its API socket is ready. They run again when a new server takes over during live handoff, but not when a client attaches, config reloads, or a plugin is linked or enabled.”

Measured: after linking, the log contained only one line (written by the event hook); after session stop on the named session and starting it again:

event:workspace.created
startup-ran          ← only appears after the restart

So never assume a startup hook has run just because you linked the plugin. Its purpose is one-shot initialisation (restore the plugin’s own state, call the APIs it needs, exit), not a supervised daemon. A startup failure does not stop the server; it is only recorded quietly in the plugin command log.

The docs name a legitimate use: save a declarative Agent view under HERDR_PLUGIN_STATE_DIR, then read and reapply it from the startup hook — because the view has to be rebuilt after a server restart.

The event hook fires, but goes quiet when disabled#

[[events]]
on = "workspace.created"
command = ["sh", "-c", "echo \"event:$HERDR_PLUGIN_EVENT\" >> \"$HERDR_PLUGIN_STATE_DIR/events.log\""]

Measured in four steps:

create a workspace            → the log gains "event:workspace.created"    ✅ fires
after plugin disable, create → the log stays the same length (2 lines)     ✅ does not fire
invoke while disabled        → rc=1  {"code":"plugin_disabled","message":"plugin rex.env-probe is disabled"}
after plugin enable, create  → the log grows to 3 lines                    ✅ fires again

Event hooks additionally receive HERDR_PLUGIN_EVENT_JSON carrying the full event payload.

plugin action list shows inherited platforms#

{'plugin_id': 'rex.env-probe', 'action_id': 'dump-env', 'contexts': ['workspace'], 'title': 'Dump runtime env'}
keys: ['action_id', 'command', 'contexts', 'platforms', 'plugin_id', 'title']

Note that platforms appears among the action’s keys — even though I declared it only at the top level. That is inheritance made visible on the server side.

The CLI invocation form (the trap from article 1):

herdr plugin action invoke <ACTION_ID> --plugin <PLUGIN_ID>

--plugin is an option, not a positional argument. The response body carries a context (with correlation_id and focused pane information), corresponding to the socket parameter context of plugin.action.invoke.

6. The registry is global: a real side effect I hit#

The docs say plugins.json is written alongside session.json. Measured, it is global, and HERDR_CONFIG_PATH cannot move it:

After I set HERDR_CONFIG_PATH=/tmp/labcfg/config.tomlActual location
config.toml/tmp/labcfg/config.toml ✅ moved
release-notes.json/tmp/labcfg/release-notes.json ✅ moved
sessions/<name>/~/.config/herdr/sessions/<name>/ ❌ still global
plugins.json~/.config/herdr/plugins.json ❌ still global
Plugin config directory~/.config/herdr/plugins/config/<id> ❌ still global

The consequence was not theoretical: I linked a probe plugin inside an isolated session, and herdr plugin list listed it in the default session — the one I was actually working in.

So plugins are not session-scoped resources. What is per-session is the socket, the cwd, the workspace topology, and the injected HERDR_SESSION; the plugin installation is shared across every session and executes in whichever session invoked it.

When testing plugins, either accept that sharing or unlink immediately afterwards — I did the latter, and the registry is back to [] with the default session reporting No plugins installed.

The difference between unlink and uninstall: unlink only deregisters and leaves files alone; uninstall deregisters and removes Herdr-managed GitHub checkout files. For a locally linked plugin use unlink.

7. The marketplace: an automatic index that refreshes every 30 minutes#

The rules are simple, and every one of them carries a security implication:

RuleContent
Listing conditionA public GitHub repository, the topic herdr-plugin, and at least one herdr-plugin.toml on the default branch whose required metadata parses
Card granularityOne card per repository, with every valid manifest counted as a separately installable plugin
Manifest locationRoot directory or a subdirectory
RefreshEvery 30 minutes; repositories are rescanned when the default-branch head changes
What a card showsRepository name, owner, description, star count, primary language, last push time; the plugin rows show name and version and link to the exact source directory
What the index recordsThe manifest path, id, name, version, platforms, and min_herdr_version, together with the exact default-branch commit
ExcludedForks, archived repositories, repositories without a valid manifest, and malformed manifest metadata
ReviewNone

Installing directly from GitHub:

herdr plugin install ogulcancelik/herdr-plugin-examples/worktree-bootstrap

The owner/repo[/subdir...] shorthand uses git, shows a trust preview in interactive terminals, runs supported build commands, and stores the result in a Herdr-managed directory. Use --yes non-interactively and --ref to pin a revision.

The trust boundary is yours to carry#

The docs are blunt enough to quote directly:

A plugin is ordinary code that runs on your machine. Its build and runtime commands run as your user, inherit your environment, and can call the full Herdr CLI. Herdr validates the manifest and keeps each plugin’s config and state in its own directory, but it does not review or sandbox plugin code.

So, before installing:

  1. Read herdr-plugin.toml, especially [[build]], [[startup]], and every command — a startup hook is code that runs automatically, and the install preview lists all of them
  2. Read the scripts or binaries it runs
  3. Pin a revision you have reviewed with --ref
  4. Remember that min_herdr_version guarantees API compatibility, not good intentions

8. Trap list#

  1. A successful link does not mean a clean manifest. warnings can hide a misspelled event name that will never fire. Read the response body every time.
  2. A missing min_herdr_version is a hard refusal (invalid_plugin_min_herdr_version), not a warning. All four top-level required fields matter.
  3. Do not assume the startup hook ran because you linked. Only a server start or live handoff runs it.
  4. State and config are not under the same tree. Write files via the injected HERDR_PLUGIN_STATE_DIR instead of looking under ~/.config/herdr/plugins/.
  5. plugin config-dir prints the config directory only, and requires a <plugin_id>.
  6. Do not write durable state into HERDR_PLUGIN_ROOT — under GitHub install it is a managed checkout that a reinstall replaces.
  7. The plugin registry is global and HERDR_CONFIG_PATH cannot move it. Unlink after testing.
  8. plugin link does not run build commands, so “it works when linked but install fails” is normal — build your working tree yourself during local development.
  9. Build commands get no socket environment, so do not call Herdr from a build.
  10. A plugin command cannot start a new Herdr client (HERDR_ENV=1 is injected). Operate the existing server via HERDR_BIN_PATH or the existing socket.
  11. Windows portability: prefer HERDR_BIN_PATH plus the CLI; do not assemble named pipe names yourself.
  12. Local action / pane / link handler ids cannot contain dots — the qualified plugin.id.action form needs the dot as a separator.
  13. Registering actions at runtime is impossible (not in v1); dynamic behaviour requires combining statically declared entry points.
  14. Being listed in the marketplace is not a review pass. It only means the repository tagged itself.

Frequently Asked Questions

Do I need to learn an SDK to write a Herdr plugin?

No. The documentation is explicit that there is no separate plugin SDK and no restricted command set — the entire Herdr CLI is the plugin API. The command declared in the manifest is an argv array, which can be bash, node, python, a Rust binary, lua, or anything your machine can run. When it needs to do more, the command calls back into Herdr through the binary at HERDR_BIN_PATH or talks to the socket directly. Herdr owns the host surface: installation, manifest validation, keybindings, terminal panes, events, invocation context, and socket access. The plugin owns its implementation language, dependencies, files, and durable state.

My plugin will not install and reports invalid_plugin_min_herdr_version. What does that mean?

min_herdr_version is one of four required top-level fields (id, name, version, min_herdr_version) and omitting it is refused. Two error codes were measured here: with the field missing, invalid_plugin_min_herdr_version with the message plugin min_herdr_version is required; with a version newer than the current binary, plugin_requires_newer_herdr, whose message on this machine reads plugin requires Herdr 0.99.0 or newer; current Herdr is 0.9.2. The field means the oldest Herdr version that supports the plugin APIs, event names, and manifest fields your plugin uses, which makes it both an installation gate and a promise you are making to users.

Why did my startup hook not run?

Because startup hooks run only after the server has restored the session and its API socket is ready. Linking or enabling a plugin does not trigger them, and neither does attaching a client or reloading config. Measured: after linking, the hook's log file contained only a line written by the event hook; after stopping the named session and starting it again, startup-ran finally appeared. Also remember that it is a one-shot initialisation command rather than a supervised daemon: restore your own state, call the Herdr APIs you need, and exit. A startup failure does not stop the server, it is only recorded quietly in the plugin command log.

Where should a plugin put its configuration and its runtime state?

Use the two injected directories rather than assembling paths yourself, and know that they are not under the same tree. Measured, HERDR_PLUGIN_CONFIG_DIR is ~/.config/herdr/plugins/config/<plugin_id> while HERDR_PLUGIN_STATE_DIR is ~/.local/state/herdr/plugins/<plugin_id> — config under the config tree, state under the state tree. I initially wrote to $HERDR_PLUGIN_STATE_DIR/env.log and then looked under ~/.config/herdr/plugins/, found nothing, and concluded the write had failed. It had succeeded; the file was in the state tree. One CLI trap: herdr plugin config-dir <id> prints the config directory, never the state directory.

Can I install a plugin for just one session?

No. The plugin registry plugins.json is global, living at ~/.config/herdr/plugins.json, and HERDR_CONFIG_PATH does not relocate it — measured by pointing the config directory at /tmp in an isolated session, linking a probe plugin, and then seeing it listed by herdr plugin list in the default session too. What is per-session is the socket and the runtime environment (the injected HERDR_SOCKET_PATH and HERDR_SESSION point at that session), while the plugin installation is global and executes in whichever session invoked it.

Does the Herdr plugin marketplace review submitted plugins?

No. The marketplace indexes public GitHub repositories tagged with the topic herdr-plugin, as long as the default branch contains at least one herdr-plugin.toml whose required metadata parses. One card per repository, and every valid manifest counts as a separately installable plugin. The index refreshes every 30 minutes and rescans when a repository's default-branch head changes. The docs put it bluntly: being listed means the repository tagged itself, not that Herdr vetted it. Forks, archived repositories, repositories without a valid plugin manifest, and malformed manifest metadata are all excluded.
