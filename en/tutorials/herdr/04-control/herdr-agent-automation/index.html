Herdr Agent Automation in Practice: Three Primitives, Last-Writer-Wins State Authority, and the Time My Own Measurement Lied to Me

Assemble the CLI and socket into runnable agent orchestration: what the layout, pane, and agent primitives are each responsible for, why you must read ids from the JSON of a creation command rather than guessing, a measured four-row matrix of agent targets, the three real semantics of pane report-agent (last-writer-wins across sources, a release that does not roll back, and a stale seq discarded silently while returning rc=0), the full process of the wrong conclusion I drew in an isolated session and then overturned with a single-source re-test, the state semantics of agent wait and agent prompt, alternate-screen history reads and their boundaries, and three orchestration recipes you can run directly. Baseline herdr 0.9.2.

September 30, 2026 · 18 min · 3712 words · Mengshou Programming -  |  中文

A concrete requirement: you have a coding agent running in pane A, and you want it to open a pane, start a second agent there, hand it work, wait for it to finish, and read the result back.

The whole chain needs no TUI, no second terminal, and no human. But making it work means crossing three layers of abstraction, two addressing schemes, and getting a state-reporting protocol right whose failure mode produces no error at all.

This article gives you the division of labour among the three primitives, a measured addressing matrix, the three real semantics of state reporting — and the complete story of a conclusion I measured wrong on this machine and then overturned. That part is worth more than any conclusion, because it is the exact shape of the pitfall you will hit.

Baseline: herdr 0.9.2 stable · macOS · all experiments ran in the isolated named session batch8-lab (article 1 shows how to start one); the session I actually work in, w3, was never touched.

Conclusion first#

Agent automation with Herdr has three non-optional steps: read ids out of the JSON returned by creation commands, address by pane id, and read back after reporting. Because state is last-writer-wins, a stale seq is discarded silently, and release does not roll back. Together those mean: your script must never assume “I just reported working, so it is working now”.

1. Three primitives: location, terminal, agent#

The docs give a clean division of labour:

PrimitiveResponsibility
Layout (workspace / tab / pane topology)Creating and organising terminal locations
PaneControlling a raw terminal: run commands, send input, read output, wait for output
AgentControlling a recognised coding agent by name and lifecycle state

The key sentence is: a pane exists whether or not it contains an agent; an agent is the recognised process currently running inside a pane. So agent start only activates an existing shell pane — it never creates, splits, or moves layout.

Another hierarchy detail that is easy to get wrong: creating a workspace also creates its first tab and root pane; creating a tab creates its root pane. So the normal flow is “create → take the returned root pane id → split only when that layout needs another terminal”.

Measured: what creation commands return#

herdr --session batch8-lab workspace create --cwd /tmp --label api --no-focus

{"id":"cli:workspace:create","result":{"type":"workspace_created",
  "workspace":{"workspace_id":"w8","label":"api","number":8,"active_tab_id":"w8:t1","pane_count":1,"tab_count":1,"focused":false,"agent_status":"unknown"},
  "tab":{"tab_id":"w8:t1","workspace_id":"w8","label":"1","number":1,"pane_count":1,"focused":false,"agent_status":"unknown"},
  "root_pane":{"pane_id":"w8:p1","workspace_id":"w8","tab_id":"w8:t1","cwd":"/private/tmp","foreground_cwd":"/private/tmp","agent_status":"unknown","focused":false,"revision":0,"scroll":{...}}}}

All three fields are there: .result.workspace, .result.tab, .result.root_pane — consistent with the docs.

Note that --cwd /tmp came back as /private/tmp in the result (on macOS /tmp is a symlink and Herdr reports the resolved real path). Do not compare the returned cwd with the string you passed.

And a split:

herdr --session batch8-lab pane split w8:p1 --direction right --no-focus
# → .result.pane.pane_id = "w8:p2"

pane split returns only .result.pane (no move_result-style wrapper).

The correct approach is to extract from JSON and never guess an id:

created=$(herdr workspace create --cwd ~/project --label api --no-focus)
pane_id=$(printf '%s\n' "$created" | jq -r '.result.root_pane.pane_id')

split=$(herdr pane split "$pane_id" --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

Ids like w8:p1 look patterned (workspace number, pane number), which makes it tempting to write echo "w9:p1" as a shortcut. It will occasionally be right and occasionally land on someone else’s pane — the worst class of automation bug, because it is not consistent enough to be caught by testing.

2. Addressing: a measured four-row matrix#

The documented rule: an agent target is a unique live agent name, or the pane id that currently hosts the agent. Terminal ids and bare agent-kind labels are not targets.

I ran each form in the isolated session (measured):

Target formWhat it isrcResult
reviewerA live alias created by agent rename0✅ returns the agent object
w1:p1A pane id0✅ returns the agent object
claudeAn agent kind label (the agent field)1❌ agent_not_found
term_65cb064b0fd241A terminal id1❌ agent_not_found

The third row is the most misread: agent get returns an object containing "agent":"claude", yet querying claude finds nothing. Because the agent field is the kind label and the name field is the alias:

{"agent":{"agent":"claude","name":"reviewer","agent_status":"blocked","pane_id":"w1:p1","state_change_seq":54,...},"type":"agent_info"}

Two fields, and only name is addressable.

Where an alias comes from, and how long it lives#

agent rename can give a recognised agent an alias (measured rc=0, returning the object with name). But the alias lives as long as the agent identity:

herdr --session batch8-lab agent rename w1:p1 myhelper   # rc=0, returns name: myhelper
sleep 1.5
herdr --session batch8-lab agent get myhelper
# rc=1  agent_not_found

That rename was applied to an unknown-label self-reported state (--agent lab-bot), whose underlying identity was not retained — so the alias went with it. agent rename is therefore not a way to make any string addressable; it only labels an agent identity that already exists.

The docs define the alias lifetime: it is cleared when that agent exits, is released, or is replaced; it does not permanently rename the pane.

Practical advice#

Use pane ids as targets in orchestration scripts. The name is a convenience for people; w1:p1 is the stable address. If you want a human-friendly interface, maintain your own name → pane_id table alongside it.

3. The three real semantics of state reporting (and the time I measured it wrong)#

This is the core of the article. pane report-agent returns only success or failure, and “success” means less than you would like.

Semantic one: last writer wins across sources#

Two sources reporting the same pane:

start:                              ('brand-x', 'working')
srcA reports agent-a working  →  pane:   ('agent-a', 'working')
srcB reports agent-b blocked  →  pane:   ('agent-b', 'blocked')   ← the second source took over

The pane displays the last accepted report, not “the integration you believe has authority”. Which one reported first, and whether Herdr recognises its label, does not change this.

Semantic two: release does not roll back#

srcB release-agent  →  pane:  ('agent-b', 'blocked')   ← still on srcB's state
srcA reports idle   →  pane:  ('agent-a', 'idle')

pane release-agent ends that source’s own lifecycle authority. It does not restore the pane to the previous source’s state. In other words, after a release the pane still carries the last state reported by the source being released.

Semantic three: a stale seq is silently discarded, and returns success#

srcA reports working               → pane: ('agent-a', 'working')
srcA reports blocked with --seq 1000 → rc=0, stdout empty
                                   → pane still ('agent-a', 'working')   ← nothing happened

This is the most dangerous one: the command succeeds, prints nothing, and the state does not change. The docs say Herdr ignores reports whose seq is not higher than the last value it accepted, which prevents late or out-of-order reports from overwriting newer state — correct by design, but the failure signal is zero.

So:

  • Use a millisecond timestamp as seq (python3 -c 'import time;print(int(time.time()*1000))' or date +%s%3N); it is naturally monotonic across sessions and restarts
  • Read back with pane get after any report that matters. Do not trust rc=0

How I got this wrong#

This is worth recording in full, because it is exactly how the word “measured” gets misused.

In my first round in the isolated session I did this: repeatedly report on the same pane from four different sources (labtest, labprobe, rawprobe, custom:docs), alternating the label between lab-bot (unknown to Herdr) and claude/pi/grok (kinds Herdr knows), incrementing seq from a shared counter.

The observed pattern was remarkably clean:

label=lab-bot  → +0.1s present, +0.5s present, +1.2s gone
label=claude   → +0.1s present … +11.6s still present
label=grok     → +11.6s still present (and grok is not even installed)
label=kitt-e   → gone immediately

I concluded: “Herdr only retains agent labels it knows, and unknown labels are cleared at the next detection tick (about 0.4 seconds).” That conclusion was corroborated by the documented statement that adding a completely new agent still requires a Herdr binary update — it looked airtight.

Then I ran a second round — a single source, clean state (first release-agent-ing every source that had ever touched that pane):

=== SINGLE source, shell foreground, UNKNOWN label:
   + 0.1s -> ('brand-x', 'working')
   + 0.5s -> ('brand-x', 'working')
   + 1.0s -> ('brand-x', 'working')
   + 2.0s -> ('brand-x', 'working')
   + 3.0s -> ('brand-x', 'working')
   + 5.0s -> ('brand-x', 'working')     ← the unknown label held for over 5 seconds

The unknown label brand-x was perfectly stable. My first round was wrong.

Where it went wrong: in the first round, each source’s “last accepted seq” is accounted separately. As I alternated reports across several sources while incrementing a shared counter, a new report from one source was blocked by its own earlier, higher seq, or was overwritten by another source reporting later. The “disappeared after 0.4 seconds” I observed was actually another source’s state becoming the pane’s displayed value again — not “the unknown label being cleared”.

More ironically, the observation that “grok persisted despite not being installed” persisted for the wrong reason: grok’s report simply happened to be the last one accepted in that round.

Three lessons, reproduced verbatim in the trap list:

  1. In a multi-variable experiment, an “A works, B does not” contrast must first rule out shared state. My seq counter and my source list were both shared.
  2. A conclusion that corroborates the documentation is still an unproven conclusion. The statement that a binary update is required is true, but it does not explain what I measured.
  3. Overturning yourself is cheap: clean the state, use one source, run it again. That took about thirty seconds and saved an entire wrong article.

Settling the docs question#

Worth closing the loop, since it looked like a conflict: the example in socket-api.mdx for pane.report_agent uses "agent": "docs-bot", a label Herdr does not know. That label is accepted and retained in measurement (brand-x behaves the same way under a single source). So the example is fine, and I misread it in round one.

A related fact that still holds#

Although an unknown label can retain its state, it is still not addressable: agent get <self-reported-label> continues to return agent_not_found (the matrix in section 2). Retaining state and being addressable are two different things.

4. Waiting and prompting: the exact boundary of state semantics#

agent wait#

herdr agent wait <target> [--until STATUS]... [--timeout MS]
  • Without --until it matches idle, done, and blocked; unknown must be given explicitly
  • If the current state already matches it returns immediately, so “check first, then wait” is redundant
  • Without --timeout it waits indefinitely — in CI that is a hang
  • A timeout is the timeout error, JSON on stderr, exit code 1
  • --until can be repeated to accept several states

idle and done both mean “ready for input”. The difference is who has seen it: done is idle but not yet marked as seen, and explicit pane focus / agent focus mark the target as seen — reads do not. Each TUI client tracks which completions it has viewed independently, so the Done badge on screen and the state reported by the CLI can disagree (module 3 article 1 covers the same mechanism from the detection side).

If your orchestration logic depends on “this task genuinely completed once”, use exact --until states rather than relying on the done/idle distinction. The docs also mention that an agent response may carry completion_seq, identifying the current idle transition as completed work independently of who has viewed it. It matches that transition’s state_change_seq; startup and session changes do not set it. Older servers may omit the field.

agent prompt#

herdr agent prompt <target> <text> [--wait] [--until STATUS]... [--timeout MS]

Four semantics, consistent between docs and measurement:

  1. Text plus a delayed Enter as one ordered submission, honouring the terminal’s live bracketed-paste mode; it can prompt an agent that is already working
  2. Success without --wait acknowledges the writes, not the start of a turn
  3. An agent that is already blocked returns agent_blocked immediately, without writing any input — a guard, not something to work around
  4. With --wait, when the prompt starts from a non-working state Herdr waits up to five seconds after submission to observe working or blocked, otherwise returning agent_prompt_stalled; if the caller’s timeout expires first, you get the ordinary timeout error

The intent behind rule 4 is explicit: it prevents an unrelated idle, done, or session change from satisfying the wait.

One more that must be internalised: --until is rejected on agent prompt unless --wait is also present (the docs: --until narrows the matching states and is rejected unless --wait is also present).

agent start#

herdr agent start reviewer --kind codex --pane "$review_pane" -- -m gpt-5.4
  • The target pane must be an available shell pane: the shell itself owns the foreground, with no foreground command, editor, or agent running
  • A successful start returns only after Herdr detects the expected agent in the same terminal and marks it ready for interactive input — not “the process started”
  • If detection reports blocked during startup, the command returns agent_not_ready immediately
  • The default startup timeout is 30000 ms; --timeout must be greater than 3000 and at most 300000
  • Names must match [a-z][a-z0-9_-]{0,31} and be unique among live agents
  • 24 kinds: pi, claude, codex, gemini, cursor, devin, agy, cline, omp, mastracode, opencode, copilot, kimi, kiro, droid, amp, grok, hermes, kilo, qodercli, qwen, letta, maki, muse

Remember that agent start does not create layout — split and obtain the pane first, then start.

One usage detail confirmed by measurement: parameter forms for pane run#

herdr --session batch8-lab pane run w8:p2 "echo QUOTED_FORM_OK"   # ✅ one quoted string works too
herdr --session batch8-lab pane run w8:p2 echo QUOTED_FORM_OK     # ✅ the multi-argument form works
herdr --session batch8-lab pane run w8:p2 -- echo X               # ❌ -- is sent into the shell

The docs’ recipes use the quoted single-argument form (herdr pane run w1:p3 "just test --watch"), which works as measured — and it is the right form when the command itself contains --, because the --watch inside the quotes is the command’s own argument and never touches Herdr’s parser.

5. Three recipes you can run directly#

Recipe 1: start a helper, give it work, and wait for it to settle#

#!/usr/bin/env bash
set -euo pipefail

# ① Open a pane to the right of the current one and take the id from the JSON
split=$(herdr pane split --current --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')

# ② Start the agent in that pane (the pane must be an available shell)
herdr agent start reviewer --kind codex --pane "$review_pane" -- -m gpt-5.4

# ③ Assign work and wait for it to settle
herdr agent prompt reviewer "Review the current diff" --wait --timeout 120000

# ④ Collect the result
herdr agent read reviewer --source recent-unwrapped --lines 120

Every jq extraction is necessary, for the reason given in section 1.

Recipe 2: wait for the agent to ask, inspect, then decide#

herdr agent wait reviewer --until blocked --timeout 120000
herdr agent read reviewer --source recent-unwrapped --lines 80
herdr agent send-keys reviewer esc

agent send-keys sends logical key names: enter, up, esc (escape is an alias), ctrl+c. Herdr validates every key before writing any bytes, so it never sends half of them.

Why send-keys is mandatory here rather than prompt: an agent in blocked state is refused outright by prompt. That is deliberate — an approval dialog needs an explicit key, not a piece of text.

Recipe 3: do not treat ordinary processes as agents#

herdr pane run w1:p3 "just test --watch"
herdr pane run w1:p3 "npm run build"
herdr pane wait-output w1:p3 --regex "passed|failed" --timeout 120000

The docs are explicit: use pane wait-output for ordinary commands and servers, and agent wait for coding agents. pane wait-output does not interpret agent lifecycle at all.

One measured detail: pane wait-output checks the current snapshot immediately, so output that already exists can match. That means if you do not clear the screen, you may match a leftover marker from the previous round. In my measurement waiting for MARKER_7788, the returned matched_line was rex@… /tmp % echo MARKER_7788 — it matched the echoed command line, not the output line. Choose a marker that does not appear in the command string.

6. The boundary of long reads: the alternate screen#

Full-screen agents such as Claude Code and OpenCode render their transcript in the terminal’s alternate screen rather than in Herdr’s host scrollback. So “reading more than one screen of history” needs special handling.

The documented mechanism (I had no full-screen agent running, so this path is not verified on this machine):

  • For an idle, recognised agent at the bottom of its transcript, a recent or recent-unwrapped read automatically uses the agent’s own mouse-scroll interface when --lines requests more than the visible screen. Herdr collects overlapping pages and returns the viewport to the bottom before completing the read. The same behaviour applies to pane read when the pane contains that agent, with no additional option
  • All other reads remain passive: visible, detection, ANSI reads, output waits and subscriptions, a manually scrolled agent, a direct attachment, and applications that do not report mouse-wheel input — Herdr does not move the application viewport for any of these
  • An explicit agent read --lines N that needs alternate-screen history returns agent_not_idle while the agent is working, blocked, or unknown; wait for idle and retry, or use --source visible

One thing I did measure, and which is easy to misread as a contradiction: agent read w1:p1 --source recent-unwrapped --lines 200 against a pane whose agent was reported as blocked returned rc=0 with real text, not agent_not_idle. That is correct behaviour — the agent_not_idle guard only applies when the read actually needs alternate-screen history, and content fitting in scrollback does not.

If a full response is still unavailable, the docs give a genuinely practical approach: ask the agent to write the answer as Markdown in a temporary directory and reply only with the file path, then read the file directly. In orchestration that is far more reliable than scrolling the screen repeatedly.

Incidentally, --lines defaults to 80 rows for recent sources; visible and detection return the full snapshot when --lines is omitted.

7. Trap list#

  1. Never guess a pane id. Every creation command prints JSON; take it from .result.root_pane.pane_id or .result.pane.pane_id.
  2. One lifecycle-authority holder per pane. Multiple sources are last-writer-wins, and you will see a state you did not report.
  3. release-agent does not roll back. After a release the pane still carries the released source’s last state.
  4. A stale seq is silently discarded, with rc=0 and no output. Use a millisecond timestamp as seq and read back with pane get after important reports.
  5. agent wait has no default timeout. Always pass --timeout in CI or you will hang forever.
  6. Distinguish exit code 1 from 2: 1 is runtime (target gone, timeout), 2 is a usage error (do not retry).
  7. --until on agent prompt requires --wait, otherwise it is rejected.
  8. agent prompt refuses a blocked agent with agent_blocked and writes nothing. To answer an approval use agent send-keys.
  9. agent start does not create layout, and the pane must be at a shell prompt; --timeout must fall between 3000 and 300000.
  10. Do not add -- to pane run (measured in article 1); quote the whole string when the command itself contains --.
  11. wait-output’s marker can match the echoed command line rather than the command output.
  12. After pane move you must switch to .result.move_result.pane.pane_id (measured w8:p2 → w1:p5), with the old value in previous_pane_id. A wait already in progress ends with agent_not_running.
  13. pane move’s --workspace cannot be used alone (measured rc=2, a usage error); combine it with --new-tab or --new-workspace, or pass --tab directly.
  14. Never run a controlled experiment with shared state between arms (the mistake in section 3). Clean the state, use one source, re-run — thirty seconds of work.

Frequently Asked Questions

Can I use Herdr to let one agent direct another agent?

Yes — that is the layer Herdr has that tmux does not. The agent in one pane can call Herdr's CLI or socket: split a new pane with pane split and take the returned pane id, start a supported agent with agent start and hand it that pane, then give it work with agent prompt --wait --timeout, and collect the result with agent read. The whole chain needs no TUI interaction and no second terminal. The docs call this layer three primitives: layout handles location, pane handles a raw terminal, and agent handles a recognised coding agent together with its lifecycle state.

Why did the agent state I reported change without me reporting again?

Because multiple sources on one pane are last-writer-wins. Measured: after srcA reports agent-a working the pane shows agent-a, and once srcB reports agent-b blocked the pane shows agent-b — whatever was accepted last is what the pane now displays. Note also that release-agent does not roll back: after srcB releases, the pane still sits on agent-b/blocked rather than reverting to srcA's state. So keep exactly one lifecycle-authority holder per pane, and have any script that depends on state read it back before trusting it.

Why did my report with an incrementing counter have no effect and no error?

Because a stale seq is silently discarded and the command still succeeds. Measured: report working, then report blocked with seq=1000; the command returns rc=0 with empty stdout, and the pane state is still working. Herdr ignores reports whose sequence number is not higher than the last value it accepted, which prevents late or out-of-order reports from overwriting newer state — that is by design, but the failure signal is zero. Use a millisecond timestamp as your seq and read back with pane get after any report that matters.

How long will agent wait wait, and how do I know it timed out?

Without --timeout it waits indefinitely. A timeout is a runtime error: JSON on stderr with exit status 1. Usage errors exit with status 2 and must not be retried. The default match set is idle, done, and blocked; waiting for unknown requires an explicit --until unknown. agent wait also returns immediately when the current state already matches, so checking first and waiting are equivalent.

What is the difference between agent prompt and pane send-text?

Three things. prompt writes text plus an encoded Enter as one ordered submission and honours the terminal's live bracketed-paste mode; send-text sends literal text with no Enter. prompt resolves through agent addressing, so it rejects the operation if that agent no longer controls the pane, whereas send-text addresses the terminal regardless of its occupant. And prompt refuses an agent that is already blocked, returning agent_blocked without writing any input — a guard that stops you typing a prompt into an approval dialog. To answer an approval UI, use agent send-keys deliberately.

Why does agent get fail when I use the agent's name?

It depends where that name came from. Only two targets are legal: a unique live agent name, or the pane id currently hosting the agent. An agent started with agent start has a live name, and one named with agent rename does too; but the label you pass to pane report-agent --agent is only a display name and is not a live name. Measured four-row matrix: an alias created by agent rename returns rc=0, a pane id returns rc=0, the kind label claude returns rc=1 agent_not_found, and a terminal id returns rc=1 agent_not_found. Automation scripts should always use pane ids.
