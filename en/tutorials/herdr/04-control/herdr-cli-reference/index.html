Herdr CLI Field Guide: 18 Verbs, Three Exit Codes, Four-Level Session Routing, and the Nested-Launch Gate You Will Hit From Inside an Agent

Read the Herdr command line as an interface rather than a menu: measured mappings between 18 top-level verbs and 102 socket methods, the single-line JSON envelope, where the 0/1/2 exit-code boundary sits, four-level session routing from --session to HERDR_SOCKET_PATH to HERDR_SESSION to the default socket, the real on-disk location of a named session socket, why HERDR_CONFIG_PATH relocates config.toml but not the sessions directory or plugins.json, the two gates that both reject a nested herdr, the addressing boundary between pane ids and agent targets, and six parameter traps including pane run handing a literal -- to your shell.

September 30, 2026 · 20 min · 4230 words · Mengshou Programming -  |  中文

You have a coding agent running in a Herdr pane, and now you want that agent to operate Herdr in return: open a pane to run tests, wait for the agent in another pane to finish, read a chunk of screen output.

The first reaction is herdr --help, and then you are looking at 22 usage lines, 18 verbs, and between one and twenty-five subcommands under each — while the “Common commands” section shows you about ten of them.

This article will not transcribe the commands. It gives you three things: the real shape of the command surface (what is for people and what is for scripts), the output and exit-code contract (which is everything script reliability depends on), and routing and addressing rules (which decide which session and which pane your command reaches).

Baseline: herdr 0.9.2 stable · macOS · every output below was measured on this machine, and anywhere it says “measured” you can reproduce it line by line.

Conclusion first#

herdr --help is a menu for people; the socket API is the interface, and the CLI is a thin wrapper over the API. So the right way to read the CLI is not to memorise commands but to remember three things: output is always a single-line JSON envelope, there are exactly three exit codes 0/1/2 and the error for 1 goes to stderr, and session routing has four levels of precedence. Nearly everything else that bites you comes from two boundaries: you are inside Herdr (the nested-launch guard), and the name you think is a name is not one (target addressing).

1. The real shape of the command surface: 18 verbs, 102 methods#

Start with a measured table. The left column is the top-level CLI verb, the right column is the number of subcommands its own help lists:

Measured: the Usage section of herdr --help lists 22 lines, but those are usage examples, not a command inventory — plugin, terminal, and status do not appear there. To confirm whether a verb exists, run herdr <verb> --help and see whether it prints a usage block with a description. Conversely, herdr doctor answers:

unknown command: doctor
run 'herdr --help' for usage

with exit code 2 (measured). In other words there is no doctor-style one-shot health check; troubleshooting is done with config check, status, and api snapshot separately.

The CLI does not cover the whole interface#

herdr api schema --json emits a 272 KB JSON Schema on this machine, listing 102 methods across 19 families:

pane 35 · agent 12 · plugin 11 · workspace 9 · tab 7 · server 6 · worktree 4
layout 3 · integration 3 · events 2 · client 2
+ 8 single-method families: ping / command.invoke / session.snapshot / popup.close
  / notification.show / product_announcement.dismiss / release_notes.dismiss
  / client_shell.surface.set

Comparing against the first table shows the structure: the CLI verb count (18) is far below the method count (102). Methods like pane.scroll, pane.clear, pane.link.activate, layout.apply, agent.view.set, and command.invoke have no CLI equivalent and are reachable only over the socket (article 2).

The reverse also holds and is worth memorising: the CLI’s id field is the method it called. herdr pane current returns "id":"cli:pane:current", and herdr workspace list returns "id":"cli:workspace:list". So from any CLI output you can immediately infer the underlying method name and look up its parameter definitions in the schema.

There is a manual for agents hidden in the help#

Every help output ends with this block (measured):

  Help a human understand or set up Herdr for the first time:
    https://herdr.dev/agent-guide.md
  Debug or investigate a problem with Herdr:
    https://herdr.dev/llms.txt
  Control Herdr panes, agents, or workspaces:
    SKIP if a Herdr skill is already in your context. Otherwise run: herdr --skill

herdr --skill prints a 14162-byte skill file on this machine — no network, no installation. That is the operating manual for agents, and it is far more complete than --help. Read it before writing agent automation.

Incidentally, the error that refuses nested launch also quotes Jurassic Park. Details like that confirm that Herdr’s error messages are written for humans to read, while its JSON errors are written for scripts to parse. Both exist; do not mix them up (next section).

2. The output contract: a single-line JSON envelope plus three exit codes#

What success looks like#

All machine-readable output is one line of JSON in a fixed envelope:

herdr pane current

{"id":"cli:pane:current","result":{"pane":{"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-hugo","focused":true,"pane_id":"w3:p2","revision":1,"tab_id":"w3:t2","terminal_id":"term_65ca0990363e22","workspace_id":"w3"}}}

Three conventions are worth isolating:

  1. id is not a request id, it is a command identifier. The CLI generates it as cli:<verb>:<subcommand>. When you connect to the socket directly, id is whatever you sent (article 2).
  2. result.type is the discriminant. The same result field has a different shape per command, so branch on type rather than guessing keys.
  3. Success may produce no output at all. herdr pane report-agent prints nothing on success (measured: rc=0, stdout empty). Do not treat “no output” as failure — check the exit code.

What failure looks like#

Measured, four cases, with a clean boundary on exit codes and stream:

CaseCommandrcstdoutstderr
Target does not existherdr agent get nosuch1empty{"error":{"code":"agent_not_found","message":"agent target nosuch not found"},"id":"cli:agent:get"}
Wait timed outherdr pane wait-output w1:p1 --match NEVER --timeout 12001emptyJSON error
Wrong option nameherdr pane list --bogus2emptyunknown option: --bogus
Verb does not existherdr doctor2emptyunknown command: doctor

This matches the documented statement that a timeout or server error is emitted as JSON on stderr with exit status 1, and CLI usage errors exit with status 2 — measured as consistent.

So the correct shape in a script is:

# ① Handle usage errors separately from runtime errors: 2 means you typed it wrong, 1 means the environment or target is wrong
if ! out=$(herdr agent wait "$PANE" --until idle --timeout 60000 2>/tmp/err); then
  rc=$?
  if [ "$rc" -eq 2 ]; then echo "bad command line, do not retry"; exit 2; fi
  echo "runtime failure: $(cat /tmp/err)"   # this is JSON, jq .error.code works
  exit "$rc"
fi

Two rules you must internalise:

  • Error JSON goes to stderr, not stdout. So herdr xxx | jq hands jq an empty input on failure, and you will misread “it failed” as “there is no data”. To capture the error you must redirect stderr separately.
  • Exit code 2 must not be retried (your command line is wrong); exit code 1 is the one that may need a human.

--json is not a global flag#

Only some commands accept --json: api schema, agent explain, plugin list, machine status, and similar. Default output is already JSON for list-shaped commands, and text for human-readable ones (plugin list, integration status, status), where you need --json explicitly.

herdr status is a typical case: by default it prints three text sections (client: / server: / update:), while herdr status client and herdr status server each print one — measured:

# herdr status client
version: 0.9.2
channel: stable
protocol: 22
endpoint_protocol_generation: 1
binary: /Users/rex/.local/bin/herdr

# herdr status server
status: running
version: 0.9.2
endpoint_compatible: yes
private_protocol: 22
private_protocol_compatible: yes
socket: /Users/rex/.config/herdr/herdr.sock

Note protocol: 22 and endpoint_protocol_generation: 1 — they are the client/server compatibility criteria. Checking endpoint_compatible: yes before you start talking to the socket is far cheaper than handling a protocol error afterwards.

3. Session routing: four levels of precedence and two directories that do not move#

Which server a CLI command reaches is decided in this order (defined by the docs, each level verified on this machine):

1. explicit --session <name>
2. HERDR_SOCKET_PATH
3. HERDR_SESSION=<name>
4. the default session socket

Named sessions get their own socket:

~/.config/herdr/herdr.sock                          ← default
~/.config/herdr/sessions/<name>/herdr.sock          ← named

Measured with a session called batch8-lab, herdr session list reports them separately:

name                 status   directory                                        socket
default              running  /Users/rex/.config/herdr                         /Users/rex/.config/herdr/herdr.sock
batch8-lab           running  /Users/rex/.config/herdr/sessions/batch8-lab     /Users/rex/.config/herdr/sessions/batch8-lab/herdr.sock

And herdr --session batch8-lab workspace list returns that session’s own w1, completely unrelated to the w3 I was using:

{"id":"cli:workspace:list","result":{"type":"workspace_list","workspaces":[{"active_tab_id":"w1:t1","agent_status":"unknown","focused":true,"label":"tmp","number":1,"pane_count":1,"tab_count":1,"workspace_id":"w1"}]}}

This is the safety boundary: any write operation carrying --session physically travels a different socket and cannot hurt the session you are working in. Experiments, integration tests, destructive scripts — all of them should be isolated this way.

But HERDR_CONFIG_PATH is not an isolation mechanism#

This was the most surprising measurement in the article. I wanted to move the entire Herdr state to /tmp, so I set HERDR_CONFIG_PATH=/tmp/labcfg/config.toml and started a labcfg session. Result:

ItemActual locationMoved?
config.toml/tmp/labcfg/config.toml✅ moved
release-notes.json/tmp/labcfg/release-notes.json✅ moved
Session directory and socket~/.config/herdr/sessions/labcfg/❌ still global
Plugin registry~/.config/herdr/plugins.json❌ still global
Plugin config directory~/.config/herdr/plugins/config/<id>❌ still global

The last row is not a paper deduction — I linked a probe plugin inside the labcfg session, and herdr plugin list in the default session showed it too. For that reason I immediately ran plugin unlink and returned the registry to [].

The conclusion must be stated plainly: HERDR_CONFIG_PATH relocates the configuration file, not runtime state. The unit of isolation is the named session, while the plugin registry is shared globally — there is no such thing as a plugin that is enabled for one session only.

There is also a symlink worth knowing about in a named session directory#

Measured contents of ~/.config/herdr/sessions/batch8-lab/:

herdr.sock            ← this session's own API socket
herdr-client.sock
herdr-server.log
herdr-client.log
session.json
session-snapshots/
herdr.sock.agent -> /Users/rex/.config/herdr/herdr.sock.agent   ← points back at the default session!

The last line is a symlink to the default session’s agent socket. In other words, the agent reporting channel is not one per named session. Anyone writing a multi-session agent integration needs to know this, or they will believe they have started a per-session agent reporting endpoint.

4. You are inside Herdr: two gates and one way through#

This is the most realistic problem in agent automation: the agent runs in a Herdr pane and wants to open an isolated session to experiment.

Gate one: the nested-launch guard#

Measured, running herdr --session batch8-lab inside a Herdr pane:

error: nested herdr is disabled by default.
see configuration if you want to enable it.

"you were so preoccupied with whether you could, you didn't stop to think if you should." — dr. malcolm

The reason is straightforward: Herdr injects HERDR_ENV=1 into every pane, and the client refuses to nest when it sees that variable. It is a default guard against “agent opens sessions until it eats the machine”.

Gate two: a non-interactive environment has no terminal size#

Clear the variables and try again (env -u HERDR_ENV -u HERDR_PANE_ID), and the error changes:

herdr: cannot attach without a usable terminal: terminal reported a zero-sized grid; run inside a terminal

The two gates are different in nature: the first is policy (configurable), the second is a physical condition (the client needs a terminal that can report a row and column count in order to render). In CI, in scripts, and under the script command, ioctl reports a size of 0×0 and the client gives up — it refuses to draw on a screen that does not exist.

Incidentally, macOS script -q /dev/null cmd does not give a real size either, so do not expect script to paper over it.

A way through that works: a pty with a size#

Measured as effective: use Python’s pty.fork() to spawn the child, then set the window size explicitly before exec:

import os, pty, fcntl, termios, struct, select, time, signal

env = dict(os.environ)
for k in ("HERDR_ENV", "HERDR_PANE_ID", "HERDR_SOCKET_PATH", "HERDR_BIN_PATH"):
    env.pop(k, None)                      # gate one

pid, fd = pty.fork()
if pid == 0:
    os.execvpe("herdr", ["herdr", "--session", "batch8-lab"], env)

# gate two: give this pty a real row and column count
fcntl.ioctl(fd, termios.TIOCSWINSZ, struct.pack("HHHH", 40, 140, 0, 0))

# Let the client run long enough to bring the server up, while we only read output
deadline = time.time() + 10
while time.time() < deadline:
    r, _, _ = select.select([fd], [], [], 0.3)
    if r:
        try:
            if not os.read(fd, 65536):
                break
        except OSError:
            break

os.kill(pid, signal.SIGTERM)              # the client dies, the server stays

After running it, herdr session list shows batch8-lab as running while the client in that pty has already been killed. The server outlives the client — and the negotiated capabilities state this explicitly (measured):

{"id":"r1","result":{"type":"pong","version":"0.9.2","protocol":22,
  "capabilities":{"live_handoff":true,"detached_server_daemon":true,
    "endpoint_protocol_generation":1,"surface_interest":true,
    "health_check":true,"ssh_agent_registration":true}}}

detached_server_daemon: true is the promise that “the client is not a parent-process dependency of the server”. So the right mental model for starting an isolated session is: the client is temporary scaffolding whose only job is to bring the server up; once it is up you work entirely through the CLI and socket, with no TUI needed.

Clean up with session stop, never server stop#

After testing:

herdr session stop batch8-lab     # stops only this named session

herdr server stop stops whichever server your command routed to — if your --session is wrong or missing, that is the session you are using. Never use server stop in a script; to stop a test session use session stop <name>. That rule is the first item in the trap list below.

5. Target addressing: three kinds of id, two of which work#

Herdr has several id shapes that all look similar — w1:p1 / term_65ca0990363e22 / lab-bot — but only two can be targets.

The documented rule: an agent target is either a unique live agent name or the pane id that currently hosts the agent. Terminal ids and bare agent-kind labels are not targets.

I only really understood this rule after one failing measurement.

Measured: a display name is not a live name#

I self-reported an agent for a pane:

herdr --session batch8-lab pane report-agent w1:p1 \
  --source labtest --agent lab-bot --state working --seq <ms>

And agent list did show it:

{"agents":[{"agent":"lab-bot","agent_status":"working","pane_id":"w1:p1","state_change_seq":5,...}],"type":"agent_list"}

But immediately afterwards:

herdr --session batch8-lab agent get lab-bot
# {"error":{"code":"agent_not_found","message":"agent target lab-bot not found"},"id":"cli:agent:get"}   rc=1

herdr --session batch8-lab agent get w1:p1
# {"error":{"code":"agent_not_found","message":"agent target w1:p1 not found"},"id":"cli:agent:get"}

The self-reported agent looked completely unaddressable. But that was my own test sequencing: I ran agent get several seconds later, by which time the state had already been cleared (article 3 covers that 0.4-second window). Re-measuring, querying immediately after the report:

+0.01s  agent get lab-bot               rc=1  agent_not_found
+0.01s  agent wait w1:p1 --until working rc=0  ✅ success, the agent field is lab-bot
+0.02s  agent explain w1:p1             rc=1  agent_explain_unavailable
                                                  "does not have a detected agent label"

Three commands, three semantics, separated in a single run:

CommandTarget formResultWhy
agent waitpane id✅ rc=0Addresses through the pane, so it hits self-reported state
agent getself-reported name❌ agent_not_foundA display label is not a live agent name
agent explainpane id❌ agent_explain_unavailableexplain only reports detection, and self-reporting is not detection

So the correct addressing rule is: automation scripts should always target by pane id. Names are for people; the pane id is the stable address. Only agents started with agent start have an addressable name (the docs say agents started through agent start require a name, while manually launched agents remain unnamed and use their pane ID).

Why the distinction matters#

Because “name” has three different sources in Herdr and only one of them is addressable:

  1. The <name> in agent start <name> --kind ... — addressable, constrained to [a-z][a-z0-9_-]{0,31}, unique among live agents
  2. The <label> in pane report-agent --agent <label> — a display label that appears in agent list and the sidebar, but is not a target
  3. Kind labels recognised by the detection manifests (claude, pi, codex…) — used internally by Herdr; agent explain --agent LABEL accepts one, but that is a parameter for explaining an offline fixture, not a target

The interaction between sources 2 and 3 hides an even deeper trap (a self-reported label has to be a kind Herdr knows in order to be retained), which is the subject of article 3.

6. Six parameter traps, all measured#

① pane run does not consume --#

herdr --session batch8-lab pane run w1:p1 -- echo hello-from-herdr-cli
# what actually runs in the pane: -- echo hello-from-herdr-cli
# zsh: command not found: --

pane run <PANE_ID> <COMMAND>... takes a variadic positional COMMAND, so -- is sent through as the first argument. The correct form is:

herdr --session batch8-lab pane run w1:p1 echo hello-from-herdr-cli
# reading it back 2 seconds later with pane read:
# rex@… /tmp % echo hello-from-herdr-cli
# hello-from-herdr-cli

By contrast, pane report-agent’s -- RESUME_COMMAND... does need the -- (the docs state the separator explicitly). Two conventions coexist in the same binary, and the test is whether <COMMAND>... in the help is preceded by a --.

② --match / --regex on pane wait-output form a required exclusive group#

The Usage line reads [--match <TEXT>|--regex <PATTERN>] — a clap required group. Omitting both is a usage error (rc=2). Supplying both is an exclusivity error.

Measured, a wait-and-match loop:

( sleep 2; herdr --session batch8-lab pane run w1:p1 echo MARKER_7788 ) &
herdr --session batch8-lab pane wait-output w1:p1 --match MARKER_7788 --timeout 8000

{"id":"cli:pane:wait-output","result":{"matched_line":"rex@… /tmp % echo MARKER_7788","pane_id":"w1:p1","read":{"source":"recent_unwrapped","text":"…\nMARKER_7788\n…","truncated":false},"type":"output_matched"}}

Note that the return also carries the whole snapshot in the read field, so you do not need to read again after matching. And matched_line matched the command line itself (echo MARKER_7788), not the output line — because the echo is on screen too. That is a real trap: if you are waiting for a command’s output, choose a marker string that does not appear in the command line.

③ pane read has four sources, wait-output has three#

pane read       --source  visible | recent | recent-unwrapped | detection
pane wait-output --source  visible | recent | recent-unwrapped

detection exists only on read — it gives the bottom-buffer view the detector saw, which is how you reproduce “why was the state judged wrong”. To reproduce the input of agent explain from the CLI, use it.

--format has text and ansi (read supports it, wait-output does not, but it does have --strip-ansi).

④ The parameter of api schema is --output, not --out#

herdr api schema --out /tmp/s.json
# usage: herdr api schema [--json | --output PATH]

And --json and --output are mutually exclusive (the usage line reads [--json | --output PATH]). The default output is a human-readable summary:

Herdr API schema
protocol: 22
schema_version: 1
schemas: error_response, event, request, subscription_event, success_response

For machine-readable output use --json redirected to a file (272578 bytes measured).

⑤ The plugin id of plugin action invoke is an option, not a positional argument#

herdr plugin action invoke rex.hello-lab hello
# unknown option: hello      ← the second positional argument failed to parse as an option

The correct form (the help states invoke [OPTIONS] <ACTION_ID>, and the plugin is --plugin <ID>):

herdr plugin action invoke hello --plugin rex.hello-lab

⑥ plugin config-dir requires a plugin id#

herdr plugin config-dir
# usage: herdr plugin config-dir <plugin_id>

7. Trap list#

  1. server stop stops whichever server you routed to. Forgetting --session means it stops the session you are using. In scripts, stop a test session only with herdr session stop <name>.
  2. Do not use HERDR_CONFIG_PATH as isolation. Measured: it relocates only config.toml and release-notes.json, while sessions/ and plugins.json stay global. The unit of isolation is the named session; the plugin registry is global and has no per-session scope.
  3. Error JSON goes to stderr, not stdout. herdr xxx | jq hands jq an empty input on failure, so you read “it failed” as “no data”. Redirect stderr separately to catch errors.
  4. Success may produce zero output. pane report-agent and pane run print nothing on success. Judge success by exit code, not by “is there output”.
  5. Do not retry exit code 2 (your command line is wrong); 1 is the one that needs judgement (target lost / timeout). Collapsing both into a single if ! cmd makes you retry a syntax error thirty times.
  6. A self-reported --agent name is not a target. Automation should always use pane ids. agent get <self-reported-name> returns agent_not_found, and that is not a bug.
  7. agent explain always fails for a self-reported agent (agent_explain_unavailable). explain explains detection, not reporting.
  8. Do not add -- to pane run, and do add it for the resume command of pane report-agent. Two conventions coexist.
  9. wait-output’s --match can match the echoed command line rather than the command output. Pick a marker that does not appear in the command string.
  10. pane.renamed is not an event name. The pane-side name is pane.updated (this is more damaging inside a socket subscription, see article 2: the entire subscription fails atomically).
  11. The Usage section of --help is not a command inventory. plugin, terminal, and status are absent from it. Do not infer the feature surface from it — use the 102 methods of herdr api schema.
  12. The nested-launch guard is default behaviour, not a broken environment. Starting Herdr inside Herdr requires both clearing HERDR_ENV/HERDR_PANE_ID and supplying a pty with a real size; doing only one just changes which error you get.

9. Quick reference: the commands I would actually use#

A minimal subset you will really reach for, rather than all 102 methods:

# Environment and compatibility (check this before anything else)
herdr status                         # client / server / update
herdr session list                   # which sessions exist, and where their sockets are

# Read-only reconnaissance
herdr api snapshot                   # everything: workspaces, tabs, panes, layouts
herdr pane list --workspace w1       # the panes of one workspace
herdr pane current                   # which pane I am in (most common inside an agent)
herdr pane read w1:p1 --source recent --lines 40

# Writes (first confirm --session points at an isolated session)
herdr --session lab pane run w1:p1 npm test
herdr --session lab pane wait-output w1:p1 --regex 'exit code [0-9]+' --timeout 60000
herdr --session lab agent wait w1:p1 --until idle --timeout 300000

# Diagnostics
herdr config check                   # validate config.toml and print diagnostics
herdr agent explain w1:p1 --json     # why the state was judged that way (detected agents only)

api snapshot is the most underrated entry here: one call returns version, protocol, every workspaces / tabs / panes / layouts, and the three focused_*_id fields. Take one snapshot before writing automation and write the ids down — far faster than guessing ids and collecting pane_not_found.

Frequently Asked Questions

How many Herdr CLI commands are there?

Two layers. The human- and script-facing layer has 18 top-level verbs: agent, api, channel, completion, config, integration, machine, notification, pane, plugin, server, session, tab, terminal, update, worktree, and workspace, plus the utility verbs status and completion. The pane family is the largest with 25 subcommands; agent and plugin have 11 each; machine has 8. The real interface layer is the socket API: herdr api schema --json emits 102 methods across 19 families, of which pane accounts for 35. The CLI is a thin wrapper over that API and covers less of it.

How do I tell why a Herdr command failed?

Look at the exit code — there are exactly three. 0 is success. 1 is a runtime error, and the error JSON goes to stderr while stdout stays empty, for example agent_not_found when you query a target that does not exist. 2 is a usage error: a wrong option name or a subcommand that does not exist, so herdr pane list --bogus answers unknown option: --bogus and herdr doctor answers unknown command: doctor. Handling 1 and 2 differently matters: 2 means you wrote the command wrong and retrying is pointless, 1 means the environment or the target is at fault.

Why is starting a new Herdr session from inside Herdr refused?

Because of the nested-launch guard. Herdr injects HERDR_ENV=1 into every pane, and the client refuses to nest when it sees that variable, reporting nested herdr is disabled by default. That is an intentional default rather than a bug, since otherwise an agent could multiply sessions indefinitely. Clearing HERDR_ENV and HERDR_PANE_ID for the child gets you past it, but you then hit a second gate: a non-interactive environment has no usable terminal size, and the client reports terminal reported a zero-sized grid. Actually starting an isolated session requires giving it a pty with a real window size.

How do I keep a command from touching the session I am working in?

Use --session <name>, which sits first in the four-level routing precedence. A named session has its own socket at ~/.config/herdr/sessions/<name>/herdr.sock, so the command physically cannot reach your default session. Note that HERDR_CONFIG_PATH is not an isolation mechanism: measured on this machine it relocates config.toml and release-notes.json but the sessions directory stays anchored under ~/.config/herdr/sessions/ and the plugin registry plugins.json stays in its global location.

Why does herdr pane run fail when I add a -- separator?

Because pane run does not consume --. Measured: herdr pane run w1:p1 -- echo hi sends a literal -- echo hi to the pane's shell, and zsh answers command not found: --. Write it as herdr pane run w1:p1 echo hello instead, with the command and its arguments following the pane id. The trap exists because many CLIs use -- to separate options from positional arguments, but here COMMAND is a variadic positional argument and needs no separator.

What can an agent command actually target?

Two things: a unique live agent name, or the pane id that currently hosts the agent. Terminal ids and bare agent-kind labels are not targets. The easiest trap is a self-reported name: if you report with herdr pane report-agent --agent my-bot, my-bot is a display label rather than a live agent name, so herdr agent get my-bot answers agent_not_found. Only agents started with agent start have an addressable name; manually launched agents stay anonymous and are addressed by pane id.
