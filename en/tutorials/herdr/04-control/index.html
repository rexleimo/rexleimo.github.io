Module 4: Programmable Control

Modules 0–3 covered how a person works in Herdr. This module covers the other half: how code treats Herdr as an interface.

This is where Herdr separates itself from tmux and zellij. It is not “it happens to have a CLI” — the whole UI sits on top of a socket API, the CLI is a thin wrapper over it, and plugins are the frozen form of it. Your only decision is which layer to enter from.

All four articles were measured in isolated named sessions, including the complete lifecycle of a real probe plugin.

Baseline: herdr 0.9.2 stable · macOS · docs pinned to v0.9.2 Measured scale: 18 top-level CLI verbs, 102 socket methods, 27 subscribable events, 22 agent detection manifests, 14 injected plugin environment variables

Prerequisites

  • Module 0 done, and herdr status shows a running server
  • Comfortable reading JSON and writing a little shell or Python (articles 2 and 3 send socket frames)
  • Article 3 assumes you have read Agent states first: the state semantics are the premise of any orchestration
  • Article 4 assumes you can write TOML and have a runnable script on hand

Learning goals

After this module you can answer:

  • How do the 18 CLI verbs and the 102 socket methods relate, and which capabilities only the socket has
  • Why herdr xxx | jq will lie to you on failure, and what to do differently for exit codes 1 and 2
  • The precedence of --session, HERDR_SOCKET_PATH, and HERDR_SESSION, and why HERDR_CONFIG_PATH is not an isolation mechanism
  • Starting a second Herdr from inside a Herdr pane is refused twice — why, and how to get around it
  • What an agent target can actually be (a measured four-row matrix), and why agent get claude fails
  • Why “I just reported working” does not mean “it is working now”
  • Why you cannot reuse a socket connection for a second request, and why subscriptions can
  • Why events.subscribe and events.wait use two different event-naming schemes, and how many event types the latter actually supports
  • Your plugin linked successfully but its event hook never fires — what is the most likely cause
  • Why a plugin’s config directory and state directory are not under the same tree

One-sentence conclusion

Herdr’s control surface is an NDJSON socket API; the CLI is a wrapper over it and a plugin is its frozen form. All three layers share one control surface, but only the socket layer is the complete interface. And the engineering meaning common to all three is: accepted is not applied — rc=0 does not mean the state was kept, a successful link does not mean the manifest is clean, and a sent subscription does not mean it took effect. Read it back at every step.

A note on method

Every conclusion in this module came from isolated sessions, and the method is itself worth recording:

  1. Start a named session under a pty with a real window size (article 1 has runnable code)
  2. Every write operation carries --session <name>, so it physically reaches a different socket
  3. Clean up with herdr session stop <name>, never server stop
  4. Experiments touching the global registry (plugins) unlink immediately and verify plugins.json is back to []

Article 3 additionally records a measurement I got wrong and then overturned — that part is not decoration, it is the most practically useful content in the module.
