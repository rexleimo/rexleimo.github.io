Herdr's Five Session-State Paths: detach, Snapshot Restore, History Replay, Agent-Native resume, and live handoff

'After I close the window / drop SSH / upgrade Herdr / reboot the machine, is my agent still there?' has five different answers. This article takes each Herdr state path apart: live persistence (processes keep running after detach), snapshot restore (layout returns but processes do not, including session-backups recovery copies and the 48 session-snapshots layout copies), pane screen history replay (an experimental feature, off by default), native agent session restore (on by default, with the minimum integration version and resume command for all 18 agents), and live handoff (experimental, opt-in); plus a priority and enablement recommendation for the four paths.

September 29, 2026 · 14 min · 2963 words · Mengshou Programming -  |  中文

Verified version: herdr 0.9.2 (stable channel) · tested on this machine: macOS / Apple silicon · 2026-09-29

The thing people fear most with long-running agents is: it’s gone. In Herdr, “gone” is actually five completely different situations with completely different remedies. The cost of confusing them: you think it is still running when you stopped it two hours ago, or you think everything is lost when one command would have restored the conversation.

Conclusion first:

Separate four independent questions instead of asking the compound question “is it still there”: ①are the processes alive ②did the layout come back ③did the screen content come back ④did the agent rejoin its conversation. After detach all four are “yes”; after a server restart only ② is yes, and ③④ each need their own switch; live handoff aims for “as many of the four as possible”, but it is experimental and opt-in.

The official matrix (reproduced verbatim — this is the most important table in the article):

SituationProcesses still runningLayout backRecent screen backAgent conversation rejoined
reattach after detach✅ yes✅ yes✅ yes, from the live terminal✅ yes, because the process never stopped
server restart❌ no✅ yes⚠️ only with pane screen history enabled⚠️ only with native agent session restore
upgrade without --handoff⚠️ compatible servers keep running; servers needing a restart may need stop/restart✅ yes after a restart⚠️ only with pane screen history enabled⚠️ only with native agent session restore
upgrade with --handoff🔶 best effort (supported running servers)✅ yes✅ yes, from the live terminal if the handoff succeeded✅ yes, the process stayed up if the handoff succeeded

That dashed line above is an explicit official rule: when native agent session restore applies to a pane, Herdr restores the agent session instead of replaying saved screen history for that pane. The two do not stack.

Path 1 · Live persistence: detach (the strongest one)#

ctrl + b q      # detach; the pane and the agent keep running
herdr           # reattach later

The official words: This is the strongest persistence path because the original processes never stop. — this is the strongest persistence path, because the original processes never stop.

The server holds the panes in the background. Detach only removes the client. Therefore:

  • shells, agents, dev servers, tests, any command process are all still running
  • what you see on reattach is a live terminal, not a snapshot
  • and the agent’s conversation is of course intact, because it was never interrupted

Closing the terminal window outright is equivalent to detach.

To really stop:

herdr server stop

This is the biggest newcomer misconception, also stressed in the mouse workflow article : closing a window ≠ stopping.

Path 2 · Snapshot restore: the layout returns, the processes do not#

When the server stopped and came back, the original pane processes no longer exist. Herdr restores the saved shape of the session:

workspaces, tabs, panes, cwd, layout, focus

Explicitly not preserved: running shells, servers, tests, any process. Panes that do not qualify for a stronger recovery path come back as a new shell in the saved directory.

A considerate failure behaviour#

If the saved directory is unavailable, or the shell cannot start:

the pane stays in the layout carrying an error, rather than vanishing or being moved to your home directory. Its saved directory and agent session reference remain intact.

Fix the directory or shell config and restart the server to retry, or close the pane explicitly to remove it. (Contrast tmux: no directory, no window. Herdr chose to keep the evidence.)

How cwd is determined#

At save time, where the operating system exposes the shell’s directory, Herdr prefers the live shell’s directory; after the shell exits, the last confirmed directory is kept. On other platforms it falls back to the directory reported by the shell.

That distinction matters in the “close the window right after cd” scenario — the first is kernel-level truth, the second depends on shell integration.

What if session.json is broken#

If session.json cannot be read, fails to parse, or needs a newer version of Herdr:

  1. Herdr records why the load failed
  2. it saves the original bytes into session-backups/ next to session.json, before saving or clearing the replacement session
  3. the recovery path is recorded in the log field persist.backup
  4. a file missing at startup is checked once more before the first save or clear

The rule details:

  • the three most recent recovery copies are kept; older ones are pruned only after a new copy has been written safely
  • if writing the recovery copy fails, autosave and shutdown leave the original file untouched, log the failure, and retry on the next save request
  • recovery copies are never auto-restored. To restore: stop the affected server → copy the recovery file over its session.json → start again
  • recovery copies do not contain pane screen history
  • these “load-failure recovery copies” and the normal snapshot history are two different systems

Path 2.5 · Shutdown protection and 48 layout snapshots#

systemd-logind shutdown delay (Linux only)#

On Linux with systemd-logind, Herdr listens for the host’s shutdown warning and requests a short delay to save and stop — which happens before logind proceeds with the shutdown.

Limits (all stated in the docs): the delay length is set by the operating system, Herdr will not block shutdown indefinitely; without logind there is no such protection; and it does not cover forced shutdown, power loss, or processes killed before the warning arrives.

session-snapshots/: up to 48 layout snapshots#

Available on every platform, next to session.json. Rules:

  • the first saved layout is copied immediately
  • later saves or clears may append a snapshot of the last saved layout, at most once every 15 minutes
  • unchanged snapshots are not duplicated
  • the interval survives server restarts — so “a burst of panes exiting or restarting” cannot rotate every old layout away
  • ⚠️ your most recent changes may not be in a recovery snapshot

Normal pane closures still update session.json. There is no recovery prompt, and no automatic restore of an old snapshot.

The four manual layout-restore steps (official flow)#

# 1. find the affected session directory
herdr session list --json

# 2. stop that server (server stop for the default session, session stop <name> for a named one)
herdr server stop
# or: herdr session stop work

# 3. back up the current session.json, then copy your chosen file from session-snapshots/ over it
#    (the file's modification time tells you when the snapshot was taken)

# 4. start the session again
herdr

What a snapshot has and has not:

hashas not
layout (workspace/tab/pane/focus)running processes
agent session referencespane screen history

The docs add a security note: treat these as private session data. Also, snapshot write failures are logged but do not block the main session save.

Path 3 · Pane screen history replay: getting screen content back#

After a full server restart, this recovers recent terminal content without restoring the old processes.

Off by default, and the reason is stated plainly:

because pane output can contain secrets, tokens, prompts and command output.

Enable it:

[experimental]
pane_history = true

Once on, history lives in session-history.json next to session.json. The official requirement: treat Herdr’s config/session directories like your terminal history (that is: do not casually sync or commit them).

Two hard limits:

  1. replay only happens when the layout matches the saved one exactly. History from a different layout is ignored — including after a manual snapshot restore
  2. older history files without a layout validation field are also ignored; newly saved history can replay on the next restart

So this path is narrower than it sounds: it rescues “the server died unexpectedly but the layout never changed”.

Path 4 · Native agent session restore: letting the agent rejoin its conversation (on by default)#

Some agents can restore their own conversation session. Using session references reported by the official integrations, Herdr can restart supported agent panes after a Herdr server restart.

On by default. To turn it off:

[session]
resume_agents_on_restore = false

Trigger conditions: the pane reported a native session reference through a current official Herdr integration, or the agent in the pane reported its own resume command (the latter is covered in module 3’s adding Herdr support to your own agent ).

Timing detail (easy to miss):

after a client attaches and supplies terminal size and theme context, Herdr restores eligible agent panes across workspaces and tabs; each pane does not have to be focused.

In other words: the restore happens the moment you attach, and it happens in bulk.

Check the integration versions on your machine:

herdr integration status                       # lists all 18 paths and their installed state
herdr integration install <agent>              # reinstall an outdated integration

Measured on this machine (none installed):

herdr integration status   # → 18 lines of "not installed"

Note the causal chain here: no integration → no session reference reported → after a server restart the agent cannot rejoin its conversation and can only come back as a new shell. An integration is not just a status badge; it is the precondition for native restore.

Fallback rule: unsupported, missing, invalid, duplicate, or expired session references all restore as a plain shell in the saved directory — no crash, no guessing.

Path 5 · Live handoff: keeping processes alive while replacing the server#

The first four paths are “the processes are gone, how do we rebuild state”. Handoff is the reverse:

it tries to keep the current processes alive rather than rebuilding state after the old server stops.

Its use is flows that must replace a running Herdr server: upgrades and remote attaches. It asks the old server to transfer its live panes to the new one.

Experimental, opt-in:

herdr update --handoff
herdr --remote workbox --handoff

What it preserves and what it does not#

✅ preserved (durable, server-owned session state)❌ not preserved (transient coordination across the replacement boundary)
the pane’s PTY and processesin-flight CLI or API requests
agent identity and durable metadatawaits
plugin / session state the replacement server needssubscription streams
client sockets
inter-pane messages

The official advice: clients should reconnect and retry those.

The 64-pane limit and batching#

An updated Unix server can transfer more than 64 panes in one handoff by batching the transfer. But there is a precondition: the sending server must already contain this support — an older running server is still bound by its own 64-pane limit on the first upgrade. That limit may require one ordinary server restart (which ends the pane processes). Batching does not change the upgrade’s installation order and does not remove the other handoff compatibility requirements.

When you do not actually need handoff#

These two official lines remove a lot of anxiety:

  • herdr update (without handoff) installs the new client and lets endpoint-generation-1 servers keep running
  • herdr --remote workbox (without handoff) also lets a compatible remote server keep running even when the versions differ

There is exactly one case where a stop is required: the one-time upgrade from a pre-generation-1 server. Use --handoff when you specifically want to replace a supported running server without losing its pane processes.

One more hard limit:

herdr update --handoff only applies to installations managed by Herdr’s own updater. Homebrew, mise and Nix installs are updated through their package manager, so herdr update is disabled in those environments and cannot perform a live handoff.

Named sessions: the unit of state isolation#

For mutually independent Herdr servers, use named sessions:

herdr session list
herdr session attach work
herdr session attach side-project
herdr session stop work
herdr session delete side-project

A named session has its own panes, tabs, workspaces, socket and runtime state, but still shares the one global config file.

Two traps:

  1. when deleting, the name must match herdr session list exactly, including case. On a case-insensitive filesystem, herdr session delete foo refuses to delete a session named Foo
  2. in scripts always add --json: herdr session list --json, herdr session stop work --json, herdr session delete side-project --json

Named sessions work remotely too: herdr --remote workbox --session agents.

Which switches should I turn on? A decision table#

Your situationRecommendation
local only, occasionally closes windowsconfigure nothing. detach is already the strongest path
the machine reboots / the server gets stoppedmake sure your agents have an official integration at a new enough version (path 4 is on by default, but no integration means no references)
agent output contains sensitive materialdo not enable pane_history (it is off by default, and that is the correct default)
you often need pre-restart output and it contains nothing sensitiveenable [experimental] pane_history = true and protect the config/session directories like terminal history
you upgrade Herdr often and have long tasks runninguse herdr update --handoff (precondition: script install; package-manager installs cannot)
more than 64 panesdo one ordinary upgrade first so the sending server gains batching support, then rely on handoff beyond 64
you want to avoid state problems entirelyone named session per project, to bound the blast radius

Traps to avoid#

  1. herdr server stop is the irreversible one. It ends every pane process. Think before reflex.
  2. Layout snapshots are never auto-restored and there is no prompt. You must walk the four steps manually. So when you notice a wrong layout, stop operating and check modification times in session-snapshots/ first.
  3. When session.json fails to parse, the original bytes go to session-backups/ — but nothing is auto-restored. Look for the persist.backup field in the logs to get the path.
  4. Pane screen history replays only on an exact layout match. You restored a snapshot manually → the layout changed → history is ignored. These two recovery mechanisms are mutually exclusive; do not hope to stack them.
  5. native restore takes priority over history replay, and applies once per pane. The same pane will not both rejoin a conversation and replay its screen.
  6. No official integration = no session reference = no conversation after a restart. herdr integration status is a command worth checking periodically.
  7. An integration that is too old also fails to restore. Compare against the table above and reinstall with herdr integration install <agent>.
  8. Package-manager installs cannot use herdr update --handoff. Homebrew / mise / Nix go through their package manager, where herdr update is disabled.
  9. handoff interrupts in-flight requests and subscription streams. If your automation is parked on herdr pane wait or a streaming subscription, reconnect and retry after the handoff.
  10. Linux shutdown protection does not cover power loss or forced shutdown. Do not treat it as a UPS.
  11. session.json and session-history.json are private data. Do not commit them to git, do not sync them to a random cloud drive.

Frequently Asked Questions

Do processes survive detach?

Yes. This is the strongest persistence path: ctrl+b q disconnects the client while the Herdr server keeps holding the panes, shells, agents, servers, tests and command processes. Running herdr later reattaches to the same session, because the original processes never stopped. Only herdr server stop actually stops them.

What comes back after a server restart?

Only the layout snapshot: workspaces, tabs, panes, cwd, layout and focus. The original processes are gone, and any pane that does not qualify for a stronger recovery path comes back as a new shell in its saved directory. To recover screen content you need experimental.pane_history; to have an agent rejoin its conversation you need native agent session restore (on by default).

Is agent-native conversation restore on by default?

Yes. It uses session references reported by the official integrations to restart supported agent panes after a Herdr server restart. To turn it off set session.resume_agents_on_restore = false. Check installed integration versions with herdr integration status, and reinstall outdated ones with herdr integration install <agent>.

Why is pane history replay off by default?

Because pane output can contain secrets, tokens, prompts and command output. You enable it with experimental.pane_history = true, and history is stored in session-history.json next to session.json. The official requirement is to treat Herdr's config/session directories like your terminal history.

Can I recover an accidentally deleted layout?

Yes, from the layout snapshots in session-snapshots/ (up to 48 copies, on every platform; the first is saved immediately, later ones at most every 15 minutes, and the interval survives server restarts). Four steps: find the directory with herdr session list --json, stop that server, back up the current session.json and copy your chosen snapshot over it, then start again. Snapshots contain layout and agent session references only, not running processes or screen history.

What is live handoff and should I enable it?

It is an experimental feature for flows that must replace a running server, such as upgrades and remote attaches: the old server transfers its live panes to the new one, preserving pane processes. It is opt-in via herdr update --handoff or herdr --remote workbox --handoff. It preserves PTYs, processes, agent identity and durable metadata, but not transient coordination across the replacement boundary (in-flight requests, waits, subscription streams, client sockets and inter-pane messages may break).
