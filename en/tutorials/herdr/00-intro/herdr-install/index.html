Installing and Verifying Herdr: Three Platforms, Five Channels, and How to Prove It Worked

Install herdr 0.9.2 on macOS / Linux / Windows: the real commands for all five channels (installer script, Homebrew, mise, Nix, manual download) and how each one upgrades; how to switch between the stable and preview channels and why an old Windows preview install cannot switch back; how to read every field of herdr status; and exactly what appears under ~/.local/bin, ~/.config/herdr and ~/.local/state/herdr once it is installed. Includes a failure triage table.

September 29, 2026 · 12 min · 2440 words · Mengshou Programming -  |  中文

Verified version: herdr 0.9.2 (stable channel, released 2026-09-29) · tested on this machine: macOS / Apple silicon · 2026-09-29

This article does one thing: install Herdr correctly, and give you a way to prove to yourself that you did.

Conclusion first, because it decides every upgrade you will ever do:

There are five install channels, but only “official installer script” can be upgraded with herdr update. Anything installed via Homebrew / mise / Nix must go through its own package manager; mixing them produces the mismatch where the client is new and the server is old. Decide how you intend to upgrade before you pick a channel.

2. macOS / Linux: the official installer script#

curl -fsSL https://herdr.dev/install.sh | sh
herdr

The installer downloads the release binary for your platform and puts it on PATH. A fresh direct install defaults to the stable channel.

Where it landed on this machine:

$ which herdr
/Users/rex/.local/bin/herdr

$ ls -la ~/.local/bin/herdr
-rwxr-xr-x  1 rex  staff  22194464 Sep 29 22:56 /Users/rex/.local/bin/herdr

A single ~22 MB static binary with no extra runtime dependency (it is written in Rust, see the previous article ).

3. Windows: two installs, the second one exists for corporate environments#

The standard PowerShell install:

powershell -ExecutionPolicy Bypass -c "irm https://herdr.dev/install.ps1 | iex"

If endpoint security (EDR) blocks this “fileless” command — extremely common on company machines — fall back to cmd.exe, which writes a file first:

curl.exe -fsSLo install.cmd https://herdr.dev/install.cmd && install.cmd && del install.cmd

Two more Windows details that trip people up, both from the official install docs:

  1. PATH points at a version-numbered directory for the current release, and the installer also maintains current and a stable bin compatibility alias, so upgrading never has to overwrite a running herdr.exe (Windows does not allow overwriting a running executable; this design routes around that).
  2. Do not cherry-pick from the ZIP. herdr-windows-x86_64.zip contains herdr.exe plus its app-local ConPTY runtime; the whole directory must stay together. Copying only herdr.exe will not run.

Also: an old preview install on Windows stays on preview until you explicitly switch back with herdr channel set stable.

4. The three package-manager routes#

Homebrew#

brew install herdr

mise#

mise use -g herdr

Trap: if mise says herdr not found in mise tool registry, your mise predates Herdr entering the registry. Upgrade mise and retry; if you really do not want to, the official stopgap is:

mise use -g github:herdrdev/herdr

Nix (builds from source)#

nix run     github:herdrdev/herdr/v0.x.y
nix build   github:herdrdev/herdr/v0.x.y
nix profile install github:herdrdev/herdr/v0.x.y

Replace v0.x.y with the latest release tag. Omitting the tag tracks master; the official recommendation for normal installs is to use a release tag.

The flake also offers a development shell:

nix develop github:herdrdev/herdr

How you upgrade depends on how you installed:

nix profile list                      # find the Herdr entry
nix profile upgrade <index-or-name>     # profile install
nix flake update herdr                  # if it is an input in your own flake

5. Manual download#

Take the matching asset from GitHub Releases External link :

SystemAsset name
Linux x86_64herdr-linux-x86_64
Linux aarch64herdr-linux-aarch64
macOS Intelherdr-macos-x86_64
macOS Apple siliconherdr-macos-aarch64
Windows x86_64herdr-windows-x86_64.zip

On Linux / macOS you add the execute bit and put it on PATH yourself:

chmod +x herdr-linux-x86_64
mv herdr-linux-x86_64 ~/.local/bin/herdr

There is no native Windows ARM64 asset — it runs the x86_64 build under Windows emulation.

6. Verification: three steps, all green or it is not installed#

Step 1: version#

$ herdr --version
herdr 0.9.2

If your shell says herdr is not found, restart the terminal or check that the install directory is on PATH.

Step 2: it starts#

cd your-project-directory
herdr

Herdr automatically starts or attaches the local default background session and opens one workspace automatically when there is none. You do not have to manage the socket. The first run walks you through onboarding.

You can also look at half of it: herdr status server / herdr status client. Measured on this machine, herdr status server:

status: running

private_protocol_compatible: yes

Two self-check commands worth memorising#

$ herdr channel show
stable

$ herdr config check
config: ok

config check validates config.toml and prints diagnostics; run it after every config edit — far faster than starting the server to find out.

7. Upgrading: the real semantics of herdr update#

This section is where accidents happen, because it is not like a normal CLI upgrade where “installed means new”.

Default behaviour (following the wording of the official install docs):

  • the new binary is installed, but servers on endpoint-generation 1 and their pane processes keep running
  • you run herdr again and attach with the new client
  • pure client-side changes take effect immediately
  • new server-side actions stay unavailable until that server is updated and restarted — meanwhile the client shows a notice rather than disconnecting
  • servers older than endpoint generation 1 need one final stop

When an upgrade finishes, herdr update lists:

  1. servers still running the old version, with the command to restart each one
  2. your saved SSH machines — each runs its own Herdr, so you have to run herdr update on every one of them

The experimental live handoff#

herdr update --handoff

Performs an experimental live handoff for supported running sessions. When both the old and the new server support agent-status transfer, live handoff preserves agent state reported by hooks until the next report arrives. Known side effect: an agent handed over from the old server may briefly show as idle.

Note: live handoff does not apply to Homebrew / mise / Nix package-manager upgrades. For those installs the sequence is: upgrade with the package manager → run herdr again to attach with the new client → compatible old servers keep running → when you actually need the new version’s server-side changes, restart with herdr server stop or herdr session stop <name>.

8. Channels: stable or preview#

herdr channel set preview    # switch to preview (GitHub prereleases cut from master)
herdr channel set stable     # switch back to stable
herdr channel show           # show the current channel

For a direct install, switching channels immediately checks that channel and installs its latest binary. If that update fails, run herdr update again to retry from the configured channel.

The factual baseline (measured from GitHub Releases, 2026-09-29):

  • v0.9.2 was released 2026-09-29, v0.9.1 on 2026-09-16 — roughly one stable every two weeks
  • preview releases look like preview-2026-09-29-9dc3a1df2b56, dated and commit-stamped, almost one per day

My recommendation: stay on stable for daily use and production. The value of preview is “I want a specific fix before the next stable”; the price is what the docs call “can regress”. On Windows even more so — the official docs state plainly that stable is the recommended channel for normal Windows use.

One Windows corner case: if an old preview build refuses herdr channel set stable, run herdr update once while still on preview, then retry the channel switch.

9. What landed on disk (measured on this machine)#

This material is scattered across several doc pages; here it is in one place, which is very useful when troubleshooting:

~/.local/bin/herdr                     # the binary (22 MB)

~/.config/herdr/
├── config.toml                        # config; on this machine it is one line: onboarding = false
├── herdr.sock                         # main socket (server)
├── herdr-client.sock                  # client socket
├── herdr.sock.agent                   # symlink → the launchd SSH agent listener
├── session.json                       # persisted session state (version 3, workspaces=1 here)
├── session-snapshots/                 # recovery snapshots, timestamped filenames
├── herdr-server.log                   # server log (structured, with event/subsystem/outcome fields)
├── herdr-client.log                   # client log
└── .plugins.lock                      # plugin lock file

~/.local/state/herdr/
└── agent-detection/                   # runtime state for agent detection

Three points deserve their own paragraph:

  1. herdr.sock.agent is a symlink, on this machine to /var/run/com.apple.launchd.06viBMHaY4/Listeners — meaning Herdr wires the SSH agent socket into panes (inside a pane, SSH_AUTH_SOCK points at it). That explains why ssh from inside Herdr to a remote machine does not need to unlock your keys again. Logs for named sessions live under ~/.config/herdr/sessions/<name>/.
  2. session.json is human-readable JSON: the workspace / tab / pane tree with their cwd values. To know “what exactly did Herdr remember”, reading this file is the fastest way.
  3. The logs are structured, like this (verbatim server log from this machine, paths truncated):
INFO herdr::persist::writer: preserved session recovery copy event="persist.backup" subsystem="persist" outcome="ok" path=.../session.json
INFO herdr::logging: session saved event="persist.save" subsystem="persist" outcome="ok" path=.../session.json workspaces=1
INFO herdr::logging: tab focused event="tab.focus" subsystem="tab" outcome="ok" workspace_id="w3" tab_id="w3:t1"

Every line carries event / subsystem / outcome, so grep 'outcome="err"' finds every failure. To tune log verbosity: HERDR_LOG=herdr=debug.

Environment variables visible inside a pane (measured)#

Running env | grep -i herdr inside a Herdr pane:

HERDR_ENV=1
HERDR_PANE_ID=w3:p2
HERDR_TAB_ID=w3:t2
HERDR_WORKSPACE_ID=w3
HERDR_SOCKET_PATH=/Users/rex/.config/herdr/herdr.sock
HERDR_STARTUP_CWD=/Users/rex
HERDR_BIN_PATH=/Users/rex/.local/bin/herdr
TERM_PROGRAM=herdr
SSH_AUTH_SOCK=/Users/rex/.config/herdr/herdr.sock.agent

The variables the official docs list as settable (mostly for reading):

VariablePurpose
HERDR_CONFIG_PATHoverride the config file path
HERDR_SESSIONselect a named session for CLI commands
HERDR_SOCKET_PATHlow-level socket path override
HERDR_PROCESS_DETECTIONLinux process-detection strategy: native (default) or opt-in child-groups
HERDR_ENV1 inside processes managed by Herdr
HERDR_PANE_ID / HERDR_TAB_ID / HERDR_WORKSPACE_IDpublic id of the current pane process
HERDR_LOGlog filter, e.g. HERDR_LOG=herdr=debug
HERDR_DISABLE_SOUNDsuppress playback even when sound notifications are enabled

HERDR_STARTUP_CWD and HERDR_BIN_PATH also exist on this machine but are not in that official table — fine to use in scripts, but know they carry no documented promise today.

HERDR_ENV=1 is the most useful of them all: it is the test for “am I already inside Herdr”. The official agent guide explicitly asks AI assistants to check it first, because Herdr blocks nested startup by design — running herdr inside a pane will not give you a second layer.

Frequently Asked Questions

How do I install Herdr?

On macOS / Linux run curl -fsSL https://herdr.dev/install.sh | sh; on Windows run powershell -ExecutionPolicy Bypass -c "irm https://herdr.dev/install.ps1 | iex" in PowerShell. You can also use brew install herdr, mise use -g herdr, nix profile install github:herdrdev/herdr/<tag>, or download the binary manually from GitHub Releases.

How do I verify the install?

Three steps: herdr --version should print herdr 0.9.2; herdr should start or attach to the default session; and in herdr status, server.status should be running, client and server versions should match, and endpoint_compatible should be yes.

When does herdr update not work?

Only installs done with the official installer can use herdr update. Homebrew, mise and Nix installs must be upgraded through their own package manager, otherwise you end up with a new client and an old server.

What is the difference between stable and preview?

The direct install defaults to stable. Preview is a GitHub prerelease cut from master (almost one per day): fixes land faster, but the official docs say plainly that it can regress. Switch with herdr channel set preview / set stable, and switching immediately installs that channel's latest binary. Package-manager installs do not use the preview channel.

Where is the config file, and what if it is missing?

On Linux/macOS it is ~/.config/herdr/config.toml, on Windows %APPDATA%\herdr\config.toml. Herdr runs fine without one (measured on this machine: config.toml contains a single line, onboarding = false). Use herdr --default-config to see every default and herdr config check to validate.

What if enterprise security software blocks the install on Windows?

The official fileless PowerShell command (irm | iex) is commonly blocked by endpoint security. Use cmd.exe instead: curl.exe -fsSLo install.cmd https://herdr.dev/install.cmd && install.cmd && del install.cmd.
