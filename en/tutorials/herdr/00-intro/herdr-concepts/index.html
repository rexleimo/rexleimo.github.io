Herdr Core Concepts: session / workspace / tab / pane / agent / mode

The six-layer Herdr model in one pass: session is the background server's namespace, workspace is the project-level container, tab is a layout, pane is a real terminal, agent is the recognised process (five states and the per-client 'seen' semantics), mode decides where keystrokes go among terminal/prefix/navigate. Includes a real session.json and herdr agent list from this machine, plus a granularity decision table for when to open a new pane / tab / workspace / session.

September 29, 2026 · 14 min · 2900 words · Mengshou Programming -  |  中文

Verified version: herdr 0.9.2 (stable channel) · tested on this machine: macOS / Apple silicon · 2026-09-29

This article covers the six-layer model in one pass. It needs its own article because almost everyone arriving from tmux confuses the session and workspace layers — in tmux a session is both the isolation boundary and the project container, while Herdr splits those two jobs apart.

Conclusion first:

One repo (or one task, or one investigation) = one workspace. Most people only ever need the default session. A named session is a completely separate runtime namespace: what you get is an independent socket and independent persisted state, and what you pay is having to remember what lives in which session.

1. Session: the background server’s namespace#

A session is the persisted Herdr server namespace. Running plain herdr attaches the default session.

Named sessions are completely separate runtime namespaces:

herdr session list
herdr session attach work
herdr session attach side-project

The official selection criterion is explicit:

Use workspaces first. Use named sessions when you need completely separate panes, sockets, and persisted runtime state.

Use a workspace first. Only reach for a named session when you need completely independent panes, sockets and persisted runtime state.

Translated into real situations:

Your needWhat to use
three projects open at once, and you want to see at a glance in the sidebar which one is waitingthree workspaces (same default session)
work and personal projects fully isolated, not even sharing a sockettwo named sessions
one machine running non-interfering agent fleets for different teams/usersnamed sessions
you just want a clean environment for one long taskone workspace + one dedicated tab is usually enough

Log and state locations follow the session: the default session lives in ~/.config/herdr/, named sessions under ~/.config/herdr/sessions/<name>/ (per the official agent guide).

2. Workspace: the project-level container#

A workspace is the top-level project container. Use one workspace per repo, task, or investigation.

A workspace is the top-level project container, and the official advice is one repo, one task, or one investigation = one workspace.

It owns tabs and panes, and has one crucial behaviour:

Its sidebar state rolls up from the agents inside it, so you can see which project needs attention.

Its sidebar state is rolled up from the agents inside it, so you can tell which project needs you.

That is the technical reason behind “one repo, one workspace”: the rollup granularity is the workspace. If you cram eight projects into one workspace, the sidebar can only tell you “something in this pile is waiting on you”, not which project.

Measured on this machine, real herdr workspace list output:

{"id":"cli:workspace:list","result":{"type":"workspace_list","workspaces":[
  {"active_tab_id":"w3:t1","agent_status":"working","focused":true,
   "label":"rex-videos","number":1,"pane_count":3,"tab_count":3,
   "workspace_id":"w3"}]}}

Note that agent_status: "working" is a rolled-up value, label takes the directory name rex-videos (the behaviour when a workspace’s custom_name is null), and number is what you use to jump to it by number in the UI.

3. Tab: one layout inside a workspace#

A tab is the layout unit within a workspace. The official usage suggestion is split by view: agents, logs, server, review.

One property is easy to overlook but very important:

Tabs are addressable from the CLI and socket API.

Tabs can be addressed from the CLI and the socket API. That means you can script “open a pane in the logs tab and run the tests” without stealing focus from the tab the user is looking at. This is the foundation of module 4, programmatic control.

Tab ids on this machine look like w3:t1, w3:t2, w3:t4 — i.e. <workspace>:t<number>. Note the numbers are not contiguous (t3 is gone), because numbers are not recycled when a tab closes; public_tab_numbers records the set of currently valid numbers.

4. Pane: a real terminal#

A pane is a real terminal. Herdr renders the terminal output, sends input back to the process, and preserves the pane across client detach.

A pane is a real terminal: Herdr renders its output, sends input back to the process, and keeps the pane alive across client detach.

The capability list (per the official concepts page):

  • it can be split to the right or down
  • it can be renamed manually
  • it can be read from the CLI (herdr pane read)
  • input can be sent to it (herdr pane send-keys)
  • it can be closed

Pane ids look like w3:p1, w3:p2, w3:p4 — <workspace>:p<number>, and again numbers are not recycled after close.

5. Agent: the one layer Herdr genuinely adds#

tmux has an equivalent for the first four layers (session/window/pane plus a server). The agent layer is Herdr’s added semantics, and its reason for existing.

An agent is a process Herdr recognizes inside a pane. Herdr detects agents from foreground processes, screen manifests, and optional integrations.

Detection has three sources: the foreground process, a screen manifest, and optional integrations. The first two need no configuration; the third requires installing something (see module 3 ).

The five states#

StatePrecise meaning
blockedthe agent needs input, approval, or a decision
workingthe agent is running
donethe agent finished and you have not looked yet
idlethe agent finished or is waiting, and it has already been seen
unknownHerdr cannot classify it confidently

There is a deeply counter-intuitive design here — make sure you get it#

Official text:

Each client tracks which completions it has displayed. Viewing a completion in one client does not clear another client’s Done badge. CLI/API statuses use the server’s seen state, so they need not match a particular client’s badge; both idle and done mean ready for input.

Broken into three points:

  1. “Has it been seen” is recorded per client, not globally. Looking at a completion on your laptop does not clear the Done badge on your phone’s client.
  2. The CLI / API return the server-side seen state, so they need not match the badge of the client on your screen. This is not a bug; stop arguing between herdr agent list and the sidebar.
  3. done and idle are substantively the same: both mean “ready for input”. The only difference is whether you have looked.

If you are writing automation (module 4 material), the rule this implies is: if you care about “can I feed it the next instruction”, test done + idle together; only use done when you care about “is there a new result a human has not seen”.

Measured on this machine: how the three id levels line up#

{"agent":"pi","agent_status":"working",
 "cwd":"/Users/rex/codes/rex-hugo","foreground_cwd":"/Users/rex/codes/rex-hugo",
 "focused":false,"pane_id":"w3:p2","revision":1,"state_change_seq":38,

 "terminal_title":"π - rex-hugo","terminal_title_stripped":"π - rex-hugo",

FieldMeaning
agentthe recognised agent name (here pi)
agent_statusone of the five states
cwd / foreground_cwdthe pane’s working directory / the foreground process’s working directory (they can differ, e.g. if you cd elsewhere inside the pane before starting the agent)
pane_id / tab_id / workspace_idthe three container ids, exactly the w3:p2 / w3:t2 / w3 pattern described above
terminal_idthe terminal instance id; changes when a pane is recreated
terminal_title / _strippedthe raw terminal title / the version with control sequences stripped

focusedwhether it is the current focus

To find out why a given pane was classified as it was, use herdr agent explain <target> --json — it spreads the detector’s evidence in front of you. That is the first troubleshooting move; do not guess.

6. Client and server: who owns what#

By default, Herdr runs as a background server plus one or more attached clients. The server owns panes and process state. The client is the terminal UI attached to that server.

The server owns panes and process state; the client is just a terminal UI attached to it.

The sizing rules with multiple clients (the docs are unusually detailed here, because it is the easiest thing to trip over):

  • one client only: all tabs follow its size, as before
  • multiple clients: each client can view its own workspaces and tabs; different tabs follow their own client
  • multiple clients on the same tab: the last client that focused, selected or interacted determines that tab’s pane sizes

So “I attached from my phone and the desktop layout suddenly got squashed” is this rule working as designed — the phone became the last client to interact.

Two actions you must not confuse:

# detach: the client leaves, server and agents all still there
ctrl+b then q

# actually ending the session and stopping every pane
herdr server stop

7. Mode: where your keystrokes actually go#

Herdr has three modes; understanding them is understanding “why my shortcut did nothing”:

ModeWhere keys goHow you enter it
terminal modeinto the focused pane (i.e. to whatever runs inside)the default state
prefix modewaits for one Herdr action key, then returns to terminal modepress the prefix key (default ctrl+b)
navigate modea persistent workspace navigation surfacevia a binding (e.g. prefix+w)

The prefix press needs special attention: press ctrl+b, release, then press the action key. Not all three at once.

The most useful action keys (from the official quick-start table):

ActionKey
split rightprefix+v
split downprefix+minus
new tabprefix+c
next / previous tabprefix+n / prefix+p
workspace navigationprefix+w
new workspaceprefix+shift+n
detach clientprefix+q
list every binding currently in effectprefix+?
enter copy mode (keyboard copy)prefix+[

prefix+? is the one worth memorising — it is live, showing the bindings actually in effect right now, including your own changes. When you forget a key, press it; do not go digging through docs.

8. Mouse-first: the keyboard is an optional layer#

The official concepts page gives this its own section, which shows it is design intent rather than a convenience feature:

Herdr is mouse-native. You can click panes, tabs, workspaces, and agents. You can drag split borders, select text, and use right-click menus. Everything below is also reachable by mouse; keyboard bindings are an optional layer.

The concrete gestures (quick-start page):

  • click a pane / tab / workspace / agent to focus it
  • drag a split border to resize
  • right-click for a context menu containing split-pane and new-tab
  • drag-select text to copy it to the clipboard, no ctrl+c needed
  • double-click selects a token; holding the second click and dragging extends the selection word by word
  • Ctrl + click opens links inside a pane (OSC 8 hyperlinks and http(s)://, including links whose ends fall outside the visible area when wrapped). On macOS, when mouse capture is on, Herdr-handled links use Ctrl-click; Cmd-click only works through the terminal’s native bypass (e.g. Shift-Cmd-click, or ui.mouse_capture = false)

If you do not want Herdr grabbing the mouse:

[ui]
mouse_capture = false

There is also an advanced switch, ui.right_click_passthrough_modifier: with it set, “that modifier + right-click” passes through the right button’s press/hold/drag to mouse-reporting programs inside the pane (for example a TUI agent’s own right-click menu). To send plain right-clicks straight to a given pane program, choose Send right-clicks to pane in its menu, or run inside it:

herdr pane input --current --right-click pane

After that, right-clicking the pane’s border brings Herdr’s own menu back.

 "active": 0, "selected": 0,

 "collapsed_space_keys": []}

Re-check the concepts against this JSON and they stick:

  • version: 3 is the state format version, not the Herdr version
  • workspace w3’s identity_cwd is rex-videos — a workspace’s identity is bound to a directory, and its label comes from there too
  • public_tab_numbers is [1,2,4] and next_public_tab_number is 5 — confirming numbers are not recycled (tab 3 was closed)
  • every layout here is {"Pane": n}, i.e. a single pane with no splits; after splitting this field becomes a tree
  • each pane stores only cwd — the process itself is not here; it lives in the server’s memory and the PTY is held by the server
  • zoomed / focused / active_tab are UI state, and they are persisted too

So the precise answer to “what does Herdr remember” is: it remembers layout, identity and cwd, plus (via snapshots and agent integrations) what is needed to restore; live processes belong to the server. That boundary is exactly what module 1 article 3, the five state paths, is about.

10. Granularity decision table: what should you actually open next#

This table is what I worked out by using it; it is not in the official docs:

SituationOpen a new…Reason
another long task (another agent) in the same projectpane (same tab or a new one)the sidebar rolls up at workspace level, so same project belongs in the same workspace
you want to separate “the agent fleet” from “logs/services” visuallytaba tab is the layout unit and is CLI-addressable, so scripts can push things into it
a different repo / an unrelated piece of workworkspacethe rollup granularity is the workspace; mixing them makes the sidebar meaningless
a throwaway risky experiment you do not want to pollute the main environment withworkspace, plus a tab if neededclosing a workspace is cleaner than cleaning up panes
work and personal fully isolated, not even sharing a socketnamed sessiona session is a runtime namespace, the highest isolation level
running agent fleets for different teams/users on one machinenamed sessionindependent persisted state and log directories (sessions/<name>/)
you just want to look at one agent’s terminalattach directly to that agentno layout switching needed; see herdr agent attach

11. Traps to avoid#

  1. Do not run herdr inside a pane. echo $HERDR_ENV first — 1 means you are already in; Herdr blocks nested startup by design. The pane also exposes HERDR_PANE_ID / HERDR_TAB_ID / HERDR_WORKSPACE_ID / HERDR_SOCKET_PATH, which is very handy in scripts.
  2. Do not cram eight projects into one workspace. The sidebar’s rollup granularity is the workspace; mixing them throws away Herdr’s most valuable capability.
  3. done vs idle is not “finished vs idle”. Both mean ready for input; the only difference is whether you have looked, and seen-state is recorded separately per client. It is normal for CLI output not to match the badge on your screen.
  4. detach ≠ stop. After prefix+q or closing the window, the server and agents are all still there; only herdr server stop really stops things. Conversely, if an agent has vanished, first check whether the server was stopped or the machine rebooted.
  5. When several clients view the same tab, size belongs to whoever interacted last. Attaching from a phone squashes the desktop layout; that is not a rendering bug. Avoid it by not pointing two clients at the same tab.
  6. Do not default to “one session for everything” and then spawn workspaces frantically inside it. Isolation at the session layer costs something: you have to remember what lives in which session, and logs scatter across sessions/<name>/. Almost everyone only needs the default session plus multiple workspaces.

Frequently Asked Questions

What is the difference between a Herdr session and a workspace?

A session is the background server's namespace: it decides the socket, the persisted state and the isolation boundary of the runtime. A workspace is a project-level container inside a session; it owns tabs and panes, and the sidebar rolls agent state up per workspace. The official guidance is to use workspaces first and named sessions only when you need completely separate panes, sockets and persisted state.

What are the Herdr agent states?

blocked (needs your input, approval or decision), working (running now), done (finished but you have not seen it yet), idle (finished or waiting, and already seen), unknown (cannot be classified confidently). Both idle and done mean ready for input; they differ only in whether it has been seen.

Why does the agent state from the CLI disagree with the badge on my screen?

Each client records which completions it has displayed. Viewing a completion in one client does not clear another client's Done badge. The CLI and API use the server's seen state, so they need not match any particular client's badge.

What happens when several terminal windows attach to one Herdr?

That is allowed. With a single client all tabs follow its size. With multiple clients each can view its own workspaces and tabs, and tabs follow their own client. When several clients view the same tab, the last one that focused, selected or interacted determines that tab's pane sizes.

What is prefix mode and which key is the prefix?

Three modes: terminal mode sends keys into the current pane; prefix mode waits for one Herdr action key after the prefix; navigate mode is a persistent workspace navigation surface. The prefix defaults to ctrl+b, pressed as ctrl+b, release, then the action key — for example c for a new tab, w for workspace navigation, q to detach. prefix+? lists every binding currently in effect.

How do I tell whether I am already inside Herdr?

Check the HERDR_ENV variable: the value 1 means you are. Inside the same pane there are also HERDR_PANE_ID, HERDR_TAB_ID, HERDR_WORKSPACE_ID and HERDR_SOCKET_PATH to read your own identity from. Herdr blocks nested startup by design, so running herdr again in a pane will not give you a second layer.
