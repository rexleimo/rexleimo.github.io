What Herdr Is: Why tmux Stopped Being Enough

Herdr is 'the runtime your coding agents live on': a Rust Apache-2.0 project where a background server holds the real terminals and the TUI / CLI / plain SSH session are just clients attached to it. What it adds over tmux is semantics — agent state (blocked / working / done / idle), attaching straight to a single agent, and a read-send-wait API for scripts and agents. This article shows the difference using real output from herdr 0.9.2 on this machine, and is honest about who does not need it.

September 29, 2026 · 11 min · 2207 words · Mengshou Programming -  |  中文

Verified version: herdr 0.9.2 (stable channel, released 2026-09-29) · tested on this machine: macOS / Apple silicon · 2026-09-29

This article answers one question: what Herdr actually is, and on what grounds it is not “yet another tmux”.

Conclusion first, argument afterwards:

Herdr is a runtime, not an app. A background server holds the real terminal processes and your agents live in them; the TUI, the CLI, even a plain SSH session are all just clients that attach. tmux has the same server/client structure — what Herdr adds is semantics: it knows which pane holds an agent, whether that agent is blocked waiting for you or working, and how to wait for it rather than poll it.

1. Start with a scenario you have probably already hit#

Say you have all of these open at once today:

  • an agent refactoring the backend, running for 20 minutes
  • an agent writing tests that stopped halfway to ask you to confirm a delete
  • npm run dev serving the frontend
  • a log window
  • an SSH session to a dev box with two more agents in it

Now: which one is waiting on you?

With tmux the answer is “no idea, go look one by one”. tmux ls tells you there are 3 sessions, but not which session has an agent stuck on “needs you to approve this command”. You can only prefix + n through them, or watch the screen waiting for a notification.

That is not a tmux bug. tmux dates from around 2007 and its design goal was “let human terminal sessions survive” — persistent PTYs, detach, SSH back in and reattach. It does that extremely well, and Herdr inherits that whole capability intact. What it never did was “understand what runs in the pane”, because in the era it was born in, only shells ran in panes.

In 2026 that changed: panes now hold active processes. They work on their own, stop halfway to ask you to approve a command, and finish waiting for you to look. So “which one is waiting on me” became a question you answer dozens of times a day.

Herdr is designed around exactly that question. The official repo description is seven words:

the runtime your coding agents live on

2. The definition, split into three layers#

The official positioning is Terminal workspace manager for AI coding agents. Unpacked, that is three capability layers, each matching an action you will really use.

Layer 1: it is a multiplexer (identical to tmux here)#

A single background server process holds the real terminals (PTYs); clients attach to render them. Detach, close the terminal window, drop SSH — the processes in your panes keep running.

herdr            # start or attach the default background session
# ctrl+b then q  → detach, the agent keeps running
herdr            # run it again and you are back in the same session
herdr server stop  # if you truly want everything stopped, this is the only way

Here is the most common beginner mistake: thinking that closing the window stopped things. It did not. To stop, use herdr server stop.

Layer 2: it is mouse-first (the opposite of tmux here)#

The barrier to tmux is bindings. Herdr explicitly makes the mouse the primary entry point and the keyboard an optional layer:

  • click a pane / tab / workspace / agent to focus it
  • drag a split border to resize
  • split panes and create tabs from the right-click menu
  • drag-select text to copy it to the clipboard (no ctrl+c needed); double-click selects a token, and holding the second click drags to extend word by word
  • ctrl + click opens links inside a pane (OSC 8 hyperlinks and http(s):// are supported, including wrapped links)

The official docs, verbatim: No keybindings are required to use Herdr.

If you simply dislike terminal programs grabbing the mouse, one line turns it off:

[ui]
mouse_capture = false

Layer 3: it is agent-aware (this layer is its reason to exist)#

Herdr recognises the coding agent in a pane, assigns one of five states, and rolls them up per workspace in the sidebar. This is the real herdr agent list output from this machine (re-wrapped for line breaks, content unchanged):

{"id":"cli:agent:list","result":{"agents":[
  {"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-videos",
   "focused":true,"pane_id":"w3:p1","tab_id":"w3:t1",
   "terminal_title":"π - rex-videos","workspace_id":"w3"},
  {"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-hugo",
   "pane_id":"w3:p2","terminal_title":"π - rex-hugo"},
  {"agent":"pi","agent_status":"working","cwd":"/Users/rex/codes/rex-hugo",
   "pane_id":"w3:p4","terminal_title":"π - rex-hugo"}],"type":"agent_list"}}

Note several things:

  • it identified the agent as pi, not “some node process”
  • it knows each agent’s cwd (which project), pane_id, tab_id, workspace_id
  • it captured the terminal title π - rex-hugo
  • the state is working

And this machine has not one Herdr integration installed:

$ herdr integration status
pi: not installed (/Users/rex/.pi/agent/extensions/herdr-agent-state.ts)
omp: not installed (/Users/rex/.omp/agent/extensions/herdr-omp-agent-state.ts)
claude: not installed (/Users/rex/.claude/hooks/herdr-agent-state.sh)

This is the first key to understanding Herdr: detection and integrations are two different systems. Detection works through three channels — foreground process + screen manifest + optional integration — so you get baseline capability with zero configuration. An integration (a reporting script installed into the agent’s hook / extension directory) additionally buys you lifecycle-grade state and agent-native session restore — but it does not necessarily replace screen detection. Module 3 takes that apart in a whole article.

3. Herdr vs tmux / zellij, point by point#

First what is the same, because this is the part most easily overstated:

  • both are server + client, with panes alive in the server
  • both support detach / reattach and reconnecting over SSH
  • both have a prefix key (Herdr’s also defaults to ctrl+b, same as tmux)
  • both split panes, open multiple tabs and keep scrollback

Now the six things that differ:

Dimensiontmux / zellijHerdr
What a pane is to ita PTY; it does not care what runs insideit tries to determine “which agent is this” and tracks its state
State semanticsnone. tmux ls gives session namesfive states blocked / working / done / idle / unknown, rolled up per workspace in the sidebar
Waiting for an agentyou poll (capture-pane + grep)first-class: herdr agent wait, plus state subscriptions over the socket API
Interaction entrykeyboard-first, mouse support bolted on latermouse-first, keyboard optional (mouse_capture = false available)
Multiple machinesone tmux per machine, you switch windows yourselfLocal and saved SSH machines in the same window, merged agent list, independent reconnect per connection
Direct access to one agentno equivalent conceptyes: attach straight to a single agent’s terminal

The official compare page External link gives a larger matrix splitting 9 tools into five categories. Note this is a vendor’s own comparison and therefore has a position; I list it because the classification dimensions themselves are useful reference:

CategoryExamples“Does the work survive when the thing you were looking at goes away?”
runtime + clientsHerdrYes. The server holds the terminals; the TUI can crash and the agent never notices
terminal multiplexerstmux / zellijYes. Detach and you are fine, but there is no agent semantics
terminal appscmux / WarpDepends on session restore. The work moved into its window, its renderer
process dashboardsSoloOnly while the app is open. It watches dev-stack up/down
managed appsConductor / Emdash / SupersetOnly while the app is open. Quit the app, the agents stop with it

The official write-up itself highlights the decisive row in that table: what happens to the agents when the thing you’re looking at goes away — what happens to the agents when the thing you are looking at disappears.

I agree with that criterion, because for “agents running long tasks” it is the one that bites: with an app-shaped tool, you quit it to save memory and eight agents that have been running for half an hour are gone. Under the runtime shape, the client is disposable.

One thing to say plainly: these categories are not enemies. Herdr’s own docs say so — it can be paired with a worktree/diff manager, and it runs inside whatever terminal you already like (no need to change ghostty / kitty / iTerm / alacritty).

Two points worth noting:

  1. The version is still 0.9.x, not 1.0. It iterates fast (a stable every 13 days, with a preview almost daily in between), which for a user means: fixes land quickly, but the official docs say explicitly that the preview channel “can regress”. In production, stay on stable.
  2. Rust + Apache-2.0 means it can be audited and self-built (the official Nix flake is provided), which is a hard requirement inside enterprise networks.

5. Five traps worth remembering from this article alone#

  1. Do not run herdr inside a Herdr pane. The docs are explicit that Herdr blocks nested startup by design. How to tell whether you are already inside: echo $HERDR_ENV — the value is 1 if you are. (Every measurement in this column was taken inside a Herdr pane, with HERDR_ENV=1 and TERM_PROGRAM=herdr.)
  2. Do not feed Herdr a tmux config. It does not eat .tmux.conf; the config file is ~/.config/herdr/config.toml (on Windows %APPDATA%\herdr\config.toml), and it runs fine with no config file at all. To see every default: herdr --default-config (measured on this machine: 377 lines, all commented-out defaults).
  3. Closing a window ≠ stopping. The panes and agents are still in the server. To really stop: herdr server stop. Conversely, if an agent mysteriously “disappeared”, first check whether the server was stopped or the machine rebooted — those two cases have different recovery paths, see module 1 article 3.
  4. herdr update only works for installer-based installs. Homebrew / mise / Nix installs must be upgraded with their own package manager, otherwise you end up with a new client and an old server. To check for that mismatch: herdr status, look at endpoint_compatible and update.server_binary_stale.
  5. Do not assume installing an integration solves everything. The docs repeat it: an integration may provide lifecycle state, native session restore, or both, but it does not necessarily replace screen detection. The diagnostic order is always herdr agent list first (what does it see), then herdr agent explain <target> --json (why did it decide that), and only then herdr integration status.

6. Who does not need Herdr#

Saying the negative part clearly beats one-sided praise:

  • You run one agent locally and look at it when it finishes. A normal terminal window plus the agent’s own notifications is enough; an extra resident server is pure overhead.
  • What you want is a better terminal. Herdr explicitly does not replace your terminal; it runs inside the one you have. A new renderer or new completion experience is ghostty / Warp / kitty territory.
  • What you want is worktree / diff / review-queue management. That is the core capability of managed apps like Conductor / Emdash / Superset; Herdr merely pairs with them.
  • You need a native Windows ARM64 build. Today you get the x86_64 build under Windows emulation: usable, not native.
  • You flatly reject a resident background process. All of Herdr’s value rests on “the server outlives the client”; refuse that model and you cannot use it.

Frequently Asked Questions

What is Herdr?

The official two-sentence definition: a terminal workspace manager for AI coding agents, and the repo description 'the runtime your coding agents live on'. Technically it is a multiplexer: a background server holds the real terminal processes and clients attach to render them.

How is Herdr different from tmux?

The persistence half is identical (the server owns the PTYs, processes keep running after detach, you can SSH back in). The difference is that Herdr knows which pane holds an agent, whether it is blocked or working, and how to wait for it instead of polling it. Herdr is also mouse-first, and its TUI / CLI / plain SSH are all clients of the same runtime.

Is Herdr open source, and what is it written in?

Yes. The repository is github.com/herdrdev/herdr, written in Rust under the Apache-2.0 licence, created 2026-03-27, with roughly 41k stars as of 2026-09-29. The official docs also provide a Nix flake for building from source.

Which platforms does Herdr support?

The stable channel ships Linux, macOS and Windows x86_64 binaries. Windows is GA but with platform caveats; Windows ARM64 runs the x86_64 build under Windows emulation.

Do I have to memorise keybindings to use Herdr?

No. Herdr is mouse-first: click panes/tabs/workspaces, drag split borders, right-click to split and create, drag-select to copy. The keyboard is an optional layer; the prefix key defaults to ctrl+b, and prefix+? lists every binding currently in effect.

Can Herdr recognise my agent without any integration installed?

Yes. Detection comes from the foreground process, a screen manifest and optional integrations. Verified on this machine: with all 18 official integrations reporting 'not installed', herdr agent list still correctly identified 3 pi agents in state working. Integrations buy you more reliable lifecycle state and agent-native session restore.
