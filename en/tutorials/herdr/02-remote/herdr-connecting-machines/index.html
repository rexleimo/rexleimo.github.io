Connecting Herdr to Machines: Local and Saved SSH Machines in One Window, a Cross-Machine Agent View, Independent Reconnect

Put local work and remote agents in the same Herdr window: the interactive discovery flow of herdr machine add and its naming rules, one profile mapping to exactly one remote session, client/server compatibility negotiation and approval-based installation, who streams and who only updates state when you switch machines, the dimmed-cache semantics on connection loss, the three connection states Reconnecting / Attention (!auth, !error) / saved-machine file error, SSH authentication recovery (machine status, machine reconnect, ControlPersist 600), and the easiest trap to fall into — ID scoping: w1:p1 can exist on two machines, so remote automation must carry the --machine prefix.

September 29, 2026 · 16 min · 3314 words · Mengshou Programming -  |  中文

Verified version: herdr 0.9.2 (stable channel) · tested on this machine: macOS / Apple silicon · 2026-09-29 Measured herdr machine list on this machine: No saved SSH machines. (a clean environment, which happens to be ideal for describing the default behaviour)

The previous two articles covered one machine. But a real agent workflow usually looks like: two agents on the laptop, three on a Linux build box, and maybe a GPU machine somewhere.

Herdr’s answer is not “open three terminal windows”. It is:

Save an SSH machine once, then switch between its workspaces and Local inside the same Herdr window, without opening another client. The agent list includes connected machines, so you can see which machine the work is running on and which agent is waiting for an answer.

Conclusion first:

Three things to memorise before anything else. ① each machine has its own server — dropping one does not affect the others, and that is design, not luck. ② one profile maps to one remote session, not “all sessions on that machine”. ③ IDs are scoped per server — w1:p1 may exist on two machines at once. So remote automation must carry the --machine prefix, or you will send commands to the wrong machine.

1. Before connecting: get plain SSH working first#

Precondition: you have normal SSH access to the remote machine. Verify it:

ssh workbox

workbox may be a host in your SSH config, or you can use a target form directly: ssh://you@server:2222.

Platform support matrix (multi-machine connections):

Local clientRemote server
Linux / macOS / WindowsLinux or macOS, x86_64 or aarch64
Linux / macOS / WindowsWindows, x86_64 only

Two more distinctions about install behaviour that matter:

  • interactive installation may install or update the full remote package after confirming with you
  • background reconnect only discovers (installed packages) and never installs anything

2. herdr machine add: how a profile is born#

It must run in an interactive terminal, so Herdr can ask you before installing or replacing anything:

herdr machine add workbox

The session discovery flow (per the official wording)#

In an interactive terminal Herdr discovers running sessions:

SituationHerdr’s behaviour
exactly one running sessionauto-selects it
severallets you choose with Up/Down + Enter; Esc or Ctrl+C cancels
query succeeded but no running sessionuses default
no Herdr installation foundoffers to install for default
the installed binary cannot report its sessionserrors; use --remote-session <name> explicitly

Skip discovery and name the session directly:

herdr machine add workbox --remote-session agents

Non-interactive commands always use default unless you pass --remote-session.

Naming rules#

CaseShown in the sidebar as
machine add workbox (default session)workbox (the SSH host with the user@ prefix stripped)
with --label "Build machine"Build machine
with --remote-session agents and no --labelworkbox/agents
default name already takenmachine add requires you to pass --label

A machine profile targets one remote session; it does not merge every session on the host. To see two sessions on the same machine, add it twice with two different --label values.

Compatibility negotiation and approval-based installation#

This is where Herdr behaves with restraint, worth reading item by item:

  • Herdr checks both the installed binary and the running server
  • it starts the requested background server before saving the profile
  • compatible client and server versions do not have to match (negotiation, not equality)
  • missing or incompatible installations go through an approval-based install flow
  • when a running server must be replaced, the install flow asks first before stopping it and its pane processes, then starts a compatible server. The default answer is No.
  • if both install and replacement are needed, one confirmation covers both
  • machine add does not use the experimental live handoff
  • cancelling or a failed install → the profile is not saved

On a Windows server there is one extra step: the install flow inspects the executables used by Herdr processes owned by the SSH user and verifies their capabilities before reusing them — so even if the SSH PATH points at an older install, a compatible running build can still be used.

After adding#

herdr

opens the UI. If a local client was already open:

  • a newly added, enabled machine usually appears within a second and connects in the background without changing your current selection
  • a machine switch in progress finishes first, and only then are profile changes applied
  • the remote server keeps running after the install flow exits

3. Switching between machines#

Mouse#

Select a machine in the sidebar, or one of its workspaces.

The key semantics:

The selected machine receives your pane input and terminal size, and supplies the visible terminal content and graphics. Other connected machines keep updating their workspace information, agent state and notifications, but do not stream pane screens.

That is why “watching four machines in one window” is feasible bandwidth-wise — only one picture is flowing.

Collapse arrows: clicking the arrow next to any machine collapses or expands its workspace list without switching away from your current workspace. It also works while that machine is reconnecting.

Keyboard: prefix+w#

Press prefix+w, then use the workspace navigation keys (default Up/Down) to highlight workspaces across connected machines in sidebar order:

KeyBehaviour
Enteractivates the highlighted workspace
Esc or the prefix keycancels, no switch
—both compact and expanded sidebars reveal the highlighted row, including under a collapsed machine
—on desktop it wraps at both ends; the mobile switcher stops at the first or last workspace
—disconnected machines are skipped

One operational discipline that prevents accidents (the docs call it out explicitly):

When you highlight a workspace on another machine, press Enter before using any other keyboard action. This prevents pane / tab / workspace / custom-command shortcuts from acting on the current machine by mistake.

Clicking cancels the keyboard preview on the remote surface. The expanded sidebar honours each machine’s own collapsed worktree groups.

Local’s special status#

  • Local opens immediately at startup, without waiting for SSH connections
  • selecting Local also cancels an unfinished remote switch, without waiting for the remote machine to answer
  • if Local itself is reconnecting, your selection is restored once it is ready
  • Local accepts input only after its new screen and terminal settings are ready
  • one stuck machine cannot hold up input on another

That last line is the most important availability guarantee in the multi-machine story.

By the way: multiple Herdr clients can view different tabs on the same server independently; for the shared-tab sizing question see the client-server section of core concepts .

What you actually see when a connection drops#

When the connection is lost, the last workspace and agent state remain visible but dimmed. That is cached information, not live state. Until a new connection and a matching screen arrive, input and navigation to those cached panes stay disabled. Reconnecting never takes the selection away from the machine you are using.

The “dimmed” visual cue deserves to be memorised deliberately: dim = the state you think you have, not the real state.

4. Renaming, disabling, removing#

Read the profile ID from the list first; do not derive it from a label or hostname:

herdr machine list
herdr machine rename <profile-id> --label "New name"
herdr machine disable <profile-id>
herdr machine enable <profile-id>
herdr machine remove <profile-id>

In scripts, add --json to machine list.

Measured on this machine (no saved machines yet):

$ herdr machine list
No saved SSH machines.

$ herdr machine status
No saved SSH machines.

$ herdr machine --help
Manage saved SSH machines

Commands:
  list       List saved SSH machines
  status     Check saved machines without prompting for authentication
  reconnect  Authenticate a saved machine in this terminal and verify connectivity
  add        Prepare the remote Herdr server and save an SSH machine
  rename / remove / enable / disable ...

Note the official description of status: Check saved machines without prompting for authentication — no credential prompt, which is what makes it usable in scripts and health checks.

The semantic difference between the three operations:

Operationprofileremote server / agent
renamechanges the display label, does not reconnectunaffected
disablekept, usable again lateronly disconnects that machine from the client; the remote session and agents keep running, even if the host becomes unreachable
removeforgottensame as above

Two boundary behaviours:

  • removing or disabling the machine you are viewing → you are sent back to Local.
  • if Local is also unavailable, Herdr says so and retries its connection rather than picking another remote machine. With enabled saved machines, the client can stay usable even when Local fails or restarts.

5. The three connection states and what to do in each#

StateMeaningWhat you should do
Reconnectingautomatic retry after a network drop, sleep, or SSH failureusually nothing at all
Attentionthe target needs an action: authentication, host-key approval, or a compatible serverclick the badge to see the error and the CLI command it gives you
Saved-machine file errorthe directory file is unreadable or invalidnothing: current connections are unaffected, Herdr notifies and retries the read automatically

Reconnecting’s retry policy (the details matter)#

  • repeated failures increase the delay, up to two minutes
  • a brief successful connection does not reset that delay
  • a connection must stay healthy for one minute before the next interruption gets fast retries again
  • SSH connections are checked for application-layer activity and probed actively when quiet — so a broken connection will not show Online indefinitely
  • Local detects native connection close or failure rather than using remote health probes

The two Attention badges#

  • ! auth = authentication failed
  • ! error = something else
  • click the badge → shows the latest error plus the relevant CLI command
  • it never opens a credential popup
  • in a collapsed sidebar both appear as !
  • the rest of the machine row keeps its normal expand/collapse behaviour
  • an unknown or changed host key stays in Attention (host-key checking behaviour is unchanged)
  • other machines remain usable

The hard boundary on background connections (the most misunderstood rule)#

A background connection never answers prompts, and never installs, updates, restarts or hands off a server.

So for non-authentication Attention, run the standalone install command Herdr points you at, in an interactive terminal:

herdr --remote workbox

Use your profile’s target; if you chose a named session when adding, include --session <name> here too. Follow the prompts and an open client retries automatically.

Two disciplines:

  1. machine reconnect neither installs nor updates Herdr (it only authenticates and verifies connectivity)
  2. do not stop a running server merely because its version differs from the client’s

When authentication fails#

Check plain SSH first. For passphrase-protected keys, ssh-add them into ssh-agent before Herdr’s non-interactive background reconnect starts.

Git authentication and SSH signing (inside remote panes)#

Enable this in your SSH config for trusted hosts:

ForwardAgent yes

Herdr will not turn forwarding on for you. Once it is on:

  • when a session starts with an agent, updated Linux and macOS servers give panes a stable agent address, so both existing and new panes can use the forwarded agent after a --remote or saved-machine reconnect
  • a working inherited agent or an earlier connection takes priority over later clients and transient install checks; if it disappears, another live attachment can supply the agent
  • ⚠️ this needs an updated remote server, not just an updated local client
  • a Local session started without an agent leaves SSH_AUTH_SOCK untouched
  • panes created before the server update, or before an agent was first supplied to the session, keep their original environment and must be recreated once to inherit the stable address
  • older compatible servers and connections without agent forwarding still attach normally

6. The SSH authentication recovery mechanism#

This section’s machinery is convoluted, but understanding it saves a lot of “why is it asking me to authenticate again”.

On Linux and macOS clients, and when remote.manage_ssh_config = true:

Herdr shares one approved OpenSSH connection between machine add, sidebar and saved-machine API commands.

The three related commands and concepts:

Command / conceptDescription
herdr machine status [<label-or-id>] [--json]a fresh, non-interactive check
what Reachable meansthe remote Herdr server is available now; it does not mean every open TUI is connected
herdr machine reconnect <label-or-id>completes native SSH authentication in the terminal and verifies the saved machine; does not install or update Herdr

The recovery timeline:

  • an open client re-checks failed connections within 30 seconds, no restart needed
  • the shared connection uses ControlPersist 600 (10 minutes idle) — ⚠️ that is not an MFA lifetime. Live connections can stay open, but corporate policy, the SSH server or the network may end them sooner
  • recovery on local Windows is not yet supported
  • for unmanaged SSH connections, authentication remains your responsibility: running ssh by itself does not authorise Herdr unless it is using the shared ControlPath
  • host-key checking is unchanged: an unknown or changed host key is still Attention

Background idle cleanup#

When both installations support bridge idle cleanup, a saved-machine connection to Linux and macOS closes its remote bridge after one minute with no traffic in either direction:

  • sleep counts toward that window, checked when the host wakes
  • quiet healthy connections exchange health checks; you do not need to type to keep watching continuous output
  • cleanup preserves the remote Herdr server, sessions and pane processes
  • older installations remain compatible without this optional cleanup

7. Settings, ID scope, and automation#

Whose settings does the UI use?#

The UI uses the client’s local theme, sidebar settings and keybindings by default. Custom commands and plugins advertised by the selected server still run on that server. Herdr does not copy local command plugins, configuration, executables or keys onto the SSH host. A missing remote command fails visibly.

After changing client settings, use the UI’s reload config action.

Sidebar agent rows: when several machines exist, the default agent row shows a machine token. Existing custom rows are preserved — if you want that label in your layout, add machine explicitly. Sidebar row layouts External link also support conditional colours for the machine label.

ID scope: the biggest trap in this article#

Workspace, tab and pane IDs and agent names are scoped to a single server. Two machines can both contain w1:p1, or both have an agent named reviewer.

And one counter-intuitive behaviour:

Selecting a machine in the UI does not redirect CLI commands already running inside a pane — they still use the session and socket that pane inherited.

So the correct shape of remote automation is:

# 1. list the agents on the remote machine first
herdr --machine <label-or-id> agent list

# 2. then control those remote IDs with the same prefix
herdr --machine <label-or-id> pane send --pane w1:p1 ...
  • the CLI uses the saved profile’s SSH target and session directly; it does not need an open TUI
  • without --machine, the existing session/socket routing is completely unchanged

(For which commands are supported, the update requirements and the remote path rules, see the saved SSH machines section of the CLI reference External link .)

8. What is stored, and what is not#

The profile stores only: an opaque ID, the label, the SSH target, the explicit remote session, and the enabled state.

Herdr stores no passwords, private keys, agent tickets or SSH control sockets in the catalogue. Authentication stays with OpenSSH.

Cached separately: each machine’s remote OS and resolved executable path, so repeated --machine commands can skip discovery.

  • existing profiles learn missing information on first use
  • this cache is optional: a missing, invalid or unwritable cache file does not stop commands working
  • commands still check live server compatibility
  • if the cached executable is missing, or no longer supports API forwarding, Herdr rediscovers it during the initial read-only check
  • ⚠️ it never automatically repeats a command that could have changed remote state (a design decision worth applauding)

Version and capability negotiation#

  • client and server negotiate compatibility rather than requiring matching versions
  • saved-machine connections additionally require the server’s surface_interest and health_check capabilities — an older server without them shows Attention until it is explicitly updated, even though standalone attach would work
  • other missing server methods only disable the corresponding actions
  • updating a compatible client does not replace the running remote server, nor stop its agents — when you need new server-side behaviour, update that server explicitly
  • a normal replacement asks first before stopping the server and its pane processes
  • live handoff is experimental and opt-in: for a supported server that must be replaced during a standalone install flow you can add --handoff to herdr --remote explicitly; ordinary connecting and authentication fixes never require it

9. Traps to avoid#

  1. Confirm ssh workbox works before machine add. Authentication problems surface there, ten times faster than guessing inside Herdr.
  2. Passphrase-protected keys need ssh-add first. Background connections do not prompt; they simply fail into ! auth.
  3. Run machine add in an interactive terminal. Background connections never answer prompts, install, update, restart or hand off.
  4. One machine, one session. To see two sessions on one host, add it twice with two --label values.
  5. Remote automation must carry --machine. Otherwise w1:p1 may point at your local machine — IDs are scoped per server.
  6. Selecting a machine in the UI ≠ redirecting the CLI. Commands already running in a pane use that pane’s inherited session/socket.
  7. Do not click the sidebar to retry on ! auth. Run herdr machine reconnect <label-or-id> in a terminal; for non-authentication Attention, run the herdr --remote <target> command Herdr suggests.
  8. Do not stop the remote server “to align versions”. Versions need not match; stopping ends every pane process.
  9. Dimmed rows are cache. Do not act on them; wait for the reconnect.
  10. ControlPersist 600 is not an MFA lifetime. Corporate policy may cut connections sooner, and that is normal.
  11. Herdr will not set ForwardAgent yes for you. And panes created before the server update must be recreated once to inherit the stable agent address.
  12. Removing a machine does not stop the remote agents. That is a feature; but it also means you may think you cleaned up while they are still running — to really stop them, run herdr server stop on that machine.

Next step#

Multi-machine solves “watch several machines from one window”. But remote work itself has three completely different paths: SSH in and run herdr, the herdr --remote thin client, and mobile SSH — they differ in clipboard capability, where keybindings come from, and who owns the UI. How to choose is in the three remote work paths .

Frequently Asked Questions

Does a disconnect on one machine affect the others?

No. Each machine keeps its own Herdr server, sessions and running processes, so losing the connection to one machine does not disconnect the others. Reconnecting also never steals the selection away from the machine you are currently using.

Does one herdr machine add profile cover every session on the host?

No. A machine profile targets exactly one remote session. Without --remote-session, Herdr discovers running sessions in an interactive terminal: it auto-selects when there is only one, offers Up/Down plus Enter when there are several, cancels on Esc or Ctrl+C, uses default when the query succeeds but nothing is running, and offers to install for default when no Herdr installation is found.

How is a saved machine's name chosen?

By default the label is the name of the default session, i.e. the SSH host with the user@ prefix removed, for example workbox. --label "Build machine" overrides it. If you pass --remote-session agents without a label it shows as workbox/agents. When the default name is taken, machine add requires you to pass --label.

Do the other machines keep updating while I look at one?

They do. The selected machine receives your pane input and terminal size and supplies the visible terminal content and graphics; other connected machines keep updating their workspace information, agent state and notifications, but do not stream pane screens.

What does the sidebar show after a connection drops?

The last workspace and agent state remain visible but dimmed. That is cached information, not live state. Input and navigation to those cached panes stay disabled until a new connection and a matching screen arrive.

Why must remote automation commands include --machine?

Because workspace, tab and pane IDs and agent names are scoped to a single server: two machines can both contain w1:p1, or both have an agent named reviewer. Selecting a machine in the UI does not redirect CLI commands already running inside a pane — those still use the session and socket that pane inherited. So list first with herdr --machine label-or-id agent list, then keep the same prefix on every command that controls those remote IDs.
