Herdr's Three Remote Work Paths: Run herdr over SSH, the --remote Thin Client, or Mobile SSH — How to Choose

The official principle is 'run Herdr where the work lives, attach from wherever you are'. This article compares the real differences between the three remote paths: SSH in and run herdr (tmux-style, simplest, but entirely remote and blind to your local clipboard), herdr --remote (the remote server owns the panes and streams, your local Herdr draws the UI with local theme and keybindings, and image clipboard paste can be bridged), and mobile SSH (no app and no web dashboard needed, the TUI adapts to a narrow screen); plus direct terminal attach via herdr agent attach / terminal attach, where the remote binary comes from, whether versions must match, manage_ssh_config and ControlPersist, and why passphrase-protected keys need ssh-add first.

September 29, 2026 · 12 min · 2455 words · Mengshou Programming -  |  中文

Verified version: herdr 0.9.2 (stable channel) · tested on this machine: macOS / Apple silicon · 2026-09-29

The official “how to work remotely” page is one sentence long, but it is the charter for the whole remote model:

Run Herdr where the work lives. Attach from wherever you are.

The architectural facts behind that sentence (covered in core concepts ):

Herdr is a background session server plus one or more terminal clients. Panes keep running inside the server. Clients attach, detach, and render the session.

So the real question about “remote” is not “can I connect” but: where is the server, where is the UI, who owns the clipboard, who owns the keybindings. Those four questions account for every difference between the three paths.

Conclusion first:

Default to herdr --remote <host>. It is the only path where the work runs remotely and the UI runs locally, and therefore the only one that can bridge local desktop capability (image clipboard paste). Already living in an SSH shell, or on a phone → just ssh in and run herdr — the least effort. Wanting several machines in one window → do not use any of these three; use herdr machine add (see the previous article ).

The official wording for when to use A is specific:

Use this path when you already live in an SSH shell, when you are using an SSH client on a phone or tablet, or when you want the simplest possible setup.

For B:

Use this path when you want a remote session to feel local.

A and C are really the same path (C just swaps the terminal for a phone), so the rest of this article concentrates on B plus the underlying mechanisms all three share.

2. Path A: SSH in and run herdr#

ssh you@server
herdr

It behaves exactly like a terminal multiplexer:

  • your shell is remote
  • the Herdr server is remote
  • agents and panes run on the remote machine
  • ctrl+b q to detach, drop the connection, then SSH back in and run herdr again

The one cost (stated explicitly in the docs):

If you SSH into the server and run herdr there, Herdr runs entirely on that server and cannot reach your local desktop clipboard beyond ordinary terminal text paste.

For pure text workflows that is irrelevant; for “take a screenshot and hand it to the agent” it is fatal — and that is what path B is for.

3. Path C: the phone#

Herdr works on a phone with no mobile app and no web dashboard. Install any SSH client, connect to the machine running the agents, and start Herdr there.

ssh you@server
herdr

The same persistent Herdr session opens inside your phone terminal. The docs specifically note: the TUI adapts to narrow screens, so you can inspect agents, switch workspaces and check panes without leaving SSH.

On iPhone the official write-up name-drops moshi External link as working well.

The value of this path is not feature count, it is that it reuses the same server: a session you detached on your laptop is the same set of live agents your phone attaches to.

4. Path B: herdr --remote (the thin client)#

herdr --remote workbox
herdr --remote ssh://you@server:2222

The division of labour:

The remote server holds the running panes and sends their terminal content and session state over SSH. Your local Herdr draws the UI, including its sidebar, menus and theme.

Why “the client is local” matters so much#

Because local desktop capabilities can be bridged. The official example is image clipboard paste:

Because the client runs locally, Herdr can bridge local desktop features into the remote session, for example image clipboard paste — by copying the image to a remote temporary file and pasting that path.

Path A structurally cannot do this: its client is remote and never sees your local clipboard.

Whose keybindings apply (an easy detail to miss)#

By default, herdr --remote uses your local Herdr’s keybindings for that attach. That keeps local muscle memory valid even when the remote server’s config differs. After editing local keybindings, apply them with the UI’s reload config action — no detach needed. When you want the remote server’s config, use --remote-keybindings server.

⚠️ One security design decision:

Local custom command keybindings are not sent, because those commands would run on the remote host.

In other words, the lazygit popup you configured in your local [[keys.command]] will not appear in a --remote session — it will not take your local command definitions and execute them remotely.

Reusing an SSH config target#

Host workbox
  HostName server.example.com
  User you
  Port 2222

herdr --remote workbox

Remote named sessions#

herdr --remote workbox --session agents

Combining --session with --remote attaches a named session on the remote host.

5. Mechanisms shared by all three paths#

This section applies to A/B/C alike (the only difference being who triggers it).

Platforms and versions#

Support matrix (remote attach and saved SSH machines):

Local clientRemote host
Linux / macOS / WindowsLinux or macOS, x86_64 or aarch64
Linux / macOS / WindowsWindows, x86_64 only

Once both sides support the stable endpoint generation, local and remote versions do not need to match.

Where the remote binary comes from (three sources)#

On Linux and macOS hosts, Herdr’s search order:

  1. prefer an already-compatible herdr on the remote PATH
  2. then check the common direct-install, Homebrew, mise and Nix profile install paths

On Windows hosts: it checks PATH and the active managed release.

If no compatible binary exists:

Run modeBehaviour
interactiveoffers to install or update one
non-interactivefails rather than modifying the host

Install location: ~/.local/bin/herdr on Linux and macOS; the full Windows package with its app-local ConPTY runtime on Windows. If ~/.local/bin is not on the remote PATH, Herdr warns you after installing.

The three ways a binary can be supplied:

CaseSource
Linux/macOS host and matching platformcopy the current local binary
Homebrew / mise / Nix install, different platform, or a Windows hostdownload the release asset matching the current client version from https://herdr.dev/latest.json
local build or custom packagepoint at the local file with HERDR_REMOTE_BINARY
HERDR_REMOTE_BINARY=target/release/herdr herdr --remote workbox

Use the bare Herdr executable for Linux or macOS targets; use the full herdr-windows-x86_64.zip package for Windows targets.

How the SSH connection is managed#

By default, herdr --remote runs the remote install and bridge through a temporary SSH config: it first includes your own SSH config, then appends fallback keepalive settings. Existing user keepalive settings win.

  • Linux and macOS clients also use a control socket private to each attach for connection reuse
  • Windows OpenSSH does not (no such reuse)
  • to opt out of Herdr’s generated config and control socket entirely:
[remote]
manage_ssh_config = false

After that it is plain ssh.

Authentication#

  • remote attach uses your normal OpenSSH authentication
  • if the target uses a passphrase-protected key and you are in a non-interactive shell, script, CI job or phone terminal (i.e. anywhere a passphrase prompt cannot be shown), load the key into ssh-agent first:
ssh-add
herdr --remote workbox
  • for any remote authentication failure, verify plain SSH access with ssh workbox first, then run herdr --remote workbox again

Does a differing version restart my remote server?#

A version difference alone never replaces or restarts a running remote server. Remote attach asks before stopping a server only when it lacks required compatibility or detached-daemon support. The default answer is No — stopping the server ends its pane processes.

When you genuinely need that one-time upgrade and want to keep the pane processes, add --handoff explicitly:

herdr --remote workbox --handoff

(What handoff does and does not preserve is in the five session-state paths . Repeating it: it is experimental, and machine add does not use it.)

6. A fourth route: direct terminal attach (without the whole workspace UI)#

Strictly speaking this is not a “remote path”, but it answers the other half of the same question: I want only that one agent’s terminal, not the entire UI.

A full Herdr attach opens the whole workspace UI. A direct attach opens a server-owned terminal inside your current terminal.

Availability: Linux and macOS, not native Windows.

# by agent target
herdr agent attach reviewer

# by terminal ID
herdr terminal attach term_abc123

Behaviour:

  • it streams the currently rendered terminal state first, then live ANSI frames
  • input goes straight to that terminal
  • ctrl+b q detaches
  • ctrl+b ctrl+b sends a literal ctrl+b (otherwise you can never type the prefix key itself)
  • ⚠️ only one writable direct attach client owns a terminal’s input and resize — to seize it, use --takeover:
herdr terminal attach term_abc123 --takeover

Two modes for third-party bridges#

If you only need the rendered terminal bytes, use the read-only terminal session observer:

herdr terminal session observe w1:p1 --cols 120 --rows 40
  • prints newline-delimited JSON terminal.frame records, with ANSI bytes as base64
  • prints a terminal.closed record when the server closes the stream
  • several observers can watch the same terminal at once, without occupying input, resize, scroll or takeover ownership

For an interactive bridge, use the writable terminal session controller:

herdr terminal session control w1:p1 --takeover --cols 120 --rows 40
  • prints the same newline-delimited frame records and reads newline-delimited JSON commands from stdin
  • terminal.input sends text or base64 bytes
  • terminal.resize changes the controller viewport
  • terminal.scroll scrolls the attached viewport
  • terminal.mouse sends a mouse event at a cell to an application with mouse reporting enabled
  • terminal.release closes the controller
  • at any moment only one controller owns input and resize

These two commands are the foundation of module 4, programmatic control — if you want a web status dashboard or a chat bot, start here rather than parsing a TUI.

7. How to choose: a decision table#

Your situationWhich to pick
code and credentials are all localherdr, do not bother with remote
you already work permanently inside ssh to that boxpath A (ssh + herdr), closest to your existing habit
you want local theme, keybindings and image paste on remote sessionspath B (herdr --remote)
a quick agent-status check from a phone / tabletpath C (SSH client + herdr)
local plus several remote machines in one windowherdr machine add (previous article )
you want one agent’s terminal, embedded in another toolherdr agent attach <name>
building a read-only monitoring panel / recorderherdr terminal session observe
building an interactive bot or web consoleherdr terminal session control --takeover
CI / scripts connecting remotelythe non-interactive form of path B — note it will not install the remote binary for you; missing means failure

8. Traps to avoid#

  1. To paste an image to a remote agent you must use --remote. SSH-ing in and running herdr structurally cannot read your local desktop clipboard.
  2. --remote uses local keybindings by default, not the remote ones. When “the keybindings I configured remotely do nothing” confuses you, add --remote-keybindings server. Conversely, local custom command keybindings are not sent to the remote.
  3. No detach needed after editing local keybindings. Use the UI’s reload config action.
  4. ssh-add first in non-interactive contexts. A passphrase key in a script / CI / phone terminal cannot prompt, and authentication simply fails.
  5. On authentication failure, run ssh workbox first. Splitting the problem into “SSH itself is broken” versus “it is a Herdr issue” halves the debugging time.
  6. Do not expect Herdr to auto-install the remote binary in CI. Non-interactive runs fail rather than modifying the host — correct behaviour, but it means you must pre-install in the image.
  7. You get a warning when ~/.local/bin is not on the remote PATH. Do not ignore it, or the next attach has to rediscover.
  8. Do not stop the remote server to align versions. Versions need not match; you are only asked when compatibility or detached-daemon support is missing, and the default answer is No.
  9. --handoff is experimental and machine add never uses it. Use it only when you specifically need “replace the server but keep the pane processes”.
  10. ctrl+b ctrl+b is how you emit a literal ctrl+b. Forgetting this during a direct attach makes you think the program in the pane is broken.
  11. Direct attach ownership is exclusive. A second person failing to attach is not a bug; take over deliberately with --takeover.
  12. Windows has neither direct terminal attach nor control socket reuse. Confirm this before designing cross-platform automation.

Frequently Asked Questions

What is the difference between ssh-ing in and running herdr versus herdr --remote?

In the first case Herdr runs entirely on the server and behaves like a terminal multiplexer; it cannot reach your local desktop clipboard beyond ordinary terminal text paste. With herdr --remote, the remote server owns the running panes and sends terminal content and session state over SSH, while your local Herdr draws the UI, including sidebar, menus and theme. Because the client is local, local desktop features can be bridged — for example image clipboard paste copies the image to a remote temporary file and pastes that path.

Do I need an app to use Herdr on a phone?

No mobile app and no web dashboard. Install any SSH client, connect to the machine running the agents, and start herdr there: the same persistent session opens inside your phone terminal. The TUI adapts to narrow screens, so you can inspect agents, switch workspaces and check panes. The official docs mention that moshi works well on iPhone.

Does herdr --remote use local or remote keybindings?

Your local Herdr's keybindings by default, so local muscle memory keeps working even when the remote server is configured differently. After editing local keybindings, apply them with the UI's reload config action without detaching. Use --remote-keybindings server to take the remote server's config. Note that local custom command keybindings are not sent, because those commands would run on the remote host.

Must the local and remote Herdr versions match?

No. Once both sides support the stable endpoint generation, local and remote versions do not need to match. The remote binary comes from one of three places: the current local binary can be copied on a matching Linux/macOS host; otherwise a release asset matching the current client version is downloaded from https://herdr.dev/latest.json (Homebrew/mise/Nix installs, differing platforms, or a Windows host); and for local builds or custom packages, HERDR_REMOTE_BINARY specifies the path.

What happens if Herdr is not installed on the remote?

On Linux and macOS hosts Herdr first looks for an already-compatible herdr on the remote PATH, then checks the common direct-install, Homebrew, mise and Nix profile paths; on Windows hosts it checks PATH and the active managed release. If no compatible binary exists, an interactive run offers to install or update one and a non-interactive run fails rather than modifying the host. Linux/macOS installs go to ~/.local/bin/herdr, with a warning afterwards if that directory is not on the remote PATH.

Will a mere version difference restart my remote server?

No. A version difference alone never replaces or restarts a running remote server. Remote attach asks before stopping a server only when it lacks required compatibility or detached-daemon support, and the default answer is No, because stopping ends its pane processes. Add --handoff explicitly only when you need that one-time upgrade and want to keep the pane processes.
