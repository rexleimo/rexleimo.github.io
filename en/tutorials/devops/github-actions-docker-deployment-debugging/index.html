Deploying a Docker Service with GitHub Actions: A Troubleshooting Story About SSH, Ports, and Go Versions

A sanitized deployment postmortem covering gateway port conflicts, GitHub Environment Secrets, SSH key authentication, Docker-only builds, and a Go version mismatch.

August 29, 2026 · 11 min · 2256 words · Rex Programming -  |  中文

In many tutorials, automated deployment looks like this:

git push
  ↓
GitHub Actions
  ↓
docker compose up -d
  ↓
Deployment complete

It looks like a straight highway.

Anyone who has actually done it knows that the real experience is closer to driving to an unfamiliar city. The map says twenty minutes, then the entrance is under construction, the toll booth rejects your card, and the destination turns out to have the wrong street number.

This article records a sanitized Docker deployment case. The service is called example-api and runs on a VPS that already hosts a web gateway. Project names, domains, IP addresses, usernames, paths, and credentials are fictional.

The point is not one particular application. The point is a reusable troubleshooting method: verify one layer at a time, and never confuse “it should work” with “it has been verified.”

1. Start with architecture: who owns what?#

The example server already runs three containers:

  • a WordPress container;
  • a Caddy gateway container;
  • a database container.

The existing Caddy gateway already owns host ports 80 and 443 for public HTTPS and domain routing.

If the new API project brings along another Caddy and tries to claim the same ports, Docker will be honest:

port is already allocated

The first step is therefore not writing CI/CD. It is separating responsibilities:

Existing Caddy
  ├── website.example.com → WordPress
  └── api.example.com     → example-api

example-api
  └── listens on 8080 inside its container

The API project no longer starts its own Caddy. It only starts the API container.

2. A host port and a container port are different things#

The API can continue listening on port 8080 inside the container without taking over host ports 80 or 443. Map it to a high port bound only to localhost:

services:
  api:
    build:
      context: ..
      dockerfile: deploy/Dockerfile
    restart: unless-stopped
    ports:
      - "127.0.0.1:18080:8080"

This means:

host 127.0.0.1:18080
        ↓
container port 8080

The three parts mean:

  • 127.0.0.1: only the host can access the published port;
  • 18080: the port on the host;
  • 8080: the port inside the container.

Do not assume that a container using 8080 automatically occupies host port 8080. The host is occupied only when you publish a port.

Also avoid casually writing:

- "18080:8080"

That binds 18080 on all host interfaces and may expose the API directly to the Internet. Binding to 127.0.0.1 lets the existing gateway reach the service locally while keeping the API itself off the public interface.

3. GitHub Actions should deploy the service, not build it twice#

The service lives in its own repository. The goal is simple: every push to main makes the server pull the latest code, build the image, and restart the API.

A common first draft is unnecessarily large:

Checkout repository
  ↓
Install Go
  ↓
Run tests on the GitHub Runner
  ↓
SSH to the VPS
  ↓
Pull the repository again on the VPS
  ↓
Build Docker on the VPS

If the Runner’s real job is only to tell the VPS to deploy, its checkout, Go installation, and test stage add extra failure points. The actual source of truth is the repository pulled by the VPS.

A leaner split is:

GitHub Actions
  ├── validate the deployment key
  └── SSH to the server

VPS
  ├── pull its repository
  ├── generate runtime articles or assets
  ├── build the Docker image
  └── start the container

A minimal workflow looks like this:

name: Deploy example-api

on:
  push:
    branches:
      - main
  workflow_dispatch:

concurrency:
  group: example-api-production
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    timeout-minutes: 20

    steps:
      - name: Validate deployment key
        env:
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
        run: |
          set -eu
          umask 077
          printf '%s\n' "$DEPLOY_SSH_KEY" > "$RUNNER_TEMP/deploy_key"
          ssh-keygen -y -f "$RUNNER_TEMP/deploy_key" > "$RUNNER_TEMP/deploy_key.pub"
          ssh-keygen -lf "$RUNNER_TEMP/deploy_key.pub"
          rm -f "$RUNNER_TEMP/deploy_key" "$RUNNER_TEMP/deploy_key.pub"

      - name: Deploy to VPS
        uses: appleboy/ssh-action@v1.2.0
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          script_stop: true
          command_timeout: 15m
          script: |
            set -eu
            APP_DIR=/srv/example-api
            cd "$APP_DIR"
            git fetch origin main
            git pull --ff-only origin main
            cd deploy
            docker compose build api
            docker compose run --rm api \
              /app/publish-article \
              -src /app/articles-src \
              -out /app/articles
            docker compose up -d --remove-orphans
            docker compose ps
            curl --fail --silent --show-error \
              http://127.0.0.1:18080/ >/dev/null

4. Where to configure environment variables: VPS and GitHub are separate#

This is the part that causes the most confusion. There are two different groups of configuration, stored in two different places.

4.1 Application variables on the VPS#

These variables are needed when the API container runs:

ADMIN_JWT_SECRET=a-long-production-secret
WECHAT_APP_ID=optional
WECHAT_SECRET=optional
WECHAT_MCH_ID=optional

They belong in the server’s deployment directory:

/srv/example-api/deploy/.env

Docker Compose reads them through entries such as:

environment:
  - ADMIN_JWT_SECRET=${ADMIN_JWT_SECRET:?ADMIN_JWT_SECRET is required}

This .env answers the question:

What configuration does the application need at runtime?

It must stay on the server and must not be committed to GitHub.

4.2 GitHub Actions deployment Secrets#

Open the independent service repository in GitHub, then follow this exact path:

Repository
→ Settings
→ Secrets and variables
→ Actions

There are usually two relevant areas:

Environment secrets
Repository secrets

This example uses Environment secrets:

  1. Find the Environments area and click Manage environments.

  2. Create an environment named:

    production

  3. Open the production environment.

  4. Find Environment secrets.

  5. Click Add secret or New environment secret.

  6. Create these three secrets:

    DEPLOY_HOST
DEPLOY_USER
DEPLOY_SSH_KEY
SecretValue
DEPLOY_HOSTVPS public IP or hostname, without https:// or :port
DEPLOY_USERThe Linux deployment user, for example deploy
DEPLOY_SSH_KEYThe complete private key used by GitHub Actions

The private key must include its full boundaries:

-----BEGIN OPENSSH PRIVATE KEY-----
...
-----END OPENSSH PRIVATE KEY-----

Do not enter the private-key passphrase, the VPS login password, or a .pub public-key file in DEPLOY_SSH_KEY.

4.3 The Environment name must match the YAML#

If the Secrets belong to the production environment, the workflow must contain:

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production

Without this line, GitHub may show the Secrets in the web interface while the Job receives empty values. The resulting error is often:

Error: missing server host

The references inside the workflow remain:

host: ${{ secrets.DEPLOY_HOST }}
username: ${{ secrets.DEPLOY_USER }}
key: ${{ secrets.DEPLOY_SSH_KEY }}

If you choose Repository secrets instead, the Job does not need an Environment binding. Pick one model and use it consistently.

5. Failure one: the Environment Secret exists, but Actions says there is no Host#

The first run produced:

Error: missing server host

The three names were visible in GitHub, but they had been created under an Environment that the Job did not use. The fix was not to rename the host or regenerate the key. The fix was to make the workflow and the Environment agree.

The lesson is simple:

A Secret existing in GitHub does not mean the current Job can read it. Check both the Secret scope and the Job’s Environment binding.

6. Failure two: SSH handshake failure#

After the Environment was bound, the error changed to:

ssh: handshake failed: ssh: unable to authenticate
attempted methods [none publickey]

This change was useful. It meant the Runner had reached the SSH service, but the server had rejected the public-key authentication.

The two halves must be configured like this:

GitHub Secret DEPLOY_SSH_KEY
        = private key

VPS ~/.ssh/authorized_keys
        = matching public key

For a user called deploy, the file is:

/home/deploy/.ssh/authorized_keys

The expected permissions are:

chmod 700 /home/deploy/.ssh
chmod 600 /home/deploy/.ssh/authorized_keys
chown -R deploy:deploy /home/deploy/.ssh

7. Do not guess which key is which: compare fingerprints#

File names are not proof. Public-key fingerprints turn the question into a direct comparison.

On the GitHub Runner, derive a public key from the Secret and print only its fingerprint:

printf '%s\n' "$DEPLOY_SSH_KEY" > /tmp/deploy_key
ssh-keygen -y -f /tmp/deploy_key > /tmp/deploy_key.pub
ssh-keygen -lf /tmp/deploy_key.pub

On the VPS, print the authorized-key fingerprints:

ssh-keygen -lf /home/deploy/.ssh/authorized_keys

The fingerprints must match exactly:

fingerprint derived from GitHub Secret
        =
fingerprint in authorized_keys

Two valid ED25519 keys can still be completely different keys. A frequent cause is updating the VPS with a new public key while leaving an older private key in GitHub, or editing the wrong Environment.

8. Failure three: local SSH works, but the GitHub Runner times out#

Another run produced:

dial tcp <host>:22: i/o timeout

This is different from an authentication failure:

i/o timeout       = TCP connection did not complete
authenticate error = TCP and SSH handshake completed, key was rejected

A local test such as:

nc -vz example.com 22

only proves:

your computer → VPS:22

GitHub Actions uses a different source network:

GitHub Runner → VPS:22

Check the VPS and cloud firewall:

sudo ss -ltnp | grep ':22'
sudo ufw status verbose
sudo fail2ban-client status

The SSH service should listen on a public interface, not only on 127.0.0.1. If a non-standard SSH port is used, configure it explicitly:

port: ${{ secrets.DEPLOY_PORT }}

The host value should be a plain public IP or hostname, not a URL:

203.0.113.25

9. Failure four: the VPS has no Go#

Once SSH worked, remote diagnostics stopped at:

command -v go

The VPS did not have Go installed. But this exposed a design mistake: the deployment script was running:

go run ./cmd/publish-article

on the host, even though the service was supposed to run in Docker.

The better design is for Docker to own the build environment. The VPS should need only:

Git
Docker
Docker Compose
SSH

10. Compile the publishing tool into the Docker image#

Use a multi-stage Dockerfile:

FROM golang:1.25-alpine AS builder
WORKDIR /build

COPY go.mod go.sum ./
RUN go mod download
COPY . .

RUN CGO_ENABLED=0 go build -o /app/server ./cmd/server
RUN CGO_ENABLED=0 go build -o /app/publish-article ./cmd/publish-article

FROM alpine:3.19
RUN apk add --no-cache ca-certificates
WORKDIR /app

COPY --from=builder /app/server .
COPY --from=builder /app/publish-article .
COPY migrations ./migrations

EXPOSE 8080
CMD ["./server"]

Mount the source and runtime article directories:

volumes:
  - ./data:/app/data
  - ./articles:/app/articles
  - ../articles-src:/app/articles-src:ro

The deployment then becomes:

docker compose build api

docker compose run --rm api \
  /app/publish-article \
  -src /app/articles-src \
  -out /app/articles
docker compose up -d --remove-orphans

Go exists only inside the Docker builder stage. The VPS host does not need Go.

11. Failure five: the builder’s Go version is too old#

After moving the build into Docker, another error appeared:

go.mod requires go >= 1.25.0
running go 1.24.13

The Dockerfile used:

FROM golang:1.24-alpine

while go.mod required Go 1.25 or newer. The fix was:

FROM golang:1.25-alpine AS builder

The builder image is part of the project dependency graph. Always compare:

go.mod requirement
Docker builder version
local Go version

12. Make diagnostics identify the failing layer#

Useful logs should be grouped by layer:

echo "=== remote identity ==="
whoami
id
hostname
pwd

echo "=== runtime versions ==="
command -v docker
docker --version
docker compose version

echo "=== deployment paths ==="
stat -c '%A %U:%G %n' \
  "$HOME" "$HOME/.ssh" "$HOME/.ssh/authorized_keys" \
  "$APP_DIR" "$APP_DIR/.git" 2>&1 || true

echo "=== authorized key fingerprints ==="
ssh-keygen -lf "$HOME/.ssh/authorized_keys" 2>&1 || true

echo "=== port and docker state ==="
ss -ltn 2>/dev/null | grep -E ':(22|18080)\\b' || true
docker ps

A useful error map is:

LayerTypical errorMeaning
Secret scopemissing server hostEnvironment is not bound or Secret is unavailable
SSH networki/o timeoutTCP connection did not complete
SSH authenticationunable to authenticateKey, user, or authorization mismatch
Remote runtimecommand not foundMissing command or PATH issue
Gitcould not readVPS cannot pull the repository
Composerequired variable missingServer .env is missing or empty
Docker buildgo.mod requiresBuilder image is too old
Health checkcurl --failContainer, port, or API readiness problem

The worst outcome is not a failed deployment. It is a failed deployment that only says “deployment failed.” That is like repairing a clock while blindfolded and stopping when you hear a new noise.

13. The final automated deployment loop#

The complete flow is:

Push to the independent repository
        ↓
GitHub Actions starts
        ↓
Read production Environment Secrets
        ↓
Validate the deployment-key fingerprint
        ↓
SSH into the VPS
        ↓
Enter the fixed application directory
        ↓
git fetch + git pull
        ↓
Build the Docker image
        ↓
Generate runtime articles inside a container
        ↓
docker compose up -d
        ↓
Check container status
        ↓
Check 127.0.0.1:18080
        ↓
Existing gateway proxies the public domain

The responsibilities are now clear:

Application repository
  → source code and deployment workflow

GitHub Actions
  → trigger and SSH connection

VPS
  → pull code and run Docker

Docker
  → reproducible build environment

Compose
  → container orchestration

Existing gateway
  → public 80/443 entry point

Conclusion: automation means clear boundaries#

This deployment encountered many failures:

  • gateway port conflicts;
  • Environment Secrets not visible to the Job;
  • SSH public-key authentication failures;
  • GitHub Runner network timeouts;
  • missing Go on the VPS;
  • an outdated Go version in the Docker builder.

They all pointed to the same underlying issue: the system boundaries were not explicit enough at the beginning.

Who owns ports 80 and 443? Who handles HTTPS? Who pulls the repository? Does Go run on the host or inside Docker? Where do the Secrets live? Who generates runtime article files?

If those questions are not answered in advance, the deployment system will answer them for you, usually with an error message.

Reliable CI/CD is not about stuffing more commands into YAML. It is about giving each component one clear responsibility:

GitHub Actions triggers and connects
VPS pulls and runs
Docker provides the build environment
Compose orchestrates containers
The existing gateway owns the public entry point

Once those boundaries are clear, deployment stops being an act of prayer and becomes a matter of pushing code and reading the right log.

This is a sanitized, general deployment troubleshooting record. Project names, domains, IP addresses, usernames, paths, and credentials in the examples are fictional. Never expose private keys, passwords, tokens, server addresses, or internal infrastructure details in logs, articles, or chat messages.

Frequently Asked Questions

Why does adding a new API container report the error "port is already allocated"?

Because the existing Caddy gateway has already occupied ports 80 and 443 on the host machine. If the newly added API project also includes Caddy and tries to use host ports 80/443, a port conflict occurs. The solution is to split responsibilities: the API should not start its own gateway, only start the API container, and map the container port to a high-numbered host port.

When mapping ports, what is the difference between 127.0.0.1:18080:8080 and 18080:8080?

127.0.0.1:18080:8080 only allows local access from the host to port 18080, so the API is not directly exposed to the public network. 18080:8080 listens on all network interfaces, so the API may bypass the gateway and be directly exposed to the public network. The former is recommended.

In GitHub Actions, is it necessary to first check out the code, install Go, and build?

If the workflow's only goal is to notify a VPS to deploy, then no. A simpler division of responsibilities is: GitHub Actions only verifies the deployment key and SSHes to the server; the VPS itself pulls the repository, builds the Docker image, and starts the container. This reduces time and failure points.

Where should the environment variables required by the API at runtime be placed?

Place them in the .env file in the VPS deployment directory, for example /srv/example-api/deploy/.env, and Docker Compose will read it automatically. This .env file is server production configuration and should not be committed to GitHub.

What is the difference between Environment secrets and Repository secrets? What should be noted when using Environment secrets?

If a secret is stored in Repository secrets, the workflow does not need to declare an Environment. If it is stored in Environment secrets, the workflow must bind the corresponding Environment. Both approaches work, but one project should preferably choose only one. When troubleshooting, first confirm which area the secret is in, the exact Environment name, and whether the job's environment field is written consistently.
