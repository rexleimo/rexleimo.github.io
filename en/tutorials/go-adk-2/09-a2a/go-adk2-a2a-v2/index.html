The A2A v2 server side: the Executor's nine event-mapping rules, and the Agent Card that generates itself

server/adka2a/v2 in ADK Go v2.4.0: the complete rules by which the Executor translates a session.Event into an a2a.Event (Submitted → Working → ArtifactUpdate{Append:true} → empty LastChunk → Completed/Failed/InputRequired), the two output modes OutputArtifactPerRun and OutputArtifactPerEvent, the coupling requirement between RunnerProvider and plugin installation, the exact trigger conditions of the four callbacks, why ADKExtensionURI is a metadata key rather than an Extensions.Activate call, how BuildAgentSkills derives skills from the agent tree, and the dual-protocol agent card produced by the a2a sub-launcher of the web launcher.

September 26, 2026 · 15 min · 3038 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources server/adka2a/v2/{executor.go,agent_card.go,extension.go,input_required.go,doc.go,conversions.go}, cmd/launcher/web/a2a/a2a.go, dependency github.com/a2aproject/a2a-go/v2.

1. What the package does: exactly one thing#

The package comment of server/adka2a/v2/doc.go:

Package adka2a allows exposing ADK agents via A2A.

NewExecutor returns an a2a-go AgentExecutor. To serve it over HTTP, wrap it
with a2a-go's request handler and transport-specific HTTP handler, such as
[a2asrv.NewHandler] and [a2asrv.NewJSONRPCHandler].

The layering is clean: adka2a handles only the translation from ADK events to A2A events; HTTP/JSON-RPC transport comes from the official a2a-go library. So:

executor := adka2a.NewExecutor(adka2a.ExecutorConfig{
	RunnerConfig: runner.Config{AppName: agentName, Agent: root, SessionService: sessSvc},
})
reqHandler := a2asrv.NewHandler(executor, a2aOptions...)   // a2aOptions comes from launcher.Config.A2AOptions
jsonrpc    := a2asrv.NewJSONRPCHandler(reqHandler)

That Executor satisfies the interface is a compile-time guarantee (the source contains var _ a2asrv.AgentExecutor = (*Executor)(nil)), and the entry point is:

func (e *Executor) Execute(ctx context.Context, execCtx *a2asrv.ExecutorContext) iter.Seq2[a2a.Event, error]

iter.Seq2 again — A2A streaming and ADK’s internal event stream use the same iterator idiom; no channels involved.

2. The event mapping contract (nine rules, quoted from the type comment)#

Executor invokes an ADK agent and translates session.Events to a2a.Events
according to the following rules:
 - If the input doesn't reference any a2a.Task, produce a Task with TaskStateSubmitted state.
 - Right before runner.Runner invocation, produce TaskStatusUpdateEvent with TaskStateWorking.
 - For every session.Event produce a TaskArtifactUpdateEvent{Append=true} with transformed parts.
 - After the last session.Event is processed produce an empty TaskArtifactUpdateEvent{Append=true}
   with LastChunk=true, if at least one artifact update was produced during the run.
 - If there was an LLMResponse with non-zero error code, produce a TaskStatusUpdateEvent with
   TaskStateFailed. Else if there was an LLMResponse with long-running tool invocation, produce a
   TaskStatusUpdateEvent with TaskStateInputRequired. Else produce a TaskStatusUpdateEvent with
   TaskStateCompleted.

Laid out as a timeline (this is the only map that helps when debugging cross-language problems):

#A2A eventState/flagWhen
1TaskSubmittedwhen the input references no existing task
2TaskStatusUpdateEventWorkingimmediately before runner.Run
3TaskArtifactUpdateEventAppend=trueone per session.Event (with transformed parts)
4TaskArtifactUpdateEventAppend=true, LastChunk=true (empty body)after the last event is processed, and only if the run produced at least one artifact
5TaskStatusUpdateEventFailedsome LLMResponse has a non-zero error code
6TaskStatusUpdateEventInputRequiredsome LLMResponse carries a long-running tool invocation
7TaskStatusUpdateEventCompletednone of the above

Three conclusions that must be derived from the mapping rules:

  1. The InputRequired test is “a long-running tool invocation”, not Event.RequestedInput. That is: module 5’s HITL (adk_request_input) and module 3’s tool confirmation (adk_request_confirmation) both appear on the A2A side as “a long-running tool has not come back” — because NewRequestInputEvent really does write ev.LongRunningToolIDs = []string{req.InterruptID} (module 5 article 5, step ④). Two pause protocols converge into one at the A2A boundary.
  2. Rule 3 says “every session.Event” → combined with module 7’s streaming, partial events each emit an artifact update too (Append=true is naturally incremental).
  3. The closing LastChunk is an “empty event”, present only when artifacts were produced. A client must not read “received LastChunk” as “there was definitely content”.

3. OutputMode: one artifact or many#

const (
	// OutputArtifactPerRun produces a single artifact per runner.Runner.Run.
	OutputArtifactPerRun OutputMode = "artifact-per-run"
	// OutputArtifactPerEvent produces an artifact per non-partial session.Event.
	// While agent is emitting events an artifact is build incrementally (parts are append to it).
	// The next partial event replaces accumulated contents and seals the artifact, meaning
	// the next event from this agent will create a new artifact.
	OutputArtifactPerEvent OutputMode = "artifact-per-event"
)
default artifact-per-runartifact-per-event
artifact count1 for the whole runone per non-partial event
incrementalityparts keep being appendedappend to the current artifact; a partial event replaces the accumulated content and seals it
semantics“this run’s answer”“what each agent said”
fitssingle agent, final answer onlymulti-agent collaboration, graph workflows that must keep stage boundaries

⚠️ The per-event line “The next partial event replaces accumulated contents and seals the artifact” has a counter-intuitive consequence: a partial event is a seal, not an append. Streaming a graph gives you “a new artifact cut every time a fragment begins”, and the count can far exceed the number of agents. Do not infer the agent count from the artifact count.

4. ExecutorConfig: what each of the nine fields is for#

type ExecutorConfig struct {
	RunnerConfig              runner.Config      // used by the default provider to call runner.New; ignored when RunnerProvider is set
	RunnerProvider            RunnerProvider     // controls how the runner is built (one per request)
	RunConfig                 agent.RunConfig    // configuration passed to runner.Run
	BeforeExecuteCallback     BeforeExecuteCallback
	AfterEventCallback        AfterEventCallback
	AfterExecuteCallback      AfterExecuteCallback
	A2APartConverter          A2APartConverter   // A2A part → genai.Part
	GenAIPartConverter        GenAIPartConverter // genai.Part → A2A part
	OutputMode                OutputMode         // default artifact-per-run
	A2AExecutionCleanupCallback A2AExecutionCleanupCallback
}

RunnerProvider: the one hard constraint#

type Runner interface {
	Run(ctx context.Context, userID, sessionID string, msg *genai.Content, cfg agent.RunConfig) iter.Seq2[*session.Event, error]
}
type RunnerProvider func(ctx context.Context, reqCtx *a2asrv.ExecutorContext, plugin *plugin.Plugin) (RunnerConfig, Runner, error)

The sentence in the comment is a hard requirement: “The provided plugin must be installed in the returned Runner for callbacks taking ExecutorContext to work correctly.”

Meaning: with a custom RunnerProvider you must install the plugin you were handed into your Runner (runner.Config.PluginConfig), otherwise AfterEventCallback / AfterExecuteCallback / A2AExecutionCleanupCallback cannot obtain the ExecutorContext — no error, the context is simply empty. This is the quietest way to break things in this whole article.

RunnerConfig (the small struct the provider returns) holds only three things as well: AppName (used for both the session key and the A2A event metadata) and Agent (the root agent).

Note that the Run signature on the Runner interface has no opts ...RunOption — a custom provider cannot use runner.WithStateDelta / WithYieldUserMessage (mentioned in module 4). To inject a state delta on the A2A surface, go through BeforeExecuteCallback to modify ctx, or extend it yourself.

The trigger conditions of the four callbacks (stated precisely in the comments)#

type BeforeExecuteCallback   func(ctx context.Context, reqCtx *a2asrv.ExecutorContext) (context.Context, error)
type AfterEventCallback      func(ctx ExecutorContext, event *session.Event, processed *a2a.TaskArtifactUpdateEvent) error
type AfterExecuteCallback    func(ctx ExecutorContext, finalEvent *a2a.TaskStatusUpdateEvent, err error) error
type A2AExecutionCleanupCallback func(ctx context.Context, reqCtx *a2asrv.ExecutorContext, subAgentCards []*a2a.AgentCard, result a2a.SendMessageResult, cause error)
CallbackWhenWhat you can doCaveats
BeforeExecuteCallbackbefore execution startsshape the ctx, or return an error to block the execution outrightthe return value replaces ctx, so it is a good place to inject tenant information
AfterEventCallbackafter one event converts successfullyadd metadata to the event; returning an error aborts the runthe comment is explicit: ADK’s own errors and event-handling errors do not reach this callback (those become TaskStateFailed); to intercept such errors use AfterExecuteCallback
AfterExecuteCallbackonce execution settles on completed/failedadd metadata, logit receives the terminal event plus err; this is the audit point
A2AExecutionCleanupCallbackafter execution or cancellation ends (failures included)cleanupwhen not supplied, the default behaviour is to log the failure reason; the subAgentCards parameter shows it is also the sub-agent resource release point

AfterEventCallback receives the converted *a2a.TaskArtifactUpdateEvent; mutating it does not affect the ADK-side session.Event (which is only there as the second argument for reference).

Custom part converters#

// Implementations should generally remember to leverage adka2a.ToGenAiPart for default conversions
// nil returns are considered intentionally dropped parts.
type A2APartConverter func(ctx context.Context, a2aEvent a2a.Event, part *a2a.Part) (*genai.Part, error)
type GenAIPartConverter func(ctx context.Context, adkEvent *session.Event, part *genai.Part) (*a2a.Part, error)

A nil return means the part was dropped intentionally, not an error. Custom types (say turning an internal widget part into an A2A data part) belong here — but remember to fall back to ToGenAiPart/ToA2APart on every other branch, or you will swallow the types you did not mean to touch.

5. ADKExtensionURI: a cross-language incident fixed by one metadata key#

This is the most valuable comment I found in v2.4.0; unpacked line by line:

// ADKExtensionURI identifies the ADK A2A integration extension.
//
// [Executor] writes it as a metadata key on every task and task status update
// it emits. The key tells a client that the payload follows ADK conventions:
// content is spread across task artifacts and the status message, with
// long-running function calls carried by the latter.
//
// A client that does not find the key may assume artifacts hold the whole
// response. An ADK Python client does exactly that, and consequently misses the
// long-running function call of an input-required task, synthesizing a
// mock_function_call_for_required_user_input in its place. See
// https://github.com/google/adk-go/issues/913.
//
// The key is metadata rather than an [a2asrv.Extensions.Activate] call because
// activation is reported through the X-A2A-Extensions response header, which an
// ADK Python client does not read. Declaring the extension in an
// [a2a.AgentCard] is not a substitute either: the card describes an agent
// before a request, and clients pick how to read a response from the response
// itself.
const ADKExtensionURI = "https://google.github.io/adk-docs/a2a/a2a-extension/"

Four layers of information:

  1. ADK responses are inherently scattered: the body lives in artifacts, long-running function calls in the status message. A standard A2A client defaults to “artifacts are everything”, so it loses the function call needed by input-required and degrades to mock_function_call_for_required_user_input (issue #913).
  2. This key is the “also read the status message” signal, written onto the metadata of every Task and TaskStatusUpdateEvent.
  3. Why not standard extension negotiation (Extensions.Activate): activation is reported through the X-A2A-Extensions response header, and the adk-python client does not read that header.
  4. Why declaring it in the agent card is not enough either: the card describes an agent before a request, while clients decide how to read a response from the response itself.

There is also a precision requirement in the implementation:

// Only tasks and task status updates qualify: a2a merges status update metadata
// into the task, while artifact update metadata is merged into the artifact.
func addADKExtensionMeta(event a2a.Event) {
	switch v := event.(type) {
	case *a2a.Task:                 v.Metadata = metaWithADKExtension(v.Metadata)
	case *a2a.TaskStatusUpdateEvent: v.Metadata = metaWithADKExtension(v.Metadata)
	}
}

Only these two event types have metadata that reaches a place clients can read (a2a merges status-update metadata into the task; artifact-update metadata only lands in the artifact). So when you write your own conversion layer, do not expect metadata on artifacts to be visible to a generic client.

The first action of Execute is yield = withADKExtensionMeta(yield) — it wraps the downstream yield, so every outgoing event carries the key.

The agent card declares it too (next section): both sides carry it, but what a client actually reads is the one in the response.

5.5. Identity mapping: ContextID is the sessionID#

toInvocationMeta in server/adka2a/v2/metadata.go defines how an A2A request maps onto ADK’s (user, session):

userID, sessionID := "A2A_USER_"+reqCtx.ContextID, reqCtx.ContextID

// a2a sdk attaches authn info to the call context, use it when provided
if callCtx, ok := a2asrv.CallContextFrom(ctx); ok {
	if callCtx.User != nil && callCtx.User.Name != "" {
		userID = callCtx.User.Name
	}
}

meta := map[string]any{
	ToA2AMetaKey("app_name"):   config.AppName,
	ToA2AMetaKey("user_id"):    userID,
	ToA2AMetaKey("session_id"): sessionID,
}

Four points:

  1. sessionID = the peer’s ContextID — session continuity is entirely controlled by the client. The same ContextID is the same session (so module 4’s multi-turn memory holds automatically).
  2. userID defaults to a synthesis: "A2A_USER_" + ContextID, not a real user. It is an isolation prefix, not an identity.
  3. With authentication the authenticated principal overrides it: a2a-go attaches authn info to the CallContext, and callCtx.User.Name wins when non-empty. So whether userID can be trusted depends on whether you configured A2A authentication (launcher.Config.A2AOptions).
  4. These three values (app_name / user_id / session_id) are written back onto every event as adk_* metadata — during cross-language packet capture they are how you locate a session.

toEventMeta additionally attaches (each only when non-empty):

for k, v := range map[string]string{
	"invocation_id": event.InvocationID,
	"author":        event.Author,
	"branch":        event.Branch,
} { if v != "" { result[ToA2AMetaKey(k)] = v } }
// plus: citations / grounding / usage / custom_metadata / error_code

⚠️ branch and custom_metadata cross the wire — the two easiest data exits to overlook; the security implications are in article 2, section 9 .

6. The agent card the launcher generates#

SetupSubrouters in cmd/launcher/web/a2a builds it directly (this is what your production /agent-card.json serves):

rootAgent := config.AgentLoader.RootAgent()
agentCard := &a2acore.AgentCard{
	Name:               rootAgent.Name(),
	Description:        rootAgent.Description(),
	DefaultInputModes:  []string{"text/plain"},
	DefaultOutputModes: []string{"text/plain"},
	SupportedInterfaces: []*a2acore.AgentInterface{
		{URL: publicURL,      ProtocolBinding: a2acore.TransportProtocolJSONRPC, ProtocolVersion: a2acore.Version},
		{URL: publicCompatURL, ProtocolBinding: a2acore.TransportProtocolJSONRPC, ProtocolVersion: a2av0.Version},
	},
	Version:        "2.0.0",
	Skills:         adka2a.BuildAgentSkills(rootAgent),
	Capabilities: a2acore.AgentCapabilities{
		Streaming: true,
		Extensions: []a2acore.AgentExtension{{
			URI: adka2a.ADKExtensionURI,
			Description: "Content is spread across task artifacts and the status message, which carries long-running function calls.",
		}},
	},
}

Six points:

  1. Two interfaces, two protocol versions: one for the current A2A version (a2acore.Version), one for v0 compatibility (a2av0.Version), mounted at apiPath and compatAPIPath respectively:

    router.Handle(apiPath,        a2asrv.NewJSONRPCHandler(reqHandler))
router.Handle(compatAPIPath,  a2av0.NewJSONRPCHandler(reqHandler))
router.Handle(a2asrv.WellKnownAgentCardPath, a2asrv.NewAgentCardHandler(compatProducer))

    One executor serving two protocol versions, so legacy clients can connect too.

  2. Version: "2.0.0" is a hard-coded string (the card’s version, not the module version).

  3. Input and output modes default to text/plain only — if you want peers to send you images or audio, either rewrite the card with your own producer, or be aware this declaration influences what the peer chooses to send.

  4. Streaming: true.

  5. Skills are derived from the agent tree by BuildAgentSkills(rootAgent):

    func BuildAgentSkills(agent agent.Agent) []a2a.AgentSkill {
    return slices.Concat(buildPrimarySkills(agent), buildSubAgentSkills(agent))
}

    The primary agent plus each sub-agent contributes skills, so your agent hierarchy leaks to the outside world through the agent card (including every layer’s Description). Look at the card before exposing it.

  6. A related detail: the description text undergoes person rewriting ("You are" → "I am", "your" → "my"), because an agent’s Description is written as instructions to the model while the card must read as a self-introduction to outsiders.

7. Validated at startup: the compaction dry-run#

The first thing the a2a sub-launcher does is refuse an unservable compaction configuration:

// Refuse a compaction config this surface cannot serve, before it serves
// anything. A config can pass its own shape check and still be unservable,
// the plainest case being no Summarizer over a root agent with no model to
// default to, and without this the process starts healthy and then fails
// every request. The other surfaces do the same dry run.
if err := compactionvalidate.AgainstRootAgent(config.Compaction, config.AgentLoader.RootAgent(), runner.Config{…}); err != nil {
	return err
}

“Passes its own shape check” ≠ “can be served for this agent” — the plainest broken configuration: Config.Validate() succeeds (the shape is legal) but you supplied no Summarizer and the root agent has no default model to fall back on. This dry-run makes the process fail at startup instead of “start healthy, then fail every request”.

Module 8 showed the triggers surface doing the same validation (AgainstAgents) — all four surfaces (web/api/a2a/triggers) do a dry run, which is a deliberate consistency design in ADK Go v2.4.0, and your own entry points should do the same.

8. HandleInputRequired: routing the peer’s answer back to the function call#

// HandleInputRequired checks if the input message contains responses to all function calls
// … If a non-nil event is returned the invoking code needs to use the event as the result
// of the execution
func HandleInputRequired(reqCtx *a2asrv.ExecutorContext, content *genai.Content) (*a2a.TaskStatusUpdateEvent, error)

The comment contains one more detail that affects your event stream:

If a part was incorporated into the final task status update the original event
is modified to not include it,

A part absorbed into the status message is removed from the original event (so the same content does not appear twice, once in an artifact and once in the status message). So during debugging, “present on the ADK side, absent from the A2A artifact” is not necessarily a bug — it may have been moved here.

“Responses to all function calls are required” matters a lot for clients: if one input-required holds two pending calls (say a tool confirmation plus a business input), answering only one counts as unmet. Module 5’s “at most one RequestedInput per activation” helps here, but tool confirmation and input requests are two separate systems and can still coexist.

9. Getting started and verifying#

# start the service
go run ./myagent web api a2a

# inspect the card (path comes from a2asrv.WellKnownAgentCardPath)
curl -s localhost:8080/api/.well-known/agent-card.json | jq '.name, .version, .capabilities, (.supportedInterfaces|length), (.skills|length)'

# the two invoke endpoints (both under -path_prefix, default /api)
#   POST /api/a2a/v1/invoke   ← apiPath, the current A2A protocol version
#   POST /api/a2a/invoke      ← compatAPIPath, v0 compatibility

Two constants in the source:

const apiPath = "/a2a/v1/invoke"
const compatAPIPath = "/a2a/invoke"

Then check whether the response metadata carries the extension key (section 5):

curl -s ... | jq '.result.status.message.parts'
curl -s ... | jq '.result.metadata'

Only when "https://google.github.io/adk-docs/a2a/a2a-extension/" appears in the task / status metadata does the peer have a chance to read long-running function calls correctly.

Checklist#

  • OutputMode chosen deliberately, and artifact counts interpreted through it
  • a custom RunnerProvider installs the passed-in plugin into the Runner
  • “ADK’s own errors” are intercepted with AfterExecuteCallback, not AfterEventCallback
  • custom part converters fall back to ToGenAiPart/ToA2APart, and nil is understood as “drop”
  • confirmed the client reads ADKExtensionURI from task metadata (otherwise input-required degrades to a mock call)
  • agent card inspected before exposure: BuildAgentSkills publishes the sub-agent structure
  • input/output modes match reality (the default is text/plain only)
  • the startup path keeps the compaction dry-run; refuse to serve rather than fail every request
  • one input-required answer covers all pending function calls

For the client side (calling someone else’s A2A agent, and the cross-language trust boundary) see article 2: the A2A client and cross-language interop .

Frequently Asked Questions

How does ADK Go expose an agent as an A2A service?

Two routes. The easy one adds the a2a keyword to the web launcher (go run ./myagent web api a2a), which builds the executor, agent card and JSONRPC handler for you. For anything custom, call adka2a.NewExecutor(adka2a.ExecutorConfig{RunnerConfig: runner.Config{…}}) and wrap it yourself with a2asrv.NewHandler / NewJSONRPCHandler.

How many events does one agent run produce on the A2A side?

With the default artifact-per-run: one Submitted Task, one Working TaskStatusUpdateEvent, one TaskArtifactUpdateEvent{Append:true} per session.Event, plus an empty LastChunk=true if the run produced any artifact, and finally Completed / Failed / InputRequired as appropriate.

How do I choose between OutputArtifactPerEvent and OutputArtifactPerRun?

The default is per-run (one artifact for the whole run). Per-event emits one artifact per non-partial session.Event, and when a partial event arrives it replaces the accumulated content and seals the artifact — use it in multi-agent collaboration to distinguish who said what.

Why can't my A2A client see long-running function calls?

Check whether the ADKExtensionURI key is in the task metadata. It signals that content is spread across artifacts and the status message; a client that does not find the key (such as the current adk-python) assumes artifacts are the whole response and therefore misses the long-running function call of an input-required task.

Can the A2A surface enable context compaction?

You can configure it, but startup performs a dry-run validation: if compactionvalidate.AgainstRootAgent fails, the process refuses to start. The reason is that a configuration passing its own shape check can still be unservable, most often no Summarizer and a root agent with no default model.

Do I have to write the skills in the agent card by hand?

Not on the launcher route: it calls adka2a.BuildAgentSkills(rootAgent) and derives them from the agent tree (the agent plus its sub-agents). You only fill them in when you write the card yourself.
