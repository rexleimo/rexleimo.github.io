2.x Project Layout and go.mod Conventions: Making an ADK Go Project Maintainable by a Team

Directory conventions for the ADK Go v2.4.0 era, go.mod and toolchain pinning, using go.work during v1/v2 coexistence, standalone submodules (plugin/agentanalytics), how to split graphs and tools into packages, testdata goldenfiles, and CI conventions.

September 26, 2026 · 8 min · 1687 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0 · Go 1.27.1

A working environment only proves “this one machine of yours runs”. What this article wants is someone else cloning it and running within five minutes, CI building within three, and nobody needing to remember why it was written this way in six months.

2.x affects structure more than 1.x did: there is now a graph engine (workflow), a registry and security layer (agentregistry/auth/authn/authz), and compaction (session/compaction). Without constraints, all of it ends up growing inside the same main.go.

Recommended layout (mid-sized application)#

myagent/
├── cmd/
│   └── agent/
│       └── main.go              # does exactly one thing: read config → assemble → Execute(ctx, cfg, os.Args[1:])
├── internal/
│   ├── agents/                  # LlmAgent definitions, one agent per file
│   │   ├── coordinator.go       #   Mode: llmagent.ModeChat (default, root)
│   │   ├── weather.go           #   Mode: llmagent.ModeSingleTurn
│   │   └── booking.go           #   Mode: llmagent.ModeTask + InputSchema/OutputSchema
│   ├── graph/                   # graph topology: nodes + edges, no business logic
│   │   ├── research.go          #   AddFanOut / NewJoinNode / AddFanIn
│   │   └── routing.go           #   StringRoute / IntRoute / MultiRoute
│   ├── tools/                   # functiontool / MCP toolset / skill directories
│   ├── store/                   # construction and migration of session/artifact/memory services
│   ├── platformx/               # custom platform providers (deterministic time/UUID, tests and replay only)
│   └── config/                  # config struct + validation (credentials, model name, timeouts, compaction)
├── testdata/
│   ├── golden/                  # event sequence snapshots (.events.json / .events.yaml)
│   └── skills/                  # SKILL.md samples used by SkillToolset
├── deploy/
│   ├── Dockerfile
│   └── cloudrun.tf | agentengine.yaml
├── .env.example
├── go.work                      # only needed during migration or in a monorepo; see below
├── go.mod
└── go.sum

Three hard rules:

  1. main.go contains no agent logic. Its job ends at “fill in launcher.Config and call Execute”. The reason is practical: once logic lives in main, you cannot swap the SessionService or inject a platform provider in tests.
  2. Keep topology separate from node implementations. internal/graph/ describes only “who connects to whom, under which routing condition”; node functions belong in internal/agents/ or internal/tools/. 2.x’s workflow.EdgeBuilder makes topology very thin, and when it is mixed with implementation you lose sight of a change’s blast radius.
  3. internal/, not pkg/ — unless you genuinely intend for others to import your agent definitions, which is the agentregistry road (see module 10).

go.mod conventions#

module github.com/yourorg/myagent

go 1.27.1

require (
	github.com/joho/godotenv v1.5.1
	google.golang.org/adk/v2 v2.4.0
	google.golang.org/genai v1.xx.x
)

The important points:

ConventionReason
write the go directive as a full version (1.27.1, not 1.27.0/1.26)ADK’s floor is 1.26.6; a lower value collides with the stdversion vet check added in Go 1.27 during go test
pin the ADK dependency, never @latestupstream ships a 2.x minor every 4-6 weeks (v2.1→v2.4 took only 7 weeks), and behaviour changes
run go list -m -u all every two weeks to see if a new v2.x landeddo not discover v2.5.0 only after something breaks
upgrades go in their own PR, with the version number in the descriptiongo version -m traces a production binary back, and the PR record explains why it was bumped
after a production build, record it: go version -m ./agent > build-info.txtthe first question during an incident is always “which version is actually running”

Upstream has a standalone submodule you must fetch separately: in the v2.4.0 tree, plugin/agentanalytics carries its own go.mod (plugin/agentanalytics/go.mod), so it is not in the main module’s package set:

go get google.golang.org/adk/v2/plugin/agentanalytics@v2.4.0

The first go build will also pull google.golang.org/adk (the 1.x path) into the module cache — this is normal, not your mistake: 1.x is the main module, and several of /v2’s internal and toolchain dependencies still resolve through it. Do not add exclude to make things “look clean”; that only produces harder-to-diagnose problems.

The v1/v2 coexistence window: two approaches#

Because google.golang.org/adk and google.golang.org/adk/v2 are two modules, a single go.mod can require both at once. That is what makes package-by-package canary migration possible (details in the migration article ).

Approach A: coexist inside one module (recommended while converting)

require (
	google.golang.org/adk   v1.7.0   // older packages not yet migrated
	google.golang.org/adk/v2 v2.4.0  // newly written packages
)

The discipline required: one package uses one line only, and never mix the two type systems in a single file (agent.Context is a different type on each line, so mixing fails compilation immediately — which is a good thing, the compiler is checking for you). Once migration completes, delete the old require and run go mod tidy.

Approach B: go.work (monorepo, or when you need a local fork of upstream)

go 1.27.1

use (
	./apps/customer-agent     // on /v2
	./libs/legacy-router      // still on /v1
	../internal/adk-fork      // added only when debugging against local sources
)

go.work should be committed, but CI must not depend on it (CI runs with GOWORK=off to verify that “a standalone clone still builds”). This discipline catches “compiles only on my machine” problems early.

Multiple agents and choosing a loader#

v2.4.0’s agent/loader.go offers two (its comments still carry a TODO about moving them to a better home, so do not treat loader internals as stable API):

// a single root agent
loader := agent.NewSingleLoader(rootAgent)

// one root plus several others (switchable in the Dev UI, loaded by name)
loader, err := agent.NewMultiLoader(rootAgent, subAgentA, subAgentB)

Interface surface: ListAgents() []string, LoadAgent(name string) (Agent, error), RootAgent() Agent.

The decision rule is simple: do you need to serve several independently conversable agents in one process. If yes, use NewMultiLoader and treat agent names as a routing key (together with the web/api endpoints in launcher.Config). If it is just “one root plus some SubAgents”, NewSingleLoader is enough — and note that SubAgents are not loaders; do not conflate the two.

launcher.Config is your assembly manifest#

In 2.x’s cmd/launcher/launcher.go, the fields of Config are the complete set of runtime capability switches:

config := &launcher.Config{
	AgentLoader:      agent.NewSingleLoader(root),
	SessionService:   ss,          // session.InMemoryService() | session/database | session/vertexai
	ArtifactService:  as,          // artifact | artifact/gcsartifact
	MemoryService:    ms,          // memory | memory/vertexai
	A2AOptions:       []a2asrv.RequestHandlerOption{ /* ... */ },
	PluginConfig:     pc,          // runner.PluginConfig
	TelemetryOptions: []telemetry.Option{ /* ... */ },
	Authenticator:    authn.NewNoop(),       // nil = Noop; when non-nil it authenticates restapi endpoints, rejecting with 401
	Authorizer:       authz.NewStrict(),     // nil = authz.NewNoop(); Strict provides CanActAsUser(ctx, userID)
	Compaction:       nil,                   // process-wide! nil = disabled
}

Two fields that must have a place reserved in your structure from day one:

  • Authenticator / Authorizer: the security layer defaults to wide open (authn.NewNoop() / authz.NewNoop()). server/authn ships three provider implementations: header.go (headers from a reverse proxy), iap.go (Google IAP), custom.go (bring your own); server/authz offers only NewNoop() and NewStrict(), the latter exposing CanActAsUser(ctx, userID) (may the caller act as that user). This is not a “we’ll do it later” field — install a provider in week one of a new project, or every endpoint other than /health and /version is bare.
  • Compaction: the official comment states it is a process-level setting — when one launcher serves several applications through its agent loader, they share the same compaction configuration and the same Summarizer instance, meaning the same model. If two workloads need different compaction policies, or must not share a summarizer, you have to split the process. That constraint decides your deployment-unit granularity; it is an architectural decision, not a config item.

Configuration and credentials#

type Config struct {
	ModelName   string        // "gemini-flash-latest"
	Location    string
	Timeout     time.Duration // node-level default
	GeminiKey   string        // or rely on Vertex ADC
	UseVertex   bool
}

func Load() (Config, error) { /* read env → validate → return */ }

The convention: credentials come only from environment variables, and the config struct is assembled and validated once in main. Never let os.Getenv calls scatter through agent definitions. The reason: switches like GOOGLE_GENAI_USE_VERTEXAI will inevitably be missed during an environment switch if they are spread around.

The goldenfile point deserves emphasis: the graph-engine refactor (module 5) will almost certainly change your event sequence, and without a baseline snapshot you cannot tell “an expected structural change” apart from “a regression bug”.

CI conventions#

# .github/workflows/ci.yml
image: golang:1.27.1
env:
  GOTOOLCHAIN: go1.27.1+auto    # pinned, predictable behaviour
  GOWORK: off                    # no "compiles only on my machine"
cache:
  paths: ['${{ env.GOMODCACHE }}']
steps:
  - run: go vet ./...
  - run: go test -race -count=1 ./...
  - run: go test -tags=integration -count=1 ./...   # needs credentials, main branch only
  - run: go build -trimpath -o agent ./cmd/agent
  - run: go version -m ./agent > build-info.txt

Frequently Asked Questions

What directory layout do you recommend for an ADK Go project?

cmd/ for entry points, internal/agents/ for LlmAgent definitions, internal/tools/ for function tools, internal/graph/ for topology, internal/store/ wrapping the session/artifact/memory services, and testdata/ for event goldenfiles and skill assets.

Can v1 and v2 coexist in the same repository?

Yes, because they are different module paths (google.golang.org/adk and google.golang.org/adk/v2). During migration you can roll out package by package; use go.work for cross-module joint development.

Why does the agentanalytics plugin need its own go get?

Because plugin/agentanalytics is a submodule with its own go.mod upstream, so it is not part of the main module's package set.

How do I switch between one root agent and several agents?

launcher.Config.AgentLoader takes agent.NewSingleLoader(a) for one root, or agent.NewMultiLoader(root, others...) for multiple roots/agents loaded by name.

What should I watch for when publishing my own ADK wrapper?

If your library is released as major version 2, its module path must also carry /v2, and the go directive in go.mod must not be lower than what your dependency requires (go 1.26.6 for ADK v2.4.0).
