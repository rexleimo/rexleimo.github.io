Capstone: stitching ten modules into one shippable image-intelligence agent

End-to-end delivery on ADK Go v2.4.0: a fetch → analyse → human-approval pipeline agent built with workflowagent plus Chain, a FunctionNode for the deterministic fetch, an AgentNode carrying an llmagent, a DynamicNode with ResumeOrRequestInput for HITL, RetryConfig for backoff, OutputKey to pass the brief, a postgres session service for persistence, loggingplugin and retryandreflect for cross-cutting concerns, telemetry.New for observability, universal.NewLauncher with authn.NewIdentityAwareProxy and authz.NewStrict for the web surface, and adkgo deploy cloudrun to publish it. All code passes go build and go vet.

September 26, 2026 · 13 min · 2711 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0 + Go 1.26.8. Every Go fragment in this article really passes go build ./... and go vet ./... (zero errors, zero warnings) — the promise made in module 0.

This article introduces no new API. It does one thing: turn the decisions from the previous ten modules into a single program, and explain why each part is shaped as it is. The target shape:

fetch (deterministic) → analyse (model) → human approval (HITL)
     ↓ RetryConfig backoff     ↓ ResumeOrRequestInput
  postgres session persistence ←  OutputKey carries the brief
     ↓
 loggingplugin + retryandreflect cross-cutting  +  telemetry export
     ↓
 universal.NewLauncher(api + webui) + IAP authn + Strict authz
     ↓
 adkgo deploy cloudrun

1. go.mod and dependencies (module 1)#

module intel

require (
	github.com/google/jsonschema-go v0.4.3

The /v2 is mandatory (module 0). jsonschema-go appears here because of the HITL response schema below.

2. Domain types: the edges of the graph are these types flowing (module 5)#

type Raw struct {
	Sources []string `json:"sources"`
	Items   []string `json:"items"`
}

type gateIn struct {
	Summary string `json:"summary"`
}

type Approved struct {
	Approved bool   `json:"approved"`
	Note     string `json:"note,omitempty"`
}

Why gateIn has only one field, Summary: analyzer writes its result into state with OutputKey: "brief/summary" (module 4), and the engine assembles the input of the downstream human_gate from state according to the schema. A small declared schema is a constraint surface for the model and a contract for the reader (module 6, article 2).

3. The deterministic node: fetching is not handed to the model (module 5’s first principle)#

func fetchFeeds(ctx agent.Context, in Raw) (Raw, error) {
	in.Items = append(in.Items, in.Sources...)
	return in, nil
}

fetchNode := workflow.NewFunctionNode[Raw, Raw]("fetch", fetchFeeds, workflow.NodeConfig{
	RetryConfig: &workflow.RetryConfig{MaxAttempts: 3, InitialDelay: time.Second},
})

Three decisions:

DecisionReason
NewFunctionNode (not tool + llmagent)fetching must happen; no model is needed to decide “should I fetch”. Module 5: certain steps get nodes
the generic parameters [Raw, Raw]input and output types are written straight into the function signature, and the engine derives the schema from them
RetryConfig{MaxAttempts: 3, InitialDelay: 1s}the field is MaxAttempts (including the first execution), not MaxRetries — the trap from module 5 article 4. BackoffFactor/Jitter/MaxDelay/ShouldRetry are also tunable

A functiontool is deliberately kept as an opening for “let the model decide which source to pull”:

pullTool, err := functiontool.New(functiontool.Config{
	Name: "pull_feeds", Description: "Pull raw items by source",
}, func(c agent.Context, in Raw) (Raw, error) { return fetchFeeds(c, in) })
if err != nil {
	return nil, fmt.Errorf("tool: %w", err)
}

functiontool.New returns an error (module 3), so it must be handled here.

4. The model node: give the model only that one uncertain job (modules 2 + 6)#

m, err := gemini.NewModel(ctx, "gemini-flash-latest", nil)
// …
analyzer, err := llmagent.New(llmagent.Config{
	Name: "analyzer", Model: m,
	Description: "Extract conclusions and risks from raw items",
	OutputKey:   "brief/summary",
})
// …
analyzeNode, err := workflow.NewAgentNode(analyzer, workflow.NodeConfig{
	RetryConfig: &workflow.RetryConfig{MaxAttempts: 2},
})

Four points:

  1. gemini.NewModel(ctx, name, cfg) is the v2 constructor (module 0: agents.NewLlm is gone); it returns (model.LLM, error).
  2. Name is the tool name visible to the model (module 6, article 2), so analyzer must be chosen as “an identifier the model reads”.
  3. Description is the tool description — write “extract conclusions and risks from raw items” rather than “analyse”, because it doubles as a hint about when to call it.
  4. OutputKey: "brief/summary": module 4’s standard way of landing an agent result in state. State keys use a prefix/name hierarchy, which avoids collisions when several agents cooperate.

⚠️ I deliberately left Mode out of llmagent.Config — the IncludeContents asymmetry from module 6 article 2 (as a single-turn node, unset behaves differently from an explicit IncludeContentsDefault) is a live example right here: for an agent used as a graph node, either write Mode: llmagent.ModeSingleTurn explicitly, or know that unset means it only sees the current turn. This design relies on InputSchema-driven structured input, so unset is acceptable — but write the comment down.

5. The HITL node: a one-line pause (module 5, article 5)#

func approvalSchema() *jsonschema.Schema {
	s, err := jsonschema.For[Approved](nil)
	if err != nil {
		panic(err) // a static type, so it fails at startup
	}
	return s
}

func humanGate(ctx agent.Context, in gateIn, emit func(*session.Event) error) (Approved, error) {
	var out Approved
	val, err := workflow.ResumeOrRequestInput(ctx, emit, session.RequestInput{
		Message:        "Approve this brief for publication?",
		ResponseSchema: approvalSchema(),
		Payload:        map[string]any{"summary": in.Summary},
	})
	if err != nil {
		return out, err // ErrNodeInterrupted, or an emit failure
	}
	raw, _ := json.Marshal(val)
	_ = json.Unmarshal(raw, &out)
	return out, nil
}

gateNode := workflow.NewDynamicNode[gateIn, Approved]("human_gate", humanGate, workflow.NodeConfig{})

Why each part is written this way:

  1. Leave InterruptID empty. The comment on RequestInput.InterruptID says: “leave it empty and the engine fills in a fresh UUID (the recommended default)”, and warns explicitly: Dev UI keys by ID, so reusing a fixed literal within one session means later requests stop showing an input box. Hand-copying a "approval" constant is exactly this bug.

  2. ResponseSchema is derived from the Go type with jsonschema.For[Approved](nil), i.e. the same source as the Approved struct — a hand-written JSON Schema will eventually drift from the code.

  3. Payload carries the brief to be approved, so the UI can decide while looking at the content.

  4. Expanded, ResumeOrRequestInput is precisely the three-paragraph boilerplate from module 5 article 5:

    func ResumeOrRequestInput(ctx agent.Context, emit func(*session.Event) error, req session.RequestInput) (any, error) {
	if reply, ok := ctx.ResumedInput(req.InterruptID); ok {
		return reply, nil
	}
	if err := emit(NewRequestInputEvent(ctx, req)); err != nil {
		return nil, err
	}
	return nil, ErrNodeInterrupted
}

    Its return type is any (not your struct), so this code uses json.Marshal + Unmarshal to land on Approved. Why not a type assertion: the resume payload was deserialised out of session events, so at runtime it is a map[string]any — asserting *Approved directly panics every time. This “second encode/decode” looks clumsy, but it is the only sound conversion across the event boundary.

  5. Return immediately when err != nil: ErrNodeInterrupted must bubble up untouched, because the scheduler relies on it to move the node to NodeWaiting (module 5). Wrapping it into some other error here ends the whole turn, and the human never gets asked again.

The panic inside approvalSchema is acceptable: the input is a static type, so failure can only be a programming error, and crashing at startup beats returning a vague error at run time.

6. Building the graph: workflowagent, not a hand-written Workflow (modules 5 + 6)#

return workflowagent.New(workflowagent.Config{
	Name:        "intel",
	Description: "Daily intelligence brief: fetch, analyse, human approval",
	SubAgents:   []agent.Agent{analyzer},
	Edges: workflow.Chain(
		workflow.Start,
		fetchNode,
		analyzeNode,
		gateNode,
	),
})

Four choices:

  1. workflowagent.New rather than workflow.New(...) driven by hand: because we want automatic resume. Module 5 article 5 explained that the workflowagent wrapper checks ctx.UserContent() for a FunctionResponse matching an InterruptID it already emitted, and dispatches Run versus Resume accordingly. You only hand-write wf.Resume when you drive a *workflow.Workflow directly.
  2. Config has only six fields (Name/Description/SubAgents/Before…/After…/Edges), no MaxConcurrency, no StateSchema — if you need those, dive down to workflow.New (module 6, article 1).
  3. SubAgents: []agent.Agent{analyzer} makes it visible to the Dev UI and the agent-graph endpoint (module 6), and leaves room for a future transfer_to_agent. Note that analyzer is simultaneously a graph node and a sub-agent — that is allowed, and the two arrival paths differ (the graph drives by edges; the model transfers by name).
  4. workflow.Chain returns []Edge, which is exactly the type of Edges — so Chain is syntax sugar for “the linear default”, and adding routing means pushing another workflow.NewConditionalEdge(...) into the same slice (module 5, article 3).

7. Persistence and observability (modules 4 + 8 + 10)#

providers, err := telemetry.New(ctx, telemetry.WithOtelToCloud(false))
providers.SetGlobalOtelProviders()

db, err := gorm.Open(postgres.Open(os.Getenv("DATABASE_URL")), &gorm.Config{})
sessSvc, err := database.NewSessionServiceFromDB(db)

logP := loggingplugin.MustNew("intel_audit")
retryP, err := retryandreflect.New(
	retryandreflect.WithMaxRetries(2),
	retryandreflect.WithTrackingScope(retryandreflect.Invocation),
)
plugins := []*plugin.Plugin{logP, retryP}
defer func() {
	for _, p := range plugins {
		if cerr := p.Close(); cerr != nil {
			log.Printf("close plugin %s: %v", p.Name(), cerr)
		}
	}
}()

Four decisions:

DecisionReasonSource
WithOtelToCloud(false), only our own collectordata stays inside our VPC; GCP traces need an explicit switch, and the GCP logs exporter is not implemented in v2.4.0module 10, article 2 §5
database.NewSessionServiceFromDB(db) rather than session.NewInMemorya HITL session must survive a process restart — the graph state lives in the session events (ReconstructRunState), and in-memory storage loses it on restartmodules 4 + 5 article 5
loggingplugin.MustNew("intel_audit") with a unique namea duplicate name makes runner.New fail outrightmodule 10, article 2 §2
retryandreflect with the Invocation scopethe Global counter is shared across users, so in a multi-tenant service one tenant’s failures exhaust everyone’s retry budgetmodule 10, article 2 §3

⚠️ plugins is closed by our own defer: in v2.4.0 the library has no non-test path calling PluginManager.Close(), and runner.PluginConfig.CloseTimeout is “assigned but never read”. This is the single most important fact in this article to verify independently.

8. Two run shapes (module 8)#

if os.Getenv("INTEL_RUN_ONCE") == "1" {
	runOnce(ctx, root, sessSvc)
	return
}

l := universal.NewLauncher(
	web.NewLauncher(api.NewLauncher(), webui.NewLauncher()),
)
if err := l.Execute(ctx, &launcher.Config{
	SessionService: sessSvc,
	AgentLoader:    agent.NewSingleLoader(root),
	PluginConfig:   runner.PluginConfig{Plugins: plugins},
	Authenticator:  authn.NewIdentityAwareProxy(),
	Authorizer:     authz.NewStrict(),
}, os.Args[1:]); err != nil {
	log.Fatalf("launch: %v\n\n%s", err, l.CommandLineSyntax())
}

One binary, two shapes, split by INTEL_RUN_ONCE — that is module 8’s “adkgo only deploys, the web entry lives in your main”.

Four correspondences:

  1. universal.NewLauncher(web.NewLauncher(api.NewLauncher(), webui.NewLauncher())): web.NewLauncher returns a launcher.SubLauncher, and you must wrap it in universal.NewLauncher to get Execute (module 2, article 3). If you want the shortcut, use full.NewLauncher().
  2. launcher.Config is the only injection point — both SessionService and AgentLoader come in this way (the field table in module 8, article 2).
  3. authn.NewIdentityAwareProxy() and authz.NewStrict() must be a pair: the quadrant table of module 10, article 1 — only the former means any logged-in user can impersonate any user, only the latter means the service denies everything.
  4. PluginConfig is passed into the launcher too, so every runner.New on the web surface carries the plugins — note that getRunner rebuilds the Runner per request (module 7), which means plugin instances are shared and cross-session (the reason retryandreflect uses a sync.Mutex).

The batch shape#

func runOnce(ctx context.Context, root agent.Agent, sessSvc session.Service) {
	const app, user = "intel", "cron"
	sess, err := sessSvc.Create(ctx, &session.CreateRequest{AppName: app, UserID: user})
	if err != nil {
		log.Fatalf("create session: %v", err)
	}
	r, err := runner.New(runner.Config{AppName: app, Agent: root, SessionService: sessSvc})
	if err != nil {
		log.Fatalf("runner: %v", err)
	}
	msg := &genai.Content{Role: "user", Parts: []*genai.Part{{Text: `{"sources":["rss://a"]}`}}}
	for ev, err := range r.Run(ctx, user, sess.Session.ID(), msg, agent.RunConfig{}) {
		if err != nil {
			log.Fatalf("run: %v", err)
		}
		if ev.Output != nil {
			log.Printf("output from %s: %v", ev.Author, ev.Output)
		}
	}
}

Three points:

  1. Create the session explicitly, instead of runner.Config{AutoCreateSession: true}. The reason is worth remembering: adkrest.ServerConfig has no AutoCreateSession field, and handler.go does not set it when building the RuntimeAPIController — so on the REST path it is always false and the session must exist first. Write batch and web consistently; do not rely on AutoCreateSession on one side and manual Create on the other.
  2. for ev, err := range r.Run(...) — the iterator protocol, and any err means break (as in modules 4/5).
  3. ev.Output, not ev.Content: a graph node’s structured product is in Output (module 5); Content is the text shown to the model.

⚠️ This path deliberately does not auto-approve HITL. On the batch path, reaching human_gate emits adk_request_input and pauses; either you read ev.RequestedInput in this function and append a FunctionResponse event then Resume (module 5, article 5), or the batch shape should not contain a human node at all — that is a product decision, not something the framework can make for you.

9. Deployment (module 8, article 1)#

FROM golang:1.27 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags=-s -ldflags=-w -o /exe ./cmd/intel

FROM gcr.io/distroless/static-debian11
COPY --from=build /exe /app/exe
ENTRYPOINT ["/app/exe"]

docker build -t REGION-docker.pkg.dev/PROJ/repo/intel:latest .
docker run -p 8080:8080 -e GEMINI_API_KEY=... -e DATABASE_URL=... \
  intel web api webui -global_port 8080

go install google.golang.org/adk/v2/cmd/adkgo@latest
adkgo deploy cloudrun --project_id "$PROJ" --region "$REGION" \
  --image REGION-docker.pkg.dev/PROJ/repo/intel:latest --a2a false --debug_api false

ENTRYPOINT ["/app/exe"] rather than /app/exe web — leave the subcommand to the CMD ["/app/exe","web","-port","<port>"] that adkgo generates, so the two do not fight (module 8, article 1, section 2).

--a2a false: this agent has a human approval step, so it does not need A2A exposure for now. If you really want multi-agent cooperation, see module 9 — and remember to configure authentication for the A2A surface separately (it does not go through launcher.Config.Authenticator).

Conclusion: the one through-line of the whole series#

Looking back, the ten modules of ADK Go v2 keep restating one thing from four angles:

  • Types are contracts: the single agent.Context interface (module 2), one iter.Seq2 stream protocol (modules 4/5/7/9), generic nodes and tools that turn Go types directly into model-side schemas (modules 3/5), and every place any appears is a validation point (modules 5/6).
  • State is the only truth: graph state lives in session events (modules 4/5), so the session store determines every recovery capability; OutputKey with a prefix/name hierarchy is the standard way for agents to communicate (modules 4/6).
  • Pausing is a state, not an error: ErrNodeInterrupted must bubble untouched, InterruptID must be unique, LongRunningToolIDs keeps an event from counting as final (modules 5/6/7) — HITL and long-running tools ride the same mechanism.
  • Every default is a development value: NewInMemory, authn.Noop + authz.Noop, telemetry with no exporter, CloseTimeout and the Pub/Sub MaxConcurrentRuns, -include_debug_api false (modules 8/10). “A field exists” and “a field takes effect” are two different things — that thread runs through the whole series, and it is why every conclusion here was traced back to the v2.4.0 source or a compile.

Thirty articles, and the series ends here. Go back and read the modules your scenario needs: for a tool-shaped agent start with modules 3 + 6, for process automation start with modules 5 + 4, and for a service exposed to others start with modules 8 + 9 + 10.

Frequently Asked Questions

Can this example's code run as-is?

Every Go fragment was run through go build and go vet (zero errors) in an isolated module under /tmp against adk/v2 v2.4.0 plus go1.26.8. You supply a GEMINI_API_KEY and a PostgreSQL DSN, then use the commands at the end of the article.

Why is the fetch a FunctionNode instead of letting the model call a tool?

Because fetching is a deterministic step that must happen. The first principle of module 5 is "certain steps get nodes, uncertain judgements get models". Here llmagent does exactly one uncertain thing: extract the conclusion and the risks.

What does the human approval step look like in the web UI?

The node emits an adk_request_input FunctionCall event (workflow.NewRequestInputEvent), which appears on the A2A and REST sides as the task entering input-required (module 9). Dev UI pops an input box; once the user submits, workflowagent recognises the resume and re-runs the graph.

What does ResumeOrRequestInput save me?

Three lines of boilerplate. It is equivalent to "return the answer when ctx.ResumedInput(InterruptID) hits, otherwise emit NewRequestInputEvent and return ErrNodeInterrupted". Hand-copy it if you prefer, and copying it wrong means the node never resumes.

One session per delivery — how do I write the scheduled batch then?

See runOnce: Create a session, then runner.Run. Remember the trigger semantics from module 8 — retries reuse the session (context accumulates) while deliveries do not. For cross-day memory use OutputKey plus a memory service, not the same sessionID.

Why must I close the plugins myself?

No non-test path in the v2.4.0 library calls PluginManager.Close(), Runner has no Close method, and PluginConfig.CloseTimeout is assigned but never read. So whatever resources your plugins hold, you release them on your own exit path (module 10, article 2).
