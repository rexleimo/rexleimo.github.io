Events and platform: the three replaceable seams behind NewEvent(ctx,…)

The ADK Go v2.4.0 event model and the platform package: who writes and who reads each of the 12 fields once Event embeds model.LLMResponse, the two orthogonal history-visibility rules of Branch and IsolationScope, the seven fields of EventActions including the framework-exclusive Compaction, why NewEvent(ctx,…) must take a ctx, and how the platform.Now / NewUUID / RunTasks seams enable deterministic replay and concurrency-controlled tests.

September 26, 2026 · 8 min · 1701 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources session/session.go (Event, EventActions, RequestInput, NodeInfo and EventCompaction are all defined there — there is no session/event.go) and platform/{doc.go,time.go,uuid.go,exec.go}.

Module 0 noted that session.NewEvent gained a ctx parameter, and many people read that as a signature change. It is actually the foundation of testability for all of 2.x: an event’s identity card (ID) and heartbeat (timestamp) stopped “asking the system directly” and started “asking the provider attached to the ctx”.

First, what an event actually looks like#

type Event struct {
	model.LLMResponse          // embedded: Content / Partial / UsageMetadata / FinishReason and friends

	// Set by storage
	ID        string           `json:"id"`
	Timestamp time.Time        `json:"timestamp"`

	// Set by agent.Context implementation.
	InvocationID   string      `json:"invocationId"`
	Branch         string      `json:"branch,omitempty"`
	IsolationScope string      `json:"isolationScope,omitempty"`
	Author         string      `json:"author"`
	Actions        EventActions `json:"actions"`

	LongRunningToolIDs []string      `json:"longRunningToolIds,omitempty"`
	Routes             []string      `json:"routes,omitempty"`
	RequestedInput     *RequestInput `json:"requestedInput,omitempty"`
	Output             any           `json:"output,omitempty"`
	NodeInfo           *NodeInfo     `json:"nodeInfo,omitempty"`
}

Embedding model.LLMResponse has real consequences: ev.Content, ev.Partial and ev.UsageMetadata are promoted fields. So deciding “is this event a model reply” always requires a nil check — LLMResponse is embedded by value, and an “action event” with all fields empty (a tool response, a state change) is indistinguishable at the type level.

The twelve fields are easier to remember grouped by who writes and who reads:

Written byFieldsRead by
storage layerID, Timestampordering, resume-from-checkpoint, GetRequest.After
the agent.Context implementationInvocationID, Author, Actions, Branch, IsolationScopestate merging, prompt assembly
model / tool streamContent (embedded), Partial, LongRunningToolIDsclient rendering, async callbacks
the graph engineRoutes, RequestedInput, Output, NodeInfothe scheduler, the UI

Timestamp is written by storage (the comment says Set by storage) — NewEvent fills an initial value, but on persistence storage wins, so do not treat the local clock as the source of truth.

History visibility: two orthogonal mechanisms#

This is the most commonly misconfigured part of 2.x multi-agent setups.

Branch: a dotted path, providing sibling isolation

agent_1.agent_2.agent_3     ← agent_1 is the parent of agent_2, and so on

The comment verbatim: “Branch is used when multiple sub-agent shouldn’t see their peer agents’ conversation history.” Sub-agents read and write along their own branch, and siblings cannot see each other.

IsolationScope: exact match, providing private scope

// an event is visible only when event.IsolationScope equals the
// agent's isolation scope (exact match; empty sees only empty)

⚠️ empty sees only empty — an agent with no scope cannot see any scoped event at all. That means events produced by a dynamic sub-agent (whose scope looks like <parent-path>/<child-name>@<run_id>) are invisible to a parent that itself has an empty scope. For the parent to see them, either put both in the same scope, or pass them out explicitly through the node’s Output — do not expect history to converge on its own.

To read the current values inside a tool: ctx.Branch() and ctx.IsolationScope() (already listed in module 2’s context method table).

EventActions: seven fields and one forbidden zone#

type EventActions struct {
	StateDelta               map[string]any                        `json:"stateDelta"`
	ArtifactDelta            map[string]int64                      `json:"artifactDelta"`
	RequestedToolConfirmations map[string]toolconfirmation.ToolConfirmation `json:"requestedToolConfirmations,omitempty"`
	SkipSummarization        bool                                  `json:"skipSummarization,omitempty"`
	TransferToAgent          string                                `json:"transferToAgent,omitempty"`
	Escalate                 bool                                  `json:"escalate,omitempty"`
	Compaction               *EventCompaction                      `json:"compaction,omitempty"`
}
  • StateDelta / ArtifactDelta: NewEvent initialises them to non-nil maps, so you can write directly; a bare Event{} literal leaves them nil and writing panics.
  • RequestedToolConfirmations: this is where module 3’s HITL lands, keyed by function call ID.
  • SkipSummarization: valid only on function response events (comment: Only valid for function call response event); setting it stops the framework from asking the model to summarise the tool result — a switch that saves one model call.
  • TransferToAgent / Escalate: LLM-driven hand-off and escalation, expanded in module 6.
  • Compaction is framework-exclusive, comment verbatim:
Setting it from a tool handler or a callback has no effect: it is
cleared wherever caller-supplied actions are copied onto an event.
A record is not a request but an instruction to drop the events it
names and show its own content in their place, which is not a
decision the code running inside a turn gets to make about the
conversation it is running in.

In plain language: whether history may be deleted is not a decision the code inside a turn gets to make. A compaction summary event looks like this: Compaction != nil, LLMResponse.Content == nil, no state or artifact delta — which is exactly why the previous article insisted that storage implementations must round-trip Compaction unchanged.

On serialisation: MarshalJSON omits StateDelta and ArtifactDelta when they are nil. So hand-written event JSON lacking those two keys is legal, and it deserialises back to nil maps (you cannot write to them directly).

Graph-engine-only fields (a foreshadowing of module 5)#

type RequestInput struct {
	InterruptID    string              `json:"interruptId"`      // must be echoed back on resume
	Message        string              `json:"message,omitempty"`
	ResponseSchema *jsonschema.Schema  `json:"responseSchema,omitempty"`
	Payload        any                 `json:"payload,omitempty"`
}

type NodeInfo struct {
	Path            string   // empty for a static top-level node; "<parent-path>/<child-name>@<run_id>" for a dynamic child
	MessageAsOutput bool     // when set and Output is nil, readers use the event body as the node output
	OutputFor       []string // which nodes this output counts for (a delegation chain shares one copy instead of emitting duplicates)
}

The RequestedInput comment carries one hard constraint: “At most one event per node activation may carry this field” — a single node activation may emit at most one human-request event. The scheduler observes this field during event dispatch to move the node to NodeWaiting, and the UI reads the same field to render the input box. Do not hand-make a second one, or the resume semantics go wrong.

NodeInfo.Path uses the @run_id suffix to distinguish the Nth execution of the same dynamic node — that is the key to keeping history unpolluted after a dynamic node re-runs.

NewEvent and the three seams#

func NewEvent(ctx context.Context, invocationID string) *Event {
	return &Event{
		ID:           platform.NewUUID(ctx),
		InvocationID: invocationID,
		Timestamp:    platform.Now(ctx),
		Actions:      EventActions{StateDelta: make(map[string]any), ArtifactDelta: make(map[string]int64)},
	}
}

The platform package describes itself (doc.go) as “seams for overriding system operations”. By default it uses the wall clock and random UUIDs. All three seams share one shape — function type + attach to context + read:

type TimeProvider func() time.Time
func WithTimeProvider(ctx context.Context, p TimeProvider) context.Context
func Now(ctx context.Context) time.Time

type UUIDProvider func() string
func WithUUIDProvider(ctx context.Context, p UUIDProvider) context.Context
func NewUUID(ctx context.Context) string

type TaskRunner func(ctx context.Context, tasks []func(context.Context))
func WithTaskRunner(ctx context.Context, runner TaskRunner) context.Context
func RunTasks(ctx context.Context, tasks []func(context.Context))

Three design intentions:

  1. Providers live on the ctx, not in a package-level variable. doc.go says so directly: “Carrying the provider on the context (rather than in a package-level variable) also keeps the provider scoped to a single call tree, which is what makes concurrent runs with independent providers safe.” — parallel subtests can each install their own fake clock without cross-talk.
  2. A nil provider is ignored and falls back to the default (the ok && p != nil checks in uuid.go / time.go), so installing nil does not explode.
  3. RunTasks enforces its own completion barrier: it wraps each task with defer wg.Done() before handing it to the runner, and performs wg.Wait() itself. That is why the comment can state: “Callers may therefore read per-task results as soon as RunTasks returns, even if a custom runner does not block until its tasks finish.” An empty or nil slice returns immediately and does nothing.

Recipe: deterministic replay tests#

// a fixed clock plus predictable IDs make the event sequence fully deterministic
base := time.Date(2026, 9, 26, 10, 0, 0, 0, time.UTC)
tick := 0

ctx := platform.WithTimeProvider(context.Background(), func() time.Time {
	tick++
	return base.Add(time.Duration(tick) * time.Second)   // advance one second per call
})
ctx = platform.WithUUIDProvider(ctx, func() string {
	return fmt.Sprintf("evt-%04d", seq.Add(1))
})

ev := session.NewEvent(ctx, "inv-1")   // ID and Timestamp both fully predictable

Why the clock must advance rather than stay fixed: event ordering depends on Timestamp, and identical timestamps make replay order unstable (especially on a database backend). A monotonically advancing fake clock lets you assert content and order at the same time.

You can pin concurrency too (particularly useful for reproducing interleaved-event bugs):

// a serial runner: removes the ordering jitter introduced by goroutine scheduling
ctx = platform.WithTaskRunner(ctx, func(ctx context.Context, tasks []func(context.Context)) {
	for _, t := range tasks {
		t(ctx)          // one goroutine at a time, order matches the slice
	}
})

All three motivations named in the doc are covered: limit concurrency, substitute your own executor, run everything sequentially in one goroutine.

Note: providers attach to the root ctx, and every derived ctx inherits them. So “a fresh ctx per test case” is mandatory — never attach to a process-wide shared ctx.

Walking events: three ways#

sess, err := svc.Get(ctx, &session.GetRequest{AppName: "a", UserID: "u", SessionID: "s"})
if err != nil { … }

// ① range-over-func (preferred)
for ev := range sess.Session.Events().All() {
	if ev.Actions.Compaction != nil { … }   // a compaction summary event
}

// ② indexed access (the Events interface guarantees order)
n := sess.Session.Events().Len()
last := sess.Session.Events().At(n - 1)

The All() comment on the Events interface states “preserving their order”, so indexed access is safe. Detect a compaction summary with ev.Actions.Compaction != nil; do not use Content == nil as the test — tool responses and similar events may also have empty Content, but their Actions.Compaction is always nil.

Frequently Asked Questions

Why does session.NewEvent need an extra ctx in v2?

Because the event ID and timestamp no longer call time.Now or a random UUID directly; they go through platform.NewUUID(ctx) and platform.Now(ctx). Providers can be attached to the ctx, which is what makes events deterministic and replay-safe.

Which seams does the platform package expose?

Three: WithTimeProvider(ctx, TimeProvider) plus Now(ctx), WithUUIDProvider(ctx, UUIDProvider) plus NewUUID(ctx), and WithTaskRunner(ctx, TaskRunner) plus RunTasks(ctx, tasks).

What is the difference between Branch and IsolationScope?

Branch is a dotted path (agent_1.agent_2.agent_3) used so sibling sub-agents cannot see each other's history. IsolationScope is exact matching — an event's scope must equal the agent's scope to enter the prompt, and empty sees only empty.

Can I set Actions.Compaction from a tool?

Setting it has no effect. The source comment is explicit: the field is written by the framework and read during prompt assembly, and caller-supplied actions are cleared when copied onto an event.

Can a custom TaskRunner run tasks asynchronously?

Yes. RunTasks enforces its own completion barrier with sync.WaitGroup, so even if the runner does not block, reading per-task results once RunTasks returns is safe.

Will two concurrent tests with different providers interfere?

They will not. Providers are attached explicitly to the context.Context rather than held in a package variable, so their scope is a single call tree — the platform package comment states this.
