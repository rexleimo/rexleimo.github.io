Context compaction: how to set the sliding window and tail retention, and what measured recall tells you about the cost

A deep dive into session/compaction in ADK Go v2.4.0: the trigger timing of the two strategies and constant-factor versus a genuine ceiling, a 60-turn measured comparison of prompt lengths, why recall is all-or-nothing, the verbatim Durable facts clause in the default prompt (measured 5 of 10 conversations losing everything versus 9 of 10 losing nothing), the escape hatch of putting unrecoverable facts in state, the five Config fields and Validate rules, ErrCompaction versus decline and failure, tail retention bypassing the plugin pipeline (required reading if you redact), and the launcher's process-wide constraint.

September 26, 2026 · 14 min · 2805 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources session/compaction/{compaction.go,llm_summarizer.go}, session/session.go (EventCompaction), cmd/launcher/launcher.go, and the samples examples/compaction, examples/compactionrecall.

session/compaction is a 2.x-only package (absent from 1.x). Its package comment is the most honest performance documentation I have seen anywhere in ADK — it gives measured numbers, states the conditions under which it fails to work, and explains how the defaults were derived. This article is essentially that comment translated into decisions you can execute.

The one-line principle: it appends a summary event, it never deletes history#

type EventCompaction struct {
	StartTimestamp   time.Time      // start of the covered range
	EndTimestamp     time.Time      // end of the covered range
	CompactedContent *genai.Content // the summary itself
	ExcludedEvents   []EventRef     // the specific events it supersedes ({InvocationID, Timestamp})
}

The package comment verbatim:

A compaction never modifies or deletes history. Summarizing a range of events appends one new session.Event carrying a session.EventCompaction that records the covered timestamp range and the summary content. When the next prompt is built, the raw events inside that range are dropped and the summary is materialized in their place.

Three consequences, all of which affect operations:

  1. The database does not shrink — what changes is which events get read when assembling a prompt. If you want actual slimming you must archive it yourself.
  2. The audit trail stays complete (ExcludedEvents names each event individually), which is good for compliance.
  3. A compaction event must round-trip through storage unchanged — its Content is nil and it carries no delta, so a backend that decides “should I store this” by content silently drops it, and then every turn re-summarises the same stretch and pays again (this is in the storage contract of the first article of this module ).

Two strategies: one lowers a constant, one actually caps#

Sliding window
  trigger: after an invocation completes, once CompactionInterval
           user-initiated invocations have accumulated
  action:  replaces that batch of invocations with one summary
  key:     a summary is never re-summarized
  result:  the prompt still grows with conversation length,
           only with a shallower slope (a constant factor)

Tail retention
  trigger: inside an invocation, before the model call, once prompt
           tokens reach TokenThreshold
  action:  summarizes everything except the most recent
           EventRetentionSize events, seeding the new summary with the old
  result:  history = one rolling summary + a raw tail → the prompt is bounded

If you need a real ceiling, enable tail retention — the comment verbatim: “An agent that needs a genuine ceiling on prompt size should enable it.”

The sliding window has a hidden second role: it drains window by window. CompactionInterval also bounds the range of a single pass, so turning compaction on in an already-long session digests the backlog one window at a time rather than summarising everything at once.

The classic misconfiguration: tail retention never fires#

The failure mode named in the comment:

Tail retention fires only when more events have accumulated since the last sliding-window compaction than EventRetentionSize holds back. A short interval keeps that number small, and with a large retention size it never reaches it: tail retention never runs, and the prompt grows with the conversation as though it were not configured at all.

A 60-turn measurement (summaries around 500 characters):

CompactionIntervalEventRetentionSizefinal promptshape
21013,935 charsstill growing
3109,147 charsstill growing

The rule in one sentence: EventRetentionSize must be smaller than the number of events produced per compaction cycle. The last row matters more: tail retention alone is a configuration that requires no arithmetic — if you need a ceiling, start there.

Compare the upstream sample: examples/compaction/main.go deliberately enables only the sliding window (CompactionInterval: 2, OverlapSize: 1) and comments out tail retention with the reason stated — it would not fire at that interval. The compactionrecall example command gives another pair: -threshold=32000 -retention=10.

The cost: recall is all-or-nothing#

This is the part of the article worth reading three times.

The loss, when it happens, is not gradual. Each pass either copies a value forward or generalizes it to its label — “the deployment region” in place of “europe-west4” — and a value replaced by its label cannot come back, because the next pass sees only the previous summary and the retained tail. So recall tends to be all or nothing rather than fading.

Why it is not gradual decay: each tail-retention pass can only see “the previous summary + the retained tail”. Once a value has been written as a label, the original text is in no input any more.

So do not look at averages. The compactionrecall comment calls out this exact statistical trap:

a config tends to score 8/8 or 0/8 rather than something in between, and two configs that both average 50% can mean “always half-remembers” and “works perfectly half the time”.

Which is why that sample defaults to -runs=3 and prints each run’s score individually.

The Durable facts clause in the default prompt#

The default template (defaultPromptTemplate) has three CRITICAL INSTRUCTIONS sections; quoted verbatim:

1. Explicitly identify and state the primary language used by the user
   at the top of your summary (e.g., "Conversation Language: English").
2. If the agent called any tools, accurately list the exact tool names
   used to maintain tool grounding.
3. Maintain a section titled "Durable facts" listing every concrete
   detail the user has stated: identifiers, names, dates, numbers, chosen
   options and the reasons given for them. Copy each one verbatim. …
   Never drop or generalize a durable fact to save space; drop narrative instead.

How upstream verified that this clause earns its place (8 arbitrary facts, buried in early turns, summarised away, then each one asked again):

promptresult
without this verbatim-retention instructionin 5 of 10 conversations all of them were lost (8/8 → 0/8)
the default prompt9 of 10 conversations lost nothing

⚠️ Two direct consequences:

  • when you supply a custom PromptTemplate, copy this clause in, otherwise you dismantle a protection that was validated by measurement;
  • wording that only asks for a “concise summary” is enough to reintroduce the loss — the comment verbatim: “asking only for a ‘concise’ summary is enough to do the loss”.

Verbatim retention is not free#

Carrying values forward costs summarizer calls, because larger summaries cross TokenThreshold sooner: about twice as many in the same measurement.

Bigger summaries → TokenThreshold is crossed sooner → the summariser model is called more often. In the same measurement, summarizer calls roughly doubled.

Which yields the most valuable design recommendation in this article —

The escape hatch: information that cannot be lost should not go through the summarizer#

Where that matters, or where the detail absolutely cannot be lost, keep it out of the summary altogether. Compaction does not touch session state, and an Instruction referencing state with a {key} placeholder is re-templated on every request, so a value held there reaches the model however many passes have run.

Those three sentences stitch the first two articles of this module into one coherent strategy:

// concrete values that must outlive the session: put them in state and re-inject by template
ctx.State().Set("user:deployment_region", "europe-west4")

a, _ := llmagent.New(llmagent.Config{
	Instruction: "The deployment region is fixed to {user:deployment_region}; every resource operation uses it.",
	// …
})
Kind of informationWhere it goesWhy
constants / IDs / regions / prices that must apply verbatimstate + a {key} templatecompaction never touches state, the template re-renders each turn, so it is permanent
the conversation’s course, decision rationale, open taskshand it to the summariserthat is what it is good at, and it is also the bulk
large text or filesartifacts ({artifact.x} is likewise fetched fresh each turn)same logic as state, and it does not sit resident in the prompt

Keeping a critical fact in the conversation and hoping the summariser carries it through is handing a deterministic mechanism to a probabilistic one. That is the real takeaway of this article.

The five Config fields and the Validate rules#

type Config struct {
	CompactionInterval int   // sliding window: how many invocations per pass; 0 disables; also bounds one window
	OverlapSize        int   // sliding window: pull back this many already-compacted invocations for continuity
	TokenThreshold     int   // tail retention: prompt token threshold; 0 disables
	EventRetentionSize int   // tail retention: how many recent events stay raw; required together with TokenThreshold
	Summarizer         Summarizer // nil → build an LLMSummarizer from the root agent's model
}

Three easily misconfigured semantics, all stated in the comments:

  1. OverlapSize overlap means “duplicated”, not “shared”: the invocation pulled back gets described by both summaries, the model sees it twice, and the prompt carries roughly OverlapSize invocations’ worth of extra text. It also cannot be removed afterwards (the duplication is already in the summary prose). Leave it at 0 unless windows visibly lose the thread.
  2. Neither strategy enabled → Validate() errors (“it would occupy a configuration step and do nothing”). To disable, leave the whole Config nil.
  3. TokenThreshold set but EventRetentionSize zero → error, and a specific one: “a compaction would summarize the whole conversation including the turn being answered” — the window would extend to the newest event and summarise away the very line the model is about to answer.

When Summarizer is nil the runner builds the default implementation from the root agent’s model, which is why the comment warns: the root agent must be an LLM agent. A pure-workflow root plus a nil Summarizer means you must supply one explicitly.

Failure versus decline: two kinds of “not summarised”#

var ErrCompaction = errors.New("context compaction failed")

The Summarizer interface comment distinguishes two returns:

// Returning a result with no content and no error is a decline: this range
// was not summarized, the caller leaves history alone and carries on.
// Returning an error is a failure, which is reported and traced. Reporting
// a failure as a decline makes a summarizer that never succeeds look
// identical to an idle one while the prompt keeps growing on every turn.
type SummarizeResult struct {
	Content *genai.Content                                // nil means decline
	Usage   *genai.GenerateContentResponseUsageMetadata   // meaningful even on decline or failure
}
  • do not use a decline to mask an error. When writing your own Summarizer, reporting a failure as a decline produces “looks idle while the prompt grows every turn”.
  • fill in Usage even on declines and failures: the summariser may have spent money without producing a usable result, and “compaction that never succeeds” is the most expensive kind.
  • Branch on ErrCompaction at the call site:
for event, err := range r.Run(ctx, uid, sid, content, agent.RunConfig{}) {
	if errors.Is(err, compaction.ErrCompaction) {
		log.Printf("compaction failed: %v", err)   // a bookkeeping failure; this turn's answer is unaffected
		continue
	}
	if err != nil {
		return err
	}
	// handle the event normally
}

The comment’s justification: “Compaction is bookkeeping: the events of the turn are already persisted before it runs, so a failure costs a smaller prompt later, not the user’s answer.” But it still surfaces — a compaction that never succeeds deserves to be known about.

⚠️ Tail retention bypasses the plugin pipeline (required reading if you redact)#

Summaries produced by this strategy do not pass through the plugin pipeline. … Tail retention runs inside an invocation and appends directly, so a plugin does not see it. An application relying on a plugin to redact content before it is stored should know these events bypass it, because nothing reports that they did.

Broken out:

sliding windowtail retention
when it runsafter an invocation endsinside the invocation, before the model call
path to storagethe runner’s regular appenda direct append
can a plugin see the summary event✅❌

Upstream adds that this is not their idiosyncratic choice: neither the adk-python nor the Kotlin path runs plugin hooks, and Kotlin is the reference design for this one. So do not expect a plugin to intercept compacted content — do the redaction before it enters the session, or enable only the sliding window.

The six knobs of LLMSummarizer#

type LLMSummarizerConfig struct {
	Model                 model.LLM       // required
	PromptTemplate        string          // must contain ConversationHistoryPlaceholder; empty = built-in
	MaxToolContentChars   int             // default 2000; negative = no truncation
	MaxTranscriptChars    int             // default 200_000; negative = no limit
	Timeout               time.Duration   // default 0 = no timeout
	GenerateContentConfig *genai.GenerateContentConfig // SystemInstruction and Tools are cleared
}

Four practical judgements taken from the comments:

  • MaxToolContentChars applies to ordinary text as well (deliberately): pasted documents and tool results re-emitted as text count too, otherwise the same payload would cost differently depending on which part type it landed in. It counts characters, not bytes — so a Chinese conversation is not systematically underestimated.
  • exceeding MaxTranscriptChars is an error, not a drop of the oldest turns: those turns are still recorded as inside the “covered” range, so dropping them would truly lose them. The cost is a larger prompt this turn; the fix is a smaller window.
  • Timeout is worth setting: the summariser call runs synchronously inside the run loop, so a hang stalls the following turn — and “compaction is an optimisation, giving it up is cheap”.
  • the runner passes the root agent’s GenerateContentConfig: the safety switches and output limits you set for your application also govern “the one call that can see the entire transcript”; omit it and it silently falls back to provider defaults. Meanwhile SystemInstruction and Tools are forcibly cleared — the summariser has its own instruction and must not be handed tools.

The built-in template “is not published and is not a contract” (the comment: it is the wording of one default, and exporting it would make every improvement a breaking change) — so never assert on the prompt’s content in code; if you need stable wording, supply your own PromptTemplate.

Deployment: this is a process-level setting#

The cmd/launcher comment:

This setting is process-wide. One launcher can serve many applications through its agent loader, and they all get this config or none of them do, including the same Summarizer instance and so the same model. If different applications need different compaction, or must not share a summarizer, run them separately.

Three deployment conclusions:

  1. do not expect per-application compaction configuration — if you need different strategies, deploy as separate processes.
  2. one expensive model serves every application (shared instance), so both cost and compliance must be assessed per process.
  3. launcher.Config has a Validate() that checks the compaction configuration at startup. The comment’s rationale is practical: runners are constructed per request, so not checking up front yields “the process comes up, every request fails, and the error message contains nothing an operator can act on”.

Applications that call runner.New themselves are not bound by points 2 and 3, but must call cfg.Compaction.Validate() themselves.

Checklist#

  • state the goal: cheaper, or bounded. Bounded → tail retention (TokenThreshold + EventRetentionSize)
  • when enabling both, verify EventRetentionSize < events per cycle, and after launch spot-check that prompt length really flattened
  • migrate every concrete value that cannot be lost into state + a {key} template, or into artifacts
  • a custom PromptTemplate must carry the verbatim-retention clause, and be run through compactionrecall
  • set Timeout; pass the root agent’s GenerateContentConfig
  • if you rely on a plugin for redaction, enable only the sliding window, or move redaction earlier
  • branch on errors.Is(err, compaction.ErrCompaction) at the call site so it never fails the whole turn
  • the session service backend must pass sessiontestsuite, confirming Compaction round-trips

With that, module 4 is complete: state holds the facts that must not change, platform supplies determinism, compaction bounds the growth. Next is 2.x’s largest addition — Module 5: The Graph Workflow Engine → .

Frequently Asked Questions

How do I enable context compaction in ADK Go 2.x?

runner.Config.Compaction = &compaction.Config{...}. Leaving the whole Config nil disables it; at least one strategy must be enabled or Config.Validate() errors outright.

Should I use the sliding window or tail retention?

If you need a bound on prompt size, use tail retention (TokenThreshold + EventRetentionSize) — it requires no arithmetic. The sliding window only shrinks by a constant factor and never caps, so on its own it suits cases where you do not want to change the shape of the summary.

What should I watch when enabling both?

EventRetentionSize must be smaller than the number of events produced within one compaction interval, otherwise tail retention never fires and the prompt grows as if unconfigured. That single rule is the intuition the package comment gives.

Does compaction lose concrete values stated early on?

It does, and it loses them all-or-nothing — each pass either copies a value forward or generalizes it to its label (substituting 'the deployment region' for europe-west4), and once generalized it cannot come back. The default prompt's Durable facts clause exists to suppress this.

How should I handle information that absolutely cannot be lost?

Do not hand it to the summarizer. Put it in session state and reference it from the Instruction with a {key} placeholder: compaction never touches state, and the template re-renders on every request, so the value survives however many passes run.

Does a compaction failure fail the current answer?

It should not. ErrCompaction marks a bookkeeping failure — the turn's events were persisted long before it ran, so the only cost is a larger prompt next turn. Distinguish it with errors.Is, log it, and continue.
