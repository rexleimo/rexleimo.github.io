The unified agent.Context: the single most important type in 2.x

ADK Go 2.x merged ToolContext and CallbackContext into agent.Context. This article walks its capability surface method by method against the v2.4.0 source: the invocation / agent call / step terminology, State/Actions/SearchMemory/RequestConfirmation, the parallel-isolation semantics of Branch and IsolationScope, the StrictContextMock testing pattern, and four anti-patterns.

September 26, 2026 · 8 min · 1536 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, source file agent/context.go (checked line by line against the text as of 2026-09-26).

If 2.x lets you memorise exactly one type, this is it. The graph engine, HITL, memory retrieval, state access and your entire testing approach all hang off agent.Context. In the 1.x era you mapped between ToolContext and CallbackContext; after 2.x that work is gone.

Pin the terminology first: invocation / agent call / step#

agent/context.go opens with an official comment that I think is the most worthwhile model diagram in all of ADK Go to memorise:

┌─────────────────────── invocation ──────────────────────────┐
┌──────────── llm_agent_call_1 ────────────┐ ┌─ agent_call_2 ─┐
┌──── step_1 ────────┐ ┌───── step_2 ──────┐
[call_llm] [call_tool] [call_llm] [transfer]

The official definitions:

Layerstarts atends atowned by
invocationone user messagethe final response (may contain several agent calls)runner.Run()
agent callone agent.Run()that Run() returningthe specific Agent
stepone LLM callLLM and tools both finish, or someone calls EndInvocation()the LlmAgent’s internal loop

Two details that are easy to miss:

  1. An invocation can contain several agent calls — whenever an agent requests a transfer to another agent. So “one user question” and “one model call” are not the same thing.
  2. “Summarising the function response” counts as another step, because it is an extra LLM call. This single fact determines how your token bill should be read.

Why memorise it? Because billing, timeouts, cancellation and retry boundaries all live here. NodeConfig.Timeout bounds a node’s single activation, the invocation deadline comes from the ctx you pass to Run(), and step counts LLM calls — three layers each governing one segment. Confuse them and you get “I clearly set a 5-second timeout, why did it run for 40 seconds”.

How Context is composed: four capability segments assembled into one interface#

type Context interface {
	ReadonlyContext      // read-only view
	InvocationContext    // ownership and control of this invocation
	// —— callback segment ——
	Artifacts() Artifacts
	State() session.State
	// —— tool segment ——
	FunctionCallID() string
	Actions() *session.EventActions
	SearchMemory(ctx context.Context, query string) (*memory.SearchResponse, error)
	ToolConfirmation() *toolconfirmation.ToolConfirmation
	RequestConfirmation(hint string, payload any) error
	// —— graph node segment ——
	ResumedInput(interruptID string) (any, bool)
	Path() string
	RunID() string
	SubScheduler() DynamicSubScheduler
	// —— derivation ——
	WithAgentContext(ctx context.Context) Context
	WithAgentTimeout(timeout time.Duration) (Context, context.CancelFunc)
	WithAgentCancel(...) ...
}

Three places where you really must be careful#

① HITL ordering: check the state first, then issue the request#

The source comment gives this exact shape:

// inside a tool: before performing the sensitive action
if confirmation := ctx.ToolConfirmation(); confirmation == nil {
	// no confirmation record yet — request one, and do not run the sensitive action this turn
	if err := ctx.RequestConfirmation(
		"Transfer 5000 to the account ending 1234 — please confirm",
		map[string]any{"amount": 5000, "to": "****1234"},
	); err != nil {
		return nil, err
	}
	return nil, nil          // hand back to the engine and wait for the user's decision
}
// once confirmation != nil, read its state to decide whether to proceed or refuse

Two semantic traps:

  • RequestConfirmation returning nil only means “the confirmation request was successfully queued”, not that the user approved. The official comment stresses this. This execution of the tool suspends and only continues after the user responds.
  • The confirmation request makes the framework emit a special event (a FunctionCall such as adk_request_confirmation) to the client/UI. A headless scenario with no UI must consume that event itself, otherwise the symptom is “the agent just sits there”.

② Branch() and IsolationScope(): parallel sub-agent isolation depends on them#

From the source comments:

  • Branch() — a hierarchical path like agent_1.agent_2.agent_3, where agent_1 is the parent of agent_2. Its purpose is “several parallel sub-agents must not see each other’s session history”, and it primarily serves parallel agents, which run concurrently.
  • IsolationScope() — once set, the agent’s prompt history contains only events whose IsolationScope matches exactly; an empty value means no scoping.

The engineering consequence is blunt: if you neglect Branch/IsolationScope inside parallel branches, branch A will pick up branch B’s intermediate conclusion as established fact and keep reasoning from it. That class of bug presents as “the answer occasionally crosses wires” and is extremely hard to reproduce. Module 5 demonstrates it on a real topology when covering JoinNode.

③ WithContext is temporary — do not lean on it#

InvocationContext carries this comment (quoted verbatim):

// WithContext returns a new instance of the context with overridden embedded context.
// NOTE: This is a temporary solution and will be removed later. The proper solution
// we plan is to stop embedding go context in adk context types and split it.
WithContext(ctx context.Context) InvocationContext

Upstream’s plan is to stop embedding context.Context in ADK context types and split it out. Therefore:

  • where you need to “swap the underlying ctx” (injecting a provider, adding a timeout), prefer WithAgentTimeout / WithAgentCancel;
  • do not pass WithContext(...) around between library functions — it will most likely be removed in some v2.x release (this is API-stability risk, not a present-tense breakage);
  • and do not store an agent.Context in a struct for long-term holding — it is a per-activation handle, and reusing it across invocations is guaranteed to go wrong.

Testing: StrictContextMock is the only correct posture#

With an interface this large, hand-writing a fake is self-flagellation, and it keeps breaking as the interface grows. The right way:

type fakeContext struct {
	agent.StrictContextMock
	actions *session.EventActions
}

func (f *fakeContext) Actions() *session.EventActions { return f.actions }

var _ agent.Context = (*fakeContext)(nil)   // compile-time assertion against the unified interface

func TestTransferToolWritesState(t *testing.T) {
	sd := map[string]any{"confirmed": true}
	ctx := &fakeContext{
		StrictContextMock: agent.StrictContextMock{Ctx: t.Context()},
		actions:           &session.EventActions{StateDelta: sd},   // note the field is named StateDelta
	}
	if err := myTool(ctx, payload); err != nil {
		t.Fatalf("tool failed: %v", err)
	}
}

Two reasons this is the better trade (both stated in the official migration guide):

  1. Forward compatibility: StrictContextMock implements the full unified-context method set, so when the interface gains methods later your fake needs no change.
  2. Failures stay loud: an unoverridden method panics with "not implemented". A hand-written mock returning zero values lets tests “pass for the wrong reason” — the nastiest kind of false green during a period of rapid framework change.

On agent.StrictContextMock{Ctx: ...}, the four standard context.Context methods (Deadline/Done/Err/Value) read from Ctx and do not panic.

Anti-pattern list#

Anti-patternConsequenceCorrect approach
context.Background() mid-chainloses platform providers (time/UUID) and tracing, replay tests turn flakypass the ctx you already hold straight through
storing agent.Context in a global or struct fieldthe same handle gets reused across invocations, state and events get crosseduse it only within the function’s lifetime
running the sensitive action right after RequestConfirmationthe user has not agreed yet, but the money has movedreturn immediately after the request and wait for the resume
hand-writing a complete mocka batch of methods to add on every v2.x upgradeembed StrictContextMock
ignoring Branch()/IsolationScope() in parallel brancheshistories leak between branches, answers are “occasionally weird”design the isolation scope explicitly
deriving ctx via WithContextupstream plans to remove itWithAgentTimeout / WithAgentCancel
assuming “one invocation = one LLM call”timeouts, billing and cancellation all set at the wrong layerdesign against invocation / agent call / step

Frequently Asked Questions

What is agent.Context in ADK Go 2.x?

It is the single context type passed to callbacks and tools, merged from 1.x's ToolContext and CallbackContext. It embeds context.Context and provides session/state read-write access, event actions, memory retrieval, HITL confirmation and graph-node runtime information.

Why did 2.x merge ToolContext and CallbackContext?

Because callbacks and tools routinely need the same capabilities: read state, mutate event actions, request user confirmation. While they were split, the same logic had to be written against two interfaces, and tested with two mocks.

How should I handle agent.Context in tests?

Embed agent.StrictContextMock, override only the methods the case actually calls, and assert var _ agent.Context = (*fakeContext)(nil). Unoverridden methods panic, so a dirty call is exposed immediately.

What is the difference between Branch and IsolationScope?

Branch is a hierarchical path like agent_1.agent_2.agent_3, used so parallel sub-agents cannot see each other's session history. IsolationScope is an exact-match event scope: only events whose scope is equal enter the model prompt history, and an empty value means no scoping.

Can I call context.Context methods on agent.Context directly?

Yes. It embeds context.Context, so Deadline/Done/Err/Value are all there, and the ctx agent.Context received by a node or tool function can be passed straight down as a context.Context.
