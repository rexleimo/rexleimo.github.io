The launcher family: which of console / web / full / prod / universal / agentengine to pick

A complete map of ADK Go v2.4.0 runtime entry points: the Launcher and SubLauncher interfaces, Config.Validate, universal's default sub-launcher rule, how full and prod compose, web's api/webui/a2a/pubsub/eventarc keywords, the default open authn/authz, and h2c — with a selection decision table and a troubleshooting list.

September 26, 2026 · 8 min · 1579 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources under cmd/launcher/ (launcher.go, universal/universal.go, full/full.go, prod/prod.go, web/web.go, console/console.go).

The launcher is a 2.x application’s only runtime entry point, but the official docs never spell out how the pieces compose — which is why a great many production deployments are running full (Dev UI included, console included, no authentication by default). This article pins the interfaces, the compositions, the defaults and the selection rule in one go.

The interface: two methods describe a launcher#

// cmd/launcher/launcher.go
type Launcher interface {
	// Execute parses command-line arguments and runs the launcher.
	Execute(ctx context.Context, config *Config, args []string) error
	// CommandLineSyntax returns a string describing the command-line flags and arguments.
	CommandLineSyntax() string
}

type SubLauncher interface {
	// Keyword returns the command-line keyword that activates this sub-launcher.
	Keyword() string
	// Parse parses the arguments for the sub-launcher. It should return any unparsed arguments.
	Parse(args []string) ([]string, error)
	// CommandLineSyntax returns a string describing the command-line flags and arguments.
	CommandLineSyntax() string
	// SimpleDescription provides a brief, one-line description of the sub-launcher's function.
	SimpleDescription() string
	// Run executes the sub-launcher's main logic.
	Run(ctx context.Context, config *Config) error
}

(web defines its own wider sub-launcher interface with an extra SetupSubrouters for mounting routes and wrapping handlers — that is a web-layer extension point, not part of launcher.SubLauncher.)

universal is the combinator:

// NewLauncher returns a new universal launcher.
// The first element on launcher list will be the default one if there are no arguments specified
func NewLauncher(sublaunchers ...launcher.SubLauncher) launcher.Launcher

Memorise that default rule: the first sub-launcher in full is console, so

go run .            # ≡ go run . console
go run . web api    # explicitly choose web, then choose its api sub-launcher

web is itself a universal-style container, and Keyword() decides the command-line names (api, webui, a2a, pubsub, eventarc, agentengine). Its CommandLineSyntax() prints the whole “available sub-launcher list plus each one’s syntax” — that is the only thing you need to remember:

l := full.NewLauncher()
if err := l.Execute(ctx, cfg, os.Args[1:]); err != nil {
	log.Fatalf("run failed: %v\n\n%s", err, l.CommandLineSyntax())   // ← do not drop this half
}

The composition (verbatim from source)#

// cmd/launcher/full/full.go
func NewLauncher() launcher.Launcher {
	return universal.NewLauncher(
		console.NewLauncher(),
		web.NewLauncher(
			webui.NewLauncher(),
			a2a.NewLauncher(),
			pubsub.NewLauncher(),
			eventarc.NewLauncher(),
			api.NewLauncher(),
		),
	)
}

// cmd/launcher/prod/prod.go
// Package prod provides easy way to play with ADK with all available options without
// development support (no console, no ADK Web UI) including only production
// options like the REST API and A2A support.
func NewLauncher() launcher.Launcher {
	return universal.NewLauncher(
		web.NewLauncher(api.NewLauncher(), a2a.NewLauncher()),
	)
}

Shrinking the exposed surface (production wants only the REST API, no A2A, no UI at all) is the habit most worth building in 2.x:

import (
	"google.golang.org/adk/v2/cmd/launcher"
	"google.golang.org/adk/v2/cmd/launcher/universal"
	"google.golang.org/adk/v2/cmd/launcher/web"
	"google.golang.org/adk/v2/cmd/launcher/web/api"
)

l := universal.NewLauncher(web.NewLauncher(api.NewLauncher()))   // mount api only

launcher.Config: every capability switch is on this one table#

type Config struct {
	SessionService   session.Service
	ArtifactService  artifact.Service
	MemoryService    memory.Service
	AgentLoader      agent.Loader
	A2AOptions       []a2asrv.RequestHandlerOption
	PluginConfig     runner.PluginConfig
	TelemetryOptions []telemetry.Option
	Authenticator    authn.Authenticator   // nil → authn.NewNoop()
	Authorizer       authz.Authorizer      // nil → authz.NewNoop()
	Compaction       *compaction.Config    // nil → disabled; process-wide
}

The comment on Config.Validate() reads: “Validate reports a Config that cannot work, before anything starts serving.” In other words, assembly errors should detonate before Execute, not surface on the first request after the service is up. Call it explicitly during CI smoke tests:

cfg := &launcher.Config{AgentLoader: agent.NewSingleLoader(root), SessionService: ss}
if err := cfg.Validate(); err != nil {
	log.Fatalf("bad launcher config: %v", err)
}

Open by default: Authenticator / Authorizer#

The Config comment is explicit: when Authenticator is non-nil it authenticates every restapi endpoint except /health and /version, returning 401 without valid credentials, and attaching the caller’s identity to the ctx once authenticated. The default nil means authn.NewNoop().

Available providers (the server/authn directory):

FilePurpose
header.gotrust identity headers forwarded by a reverse proxy (pairs with a gateway/LB converging the entry point)
iap.goGoogle IAP (Identity-Aware Proxy) token verification
custom.gocustom schemes (API key, bearer, …)
noop.goauthn.NewNoop()

On the authorisation side, server/authz offers only NewNoop() and NewStrict(); strict provides CanActAsUser(ctx, userID) error — it verifies “may this caller act as this userID”.

Why this is critical: ADK’s REST session API addresses by three levels: app/user/session. Without authz.NewStrict(), anyone who has the URL can read and write session history under somebody else’s userID. Shipping full to production with Noop authorisation is equivalent to exposing your session database to the public internet.

The process-wide constraint on Compaction#

The comment, condensed:

  • sliding-window compaction shrinks the prompt by a constant factor, and only tail retention (EventRetentionSize) actually bounds growth; if the events accumulated between two sliding-window compactions never exceed the tail-retention capacity, the mechanism spins idle;
  • this is a process-level setting: when one launcher serves several applications through its agent loader, they all use the same configuration and the same Summarizer instance (i.e. the same model);
  • if different applications need different compaction policies, or must not share a summarizer, you must split the processes.

There is one more implicit constraint on the runner side: with no Summarizer specified, the runner installs a compaction.LLMSummarizer using the root agent’s model — which requires the root to be an LLM agent; and that “you did not ask for it but it will happen” call carries a default timeout (defaultSummarizerTimeout), because compaction runs inside the run loop and an unresponsive provider would otherwise hold the turn open indefinitely.

Two runtime details that get overlooked#

① console installs signal handling. From the source: ctx, cancel := signal.NotifyContext(ctx, os.Interrupt), and it drives exactly the iterator from route B:

for event, err := range r.Run(ctx, userID, sess.ID(), userMsg, agent.RunConfig{StreamingMode: streamingMode}) {
	if err != nil { /* A compaction failure is not this turn's failure. */ }
}

Two implications: under console, Ctrl-C ends the current turn gracefully; and a compaction failure is not this turn’s failure — that is official semantics, and if you wrap the runner yourself you should keep it consistent.

② the web launcher enables h2c since v2.2.0 (HTTP/2 cleartext, PR #826). Reverse proxies and load balancers need matching configuration, otherwise you get the “HTTP/2 works locally, degrades to HTTP/1.1 behind the gateway” behaviour difference; and remember to disable response buffering in the middle layer for SSE/streaming endpoints.

Frequently Asked Questions

Which launchers exist in ADK Go 2.x?

Six kinds under cmd/launcher: console, web (with api/webui/a2a/agentengine/triggers sub-launchers), full, prod, universal and agentengine. Both full and prod are universal composition presets.

What exactly does full.NewLauncher() compose?

Verbatim from source: universal.NewLauncher(console.NewLauncher(), web.NewLauncher(webui.NewLauncher(), a2a.NewLauncher(), pubsub.NewLauncher(), eventarc.NewLauncher(), api.NewLauncher())).

Which mode do you get if you run it with no arguments?

The comment on universal.NewLauncher states that the first element of the list is the default when no arguments are given. In full the first one is console, so go run . is equivalent to go run . console.

Which launcher should production use?

prod.NewLauncher() = universal(web(api, a2a)): REST API and A2A only, with no console and no ADK Web UI. Use full for development and demos.

Does the launcher authenticate by default?

No. A nil Config.Authenticator becomes authn.NewNoop() and a nil Authorizer becomes authz.NewNoop(), so every endpoint other than /health and /version is effectively open. You must install providers explicitly.

What is the relationship between adkgo and the launcher?

There is none. adkgo only deploys (deploy cloudrun / deploy agentengine); the console/web/api runtime subcommands come from the launcher you chose in main.go.
