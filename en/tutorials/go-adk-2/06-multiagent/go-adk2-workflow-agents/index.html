The three fixed orchestration agents: Sequential / Parallel / Loop, their implementation semantics and boundaries

The three agent/workflowagents packages in ADK Go v2.4.0: Config wraps a single agent.Config (LoopAgent adds MaxIterations uint), all three reject a custom Run, Sequential's fixed ordering and RunLive entry point, Parallel's errgroup plus <parent>.<child> branch naming and early-stop cancellation with teardown waiting, Loop's count==0 indefinite loop and Actions.Escalate exit, and where the selection boundary lies against the graph workflow engine.

September 26, 2026 · 7 min · 1376 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources agent/workflowagents/{sequentialagent,parallelagent,loopagent}/agent.go, samples examples/workflowagents/*.

Let me clear one thing up first: these three packages are not new in 2.x (they exist in the v1.7.0 tree); what 2.x did to them was “keep them, but no longer as the only option”. The previous module’s graph engine pushed orchestration to the far end; this article covers the middle ground — when the orchestration shape is fixed, you do not need a graph.

All three Configs look the same#

type Config struct {
	AgentConfig agent.Config    // all three packages have this one field
}

// loopagent has one more
type Config struct {
	AgentConfig   agent.Config
	MaxIterations uint
}

There is no SubAgents []agent.Agent field — sub-agents travel through AgentConfig.SubAgents and are read at runtime via ctx.Agent().SubAgents(). So the construction shape is:

seq, err := sequentialagent.New(sequentialagent.Config{
	AgentConfig: agent.Config{
		Name:      "pipeline",
		SubAgents: []agent.Agent{extract, transform, load},
	},
})

One hard rule shared by all three New functions:

if cfg.AgentConfig.Run != nil {
	return nil, fmt.Errorf("SequentialAgent doesn't allow custom Run implementations")
}

Run may not be set. Orchestration semantics belong to the package, not to you as an override hook. (Want custom orchestration? Then it is the graph engine, or agent.New with your own Run.)

Each also stamps state.AgentType = TypeSequentialAgent / TypeParallelAgent / TypeLoopAgent — the telemetry layer uses it to distinguish span types (expanded in module 10).

Sequential: a fixed order, and the only one with RunLive#

// SequentialAgent executes its sub-agents once, in the order they are listed.
// Use the SequentialAgent when you want the execution to occur in a fixed,
// strict order.

“once” is the keyword: each sub-agent runs exactly one time, it is not a loop.

The seqAgent struct is worth noting — beyond agent.Agent it embeds an extra *agentinternal.State, and implements RunLive:

func (s *seqAgent) RunLive(ctx agent.InvocationContext) (agent.LiveSession, iter.Seq2[*session.Event, error], error)

Sequential is the only one of the three exposing a live entry point (the other two New functions return a bare agent.Agent). So when a voice/real-time pipeline needs a fixed order, Sequential is the one that works out of the box; Parallel/Loop need you to wire live yourself (module 7 covers LiveSession).

Parallel: errgroup, branch naming, early stop#

The run() implementation has three engineering details worth examining one by one.

① each sub-agent gets its own branch:

branch := fmt.Sprintf("%s.%s", curAgent.Name(), sa.Name())
if ctx.Branch() != "" {
	branch = fmt.Sprintf("%s.%s", ctx.Branch(), branch)
}

In other words Parallel performs sibling isolation automatically — while agentA and agentB run together, their intermediate events are mutually invisible (the Branch semantics from module 4 article 2 apply here). If you want them to share one context, do not use Parallel: use an explicit shared node in a graph, or pass values through state.

② each child ctx is rebuilt, not inherited:

subCtx := icontext.NewInvocationContext(errGroupCtx, icontext.InvocationContextParams{
	Artifacts: ctx.Artifacts(), Memory: ctx.Memory(), Session: ctx.Session(),
	Branch: branch, Agent: subAgent, UserContent: ctx.UserContent(),
	RunConfig: ctx.RunConfig(), InvocationID: ctx.InvocationID(),
})

Note the absence of a State field — the session is shared (Session: ctx.Session()), so state reads and writes go through one session. That also means concurrent sub-agents writing the same state key is a race (module 4: State.Set eventually lands via event deltas, but concurrent writes inside one turn remain unsafe). To pass values between concurrent branches, use different keys, or hand them to a JoinNode-style downstream aggregator.

③ the early-stop versus teardown trade-off (comment transcribed verbatim):

Cancelable so an early consumer stop aborts each sub-agent's in-flight Run
promptly. Teardown still runs to completion and the iterator waits for it
(see the deferred cleanup), so a sub-agent that blocks in teardown blocks run.

Cancellation is immediate, but deferred teardown is waited on. So: do not block without a timeout in a sub-agent’s cleanup logic (callbacks, flushes, closing remote connections), otherwise the “stop” button still leaves things stuck.

Error propagation uses errgroup.WithContext: any sub-agent returning an error → overall error, and the other branches get cancelled. The error is wrapped once as failed to run sub-agent %q: %w — errors.Is still works.

Loop: two exit conditions#

func (a *loopAgent) Run(ctx agent.InvocationContext) iter.Seq2[*session.Event, error] {
	count := a.maxIterations
	return func(yield func(*session.Event, error) bool) {
		for {
			shouldExit := false
			for _, subAgent := range ctx.Agent().SubAgents() {
				for event, err := range subAgent.Run(ctx) {
					if !yield(event, err) { return }
					if event != nil && event.Actions.Escalate { shouldExit = true }
				}
				if shouldExit { return }
			}
			if count > 0 {
				count--
				if count == 0 { return }
			}
		}
	}
}

Five semantics read straight out of the code:

  1. MaxIterations == 0 = loop forever, confirmed by the comment: “LoopAgent runs indefinitely or until any sub-agent escalates”. Before passing 0, make sure an escalate exit exists, or you have an infinite loop hammering the model. The field type is uint (not int), so negatives are not a concern.
  2. exit happens via event.Actions.Escalate — a sub-agent setting that flag on an event terminates the whole loop. That is the actual use of the EventActions field from module 4.
  3. The escalate check has the granularity of a full sub-agent iteration: all events of the current sub-agent are processed first, then shouldExit is examined. It is not per-event interruption — so the remaining events of the escalating sub-agent are still yielded.
  4. When yield is refused (the consumer breaks), it returns immediately without waiting for cleanup.
  5. Every iteration re-reads ctx.Agent().SubAgents() — the order is fixed and the membership is fixed, so you cannot swap sub-agents at runtime.

⚠️ A common incident: a Loop with no escalate plus a large MaxIterations, and every iteration hits N LLM agents. In production set both MaxIterations and an escalate exit, and give the node a Timeout (in a graph) or a deadline on the caller side.

Which to use when#

ShapeUseRationale
a fixed A→B→C pipelinesequentialagentthree lines, and it supports RunLive
several concurrent lookups that do not need each other’s resultsparallelagentautomatic branch isolation + errgroup
“draft → review → revise” repeated until it passesloopagent + escalatebuilt-in counting and escalation exit
conditional branches / fan-in aggregation / asking a human mid-runthe workflow graph enginefixed orchestration supports none of these
you only learn the steps at runtimegraph + DynamicNodefixed membership versus dynamic
the LLM decides whom to delegate tocollaboration modes (the next article )delegation is model behaviour, not graph structure

The two compose: workflow.NewAgentNode(seq, cfg) makes a Sequential agent a graph node — the graph handles branching and resume, the fixed internal pipeline stays with the lightweight orchestrator. Do not shatter a three-step straight line into five nodes just to use a graph — readability regresses.

Migration note#

Coming from 1.x, these three packages are drop-in compatible in name and shape; the change is conceptual: they are now the simple end of a spectrum whose expressive end is the graph engine. If your 1.x code nests Sequential inside Loop inside Parallel to fake a conditional branch, that is precisely the pattern module 5 replaces with routes and a JoinNode.

Frequently Asked Questions

How do I choose between SequentialAgent / ParallelAgent / LoopAgent and a graph workflow?

Fixed order, no branching, no resume requirement → the three fixed orchestration packages are the cheapest. Conditional routing, fan-in barriers, pause/resume across requests, dynamic dispatch → the workflow graph engine (module 5).

What can go into their Config?

Only one layer, AgentConfig agent.Config (LoopAgent additionally has MaxIterations uint). Sub-agents are passed via AgentConfig.SubAgents, and the orchestration logic accepts no custom Run — setting one errors outright.

Is ParallelAgent really concurrent?

Yes, via errgroup. Each sub-agent gets its own branch (<parent>.<child>, prefixed when a parent branch exists), so siblings cannot see each other's history by default.

When does LoopAgent stop?

Two conditions: MaxIterations exhausted (0 means unlimited), or any sub-agent's event sets Actions.Escalate to true. The latter returns as soon as the current sub-agent's iteration completes.

Does an early consumer break leak goroutines?

Not in Parallel — it cancels the sub-agents and drains the result channel before returning. But the comment warns that a sub-agent blocking in teardown blocks the whole run.

Can these agents be used as graph nodes?

Yes. They are all agent.Agent, so you can drop them straight into a graph with workflow.NewAgentNode(a, cfg).
