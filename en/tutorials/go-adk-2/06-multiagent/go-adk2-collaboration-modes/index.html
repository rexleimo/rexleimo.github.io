Collaboration modes: chat / task / single_turn, and the tools the framework installs for your model

How llmagent.Config.Mode lands in ADK Go v2.4.0: installTaskTools attaching a same-named delegation tool on the parent according to each sub-agent's mode, ModeTask receiving its own finish_task, the delegation tool's Name/Description/Parameters all coming from the agent configuration, the do-not-call-in-parallel sentence hardcoded into the task tool description, DefersResponse and the synthesizeTaskFREvent detour, the different IncludeContents default for a single_turn node, and using the nine TestDelegation_* cases as the specification.

September 26, 2026 · 12 min · 2433 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources agent/llmagent/{llmagent.go,testdata/}, internal/workflowinternal/{single_turn_tool.go,task_agent_tool.go,finish_task_tool.go,task.go}, internal/llminternal/agent_transfer.go, samples examples/multiagent/*.

Module 5’s graph answers “who runs first is decided by code”. This article answers the other half: “who does the work is decided by the model”.

1. The four Mode values and the default rule#

type Mode = llminternal.Mode

const (
	ModeUnset      = llminternal.ModeUnset // not explicitly set
	ModeChat       = llminternal.ModeChat        // reachable via transfer_to_agent
	ModeTask       = llminternal.ModeTask        // clarifies with the human over several turns to finish
	ModeSingleTurn = llminternal.ModeSingleTurn  // does not talk to the user, returns the result when done
)

The comment on the Config.Mode field compresses the default rule into one line:

Default value is ModeChat as a sub-agent, ModeSingleTurn as a node in a workflow.

The same agent behaves differently depending on where you put it. That is why ResolveMode(mode, fallback) exists — ModeUnset is not “chat”, it is “decide by context”:

switch llminternal.ResolveMode(subState.Mode, llminternal.ModeChat) {
case llminternal.ModeSingleTurn: /* … */
case llminternal.ModeTask:       /* … */
}

Note that the switch has no chat branch — see the next section.

2. installTaskTools: delegation tools grow, you do not write them#

llmagent.New always runs this step before returning:

if err := installTaskTools(a); err != nil { return nil, err }

Its logic has two halves whose direction and target differ completely:

if state.Mode == llminternal.ModeTask {
	finishTool, err := workflowinternal.NewFinishTaskTool(a)
	state.Tools = append(state.Tools, finishTool)     // ① attached to the agent itself
}

for _, sub := range a.SubAgents() {
	switch llminternal.ResolveMode(subState.Mode, llminternal.ModeChat) {
	case llminternal.ModeSingleTurn:
		t, _ := workflowinternal.NewSingleTurnTool(sub)
		state.Tools = append(state.Tools, t)          // ② attached to the parent
	case llminternal.ModeTask:
		t, _ := workflowinternal.NewTaskAgentTool(sub)
		state.Tools = append(state.Tools, t)          // ② attached to the parent
	}
}
You areThe framework attachesOn whomName
a ModeTask agentfinish_taskitselfthe constant FinishTaskToolName = "finish_task"
a parent whose sub-agent is ModeTaskthe task delegation toolthe parent= the sub-agent’s Name()
a parent whose sub-agent is ModeSingleTurnthe single_turn delegation toolthe parent= the sub-agent’s Name()
a parent whose sub-agent is ModeChat (or unset)nothing at all—it goes through transfer_to_agent

The last row is the real watershed between the three modes. The README sums it up in one line:

A single_turn or task sub-agent returns control to the coordinator automatically once it produces its result; no explicit transfer_to_agent call is required (this contrasts with default chat mode, which requires a manual handoff).

chat = hand off and lose touch (control goes to the other side and never returns on its own); single_turn / task = call and return (the model treats it as a function, gets a result, and keeps thinking).

Consequence one: Name and Description are the tool contract#

Both delegation tools’ Name() is a single line:

func (t *TaskAgentTool) Name() string      { return t.agent.Name() }
func (t *SingleTurnTool) Name() string     { return t.agent.Name() }
func (t *TaskAgentTool) Description() string { return t.agent.Description() }

So your agent naming goes straight into the model’s tool-selection prompt. A name like "a1" is asking the model to guess; Description must state “when to call me, what input I need, what I return”. This matters more than in 1.x, because delegation is now a tool call rather than a routing label.

Consequence two: InputSchema decides the parameter shape#

MakeFunctionDeclaration(curAgent) (single_turn) and createTaskAgentFuncDeclaration (task) share one implementation:

decl := &genai.FunctionDeclaration{Name: curAgent.Name(), Description: …}
if agentInputSchema := getInputSchema(curAgent); agentInputSchema != nil {
	decl.Parameters = agentInputSchema
} else {
	decl.Parameters = &genai.Schema{Type: "OBJECT",
		Properties: map[string]*genai.Schema{"request": {Type: "STRING", /* the task variant adds one description line */}},
		Required:   []string{"request"}}
}

No InputSchema → the fallback is {request: string} (required). The task variant’s description line is "Detailed instructions or context for the task sub-agent.".

Consequence three: the task tool’s description hardcodes a behavioural constraint#

Description: strings.TrimSpace(fmt.Sprintf(
	"%s\nIMPORTANT: This tool delegates execution to a specialized agent. Do NOT call this tool in parallel with any other tools.",
	curAgent.Description())),

You did not write that sentence; the framework added it. It means: task delegation must not be called in parallel with other tools (delegation hands control to the sub-agent wholesale, so the parallel half would have no moment to execute). The single_turn variant does not carry it — single_turn may run in parallel, and the README’s example input What's the weather like at home today? chains several tools together.

So “can I delegate in parallel” is decided by the mode, not by you wrapping things in Parallel. Even the official testdata has only TestDelegation_02_ChatToTwoTaskSequential (two tasks, sequential); the parallel one is TestDelegation_04_ChatToTwoSingleTurnParallel — the name is the answer.

Consequence four: non-Gemini models need an extra response declaration#

if !googlellm.IsGeminiAPIVariant(agentState.Model) {
	if outputSchema != nil { decl.ResponseJsonSchema = &genai.Schema{Type: "OBJECT"} }
	else { decl.ResponseJsonSchema = &genai.Schema{Type: "STRING"} }
}

Changing the model changes the tool declaration sent to it (Gemini is skipped because it has native structured output). Remember this difference when you evaluate across models.

3. finish_task: the task agent’s “submit” action#

const (
	FinishTaskToolName      = "finish_task"
	FinishTaskSuccessResult = "Task completed."
)

The comment establishes two things:

NewFinishTaskTool allows the model to signal that the agent has completed its task.
On success it sets `tool_context.actions.finish_task` with a serialized `TaskResult` dict.

taskAgent: ... The agent's `output_schema` is used for validation. If None, the
default schema (a single `result` string) is used.
Who calls itthe task agent itself (the model decides when it is done)
Validated againstyour OutputSchema; without one it degrades to {result: string}
Where the result landsfinish_task on actions (a serialised TaskResult)
Failure surfacethe model never calls it → the task is never “submitted”; output violates the schema → see the retry case below

Three data structures (internal/workflowinternal/task.go, all exported):

type TaskRequest struct { AgentName string; Input map[string]any }
type TaskResult struct { Output any }
type DefaultTaskInput struct { Goal string; Background string }

DefaultTaskInput{Goal, Background} is the official answer to “what should I pass when I write no schema” — stating the goal and the background as two fields when delegating is more reliable than stuffing one blob into request.

4. Task delegation bypasses the tool pipeline#

Two counter-intuitive implementation details:

func (t *TaskAgentTool) Run(toolCtx agent.Context, args any) (map[string]any, error) {
	// Framework handles task delegation dispatch directly via the LlmAgent chat wrapper.
	return nil, nil
}

// DefersResponse implements toolinternal.ResponseDeferrer: the FunctionResponse for
// a task delegation is produced by the chat wrapper (synthesizeTaskFREvent), not by
// the standard tool-execution pipeline.
func (t *TaskAgentTool) DefersResponse() bool { return true }

What that means:

  1. Run is empty. Intercepting the task delegation name in BeforeToolCallbacks / AfterToolCallbacks shows you arguments and a “result” that do not represent real execution — the chat wrapper runs the sub-agent. To observe task delegation, read the sub-agent events in the event stream, not the tool callbacks.
  2. The FunctionResponse is synthesised. That is how multi-turn clarification inside a task (sub-agent asks the human → human answers → continue) can hang off this delegation call without timing out. The official TestDelegation_06_ChatToTaskHITLResume tests exactly this: a task sub-agent pauses internally to ask, the outer layer resumes.

One aside: module 5 noted that dispatching a task-mode LlmAgent from a graph via RunNode requires WithIsolationScopeFromNodePath() (unique across nested graphs and duplicate names) — the same isolation need is handled inside the chat wrapper on this path. The two routes differ; do not conflate them.

5. IncludeContents: history visibility for single_turn#

type IncludeContents string

const (
	IncludeContentsNone   IncludeContents = "none"
	IncludeContentsDefault IncludeContents = "default"
)

The field comment on Config.IncludeContents contains an asymmetry you must remember:

Left unset, an agent placed as a single_turn workflow node sees only the current turn.
Setting IncludeContentsDefault explicitly keeps the history even there.
Settingan ordinary conversational agentas a single_turn workflow node
unset (zero value)sees historysees only the current turn
IncludeContentsDefaultsees historysees history
IncludeContentsNonecurrent turn plus its own later eventscurrent turn only

“Setting it explicitly is not the same as leaving the field unset” — the comment says so in words (“Setting it explicitly is not the same as leaving the field unset”). This is the most easily missed silent difference in the module: the same agent behaves normally when run directly, then “loses its memory” once placed in a graph as a single_turn node. If you want it to remember, pass IncludeContentsDefault explicitly.

6. Direction rules for transfer_to_agent#

The top of internal/llminternal/agent_transfer.go (aligned with Python’s auto_flow.py) defines two flows:

SingleFlow: no sub-agents are allowed, i.e.
    DisallowTransferToParent == true && DisallowTransferToPeers == true && len(SubAgents) == 0

AutoFlow — Agent transfers are allowed in the following directions:
  1. From parent to sub-agent.
  2. From sub-agent to parent.
  3. From sub-agent to its peer agent.
Peer-agent transfers are only enabled when all the following conditions are met:
  - The parent agent is also an LLMAgent.

Three practical conclusions:

  1. to disable transfer entirely (an agent that cannot pass the buck): all three conditions must hold — both Disallow* true and SubAgents empty. Setting only DisallowTransferToParent is not enough.
  2. Peer transfer requires the parent to be an LLMAgent too. When the parent is a non-LLM orchestrator such as sequentialagent / workflowagent, the children cannot transfer to each other — they have no common reasoning parent.
  3. Cross-peer transfer has an official case behind it: TestDelegation_09_ChatPeerTransferAcrossSiblings.

7. OutputSchema and set_model_response#

The comment on Config.OutputSchema hides a “the framework does not sacrifice tool capability” design:

When OutputSchema is set, the framework transparently injects a
set_model_response tool so the model can still invoke other tools
(function tools, RAG, agent transfer, etc.) while producing structured output.
See internal/llminternal/outputschema_processor.go for details.

Structured output is not implemented by forcing JSON mode — it gives the model a “submit the final answer” tool. So after setting OutputSchema the model can still call tools and still transfer. If you find that a schema blocks tool calls, the problem is elsewhere in your configuration, not in this mechanism.

8. Treat the testdata as the specification#

The TestDelegation_* cases in agent/llmagent/testdata/ are the behavioural contract for this machinery, numbered roughly in increasing difficulty:

CaseWhat it verifies
01_ChatToTaskToToola three-level pass-through: chat → task → tool
02_ChatToTwoTaskSequentialtwo tasks delegated sequentially
03_ChatToSingleTurna single single_turn delegation
04_ChatToTwoSingleTurnParalleltwo single_turn calls in parallel (not possible with task)
05_ChatChainedThroughChatToTaska chat → chat → task chained transfer
06_ChatToTaskHITLResumeasking a human inside a task sub-agent, then resuming
07_ChatToTaskValidationRetryretrying after schema validation fails
08_ChatToTaskPlusFunctionTooltask delegation mixed with an ordinary function tool
09_ChatPeerTransferAcrossSiblingstransfer between peers

Run these before changing any of this behaviour. Each case ships a .events.yaml (the expected event stream) plus a .httprr (recorded model requests/responses), so they replay locally — no API key needed.

9. A complete, compilable example#

The three-mode combination in examples/multiagent/collaboration/main.go:

weatherChecker, err := llmagent.New(llmagent.Config{
	Name:  "weather_checker",            // this is the tool name the model sees
	Model: model,
	Mode:  llmagent.ModeSingleTurn,      // never asks the human, returns automatically
	Tools: []tool.Tool{getWeatherTool, userInfoTool, geocodeAddressTool},
})

flightBooker, err := llmagent.New(llmagent.Config{
	Name:         "flight_booker",
	Model:        model,
	Mode:         llmagent.ModeTask,      // allowed to ask clarifying questions
	InputSchema:  flightInputSchema,      // decides the delegation tool's parameter shape
	OutputSchema: flightResultSchema,     // decides what finish_task validates against
	Tools:        []tool.Tool{searchFlightsTool, bookFlightTool},
})

travelPlanner, err := llmagent.New(llmagent.Config{
	Name:      "travel_planner",
	Model:     model,
	SubAgents: []agent.Agent{weatherChecker, flightBooker},
	// Mode left empty = ModeUnset, treated as chat when it is the root
})

The README’s closing advice: “The coordinator delegates by mentioning the sub-agent’s name in its instruction.” That is, name weather_checker / flight_booker and their applicable situations in the coordinator’s Instruction — the delegation tools are already injected automatically; your job is to tell the model when to use them.

The four official sample inputs, covering three paths:

What's the weather like at home today?              → single_turn
Is it raining in Tokyo?                             → single_turn + several tools
Please book me a flight from Zurich to London on 2026-07-12. I'm Alex Müller, window seat.
                                                    → task, all information present, no follow-up
Book a flight Zurich → Barcelona on 2026-08-01.     → task, passenger name missing, it asks back

How to run it:

export GOOGLE_API_KEY=...
go run ./examples/multiagent/collaboration console
go run ./examples/multiagent/collaboration web api webui

Narrower samples: examples/multiagent/single_turn (single_turn only) and examples/multiagent/task_sub_agent (two task sub-agents).

10. Choosing: modes versus graphs#

NeedPick
fixed steps, you decide the orderthe graph / sequentialagent (modules 5 and 6-1)
whom to call depends on this user utterancecollaboration modes
the subtask must ask the human and clarify over turnsModeTask + Input/OutputSchema
pure lookups, no interaction, must run in parallelModeSingleTurn (parallel allowed, see case 04)
you must resume the whole turn’s state across requeststhe graph (RunState + Resume); modes do not provide this
you only want “hand off and never come back”ModeChat + transfer_to_agent

They compose: put a chat coordinator agent in a graph node and it will still install delegation tools for its own SubAgents. In the other direction, finish_task and graph HITL are two pause mechanisms (the first is the model voluntarily submitting its answer, the second is adk_request_input being forced to wait for a human) — do not expect one to trigger the other.

Checklist#

  • every sub-agent’s Name is a semantically readable name for the model, and Description says when to use it
  • any task agent needing structured round-trips gets both InputSchema and OutputSchema
  • task delegation is never placed in the same parallel batch as other tools
  • a single_turn node that needs history sets IncludeContentsDefault explicitly
  • for an agent that must not pass the buck: both Disallow* flags plus an empty SubAgents, all three
  • in peer-transfer scenarios, confirmed that the parent is an llmagent
  • task delegation is observed through the event stream, not through tool callbacks

Frequently Asked Questions

Does a sub-agent's mode change the parent agent?

It does, automatically. installTaskTools inside llmagent.New walks the SubAgents and appends a delegation tool to the parent's Tools for each sub-agent according to its Mode; a ModeTask sub-agent also gets a finish_task tool of its own.

What is the delegation tool called?

Exactly the sub-agent's Name(). Name() in TaskAgentTool and SingleTurnTool is just return t.agent.Name(), and Description() works the same way. So the agent's name and description are the tool contract the model sees.

What is the biggest difference between chat and the other two?

A chat sub-agent gets no delegation tool and is reached by a manual transfer_to_agent, and control does not come back on its own; single_turn and task return their result to the coordinator automatically once done, with no explicit transfer required.

What happens if I write no InputSchema?

The framework supplies a fallback parameter: {request: string}, required. The task variant also carries the description 'Detailed instructions or context for the task sub-agent.'. So it runs without a schema, but the model can only stuff in one sentence of natural language.

Can a task sub-agent ask the human?

Yes — there is a dedicated official case, TestDelegation_06_ChatToTaskHITLResume. The delegation tool's DefersResponse() is true, so its FunctionResponse is synthesised by the chat wrapper rather than going through the standard tool execution pipeline.

Does a single_turn sub-agent see the history?

Not by default. The Config.IncludeContents comment says that left unset, an agent placed as a single_turn workflow node sees only the current turn, and only setting IncludeContentsDefault explicitly preserves history.
