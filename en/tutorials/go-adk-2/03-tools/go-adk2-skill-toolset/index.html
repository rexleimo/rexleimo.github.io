SkillToolset: turning a SKILL.md directory into capability the agent loads on demand

A complete tour of tool/skilltoolset in ADK Go v2.4.0: the five methods of skill.Source and its sentinel errors, NewFileSystemSource(fs.FS), the two preload modes (WithCompletePreloadSource / WithFrontmatterPreloadSource) and the reload closure, merging several sources with NewMergedSource, the SKILL.md frontmatter specification (including both allowed-tools spellings), and the three automatically injected tools list_skills/load_skill/load_skill_resource plus the XML inventory injected by ProcessRequest.

September 26, 2026 · 8 min · 1660 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources tool/skilltoolset/{toolset.go,skill/*.go}, tool/skilltoolset/internal/skilltool/, and the samples under examples/skills/.

This is the most underrated package in 2.x. The problem it solves is concrete: you have a pile of domain procedures (quoting rules, weekly report templates, compliance check steps). Putting them in Instruction blows up the prompt and they interfere with each other, yet the model must know they exist.

SkillToolset’s answer is two-stage loading: only the frontmatter (name + description) stays resident in the prompt, while bodies and resources are fetched by the model itself through tools when needed.

Directory structure (as defined explicitly in the official default instruction)#

skills/
└── weather/
    ├── SKILL.md          # required: frontmatter + instruction body
    ├── references/       # optional: supplementary docs, e.g. weather_us.json
    ├── assets/           # optional: templates, scripts and other resources
    └── scripts/          # optional: executable scripts (run via bash)

A SKILL.md example (verbatim from upstream examples/skills/skills/weather/SKILL.md):

---
name: weather
description: A skill to check weather in different countries.
---
# Weather Skill

This skill provides weather information for different countries.

## Instructions
1. When asked about weather in a specific country, check if there is a resource file for that country in the `references/` directory.
2. The resource file will be named `weather_<country_code>.json`. Supports `us` and `pl`.
3. Report the weather for the country to the user.

The frontmatter fields (skill.Frontmatter, whose comment points at https://agentskills.io/specification#frontmatter):

type Frontmatter struct {
	Name          string            `yaml:"name"`
	Description   string            `yaml:"description"`
	License       string            `yaml:"license,omitempty"`
	Compatibility string            `yaml:"compatibility,omitempty"`
	Metadata      map[string]string `yaml:"metadata,omitempty"`
	AllowedTools  []string          `yaml:"allowed-tools,omitempty"`
}

allowed-tools has two legal spellings: the scalar string from the specification (allowed-tools: "Bash, Read") and the YAML sequence that early ADK Go accepted. Internally a custom UnmarshalYAML on allowedToolsYAML accepts both and then splits with splitAllowedTools — your own skill Source implementation must stay compatible with this, or SKILL.md files from the wider tool ecosystem will fail to parse.

Note: Description is the only piece that enters the resident prompt, and it decides whether the model bothers to call load_skill. Write a single decidable sentence like “A skill to check weather in different countries”, not “weather stuff”.

Minimal wiring#

source := skill.NewFileSystemSource(os.DirFS("./skills"))

skillToolset, err := skilltoolset.New(ctx, skilltoolset.Config{Source: source})
if err != nil {
	log.Fatalf("Failed to create skill toolset: %v", err)
}

a, err := llmagent.New(llmagent.Config{
	Name:        "skills_agent",
	Model:       model,
	Description: "Agent to demonstrate using skills.",
	Instruction: "You are a helpful assistant.",
	Toolsets:    []tool.Toolset{skillToolset},
})

Config has only three fields:

type Config struct {
	Source            skill.Source   // required; nil errors immediately with "skill source must be provided"
	Name              string         // defaults to "SkillToolset"
	SystemInstruction string         // default shown below
}

New takes a ctx: func New(ctx context.Context, cfg Config) (*SkillToolset, error) — because enumeration happens at construction (the ListSkills tool needs the inventory), so an invalid SKILL.md on disk detonates at startup, which is a good thing.

The three tools it hands the model#

ToolPurposeKey arguments
list_skillslist available skills (frontmatter level)—
load_skillread a skill’s full instruction bodyname
load_skill_resourceread files inside a skill directory (references/*, assets/*, scripts/*)skill_name, path

The default system instruction (defaultSkillSystemInstruction in the source, key passages quoted verbatim):

You can use specialized 'skills' to help you with complex tasks. You MUST use the skill tools to interact with these skills.

1. If a skill seems relevant to the current user query, you MUST use the `load_skill` tool with `name="<SKILL_NAME>"` to read its full instructions before proceeding.
2. Once you have read the instructions, follow them exactly as documented before replying to the user. …
3. The `load_skill_resource` tool is for viewing files within a skill's directory … Do NOT use other tools to access these files.

All three are hard constraints (MUST / Do NOT), so do not casually override SystemInstruction — the third clause matters most, since it stops the model from using a shell to bypass the skill directory. If you truly need customisation, append to the end rather than replacing.

What actually ends up in the prompt#

func (ts *SkillToolset) ProcessRequest(ctx agent.Context, req *model.LLMRequest) error {
	skills, err := ts.source.ListFrontmatters(ctx)
	if err != nil { return err }
	if len(skills) == 0 { return nil }
	utils.AppendInstructions(req, ts.systemInstruction, skilltool.SkillsToXML(skills))
	return nil
}

Three takeaways:

  1. It runs on every model request — so the cost of ListFrontmatters is paid once per turn, which is precisely why preloading exists below.
  2. What gets injected is the XML inventory of frontmatters (SkillsToXML), not the bodies. Cost ≈ one line of name+description per skill.
  3. When len(skills) == 0 injection is skipped entirely — an empty skill directory does not burn tokens for nothing.

Performance: two preload modes plus hot reload#

A bare fileSystemSource reads from disk every time (ListFrontmatters walks the directory and parses each SKILL.md). Once you have several skills you pay that per turn, so the skill package offers two decorating sources:

// full preload: frontmatter, body and resources all go into memory
source, reload, err := skill.WithCompletePreloadSource(ctx, source)

// frontmatter only: the inventory stays resident, bodies and resources still read from disk
source, reload, err := skill.WithFrontmatterPreloadSource(ctx, source)

Signature: func With…PreloadSource(ctx context.Context, source Source) (Source, func(context.Context) error, error)

  • the second return value is the reload closure — hook it to a file watcher or an admin endpoint and you can hot-reload skills without restarting the process;
  • internally it is a sync.RWMutex plus map[string]*completePreloadSkillData (resources indexed as a map for fast lookup), so concurrent reads are safe;
  • the official examples/skills/main.go uses the full preload.

Which to choose: small skill bodies (a few KB) → full preload; large or numerous bodies and resources → preload frontmatter only and let load_skill read from disk on demand.

Merging several sources#

src := skill.NewMergedSource(
	skill.NewFileSystemSource(os.DirFS("./skills")),        // team-shared
	skill.NewFileSystemSource(os.DirFS("./skills-local")),  // private to this repo
)

NewMergedSource(sources ...Source) Source. Mind the conflict semantics: the Source interface requires implementations to return ErrDuplicateSkill on duplicates — the same skill name in two sources is an error, not an override. To get overriding behaviour, rename the one that should lose, or implement a priority-aware Source yourself.

Implementing Source yourself#

Source has only five methods, so a database, object store or CMS backend is not hard:

type Source interface {
	ListFrontmatters(ctx context.Context) ([]*Frontmatter, error)
	ListResources(ctx context.Context, name, subpath string) ([]string, error)
	LoadFrontmatter(ctx context.Context, name string) (*Frontmatter, error)
	LoadInstructions(ctx context.Context, name string) (string, error)
	LoadResource(ctx context.Context, name, resourcePath string) (io.ReadCloser, error)
}

Two hard requirements in the interface comment: it must be concurrency-safe, and it must return the package’s sentinel errors:

ErrInvalidSkillName, ErrInvalidFrontmatter, ErrSkillNotFound,
ErrDuplicateSkill, ErrInvalidResourcePath, ErrResourceNotFound

Why the emphasis on sentinel errors: the tool layer uses them to translate “skill not found” into actionable feedback for the model (so it can retry with another name) rather than a 500. Returning fmt.Errorf("no such skill") throws that capability away.

Also, LoadResource returns an io.ReadCloser and the comment states the caller owns the Close — your implementation must neither close it early nor cache and reuse an already-closed reader.

Ready-made parsing, validation and assembly helpers (reuse them for import/export and CI validation):

fm, body, err := skill.ParseBytes(content)   // frontmatter + remaining markdown
fm, err       := skill.Parse(bufio.NewReader(f))
err           := skill.Validate(fm)
data          := skill.Build(fm, markdown)   // reverse assembly

Validate rejects skills with illegal names or missing descriptions — run Validate over every SKILL.md in CI, which is far cheaper than discovering it via a production startup failure.

The security boundary is yours to draw#

scripts/ holds executable scripts, and the default instruction encourages the model to read files via load_skill_resource. ADK itself provides no sandbox, so:

  • put only trusted content in the skill directory. Dropping an externally fetched SKILL.md straight into skills/ turns prompt injection into an executable path;
  • if you really run scripts/, add confirmation at the tool layer — which is exactly where the previous article on HITL pays off: set RequireConfirmation: true on the function tool that executes scripts;
  • use allowed-tools to narrow the tool surface that skill may touch;
  • in production, point the Source at read-only, versioned storage (a directory baked into the image, or object storage with checksums) rather than a writable volume.

Testing#

func TestSkillSurface(t *testing.T) {
	src, _, err := skill.WithCompletePreloadSource(ctx, skill.NewFileSystemSource(os.DirFS("./testdata/skills")))
	if err != nil {
		t.Fatal(err)
	}
	fms, err := src.ListFrontmatters(ctx)
	if err != nil {
		t.Fatal(err)
	}
	for _, fm := range fms {
		if err := skill.Validate(fm); err != nil {
			t.Errorf("skill %q invalid: %v", fm.Name, err)
		}
	}
}

Deterministic assertions that need no model: the inventory lists, every frontmatter validates, LoadInstructions is non-empty, and ListResources finds the files under references/. Whether the model chooses to use a skill is a separate question — that belongs in an evaluation set (module 10).

Frequently Asked Questions

What is a skill in ADK Go 2.x?

A folder: a required SKILL.md (YAML frontmatter plus markdown instructions) and optional references/, assets/ and scripts/ directories. The agent reads them on demand through tools instead of everything being stuffed into the prompt.

How do I wire it in?

source := skill.NewFileSystemSource(os.DirFS("./skills")), then skilltoolset.New(ctx, skilltoolset.Config{Source: source}), and put the returned *SkillToolset into llmagent.Config.Toolsets.

Which tools does it give me?

Three: list_skills, load_skill and load_skill_resource. They are constructed inside skilltoolset.New; you do not write them.

Is the skill inventory pushed into the prompt on every request?

Yes. SkillToolset implements ProcessRequest and appends the system instruction plus every skill's frontmatter (as XML) before each model request; it skips injection when the skill list is empty. So bodies never go in — only name and description.

Do I need to restart after editing the skills directory?

It depends on the source. A bare NewFileSystemSource reads from disk each time, so edits take effect immediately; a preload source reads from cache, and you use the returned reload closure to hot-update.

What is allowed-tools for?

A field in the SKILL.md frontmatter (the specification comes from agentskills.io) declaring which tools that skill may use; ADK accepts both the scalar string spelling and the YAML sequence spelling.
