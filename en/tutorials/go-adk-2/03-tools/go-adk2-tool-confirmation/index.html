Tool confirmation (HITL): is one flag enough, or should you take over the protocol?

The two-gear tool confirmation design in ADK Go v2.4.0: declarative RequireConfirmation / RequireConfirmationProvider / tool.WithConfirmation versus the manual ctx.ToolConfirmation() + ctx.RequestConfirmation(hint, payload); the adk_request_confirmation protocol contract (the FunctionResponse must carry the same id, the same name, and confirmed), toolconfirmation.OriginalCallFrom parsing, idempotent re-entry and how to use FunctionCallID.

September 26, 2026 · 8 min · 1626 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources tool/tool.go, tool/toolconfirmation/tool_confirmation.go, agent/context.go, and the sample examples/toolconfirmation/main.go.

2.x made human-in-the-loop a first-class citizen, and gave it two gears: a declarative one-line configuration, and a manual one with full control. The package comment of the official sample states the selection criterion clearly:

It uses ctx.ToolConfirmation() and ctx.RequestConfirmation() to define the confirmation process. This is the example for most advanced scenario which gives the full control how to define confirmation flow. For simpler setup use RequireConfirmation or RequireConfirmationProvider in functiontool.Config.

Conclusion first: use the declarative gear in 90% of cases. Escalate to manual only when you need “modify the arguments then execute”, partial approval, or an approver who must see a human-readable summary.

Gear one: declarative (the recommended starting point)#

deleteTool, err := functiontool.New(functiontool.Config{
	Name:                "delete_records",
	Description:         "Deletes records by query",
	RequireConfirmation: true,             // ← one line
}, func(ctx agent.Context, in DeleteArgs) (DeleteResult, error) {
	return doDelete(in), nil
})

Deciding dynamically (ask or not based on the arguments):

type TransferArgs struct {
	Amount   float64 `json:"amount"`
	Currency string  `json:"currency"`
}

cfg := functiontool.Config{
	Name:        "transfer_money",
	Description: "Transfer money between accounts",
	// the signature must be func(toolInput TransferArgs) bool — note it is this tool's own input type
	RequireConfirmationProvider: func(in TransferArgs) bool {
		return in.Amount > 1000        // small amounts pass straight through
	},
}

⚠️ The RequireConfirmationProvider field is typed any, so a wrong signature produces no compile error. The safe pattern is to declare a named type first and assign through it, letting the compiler check for you:

type confirmFn func(TransferArgs) bool

var p confirmFn = func(in TransferArgs) bool { return in.Amount > 1000 }
cfg.RequireConfirmationProvider = p

At the toolset layer (MCP and other grouped tools) the signature is different:

// tool.ConfirmationProvider
type ConfirmationProvider func(toolName string, toolInput any) bool

ts := tool.WithConfirmation(mcpToolSet,
	false,
	func(name string, input any) bool {
		return name == "create_issue" || name == "delete_branch"
	})

WithConfirmation(toolset, requireConfirmation bool, provider ConfirmationProvider) Toolset — the provider outranks the flag (source comment: If set, this takes precedence).

What actually happens on the protocol#

The FunctionCall the framework emits has a constant name:

// tool/toolconfirmation/tool_confirmation.go
const FunctionCallName = "adk_request_confirmation"

Its args contain two keys (summarised from the source comment):

  • "toolConfirmation": a ToolConfirmation, carrying Hint;
  • "originalFunctionCall": the call the model actually wanted to make (name + args).

The source places five hard requirements on the client. I list them verbatim — this is the contract your frontend must implement:

1. Listen for events containing a FunctionCall with this name.
2. Extract the details of 'originalFunctionCall' from the arguments.
3. Present a clear confirmation prompt to the human user, explaining the action and potential consequences.
4. Capture the user's decision (e.g., true for yes/approve, false for no/deny).
5. Send a FunctionResponse message back to the ADK. This FunctionResponse MUST:
     - Have the same 'id' as the received "adk_request_confirmation" FunctionCall.
     - Have the name set to "adk_request_confirmation".
     - Include a response payload, typically a map like {"confirmed": bool}.

The id and name must match — get either of those wrong and the framework never receives the answer, so the tool stays pending confirmation forever. This is the most common mistake when writing your own frontend.

The ToolConfirmation struct (verbatim v2.4.0):

type ToolConfirmation struct {
	Hint      string `json:"hint"`       // the reason shown to the user
	Confirmed bool   `json:"confirmed"`  // the user's decision; normally the zero value until answered
	Payload   any    `json:"payload"`    // application-defined data
}

Payload is any and works in both directions: on the request you can attach “about to delete 3000 lines” for the approver to read, and on the answer attach “approved for 5 days, not 10” — the official sample below does exactly that.

Gear two: manual takeover (full control of the confirmation flow)#

The leave-approval scenario from examples/toolconfirmation/main.go, dissected segment by segment:

func requestVacationDays(ctx agent.Context, args RequestVacationArgs) (*RequestVacationResults, error) {
	// ① use FunctionCallID as the correlation key across pause/resume
	if confirmation := ctx.ToolConfirmation(); confirmation == nil {
		requestID := nextRequestID()
		requestsByReqID[requestID] = &VacationRequest{ID: requestID, UserID: args.UserID, Days: args.Days, Status: "PENDING"}
		requestsByCallID[ctx.FunctionCallID()] = req

		// ② request confirmation; the payload is handed to the approver unchanged
		if err := ctx.RequestConfirmation(
			"Please approve or reject the tool call ... by responding with a FunctionResponse with an expected ToolConfirmation payload.",
			ConfirmationPayload{DaysApproved: 0}); err != nil {
			return nil, err
		}
		// ③ this turn returns a "pending approval" result and must not continue
		return &RequestVacationResults{Status: "Manager approval is required.", RequestID: requestID}, nil
	}

	// ④ re-entry after resume: find the context again via the same FunctionCallID
	req, ok := requestsByCallID[ctx.FunctionCallID()]
	if !ok {
		return nil, fmt.Errorf("unable to get request using function call id %s", ctx.FunctionCallID())
	}
	if !confirmation.Confirmed {
		req.Status = "REJECTED"
		return &RequestVacationResults{Status: "The time off request is rejected.", DaysApproved: 0, RequestID: req.ID}, nil
	}

	// ⑤ approved — and you can still read the payload the approver edited (partial approval)
	var payload ConfirmationPayload
	jsonRoundTrip(confirmation.Payload, &payload)          // any → struct requires a JSON round trip
	approvedDays := min(payload.DaysApproved, args.Days)   // the approver may lower it, not raise it
	req.Status = "APPROVED"
	return &RequestVacationResults{Status: "The time off request is accepted.", DaysApproved: approvedDays, RequestID: req.ID}, nil
}

Five designs in this sample that are worth copying directly:

  1. ctx.ToolConfirmation() == nil is the test for “first entry”. Non-nil means this is a re-entry after confirmation.
  2. ctx.RequestConfirmation(hint, payload) returning nil only means “the request was sent”, not that it was approved — the source comment stresses this (It does NOT mean the action is approved). So you must return immediately afterwards and not proceed with the sensitive action.
  3. Use FunctionCallID() as the idempotency key. On resume the framework re-runs the same tool function, and you need a key to recover the requestID/state created the first time. The map is a sample simplification; in production put it in a database.
  4. confirmation.Payload is any. What comes back from JSON deserialisation is a map[string]any — the official sample performs a json.Marshal + json.Unmarshal round trip to obtain a struct. Do not type-assert directly.
  5. The approver can change the arguments (lowering DaysApproved). That is the reason the manual gear exists: the declarative gear can only approve or deny, the manual gear can approve with modifications.

What happens after a rejection#

Two sentinel errors on the framework side:

var ErrConfirmationRequired = errors.New("requires confirmation, please approve or reject")
var ErrConfirmationRejected = errors.New("call is rejected")

When rejected, the original tool is not executed and the model receives an error-type function response. So your Instruction should tell it in advance that “if it was rejected, ask the user whether to change the conditions” — otherwise the model will plough on holding an error.

Unwrapping the original call#

Frontends and middleware routinely need “what was this actually trying to call”:

original, err := toolconfirmation.OriginalCallFrom(functionCall)  // *genai.FunctionCall

OriginalCallFrom accepts both encodings of originalFunctionCall (an object, or a JSON string), so replies from differently versioned UIs all parse — hand-rolling that logic is duplicated work.

How it differs from graph-node HITL (do not conflate them)#

The two mechanisms can coexist: a graph node that calls a tool requiring confirmation produces two layers of interaction — “node paused” plus “tool confirmation”. Design the node boundaries first, then decide which tools need confirmation, otherwise the resume semantics will collide.

How to test it#

A confirmation flow spans two turns, so do not use the launcher in tests — drive the runner twice by hand:

// turn one: should produce an adk_request_confirmation call, and must not perform the real deletion
for ev, err := range r.Run(ctx, uid, sid, msg, agent.RunConfig{}) { … }

// assert a pending-confirmation event appeared and that no side effect happened
if !hasConfirmationCall(events, toolconfirmation.FunctionCallName) { t.Fatal("no confirmation requested") }
if store.DeletedCount() != 0 { t.Fatal("tool executed before approval") }

// turn two: feed the FunctionResponse (same id, same name, confirmed:true) back as user content

This kind of test is the only reliable guarantee for HITL — “no approval means no side effect” is a safety invariant you must assert.

Frequently Asked Questions

How do I make ADK Go 2.x ask the user before running a tool?

The cheapest route is functiontool.Config.RequireConfirmation=true (or the same-named field on mcptoolset, or wrapping a toolset with tool.WithConfirmation). For dynamic decisions use RequireConfirmationProvider / tool.ConfirmationProvider.

What does the confirmation request look like on the protocol level?

The framework emits a FunctionCall whose name is the constant toolconfirmation.FunctionCallName = "adk_request_confirmation", whose args carry toolConfirmation (including the hint) and originalFunctionCall.

How should the frontend answer?

Send back a FunctionResponse whose id equals the FunctionCall you received, whose name is adk_request_confirmation, and whose payload includes {"confirmed": bool} (optionally with your own payload). true executes the original call, false intercepts it and returns an error.

Is the tool function re-executed after the answer arrives?

Yes. Once confirmed, the framework re-runs the tool with the same arguments, so the tool must distinguish "first entry" from "re-entry after approval" — the test is whether ctx.ToolConfirmation() is nil.

How do I get the wrapped original call back?

toolconfirmation.OriginalCallFrom(functionCall) restores originalFunctionCall from the adk_request_confirmation args, accepting both the object and JSON-string encodings.

Is graph-node HITL the same thing as tool confirmation?

No. Tool confirmation travels as an adk_request_confirmation FunctionCall; graph-node pausing travels as workflow.NewRequestInputEvent plus ErrNodeInterrupted. Two mechanisms — module 5 covers the latter.
