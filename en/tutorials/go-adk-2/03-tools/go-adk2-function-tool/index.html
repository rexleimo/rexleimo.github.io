Function tools and streaming tools: functiontool.New, every Config field, and the context available inside a tool

The foundation of the ADK Go v2.4.0 tool layer: functiontool.New's generic Func[TArgs,TResults] signature, automatic schema inference (jsonschema rather than genai.Schema), NewStreaming returning iter.Seq2[string,error], the real semantics of IsLongRunning, what a tool can do through agent.Context, and the official agenttool workaround for the Google Search plus function tool conflict.

September 26, 2026 · 8 min · 1698 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources tool/tool.go, tool/functiontool/{function.go,streaming_function.go}, tool/agenttool/, tool/toolutils/, and the sample examples/tools/multipletools/main.go.

A tool is the only place where an agent can change the outside world. At this layer 2.x did something genuinely useful: the first parameter of a tool function is now the unified agent.Context — a tool is no longer a pure function, it can see the session, mutate state, emit events and demand human confirmation. This article covers function tools and streaming tools completely; MCP comes next.

The minimal function tool: one generic signature does it#

type Input struct {
	LineCount int `json:"lineCount"`
}

type Output struct {
	Poem string `json:"poem"`
}

poemTool, err := functiontool.New(functiontool.Config{
	Name:        "poem",
	Description: "Returns poem",
}, func(ctx agent.Context, in Input) (Output, error) {
	return Output{Poem: strings.Repeat("A line of a poem,", in.LineCount) + "\n"}, nil
})

The type definitions in the source (verbatim v2.4.0):

// Func represents a Go function that can be wrapped in a tool.
// It takes a agent.Context and a generic argument type, and returns a generic result type.
type Func[TArgs, TResults any] func(agent.Context, TArgs) (TResults, error)

func New[TArgs, TResults any](cfg Config, handler Func[TArgs, TResults]) (tool.Tool, error)

Three immediate consequences:

  1. You do not write JSON Schema. With Config.InputSchema/OutputSchema left nil they are inferred from the generic parameters (// Input schema is automatically inferred from the input and output types.). Struct tags such as json:"city" control field names.
  2. The return value may be any type, not map[string]any. The tool.Tool interface’s Run returns map[string]any, but functiontool handles serialisation for you — that is why it is more comfortable than implementing the interface bare.
  3. Illegal parameter types return functiontool.ErrInvalidArgument (for example a map, or a type that cannot be mapped to a JSON Schema), so do not ignore the error from New.

To give the model more hints, use the jsonschema tag (the official MCP sample does exactly this):

type Input struct {
	City string `json:"city" jsonschema:"city name"`
}

Every field of functiontool.Config (7)#

FieldTypeMeaning

The two schema fields are typed jsonschema.Schema, whereas llmagent.Config.InputSchema/OutputSchema use genai.Schema — one concept, two types. This is a known upstream inconsistency (the llmagent side carries a TODO about switching to jsonschema). Do not let it into your own abstraction layer; wrap a conversion function.

RequireConfirmationProvider is any, and the signature matters#

// Required signature for a provider function:
// func(toolInput ToolArgs) (bool)
// where ToolArgs is the input type of your go function

Note it receives your tool’s own input type, not (name, input) — that differs from tool.ConfirmationProvider (func(toolName string, toolInput any) bool, used at the toolset layer). Because any is not compile-time checked, a wrong signature only explodes at runtime. Article 3 in this module gives a safe pattern.

The real semantics of IsLongRunning#

Once marked, the framework stops treating it as a synchronous call awaiting a result. The typical shape is “acknowledge first, fill in later”: the tool returns a request_id immediately and the real result is written back into the session in a separate turn driven by an external event (pubsub/eventarc, article 8 of module 8). Do not expect it to poll for you.

Streaming tools: NewStreaming returns iter.Seq2[string, error]#

type StreamingFunc[TArgs any] func(agent.Context, TArgs) iter.Seq2[string, error]

func NewStreaming[TArgs any](cfg Config, handler StreamingFunc[TArgs]) (tool.Tool, error)

searchTool, err := functiontool.NewStreaming(functiontool.Config{
	Name:        "live_search",
	Description: "Search and stream results as they arrive",
}, func(ctx agent.Context, in Input) iter.Seq2[string, error] {
	return func(yield func(string, error) bool) {
		for _, chunk := range fetchChunks(ctx, in) {
			if !yield(chunk, nil) {
				return          // the consumer broke out; stop immediately
			}
		}
	}
})

Three things you must remember:

  • If yield returns false, return immediately. False means the downstream no longer wants data (client disconnected, cancelled via break). Ignoring the return value is the most common streaming leak — which lines up exactly with the iter protocol and goroutine-leak detection discussed in the toolchain article .
  • There is no TResults type parameter: a streaming tool’s output is simply a sequence of string chunks, so only TArgs remains.
  • The underlying interface is RunStream(ctx agent.Context, args any) iter.Seq2[string, error], and it implements toolinternal.StreamingFunctionTool — chunks are only truly pushed one at a time when the model request is streaming; under a non-streaming configuration they get accumulated into a single result. The switch is in module 7.

What a tool can reach internally (the tool segment of agent.Context)#

This is the genuinely valuable part after 2.x merged ToolContext/CallbackContext:

func myTool(ctx agent.Context, in Input) (Output, error) {
	// read
	who := ctx.UserID()
	app := ctx.AppName()
	sid := ctx.SessionID()
	scope := ctx.IsolationScope()     // isolation scope, empty = not isolated
	branch := ctx.Branch()            // "a1.a2.a3", how parallel sub-agents stay invisible to each other
	callID := ctx.FunctionCallID()    // unique ID of this tool call

	// read/write state
	prev, _ := ctx.State().Get("approved_days")

	// semantic memory retrieval
	mem, err := ctx.SearchMemory(ctx, "user preferences")

	// mutate state / transfer agents / end this turn
	ctx.Actions().StateDelta["last_tool"] = callID
	ctx.Actions().TransferToAgent = "summarizer"
	ctx.EndInvocation()

	// HITL (article 3)
	if c := ctx.ToolConfirmation(); c == nil {
		return out, ctx.RequestConfirmation("About to delete 3000 lines — confirm?", map[string]any{"lines": 3000})
	}
}

Actions() returns a *session.EventActions, and that is the single back door through which a tool influences agent behaviour — StateDelta, TransferToAgent, EndInvocation, SkipSummarization all live on it. Full field list in module 4 .

Why FunctionCallID() matters: both HITL and long-running tasks work by “pause — resume”, and on resume the framework re-runs the tool function with the same call ID. So you must use it as an idempotency key when storing progress, or you will double-charge or double-create. The official sample in article 3 does exactly that.

The official workaround: Google Search cannot share an agent with function tools#

The package comment in examples/tools/multipletools is blunt:

demonstrates a workaround for using Google Search tool with other tools ... This is necessary due to limitations in the genai API.

The shape is split sub-agents by tool type, with the root calling them through agenttool:

searchAgent, _ := llmagent.New(llmagent.Config{
	Name: "search_agent", Model: model,
	Description: "Does google search.",
	Instruction: "You're a specialist in Google Search.",
	Tools:       []tool.Tool{geminitool.GoogleSearch{}},
})

poemAgent, _ := llmagent.New(llmagent.Config{
	Name: "poem_agent", Model: model,
	Description: "returns poem",
	Instruction: "You return poems.",
	Tools:       []tool.Tool{poemTool},
})

root, _ := llmagent.New(llmagent.Config{
	Name: "root_agent", Model: model,
	Description: "You can do a google search and generate poems.",
	Instruction: "Answer questions about weather based on google search unless asked for a poem," +
		" for a poem generate it with a tool.",
	Tools: []tool.Tool{
		agenttool.New(searchAgent, nil),
		agenttool.New(poemAgent, nil),
	},
})

Two details decide whether this works:

  • Description is the routing key. The root’s model reads only that text when deciding whom to delegate to, so write a concrete verb like “does google search”, not “a helpful agent”.
  • The root’s Instruction must state the arbitration rule (the official “unless asked for a poem” is precisely that arbitration).

This restriction is worth memorising, because it defeats the intuitive design of “one agent, five kinds of tool” — when tool types conflict, ADK’s answer is more agents, not more tools.

Filtering and trimming a toolset#

ts := tool.FilterToolset(mcpToolSet, tool.AllowedToolsPredicate([]string{"get_weather"}))
  • tool.Predicate = func(ctx agent.ReadonlyContext, tool Tool) bool — it receives a read-only context, so you can admit tools dynamically per user or state;
  • StringPredicate(names) / AllowedToolsPredicate(names) are ready-made whitelist implementations;
  • mcptoolset.Config.ToolFilter is marked Deprecated: use tool.FilterToolset instead, so new code should not use that field.

Why trim proactively: tool declarations go into the prompt, and the schemas of a few dozen MCP tools can consume thousands of tokens, while also diluting the model’s chance of picking the right one. Trimming is the first move that saves money and improves accuracy at the same time.

Self-check#

// tool count and names directly determine cost, so assert them in tests
func TestToolSurface(t *testing.T) {
	tools, err := ts.Tools(readonlyCtx)
	if err != nil {
		t.Fatal(err)
	}
	if len(tools) != 1 || tools[0].Name() != "get_weather" {
		t.Fatalf("unexpected toolset: %v", names(tools))
	}
}

A function tool is a plain Go function, so call it directly to test its logic (pass an agent.StrictContextMock) instead of routing through the model every time.

Frequently Asked Questions

How do I define a function tool in ADK Go 2.x?

functiontool.New(functiontool.Config{Name, Description}, handler), where the handler signature is the generic functiontool.Func[TArgs,TResults] = func(agent.Context, TArgs) (TResults, error); input and output schemas are inferred from the types.

How do I write a streaming tool?

functiontool.NewStreaming(cfg, handler), where the handler returns iter.Seq2[string, error] — yielding text chunks and errors one at a time so results stream to the frontend as they are produced.

What context does a tool receive internally?

The unified agent.Context: State()/ReadonlyState(), Session(), Artifacts(), Memory(), SearchMemory(), Actions() (mutate state, transfer agents), FunctionCallID(), ToolConfirmation()/RequestConfirmation(), plus IsolationScope() and Branch().

Why does Google Search stop working when I add my own function tools?

A genai-layer limitation: built-in search tools and function declarations cannot be attached to the same LlmAgent. The official examples/tools/multipletools workaround wraps each tool class in its own sub-agent and calls them from the root via agenttool.New(subAgent, nil).

What does IsLongRunning do?

It marks the tool as a long-running task: the framework stops treating it as an ordinary synchronous call awaiting a result, so a frontend can return an acknowledgement first and fill in later. functiontool.Config has the field; on the MCP side the server declares it.

How do I temporarily disable a tool?

Use tool.FilterToolset(toolset, tool.StringPredicate(names)) for a whitelist, or write your own tool.Predicate = func(agent.ReadonlyContext, tool.Tool) bool. mcptoolset.Config.ToolFilter is marked Deprecated in favour of FilterToolset.
