The MCP Toolset: Transport/Endpoint/Auth wiring and self-healing disconnects

A complete tour of tool/mcptoolset in ADK Go v2.4.0: the seven fields of mcptoolset.New(Config) and their mutual-exclusion rules, an in-memory MCP server for tests, the Endpoint shortcut for streamable HTTP, the auth.CredentialProvider versus OAuthHandler fight over the Authorization header, connectionRefresher retry semantics, plus toolset trimming and confirmation policies.

September 26, 2026 · 6 min · 1243 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources tool/mcptoolset/{set.go,client.go,tool.go}, auth/, and the sample examples/mcp/main.go.

MCP is the cheapest extension point in 2.x: external tools need not a line of glue, one toolset brings them in. But mcptoolset.Config has only seven fields, and three of them (Transport/Endpoint/Auth) carry mutual-exclusion rules that produce no compile error and only detonate on the first call. This article pins those rules down.

Three ways to wire it#

① An in-process server (tests and reuse of your own tools)#

The first mode in the official examples/mcp/main.go — run an MCP server inside the same process:

import "github.com/modelcontextprotocol/go-sdk/mcp"

type Input struct {
	City string `json:"city" jsonschema:"city name"`
}
type Output struct {
	WeatherSummary string `json:"weather_summary" jsonschema:"weather summary in the given city"`
}

func GetWeather(ctx context.Context, req *mcp.CallToolRequest, input Input) (*mcp.CallToolResult, Output, error) {
	return nil, Output{WeatherSummary: fmt.Sprintf("Today in %q is sunny\n", input.City)}, nil
}

func localMCPTransport(ctx context.Context) mcp.Transport {
	clientTransport, serverTransport := mcp.NewInMemoryTransports()

	server := mcp.NewServer(&mcp.Implementation{Name: "weather_server", Version: "v1.0.0"}, nil)
	mcp.AddTool(server, &mcp.Tool{Name: "get_weather", Description: "returns weather in the given city"}, GetWeather)
	if _, err := server.Connect(ctx, serverTransport, nil); err != nil {
		log.Fatal(err)
	}
	return clientTransport
}

The value of this route is not production, it is testing: tool logic is written in MCP protocol form, the agent side depends only on tool.Toolset, and both halves can be exercised independently.

② Build the transport yourself (when you need OAuth or a custom HTTP client)#

ts := oauth2.StaticTokenSource(&oauth2.Token{AccessToken: os.Getenv("GITHUB_PAT")})

mcpToolSet, err := mcptoolset.New(mcptoolset.Config{
	Transport: &mcp.StreamableClientTransport{
		Endpoint:   "https://api.githubcopilot.com/mcp/",
		HTTPClient: oauth2.NewClient(ctx, ts),
	},
})

③ Give only the Endpoint (least work; ADK builds the transport)#

mcpToolSet, err := mcptoolset.New(mcptoolset.Config{
	Endpoint: "https://api.githubcopilot.com/mcp/",
	Auth:     myCredentialProvider,      // see below
})

The semantics of Endpoint (source comment): “when set and Transport is nil, builds a streamable HTTP transport (mcp.StreamableClientTransport) targeting this URL. Ignored when Transport is set.”

So supplying Transport and Endpoint together means Endpoint silently does nothing. That is the most commonly stepped-on rule here.

Auth and OAuthHandler fight over the same header#

This passage in the source comment is an explicit warning:

Don’t also set OAuthHandler on a supplied *mcp.StreamableClientTransport: Auth is applied last and overwrites the Authorization header, so the two would fight over the same request.

The mechanism: authHTTPClient(base, provider) uses a context-aware RoundTripper that stamps Authorization last, on every outbound request. Therefore:

  • want ADK to manage credentials → use Config.Auth and do not set OAuthHandler on the transport;
  • want the MCP SDK’s own OAuth → set OAuthHandler and do not use Auth.

The auth package is a new package unique to 2.x (absent from the v1.7.0 tree). It serves both MCP outbound credentials and server/authn inbound authentication, and is the starting point of 2.x’s unified credential layer.

Self-healing disconnects: connectionRefresher#

mcptoolset does not use a *mcp.ClientSession directly; it wraps it:

type connectionRefresher struct { client *mcp.Client; transport mcp.Transport }

func (c *connectionRefresher) CallTool(ctx, params) (*mcp.CallToolResult, error)
func (c *connectionRefresher) ListTools(ctx) ([]*mcp.Tool, error)
func withRetry[T any](ctx, c, fn func(*mcp.ClientSession) (T, error)) (T, bool, error)
func shouldRefreshConnection(err error) bool

Three layers of meaning, each worth memorising:

  1. ListTools may re-fetch every time, so a hot-updated tool list on the MCP server is picked up (which is also why a toolset costs more than a static tool list — every request construction has to list the tools).
  2. The session is rebuilt and retried only when the error is classified as connection-type (shouldRefreshConnection). Business errors are never retried — your CallTool will not be run twice for a domain failure.
  3. Retry applies to any return type (withRetry[T any]), so idempotency of the tool call remains your responsibility: if the server executed successfully before the timeout and only the response was lost, the retry after reconnecting will execute it a second time. Write-oriented MCP tools need idempotency keys.

Attaching it to an agent#

a, err := llmagent.New(llmagent.Config{
	Name:        "helper_agent",
	Model:       model,
	Description: "Helper agent.",
	Instruction: "You are a helpful assistant that helps users with various tasks.",
	Toolsets: []tool.Toolset{
		mcpToolSet,
	},
})

Note the field is Toolsets (plural), sitting alongside Tools. Tools holds individual tools, Toolsets holds groups, and you may supply both.

Combining trimming with confirmation:

// admit only two tools, and require confirmation for one of them
filtered := tool.FilterToolset(mcpToolSet, tool.AllowedToolsPredicate([]string{"get_weather", "create_issue"}))

confirmed := tool.WithConfirmation(filtered,
	false, // do not enable it wholesale
	func(toolName string, toolInput any) bool {
		return toolName == "create_issue"   // only the write operation needs confirmation
	})

tool.WithConfirmation(ts Toolset, requireConfirmation bool, provider ConfirmationProvider) Toolset is a toolset-level general wrapper: it applies to any toolset, not just MCP.

Lifecycle: who closes the connection#

mcptoolset.New only builds the object; the connection is lazy (established on the first Tools()/CallTool, rebuilt by the refresher when it drops). That implies:

  • startup will not fail because an MCP server is unreachable — the fault is deferred to the first tool call. In CI, call ts.Tools(ctx) once explicitly as a liveness probe.
  • There is no Close in Config, and the tool.Toolset interface has no close method either. A stdio server’s child process lifecycle follows the *mcp.Client/transport, so when you run several MCP servers long-term, hold the *mcp.Client yourself and inject it via Config.Client — that keeps the shutdown authority in your hands.

Frequently Asked Questions

How does ADK Go 2.x connect to an MCP server?

mcptoolset.New(mcptoolset.Config{Transport: …}) or Config{Endpoint: "https://…"} returns a tool.Toolset, which you put into llmagent.Config.Toolsets.

What happens if I set both Transport and Endpoint?

Endpoint only takes effect when Transport is nil (source: when set and Transport is nil, builds a streamable HTTP transport). With Transport set, Endpoint is ignored.

What does Config.Auth do?

auth.CredentialProvider injects credentials into every outbound HTTP request through a context-aware RoundTripper, and it only works with a streamable HTTP transport; pairing it with stdio is a configuration error.

Can I use Auth and my own transport's OAuthHandler together?

No. The source states that Auth is applied last and overwrites the Authorization header, so the two fight over the same request. Pick one.

What happens when the MCP connection drops?

mcptoolset wraps the client in a connectionRefresher: when CallTool/ListTools fails with what it classifies as a connection error, it rebuilds the session and retries (withRetry). You do not reconnect yourself.

How do I expose only part of an MCP server's tools?

Use tool.FilterToolset(ts, tool.StringPredicate(names)). mcptoolset.Config.ToolFilter is Deprecated.
