Chat UI and the wire protocol: /run, /run_sse, /run_live, and the Dev UI pieces ADK Go leaves unimplemented

The server/adkrest wire layer of ADK Go v2.4.0: how the three runtime endpoints differ (POST /run, POST /run_sse with its SSE frame format and write deadline, GET /run_live with WebSocket frames and a hardcoded LiveRunConfig), the strict decoding of RunAgentRequest and that functionCallEventId which is accepted but ignored, what a per-request Runner means, the DevPrefix=/dev/apps/{app_name} v2 API split, and the three feature areas deliberately answered with 501 (including why 404 would be wrong).

September 26, 2026 · 14 min · 2771 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources server/adkrest/{adkrest.go,internal/routers/*,internal/models/*,controllers/*}, cmd/launcher/web/{web.go,webui/webui.go}.

Module 2 covered the launcher and module 7 article 1 covered in-process streaming. This article is the wire layer: what a frontend actually has to talk to.

1. The three runtime paths#

server/adkrest/internal/routers/runtime.go declares exactly three routes:

Route nameMethodPathShape
RunAgentPOST/runone-shot JSON returning []*session.Event
RunAgentSsePOST/run_ssetext/event-stream, event by event
RunAgentLiveGET/run_liveWebSocket (gorilla/websocket)

The request body (models.RunAgentRequest):

type RunAgentRequest struct {
	AppName    string        `json:"appName"`
	UserId     string        `json:"userId"`
	SessionId  string        `json:"sessionId"`
	NewMessage genai.Content `json:"newMessage"`
	Streaming  bool          `json:"streaming,omitempty"`
	StateDelta *map[string]any `json:"stateDelta,omitempty"`
	// FunctionCallEventID identifies the event whose function call this
	// request answers (e.g. a human-in-the-loop reply from the web UI).
	// Accepted for adk-python parity but currently ignored; declared so
	// strict decoding (DisallowUnknownFields) does not reject the request.
	FunctionCallEventID *string `json:"functionCallEventId,omitempty"`
}

Four decoding facts you must know:

  1. appName / userId / sessionId / newMessage are all required non-empty (AssertRunAgentRequestRequired); missing any one gives an immediate 400.

  2. Decoding uses DisallowUnknownFields() — one extra field and the whole request 400s. This is where cross-language alignment breaks most often, and it is exactly why functionCallEventId must be declared (the comment says it exists only so strict decoding does not reject the request).

  3. ⚠️ functionCallEventId is currently ignored. So a HITL reply cannot rely on this field; turn it into a FunctionResponse part inside newMessage:

    newMessage: genai.Content{
    Role: genai.RoleUser,
    Parts: []*genai.Part{{FunctionResponse: &genai.FunctionResponse{
        ID:     "<the FunctionCall.ID from the earlier event>",
        Name:   "adk_request_input",       // or adk_request_confirmation
        Response: map[string]any{"confirmed": true},
    }}},
}

    Matching the ID is the only routing key (module 3’s confirmation flow and module 5’s adk_request_input both dispatch by ID).

  4. Streaming only starts with streaming:true: in getRunner it is literally

    streamingMode := agent.StreamingModeNone
if req.Streaming { streamingMode = agent.StreamingModeSSE }

    One more easily missed consequence: agent.RunConfig sets only StreamingMode here — SaveInputBlobsAsArtifacts is always false over REST. If you want uploaded images saved as artifacts automatically, the REST path cannot do it; you must move them yourself between frontend and backend.

2. The actual shape of an SSE frame#

RunSSEHandler’s complete behaviour (in source order):

rc := http.NewResponseController(rw)
deadline := time.Now().Add(c.sseTimeout)
rc.SetWriteDeadline(deadline)          // ① per request, overriding the server-wide timeout
// … decoding, authz.CanActAsUser, validateSessionExists and getRunner all happen before headers are set

rw.Header().Set("Content-Type", "text/event-stream")
rw.Header().Set("Cache-Control", "no-cache")
rw.Header().Set("Connection", "keep-alive")
rc.Flush()                             // ② flush immediately so a dropped client connection is noticed

for event, err := range r.Run(...) {
	if err != nil {
		if errors.Is(err, compaction.ErrCompaction) { log.Printf(…); continue }  // ③
		flashErrorEvent(rc, rw, err)                  // ④
		continue
	}
	if event == nil { continue }
	marshalledData, _ := json.Marshal(models.FromSessionEvent(*event))
	flashEvent(rc, rw, string(marshalledData))        // ⑤ one flush per event
}
#BehaviourWhat it means for you
①SSE has its own write timeout (the sseTimeout field), commented as a per-request override of the server-wide timeoutthis is what to tune for long jobs: web api exposes it as -sse-write-timeout (default 120s), and the reverse proxy’s proxy_read_timeout must be relaxed together with it
②validate first, then set headers, and flush right aftervalidation failures can still return a normal HTTP status; once you are inside SSE, errors can only travel as event: error
③compaction.ErrCompaction is logged only, never sentthe comment’s reason: “Streaming an error event here would tell a client its answer failed after it has already received it.” (the wire-layer counterpart of module 4’s “compaction is bookkeeping, not conversation”)
④an error frame is two lines: event: error\n + data: {"error":"…"}\n\nthe client must handle event: error separately, not treat it as ordinary data
⑤a normal frame is data: <event JSON>\n\none event at a time, flushed immediately
—a marshal failure → return (disconnect); a failing flashErrorEvent → returnan answer already delivered to the client is never retroactively re-judged

The event JSON’s fields come from models.FromSessionEvent, and note that it flattens LLMResponse’s fields to the top level:

type Event struct {
	ID           string           `json:"id"`
	InvocationID string           `json:"invocationId"`
	Branch       string           `json:"branch,omitempty"`
	Author       string           `json:"author"`
	Partial      bool             `json:"partial,omitempty"`
	LongRunningToolIDs []string   `json:"longRunningToolIds,omitempty"`
	Content      *genai.Content   `json:"content"`
	TurnComplete bool             `json:"turnComplete,omitempty"`
	Interrupted  bool             `json:"interrupted,omitempty"`
	ErrorCode    string           `json:"errorCode,omitempty"`
	ErrorMessage string           `json:"errorMessage,omitempty"`
	FinishReason genai.FinishReason `json:"finishReason,omitempty"`
	ModelVersion string           `json:"modelVersion,omitempty"`
	InputTranscription  *genai.Transcription `json:"inputTranscription,omitempty"`
	OutputTranscription *genai.Transcription `json:"outputTranscription,omitempty"`
	Actions      EventActions     `json:"actions"`
	Output       any              `json:"output,omitempty"`
	NodeInfo     *session.NodeInfo `json:"nodeInfo,omitempty"`
}

This is the frontend parsing contract. Three points:

  • partial / turnComplete (the two fields from article 1) are not inside a nested llmResponse, they are top level;
  • the wire key for nodeInfo is nodeInfo (camelCase) — when writing TS types, do not guess from the Go field name;
  • a graph workflow’s final product is the top-level output, and actions.compaction lives inside actions.

The minimal working frontend parser (TS):

const res = await fetch('/run_sse', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ appName, userId, sessionId, streaming: true,
                         newMessage: { role: 'user', parts: [{ text: prompt }] } }),
});
const reader = res.body!.getReader();
const dec = new TextDecoder();
let buf = '';
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  buf += dec.decode(value, { stream: true });
  let i;
  while ((i = buf.indexOf('\n\n')) >= 0) {       // frames are separated by a blank line
    const frame = buf.slice(0, i); buf = buf.slice(i + 2);
    let name = 'message', data = '';
    for (const line of frame.split('\n')) {
      if (line.startsWith('event: ')) name = line.slice(7);
      else if (line.startsWith('data: ')) data += line.slice(6);
    }
    if (name === 'error') { showError(JSON.parse(data).error); continue; }
    const ev = JSON.parse(data);
    if (ev.partial) appendToTypewriter(ev.content?.parts?.[0]?.text ?? '');
    else replaceMessage(ev.author, ev.content?.parts?.[0]?.text ?? '');  // replace wholesale!
  }
}

⚠️ Do not use EventSource — it supports only GET and no custom body. Parse by hand with fetch + ReadableStream (the code above).

3. /run_live: WebSocket frames and a hardcoded configuration#

q := req.URL.Query()
appName := q.Get("appName"); if appName == "" { appName = q.Get("app_name") }
// userId / sessionId likewise accept both spellings

Parameters travel in the query string, and both camelCase and snake_case are accepted. Missing any of the three → appName, userId, and sessionId are required (this happens before the Upgrade, so it is an ordinary HTTP error).

Client → server, two frame types:

FrameMapping
Binaryagent.LiveRequest{RealtimeInput: &genai.Blob{MIMEType: "audio/pcm;rate=16000", Data: p}}
Text (JSON models.LiveRequest){content, blob, activityStart, activityEnd, close}
type LiveRequest struct {
	Content       *genai.Content       `json:"content,omitempty"`
	Blob          *blob                `json:"blob,omitempty"`          // {mime_type, data}
	ActivityStart *genai.ActivityStart `json:"activityStart,omitempty"`
	ActivityEnd   *genai.ActivityEnd   `json:"activityEnd,omitempty"`
	Close         bool                 `json:"close,omitempty"`
}

Text frame precedence (the source’s if-else chain, exactly one is honoured): ActivityStart > ActivityEnd > Blob. close:true breaks the read loop immediately.

⚠️ The binary frame’s MIME is hardcoded: audio/pcm;rate=16000. Any other sample rate or encoding must go through blob.mimeType in a text frame.

Server → client: ws.WriteJSON(models.FromSessionEvent(*event)) — the same event schema as SSE, so your event parsing code is reusable.

The configuration line is the real limitation:

liveSession, eventIter, err := r.RunLive(req.Context(), userID, sessionID, agent.LiveRunConfig{
	MaxLLMCalls:              100, // Reasonable default
	ResponseModalities:       []genai.Modality{genai.ModalityAudio},
	InputAudioTranscription:  &genai.AudioTranscriptionConfig{},
	OutputAudioTranscription: &genai.AudioTranscriptionConfig{},
})

These four values are hardcoded server-side and cannot be passed by the client (/run_live takes no config parameter). To change the voice, SpeechConfig, EnableAffectiveDialog, Proactivity or SaveLiveBlob, there are only two options: write your own handler calling Runner.RunLive directly, or add a custom router to adkrest.

The shutdown path is worth copying as well: sendClose sets SetReadDeadline(now+1s) and then drains the remaining messages — the WebSocket “send close, then receive the client’s close” handshake; implement it the same way or you will get broken pipe.

4. Route layering: the /dev/apps/{app_name} prefix#

One constant in internal/routers/routers.go tells the whole history of the v2 API split:

// DevPrefix is the path prefix ADK v2 clients use for developer-only
// endpoints: evaluation, tracing, the agent builder and the tests tab.
//
// ADK split its API in two at v2. Production endpoints keep their original
// paths, while everything a developer tool needs moved under
// /dev/apps/{app_name}/. The ADK web UI has addressed these endpoints this way
// since then, so a route reachable only at the pre-v2 path is unreachable from
// the UI.
const DevPrefix = "/dev/apps/{app_name}"

This is the sharpest migration issue: a backend that registers only the pre-v2 path (for example /debug/trace/{event_id}) means the Dev UI cannot open the trace view — the UI requests /dev/apps/{app}/debug/trace/session/{sid}.

The actual route table for comparison (both sets are registered in the official build, and that is the point):

CapabilityProduction pathDev path
session traceGET /debug/trace/session/{session_id}GET /dev/apps/{app}/debug/trace/session/{session_id}
event traceGET /debug/trace/{event_id}GET /dev/apps/{app}/debug/trace/{event_id}
event graphGET /apps/{a}/users/{u}/sessions/{s}/events/{e}/graphGET /dev/apps/{a}/users/{u}/sessions/{s}/events/{e}/graph
agent graphGET /dev/apps/{a}/build_graph, /build_graph_image—
apps / sessionsGET /list-apps, /apps/{a}/users/{u}/sessions[/{s}] (full CRUD)—
artifactsGET/DELETE /apps/{a}/users/{u}/sessions/{s}/artifacts[/{name}[/versions/{v}]]—
versionGET /version—

What a Chat UI minimally needs: /list-apps to pick an application → POST /apps/{…}/sessions to create a session → /run_sse to converse → GET …/artifacts/{name} to pull images/PDFs → GET /debug/trace/session/{sid} to debug.

⚠️ The last one is conditional: the debug routes are registered only when -include_debug_api is true (the flag comment: “will be included in the API if and only if the flag is set to true”). So the Dev UI’s trace view is unavailable by default — local debugging needs the switch, and production should leave it off (the next section explains why).

5. Three areas deliberately left undone: why 501 rather than 404#

The opening comment of controllers/devfeatures.go is the most careful handling of “not implemented” I have seen:

// This file answers the developer-only endpoints that the ADK web UI calls but
// ADK Go does not implement: evaluation, the agent builder, and the tests tab.
//
// They are registered rather than left unrouted on purpose. An unrouted path
// returns a bare 404 that a client cannot distinguish from talking to the wrong
// server or the wrong path prefix, and it hides the fact that the UI expects
// the endpoint at all. Registering them makes the gap explicit, gives each
// response a body a developer can read, and makes the behavior testable.

The three groups are handled differently, each with a stated reason:

Endpoint familyResponseReason
eval execution / tests501 Not Implemented + {"error":"<feature> is not implemented in ADK Go","detail":…}“501 tells a client the endpoint is recognised and the feature is missing, which is the difference between ’this server is a different version’ and ’this server cannot do that’.”
GET /dev/apps/{a}/metrics-info200 + {"metricsInfo":[]}“An empty list is the accurate answer and keeps the client from logging a transport error for a question that has a valid empty result.”
GET /dev/apps/{a}/builder (read config)200 + empty body (text/plain)“ADK Go agents are defined in Go code, so there is no editable configuration to hand back, and the UI reads an empty body as ’nothing to edit here’ and disables the builder toggle.”

There is also a war story that must be transcribed — it explains why the string “not installed” has to appear in eval’s detail:

// NotInstalledDetail is the marker the ADK web UI looks for to tell "this
// server cannot run evals" apart from "this eval run failed".
// … An earlier version of this file answered the eval endpoints with 404 instead,
// on the theory that the UI hides its Evals tab on a 404. It does not: the eval
// tab component emits that decision on a shouldShowTab output, and the side
// panel that hosts the component subscribes to four of its outputs but not that
// one. The signal goes nowhere, so 501 is used, consistently with every other
// unimplemented developer endpoint.
const NotInstalledDetail = "not installed"

Three conclusions:

  1. the UI decides “this server cannot run evals” by looking for the substring “not installed” in detail, not by status code. If you write your own backend against the ADK Web UI, that phrase must appear in detail.
  2. “404 hides the tab” is false — the comment records exactly why they went back to 501. Do not “optimise” this by intuition.
  3. if an empty answer is correct, do not raise an error (metrics-info, builder) — an error status manufactures meaningless transport-error logs on the client.

This design is worth lifting into your own projects outright. It is an order of magnitude more rigorous than the usual “not implemented, so 404 or 501, pick one”.

6. The webui sub-launcher: the UI is embedded in your binary#

cmd/launcher/web/webui/webui.go:

//go:embed distr/*
var content embed.FS

The Web UI’s static assets are compiled into your binary and mounted as a SubLauncher of the web launcher (Keyword() = "webui"). Hence:

go run ./yourapp web api            # API only
go run ./yourapp web api webui      # also mount the Dev UI

After startup it prints:

printer(fmt.Sprintf("       webui:  you can access API using %s%s", webURL, w.config.pathPrefix))

pathPrefix is configurable — when you mount under a subpath, both the UI’s asset base and the API prefix must change with it; do not only edit nginx. webui handles precisely that:

// rewriteBaseHref points the <base href> of index.html at pathPrefix.
replacement := []byte(`<base href="` + html.EscapeString(pathPrefix) + `"`)

The four flags of the api sub-launcher (all measured from the source’s flag definitions):

FlagDefaultPurpose
-path_prefix/apithe REST API prefix (registerAPIRoutes mounts under it)
-sse-write-timeout120sthe SSE write timeout
-webui_addresslocalhost:8080the UI origin allowed by CORS (a bare host+port is read as http://; * means any origin)
-include_debug_apifalse⚠️ comment verbatim: “debug endpoints are not safe to be used in production environment, do not set them to true in production.”

When prefixes diverge, the thing people forget is CORS: after moving the UI to another host, if -webui_address is not updated, the browser blocks /api/run_sse at the preflight (Access-Control-Allow-Methods is assembled by corsAllowMethods from the actual set of registered route methods).

For contrast, the api sub-launcher itself (cmd/launcher/web/api/api.go) mounts the adkrest route set. The two are sibling sub-launchers, not a containment relation — “UI + API” requires writing both keywords, api webui.

7. One Runner per request — why that is fine#

func (c *RuntimeAPIController) getRunner(req models.RunAgentRequest) (*runner.Runner, *agent.RunConfig, error) {
	curAgent, err := c.agentLoader.LoadAgent(req.AppName)
	r, err := runner.New(runner.Config{
		AppName: req.AppName, Agent: curAgent,
		SessionService: c.sessionService, MemoryService: c.memoryService,
		ArtifactService: c.artifactService, PluginConfig: c.pluginConfig,
		Compaction: c.eventsCompactionConfig, AutoCreateSession: c.autoCreateSession,
	})
	…
}

Two judgements:

  1. Safe: a Runner holds no session state — all of it lives in session.Service (module 4). Module 5 likewise confirmed that an agent instance can serve many sessions concurrently.
  2. Not free: every request performs LoadAgent + runner.New. agent.NewSingleLoader does not care, but if you configured agent.NewMultiLoader with a remote loader, or the agent constructor does heavy work (opening MCP connections, reading files), this hot path amplifies it. Under high concurrency, wrap a caching loader yourself.

Compaction is passed straight through from the server configuration — echoing module 4’s rule that launcher-level compaction is process-shared.

Checklist#

  • the frontend uses fetch with hand-parsed SSE, not EventSource
  • frames are split on \n\n, and the event: error branch is handled
  • partials accumulate, non-partial replaces wholesale (prevents doubled text)
  • HITL replies go through newMessage’s FunctionResponse, never depending on functionCallEventId
  • the request body carries no extra fields (DisallowUnknownFields)
  • sseTimeout and the reverse proxy’s read timeout are relaxed together (web api -sse-write-timeout, default 120s)
  • after moving the UI to another origin, -webui_address is updated (or CORS blocks at the preflight)
  • production never enables -include_debug_api
  • if blobs must become artifacts automatically, do not use REST (only a direct Runner call can set it)
  • dev-class endpoints are registered under both paths (/dev/apps/{app}/… plus the original)
  • a custom backend facing the Dev UI: unimplemented features answer 501 with detail containing “not installed”, and empty-answerable ones answer 200 with an empty value
  • Live: non-16k PCM audio goes through the text frame’s blob.mimeType; changing MaxLLMCalls or the voice requires your own handler

Frequently Asked Questions

How does a frontend consume a streamed answer from ADK Go?

POST /run_sse with streaming:true in the body, parsed as SSE frames (a data: line carrying one JSON object, terminated by a blank line). Note that the browser's native EventSource only supports GET, so you must parse it yourself with fetch + ReadableStream.

How are SSE errors delivered to the client?

An extra event: error line followed by data: {"error":"…"}. compaction.ErrCompaction is the exception — it is logged but never sent, because reporting failure after the client already received its answer would be misleading.

How do I answer a HITL prompt?

Do not use functionCallEventId — adkrest comments explicitly that it is accepted for adk-python parity and currently ignored. Put a FunctionResponse in newMessage.parts instead, with the ID matching the FunctionCall.ID from the earlier event.

Why do the Dev UI's Evals / Agent Builder / Tests tabs fail?

ADK Go does not implement those three, but deliberately registers the routes and answers 501 with {error, detail}. A 404 would leave clients unable to tell a wrong path from a missing capability, and the UI would not hide the tab.

How does realtime voice work?

GET /run_live?appName=&userId=&sessionId= upgrades to WebSocket. Binary frames are treated as 16k PCM audio automatically; text frames are JSON (content/blob/activityStart/activityEnd/close). The configuration is hardcoded server-side (MaxLLMCalls 100, audio output, two-way transcription).

Why is a new Runner built for every request?

adkrest's getRunner really does call runner.New per request. That is safe because a Runner holds no session state (it lives in session.Service), but note that the hot path also re-runs LoadAgent each time.
