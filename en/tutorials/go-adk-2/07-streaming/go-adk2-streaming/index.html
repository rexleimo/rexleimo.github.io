The three streaming layers: what Partial/TurnComplete really mean, the aggregator, and the half-contract that break discards

Streaming in ADK Go v2.4.0: the relationship between the model layer GenerateContent(ctx,req,stream bool), the event layer iter.Seq2, and the wire layer SSE/WebSocket; agent.StreamingMode exposing only none/sse with bidi hidden internally; what the LLMResponse.Partial note about the Runner fully processing only the final non-partial event implies; how streamingResponseAggregator buffers text, stitches thought signatures and rebuilds tool arguments from PartialArgs jsonPath; the full Event.IsFinalResponse() decision including why compaction events are excluded; and the subtle contract that compaction runs in a defer so early break still gets it.

September 26, 2026 · 16 min · 3285 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources model/llm.go, agent/run_config.go, agent/live.go, internal/agent/runconfig/run_config.go, internal/llminternal/stream_aggregator.go, session/session.go, runner/runner.go.

1. Separate the three layers first#

Most “why doesn’t streaming work” reports come from collapsing three layers into one.

LayerTypeOwner
model layermodel.LLM.GenerateContent(ctx, req, stream bool) iter.Seq2[*model.LLMResponse, error]the model adapter (gemini, openaimodel, apigee, yours)
event layerRunner.Run(...) iter.Seq2[*session.Event, error]the Runner plus flow processors
wire layerSSE data: {json}\n\n / WebSocket JSON framesserver/adkrest (article 2 )

stream is the third parameter of GenerateContent, not a separate interface. One model.LLM implementation carries both streaming and non-streaming:

type LLM interface {
	Name() string
	GenerateContent(ctx context.Context, req *LLMRequest, stream bool) iter.Seq2[*LLMResponse, error]
}

2. There is only one public switch value#

type StreamingMode string

const (
	// StreamingModeSSE enables server-sent events streaming, one-way, where
	// LLM response parts are streamed immediately as they are generated.
	StreamingModeNone StreamingMode = "none"
	StreamingModeSSE  StreamingMode = "sse"
)

type RunConfig struct {
	StreamingMode StreamingMode
	// If true, ADK runner will save each part of the user input that is a blob
	// (e.g., images, files) as an artifact.
	SaveInputBlobsAsArtifacts bool
}

The internal version in internal/agent/runconfig adds one value and one field:

type StreamingMode string
const (
	StreamingModeNone StreamingMode = "none"
	StreamingModeSSE  StreamingMode = "sse"
	StreamingModeBidi StreamingMode = "bidi"   // ← absent from the public package
)
type RunConfig struct {
	StreamingMode StreamingMode
	Live          *agent.LiveRunConfig
}

The only thing Runner.Run does with it is put it into the context:

ctx = runconfig.ToContext(ctx, &runconfig.RunConfig{
	StreamingMode: runconfig.StreamingMode(cfg.StreamingMode),
})

and the LLM flow reads it back to decide whether to pass stream=true or false to GenerateContent.

Three consequences:

  1. StreamingMode is a per-invocation parameter, not agent configuration. The same agent streaming this turn and not the next is perfectly legal.
  2. You cannot get bidi (Run’s signature only accepts agent.RunConfig). Bidirectional streaming belongs to RunLive, which hardcodes StreamingMode: runconfig.StreamingModeBidi, // Live is always bidirectional streaming.
  3. Whether a response streams is not decided by the launcher: adkrest computes agent.StreamingModeNone/SSE per request from the streaming field in the body (article 2 expands on this).

3. Partial: the Runner fully processes only the last one#

The comments on these two fields of model.LLMResponse are the ones worth memorising from this whole article:

// Partial indicates whether the content is part of a unfinished content stream.
// Only used for streaming mode and when the content is plain text.
// The Runner fully processes only the final non-partial event, partial
// events are simply forwarded downstream (eg. to UI for display).
Partial bool `json:"partial,omitempty"`

// Indicates whether the response from the model is complete.
// Only used for streaming mode.
TurnComplete bool `json:"turnComplete,omitempty"`

Broken into three rules:

RuleConsequence
Partial is meaningful only for plain texttool calls and function responses do not use partial semantics
the Runner fully processes only the final non-partial eventcallbacks, state deltas, tool execution and persistence all hang on that event
partial events are forwarded onlydo not expect word-by-word fragments in AfterModelCallbacks

So the correct division of labour is:

for ev, err := range r.Run(ctx, userID, sessID, msg, agent.RunConfig{StreamingMode: agent.StreamingModeSSE}) {
	if err != nil { return err }
	if ev == nil { continue }

	if ev.Partial {
		ui.AppendText(ev.Content.Parts[0].Text)   // feed only the typewriter effect
		continue
	}
	// non-partial: this is the authoritative version — persistence, billing and parsing all happen here
	final = ev
}

⚠️ A given character does not appear in a partial and then “again appended” in the final event — the final event carries the fully aggregated text (next section). If your UI accumulates partials and then also repaints from the final event, it must replace wholesale rather than append, or the text doubles. That is the number one streaming UI bug.

4. What the aggregator actually does#

The type comment of internal/llminternal/stream_aggregator.go:

streamingResponseAggregator aggregates partial streaming responses.
It aggregates content from partial responses, and generates LlmResponses for
individual (partial) model responses, as well as for aggregated content.

The state machine fields (copied verbatim, since they are the behaviour list):

usageMetadata     *genai.GenerateContentResponseUsageMetadata
groundingMetadata *genai.GroundingMetadata
citationMetadata  *genai.CitationMetadata
response          *model.LLMResponse

currentThoughtSignature []byte          // keeps the Gemini "thinking" signature across chunks

sequence             []*genai.Part
currentTextBuffer    string
currentTextIsThought bool
finishReason         genai.FinishReason

currentFunctionName             string
currentFunctionID               string
currentFunctionArgs             map[string]any
currentFunctionThoughtSignature []byte

Four behaviours worth noting:

  1. ProcessResponse can yield two responses at once — comment: “yields that result, also yielding an aggregated response if the GenerateContentResponse has zero parts or is audio data”. Audio and empty chunks trigger immediate aggregation, because audio cannot be rendered “token by token”.

  2. A text buffer plus Close() for the tail: Close generates an aggregated response at the end, if needed. There is always a complete text version at the end of the stream.

  3. Tool arguments are stitched segment by segment:

    for _, arg := range part.FunctionCall.PartialArgs {
    jsonPath := arg.JsonPath
    value, ok := s.getValueFromPartialArg(arg, jsonPath)
    s.setValueByJSONPath(jsonPath, value)   // writes back into a nested map along paths like "$.a.b[0]"
}

    The model side really does expose half-finished arguments (PartialArgs + JsonPath), but the aggregator assembles complete Args before handing them to tool execution. To show “arguments being generated” in a UI you must tap the model layer yourself — you will not find it at the event layer.

  4. thoughtSignature is maintained separately (one for text, one for function calls). Gemini’s thinking content binds a signature across chunks, and losing it makes the next request fail — if you write your own model adapter this is a mandatory lesson: do not copy only Text.

5. Deciding the terminal state: the full logic of IsFinalResponse()#

This is the function consumers should use most and implement wrongly most often. The full source:

func (e *Event) IsFinalResponse() bool {
	// A compaction event is bookkeeping rather than conversation: it carries a
	// record and no content of its own. It satisfies every clause below, so
	// without this a streaming client deciding what to show a user would surface
	// an empty final response every time compaction ran.
	if e.Actions.Compaction != nil {
		return false
	}
	if e.Actions.SkipSummarization || len(e.LongRunningToolIDs) > 0 {
		return true
	}
	return !hasFunctionCalls(&e.LLMResponse) &&
		!hasFunctionResponses(&e.LLMResponse) &&
		!e.LLMResponse.Partial &&
		!hasTrailingCodeExecutionResult(&e.LLMResponse)
}

Four tests, each with a trap:

TestMeaningTrap
Actions.Compaction != nil → falsea compaction event is bookkeepingdo not render it as an “empty answer” (the comment describes exactly that incident)
SkipSummarization, or LongRunningToolIDs non-empty → truelong-running tools / skipped summarisation also count as terminala long-running tool (async / delegation) declares terminal early, when the real result has not arrived yet
no functionCall / functionResponseonly pure text counts as an answertool turns do not
!Partialonly non-partial can be terminala partial chunk is never terminal ✓

One more line in the field comment is routinely overlooked:

Note: when multiple agents participate in one invocation, there could be
multiple events with IsFinalResponse() as True, for each participating agent.

A single turn may contain several “final answers” (one per participating agent). So do not write if ev.IsFinalResponse() { break } to “get the answer” — in a multi-agent scenario you would leave with the first agent’s reply. To end the whole turn, key off InvocationID plus your own “root agent terminal” test, or rely on the natural end signalled by yield returning false.

6. If I break out of the stream, does compaction still run?#

It does. This comment in runner.Run was written specifically for streaming consumers and deserves reading in full:

// Compaction has to happen however iteration ends. Breaking out of the
// range loop on the terminal event is the ordinary streaming idiom, and
// what the A2A executor does, so a hook placed only after the loop
// would never run for those callers and compaction would silently never
// happen. Deferring makes it unconditional.
//
// On an early exit the error cannot be yielded, because yield must not
// be called once it has returned false, so it is logged instead.

Three contracts:

  1. Compaction is inside a defer precisely to accommodate “break on seeing the terminal event”. An early exit does not lose compaction.
  2. The error is unavailable after an early exit — it can only go to server logs. So after a break, do not assume “no error means no error happened”.
  3. Once yield has returned false you must never call yield again (a hard rule of Go iter, restated in this comment). Custom producers violate it most often.

7. How errors travel through the stream#

The error in iter.Seq2[*session.Event, error] shares one cursor with the events:

for ev, err := range stream {
	if err != nil { /* terminate or degrade */ }
	if ev == nil { continue }   // when there is an error, ev may be nil
}

The source is full of if !yield(event, err) { return } and yield(nil, err) — that is what “an error is one more in-stream event” means here, and not panic semantics or channel-close semantics.

For consumers: never decide validity with if ev != nil alone; test err first. Module 4 made the same point about event persistence: the error handling in RangeEvents uses err != nil && ev != nil before breaking.

8. Live: bidirectional streaming is a different API#

func (r *Runner) RunLive(ctx context.Context, userID, sessionID string,
	cfg agent.LiveRunConfig, opts ...RunOption,
) (agent.LiveSession, iter.Seq2[*session.Event, error], error)

type LiveSession interface {
	Send(req LiveRequest) error
	Close() error
}

type LiveRequest struct {
	// RealtimeInput can be *genai.Blob, *genai.ActivityStart, or *genai.ActivityEnd.
	RealtimeInput any
	// Content represents standard text or multimodal content from the user.
	// Can also represent a reply to a tool call if it contains a FunctionResponse part.
	Content *genai.Content
}

Mind the signature: RunLive has no msg parameter — the source comment says // msg is nil for Live run as it's streaming. All input goes through LiveSession.Send.

The ten fields of LiveRunConfig (all passed straight through to Gemini Live):

type LiveRunConfig struct {
	ResponseModalities       []genai.Modality
	SpeechConfig             *genai.SpeechConfig
	InputAudioTranscription  *genai.AudioTranscriptionConfig
	OutputAudioTranscription *genai.AudioTranscriptionConfig
	RealtimeInputConfig      *genai.RealtimeInputConfig
	EnableAffectiveDialog    bool
	Proactivity              *genai.ProactivityConfig
	SessionResumption        *genai.SessionResumptionConfig
	SaveLiveBlob             bool
	MaxLLMCalls              int
}

Three worth singling out:

  • MaxLLMCalls: the model-call ceiling for a Live turn (prevents a voice loop). adkrest’s /run_live hardcodes MaxLLMCalls: 100, // Reasonable default — when you start Live over REST you cannot change this value; to change it, build the Runner yourself.
  • SaveLiveBlob: stores realtime audio blobs into artifacts. Defaults to false, and if you do not store them there is nothing to review afterwards.
  • SessionResumption + LLMResponse.SessionResumptionHandle: reconnecting after a drop continues via this handle instead of rebuilding the session.

Concurrency semantics (mentioned in module 6): LiveSession follows a single active child session model. sequentialagent’s implementation makes it clearest — it keeps an activeSess behind a mutex, so at any moment exactly one sub-agent’s live session is active:

if s.closed { return fmt.Errorf("session is closed") }
if s.activeSess == nil { return fmt.Errorf("no active sub-agent live session") }

So in a chained or sequential live orchestration, switching agents replaces the old child session, and calling Send on a stale LiveSession produces one of these two errors.

Not every agent can run Live either: among Sequential/Parallel/Loop, only SequentialAgent implements RunLive (module 6, article 1), and adkrest performs a liveAgent, ok := ... assertion.

9. Three terminal-state rules in base_flow.go that appear in no documentation#

Everything above is “what the fields say”. These three are “what the runtime does”, all from internal/llminternal/base_flow.go, and each one explains a class of production oddity.

9.1 Final but no answer: a thinking-only turn re-calls the model#

const maxConsecutiveThoughtOnlyTurns = 10

if lastEvent.IsFinalResponse() {
	// A thought-only ("thinking") turn reports as final but has no
	// answer; don't stop on it — call the model again. Give up once
	// the model has produced only thoughts too many times in a row,
	// leaving the last thinking event as the result.
	if !isThoughtOnlyTurn(lastEvent) { return }
	thoughtOnlyTurns++
	if thoughtOnlyTurns >= maxConsecutiveThoughtOnlyTurns { /* give up, return the last thinking event */ }
}

Meaning: IsFinalResponse() == true does not guarantee a readable answer. A thinking model (thought parts without body text) reports final first, and the framework calls again, up to 10 times. So:

  • when you count “how many model calls this turn made”, thinking-only turns are extra consumption, not a bug;
  • receiving a final event with empty content or only thoughts at the frontend is a legal intermediate state (you only truly get one after the tenth abandoned attempt);
  • the log line produced %d consecutive thought-only turns without an answer (limit %d) — seeing it means the model is spinning, and you should change the model or the prompt.

9.2 A stream ending on a partial: this turn never enters session history#

if lastEvent.LLMResponse.Partial {
	// The last event is a partial streaming response. The realistic cause
	// is a producer that ends a stream without a terminal aggregate (e.g.,
	// an a2a peer whose stream ends on an appended artifact chunk with no
	// terminal status). The turn was truncated, not completed, which is
	// not expected, so we log a warning and return instead of looping again.
	log.Printf("adk: agent %q (invocation %q): step ended on a partial event from %q; the producer did not close its stream with an aggregated final event, so the turn will not appear in session history", …)
	return
}

Three conclusions:

  1. The framework neither retries nor errors: it logs a warning and returns. So this class of lost turn is entirely invisible at the API level — only the logs show it.
  2. The named likely cause: an A2A peer (a stream ending on an appended artifact chunk with no terminal status). Module 9 meets it again.
  3. turn will not appear in session history — when the next turn reads history, this passage simply does not exist, and the user perceives “it forgot what I just said”. If you write your own streaming producer (including a custom model.LLM or a custom A2A executor), you must close the stream with a non-partial aggregated event.

9.3 Tool results get copied into visible text (but confirmation tools do not)#

// SkipSummarization causes the parent agent loop to terminate on this
// event … without the LLM ever seeing the function response. Since most UIs
// don't render function response parts, attach the result as a visible text
// part so it isn't silently dropped from the terminal event.
//
// This only applies to tools that opt in via
// SkipSummarizationResultDisplayer (agenttool): SkipSummarization is
// also set by tools whose result is an internal detail never meant
// for display - e.g. a pending tool confirmation … or a UI/widget tool's
// acknowledgement - and those must not have their result leaked into
// a visible text part.
if actions := toolCtx.Actions(); actions.SkipSummarization {
	if displayer, ok := curTool.(toolinternal.SkipSummarizationResultDisplayer); ok && displayer.DisplayResultOnSkipSummarization() {
		if text, ok := displayableToolResultText(result); ok {
			parts = append(parts, &genai.Part{Text: text})   // one extra text part on the same event
		}
	}
}

Four facts:

FactImpact
a tool result event may carry both a functionResponse and a text partfrontends that read parts[0] intermittently land on the functionResponse and “see no answer” — iterate the parts
only when the tool explicitly opts in via DisplayResultOnSkipSummarization() (agenttool does)ordinary tools get no extra copy, so do not depend on it
pending confirmations (RequestedToolConfirmations) and widget tools deliberately do notthe comment’s words: “must not have their result leaked into a visible text part” — this is leak prevention, not a missing feature
tool errors are read from result["error"] (accepting both error and string)return map[string]any{"error": err} from a tool is treated as a tool error, not an ordinary result

Two more hard facts read from the same function, worth memorising while we are here:

  • the tool result event’s Content.Role is "user" (not "model") — a UI that filters messages by role will attribute the tool echo to the user.
  • result == nil plus the tool’s DefersResponse() or IsLongRunning() → returns directly with no functionResponse event (module 6’s task delegation relies on exactly this).
  • ev.Actions.Compaction = nil — confirming module 4 once more: a Compaction written by a tool is erased.

10. Supporting streaming in a custom model#

When you implement model.LLM, the entire streaming contract is your responsibility:

  1. with stream=true, yield chunk by chunk, one *LLMResponse per chunk;
  2. set Partial: true on intermediate chunks, and the last plain-text chunk must be Partial: false carrying the complete text;
  3. set TurnComplete: true when the turn ends;
  4. attach usage/citations/grounding to the final response (the aggregator accumulates usageMetadata);
  5. on error, yield(nil, err) — do not keep yielding after returning an error;
  6. if you use Gemini thought signatures, pass them through verbatim, or the next request 400s.

Implement against contracts 1–4 above, and add the hard requirement from 9.2: the stream must close with a non-partial aggregated event, or the whole turn never enters history.

The reference implementations to compare against are model/gemini and model/openaimodel (the latter also has to handle “OpenAI has no thought signature”).

11. The minimal correct consumer#

func streamAnswer(ctx context.Context, r *runner.Runner, userID, sessID string, msg *genai.Content) (string, error) {
	var final string
	var sb strings.Builder
	breakSeen := false

	for ev, err := range r.Run(ctx, userID, sessID, msg, agent.RunConfig{
		StreamingMode: agent.StreamingModeSSE,
	}) {
		if err != nil {
			// in-stream error: after an early exit the error may only live in server logs, so best effort here
			return "", fmt.Errorf("stream: %w", err)
		}
		if ev == nil {
			continue
		}
		if ev.Partial {
			sb.WriteString(textOf(ev))    // accumulate partials only
			continue
		}
		breakSeen = true
		final = textOf(ev)                // non-partial: replace wholesale, never append
	}
	if final == "" && breakSeen {
		final = sb.String()               // fallback for a stream that ended on partials
	}
	return final, nil
}

Every point comes from the sections above: accumulate partials, replace on non-partial, test err first, skip ev == nil, and do not break inside the stream (if you really must stop, return out of the range so the deferred compaction still runs).

Checklist#

  • business logic hangs only on non-partial events
  • the UI accumulates partials and replaces wholesale on the final event (never appends)
  • terminal state is decided with IsFinalResponse(), accepting “several terminals per turn”
  • compaction events are never rendered as an answer (skip when Actions.Compaction != nil)
  • in the consumer loop, err is tested before ev != nil
  • when blobs must reach artifacts, set RunConfig.SaveInputBlobsAsArtifacts
  • Live: SaveLiveBlob decides whether audio is kept, MaxLLMCalls is a hard ceiling, and an old LiveSession is discarded after switching agents
  • a custom model satisfies the six partial/turnComplete contracts

The wire layer — how this becomes SSE the browser can consume, and what the Chat UI actually implements — is in Chat UI and the wire protocol .

Frequently Asked Questions

Does the Runner process every chunk in streaming mode?

No. The comment on model.LLMResponse.Partial states that the Runner fully processes only the final non-partial event and that partial events are simply forwarded downstream (for example to the UI for display). So business logic belongs on the non-partial event, and only UI rendering looks at partials.

How do I know a turn is over?

On the event stream use Event.IsFinalResponse(); the wire JSON has a separate turnComplete field. Note that when several agents take part in one turn there can be several events with IsFinalResponse()==true, one per participating agent.

Why can't I see my compaction event in the stream?

Two layers of protection: IsFinalResponse() returns false immediately when Actions.Compaction != nil, and the adkrest SSE loop logs compaction.ErrCompaction without sending it. Compaction is bookkeeping, not conversation content.

Why is there no bidi in agent.StreamingMode?

The public constants are only StreamingModeNone and StreamingModeSSE. bidi lives in the internal runconfig and is forced only by Runner.RunLive — bidirectional streaming is exclusive to Live and cannot be turned on through Run.

Can I watch tool arguments being generated?

At the model layer yes (PartialArgs with jsonPath arrive segment by segment), but the aggregator stitches them into complete args before handing them over. Business code therefore sees complete arguments; only the UI side needs to care about half-finished ones.

Is it safe to break out of the event stream early?

It is safe, with a half-contract: compaction runs inside a defer precisely to accommodate the common 'break on the terminal event' idiom (the A2A executor does exactly that). When you write your own consumer loop, also stop relying on yield after a break.
