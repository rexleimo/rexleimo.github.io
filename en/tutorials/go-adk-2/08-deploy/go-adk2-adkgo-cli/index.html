The `adkgo` CLI: a command that only deploys, and the Dockerfile it generates for you

A complete tour of cmd/adkgo in ADK Go v2.4.0: it has only the deploy branch (two targets, cloudrun and agentengine, registered via blank imports), the Dockerfile cloudrun generates is distroless plus a CMD invoking web on the server port (so your entry point must accept the web subcommand), the relationship between the local authenticating proxy on 8081 and a2a_agent_url, the six switches --a2a/--api/--webui/--debug_api/--pubsub/--eventarc, agentengine's source archive upload and its three memory bank flags, and why there is no adk run / adk web / adk eval.

September 26, 2026 · 9 min · 1721 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources cmd/adkgo/{adkgo.go,internal/root/root.go,internal/deploy/*}.

1. It really only has deploy#

The entire meaningful content of cmd/adkgo/adkgo.go:

package main

import (
	_ "google.golang.org/adk/v2/cmd/adkgo/internal/deploy/agentengine"
	_ "google.golang.org/adk/v2/cmd/adkgo/internal/deploy/cloudrun"
	"google.golang.org/adk/v2/cmd/adkgo/internal/root"
)

func main() { root.Execute() }

The root command:

var RootCmd = &cobra.Command{
	Use:   "adkgo",
	Short: "CLI tool for use with ADK-GO",
	Long:  `adkgo is a CLI tool which allows developer to quickly deploy and test an agentic application`,
}

The deploy command itself:

var DeployCmd = &cobra.Command{
	Use:   "deploy",
	Short: "Makes deployment to various platforms easy",
	RunE: func(cmd *cobra.Command, args []string) error {
		if len(args) == 0 { return cmd.Help() }   // no target given, print help
		return nil
	},
}
func init() { root.RootCmd.AddCommand(DeployCmd) }

So the command tree is three levels: adkgo → deploy → {cloudrun, agentengine}. The two targets register themselves by calling deploy.DeployCmd.AddCommand(...) in their own init(), and the main file triggers that through empty imports — to add a third deployment target, write a package and add one blank import, which is a deliberate plugin design.

Three “there is none” facts to know in advance (anyone coming from 1.x or from the Python version will ask):

ExpectationReality
adkgo run / adkgo web (run locally)none. Local development is your own main.go + cmd/launcher: go run ./myagent console, ... web api webui (module 2, article 3 )
adkgo scaffold / new (generate a skeleton)none. Create the module and main.go by hand (module 1, article 2 )
adkgo eval (evaluation)none, and ADK Go does not implement evaluation at all — adkrest registers the eval endpoints as 501 with "not installed" in detail (module 7, article 2 )

⚠️ The root command’s Long says “deploy and test”, yet there is no test or eval subcommand — that description is stale, do not treat it as a contract.

2. Installation#

go install google.golang.org/adk/v2/cmd/adkgo@v2.4.0
adkgo deploy --help

cmd/adkgo is a standalone main package, so go install <path>@<version> is the cleanest — do not go get it into your project, which would drag the Cloud Run / Agent Engine SDK dependencies (cloud.google.com/go/clouddeploy, aiplatform, …) into your go.mod just to fetch a CLI.

Both targets require gcloud installed and authenticated locally (--project_name / --region are jointly required, both default to the empty string in the source, and omitting them fails only at the deployment stage).

3. deploy cloudrun: local compile + distroless image + authenticating local proxy#

The command description (verbatim):

Deployment prepares a Dockerfile which is fed with locally compiled server
executable containing Web UI static files.
Service on Cloudrun is created using this information.
Local proxy adding authentication is started.

Three actions: ① compile locally a server executable containing the Web UI static files; ② create the service from the Dockerfile it generates; ③ start an authenticating local proxy.

The generated Dockerfile (these are literally the lines concatenated in the source)#

FROM gcr.io/distroless/static-debian11
COPY <execFile>  /app/<execFile>
EXPOSE <server_port>
CMD ["/app/<execFile>", "web", "-port", "<server_port>"]

Four consequences, each of which can spare you one failed deployment:

  1. there is no shell, no curl, no apt in distroless/static. In-container diagnosis relies on logs only — do not plan on exec -it /bin/sh.
  2. The CMD carries web -port <port> — your entry point must be a launcher that can parse the web subcommand (universal/web), not a bare server calling ListenAndServe itself. Otherwise the image comes up with unknown command "web". This is the most common cause of cloudrun deployment failure.
  3. EXPOSE/server_port must match Cloud Run’s actual port:
    adkgo deploy cloudrun --server_port 8080 ...
  4. Web UI static assets are embedded at compile time (//go:embed distr/*, discussed in module 7), so there is no static/ directory to mount in the image and no replaceable frontend files.

Every flag (copied from the source, with defaults)#

FlagShortDefaultMeaning
--project_name-pemptythe GCP project
--region-remptythe GCP region
--service_name-semptythe Cloud Run service name
--temp_dir-temptybuild temp directory, defaults to os.TempDir() (the Dockerfile is written there)
--entry_point_path-eemptypath to the entry main
--server_port8080the cloud service port
--proxy_port8081the local proxy port
--a2atrueenable the A2A sub-router
--a2a_agent_url-ahttp://127.0.0.1:8081the URL advertised for this agent in the public agent card
--apitrueenable the REST API
--webuitrueenable the Web UI
--debug_apifalseenable the Debug API (requires --api)
--pubsubfalsemount the PubSub trigger sub-router
--eventarcfalsemount the Eventarc trigger sub-router
--pubsub_max_retries / _base_delay / _max_delay / _max_concurrent_runs3 / 1s / 10s / 100PubSub trigger retries and concurrency
--eventarc_max_retries / _base_delay / _max_delay / _max_concurrent_runsas aboveEventarc trigger (the two parameter sets are independent)

Three things people misread:

  • A2A is on by default (--a2a defaults to true), which means the api/webui/a2a sub-routers are all mounted on the same web server unless you say otherwise. To avoid exposing A2A, pass --a2a=false explicitly.
  • The default of --a2a_agent_url is the local proxy address (127.0.0.1:8081). This value is written into the public agent card — leave it alone and other agents receive your laptop’s address, so cross-machine calls must fail. At deploy time it should be the Cloud Run public URL.
  • --debug_api and the triggers are separate switches, but adkrest’s own words about the debug endpoints are “not safe to be used in production environment” — do not enable it in the cloud.

4. deploy agentengine: source archive upload with in-place update#

Deploys the application to Agent Engine. It creates a source archive, uploads it
to create a Reasoning Engine, and cleans up temporary files.

The mechanism difference from cloudrun is fundamental: cloudrun ships “a local build artifact plus an image”, agentengine “packs and uploads source, and lets the service build the Reasoning Engine”.

FlagShortDefaultMeaning
--project_name-pemptyas above
--region-remptyas above
--name-semptythe Agent Engine name
--temp_dir-temptytemp directory (for packing)
--server_port8080the service port
--entry_point_path-eemptythe entry main
--source_dir-demptythe directory to archive, defaults to the current working directory
--agent_engine_idemptyif given, updates that instance in place; otherwise creates a new one
--mem_deployfalsealso deploy a memory bank
--mem_modelpublishers/google/models/gemini-2.5-flashthe memory generation model
--mem_ttl8760h (365 days)memory TTL

Four practical points:

  1. It archives the current working directory by default. Running from a monorepo root uploads unrelated content — pass --source_dir explicitly, and confirm .gitignored build output is not inflating the archive.
  2. --agent_engine_id is the update switch. In CI, record the ID returned by the first deployment (or look it up before passing it), otherwise every run creates a new instance.
  3. The Go version constant used for building is defaultBuilderGoVersion = "latest". “latest” means non-reproducible: one day an upstream Go release changes behaviour and your deployment changes with it. If you need stability, control the build environment explicitly in your own pipeline (there is no flag for this constant).
  4. The three memory bank flags are an optional second step. --mem_deploy creates a memory bank alongside, and --mem_model defaults to gemini-2.5-flash (note: the memory generation model is a separate thing from the conversation model; it does not follow the agent). This also corresponds to the Vertex implementation of memory.Service in module 4 — only with mem_deploy does load_memory/preload_memory have hosted memory to talk to.

5. The whole deployment chain#

Drawing this chain is what lets you know which segment to inspect when it breaks:

your main.go (launcher/universal or web)
  └─ go build (local cross-compile, including the //go:embed frontend assets)
       └─ Dockerfile: distroless/static + COPY + CMD ["web","-port","8080"]
            └─ gcloud → the Cloud Run service
                 └─ local proxy (:8081, adding authentication) → your browser / Dev UI / agent card

One check per breakage point:

SymptomLook at
will not start, logs say unknown command "web"the entry point is not a launcher (consequence 2 in section 3)
the service is up but the UI is blankwhether --webui/--api were disabled, and whether -port matches --server_port
other agents cannot reach your A2A--a2a_agent_url is still 127.0.0.1:8081 (module 9 expands on the agent card)
messages lost after trigger 429s--pubsub/--eventarc not enabled, or trigger_max_retries too small (article 2 )

6. Working with CI#

adkgo depends on gcloud and a local Go toolchain, so in CI:

  1. Pin the Go version as described in module 0, article 3 (adk/v2 requires go 1.26.6+). Use setup-go with an explicit version in CI; do not rely on the image’s bundled Go.
  2. Authenticate gcloud with workload identity, and never commit key files to the repository (module 0’s privacy boundary applies to deployment as well).
  3. cloudrun performs a real go build on the CI machine, so CI build caching (GOCACHE/module cache) visibly affects deployment duration — several minutes on a cold run is normal.
  4. --temp_dir points at the system temp directory by default. In CI where temp space is tight (common on small runners), point it explicitly at a mount with capacity.

Checklist#

  • the entry point is a launcher/universal that accepts web -port N
  • --project_name / --region / --service_name are fixed in the script, never interactive
  • --a2a_agent_url is set to the public URL (or pass --a2a=false)
  • --debug_api stays false
  • agentengine: explicit --source_dir, and record --agent_engine_id for in-place updates
  • when you need event triggers, configure --pubsub/--eventarc together with the four retry parameters
  • in CI: Go version pinned, temp directory has room, gcloud uses workload identity

Frequently Asked Questions

Does adkgo have run / web / eval?

No. cmd/adkgo registers only the deploy command (in the v2.4.0 source the root has exactly two blank imports, agentengine and cloudrun). Development and preview use your own main plus cmd/launcher subcommands, and eval is simply not implemented in ADK Go.

Why write go install google.golang.org/adk/v2/cmd/adkgo@v2.4.0 rather than go get?

It is a standalone main package under cmd/, so a versioned go install is the cleanest route and keeps your project's go.mod untouched.

Does cloudrun deployment build a Docker image?

It first compiles a local executable with the Web UI static files embedded, generates a Dockerfile whose base is gcr.io/distroless/static-debian11, and hands that to Cloud Run. There is no shell in the image, and no tooling beyond CA certificates.

The UI will not open after deploying?

Check first whether --webui (default true) or --api (default true) was explicitly turned off, then remember the generated CMD is web -port <server_port>, so your entry point must be a launcher that parses the web subcommand, not a bare http.Server.

Can I enable --debug_api in production?

Not advisable. The flag description itself says it only makes sense with --api, and adkrest's own words about the debug endpoints are that they are not safe to be used in a production environment.

What is the biggest difference between the Agent Engine and Cloud Run deployments?

cloudrun is local compile + image + local authenticating proxy; agentengine packs and uploads your source and lets the service build a Reasoning Engine, adding --source_dir, --agent_engine_id (in-place update) and three memory bank switches.
