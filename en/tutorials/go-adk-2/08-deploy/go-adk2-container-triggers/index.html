Containers, session storage and triggers: one session per delivery, and Pub/Sub redelivers once 429s are exhausted

The event-triggered deployment surface of ADK Go v2.4.0: the message contracts of the /apps/{app_name}/trigger/pubsub and /trigger/eventarc endpoints (base64 data, attributes merged in, CloudEvents structured versus binary modes), userID coming from the subscription or event.Source, one session per delivery with retries reusing it, 429 detection by error-string containment, exponential backoff with half jitter, a 500 after exhaustion so the upstream redelivers, ErrCompaction being logged without NACKing, the fact that the concurrency semaphore is never wired in the Pub/Sub controller, and why compaction is nearly pointless on the trigger surface.

September 26, 2026 · 14 min · 2917 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources server/adkrest/controllers/triggers/{triggers.go,pubsub.go,eventarc.go,config.go}, cmd/launcher/web/triggers/{pubsub,eventarc}, server/adkrest/internal/models/triggers.go.

The previous article covered “how to push the service out”. This one covers how it gets invoked once deployed, and the semantics unique to the trigger surface.

1. Two endpoints, six switches#

How to start them (flags of adkgo deploy cloudrun, or the local web sub-launchers):

go run ./myagent web api webui pubsub eventarc
# when deploying: adkgo deploy cloudrun --pubsub --eventarc ...

The routes they register (both sub-launchers go through SetupSubrouters):

subrouter.HandleFunc("/apps/{app_name}/trigger/pubsub", controller.PubSubTriggerHandler).Methods(http.MethodPost)
subrouter.HandleFunc("/apps/{app_name}/trigger/eventarc", controller.EventarcTriggerHandler).Methods(http.MethodPost)

Both sit under {path_prefix}, default /api (each sub-launcher has its own -path_prefix defaulting to /api, with TrimSuffix("/") applied). So the full paths are:

POST /api/apps/{app_name}/trigger/pubsub
POST /api/apps/{app_name}/trigger/eventarc

After startup the sub-launcher prints the actual URL:

printer(fmt.Sprintf("       pubsub:  PubSub trigger endpoint is available at %s%s/apps/{app_name}/trigger/pubsub", webURL, p.config.pathPrefix))

Copy that into the Eventarc/PubSub subscription’s push endpoint, do not hand-assemble it — app_name is a path parameter read from the mux variables via appName(r); when it is missing the handler returns 500 (“no application name provided”), not 400.

The four flags at the sub-launcher layer (pubsub and eventarc each have their own set of same-named flags, independent):

FlagDefaultValidation (returns an error straight from Parse)
-path_prefix/apitrailing slash trimmed
-trigger_max_retries3must be > 0
-trigger_base_delay1smust be ≥ 0
-trigger_max_delay10smust be > 0
-trigger_max_concurrent_runs100must be > 0

Note that on the adkgo deploy cloudrun side the corresponding flag names are prefixed (--pubsub_max_retries / --eventarc_base_delay / …, see the previous article), and they end up in the same TriggerConfig.

2. Message → agent input: not a verbatim relay#

Pub/Sub push#

type PubSubTriggerRequest struct {
	Message      PubSubMessage `json:"message"`
	Subscription string        `json:"subscription"`
}
type PubSubMessage struct {
	Data        []byte            `json:"data"`  // comment: This will always be a base64-encoded string.
	MessageID   string            `json:"messageId"`
	PublishTime string            `json:"publishTime"`
	Attributes  map[string]string `json:"attributes,omitempty"`
	OrderingKey string            `json:"orderingKey,omitempty"`
}

Data []byte + JSON means Go base64-decodes automatically, so string(req.Message.Data) gives you the original bytes.

The content assembly rule (messageContentFromPubSub):

messageContent := make(map[string]any)
if len(req.Message.Data) > 0       { messageContent["data"] = string(req.Message.Data) }
if len(req.Message.Attributes) > 0 { messageContent["attributes"] = req.Message.Attributes }
if len(messageContent) == 0 { return "", fmt.Errorf("empty message data and attributes") }
agentMessage, _ := json.Marshal(messageContent)

Three consequences:

  1. the agent receives a JSON string: {"data":"…","attributes":{"k":"v"}}, not a bare payload. Write instructions expecting that wrapper (otherwise the model will busy itself “interpreting JSON”).
  2. attributes alone are legal — when all the event semantics live in attributes, this is exactly what you want.
  3. both empty → 400 (“empty message data and attributes”). Pub/Sub redelivers an empty message under its backoff policy, so watch for amplification.

Identity:

userID := req.Subscription
if userID == "" { userID = pubSubDefaultUserID }   // "pubsub-caller"

userID = the subscription name. Implication: every message under one subscription shares a single user-scope namespace (user: prefixed state, artifacts and memory all land on it). Do not expect per-business-principal isolation here — either carry the principal in the message and design explicit keys beyond app:, or use one subscription per tenant.

Eventarc / CloudEvents#

if contentType == "application/cloudevents+json" {
	// structured mode: the whole body is a CloudEvent, data lands in event.Data
	json.NewDecoder(r.Body).Decode(&event)
} else {
	// binary mode: the whole body is the data, read as raw bytes
	bodyBytes, _ := io.ReadAll(r.Body)
	event.Data = bodyBytes
}

then it forks:

// if data holds a Pub/Sub envelope, unwrap one layer and reuse the PubSub content assembly
if err := json.Unmarshal(event.Data, &pubsub); err == nil && (pubsub has content) {
	agentMessage, err = messageContentFromPubSub(pubsub)
} else {
	// otherwise serialise the whole CloudEvent and hand that to the agent
	messageBytes, err := json.Marshal(event)
}

So Eventarc has two input shapes whose behaviour differs:

UpstreamWhat you receiveWhat the agent actually sees
Eventarc ← Pub/Sub (most common)data is a Pub/Sub envelopeunwrapped into {"data":…,"attributes":…} — identical to the Pub/Sub channel
Eventarc ← other sources (Storage, Firestore, …)data is the business event bodythe JSON of the whole CloudEvent (including id/source/type/time/data)

The type comment on models.EventarcTriggerRequest.Data names this uncertainty exactly:

// In structured mode, ``data`` is always present.
// In binary mode, the entire body is the data (often a Pub/Sub wrapper).
// But sometimes it can be just a JSON object.

Conclusion: write the agent’s instruction assuming “input is a JSON document whose field structure varies”, and the most robust approach is to have the agent read the type field first to classify the event (in the whole-CloudEvent shape, type is inside it).

Identity: userID := event.Source. The source path becomes the user — events from one bucket/topic share a user scope, with the same “aggregate by source” semantics as the Pub/Sub line.

The status-code style differs slightly from the Pub/Sub channel: a binary-mode body read failure → 500; failing to split a Pub/Sub envelope out of data → 500; no extractable content → 400.

3. One session per delivery#

This is the most important semantics of the trigger surface, and the source comment explains it better than any documentation:

// RunAgent runs the agent for the given message and returns the resulting events.
func (r *RetriableRunner) RunAgent(ctx context.Context, appName, userID, messageContent string) ([]*session.Event, error) {
	// One session per delivery. Retries of that delivery reuse it, so a
	// throttled message accumulates invocations rather than starting over.
	sessResp, err := r.sessionService.Create(ctx, &session.CreateRequest{AppName: appName, UserID: userID})
	…
	userMessage := genai.Content{Role: "user", Parts: []*genai.Part{{Text: messageContent}}}
	curAgent, _ := r.agentLoader.LoadAgent(appName)
	runR, _ := runner.New(runner.Config{AppName: appName, Agent: curAgent, SessionService: r.sessionService,
		MemoryService: r.memoryService, ArtifactService: r.artifactService,
		PluginConfig: r.pluginConfig, Compaction: r.eventsCompactionConfig})
	return r.runAgentWithRetry(ctx, runR, sessResp.Session.UserID(), sessResp.Session.ID(), &userMessage)
}

Four consequences:

  1. There is no conversation history between messages. Every delivery is a new session, and {user:…} / {…} placeholders cannot see “the previous message”. For cross-message memory there are only two routes: memory.Service (load_memory / preload_memory), or you reuse session IDs by business key yourself — the trigger surface gives you no entry point for that (CreateRequest carries no State).
  2. Retries of one delivery share the session (“accumulates invocations rather than starting over”). So throttling retries are not idempotent: the second attempt sees the partial event history the first one wrote. The requirement “side effects must be idempotent” is especially hard on triggers.
  3. Message content travels as Parts: []*genai.Part{{Text: messageContent}} — a text part. Binary in Pub/Sub data does not become inlineData; it is turned into a string from bytes. To pass attachments: use artifacts and put a URI in the message (module 4).
  4. Every delivery performs LoadAgent + runner.New, as adkrest does (module 7, article 2). Under high trigger throughput these two are real cost, so the loader must cache.

4. The two-layer 429 retry contract#

// runAgentWithRetry uses exponential backoff with jitter to handle 429 rate-limit errors.
// After MaxRetries is exhausted, raises an error to signal the upstream service (Pub/Sub, Eventarc)
// to retry at a higher level.
for i := 0; i <= r.triggerConfig.MaxRetries; i++ {
	resp := runR.Run(ctx, userID, sessionID, userMessage, agent.RunConfig{StreamingMode: agent.StreamingModeNone})
	isThrottled := false
	for event, err := range resp {
		if err != nil {
			if errors.Is(err, compaction.ErrCompaction) { log.Printf("triggers: %v", err); continue }   // ①
			runErr = err
			if isResourceExhausted(err) { isThrottled = true }
			break
		}
		events = append(events, event)
	}
	if !isThrottled && runErr == nil { return events, nil }          // ②
	if i < r.triggerConfig.MaxRetries && isThrottled {
		time.Sleep(calculateBackoff(i, r.triggerConfig.BaseDelay, r.triggerConfig.MaxDelay))
		runErr = nil                                                 // ③
		continue
	}
	break                                                            // ④
}
return nil, runErr

Five points:

① A compaction failure does not NACK. The comment’s reason is blunt:

// A compaction failure is bookkeeping, not the delivery. The
// agent has already answered and its events are persisted, so
// failing here would NACK a message that was handled, and on
// Pub/Sub push that means redelivering work already done.

continue (rather than break) — keep consuming the event stream and finish the turn normally. This is the same judgement implemented twice, here and in module 7’s adkrest (log only, never send an error frame).

② StreamingModeNone. Triggers never stream — events are collected into a slice and the status code is decided afterwards. The partial semantics from the frontend do not exist here.

③ Only 429/ResourceExhausted retries. The test is string matching:

func isResourceExhausted(err error) bool {
	return err != nil && (strings.Contains(err.Error(), "429") || strings.Contains(err.Error(), "ResourceExhausted"))
}

⚠️ This is the fragile point: a throttling error whose message does not contain 429 / ResourceExhausted is treated as a permanent error (the break after ② → a single 500, with no in-process retry). If you implement your own model.LLM adapter, make sure your rate-limit errors carry one of those two strings, or you silently lose the backoff layer.

④ A non-throttle error fails immediately (break → return nil, runErr → HTTP 500 → upstream redelivers). So “should we retry” is something you can only keep managing upstream (the subscription’s dead-letter and retry policy).

⑤ The backoff formula:

backoff := float64(base) * math.Pow(2, float64(attempt))
delay := min(time.Duration(backoff), maxDelay)
jitter := time.Duration(rand.Float64() * float64(delay) * 0.5)
return delay + jitter

With the defaults: 1s→2s→4s, each plus 0–50% jitter, capped at 10s. Note that jitter is added after the cap, so a single wait can worst-case reach maxDelay * 1.5 (15s by default). A full delivery can block for ≈ 3 + 6 + 12 = 21s plus model time — this must be shorter than your subscription’s push timeout and the gateway timeout in front of --server_port, otherwise the upstream thinks it failed while this side is still running.

The response body is always:

type TriggerResponse struct {
	Status string `json:"status"`   // 'success' or error message
}

Success → 200 {"status":"success"}; failure → {"status":"<error text>"} with the corresponding status code. Do not judge success by HTTP 200 plus the status field — the status code is authoritative.

5. Concurrency limiting: one implementation fact#

Both controllers share the same skeleton:

if c.semaphore != nil {
	c.semaphore <- struct{}{}
	defer func() { <-c.semaphore }()
}

but only one side assigns the channel at construction:

// eventarc.go
func NewEventarcControllerWithConfig(cfg ControllerConfig) (*EventarcController, error) {
	…
	return &EventarcController{
		runner:    retriable,
		semaphore: make(chan struct{}, cfg.TriggerConfig.MaxConcurrentRuns),   // ✅ created
	}, nil
}

// pubsub.go
func NewPubSubControllerWithConfig(cfg ControllerConfig) (*PubSubController, error) {
	retriable := newRetriableRunner(cfg)
	if err := retriable.validateCompaction(); err != nil { return nil, err }
	return &PubSubController{
		runner: retriable,          // ⚠️ semaphore never assigned
	}, nil
}

I verified in the v2.4.0 source: PubSubController.semaphore has no assignment anywhere (only the declaration and the nil check), so -trigger_max_concurrent_runs has no effect on the Pub/Sub channel; it does work on the Eventarc channel. This is not design intent (the field and the guard are both still there, it is simply unwired), but this is the current behaviour, therefore:

  • do not expect --pubsub_max_concurrent_runs 50 to actually cap concurrency; control Pub/Sub push concurrency via the subscription’s max_delivery_attempts / ordering / your own limiter;
  • for real limiting, wrap the handler with your own semaphore (chan struct{} or golang.org/x/sync/semaphore) at the container entry point;
  • related: if MaxConcurrentRuns were 0, make(chan struct{}, 0) is an unbuffered channel — c.semaphore <- struct{}{} would block until someone reads, i.e. self-deadlock. The triggerMaxRuns <= 0 check in the sub-launcher’s Parse is what prevents this, so do not bypass the launcher and construct a TriggerConfig yourself without validating.

The flag description of --pubsub_max_concurrent_runs, “Maximum concurrent PubSub trigger runs”, does not match actual behaviour. This is an upstream defect awaiting a fix; check the source of your own version before relying on it.

6. Compaction is nearly pointless on the trigger surface#

The comment on ControllerConfig.Compaction is the clearest statement of this and deserves a full read:

// Note what a trigger surface is. A delivery gets a session of its own, so
// history does not accumulate across messages and a sliding window counting
// completed invocations has little to count. Tail retention works normally,
// because it measures the prompt inside a single run.

newRetriableRunner goes further and logs one advisory per sliding-window configuration (without refusing to start):

Your configurationLog contentMeaning
CompactionInterval == 1“fires on every delivery and writes a summary into a session that is discarded when the delivery ends. Use TokenThreshold and EventRetentionSize to compact within a single run.”a wasted summariser call whose product nobody reads
CompactionInterval > 1“a delivery handled in one attempt runs a single invocation, so the window will not reach its interval.”essentially never triggers (only a retried delivery has multiple invocations)

So the correct posture on triggers:

  1. do not enable compaction by default (leave Compaction nil). One message, one turn — there is nothing to compact.
  2. A single message can still cause many internal invocations (complex agents, many tools, retries) → to bound the prompt use tail retention: TokenThreshold + EventRetentionSize. It measures the prompt within one run and is unrelated to cross-delivery, so it works normally on triggers.
  3. Do not skip the construction-time validation: NewXxxControllerWithConfig calls validateCompaction() (internally compactionvalidate.AgainstAgents, checking the compaction configuration against the agents) and returns an error; the Launcher side turns it into a startup failure. The older NewXxxController (without WithConfig) discarded that error (c, _ :=) — which is why it is Deprecated, with the stated reason “which surfaces a configuration error instead of discarding it” and a note that it is “a candidate for removal at the next major version”. New code should always use the WithConfig variant.

7. Choosing session storage (container scenarios)#

Both triggers and web must persist sessions, and a container restart must not lose them:

OptionFitsNotes
session.InMemoryService()local dev, single-instance demolost on restart, invisible across instances — do not use in a container
session/database (GORM)Cloud Run / any containersee module 4, article 1 : database.NewSessionService(dialector) + database.AutoMigrate(svc); AutoMigrate only accepts *databaseService
session/vertexaiVertex AI Reasoning Enginevertexai.NewSessionService(ctx, VertexAIServiceConfig{ProjectID, Location, ReasoningEngine}); event IDs are assigned by the server and are not written back into the object

Matching module 8 article 1: adkgo deploy cloudrun uses the launcher configuration inside your own main — the CLI never assigns session/artifact/memory services for your launcher.Config. So before deploying, confirm your entry point is not NewInMemory: go run ./myagent web api webui pubsub works, but multi-instance Cloud Run with scale-to-zero will shred your sessions.

launcher.Config is the service injection point (fields: SessionService / ArtifactService / MemoryService / AgentLoader / PluginConfig / Compaction / Authenticator / Authorizer):

import (
	"gorm.io/driver/postgres"
	"gorm.io/gorm"

	"google.golang.org/adk/v2/agent"
	"google.golang.org/adk/v2/cmd/launcher"
	"google.golang.org/adk/v2/cmd/launcher/universal"
	"google.golang.org/adk/v2/cmd/launcher/web"
	"google.golang.org/adk/v2/cmd/launcher/web/api"
	"google.golang.org/adk/v2/cmd/launcher/web/triggers/eventarc"
	"google.golang.org/adk/v2/cmd/launcher/web/triggers/pubsub"
	"google.golang.org/adk/v2/session/database"
)

db, err := gorm.Open(postgres.Open(dsn), &gorm.Config{})
if err != nil { log.Fatal(err) }
sessSvc, err := database.NewSessionServiceFromDB(db)
if err != nil { log.Fatal(err) }

l := universal.NewLauncher(
	web.NewLauncher(
		api.NewLauncher(),            // required: it is how agentLoader/services reach adkrest
		pubsub.NewLauncher(),         // POST {prefix}/apps/{app}/trigger/pubsub
		eventarc.NewLauncher(),       // POST {prefix}/apps/{app}/trigger/eventarc
	),
)
if err := l.Execute(ctx, &launcher.Config{
	SessionService: sessSvc,
	AgentLoader:    agent.NewSingleLoader(root),
}, os.Args[1:]); err != nil {
	log.Fatalf("run failed: %v\n\n%s", err, l.CommandLineSyntax())
}

Three places people get wrong (all compile-verified on v2.4.0):

  1. web.NewLauncher(sublaunchers...) returns a launcher.SubLauncher, and you still need universal.NewLauncher(...) around it to get an executable launcher.Launcher; using full.NewLauncher() skips that (it already contains console + web, see module 2, article 3 ).
  2. The trigger sub-launchers live in cmd/launcher/web/triggers/{pubsub,eventarc}, not directly under cmd/launcher/web/. Their Keyword()s are pubsub / eventarc, so the command line is ... web pubsub eventarc.
  3. All three sub-launchers share the same SessionService and the same Compaction from launcher.Config — the “compaction is useless on triggers” finding from the previous section is a side effect of that global setting: if you enabled the sliding window for long web sessions, every delivery eats one extra summariser call and prints that advisory. Either use tail retention, or split into two entry points yourself.

Checklist#

  • the trigger endpoint URL is copied from the startup log, with app_name already in the path
  • the agent instruction is written assuming “input is JSON, may carry attributes, may be a whole CloudEvent”
  • cross-message memory uses memory.Service, not sessions
  • side effects are idempotent (retries of one delivery share the session and history accumulates)
  • rate-limit error text contains 429 or ResourceExhausted, otherwise backoff is lost
  • total in-process backoff < upstream push timeout and gateway timeout
  • do not rely on --pubsub_max_concurrent_runs; limit on the Pub/Sub side yourself
  • use NewXxxControllerWithConfig and handle the validation error it returns
  • no sliding-window compaction on triggers; use TokenThreshold + EventRetentionSize when the prompt must be bounded
  • in containers, sessions use database or vertexai, never InMemoryService

Frequently Asked Questions

Does one trigger message open a session?

Yes. RetriableRunner.RunAgent calls session.Create for every delivery, and retries of that delivery reuse it, so a throttled message accumulates invocations rather than starting over. History is not shared across messages.

Who is the userID?

PubSub uses req.Subscription (pubsub-caller when empty); Eventarc uses event.Source. That means every message under one subscription shares the same user-scoped state namespace.

How does message content become agent input?

Not verbatim. The controller composes data and attributes into {"data":"…","attributes":{…}} and JSON-marshals it, so the model sees a JSON document rather than a bare string.

How is 429 handled?

Two layers: in-process exponential backoff retries (default 3 attempts, 1s base, 10s cap, plus up to 50% jitter), and once they are exhausted or for a non-throttle error it answers 500 so Pub/Sub / Eventarc redeliver themselves.

Should I enable compaction for triggers?

Essentially no. One delivery is one session and most deliveries finish in one attempt, so a sliding window has nothing to compact. The source logs one advisory per interval shape (==1 and >1) and recommends TokenThreshold + EventRetentionSize instead.

Does MaxConcurrentRuns take effect?

It does for Eventarc (the constructor creates the semaphore channel); but the Pub/Sub WithConfig constructor never assigns the semaphore, so the handler's if c.semaphore != nil is always false and the cap is inert there. Add your own limiting if you need it.
