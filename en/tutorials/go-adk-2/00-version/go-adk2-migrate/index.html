Migrating 1.x → 2.x in Practice: Module Path, agent.Context, NewEvent(ctx)

A complete hands-on migration of ADK Go from 1.x to 2.x: go.mod and toolchain, import rewriting, adding ctx to session.NewEvent, agent.Context unification with StrictContextMock, rewriting orchestration as a graph, per-package verification and rollback strategy.

September 26, 2026 · 10 min · 2091 words · Mengshou Programming -  |  中文

Verified against: starting point v1.7.0, ending point v2.4.0; official migration doc google/adk-go/README-v2.md (text as of 2026-09-26).

The previous article covered what 2.0 has. This one covers how to move the code you already have across without breaking it.

First, good news most tutorials will not tell you: v1 and v2 are two different Go modules (google.golang.org/adk and google.golang.org/adk/v2), which means they can appear in the same go.mod simultaneously. So the correct posture is not a big-bang rewrite but a package-by-package canary migration.

The migration ledger: 4 mandatory + 1 optional#

#ItemMandatory?Automation level
1Raise the Go toolchain to 1.26.6+✅manual (CI image + local)
2Switch the dependency to adk/v2✅go get
3Add /v2 to every import✅scriptable
4session.NewEvent + test mocks✅the compiler lists every site
5Sequential/parallel/loop → graph engine⭕ optionalmust be hand-written

The first four are about making it compile; only the fifth makes it better. Do not invert that order: get it running first, then change the architecture.

Step 0: establish a baseline, do not go in naked#

Pin these three things before migrating, otherwise you will never tell “I broke it” apart from “it was already like that”:

git status --porcelain          # clean
go build ./...                  # must be green
go test -race ./... 2>&1 | tee /tmp/v1-baseline.log

For an event-driven library like ADK, tests you have not run are not tests. If the 1.x project has thin coverage, add a behaviour snapshot layer first: capture the event sequence (type/partial/stateDelta) of one full root-agent invocation as a goldenfile, then diff it byte for byte after migrating. This is my standard procedure for framework upgrades and it is an order of magnitude faster than debugging afterwards.

Step 1: the toolchain#

go version                       # check what you have now
# you need go1.26.6 or newer (current stable: go1.27.1)

Why raise the toolchain first? Because as soon as ADK’s go.mod says go 1.26.6, Go 1.24/1.25 stops you dead:

go: google.golang.org/adk/v2@v2.4.0 requires go >= 1.26.6 (running go 1.25.6; GOTOOLCHAIN=local)

With GOTOOLCHAIN=auto (the default) Go downloads the go1.26.6 toolchain itself; but CI environments behind restrictive networks often pin it to local (or block the proxy.golang.org delivery path outright), and then you stall on exactly that error. Two fixes:

# Option A: allow automatic toolchain delivery (needs module proxy access)
go env -w GOTOOLCHAIN=auto

# Option B: pin an explicit local toolchain (preferred in CI, predictable behaviour)
go env -w GOTOOLCHAIN=go1.27.1+auto

In a CI image the cleaner move is to change the base image:

# .github/workflows/ci.yml
container:
  image: golang:1.27.1        # stop using golang:1.24 / golang:1.25

Bump your own project’s go.mod too, otherwise the low version number emitted by go mod init will have “APIs that only exist in 1.26” blocked during go test by a newer vet check (from Go 1.27, go test runs stdversion by default, which reports exactly “you used a library API newer than your go directive”).

go get go@1.26.6    # or go@1.27.1

Step 2: switch the dependency to /v2 (keeping 1.x coexisting)#

go get google.golang.org/adk/v2@v2.4.0
go list -m all | grep 'golang.org/adk'

You should see both lines present, which is the normal state mid-migration:

google.golang.org/adk v1.7.0
google.golang.org/adk/v2 v2.4.0

Why keep 1.x deliberately: in a mid-sized project ADK imports usually scatter across 30-80 files. If you change them all and then compile, the error output becomes an unreadable wall. Keeping 1.x lets you “finish a package, compile a package”.

Step 3: rewrite the imports#

First see how much there is:

grep -rln '"google.golang.org/adk' --include='*.go' . | wc -l

Then batch-replace. Three requirements: the bare root package "google.golang.org/adk" (no trailing slash) must not be missed; the repository name google.golang.org/adk-go in comments/docs and https://google.golang.org/adk/... links must not be collateral damage; and lines already carrying /v2 must be skipped idempotently.

So the script below only touches lines whose entire shape is an import statement (aliased, _, and . forms are all covered). I ran it against sample files to verify:

#!/usr/bin/env perl
# adkimp.pl —— rewrite ADK Go import paths from 1.x to /v2, touching import lines only
use strict; use warnings;
my $total = 0;
while (my $l = <>) {
    if ($l =~ m{^(\s*(?:(?:[A-Za-z_][A-Za-z0-9_]*|_|\.)\s+)?)\"google\.golang\.org/adk((?:/[^\"]*)?)\"\s*$}) {
        my ($pre, $rest) = ($1, $2);
        my $path = $rest =~ m{^/v2(/|\z)} ? "google.golang.org/adk$rest"
                                         : "google.golang.org/adk/v2$rest";
        $total++ if $path ne "google.golang.org/adk$rest";
        $l = qq{$pre\"$path\"\n};
    }
    print $l;
}
print STDERR "rewritten import lines: $total\n";

git ls-files '*.go' | xargs perl -i adkimp.pl   # inspect with git diff first

# double-check: any 1.x imports left behind
grep -rn '"google\.golang\.org/adk"' --include='*.go' . | grep -v '/v2"'
grep -rn '"google\.golang\.org/adk/' --include='*.go' . | grep -v '/adk/v2/'

# confirm no collateral damage: repo names and links in comments should still be there
grep -rn 'adk-go' --include='*.go' .

When it finishes, run gofmt -l . for formatting and hand the rest to the compiler.

go fix will not help here. Go 1.26 rewrote go fix into “modernizers” (which, together with //go:fix inline, lets you express your own API migrations as rules), but it only understands the language and the standard library. ADK’s renames still need gopls plus the compiler.

Step 4: the two real breakages the compiler will point at#

4.1 session.NewEvent gained a ctx#

// v1
ev := session.NewEvent(ctx.InvocationID())
ev := session.NewEventWithContext(ctx, ctx.InvocationID())  // transitional form, removed in v2

// v2
ev := session.NewEvent(ctx, ctx.InvocationID())

The change itself is mechanical, but do not pass the wrong ctx. The official docs state explicitly that the event ID and timestamp are now decided by providers attached to the ctx (platform.WithTimeProvider / platform.WithUUIDProvider). Therefore:

// ❌ wrong: minting a fresh ctx mid-chain drops all provider injection,
//          and deterministic replay stops working
ev := session.NewEvent(context.Background(), ctx.InvocationID())

// ✅ right: pass the current agent.Context / context.Context straight through
ev := session.NewEvent(ctx, ctx.InvocationID())

agent.Context embeds context.Context, so the ctx agent.Context in your hand can be passed as the first argument directly. The rule matches the standard library: context.Background() appears only in main, init, and top-level test setup.

If a helper of yours does not accept a ctx yet, add a ctx context.Context parameter and pass it down from the caller. That is the only correct direction.

4.2 Context unification: your mocks break on the spot#

ToolContext and CallbackContext merge into a single agent.Context. Production code usually benefits (callbacks finally reach the tool-level things), but test code explodes first: an old MockCallbackContext implemented only the previous method set, so widening the interface turns it into a compile error.

Do not implement the methods by hand (the official guide offers this route, but it is purely reactive):

// every added method means editing the mock again: forever chasing the interface
func (m *MockCallbackContext) Actions() *session.EventActions { return nil }
func (m *MockCallbackContext) FunctionCallID() string { return "" }
// ...

Embed agent.StrictContextMock instead:

type fakeContext struct {
	agent.StrictContextMock
}

var _ agent.Context = (*fakeContext)(nil) // compile-time assertion against the unified interface

func TestSomething(t *testing.T) {
	cc := &fakeContext{agent.StrictContextMock{Ctx: t.Context()}}
	// override only the methods this case actually calls
}

Two reasons this is the better trade:

  1. Forward compatibility: when the interface gains methods later, embedders need no change.
  2. Failures stay loud: an unoverridden method panics with "not implemented", so a dirty call detonates immediately; a hand-written mock returns zero values silently and lets you pass tests for the wrong reasons.

While you are here, start using t.Context() (available since Go 1.24) — it cancels automatically at test end and is cleaner than context.Background().

Step 5 (optional): rewrite orchestration as a graph#

Once steps 1-4 pass, your 1.x semantics should be preserved as-is — agent/workflowagents/{sequential,parallel,loop}agent kept their paths in 2.x, but they are now built on the graph engine (in 1.x they were standalone implementations). So even if you do not rewrite anything, you must re-verify orchestration behaviour: iteration caps, when sub-agents transfer, Event.Routes semantics, and cancellation propagation across parallel branches.

What is genuinely worth rewriting into workflowagent + a graph:

What you wrote in 1.xThe 2.x graph equivalentPayoff
Sequential + hand-rolled conditional jumpsStringRoute / IntRoute / MultiRoutebranches become edges, one less code layer
Parallel + your own errgroup aggregationAddFanOut + NewJoinNode + AddFanInthe engine owns the fan-in barrier
An outer for-loop wrapping retriesNodeConfig{RetryConfig: workflow.DefaultRetryConfig()}retry drops to node granularity
A global timeout via context.WithTimeoutper-node timeoutone failing node no longer drags the whole run
Asking a human by re-prompting repeatedlyRequestInput + ErrNodeInterruptedstate persists, so a restart can resume

A conversion example (a sequential chain, from the official examples/workflow/basic/main.go):

package main

import (
	"context"
	"log"
	"os"
	"strings"

	"google.golang.org/adk/v2/agent"
	"google.golang.org/adk/v2/agent/workflowagent"
	"google.golang.org/adk/v2/cmd/launcher"
	"google.golang.org/adk/v2/cmd/launcher/full"
	"google.golang.org/adk/v2/workflow"
)

func main() {
	ctx := context.Background()

	upperFn := func(ctx agent.Context, input string) (string, error) {
		if input == "" {
			return "No input received", nil
		}
		return strings.ToUpper(input), nil
	}
	suffixFn := func(ctx agent.Context, input string) (string, error) {
		return input + " IS AWESOME!", nil
	}

	nodeConfig := workflow.NodeConfig{RetryConfig: workflow.DefaultRetryConfig()}
	nodeA := workflow.NewFunctionNode("upper", upperFn, nodeConfig)
	nodeB := workflow.NewFunctionNode("suffix", suffixFn, nodeConfig)

	edges := workflow.Chain(workflow.Start, nodeA, nodeB)

	root, err := workflowagent.New(workflowagent.Config{
		Name:        "simple_sequence_workflow",
		Description: "Converts string to uppercase and appends a suffix",
		Edges:       edges,
	})
	if err != nil {
		log.Fatalf("failed to create workflow: %v", err)
	}

	l := full.NewLauncher()
	if err := l.Execute(ctx, &launcher.Config{
		AgentLoader: agent.NewSingleLoader(root),
	}, os.Args[1:]); err != nil {
		log.Fatalf("Run failed: %v\n\n%s", err, l.CommandLineSyntax())
	}
}

Note that workflowagent is itself an agent.Agent, so it can be placed inside someone else’s SubAgents. This is the most important mental shift in 2.x orchestration: the graph is not a “workflow engine”, the graph is a kind of Agent. Details in module 5 .

Step 6: verification and gradual rollout#

go build ./...
go vet ./...
go test -race ./...
go test ./... -run 'Integration' -count=1     # diff the event sequence against the goldenfile

Suggested ordering (one commit per step, each independently revertable):

  1. Toolchain + go.mod (not one line of code changes, still on the 1.x dependency)
  2. Batch import rewrite + compile-error fixes (this step surfaces 4.1 and 4.2 together, because the compiler names every site)
  3. Switch test mocks to StrictContextMock
  4. Behaviour regression: goldenfile fully green
  5. Convert one low-value workflow to the graph engine and run it for a week
  6. Then migrate in bulk

Step 5 is the key one — migrate something you would not miss, and pay your tuition (JoinNode partial failure, state lost after resume) inside a small blast radius.

Finally drop the 1.x dependency:

go mod tidy
go list -m all | grep 'golang.org/adk'    # only /v2 remains

Common traps, ranked by how often they bite#

  1. CI image not upgraded → requires go >= 1.26.6. See step 1.
  2. Mock fails to compile → not a bug, the interface was unified. Use StrictContextMock.
  3. Stuffing context.Background() into NewEvent → compiles fine, timestamps go haywire, replay tests turn flaky.
  4. GOFLAGS=-mod=mod plus an internal proxy that has not mirrored /v2 → the package will not resolve. Point GOPROXY at a proxy with egress, or vendor it.
  5. Two genai versions after go mod tidy → v2 depends on a newer google.golang.org/genai than 1.x; normal during coexistence, gone once 1.x is removed.
  6. Expecting adkgo version to report a version → that subcommand does not exist; use go list -m google.golang.org/adk/v2.
  7. Copy-pasting go install google.golang.org/adk/cmd/adk@latest from the old series → that package no longer exists.
  8. Converting parallel branches to a graph without setting node timeouts → one stuck external call drags the entire fan-in down with it, which is the most common migration-era production incident (detailed in the next module).

Frequently Asked Questions

Can ADK Go 1.x and 2.x coexist?

Yes. They are different module paths (google.golang.org/adk and google.golang.org/adk/v2), so one go.mod can depend on both at the same time. That means you can migrate package by package in a canary fashion instead of changing everything in one pass.

What is the minimum needed to migrate to ADK Go 2.x?

Four things: raise the Go toolchain to 1.26.6+; switch the go.mod dependency to google.golang.org/adk/v2; add /v2 to every import; fix the ctx parameter of session.NewEvent and the agent.Context interface in your test mocks.

Do I need to switch the CLI from adk to adkgo?

Late 1.x already used cmd/adkgo; only the much older v0.x-era cmd/adk needs changing. Note that adkgo has no version subcommand — use go list -m to check versions.

Do Sequential/Parallel/Loop still work after migrating?

The package paths agent/workflowagents/{sequential,parallel,loop}agent are unchanged, but in 2.x they are built on the new graph engine, so orchestration semantics need re-verification. New code should use workflowagent plus a graph directly.

Can go fix perform the ADK migration automatically?

No. The go fix rewritten in Go 1.26 only handles language and standard-library idioms; it knows nothing about ADK's type renames. The main loop is still gopls plus the compiler reporting each site.
