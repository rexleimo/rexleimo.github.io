What ADK Go 2.0 Brings: the v0.2 → v1.7 → v2.4 Change Map

A major-version change map verified against the google/adk-go v2.4.0 source tree: the graph workflow engine, the three collaboration modes, the unified agent.Context, the adkgo CLI rename, and the Go 1.26.6 floor.

September 26, 2026 · 11 min · 2304 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0 (2026-09-11) | compared against v1.7.0 (2026-09-14) and v0.2.0 (2025-11-21) Evidence: the GitHub source trees of all three tags + release notes + the official README-v2.md migration guide, each checked directly rather than relayed second-hand.

Our previous series, Go ADK Complete Guide , was written in the v0.2.0 era. Looking back, the problem with those articles was never that they were badly written — it is that the entire baseline went stale: the CLI name, module path, Go floor, context types and orchestration model all changed. So this change map has one job first: separate the changes that mean “fix your imports” from the ones that mean “rewrite into a different architecture”.

Conclusion table first, then each item in turn.

One detail that is easy to get wrong: the platform package is not new in 2.x — v1.7.0 already had platform/time.go and platform/uuid.go. What changed is that 2.x wired it into event generation (see section 3). This is the kind of nuance you only get right by reading the source tree.

2. The real architectural change: the graph workflow engine#

The v2.0.0 release notes list this as the headline feature, and it earns that position. A new top-level workflow package appeared, and the files in the source tree already lay out the capability surface:

The corresponding user-facing API, from the official examples/workflow/basic/main.go (verbatim v2.4.0, unedited):

package main

import (
	"context"
	"log"
	"os"
	"strings"

	"google.golang.org/adk/v2/agent"
	"google.golang.org/adk/v2/agent/workflowagent"
	"google.golang.org/adk/v2/cmd/launcher"
	"google.golang.org/adk/v2/cmd/launcher/full"
	"google.golang.org/adk/v2/workflow"
)

func main() {
	ctx := context.Background()

	upperFn := func(ctx agent.Context, input string) (string, error) {
		if input == "" {
			return "No input received", nil
		}
		return strings.ToUpper(input), nil
	}
	suffixFn := func(ctx agent.Context, input string) (string, error) {
		return input + " IS AWESOME!", nil
	}

	nodeConfig := workflow.NodeConfig{
		RetryConfig: workflow.DefaultRetryConfig(),
	}
	nodeA := workflow.NewFunctionNode("upper", upperFn, nodeConfig)
	nodeB := workflow.NewFunctionNode("suffix", suffixFn, nodeConfig)

	edges := workflow.Chain(workflow.Start, nodeA, nodeB)

	myWorkflow, err := workflowagent.New(workflowagent.Config{
		Name:        "simple_sequence_workflow",
		Description: "Converts string to uppercase and appends a suffix",
		Edges:       edges,
	})
	if err != nil {
		log.Fatalf("failed to create workflow: %v", err)
	}

	config := &launcher.Config{
		AgentLoader: agent.NewSingleLoader(myWorkflow),
	}
	l := full.NewLauncher()
	if err = l.Execute(ctx, config, os.Args[1:]); err != nil {
		log.Fatalf("Run failed: %v\n\n%s", err, l.CommandLineSyntax())
	}
}

Three paradigm signals are worth noticing while reading this:

  1. The workflow itself is an Agent (workflowagent). It can go into SubAgents and nest alongside llmagent. In 1.x “workflow” was an orchestration concept owned by the runner; in 2.x it is an aggregate of graph nodes.
  2. Node function signatures take agent.Context, not context.Context. This unified context is simultaneously the ctx, the session handle, the event emitter and the state read/write entry point.
  3. Retry is node-level configuration (NodeConfig.RetryConfig) rather than a for-loop you hand-write around the call.

The official sample set (examples/workflow/) pins the capability surface precisely. Laid out as a table, it is also the table of contents for module 5 :

SampleWhat it demonstratesNeeds an LLM

complexfan-out → JoinNode fan-in → LLM synthesis (AddFanOut/AddFanIn)yes
routing/stringbranching on a string value via StringRouteno
routing/intbranching on a numeric value via IntRoute / MultiRoute[int]no
routing/llmLLM classification, dispatched by the engine over StringRouteyes
hitl_simpleminimal two-node pause/resume (RequestInput)no
hitl_rerunsingle-node re-entrant HITL (ResumeOrRequestInput)no

There are only four core concepts:

  • Nodes — FunctionNode (a Go function), AgentNode (wraps an LlmAgent), ToolNode (wraps a tool.Tool), JoinNode (fan-in barrier), DynamicNode (imperative orchestrator)
  • Edges — workflow.Chain / workflow.Concat / EdgeBuilder (Add / AddFanOut / AddFanIn)
  • Routing — a node writes a label onto Event.Routes, and edges match it with StringRoute / IntRoute / MultiRoute
  • HITL — a node emits RequestInput to pause, and execution continues once a human replies

3. Breaking changes (three from README-v2.md, plus one measured)#

1. The module path carries /v2#

Go’s major version rule; every import gets rewritten:

-	"google.golang.org/adk/agent"
-	"google.golang.org/adk/agent/llmagent"
-	"google.golang.org/adk/model/gemini"
+	"google.golang.org/adk/v2/agent"
+	"google.golang.org/adk/v2/agent/llmagent"
+	"google.golang.org/adk/v2/model/gemini"

2. session.NewEvent now takes a context.Context first#

// v1 (including the temporary NewEventWithContext)
ev := session.NewEvent(ctx.InvocationID())
ev := session.NewEventWithContext(ctx, ctx.InvocationID())

// v2
ev := session.NewEvent(ctx, ctx.InvocationID())

Why is this worth its own bullet? Because the event ID and timestamp are now decided by providers supplied through the platform package (platform.WithTimeProvider / platform.WithUUIDProvider). The doc comment on session.NewEvent is blunt about it: this lets callers such as the workflow engine produce events that are deterministic and replay-safe. In other words, the extra ctx parameter is the precondition for resumable graph execution — it was not added casually.

The engineering consequence: every helper of yours that constructs events must start threading ctx downwards. Do not call context.Background() in the middle of a function — the official migration guide calls this out specifically.

3. Context unification: ToolContext + CallbackContext → agent.Context#

The merge itself is good (callbacks finally receive the same thing tools do), but your test mocks break on the spot: an old mock implemented only the CallbackContext method set, so as soon as the interface widens, var _ agent.Context = (*MyMock)(nil) fails to compile.

The official guide offers two fixes. The tedious one is implementing the methods by hand:

func (m *MockCallbackContext) Actions() *session.EventActions                       { return nil }
func (m *MockCallbackContext) FunctionCallID() string                               { return "" }
func (m *MockCallbackContext) ToolConfirmation() *toolconfirmation.ToolConfirmation { return nil }
func (m *MockCallbackContext) RequestConfirmation(hint string, payload any) error {
	return fmt.Errorf("RequestConfirmation() is not supported for MockCallbackContext")
}
func (m *MockCallbackContext) SearchMemory(ctx context.Context, query string) (*memory.SearchResponse, error) {
	return nil, fmt.Errorf("SearchMemory() is not supported for MockCallbackContext")
}

The smart one is to embed agent.StrictContextMock and override only the methods you actually use:

type fakeContext struct {
	agent.StrictContextMock
}

var _ agent.Context = (*fakeContext)(nil)

func TestSomething(t *testing.T) {
	cc := &fakeContext{agent.StrictContextMock{Ctx: context.Background()}}
	// override on fakeContext whichever methods you need
}

The difference is not convenience, it is forward compatibility: when the interface gains more methods later, a fake embedding StrictContextMock will not break. And any method you did not override panics with “not implemented”, so a dirty call explodes immediately instead of quietly returning a zero value that lets your assertion pass for the wrong reason.

The implementation files in the v2 tree: agent/context.go, agent/common_context.go, agent/common_context_mock.go, agent/context_mock.go, plus agent/tool_context_wrapper.go / agent/callback_context_wrapper.go, which remain as compatibility wrappers.

4. The CLI is renamed adkgo (added from measurement; the official migration guide does not mention it)#

Both the v1.7.0 and v2.4.0 trees contain only cmd/adkgo, never cmd/adk:

// cmd/adkgo/adkgo.go
// adkgo is a CLI tool to help deploy and test an ADK application.
package main

import (
	_ "google.golang.org/adk/v2/cmd/adkgo/internal/deploy/agentengine"
	_ "google.golang.org/adk/v2/cmd/adkgo/internal/deploy/cloudrun"
	"google.golang.org/adk/v2/cmd/adkgo/internal/root"
)

func main() { root.Execute() }

The root command is Use: "adkgo". So everything in the old series that used these commands is now broken:

go install google.golang.org/adk/cmd/adk@latest   # 404, the package does not exist
adk version                                       # command not found

The correct form (details in module 1, article 1 ):

go install google.golang.org/adk/v2/cmd/adkgo@latest
adkgo --help

Two traps to flag early: adkgo has no version subcommand (the root command only mounts deploy, under which sit cloudrun and agentengine), so you check the version with go list -m google.golang.org/adk/v2; and adkgo does not run agents — it is a deployment CLI. The console / web / api / webui runtime subcommands come from the launcher inside your own main.go, printed by l.CommandLineSyntax(). Again, see module 1, article 1 .

Also note the deploy subcommands: v2 ships deploy/cloudrun and deploy/agentengine drivers, registered via blank imports — if you add a private deployment target, that is the same pattern.

4. New capability surface (not just signature changes)#

Beyond the graph engine, the structural additions in v2.4.0 relative to 1.x:

① The three collaboration modes. llmagent.Config gained a Mode field. It is defined in internal/llminternal (type Mode = llminternal.Mode, a string type):

ModeChat       Mode = "chat"
ModeTask       Mode = "task"
ModeSingleTurn Mode = "single_turn"

The semantic differences (from the official collaboration sample):

Sub-agentModeCan it talk to the user?When does it hand control back
travel_plannerchat (root)full conversationn/a
weather_checkersingle_turnnoautomatically, returning its result
flight_bookertaskyes, it may ask clarifying questionsautomatically, returning a structured result

Combined with InputSchema / OutputSchema (*genai.Schema), a task sub-agent’s inputs and outputs are constrained by schema — the official testdata even includes a case named TestDelegation_07_ChatToTaskValidationRetry, i.e. “retry after schema validation fails”, which tells you these are not decorative fields.

② Registry and server-side security layer. agentregistry (client.go / factory.go / registry.go / requester.go / resolve.go, treating agents as registrable, resolvable resources), auth + auth/gcp, and server/authn + server/authz (authentication/authorisation on the launcher side). The old series was almost silent on “who may call my agent”; 2.x turns that into proper packages.

③ The tool and model layers. Take the set difference between the v1.7.0 and v2.4.0 package directories, and the packages unique to 2.x are these (this list was computed, not recalled):

agent/workflowagent   auth                  model/openaimodel     server/authz
agentregistry         auth/gcp              plugin/agentanalytics session/compaction
server/authn          tool/toolutils        workflow

Conversely, the “in 1.x and also in 2.x” removal set is empty — 2.x deletes no packages, it only adds them. Two points worth dwelling on:

  • model/openaimodel exists only in 2.x. If you want to run ADK Go against an OpenAI-compatible endpoint, 1.x has no official adapter — a big deal for anyone behind a relay or self-hosted gateway (covered in module 2).
  • session/compaction (context compaction) is likewise 2.x-only: the v2.4.0 tree contains examples/compaction and examples/compactionrecall, plus agent/llmagent/testdata/TestCompactionE2E.httprr.

Meanwhile tool/skilltoolset, tool/exitlooptool, tool/loadartifactstool, tool/preloadmemorytool, the streaming variants of tool/functiontool, plugin/retryandreflect and tool/toolconfirmation already existed in v1.7.0 — do not let “2.0 new features” headlines mislead you.

④ A2A. server/adka2a/v2 and agent/remoteagent/v2 (the version 2 implementation of the A2A protocol) were already present in v1.7.0, so this is not a 2.x selling point. The real delta on the 2.x line is fixes and tightening: for instance v2.4.0 pins the interface URLs of a fetched agent card to the card’s origin (an SSRF-style drift guard), and remoteagent/v2 correctly runs after-callbacks once artifact events are aggregated. Those details are in module 9 .

5. 1.x still gets updates — do not believe that “2.x is the only option”#

A counter-intuitive fact worth writing down so readers are not herded:

v1.7.0  2026-09-14   ← three days newer than v2.4.0
v2.4.0  2026-09-11

Upstream configures a separate release-please-config-v1.json and manifest for 1.x, and CI runs on both the main and v1 branches (the v2.1.0 changelog contains docs(contributing): document v1/v2 branch split and ci: run Go workflow on main and v1 branches). Which means:

  • 1.x is a maintained older major version, not a dead branch;
  • but 1.x will never receive the graph engine, collaboration modes, or the agent.Context unification — those are 2.x-only;
  • 1.x’s Go floor is go 1.25.0, and Go officially maintains only two minor releases at a time (currently 1.27.x / 1.26.x), so 1.25 no longer receives security updates. That, not the shiny features, is the real reason to move to 2.x.

My judgement, then: new projects go to 2.x unconditionally; existing 1.x projects migrate on a cost-based schedule, but the toolchain must move to Go 1.26.6+ first (reasons in article 3).

6. Cross-language alignment: why you will also see “ADK 2.10”#

A quick clarification of a common version confusion. The multilingual implementations of ADK do not synchronise version numbers:

ImplementationLatest on 2026-09-26When 2.0.0 landed
Python google-adk2.10.0earlier than Go
Go google.golang.org/adk/v22.4.02026-06-30
Java / Kotlin / TypeScript / Webeach independent—

So “ADK 2.0” in a Go context means v2.0.0 (2026-06-30), while Python had already reached 2.10. When an English tutorial’s version numbers do not line up, first confirm which language implementation it describes — that is exactly the trap the two articles in A2A and cross-language deal with.

Frequently Asked Questions

Is there an ADK Go 2.0?

Yes. google/adk-go released v2.0.0 on 2026-06-30 and moved the module path to google.golang.org/adk/v2 at the same time. As of 2026-09-26 the latest is v2.4.0 (2026-09-11).

Is ADK Go 1.x still maintained?

It is. The 1.x line releases independently and is currently at v1.7.0 (2026-09-14); the upstream repo has a v1 branch and its own release-please configuration. But new architecture such as the graph workflow engine only lands in 2.x.

What is the ADK Go 2.x module path?

google.golang.org/adk/v2, installed with go get google.golang.org/adk/v2. Every import must carry the /v2 suffix.

Which Go version does ADK Go 2.x need?

v2.4.0 declares go 1.26.6 in go.mod, so 1.26.6 is the floor. Go 1.27.x works too and is the practical baseline for this series. The 1.x line (v1.7.0) declares go 1.25.0.

Does the old adk command-line tool still work?

No. The 2.x CLI package is cmd/adkgo and the binary is called adkgo; there is no cmd/adk in the 2.x tree, so go install google.golang.org/adk/cmd/adk@latest fails.

Do 1.x Sequential/Parallel/Loop still exist in 2.x?

They exist as workflowagents (sequentialagent/parallelagent/loopagent), but they are now built on top of the graph engine and behave differently from their standalone 1.x implementations, so orchestration semantics need re-verification during migration.
