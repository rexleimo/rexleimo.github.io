All node types: Node's nine methods, six built-in nodes, and NodeConfig's tri-state pointers

The node layer of the ADK Go v2.4.0 graph engine: when each of the nine workflow.Node methods is called, BaseNode and custom nodes, the four constructors of the FunctionNode family (including FromState's parameter binding and the node_input escape hatch), EmittingFunctionFn, the constructors and semantics of AgentNode/ToolNode/JoinNode/WorkflowNode/ParallelWorker, and why the seven NodeConfig fields (ParallelWorker/RerunOnResume/WaitForOutput/RetryConfig/Timeout/EmitsOwnSpan) use pointers.

September 26, 2026 · 8 min · 1647 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources workflow/{workflow.go,base_node.go,config.go,function_node.go,agent_node.go,tool_node.go,join_node.go,parallel_worker.go,workflow_node.go,dynamic_node.go}.

Module 1 stated that in Go a workflow graph is a first-class Agent. This article covers the smallest execution unit: the node.

The Node interface: nine methods, two validation hooks#

type Node interface {
	Name() string
	Description() string
	Config() NodeConfig
	InputSchema() *jsonschema.Resolved        // nil = no schema, no input validation
	OutputSchema() *jsonschema.Resolved       // nil = no output validation
	ValidateInput(input any) (any, error)     // before Run, on every activation
	ValidateOutput(output any) (any, error)   // before forwarding each event with non-nil output
	Run(ctx agent.Context, input any) iter.Seq2[*session.Event, error]
}

A few things to note:

  1. The schema type is *jsonschema.Resolved (github.com/google/jsonschema-go/jsonschema), not genai.Schema. Constructors accept a *jsonschema.Schema and store the result of an internal Resolve(nil). This is the continuation of the “two schema type families” point from module 3.
  2. ValidateInput’s return value may be transformed (comment: “might be coerced/parsed/transformed”). In other words the validator is entitled to deserialise a map[string]any into your strong type — do not convert again inside Run, just use the type the node hands you.
  3. Run returns iter.Seq2[*session.Event, error], not a channel. So the node body computes and yields as it goes, and cancellation arrives as yield returning false.

BaseNode implements the first seven methods for you:

type MyNode struct{ workflow.BaseNode }

func NewMyNode(name string) *MyNode {
	return &MyNode{BaseNode: workflow.NewBaseNode(name, "my node", workflow.NodeConfig{})}
}
// the schema variant (note: this one takes an already-Resolved *jsonschema.Resolved, and returns no error):
//   resolved, err := (&jsonschema.Schema{Type: "object"}).Resolve(nil)
//   workflow.NewBaseNodeWithSchemas(name, desc, cfg, resolved, nil)

func (n *MyNode) Run(ctx agent.Context, input any) iter.Seq2[*session.Event, error] {
	return func(yield func(*session.Event, error) bool) {
		ev := session.NewEvent(ctx, ctx.InvocationID())
		ev.Output = strings.ToUpper(input.(string))
		if !yield(ev, nil) {
			return
		}
	}
}

The interface comment verbatim: “Custom nodes typically embed BaseNode … and supply only Run.”

⚠️ One inconsistency (found only by measuring): neither NewBaseNode nor NewBaseNodeWithSchemas returns an error, and the latter takes an already resolved *jsonschema.Resolved; whereas constructors like NewFunctionNodeWithSchema / NewAgentNodeWithSchemas / NewToolNodeWithSchemas take an unresolved *jsonschema.Schema and return an error (because they call Resolve internally). Two styles inside one package — custom nodes must Resolve themselves first.

The FunctionNode family: four constructors#

// ① the common one: generic in/out parameters, schema inferred
wf := workflow.NewFunctionNode("normalize",
	func(ctx agent.Context, in string) (string, error) { return strings.TrimSpace(in), nil },
	workflow.NodeConfig{})

// ② explicit schemas (returns error, because Resolve must run)
n2, err := workflow.NewFunctionNodeWithSchema[In, Out]("parse", fn, inputSchema, outputSchema, cfg)

// ③ the emitting variant: can yield intermediate events (progress, stream fragments)
n3 := workflow.NewEmittingFunctionNode("report",
	func(ctx agent.Context, in In, emit func(*session.Event) error) (Out, error) {
		for _, step := range steps {
			if err := emit(progressEvent(step)); err != nil { return zero, err }
		}
		return Out{...}, nil
	}, cfg)
n4, err := workflow.NewEmittingFunctionNodeWithSchema[In, Out](...)

// ④ take parameters from state (Params must be a struct)
n5, err := workflow.NewFunctionNodeFromState[Params, Out]("render",
	func(ctx agent.InvocationContext, p Params) (Out, error) { ... }, cfg)

The EmittingFunctionFn type alias:

type EmittingFunctionFn[IN, OUT any] = func(ctx agent.Context, in IN, emit func(*session.Event) error) (OUT, error)

④ is the easiest to miss and the most useful — the three rules from the comment:

type Params struct {
	UserQuery string              // by default reads state["UserQuery"]
	Tone      string `state:"tone"`   // explicit key override
	Input     MyIn  `state:"node_input"` // or name the field NodeInput: get the raw upstream output
}
  • the field name is the state key by default (state:"my_key" overrides it);
  • state:"node_input" is the escape hatch: use it when you want both state and the upstream output;
  • if Params is not a struct the constructor returns an error outright (“params must be a struct type”).

The companion StateFieldNames() []string lets the engine validate statically — the StateParamsAware interface next to Node is the marker for it, and when the fields declared with WithStateSchema do not match what the node actually consumes, it fails at startup instead of silently returning nothing at runtime.

AgentNode / ToolNode: turning agents and tools into nodes#

// AgentNode: four constructors
n, err := workflow.NewAgentNode(a, cfg)                                        // no schema
n, err = workflow.NewAgentNodeWithSchemas(a, inputSchema, outputSchema, cfg)   // explicit
n, err = workflow.NewAgentNodeTyped[In, Out](a, cfg)                           // inferred from generics
// the private newAgentNodeWithSchemasTyped is the "generics + explicit override" entry point

// ToolNode: one extra constructor, NewNamedToolNode (lets you name the node)
n, err = workflow.NewToolNode(myTool, cfg)
n, err = workflow.NewToolNodeWithSchemas(myTool, inS, outS, cfg)
n, err = workflow.NewToolNodeTyped[In, Out](myTool, cfg)
n, err = workflow.NewNamedToolNode("step3", myTool, cfg)

ToolNode requires the tool to implement the internal runnableTool (Run(agent.Context, any) (map[string]any, error)) — functiontool satisfies it, a custom tool.Tool may not. That is a genuine difference between “orchestrating a tool in a graph” and “attaching a tool to an agent”.

AgentNode carries a cluster of semantics worth knowing (the source function names are the evidence): synthesizeAgentOutput (when an agent only speaks and never sets output, node output is synthesised from the model text), isOwnAgentEvent (distinguishing “this agent’s own events” from those of its descendants), nodeInputToContent (converting node input into a genai.Content to feed the agent). Together these three mean AgentNode permits “text as output”, and BaseNode.modelText / projectTextOntoSchema take the same road (projecting model text onto a schema to produce a struct).

JoinNode: the fan-in barrier#

join := workflow.NewJoinNode("merge")
// with a schema: workflow.NewJoinNodeWithSchema("merge", resolved)

The contract (summarising the comment verbatim):

  • activated exactly once, after every predecessor declared on the graph edges has completed;
  • input is a map[string]any whose keys are predecessor node names and values their outputs;
  • its own output is that map, emitted as is.

⚠️ The two most common mistakes:

  1. every incoming edge feeds the barrier, so adding conditional routing to a JoinNode is a configuration error — the barrier waits for all declared predecessors, and a predecessor skipped by routing never arrives, so the graph stalls.
  2. The schema passed to NewJoinNodeWithSchema validates each predecessor’s output, not the merged map; when a predecessor’s output is nil, validation is skipped and nil is preserved.

ParallelWorker: concurrency over a list#

pw, err := workflow.NewParallelWorker("bulk", workerNode, 8, workflow.NodeConfig{ParallelWorker: true})

Signature NewParallelWorker(name string, wrapped Node, maxConcurrency int, cfg NodeConfig). It runs wrapped concurrently over each item of the input list, and maxConcurrency here is a node-level parameter (a different knob from the graph-level WithMaxConcurrency limit), finally collecting everything into a single aggregate output event.

FunctionNode has the matching NodeConfig.ParallelWorker switch, and the comment describes its behaviour: “runs the node concurrently for each item of a list-typed input. The engine collects per-item outputs and emits a single aggregate output event.”

WorkflowNode: a sub-graph as a node#

sub, err := workflow.NewWorkflowNode("sub", subEdges)   // note: there is no opts parameter
n, err := workflow.NewWorkflowNode("sub", edges)

A sub-workflow must not share the parent’s name — ErrSubWorkflowNameCollision (“sub-workflow name collision”) is blocked at graph construction time by validateSubWorkflowNames. The reason is in article 2: the name is the persistence namespace of RunState.

NodeConfig: seven fields, two tri-state pointers#

type NodeConfig struct {
	ParallelWorker  bool
	RerunOnResume   *bool          // tri-state
	WaitForOutput   *bool          // tri-state
	RetryConfig     *RetryConfig   // nil = no retry
	Timeout         time.Duration  // 0 = bounded only by the parent invocation deadline
	EmitsOwnSpan    bool
}

The comment states why pointers: “pointer-typed fields are tri-state so node implementations can distinguish ‘user explicitly opted out’ (&false) from ‘user did not configure’ (nil)”. The tri-state semantics:

Field&true&falsenil
RerunOnResumererun mode (the node starts over from scratch)handoff mode (the answer becomes input to the successor)the engine currently treats it as handoff
WaitForOutputif the child emits no output, keep the parent parked and rerun itcomplete normallyengine default (false for most nodes)

The justification for WaitForOutput is written concretely: when a child dispatched by RunNode finishes without setting output, it is better to park and rerun than to let the parent “finish falsely with a zero value” — multi-turn sub-agents need this. It currently only takes effect on the RunNode (dynamic child scheduler) path.

EmitsOwnSpan is a telemetry detail: set it when the node already opens its own span (an LlmAgent node emits invoke_agent, for instance) and the scheduler stops wrapping an extra invoke_node around it, keeping the span tree consistent with adk-python.

Timeout is applied with context.WithTimeout around each activation — note the granularity is “an activation”, not “the node’s whole lifecycle”, so with retries configured every attempt gets its own budget (expanded in article 4).

Which to pick: a decision table#

NeedUse
a single pure-function transformNewFunctionNode
progress or streaming intermediate eventsNewEmittingFunctionNode
parameters scattered across stateNewFunctionNodeFromState
let some agent participate in the graphNewAgentNodeTyped (when you have in/out types)
an existing tool you want to orchestrateNewToolNode / NewNamedToolNode
wait for several branches then mergeNewJoinNode
run a list item by item, concurrentlyNewParallelWorker or Config.ParallelWorker
reuse a sub-graphNewWorkflowNode
you only know at runtime what to runNewDynamicNode + RunNode (article 5)

Frequently Asked Questions

What must a custom graph node implement in ADK Go 2.x?

The workflow.Node interface has nine methods. In practice you embed workflow.BaseNode (built with NewBaseNode) and implement only Run — Name/Description/Config/InputSchema/OutputSchema/ValidateInput/ValidateOutput all come with defaults.

What happens if Node.InputSchema() returns nil?

Nothing is validated. The interface comment says it plainly: returning nil means no schema and no input validation. OutputSchema behaves the same.

When are ValidateInput and ValidateOutput called?

ValidateInput is called by the scheduler before every activation's Run. ValidateOutput is called for each yielded event whose output is non-nil, just before it is forwarded to consumers. Both may return a coerced value.

Why are NodeConfig's RerunOnResume/WaitForOutput *bool?

Tri-state: &true opts in explicitly, &false opts out explicitly, nil means the user configured nothing. The config.go comment states this distinguishes 'explicitly opted out' from 'not configured', and the engine applies its default accordingly (nil → handoff mode).

What if a FunctionNode needs session state rather than upstream output?

Use workflow.NewFunctionNodeFromState[Params, OUT]: Params must be a struct, fields are read from state under their Go field names by default, `state:"my_key"` overrides that, and `state:"node_input"` (or a field named NodeInput) gives you the raw upstream output.

What do JoinNode and ParallelWorker each do?

JoinNode is the fan-in barrier: it waits for all predecessors and outputs a map[predecessor name]output. ParallelWorker runs one node concurrently over each item of a list and collects the results into a single aggregate output event. The first waits, the second spreads.
