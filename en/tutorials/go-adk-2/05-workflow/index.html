Module 5: The Graph Workflow Engine (core of ADK Go 2.x)

A complete tour of the workflow package: node types, Chain/EdgeBuilder/fan-out-join, routing, concurrent scheduling with per-node retry and timeouts, and HITL pause/resume with dynamic graphs
5 POSTS

Module 5: The Graph Workflow Engine

This is ADK Go 2.0’s headline feature and the largest increment of this column over the old one. The workflow and agent/workflowagent packages exist only in 2.x (absent from the v1.7.0 tree).

One-line positioning: the graph is not a “workflow engine”, the graph is a kind of Agent. workflowagent implements agent.Agent, so it can appear inside someone else’s SubAgents, and a launcher can serve it directly as the root agent.

// connecting edges
workflow.Chain(start, a, b)                       // returns nil with fewer than 2 nodes
workflow.Concat(chain1, workflow.Edge{…})         // accepts only Edge / []Edge, silently ignores other types

// assembling into an Agent (resume handled automatically)

NodeConfig fields (all optional): ParallelWorker bool, RerunOnResume *bool, WaitForOutput *bool, RetryConfig *RetryConfig, Timeout time.Duration, EmitsOwnSpan bool.

Key constraints of this module (all checked against the source)

  1. Always take a copy of workflow.DefaultRetryConfig() and then modify it — unset fields in a struct literal are zero values (RetryConfig{MaxAttempts: 5} means five immediate retries). Defaults: 5 attempts / 1s / 60s / 2x / full jitter, and defaultShouldRetry does not retry ErrInputValidation.
  2. Timeout defaults to 0, meaning the node is bounded only by the parent invocation deadline; granularity is one activation.
  3. A JoinNode may not have conditional incoming edges (the barrier waits for every declared predecessor, and one skipped by routing never arrives).
  4. Two edges with the same (From,To) on one node are rejected (ErrDuplicateEdge, regardless of Route); to send several conditions to one target, use MultiRoute.
  5. If no route matches and there is no Default, the graph dies silently — it is not an error. Every node with out-degree > 0 needs either an unconditional edge or a Default (note that an unconditional edge does not suppress Default).
  6. Per activation: at most one event carrying Output, at most one carrying Routes (the test is != nil), at most one RequestedInput.
  7. WithMaxConcurrency does not govern dynamic children dispatched by RunNode (that deadlocks).
  8. The graph name is the persistence namespace inside RunState: an empty name disables resume; there is currently no graph fingerprint check, so changing the graph structure and deploying straight away silently ingests stale RunState.
  9. workflowagent.Config has only 6 fields and internally just calls workflow.New(name, edges) — there is no MaxConcurrency or StateSchema entry point; one agent instance can serve many sessions concurrently (RunState lives in session.State).
  10. HITL pauses travel as an adk_request_input FunctionCall (a wire format shared with other runtimes); tool confirmation travels as adk_request_confirmation. InterruptID must be unique per run, or the Dev UI stops showing the prompt.

⚠️ Two high-frequency traps (the source comment’s own words):

  1. Build RetryConfig by copying workflow.DefaultRetryConfig() and then setting fields. With a struct literal, unset fields are zero values, not defaults, and a zero value means “no retry, no backoff, no jitter”. Defaults: MaxAttempts 5, InitialDelay 1s, MaxDelay 60s, BackoffFactor 2.0, Jitter 1.0, and defaultShouldRetry does not retry ErrInputValidation.
  2. With Timeout at 0 (the default) the node is bounded only by the parent invocation context’s deadline — one stuck external call can hold up the entire fan-in.
