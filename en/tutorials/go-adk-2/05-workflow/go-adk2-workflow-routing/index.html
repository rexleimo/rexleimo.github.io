Routing and conditional execution: what Default really means, silent dead ends, and a deduplicated edge

Conditional execution in ADK Go v2.4.0: how the Route interface reads event.Routes, the exact matching rules of StringRoute/IntRoute/BoolRoute/MultiRoute/Default, the four scheduling semantics in findSuccessors (unconditional edges do not suppress Default, Default fires only when no concrete route matched, all-miss-without-Default is a silent dead end, same-target deduplication), the per-activation hard constraints (ErrMultipleOutputs/ErrMultipleRoutingEvents/ErrMultipleTerminalOutputs), the implicit behaviour that a FunctionNode must return *session.Event to carry routes, and branch derivation during fan-out.

September 26, 2026 · 8 min · 1666 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources workflow/{workflow.go,scheduler.go,function_node.go,validation.go}.

Routing is the only mechanism in the graph engine that hands control of execution to data, and it is also the least documented and most often guessed wrong. Every rule below comes from the comments of one function, findSuccessors — unpacked into actionable items.

The mechanism: events carry strings, edges consume strings#

// the Route interface has exactly one method
type Route interface {
	Matches(event *session.Event) bool
}

// the matching implementation: a linear scan of event.Routes for string equality
func matchRoute(routeValue string, event *session.Event) bool {
	for _, v := range event.Routes {
		if v == routeValue { return true }
	}
	return false
}

So the node owns “which road am I”, the edge owns “which road goes to which node”. Both sides are pure data — there is no expression language.

The node side is one line:

func classify(ctx agent.Context, in string) (*session.Event, error) {
	ev := session.NewEvent(ctx, ctx.InvocationID())
	ev.Output = in
	if urgentRe(in) {
		ev.Routes = []string{"urgent"}
	} else {
		ev.Routes = []string{"normal"}
	}
	return ev, nil
}

The five Route types, with exact rules#

TypeComparisonExample
StringRouteliteral stringStringRoute("urgent")
IntRoutefmt.Sprint(r), compared as a decimal stringIntRoute(2) ↔ Routes: ["2"]
BoolRoutethe string forms "true"/"false"BoolRoute(true) ↔ Routes: ["true"]
MultiRoute[T comparable]matches if any value in the list does (again via fmt.Sprint)MultiRoute[string]{"a","b"}
DefaultMatches is always false, recognised specially by the scheduler{From: c, To: fallback, Route: workflow.Default}

Two traps:

  1. IntRoute/BoolRoute compare as strings. Writing "02" in the event against IntRoute(2) does not match (fmt.Sprint(2) == "2"). This bites especially when replaying events recorded across languages (module 9 runs into it).
  2. MultiRoute[T]’s T is comparable, and mixing types means each is fmt.Sprinted separately, so MultiRoute[any]{1, "1"} matches the same value twice. Do not write that.

The four rules of findSuccessors#

Quoting the comment rule by rule:

① Edges with no Route always fire (and do not suppress Default).
② Edges with a concrete Route fire only if Route.Matches(event) is true.
③ Duplicate To targets are deduplicated (same target node may not be
   queued twice for one parent activation).
④ The Default edge fires when no concrete Route matched. An unconditional
   edge does not count as a "match" for this purpose, so a graph with one
   unconditional edge and one Default edge fans out to both targets.

Plus the most counter-intuitive one:

⑤ If every outgoing edge has a concrete Route and none matched, and no
   Default is present, the workflow silently dead-ends at this node.
   The absence of a matching route is treated as a deliberate decision
   not to continue, not an error.

Rule ④ deserves emphasis: Default is governed only by “did a concrete route match”, and unconditional edges do not participate in that test. Hence:

{From: a, To: b},                              // unconditional: always runs
{From: a, To: c, Route: workflow.Default},     // runs when no concrete route matched
// result: after a completes, both b and c run (a fan-out!)

To make Default the only fallback, you must add a concrete route to every other outgoing edge of that node (the “all conditional” shape from rule ⑤).

Rule ③ is the flip side of ErrDuplicateEdge: an identical (From,To) is rejected at construction, so “several conditions for one target” can only be expressed with MultiRoute (the validation comment gives exactly that guidance); and at runtime, even if two different sources point at the same target and both are hit by one activation, it deduplicates into one.

Rule ⑤ is where production incidents cluster: every edge conditional, none matching → no error, the graph just quietly ends. On the event stream you cannot tell “did not finish” from “finished early”. There is only one defence: every node with out-degree > 0 keeps either an unconditional edge or a Default.

Three hard “only one per activation” constraints#

ErrMultipleOutputs        // only one event with Output per activation
ErrMultipleRoutingEvents  // only one event with Routes per activation
ErrMultipleTerminalOutputs// several terminal nodes producing output → the workflow output is ambiguous

All three are defined in scheduler.go (note: not in errors.go, so do not only grep errors.go when looking for them).

One implementation detail in handleEvent is worth knowing:

if it.ev.Routes != nil {
	nr.setRoutingEvent(it.ev, it.nodeName)   // reports ErrMultipleRoutingEvents if one exists
}

The test is != nil, not len(...) > 0. So ev.Routes = []string{} (an empty but non-nil slice) is taken as “this activation’s routing event”, and emitting a second one errors out — if you want “no routing decision”, do not touch the field at all and leave it nil.

There is more: Routes: []string{} also prevents Default from firing (since a routing event exists and every Matches failed). As shown, matchRoute scanning an empty slice must return false, and concreteMatched depends on whether concrete routes exist on the edges… an empty slice plus concrete route edges = all miss = the silent dead end of rule ⑤. This is the hardest class of graph bug I have seen; it belongs on your checklist.

Attribution of descendant events is in this same logic: an event whose NodeInfo.Path differs from the current node name is a child event forwarded by a dynamic node, and its Output/Routes belong to the child, not to the parent’s accumulator. The only exception is RequestedInput — a child’s pause unwinds the parent’s execution, so the parent must move to NodeWaiting, otherwise Resume’s InterruptID will not line up.

Letting a FunctionNode carry its own routes#

The return-type dispatch in FunctionNode.Run (in source order):

if ev, ok := output.(*session.Event); ok { yield(ev, nil); return }   // ← forwarded directly, Routes preserved
if c, ok := output.(*genai.Content); ok { event.Content = c }
else if c, ok := output.(genai.Content); ok { event.Content = &c }
else { event.Output = output }

The comment names the intent: “This ensures that a custom FunctionNode can explicitly route its output (via event.Routes) to select conditional successors.”

So three return types give three semantics:

Return typeWhere it lands on the eventCan it set Routes
*session.Eventyielded as is✅ the only route to it
*genai.Content / genai.Contentevent.Content❌
any other valueevent.Output❌

⚠️ The cost: when you return *session.Event, the downstream input is the whole event (you must put the value into ev.Output yourself, or the successor gets nothing). So “I just want to emit an output” → do not return an event; use it only when you need routing.

The same applies to streaming / multi-event nodes (NewEmittingFunctionNode): emit events carrying Routes yourself and the final returned OUT becomes the output — just do not emit two events carrying Routes, which collides with ErrMultipleRoutingEvents immediately.

How branch is computed on fan-out#

Routing decides “who runs”, branch decides “who can see whom”. The three rules at the end of findSuccessors:

  • a single successor: inherits the parent branch unchanged;
  • a fan-out to more than one successor: each non-Join successor is tagged <parentBranch>.<successorName>@1;
  • a JoinNode successor: computes its own — the common dotted prefix (commonBranchPrefix) of all completed predecessors’ branches.

The @1 here is a fixed run id (the comment explains that the static scheduler does not auto-count repeated segments, so a sub-branch stays stable when a loop returns to the same node).

Why this matters: when a branch hosts an LLM agent, branch decides whose messages it can see in the prompt history (article 2 of module 4). Sibling branches being mutually invisible after a fan-out is default behaviour, not something you configured — conversely, if you want two parallel branches to share context, you must avoid triggering the sub-branch split (make it sequential, or hang both off the same unconditional chain).

Letting the LLM choose the route (detailed next)#

The graph engine provides only the Routes data plane. “Who decides routes” is entirely up to your node implementation — three common approaches:

// ① rules: if/switch inside a function node (this article's example)
// ② schema classification: an agent node with OutputSchema, the node function fills Routes from output fields
// ③ the LLM picks directly: have the agent output an enum, then translate it into Routes in a FunctionNode layer

Approaches ② and ③ involve AgentNode’s output projection and the transfer semantics of collaborative agents — see Module 6: New Multi-Agent Patterns .

Checklist#

  • every node with out-degree > 0 has a Default edge or at least one unconditional edge (guards against the silent dead end of rule ⑤)
  • no node has two edges with the same (From,To) (ErrDuplicateEdge)
  • exactly one event with Routes per activation, and leave it nil when no routing is needed
  • the Routes values behind IntRoute/BoolRoute are in fmt.Sprint form ("2", not "02")
  • when returning *session.Event, ev.Output is set as well
  • is any conditional routing entering a JoinNode? — it should not be (the barrier semantics from article 2)

Frequently Asked Questions

How does conditional branching work in ADK Go graph workflows?

The node writes ev.Routes = []string{"urgent"} on the event it emits, and the edge carries Route: workflow.StringRoute("urgent"). The scheduler compares the event's Routes against each edge's Route.

How does workflow.Default match?

Its Matches always returns false — Default never goes through Matches. The scheduler recognises edge.Route == Default separately and fires it only when no concrete route matched.

Does an unconditional edge block Default?

No. The comment says it outright: unconditional edges always fire and do not count as a match. So one unconditional edge plus one Default edge fans out to both targets.

What happens if no route matches at all?

A silent dead end, provided there is no Default. The comment: "The absence of a matching route is treated as a deliberate decision not to continue, not an error." That is design, not a bug — which is why you need a fallback edge.

Can one node emit several events carrying routes?

No: ErrMultipleRoutingEvents. Likewise one activation may have only one output (ErrMultipleOutputs), and several terminal nodes producing output raises ErrMultipleTerminalOutputs.

Why do the Routes I set on a FunctionNode have no effect?

Routing only works if you return *session.Event (writing ev.Routes/ev.Output yourself) — FunctionNode yields it directly when it detects that return type. Returning an ordinary value makes the framework build the event itself, and there is nowhere for your route to go.
