Dynamic graphs and HITL: RunNode's seven options, the adk_request_input wire format, and resuming across requests

The two hardest pieces of the ADK Go v2.6.0 graph engine together: runtime orchestration with DynamicNode + RunNode (the seven With* options, stable-RunID single-flight deduplication, failure classification, output delegation), the synthetic adk_request_input FunctionCall produced by NewRequestInputEvent and LongRunningToolIDs, the InterruptID uniqueness requirement (the Dev UI tracks answered requests by ID and never re-asks), the re-entry and handoff modes of RerunOnResume with the branch in duplicate-Resume semantics, the one-line ResumeOrRequestInput form, Workflow.Resume and ErrNothingToResume, how ReconstructRunState rebuilds state from event history (since v2.6.0 RunState is no longer persisted as a blob), and the hard limitation that parallel HITL is not supported.

September 26, 2026 · 16 min · 3317 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.6.0 (released 10-13), sources workflow/{dynamic_node.go,run_node.go,request_input.go,resume.go,persistence.go,state.go,errors.go,dynamic_scheduler.go}, samples examples/workflow/{hitl_simple,hitl_rerun,dynamic/*}; passages marked “since v2.6.0” are behaviour changes relative to v2.4.0.

The graphs in the previous four articles are all fixed at construction time. This one handles two runtime concerns: code deciding what to run on the spot (dynamic child nodes) and asking a human mid-flight (HITL). They share one pause/resume mechanism under the hood, so they belong in one article.

1. Pausing: what NewRequestInputEvent actually sends#

The minimal form (the real structure of examples/workflow/hitl_simple/main.go):

ask := workflow.NewEmittingFunctionNode[any, any]("ask_name",
	func(ctx agent.Context, in any, emit func(*session.Event) error) (any, error) {
		// Unique InterruptID per request: a reused ID would let the
		// client treat a fresh prompt as already answered.
		if err := emit(workflow.NewRequestInputEvent(ctx, session.RequestInput{
			InterruptID: "ask_name-" + uuid.NewString(),
			Message:     "What is your name?",
		})); err != nil {
			return nil, err
		}
		return nil, workflow.ErrNodeInterrupted
	},
	workflow.NodeConfig{},
)

greet := workflow.NewFunctionNode[any, string]("greet", /* … */, workflow.NodeConfig{})

rootAgent, err := workflowagent.New(workflowagent.Config{
	Name:  "hitl_simple",
	Edges: workflow.Chain(workflow.Start, ask, greet),
})

⚠️ There is a piece of knowledge many people lack: you do not have to call wf.Resume yourself. workflowagent.New wraps a layer called workflowAgent, and its comment is unambiguous:

workflowAgent is the wrapper that dispatches between Workflow.Run (fresh turn)
and Workflow.Resume (resume turn). The dispatch decision is made by inspecting
ctx.UserContent for a FunctionResponse targeting a previously-emitted RequestInput.

Which means: once the user returns a FunctionResponse pointing at an InterruptID, the next turn automatically takes the resume path (detectResume does this). Writing Resume by hand is only necessary when you drive a *workflow.Workflow directly (without workflowagent) — the final section of this article covers that form.

Three additional hard facts read out of the New source:

  1. workflowagent.Config has only 6 fields (Name / Description / SubAgents / BeforeAgentCallbacks / AfterAgentCallbacks / Edges) — no MaxConcurrency, no StateSchema, because internally it is simply workflow.New(cfg.Name, cfg.Edges) with no options passed. To cap concurrency you must construct the *workflow.Workflow yourself and wrap it.
  2. graph name = agent name, so as long as Name is non-empty, every event carries this path prefix (since v2.6.0 this is just a label, not a persistence switch — see article 2).
  3. The comment states plainly that one agent instance can serve many concurrent sessions — the v2.6.0 words: “the per-invocation run state is rebuilt from session event history on a resume turn rather than held on the agent”. So do not build a new agent per request, and there is no need for locks.

The upstream README distinguishes the two samples in one line each:

Sample Demonstrates
hitl_simple a minimal two-node pause/resume (ask pauses, greet catches the answer by handoff)
hitl_rerun single-node re-entrant HITL using ResumeOrRequestInput

NewRequestInputEvent(ctx, req) performs six things internally (itemised from the source):

if req.InterruptID == "" { req.InterruptID = uuid.NewString() }   // ① a fallback ID
ev := session.NewEvent(ctx, ctx.InvocationID())
ev.RequestedInput = &req                                          // ② the dedicated field
args := map[string]any{"interruptId":…, "message":…, "payload":…} // ③ mirrored into args
if req.ResponseSchema != nil { args["responseSchema"] = … }
ev.LLMResponse = model.LLMResponse{Content: &genai.Content{
	Role: genai.RoleModel,
	Parts: []*genai.Part{{FunctionCall: &genai.FunctionCall{
		ID: req.InterruptID, Name: WorkflowInputFunctionCallName, Args: args,
	}}}}}
ev.LongRunningToolIDs = []string{req.InterruptID}                // ④ marked long-running
ev.Author = ctx.Agent().Name()                                   // ⑤ attribution
ev.Branch = ctx.Branch()                                         // ⑥ branch ownership

Step ③ is the crux: it writes two channels at once.

  • Event.RequestedInput is for the scheduler (“this node wants to pause, move it to NodeWaiting”);
  • the synthetic FunctionCall is for generic clients — the comment verbatim: “so generic FunctionResponse-by-ID dispatch can route the human’s reply back to this agent on the follow-up turn”, and a client can render the prompt from args alone without parsing the dedicated field.

The wire name is a constant:

const WorkflowInputFunctionCallName = "adk_request_input"

The comment characterises it firmly: this is a wire-format identifier shared with other ADK runtimes, and changing it requires cross-runtime coordination — “a session recorded by one runtime must be able to round-trip through resume dispatch on any other runtime”. So do not invent a second pause protocol in your frontend: adopting this one makes you cross-language by default.

Compare module 3’s tool confirmation: toolconfirmation.FunctionCallName = "adk_request_confirmation". Two names with the same prefix and different meanings, one asking for parameter approval and one for business input — your UI needs two rendering paths.

InterruptID uniqueness is not a suggestion, it is a functional requirement#

The comment names the client behaviour:

Avoid a fixed literal that recurs across separate runs in the same
session: clients such as the Dev UI track answered requests by this ID
and will not re-prompt for one already resolved earlier in the session.

The consequence of hardcoding "ask_name": the second time the same session reaches this node, the UI believes “this ID was already answered” and stops prompting, so the flow stalls silently. The correct posture is exactly the sample’s "node name-" + uuid (“readable-but-unique”).

The four fields of session.RequestInput:

type RequestInput struct {
	InterruptID    string              `json:"interruptId"`
	Message        string              `json:"message,omitempty"`         // the question shown to the human
	ResponseSchema *jsonschema.Schema  `json:"responseSchema,omitempty"`  // constrains the answer's shape
	Payload        any                 `json:"payload,omitempty"`         // context shown to the human
}

⚠️ One hard constraint (the field comment on Event.RequestedInput): “At most one event per node activation may carry this field.” One activation, one question. To ask several people in parallel → split into several nodes.

2. Two resume modes: re-entry versus handoff#

type NodeConfig struct {
	RerunOnResume *bool   // tri-state
	WaitForOutput *bool
	// …
}
&true re-entry &false handoff nil
Who receives the answer the asker re-runs from the start the asker’s successor takes the answer as input the engine currently treats it as handoff
Does the asker re-execute ✅ yes (side effects must be idempotent) ❌ no no
How to read the answer ctx.ResumedInput(interruptID) it is simply the node’s input —
NodeState.ResumedInputs accumulates answers across repeated prompts absent (comment: absent for handoff-mode) —
Typical sample hitl_rerun hitl_simple

DynamicNode changes the default for you — applyDynamicDefaults is four lines: when RerunOnResume == nil it forces &true. An orchestrator that gets paused must be able to continue with its remaining orchestration logic; handoff would be meaningless for it.

The one-line form for re-entry (ResumeOrRequestInput, six parameters collapsed to two):

reply, err := workflow.ResumeOrRequestInput(ctx, emit, session.RequestInput{
	InterruptID: "approve-" + uuid.NewString(),
	Message:     "Delete these 3000 lines?",
})
if err != nil {
	return nil, err        // first turn: it already emitted the pause event, err == ErrNodeInterrupted
}
// reaching here = the human's answer is in hand

The implementation is three steps and worth memorising (because it is the standard skeleton of “re-entry”):

if reply, ok := ctx.ResumedInput(req.InterruptID); ok { return reply, nil }
if err := emit(NewRequestInputEvent(ctx, req)); err != nil { return nil, err }
return nil, ErrNodeInterrupted

⚠️ InterruptID must be the stable one (comment: “req.InterruptID is the shared key for the request and the resume lookup”). If you mint a fresh uuid.NewString() here too, the re-entry generates a new ID, ctx.ResumedInput never finds it → an infinite pause. In the samples the ID comes from state or another deterministic source. This is the most common mistake in re-entry mode, and I nearly made it while writing this article.

WaitForOutput is a third kind of “pause”, but it has no interrupt ID: when a child dispatched by RunNode finishes without setting output, the parent is parked and rerun rather than falsely completing with a zero value. The corresponding error is interesting — it is wrapped:

ErrNodeWaitingForOutput = fmt.Errorf("%w: waiting for output", ErrNodeInterrupted)

The comment says this is deliberate: “Wraps ErrNodeInterrupted so existing errors.Is(ErrNodeInterrupted) checks still treat it as a pause.” To separate “asking a human” from “waiting for output”, use errors.Is(err, workflow.ErrNodeWaitingForOutput).

3. Resuming: the semantics of Workflow.Resume (v2.6.0 branches by mode)#

func (w *Workflow) Resume(
	ctx agent.Context,
	state *RunState,
	responses map[string]any,     // key = InterruptID, value = the human's answer
) iter.Seq2[*session.Event, error]

The contract (v2.6.0 branches the duplicate-submit semantics by re-entry/handoff — far more explicit than v2.4.0):

  1. Validate before consuming: the payload is first validated against the interrupt’s declared ResponseSchema (a mismatch → ErrInvalidResumeResponse, the node stays in NodeWaiting with its interrupt still recorded, and you can retry with a corrected payload). Duplicate submissions are no longer “naturally idempotent” — it branches by mode:

    • A re-entry node (RerunOnResume=&true): is set to NodePending and scheduled again, the answer delivered via ctx.ResumedInput — a duplicate Resume re-runs it a second time. The comment verbatim: “a duplicate Resume re-runs it a second time”.
    • A handoff node: is set to NodeCompleted, the answer is routed to the successor, and the asker never re-executes; a duplicate submit matches no waiting node and falls into point 3.

    So a caller that must treat a double-submit as success has to tolerate ErrNothingToResume (comment: “It is never a no-op in the re-entry case”). When a frontend re-clicks “submit”, handoff mode is safe; re-entry mode genuinely runs the node again — side effects must be idempotent.

  2. A waiting node that was not answered stays put (if responses lacks its ID it remains NodeWaiting).

  3. A non-empty responses matching no waiting node → ErrNothingToResume, and the comment explains the motive: “so the caller can distinguish a successful resume from a stale or mistargeted submission” — typically the response targeted a stale or already-consumed interrupt, or the graph has evolved and the waiting node no longer exists (the release risk from article 2 showing up at runtime). An empty map or nil state is a clean no-op and raises no error.

One implementation detail that directly shapes graph design: Resume runs two passes — when one call satisfies several askers, JoinNodes first see “all predecessors NodeCompleted” before the barrier is evaluated. Otherwise a JoinNode would misjudge a half-complete state.

Answers are validated against ResponseSchema (validateResumeResponse), and a mismatch returns:

var ErrInvalidResumeResponse = errors.New("workflow: resume response does not match request schema")

So ResponseSchema is not merely for rendering a UI form — it is a server-side validation contract too. Frontend validation is only user experience; this server-side copy is the guarantee.

4. Where the state comes from: ReconstructRunState#

Cross-request resume does not rely on “an object still living in the process”, it relies on recomputing from event history:

state, err := wf.ReconstructRunState(sess, invocationID)   // rebuild from session events
if err != nil { … }
for ev, err := range wf.Resume(ctx, state, map[string]any{interruptID: reply}) { … }

The two scanners in persistence.go divide the work cleanly:

  • scanHistory(events, nodesByName, invocationID): collects per node the interrupts (insertion order kept stable), resolved (interrupt ID → the last answer), resolvedCount, and the interruptSchemas re-extracted from events, and maintains interruptOwner (who asked);
  • collectNodeOutputs(events, …): derives each node’s output and whether it completed.

resolvedCount == 1 is exactly the answeredThisTurn from the previous section (answered for the first time this turn versus a duplicate replay) — the idempotency discriminator is recomputed too, not persisted.

The comment on NodeState.Interrupts confirms the provenance of this design: “Mirrors adk-python NodeState.interrupts.”

The persistence boundary (v2.6.0: event-history rebuild, no stored blob)#

The RunState comment in state.go (v2.6.0) pins the direction: “It is not carried across turns as a stored value: a resume turn rebuilds it by scanning session event history (see ReconstructRunState)”. Cross-request state actually lives in the session event stream; RunState is only a recomputed product of the resume turn. Three boundaries:

  • the isolation unit is the invocation ID: ReconstructRunState(sess, invocationID) scopes one run by it (the runner reuses the paused turn’s invocation ID on the resume turn, so pause and answer share one). An empty invocationID = scanning all history — then two graphs in one session with duplicated node names are guaranteed to collide (article 2’s collision condition).
  • renaming nodes / restructuring the graph and deploying = stranded HITL: the rebuild matches history by node name; an old-name waiting record can no longer be found, so that interrupt waits forever for an answer and Resume only reports ErrNothingToResume. The v2.4.0-era “swap the name to open a new namespace” remedy is dead — name is just a path prefix, changing it does not affect event attribution. Clear pending sessions before touching a node name.
  • node Input/Output must be JSON-encodable (the NodeState fields are unchanged); binary goes to artifacts with a URI in state.

5. Dynamic graphs: DynamicNode + RunNode#

orchestrator := workflow.NewDynamicNode[Issue, Report]("orchestrate",
	func(ctx agent.Context, in Issue, emit func(*session.Event) error) (Report, error) {
		fix, err := workflow.RunNode[FixResult](ctx, fixerAgent, in)
		if err != nil {
			if errors.Is(err, workflow.ErrNodeInterrupted) {
				return zero, err          // the child asked a human; let it bubble
			}
			var nre *workflow.NodeRunError
			if errors.As(err, &nre) {
				log.Printf("child %s (%s) failed: %v", nre.ChildName, nre.ChildPath, nre.Cause)
			}
			return zero, err
		}
		return Report{Fix: fix}, nil
	},
	workflow.NodeConfig{},
)

Signature RunNode[OUT any](ctx agent.Context, child Node, input any, opts ...RunNodeOption) (OUT, error) — the generic result gives you the type directly, no manual assertion.

The failure classification table#

The RunNode comment lists four classes, transcribed:

Test Meaning
errors.Is(err, ErrNodeInterrupted) the child paused for HITL (including the wrapped ErrNodeWaitingForOutput)
errors.Is(err, ErrNodeFailed) + errors.As(&NodeRunError) the child failed after exhausting retries; the struct carries ChildName/ChildPath/RunID/Cause
ErrInvalidRunNodeContext the ctx is not the ctx of a currently executing dynamic node (no child scheduler)
ErrInvalidRunID the custom run id is illegal
ctx.Err() the parent was cancelled

The ErrInvalidRunID rules are very specific (purely numeric ids are reserved):

id must be non-empty, contain at least one non-digit character
(purely numeric ids collide with the auto-counter), and exclude the
composite-path separators '/' and '@'.

The seven options#

Option Purpose Caveat
WithRunID(id) replaces the auto counter with a stable ID (so reorderable lists key on an order id) the ID format rules above; since v2.6.0 single-flight dedup within one activation, see the dedicated section below
WithUseSubBranch() derives <parentBranch>.<childName>@<runID> mandatory for concurrent or independent children, otherwise an LLM child agent sees its siblings’ events
WithOverrideBranch(b) replaces the inherited branch outright composable with WithUseSubBranch: override sets the base, then the child segment is appended
WithUseAsOutput() promotes the child’s output to the orchestrator’s terminal output (the Go return value is discarded) at most one per activation; a second → ErrOutputAlreadyDelegated
WithIsolationScope(s) tags the child and its events with a scope empty = no scope
WithIsolationScopeFromNodePath() uses the full node path as the scope (unique across nested graphs and duplicated names) how task-mode LlmAgents do it; when both are set WithIsolationScope wins
WithRaiseOnWait() treats a child ending with pending long-running tools as an interruption rather than a clean completion a chat orchestrator dispatching task-mode children must distinguish “the child paused” from “the child ended cleanly but set no output”

WithUseAsOutput has a knock-on effect covered in article 2: NodeInfo.OutputFor lists “which node paths this output counts for” (the emitter plus all delegating ancestors), so one event stands in for the whole delegation chain rather than each layer emitting a duplicate.

Two helpers inside DynamicNode are also worth knowing: coerceInput (converts the upstream any into IN) and composePath (builds <parent-path>/<node name>@<runID>) — this is where dynamic child paths are defined, and it is the origin of the @run_id suffix in module 4’s NodeInfo.Path.

Single-flight deduplication: the four engineering rules of a stable RunID (new in v2.6.0, #1043)#

The WithRunID comment was expanded in v2.6.0 into a hard contract; the core in one sentence: a stable ID = a deduplication key within one activation of a dynamic node.

A stable id deduplicates calls within one activation of the enclosing
dynamic node: a repeat returns the first run's output without
re-running the child, and calls that overlap in time share one
execution and its outcome. A failed or interrupted run is not
retained, so a later call runs the child again. Do not rely on this
across a HITL pause: the resume turn re-executes the dynamic node's
body, and a child that completed before the pause can run again.

Broken into four rules:

  1. Repeat calls within the same activation = cache hit: a second RunNode(id="order-42") returns the first run’s output directly without re-running the child; concurrent calls that overlap in time share one execution and its outcome (inflightByPath in dynamic_scheduler.go is this single-flight table).
  2. Failed / interrupted runs are not cached: anything that crashed or paused is not retained — the next call re-runs the child. This is deliberate; do not count on the cache to cover for you.
  3. Across a HITL pause it does not hold: the resume turn re-executes the dynamic node’s body, so a child that completed before the pause may run again (two sides of the same coin as the duplicate Resume re-run in section 3’s re-entry mode).
  4. Self-wait deadlock: a non-dynamic child node must not call RunNode with its own name+id from inside its own run — the inner call resolves to the self that is currently running and waits for it to finish, i.e. waits on itself, until the invocation is cancelled. Dynamic nodes can recurse this way, because their body schedules children under its own path.

One companion change in the same release: makeEmit now reports whether the consumer is gone (consumerGone()). After the caller breaks out of the range loop, emit inside the node body returns context.Canceled, and the orchestrator checks this flag before every yield and stops — when “the user stops generation”, the dynamic orchestrator no longer runs blind into a closed consumer.

Checklist#

  • InterruptID is unique per run (prefix + UUID), and re-entry mode looks the same ID up on resume
  • ResponseSchema is set — it doubles as a server-side validation contract
  • a re-entry node body is idempotent (it will be re-run from the start)
  • only one human is asked per activation; to ask in parallel, split into nodes (ErrParallelHITLUnsupported)
  • concurrent children got WithUseSubBranch()
  • Resume handles ErrNothingToResume (a stale or mistargeted submission)
  • the graph name is non-empty; before renaming nodes / restructuring the graph, clear the pending HITL sessions (the rebuild won’t match the old node names → ErrNothingToResume)
  • stable-RunID deduplication only holds within one activation; do not assume it across a HITL pause (the resume turn re-runs the dynamic body)
  • a non-dynamic child node does not call RunNode with its own name+id from inside its own run (self-wait deadlock)
  • everything carried across a pause is JSON-encodable, and binary goes through artifacts

Module 5 closes here: this graph engine is a first-class Agent in Go — it can pause, resume, be driven by an LLM, and its wire format is aligned across languages. Next up is Module 6: New Multi-Agent Patterns — workflowagents and the chat / task / single_turn modes of collaborative agents.

Frequently Asked Questions

How does a graph node ask a human and pause?

Yield a workflow.NewRequestInputEvent(ctx, session.RequestInput{...}) and then return workflow.ErrNodeInterrupted. The scheduler observes Event.RequestedInput and moves the node to NodeWaiting, and the turn refuses to finalize.

How do I choose between re-entry and handoff mode?

NodeConfig.RerunOnResume: &true is re-entry (the asker runs from the start again and reads the answer via ctx.ResumedInput), &false is handoff (the answer becomes the successor's input and the asker never re-executes), nil is currently treated by the engine as handoff. DynamicNode sets re-entry for you by default.

Can one node ask two people at once?

No. One activation may hold at most one pending HITL; violating it returns ErrParallelHITLUnsupported. To ask in parallel, split into multiple nodes.

What are the rules for InterruptID?

It must be unique per run. Clients such as the Dev UI record "already answered" by this ID, so a fixed literal stops ever re-prompting. Use a readable prefix plus a UUID, e.g. "human_review-" + uuid.NewString().

Is RunNode only usable inside a DynamicNode?

Correct. The ctx must carry a child scheduler, otherwise you get ErrInvalidRunNodeContext. The test is whether ctx.SubScheduler() is non-nil.

How does resuming across requests work?

RunState is no longer persisted as a blob (v2.6.0). The resume turn rebuilds it by scanning session event history via wf.ReconstructRunState(sess, invocationID), then wf.Resume(ctx, state, map[interruptID]payload) drives it.
