Scheduler lifecycle and retries: seven node states, five backoffs, and a default that refuses to retry validation errors

The scheduling layer of the ADK Go v2.4.0 graph engine: the exact semantics of the seven NodeStatus values including the two causes of NodeWaiting, why NodeRunning must be re-scheduled after a restart and the two sources of NodeCancelled, what NodeState/RunState may and may not persist and how binary payloads are handled, DefaultRetryConfig's 5/1s/60s/2.0/full-jitter policy, the two exportable pure functions ShouldRetry and CalculateDelay, why ErrInputValidation is not retried by default, struct literal versus DefaultRetryConfig, plus concurrency caps and cancellation propagation (cancelAll/echoesCancellation/nil on sibling cancellation).

September 26, 2026 · 10 min · 1949 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources workflow/{state.go,scheduler.go,retry.go,config.go,errors.go}.

The first two articles covered “what the graph looks like and where it goes”; this one covers “where each node is right now, and what happens when it fails”. The 2.x scheduler state machine is written rigorously, and the state definitions are themselves the documentation.

Seven states, semantics transcribed one by one#

type NodeStatus uint8

const (
	NodeInactive  NodeStatus = iota // zero value: untouched so far
	NodePending                     // ready to run (input arrived, or queued for retry after a failure)
	NodeRunning                     // a task is in flight within this process
	NodeCompleted                   // finished and produced output
	NodeWaiting                     // paused (two causes, see below)
	NodeFailed                      // returned an error and exhausted the retry policy. Terminal
	NodeCancelled                   // cancelled. Two sources, terminal
)

Four key rules from the comments:

  1. NodePending has two sources: “input arrived” and “queued for retry after failure”. So under WithMaxConcurrency throttling a node sits in NodePending — when diagnosing a stall, first tell “no input yet” apart from “rate limited”.
  2. NodeCompleted is not an absolute terminal state: the comment states “a node in NodeCompleted may still be re-triggered by a fresh entry in the trigger buffer (this is what enables loops as graph cycles)”. This is exactly how loops are implemented.
  3. As soon as NodeWaiting appears, the whole workflow refuses to finalize: “While any node is NodeWaiting the workflow does not finalize.” Two causes share one state: HITL pause / fan-in incomplete (WaitForOutput=true, e.g. a JoinNode). When chasing “the graph never ends”, first determine which one it is — a non-empty NodeState.Interrupts means HITL, an unfinished predecessor means fan-in.
  4. NodeRunning is a process-local concept, and the comment demands outright:
A NodeRunning entry that has no live task in the run state
(e.g. after a process restart) must be re-scheduled.

Which means node bodies must be safe to re-run — after crash recovery the same node runs again, so side effects (writing to a database, sending messages) must be idempotent. This matters most when it stacks with article 5’s HITL rerun mode (RerunOnResume).

The NodeCancelled comment deserves transcription too:

NodeCancelled means the node was cancelled: either because a sibling
node failed and the engine cancelled all running tasks, or because the
invocation context was cancelled from outside the engine. Terminal in
both cases — the two are told apart by whether the run reports an error,
not by this status.

To learn “did we fail or were we implicated”, look at the error, not the status. handleCompletion implements precisely that:

if s.parentCtx.Err() != nil {
	if it.err != nil && !s.echoesCancellation(it.err) {
		ns.Status = NodeFailed
		return it.err                 // keep the original error, it "says more than cancelled"
	}
	ns.Status = NodeCancelled
	return nil
}
if errors.Is(it.err, context.Canceled) {
	ns.Status = NodeCancelled
	return nil                        // a sibling cancellation, not the original error
}

(The comment also names the cross-implementation alignment: adk-python’s _cleanup_all_tasks in its finally block marks every reclaimed task CANCELLED without distinction.)

The lifecycle record: what may persist and what may not#

type NodeState struct {
	Status        NodeStatus   `json:"status"`
	Input         any          `json:"input,omitempty"`
	Output        any          `json:"output,omitempty"`
	TriggeredBy   string       `json:"triggeredBy,omitempty"`
	Branch        string       `json:"branch,omitempty"`
	Interrupts    []string     `json:"interrupts,omitempty"`
	Attempt       int          `json:"attempt,omitempty"`
	ResumedInputs map[string]any `json:"resumedInputs,omitempty"`
	// private and not persisted: interruptSchemas, answeredThisTurn
}

type RunState struct {
	Nodes map[string]*NodeState // a missing entry = inactive
}

The RunState comment: “It rides in session.State across pause and resume turns”. That imposes one hard constraint, and the NodeState comment supplies the handling:

JSON-marshallable: ... The Input, Output, and PendingRequest.Payload fields
are typed any and must therefore be JSON-encodable for the persisted state
to round-trip. Nodes that need to carry binary data across a pause should
store the bytes via agent.Artifacts and stash a URI string in place of the
bytes.

So: to carry binary across a pause, store it as an artifact and keep a URI string in state. Do not expect a custom type inside an any other than []byte to survive (either json.Marshal fails on the spot, or unexported fields are silently dropped).

Two fields that “look persisted but are not” — understanding them saves a lot of confusion:

  • interruptSchemas: rebuilt from the event history on every request (comment: “the schema lives only in the events and is rebuilt each turn”), so Resume can validate the payload shape, but you cannot read it back from RunState.
  • answeredThisTurn: the idempotency discriminator — separating “answered for the first time this turn” from “a duplicate resume replay”. A terminal handoff asker (no successor) relies on it to count the first answer as a valid resume and the duplicates as no-ops.

Mind the wording of Attempt: “the number of times this node has been failed” — it counts failures, not executions. ShouldRetry(cfg, err, failedAttempts) compares it against MaxAttempts.

Retry: the defaults, two testable pure functions, and one counter-intuitive default behaviour#

// the recommended posture (verbatim from the config.go comment)
rc := workflow.DefaultRetryConfig()   // returns a copy
rc.MaxAttempts = 10
cfg := workflow.NodeConfig{RetryConfig: rc}

The default policy (defaultRetryConfig):

MaxAttempts: 5, InitialDelay: time.Second, MaxDelay: 60*time.Second,
BackoffFactor: 2.0, Jitter: 1.0, ShouldRetry: defaultShouldRetry,

The comment translates these numbers into plain words: “5 attempts, 1s initial delay, 60s cap, 2x backoff, full jitter, retry every error”.

⚠️ “retry every error” does not match the implementation, and this is the single most important warning in this article. The field comment says “If not specified, default to true”, but the code’s default is:

func defaultShouldRetry(err error) bool {
	return !errors.Is(err, ErrInputValidation)
}

That is, input validation failures are not retried by default. The rationale for ShouldRetry is in the comment: “we do not retry input validation errors because the input is deterministic per activation. Retrying would just loop on the same failure.”

The reasoning is sound, but the documented field and the implementation disagree — rely on “retries everything by default” and you fall through. When you genuinely need validation errors retried, the comment leaves the door open: set ShouldRetry explicitly (“This allows users to override the default behavior and retry validation errors if desired”).

The exact semantics of each RetryConfig field:

FieldSemanticsBoundaries
MaxAttemptstotal attempts including the first0 or 1 = no retry; defaults to 5 when unset
InitialDelaydelay before the first retrydefaults to 1s when unset
MaxDelaydelay ceilingdefaults to 60s when unset; <=0 means uncapped
BackoffFactormultiplier per attempt1.0 constant, 2.0 exponential, <1.0 shrinks each time (allowed); <=0 is treated as 1.0 (otherwise it collapses to 0)
Jittera random factor in [0,1]the actual delay is sampled from delay * (1 ± Jitter); 0 = fully deterministic
ShouldRetrypredicate; retry only if truefalls back to defaultShouldRetry when nil

RetryConfig is deliberately a “flat pure value” struct, and the comment says so: “no dependency on cenkalti/backoff/v5”. So you can unit-test the delay algorithm yourself — the two exported functions exist for exactly that:

d := workflow.CalculateDelay(rc, 3)              // how long to wait after the 3rd failure
ok := workflow.ShouldRetry(rc, err, failedCount) // should we try again

CalculateDelay’s implementation is worth two glances because of two easily forgotten behaviours: jitter is applied after the cap (so near MaxDelay you can slightly exceed it), and a post-jitter delay < 0 is clamped back to 0. Use Jitter: 0 in tests to get deterministic values.

Why not a struct literal: the comment is explicit — “Constructing via struct literal is permitted but discouraged: any unset field defaults to its zero value, not to DefaultRetryConfig’s value. The zero RetryConfig is a valid ’no retry, no backoff, no jitter’ policy.” Meaning RetryConfig{MaxAttempts: 5} yields InitialDelay: 0 (five immediate retries), not a 1-second start. Only reading the comment protects you from this.

NodeConfig.RetryConfig itself is a *RetryConfig, and nil means the node does not retry (no retry by default! Retrying is enabled per node, explicitly).

Concurrency, timeouts, cancellation#

Graph-level cap: workflow.New(name, edges, workflow.WithMaxConcurrency(8)). n <= 0 disables it; overflow nodes sit in NodePending.

⚠️ The exception written in the comment must be memorised:

Does NOT apply to dynamic sub-nodes invoked via workflow.RunNode from
inside a DynamicNode body — they are awaited inline by the parent and
gating them would deadlock.

Node-level concurrency is a different knob: ParallelWorker (NewParallelWorker(name, wrapped, maxConcurrency, cfg)) and NodeConfig.ParallelWorker bool. The graph-level cap governs “how many nodes run at once”, the node-level one governs “how many list items run at once”. They are independent.

Timeouts: NodeConfig.Timeout, and the comment pins the granularity — “bounds a single activation of the node via context.WithTimeout on the per-node context” — one budget per activation, and 0 (default) means bounded only by the parent invocation deadline. So with retries configured, Timeout × MaxAttempts is this node’s worst-case wall clock.

Cancellation: cancelAll() is invoked by the consumer on break or failure. The engineering implication: node bodies must honour ctx cancellation — exit immediately when yield returns false, and add ctx.Err() checks inside long loops. The engine guarantees no leak after wg.Wait(), but only on the precondition that your nodes actually terminate.

How failures surface#

type NodeRunError struct {
	ChildName string   // "fixer_agent"
	ChildPath string   // "code_workflow/fixer_agent@2"
	RunID     string   // auto-counted, or supplied via WithRunID
	Cause     error
}
// Error(): "workflow: dynamic child <path>: <cause>"

Use errors.As for the fields and Unwrap for the cause. At the outer boundary test with errors.Is(err, workflow.ErrNodeFailed) (comment: “wraps a child node’s runtime failure after retries” — a node only becomes NodeFailed once retries are exhausted).

One telemetry detail: isNodeControlFlow(err) separates control-flow errors such as ErrNodeInterrupted from genuine failures so they do not pollute span error records. Which means “a red node in the trace” is a real failure — HITL pauses never get mixed in.

Checklist#

  • every node is safe to re-run (NodeRunning must be re-scheduled after a restart)
  • RetryConfig is always obtained by copying DefaultRetryConfig() and then modified
  • if validation errors must be retried, set ShouldRetry explicitly (the default refuses)
  • nodes with side effects set a Timeout; estimate the Timeout × MaxAttempts upper bound
  • everything that crosses a HITL pause is JSON-encodable; binary goes through artifacts + a URI
  • graphs with many dynamic nodes: do not expect WithMaxConcurrency to gate them (deadlock)
  • when the workflow will not finalize, check for a NodeWaiting node first, then separate HITL from fan-in

Frequently Asked Questions

What is the default retry policy for ADK Go graph nodes?

Five attempts including the first, 1 second initial delay, a 60 second cap, factor 2.0, full jitter (Jitter=1.0), and ErrInputValidation is not retried by default. But the policy only applies when you explicitly set NodeConfig.RetryConfig — nil means no retry.

Why is a struct literal discouraged for RetryConfig?

The comment says it outright: fields you leave unset are zero values, not defaults. A zero RetryConfig is a legitimate 'no retry, no backoff, no jitter' policy. To customise, copy DefaultRetryConfig() and then override.

How many ways can a node reach NodeWaiting?

Two share one state: HITL pause (a RequestInput was yielded and it waits for a FunctionResponse), and fan-in (WaitForOutput=true, it ran but predecessors are incomplete). While any node is NodeWaiting the workflow does not finalize.

What happens to NodeRunning nodes after a process restart?

The status comment requires it explicitly: a NodeRunning entry with no live task in the run state (for example after a process restart) must be re-scheduled. So node bodies must be idempotent.

Is a cancelled node a failure?

No. Cancellation caused by a sibling failing returns a nil error (only the original error is preserved); only an external cancellation makes the run report an error. The discriminator is whether the run reports an error, not the NodeCancelled status itself.

How do I configure the concurrency cap?

workflow.New's WithMaxConcurrency(n) option (n<=0 disables it); overflow nodes queue as NodePending. Note it does not govern dynamic children dispatched by RunNode — that would deadlock.
