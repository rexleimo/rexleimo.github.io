Edges and the execution model: EdgeBuilder, the eight graph validations, and that single consumer goroutine

The wiring layer of the ADK Go v2.6.0 graph engine: Edge{From,To,Route} and the Start sentinel, EdgeBuilder's six methods plus Chain/Concat, the eight legality checks in workflow.New (duplicate edges, multiple default routes, unreachable nodes, unconditional cycles, sub-graph name collisions…), name being only a node-path prefix (a label, no longer a persistence namespace), AddRoutes' byte-lexicographic determinism, the one-goroutine-per-node plus single-consumer execution model, what yielding events in arrival order implies, and the userInput text concatenation rule.

September 26, 2026 · 9 min · 1782 words · Mengshou Programming -  |  中文

Verified version: google.golang.org/adk/v2 v2.6.0 (released 10-13), sources workflow/{workflow.go,edgebuilder.go,graph.go,validation.go}; every difference from v2.4.0 in this article comes from the side-by-side two-version source comparison.

An edge is just three fields#

type Edge struct {
	From  Node
	To    Node
	Route Route   // a condition; nil means an unconditional edge
}

var Start Node = &startNode{BaseNode: NewBaseNode("START", "Start node", NodeConfig{})}

Start is a sentinel: its Run yields nothing (func(yield ...) {}) and exists only as “the entry point of the graph”. Hence every graph needs an edge with From: workflow.Start, or you get ErrNoStartNode.

The bare form is entirely sufficient:

wf, err := workflow.New("my-flow", []workflow.Edge{
	{From: workflow.Start, To: intake},
	{From: intake, To: classify},
	{From: classify, To: urgent, Route: workflow.StringRoute("urgent")},
	{From: classify, To: normal, Route: workflow.StringRoute("normal")},
	{From: urgent, To: join},
	{From: normal, To: join},
})

Three terser ways to build them#

// ① a chain
edges := workflow.Chain(a, b, c)     // returns nil when len < 2 (no error)

// ② mixed merge: accepts both Edge and []Edge
edges := workflow.Concat(
	workflow.Chain(a, b),
	workflow.Edge{From: b, To: c, Route: workflow.BoolRoute(true)},
	[]workflow.Edge{{From: c, To: d}},
)

// ③ a fluent builder
edges := workflow.NewEdgeBuilder().
	Add(workflow.Start, a).
	AddRoute(a, b, workflow.IntRoute(2)).
	AddFanOut(b, c1, c2, c3).
	AddFanIn(join, c1, c2, c3).
	AddRoutes(a, map[string]workflow.Node{"x": b, "y": d}).   // converted to StringRoute internally
	Build()

Concat(items ...any) uses a type switch that recognises only Edge and []Edge — a wrong type raises no error, it is silently ignored, which is what makes it more dangerous than append. After writing one, print len(edges).

AddRoutes takes a map[string]Node and turns each route key into a StringRoute. Since v2.6.0 the edges are added in byte-lexicographic order of the route key ("10" before "2") — that is the October fix (#1268); in v2.4.0 Go’s random map-iteration order made the emitted edge order unstable and tests flaky. The order is now observable: it drives successor start order, and also the order of the pending queue under WithMaxConcurrency. To control the order, use AddRoute one at a time (a Default edge can only be added that way — AddRoutes cannot express it).

The eight checks in workflow.New#

New(name, edges, opts...) runs validateNodes → validateSubWorkflowNames → newGraph → validateWorkflow in order. Any failure returns an error at construction time, not at runtime:

Sentinel Trigger Notes
ErrDuplicateNodeName two distinct instances sharing one Name() the lifecycle map is keyed by name, so a collision cross-wires state
ErrNoStartNode no outgoing edge from START
ErrNodePointsToStart some node points back at START the entry point must not be treated as an ordinary predecessor
ErrDuplicateEdge identical (From, To) pair Route is not examined; the comment names the alternative directly: use MultiRoute for several conditions to one target
ErrMultipleDefaultRoutes a node has more than one default route see article 3
ErrNodesNotReachable a node is unreachable from START written but never executed
ErrUnconditionalCycle a cycle with no conditional edge in it an unconditional cycle is an infinite loop, rejected outright
ErrSubWorkflowNameCollision a sub-workflow shares the parent’s name the validation logic is unchanged in v2.6.0; the “persistence namespace” rationale in the old comment was rewritten along with the name semantics (see the section below) — read it now as a path label: under the same prefix, sub-graph and parent-graph node event paths mix up

One comment on the last group records an important fact: the NodeCompleted state can be reactivated by a new entry in the trigger buffer — “this is what enables loops as graph cycles”. In other words, a legal loop = a cycle plus a conditional edge, with routing making the loop converge.

name is only a path prefix, not a namespace (changed in v2.6.0)#

The v2.4.0 comment told a different story: name took part in the persistence key of session.State, two graphs with the same name in one session would silently overwrite each other’s RunState, an empty name disabled persistence, and upstream had a “graph fingerprint check” TODO hanging around. v2.6.0 replaced that entire comment, and the semantics became:

// The name labels this workflow's nodes on the paths Run records: Run
// prefixes the node path with it, except for a root wrapper. ...
// The prefix is a label, not a namespace - history is attributed to a run
// by invocation ID, not by this name, so the only thing keeping two
// workflows that share a node name apart is that their runs carry
// different invocation IDs.

Three changes:

  1. The persistence model changed. RunState is no longer stored under name into session.State as a blob and read back; a resume turn recomputes it by scanning session event history (ReconstructRunState(sess, invocationID), persistence.go; the state.go comment verbatim: “It is not carried across turns as a stored value: a resume turn rebuilds it by scanning session event history”). The history scan scopes a single run by invocation ID — two runs one after another in the same session do not cross-wire, because event attribution goes through the node name in the node path, and the workflow-name segment is ignored outright.
  2. Empty name means something new: not “disable persistence” but “no path prefix” — nodes are recorded under the bare node path.
  3. The collision condition changed: you no longer worry about “two graphs with the same name silently overwriting each other’s RunState” (that mechanism is gone); you now worry about same-named nodes within the same invocation — when two graphs share a node name, event attribution resolves by node name, whatever the workflows are called; with an empty invocationID this collision is unavoidable.

The release-safety advice changes with it: the old “rename to open a new namespace” no longer works — renaming only changes the path prefix, and event-history attribution (by node name + invocation ID) is unaffected. The real risk is deploying after changing node names or the graph structure: ReconstructRunState cannot find the pending records under the old node names when it scans history, so unresolved HITL will never receive its answer (article 5’s Resume returns ErrNothingToResume). When you must change a node name across a release, drain the pending sessions first. (The graph-fingerprint TODO is still pending upstream in v2.6.0 — there is still no fingerprint check today.)

The execution model: one goroutine per node, one consumer#

The comment on Run states the model cleanly:

The engine model: each scheduled node runs in its own goroutine pushing events into a buffered channel. A single consumer goroutine (this one) drains the channel, applies state-side effects, yields events to the caller, and schedules successors when nodes complete. The consumer is the only mutator of the per-node lifecycle map and of session state.

Four engineering implications:

  • a node body does not need a lock to mutate session state — that is the consumer’s job. Your node only needs its own internal state to be concurrency-safe.
  • events are yielded in arrival order (comment: “in arrival order”). There is no determinate order between concurrent branches, so do not assume downstream that “A’s event always precedes B’s”. If you need an order, build a dependency in the graph, or attach a JoinNode.
  • break mid-stream is part of the contract: “the caller may break from the range loop at any point and the engine will cancel all in-flight nodes before returning”. So a UI-side “stop generating” can just break; the engine cancels and calls wg.Wait() (the comment at the end of RunNode: All goroutines have returned; ensure no leak).
  • WithMaxConcurrency(n) queues the overflow as NodePending (n <= 0 disables the cap), but it does not apply to dynamic children dispatched by RunNode — the parent awaits its children in place, so stalling a child deadlocks. That exception is written in the WithMaxConcurrency comment and bites easily.

Two ways to drive it#

// ① run it as an agent (the Runner calls it): input comes from this turn's user content
for ev, err := range wf.Run(ctx) { … }

// ② pass input explicitly (this is exactly what WorkflowNode does internally)
for ev, err := range wf.RunNode(ctx, myInput) { … }

Run first does one thing: it “promotes” the ctx into a path-bearing context — Path = "<wfName>@1" (or parent-path/<wfName>@1 when a parent path exists) and RunID = "1", then calls w.RunNode(c, userInput(c)).

⚠️ userInput’s behaviour is worth memorising: it returns all non-empty Text parts of ctx.UserContent().Parts concatenated into one string, and returns nil when UserContent() is nil. Multimodal input (image parts) is dropped — if a graph needs images, do not expect Run to pass them: use RunNode with explicit input, or fetch from state/artifact with {artifact.x}.

The isRootWrapper option also explains a phenomenon: when the Runner runs a single non-graph agent, Go constructs a synthetic one-node wrapper workflow so every execution goes through the same graph engine. In that case the parent namespace prefix is not added, keeping event paths strictly aligned with adk-python (Python does not wrap). The path differences like app/agent@1 you see in telemetry originate here.

Troubleshooting quick reference#

Symptom Check first
New reports nodes not reachable from start node a missing outgoing START edge, or an edge written backwards
the graph stalls at some node is that node a JoinNode? does a conditional edge point at it (not allowed)
odd behaviour after resume did you rename nodes / change the graph structure but an old session is still waiting on HITL? (reconstruction won’t match, Resume reports ErrNothingToResume); when the invocationID is empty, same-node-name history mixes up
concurrent branches emit in unstable order expected, it is arrival order; add a dependency or a JoinNode if you need order
multimodal input never reaches the graph Run concatenates text parts only — pass it explicitly via RunNode

Frequently Asked Questions

How do I declare workflow edges in ADK Go 2.x?

[]workflow.Edge{{From: workflow.Start, To: a}, {From: a, To: b}}, or workflow.Chain(a, b, c) to build a chain, NewEdgeBuilder() for chaining calls, and Concat(...) to merge mixed fragments.

Can two edges go from A to B with different routes?

No. ErrDuplicateEdge: an identical (From,To) pair counts as duplicate regardless of Route. To express several conditions for one target, use MultiRoute.

What is the workflow name for?

Since v2.6.0 it is only the prefix of node paths (a label): event attribution goes through the node name, ignoring the workflow-name segment; what actually scopes a single run is the invocation ID (under an empty invocationID, two graphs with the same node name always mix up).

Do nodes in the graph run concurrently?

They do — each scheduled node runs in its own goroutine pushing events into a buffered channel, and only a single consumer goroutine mutates the lifecycle map and session state.

Can I rely on event order?

Causal order, yes; global arrival order, no — events from concurrent branches are yielded in arrival order. If you need a determinate order, add a dependency in the graph (or use a JoinNode).

Which errors does workflow.New check for?

Eight sentinels: duplicate node name, no START, a node pointing at START, duplicate edge, multiple default routes, unreachable node, unconditional cycle, sub-workflow name collision.
