Edges and the execution model: EdgeBuilder, the eight graph validations, and that single consumer goroutine

The wiring layer of the ADK Go v2.4.0 graph engine: Edge{From,To,Route} and the Start sentinel, EdgeBuilder's six methods plus Chain/Concat, the eight legality checks in workflow.New (duplicate edges, multiple default routes, unreachable nodes, unconditional cycles, sub-graph name collisions…), the consequences of name being RunState's persistence namespace and the graph-evolution risk, the one-goroutine-per-node plus single-consumer execution model, what yielding events in arrival order implies, and the userInput text concatenation rule.

September 26, 2026 · 7 min · 1487 words · Mengshou Programming -  |  中文

Verified against: google.golang.org/adk/v2 v2.4.0, sources workflow/{workflow.go,edgebuilder.go,graph.go,validation.go}.

An edge is just three fields#

type Edge struct {
	From  Node
	To    Node
	Route Route   // a condition; nil means an unconditional edge
}

var Start Node = &startNode{BaseNode: NewBaseNode("START", "Start node", NodeConfig{})}

Start is a sentinel: its Run yields nothing (func(yield ...) {}) and exists only as “the entry point of the graph”. Hence every graph needs an edge with From: workflow.Start, or you get ErrNoStartNode.

The bare form is entirely sufficient:

wf, err := workflow.New("my-flow", []workflow.Edge{
	{From: workflow.Start, To: intake},
	{From: intake, To: classify},
	{From: classify, To: urgent, Route: workflow.StringRoute("urgent")},
	{From: classify, To: normal, Route: workflow.StringRoute("normal")},
	{From: urgent, To: join},
	{From: normal, To: join},
})

Three terser ways to build them#

// ① a chain
edges := workflow.Chain(a, b, c)     // returns nil when len < 2 (no error)

// ② mixed merge: accepts both Edge and []Edge
edges := workflow.Concat(
	workflow.Chain(a, b),
	workflow.Edge{From: b, To: c, Route: workflow.BoolRoute(true)},
	[]workflow.Edge{{From: c, To: d}},
)

// ③ a fluent builder
edges := workflow.NewEdgeBuilder().
	Add(workflow.Start, a).
	AddRoute(a, b, workflow.IntRoute(2)).
	AddFanOut(b, c1, c2, c3).
	AddFanIn(join, c1, c2, c3).
	AddRoutes(a, map[string]workflow.Node{"x": b, "y": d}).   // converted to StringRoute internally
	Build()

Concat(items ...any) uses a type switch that recognises only Edge and []Edge — a wrong type raises no error, it is silently ignored, which is what makes it more dangerous than append. After writing one, print len(edges).

AddRoutes takes a map[string]Node and turns each route key into a StringRoute. Go map iteration order is random, so the order of the edges it emits is unstable — graph semantics do not depend on edge order (routing asks “which ones match”, not “the first match”), but if you have a test asserting on the edges slice contents, it will be flaky.

The eight checks in workflow.New#

New(name, edges, opts...) runs validateNodes → validateSubWorkflowNames → newGraph → validateWorkflow in order. Any failure returns an error at construction time, not at runtime:

SentinelTriggerNotes
ErrDuplicateNodeNametwo distinct instances sharing one Name()the lifecycle map is keyed by name, so a collision cross-wires state
ErrNoStartNodeno outgoing edge from START
ErrNodePointsToStartsome node points back at STARTthe entry point must not be treated as an ordinary predecessor
ErrDuplicateEdgeidentical (From, To) pairRoute is not examined; the comment names the alternative directly: use MultiRoute for several conditions to one target
ErrMultipleDefaultRoutesa node has more than one default routesee article 3
ErrNodesNotReachablea node is unreachable from STARTwritten but never executed
ErrUnconditionalCyclea cycle with no conditional edge in itan unconditional cycle is an infinite loop, rejected outright
ErrSubWorkflowNameCollisiona sub-workflow shares the parent’s namenamespace conflict

One comment on the last group records an important fact: the NodeCompleted state can be reactivated by a new entry in the trigger buffer — “this is what enables loops as graph cycles”. In other words, a legal loop = a cycle plus a conditional edge, with routing making the loop converge.

name is not a label: it is a persistence namespace#

// the comment on New (excerpt)
// The name forms part of the session.State key under which this
// workflow's RunState is persisted. It must be unique within any session
// that runs more than one workflow: two workflows sharing a name and a
// session will silently overwrite each other's RunState, leading to
// corrupted resume behaviour. ... An empty name disables persistence.

Three consequences:

  1. one session running several graphs means the names must all differ, otherwise resume behaviour corrupts silently (no error!).
  2. to make a graph resumable across turns (HITL), name must be non-empty. An empty-named graph runs normally, but RunState is neither written nor read.
  3. Upstream left two TODOs, one of which bears directly on release safety:
// TODO(wolo): record a graph fingerprint (e.g. sorted node names hash)
// on the Workflow and verify it against any loaded RunState in Resume;
// today a name collision or a graph evolution between deploys silently
// corrupts the resume path.

There is no graph fingerprint check today. So if you rename a node or change the graph structure and deploy while live sessions still hold unfinished state, the resume path silently ingests corrupt data. When a graph structure changes across a release, deal with the old RunState first (or give the new graph a fresh name — since name is part of the persistence key, changing it is equivalent to opening a new namespace).

The execution model: one goroutine per node, one consumer#

The comment on Run states the model cleanly:

The engine model: each scheduled node runs in its own goroutine pushing events into a buffered channel. A single consumer goroutine (this one) drains the channel, applies state-side effects, yields events to the caller, and schedules successors when nodes complete. The consumer is the only mutator of the per-node lifecycle map and of session state.

Four engineering implications:

  • a node body does not need a lock to mutate session state — that is the consumer’s job. Your node only needs its own internal state to be concurrency-safe.
  • events are yielded in arrival order (comment: “in arrival order”). There is no determinate order between concurrent branches, so do not assume downstream that “A’s event always precedes B’s”. If you need an order, build a dependency in the graph, or attach a JoinNode.
  • break mid-stream is part of the contract: “the caller may break from the range loop at any point and the engine will cancel all in-flight nodes before returning”. So a UI-side “stop generating” can just break; the engine cancels and calls wg.Wait() (the comment at the end of RunNode: All goroutines have returned; ensure no leak).
  • WithMaxConcurrency(n) queues the overflow as NodePending (n <= 0 disables the cap), but it does not apply to dynamic children dispatched by RunNode — the parent awaits its children in place, so stalling a child deadlocks. That exception is written in the WithMaxConcurrency comment and bites easily.

Two ways to drive it#

// ① run it as an agent (the Runner calls it): input comes from this turn's user content
for ev, err := range wf.Run(ctx) { … }

// ② pass input explicitly (this is exactly what WorkflowNode does internally)
for ev, err := range wf.RunNode(ctx, myInput) { … }

Run first does one thing: it “promotes” the ctx into a path-bearing context — Path = "<wfName>@1" (or parent-path/<wfName>@1 when a parent path exists) and RunID = "1", then calls w.RunNode(c, userInput(c)).

⚠️ userInput’s behaviour is worth memorising: it returns all non-empty Text parts of ctx.UserContent().Parts concatenated into one string, and returns nil when UserContent() is nil. Multimodal input (image parts) is dropped — if a graph needs images, do not expect Run to pass them: use RunNode with explicit input, or fetch from state/artifact with {artifact.x}.

The isRootWrapper option also explains a phenomenon: when the Runner runs a single non-graph agent, Go constructs a synthetic one-node wrapper workflow so every execution goes through the same graph engine. In that case the parent namespace prefix is not added, keeping event paths strictly aligned with adk-python (Python does not wrap). The path differences like app/agent@1 you see in telemetry originate here.

Frequently Asked Questions

How do I declare workflow edges in ADK Go 2.x?

[]workflow.Edge{{From: workflow.Start, To: a}, {From: a, To: b}}, or workflow.Chain(a, b, c) to build a chain, NewEdgeBuilder() for chaining calls, and Concat(...) to merge mixed fragments.

Can two edges go from A to B with different routes?

No. ErrDuplicateEdge: an identical (From,To) pair counts as duplicate regardless of Route. To express several conditions for one target, use MultiRoute.

What is the workflow name for?

It is the namespace of RunState inside session.State, so it must be unique whenever one session runs more than one workflow. An empty name disables persistence, and Resume then finds no state to restore.

Do nodes in the graph run concurrently?

They do — each scheduled node runs in its own goroutine pushing events into a buffered channel, and only a single consumer goroutine mutates the lifecycle map and session state.

Can I rely on event order?

Causal order, yes; global arrival order, no — events from concurrent branches are yielded in arrival order. If you need a determinate order, add a dependency in the graph (or use a JoinNode).

Which errors does workflow.New check for?

Eight sentinels: duplicate node name, no START, a node pointing at START, duplicate edge, multiple default routes, unreachable node, unconditional cycle, sub-workflow name collision.
