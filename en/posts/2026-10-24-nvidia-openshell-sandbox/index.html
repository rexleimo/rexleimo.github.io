NVIDIA Built a 'Catching-You-Red-Handed' Sandbox for AI Agents in Rust: Inside OpenShell

NVIDIA's open-source agent runtime OpenShell: 28 Rust crates, Landlock + seccomp + SMT formal verification to stop agents from stepping out of line. I compiled and ran the full CLI + gateway on a 2-core box, default policy auto-applied, escalation sequence re-run, single exec wall 278ms. Numbers at the end.

October 24, 2026 · 8 min · 1676 words · DreamBeast -  |  中文

OpenShell is NVIDIA’s open-source agent runtime (HN on 10-23, 489 points). What it does is concrete: an autonomous agent has to read files, install packages, call APIs, and use secrets, and OpenShell stops every one of those actions at the kernel level. The policy does not rely on the agent being well-behaved. It relies on syscall filtering plus Landlock file isolation plus an L7 network policy mesh. The extra layer is formal verification: before a policy change lands, it goes through an SMT solver, which proves what new access that change would permit, and a human approves after. I compiled and ran both the CLI and the gateway on my own box. Machine, versions, and the compile traps I hit are all at the end.

Why Agents Need a “Catching-You-Red-Handing” Layer#

The more capable an agent, the more it has to touch the real system: install dependencies, write to output dirs, call paid APIs. The usual move is to give the agent a container and let the container be the security boundary, jailbreaks happen by finding image vulns. OpenShell’s boundary is not on the container: each agent runs in its own sandbox, kernel controls restrict which files it can access and which syscalls it can make, and every outbound connection goes through a policy check before it leaves the sandbox. The agent never sees the real secret; OpenShell only injects credentials when a request is bound to an approved endpoint. Two lines of defense, split: the runtime stops escalation, the policy layer does a formal proof before a change lands.

The Mechanism Down to Source#

Twenty-eight Rust crates in the repo, five are the security-critical ones. openshell-sandbox is the executor: linux/seccomp.rs generates the syscall allowlist, linux/landlock.rs confines file access to the declared dirs. openshell-supervisor manages process lifecycle and namespaces. openshell-network is the L7 proxy, every HTTP request is checked against the policy engine one by one, denials carry OCSF-structured logs (NetworkActivityBuilder, four-level Severity). openshell-policy is the policy engine itself, declarative YAML. openshell-prover is the formal verifier, backed by an SMT solver (z3 0.21; the default build links the system libz3, and the repo ships two features, vendored-z3 and prebuilt-z3, to switch how z3 is compiled).

A minimal policy looks like this (from examples/policy-advisor/sandbox-policy.yaml):

version: 1
network_policies:
  anthropic:
    name: Anthropic API
    endpoints:
      - { host: api.anthropic.com, port: 443 }

Only that one endpoint is allowed through, every other outbound connection gets stopped at the proxy. If the agent wants another host, the path is: policy change, prover verifies, a human approves. Or it is just denied. The design of “credentials only injected at approved endpoints” keeps the blast radius of a leaked key inside the few lines of policy you declared.

Getting the Compile Chain Through Locally: z3 Is the First Wall#

My box: 2-core EPYC, rustc 1.95. The clone is 52MB (no target). With default features, cargo build --release first fails at link time: rust-lld cannot find -lz3, because openshell-prover depends on the SMT solver z3 and the default is a system library. This machine has no sudo to install libz3-dev, so I switched to the feature the repo already ships:

cargo build --release -p openshell-gateway --features vendored-z3

vendored mode makes z3-sys source-compile the C++ z3 (z3-src 501). That needs cmake, which the system lacks, so I installed a static cmake with uv (uv tool install cmake, lands in ~/.local, doesn’t touch the system) and then built. The z3 C++ full release took 29 minutes on this 2-core box (the out dir ends up 314MB, the arith/solver submodules are the heavy part). The gateway binary is 105,963,480 bytes (106MB, links z3 static + the whole dep tree); the CLI binary is 26,573,136 bytes (26.6MB); CLI cold start --help measured 12ms.

Compile-time ledger: openshell-cli first build, wall 10m24s (of which 8m36s was the prover dependency tree, link died on missing -lz3); the gateway full build with vendored-z3, wall 33m38s (z3 C++ 29 min + 28 Rust crates + link), peak memory 2.85GB. Against the Proa benchmark repo’s first build at 6m33s on the same machine, OpenShell’s dependency tree is a tier heavier (gRPC/tonic + SMT + container driver, the whole kit).

Local Gateway + Sandbox: The Escalation Sequence, Re-run#

Docker driver + local mTLS gateway, minimal setup (full commands at the end): gateway comes up on 127.0.0.1:17670, the CLI registers over mTLS (client cert goes in XDG_CONFIG_HOME/openshell/gateways//mtls/), and sandbox create reaches Ready within 60 seconds.

After the sandbox is up, a default policy is applied automatically; sandbox get demo prints it out: /bin, /usr, /lib, /etc, /var/log all read-only, /tmp read-write, Landlock compatibility set to best_effort. Three escalation sequences:

ActionResult
sandbox exec echo (normal command)passes, single exec wall 278ms
touch /etc/probe (read-only region)Permission denied, stopped by Landlock
echo probe > /tmp/wool.txtpasses, written and read back

The 278ms is one full exec chain: CLI to mTLS gRPC to gateway to supervisor to the process inside the sandbox to the result coming back, the whole proxy stack in one pass. The default policy’s Landlock section is declarative YAML; for the agent to reach a new directory it goes through the “policy change request, formal verification, human approval” flow. That layer I did not drive the prover through independently on this box; I quote the official README’s description.

What I Did Not Re-run#

The Kubernetes multi-tenant shape is unverified (no cluster on this box). The formal verifier (prover) has no ready-made entry point on this box to drive a single policy-change proof by itself (prover-cli depends on z3 compiling, but the in-repo e2e runs the full with-docker-gateway.sh suite; the path to a minimal single-node proof is still being dug out). This piece backs the compile numbers, the mechanism breakdown, and the three escalation-sequence outputs from the minimal sandbox demo. The formal-verification section is quoted from the official README, not independently driven.

FAQ#

Q: The agent is locked in the sandbox, how does it call APIs? A: All outbound traffic goes through the openshell-network L7 proxy, which checks each request against policy. Approved endpoints get their credentials injected by OpenShell; the agent process itself never holds the secret in plaintext.

Q: What is the split between Landlock and seccomp? A: Landlock manages path-level read/write file permission (the agent can only touch the dirs policy declares); seccomp manages the syscall allowlist (forbidden calls get killed or caught by seccomp-notify). Two orthogonal layers, source in two separate files under openshell-sandbox/src/sandbox/linux/.

Q: Why is NVIDIA building this? A: NV’s agent workloads run on their own GPU fleets, and the credential/file boundaries of an agent fleet is a real ops problem. OpenShell 0.1.x pushes a stable release cadence plus formal policy-change review. The pitch is “draw the map for the agent cluster,” not “shell a single agent.”

Q: Can an ordinary developer just use it? A: Yes. On a single box, Docker gateway plus sandbox create demo is enough; K8s scenarios go through Helm. The precondition is that you are willing to write policy YAML: every new host the agent wants runs the “change request to prover to human approval” flow once.

Q: Does the z3 dependency slow down every deployment? A: Only gateways that need formal policy-change verification link z3. The default build without vendored/prebuilt links the system libz3; on a machine that has the system library installed, no difference at all.

Which Camp Are You In#

If you are building an agent product and need to manage credential boundaries, OpenShell is currently the only open-source piece that makes “a formal proof before a policy change” the default flow; it is worth pulling down and running the demo before you evaluate it. If you are just running a single local agent with no fleet concept, one container layer is enough and formal verification is overkill. If you are doing compliance audits, the OCSF structured security logs (four-level Severity) line up directly with SIEM input formats. Drop your own agent sandbox setup in the comments; once I have enough samples I will write a follow-up comparing “agent runtime security boundary approaches.”

Reproducible Commands (my box: 2-core EPYC / rustc 1.95 / Docker 29.7)#

# compile (z3 via vendored, avoid the missing system libz3; cmake via uv, no system install)
git clone --depth 1 https://github.com/NVIDIA/OpenShell
cd OpenShell
uv tool install cmake
export PATH="$HOME/.local/share/uv/tools/cmake/bin:$PATH"
cargo build --release -p openshell-cli
cargo build --release -p openshell-gateway --bin openshell-gateway --features vendored-z3

# pull the runtime images
docker pull ghcr.io/nvidia/openshell/sandbox:dev
docker pull ghcr.io/nvidia/openshell/supervisor:dev
docker pull nvcr.io/nvidia/base/ubuntu:24.04

# bring up the local mTLS gateway (certificate/JWT config hand-built off the e2e/with-docker-gateway.sh template in the repo)
./target/release/openshell-gateway generate-certs --output-dir state/pki
# ...state/gateway.toml (absolute paths; the gateway_jwt section uses an Ed25519 key pair)...
./target/release/openshell-gateway --config state/gateway.toml --bind-address 127.0.0.1 \
  --port 17670 --health-port 17671 --compute-driver docker \
  --tls-cert state/pki/server/tls.crt --tls-key state/pki/server/tls.key \
  --db-url "sqlite:state/gateway.db?mode=rwc" --tls-client-ca state/pki/ca.crt

# register the CLI + create a sandbox + run the escalation sequence
export XDG_CONFIG_HOME=$PWD/state/xdg
openshell gateway select local1023
openshell sandbox create --name demo
openshell sandbox get demo              # prints the default policy (/etc read-only, /tmp read-write)
openshell sandbox exec demo -- touch /etc/probe   # -> Permission denied

Two compile traps I hit: (1) the default features link dies on -lz3 (the prover depends on the SMT solver); this machine has no sudo to install libz3-dev, so I switched to the --features vendored-z3 build that source-compiles z3-sys. (2) source-compiling z3 needs cmake; uv tool install cmake drops it into ~/.local without touching the system. Once it runs, the gateway-side log shows the line gateway-minted sandbox JWT and launch-scoped authentication is through.
