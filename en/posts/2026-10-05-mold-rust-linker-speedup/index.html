Mold 3.0 Rewrote the Linker in Rust: I Reproduced the 'Corrupt Input Segfaults' Claim — and Found the Out-of-Bounds Read in the C++ Source

mold 3.0.0 — the first Rust build of the linker — reproduces the release notes' 'remains on par' (84ms vs 87ms on 1501 .o). But the safety claim I could actually reproduce: a crafted .o (e_shnum=0, e_shoff out of bounds) SIGSEGVs the C++ build 5/5, while the Rust build fatals cleanly. Traced to input-files.cc L95: the dereference runs before the bounds check.

October 5, 2026 · 6 min · 1189 words · Dreambeast -  |  中文

The HN thread on mold 3.0.0 runs on one reflex: “Rust rewrite, so it must be faster and safer.” I tested both claims on a 2-core EPYC. One is wrong, one is right — and for the right one I could trace the difference to the exact C++ source line where the out-of-bounds read happens. Speed: on par. 1501 .o files, 3-round median: Rust 84ms vs C++ 87ms — I reproduced the release notes’ own “Linking performance remains on par with 2.42.1.” Safety: real, and reproduced. Feeding a crafted e_shnum=0 + out-of-bounds e_shoff object to the C++ build gives rc=139 (SIGSEGV), 5/5 stable; the Rust build stops with a clean one-line fatal. The difference lives at input-files.cc:95 — C++ dereferences sh_begin->sh_size before its bounds check; the Rust build at input_files.rs:456 uses slice::get to make the OOB dereference not exist. That’s the release notes’ “guarantee moved from test coverage to the type system,” in a reproducible form, not a slogan.

The speed claim dies at the first link#

“Rust is faster” is the reflex every Rust-rewrite HN thread runs on. For mold the title invites it, because mold is famous as “9x faster than GNU ld” — so readers silently upgrade that to “the Rust rewrite made it even faster.” It didn’t.

The 1501-.o workload (1500 generated C files, gcc -O2, 18MB of objects), three rounds, median:

# mold 3.0.0 (Rust)
$ ./bench/mold3/mold-3.0.0-x86_64-linux/bin/mold data/objs/*.o -o out-m3 -e main
# 84ms median (rounds: 192 cold / 80 / 84)

# mold 2.42.1 (C++)
$ ./bench/mold2421/mold-2.42.1-x86_64-linux/bin/mold data/objs/*.o -o out-m2 -e main
# 87ms median (rounds: 83 / 87 / 87 — extremely stable)

# reference: GNU ld
$ /usr/bin/ld.bfd -static -o out-bfd data/objs/*.o -e main
# ~700ms hot (a cold round hit 3.1s on page-cache miss)

3.4% apart, C++ slightly ahead after the cold round. That’s the release notes’ “on par,” reproduced. The “9.8x” story is mold-versus-GNU-ld — true in 2.42.1, still true in 3.0; the Rust rewrite added nothing measurable to the hot path. The 3.0 build changes (oneTBB dropped, mimalloc 3.5.3 statically linked, Rust 1.95+ toolchain) eat any language-level gain in a single-threaded link; the net is “flat, quietly.”

The safety claim: I reproduced the segfault — and traced it to a line#

The release notes say:

The C++ version could read memory out of bounds on such input and crash with a segmentation fault. In mold 3.0, those reads are bounds-checked, so mold stops with a panic at the faulty access instead.

Two earlier malformed-object shapes I tried (tail-truncated; shstrndx off by a few sections) fataled identically clean on both builds — the OOB check on e_shoff fires early for those. The branch this claim describes is e_shnum == 0 (section count taken from section 0’s sh_size instead) combined with an out-of-bounds e_shoff.

C++ build, src/input-files.cc L89–L97 (v2.42.1 tag):

ElfShdr<E> *sh_begin = (ElfShdr<E> *)(mf->data + ehdr.e_shoff);   // L89: pointer computed, no bounds check
i64 num_sections = (ehdr.e_shnum == 0) ? sh_begin->sh_size : ehdr.e_shnum;  // L95: e_shnum==0 → dereference sh_begin->sh_size
if (mf->data + mf->size < (u8 *)(sh_begin + num_sections))        // L97: bounds check runs AFTER the dereference
  Fatal(ctx) << mf->name << ": e_shoff or e_shnum corrupted: "

The order is the whole bug: compute sh_begin (possibly past EOF) → if e_shnum == 0, dereference sh_begin->sh_size first → then run the bounds check. A crafted object with e_shoff pointing outside the file plus e_shnum = 0 walks into L95. Whether it actually faults depends on what’s mapped at that address — small offsets can read a neighboring page fine (virtual memory is contiguous); a 1GB offset hits the mapping edge and SIGSEGVs. “Crash or not” was a layout question; “check or not” is not — the check runs after the access.

Rust build, src/input_files.rs L449–L462 (v3.0.0 tag):

let shoff = ehdr.e_shoff.get() as usize;                       // L449
let shdr_size = size_of::<ElfShdr<E>>();
let first = data.get(shoff..shoff + shdr_size).map(record_from_bytes::<ElfShdr<E>>);  // L456: get() → None on OOB, never reads
let num_sections = match (ehdr.e_shnum.get(), first) {
    (0, Some(first)) => first.sh_size.get() as usize,         // L458: first is None → no OOB dereference possible
    (n, _) => n as usize,
};
let Some(shdr_bytes) = data.get(shoff..shoff + num_sections * shdr_size) else {       // L462: backstop fatal
    fatal!("{}: e_shoff or e_shnum corrupted: {} {num_sections}", ...)
};

One line of difference: C++ puts the dereference before the check; Rust’s slice::get makes the OOB dereference not exist as a possible value. It’s not “the Rust author remembered to write an if.” An out-of-bounds read cannot be written inside the type system — the guarantee moved from test coverage to the compiler, which is the release notes’ phrase, now in a reproducible form.

Reproduce it (copy-paste):

# 1) craft the object: take a normal main.o, set e_shoff=0x40000000 (1GB), e_shnum=0
python3 - <<'EOF'
import struct
d = bytearray(open("data/objs/main.o","rb").read())
struct.pack_into("<Q", d, 0x28, 0x40000000)   # e_shoff
struct.pack_into("<H", d, 0x38, 0)            # e_shnum = 0 → triggers the L95 dereference branch
open("/tmp/corrupt-oob.o","wb").write(bytes(d))
EOF

# 2) C++ build: SIGSEGV
$HOME/bench/mold2421/mold-2.42.1-x86_64-linux/bin/mold /tmp/corrupt-oob.o data/objs/main.o -o /dev/null -e main
# → exit 139 (SIGSEGV), no stderr, measured 5/5 stable

# 3) Rust build: clean fatal
$HOME/bench/mold3/mold-3.0.0-x86_64-linux/bin/mold /tmp/corrupt-oob.o data/objs/main.o -o /dev/null -e main
# → exit 1: "mold: fatal: /tmp/corrupt-oob.o: e_shoff or e_shnum corrupted: 1288 13"
buildexitbehavior
mold 2.42.1 (C++)139 = SIGSEGVno stderr, hard crash, 5/5 stable
mold 3.0.0 (Rust)1 = fatalone-line diagnostic, controlled stop

The practical surface: this risk class is “your build ever links a .o that isn’t compiler output” — corrupted CI caches, truncated tarballs, third-party prebuilt objects. 3.0 turns that from a crash of the link step into a one-line error you can grep.

What 3.0 is actually selling#

Speed was never the pitch; the release notes say so plainly. The strategic line: 3.x targets the remaining GNU-ld compatibility gaps (linker scripts above all) to “pave the way for mold to be adopted as the default linker in Linux distributions.” mold has been stuck at “fast, but linker-script compatibility lags” for years; pinning the default-distro-linker slot is what turns its existing 9.8x over GNU ld from an opt-in for enthusiasts into the default for everyone.

Boundaries, stated#

  • The SIGSEGV is reproducible but degree-dependent: a 1GB offset faults 5/5 on this box; small offsets can read a neighboring mapped page without faulting — the point is check-after-dereference in C++ vs no-dereference-possible in Rust, not “C++ always crashes, Rust never does”
  • Speed comparison is static-link against ld.bfd -static (dynamic-link flags mismatched my distro); both mold builds emit byte-identical 10.14MB outputs, so the two mold versions are directly comparable
  • 2-core EPYC slice, non-exclusive: 3-round medians with the cold round (page-cache miss) reported separately

Forward this to the colleague asking “the Rust linker — faster and safer then?” Faster was already true in 2.x (mold vs GNU ld, 9.8x). Safer is the new part, and it’s the worst-case one: I found the exact C++ line that does the out-of-bounds read (input-files.cc:95) and the Rust rewrite’s answer to it (input_files.rs:456). Follow “Dreambeast” — last piece I measured the Headstart “up to 2x” claim on this same box; this piece splits “Rust rewrite” into speed (flat) and safety (reproducible segfault→fatal), and only one of the two was real.

Frequently Asked Questions

Is mold 3.0 faster than 2.42.1?

No. 1501-.o link, 3-round median: 84ms (Rust) vs 87ms (C++), a 3.4% gap inside noise. The release notes say 'remains on par' — reproduced locally.

So what did the Rust rewrite actually buy?

Worst-case behavior on malformed input: a crafted .o (e_shnum=0, e_shoff out of bounds) SIGSEGVs the C++ build 5/5; the Rust build stops with a one-line fatal. Traced to C++ input-files.cc L95, where the section-header pointer is dereferenced before the bounds check.

Should I switch to 3.0 now?

Drop-in CLI-compatible release. If your build ever links third-party / corrupt / truncated .o files (CI caches, tarballs), the crash-vs-fatal difference is worth it; otherwise 2.42.1 is fine.
