Mold 3.0: The Linker Rewritten in Rust — I Measured It, Speed Is Unchanged

mold 3.0.0 rewrote the C++ linker in Rust. The official release notes say 'Linking performance remains on par with 2.42.1' — I reproduced that on a 2-core EPYC: 84ms vs 87ms across 1501 .o files. The value is type-system memory safety and a path to becoming the default distro linker, not speed.

October 5, 2026 · 6 min · 1090 words · Dreambeast -  |  中文

On October 5, rui314 released mold 3.0.0 — the first official Rust build of the high-speed linker. The HN post title is “Mold 3.0: Linker Rewritten in Rust”, and the first reflex in the comments was: “It must be faster in Rust, right?” Short answer: no. On my 2-core EPYC, linking 1501 .o files (18MB of load), 3-round median: mold 3.0.0 (Rust) 84ms, mold 2.42.1 (C++) 87ms — a 3.4% gap, inside noise. The official release notes literally say: “Linking performance remains on par with 2.42.1.” I reproduced that claim locally. You rewrite the language and swap the entire build system, and the speed doesn’t move a millimeter. That’s not a failure — it’s the first step to understanding what Rust actually bought in the linker scenario.

This article covers three things: ① the Rust rewrite is not faster — “on par” proven locally with 1501 .o; ② what the value actually is — memory safety promoted from test coverage to type-system guarantees, dependency slimming, and a path to becoming the default distro linker; ③ local 2-core EPYC numbers plus three stated boundaries. Machine: AMD EPYC 9354P 2-core slice, mold 3.0.0 (Rust) / 2.42.1 (C++) / system ld.bfd, measured 2026-10-05, every number reproducible with the commands shown.

The release notes already said “same speed” — I verified it locally#

The mold 3.0.0 release notes say on the first screen: “Linking performance remains on par with 2.42.1.” I reproduced that claim locally:

# Same 1501 .o files (gcc -O2, 18MB of load), 3-round median
$ mold3/mold-3.0.0-x86_64-linux/bin/mold data/objs/*.o -o out -e main
#   84ms  (Rust)
$ mold2421/mold-2.42.1-x86_64-linux/bin/mold data/objs/*.o -o out -e main
#   87ms  (C++)
$ /usr/bin/ld.bfd -static -o out data/objs/*.o -e main
#   824ms (GNU ld, 9.8x slower)

A 3.4% gap, inside the noise. I can’t fault the official “on par” wording — it held up on my box.

So what is the actual value#

mold 3.0 moved three things; speed is the least interesting of them:

1. Memory-safety guarantees move from “test coverage” to “the type system”

On malformed input, the official release notes say: “The C++ version could read memory out of bounds on such input and crash with a segmentation fault. In mold 3.0, those reads are bounds-checked, so mold stops with a panic at the faulty access instead.”

I ran two corrupted-input experiments (tail-truncated by 512B / shstrndx off by 3 sections), and both versions behaved identically — clean fatal errors, no C++ crash vs Rust panic difference reproduced:

$ mold3 data/objs/... -o out -e main   # feed a tail-truncated .o
mold: fatal: corrupt-trunc.o: e_shoff or e_shnum corrupted: 10704 14
$ mold2421 data/objs/... -o out -e main
mold: fatal: corrupt-trunc.o: e_shoff or e_shnum corrupted: 10704 14

Honest note: I could not reproduce the segfault scenario the release describes. That doesn’t change the judgment — the Rust build’s guarantee is language-level (an OOB read simply cannot exist in the type system), not “I added an if-check.” The C++ version’s safety rests on test-case coverage; the Rust version’s rests on the compiler. One is “known holes are patched”; the other is “this class of hole cannot be written.”

2. The engineering surface sheds a pile of dependencies

Build system CMake → Cargo (one cargo build --release, needs Rust 1.95+); drops the oneTBB runtime dependency; mimalloc 3.5.3 now statically linked; test suite ctest → cargo test. A burden off the maintainers, zero impact on users.

3. The real strategy: a path into distros

The most title-bait-able line in the release notes: “The goal of mold 3.x is to close the remaining compatibility gaps with GNU ld, particularly in linker script support, and to pave the way for mold to be adopted as the default linker in Linux distributions.”

mold has always been stuck at “fast, but linker-script compatibility lags.” 3.0 pins the target at “default linker” — only once it ships as the distro default does the 9.8x link speedup (local ld.bfd median 824ms vs mold 84ms) reach every C developer by default.

Boundaries, stated#

  • Single-threaded link on a 2-core EPYC slice; the official numbers cover multi-core scenarios; the 9.8x is a static ld.bfd comparison, dynamic-linking gaps differ
  • The corrupt-input experiments did not reproduce the C++ segfault the release describes — both crafted malformed .o files are cleanly rejected by both versions; “segfault→panic” is a language-level guarantee, not an observable behavior difference; stated as such in the text
  • 3.0 is a drop-in replacement: identical CLI options, target architectures, and output as 2.42.1 (officially verified across every target’s test suite plus a full Gentoo build), zero migration cost

FAQ#

  • Is mold 3.0 faster than 2.42.1? No. Median 84ms vs 87ms on 1501 .o links, flat. The release notes say “remains on par” — reproduced locally.
  • So what’s the point of the Rust rewrite? Not speed — three things: memory safety moved from test coverage to the type system, dependency slimming (no oneTBB/CMake), and a path to becoming the default Linux distro linker.
  • Should regular users upgrade now? No rush. 3.0 is a drop-in replacement with identical CLI compatibility; if you don’t care about the GNU ld compatibility gaps or the distro-default story, 2.42.1 is fine.
  • Who benefits from the 9.8x over ld.bfd? Anyone on the default system linker (bfd) building lots of C/C++: switching to mold is a zero-cost speedup. Rust projects already default to mold or lld, so this mainly targets C/C++ toolchains.
  • Where does “the Rust rewrite is faster” come from? HN title bait plus the generic “Rust is fast” mental model. The release notes say “remains on par” on the first screen — reading the source saves you the misread.

Forward this to the colleague still waiting 824ms on GNU ld, who assumed “a Rust linker must be faster.” Follow “Dreambeast” — in the Headstart piece I measured the “up to 2x” claim on this same 2-core box; this piece measures the generic “Rust is faster” reflex the same way. The verdict both times: the release notes’ first screen already said it — reading the source beats reading the HN title.
