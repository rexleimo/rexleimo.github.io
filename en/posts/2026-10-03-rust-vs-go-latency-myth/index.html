Rust vs Go Microservices: The "3x Faster" Latency Claim Is Fake

The tech-tribal lore says rewriting a service in Rust makes it "3x faster." So I wrote the same CRUD microservice in Rust (axum) and Go (stdlib net/http), pinned both to one two-core box, and hammered it across six benchmark groups. No latency tier is anywhere near 3x; at mid concurrency Go's p99 is actually lower; the place Rust really pulls 2-3x ahead is memory. All numbers, code, and the bench harness are open for you to reproduce.

October 3, 2026 · 6 min · 1085 words · Dreambeast Programming -  |  中文

There is a piece of tech-tribal lore that keeps resurfacing: “Rewrite the service in Rust and it gets 3x faster.” I have heard it enough times that it started to itch - 3x faster, but faster at what? Latency? Throughput? Memory?

I did not want to argue from vibes. So I took one CRUD microservice, wrote it twice - Rust with axum, Go with stdlib net/http - and pinned both to the same two-core box under the same load, then hammered them and recorded latency, throughput, and memory. Everything is open source at the end: data, code, bench script. Reproduce it, or don’t believe it.

The spoiler, so you can read with a map in hand:

  • Latency (p99) never comes anywhere near 3x, at no concurrency tier - the largest relative gap is under 20%, and the lead changes hands.
  • At mid concurrency (100), Go’s p99 is actually lower than Rust’s (23.2ms vs 26.0ms).
  • Rust’s real, measurable edge is memory: steady-state RSS runs about 1/2 to 1/3 of Go’s.
  • Both services collapse under the heaviest tier (p99 climbs from 0.4ms into the hundreds of ms); the bottleneck is locks and scheduling, not the language itself.

Method: keeping the two sides honest#

One two-core / 7.8GB Linux box. Two services with line-for-line equivalent logic:

Rust buildGo build
Frameworkaxum 0.8 + tokio + serdestdlib net/http
Optimizationrelease: opt-level=3, lto=truego1.27.1, GOMAXPROCS=2 GOGC=100
EndpointGET /api/items/item-0 (reads an in-memory map)same

The load is a pure GET read path: each service seeds 1000 records into an in-memory map on startup, and the bench hammers one of them. I chose GET on purpose to isolate the language/framework layer - no database, no write contention (POST would sharpen the read-write lock fight and favor Go, muddying the conclusion; I call that out below).

One wrinkle in the harness: this box has GitHub walled off, so the usual load tools would not install. Rather than fight it, I wrote a tiny load generator in pure Go stdlib (concurrent workers + percentile stats). It pins itself to GOMAXPROCS=1 so it holds one core and leaves both services an even break. The generator ships too.

For each concurrency tier (c = 10 / 100 / 500) I ran a 2000-request warmup, then n = c x 100 requests, capturing p50/p90/p99, throughput, and error rate, plus a steady-state VmRSS sample.

Why “3x” does not survive contact with the tables#

Put the three tables side by side and “Rust is 3x faster” has no number to lean on:

  1. Latency is nowhere near 3x. The p99 gap at matched concurrency stays under 20% across the board, and the lead flips hands - c=10 Rust ahead, c=100 Go ahead, c=500 Rust ahead again. That is not “a stable 3x lead”; that is the same order of magnitude with noise on top.
  2. Go beating Rust at mid concurrency (23.2 vs 26.0ms) is not an accident. The Rust build uses an RwLock - many readers, and one writer closes the gate on everyone. Under a pure read load it should win, and yet at c=100 Rust’s throughput (18833) is lower than its c=10 number (23226): the read lock itself became the bottleneck. Go’s RWMutex behaves more smoothly here. Whether a language is “fast” depends on which lock you reach for and how you schedule - not on the name of the language.
  3. Both services collapse at c=500, and that is the point. Throughput falls from ~20k req/s at c=10 to ~5k at c=500 (a 4x drop), and p99 climbs from 0.4ms into the 100-180ms range. Rust and Go fall together, which says the bottleneck lives in the shared read-write lock plus two-core scheduling - not in the language choice.

In one line: on the read path, axum and net/http are the same order of magnitude; crediting “3x faster” to Rust is quietly counting noise in that band as a lead.

Where Rust actually pulls the gap: memory#

Latency does not produce a 3x figure, but memory does - at low concurrency steady state, Rust 4.4MB vs Go 13.4MB is right about 3x; the gap narrows as concurrency rises (locks and transient objects take over), yet Rust stays at 1/2 to 1/3 of Go throughout.

This is the Rust selling point that should actually be remembered for microservices: you pack more replicas per unit of memory. Same budget, Rust runs denser than Go - and that bites hardest in cloud-edge / IoT / high-concurrency, low-memory deployments. And that 3x number is a memory number, not a latency one - the “3x” in the headline belongs on the memory ledger.

When to pick Rust, when Go is enough#

  • Pick Rust when memory is the constraint (dense deploys, cloud-edge, embedded services), when you need deterministic latency on write-heavy traffic, or when the team is already on the Rust stack. A 2-3x memory edge is real money.
  • Go is enough for run-of-the-mill CRUD / gateway / back-office services, where team familiarity, ecosystem, and hiring cost are the binding constraints - and on the read path Go is faster than your priors assume (this very article’s c=100 tier is a Go win). Reaching for Rust to chase a mythical “3x” is a bad trade.

The pick should track your bottleneck: memory-bound, go Rust; team-velocity-bound, Go is steadier.

Honest caveats (read these)#

  • Not tested: databases, GC tuning, startup time, or the write path (POST contention).
  • This is a two-core box; absolute numbers do not transfer to production multi-core boxes. The claims in this post are about ratios, not absolute values.
  • Pure GET read path, no write pressure.
  • The full reproduction kit - both service sources, the generator, the bench script, all raw logs, this number list - lives in the repo under bench/. Run it and try to make me look wrong.

Reproduction path: repo bench/ (svc-rust, svc-go, bench-cli, run-bench.sh, results/numbers.md). Both services are database-free, in-memory maps; the load generator is pinned to GOMAXPROCS=1 on one core while the service under test runs GOMAXPROCS=2.

Frequently Asked Questions

Is Rust really not 3x faster than Go?

On my two-core box, on a pure GET read path, the p99 gap is under 20% at every concurrency tier, and the winner flips: at concurrency 100, Go's p99 (23.2ms) is actually lower than Rust's (26.0ms). No latency number backs the "3x" claim.

Then where does Rust win?

Memory. Steady-state VmRSS is 4.4MB for Rust vs 13.4MB for Go at low concurrency - right about 3x; across the board Rust runs at 1/2 to 1/3 of Go. The same budget packs more Rust replicas, which matters most for cloud-edge, high-density, memory-tight deployments.

Why do both collapse at high concurrency?

At concurrency 500 both services' p99 jumps from a 0.4ms baseline to 100-180ms and throughput drops ~4x, Rust and Go together. The bottleneck is the shared read-write lock plus scheduling on a two-core box, not the language choice.

Can I reproduce these numbers?

Yes. Both service sources (svc-rust, svc-go), the custom load generator (bench-cli, pure Go stdlib, written because GitHub is walled off here and hey could not be installed), the bench script (run-bench.sh), and the full raw logs are open in the repo under bench/.
