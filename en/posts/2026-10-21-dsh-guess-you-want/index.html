dsh's Composer Started Guessing What You'll Say: 512 Tokens Buys Your Opening Move

DeepSeek Harness's community plugins give the dsh composer a 'guess what you'll say' layer: after each agent turn, ghost text drafts your next prompt and Tab adopts it. Bounded 512-token LLM calls plus local zsh-style prefix completion, with redaction and no core changes.

October 20, 2026 · 9 min · 1753 words · Dreambeast -  |  中文

Claude Code, Codex, Cursor: the agents you feed instructions to all have one thing in common. Their composers are dumb. You type, they wait, they don’t guess. The community around DeepSeek Harness (dsh) has pried that open. After each AI turn, gray ghost text appears in the composer with what you’re about to say next; Tab drops it into the draft. The feature is called “guess what you’ll say,” and every bit of it is community web plugins. Not one line of official code was touched.

Three things to say about it. First, what it is and how it works: one bounded auxiliary LLM call plus a local history-completion layer, with the bill starting at 512 tokens. Second, why it matters: it exposes where agent harnesses are heading, full ownership of the human-machine dialogue, and the composer was the last unclaimed interface. Third, why this happened on dsh instead of elsewhere: everything-is-a-plugin architecture lets third parties rebuild the input layer in pure DOM overlays while the core just supplies hooks.

What it looks like#

dsh-suggest-prompt works like this. Each agent turn ends in completed, and the plugin hangs one auxiliary LLM call off the turn/end event. It takes the last user turn and the assistant’s final answer, tags them, and the model follows a system prompt that says “predict the next prompt in the user’s voice.” The web side renders the result as a light-colored ghost placeholder in the composer; Tab (recordable to any key) fills the draft. Reply language follows the session: CJK in the last user message means Simplified Chinese, otherwise English.

Unadopted is not wasted. Delete back to an empty draft and the persisted suggestion reappears without a new request; type anything and the ghost text steps aside immediately; the whole interception stays silent during IME composition. Empty model replies, meta-text, evaluative filler, assistant-voice phrasing: silently skipped, no error, no event written.

dsh-prompt-history does the fuller job on the same requirements: up/down history with bash history-search-backward semantics (prefix search, pending-line restore), Ctrl+R reverse search, a copy/quote/side-chat toolbar above selections, right-click paste, and a second parallel agent thread in the right pane. 12KB client bundle, entirely browser-local, pure UI behavior with zero session events.

The cost ledger: what 512 tokens buys#

Broken down, this is the most interesting part of the whole thing.

No thinking by default. The auxiliary call carries reasoningEffort: off (serialized as thinking: disabled on DeepSeek) so a single predicted sentence doesn’t burn inference budget; models that reject the field are retried once without it, and the rejection happens before any network I/O, so it costs almost nothing.

Last turn only. maxRecentTurns defaults to 1; intermediate tool calls and reasoning never reach the suggestion model. The transcript has a maxTranscriptChars budget, the suggestion has a visible-character cap, and the whole call has three gates: bytes, tokens, timeout.

No charge to the main request. The main agent’s token bill is untouched. Prediction is at most one parallel auxiliary call per turn, and cache hits on the same context skip the request entirely.

My judgment: those 512 tokens don’t buy “typing for you.” They buy driving the cost of deciding what to ask down to near zero. The most expensive part of an agent workflow is never tokens, it’s intent switching. The AI just finished a refactor, and you have to remember “oh, run the tests” — that opening move costs a hundred times more than the keystrokes. Ghost text remembers it for you, Tab once, and the intent lands.

The local half: it guesses offline#

Don’t equate “guess what you’ll say” with “a model call every turn.” dsh-suggest-ghost is two-track: when the draft is empty, LLM whole-sentence prediction; the moment you start typing, it switches to zsh-autosuggestions-style prefix completion, purely local, ranked by conversation history — recency first, in-session frequency second, cross-session heat third, matching case-insensitively and ignoring whitespace and fullwidth/halfwidth punctuation differences.

That’s zsh’s gray completion, ported into an agent composer. You had “fix that 500” in your prompt history; this time you type “fix that” and the gray part completes it. History source is the session’s own message records (user/steering nodes), it survives reloads, cross-session memory is off by default (200-entry browser-local cap when on).

The value of two-track shows up in the cost curve: high-frequency repeat scenarios (“run the tests”) hit local history at zero tokens; genuinely new intent falls to LLM prediction. That’s the right design. One easily missed layer: the prefix-completion ranking is “recency > in-session frequency > cross-session heat,” which is the mathematical expression of usage habit. A phrase you hammered last week outranks a one-off from three days ago — closer to reality than raw total-count sorting.

Why a plugin, not an official feature#

dsh’s own composer is a Lexical contenteditable host. Official provides the conversation.input.overlay slot and the inputActions.setDraft API, but no prediction logic. The plugin does everything in DOM overlays without touching the core.

This isn’t a dsh-specific compromise, it’s its architectural stance: everything is a plugin. The official hooks land at exactly the right granularity — turn/end, input.overlay, appendPluginRecord — enough for a third party to take the whole input layer and rebuild it while the agent core stays untouched. dsh-suggest-prompt writes its log entries as ignorable plugin records (plugin:suggest-prompt/suggested); readers who don’t know the type retain and skip it, and the session always cold-reads. On older harness versions lacking the record API, the plugin stays fully dormant — it would rather be empty than write private event types, because a private event written into the log makes the whole session unreadable on cold read.

That detail says more than the feature: community plugin discipline is already high enough to respect session-format compatibility constraints.

The TypeScript argument: ecosystem beat performance#

Since the 08-13 open-source drop, the most common HN complaint is “why TypeScript.” Roughly 219 packages, 450k lines of TS, pnpm monorepo — conspicuous in an agent harness crowd that cares about speed.

The official community’s answer, which I think holds: this isn’t a runtime choice, it’s a distribution choice. dsh’s whole thesis is “everything is a plugin,” so plugins must install easily, resolve dependencies, and ship instantly. npm has no rival on “install a random package at runtime” — Rust has crates.io, Go has modules, Python has PyPI, but none of them combine JS’s zero-config publishing, existing ecosystem, and hot-install habit. The 101-plugin field test makes the point: 11 install cleanly from npm, 81 exist as bare GitHub repos (dsh plugin add github:owner/repo just works), 4 need extra runtimes, 3 won’t install. The reason the 81/10 bare-GitHub share works at all is that dsh add is a thin wrapper over Node’s install machinery — you can’t reproduce that in Rust or Go without first building an npm equivalent.

The performance counterargument ignores where the time actually goes: in an agent harness, the dominant cost is the model round trip across the network. Deciding the next step happens inside the model, not in the Node process. Node’s slow parts (cold start, JSON parsing, string handling) are noise against second-scale model round trips. Picking Rust speeds up the 1% while adding friction to the 99% of plugin distribution — the wrong trade for a framework betting on community ecosystem.

I agree with that judgment. One caveat: with 81 bare GitHub repos, the quality floor is whatever the community holds. Plugin breakage shows up as ERR_PNPM_FETCH_404 or CJS/ESM mismatches; the official troubleshooting guide covers both, but users still carry their own share of the dirty work.

Four-line summary#

Scenario Approach Cost Verdict
Repeated prompts Local prefix completion (zsh-autosuggestions port) 0 tokens Workhorse for high-frequency scenarios, correct
New intent One LLM whole-sentence prediction per turn, 512-token budget ≤1 call/turn Buys intent-switching cost, worth it
Credential safety Transcript redacted before send, last turn only — LLM off = zero network, clear boundary
Adoption Tab fills draft, Enter sends — Non-intrusive, Esc discards

FAQ#

Official dsh feature? No — community web plugins (the suggest-ghost / prompt-history / suggest-prompt / input-assist family). Official provides plugin mount points, turn/end hooks, and the composer overlay API; it wrote none of the logic.

Will prediction leak my API key? Per suggest-prompt’s implementation, the transcript is credential-redacted before send, and only the last user turn plus the assistant’s final answer is sent, with tool-call intermediates excluded. For zero network, switch off the LLM suggestion in plugin settings and keep local prefix completion only.

Versus Claude Code’s completion? Same direction (gray text + Tab to adopt is deliberately matching Claude Code’s behavior), but where Claude Code ships it built-in, this version is a plugin layer. Difference is in installation: one dsh plugin add line, no waiting on the official roadmap or release cadence — at the cost of a quality floor that community self-discipline has to hold.

Won’t install? Prerequisite is dsh ≥ 0.2.0-rc.2 (0.2.0 changed the session projection and web client module contracts; older versions stay dormant by design). Install with dsh plugin --profile web add dsh-suggest-ghost, restart dsh web, Ctrl+Shift+R to hard-refresh the page; it works with no configuration.

Worth moving to dsh just for this? If you already run dsh workflows, it’s one plugin install, free. If you don’t, migrating just for input prediction is not worth it — it solves efficiency in high-frequency agent dialogue, not a general-purpose tool need.

The close#

The composer is the last interface of agent tooling. The model writes code, runs tests, connects to MCP — the only thing still left purely to humans is “what are you going to say next.” The dsh community plugged that gap with a batch of 12KB web plugins without touching a line of official core: the hooks were fine-grained enough that a third party could rebuild the entire input experience.

A 512-token budget buying intent that can’t evaporate: I’d call that a fair deal.

Frequently Asked Questions

Is this an official dsh feature?

No. dsh itself (deepseek-ai/deepseek-harness) ships no input prediction. Everything comes from community web plugins: dsh-suggest-ghost, dsh-prompt-history, dsh-suggest-prompt, dsh-input-assist. The official side provides the plugin mount points and turn/end event hooks.

Does the prediction call see my credentials?

Per dsh-suggest-prompt's implementation, the transcript is credential-redacted before send; by default only the last user turn and the assistant's final answer are sent, no intermediate tool calls. Budget is around 512 tokens.

Does it work without an LLM?

Yes. Prefix completion is purely local history (zsh-autosuggestions style: recency > in-session frequency > cross-session heat), zero network requests. The LLM half is the whole-sentence next-prompt prediction, and it has its own off switch in plugin settings.

Does Tab-accept send the suggestion?

No. Adoption only fills the composer draft; it stays editable and Esc discards it. Enter is what actually sends the message.

Why is dsh built in TypeScript?

The bet is on plugin distribution, not runtime performance: npm's zero-config publishing plus dependency resolution. The 101-plugin field test: 11 install straight from npm, 81 as bare GitHub repos, 4 need extra runtimes, 3 won't install. The agent's dominant cost is the model round trip, not the harness language.
