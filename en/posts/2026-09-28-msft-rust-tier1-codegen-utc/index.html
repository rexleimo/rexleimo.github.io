Microsoft Makes Rust a Tier-1 Language: 100+ Repos Sharing One Compiler Backend — But It's Closed Source

On September 10, a guest post on the Rust Foundation site made it official: Rust now holds Tier-1 language status inside Microsoft, alongside C++, C#, and TypeScript. The real substance is rustc_codegen_utc — wiring rustc directly into MSVC's UTC code generator so Rust and C++ share one optimizer. I checked the most-repeated claims against the sources; three of them don't hold: no wholesale Rust replacement, no first-party Visual Studio tooling, and the backend is closed source with no open-source plan.

September 28, 2026 · 6 min · 1247 words · Mengshou Coding -  |  中文

The bottom line first#

On September 10, the Rust Foundation site published a guest post by Victor Ciura, Principal Engineer on Microsoft’s Rust tooling team. One sentence is the actual news: Rust now holds Tier-1 language status inside Microsoft, on par with C++, C#, and TypeScript. The RustConf 2026 keynote in Montréal announced it on stage; HN front page ran it for a day.

But the article is being retold badly. I checked the official post, The Register’s coverage, and the HN thread. The three most-repeated claims all fail. This piece fixes those and explains the one genuinely interesting engineering artifact — rustc_codegen_utc. Three conclusions up front:

  1. “Microsoft is replacing C/C++ with Rust” is a misreading. The post itself draws the line: C++ still dominates after decades; the shared backend exists so “many systems will use both languages for years to come.”
  2. The engineering substance is the UTC backend: rustc wired directly into MSVC’s UTC code generator, so Rust and C++ finally share one optimizer. 100+ Microsoft repositories already build with it.
  3. It is closed source, and Microsoft has no plan to open-source it. That’s the most-omitted sentence in the story.

What Tier-1 actually buys#

Tier-1 is an internal engineering commitment, not a marketing badge. The post lists five things:

Tier-1 itemWhat it lands as
Secure toolchain buildsrustc/std/tools through supply-chain-hardened builds
Developer toolingTooling at the C++/C# quality bar
Quality workflowsAligned with existing release pipelines
Deep platform integrationWindows platform capabilities open to Rust directly
SDL complianceMicrosoft’s mandatory security development lifecycle, Rust projects enter unchanged

The context numbers: Azure CTO Mark Russinovich at RustConf 2025 put it at ~70% of Windows CVEs are memory-safety issues — his point being that no amount of C/C++ hardening reaches what Rust guarantees by construction. Microsoft has invested “millions of dollars” in the Rust project, and win32kbase_rs.sys, a Rust component, already ships in the Windows kernel — a bug found there crashes the system instead of opening a privilege-escalation hole. Tier-1 formalizes that track record.

rustc_codegen_utc: a fourth backend, same family#

The technical value of this story is all in rustc_codegen_utc. It’s a fourth codegen backend for rustc, in the same architectural family as rustc_codegen_llvm, rustc_codegen_gcc, and rustc_codegen_cranelift, plugging into the same backend interface — except it connects rustc’s shared compiler machinery to UTC, the code generator inside MSVC.

The analogy: previously, Rust on Windows went rustc → LLVM → object file, then entered the MSVC world as an outsider — ABI-compatible, but invisible to the whole-program machinery MSVC accumulated over decades. The UTC backend welds rustc into MSVC’s own pipeline; Rust and C++ object files meet the same optimizer.

The post’s inheritance list:

  • High compatibility with the Windows tooling ecosystem and ABI
  • Binary hardening and code-security features
  • Post-link compliance, analysis, and servicing (including Hotpatch)
  • Seamless Rust/C++ interop for hybrid projects
  • Cross-language inlining, optimization, and SPGO (sample-profile-guided optimization)
  • Debugging and crash-dump analysis
  • Profiling, diagnostics, and coverage

Cross-language inlining is the most concrete one: in a hybrid project, Rust functions and C++ callers finally sit under one optimizer for inlining, PGO, and whole-program decisions — previously two optimizers made two sets of assumptions.

Three timeline points: production-ready since early 2026, self-hosting since Rust 1.90 (the backend compiles itself with the toolchain it targets), 100+ Microsoft repositories building with it today, with more adopting weekly.

Three repeated claims, checked one by one#

This is the body of the piece. Each claim is retold a lot; I checked each against its source:

Claim 1: “Microsoft is replacing all of C/C++ with Rust.” Fails. The post itself: C++ “still dominates after decades of development,” and the shared backend exists precisely so both languages participate equally for years. The 2030 goal of eliminating C/C++ (Galen Hunt) is about memory-safety risk reduction via mixed-language migration, not a wholesale rewrite.

Claim 2: “Tier-1 means first-party Rust tooling in Visual Studio.” Fails. HN commenters pointed this out on the spot and The Register confirms it: this is an internal engineering tier; Visual Studio ships no first-party Rust tooling. The main route, for Microsoft’s own developers included, remains VS Code plus the community-built rust-analyzer. Tier-1 buys toolchain builds, quality pipelines, and platform integration — not the IDE experience.

Claim 3: “The UTC backend is open source; Rust just gained a public backend.” Fails, and this is the most important one. It’s closed source, and the Rust Project maintainers’ relayed position is that Microsoft has no open-source plan. For a community accustomed to inspecting and hacking its own toolchain, that’s a real friction point.

Honest notes#

Three boundaries, stated plainly:

  1. I have seen zero lines of the UTC backend — it’s closed source, so every item on the inheritance list is a re-statement of Microsoft’s official position, not verified by me.
  2. No performance numbers exist for cross-language inlining / SPGO. Microsoft, The Register, and the HN thread all omit them. “One optimizer” is an architectural fact; the benefit is inference.
  3. The 70% CVE statistic is old — it dates to MSRC’s 2019 analysis and hasn’t moved in a decade. It measures the problem’s magnitude; it does not predict CVEs dropping 70% after Rust adoption.

FAQ#

Q: My project mixes Rust and C++. What does this backend do for me?

Directly: nothing — it’s internal and closed. Indirectly: a second production-grade backend exposes places where rustc has quietly assumed LLVM’s behavior under real Windows workloads; those fixes land upstream. Rust has had exactly one production code generator (LLVM) for its whole life — this is a rare source of pressure. If you ship Windows libraries, watch the mixed-language compatibility fixes.

Q: Why build this instead of just using Clang/LLVM?

On non-Windows platforms, a hybrid project can already share the LLVM backend (compile the C++ with Clang). On Windows, MSVC is the native platform compiler, and decades of platform capability live inside it; the LLVM path leaves Rust at the platform boundary. The UTC backend is the Windows-native equivalent of the shared-backend trick.

Q: Will “Tier-1” become a template other vendors copy?

It’s Microsoft’s internal tier today, with no cross-vendor standard component. But the “70% of CVEs are memory issues” argument, plus Rust already in the Windows kernel, is a public narrative OS vendors can stand on. Whether others follow depends on their own CVE bills, not on this post.

Which side are you on#

Pick a lane in the comments:

  • Upstream-waiters: UTC is closed; wait for the compatibility fixes to flow into rustc, stay on LLVM;
  • Windows mixed-language shops: Rust/C++ dual-language projects, cross-language inlining is the thing you care about most — this is your lane;
  • Security-narrative people: 70% of CVEs are memory issues, Rust in the kernel is the direction, Tier-1 just signed it.

Post your project’s Rust share and target platform; if I get enough, I’ll write a follow-up: rustc_codegen_utc’s interface design compared layer by layer against the Cranelift and GCC backends — doable from the public backend interface alone, no UTC source required.

Forward this to the colleague who still complains that “Rust tooling is second-best on Windows” — Microsoft already did the backend work; the gap they’re complaining about is being filled by a 100+ repo pipeline.

Frequently Asked Questions

What does Tier-1 actually mean? Is it an industry standard?

No. It's Microsoft's internal engineering tier, not any industry standard. Tier-1 means internal Rust teams get a paved path from laptop to production: secure toolchain builds, developer tooling, quality workflows, deep platform integration, and SDL compliance. Same tier as C++, C#, and TypeScript.

Can I use rustc_codegen_utc?

Not yet. It's an internal DevDiv backend, self-hosting since Rust 1.90, used by 100+ Microsoft repos, with no public release and no upstreaming plan. Your main value from it: the compatibility issues a second production-grade backend exposes get fixed upstream.

Will the UTC backend be open-sourced?

Not currently. Rust Project maintainers relayed on Zulip that Microsoft has no plans to open-source it. It belongs to the same architectural family as rustc_codegen_llvm/gcc/cranelift, but its source isn't public — that's the community's biggest friction point right now.

What's the advantage over the LLVM backend?

Not codegen quality — it's platform capability inheritance: Windows ABI conventions, binary hardening, Hotpatch, crash-dump analysis, SPGO (sample-profile-guided optimization), cross-language inlining. A Rust object file from the LLVM backend is ABI-compatible but doesn't participate in MSVC's decades of whole-program machinery.
