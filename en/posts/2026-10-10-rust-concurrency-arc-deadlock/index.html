Rust Has No GC — Concurrency Still Breaks: 100 Threads Fighting Over One Counter Lose 51%~81% of Updates (Measured)

“No GC, therefore safe concurrency” is a misconception. Rust pushes data races to compile time and leaves deadlocks and logic bugs at runtime. 100 threads × 100k increments on one shared counter: 51%~81% of updates lost in 5 rounds on -O0; 0 lost under -O — under UB, correctness is luck. All examples reproducible: double-lock deadlock, RefCell/Mutex/Atomic postures, Rc vs Arc.

October 10, 2026 · 7 min · 1345 words · Dreambeast Coding -  |  中文

“No GC” gets blamed for concurrency bugs — the real enemy is data races#

GC decides when objects die. Concurrency programs usually break before that: what you read when two threads write the same memory at once — data races. Rust’s answer is explicit: no GC; push data races to compile time (the Send/Sync checks reject what they can’t prove safe), leave deadlocks and logic bugs to runtime.

Every example in this piece ran on one box: AMD EPYC 9354P (2 vCPU), 7GB RAM, rustc 1.99.0. Each example ships with its repro command; every number in the text comes from real output. Three layers, three examples:

  • Stopped at compile time: Rc across threads (example 3a, the E0277 error verbatim)
  • Explodes only at runtime: double-lock deadlock (example 1, 2s timeout verdict), RefCell second-mutable-borrow panic (3b-A)
  • Nothing stops it: an UnsafeCell + raw pointer builds an unsynchronized shared counter (example 2, the main course)

Example 1: double-lock deadlock — a 2-second timeout verdict#

The classic shape: thread A takes lock a then lock b; thread B (here, the main thread) takes lock b then lock a. Each holds one and waits on the other, forever.

Verdict mechanism: the worker sends a signal over an mpsc channel when it finishes; the main thread recv_timeout(2s). No signal within 2s = deadlock established.

let a = Arc::new(Mutex::new(1_u64));
let b = Arc::new(Mutex::new(2_u64));
let (tx, rx) = mpsc::channel();

let (a2, b2) = (a.clone(), b.clone());
let worker = thread::spawn(move || {
    let _x = a2.lock().unwrap();            // take a first
    thread::sleep(Duration::from_millis(50));
    let _y = b2.lock().unwrap();            // then b — never comes
    let _ = tx.send("worker finished");
});

let _y = b.lock().unwrap();                 // main: take b first
thread::sleep(Duration::from_millis(50));

match rx.recv_timeout(Duration::from_secs(2)) {
    Ok(msg)  => println!("no deadlock: {msg}"),
    Err(RecvTimeoutError::Timeout) => println!("deadlock confirmed"),
    _        => {}
}

Output on this box (rustc --edition 2021 -O deadlock.rs -o deadlock && ./deadlock):

main: holds b; worker holds a; the mutual-wait condition is met
deadlock confirmed: worker did not finish within 2s — it is blocked on b.lock() (main holds b, worker holds a)

Deadlocks are invisible to the compiler — Mutex itself is safe; wrong lock ordering is a logic error. Two fixes: agree on a global lock order (always a→b), or put both resources behind one lock.

Example 2: 100 threads on one counter — two unsafe signatures first, then the loss#

This is the main course, and the section that matters most. Goal: reproduce the classic “shared counter mutated without a lock” bug from Java/C++. Doing it in Rust is hard on purpose. Two compile-time gates you can’t skip:

Gate 1: UnsafeCell is not Sync. For cross-thread shared mutable cells, Rust’s legal channels are only Mutex and atomics. Wrapping UnsafeCell in an Arc is rejected, verbatim:

error[E0277]: `UnsafeCell<i64>` cannot be shared between threads safely
  --> src/race.rs:22:44
   |
22 |                   handles.push(thread::spawn(move || {
   |                              |
   = help: the trait `Sync` is not implemented for `UnsafeCell<i64>`

Gate 2: raw pointers are not Send. Going the unsafe route means the closure carries a *mut i64 across threads — you must hand-write a Send newtype (plus Copy, since the loop re-captures it every iteration). Sign these two “disclaimers” before the run starts:

#[repr(transparent)]
struct Shared(*mut i64);
unsafe impl Send for Shared {}
impl Copy for Shared {}
impl Clone for Shared {
    fn clone(&self) -> Self { *self }
}

The run: one UnsafeCell<i64> on the stack, 100 threads each doing 100k load-modify-stores, zero synchronization. Expected: 10,000,000. Control group: the same load on Arc<AtomicI64>.

Output on this box (rustc --edition 2021 race.rs -o race && time ./race, -O0, default tier):

== unsynchronized shared i64 (5 rounds): expected 10000000 ==
  round 1: 2831309   lost 7168691 (71.69%)
  round 2: 1865145   lost 8134855 (81.35%)
  round 3: 4870351   lost 5129649 (51.30%)
  round 4: 2734908   lost 7265092 (72.65%)
  round 5: 2455018   lost 7544982 (75.45%)
== AtomicI64 control: 10000000 (exactly 10000000, zero loss) ==

Loss tracks how badly the scheduler interleaves: 51%–81% is the typical band for 100 threads tearing a load-modify-store on this machine. Recompile the same source with -O and run again:

== unsynchronized shared i64 (5 rounds): expected 10000000 ==
  rounds 1–5: 10000000   lost 0 (0.00%)

Zero loss under -O. This code is undefined behavior — the compiler may drop the updates or keep them; both outcomes are UB. Five clean rounds under -O is not a fix, it’s luck. That is exactly why unsynchronized shared read-modify-write never belongs in production: the failure mode depends on optimization tier, microarchitecture and scheduling. Unreproducible means it hasn’t happened yet, not that it won’t.

Control numbers, same box, same load:

Scheme 100 threads × 100k result Loss
UnsafeCell + raw pointer, -O0 5 rounds: 2.83M / 1.87M / 4.87M / 2.73M / 2.46M 51.3%–81.4%
UnsafeCell + raw pointer, -O 5 rounds: 10.00M × 5 0% (UB luck)
Arc<AtomicI64> (Relaxed) 10,000,000 0%
Arc<Mutex<u64>> (example 3b) 10,000,000 0%

Example 3: Rc → Arc, and three postures for shared mutability#

3a: Rc across threads — rejected at compile time. Putting Rc<Vec<_>> into thread::spawn fails with:

error[E0277]: `Rc<Vec<i32>>` cannot be sent between threads safely
  --> src/rc-thread.rs:9:28
   |
 9 |       let _t = thread::spawn(move || {
   |                |
   = help: within this closure, the trait `Send` is not implemented for `Rc<Vec<i32>>`

Rc’s count is a plain integer — a single-thread assumption. Under concurrency the count itself would race, so it isn’t Send. Swap Rc::new for Arc::new (atomic count) and the same line compiles.

3b: once cross-thread, three postures for “writing in”. Arc<T> alone gives shared read-only; to write, the inner type must carry its own mutability channel:

Posture Mechanism Measured on this box
A. RefCell single-thread interior mutability, runtime borrow check a second RefMut while one is held: panicked: RefCell already borrowed (already mutably borrowed). Also RefCell is not Send: Arc<RefCell<T>> cannot cross threads
B. Mutex<T> cross-thread write contention serialized 100 threads × 100k = 10,000,000, exact
C. AtomicU64 single-value, lock-free 100 threads × 100k = 10,000,000, exact

The RefCell panic is a runtime discovery — the same class of “logic bug” as the deadlock in example 1: every line type-checks, the program explodes when it runs.

Three layers: which error is caught where#

Error class Caught at Example in this piece
Data race (unsynchronized shared read/write) Compile time: code without Send/Sync proof doesn’t build Rc across threads (3a), UnsafeCell not Sync
Deadlock Runtime: wrong lock order compiles fine double-lock (example 1)
Interior-mutability conflict Runtime: RefCell second RefMut panics 3b-A
Undefined behavior Nowhere: under UB, results are luck example 2’s “0 loss” under -O

“No GC” only answers how long objects live, not what two threads writing at once produce. Rust’s answer front-loads what it can: races into the type system, deadlocks left to runtime and lock-ordering discipline; the unsafe remainder is on whoever writes it.

Frequently Asked Questions

No GC in Rust — does that make concurrency safe?

No. Rust pushes data races (unsynchronized concurrent read/write of the same memory) to compile time: the Send/Sync checks reject the code. Deadlocks, logic errors, and anything you write behind unsafe stay at runtime. Three examples cover three layers: compile-time rejection (Rc across threads), runtime explosions (double-lock deadlock, RefCell), and the layer that stops nothing (UnsafeCell + raw pointers = UB).

Why do 100 threads × 100k increments lose 51%~81%?

Each thread does a torn load-modify-store: read the shared cell, increment locally, write back. 100 threads doing this concurrently overwrite each other (lost updates). Measured on a 2-vCPU box, 5 rounds: 51.30% / 71.69% / 72.65% / 75.45% / 81.35% lost. Swapped to Arc<AtomicI64> or Mutex: exactly 10,000,000, zero loss.

0 loss under -O — is it safe then?

No. Under -O0 the loss is 51%~81%; under -O all 5 rounds come back at 0. The code is undefined behavior — the compiler may drop updates or not; both outcomes are UB. “Correct by luck after optimization” is not a safety argument.

Rc vs Arc — what's the difference?

Reference-counting strategy: Rc is a plain integer (single-thread assumption, not Send) and is rejected at compile time across threads; Arc uses atomic counters (one atomic add/sub each), so it can cross threads. Inside a single thread Rc is usually cheaper; across threads or processes, Arc is mandatory.

RefCell or Mutex, when?

Single-thread interior mutability: RefCell (runtime borrow checks; a second RefMut panics). Cross-thread mutable sharing: Mutex or atomic types. RefCell is not Send — Arc<RefCell<T>> cannot cross threads; the legal channels for concurrent mutation are Mutex<T> and the atomics.
