Can You Actually Write SIMD in Rust in 2026: I Ran All 4 Routes on Zen4

shnatsel asserts Zen4 maps 512-bit instructions to 256-bit execution. My EPYC 9354P is exactly Zen4 — so I wrote a 4-route throughput benchmark (auto-vectorize / wide / pulp / 3 target-cpu tiers) and checked by hand: assembly proves 0 512-bit ZMM instructions, and I wrote up the DCE trap where the loop disappears out of thin air.

October 4, 2026 · 6 min · 1156 words · Dreambeast -  |  中文

shnatsel’s The state of SIMD in Rust in 2026 asserts: “Zen4 has no native 512-bit; it maps 512 to 256-bit execution, yet the benchmarks beat Intel’s native 512.” That claim lands exactly on my machine — AMD EPYC 9354P is Zen4. I wrote a 4-route throughput benchmark (auto-vectorization / wide / pulp / 3 target-cpu tiers) and checked it by hand.

Conclusion first#

  1. Hand-written SIMD on stable Rust is usable now; no nightly needed: std::simd is still nightly-locked, but the two stable crates wide + pulp already get you full 256-bit width, and in my real runs they beat auto-vectorization.
  2. Auto-vectorization is Schrödinger’s fast: the same chunks code compiles to 37.8 GB/s on target-cpu=x86-64-v2, but on the v3/zen4 tiers the loop is eliminated wholesale by the compiler (0.0000ms, physically impossible). Throughput depends on which target-cpu tier you compile with, not on the code.
  3. Zen4’s fake 512, proven: on target-cpu=zen4, objdump counts 0 512-bit ZMM instructions and 512 256-bit YMM instructions across the whole binary — you write the 512 API, the compiler hands you 256-bit instructions; the run comes out at 43.2 GB/s, 16% faster than the v2 tier.

What I did#

The benchmark is bench/simd-bench (stable rustc 1.99.0), the same 4M f32 (16MB×2), 4 routes:

fn auto_sum(a: &[f32]) -> f32 { a.iter().sum() }        // naive scalar
fn auto_sum_chunks(a: &[f32]) -> f32 {                  // 4-way accumulators, let the compiler auto-vectorize
    [0f32;4].iter().zip(a.chunks(4))
        .map(|(acc,ch)| ch.iter().fold(*acc, |s,x| s+x)).sum()
}
fn wide_dot(a,b: &[f32]) -> f32 { /* wide::f32x8 by hand */ }
fn pulp_dot_v3(a,b: &[f32]) -> f32 { /* pulp V3 256-bit by hand */ }

Each target-cpu tier is built and timed separately (RUSTFLAGS="-C target-cpu=..." cargo build --release) — only then can you see which tier unlocks auto-vectorization.

Core data (GB/s effective, higher is faster)#

Routex86-64-v2x86-64-v3zen4
auto_sum(iter.sum) scalar9.49.49.7
auto_sum(chunks) auto-vect37.80.0000*0.0000*
wide f32x8 by hand28.335.338.1
pulp V3 256-bit by hand37.142.943.2

* = the compiler eliminated the loop wholesale (dead-code elimination). Reading 32MB can’t possibly finish in 2µs — this is the first pitfall of a throughput benchmark: anywhere black_box didn’t wrap, at the higher target-cpu tiers the compiler deletes the “compute-once-read-once” loop down to the root. The fix (print the result + black_box) sometimes still doesn’t hold; before you trust wall-clock, objdump and confirm the vaddps is still spinning.

The assembly proof: Zen4’s “fake 512”#

$ RUSTFLAGS="-C target-cpu=zen4" cargo build --release
$ objdump -d target/release/simd-bench | grep -c "vaddps.*%zmm"   # 512-bit
0
$ objdump -d target/release/simd-bench | grep -c "vaddps.*%ymm"   # 256-bit
512

The c5 prefix is a 256-bit VEX instruction; true AVX-512 needs the 62 EVEX prefix. Zero ZMM instructions across the whole binary — the original’s “Zen4 maps 512 to 256-bit execution” is proven literally (I don’t have an Intel-native-512 machine, so I could only verify up to “16% faster than the v2 tier”).

When NOT to write SIMD#

After running this, the thing I most want to say is this one: for pure reductions (sum/dot/min/max) where the data saturates memory bandwidth, the bottleneck is memory, not CPU — my box’s 43 GB/s is the “effective bandwidth” of re-reading 16MB from L3; put a real 1GB dataset on it and you’re immediately slammed back to the DDR4/5 ceiling (40-50 / 80-90 GB/s), and the SIMD-vs-scalar gap gets flattened by the memory bottleneck. One-line test: a hotspot function with <2 FLOP per byte — do cache tiling / prefetch first, don’t reach for SIMD.

wide or pulp#

  • wide 0.7’s ceiling is f32x8 (256-bit used half-width); no f32x16; my box 38.1
  • pulp’s V3 is full 256-bit (AVX2); my box 43.2, the stable winner
  • Both are stable. “Hand-written SIMD requires nightly” — that 2025 belief is out of date as of 2026

A pulp dot product that compiles as-is (stable, real-ran on my box):

use pulp::{cast, f32x8, Simd};
use pulp::x86::V3;

fn dot_f32_v3(a: &[f32], b: &[f32]) -> Option<f32> {
    let simd = V3::try_new()?;             // returns None on machines without AVX2 — you MUST fall back to scalar
    struct Impl<'a> { simd: V3, x: &'a [f32], y: &'a [f32] }
    impl pulp::NullaryFnOnce for Impl<'_> {
        type Output = f32;
        #[inline(always)]
        fn call(self) -> f32 {
            let Self { simd, x, y } = self;
            let (x8, x1) = pulp::as_arrays::<8, _>(x);
            let (y8, y1) = pulp::as_arrays::<8, _>(y);
            let mut acc = simd.splat_f32x8(0.0);
            for (x, y) in x8.iter().zip(y8.iter()) {
                let x: f32x8 = cast(*x);
                let y: f32x8 = cast(*y);
                acc = simd.add_f32x8(acc, simd.mul_f32x8(x, y));
            }
            let mut acc = simd.reduce_sum_f32s(acc);
            for (x, y) in x1.iter().zip(y1.iter()) { acc += x * y; }  // remainder MUST be scalar
            Some(acc)
        }
    }
    simd.vectorize(Impl { simd, x: a, y: b }).map(|r| r)
}

Two must-hit traps: f32x8/Simd don’t live under the pulp:: root (you need use pulp::x86::V3 + use pulp::{cast, f32x8, Simd}); V3::try_new() returns an Option and does NOT panic — on ARM / older machines you must handle the fallback.

Picking target-cpu at deploy time#

  • Self-hosted servers / containers: just use -C target-cpu=zen4 to saturate the local machine; don’t add multiversioning complexity to yourself
  • Distributing to others: multiversioning (multiple binaries + CPUID probing) is only worth it when the function is long enough and the fleet is heterogeneous; if the function is too short, the probe/jump fixed overhead is a big slice of the total and the net gain is negative — scalar + auto-vectorization is better. I did not measure multiversioning’s probing overhead on my box; marked unverified.

Honesty statement#

  • This box is a 2-core shared slice; read the relative values, not the absolute ones. GB/s is effective read bandwidth, not true memory bandwidth.
  • Verified: 4-route throughput, 3 target-cpu tiers, the DCE trap, Zen4’s 512 mapping (assembly 0 ZMM / 512 YMM), stable wide/pulp.
  • Not verified (paraphrased from the original): old Intel Skylake all-core AVX-512 downclocking, trig + multiversioning small-function overhead, the “beats Intel native 512” half of the claim.
  • Reproduce: RUSTFLAGS="-C target-cpu=zen4" cargo build --release && ./target/release/simd-bench (in bench/simd-bench).

FAQ#

Q: Can stable Rust write SIMD? A: Yes. std::simd is still nightly, but wide + pulp are both stable, and in my real runs they outpace auto-vectorization.

Q: Why is auto-vectorization unreliable? A: It depends on two variables: how many accumulator lanes you write (chunks(4) is 4x, naive sum is not) + the compile-time target-cpu (v2 tier 37.8, v3/zen4 tiers DCE’d to 0). Same code, two tier builds, throughput swings from 37.8 to “nothing.”

Q: wide or pulp? A: pulp V3 full 256-bit (43.2) > wide f32x8 (38.1, its ceiling). API simplicity → wide; full bandwidth → pulp.
