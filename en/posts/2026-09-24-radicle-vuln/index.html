Radicle, Fully Exposed: After the Noise Handshake, Everything Travels in the Clear

On Sept 23, Radicle disclosed that every released version ships unencrypted, unauthenticated node traffic. After the Noise XK handshake (32/32/48 bytes), data goes straight onto the raw socket. The official guidance: treat every private repository that crossed the wire as already public.

September 24, 2026 · 8 min · 1658 words · Mengshou Coding -  |  中文

On Sept 23, Radicle published what you could call a rare post on radicle.dev, titled without any padding: Disclosure of Vulnerability in the Network Protocol External link . It pulled 125 points on HN with 49 comments, and the comment section was nearly unanimous: “A P2P layer of a decentralized Git with no TLS at all?” — the answer is worse. It’s not that there’s no TLS. It’s that after the handshake, nobody is managing encryption at all.

Three conclusions up front:

  1. Every released version (through 1.10.3) of Radicle’s node sends plaintext over the raw socket after the handshake;
  2. The connection handshake permits Node ID impersonation, so the private-repo allow list can’t stop a direct spoof;
  3. The official guidance is one hard sentence: treat every private repository that has crossed the network as already leaked, and rotate any keys that were stored in the clear.

This post covers three things: where the bug actually lives in code, what to do today (the official discipline checklist, item by item), and why the fix has to ship as a breaking major release.

Two vulnerabilities, one attack chain#

The disclosure lists two independent flaws. Neither is novel in isolation; stacked together, they’re the real story:

#FlawReporter / dateConsequence
1Post-handshake traffic is unencryptedKonstantinos Maninakis, 2026-06-24Any observer on the path (ISP, transit, relay) can read every object
2Peer identity is forgeable at the handshakecryptocode, 2026-08-12An attacker can impersonate an allow-listed Node ID and pull private repos

Flaw 2 alone is hard to weaponize: the allow list isn’t public, so an attacker off the path has to guess a legal Node ID — a 20+ character ID is a long shot. Combine the two and the chain closes: a path observer can trivially see the Node IDs at both ends of a connection, and both of those are normally on each other’s allow lists. Ride the path to read plaintext, pick up an ID, then step off the path and connect with it to pull the entire private repository on demand. The official wording:

The realistic threat is anyone on the path between your node and the node it syncs with, and no setting or allow-list protects against them.

Integrity is still held: Git objects are content-addressed, refs are signed, and tampering gets caught at the storage layer. The disclosure deliberately scopes itself to confidentiality only, and the boundary is drawn cleanly — a good sign the team isn’t overselling the fix’s scope.

Root cause: one is_complete() condition, semantics exactly backwards#

All the byte-level detail comes from the reporter’s writeup External link (he’s building Grove, a Radicle node that runs inside a browser tab, and he rewrote the transport byte for byte in TypeScript). Every Radicle connection starts with a Noise XK handshake — the same protocol family WireGuard uses, three messages:

  1. Dialer: ephemeral public key + Diffie-Hellman against the peer’s long-term public key. 32 bytes out.
  2. Responder: its own ephemeral key + a second DH. 32 bytes back.
  3. Dialer: its long-term key, encrypted under what the two now share. 48 bytes out (32-byte key + 16-byte auth tag).

When message three lands, both sides derive their symmetric key pairs — what Noise calls the split, and the entire point of the handshake. The problem starts from exactly that moment: in radicle-node’s session.rs, the generic Protocol wrapper checks a single condition on every write —

// crates/radicle-node/src/reactor/session.rs, Radicle 1.9.1 (1.10.3 keeps the same logic, field renamed)
impl<M: StateMachine, S: Session> Write for Protocol<M, S> {
    fn write(&mut self, buf: &[u8]) -> io::Result<usize> {
        if self.state.is_complete() || !self.session.is_established() {
            log::trace!(target: M::NAME, "Passing writing to inner session");
            return self.session.write(buf);   // ← straight onto the raw socket
        }
        // ... handshake-phase messages ...
    }
}

buf is everything the node says next: gossip, ref announcements, the Git pack of a private repository. The two branches that fire this condition are too early (the socket underneath isn’t established, there’s nothing to encrypt yet) and too late (handshake done — precisely when encryption should begin). Both extremes take the same branch, and both end up in plaintext. The code’s own log line is blunter than any annotation: “Passing writing to inner session.”

How did it happen? The same Protocol also wraps SOCKS5 sessions: under SOCKS5 semantics, once the proxy handshake completes you’re supposed to get out of the way and pass bytes through — this branch is correct for that case. Under Noise, the end of the handshake is where the real work starts. One is_complete(), two exactly opposite meanings, one implementation — and the one that got implemented is the SOCKS5 half. Meanwhile noise-framework 0.4.1 does compute both directions of cipher state and stores them on NoiseState::Active (the fields are even public), but it exposes only two accessors: get_handshake_hash and get_remote_static_key. The node is told “the handshake succeeded” and never gets the keys themselves. The encryption loop was simply never written. (The reporter’s post includes the complete fix patch: chunking, length framing, encrypt_with_ad — everything.)

Corroborating detail: Maninakis captured a production seed. The first byte after the handshake, offset 32, is ASCII r — the start of rad, the node announcement. His words: “I didn’t believe it at first.”

What to do today: the official discipline checklist#

The official workaround is four items; I’ve ordered them by execution sequence (the first two stop the bleeding, the last two clean up):

ActionCommand / operationNote
Inventoryrad ls --private --allList every private repository in storage
Stop seedingrad block <RID> per repository (not rad unseed)Default seeding policy is block, so on stock configs rad unseed suffices — but if you flipped the default to allow, an unseed leaves the repository still being served. rad block is explicit and checked first, so it works either way
Stop the noderad node stopServe nothing at all
Rotate secretsAny credential / token / key ever stored in a private repository: treat it as publicNothing un-sends data that already crossed the wire; Tor / VPN doesn’t stop impersonation, so don’t count on it

Three hard limits the official post draws, accepted verbatim:

  • rad block only stops your node serving the repository. It doesn’t delete the local copy (it lives at $(rad path)/storage/<RID without the rad: prefix>), and it doesn’t reach copies that allow-listed peers already fetched — those peers run nodes with the identical flaw, and they need to block too;
  • data that has already synced across the network is disclosed; there is no undo;
  • pointing node.proxy at Tor is not confidentiality: it just moves your plaintext traffic to the Tor exit, where the exit operator still reads it. Onion peers require the separate node.onion setting.

In passing, Grove (same vendor, cyphernet-labs) speaks the same wire — Maninakis names it in his post.

Why the fix must be a breaking major release#

The direction is set: replace the custom transport layer wholesale with iroh External link — a QUIC/TLS-based, open-standards P2P stack that also brings NAT traversal. The disclosure’s own words: the vulnerabilities “have given us all the more reason to move forward with this.”

Why no minor hotfix? Two causes stacked: the wire has no version negotiation and the fix is wire-incompatible. A patched node and an unpatched node simply can’t talk, so the network partitions into two islands. The team’s mitigation is to “focus breakage on the network end, keeping storage layout compatible” — your repositories don’t have to migrate, but a 1.x node that upgrades to 2.0 loses its 1.x peers.

This is the unavoidable sin of P2P systems: a central service can canary, dual-run, and negotiate per connection. In a P2P network every node is its own server and nobody controls the upgrade cadence. Radicle chose to publish before the fix lands, and the reason is in the post: “you can act on it today, and no fix we release later can undo an exposure that has already happened.” That posture is uncommon in open source and worth noting.

Honest disclosure#

The usual error-source caveats:

  • This post did not reproduce the plaintext transport on a local Radicle node (no 1.x deployment environment here). Byte-level details (32/32/48, the rad at offset 32, the session.rs source) are all sourced from Maninakis’s writeup and Radicle’s official disclosure; line numbers are from the trimmed 1.9.1 listing, with 1.10.3 being “same condition, renamed field”;
  • on the fix side there’s only the official roadmap (iroh, breaking major) and no timeline; this post doesn’t predict a release date;
  • “treat every private repository that crossed the wire as leaked” is the official recommendation, not a mathematical conclusion — actual exposure depends on how many parties your sync path really traversed, and this post won’t risk-assess any specific path.

Frequently Asked Questions

Are public repositories affected?

Marginal damage. Public data was already meant for everyone, so a path observer gains nothing. Private repositories are the story: plaintext transport plus forgeable allow-listed identities means your private code was effectively public to anyone on the path.

Does Tor or a VPN fix this?

Not the impersonation part. The official disclosure says it plainly: Tor, I2P, and VPNs hide traffic from path observers, but a forger doesn't need to be on the path — it connects to your node with a spoofed allow-listed Node ID and pulls the private repository directly. 'Not sufficient to protect your data,' in their words.

What's the difference between `rad unseed` and `rad block`?

`rad unseed` only removes the repository's seeding policy; the node falls back to its default. If you flipped the default to `allow`, your node keeps serving the repository after an unseed. `rad block` sets an explicit block that the node checks first, regardless of default. The official docs recommend `rad block`.

When is the fix shipping?

Work in progress, no date. The plan replaces the custom Noise-based transport with iroh (QUIC/TLS-based, open standards). The wire change is incompatible, so it must ship as a breaking major release — 1.x and 2.x nodes will not interconnect, and the network partitions into two islands.

Is a local private repository that never synced safe?

The storage layer is sound: content-addressed Git objects plus signed refs mean nobody can forge contents — only read them. All the risk is in the 'transmitted' step. A local copy that never crossed the network is unaffected.
