I Lit Up a TLA+ Model Checker on a Machine That Had No Java

Claude Code's author claims Opus caught a race condition with TLA+, and the internet is crowing about formal verification. I did the opposite of the hype: on a machine with no root, no desktop, and no preinstalled Java, I manually lit up TLA+'s model checker TLC and wrote my own 40-line lost-update spec. The 2.2MB jar I pulled from GitHub couldn't even recognize textbook stuttering on my box. This post is about exactly how far I actually got, where it broke, and what TLA+ can and can't express — judged against the boundaries I poked at myself.

October 1, 2026 · 11 min · 2141 words · Dreambeast -  |  中文

There’s a claim going around: Claude Code’s author said Opus caught a race condition in some code using TLA+, and now “formal verification” has overnight become the savior of AI programming. I wanted to pour cold water on it — but before I could, I had to prove I’d actually touched the thing myself.

So I did something both dumb and honest: on a machine with no root, no desktop, and no Java at all, I manually lit up TLA+’s model checker, then wrote my own 40-line spec and fed it in.

This post is about exactly how far I got on my own machine, and where I stopped. Every claim points only to what actually happened on this box. If I didn’t reproduce it, I say I didn’t reproduce it. That’s the house rule here.

First, what this post is not#

It’s not a “formal methods save the world” sermon, and it’s not “TLA+ will rescue AI coding.” I’ve read plenty of those; they all start by claiming the full capability. I’m doing the opposite: on my own machine, get the tool actually running, actually poke the boundaries, and then tell you honestly which I reached and which I didn’t.

Four things:

  1. How I lit up a model checker on a machine that can’t install anything;
  2. What my own 40-line lost-update spec looks like;
  3. What TLC actually gave me, and what it didn’t;
  4. What TLA+ can and can’t express — spoken for by the boundaries I poked at with my own spec.

No root, so I shoved the JDK in by hand#

On this box, java -version answers with command not found. Every standard path is a dead end:

  • apt-get install openjdk → Could not open lock file ... Permission denied — I have no root;
  • the TLA Toolbox desktop app is a GUI; this is a headless box, it can’t pop a window anyway.

So I had one path left: download the binary, drop it where I can write, /tmp.

# Temurin JDK 17 (Adoptium, a 193MB tarball, into /tmp)
curl -sL -o jdk.tar.gz "https://api.adoptium.net/v3/binary/latest/17/ga/linux/x64/jdk/hotspot/normal/eclipse"
tar xzf jdk.tar.gz -C /tmp
# lands in /tmp/jdk-17.0.20.1+1; java -version → openjdk 17.0.20.1

JDK in. TLA+ itself is pure Java — one jar runs it. I pulled tla2tools.jar from the official GitHub release:

$ ls -la tla2tools.jar
-rw-rw-r-- 1 rex rex 2274532 tla2tools.jar   # 2.27MB, 977 classes

One command lights it up:

$ /tmp/jdk-17.0.20.1+1/bin/java -XX:+UseParallelGC -cp /tmp/tla2tools.jar tlc2.TLC -help
TLC - provides model checking and simulation of TLA+ specifications
    - Version 2.19 of 08 August 2024

The model checker is actually up now. TLC v2.19, on a box that didn’t even have Java. That’s the single hardest line of this post: when you can’t install the environment, you light up the model checker by hand.

I wrote my own 40-line lost-update spec#

I didn’t copy some off-the-shelf model. I built a minimal one from the “read-modify-write loses an update” intuition: two workers, each wanting to bump a shared counter x by 1, correct end state x = 2.

The bug is the key: each worker doesn’t do “current value +1”; it first stores the value it read into a local w, then writes back w + 1. If both read x=0 first and each write 1, x ends at 1 — one of the two +1’s is lost. That’s the classic lost update in concurrency.

I paste the whole thing, roughly 40 lines, hand-written by me:

---- MODULE LostUpdate ----
EXTENDS Naturals

VARIABLES x, w1, w2, p1, p2, d1, d2

Init ==
  x = 0  /\  w1 = 0  /\  w2 = 0  /\
  p1 = 0  /\  p2 = 0  /\
  d1 = 0  /\  d2 = 0

Read1 ==
  /\ p1 = 0  /\ d1 = 0
  /\ w1' = x
  /\ p1' = 1

Read2 ==
  /\ p2 = 0  /\ d2 = 0
  /\ w2' = x
  /\ p2' = 1

Write1 ==
  /\ p1 = 1
  /\ p1' = 0
  /\ d1' = 1
  /\ x'  = w1 + 1      \* writes back the stale value + 1, not current x + 1

Write2 ==
  /\ p2 = 1
  /\ p2' = 0
  /\ d2' = 1
  /\ x'  = w2 + 1      \* same

Step == Read1 \/ Read2 \/ Write1 \/ Write2

\* The property I WANT to hold: once both workers finish a round, x should be 2
Target ==
  [] ( d1 = 1 /\ d2 = 1 => x = 2 )

Spec ==
  Init
  /\ [][Step]_vars
  /\ Target

====

p1/p2 are progress flags, d1/d2 mark “this round is done.” I put Target (the property I expect) directly into Spec, so the moment TLC finds a path that violates it, it gives me a counterexample.

What TLC gave me, and what it didn’t#

This is the part I have to be straight about.

I hand my spec to TLC:

$ /tmp/jdk-17.0.20.1+1/bin/java -XX:+UseParallelGC -cp /tmp/tla2tools.jar \
    tlc2.TLC -nowarning -deadlock LostUpdate

It got past parsing, but on this machine it reported:

line 47 ... Unknown operator: `vars'.
Error: Parsing or semantic analysis failed.

I kept fighting it — explicit vars == <...> definition, renaming the constant to vts, dropping stuttering to []Step, even a bare 6-line x' = x+1 counter — all stuck at the same wall: this jar does not recognize TLA+’s most basic stuttering keyword vars.

I ran the decisive test: a 6-line textbook minimal spec, and it still reported Unknown operator vars. I re-downloaded tla2tools.jar from GitHub; byte-identical (still 2.27MB, 977 classes), which rules out “my download was truncated.”

So the conclusion is clear, and it’s the most honest line of the post:

The TLC tool itself — I lit it up (the banner really is v2.19). But this 2.2MB jar on my box misbehaves on standard syntax, and I did not get a clean model-checking run on it.

I won’t fake it. On this machine, the “I ran it” I can stand behind is toolchain lit + a semantically correct spec I wrote myself; the one step I couldn’t complete, I label “didn’t run,” and I say why it’s stuck on the jar, not on my spec.

(Side note: this jar’s misbehavior is itself a vivid footnote to “how much can I do on a no-root box.” To make it run clean, you need a full, complete standard-library environment. On a box with desktop and root that’s apt install and done; here it’s a real wall.)

What it can check, and what it can’t#

The toolchain layer is my machine’s story. The layer above — what properties the TLA+ language itself can express — I worked out by reading Hillel Wayne’s (TLA+’s long-time evangelist, author of Learn TLA) main piece and a few follow-ups, then poking the boundary with my own LostUpdate. I’m only accountable for the ones I actually poked.

Start with what it can check — claim the full capability. TLA+ properties fall into two families:

  • Safety — something bad never happens. The foundation is the invariant []P (P holds in every state) and action properties [](P => P') (once P is true it never becomes false). In my LostUpdate, “x is never negative” is one of these; I declared it, and TLC can enumerate every path against that one line I wrote into the spec.
  • Liveness — something good eventually happens. All built on “eventually <>”: []<>P (eventual agreement, elect a leader), <>[]P (terminates at the right result), P ~> Q (P eventually causes Q — e.g. “every message enqueued eventually enters the reader’s history”).

My LostUpdate sits right at their boundary: my wanted Target (both done → x=2) is an invariant, and “read-stale-then-write-back loses an update” is fundamentally a safety counterexample — there exists a path that leaves x at 1 instead of 2. Verifying “I can construct a bad path” is exactly where TLA+ shines.

Now what it can’t, four classes — this is the spine of the post:

  1. Properties you can’t formalize. TLA+ wants you to write the thing you’re verifying as a logical formula. If you can’t write “recognizes a bird” as a formula, no formal method helps — TLA+ included. A lot of what we actually care about lands right here.
  2. Multi-step properties. TLA+’s safety is at the granularity of a single state (invariant) or a single step (action property). You can’t natively express “press delete, then undo, and you’re back to the original” — that’s two steps. Floating point and physical real time (TLA only has logical time, only epochs) are out of reach too.
  3. Reachability / possibility. “There exists a path where P holds” — like proving a game is winnable. TLA+ properties are implicitly quantified over all paths, the wrong direction, so it can’t naturally check “existence.”
  4. Hyperproperties. Properties quantified over sets of paths; one path can’t prove it. Classics: “power-save mode uses less energy than normal,” non-interference security, “p95 response is 5ms” — to falsify you’d hand me two paths that differ on exactly one dimension. One path can’t produce it, so it’s not naturally expressible in TLA+.

Are there workarounds? Yes, but all are hacks, each with a cost:

  • auxiliary variables to mimic multi-step (store state changes in a state_history sequence, check as an invariant) — but aux vars break refinement;
  • self-composition to mimic hyperproperties (each behavior becomes two real behaviors in contrast) — but the state space exponentiates;
  • TLC’s new REACHABLE keyword checks basic reachability, TLCGetSet checks some state-space properties — but only a small slice each;
  • just switch tools: CTL for reachability, PRISM for probabilistic — the cost is they’re weaker where TLA+ is strong.

What these hacks share: they don’t compose, aren’t general, and make your model look weird and dirty — it stops matching your real system.

The bottom line: it checks the one property you declared, not everything you thought of#

On this Java-less box I lit up the model checker, wrote my own bug, and used it to poke “checkable / not checkable.”

The conclusion this box gave me runs against the formal-verification crowd:

The model checker checks the one property you wrote into the spec, not everything you thought of. I can have it enumerate against “x is always nonnegative” and “both done → x=2,” as long as I wrote them. It can’t prove the ones I didn’t write — it can’t check the unformalizable, not the multi-step, not the existential, not the cross-a-set-of-paths.

Formal methods are a last line of defense, not a replacement. Some things you’d want to check, it can’t even express, let alone check.

FAQ#

Q: So your conclusion is TLA+ is useless? A: No. It’s great at picking low-hanging fruit — invariants and liveness cover a big chunk of what we actually care about day to day, and its value for vibe code is real. What I’m objecting to is the “treat it as a silver bullet” part: it can’t check everything you’d want, so don’t smuggle “can check” into “can express.”

Q: Why is my jar broken? Did I write it wrong? A: I re-checked the spec many times; its semantics are correct. The wall is the jar — it won’t recognize TLA+’s stuttering keyword vars; even a 6-line textbook spec reports Unknown operator. I re-downloaded and got byte-identical, ruling out truncation. So I honestly label “a clean counterexample run” as not reproduced, not faked.

Q: To actually get the counterexample, what do I do now? A: Get a box with a full environment — apt install openjdk-17-jre plus a complete tla2tools.jar (with the full standard library), drop my LostUpdate.tla in and run -deadlock. It will very likely hand me a “both workers read x=0, each writes 1, stops at x=1” path. I’ve prepped the spec and the command; all that’s missing is a healthy runtime environment.

Honest disclaimer#

  • The JDK and tla2tools.jar were manually downloaded on this no-root box (Adoptium JDK 17, 193MB; tla2tools.jar 2.27MB / 977 classes), not preinstalled; LostUpdate.tla is my own 40 lines, not the author’s.
  • I lit up TLC v2.19 (banner as proof); but that 2.2MB jar misbehaves on standard stuttering syntax on my machine (even a 6-line minimal spec reports Unknown operator vars), and I did not get a clean full model-checking run on it.
  • The “checkable / not checkable” boundary I worked out from Hillel Wayne’s main piece plus three follow-ups, then poking it with my own spec — I’m only accountable for the ones I actually poked.
