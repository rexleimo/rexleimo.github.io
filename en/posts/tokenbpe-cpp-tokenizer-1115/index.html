TokenBpe: A Hand-Rolled C++20 Tokenizer Where 240 MB/s Comes From a Dozen Multiplied Micro-Tricks

Unica2804/Token_BPE is a 0-star personal repo: a hand-written C++20 BPE tokenizer reporting 240 MB/s encode throughput. I pulled the whole source and checked the mechanics claim by claim, then ran a single-threaded control on my 2-core box. Full post and discussion live on the BBS.

November 16, 2026 · 4 min · 728 words · Dreambeast -  |  中文

Every LLM request crosses the tokenizer twice, once in and once out, and almost nobody looks at it twice. A personal repo, Unica2804/Token_BPE, turns that invisible fixed cost into a hand-written C++20 BPE implementation reporting 240 MB/s encode throughput. 0 stars, 0 forks, no releases, MIT, 14 commits. Every performance number in this piece is the author’s own output on the author’s own machine, with no external reproduction, and the benchmark script is the author’s too. What I did: pulled the full source and checked the mechanics claim by claim, then ran a single-threaded control on my 2-core box. The value here is not believing 240 MB/s — it is seeing where the savings come from, and tricks do not care whose machine they ran on.

Pipeline diagram drawn by us from the main-branch source (file and line references pulled and checked 2026-11-15); all throughput figures are author-reported.

The fixed cost nobody watches#

The incumbents in this slot are two: OpenAI’s tiktoken, Rust core with Python bindings (its README claims 3-6x over comparable open-source tokenizers, measured on 1GB of text against tokenizers 0.13.2); and Hugging Face’s tokenizers, also Rust-cored, at 11,247 stars (GitHub API, 11-15). TokenBpe takes the other road: one person, C++20 from scratch, those two as the control group.

The machinery in the hot path#

Pre-tokenization drops the regex engine entirely: swar.hpp classifies 8 bytes at a time with pure 64-bit integer ALU — no SSE/AVX intrinsics, one instruction where eight branches used to be. The merge phase lays fragments on a thread_local scratchpad, one linked-list node per byte, and a merge is three assignments — O(1) unlink, zero string allocation on the hot path. Each worker gets its own 512 KiB direct-mapped cache (8,192 cache-line-aligned slots); fragments up to 22 bytes that hit skip the whole merge. A dual cursor splits the text at whitespace near the midpoint and feeds two independent dependency chains into the same core — instruction-level parallelism, no extra threads. The author’s summary: no single killer trick, just a dozen small multipliers over boundary copies, allocations, cache misses and dependency chains.

The 1.75x that is not an algorithm#

The sneakiest cost sits one step outside the code, at the Python boundary. TokenBpe hands the encode result over as a heap-moved vector wrapped in a capsule, returns a real ndarray, and drops the GIL around each compute segment via nanobind. Author-reported README table: 239.98 MB/s on the ndarray path vs 137.40 MB/s returning list[list[int]] for the same model and input — a 1.75x gap that is pure boundary tax. That bill applies to every Python extension tokenizer, whatever language hides underneath.

What my 2-core box says#

My box is a 2-core shared vCPU slice (EPYC 9354P); the author’s full -march=native comparison (his environment: i5-11260H, GCC 14.3.0, Python 3.13) is out of reach. What I could run is a single-threaded control: pip-installed tiktoken 0.14.0 (same version as the author’s), the repo’s own shakespeare.txt at 1,115,394 bytes, chunked per benchmark.py into 18 newline-aligned 64KiB blocks, RAYON_NUM_THREADS=1, median of 15 — 2.15 MB/s, roughly 5x under the author’s single-threaded tiktoken figure of 11.55 MB/s, about what a shared-core box should show. The harder reading: my run emitted 338,025 tokens, byte-identical to the tiktoken column in the author’s table — the denominators match across machines.

The limits are worth more than the numbers#

On the same corpus TokenBpe produces 331,572 tokens, about 1.9% fewer than tiktoken/HF’s 338,025 (author-reported) — the regex approximation in pre-tokenization showing up as a count. Fine as an accelerator; not a drop-in anywhere token counts are load-bearing: billing, training-data reproduction, prompt-cache keys. The author writes this into Known limitations himself. Also from reading the source line by line: one shared task slot in the pool (not reentrant), the threads parameter effectively ignored, and fragments over 22 bytes never touch the cache.

Frequently Asked Questions

Can TokenBpe replace tiktoken in my project?

No. Its pre-tokenizer approximates the GPT-2 regex, producing about 1.9% fewer tokens on the same corpus, and the id space is not aligned. Anywhere exact token counts matter — billing, cache keys, data reproduction — do not swap.

Where does the speed actually come from?

Three layers. Algorithmic: SWAR classification, direct-mapped cache, linked-list merge. Structural: dual-cursor ILP, a persistent worker pool. Boundary: capsule handoff, dropping the GIL. The boundary layer alone is worth 1.75x (author-reported).

How trustworthy is an author-written benchmark?

The methodology keeps its promises: newline-aligned 64KiB chunks, same vocab, roundtrip check before timing, median of 9, and the script is public. But the person who wrote the project also wrote the harness, and there is no external reproduction record. Read it as a lead, not a verdict.
