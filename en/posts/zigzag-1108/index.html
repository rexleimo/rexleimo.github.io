18 MB vs 871 MB: I Read the 18 MB Open-Source Mac Browser Before Arc Shuts Down

Zigzag：Swift+AppKit+WebKit 原生 Mac 浏览器，18 MB、Apache 2.0、自带广告拦截与 Chrome 扩展兼容。

November 8, 2026 · 6 min · 1277 words · Dream Beast -  |  中文

Arc is dead in six weeks. The browser that defined the “spaces + split view” feel on the Mac stops running December 22, and a week ago a Shanghai high-schooler open-sourced what I’m calling the cleanest answer yet: Zigzag, a Swift + AppKit + system-WebKit browser that installs at 18 MB (self-reported by the author in the launch post; the Arc on the same machine measured 871 MB). I read the full README and the 67-reply linux.do thread, and this is the breakdown: how the size works, how the extension bridge is built, what Arc users actually lose in migration, and three design patterns worth stealing for any local-first app.

The math: 18 MB vs 871 MB#

The size difference is not a trick. Zigzag ships no Chromium and no Electron; the engine is the WebKit that already ships with macOS. Each tab is a WKWebView; inactive tabs keep their snapshot and state and don’t reload when you return. The README puts the codebase at roughly 56,000 lines of Swift 6 and AppKit around the web view, with about 190 tests covering import, passwords, URL handling, history and security fixes.

What you give up by not shipping an engine: security fixes arrive with macOS updates instead of from you. That’s actually the point of the architecture — the app stays small because it never owns the part of the stack that needs the most auditing.

Repo status as of 2026-11-08: 27 stars, Apache-2.0 (GitHub API), beta, free. Apache-2.0 means you can fork and ship it commercially; the name, icon and logo are trademarks and a fork has to rename itself. The author’s one line: “It’s my everyday browser, but you’ll find bugs.”

The extension bridge is the real engineering#

The interesting 40% of this project is how Zigzag runs Chrome extensions on WebKit. WebKit’s WKWebExtensionController — the API that forces the macOS 15.4 or later minimum — lets Zigzag download a CRX3 package from the Chrome Web Store, verify its signatures, and load it. For every Chrome API that WebKit doesn’t have (history, bookmarks, downloads, notifications, side panels, offscreen pages, web sign-in, tab audio, new-tab pages, user scripts), Zigzag answers through its own small bridge, and it checks each call against the permissions the extension itself declared. 1Password connects through native messaging to its helper app.

The practical list, from the launch post and README: 1Password, Dark Reader, Shazam and most popular extensions work. One correction the author made in-thread: new Tampermonkey (MV3) currently installs but its scripts don’t run, because the userScripts API is Chrome-specific and WebKit doesn’t have it. The plan is to implement script injection in Zigzag itself — “not just make it look usable, but make the scripts actually inject and run” — and he asked the thread for its most-used scripts as test cases. If you depend on user scripts, wait for that version.

Data stays local. Spaces/pins/favorites live in Library.json, open tabs in Session.json, history in SQLite, all under ~/Library/Application Support/Zigzag; writes are debounced and atomic, and a file that can’t be read is set aside, never overwritten. Passwords are Keychain items (iCloud Keychain sync, Touch ID unlock, passkeys supported). Ad blocking is ~130,000 rules — EasyList, EasyPrivacy and EasyList China — pre-converted with SafariConverterLib into WebKit content rule lists, compiled once and cached; the lists update with Zigzag releases, not on their own.

The feel: spaces, split view, peek, all-tabs#

Import from Arc (File › Import from Another Browser) brings over spaces, pinned tabs, pinned folders, favorites, history and passwords; the pile of open tabs is deliberately left behind. Other import sources: Chrome, Safari, Dia, Edge, Brave, Vivaldi, Opera, Firefox, Zen.

The feature set that justifies the “Arc successor” label:

  • Spaces — each with its own color, pinned tabs and folders; switch by swiping the sidebar or nudging the mouse wheel sideways.
  • Split view — drag a tab onto the page and it opens beside you; pin a split and it stays one.
  • Peek — Shift-click a link to glance at it over the page you’re on.
  • All tabs (⇧⌘) — every space at once, filterable, and you can drag tabs between spaces.
  • Command bar (⌘T/⌘L) — finds open tabs, history and sites; type you, press Tab, you’re searching YouTube.

The privacy posture is harder than most browser defaults: no account, no analytics, no telemetry, and no dependency on the author’s servers. The only thing he hosts is the Sparkle 2 update feed (EdDSA-signed updates, Developer ID signed and notarized) — if it disappeared, the app keeps working. The README’s privacy section lists the only other self-initiated connections: the daily update check (version only), search suggestions (optional; Google, DuckDuckGo, Brave, Bing, Kagi, Ecosia), site icons, and at most a daily extension-update check.

The gap list — read before you migrate#

From the README’s “What’s missing” and the launch post:

  1. No sync between Macs or to iPhone. Passwords sync via iCloud Keychain; spaces and tabs don’t.
  2. No separate profiles — every space shares the same logins.
  3. No space emoji/icons yet, so Arc’s don’t come over; space colors import as the nearest Zigzag color.
  4. No Little Arc — links from other apps open as tabs in your window.
  5. No Boosts, Easels, Notes, or AI features.
  6. A few Chrome extension APIs are absent: tab groups, proxy and debugger settings, Chrome’s Google account sign-in (identity.getAuthToken), the old request-blocking webRequest.
  7. macOS 15.4+ only. Overall still beta.

Three signals from the 67 replies#

Worth quoting, all self-reported by the author in-thread:

  • iPad is plausible, and the reason is WebKit. Asked about an iPad version, he said he’s an iPad user, “iPad is also WebKit, so Zigzag’s path fits iPad too” — but the Mac version comes first, because after Dec 22 the window to replace Arc is real.
  • Who’s writing this. When asked whether it’s hand-crafted, he answered that most of the code was written with Claude Code but “isn’t AI slop”, and that he’s a real person — a high-school student in Shanghai — who has been running Zigzag as his main browser for several weeks and wrote the launch post from inside it. No Windows version exists: Swift, AppKit and system WebKit are all Mac-only, which would mean a rewrite.
  • The competitive bar. A thread user compared it to Search Browser, another WebKit-based option; the author’s take: Search had many stars but “felt off in use, so I just wrote one myself.”

What to steal, if you ship local-first software#

Zigzag is Swift, not Rust, but its product arithmetic transfers cleanly:

  1. Thin shell + system engine. Don’t ship the engine you don’t own: 56k lines for 18 MB, and the part of the stack that needs constant security attention is patched by the OS. The Rust-side equivalents (WebKitGTK, wry) obey the same math.
  2. Bridge the API gap; don’t wait for the engine. The extension bridge answers missing Chrome APIs itself and validates each call against the extension’s declared permissions — release cadence decouples from the kernel.
  3. Never overwrite bad data. Debounced atomic writes, unreadable files set aside. In an app that holds passwords and history, that property outweighs any performance line-item.

Arc’s Dec 22 shutdown removes a real cohort of “spaces + split view” users from the Mac. 27 stars on day one says the pickup is just starting. Beta plus single-maintainer is the risk; Apache-2.0 is the hedge — the code is out, so it can be carried forward even if the author isn’t.

Sources: linux.do t/3137690 (launch post + author replies, 2026-11-07); github.com/ZigaoWang/zigzag README (fetched 2026-11-08; stars and license via GitHub API the same day); zigzagbrowser.com. All quoted figures are as reported by the author or README; sizes were not independently reproduced.
