Google Used AI to Rewrite a C Library in Rust: 30M GIFs Later, It Was Immune Before the CVE Even Existed

Google's security team rewrote the 3,000-line C image library giflib in Rust with Gemini, keeping the business logic free of unsafe. Validation wasn't a test run: 30M+ GIFs in a full regression, 200M+ differential fuzz iterations, adversarial AI review, and expert sign-off on every unsafe block. The best footnote: the original C version later shipped an out-of-bounds heap write (CVE-2026-26740) that migrated services were structurally immune to — before anyone knew the CVE existed.

October 1, 2026 · 8 min · 1600 words · Dreambeast -  |  中文

The short version#

On August 24, Google Bug Hunters published an engineering post-mortem: Scaling Memory Safety: AI-Assisted Rewrites of C/C++ Dependencies to Rust External link . The authors, Bastian Kersting (software engineer) and Max Hils (security engineer), did something very concrete: they used Gemini to rewrite giflib, a 3,000-line C GIF library, into Rust — an ABI-compatible drop-in replacement deployed across Google’s own production infrastructure.

Three conclusions up front, all numbers from Google’s official blog (as of the Aug 24 publication):

  1. It works. A C library of ~3,000 lines with no SIMD/assembly and a stable interface can be translated in one shot. What follows is FFI-boundary iteration plus a differential-testing feedback loop — not prompt engineering folklore.
  2. Trust must be earned. Not from “AI wrote it,” but from 30M+ GIF regression runs, 200M+ differential fuzz iterations (6+ days side-by-side), adversarial AI review, and experts signing off on every unsafe block.
  3. The payoff is structural immunity. The original C giflib later got assigned an out-of-bounds heap write vulnerability (CVE-2026-26740); services already on the Rust version were immune. Google’s exact words: they didn’t know about the CVE while they were doing the work. Immunity was a side effect of the architecture, not a targeted patch.

Why giflib: the pilot wasn’t random#

The official reasoning is worth copying:

  • Memory-safety bugs account for roughly 70% of C/C++ vulnerabilities (Google’s own cited research data). Third-party libraries are especially exposed — they parse untrusted data, often in unsandboxed environments.
  • As LLMs get stronger, the window between a vulnerability’s discovery and its weaponization keeps shrinking — so fixing what you already run beats waiting for a new version.
  • giflib (by Eric S. Raymond) was an ideal target: ~3,000 lines, no SIMD/assembly, stable codebase. Clean complexity profile, fast to validate end-to-end.

Choosing the target is lesson one: the first AI rewrite shouldn’t be your most complex library. It should be something small enough to verify in one shot.

The pipeline: three steps#

Google’s post breaks the process into three:

Step 1: one-shot translation#

Small enough, Gemini translated the whole C codebase in one pass. This part isn’t the interesting one — the interesting parts are the next two.

Step 2: FFI boundary iteration (the counterintuitive part)#

This is the most important section of the whole post. Replacing a C library with Rust does not zero out your unsafe code: to stay ABI-compatible with existing C callers, the Rust side has to model the C API, and pointer lifetimes at that boundary are managed by hand. Google’s words:

We identified defects and an initially very unsound memory management pattern within the FFI boundary.

In plain terms: the AI’s first-pass FFI layer was itself unsound. They iterated prompts to fix the C-compatible wrapper, and every remaining unsafe block was expert-reviewed before it shipped.

The counterintuitive bit: people picture “AI writes Rust” as a risk of “wrong logic.” This post says the biggest risk lives at the language boundary — that’s where AI most easily writes code that looks right but leaks. Business logic: zero unsafe. Unsafe concentrated entirely in the FFI layer, guarded with safer_cffi.

Step 3: validation feedback loop#

Behavioral and logic defects found in differential testing get fed back to the model for targeted fixes. The AI doesn’t stop at “done” — it owns the “test → fix” loop.

Four validation gates, in order of strength#

This is the “can AI rewrites reach production” question, and Google’s stack:

GateWhat it didResult
1. Full regression30M+ real GIFs through the internal data pipeline, output diffed against the C versionbehavioral parity
2. Differential fuzzingC and Rust implementations fuzzed side-by-side, 6+ days, 200M+ iterationsno logic deviations
3. Adversarial AI reviewLLM prompts specifically hunting subtle behavioral differences between the two codebasescaught an LZW decoder edge case — and an out-of-bounds write that a Google-internal legacy patch had introduced into the original C source (fixed in the Rust version)
4. Expert sign-offevery unsafe block reviewed by humansjudged correct

Note gate 3’s byproduct: the validation pipeline didn’t just protect the new code — it also fixed an out-of-bounds write that Google’s own legacy patch had put into the original C version. That’s the difference between rewriting and patching: a patch fixes what you know about; a language change closes a whole class.

The best footnote: CVE-2026-26740#

Google titles the section “Real-World Efficacy.” What happened:

  • Shortly after rollout began, the original C giflib got an out-of-bounds heap write vulnerability, assigned CVE-2026-26740 External link .
  • Production services already on the Rust version were structurally immune.
  • Google’s exact words: “we didn’t know about the disclosure or the CVE while working on this.”

Read that slowly: they didn’t “find the zero-day, then patch the zero-day.” They closed off the zero-day’s room to exist — through an architectural change — while not knowing it existed. That’s the gap between secure-by-design and patching: patches chase vulnerabilities; architecture leaves them nowhere to run. Google adds one more line: future giflib memory-safety vulnerabilities are already out of reach for them.

Performance and architectural side effects#

Two things against the defaults:

  1. Performance-neutral. The “Rust adds bounds checks, so it’ll be slower” assumption didn’t hold up — monitoring across Google’s image-processing services confirmed parity, and they’ve observed neutral-or-better performance across many Rust replacements.
  2. Lower tail latency. The C version ran in unsandboxed environments and needed resource-heavy sandboxing to keep it in check; the Rust version let them delete that layer. Security simplification became a performance win — Google’s own framing: secure-by-design happened to align with a business goal (latency).

What you can lift from the repo#

google/giflib-rs External link is open source (MIT; I pulled it and cross-checked the README and Cargo.toml — every number matches):

  • Version 6.1.301: reads as “ported from giflib 6.1.x, patch component padded to two digits for giflib-rs’s own patch releases.” Edition 2024, deps: libc 0.2.186 + safer_cffi 0.2 (patched to Google’s fork), build-dep bindgen 0.72.1.
  • Zero unsafe in business logic (README’s words); unsafe exists only to “provide a C API and deal with pointers passed from C.”
  • The README explicitly recommends: if you don’t need ABI compatibility, just use the gif External link crate — “idiomatic Rust APIs, substantially faster.” Google drew the “don’t Rust just for Rust’s sake” line for you.
  • The repo is not an officially supported Google product and is not in the vulnerability rewards program — third-party maintained; mind that when citing.

Three known differentials (downstream, watch out)#

The README lists 3 places where behavior deliberately differs from C — all of them bug fixes:

  1. Error field on invalid dimensions: C’s DGifSlurp returns GIF_ERROR on bad dimensions (width/height ≤ 0, or overflow) but leaves GifFile->Error at 0. The Rust version sets D_GIF_ERR_DATA_TOO_BIG (108).
  2. Write return codes: C silently ignores write() failures and returns GIF_OK; Rust checks the return and errors out.
  3. OOM behavior: C returns an error code on allocation failure; Rust panics. Google notes: Linux overcommits by default and uses the OOM killer, so this is usually a non-issue in practice.

If your downstream code relies on the old behavior (e.g. a fallback that keys off “returned error but Error field still 0”), these three will bite you on migration. Another difference between rewrite and patch: a rewrite gets to fix bugs, but a bug fix is a behavior change for downstream.

FAQ#

Can we just trust AI-written Rust? No. The takeaway: AI handles “fast translation”; trust comes from four validation layers — full regression, differential fuzzing, adversarial review, expert unsafe sign-off. Skip one and it doesn’t ship.

My C dependency is small. Same play? Two preconditions: a differential behavioral baseline (real datasets or existing tests), and acceptance of deliberate behavior changes. No baseline and you can’t verify the translation.

Did the unsafe go to zero? Business logic: yes (0 lines). FFI boundary: no — you have to take C callers’ pointers, so it stays, guarded by safer_cffi plus human review. “The Rust version” doesn’t mean “no unsafe.” It means “unsafe is confined to a room with a fence.”

Who does CVE-2026-26740 hurt? Anyone still parsing untrusted input with the original C giflib. If you’re on giflib-rs, you’re immune. Check NVD for ratings (CVE page External link ); this post doesn’t rate or reproduce it independently.

Will performance drop? Official monitoring: neutral. Dropping the sandboxing layer actually cut tail latency. Run your own benchmarks before committing.

Frequently Asked Questions

Can AI-written Rust go straight to production?

Not raw. Google's validation stack has four layers: full regression on 30M+ GIFs (behavior parity), 200M+ differential fuzz iterations (C and Rust side-by-side, 6+ days), adversarial AI review (specifically hunting behavioral differences between the two codebases), and expert sign-off on every unsafe block. The AI does the translation and iteration; trust is earned with validation data plus human signatures.

Does the rewrite remove all vulnerabilities?

Not all, but it removes a whole class. giflib-rs has zero unsafe in the business logic; unsafe lives only at the FFI boundary (where C callers hand you pointers), guarded with safer_cffi. Out-of-bounds writes and use-after-free are architecturally blocked — which is exactly the class CVE-2026-26740 belongs to, an out-of-bounds heap write in the original C version that the Rust version is immune to.

Can I copy this for my own C dependencies?

Yes, with two preconditions: you need a differential behavioral baseline (real datasets, existing tests) or you can't verify the AI got it right; and you must accept deliberate behavior changes. giflib-rs's README lists 3 known differentials, all intentional bug fixes in the C code (error field not set, write failures ignored, OOM behavior). If downstream code depends on the old behavior, these will bite you. Also, the README says: if you don't need ABI compatibility, just use the gif crate — it's faster and more idiomatic.
