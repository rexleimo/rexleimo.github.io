Why Rust CLI Tools Feel Great: ripgrep Searches 100GB in ~10MB — and It Isn't a 'Rust Magic'

The 'ripgrep searches 100GB in 10MB' claim has no official source — I checked BurntSushi's blog, the biggest single-file benchmark is 13GB of subtitles. But the underlying principle is real, and I proved it: on a 2-core box, 256MB/1GB/4GB corpora, ripgrep's RSS barely moves (7MB flat) while a 'read everything into memory' implementation balloons to 4GB. The secret is bounded memory + streaming fixed buffers, not Rust speed. Full reproducible code open-sourced.

October 3, 2026 · 10 min · 2040 words · Dreambeast Programming -  |  中文

The “ripgrep searches 100GB in 10MB” line is everywhere in the tech world. Before writing this I went through BurntSushi’s ripgrep blog and README twice, hunting for that exact figure — I didn’t find it. His 2016 deep-dive caps out at a 13GB OpenSubtitles file (single) and the Linux kernel tree (multi-file). “100GB” is a marketing number that grew in the retelling.

But the principle underneath it — memory that doesn’t grow with data size — is documented right there in his blog (“Thou Shalt Not Search Line By Line”), and it’s reproducible with a minimal experiment. That’s the path I took: don’t memorize the number, verify the mechanism.

TL;DR#

I built 256MB / 1GB / 4GB corpora and ran ripgrep 14.1.0 on a 2-core box:

  • RSS doesn’t move: 6.9 → 7.3 → 7.8 MB as data grows 16x. A flat line.
  • The “read everything into memory” control balloons: 274MB → 1.0GB → 4.0GB. A 45° slope.
  • 5 mechanisms, each with a source: streaming fixed buffers, mmap being counterintuitively slower, SIMD literal extraction, finite-state-machine linear-time regex, lock-free work-stealing.
  • The takeaway for your CLI: bounded-buffer streaming is the line between “handles 100GB” and “handles 100MB” — and it has nothing to do with the language.

This machine is the same one from my last piece (Rust vs Go microservices): 2 cores / 7.8GB Linux, Ubuntu, ripgrep 14.1.0 via apt (GitHub is walled on this box; apt sources are enough).

I built 3-tier corpora: fixed seed, small is a prefix of large#

I didn’t reuse an existing dataset — I made one:

$ rg --version
ripgrep 14.1.0

$ python3 make-corpus.py /tmp/rgbench/c256 256
generated /tmp/rgbench/c256: 3913 files, ~256MB (seed=20261003)

$ python3 make-corpus.py /tmp/rgbench/c1g 1024
generated /tmp/rgbench/c1g: 15651 files, ~1GB (seed=20261003)

$ python3 make-corpus.py /tmp/rgbench/c4g 4096
generated /tmp/rgbench/c4g: 62609 files, ~4GB (seed=20261003)

One third of the files carry the same literal needle_foo42. The fixed seed means the 256MB tier is a byte-prefix of the 1GB tier — the hit distribution on the small set sits entirely inside the large one, so there’s no “the corpus changed version and memory inflated” confound. That’s the most important property of this corpus: data size is additive.

Why plant a literal? Because when ripgrep searches a literal it doesn’t run the full regex engine at all (next section) — that’s its fastest, most “production CLI”-shaped path.

The thing under test + 2 controls#

# under test: warm up once (page cache hot), then measure
$ rg needle_foo42 /tmp/rgbench/c256 > /dev/null   # warmup
$ /usr/bin/time -v rg needle_foo42 /tmp/rgbench/c256 2> /tmp/t.txt
$ grep -E 'Elapsed|Maximum resident' /tmp/t.txt
        0.07s    # 1305 files hit
       6.9MB

# control A: naive single-threaded Python search (streaming, no optimization)
$ /usr/bin/time -v python3 py-baseline.py /tmp/rgbench/c256 needle_foo42
        1.56s    # 1305 hits
       12.0MB

# control B: read ALL files into memory, then process (the key counter-proof)
$ /usr/bin/time -v python3 py-loadall.py /tmp/rgbench/c256
        0.22s
      274MB      # note: 7x faster than A, but 23x the RSS

Control B’s output is the linchpin — it beats A on timing by 7x (after reading it all, the lookup is an in-memory scan, much faster than line-by-line I/O), but RSS jumps 23x. That’s the thing I wanted to amplify at the 4GB tier.

The data: rg is a flat line, control B is a 45° slope#

Data size ×16 (256MB→4GB), ripgrep’s peak RSS 6.9→7.3→7.8MB — a flat line. That’s the most direct reproducible proof of “bounded memory”: all three points land back near 7MB on a local re-run.

Timing is a separate story (the 4GB tier’s 26s is mostly I/O reading from disk; I separate that out next section).

Same corpus, two Python styles:

  • Stream (control A): RSS steady at 12MB, time 1.6s→3.7s→46s (I/O-bound). “Bounded but slow.”
  • Read-all (control B): RSS follows data size, 274MB→1.0GB→4.0GB. “Fast but unbounded.”

ripgrep gets both: bounded RSS (7MB flat) AND not slow (4GB in 26s, still faster than A). Why? — the five mechanisms below.

One chart nails “bounded vs unbounded”#

Left panel: data size ×16, rg’s RSS holds near 7MB; right panel: same data size, the “read-all” implementation’s RSS climbs to 4GB. This is what “10MB searches 100GB” is actually saying: ripgrep’s memory is independent of total data size, so extrapolating to 100GB is still just a few MB.

Extrapolate control B’s slope to a 100GB corpus: 100GB of data → read-all needs ~100GB of memory, while rg stays around 7MB. That’s math, not marketing.

Why it’s fast: five mechanisms, each sourced#

ripgrep’s speed isn’t “Rust is fast.” Of these five, only one is strongly language-dependent (compile-time borrows); the other four you can copy in any language:

1. Streaming fixed buffer (the “Mechanics” section)#

BurntSushi’s blog: “Thou Shalt Not Search Line By Line… Instead, search over the contents of an in-memory byte buffer of a fixed size.”

ripgrep doesn’t mmap the whole file, doesn’t read it all into memory — it searches over a fixed-size intermediate buffer incrementally. That’s where the 7MB flat line in section 3 comes from — bounded buffer, bounded RSS. The first rule for any CLI that emits a lot of data: never read all the data into memory first.

2. mmap is actually slower (the “Counterintuitive” section)#

In the same linux_literal benchmark, rg(mmap) 1.611s vs rg(ignore) 0.334s — mmap is 4.8x slower. Intuition says “mapping uses no physical memory” is a plus, but for multi-file search the virtual-memory page-fault overhead isn’t worth it; rg disables mmap and takes the I/O path. The bigger the data, the less you can lean on mmap to save you.

3. SIMD literal extraction (the “Literal optimizations” section)#

When ripgrep calls the regex library, the library auto-extracts literals from the pattern and uses memchr (compiled to SIMD, 16 bytes at a time) to find candidates first, running the full regex engine only on candidate lines. Searching a fixed string like needle_foo42, the regex engine barely participates — so literal search is an order of magnitude faster than “generic regex.” That’s why ripgrep is fastest in production scenarios (searching fixed symbols, IDs, error codes).

4. Finite state machine, linear time (the “Regex engine” section)#

ripgrep uses the Rust regex library (RE2-based finite automata), linear time on any input, with no PCRE-style exponential backtracking on patterns like (a*)*c. His blog cites an example where the old Silver Searcher gets hammered by such a pattern and ripgrep doesn’t have that failure mode. This is a language-agnostic correctness guarantee — it has nothing to do with Rust directly, just that the Rust regex library happens to do it well.

5. Lock-free work-stealing (the “Gathering files” section)#

ripgrep dispatches work to its worker pool with a Chase-Lev lock-free deque (kinghajj/deque); other tools (grep, old ag) use mutex queues. On my 2-core box: -j1 (forced single-thread) on 4GB takes 64.2s, default 2-thread takes 26.3s — ~2.4x gain with no lock-tax. This is where “Rust’s dividend” starts to show: the borrow checker makes it hard to write the Vec::extend(entire_corpus) disaster code. Rust’s value at points 1 and 5 is rejecting unbounded buffers at compile time, not “runs faster than C.”

In one line: every fraction of the speed has a source, and not one fraction comes from the word “Rust.”

What to copy for your CLI#

  • Bounded-buffer streaming; never read all the data into memory first — that’s the line between “handles 100GB” and “handles 100MB,” language-independent (1)
  • Literal first, regex second — if most of your searches are fixed strings, copy ripgrep’s literal-skip path (3); biggest win
  • mmap is not the default answer — big data ≠ “map it”; look at the access pattern first (2)
  • Rust’s value is in compile-time guarantees like (1) and (5), not the three words “runs fast” — my last piece measured Rust vs Go and debunked “3x faster latency”; this one pins “fast” down on the memory model

Three pits I actually fell into (honesty)#

Python’s first run timed out, re-run was 13x faster. On the 4GB tier my first version of the script didn’t warm up, Python single-threaded first run timed out at 300s without finishing; I assumed Python was just too slow. Re-running: 46s. The first version was the compound effect of cold page cache + no warmup. This was the biggest pitfall in writing the “control group”: if the baseline you give the control is unfair (different cache state), the whole comparison is invalid. So in the checklist I warm up once per tier, page cache hot, and list both the hot and cold values for the 1GB tier (3.69s vs 29.5s, same corpus).

Python read-all on 4GB needed 4.6GB memory, nearly OOM’d this box. 7.8G machine; running the 4GB corpus “read-all” hit 4.0GB RSS, plus the Python interpreter’s own ~30-50MB, didn’t crash but was already pressing the memory ceiling. An 8GB corpus would OOM. That’s the real cost of the “read-all” implementation — it’s not just “slow,” it’s “on an 8GB machine you can’t even run it.”

2-core box: read the trend, not the absolute value. rg’s 4GB 26s is mostly I/O (reading 4GB from disk), not slow CPU. My 2-core -j1 64s vs default 26s is ~2.4x, matching the 2-core theoretical ceiling. An 8-core box’s absolute timings are completely different, but the RSS column (7MB flat) doesn’t change — that’s what this article pins down.

Honest disclosure#

  • “10MB searches 100GB” was not reproduced (no 100GB corpus on this box), and I found no official exact source (BurntSushi’s blog tops out at 13GB of subtitles); what this article measured is the principle — bounded memory (4GB tier RSS 7.8MB flat), and the 100GB extrapolation is a principle, not a measured number.
  • 2-core box; absolute timings don’t represent multi-core production; the 4GB tier’s rg 26s wall is mostly I/O, not CPU.
  • The corpus is fixed-seed synthetic text (random English words, not a real codebase); the 1/3 hit rate is deliberate — real search hit rates are usually lower (more favorable to rg), untested.
  • Repro material all open-sourced: bench/cli/ (make-corpus.py, py-baseline.py, py-loadall.py, run-cli-bench.sh, results/numbers.md), one command to run.

FAQ#

Q: Why is ripgrep’s literal search an order of magnitude faster than generic regex? A: The regex library auto-extracts literals (Teddy128/Aho-Corasick) and uses SIMD memchr to find candidates first, running the full regex engine only on candidate lines. For fixed strings the engine barely participates, so it’s an order of magnitude faster.

Q: Isn’t mmap faster? Why doesn’t ripgrep default to mmap? A: For “scan the whole file linearly” access, mmap’s page-fault overhead isn’t worth it. Same benchmark: rg(mmap) 1.611s vs rg(default) 0.334s — mmap is 4.8x slower.

Q: I tested on 2 cores. Does the conclusion change on multi-core? A: Timings change (I/O + CPU), but the RSS column doesn’t — the 7MB flat is core-count independent. This article pins down “does RSS grow with data size,” not “how fast.”

Q: Python streaming is also 12MB flat — so “bounded” is language-independent? A: Yes. “Bounded RSS” is doable in Python too (12MB flat) — it’s just slow, not unbounded. ripgrep gets bounded + not-slow (SIMD + parallelism + literal-skip), stacked from (1)(3)(5).

Q: What memory for 100GB actually? How do I verify myself? A: Run this article’s make-corpus.py with python3 make-corpus.py /tmp/rgbench/c100g 100*1024 (needs ~100G disk), then rg needle_foo42 /tmp/rgbench/c100g; RSS should still be 7-8MB. I couldn’t run it on this box, but the principle is verifiable.

Frequently Asked Questions

Can ripgrep really search 100GB in 10MB?

The exact '10MB for 100GB' figure has no official source I could find (BurntSushi's blog tops out at 13GB of subtitles). It's a marketing claim that grew in the retelling. But 'bounded memory' is real — I measured it with 256MB/1GB/4GB corpora: rg's RSS goes 6.9→7.3→7.8MB, essentially flat. Extrapolating to 100GB is a principle, not a measured number.

What's actually Rust about it?

Of the 5 mechanisms that make ripgrep fast, only one is strongly language-dependent (the borrow checker makes it hard to write the 'read everything' disaster code). The other four — streaming fixed buffers, mmap being slower, SIMD literals, lock-free parallelism — work in any language. Rust's value is in constraints, not 'it's fast'.

Isn't mmap faster?

For whole-file linear scanning, mmap's page-fault overhead isn't worth it. BurntSushi's own benchmark: rg(mmap) 1.611s vs rg(default) 0.334s — mmap is 4.8x slower. The bigger the data, the more you can't rely on mmap to save you.

Python streaming search is also 12MB flat, right?

Yes. 'Bounded RSS' is achievable in Python too (12MB flat) — it's just slow (46s vs rg's 26s on 4GB). ripgrep gets both bounded AND fast via SIMD + parallelism + literal-skip. That's what the 5 mechanisms add up to.

I tested on 2 cores. Does the conclusion change on multi-core?

Timings will change (I/O + CPU), but the RSS column (7MB flat) doesn't — it's independent of core count. This article pins down whether RSS grows with data size, not how fast it runs.
