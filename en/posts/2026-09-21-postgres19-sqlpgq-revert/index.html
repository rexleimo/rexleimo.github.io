Postgres 19's Graph Queries Were Reverted Four Days Before Release

SQL/PGQ shipped in the PostgreSQL 19 betas and was reverted four days after the article everyone was sharing ran it against a Neo4j workload. I followed the commit and the mailing list thread, and here is what survived.

September 21, 2026 · 12 min · 2361 words · Mengshou Coding -  |  中文

On the evening of September 3, Peter Eisentraut replied to a mailing list post. The body of his message was three words:

Ok, let’s do it.

What he agreed to remove was the headline feature of PostgreSQL 19 — SQL Property Graph Queries. Four days later the revert landed: b1f106c80cbeb18d3a0219994d98a51a6eca8ede, 2026-09-07 19:51 (UTC+2), same author, more than fifty commits and 124 files wiped in one go.

And on the very day he typed those three words, an article was making the rounds on Medium. Its title was satisfying in the way a bar fight is satisfying: Postgres 19 Adds Graph Queries. I Ran Our Neo4j Workload Against It. The author pulled a production copy onto a spare box and pointed four Cypher queries at it. Verdict: Postgres wins at one and two hops, Neo4j wins at three, and on the fourth query — the variable-length one — Postgres simply declined.

The article is real. The testing was probably real too. The thing it tested stopped existing four days later.

This is not a piece about laughing at anyone. It is about the fact that the valuable part of this story has nothing to do with whether Postgres has graph queries.

First, what exactly was reverted#

The timeline, all of it checkable:

DateEvent
2026-03-16Eisentraut commits 2f094e7a; SQL/PGQ enters main, +14888 −72, 122 files
2026-08-13PostgreSQL 19 Beta 3 ships; the manual gives Property Graphs a chapter of its own
2026-08-22Andres Freund questions the catalog representation; the thread opens
2026-09-02 19:29Melanie Plageman, RMT hat on, recommends a revert
2026-09-03 20:53Eisentraut: Ok, let’s do it
2026-09-07 19:51revert commit b1f106c8 lands

Beta 3 to revert was two weeks. Which means: any syntax you copied from a “getting started with graph queries in Postgres 19” tutorial does not exist in the release. The Release date field in the official release notes still reads 2026-??-??. Neon’s documentation now carries a banner at the top saying SQL/PGQ was reverted from PostgreSQL 19 and the earliest it could return is PostgreSQL 20.

Nobody in that article’s comments appears to have warned the author. Its publication date and the decision to revert were the same day.

What SQL/PGQ actually was#

Start with the technology, because it is worth understanding even reverted.

The PostgreSQL 19 manual has one sentence that settles what this is, and it deserves to be read slowly:

PostgreSQL implements SQL/PGQ … where a property graph is defined as a kind of read-only view over relational tables. So the actual data is still in tables or table-like objects, but is exposed as a graph for graph querying operations.

In plain terms: no graph storage engine, no adjacency lists, not one copied row. You layer a metadata declaration over tables you already have, declare that it is a graph, and query it with syntax close to Cypher.

CREATE PROPERTY GRAPH social
  VERTEX TABLES (
    users KEY (id) LABEL person PROPERTIES (id, name)
  )
  EDGE TABLES (
    follows KEY (id)
      SOURCE KEY (src) REFERENCES users (id)
      DESTINATION KEY (dst) REFERENCES users (id)
      LABEL knows
  );

And then:

SELECT * FROM GRAPH_TABLE (social
  MATCH (a IS person WHERE a.id = 42)-[IS knows]->(b IS person)
  COLUMNS (b.id, b.name)
);

CREATE PROPERTY GRAPH is pure metadata. DROP PROPERTY GRAPH removes the definition and leaves the tables alone. Eisentraut’s commit message put it more bluntly: a property graph is a new relkind, RELKIND_PROPGRAPH, and “It acts like a view in many ways. It is rewritten to a standard relational query in the rewriter.”

That one sentence is the key to every performance number and every bug that followed.

Why it was fast, and why it was slow#

CYBERTEC’s Julian Markwort ran a real verification in July, and his findings line up with what the Medium author observed: GRAPH_TABLE is a parser-level rewriter. Your arrow syntax is flattened into ordinary joins before the planner ever sees it.

One hop is a three-way join. Two hops is five. Three is seven. The shape grows mechanically, and the cost model is the one you already had.

EXPLAIN (COSTS OFF) comes out like this:

QUERY PLAN
 Hash Join
   Hash Cond: (big_knows.b = big_person_1.id)
   -> Hash Join
        Hash Cond: (big_knows.a = big_person.id)
        -> Seq Scan on big_knows
        -> Hash
             -> Seq Scan on big_person
   -> Hash
        -> Seq Scan on big_person big_person_1

Layer for layer, identical to the join tree he wrote by hand:

SELECT a.name, b.name
FROM big_knows k
JOIN big_person a ON a.id = k.a
JOIN big_person b ON b.id = k.b;

The same planner, the same statistics, the same indexes, the same EXPLAIN. There is no graph-specific execution node hiding anything. That is the structural advantage over a standalone graph database: backups, replication, row-level security, monitoring, permissions — not one new moving part.

The cost comes from the same place. The section the Medium author titled “The Part Where I Looked Foolish” is the most valuable thing in his piece, and it is worth quoting at length:

His first reverse traversal — “who follows 42” — took 340 milliseconds, and he nearly closed the terminal and declared Postgres unfit. The plan showed a sequential scan across all 38 million edges. The reason was mundane: their edge table had an index on the source column and nothing on the destination, because Neo4j traverses both directions for free and the team had never had to think about it. One CREATE INDEX ON follows (dst); later: 6 milliseconds.

His conclusion is the line I keep coming back to:

The graph database had been quietly covering for a gap in our schema for years, and I’d been calling it magic.

CYBERTEC has the clean version of the same finding: 6 edges out of 60,000 rows, found by a sequential scan. Add the index on (b) and it goes from 3.1 ms to 0.16 ms, buffer hits from 287 to 29.

So the rule is the one you already knew: if you filter on it, index it. Graph traversal just follows one column to find edges. Forward traversal lives on the primary key; reverse traversal lives on a second index. Nothing new to learn.

What it genuinely did not do#

The Beta implementation covered a useful slice of the standard, with three categories explicitly absent.

Variable-length paths. Neither -[IS knows]->+ nor -[IS knows]->{1,4} worked. Every hop had to be written by hand. To express “the depth is a variable, not a number I typed”, GRAPH_TABLE had no way to say it.

That is where the Medium article fell over: the fourth query, MATCH (a:Person {id: 42})-[:KNOWS*1..4]->(b:Person) RETURN DISTINCT b.name. The fallback is the thing everyone wrote before graph databases existed:

WITH RECURSIVE walk AS (
  SELECT dst AS id, 1 AS d FROM follows WHERE src = 42
  UNION
  SELECT f.dst, w.d + 1
  FROM walk w JOIN follows f ON f.src = w.id
  WHERE w.d < 4
)
SELECT DISTINCT id FROM walk;

It works. It is not elegant.

Shortest path. ANY SHORTEST and ALL SHORTEST were unimplemented; WITH RECURSIVE plus ORDER BY depth LIMIT 1 was the realistic substitute.

Multiple patterns in one MATCH. Comma-separated patterns were unsupported; you split into two GRAPH_TABLE invocations and joined on vertex IDs. Edge isomorphism was not enforced by default either — without WHERE a.id <> b.id the same edge could match twice.

There is a layer people skip, too: standard conformance. Someone counted PostgreSQL 19’s Appendix D feature by feature. Of the 100 SQL/PGQ features, 26 were implemented. Of the 27 supported features that 19 added over 18, 26 came from SQL/PGQ — the other was the null-treatment option for LEAD and LAG, alone in its corner. Among the 74 outstanding are the path modes TRAIL, SIMPLE and ACYCLIC; without them you cannot require a path to avoid repeating vertices or edges.

Put differently: 19 got the reading entrance to graph queries, not graph query capability.

What actually killed it#

Only now does the reason for the revert surface, and it has nothing to do with benchmarks.

In her 2026-09-02 mail, Melanie Plageman of the RMT — the PostgreSQL release management team — laid out three design problems. Her words, translated:

Orphaned metadata. An external DROP TABLE ... CASCADE leaves orphaned label and property metadata behind. It shows up as phantom entries in information_schema views, causes later legitimate ALTER PROPERTY GRAPH statements to fail, and can render a graph undumpable and unrestorable. A patch on September 1 tried to fix it and was judged a stop-gap; the real fix was “out-of-scope for 19”.

Scoping granularity. When a property or label is dropped from one element of a graph but still exists elsewhere in that graph, any view built on GRAPH_TABLE becomes silently unqueryable. There is no posted fix, and the correct behaviour itself is waiting on an interpretation of the standard — including the basic question of what to do when a function is shared across two labels.

Whether there should be a pg_class entry. Andres Freund’s original concern was never confirmed resolved. And the bug Andrew Dunstan reported — AlterPropGraph() not verifying that its target is actually a property graph — suggests more code out there reading pg_class entries without distinguishing graphs from tables.

Plus a run of dependency-ordering problems with no proposed fix, such as the pg_dump dependency loop when a materialized view queries a GRAPH_TABLE.

Plageman’s landing was restrained and hard at once:

We are most concerned that there are several reported issues that pose design and behaviour questions that the community and patch authors have yet to resolve. If any desired behaviour is still unsettled, there is insufficient time to fix these in time for the release.

Eisentraut answered with those three words. His reasoning was stated elsewhere too: revert it, take the time pressure off, fix these things properly in 20, without the burden of backwards compatibility and backporting.

The feature was not cut because it lost a benchmark. Its metadata semantics could not be pinned down, and the project would rather not ship it.

So what now#

If you are stuck on “should we migrate to PG 19 for graph queries”, the answer is no — it is not there. But if your actual pain is “I do not want to maintain a Neo4j for four queries”, there are still paths:

  • Wait for PG 20 (Neon puts it at September 2027). This revert arguably makes a complete landing more likely.
  • Apache AGE. Cypher syntax as a PostgreSQL extension, with variable-length paths long since supported; the cost is extension storage and limited SQL interop.
  • Keep Neo4j or Memgraph, and add the index on the destination column of your edge table. That is the single most practical legacy of the Medium article, and it is independent of which database you run.
  • Fixed-depth traversals — friends of friends, two levels of dependencies, my friend’s employer — are what you write WITH RECURSIVE for anyway, and PG 19 coming or not changes nothing.

The judgement worth taking away#

I have no quarrel with that Medium article. It had real data, a real EXPLAIN, and a self-correction embarrassing enough to be credible. It is better than nine out of ten “new feature explainers”.

But it was written on September 3, against Beta 2. A reader copying it today gets syntax error at or near "PROPERTY".

That is not the author’s fault. It is a question about how technical articles get read. Three steps, and this is what writing this piece left me with:

  1. Check the baseline version first. Is the article based on Beta 1, Beta 2, or a GA release? If it does not say, assume the oldest. A dated version number is where freshness starts.
  2. Search the git log for the feature name. Not “new features” in the release notes — search for “revert”, “remove”, “not shipped”. One gitweb commit takes a minute and beats ten second-hand explainers. Searching b1f106c8 was enough to settle this one.
  3. When they disagree, trust the official source. The documentation’s version switcher moves between 19, devel and 18 — if a tutorial’s syntax cannot be found in the docs for your current version, then it describes something that does not exist.

“Postgres 19 has graph queries” was true in March 2026, when the code entered main. It was still true on September 3, the day an article was recommending it and its own author agreed to undo it. After September 7 it was false.

Nobody announced that it had become false. It was just reverted.

Three questions#

One, pick a side. If you are sitting on a “a Neo4j cluster held up by four queries” situation right now, which path do you take: wait for PG 20, move to Apache AGE, or keep Neo4j and fix the indexes? I lean at the last one — it does not bet on anyone’s release schedule.

Two, data collection. Are your relationship tables indexed on the source column only? My guess is a lot of you are. Report your edge-table index situation in the comments (for example “just the (src, dst) primary key”) — I want to know whether this is individual oversight or a systematic blind spot.

Three, a profile. If you have a colleague who configured a three-year-old solution from a three-year-old tutorial, forward this to them. No comment needed; they will work it out.
