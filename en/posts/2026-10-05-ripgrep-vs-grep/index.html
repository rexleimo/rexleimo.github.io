'Ripgrep Is Faster Than Grep' — I Fed It 4GB and the First Finding Is That You Can't Measure a Ratio on This Machine

'rg is 3x faster than grep' isn't stably measurable on a shared 2-core EPYC: one grep -rc pass over 3.4GB read 0.01s / 2.85s / 4.05s across three of my sessions — a 40x spread. The two layers that DO pin down: single-file hot, grep 0.003s beats rg 0.011s (rg's fixed startup cost, 3.7x), and rg by default searches 55 of 106 files in a mixed directory (byte count 1.17MB vs 12.8MB, an 11x less).

October 5, 2026 · 6 min · 1078 words · Dreambeast -  |  中文

The most stable folklore in command-line circles: “ripgrep beats grep.” I fed 4GB of corpus to both on my 2-core EPYC, and the first finding wasn’t who wins by how much — it’s that “how much” isn’t measurable on this machine at all. One grep -rc pass over the same 3.4GB corpus, three different sessions: 0.01s / 2.85s / 4.05s — a 40x spread, every run hit-count-verified, load recorded before each. On a shared 2-core slice with non-exclusive I/O bandwidth, “rg is X times faster” is only a quantity on an exclusive machine under fixed load. Everywhere else it’s a distribution.

So this piece covers the two layers that DO pin down, with full commands: ① single-file hot fixed cost — grep 0.003s vs rg 0.011s; rg’s startup tax (regex compilation + directory walker + thread pool) is a 3.7x gap on small work, 5-round median, hit-count verified, run in one session; ② “searches less” — count files, don’t time: in a mixed directory rg’s default passes 55 files, all-filters-off 106; byte count 1.17MB vs 12.8MB, an 11x.

Nailing down “you can’t measure it”: one cell, three sessions, a 40x spread#

Same machine, same corpus (3.4GB / 100 files of 34MB), same command, hit-count verified (3,000 lines each time), load recorded:

sessionloadgrep -rcstate
22:470.14 (quietest)2.85shot cache, idle
23:100.474.05shot cache, busier
next dayelevated0.01sflagged as “impossible” and re-checked 3x at the time

All three ran against a warm page cache with identical hit counts; the only variable was what else was using this shared slice. That 0.01s would imply 340GB/s of read bandwidth — this box’s I/O ceiling doesn’t reach there; most likely the I/O scheduler took a cache-bypass/lost-reads path on that run (I verified hit counts, not byte-level reads, that time). The one conclusion that survives: on this machine, I/O-bandwidth-class timings are unreliable in absolute value, and any “X times faster” flips with load.

This isn’t a disclaimer — it directly overrules my first draft of this piece (written that morning): “grep wins on small files by 2.8x, rg wins on large files by 3.3x.” Those numbers were hot-cache, specific-load measurements that don’t survive a session boundary. Re-measured in a quiet session, the small-file cell went the other way (rg single-core ~10x ahead of grep). A ratio is only a quantity on an exclusive machine under fixed load; everywhere else it’s a distribution. That sentence belongs in your muscle memory more than any “rg is X times faster.”

The layer that DOES pin down #1: single-file hot — rg carries a 3.7x fixed startup cost#

One 34MB file, hot cache, 5 rounds, hit-count verified (30 hits per file):

# corpus: data/corpus-big/big000.log (34MB, needle-7f3a9c hits 30 lines)
$ grep -c needle-7f3a9c data/corpus-big/big000.log   # 0.003s (5 rounds: 0.0034/0.0035/0.0035/0.0044/0.0039)
$ rg -c needle-7f3a9c data/corpus-big/big000.log      # 0.011s (5 rounds: 0.0054→0.013 range, median 0.011)
$ rg -j1 -c needle-7f3a9c data/corpus-big/big000.log  # 0.010s (forced single core — nearly identical to default)

Part of rg’s time is content-independent fixed cost: compiling the regex, starting the directory walker, initializing the thread pool, wiring the result plumbing. The 34MB scan itself is close between the two; rg’s ~8ms startup tax is a 3.7x gap on single-file small work. rg -j1 matching the default tier almost exactly says the pool had nothing to divide — tax still paid.

This is the most stable number in the piece: single file, hot, hit-count checked, 5 rounds in one session — I/O volume too small for the scheduler to have anything to say, <15% round-to-round variance.

The layer that DOES pin down #2: searches less — count files, don’t time#

rg’s actual design selling point is default behavior: binary detection via NUL-byte probe skips binaries, skips .gitignore, skips dotfiles. The advantage lives in searching less, not searching faster. And “searches less” has a measurement that carries zero I/O noise: count files, don’t time.

# mixed directory: 50 regular files + 5x 10MB binaries + 20 hidden + 30 .gitignored
$ rg --files data/mixed | wc -l                               # 55 (default)
$ rg --no-ignore --hidden --binary --files data/mixed | wc -l  # 106 (all filters off)
$ du -sb data/mixed/src data/mixed/assets \
        data/mixed/.hidden* data/mixed/node_modules
# src 1.17MB / assets 10MB / hidden 478KB / node_modules 1.17MB; directory total 12.8MB

rg’s default pass touches 1.17MB; all-filters-off touches 12.8MB — an 11x. grep -r behaves like “all filters off” (no binary skip, no dotfile skip, doesn’t read .gitignore) and would match that 10MB of binary byte-by-byte. No timing anywhere in this layer: --files to count, du for bytes. Zero I/O-scheduler dependence — the only layer in this piece whose conclusion holds on an exclusive or a shared machine.

So which layer of “rg is fast” should you believe#

  • “Faster on a single file” — not here; grep’s 0.003s beats rg’s 0.011s (startup tax). rg’s win on large-file pools is the parallel-throughput layer, which needs an exclusive multi-core machine to measure credibly. On this 2-core slice I state it plainly: no number, because the ratio is not a quantity here.
  • “Less memory” — measured: rg peaks at 9.7MB RSS scanning 3.95GB and 6.7MB scanning 3.4GB. RSS doesn’t grow with corpus size (streaming, file-by-file) — that’s the mechanism behind the “10MB searches 100GB” folklore. The 100GB extrapolation wasn’t done locally; only the mechanism was verified.
  • “Searches less” — holds and is reproducible: an 11x in byte count, verifiable by counting files and du, independent of machine load.

The most useful sentence in this piece, methodology-level: before running a perf test, separate which conclusions are layout invariants (file counts, byte totals, RSS order of magnitude) from load-sensitive quantities (absolute wall-time under I/O bandwidth). The former you can publish from a shared box; the latter only from an exclusive one. My morning draft treated a load-sensitive quantity as an invariant and published it; the afternoon re-measure overturned it. The overturning is worth more than the conclusion.

Forward this to the colleague who opens with “rg is 3x faster than grep, ship it” — first ask what else was running on the box when they measured that. Follow “Dreambeast”: the Mold 3.0 piece split “a Rust rewrite is faster” into speed (flat) and safety (reproducible segfault→fatal) on this same box; this piece splits “rg is fast” into startup tax, parallel throughput, and searches-less. Two of the three layers measure stably here — both get full commands. The one that doesn’t gets a written explanation of why there’s no number.

Frequently Asked Questions

So how much faster is ripgrep than grep?

Not credibly measurable on a shared 2-core box — the same 3.4GB grep pass read 0.01s / 2.85s / 4.05s across three sessions, a 40x spread. What DOES pin down: single-file hot, grep's 0.003s beats rg's 0.011s (rg's fixed startup cost, 3.7x); and rg by default searches 55 of 106 files in a mixed directory (byte count 1.17MB vs 12.8MB, an 11x less).

Where does rg's edge actually live?

In 'searches less': default binary detection (NUL-byte probe), .gitignore, and hidden-file skipping. Verify it by counting files (rg --files | wc -l) and du — no timing, no I/O load dependency. The 'parallel, faster on big-file pools' layer needs an exclusive multi-core machine to measure; stated as not done here.

How do I reproduce your conclusions?

Don't reproduce the ratios (load-sensitive). Reproduce the two stable layers: single-file hot timing (5-round median + hit-count check) and rg --files | wc -l (no timing). Full commands in the post.
