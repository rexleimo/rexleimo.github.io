Why ripgrep Is Fast: 4GB Local Corpus A/B — The Verdict Isn't What You Think

ripgrep 14.1.0 vs GNU grep 3.11 on a 2-core EPYC with 3.95GB of corpus. Counter-intuitive: on 10,000 small files grep wins by 2.8x; on 100 files of 34MB rg wins by 3.3x — same machine, same phrase, the winner flips with file layout. '10MB memory searches 100GB' verified as mechanism, not literal: rg peaks at 9.7MB RSS scanning 3.95GB.

October 5, 2026 · 7 min · 1406 words · Dreambeast -  |  中文

I fed 4GB of corpus to ripgrep and to grep — grep won. The verdict is counter-intuitive but stably reproducible (2-core EPYC, hot state, 3-round median each): on a small-file corpus (3.95GB / 10,000 files, ~400KB each) grep -rc takes 0.28s versus rg’s default 0.77s — grep is 2.8x faster; on a large-file corpus (3.4GB / 100 files, 34MB each) rg’s default 0.56s beats grep -rc’s 1.84s — rg is 3.3x faster. Same machine, same pattern, the same 4GB of data: change the file layout and the winner flips. “ripgrep beats grep” is, like “Rust beats C++”, an assertion with its preconditions elided. What rg wins on is never “per-file throughput” — it’s a scheduling policy: it only parallelizes when there are enough files to amortize the scheduler’s fixed overhead, and it only batches-scan with SIMD when files are big enough. When files are few and fragmented, that scheduler layer is a tax.

This article covers four things: ① the full local numbers on two 4GB corpora — small files favor grep, large files favor rg; ② “10MB of memory searches 100GB” verified as mechanism, not literal; ③ where the speed lives, in three layers (parallel scheduling / single-threaded throughput / searching less by default), each with local evidence; ④ three stated boundaries. Machine: AMD EPYC 9354P 2-core slice, ripgrep 14.1.0 / GNU grep 3.11, measured 2026-10-05, every number reproducible with the commands shown.

I fed 4GB of corpus to ripgrep and grep — grep won#

Two corpora, same machine, same pattern (needle-7f3a9c, 10,000 / 3,000 matching lines):

# Small-file corpus: 3.95GB / 10,000 files (~400KB each)
$ rg -c needle-7f3a9c data/corpus      # 0.77s (hot-state median)
$ rg -j1 -c needle-7f3a9c data/corpus  # 1.06s (forced single core)
$ grep -rc needle-7f3a9c data/corpus   # 0.28s (grep wins by 2.8x)

# Large-file corpus: 3.4GB / 100 files (34MB each)
$ rg -c needle-7f3a9c data/corpus-big  # 0.56s (rg wins by 3.3x)
$ rg -j1 -c needle-7f3a9c data/corpus-big  # 0.82s
$ grep -rc needle-7f3a9c data/corpus-big   # 1.84s

grep wins by 2.8x on small files; rg wins by 3.3x on large files — the only variable is file layout, and the verdict flips. What rg wins on is not “per-file throughput” — it’s a scheduling policy.

“10MB of memory searches 100GB” — what the local 4GB corpus verifies for it#

Corpusrg peak RSSgrep peak RSS
Small files 3.95GB9.7MB5.0MB (recursion accounting differs)
Large files 3.4GB6.7MB4.4MB (single 34MB file accounting)

rg scanning 3.95GB peaks at 9.7MB RSS; scanning 3.4GB drops to 6.7MB — corpus size has no monotone effect on RSS, because it processes streaming, file-by-file, and never holds the whole corpus. That’s the mechanism behind “10MB searches 100GB”: memory is O(stream buffer), not O(corpus size). grep is single-process recursive — different RSS accounting (each forked child is counted separately) — so 9.7 vs 5.0 isn’t a fair direct comparison; stated as such, and the 100GB extrapolation was not done locally.

Where the speed lives: three layers, each with local evidence#

Layer 1: parallel scheduling (pays off when files are numerous)

rg’s default thread pool = 2 × ncpu (this box: 2 cores → a pool of 4). On the small-file corpus (10,000 files), each file’s work is only ~400KB, so the pool’s scheduling + result-merging fixed overhead can’t amortize against grep’s 0.28s — rg is slower. On the large-file corpus (100 files), each file is 34MB, long enough that 4 threads parallelize nearly linearly down to 0.56s.

Check: rg -j1 (forced single core) is 1.06s on small files, 0.82s on large — in the large-file case rg’s win isn’t parallelism, it’s single-threaded throughput (next layer).

Layer 2: single-threaded throughput (pays off on big files via SIMD)

rg defaults to Rust’s regex engine — memory-safe, compile-time-optimized matching; grep 3.11 defaults to GNU regex (not PCRE2), single-threaded on 34MB files in 1.84s, while rg -j1 does it in 0.82s — single-core, rg’s single thread is 2.2x faster than grep’s. This is where “Rust is fast” actually lands on large files: not magic, but grep’s default regex engine not being the optimal path for long lines / big files.

Layer 3: default behavior (searches less, not just faster)

rg by default skips binary files, skips .gitignore, skips dotfiles; output is per-file aggregated with color and line numbers; it assumes UTF-8 and skips non-UTF-8 files. My small-file corpus was all .log, so none of those filters fired — the comparison was pure search. In a real code repository, rg’s “searches less” cuts the bytes scanned an order of magnitude below grep -r; I did not isolate that layer’s win locally — it’s listed under “further reading,” not asserted in the body.

Boundaries, stated#

  • This box has 2 cores; rg’s pool is 4 (2×ncpu) — 4 threads on 2 physical cores oversubscribe, so “large files rg wins 3.3x” gets steeper on 4+ cores; grep’s small-file lead shrinks as core count grows
  • Hot-state medians; first cold run (page-cache miss) had rg’s small-file first pass at 11.7s and grep at 16.3s — cold, both regress and the parallel advantage vanishes. “Cold-start rg is slower” is the same domain as the Headstart piece’s “2 cores: parallelism is slower than serial” — cross-referenced
  • grep 3.11’s default regex engine is not PCRE2 (grep -P switches to PCRE2, not tested); rg’s regex crate supports a subset, no backtracking — the two engines have asymmetric matching capabilities, and pure timing doesn’t cover the “what can you actually find” dimension

So should you believe “ripgrep searches 100GB in 10MB of memory”#

Believe the mechanism, not the literal number. The local 4GB corpus verified “RSS doesn’t grow monotonically with corpus size” — the O(stream) property — with 9.7MB / 6.7MB landing on the same flat curve; extrapolating to 100GB needs a bigger corpus or more files, not done locally, listed under “further reading.”

The “fast” part of the folklore, verified locally across three layers: parallelism (pays off on large files, 3.3x), single-threaded throughput (large files, 2.2x), searching less (default filters, not isolated). The counter-intuitive “grep wins on small files” result is the single most useful number from this test — it drags “rg is fast” out of folklore and back into an engineering judgment: “it depends on your file layout.”

FAQ#

  • Is ripgrep really faster than grep? Depends on file layout. Local 4GB corpus: on 10,000 small files grep’s 0.28s beats rg’s 0.77s by 2.8x; on 100 files of 34MB rg’s 0.56s beats grep’s 1.84s by 3.3x. Same machine, same phrase — the verdict flips.
  • Where does “10MB of memory searches 100GB” come from? Local 4GB corpus: rg peaks at 9.7MB RSS scanning 3.95GB and 6.7MB scanning 3.4GB — memory doesn’t scale monotonically with corpus size (streaming, file-by-file). The 100GB extrapolation wasn’t done locally; the mechanism is what I verified.
  • Is rg -j1 (single core) still faster than grep? Faster on large files (0.82s vs 1.84s, 2.2x), slower on small ones (1.06s vs 0.28s). Single-core, rg wins on the per-thread regex engine and loses on scheduler overhead.
  • Which layer does rg’s speed live in, and what should I optimize? Three layers: parallel scheduling (pays off on many files), single-threaded throughput (pays off on big files), searching less by default (order-of-magnitude fewer bytes in a code repo). Files that are numerous and fragmented: rg’s scheduler overhead outweighs its gains — grep is the right tool there.
  • What happens cold? With a page-cache miss, the parallel advantage vanishes: rg’s cold small-file run is 11.7s, grep 16.3s — both regress. The 3.3x / 2.8x only show up hot. Same domain as Headstart’s “2 cores: -Zthreads is slower than serial.”
