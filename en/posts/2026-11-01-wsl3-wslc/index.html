WSL 3 Ships: A Native Linux Container Engine on Windows, 2x Cross-System File Speed

On September 29, Microsoft moved WSL 3.0.1 to GA, landing the wslc container CLI, the Consomme network mode, and virtiofs file acceleration in one shot. I installed it on Windows 11 and walked through the architecture, networking, and honest limits.

November 1, 2026 · 4 min · 715 words · DreamBeast Dev -  |  中文

Intro: On September 29, Microsoft pushed WSL 3.0.1 to GA — the last version had been sitting at 2.9.13. The real reason for crossing 3 is that “WSL containers” finally went GA. One line: run wsl --update on Windows and you get your own Linux container engine, no Docker Desktop install. Here’s what I found, broken down.

The bottom line up front#

WSL 3 makes running Linux containers on Windows a first-class thing: the new wslc command is there as soon as you install it, and it’s just docker with a different prefix; networking moves to the Consomme mode so enterprise VPN just works; and the file protocol becomes virtiofs, making cross-system file reads roughly 2x faster.

The direction is one thing: run containers natively on Windows, without stacking an external engine on top.

How I installed it#

I just ran wsl --update, and wslc was there the moment it finished. wslc version reported 3.0.1.0 — no login, no reboot, no license prompt.

Then I ran wslc run --rm hello-world: pulled the image, executed it, got output, first try.

What wslc is#

Read the commands as docker: wslc container run, wslc container cp, wslc system info — swap the leading docker for wslc.

It pulls standard OCI images, straight from Docker Hub, and the single-container workflow is enough.

Session isolation: one VM per user#

WSLC doesn’t reuse the shared VM from WSL 2. The privileged wslservice.exe only creates virtual machines; each user session is managed by its own wslcsession.exe, running under your own user privileges.

Each session has its own virtual disk — images, containers, and networking are not shared. The upside is hard isolation between sessions and a small blast radius when something breaks, plus a lower permission level in the control plane and a tighter security boundary.

The Consomme network mode#

Why the French name? Consomme is a clarified stock in French cooking — the idea is to skim the “isolation” off the WSL network.

WSL 2’s default NAT is fully isolated, so an enterprise VPN can’t reach it. Consomme has the VM send traffic out as Ethernet frames over virtio queues, with a user-space process on the Windows side picking it up to handle DNS, routing, and port mapping.

The effect: traffic goes out under your own user identity, so VPN and firewalls treat it exactly like an ordinary Windows process.

Microsoft itself says the model is still evolving; several changelog entries fix port-range and gateway-fallback issues. Don’t expect it to be turnkey.

File performance: the “2x” is their number#

The old protocol was 9P, and slow cross-system file access was WSL 2’s #1 complaint for years. The official docs tell you to keep your project on the Linux side — that’s a workaround, not a fix.

WSL 3 defaults to virtiofs. The architecture blog’s exact words: virtiofs is roughly 2x faster than 9P. Note the “roughly” — Microsoft’s wording is restrained. The kernel also moved up to 6.18.

VS Code integration: one line to switch#

If you use VS Code Dev Containers, your workflow doesn’t change. The extension drives containers by calling the docker CLI — just point dev.containers.dockerPath at wslc.

From there, build, run, inspect, and exec all go through wslc. Keep Docker Desktop if you want; they don’t conflict, they just don’t share images.

Honest limits#

What wslc doesn’t have yet. No Compose — the official blog calls it the most requested feature, coming in the next iteration. No local k8s, and it doesn’t support the devcontainer features mechanism.

GPU passthrough works; --gpus all tested fine. So it splits into two tiers: for single containers, devcontainers, and learning containers, you can switch today; if you rely heavily on Compose or k8s, wait for Compose to land.

My take#

This move isn’t “make a Docker alternative.” It’s pulling container workloads into Windows’ own enterprise governance frame — Intune can disable it in one go, Defender can audit container processes, and Docker Desktop can’t give you that. For an individual developer it’s one install saved; for an enterprise it’s a whole layer of control saved.

Frequently Asked Questions

Do I need Windows 11?

It follows WSL — anything that can run virtualization is fine.

Can it coexist with Docker Desktop?

Yes. They run in separate VMs, don't share images, and don't conflict.

Will my existing devcontainer.json work?

Mostly. wslc doesn't support the three items: compose file, features, and runServices.

How do enterprises manage it?

Intune can disable WSL containers and restrict registry sources in one go; MDE can audit processes, files, and network activity inside containers.
