AgentScope's Event Log in Production: One KV Table, 14x Write Amplification, and the 23-Second Toll

AgentScope Java's default EVENT_LOG session mode: the journal is append-only and never compacted. Upstream measured 14-17x write amplification and O(n²) read degradation; I reproduced it locally across three backends and wrote the production playbook.

November 7, 2026 · 19 min · 3936 words · November 7, 2026 · Rexai Programming -  |  中文

A question nobody answered#

A few days ago a developer posted in a forum: building a platform-level webchat agent on the Java stack, framework of choice was Alibaba’s open-source AgentScope, and once it ran, the framework’s default event-log mode wrote every native log into a single KV table that bloated fast under multi-user concurrency. They wanted a mature way to handle it. Half a day in, nobody replied.

The answer wasn’t sitting in the forum. It was scattered across the framework source, the official docs, and the upstream issue tracker. Stitch those lines together and a concrete picture emerges: this event log was designed for audit, not for space; it grows without bound; the read side degrades quadratically with session depth. The official toolkit — pluggable backends, export, cleanup — exists, but the retention-policy page of that story is still blank in the docs. This post takes the mechanism down to source lines and settles it with upstream’s measured numbers plus my local reproduction: what happens when a multi-user webchat runs the default configuration into production, and how to fix it.

Why it’s worth writing: AgentScope Java is one of the most active Java agent frameworks of 2026 — 6,282 stars, 983 open issues, still shipping code on the day I wrote this (Nov 7). Its event-log submodule alone opened five read-side/size issues between Oct 19 and Nov 5 (#3816/#3647/#3987/#3812/#3995), followed by a pipeline of read- and write-side fix PRs sitting open (#3666 merged, #3888 pending). They are all different cuts of the same complaint: the default configuration is invisible in a single-user demo, and hits storage, latency, and recovery at once in a multi-user service.

Reading “event log” correctly#

In AgentScope Java 2.0, HarnessAgent’s default session mode is EVENT_LOG. The underlying implementation is JournalSessionLog, an immutable commit chain: each session directory (agents/s_<agent>/sessions/s_<user>/s_<session>/) holds a session header session.json, a chain-tail pointer head.json, batch-archived commits/<hash>.json files, and payloads over 64 KB stored separately as blobs/<sha256> objects[1]. Commits are linked by a SHA-256 hash chain; every submit does an atomic CAS on head.json under a writer lease (fencing), so two writers cannot take over the same session at once.

The official positioning is “audit-grade lossless log”: compaction only shrinks the window that enters the model context — the journal itself is never compacted, never rewritten. That positioning decides the character of every growth problem below: you have not hit a bug, you have hit the design. Every streaming chunk (model/chunk), every tool call (tool/requested/tool/result), every turn boundary (turn/*), and the full pre-call request (request/prepared) becomes an event; the event catalog runs to 40+ types[2].

This chain is more than “logging”. commit() validates event-seq contiguity, writes a commit file named by the batchId hash, then does the head.json CAS inside a retry loop of up to 32; if the ACK of the current commit is lost, it walks the parent pointer backwards along the chain to complete idempotent semantics (JournalSessionLog.java, L193 onward). The writer holds the lease: acquire(owner, lease) and renew(writer, lease) record owner and expiry in head, and once the lease lapses the old writer’s submissions throw “Writer renewal contention” (acquire L106, renew L166) — that is multi-replica fencing: a wedged old process cannot write the chain into a knot. The large-payload threshold is hard-wired at 65,536 bytes; an event past the line is content-addressed into blobs/<sha256> and the commit keeps only the reference.

One write-side detail people miss: SessionRecorder flushes on a 1-second scheduled tick — every second, if the buffer has events, a batch is committed[3]. Commit count follows wall-clock, not content — upstream measured 506 commits out of a 12-turn session, roughly 42 per turn[4].

Why one table runs away in multi-user#

The bloat is three mechanisms stacked. Layer one, “never delete”: the commit chain only appends; blob content-addressing deduplicates but never reclaims; total journal bytes are monotonically increasing in total events. Layer two, “re-record”: every model call re-records the entire request — message history, tool definitions, options — as request/prepared. The longer the session, the bigger that record; total volume grows near-quadratically with turns. An upstream issue asking for a compact mode is still open[5]. Layer three, “share”: in a multi-user webchat, every session lands in the same store.

The “one KV table” in that post most likely refers to the Windows/Java filesystem backend’s journal.sqlite3: the whole database is a single table session_objects(path TEXT PRIMARY KEY, version, payload); every user, every session’s commits, blobs and head sit in rows of that one table[6]. The shared KV backends (Redis/JDBC BaseStore) behave the same — session logs and memory share one namespace segment, keys shaped like agentscope:store:item:agents\0<agentId>\0users\0<userId>\0sessions\0...[7]. The official docs’ KV selection section explicitly says “don’t use OSS as a KV” (Redis/MySQL for high-frequency small objects, OSS only for big ones), but the whole page has no retention policy — someone asked in August whether RedisAgentStateStore should carry a TTL; it is still open[8].

Three source-level details explain why that SQLite table is born heavy. First, SqliteSessionStorage’s class comment reads “Windows local journal storage, using atomic SQL writes and synchronous rollback journals”: connect() opens a new DriverManager.getConnection on every call and runs PRAGMA synchronous=EXTRA (L42/L59/L63) — the strongest of SQLite’s five sync levels, and every CAS and every blob-dedupe check is its own transaction, so write amplification multiplies straight in. Second, the read path also opens a new connection per call (L85, SELECT version, payload); upstream #3647 measured 0.69 ms per fresh-connection read vs 0.053 ms with reuse[4]. Third, session listing does a substr(path, 1, length(prefix)) prefix scan (L125) with no lightweight metadata index — that is the root cause of “listing 17 sessions takes 6 seconds”[9].

The “share” layer’s cost shows up in concurrent writes. A SQLite database is single-writer by nature: at any moment one write transaction runs, and this backend sets synchronous=EXTRA on every connection, adding fsyncs on the commit path — every user’s, every session’s commits queue behind the same write lock. Multi-user concurrency produces no parallelism gain, only waiting. Redis is better: key granularity is inherently concurrent. But the framework’s key design spreads the whole log tree under one store’s namespace segment, and RedisAgentStateStore exposes no TTL entry point (#2781 asked exactly this; still open[8]). To give logs a retention cycle today you wrap your own custom SessionLogStore with an expiry policy.

The wall of numbers: tuition upstream already paid#

The upstream community has stepped in these pits deep; every number below comes from October 2026 issues, all on the “event log on the filesystem journal” setup[4]:

A 12-turn test session: journal 14.35 MB, 15,252 events, 506 commits — while the model’s actual output (text, thinking, tool args) totals only 0.83 MB. That is 14 to 17x amplification. The read side is worse: before every turn, the full commit chain is roughly replayed seven times, and SessionInteractions.pending() is an O(n²) windowed loop read (15,252 events ÷ 256 window ≈ 60 passes, each walking ~506 commits, about 60,000 store reads in total; 12.7 s for that one item). A full scan of the same data takes 0.786 s. The user-perceived degradation curve: on the same session, “commit to first token” is 0.06 s at turn 1 and 23 s at turn 10, while the model itself spends only 0.95 s for the whole turn — of the 20-30 seconds of waiting users feel, almost none of it is the model thinking[4].

The Windows backend’s read path carries an extra tax: every store read opens a fresh SQLite connection and runs PRAGMA synchronous=EXTRA — measured 0.69 ms per read vs 0.053 ms with a reused connection, 13x[4]. The session-listing interface has no lightweight metadata path at all: listing 17 sessions takes over 6 s, complexity = session count × full replay[9]; on the JDBC backend, a session with 445 commit segments takes ~35 s to reach first token on recovery[10].

One easy to miss: #3812 points out that before every model call the full request body (message history + tool definitions + options) lands in the journal as request/prepared, and in long sessions that body grows linearly with depth — total events grow near-quadratically with turns. That is the main component of the 14-17x amplification, and the direct reason it asks for a compact mode[5]. #3995 on shared storage is subtler: StoreSessionStorage does not override batch readAll, so every replay degrades to one GET per event in the remote store — more events, more round-trips, O(n²) multiplied by a network RTT[14].

Local reproduction: the real numbers of the log layer#

Upstream’s numbers are late-October; the read-side optimization #3666 (bulk segment read, one round-trip for the whole chain) landed in main on Oct 28[11]. To see the current state, I drove the log layer directly on main (v2.1.0-SNAPSHOT, fetched 2026-11-07): the real JournalSessionLog with three backends (POSIX local file, in-memory KV, SQLite single table). The event mix was synthesized from #3816’s measured session profile — 85% small streaming chunks, 7% tool traffic (2% of which crosses 64 KB into blobs), 6% full assistant messages, 2% request/prepared growing with session depth (capped at 100 KB; the O(n²) main driver at the top end), batches of 32 events simulating the 1-second heartbeat, at 2,000 / 20,000 / 200,000 scales. Machine: 2 vCPU (AMD EPYC 9354P slice), 7.8 GB RAM, JDK 17.0.21[12]. One methodology exception to flag: our usual convention is to run test code inside the LiteBox sandbox; that was not possible — HotSpot dies inside the sandbox at the seccomp PaX exec-memory probe (“failed to allocate memory for PaX check”), so everything ran on the host in a restricted workdir: all artifacts stayed in the project directory and /tmp, no global side effects. The bench tool JournalBench sits in the package-private scope of io.agentscope.harness.agent.session and drives the log layer’s public API directly — acquire for the writer lease, commit every 32 events, three read shapes measured: pending(), full scan(0, head), and 256-window readAfter loop — without touching any agent inference path, so the numbers reflect the log layer alone, no model I/O.

Four observations. First, the write-amplification denominator differs from upstream’s: locally I compare journal bytes on disk vs original payload bytes (20K scale: 26.6/22.3 ≈ 1.2x), while upstream’s 14-17x compares journal vs “what the model actually produced” — the 0.83 MB in that denominator excludes the request/prepared re-records, so both numbers are right and they measure different things. Second, pending()’s O(n²) survives the bulk-read merge: events ×10, pending jumps from ~0.2 s to ~10 s; at 200K I measured 802 s — after 200,000 events in one session, a single pending() is 13.4 minutes. The call sites are more than intuition suggests: the submit/resume/respond command entrypoints in AgentSession all call SessionInteractions.pending(log) first for validation and request-ownership resolution (AgentSession.java L161/L206, command prepare in SessionExecution.java L69); the process-restart SessionRecovery (L52) and session state-change check SessionStateAccess (L107) each call it too, and AgentSession’s dispatch is a 100 ms periodic schedule (AgentSession.java L124) — so this is not “one expensive cold recovery”, it is a charge paid on every command round-trip. That is why #3987 proposes an anchors.json at the chain tail to cut recovery to O(1)[10]. Third, the SQLite single table’s write cost is 2.4x POSIX and 11.5x in-memory KV at the 20K scale (EXTRA sync + each CAS its own transaction); at 200K the write-time gap narrows (87.6 s vs 55.8 s POSIX, 1.57x — per-commit cost is constant, absolute gap driven by commit count), but multi-user concurrent writes on one table still serialize on fsync. Fourth, in-memory KV value bytes (35.6 MB) run 34% larger than POSIX on-disk (26.6 MB), because the KV backend JSON-encodes whole commit objects; there is nothing left to strip beyond the 8-byte version prefix that POSIX files carry — flip it: real memory usage in Redis should be budgeted from the KV-side number. The 200K row’s three backends (189.6 / 254.2 / 195.5 MB) are post-blob-dedupe values: synthesized large payloads are deterministically generated per slot, so cross-turn duplicates collapse into one blob; real tool outputs differ per call, so dedupe wins are far smaller — budget capacity from the 20K scale’s 1.66 MB/simulated-turn conservative figure.

One contrast in the table deserves its own paragraph. Full scan is linear at all three scales (169 ms → 683 ms → 6.5 s; events ×100, time ×38) — that is #3666’s bulk read working. pending(), meanwhile: 180 ms → 11.2 s → 802 s; events ×100, time ×4,455 — because it is not the bulk read, it is a 256-window readAfter batch loop, and each batch walks the commit chain from the head: window count × chain length = O(n²). Note that in my bench, pendingInteractions stayed 0 throughout: there were no undelivered user events on the chain, yet the query still played the whole chain once — this O(n²) is not paid “when there are pendings”, it is paid “every time you ask”.

Extrapolating at the 20K scale’s 1.66 MB/simulated-turn (1,271 events/turn, same density as upstream’s measured session): a webchat with 1,000 daily actives, each doing 30 turns a day, adds roughly 50 GB of raw payload per day under default configuration (350 GB a week), then the SQLite single table or Redis multiplies that by another 1.2-1.6, and no component deletes anything for you. That is the complete arithmetic behind “the table bloats fast under multi-user”.

Reproducibility note: each scale’s bench results are checkpointed to JSON (event count, commit count, the four timing segments for write / full-scan / pending / looped readAfter, on-disk or KV bytes, head sequence). The machine is a fixed 2-vCPU EPYC slice — absolute values do not transfer across machines, but the ratios between backends (SQLite write = 2.4x POSIX; the O(n²) slope of pending) should reproduce on comparable hardware. The bench’s synthesized events are a deterministic profile (same slot, same content), so the 200K post-dedupe bytes are optimistic; the body deliberately extrapolates from the 20K scale.

Production adaptation: where you can actually act#

Boundaries first: I did not run the full agent end-to-end (no usable model keys); every local number comes from driving the log layer, with the event mix synthesized from upstream’s measured profile. All upstream quotes are from the October-November 2026 issues, version v2.1.0-SNAPSHOT.

The framework hands you four levers. One: swap the backend — .sessionLogStore(...) accepts any custom store implementing SessionLogStore or AtomicSessionStorage; the official contract requires atomic version-compare writes, write leases, ordered idempotent commits; plain KV read/write does not qualify[1]. This is the proper entry point for retention policy — sharding, TTL, hot/cold tiering all live at this layer. Two: export — SessionLogExporter with your application’s SessionExportSink pulls committed events incrementally into a warehouse or audit system; delivery is at-least-once, dedupe by eventId on the target[1]. Hot data in KV, cold data in the warehouse, and the table finally thins out. Three: clean up — deleteSessionState(...) deletes at session granularity; the LEGACY side’s maxPersistedContextMessages can cap persisted snapshot message counts — the default is unlimited, for backward compatibility[13]. Four: switch modes — .legacySessionHistory(true) goes LEGACY state-snapshot: bounded size (the snapshot overwrites each time), at the cost of event-level audit, replay and compact events. LEGACY state flows through AgentStateStore, which the official core plus extension modules ship with 12 implementations (InMemory, JsonFile, three Redis clients, JDBC/MySQL/PostgreSQL/Mongo, OSS/COS, JPA); snapshots keep only the context needed to resume the session, not the event timeline — HITL pending interactions, per-event tool replay, journal-based tools like session_search are all unavailable in LEGACY. If your webchat’s product surface depends on “session list + history lookback”, switching modes is cutting features, not just saving space.

Multi-replica is another thing to design up front: HarnessAgent itself is a stateless singleton; the official multi-replica recipe points all replicas at the same storage backend — RedisDistributedStore injecting BaseStore, plus RemoteFilesystemSpec (IsolationScope.USER for per-user isolation) and WorkspaceIndex, or a dedicated .sessionLogStore; the checklist demands same database, same identity, same namespace across replicas, or the hash chain grows two tails and every CAS fails[1]. Switching between EVENT_LOG and LEGACY is a one-way door: a session cannot switch mid-flight; delete the old session (deleteSessionState) and migrate to a new one, or the event-level timeline is lost.

Backup and recovery differ per backend. POSIX is a directory tree: consistency-copy agents/s_*/sessions/, copy it back on restore, the hash chain self-verifies. Windows’ journal.sqlite3 is a single file but write-locked: stop writes (or drain the instance’s traffic) before taking a consistency snapshot — copying a live database almost always lands you mid-transaction. Redis shared backends go through RDB/AOF; note log keys and memory keys live in the same store, and their versions must match on restore, or the session.json header won’t line up with the commit chain.

The upstream fix pipeline is worth tracking: #3666’s bulk segment read is merged (Oct 28)[11]; #3888’s write-side interrupt fix is an open PR — it solves: when a flush subscription is cancelled by the caller (request timeout, subscriber vanished), Reactor’s boundedElastic interrupts the thread running inside renew/commit, leaving the writer-lease state half-written and the journal write suspended[17]; #3987’s O(1) anchors recovery, #3812’s compact request records, and #3995’s per-read fix are still open[10,5,14]; #2145 points out that the tool-result eviction middleware still keeps full outputs in Redis state, bypassing the context cap on long sessions[15]. If you run long sessions in production, watch these numbers on main, not just version tags.

For that poster’s scenario (Java, multi-user webchat), an executable combination: shared Redis as BaseStore (the official default) + a custom SessionLogStore wrapping TTL and cold archive + SessionLogExporter draining to the warehouse on a schedule + deleteSessionState at session expiry. All four steps use official interfaces; nobody forks the framework. Drain cadence follows event production: under the default 1-second heartbeat flush, pull warehouse cursors at least at 5-minute granularity (exportCursor advances atomically, replay-safe), and 7 days of KV TTL covers most audit windows.

The verdict, tiered#

Single-user or a team of ten: the local default configuration is fine; growth is in the hundreds of MB; a disk won’t fill in a year. A 100-to-1,000-person webchat with active sessions and no retention policy hits the read side first: the deeper the session, the slower the first token (upstream: 23 s at turn 10), and the session-listing interface goes down before storage alarms do — the incident type most easily misdiagnosed as “the model got slow”. Teams with a real audit need: do not kill EVENT_LOG to save space; the hash chain plus content-addressed blobs has standalone value. The correct move is adding the retention policy, so “lossless” holds for hot data only. Two monitors before you go to production: journal directory bytes and commit count (both monotonic; the growth rate is your alert baseline), and the P99 of pending() latency — a sustained rise means sessions are entering the O(n²) regime; a read-side avalanche lands earlier than disk full. Size it for your own load: turns per session per day × 1.66 MB/turn (20K scale measured, conservative low-dedupe value) × active sessions, times your SQLite/Redis factor of 1.2-1.6, is your weekly log delta; past 20% of storage budget, retention policy stops being optional. In one sentence: this log is a good audit foundation and a bad default for production, exposed.

FAQ#

Can I just turn the event log off? Yes, .legacySessionHistory(true) switches to LEGACY state-snapshot mode. You give up the event-level timeline, session_search-style projections, and lossless replay; recovery stops at snapshot granularity. Mixed-deployment note: a session cannot switch modes mid-flight — the framework throws an authority mismatch; migrate to a new session[1].

How big can that single KV table get? Local 20,000 events: SQLite write 9.9 s, single file 27 MB; extrapolated at 1.66 MB/active-turn, a 1,000-DAP platform lands tens of GB per week, and the SQLite single file serializes multi-user writes on fsync — which is why the official going-to-production doc makes Redis the multi-replica default and the SQLite backend appears only in the Windows local path[7].

Windows vs Linux? The logical objects are identical (the docs say the same objects in two physical forms); the difference is execution path: POSIX does temp-file + atomic rename + directory fsync; Windows’ Java filesystem cannot sync a directory, so it uses the journal.sqlite3 single table with synchronous=EXTRA and a fresh connection per read (0.69 ms per read vs 0.053 ms reused)[6,4]. Cross-platform migration of history goes through log migration or a shared backend.

How do replicas share the log? Point every replica at the same shared backend: RedisDistributedStore injecting BaseStore plus RemoteFilesystemSpec (IsolationScope.USER to slice tenants), or .sessionLogStore(WorkspaceSessionLogStore(BaseStore)) for a log-dedicated backend. The official position: replicas must share database, identity and namespace — “each replica uses its own local directory of the same name” is not sharing[1,7].

Can old log be deleted, and how? Session-level deleteSessionState(...); batch hot/cold tiering via SessionLogExporter to the warehouse, then purge the source; the Windows backend backup needs a whole-database consistency snapshot (stop writes, then copy; or a SQLite consistency backup) — copying one file is not a complete backup[1,13].

Frequently Asked Questions

Can I just turn the event log off?

Yes: .legacySessionHistory(true) switches to LEGACY state-snapshot mode. You give up the event-level timeline and lossless replay. A session cannot switch modes mid-flight; migrate to a new session.

How big can that single KV table grow?

Local 20,000-event SQLite: 9.9 s write, 27 MB single file. Extrapolating at 1.66 MB per active turn, a 1,000-DAP platform adds tens of GB per day, and multi-user concurrent writes serialize on fsync.

Windows vs Linux?
