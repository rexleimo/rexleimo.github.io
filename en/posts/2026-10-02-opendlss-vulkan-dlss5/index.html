On a Box Without an NVIDIA Card, I Tore NVIDIA's Closed Network Apart Down to the Bone

NVIDIA's DLSS 5 neural rendering network was reimplemented in pure Vulkan, byte-exact at all 75 block boundaries. My machine has no NVIDIA card, so I can't verify the signature GPU-side bit-exact parity. But I shallow-cloned the repo, read the source, cross-checked the 71-block graph, and actually ran one PTX divider regression on my own box — I tore it apart as far as I could tear it, said what I can say, and wrote down flat what I can't.

October 1, 2026 · 7 min · 1368 words · Dreambeast -  |  中文

NVIDIA’s DLSS 5 “neural rendering” network was reimplemented in pure Vulkan, byte-exact at all 75 block boundaries. Not “good enough” — bit-exact.

My machine has no NVIDIA card (nvidia-smi comes back command not found), so I can’t verify its signature move — the GPU-side bit-exact parity. But I didn’t stop there. I shallow-cloned the repo, read its src/nr_graph.h (kBlockCount = 71 matches the README), counted the 13 GLSL reference kernels, and actually ran its bundled PTX divider regression on my own box — I tore it apart as far as I could, said what I can say, and wrote down flat what I can’t.

This post is about exactly how far I got. Every number points to a line number I grepped or an output I re-ran. If I didn’t reproduce it, I label it not reproduced.

What it actually is#

The first thing I read out of docs/network.md: it is not an upscaler. docs/network.md:27 says it plainly, The network is resolution-preserving — same-resolution input and output. What it does is “re-render the frame the engine already drew”: generate detail out of three injected Gaussian noise lanes, adjusted under style / tone / structure / skin conditioning.

docs/network.md:7-8 states the I/O crisply:

Input features: f32 [fullHeight * fullWidth][16]   (16 channels)
Output head: f32 [fullHeight * fullWidth][4]        (RGB residual + 1 temporal-blend logit)

README:18 nails the boundary: Input and output are the same resolution; it is not [an upscaler].

The network: the 71 I grepped#

That one line at src/nr_graph.h:40, static constexpr uint32_t kBlockCount = 71;, is the hardest fact I pulled from the source: 71 blocks, and README:5 says The same 71-block Swin / ViT network as DLSS-NR build 310.8.0.

README:16 states the key parameters in one breath: FP8 (E4M3) activations with FP16 accumulation, 141 MiB of weights.

I counted 13 GLSL reference kernels with ls shaders/*.comp: fused_block32 / gemm_f16 / gemm_fp8 / gemm_mlp / gemm_reduce / global_attend / global_attention / global_normalize / ops / preprocess / qkv_attention / window_attend / window_normalize. The literal E4M3 shows up in 10 of them (grep -rln), matching what docs/numerics.md describes.

The one I actually ran on this box#

No N card here, so I can’t run the GPU-side parity. But scripts/ptx/ ships a test_fast_divmod.py — pure Python, no GPU — that interprets the PTX fast-path divider instructions and checks them against exact unsigned division. I ran it on my box, twice:

$ python3 scripts/ptx/test_fast_divmod.py
fast_divmod: every n < 2^24, d = 1..32: exact

That is the one thing I can claim as “I ran it” for this post. Not a perf number, not the bit-exact parity — a PTX divider regression test that passed on a box with no GPU.

The parts I can’t run, and how I’ll say it#

I write the boundary down, no mixing:

  • GPU-side bit-exact parity: no NVIDIA card on this box (nvidia-smi absent), not reproduced. The repo’s parity command needs an NVIDIA Ada+ exposing VK_KHR_cooperative_matrix / VK_NV_cooperative_matrix2 / VK_EXT_shader_float8 / VK_NV_cuda_kernel_launch (README:88-89); I don’t have that hardware.

  • The perf table: README:59-64, RTX 4070 SUPER, whole network per frame, minimum over 40 frames:

    resolutiontime
    768×7682.8 ms
    1920×10807.8 ms
    2560×144012.6 ms
    3840×216029.3 ms

    These are the author’s numbers, measured on the author’s box; I didn’t measure them. README:61 itself says the GPU alternates between two clock states under sustained load, so medians run a few percent higher — compare minima, not medians.

  • The 141 MiB of weights: README:16 says 141 MiB of weights; README:109 says the model directory is not shipped with the repo (Nothing in this repository produces such a directory). To run it, you supply your own.

  • The WebGPU browser port: ports/browser-webgpu/README.md:188 reads A warm frame at 512×512 is 73 ms across 451 dispatches, against about 2.7 ms for the Vulkan implementation on [the same GPU]. I checked the 27-file size of that port directory, but there’s no Chrome here, so parity did not run.

The exactness lives in the specification, not the hardware. That’s my reading of README:79 — the exactness is in the specification, not in the hardware. The WebGPU port has no tensor core, no FP8, no fusion, no chaining, but the bytes are identical. A 26× gap (73 ms vs 2.7 ms) with the exactness unchanged.

One judgment I made reading the code#

This is a specification-level reimplementation, not a feature reimplementation. README:109 says a model with a different block count is refused at load — it only accepts the 71-block 310.8.0 network and refuses anything else. The weights are closed and not shipped, so “use DLSS 5 for free” is out of reach. Its value is in laying open the execution detail NVIDIA’s report left implicit: 13 readable GLSL kernels plus a Python PTX generator, each one line-checkable against the six documents under docs/ (network / execution / numerics / weights / frame, 1037 lines total).

I shallow-cloned this repo (research/opendlss-repo/), copied the six docs to research/opendlss-docs/, and cite them line by line as I dig.

The bottom line#

No N card, so I tore the source and tests apart down to the bone. 71 blocks, 13 kernels, the E4M3 spread, 141 MiB of weights, 16 in / 4 out, same-resolution and not an upscaler — all of that I grepped on my box and the line numbers match. The PTX divider regression I actually ran here; the output is every n < 2^24, d = 1..32: exact.

GPU-side bit-exact, the 4070S perf table, WebGPU parity — not reproduced, labeled “from the author’s README.” No mixing.

That’s all I can say about it.

FAQ#

Q: Can I just pull the weights and run it? A: No. README:109 says Nothing in this repository produces such a directory — NVIDIA does not ship the 141 MiB model directory. You have to source a 310.8.0-build weight set yourself; the format is a manifest.json plus stage files (packed E4M3 bytes).

Q: Without an N card, how far can I verify it? A: Source cross-checks (71 blocks, 13 kernels, E4M3 spread) plus the PTX divider regression (pure Python, no GPU). Everything above that — parity / perf / demo — needs a GPU or Chrome, and this box stops there.

Q: Of that 72 ms vs 2.7 ms gap, which number is the author’s? A: Both are from the author’s README (README:79 + ports/browser-webgpu/README.md:188); I didn’t run them. But I did check that 27-file WebGPU port directory, and the code volume matches the description.

Q: What’s OpenDLSS’s value, if not free DLSS 5? A: It’s a specification-level reimplementation — it lays open, via 13 readable kernels plus a PTX generator, the 71-block execution detail NVIDIA’s report left implicit, checkable line by line against the six docs. The weights are closed and not shipped; “free use” is not on the table.

Q: What did I actually run on my box? A: scripts/ptx/test_fast_divmod.py, output fast_divmod: every n < 2^24, d = 1..32: exact, passed on two re-runs. That’s the only line I can write “I ran it.” Everything else is sourced: local grep / author’s README / NVIDIA report — three buckets, not mixed.

Honest disclaimer#

  • I shallow-cloned the repo to research/opendlss-repo/ (no N card on this box, so no GPU-side parity / demo / WebGPU).
  • Ran locally: scripts/ptx/test_fast_divmod.py (PTX divider regression, every n < 2^24: exact) plus source cross-checks (kBlockCount=71, 13 .comp files, E4M3 spread, six docs totaling 1037 lines).
  • Not reproduced: Vulkan fast path / GPU-side bit-exact parity / perf table (4070S) / WebGPU parity (no Chrome, weights self-supplied). Those numbers come from the author’s README / NVIDIA’s report, not “I measured it.”
  • Every number is sourced: local output (PTX regression, grep line numbers) / author’s README (141 MiB, perf table, 72/2.7 ms, bit-exact verdicts) / NVIDIA report (network structure), three buckets, not mixed.

Frequently Asked Questions

What did you actually verify, and what didn't you?

Verified (ran on my box): the PTX divider regression test (output `every n < 2^24, d = 1..32: exact`, passed on two re-runs); source cross-check of the 71-block graph (`src/nr_graph.h:40 kBlockCount = 71`); the count and spread of the 13 GLSL kernels; the 27-file size of the WebGPU port. NOT verified (no GPU here): the GPU-side bit-exact parity, the perf-table numbers (2.8–29.3 ms on a 4070S, measured on the author's box), the 141 MiB weight load.

What is OpenDLSS, and does it let me use DLSS 5 for free?

No. NVIDIA does not ship the weights with the repo; you must supply your own 141 MiB model directory. The value here is not 'free DLSS 5' — it's a specification-level reimplementation that lays the 71-block execution detail NVIDIA's report left implicit open for reading, via 13 readable GLSL kernels plus a PTX generator.

What part can I actually run on my own machine?

Runs here: the PTX divider regression (pure Python, no GPU). Can't run: every GPU-side verification (no N card), the WebGPU verification (no Chrome, weights self-supplied, fixtures not in the repo), the demo (Windows + NVIDIA only). The only 'I ran it' I can claim is that one PTX regression plus the source line numbers I grepped; everything else is labeled 'from the author's README'.
