A 0.8B Model, 4GB VRAM, Turned Into a Decision Engine: I Reconciled the Two Number Sets in Unsloth's New Feature

Unsloth added a 'Decision model' capability to its fine-tuning stack: turn a small LLM like Qwen3.5 0.8B into an engine that emits option probabilities only, trainable in 4GB VRAM. Their own X post carries two sets of numbers (20.7%->74.3% and 30-37%->78%); I reconciled both against the official docs line by line. They are two different baselines that align once you split them. Includes a full-model VRAM/time table and a reproduction trap (start r=16, reproduce with r=64).

October 10, 2026 · 8 min · 1565 words · 梦兽编程 -  |  中文

The moment this hit my feed I froze for a couple of seconds - the official X post contradicts itself, with two sets of numbers.

@UnslothAI’s 2026-10-07 release post (“You can now train your own Decision model like Jev locally!”): first line claims it “increased Qwen3.5 0.8B’s aggregate accuracy from 20.7% to 74.3% across 3 decision benchmarks - on just 4GB VRAM”; the very next paragraph says “increasing downstream accuracy from 30-37% to 78%”. Same post, same model, two baselines (20.7 vs 30-37), two ceilings (74.3 vs 78) - it looks like a broken ledger.

I pulled the entire official doc page and reconciled it line by line: nothing is wrong; they are two different baselines. That “reconciling the circulating numbers” exercise is the spine of this piece.

The mechanism: a Clef head that writes no text, only scores options#

The official doc’s mechanism (quoted keywords): the LLM reads the input once, and a small head (same design as Cloudflare’s Clef) looks at the LLM’s internal representation over “each question x each option” and directly scores each option - one forward pass adjudicates many questions.

Two engineering consequences:

  • No output tokens: no autoregressive decoding, no output-side latency, and no “JSON breaks / parse fails” failure mode - structured output no longer leans on a parser as a backstop;
  • The cost is on the input side: more questions and options lengthen the sequence; inference cost scales linearly with question count, so a decision model is not zero-cost.

It is essentially a swap from “the LLM produces the answer” to “the LLM produces features + a cheap head produces the answer.” The features reuse the LLM’s semantics; the verdict goes to a cheap deterministic head, and the output stage moves from “generate” to “score.”

Reconciliation: the official two sets, split by baseline and aligned#

Put the two sources side by side:

Source A: the official doc per-benchmark table (Qwen3.5-0.8B row):

Benchmark Before After
typed-decisions 36% 73%
BANKING77 7% 74%
CLINC150 19% 76%
Mixed holdout (3,000 rows) - 78%

Source B: the official X post: “20.7% -> 74.3% (3-benchmark aggregate)” and “30-37% -> 78% (downstream)”.

Reconciliation result (my arithmetic):

  • 20.7% = (36 + 7 + 19) / 3 = 20.67 ~= 20.7 (plain mean of the three benchmarks’ “before”)
  • 74.3% = (73 + 74 + 76) / 3 = 74.33 ~= 74.3 (plain mean of the three benchmarks’ “after”)
  • 30-37%: the doc’s own words “from 30-37% (which is roughly chance level)” - it describes the range of the per-benchmark “before” values (typed 36%, 2B 33%; the 0.8B set falls in that band), not a third dataset
  • 78%: accuracy on the 3,000-row mixed holdout (typed-decisions 2000 + BANKING77 500 + CLINC150 500), matching the Holdout column of the per-benchmark table

Conclusion: the two sets inside the same post are a “three-benchmark plain mean” and a “range description + mixed holdout” - two baselines, and neither is miscalculated. The release post writes both back to back with no baseline label, so a first read makes it look like a self-contradiction. That is exactly where circulating numbers usually go wrong: the numbers are right, and the missing baseline is what is not written.

The full-model table: a 4GB-to-14GB VRAM gradient#

The official doc’s “all models” table (Test accuracy / VRAM / Training time, all vendor-reported):

Model Test accuracy VRAM Training time
Qwen3.5-0.8B 78% 4GB 42 min
Qwen3.5-2B 81% 8GB 40 min
Llama 3.2 3B 79% 4.1GB 30 min
Gemma 4 E4B 77% 14.4GB 49 min
Laya (further fine-tune) 77% 2.5GB 10 min

Three rows in detail:

  • Llama 3.2 3B in 4.1GB and 30 minutes - 1pp lower accuracy than 0.8B, a quarter of the VRAM;
  • 2B is 3pp over 0.8B (81 vs 78), double the VRAM;
  • Laya further fine-tune 2.5GB/10min: topping up an existing decision model is an order of magnitude cheaper than training from scratch.

The VRAM figures can be cross-checked one level deeper: Unsloth’s Qwen3.5 fine-tuning page lists 3GB for 0.8B BF16 LoRA (same table: 2B=5GB, 4B=10GB), and an official AMD technical article (2026-07) measured Qwen3.5 training on a 3GB-VRAM AMD card. The decision table’s 4GB (4bit recipe) and these two 3GB figures (BF16 recipe) use different recipes but match in magnitude - a 4GB card can train the 0.8B decision model; that is a three-source cross-checked conclusion, not a single-source claim.

Training-data recipe (official): typed-decisions + 12 sources (ag_news, arc, banking77, boolq, clinc150, commonsense_qa, mmlu, mnli, prompt_injections, snli, sst5, wanli); test on 3,000 rows. The test set is decontaminated against the training data - that note is what underwrites the 78%.

The reproduction trap: start r=16, reproduce with r=64#

The second pitfall, more subtle than the baseline one:

  • The doc’s “Recommended settings”: 4bit base, LoRA rank 16, lr 2e-4, 2 epochs - a starter for people to get going;
  • But the doc body also says the table numbers were “fine-tuned with a Clef head using LoRA (r=64) for one epoch”;
  • The third-party report calls it out explicitly: to reproduce the table, use rank-64; don’t compare against the starter defaults.

The doc’s example code block reads r = 16, lora_alpha = 16 (in the FastDecisionModel.get_peft_model block). The example code and the table numbers use different hyperparameters: running the example as-is will not reach 78%. The quick-validation route is in the docs too: max_steps = 60, “Qwen3.5-4B reached 76% in 10 minutes on an L4” (single L4, official figure).

Training dataset structure#

LocalLLaMA/typed-decisions is the data backbone of this tutorial; it has 30,708 downloads on Hugging Face. It ships 5 configs: all, agent_trace_observability, customer_service, invoice_processing, security_incidents. Most “decision tasks” can land on a ready-made subset without training on the full mix - for ticket routing, the customer_service subset is cleaner than all.

The docs also note: the test set is decontaminated against the training data.

What suits it, what does not#

Suits (answer in a finite set):

  • Ticket routing, intent classification (BANKING77/CLINC150 are exactly this);
  • Injection / risk screening (the training sources include prompt_injections);
  • Adjudicating several fields from one input (doc example: the same ticket gets “which team + refund or not” in one forward pass);
  • Document tagging, process branching.

Does not suit: open generation, reasoning that needs an explanation chain - those stay on the LLM text path; the decision head is just a shortcut for “produce the answer.”

One more selection note from a third party: a traditional encoder classifier may be leaner and faster, so keep it as a baseline for comparison when choosing. The decision model’s selling point is reusing the LLM’s semantic base plus structured output; it does not lead in raw accuracy.

Ecosystem slot: Jev / Laya / Clef / Kev#

This space is crowded right now:

  • Jev / Laya / Clef: the official post names them directly - “train your own Decision model like Jev.” Jev (TypeSafe) goes through an API; Laya/Clef are local branches; Clef is Cloudflare’s public design, and Unsloth’s head is Clef-same;
  • Kev (GitHub jaredpalmer): a 0.8B-27B decision-model family on Qwen3.5/3.8; the 0.8B runs on a laptop; API-compatible with the Jev protocol - the “pretrained weights vs fine-tune it yourself” split, opposite routes from the Unsloth tutorial;
  • Unsloth’s differentiation: they hand you a trainer, not weights (FastDecisionModel + DecisionTrainer in the open-source package); wire up your own Decision API when you’re done.

Data sources and baselines#

The figures in this piece are cross-checked across multiple sources: the official docs tables, the official X release post, and a third-party report (alphasignal.ai, which relays the same tables and flags them vendor-reported). Training results such as 4GB / 42min / 78% come from the official decision-model table; VRAM gets two extra cross-checks - the BF16 LoRA VRAM table on Unsloth’s Qwen3.5 fine-tuning page (0.8B = 3GB) and an official AMD technical article (2026-07) measuring Qwen3.5 training on a 3GB-VRAM AMD card. The magnitudes agree. The mean reconciliation ((36+7+19)/3=20.7, (73+74+76)/3=74.3) is pure arithmetic.

The test set is decontaminated against the training data per the official note; “30-37% ~= chance level” is the official baseline, and because per-benchmark class counts differ, the random baseline is not strictly 1/class-count.

The Unsloth tutorial and tables iterate fast; this piece tracks the 2026-10-07 snapshot.

Frequently Asked Questions

What is a decision model, and how is it different from normal LLM fine-tuning?

A normal LLM emits a stream of text tokens (it decodes, and it can break JSON). A decision model bolts on a small classification head (same design as Cloudflare's Clef): the LLM reads the input once, and the head scores each option directly and outputs probabilities. No text generation, no output-token latency, no parse failures. Fits questions whose answers live in a finite set: routing, intent, injection screening.

Which is right, 20.7%->74.3% or 30-37%->78% in the official post?

Both are right; they are different baselines. 20.7/74.3 is the plain mean of three benchmarks (typed-decisions 36->73, BANKING77 7->74, CLINC150 19->76): (36+7+19)/3=20.7, (73+74+76)/3=74.3. 30-37->78 is the docs' own phrase 'from 30-37% (roughly chance level) up to 78%', where 78% is accuracy on a 3,000-row mixed holdout. I reconcile both line by line in the body.

Does 4GB VRAM really hold?

The official decision-model table lists 0.8B fine-tune peak 4GB (42 min), Llama 3.2 3B 4.1GB - a 4bit-base + LoRA recipe. VRAM is not a single source: Unsloth's Qwen3.5 fine-tuning page lists 3GB for 0.8B BF16 LoRA, and an official AMD technical article (2026-07) measured Qwen3.5 training on a 3GB-VRAM AMD card. Three sources agree, so '4GB is enough' is a cross-checked conclusion.

Should I reproduce with the settings the docs recommend?

No. The docs' 'Recommended settings' are 4bit base + LoRA rank 16 + lr 2e-4 - a starter. But the table numbers were produced with LoRA rank 64, one epoch; the docs themselves note: to reproduce the table, use rank-64, don't compare against the starter defaults.

What tasks suit it?

Anything with a finite answer set: ticket routing, intent classification, injection screening, document tagging, multi-question adjudication. Open-ended generation and reasoning that needs an explanation chain do not - those stay on the LLM text path. A traditional encoder classifier may be leaner and faster, so keep it as a baseline when you choose.
