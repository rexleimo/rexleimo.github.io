Can Plugins Unload Without a Trace? A 92-Page Paper from Peking University × DeepSeek Turns Plug-and-Unplug into Math

arXiv 2608.25512 introduces the programming paradigm of spatiotemporal composability: revertible effects make plugin removal leave no trace, reactive coeffects deactivate dependents automatically, unified as the context paradigm and implemented in Cordis — validated in production by Koishi's 4000+ plugin ecosystem. This is a paid article; the first half is free to read.

September 9, 2026 · 6 min · 1086 words · 梦兽编程 -

If you have ever written a VSCode extension, or maintained plugins for a chat bot, you have probably hit the same wall: installing a plugin is easy; uninstalling it cleanly is not.

Timers keep firing, event listeners stay registered, database connections stay open — a disabled plugin haunts memory. VSCode’s official answer is blunt: all extensions run in one shared extension host process, and removing one with executable code means restarting the whole host.

On August 26, 2026, three researchers from Peking University and DeepSeek-AI (Yifan Shi, Wei Zhang, Tianyi Cui) turned this problem into a 92-page paper: A Programming Paradigm for Spatiotemporal Composability External link (arXiv:2608.25512). I spent a weekend reading it, and it is the most theory-heavy yet engineering-closest paper I have read this year — it supplies the missing mathematical foundation for “can a plugin system truly plug and unplug without a trace?”

Two numbers, two dimensions#

The paper opens with VSCode and two statistics (marketplace data retrieved June 9, 2026):

  • 87 of the top 100 extensions by install count contain executable code — all of them require a host restart upon removal. VSCode does offer a deactivate hook, but it is only a graceful-shutdown callback at host termination; it cannot remove a single extension live, and it splits effect creation (activate) from effect disposal (deactivate), leaving complete cleanup to each author’s diligence.
  • Only 7 of the top 100 declare extensionDependencies on non-built-in extensions. Not because plugins have no dependencies, but because the API exposes fixed surface-level extension points, and inter-extension interaction returns an untyped any — with no structural contract, nobody dares declare dependencies.

These two numbers map to the paper’s two orthogonal dimensions:

  1. Temporal composability: upon removing a component, every modification it made to the shared environment — resource allocations, event registrations, state mutations — must be completely and safely reversed;
  2. Spatial composability: components declare dependencies on one another in a structured, verifiable way, and the system resolves, provides, and withdraws them reactively, coordinating component lifecycles accordingly.

The industry status quo: restart everything#

One might say this is already solved: restart the process, hand dependencies to Kubernetes. The paper calls this the coarse-grained workaround: the operating system provides temporal composability at process granularity, container orchestrators provide spatial composability at service granularity. It works, but:

  • Every restart discards process-local accumulated state (caches, connections, partial computations), taking seconds to minutes to rebuild; keeping availability requires redundant replicas;
  • Container-level orchestration cannot express dependencies between components sharing an address space, turning what could be local function calls into network calls.

The root cause is a granularity mismatch: modern software composes at component granularity, while recovery and dependency management happen at process/container granularity. The paper’s goal is to pull both back down to the component level.

The core idea: lifting compile-time theory into the runtime#

Programming language theory has long had a pair of concepts: effect systems describe what a computation does to its environment; coeffect systems describe what it requires from the environment. But they have always been compile-time instruments over lexically fixed scopes — while plugins are loaded after deployment, beyond any lexical scope.

The paper reifies these concepts as runtime mechanisms:

  • Revertible effects: every effectful function, while transforming the context, hands the runtime an explicit inverse. On removal, the runtime replays these inverses in LIFO order and the context is recovered. Plugin authors stop writing uninstall logic — yield the inverse as you load, and the framework does the rest.
  • Reactive coeffects: a component declares what it needs (its inject list); every change to the context is classified against that list as activating, deactivating, or neutral — dependencies present means activate, dependencies gone means deactivate, anything else is ignored.

Both are unified in a single recursive context type through which every effect and coeffect is mediated — the paper calls this the context paradigm. Under it, the effects of distinct components interleave without disturbing one another, guaranteed by theorems rather than promises.

Cordis and Koishi: production-scale validation#

The ideas are implemented in Cordis, a meta-framework of spatiotemporal composability: effect tracking, coeffect resolution, a declarative component loader, configuration reconciliation, and hot module replacement.

Its best reference is Koishi: an open-source chatbot framework built on Cordis with 4000+ community plugins over four years. On Koishi, disabling a plugin from the console reverts its effects in place; during development, the HMR engine re-applies an edited plugin on save while caches and live connections elsewhere stay untouched. Independently authored plugins, coordinated by nothing beyond a dependency key, keep an open ecosystem consistent — exactly what this theory set out to prove.

There is an AI angle too: one of the paper’s motivations is the self-evolving agent harness — agents that continuously generate and replace their own tools and components, where every modification is an act of dynamic composition and a restart per modification is untenable. The authors explicitly name applying Cordis to self-evolving agent harnesses as the most compelling future validation.

The brilliant part lies beyond#

If the paper were only “pair side effects with inverses, declare your dependencies,” it would be just a well-designed DI framework. What made me re-read carefully is how it answers three harder questions:

  1. What does “recovered” even mean? Freed memory does not restore the heap layout; a discarded generative handle is never reissued. Physical state cannot be restored byte-for-byte — so what is the mathematical definition of “without a trace”?
  2. What if the unwind order is disturbed? While your inverse runs, other components’ effects may sit on top — why would it still revert cleanly? Which two components may claim to be “independent”?
  3. Who goes offline first? While dependents still read what a provider supplies, why can’t the provider leave — and does this mechanism deadlock?

The paper’s answers — observational equivalence, commutativity witnesses, the guard and the progress theorems — are the most rewarding part of all 92 pages and what set it apart from “yet another plugin framework.” The paid section fully unpacks these three answers, the nine-rule calculus, Cordis’s key algorithms (including HMR without manual accept boundaries), and the Koishi case study, ending with a reading route for the full paper.

Frequently Asked Questions

What is spatiotemporal composability?

The paper splits runtime dynamic composition into two orthogonal dimensions: temporal composability — removing a component must completely revert every modification it made (registrations, connections, state changes); and spatial composability — components declare dependencies that the system resolves and withdraws reactively. The paper formalizes these as revertible effects and reactive coeffects, lifted from compile-time effect/coeffect theory into runtime mechanisms.

Why do VSCode extensions need a restart to uninstall?

VSCode runs all extensions in a shared extension host process. Once an extension's activate function has run, there is no mechanism to unload its code individually, so disabling or uninstalling a coded extension requires restarting the whole host. The paper counted (marketplace data, June 9, 2026): 87 of the top 100 extensions by installs contain executable code.

What is Cordis, and how does it relate to Koishi?

Cordis is the meta-framework the authors built to realize the paradigm: effect tracking, coeffect resolution, a declarative component loader, configuration reconciliation, and hot module replacement. Koishi is an open-source chatbot framework built on Cordis with 4000+ community plugins accumulated over four years — the production-scale validation of the theory.

What does this have to do with AI agents?

One of the paper's motivations is the self-evolving agent harness: an AI agent that continuously generates and replaces its own tools, components, and configurations. Restarting the process on every self-modification discards runtime state; ad hoc dependency adaptation silently breaks dependents. The authors name validating Cordis on self-evolving agent harnesses as future work.

What does the paid part cover?

The free half covers the problem and core ideas. The paid part fully unpacks: the track/recover machinery of revertible effects, the three-way classification and isolation/interception of reactive coeffects, observational equivalence and commutativity witnesses, the nine-rule calculus and its metatheory, Cordis's key algorithms (including HMR without manual accept boundaries), the Koishi case study, engineering discussions, and a reading route for the 92-page paper.
