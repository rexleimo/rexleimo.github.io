Handing a 12M/week npm package to an AI for one week — the 5 guardrails worth keeping

An 11-year-old npm package (wait-on, ~12M weekly downloads) got its first week under a new maintainer run by coding agents: 27 PRs, 6 releases, plus a Rust dual-engine port that passed 496 tests. I ran the key numbers on my own machine — what's worth taking is 5 guardrails, not 'look what AI can do.'

October 3, 2026 · 9 min · 1910 words · 梦兽编程 -  |  中文

I took the full first week that a coding-agent run on wait-on — an 11-year-old npm package — and checked every key claim against my own machine: what the thing is, how the work actually moves, which rules you can copy into your own repo, and which look cool but will get you hurt if you copy them wrong.

Why this one is worth using as a yardstick: wait-on pulls ~12M downloads a week and sits inside nearly every e2e test pipeline — Grafana, WordPress, Storybook, Node’s own undici, Cloudflare, Shopify, Angular, Spotify and IBM all list it in a package.json. That position means one thing: a one-letter mistake here lands on someone else’s CI, not your own. It’s the highest-stakes place you can imagine for “an agent maintains infrastructure” — so it’s the right place to test whether guardrails can actually hold.

What wait-on does: gate the tests until the dev server is ready#

One line: it blocks until some file, port, socket or URL is ready. The canonical use is “wait for the dev server, then run the e2e suite.” First commit July 2015, 11 years old.

Why it carries so much weight. I pulled its position in the ecosystem on my own machine:

  • npm’s official stats API: 12,921,231 downloads in the last-week window (fetched 2026-10-03)
  • npm view start-server-and-test dependencies → pins "wait-on": "9.1.0" — exact-version pinned
  • jest-dev-server → detects timeouts by string-matching the error message "Timed out waiting for". Change one word in that message and its timeout detection goes blind

Those aren’t abstract “many people depend on it.” One is an exact version pin, the other treats your error text as a protocol. A bad change here means a downstream either hangs or goes false-green: tests pass, the environment never came up. That’s the bar any change on this package has to clear, and it’s the reason every guardrail below exists.

How the work actually runs: agents in parallel at night, humans set the direction#

The new maintainer (Kevin Old, Director of Engineering at Dorvie) shipped, in week one: 27 PRs merged (24 of them reviewed and merged by the original author), 17 issues closed (the oldest opened in 2017), 6 releases (the previous one sat in July), and 243 commits for the Rust dual-engine port parked on a fork’s experimental branch.

The process isn’t magic — it’s a ready-made toolchain (Every’s Compound Engineering plugin): plan before code, implement test-first, then write the non-obvious things this run taught you into docs/solutions/ for the next agent session. The Rust port stacks one layer on top: one big task split into lanes, each lane = one issue + one plan + one PR + a fixed file list, out-of-bounds doesn’t merge. That’s how several agents run in parallel overnight without stepping on each other.

One detail I deliberately checked: most of that week was “redoing,” not “writing new.” Community PRs that had sat for years (parseArgs, TypeScript types, command resources) got each rebuilt by the agents into small, tested PRs, and the release notes still credit the original contributors. The agents didn’t invent features — they safely worked down the backlog inside a repo that already had stock, tests, and review. That precondition is exactly the one you must not skip, which is the point of the next-but-one section.

The five guardrails (the real center of this post)#

The core thesis, stated plainly: the faster the work goes, the more the project needs rules a machine can check. Neither people nor agents are right every time. These five weren’t invented on a whiteboard — they were forced out by a real miss. The hardest one: the axios-to-fetch PR quietly dropped strictSSL, ca and cert in the env-proxy branch. No test combined “HTTPS target + env proxy + TLS options,” and a reviewer had to catch it. After that, test-first became mandatory.

#GuardrailOne lineMy verdict
1test-first, mandatoryevery bug starts as a failing repro; every named risk becomes a failing test; two inputs that interact → list the combinations, one test eachthe foundation. Without it, the other four are paper discipline
2one concern per PRsplit to a granularity one person can reviewthe correct fix for parallel agent output — big diffs back to “human-reviewable” size
3a human mergesagents open the PR, the maintainer decidesthe most expensive one. It dissolves “can I trust the agent” entirely: the merge decision never leaves the human
4agents can’t touch CIRust lanes may not touch .github/workflows/, only the npm-script call to cargo xtaskthe release channel is a supply-chain attack surface; an agent that can reach CI owns the whole show
5no stored publish tokensemantic-release publishes from CI via npm OIDC trusted publishing“there is no token to steal” — turns a whole class of incident from “be careful” into “structurally impossible”

My read, stated: guardrails 3 and 5 are the two worth most. #3 dissolves the “is the AI trustworthy” anxiety — you don’t have to decide, because the merge authority stays with the human. #5 upgrades key-leak incidents from “don’t screw up” to “you literally can’t.” Both ship today, in any repo, agent or not.

What NOT to copy (equally important)#

Last section said the five guardrails are copyable. This one names the things that look cooler but will bite you:

  • 8 platform binaries in one 36MB tarball: that’s forced by wait-on’s supply-chain position — it has to be “zero install scripts, installable with ignore-scripts=true.” A normal npm package uses per-platform optionalDependencies (each platform downloads only its own), and doesn’t owe the 36MB bill. The maintainer is already cutting it (target packed 8MB, currently 15MB, size budget in CI).
  • cargo-deny + cargo-vet double gate: only needed when “a native binary enters the supply chain and you must audit the crate list.” Your JS project has no 8 native binaries to audit — the double gate is dead weight.
  • multi-worker (14 lanes) parallelism: its precondition is a strict existing test suite (496 tests + 100% line coverage on the Rust core). In the parts of your repo that tests don’t cover, one extra worker is already too many — no foundation, parallel is just parallel bugs.

The test is one line: the faster the agent, the more your existing tests and guardrails are worth — not less. Speed is the searchlight that exposes the foundation; it is not the foundation.

Why Rust on the side: for the supply chain, not for speed#

The real motive ranking for the dual-engine port is: cut the supply-chain attack surface > works without Node > startup speed > correctness. The Rust core replaces the HTTP stack and the polling loop; on the JS side, theoretically, only joi is left.

One line is worth quoting on its own, and it explains why “the binary is up” is not enough: npm provenance only proves who built the binary, not that the crates inside it are safe. So the binary needs the cargo-deny/vet double gate on top, auditing the crate list.

Don’t expect a perf win either: the addon still has to boot Node — it earns zero on startup speed. Here Rust is purely “a block you can audit as a whole.”

What I actually ran on my machine (the numbers that back the claims)#

“Only publish numbers that ran” is the rule of this site, so I ran the key ones (2026-10-03):

  1. The Rust engine is not installable yet. npm view wait-on@10.0.0-rc.1 dist.unpackedSize → 57314 (57KB); npm pack opens it: only a JS entry, 0 Rust binaries. The “36MB” is a prerelease built on the fork, never published to npm — the engine waits on the experimental branch. For this kind of material, “can I install it now” matters more than “can the author run it.”
  2. The downstream pins are real. npm view start-server-and-test dependencies → "wait-on": "9.1.0"; jest-dev-server → "^8.0.1". So the 9→10 cutover must let the JS engine run one more major alongside — that’s forced by the downstream pins, not the maintainer being cautious.
  3. What I did not verify is written as not verified. The 27 PR / 496 tests / 243 commits figures come from Kevin’s first-person write-up; I did not count them in GitHub one by one; the “four big orgs list wait-on” I checked from the link list, not repo by repo. All of it is flagged in the “Honest statement” below.

The one-line takeaway#

The author’s own line lands better than any “look what AI can do” headline:

My job is to make the tests strict enough to trust code I don’t read line by line.

For you, that’s three sentences: trusting the agent is a pseudo-question (merge authority stays with the human); the faster the agent, the more your test stock is worth (searchlight, not foundation); copy the rules, not the posture — the five guardrails ship today; the 36MB tarball and the 14 lanes are another body’s supply-chain fight.

FAQ#

Do both engines run the same tests? Yes. JS engine npm test, Rust engine WAIT_ON_ENGINE=rust-strict, the same mocha suite, no pending, 100% line/region coverage on the Rust core. I did not run it locally (the npm rc package has no Rust engine yet), so this is from the write-up.

With ignore-scripts=true, does the Rust engine work? That’s exactly the point of “8 binaries in one tarball, zero install scripts” — the container test runs it ignore-scripts=true + read-only + no network. I did not verify this one; from the write-up.

Node version requirement? 10.0 wants Node 22.19+. Verify: npm view wait-on@10.0.0-rc.1 engines.

Which ones should a normal small project copy? All five from “The five guardrails” (test-first / one concern per PR / human merges / agents can’t touch CI / no stored token). Do not copy the three from “What NOT to copy” (special-case packaging / double gate / multi-worker architecture).

Frequently Asked Questions

Can I use these 5 guardrails without any AI agent?

Yes. test-first, one concern per PR, a human merges, agents can't touch CI, no stored publish tokens — none of them depend on Rust or on any agent. A repo where humans write the PRs benefits just the same; the agent is what makes rule-check speed the bottleneck.

Is AI-maintaining a 12M/week package actually reliable?

It depends on the foundation. It only works because this 11-year package has a strict existing test suite (496 tests, 100% line coverage on the Rust core). Without that foundation, the faster the agent runs, the harder it falls. I verified the key numbers on my own machine and marked every number I did not verify.

Can I install that 36MB Rust version right now?

No. On npm, 10.0.0-rc.1 is 57KB unpacked with 0 Rust binaries (I checked with npm pack) — the Rust engine is parked on an experimental fork branch and will only land in a future major. Everything installable today is pure JS.

Should a normal project copy the cool bits (8-platform 36MB packaging, cargo-deny/vet, multi-worker)?

No. Those are forced by wait-on's supply-chain position. The test is one line: the faster the agent, the more your existing tests are worth — speed is the searchlight that exposes the foundation, not the foundation itself.
