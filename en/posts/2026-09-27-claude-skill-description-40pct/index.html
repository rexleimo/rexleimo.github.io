From 30% to 0: one Skill description line cut my token bill by 57% (measured)

After I split repeated prompts into Claude Code Skills, one started jumping into the wrong flow. Instead of quoting someone else's numbers, I built a controlled experiment on my own machine: a wide description false-triggers on 30% of requests, a one-line one on 0%; role-locking the prompt body cut tokens 57%. Everything here is reproducible.

September 27, 2026 · 6 min · 1135 words · Dreambeast -  |  中文

The conclusion up front#

I split 5 repeated prompts into Claude Code Skills, and one started jumping into the wrong flow on its own. Instead of quoting someone else’s post, I built a controlled experiment and ran it on my own machine. Two numbers out of it:

  • Wide description: 30% false-trigger rate; one-line trigger condition: 0
  • Role-locking the Skill’s prompt body: 57% fewer completion tokens, measured

A Skill’s trigger authority lives in its frontmatter description lines; the body is lazy-loaded and takes zero part in the decision. Miss this, and the more Skills you write, the louder the false-triggers get. Every number below comes with a method you can rerun.

The scene#

You know this one — you split your repeated prompts into Skills, expecting set-and-forget, and instead it starts jumping between flows on its own?

I stopped guessing and built the smallest possible differential test instead of feeling it out. The method is simple: peel the trigger decision off everything else and measure it in isolation.

Experiment 1: how many false-triggers does a wide description actually cause#

I wrote 20 fixed requests: 10 that should trigger code review (“review this code”, “there’s a bug in this snippet, check it”) and 10 that shouldn’t (“fix this NPE”, “write a quicksort”, “format this code”). Then I swapped the description between two versions and had the model answer only YES/NO for each:

DescriptionHit on the 10 that should triggerFalse-triggered on the 10 that shouldn’tFalse-trigger rate
Helps with code review and code optimization10330%
Use when the user explicitly asks for a code review, or points out a bug in a code segment that needs review900

The wide version volunteered even for “write me a unit test” — “code” and “optimization” are wide enough that you can smell it from here. The narrow one cost one recall miss (“audit this function” didn’t match); acceptable. Note the shape: trigger verb + concrete words + scenario boundary. Ever since, my habit when writing a Skill is to draft the “when should this fire” line first — if I can’t write it, the Skill shouldn’t exist as a Skill.

The mechanism: the decision only reads the listing, never the body#

Why does editing one line change anything? The docs chain:

  1. A Skill’s body loads lazily — it enters the context only at the moment of trigger;
  2. But at startup the model preloads a listing: every Skill’s name + description;
  3. Trigger decision = your request matched against that listing, not the body.

Point 3 is the foundation of the whole post: a description is not a feature blurb, it’s a trigger-condition spec for the router.

Experiment 2: role-lock the prompt, tokens drop 57%#

After fixing the trigger I made one more cut — a role-lock line at the top of the Skill’s prompt:

You are a strict code-review expert. Do exactly three things:
1. Find bugs
2. Suggest fixes
3. Point out potential risks
No small talk, no background explanation.

Same eight real code-snippet review tasks, two system prompts, hard 4096 cap, none hitting the ceiling:

ControlAverage completion tokens
Loose (“helpful assistant, may explain in detail”)1421
Role-locked (the line above)616
Reduction57% (median 61%)

The model stops rambling about why it isn’t doing something, and the output is physically shorter. Correct triggering is step one of token savings; narrowing behavior is step two. Both are line-edits, zero code changes.

The 1% budget, and why I stopped treating it as theory#

The troubleshooting section hands you a number most people scroll past: the preloaded listing has a character budget — roughly 1% of the context window. Over budget, descriptions get truncated — and what gets cut is exactly the keywords the router matches on.

I didn’t leave that as a footnote. I counted my own library: 70 Skills, 3,684 description characters total, median 55, longest 105. At a 200k window, 1% is about 2,000 characters — I’m 1.8× over. The tail of my library is already truncated in the listing, and routing has been deciding on half the information.

So my discipline is a number, not a vibe: one line per Skill description, trigger conditions only, and the whole library’s character total ÷ the 1% budget ≤ 1. Five teammates each shipping ten three-line descriptions blows it instantly — count it before truncation starts causing false-triggers, not after.

How to reproduce it on your machine#

The whole harness is about 30 lines. The core:

# Trigger test: peel off the routing decision
# ROUTER: "You are a skill router. Skill [code-review] description: {desc}.
#         Request: {req}. Trigger it? Answer YES or NO only."
# 20 fixed requests (10 relevant / 10 irrelevant), run both descriptions, count YES on the irrelevant set
# Token test: same 8 snippets, one role-locked vs one loose system prompt, mean completion_tokens

Two things before you run it: (1) freeze the 20 requests and 8 snippets to disk — the description is the only variable; (2) set the token cap to 4096 and discard any measurement that hits it. Swap the model and the direction holds but the magnitude moves — I ran this on the Agnes endpoint, flash tier.

What I want to be honest about#

  • 30% / 0 false-triggers, 57% token cut, 70 Skills / 3,684 chars / 1.8× over: all measured on this machine, with the full method above. Your machine ≠ mine, expect different magnitudes; the direction shouldn’t change.
  • The 1% listing budget is verbatim from the official docs (Claude Code Skills External link ); the 3,684/70 figures are my own inventory.
  • A community post on linux.sb reports “~40% false-trigger” (related reading below) — consistent direction, value not used here.

Which camp are you in#

  • Camp A: wide descriptions are better, I’d rather false-fire than miss → did you price the false-fires? They’re your token bill and your patience every turn. Wide isn’t safety, it’s chronic blood loss;
  • Camp B: I have a few Skills, 1% budget is plenty → fine if it’s plenty; but five teammates each with ten Skills explodes that budget, and writing the rule into team norms costs you nothing;
  • Camp C: even CLAUDE.md feels too long → then this is exactly for you. One description line is the smallest maintainable surface you have.

Frequently Asked Questions

What's the difference between a Skill and dumping everything into CLAUDE.md?

CLAUDE.md is resident in every turn — the more you add, the more tokens you burn. A Skill's body loads only when triggered, so the startup cost is just its description line. Keep hot rules in CLAUDE.md; keep low-frequency specialized workflows as Skills.

How do I pick the trigger keywords in a description?

Copy the words you actually say. If you'd type 'review this for me', 'review' belongs in the description. Concrete words beat abstract nouns — my 20-request controlled test shows the wide version false-triggers at 30%, the narrow one at 0.

What if triggers become too narrow and it stops firing when it should?

Add one or two missing trigger words, observe for a week, then add more. Piling five in at once takes you straight back to the false-trigger spiral.

Why does the official doc say some descriptions get cut?

The preloaded Skill listing (name + description) has a character budget of roughly 1% of the context window; over-budget descriptions get truncated. My own library — 70 Skills, 3,684 description characters — is already 1.8× over.
