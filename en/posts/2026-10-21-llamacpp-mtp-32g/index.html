32G One GPU + Your Existing C++ llama.cpp Can Already Run Qwen3.8-27B Faster

A 32G AutoDL box that only has C++ llama.cpp: skip vLLM and skip DSpark. llama.cpp now ships MTP speculative decoding natively (Qwen3.8's GGUFs already carry the MTP layers), one free flag; go faster by attaching a 2GB DFlash2 sidecar. FP16 won't fit on one 32G card, run Q4.

October 20, 2026 · 6 min · 1123 words · Dreambeast -  |  中文

Last week I wrote up a Qwen3.8-27B speedup test (the vLLM setup, dual A800). But the box on your AutoDL runs llama.cpp — the C++ one, binaries called llama-server / llama-cli — not vLLM. A lot of people hear “27B speedup” and assume you have to install Python, install vLLM, download a pile of draft models. You don’t. The C++ program you already have is enough.

Up front: yes, it deploys, and the C++ thing you already have is exactly the least-friction route.

Why what you have already works#

Three terms, all the rest hinges on them:

  • Quantization: compressing the model weights from full-precision floats to a tighter bit width. Q4 ≈ 4 bits per weight, saving over half the space at barely any speed cost. Think of it as downscaling a hi-res photo to phone size — detail loss is small.
  • MTP (multi-token prediction): a “fast little brain” the model ships with, baked inside the model, so you download nothing extra. Turn it on and generation gets close to 2× faster.
  • Speculative decoding: a small model guesses a run of tokens, the main model verifies them in one batch, keeps the right ones. The main model is still the final authority, so it’s lossless (not trading quality for speed). MTP and DFlash2 are both flavors of it.

Three things that matter:

  1. 32G holds Q4. Qwen3.8-27B Q4 weights run ~16–17GB; add the ~1.5GB MTP head, total ~18GB, leaving ~13GB for context (KV cache). (A size-based estimate, not measured on your box — see the note at the end.)
  2. MTP is free. llama.cpp has built MTP speculative decoding since 2026-07; Qwen3.8’s GGUFs already carry the MTP layers, so one command-line flag turns it on, zero extra downloads.
  3. You don’t need vLLM. To speed this up, the llama.cpp path is enough. The vLLM route (the one that runs DSpark) is heavier, needs Python, and needs a special-format draft model — for “I just want it faster” that’s extra work.

Three steps and it’s running#

Step 1: get the model. Use unsloth’s ready GGUF (pre-quantized, MTP layers included, works as-is). For a 32G card pick Q4_K_M or UD-Q4_K_XL (~16–17GB, leaves room for context):

# On the AutoDL box (needs huggingface tools; conda images usually have it)
hf download unsloth/Qwen3.8-27B-GGUF \
  --include "*UD-Q4_K_XL*" \
  --local-dir ./Qwen3.8-27B

Can’t reach HF from inside China? Set the mirror: export HF_ENDPOINT=https://hf-mirror.com.

Step 2: confirm your C++ llama.cpp is new enough. MTP merged into mainline in 2026-07; an old build might not have it. Run one line to see if it knows the flag:

./llama-server --help 2>&1 | grep -i "spec-type\|draft-mtp"
  • It lists draft-mtp: go straight to step 3.
  • No reaction: you have an old build, recompile a CUDA build (AutoDL’s conda image ships CUDA headers, compiling is not hard — see below).

Step 3: start the server and switch MTP on. This is the one command that matters most — it’s the default plus two --spec-* flags:

./llama-server \
  -m ./Qwen3.8-27B/Qwen3.8-27B-UD-Q4_K_XL.gguf \
  --spec-type draft-mtp --spec-draft-n-max 4 \
  -ngl 99 -fa on -c 32768 \
  --host 0.0.0.0 --port 8080

Translated into plain terms:

  • -m ... is the main model file
  • --spec-type draft-mtp: enable speculative decoding using the built-in MTP source (the free one)
  • --spec-draft-n-max 4: guess up to 4 tokens per round (longer is faster but more likely to miss; 4 is a safe start on a 32G card)
  • -ngl 99: push every layer onto the GPU (don’t leave it on the CPU)
  • -fa on: flash attention on (small memory saver)
  • -c 32768: 32K context, tune to taste
  • --host 0.0.0.0 --port 8080: open it up so you can reach it from elsewhere

Once it’s up, any OpenAI-compatible client (web UI, IDE plugin, CLI) pointed at http://machine-IP:8080/v1 works. MTP is lossless throughout — output is identical to running it off, just faster.

One notch faster: add a 2GB “drafter”#

MTP is the “good enough” tier (about 1.5–2× single-stream measured). For more, attach a DFlash2 draft model (a GGUF sidecar, Q8_0 is 2GB, a 32G card holds it easily):

hf download z-lab/Qwen3.8-27B-DFlash2-GGUF \
  --include "*Q8_0*" --local-dir ./Qwen3.8-27B-DFlash2

./llama-server \
  -m ./Qwen3.8-27B/Qwen3.8-27B-UD-Q4_K_XL.gguf \
  -md ./Qwen3.8-27B-DFlash2/Qwen3.8-27B-DFlash2-Q8_0.gguf \
  --spec-type draft-dflash --spec-draft-n-max 7 \
  -ngl 99 -fa on -c 32768 --host 0.0.0.0 --port 8080

Compared to the MTP version, the only differences are the added -md (the draft model) and --spec-type flipped to draft-dflash. Short-code / short-QA scenarios show a clear jump (official numbers put the Q8 sidecar acceptance length around 5.1; I haven’t independently reproduced it). On a 32G card at 32K long context, MTP is actually better value than DFlash2 (the DFlash sidecar keeps its own KV, cost grows with context). Pick by what you actually do.

Your old C++ build has no MTP: recompile#

AutoDL’s conda image ships CUDA (with the .h headers); recompiling llama.cpp is basically one command:

# after activating the conda env
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON
cmake --build build -j --target llama-server
# then use build/bin/llama-server with the step-3 command above

(The DFlash2 path needs a build that carries DFlash2 support; the official recipe checks out PR #27342 then builds. If that’s a hassle, just use the MTP route — the mainline build covers it.)

The honest part#

  • You can run it: 32G one card + your existing C++ llama.cpp, Q4 + MTP is the lowest-cost plan — essentially “download one model + run one command.”
  • Don’t reach for FP16: full precision is 54GB, one 32G card can’t hold it. My last article was dual A800 80G running FP16; your single card should just stay on Q4, which is plenty for most tasks.
  • There’s a ceiling: a single 32G card is the “one request at a time” scenario. My last test showed that under dozens of concurrent requests the speculative gain gets eaten by contended compute (MTP falls back at high concurrency too). If you need “me, one person, don’t make me wait,” MTP is enough. If you need “one machine holding dozens of users at once,” that’s a different equation — dual cards — don’t stack more speculation.

This piece targets “AutoDL single machine 32G, already has C++ llama.cpp.” The memory figures (Q4 ≈ 16–17G, MTP ≈ 1.5G, DFlash2 Q8 ≈ 2G, FP16 ≈ 54G) are weight-size estimates, not measured on your box; speculative-decoding gains are official/community-reported, not independently reproduced by me. Qwen3.8-27B, llama.cpp, and unsloth GGUFs are open-source projects; capability changes with versions — trust the upstream.

Is that 32G card a 4090 or a 4080 Super Ultra? Solo use, or are you hooking it up to several people? Mostly long docs or short Q&A — tell me and I’ll pick the leanest of the commands above for your case.

Frequently Asked Questions

My box only has C++ llama.cpp. Can it run the Qwen3.8-27B speedup?

Yes, and it's the least-friction route. llama.cpp has shipped MTP speculative decoding since 2026-07; Qwen3.8's GGUFs already carry the MTP layers, so one --spec-type draft-mtp flag turns it on, zero extra downloads. No need to touch vLLM.

How much quant does 32G hold?

Q4_K_M / UD-Q4_K_XL (~16–17GB) is most headroom; add the ~1.5GB MTP head and you keep ~13GB for context. Q8_0 (~24.5GB) runs but leaves only ~6GB. FP16 (54GB) won't fit one 32G card; you need a dual 80G. All figures are size-based estimates, not measured on your box.

MTP or the DFlash2 sidecar?

Solo use, lowest friction: MTP (free, lossless, ~1.5–2× single-stream). Code-heavy, want the most speed: attach the DFlash2 sidecar (Q8_0 is 2GB). At 32K long context MTP is actually better value than DFlash2 (the sidecar keeps its own KV, cost grows with context).

My llama.cpp is old and has no MTP?

AutoDL's conda images ship CUDA headers, so recompiling is basically one command: cmake -B build -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON then cmake --build build -j --target llama-server. The MTP path just needs the mainline build; DFlash2 needs a build that carries DFlash2 support (the official recipe checks out PR #27342 and builds).

Is there a ceiling on the speedup?

A single 32G card is the one-request-at-a-time scenario. Under dozens of concurrent requests the speculative gain gets eaten by contended compute (MTP falls back at high concurrency too). Enough for solo use; for multi-user throughput you need dual cards, don't stack more speculation.
