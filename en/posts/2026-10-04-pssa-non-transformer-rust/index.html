A Language Model That Doesn't Use PyTorch, Hand-written in Rust: 12x Faster Generation? I Almost Believed My Own 98x

PSSA is a 21MB repo: selective SSM loop + hyperbolic memory bank + fast-weight online updates, no PyTorch. The author says 12x faster; the in-body table says 4.13x. On my box, char-normalized it's 9.3x — and I caught the 98x fake-number trap: throughput computed on the nominal token ceiling makes the two sides' workload fundamentally incomparable. twin_check reproduces 3e-8 locally; every command re-runnable.

October 4, 2026 · 6 min · 1161 words · Dreambeast -  |  中文

PSSA is a 21MB repo: a selective SSM loop + a hyperbolic memory bank + fast-weight online updates, no PyTorch, 62 Rust files. The author’s title claims “12x faster generation” while the in-body table says 4.13x. On my box (AMD EPYC 9354P / rustc 1.99.0) I first got a nominal 98.6x, then, char-normalized, 9.3x — and caught the 98x trap.

Conclusion first#

  1. “12x” is not a lie, and not true either: it’s short-generation latency vs a Transformer; batched evaluation throughput is 4.13x (the author’s own table); on my box, char-normalized, it’s 9.3x. The calibration decides the conclusion — the 98x I first computed is a fake number, because I divided by the nominal 256-token ceiling instead of by actual output.
  2. The no-PyTorch, hand-written Rust choice is a consequence of the architecture, not a marketing stunt: per-token fast-weight online updates + in-forward writes into the memory bank mean the autograd tape chases a dynamic write every step. The cost: mixed precision, distributed training, and the profiler ecosystem are all gone.

What it is#

SSM loop + hyperbolic memory bank + fast weights. The last is the key one: every token online-fine-tunes its own weights (a ridge regression consolidates what was just learned back into the base matrix). Autograd tape is designed for “fixed params + one forward + one backward”; changing weights inside forward means chasing a changing parameter path every step — the author’s own words: “fighting the framework at every step.” So the linear algebra is hand-written Rust. The architecture picked the implementation language, not the language picking the architecture.

The 98x trap#

When I first saw 98.6x my reaction was “beats the author’s 12x, nailed it.” Then I opened both outputs: PSSA produced only 107 chars on “The quick brown fox” (hit EOS), the Transformer produced a full 1023 chars (“the the the…” degenerate loop); on “In a distant galaxy” PSSA produced 0 chars. The two sides’ workload is fundamentally incomparable; dividing by the nominal ceiling inflates PSSA’s denominator tenfold. Char-normalized: 9.3x.

One hard rule for generation benchmarks: record “how many tokens/chars were actually produced” before you compute throughput — a short EOS-truncated output inflates tok/s by tenfold or more.

12x vs 4.13x: the ruling#

The README’s two numbers aren’t contradictory, they’re two workloads:

  • Line 11 “generates text about twelve times quicker” = marketing sentence
  • Lines 199-200: 4.13x = batched evaluation throughput (199,059 tokens @ 512/update: 1716 vs 415 tok/s)
  • Line 213 table: “Generating 200 tokens” 226ms vs 2735ms = 12x = short-generation latency

Architecturally it makes sense: a loop model’s per-token cost doesn’t grow with context, the longer the generation the bigger the edge; short-latency gaps get amplified, batched-evaluation gaps get diluted by vocabulary/eval overhead. My 9.3x sits in between, same direction. A marketing number in the title, a different calibration in the body — typical.

twin_check: 3e-8 reproduced locally#

$ cargo run --release --example twin_check
round 0 forward: loss=3.98721910 max_tape_diff=0.000e0
round 0 backward: max_grad_diff=2.980e-8
CPU TWIN CHECK PASSED

This is the one thing most worth copying: after a hand-written SSM step, the two independent implementations — PyTorch autograd tape vs the hand-written backward — are run on the same input and the max forward-activation diff (0.000e0) and the max backward-grad diff (2.980e-8) are reported. 3e-8 = hand-written backward is numerically equivalent to the tape, not “close enough” — it’s correct. I reproduced it on my box exactly, and the command is above.

For teams, one takeaway that can go straight into the handbook: whenever you hand-write a kernel, keep a scalar reference path; run the two on the same input and diff forward + backward — that’s the only way to catch a “generates characters but is actually saying nonsense” hand-written kernel.

Generation quality, honestly#

Short, one sentence: what it can generate is “in the ballpark” (a fox sentence), but it’s not “good text” — the author himself says the generated text “is not good, it’s too cold.” A tiny non-Transformer that’s fast to train is a research toy, not a production model; the “can it replace GPT” question doesn’t belong in this repo’s scope.

The 2 things to steal#

① A generation benchmark must record output volume first. The 98.6x I first got was inflated by “dividing by the nominal token ceiling.” Write it down: measure tok/s only after you’ve recorded actual output tokens/chars per prompt. This is the single most common fake number in LLM evaluation, and this repo’s 12x vs 4.13x is a case study.

② Hand-write a kernel, keep a scalar reference path. twin_check reports both forward and backward max diffs; threshold 1e-6 to start; put it in CI. This is the only way to prevent a “generates but is actually saying nonsense” hand-written kernel — 3e-8 is the criterion of confidence I saw on my box.

Honesty statement#

  • All data on this box (AMD EPYC 9354P / rustc 1.99.0 / stable); PSSA’s 50K-token TF control is a small model I trained locally (1.5M params), not the author’s 12.7M-token one — only comparing kernel structure, not model quality.
  • Verified: full build 4m21s, nominal 98.6x / char-normalized 9.3x, RSS 11.6MB, twin_check 3e-8, EOS/0-char cases. Not verified (paraphrased from the original): the author’s 12x / 4.13x original environments, “trains on a laptop in hours,” the O(1) cost-advantage vs context-length claim.
  • Reproduce: git clone ... && cargo build --release && cargo run --release --example twin_check (full commands in bench/numbers.md).

FAQ#

Q: Is “12x” real? A: Depends on the calibration. 12x = short-generation latency; 4.13x = batched-eval throughput; 9.3x = my box char-normalized. Any one of them is citable, but only with the calibration attached.

Q: Does it really work without PyTorch? A: It does. 62 hand-written .rs files, 4m21s release build. But you lose mixed precision / distributed / the profiler ecosystem.

Q: Can I copy its architecture into my own project? A: The architecture (SSM + hyperbolic memory + fast weights) is one of many non-Transformer routes, not state-of-the-art; the engineering (hand-written kernel + scalar reference cross-check) is what’s directly stealable.

Frequently Asked Questions

Can you cite '12x faster'?

Yes, with the calibration. 12x short-generation latency, 4.13x batch throughput (author's table), 9.3x char-normalized on my box. Cite 12x without calibration and a batch-calibration replication will make you look wrong.

Why is no-PyTorch legitimate?

Per-token weight updates + in-forward writes into the memory bank mean the autograd tape chases a dynamic write every step — the framework fights you every step. Cost: you lose mixed precision, distributed, and the profiler ecosystem. The architecture picks the implementation language, not the other way round.

Can I steal the twin_check idea?

Yes. Hand-write any kernel, keep one scalar reference path, run both on the same input, diff the forward activations and the backward grads, threshold 1e-6, put it in CI.
