A language model that doesn't need PyTorch: hand-written in pure Rust, '12x faster' than transformers? I almost believed my own 98x number

PSSA is a 21MB repo: selective SSM recurrence + hyperbolic memory bank + fast-weight online updates, no PyTorch. The author claims 12x generation speedup; the table in the README says 4.13x. I compiled and ran it locally, measured 9.3x char-normalized, and caught my own 98x fake-number trap. Gradient cross-check 3e-8 reproduced on my machine. Fully reproducible.

October 4, 2026 · 13 min · 2573 words · Dreambeast Programming -  |  中文

PSSA is a 21MB repo trending on HN: a selective SSM loop + hyperbolic memory bank + fast-weight online updates, no PyTorch, no TensorFlow, 62 Rust files. The author says “generates text 12x faster”; the throughput table in the README body says 4.13x — two contradictory numbers. I compiled and ran it on my machine (AMD EPYC 9354P / rustc 1.99), measured 9.3x char-normalized, and caught the 98x fake-number trap I myself almost fell into: computing tokens/s against the nominal token cap makes the two workloads incommensurable. Gradient cross-check 3e-8 reproduced locally, every command reproducible.

The short version#

  1. PSSA inference is genuinely fast, but “12x faster” depends on the metric. Char-normalized on my box: 9.3x. The author’s 12x is a “generate 200 tokens” short-latency metric; the 4.13x is a 199K-token batch-eval metric — two workloads, two numbers, not contradictory but easily misread together.
  2. My first benchmark said 98.6x. That was wrong. The legacy PSSA checkpoint hits EOS early on many prompts (only 107 chars out of a 1024 cap), while the transformer ran a degenerate loop to the full 1023 chars. Dividing by the nominal cap inflates PSSA’s denominator by ~10x. The correct metric is char-normalized latency — 9.3x.
  3. The most valuable thing here isn’t model quality, it’s engineering discipline: every commit’s batched kernel is cross-checked against a scalar reference path. My local twin_check run: max_grad_diff 2.98e-8 — the author’s “3e-8” claim, confirmed on my hardware.

The architecture trio: what one token does inside PSSA#

The README breaks each layer down cleanly (quoting it + my source reading). A token entering a PSSA layer goes through four things:

  1. Selective SSM recurrence (a selective diagonal SSM, “the same family as S4 and Mamba, written out scalar-first so the backward pass can be checked term by term”) — the trunk. Per-token O(d_m·d_s) state update, constant cost regardless of context length.
  2. Hyperbolic memory-bank read (bounded read from an episodic memory bank in hyperbolic space) — at most 4 slots read per token (bounded). This is the key difference from a pure recurrence: instead of cramming everything into a fixed state, it maintains a lookup table.
  3. Learned gate (decides how much of that read reaches the residual stream) — the memory contribution is gated into the residual, so memory noise can’t corrupt the trunk.
  4. SiLU MLP — standard FFN.

Defaults: d_m = 256 channels, d_s = 16 states/channel, rank-16 adapter. Parameters concentrated in the recurrence + adapter, so memory footprint is smaller than a same-scale transformer (my RSS: 11.6MB vs 57.7MB — that’s the structural difference).

Per-token fast weights: the most radical part#

“It rewrites part of its own weights while it runs” — during inference it doesn’t run fixed weights; it online-tunes its fast weights every token (ridge regression consolidates what it learned this step back into the base transition matrix). That’s why it had to be hand-written:

  • autograd tapes assume “fixed params + one forward + one backward”; PSSA mutates weights inside every token’s forward, so backward must chase a moving parameter path — “fighting the framework at every step” (the author’s words).
  • So forward/backward are written directly in Rust, with an O(N) scalar reference path kept for cross-checking (twin_check guards that line).

The cost is explicit: you lose PyTorch’s free mixed precision, distributed training, and profiler ecosystem. The author’s call: “the architecture chose the implementation language.”

What PSSA is, and why it deserves a look#

HN’s harshest thread was about the title: “a non-transformer language model written from scratch in Rust.” The three camps in the comments:

  • “Use PyTorch, otherwise you can’t tell if it’s the architecture or the implementation that’s broken”
  • “A Rust rewrite won’t beat PyTorch by much; the ops are already Cython”
  • “Rust’s value is deployment: no more fighting pip on Windows”

The author’s README answer (quoted):

“Not for speed points, and not because the language makes the architecture better. PSSA needed per-token weight updates, a memory bank written during the forward pass… Expressing that inside an autograd framework meant fighting the framework at every step.”

I buy that reason — but the price is taking on everything the framework gives you for free (mixed precision, distributed, profiler ecosystem).

What I did: compile + local small-scale training + dual-metric throughput#

Machine: AMD EPYC 9354P (Zen4, AVX-512 fully enabled, 2-core slice here) / rustc 1.99.0 / 7.8GB RAM.

$ git clone https://github.com/Sparticle62ops/pssa
$ cargo build --release
Finished `release` profile [optimized] target(s) in 4m 21s   # 62 .rs files

The repo ships a 2.2MB legacy checkpoint (data/model.pssa, inference-only V5) but no transformer counterpart — I trained one locally, 50K tokens (train-transformer, 24.7MB, 1.5M params, same scale as the PSSA model):

$ ./target/release/oxide_ai_pssa train-transformer data/downloaded.txt \
    -o data/model.trfm --max-tokens 50000 -e 1 --no-tui
✓ checkpoint written to data/model.trfm

Note: the locally-trained TF has weak weights (50K tokens is barely learned), but the throughput comparison only measures kernel structure, not model quality — a clean methodology, flagged in my honest-claims section.

The 98x trap: how to invalidate a throughput benchmark#

When my first script printed 98.6x, my instinct was “better than the author’s 12x, ship it.” Then I opened the actual outputs of both:

  • PSSA “The quick brown fox” (cap 1024) → 107 chars (“information information to extract of information to extract patterns…”, EOS early-stop)
  • Transformer, same prompt → 1023 chars (“the the the the…” degenerate loop to the cap)
  • Prompt “In a distant galaxy” → PSSA 0 chars

The two models did fundamentally different amounts of work: one stopped early, one ran to the cap. Dividing by the nominal 1024 cap inflates PSSA’s “rate” by ~10x. The correct metric is char-normalized (chars/sec) — I recomputed: 9.3x.

Five copyable disciplines from this mistake:

  1. A generation benchmark must record actual output volume, not just wall time. I wrote chars_generated into numbers.md for exactly this reason.
  2. EOS-hit ≠ done. A generative model may “choose to stop”; counting early EOS as complete output is like letting a test-taker skip questions and turn in the paper.
  3. Lock both sides to the same workload: fixed N tokens and both run to N, or char-normalize by actual output. I used the latter and explicitly labeled the workload mismatch.
  4. A legacy checkpoint’s EOS behavior is a variable. The author’s ck64 (12.7M-token trained) and the repo-shipped 2.2MB legacy weights are not the same thing; early-EOS probability differs. Re-measure after any checkpoint swap.
  5. Throughput ratio ≠ quality ratio. A recurrence’s speed is structural, not a quality win. My TF control is a 50K-token small train; I compare kernels, not models — stated plainly in the honest-claims section.

12x vs 4.13x: resolving the README’s self-contradiction#

I scanned the whole README. The two numbers are two workloads, not a contradiction:

  • Line 11: generates text about twelve times quicker — the marketing line
  • Lines 199–200 (“And it is much faster to run”): 4.13x = batch eval throughput (199,059 tokens @ 512/update: 1716 vs 415 tok/s)
  • Line 213 table: “Generating 200 tokens” 226ms vs 2735ms = 12x = short-generation latency (fixed 200-token workload)

The architectural explanation holds: a recurrence’s per-token cost doesn’t grow with context length (fixed state); a transformer re-reads the whole context every step. So the longer the generation, the bigger PSSA’s edge; short generations (under 200 tokens) show a smaller gap, and the 199K-token batch figure dilutes into eval/vocab overhead, dropping to 4x. The “12x in the title, 4.13x in the body table” smell is the classic “marketing number in the headline, different metric in the text.” My local 9.3x (char-normalized) sits between them, direction consistent.

Gradient cross-check: 3e-8 reproduced locally#

The author says every commit’s batched kernel is cross-checked against a scalar reference path, error ~3e-8. I ran their twin_check example directly:

$ cargo run --release --example twin_check
round 0 forward: loss=3.98721910 max_tape_diff=0.000e0
round 0 backward: max_grad_diff=2.980e-8
round 1 forward: loss=4.13920069 max_tape_diff=0.000e0
round 1 backward: max_grad_diff=5.960e-8
CPU TWIN CHECK PASSED: populated-memory/carry/adapter/MLP forward and backward

Confirmed on my machine: forward is bit-exact (max_tape_diff=0.000e0), backward max gradient diff 5.96e-8 — the author’s “3e-8 scale” claim holds. This is why I say “its most valuable part is engineering discipline” — the hardest bug class in hand-written ML kernels is a batched path silently diverging from the reference path, and this repo made cross-checking a mandatory CI anchor every commit.

Output quality: 1.5M params, stated plainly#

Both models are “produces text but nonsense” tier:

  • PSSA “The quick brown fox” → “information information to extract of information to extract patterns. of information to extract patterns.” (loops, doesn’t crash)
  • TF (local 50K small train) → “the the the the the…” (pure degenerate loop)

The README itself labels this a 1.5M-param research toy model on 12.7M tokens (“a settings check rather than a final number”). Don’t compare it to any production model — the selling point is the architecture’s claim (how far recurrence + memory + fast weights can learn), not the model itself.

Recurrence vs. transformer: when should you believe “fast”?#

Once the cost model is clear, “how fast” has a bound:

  • Transformer: every step re-reads the whole context, attention O(L²), per-token cost grows with generation length L. The longer the context, the slower.
  • PSSA recurrence: per token, one fixed-size state update + a bounded memory read; cost does not grow with L (O(1)/token when L is large).

Corollary (predictable, not necessarily fully verified locally): the longer the generated text, the bigger PSSA’s edge over the transformer. The author’s 200-token short-generation 12x (table), and the 199K-token batch 4.13x (table) — short-generation latency amplifies the “fast” gap, batch gets diluted by eval/vocab overhead; the direction matches the cost model.

Applicable scenarios (screen by “how long is the context, how long is the generation”):

  • agent long context / code completion / streaming long output: the recurrence’s structural edge is worth most here; worth a dedicated test.
  • short Q&A / fixed-length tasks: the gap is less dramatic; don’t take the headline’s 12x at face value.
  • batch offline evaluation: this is the 4.13x tier, where incidental overhead dominates.

My box only did a cap-256 short-generation control (9.3x char-normalized). I did not run the full long-context O(L²) vs O(1) curve (a 2-core slice can’t hold it) — marked “unverified; the direction is inferred from the cost model.”

Why this “toy” deserves a look from your team (not: swap your model)#

The 1.5M-param PSSA outputs are nonsense, but nobody should use it as a production model — its value is the architecture, not the weights. Three “stealable” angles:

  1. Recurrence + bounded memory vs. full attention is the main battleground for long context in 2026. Agent scenarios keep pushing context to codebase scale; the transformer’s O(L²) attention cost hits the bottleneck before “quality” does. PSSA’s “per-token cost doesn’t grow with L” is structural, not a hyperparameter. If you’re choosing your next LLM architecture, the recurrence/SSM family (Mamba, PSSA-style) belongs on your radar even if you ship a transformer.
  2. The hand-written kernel + scalar-reference cross-check discipline is directly portable to your project. “Every commit’s batched kernel is gradient-cross-checked against the scalar reference path (threshold 1e-6 to start)” applies to any hand-written/optimized ML kernel — it turns the hardest bug class (silent parallel/reference divergence) into a deterministic CI check.
  3. “The architecture chose the language” is a decision point worth making explicitly. If you need per-token online weights / forward-time memory writes, autograd fights you every step — hand-written (Rust / raw C) is smoother. For ordinary architectures without dynamic parameter writes, stay on PyTorch; don’t get pulled by “pure Rust is more elegant.”

One line: don’t copy its model — copy its kernel discipline and its cost-model judgment.

Stealable takeaways#

  1. Record actual output volume in any generation benchmark — the 98x trap; 99% of repros hit it.
  2. Before writing ML kernels by hand, steal its twin_check discipline: batched kernels must gradient-cross-check against the scalar reference path every commit, threshold 1e-6 to start.
  3. PyTorch vs. hand-written: decide by whether you need per-token online weight updates. If you want fast weights / forward-time memory writes, autograd fights you every step; hand-writing is smoother. Otherwise stay on PyTorch.
  4. Recurrence vs. transformer cost model: for very long generations (agent long context, code completion), the recurrence’s “per-token cost doesn’t grow with length” is a structural edge — worth a dedicated test.

Honest claims#

  • “12x” vs “4.13x” is my reading of the README’s metrics; 9.3x is my local measurement (char-normalized, AMD EPYC 9354P 2-core slice / rustc 1.99.0). Ratio will drift across machines/core counts — read the order of magnitude and the metric method, don’t copy the absolute number.
  • The training curve (12.7M tokens, CE 3.98 vs 4.43), held-out generalization (PPL 54.4 vs 83.8, next-token acc 24.1% vs 18.0%) are all transcribed from the author’s report, not reproduced locally — a 2-core box can’t run 30,000 updates.
  • The transformer control is my local 50K-token small train (not the author’s 12.7M weights); the throughput comparison measures kernel structure, not model quality. The PSSA side uses the repo-shipped legacy checkpoint (not the author’s ck64), so early-EOS behavior is weight-dependent.
  • Reproduce: bench/gen-bench.py (dual-metric throughput + RSS), cargo run --release --example twin_check (gradient cross-check), one command each.

FAQ#

Q: So can I cite “12x faster”? A: Yes, with the metric attached. 200-token short-generation latency ~12x (author’s table), long-batch throughput 4.13x (author’s table), my local char-normalized 9.3x. Cite 12x without the metric framing and a batch-metric repro will embarrass you.

Q: Why is not using PyTorch defensible? A: PSSA has per-token weight updates + forward-time memory-bank writes; the autograd tape must chase those dynamic writes every step — the framework fights you every step. Cost: no mixed precision / distributed / profiler ecosystem. The architecture chose the language.

Q: What is twin_check, and can I steal it for my project? A: It runs the batched/parallel path and the scalar reference path on the same random input and compares max forward-activation and backward-gradient difference (~3e-8 threshold) as a mandatory CI item. Stealable: keep an O(N) scalar reference path next to any hand-written kernel (especially parallel/batched versions) and cross-check.

Q: What good is a 1.5M-param small model’s learning? A: Not a production model. Its value: verifying that “recurrence + memory + fast weights” beats a transformer at the same param count / same corpus on training loss and held-out (author-reported CE 3.98 vs 4.43) — an architecture claim, not a model deliverable.

Q: My box gets 9.3x, the author’s machine claims 12x — what’s the difference? A: Different hardware (my EPYC 9354P 2-core slice vs the author’s 2-vCPU), different PSSA-side weights (my legacy checkpoint vs the author’s ck64; early-EOS changes the actual workload). The difference is in the variables, not in the method — follow gen-bench.py’s methodology and measure your own.
