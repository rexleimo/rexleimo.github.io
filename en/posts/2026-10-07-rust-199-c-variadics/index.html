Rust 1.99: C-Style Variadics Are Finally Definable in Rust — I Wrote a Sum Function and Let C Code Call It

Rust 1.99.0 (released Oct 1) moves extern "C" variadics to stable: Rust can now DEFINE (not just call) C-style ... functions, with ABI matching C's va_list. Measured on stable: C code calling three Rust variadic functions — i32 sums, a C string pointer, and mixed-ABI interleaving — all verified against independently computed C expectations, zero #![feature] gates. Plus two other new stabilizations: Vec::into_parts, String::from_utf8_lossy_owned.

October 7, 2026 · 6 min · 1230 words · Dreambeast -  |  中文

Rust has carried one 30-year gap with C: C variadic arguments — the ... in printf — could be called from Rust but never defined in it. Rust 1.99.0 (released Oct 1) closes that gap: extern "C" variadics lands in stable, with std::ffi::VaList shipped alongside. On my stable toolchain I closed the full loop: three Rust-defined variadic functions, called from C, with C independently computing its own expectations — all three matched, and not a single #![feature] gate was needed. This post publishes the reproducible code, the C-side driver, and two other 1.99 stabilizations I verified while I was at it (Vec::into_parts, String::from_utf8_lossy_owned).

The verdict up front: three facts#

  1. The ... syntax compiles on 1.99 stable with no feature gate: pub unsafe extern "C" fn f(n: u32, ap: ...) -> i64 — verified against rustc 1.99.0 on this box.
  2. The definition must be an unsafe fn: rustc enforces this explicitly (error text below), not as a style choice — variadic reads have no type-system backstop, and unsafe is the entry ticket.
  3. VaList is ABI-identical to C va_list: next_arg ≡ va_arg, clone ≡ va_copy, drop ≡ va_end, and it can cross the FFI boundary (the doc’s own words).

Rust side: three variadic functions (compiles as-is on stable)#

// variadics.rs — rustc --edition 2021 -O, no feature gate
use std::ffi::{c_char, VaList};
use std::os::raw::c_void;

/// sum of `count` i32 variadics
#[no_mangle]
pub unsafe extern "C" fn sum_i32s(count: u32, ap: ...) -> i64 {
    let mut va: VaList = ap;
    let mut sum: i64 = 0;
    for _ in 0..count {
        sum += unsafe { va.next_arg::<i32>() } as i64;
    }
    sum
}

/// read a C string pointer out of the variadic list
#[no_mangle]
pub unsafe extern "C" fn first_cstr(ap: ...) -> *const c_char {
    let mut va: VaList = ap;
    unsafe { va.next_arg::<*const c_char>() }
}

/// mixed types: fixed i32 arg + pointer/i32 interleaved in the variadics
/// (validates ABI slot alignment)
#[no_mangle]
pub unsafe extern "C" fn mix3(a: i32, ap: ...) -> i64 {
    let mut va: VaList = ap;
    let p = unsafe { va.next_arg::<*mut c_void>() };
    let b = unsafe { va.next_arg::<i32>() };
    (a as i64) * 1000 + ((p as usize) >> 48) as i64 + b as i64
}

// entry point: Rust main drives the C-side test harness
extern "C" { fn c_run(ok: *mut i32); }
fn main() {
    let mut ok: i32 = 1;
    unsafe { c_run(&mut ok) };
    if ok != 1 { std::process::exit(1); }
}

Note that all three definitions are unsafe extern "C" fn ... ap: .... When I first compiled without unsafe, rustc’s error was:

error: functions with a C variable argument list must be unsafe
  --> variadics.rs:13:40
   |
13 | pub extern "C" fn sum_i32s(count: u32, ap: ...) -> i64 {
   |                                ^^^^^^^
help: add the `unsafe` keyword to this definition

Definition is unsafe. File it under muscle memory: a variadic function is an FFI boundary with no type-system backstop.

C side: calls + independent cross-checks#

// c_harness.c — gcc -c c_harness.c -o c_harness.o
#include <stdio.h>
#include <stdint.h>

extern int64_t sum_i32s(uint32_t count, ...);   // exported from Rust via #[no_mangle]
extern const char* first_cstr(...);
extern int64_t mix3(int32_t a, ...);

void c_run(int32_t* ok) {
    // 1) i32 sums: C computes its own expectation first
    int32_t vals[5] = {42, -7, 20, 100, -1};
    int64_t expect = 0;
    for (int i = 0; i < 5; i++) expect += vals[i];
    int64_t got = sum_i32s(5, 42, -7, 20, 100, -1);
    printf("[sum]  expect=%lld  rust-variadic=%lld  %s\n",
           (long long)expect, (long long)got, got == expect ? "match" : "MISMATCH");
    if (got != expect) *ok = 0;

    // 2) C string pointer through the variadic list
    const char* s = first_cstr("hello-from-rust");
    printf("[cstr] rust read back -> %s\n", s ? s : "(null)");
    if (!s || s[0] != 'h') *ok = 0;

    // 3) mixed ABI: fixed arg 7 + pointer/i32 interleaved in variadics
    int32_t b = 3;
    void* p = (void*)0xABCDUL;          // 32-bit address, >>48 = 0
    int64_t expect3 = (int64_t)7 * 1000 + ((uintptr_t)p >> 48) + b;
    int64_t got3 = mix3(7, p, b);
    printf("[mix]  expect=%lld  rust-variadic=%lld  %s\n",
           (long long)expect3, (long long)got3, got3 == expect3 ? "match" : "MISMATCH");
    if (got3 != expect3) *ok = 0;

    printf("\n== %s ==\n", *ok ? "ALL PASS (C calling Rust variadics)" : "FAILED");
}

Measured result (rustc 1.99.0 / gcc 13.3, x86-64)#

$ gcc -c c_harness.c -o c_harness.o
$ rustc --edition 2021 -O variadics.rs -o var-test -C link-args=c_harness.o
$ ./var-test
[sum]  expect=154  rust-variadic=154  match
[cstr] rust read back -> hello-from-rust
[mix]  expect=7003  rust-variadic=7003  match

== ALL PASS (C calling Rust variadics) ==

All three pass. Case 1 validates next_arg::<i32> across the FFI boundary; case 2 reads a pointer; case 3 deliberately interleaves a fixed argument with pointer/int variadics — under the x86-64 SysV ABI, arguments past the 4th slot spill to the stack, and pointer/int interleaving is where off-by-one slots bite.

One methodology point: the cross-check runs in C, independently — C does the addition itself; Rust only pulls values out of the VaList. Agreement means the ABI slots lined up; “Rust says so” would mean nothing.

Two other 1.99 stabilizations, verified while I was at it#

Vec::into_parts / Vec::from_parts — split a Vec into (ptr, len, cap) and reassemble; from_parts is unsafe:

let v = vec![10, 20, 30, 40];
let (ptr, len, cap) = v.into_parts();
let v2 = unsafe { Vec::from_parts(ptr, len, cap) };
assert!(v2 == vec![10, 20, 30, 40] && v2.capacity() == 4);   // passes on this box

String::from_utf8_lossy_owned — lossy UTF-8 replacement that stays owned, killing the “from_utf8 → handle Err → from_utf8_lossy → into_owned” dance:

let bad: Vec<u8> = vec![0x41, 0xff, 0xfe, 0x42];   // A + two invalid bytes + B
let s = String::from_utf8_lossy_owned(bad);
// s = "A\u{FFFD}\u{FFFD}B", length 8, exactly two U+FFFD

Cross-checked against the legacy path on this box: byte-identical result.

Boundaries, stated#

  • x86-64 Linux (SysV ABI), rustc 1.99.0 stable, gcc 13.3. Variadic register rules differ per ABI (Windows x64, ARM64); next_arg behavior is ABI-defined and I did not test cross-platform.
  • next_arg only reads VaArgSafe types (integers/pointers). If the type doesn’t come out, it doesn’t come out — the type system isn’t backstopping this; that’s exactly what the unsafe costs you: you guarantee the caller’s type is compatible with T.
  • The VaList binding is constructed automatically by the ... desugar (≡ va_start) and dropped with va_end semantics — don’t also call C’s va_start/va_end by hand; that’s a legacy pattern.

1.99 is worth more than this one feature#

Variadics are a “finally expressible inside a Rust module” hole-closure (before, C API stand-ins had to stay in C); the two other APIs kill recurring FFI/string-handling awkwardness. 1.99 is one rustup update away with no breaking changes.

Frequently Asked Questions

Do variadics still need nightly in 1.99?

No. Plain 1.99.0 stable compiles with zero feature gates on this box. The cost: the definition must be an unsafe fn (rustc enforces it), and only VaArgSafe types can be read.

Is it really equivalent to C's va_list?

ABI-equivalent: std::ffi::VaList is documented as layout-compatible with the platform va_list; next_arg == va_arg, clone == va_copy, drop == va_end, and it crosses FFI boundaries.

When would you actually use this?

Writing Rust stand-ins for C libraries (the printf family), implementing APIs declared in C headers from Rust, and FFI shims. Before 1.99 that code had to live in C.

What happens if next_arg reads the wrong type?

Nothing catches it — the value is reinterpreted as T; a misaligned read means misaligned machine-code semantics, and whether it crashes is luck. That is why the definition must be unsafe: the compiler pushes all ABI responsibility onto the caller.

Versus C's va_arg macro, what does this add?

ABI-equivalent (layout and read order follow the platform ABI). What changes is the shape: values come through an iterator-style next_arg with no macro expansion, VaList owns a Drop (the va_end equivalent, no leak), and it is Clone-able (the va_copy equivalent). Rust semantics on top of the same ABI contract.
