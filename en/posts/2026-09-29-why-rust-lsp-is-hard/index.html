Why a Rust LSP Is Hard: the Author of rust-analyzer Stopped Writing, and a Newcomer Pried the Door Back Open

The rust-analyzer blog went quiet in 2023, and deep explanations of LSP internals have been scarce ever since. On September 16, Igor Aleksanov (popzxc), author of the Rust Glancer LSP, published 'Why building a Rust LSP is hard' — a long architectural walkthrough covering the virtual filesystem, query concurrency, layered indexing, and the art of guessing what the user meant. This piece pulls out the layers he argues best: why the same problem (indexing code) has two orthogonal answers — lazy salsa with cache priming versus eager full analysis flushed to disk — and why an LSP differs from a compiler at the root: the compiler has a 'done', the LSP never does.

September 29, 2026 · 7 min · 1470 words · Dreambeast -  |  中文

The upshot, first#

The rust-analyzer blog went quiet in 2023. matklad stopped writing about LSP internals, and for three years the deep stuff lived in unread source code. Then a name most people had never heard (next to matklad, anyway) pried the door back open: Igor Aleksanov, the Rust Glancer author, published a long post on September 16 — Why building a Rust LSP is hard External link .

The opening meme deserves to be quoted in full: “hello, r/rust, speaking” — “matklad doesn’t write about LSPs anymore” — “then write about LSPs yourself” — “me???”

The reason to read it isn’t “another LSP post.” It’s that the author holds two weapons at once: a close reading of the entire rust-analyzer codebase (he says he read a lot of it before writing) plus his own from-scratch LSP scars (Rust Glancer). A person who paid the cost of both routes can say “this is actually hard” with a specific hole attached to every claim, not a vague complaint. Three up-front conclusions:

  1. The root difference between an LSP and a compiler: the compiler has ‘done’, the LSP never does. Compilation is binary — built or not. An LSP has to serve useful results while you’re mid-typo, forever “guessing what the user meant.”
  2. The same problem (how to index code) has two orthogonal answers: rust-analyzer’s lazy salsa plus cache priming, and Rust Glancer’s eager full analysis flushed to disk. Neither is right; they differ in which slowness you tolerate.
  3. “Hard” isn’t any single technique. It’s every boundary condition holding at once: UTF-16 offsets, line-ending detection, out-of-band file mutations, pathological symbols with millions of matches. The author’s line nails it: building LSPs is all about pathological cases.

The compiler has ‘done’. The LSP doesn’t#

The protocol’s first initialize request already exposes the essential difference. A compiler defines “done” bluntly: the binary exists or it doesn’t. Stop after 715 of 716 crates and you get cursed at.

An LSP has no such concept. It must be useful on the first millisecond — symbol lists, hover types, completions, while the file is grammatically broken, because that’s the state you’re in while writing.

That’s the full weight of the post’s central claim: the LSP is a guessing game where every step presents a possibly-wrong state, and your job is to guess what the user intends next. A compiler may refuse broken code. An LSP can’t — its entire job is to walk you from broken to working.

A concrete example: textDocument/hover. The cursor sits on Bar in fn foo(a: Bar) {} and you owe the user an answer to “where did this Bar come from.” The chain: parse → build an item tree → resolve modules into a definition map → find the symbol under the cursor → extract its docs. Each step depends on the previous one, and the file may not even parse right now. rust-analyzer flattens the chain with salsa; Rust Glancer flattens it by having done the analysis ahead of time. Same problem, two answers, completely different cost models.

The filesystem: not in the protocol, but you must sync it anyway#

By design the LSP protocol keeps you away from the filesystem — you get “documents and edits,” because the document may be unsaved and unknowable.

The trap: the LSP assumes it’s the single source of truth, while your code sits on disk and git, formatters, and a second terminal are mutating it. The client’s notifications of those external edits are, in the author’s words, “not very faithful.”

The fix is a virtual filesystem with source generations: every request carries a version of the source state, and when the state changes, in-flight queries are invalidated and re-run. Elegant on paper, a never-ending race in practice. This is where “building an LSP is a special kind of masochism” comes from: roughly 90% of the code is state consistency, and 10% is the language itself.

Two indexing philosophies: lazy vs. eager#

This is the most valuable comparison in the post, scattered across sections. Compressed into one table:

Dimensionrust-analyzer (salsa route)Rust Glancer (eager route)
Core ideaDeclare input→output rules; lazy + memoized; no active indexingOne full analysis at startup, results flushed to disk
MemoryState stays in memory (the salsa database)Low: syntax trees evicted after use; state lives on disk
First responseSlow (needs cache priming to pre-run the workspace’s semantic layer)Fast (analysis is already on disk; only recompute what changed)
Editor restartRecompute everything (expensive)Near-instant (just read the disk)
RefactorsBuilt on parser infrastructure (rowan) — elegantDedicated hand-written algorithms, no rowan — “less elegant, works well”
CostHigh memory, slow restartsSlow first index, more implementation

The takeaway: choosing an LSP architecture isn’t choosing “correct”; it’s choosing which slowness you can live with. rust-analyzer’s slowness is felt on every keystroke; Glancer’s is one-shot (the first index), after which you can kill the editor at will.

matklad’s own review of Rust Glancer is worth quoting: two orders of magnitude less RAM than rust-analyzer, “incredibly cool.” He also poked an open wound in rust-analyzer: the ideal architecture would back dependency PSI from .rmeta files instead of running salsa over thousands of crates you never opened — his line about rust-analyzer being “that half-drawn horse meme, except only the head half” is self-deprecation with a point.

The pathological case: one Option wrecks your query plan#

The funniest section. find references — you hit option+shift+F12 on Option in VS Code, and the server must distinguish this Option from every other Option in function bodies across the entire workspace.

“It’s just searching for Option” — no. A reference search plan text-matches to find files that might contain the identifier, then walks bodies precisely. If 4,000 crates each use Option, you walk 4,000 bodies. rust-analyzer’s own blog calls this mechanism what it is: an inverted index with pruning.

The author’s closing line is the one worth pinning to your wall: “If you’re thinking ‘sure, Option has lots of textual matches, but that’s a pathological case’… building LSPs is all about pathological cases that ruin the experience for users.”

The protocol itself is working against you#

Two protocol-level traps deserve more airtime:

  1. UTF-16 line:column. The LSP counts characters in UTF-16 code units (the editor world’s de facto standard), while your source is UTF-8 and positions are lines and columns. The fix is a protocol bridge: work in UTF-8 offsets internally, convert only at the communication boundary — which requires a per-file line index, turning “parsing” into a stateful operation.
  2. Line endings. You can’t assume \r\n on Windows and \n on Unix — one repo mixes both. Guess wrong once and an edit lands in the wrong byte. So beyond the line index you must detect and store each file’s newline flavor.

The pattern: every “small” protocol convention becomes a per-file metadata state machine in your implementation. In LSP architecture, state is not the exception. It’s the norm.

Honesty box#

  • Everything here is from popzxc’s post, matklad’s Rust Glancer review, and the rust-analyzer blog. I have not read Rust Glancer’s source; the architecture comparison stands on the two authors’ own descriptions.
  • “Two orders of magnitude less RAM” is matklad’s claim, not something I reproduced locally.
  • Glancer is explicitly experimental. I have no production-readiness opinion and I’m not vouching for one.

FAQ#

Can Rust Glancer replace rust-analyzer today? The author frames it as experimental, focused on low memory and instant restarts, not feature parity. Try it if you like, but don’t expect completion and refactoring to match rust-analyzer — it’s a different route to the same destination, not a better build of the same product.

What’s the highest-leverage prerequisite for understanding LSP internals? salsa. The post points at it directly: two evenings, and read rust-analyzer’s Durable Incrementality External link and the find-usages post External link alongside it. Without salsa you can’t follow half of rust-analyzer’s code.

What does “the compiler has done, the LSP doesn’t” actually cost in practice? It means the LSP can never refuse to work. The compiler sees broken code and hands you errors; the LSP must keep completing, hovering, and diagnosing on the broken code — because that’s how you get from broken to working. That single sentence explains why all LSP engineering complexity lives in “availability under inconsistency” rather than “correctness.”

Frequently Asked Questions

What is Rust Glancer, and how does it relate to rust-analyzer?

Rust Glancer is an experimental Rust LSP by popzxc (Igor Aleksanov) aimed at low RAM and instant editor restarts — matklad puts it at two orders of magnitude less memory than rust-analyzer. It isn't a drop-in replacement; it's a second solution to the same problem, and the post's value is in holding both solutions side by side.

What makes an LSP hard? It's just an autocomplete API.

Three things: (1) a compiler has a binary 'done' — built or not; an LSP must serve useful results while your code is half-typed and necessarily broken. (2) Queries differ in cost by orders of magnitude — hover is cheap, find-references scans function bodies across the workspace — so you need parallel read queries that get cancelled the instant state changes. (3) The LSP protocol has no filesystem: only documents and edits, while the real files keep changing outside the editor in a race you can never fully win.

What is salsa, and why is it worth studying?

salsa is the incremental computation database rust-analyzer builds on: declare input→output rules, outputs are lazily computed and memoized, and only invalidated outputs recompute. The author's verdict: salsa 'feels like magic' — spend two evenings understanding it and you won't be the same. Read it alongside rust-analyzer's 'Durable Incrementality' post.

Does an end user need to care about any of this?

If you're not writing an LSP, no. But it does explain your IDE's hiccups: the lag is usually not one slow query, it's a state change cancelling a pile of in-flight queries. Knowing 'there is no done, only not-yet-enough' lets you tell a broken tool from a busy one.
