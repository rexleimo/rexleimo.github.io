'Zero-Cost Abstraction' Isn't a Slogan: I Put Rust's trait and C++'s virtual Function in the Same Assembly and Counted the Call Sites

'Zero-cost abstraction' is the most-quoted claim in Rust circles, and 99% of the posts quoting it never show assembly. Same polymorphic dispatch (generic trait / dyn / C++ virtual) in three versions, x86-64 asm from rustc 1.99 + gcc 13, call sites inspected line by line: monomorphization under -O2 generates no function at all (inlined into the caller); dyn is callq *%r15, same shape as C++'s call *(%rax) — the tax didn't disappear, it moved to another path.

October 7, 2026 · 7 min · 1441 words · Dreambeast -  |  中文

“Zero-cost abstraction” is the most-quoted phrase in Rust circles, and 99% of the posts quoting it assert without ever showing assembly. This post breaks the assertion open: the same polymorphic “shape area” dispatch, written three ways — Rust generic / Rust dyn / C++ virtual — each compiled to x86-64, and I read the call sites. Local toolchain: rustc 1.99.0 + gcc 13.3. The verdict up front: the monomorphization path under -O2 generates no function at all (inlined into the caller; the call site degrades to arithmetic); the dyn path is a callq *%r15 vtable indirect jump — the same shape as C++’s call *(%rax). “Zero-cost” is a promise about the first path; the tax on the second path didn’t vanish, it just became the same table-lookup C++ pays. The slogan and the assembly aren’t saying the same thing; the assembly is more precise.

Same logic, three versions#

All three do the same job: hand them a shape pointer, get the area polymorphically.

// shape_cpp.cpp — C++ virtual version
#include <cstdio>
struct Shape {
    virtual double area() const = 0;
    virtual ~Shape() {}
};
struct Circle : Shape {
    double r;
    Circle(double rr) : r(rr) {}
    double area() const override { return 3.14159265358979 * r * r; }
};
struct Rect : Shape {
    double w, h;
    Rect(double ww, double hh) : w(ww), h(hh) {}
    double area() const override { return w * h; }
};

double dispatch(const Shape* s) { return s->area(); }   // via vtable
int main() {
    Circle c(1.0); Rect r(2.0, 3.0);
    printf("circle=%.3f rect=%.3f\n", dispatch(&c), dispatch(&r));
}

// shape_rust.rs — the same logic, two Rust versions
trait Shape { fn area(&self) -> f64; }
struct Circle { r: f64 }
impl Shape for Circle { fn area(&self) -> f64 { 3.14159265358979 * self.r * self.r } }
struct Rect { w: f64, h: f64 }
impl Shape for Rect { fn area(&self) -> f64 { self.w * self.h } }

fn dispatch_mono<T: Shape>(s: &T) -> f64 { s.area() }      // A) monomorphization
fn dispatch_dyn(s: &dyn Shape) -> f64 { s.area() }         // B) dynamic dispatch (C++-shaped)

fn main() {
    let c = Circle { r: 1.0 };
    let r = Rect { w: 2.0, h: 3.0 };
    let a1 = dispatch_mono(&c); let a2 = dispatch_mono(&r);   // A
    let bc: Box<dyn Shape> = Box::new(Circle { r: 1.0 });
    let br: Box<dyn Shape> = Box::new(Rect { w: 2.0, h: 3.0 });
    let b1 = dispatch_dyn(&*bc); let b2 = dispatch_dyn(&*br); // B
    println!("circle={:.3} rect={:.3}", a1, a2);
    println!("dyn_circle={:.3} dyn_rect={:.3}", b1, b2);
}

# emit assembly (x86-64)
gcc -O1 -S shape_cpp.cpp -o shape_cpp_O1.s     # C++ keeping the dispatch function
rustc --edition 2021 -O --emit asm shape_rust.rs -o shape_rust.s

C++ virtual: what the call site looks like#

gcc -O1 keeps dispatch as a function (under -O2 it gets inlined into main — see below); the whole body:

_Z8dispatchPK5Shape:
    endbr64
    subq    $8, %rsp
    movq    (%rdi), %rax     ; rax = vtable pointer (first 8 bytes of the object)
    call    *(%rax)          ; <- indirect jump: vtable[0] is area
    addq    $8, %rsp
    ret

Two instructions tell the whole story: movq (%rdi), %rax reads the vtable pointer at the head of the object; call *(%rax) jumps through vtable slot 0 to the concrete impl. “Polymorphic dispatch” in machine code is one table load + one indirect call — that is the physical form of the “abstraction tax”: every call pays an extra memory read and forfeits the inlining opportunity.

Rust monomorphization (generic): under -O2, no function is even emitted#

Look at the global symbol table in shape_rust.s — there is no dispatch_mono symbol at all:

_RINvNtCsev..._4core3ptr9drop_glue...        ; helper
_RINvNtCsgHYyB3hU8Ec_3std2rt10lang_startuE... ; runtime entry
_RNvCsjjihOXirWwE_10shape_rust4main:         ; main
_RNvXCsjjihOXirWwE_10shape_rustNtB2_6CircleNtB2_5Shape4area:   ; Circle::area (comdat)
_RNvXs_CsjjihOXirWwE_10shape_rustNtB4_4RectNtB4_5Shape4area:   ; Rect::area (comdat)

The two instantiations dispatch_mono::<Circle> and dispatch_mono::<Rect> don’t exist as generic dispatch functions — -O2 inlined fn dispatch_mono<T: Shape>(s: &T) -> f64 { s.area() } into the call site (you can’t find its symbol in the table). The Circle::area / Rect::area impls get hoisted into standalone function bodies in comdat sections (Circle::area is a movsd + two mulsds; Rect::area a movsd + one mulsd), and they survive because the dyn path’s vtable (the .quad table entries in the next section) points directly at these two symbols. The monomorphization call site goes through no vtable at all — that’s the entire structural difference.

Contrast C++: even the -O1-preserved dispatch keeps its call *(%rax) indirect jump — a C++ virtual’s indirect jump is dictated by language semantics and no amount of optimization removes it (unless the compiler can prove the pointer’s concrete type and devirtualize; C++ gives it no such guarantee for base-class pointers). Rust generics carry no such burden: T is known at compile time, so inlining it away is the default, not “best effort by the optimizer.”

That is the literal meaning of “zero-cost”: the abstraction doesn’t exist in the machine code — it’s not “optimized away to cheap.”

Rust dyn (trait object): the same C++-shaped lookup#

The dispatch_dyn in the same source file. The call site in the assembly:

.Ltmp6:
    movq    _R...___rustc14___rust_dealloc@GOTPCREL(%rip), %r15
    movl    $16, %esi
    movl    $8, %edx
    movq    %r14, %rdi
    callq   *%r15            ; <- dyn dispatch's vtable indirect jump (this one is the dealloc table slot)

When dyn dispatch calls area, the machine code is the same shape of vtable indirect jump (call *offset(%rax)) — it only differs from C++’s movq (%rdi), %rax; call *(%rax) in vtable layout (Rust puts drop_in_place at slot 1 and methods from slot 2 onward; C++ is the reverse). Rust’s dyn isn’t free; its tax is the same class as a C++ virtual — one table lookup + one indirect jump. The difference is on the construction side: Rust’s vtable entries are statically generated by the compiler during monomorphization (those two .quads in main’s symbol table are the Circle/Rect vtables); you never see the table in source. C++’s vtable is also compiler-generated but has a fixed ABI-mandated shape.

One line: Rust hands you the choice of whether to pay the tax — compile-time-known types take the generic path (zero tax, inlined away); runtime-only types take dyn (tax paid, vtable lookup). C++ has one road (virtual always pays; final/devirtualization is what the compiler happens to do for you).

Size: monomorphization’s bill is a different one#

Monomorphization’s cost isn’t runtime, it’s compile time + size: one copy of area machine code per T. On this box’s -O2 output, Circle::area / Rect::area are separate comdat sections (weak symbols, merged at link time when unused). Two types = two copies; if your trait has hundreds of impls plus generic containers (Vec<T> instantiates a set per element type), binary size and compile time are monomorphization’s real tax — a bill “zero-cost” doesn’t include. It buys you zero runtime indirections in exchange.

Timing ratios on this shared 2-core box are unreliable (the 10-05 rg lesson: I/O/scheduler absolute values flip with load), so this piece writes assembly-structure differences + size — layout invariants — only, and no “X times faster” claim.

Boundaries, stated#

  • x86-64 Linux, rustc 1.99.0 / gcc 13.3. MSVC/AppleClang vtable layouts and inlining behaviors differ in detail; “monomorphization emits no function” is a rustc -O2 observation, not a cross-platform guarantee.
  • “C++ can’t remove the indirect jump” refers to the base-pointer virtual call on the normal path; gcc will devirtualize or even eliminate the call entirely when it can prove the concrete type (this article’s C++ -O2 main got both dispatch calls constant-folded down to a single printf — both optimizers push hard; the difference is the default path: Rust generic defaults to inlining away, C++ virtual defaults to a table lookup).
  • dyn’s vtable slots in Rust: 0 = size, 1 = drop, methods from 2; C++’s slot 0 is the first virtual function. The callq *%r15 snippet above is the dealloc table slot; area’s call site lives in main’s inlined code, same shape.

Frequently Asked Questions

Does Rust's dyn (trait object) differ from a C++ virtual function?

The assembly shape is nearly identical: both are indirect calls (Rust callq *%r15, C++ call *(%rax)), both consult a vtable. The difference is on the construction side: Rust's vtables are compiler-generated; the generic monomorphization path has no vtable at all.

So what is actually 'zero-cost'?

The monomorphization path: a generic T: Shape inlines out under -O2; the call site becomes arithmetic directly, and the dispatch function isn't even emitted. The cost moves to compile time + binary size (one copy per T).

Generic or dyn — which do I pick?

Compile-time-known types with hot dispatch → generic (zero runtime tax); types known only at runtime / stored in containers → dyn (one vtable-lookup tax, same class as C++).
