Rex, the New Terminal From Ghostty's Creator: A Multiplexer Shouldn't Sit Inside a Fast Terminal

Mitchell Hashimoto's new company Superlogical shipped its first product: Rex, a terminal multiplexer built on libghostty where the multiplexer IS the terminal. Persistent sessions, remote connections, program activity status. macOS public testing opened 10-05.

October 20, 2026 · 6 min · 1168 words · Dreambeast -  |  中文

Mitchell Hashimoto started another company, Superlogical, announced 07-29, with its first product in public testing since 10-05. The product is Rex, a terminal multiplexer. A man who just donated Ghostty to a non-profit and said he’d stop commercializing terminal work is back with a terminal company — that fact deserves two sentences before the product does.

Why “again” with terminals#

Hashimoto’s own account of the path: Ghostty was a “project I thought I’d throw away” from 2023, which grew into millions of daily users, a dozen core maintainers, and nearly 50 localization members, donated to a federally recognized non-profit in 2025 with the public-benefit purpose legally bound in.

But a decade of building terminals made him increasingly curious about the problems around the terminal: why is terminal usage more widespread than ever? Where is terminal IO heading in the agent era? What is tmux’s relationship to a fast terminal? He writes that these questions stopped fitting inside a non-profit project, and became the entire premise of Superlogical. Rex is the entry point; his own words: the multiplexer “isn’t the entire vision.”

What Rex is solving#

The existing multiplexer structure: you open a fast terminal (Ghostty/Kitty/Alacritty) and run tmux/zellij inside it, where the multiplexer emulates a slow terminal again. Hashimoto’s self-estimate: modern terminal IO paths are one to two orders of magnitude faster than a multiplexer’s inner emulator, so what you get is “the slow experience inside the fast terminal” — scrollback hiccups, weird selection behavior, dropped-frame scrolling, all the inner emulator’s fault.

Rex’s architectural claim is the inverse: the multiplexer should just be the terminal. It’s built on libghostty (the MIT terminal library the Ghostty team extracted, already powering Vercel’s Turborepo), with the outer layer native. Persistent sessions, remote connections, and program activity status are the headline features. The official pitch: “a drop-in replacement for whichever terminal you use today” — close the app and the session survives, reconnect from another device, remote development connects straight in. A companion CLI does automation and hooks (Hashimoto gave that CLI its own X post).

This one official screenshot lays Rex’s claim out on a single image: a row of session tabs up top, each tab a remote-capable terminal (rex-snake on a Mac Studio, Bun, fish, all open in parallel); an agent session running code review top-left; an embedded interactive Git panel (Stage/Commit/Stash keybindings) bottom-left; a Snake TUI running on the right. tmux’s equivalent screenshot is a grid of green-on-black text. What Rex sells is “this layer itself is an application.”

For agent workflows this is a real need: a long task’s terminal dies or the network drops, the session survives, its state is visible, reconnection picks up where it left off — what tmux does half-way, Rex designed as a first-class feature.

The CLI layer is the part worth playing with during public testing. Hashimoto posted the companion CLI himself: use Rex as the automation entry point, hook into CI, open tasks for coding agents, read program activity status from scripts. tmux’s CLI is that 20-year-old tmux send-keys interface; Rex makes “program activity status” a first-class citizen — which step an agent is on inside a session, which approval it’s stuck at, queryable from a script. In the public testing docs, CLI and remote connections are co-equal headline features, not a later patch.

Three things to watch#

It’s not a portable toolchain yet. Public testing is macOS only, no Linux date. tmux’s biggest asset isn’t its features, it’s “it’s on every machine.” Rex can’t take that short term; its real competition is zellij and the existing habit of “Ghostty plus tmux.”

There’s tension between company form and product promise. Ghostty’s non-profit donation is the source of the trust; Superlogical is a commercial company. Hashimoto’s personal post deliberately writes “Ghostty stays non-profit: mission, governance, license, roadmap unchanged,” separating the two lines — but libghostty was extracted from Ghostty, and Rex’s commercial product sits on libghostty. How that dependency chain gets governed later is worth watching. What public info shows already: Vercel’s Turborepo consumes libghostty, so the interface stability between a commercial closed product and a non-profit foundation library is a question both sides have to answer.

The “durable session layer” ambition is bigger than today’s multiplexer. Cross-device, agent background tasks, shared terminals, incident response — each one lands in the mature territory of VPC/remote-dev/collaboration tooling. This isn’t something a terminal project finishes alone. Superlogical’s real bet is the terminal’s position as agent-era infrastructure; Rex is the opening move. Four people (Hashimoto, Pearkes, Monk, Simpson), all with terminal or infrastructure product backgrounds, a cast built for “narrow and deep.”

FAQ#

Is Ghostty going to be abandoned? No. Donated to a non-profit with ~12 core maintainers continuing development, Hashimoto still among them; Superlogical’s statement is explicit that Ghostty’s license and roadmap are unchanged.

Linux users? macOS only during public testing. libghostty is cross-platform, the architecture can land on Linux, but the official side gives no date. For now, Mac only.

Can it coexist with tmux? Yes. Rex’s positioning is replacing the whole “terminal + multiplexer” chain, and it doesn’t stop you running tmux in any terminal; conversely, Rex’s session persistence is compatible with the old habit of running tmux inside Rex.

How do I get the beta? Register the newsletter on superlogical.com; public-testing invites have gone out in waves since 10-05. The team is hiring engineering and design (jobs page is live).

Worth switching now? Heavy macOS terminal users with lots of long agent tasks: jump into beta and try it, the session-persistence claim is worth verifying by hand. Production main machine: wait for Linux and the first stable.

The close#

tmux has spent 20 years proving the multiplexing layer is a hard need, but its form still stops at “a shell script running inside your terminal.” Rex bets that this layer should grow natively into the terminal itself, and be the infrastructure of the agent era. Public testing started 10-05; hold the product judgment for now. What’s worth tracking is the ecosystem moves after “durable session” becomes a first-class feature.

How many times has a long task died on you mid-terminal? How long have you put up with tmux’s scrollback? Talk in the comments. Send this to the colleague still tmux attach-ing into the dark on production servers.

Frequently Asked Questions

Is Rex a Ghostty replacement?

No. Rex is a terminal multiplexer (the tmux/zellij category), but it's also a terminal app: sessions, splits, and persistence are built in. Ghostty stays non-profit, its roadmap unchanged.

Can I use it now?

macOS public testing is open (10-05). Waitlist via the Superlogical newsletter; no Linux date yet.

How does it differ from tmux?

tmux runs inside your existing terminal; Rex's outer layer IS the terminal, built on libghostty (the MIT library extracted from Ghostty). Native scrollback/selection/scrolling, no slow inner-emulator IO path.

Who's on the Superlogical team?

Mitchell Hashimoto (Ghostty author, HashiCorp co-founder), Jack Pearkes (HashiCorp's first employee, ex-VP Eng), Alasdair Monk (Poolside/Vercel/HashiCorp/Heroku), Hector Simpson (design).

What's next?

Officially: start with the terminal multiplexer, then a durable session layer spanning local dev, remote access, coding agents, background jobs, and multi-person shared terminals.
