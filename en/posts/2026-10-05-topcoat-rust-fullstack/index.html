Topcoat Makes Rust 'Full-Stack'? I Ran a 36-Line Version and Found the Argument Is All in the Wording

tokio-rs shipped Topcoat 0.10.0 to crates.io; the HN thread is 9 days old and still hot — the top comment calls it a DSL, 'a wrong pattern'. I built a 36-line minimal version on a 2-core EPYC: clean build 3m57s zero warnings, incremental 13.6s, real first frame returned. Once you run it, the dispute is mostly wording: $(...) is type-checked Rust, and the no-JS fallback goes Post/Redirect/Get.

October 5, 2026 · 5 min · 897 words · Dreambeast -  |  中文

tokio-rs pushed Topcoat 0.10.0 to crates.io on 10-03. The 113-point HN thread is still hot after nine days; the top comment: “this isn’t Rust, it’s a DSL, it’s a wrong pattern.” I didn’t read the comments. I followed the official hello-world path and stood up a 36-line minimal version on my 2-core EPYC slice: clean release build 3 minutes 57 seconds with zero warnings, a one-line change re-edited in 13.6 seconds, and 127.0.0.1:3000 really returned a Hello, World! first frame. The “wrong pattern” that’s been argued for nine days — run it once and the dispute turns out to be mostly wording, not fact. But whether “full-stack” is the right word to use, I want to pull apart.

This article covers three things: where the most natural misunderstanding is, what the 36 lines actually prove, and the three boundaries I list up front. Machine: AMD EPYC 9354P 2-core slice, rustc 1.99.0, topcoat 0.10.0, measured 2026-10-05, every number tied to a command you can re-run.

Where the most natural reading goes wrong#

Hear “Rust full-stack framework” and most people’s first reflex is front and back both in Rust, WASM isomorphism, like Leptos compiling one codebase into in-browser WASM. Topcoat is not that. It’s server-rendered: components evaluate on the server and render to HTML; the client receives not “a logic blob that runs independently in the browser” but server-issued patches, plus a few signal / shard from the runtime feature. WASM isomorphism and “the server sends patches” are two different routes; conflating them is where most of the thread’s argument comes from. One line to separate it from Leptos: Leptos compiles the UI logic into the browser to run; Topcoat keeps the UI’s source of truth on the server, and the browser just receives patches.

What the 36 lines actually prove#

Here’s the minimal version. Below is the exact main.rs I ran locally — it produced the real Hello, World! first frame, comments translated for readability (pure SSR, topcoat::start boots the server, zero hand-written JS):

use topcoat::{
    Result,
    router::{module_router, page},
    view::{View, component, view},
};

// Minimal reproducible path: pure server-side rendering, no browser runtime.
// Three steps to copy: cargo new myapp && cargo add topcoat && cargo add tokio --features "rt-multi-thread,macros"
#[tokio::main]
async fn main() {
    // module_router! derives pages / layouts / routes from the Rust module tree
    topcoat::start(module_router!().build()).await.unwrap();
}

#[page]
async fn home() -> Result<impl View> {
    Ok(view! {
        <!DOCTYPE html>
        <html>
            <head>
                <title>"LLM deployment site"</title>
                // dev server auto-reloads the browser on rebuild
                topcoat::dev::script()
            </head>
            <body>hello(name: "World")</body>
        </html>
    })
}

// Reusable component: the parameter is an ordinary Rust reference, rendered to an HTML fragment
#[component]
async fn hello(name: &str) -> Result<impl View> {
    Ok(view! {
        <h1>"Hello, "(name)"!"</h1>
    })
}

Three macros are the entire complexity: module_router! derives routes/pages/layout straight from the module tree, no hand-written #[get("/...")] needed; view! renders HTML with Rust interpolation. Measured:

Now to the “looks like a DSL” objection. The reactive part in the official examples is written like: let dark = signal(cx, \|\| false);. And the template’s $(...), @click, : — the official docs classify it as a “dual Rust/JavaScript expression language” — meaning what you write inside $(...) is a type-checked Rust expression, governed by rustc at compile time, not a string template, not runtime splicing. It feels “like a DSL” because it does pull some declarative syntax into view!; but under the hood it’s Rust values and types, not another language. That’s a wording problem, not a “wrong pattern”.

The most under-appreciated part is the no-JS fallback. The official alpine-ajax counter: if JS is present it takes the patch; if JS is absent it goes Post/Redirect/Get with a full re-render. The real code, both paths:

if ajax_request(cx) {
    return view! { cx => <span id="count">(count)</span> }
        .single().await?
        .into_response(cx);
}
see_other(href!(home).resolve(cx)).into_response(cx)  // no-JS fallback

This is the most weight-bearing part of “one language to the end”: the same component, client-instant with JS, traditional form without, the server is that same Rust either way — the logic doesn’t split.

Boundaries, listed up front, 3 items#

  1. 0.10 is still 0.x; the API will move, so be careful in production — don’t bet on “tokio official blessing = stable”.
  2. Reactivity is a separate topcoat-runtime (signal / expr / shard / procedure). The 36 lines above are a minimal pure SSR, it’s not included; in the README, “(More) reactivity” is still a todo — don’t treat reactivity as out-of-the-box.
  3. The “full-stack” boundary = server rendering + patches + optional runtime, not stuffing Rust into both front and back. Benchmarking it against Next.js-style isomorphism is the wrong lane.

Closing#

The word “full-stack”: what tokio is selling is “one language to the end” — the server is Rust, and what the client receives is still that same Rust’s values and logic, not “writing in two worlds”. 36 lines is enough to run the SSR mainline; turn on the runtime feature separately for reactivity; the 0.x maturity boundary goes up front.

Frequently Asked Questions

How does it relate to Leptos?

Both are Rust UI, different route: Leptos compiles to WASM and runs in the browser; Topcoat is server-rendered and hands the browser patches. The source of truth stays on the server.

Can I ship it to production?

0.10 is 0.x — fine for prototypes and internal use; hold off on external production until the API settles.

How much steeper than Axum?

The router/page/component macros add a layer over bare Axum but remove the hand-written routing glue. The SSR core is light; the reactive runtime is the heavy part.
