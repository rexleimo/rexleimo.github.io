PostgreSQL 19 Is Out: Stop Piling On Features, Make Non-Stop Operations the Default

PostgreSQL 19 shipped on November 19, 2026. REPACK CONCURRENTLY shrinks bloated tables online without locking reads or writes, pg_plan_advice fixes bad plans without touching application code, WAIT FOR LSN makes read-your-writes on replicas a native database feature, logical replication no longer needs a restart, and sequences now replicate too. An original breakdown for DBAs and backend developers.

November 20, 2026 · 6 min · 1142 words · DreamBeast Programming -  |  中文

On November 19, 2026, the PostgreSQL Global Development Group released PostgreSQL 19. This latest major version of “the world’s most advanced open source database” has a clear theme: as key workloads scale up, they should be easier to manage, safer to change without stopping, and more predictable to query. Below are the changes that actually affect day-to-day operations and development — my own reading of them, not a retelling of the release notes.

1. REPACK CONCURRENTLY: the beginning of the end for VACUUM FULL / CLUSTER#

Any database under sustained writes has to deal with bloat: a table getting frequent UPDATE / DELETE keeps piling up dead space, wasting disk and slowing queries.

The traditional remedies were VACUUM FULL and CLUSTER, and both share one painful trait: they take an exclusive lock, so application reads and writes are blocked for the whole operation. For a 7×24 system that is effectively a planned outage.

PG 19 introduces the REPACK command:

  • reclaim bloat;
  • optionally reorder table data by an index (the effect of CLUSTER);
  • and, crucially, REPACK (CONCURRENTLY) — it never blocks reads or writes.

The official line is that REPACK supersedes VACUUM FULL and CLUSTER, which stay for compatibility. For DBAs this is the most practical item in the release: slimming a big table no longer needs a 3 a.m. maintenance window.

2. Query plans stop drifting: pg_plan_advice + pg_stash_advice#

The planner is usually reliable. But change the data distribution and a good plan can turn slow overnight — that’s the root of plenty of “it was fine yesterday, so why the slow-query alert today?” incidents.

PG 19 ships an official answer:

  • pg_plan_advice provides a small “plan advice” language that can pin the plan choice for a specific query and let you experiment with alternatives;
  • pg_stash_advice stores those advices and applies them automatically to matching queries by query identifier.

The second one matters more: you can steer a misbehaving slow query back on track without touching a single line of application code. Plan stability goes from “pray the statistics hold” to something you can intervene on and persist — genuinely hard production work, now built in.

3. Read-your-writes on replicas: WAIT FOR LSN#

Split reads from writes and you’ve almost certainly hit this: the app writes a row on the primary, reads it straight back from a replica, misses it because of replication lag, and the user decides their data was lost.

PG 19 adds WAIT FOR LSN: a session on a standby can wait until replay has reached a specified LSN (WAL position) before executing the query. Write, capture the LSN, call WAIT FOR LSN before the read, and the just-written row is guaranteed to be visible.

That’s a database-native consistency guarantee — far more dependable than sleeping a few hundred milliseconds in the app and retrying.

4. Two old logical-replication headaches, solved together#

1) No restart just to turn on logical replication. Enabling it used to mean changing wal_level and restarting, which is painful in production. In PG 19, creating the first logical replication slot automatically raises the effective WAL level to logical; the new effective_wal_level parameter shows the actual current level at any time.

2) Sequences finally replicate. CREATE PUBLICATION ... FOR ALL SEQUENCES publishes sequence values, so you no longer hand-align auto-increment IDs at failover. CREATE PUBLICATION also gains an EXCEPT clause (exclude individual tables when publishing FOR ALL TABLES), CREATE SUBSCRIPTION can use a SERVER clause to pull connection parameters from a foreign server defined by postgres_fdw, and the new retain_dead_tuples option detects update-vs-concurrent-delete conflicts and logs them in pg_stat_subscription_stats.

5. Small wins developers will notice#

  • INSERT ... ON CONFLICT DO SELECT: RETURNING can now hand back the existing row on conflict, so the common “get or create” pattern saves a network round trip.
  • COPY can emit JSON: even a single JSON array, which makes exports and downstream feeds easier.
  • String methods for SQL/JSON path: lower(), upper(), replace(), split_part(), btrim() — less nested-function gymnastics for text inside JSON.
  • Window functions support IGNORE NULLS: lead() / lag() / first_value() / last_value() / nth_value() can skip NULLs, making “last non-null value” fills much simpler.
  • random() can generate random dates / timestamps within a range: one less step when seeding test data.

6. autovacuum and observability: a fuller dashboard#

PG 19 gives autovacuum parallel capability: it can use parallel workers to vacuum indexes, controlled by the new autovacuum_max_parallel_workers parameter. It also introduces a scoring system that decides which tables to handle first, with the score breakdown visible.

New monitoring views include:

  • pg_stat_lock: statistics by lock type;
  • pg_stat_recovery: recovery status;
  • pg_stat_autovacuum_scores: autovacuum priority scores per table.

EXPLAIN ANALYZE gains an IO option (also recorded by auto_explain) that reports asynchronous I/O activity; pg_stat_wal, EXPLAIN (ANALYZE, WAL) and vacuum/analyze logs now count how much WAL is written by full-page images. Troubleshooting I/O and WAL amplification finally has first-hand data behind it.

7. Performance and quiet changes in default behavior#

Some changes make programs faster without touching a line of SQL:

  • Foreign-key check optimization: bulk inserts were close to 2× faster in testing;
  • Optimizer improvements: NOT IN becomes a more efficient anti-join when there are no NULLs; eager aggregation before a join reduces the amount of data that participates in it;
  • Automatic scaling of asynchronous I/O: after PG 18 introduced async I/O, PG 19 automatically adjusts worker count between io_min_workers and io_max_workers under io_method = worker (the default) — these two parameters replace the old io_workers;
  • LISTEN / NOTIFY scalability for many channels also improves.

Several default value changes deserve a close look before upgrading:

  • JIT is off by default — the maintainers say the old cost estimate for deciding when to enable JIT wasn’t reliable; analysts running lots of queries can turn it back on;
  • when built with LZ4 support, TOAST defaults to lz4 compression;
  • the new password_expiration_warning_threshold warns ahead of password expiry;
  • new server-side SNI support (map hostnames to different certificates via pg_hosts.conf);
  • md5 authentication now emits a deprecation warning after success (deprecated in PG 18, slated for removal — switch to SCRAM), and RADIUS authentication has been removed.

Wrapping up#

Compress PG 19 into one sentence: it turns “online, non-interrupting, intervenable” from an advanced trick into something the database ships with — slim a big table without locking it (REPACK CONCURRENTLY), fix a bad plan without changing code (pg_plan_advice), read your own writes under read/write splitting (WAIT FOR LSN), and enable logical replication without a restart.

Before upgrading, check the default changes: JIT off, TOAST compression on LZ4, RADIUS removed, and io_workers replaced by the new parameters. The full list is in the official Release Notes.

This is a technical reading based on the official announcement. For exact parameters and behavior, refer to the PostgreSQL 19 documentation (https://www.postgresql.org/docs/19/release-19.html) External link .

Frequently Asked Questions

What is the single most useful change for DBAs in PG 19?

REPACK CONCURRENTLY: reclaim bloat from a large table and optionally reorder it by an index, all without blocking reads or writes, replacing VACUUM FULL and CLUSTER which take an exclusive lock.

How do I fix stale reads after a write on a read replica?

The new WAIT FOR LSN command lets a standby session wait until replay reaches a given LSN before running the query. Write, keep the LSN, wait for it before the read, and you get read-your-writes.

Which default changes should I check before upgrading?

JIT is now off by default, TOAST defaults to lz4 compression when built with LZ4 support, RADIUS authentication has been removed, io_workers is replaced by io_min_workers / io_max_workers, and md5 auth now emits a deprecation warning.
