Thread 1 · rust-analyzer performance

Hook: a small Rust app can trigger a dependency-scale analysis job.

1/6
Your 8,000-line Rust app may be the smallest thing rust-analyzer is analyzing. In one fd run: 8,273 lines of app code 2.5M lines of dependencies 1.4 GB peak memory The dependency graph is the real workload. 🧵 #Rust #rustanalyzer
Download cover
2/6
This is not a claim about every project. It is a local analysis-stats measurement on Windows + MSVC with rust-analyzer v0.3.2997. Batch analysis is not the same as interactive LSP latency inside VS Code. Treat the numbers as a scale signal, not a promise.
Download image
3/6
Level 1: narrow the default work. cachePriming=false check.workspace=false Keep checkOnSave enabled. You trade instant cross-workspace errors for a faster current-crate loop.
4/6
Level 2: cargo-subspace. It wires rust-analyzer.workspace.discoverConfig to cargo-subspace discover and overrides checks for the saved file. Unloaded dependents will not appear in references or rename. That is the trade-off for a lazy project model.
5/6
Level 3 is the sharp knife: buildScripts.enable=false procMacro.enable=false Use it only when measurements point to build.rs or proc macros. Macro expansion and generated configuration can disappear.

The practical order: 1. Update rust-analyzer. 2. Measure cold start + save diagnostics. 3. Change one level. 4. Re-measure. Follow 梦兽编程 for measured Rust tooling notes, not cargo folklore. #RustTools #buildinpublic

Thread 2 · Rust debugging in VS Code

Hook: F5 is the last button in a three-layer compatibility chain.

1/6
F5 is not a Rust debugger. It is the final button on a 3-layer chain: Rust/MSVC toolchain → PDB → LLDB → CodeLLDB → launch.json. Break one link and VS Code says “No debugger found.” 🧵 #Rust #VSCode #CodeLLDB
Download cover
2/6
On Windows MSVC, rustup does not provide an applicable rust-lldb component. That does not mean “LLDB can never run on Windows.” It means this rustup path is the wrong one for the target. Start with CodeLLDB and verify the actual debugger build.
3/6
Install CodeLLDB and point program at the binary: target/debug/debug-demo.exe Not src/main.rs. Run cargo build first. On Linux/macOS, use the actual binary name; usually there is no .exe.
Download image
4/6
The launch.json fields that matter first: type: lldb request: launch program: target/debug/<binary> args: [...] cwd: workspace root Get these right before tuning terminal or stopOnEntry.
5/6
A conditional breakpoint turns 10 manual Continues into one condition: i == 5 At the stop: i = 5 orders.len = 5 order.total = 53.5 That is the debugger showing program state, not a guess from logs.
