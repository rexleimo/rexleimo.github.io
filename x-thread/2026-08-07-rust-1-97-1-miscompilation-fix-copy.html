1/9
升级 Rust 之后，程序在 -O 优化构建下莫名段错误，换成 debug 构建又一切正常？ 先别急着怪自己——这次大概率是编译器错了。 7 月 16 日，Rust 紧急发布 1.97.1，修复一个潜伏已久的 LLVM 误编译。 🧵
2/9
时间线非常紧凑： 7 月 9 日：Rust 1.97.0 发布，当天就有人报了 issue #159035——"segfault on Rust 1.97.0"。 一个嵌套枚举的 match，传入 None，理论上应该打印 None 正常退出，结果直接段错误。
3/9
根因有两层，缺一不可。 第一层：1.97.0 合入 PR #155850，调整了 Option 判别式的存储编码——None 的 tag 从 2 改成 -1。 单独看没问题，编译器会把存储值再映射回逻辑判别式，对外行为不变。
4/9
第二层：LLVM x86 后端的 trunc nuw 误优化。 IR 里有这么一条指令： %1 = trunc nuw i64 %0 to i1 tag = -1（全 1 位）时 nuw 约定被打破，产生 poison。LLVM 19 时代编译成 and ecx, 1（安全）；LLVM 20 之后变成 mov ecx, ecx——一条看似多余、实则致命的指令。
5/9
影响范围： - 只有 x86/x64 受影响，aarch64/riscv64gc 实测正常 - 底层 bug 从 1.87（LLVM 20）就存在，1.97.0 的改动大幅提高触发概率 - 触发条件刁钻：多 payload 字段的枚举 + match + 优化构建 不是所有程序都会踩中，踩中就是硬崩溃。
6/9
我直接在 Windows x64 / MSVC 上跑了一遍官方最小复现： rustc 1.97.0 -O → Segmentation fault（exit 139） rustc 1.97.1 -O → 正常 rustc 1.96.1 -O → 正常（Windows 上未复现） 注意：1.96.1 在 Linux 上有报告复现——误编译不保证稳定复现，这正是它最可怕的地方。
7/9
怎么确认自己有没有中招： rustc --version 还在 1.97.0？别犹豫： rustup update stable 之前出现过"优化就崩、debug 就好"的项目，升级后重点回归： cargo test --release
8/9
这次事件最反直觉的启示： Rust 的内存安全保证，挡不住编译器自己的 bug。 Rust 能保证你的代码不越界、不悬垂——前提是编译器生成的机器码是正确的。优化 pass 出错时，内存安全就变成了"在错误内存上的安全操作"。
