Codex 总是做到一半就忘记前面的代码？ 我在 Codex CLI 0.146.0 上做了一次上下文窗口实验：把 GPT-5.6-Sol 的本地模型元数据从 272K 调整到 372K。 先说结论：这不是模型升级，也不是无限上下文。 🧵
2/8
当前默认值大致是： context_window: 272000 max_context_window: 272000 effective: 95% 所以有效窗口约为： 272000 × 95% = 258400
3/8
实验配置： context_window: 372000 max_context_window: 372000 effective: 95% 计算结果： 372000 × 95% = 353400 但这只是 Codex 客户端计算出的有效预算。
4/8
最容易误解的地方： 本地模型元数据变大，不代表服务端真的支持 372K。 客户端显示 353400，只能证明本地配置被读取；服务端是否接受这么大的请求，要用真实长任务验证。
5/8
它可能帮助： - 更晚触发上下文压缩 - 大型代码仓库分析 - 长日志排查 - 长时间运行的 Agent 任务 它不会改变模型的推理能力，也不会增加跨任务永久记忆。
6/8
验证不能只看配置文件。 codex debug models 只能证明本地模型目录被读取。还要用同一个项目、同一个任务做对照测试，观察： - 第一次压缩轮次 - 最大 token 使用量 - context length exceeded - 任务耗时和输出质量
7/8
如果服务端真实上限更低，可能出现： - 请求被拒绝 - 上下文被截断 - 任务中途失败 - 延迟和消耗增加 所以一定要先备份，并使用非敏感项目测试。报错就回滚，不要继续把数字往上改。
